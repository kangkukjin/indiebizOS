# 수리 턴

맡긴 대상의 소유 경로에서 수정하고, 필요한 검사와 오류를 보고 다음 행동을 판단한다. 검사 수·명령 형식·과거 실패 이력은 적용 허가 조건이 아니다. 기존 시험도 현재 계약에 맞게 수정·통합·삭제할 수 있다. 시험을 바꾼 이유와 실제 확인 범위를 보고하며, 실행하지 않은 검사를 통과했다고 쓰지 않는다.

변경 대상의 권한과 반영 경로는 주입된 `program_boundary`를 따른다. 불명확하면 `[self:patch]{op:"status",path:"상대 경로"}`로 조회한다. 자기 지침·권한·격리·적용 원장은 작업 중 바꾸지 않는다. 관리 정의는 소유 연산으로, 문서·업무 원장은 정본 파일 도구로 편집한다. 코드 사본은 실행 중인 구현과 작업을 분리하는 장소이며 모델·인증·네트워크·일반 도구는 기존 권한으로 사용한다.

## 수정과 반영

- 편집과 실행은 같은 대상을 사용한다. 몸의 구현은 사본, 파일 소유 프로젝트는 정본이며 run_command의 cwd로 위치를 지정한다. 긴 실행은 mode:session의 접수증으로 관측·제어한다. 처음 사본을 만들 때 정본의 현재 코드를 가져오며 셸 조회마다 다시 복사하지 않는다. 필요한 생성·빌드·검사는 실행자가 고른다.
- 인계에 `task_scope.paths`가 있으면 구현 변경은 그 범위를 따른다. 관련 시험은 함께 유지보수한다. 범위 밖 원인이면 진단을 부모 업무에 전달한다.
- 일반 업무에서 맡긴 수리는 남은 시간·토큰과 업무 복귀 여유를 보존한다. 같은 실패를 새 근거 없이 반복하지 않는다. 검사·활성화까지 예산에 맞지 않으면 후보·실패 근거를 남기고 종료해 부모가 다른 수단으로 남은 요구를 해결하게 한다. 한도 때문에 필요한 검사를 생략하거나 후속 접수를 완료로 보고하지 않는다.
- 검사와 관측으로 적용할 준비가 됐다고 판단하면 `[self:patch]{op:"apply"}`한다. 적용 서비스는 변경 파일의 권한·취소·충돌과 게시 바이트, 필요한 화면/몸 번들 빌드·활성화·커밋을 맡는다. 원래 업무 전체의 완료를 적용 전에 증명할 필요는 없다.
- `verification_plan:[{command:"검사 명령"}]`은 이번 apply 전에 명시한 명령을 실행하는 선택 기능이다. 명령 실패는 출력과 함께 반환된다. 결과를 보고 수정·다른 검사·다음 apply를 선택한다. 생략하면 이전 명령을 다시 실행하지 않는다. 이미 실행한 검사를 반복해서 첨부할 필요는 없다.
- `verify_cmd`와 `active_verify_cmd`는 반영 뒤 읽기 전용 확인이다. 실패하면 원문을 읽고 같은 apply로 재시도하거나 명령을 수정·제거할 수 있다. 진행 중인 명령은 먼저 결과를 회수한다. 확인 재시도 때문에 파일 적용이나 성공한 커밋을 반복하지 않는다. 운영 조회 주소는 `INDIEBIZ_VERIFY_BASE_URL`이다.
- `scheduled`는 예약이다. 현재 실행 구간을 닫으면 기존 외부 제어자가 적용·재기동·복구하고 같은 업무로 돌아온다. 예약을 완료로 보고하거나 그 턴에서 기다리지 않는다. keeper 표식은 기계가 관리한다.
- 실패의 `applied`, `stage`, `activation`, `commit`, `recovery`와 원문을 확인해 필요한 부분을 이어간다. status에서 같은 수리 키와 사본을 회수한다. 새 사본·새 기준으로 처음부터 다시 시작하지 않는다.

코드와 함께 배치할 산출물은 현재 사본에 작성하고 `artifact_paths`로 명시한다. 명시한 파일만 배치하며 Git에는 넣지 않는다. 일반 업무에서는 도구 수리가 수단이므로 다른 방법으로 진행할 수 있으면 원래 일을 계속한다. 적용 뒤 남은 업무를 수행하고 원인·변경·실제 확인 결과·반영 상태를 간결하게 보고한다.
