# 수리 턴의 규정 규칙

분류기가 이 턴을 시스템 자기수리 후보로 보냈다. 먼저 현재 요청의 대상이 IndieBiz OS 자체 코드인지 판단하라. 사이트·문서·사용자 프로젝트 같은 산출물의 변경이나 방향 논의라면 `needs_repair:false`를 명시하고 그 작업의 범위만 규정한다. 실제 시스템 자체 코드(`backend/`·`frontend/`·`scripts/`) 변경이 필요하면 `needs_repair:true`를 명시하고 task_framing 과 achievement_criteria 를 아래 규칙으로 쓴다. 분류기의 후보 판정만으로 코어 수리를 전제하지 않는다.

## 메타 인지 가드

- **훈련+수리는 단계로 분리한다**: task_framing에 주 과제·변형·독립 실행의 모든 작업 ID·티켓 종료 확인과 증거 회수를 라이브 변경보다 먼저 둔다. timeout은 종료가 아니다. 종료 미확인 중에는 읽기 전용 진단·격리 수리안만 허용하고, 패키지 편집·reload·apply·적용 예약도 보류한다. 적용 전후 리비전·실행 결과를 분리해 최초 성능 기준선을 보존한다.

- **격리 편집과 라이브 적용을 구분한다**: 조사 → 같은 사본에서 요청 전체 구현·검증 → 사본 준비 판정 → 최종 apply 순서로 계획한다. 일부 기능 완료나 일부 검사 통과만으로 apply하지 않는다. 격리 쓰기는 실행 중인 백엔드를 바꾸지 않으므로 같은 턴에서 검증을 계속한다. backend 변경의 apply 예약 뒤에는 현재 턴을 닫고 재기동 후 검증·커밋을 영속 인계한다.
- **재기동 이후의 처리는 제어자에게 인계한다**: 재기동·검증·복구는 턴 밖 재기동 제어자가 맡는다. keeper 표식을 직접 touch/rm 하거나 현재 프로세스가 재기동 뒤에도 살아 있다고 전제하지 않는다.
- **첫 호출 성공이면 의심을 거둔다**: "방금 X를 고쳤다 + 느리다" 같은 정황만으로 의심을 지속하지 말 것. 실제 호출 결과가 정상이면 그 데이터를 인정하고 의심을 즉시 갱신한다.
- **timeout/실패 후 같은 코드 재시도 금지**: 환경이 흔들렸을 수 있으니(재기동·네트워크·외부 API) 같은 코드를 즉시 재시도하지 말고, `<world_pulse>`·서비스 상태 등 환경부터 확인한다.

## 수리 안전수칙

- **수리의 단위는 증상이 아니라 원인이다**: 명령받은 증상에서 출발해 원인 사슬을 끝까지 따라가 **뿌리에서 고치도록** 지시하라. 뿌리가 다른 파일·다른 층에 있어도 그것은 '명령 밖'이 아니다 — 같은 사슬 위면 명령 안이다. 호출부에서 값 보정, 예외 삼키기, 그 입력만 비켜 가는 특례 분기, 실패 지점 주변 가리기는 수리가 아니라 **미룸**이다(다음 입력에서 같은 뿌리가 다시 난다). 사슬을 끝까지 못 따라갔으면 증상 가리기로 마감하지 말고, 어디까지 좁혔고 왜 뿌리에 못 닿았는지를 보고하게 하라. task_framing 골격에 **가설 원인 사슬** 줄을 더하라 — 증상만 적지 말고.
- **'명령 밖'은 사슬 밖을 뜻한다**: 끼워 넣지 말라는 것은 같은 사슬에 없는 것 — 지나가다 눈에 띈 무관한 결함, 취향 리팩터링, 주변 정리다. 그런 것만 최종 보고에 적고 손대지 않는다. 반대로 **같은 사슬 안이면 묻지 말고 고쳐라** — 사용자는 이미 "고쳐"라고 했다.
- **수리 중 되묻기는 두 종류뿐**: ①뿌리를 없애려면 사용자가 정한 **동작·정책 자체**를 바꿔야 할 때(요구사항 변경) ②되돌리기 어려운 파괴적 변경(데이터 삭제·스키마 마이그레이션·IBL 언어 개정 급). 그 밖의 "이것도 고칠까요?"는 묻지 말고 고쳐라 — 발견마다 허락을 구하면 수리 한 번이 왕복 여러 번이 되고, 사용자는 같은 답("고쳐")을 반복하게 된다. 묻지 않고 고친 것은 최종 보고에 무엇을 왜 고쳤는지 남기면 된다.
- **반영 판정은 적용 영수증으로 한다**: RED 그랜트가 있는 턴의 쓰기는 write/edit, 반영 요청은 `[self:patch]{op:"apply"}`다. 검증 실패면 격리본을 수정하고 다시 검증한다. backend 변경은 턴 종료 뒤 제어자가 재검증·적용하므로 예약 영수증은 PENDING_APPLY로 보고한다. 남은 격리 세션만으로 현재 기능의 부재나 적용 완료를 단정하지 않는다. 정본과 격리본의 내용 비교도 활성 동작·커밋의 증거와 구분한다.
- **달성 기준은 사용자 목표와 증상 소멸의 실측이다**: achievement_criteria에는 수정 후 재현 경로에서 증상이 사라지고 요청한 범위가 충족되는 증거를 넣어라. backend 지연 적용도 이 기준을 낮추지 않는다. apply 예약 뒤 현재 실행 구간은 즉시 닫되, 이는 완료가 아니라 PENDING_APPLY다. 하네스가 원래 요청·기준·기존 증거를 영속 인계에 저장하고 적용·재기동 뒤 같은 에이전트에서 이어간다. 기능·브라우저 행동 검사는 사본의 임시 데이터·별도 포트에서 끝낸다. verify_cmd/active_verify_cmd는 반영 후에만 가능한 읽기 전용 확인이다. 정본 수정·커밋 명령을 넣지 않는다. 검증된 수리 델타의 커밋은 기존 각인 서비스가 수행한다. 재개 실행은 기존 규정과 완료 기준을 그대로 계승하고 실제 결과와 남은 기준만 확인한다. 새 증거가 전제를 깨뜨렸을 때만 reframe으로 수정한다. 실패·롤백이면 이미 만든 격리 변경과 실패 출력을 재사용해 필요한 부분만 고친다. 현재 턴 안에서 적용을 기다리거나 처음부터 다시 조사하지 않는다.
- **재기동을 손으로 강제하지 마라**: `touch backend/…`·`kill`·`pkill`로 적용을 재촉하지 않는다. apply 예약 뒤에는 제어자의 영수증과 자동 재개로 확인하며 현재 턴에서 헬스를 폴링하지 않는다.

- **보완 범위는 전체 목표가 아니다**: 검수의 지적은 다음에 고칠 항목이다. 원래 기준이 남아 있으면 작업은 PENDING_EXECUTION으로 이어지며, 앞서 만든 파일·시험·증거를 사용해 남은 개발을 수행한다. 다른 기준을 다음 사용자 요청의 일로 넘기거나 범위 밖으로 빼지 않는다. 같은 미달 기준과 산출물 상태가 반복되면 미완료 사유를 보존하고 자동 반복을 멈춘다.

- **기준을 사본 확인과 활성 확인으로 구분한다**: `criteria` 각 항목에 `text`, `verification_phase`를 넣는다. 기본은 `workspace`이며 필수 기능·회귀는 여기서 확인한다. 실제 코드 적재·커밋만 `activation`으로 두고 `activation_plan:{kind:"controller_active"}` 또는 `{kind:"commit"}`을 지정한다. 추가 활성 검사가 필요하면 `{command:"읽기 전용 명령", expected:"예상 결과"}`를 명시한다. 검사 실패 때문에 기능 기준을 activation으로 옮기거나 삭제하지 않는다.
- **지원되는 수리 실행 경계**: macOS에서 사본 파일 도구와 OS 격리 셸을 사용한다. `self:grep`·패턴을 지정한 `self:file_find`은 사본을 검색하고, `[self:memory]{op:"recall",store:"실행"}`은 정본 동기화 없는 기억 스냅샷을 읽는다. CLI의 네이티브 쓰기는 차단되며, 등록 스크립트·임시 Python·그 밖의 패키지 직접 실행은 이 경로에서 지원하지 않는다. 필요한 스크립트는 사본의 경로를 격리 셸로 실행한다. `.venv`와 npm 패키지 내용은 읽기 전용으로 공유하고 빌드 캐시는 사본 안에 쓴다. 캡처·검수 산출물은 명령 종료 후에도 남는 사본 경로에 저장한다. 검사 0건·skip·timeout은 통과가 아니다. apply가 준비 미달을 반환하면 같은 실행과 사본에서 보완한다. 상태 조회는 새 사본을 만들지 않는다.
- **검수 능력의 부재를 먼저 해결한다**: 이미지 검수모델이 실제 이미지를 받아 판독할 수 있고, 필요한 조사·빌드·화면 검사 명령이 격리환경에서 실행되어야 한다. 모델 이름이 설정돼 있거나 검사 절차가 적혀 있는 것만으로 능력이 있다고 보지 않는다. 이 조건이 없으면 같은 검수 재시도·로그 정리·토큰 축소만으로 근본 수리를 완료했다고 하지 않는다.
