# 어휘·스크립트·관용구 변경

반복되는 변경 절차는 `[fn:능력변경완료]{요청:{...}}`로 묶는다. 본문과 검증할 동작은
작성자가 지정하며, 계획·충돌 확인·공식 관리 연산·새 호출 검사·필요한 각인을 연결한다.
새 어휘를 추가하지 않는다. 등록 스크립트 `능력변경`이 보통 IBL 프로그램을 만들고
기존 `self:workflow`, `self:script`, `self:patch`, `self:body`가 자기 쓰기를 수행한다.

## 관용구 추가·수정·은퇴

```ibl
#!ibl edition=2
[fn:능력변경완료]{요청:{
  kind:"idiom",operation:"add",target:"배수합",
  code:"[def:배수합]($목록,$배수=2){return sum($목록)*$배수}",
  description:"목록 합계에 배수를 곱한다",
  probes:[{code:"[fn:배수합]{목록:[1,2,3],배수:3}",expected:18}]
}}
```

개정은 `operation:"update"`와 새 `code`, 은퇴는 `operation:"remove"`와 `target`이다.
`expected_revision`을 지정하면 조회한 판본과 달라졌을 때 계획부터 거절한다.
생략해도 계획 당시 판본이 실제 저장·삭제의 조건이 된다. 호출자를 깨뜨리는 변경은
기존 원장의 소비자 검사에서 거절한다. 함수 원장 변경에는 빌드·Git·재기동이 붙지 않는다.
배포 `.ibl`까지 바꾸는 경우에는 배포 소스도 별도로 편집하고 기존 코드 적용 경로를 사용한다.

## 스크립트 추가·수정·해제

본문을 `data/scripts/`에 준비하고 요청에 `kind:"script"`, `source:"data/scripts/파일.py"`를
지정한다. `registration`에는 `interpreter`, `timeout`, `callable_contract`를 넣을 수 있다.
`probes`의 `code`는 `[self:script]{id:"등록명",args:{...}}`이며 `expected`에는 실제 기대 JSON 값을 준다.
새 등록·계약 수정 직후의 검사는 새 프로그램으로 컴파일하므로 이전 고정 판본을 검증하지 않는다.

`update`에서 생략한 등록 설정은 유지한다. 파이썬 구문, 선언 계약, 본문 SHA-256,
등록 판본, 저장된 호출자의 계약을 확인한다. 파일을 준비한 뒤 계획을 만들고 실행한다.
공유 모듈·교재도 같이 바꿨다면 `files:["data/scripts/공유.py", ...]`로 명시한다.
`files`는 이 요청이 검사·각인할 파일이며 다른 작업의 변경을 넣지 않는다.

`remove`는 등록만 해제한다. 본문·실행 상태·로그는 보존한다. 정적 호출자가 남으면
먼저 전환하도록 위치를 반환한다. 동적 ID, 외부 Python 호출은 완전 탐지했다고 주장하지 않는다.
직접 `self:script register/remove`를 사용해도 잠금·조건부 갱신·호출자 보호는 동일하게 적용된다.

수리 사본에서는 기존 `self:patch apply`가 반영·활성화·각인을 맡는다. 일반 정본에서는
해당 등록부와 명시 소스만 `self:body commit`으로 각인한다. 다른 스크립트의 미커밋 등록
변경이 섞이면 커밋을 멈춘다. Git 저장소를 사용할 수 없으면 `source_change.completed:false`다.

## 어휘 추가·수정·제거

[어휘 체크리스트](new_action_checklist.md)에 따라 선언·구현·교재를 기존 편집 경로로 준비한다.
요청은 `kind:"action"`, `target:"node:action"`, `operation`, `files`와 `probes`다.
`files` 생략 시 그 어휘의 소유 패키지 또는 코어 노드 선언에서 변경 파일을 모은다.
패키지 밖 가이드·공유 구현·새 패키지의 파일은 명시한다. 기존 어휘 빌더를 실행하고,
빌드된 목표 상태를 대조한 뒤 기존 자기수리의 적용·활성 확인·각인에 위임한다.

`apply` 객체는 현재 수리의 `verification_plan`, `verify_cmd`, `active_verify_cmd`만 전달한다.
원래 사용자 목표의 검사 ID·완료 조건을 보존해야 하며, 일반 검사 하나로 바꾸지 않는다.
이미 준비된 검증 계획은 생략하면 기존 소유자가 사용한다. 허용된 수리 문맥 없이 새 권한을 만들지 않는다.
잠든 패키지를 자동 활성화하지 않는다. 제거는 저장 호출자를 먼저 전환한다.

`self:patch`가 적용을 예약하면 `complete:false`와 원래 영수증을 반환하고 턴을 닫는다.
기존 외부 제어자가 재기동 뒤 이어 간다. 이 프로그램 안에서 기다리거나 후보 사본의 성공을
정본 활성화 성공으로 바꾸지 않는다. 적용 직후에는 빌드 후보의 어휘 지문도 대조한다.

## 계획 조회·부분 재개·묶음

계획만 받으려면 다음처럼 쓴다. `plan`은 새 상태 DB가 아니라 기존 실행 기록의 반환값이다.

```ibl
#!ibl edition=2
$준비 = [self:script]{id:"능력변경",args:{op:"plan",request:$요청}}
$반영 = [self:workflow]{op:"run",edition:2,pipeline:$준비.program}
return $반영.value
```

`inputs`에 `요청` 객체를 전달한다. 계획의 `impact`는 정적으로 확인한 호출 위치와 `unknown`을
분리한다. 관용구 저장 시의 최종 소비자 보호는 기존 컴파일러·원장이 수행한다.
여러 변경은 `request:{changes:[요청1,요청2,...]}`로 묶는다. 관용구의 명시 참조를 읽어
새 부품→호출자, 제거 시 호출자→부품 순서로 실행한다. 묶음은 원자 트랜잭션이 아니며
성공한 앞 항목은 유지된다. 순환 의존은 기존 묶음 게시 또는 새 이름 이행으로 해결한다.

연결이 끊겼다면 같은 코드·입력과 기존 `resume` 영수증으로 상태를 회수한다.
`resume`은 확인된 실패도 복원하므로 실패한 검사를 몰래 재실행하지 않는다.
관용구·스크립트가 이미 반영됐고 후속 검사만 보완할 때에는 `op:"status",plan:$준비.plan`으로
먼저 대조한다. 이어 `op:"verify",plan:$준비.plan,probes:[다시 실행할 검사]`가 반환한 `program`을
실행한다. 이 경로는 등록·삭제를 반복하지 않고 상태 확인·명시 검사·남은 각인만 한다.
`probes`는 반드시 직접 고른다. 이미 성공했거나 결과가 불명인 외부 쓰기를 재실행 목록에 넣지 않는다.
어휘 적용의 재개는 기존 `self:patch` 영수증의 `recovery`를 따른다.

## 결과와 검증 범위

- `complete`: 저장 상태·필요한 소스 각인과 명시 동작 검사를 모두 통과했는지. 추가·수정에서
  `probes`가 없으면 등록은 가능하나 `complete:false`다. 제거는 부재 확인으로 판정한다.
- `observed`: 실제 판본·대상·코드/함수 원장 범위·요청 상태 일치 여부.
- `behavior_verified`, `verified_probes`: 이번 새 호출의 검증 여부·개수. 단순 목록 조회는 동작 검증이 아니다.
- `source_change`: 커밋 또는 기존 자기수리 영수증. 적용 예약·각인 실패는 완료가 아니다.

어휘의 빌드·교재 검토와 영향 기반 회귀는 기존 관문을 따른다. 필요하면
`.venv/bin/python data/scripts/capability_change.py --check-worktree`로 현재 변경의
기존 시험 선택기·빌드 신선도·층 검사를 연결한다. 긴 검사는 기존 배경 작업 방식으로 실행한다.
본문·설명·용례의 의미를 자동으로 만들어 맞다고 판정하지 않는다. 새 정의는 기존 원장 검색에서
발견되며, 필요 없는 합성 용례·상시 소개를 추가하지 않는다. 아직 전후 시간·전체 토큰 절감률은 측정하지 않았다.
