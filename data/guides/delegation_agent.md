# 프로젝트 에이전트 위임 가이드

프로젝트 내 동료 에이전트에게 작업을 위임하는 방법입니다.

## 기본 도구

```
# 동료 에이전트에게 위임 (기본: 같은 프로젝트, 비동기, 결과 자동 보고)
[others:delegate]{agent_id: "에이전트이름", message: "작업 내용"}

# 프로젝트·에이전트 조회 (agent_id 생략 시 전체 목록, 지정 시 단건 상세)
[others:agents]
[others:agents]{agent_id: "에이전트이름"}
```

## 위임 모드 (mode)

`[others:delegate]`는 mode 파라미터로 동작이 갈립니다. 기본은 `async`.

| mode | 동작 | 언제 |
|---|---|---|
| `async` (기본) | 접수증(`task_ref`·`child_task_id`) 반환, 결과는 자동 보고 체인으로 나중에 도착 | 일반적인 위임 |
| `sync` | 같은 접수 뒤 그 작업을 제한 시간 동안 기다려 `response`(결과 전문) 반환. 시간 초과면 실패로 바꾸지 않고 `task_ref`·`state` 반환, 결과는 비동기 보고로 도착 | 파이프라인 `>>` 안에서 결과를 다음 단계로 넘길 때 |
| `workflow` | `do`/`steps`의 확정 IBL을 대상 에이전트의 기존 큐에서 직접 실행. 원문·판본·입력 보존, AI 재해석 없음 (같은 프로젝트 전용) | 다른 에이전트의 도구/권한으로 파이프라인을 실행할 때 |

`async`와 `sync` 두 모드는 '기다리는가'만 다르다 — 접수·실행(상주 러너)·결과 저장은 같다(2026-10-05, 임시 실행기 은퇴).
대상 에이전트가 실행 중이어야 한다(sync 도 같다). 순환 위임(대상이 조상 사슬에 있음, 자기 자신 포함)은 접수가 거절된다.

```
# 동기 (파이프라인용)
[sense:search]{source: "gnews", query: "AI"} >> [others:delegate]{mode: "sync", agent_id: "투자/투자컨설팅", message: "투자 관점 분석"}

# 파이프라인 위임
[others:delegate]{mode:"workflow", agent_id:"기획", do:"return $값", edition:2, inputs:{값:7}}
```

`workflow`도 접수증을 먼저 반환한다. 같은 `task_ref`로 완료·실패·원 실행의 영수증을 조회한다.
`message`는 기록용 설명이다. 입력은 `inputs`로 주며 설명 문장을 실행 지시로 해석하지 않는다.
권한은 호출자·요청 제한·대상 에이전트의 교집합이다. 코드 실행에 채팅창 연결은 필요 없다.
코드 안에서 판단이 필요하면 `others:delegate`의 자연어 위임을 명시한다. 그 결과를 코드에서
써야 하면 `mode:"sync"`로 기다리고, 명시 `async`의 자식은 반환된 접수증으로 별도 조회한다.
자식 완료 보고가 원 프로그램을 다시 실행하거나 대상 AI의 새 턴을 만들지는 않는다.
헤더 없는 원문은 호출한 IBL의 판본에 고정하며 명시 edition과 헤더의 충돌은 거절한다.
기존 단계 배열은 판본 1로 실행하며 `edition:2`·`inputs`를 함께 쓸 수 없다.

## 위임 범위 (scope)

| scope | 동작 | 권한 |
|---|---|---|
| `same` (기본) | 같은 프로젝트 동료 에이전트에게 위임 | 모든 에이전트 |
| `cross` | **타 프로젝트** 에이전트에게 위임 (필요 시 프로젝트 자동 활성화) | **시스템 AI 전용** |

```
# 타 프로젝트로 위임 (시스템 AI만)
[others:delegate]{scope: "cross", agent_id: "의료/내과", message: "두통 분석"}
```

## 핵심 원칙

### 1. 자신이 할 수 있으면 직접 하세요
불필요한 위임은 금지. 자신의 도구로 처리 가능하면 직접 처리하세요.

### 2. 동료 확인
환경 프롬프트의 `<peers>` 섹션에서 동료 에이전트 이름과 역할을 확인하세요.
- `<peers>`에 동료가 없으면 위임 불가
- 에이전트 이름은 `<peers>`에 표시된 **그대로** 사용 (오타, 접미사 변경 금지)
- 자기 자신에게 위임 금지

### 3. 의도를 전달하고, 실행 방법은 맡겨라
판단을 맡길 때는 자연어 `message`로 의도와 목적을 전달하세요. 실행 절차가 이미 확정되었다면 `mode:"workflow"`로 코드를 전달하세요.

### 4. 비동기 처리
위임은 비동기로 처리됩니다. 결과는 자동으로 보고됩니다.

## 병렬 위임

서로 의존성이 없는 작업은 동시에 위임 가능:
```
[others:delegate]{agent_id: "내과", message: "두통 증상 분석"}
[others:delegate]{agent_id: "외과", message: "무릎 통증 검사 의뢰"}
```

## 순차 위임

이전 결과가 필요한 경우 **반드시 순차적으로** 위임하세요:

1. TODO로 전체 계획 작성 (두 번째 작업은 pending 상태로)
2. 첫 번째 위임만 실행
3. **실제 결과가 도착할 때까지 대기** (다음 위임 보류)
4. 결과 도착 후 TODO 업데이트하고 두 번째 위임 실행

**중요**: `[others:delegate]`가 반환하는 "위임했습니다"는 **접수 확인**일 뿐입니다.

**절대 금지:**
- 결과를 받지 않은 상태에서 "검토했습니다", "확인했습니다" 등의 표현 사용
- 위임 접수 확인만 받고 마치 결과를 받은 것처럼 행동
- 실제 결과 없이 다음 단계 작업을 위임

```
# ❌ 잘못된 예
[others:delegate]{agent_id: "내과", message: "혈압 측정해줘"}
[others:delegate]{agent_id: "내과", message: "결과 확인했습니다. 약 처방해줘"}  # 결과 없음!

# ✅ 올바른 예
[others:delegate]{agent_id: "내과", message: "혈압 측정해줘"}
# → 여기서 멈추고 실제 결과 대기 → 결과 도착 후 다음 위임
```

## 파일 경로 원칙

파일 위치를 보고할 때는 **반드시 절대경로**를 사용하세요.

```
# ❌ "결과 파일: outputs/result.txt"
# ✅ "결과 파일: /Users/.../projects/프로젝트명/outputs/result.txt"
```

## 스테이트리스 원칙

위임받는 에이전트는 **스테이트리스** 상태입니다. 이전 작업을 기억하지 못합니다.

위임 메시지에는 작업에 필요한 **모든 정보**를 포함하세요:
- 수정할 파일의 절대경로
- 구체적인 수정 내용
- 필요한 원본 데이터
- 원래 요청의 조건/제약사항

순차 위임 시 **처음 받은 조건/제약사항을 매번 포함**해야 합니다.

```
# ❌ "아까 만든 것 수정해줘"
# ✅ "파일 /Users/.../result.txt의 3번째 항목을 'ABC'로 수정해줘"
```

## 시간 지정 위임 (스케줄러 경유)

예약의 `pipeline`에는 실행할 IBL을 넣는다. 자연어 부탁은 IBL 안의 명시 위임으로 표현한다.

```ibl
[self:schedule]{seconds:60, pipeline:"[others:delegate]{agent_id:\"조사자\",message:\"최신 연구 동향을 조사하고 요약해줘\"}", edition:2}
```

확정된 절차만 실행하려면 그 IBL을 그대로 예약한다. `target_agent_id`는 실행 신원을 지정하며,
그 값이 있다고 코드를 AI 메시지로 바꾸지 않는다. 예약 실행과 결과 알림은 채팅창 연결과 독립적이다.
명시 비동기 위임의 접수는 최종 완료가 아니므로 반환된 작업 참조로 결과를 확인한다.
