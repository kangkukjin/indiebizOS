# 긴문장 상상훈련 — 복잡한 일을 IBL 프로그램으로 작성하고 실행하기

> “긴문장 상상훈련을 하자”, “긴 문장 상상훈련을 하고 싶다”, “긴 IBL 상상훈련”이라는
> 요청은 이 가이드를 따른다. 기본은 복잡한 가상 과제 하나를 작성·실행하는 1회차다.
> 사용자가 정한 분야·과제 수·자료·예산·실행 범위가 있으면 그것을 우선한다.

## 1. 목적과 다른 훈련과의 관계

**복잡한 가상 과제를 하나 또는 여러 개의 연결된 IBL 프로그램으로 표현하고 실제 실행하여,
큰 일을 작성·조합·실행·수정하기 어렵게 만드는 공통 문제를 발견한다.**
긴 프로그램을 쉽게 작성할 수 있는지와, 작성한 프로그램이 오류 없이 요청한 결과까지
만드는지를 함께 본다. 결과 품질을 지키면서 실제 완료 시간과 전체 토큰 소비를 줄이는
[IBL 진화 목적](../../docs/IBL_EVOLUTION_PURPOSE.md)에 따른다.
성공한 실행도 같은 품질에 더 적은 시간·토큰으로 도달할 수 있었는지 돌아본다.
오류 발견 수를 성과로 삼지 않으며, 공통 개선은 [수리 계획](../../docs/IBL_GENERAL_CAPABILITY_REPAIR_PLAN_2026_09_27.md)의
목적·잔여와 연결한다. 비용 수치 기록에 그치지 않고 낭비의 원인과 다음 개선을 남긴다.

| 훈련 | 출발점과 중심 질문 |
| --- | --- |
| [기존 상상훈련](imagination_training.md) | 미조합 어휘·문형에서 출발해, 이 조합이 표현되고 실행되는가를 본다. |
| 긴문장 상상훈련 | 복잡한 가상 과제를 전체 IBL 프로그램으로 작성해, 큰 일을 일관되게 표현하고 끝까지 실행할 수 있는가를 본다. |
| 상상행동(이 가이드 §4-5) | 같은 자연어 과제를 시스템 AI에 맡겨, 이해부터 결과 전달까지 일을 해냈는가를 본다. |

한 회차는 **훈련자 작성 실행**과 **시스템 AI 실행(§4-5)** 두 가지를 가질 수 있다. 앞의 것은
“쓸 수 있는 언어인가”를, 뒤의 것은 “시스템이 그 일을 해내는가”를 본다. 훈련자가 쓴 결과를
자연어만 받은 에이전트의 독립 수행 능력으로 보고하지 않는다. 같은 과제의 두 결과를 나란히 놓아야
막힌 원인이 언어인지 이해·발견·판정인지 갈린다. “상상행동훈련” 요청과 과제 만들기 원칙·외부 행동
격리는 [상상행동 가이드](imagination_action.md)가 안내한다.

**긴문장의 기준은 글자 수가 아니라 연결된 일의 규모와 의존 관계**다. 긴 문자열·같은 호출
반복으로 분량을 채우거나 함수 수를 목표로 삼지 않는다.

## 2. 요청을 받으면 이렇게 시작한다

1. 이 가이드, [IBL 조합 교재](ibl_composition.md),
   [긴문장 훈련 누적 원장](../../docs/LONG_SENTENCE_IMAGINATION_LEDGER.md)의 이전 회차 결론과 열린 갭을 읽는다.
   문법·실행 계약의 정본은 교재와 [IBL 명세](../system_docs/ibl.md)다.
2. 이전 회차와 다른 조합이나 남은 공백을 시험할 **주 과제 하나와 변형 하나**를 고른다.
   사용자가 지정하지 않은 분야·규모는 현재 실행 가능한 자료와 도구로 정하고 가정을 밝힌다.
3. 자연어 과제·입력·완료 조건·출력 위치를 적고, 전체 프로그램 작성과 실행으로 진행한다.
   계획이나 문법 검사만으로 훈련을 마치지 않는다. 실행 전제가 없으면 가능한 범위와 막힌
   경계를 남기며, 그 결과를 전체 성공으로 세지 않는다.
4. 과제가 §4-5의 규모 기준에 들면 같은 과제를 시스템 AI에 맡기는 두 번째 실행을 회차에 넣는다.
   어느 실행을 했는지 원장에 적고, 하지 않았으면 이유를 남긴다.

한 요청은 유한한 회차다. 무기한 반복이나 예약 실행은 별도 요청이 있을 때 정한다.
원자료·실행 로그·산출물의 로컬 작업 폴더는 `outputs/long_sentence_imagination/YYYY-MM-DD_N회차/`다.
`outputs/`는 git에 포함되지 않는다. **회차 요약과 갭의 정본은 위 `docs/` 누적 원장**에 남긴다.
원장에서 다음 번호를 정하고 시작 항목을 남긴다. 처음이면 1회차이며 중단한 회차 번호도 재사용하지 않는다.
로컬 폴더와 `docs/experiments/long_sentence_imagination/round_N/`의 N은 이 원장 번호와 같다.

### 회차 예산과 종료 기준

사용자 지정이 없으면 **자료 준비·작성·검수·실행·변형·원인 진단을 합해 60분**을 기본 상한으로 둔다.
작성·실행과 원인 진단에 쓴 시간을 구분한다. 수정 주기는 횟수와 이유를 기록하되,
1회차의 임시 상한 3회는 고정 제한으로 쓰지 않는다. 최초 초안 이후 오류를 고쳐 다시
검사·실행한 묶음을 한 주기로 세고, 변형 요구에 맞춘 최초 작성은 별도로 기록한다.
사용자가 정한 수정·토큰·시간 상한은 우선하며, 상한에 닿으면 새 수정·실행·탐침을 멈춘다.
상한은 시작 때 기록하고 결과를 좋게 만들려고 늘리지 않는다.
지정된 토큰·비용 예산도 함께 지키며, 관측할 수 없는 사용량은 미상으로 남긴다.

남은 시간 안에 끝내기 어려운 새 작업은 시작하지 않는다. 상한에 닿았을 때 실행 중이면
지원되는 취소·시간 제한을 사용하거나 실행 id와 회수 방법을 남기고, 아직 진행 중인 결과를
완료로 쓰지 않는다. 종료 보고·증거 보존·시험 자원 정리는 마치되 그 시간은 별도로 기록한다.
같은 원인으로 두 수정 주기 연속 진전이 없으면 해당 경로의 작성을 멈추고,
남은 예산에서 최소 재현과 원인 진단만 정리한다. 막힌 위치·소비한 시간·수정 횟수·남은
완료 조건도 작성 마찰의 증거다. 회고는 보존된 기록으로 마치고 새 실험은 다음 회차 후보로 남긴다.

모델 호출 뒤 긴 계산·렌더가 이어지면 아래 단계 분할 예제을 검토한다.
추출 결과·원문·실패를 반환하고 `$ref`로 후속 프로그램에 연결하면 계산 수리에 같은 모델 비용을 다시 내지 않는다.
전체 단일 실행과 분할 실행의 작성 비용·호출 수를 구분하며, 원천 최신성이 필요하면 새로 수집한다.

### 비싼 추출 결과를 반환한 뒤 계산·표현을 바꾸기

모델 추출 뒤 계산·렌더 수정이 예상되면 추출 프로그램이 원문·출처·추출값·실패 목록을
Record로 반환하게 한다. 그 성공 결과의 `result_ref.input_args`로 두 번째 프로그램에 전달한다.
실패한 프로그램의 모든 지역변수가 자동 복구되지는 않는다. `reuse:{run_id}`는 입력·지시·구현·모델 설정이 같은
`table:ai/brief/judge`의 성공 결과도 자동 재사용한다. 새 판단은 `reuse:{run_id,models:false}`로 요청한다.
명시적인 반환과 `$ref`는 결과를 다른 작업에 전달하거나 보관할 때 사용한다.

첫 실행: `$r=$문단 >> [table:ai]{instruction:"각 행의 수치 표기를 추출",schema:"값(문자열)",preserve_rows:true}; return {원문:$문단,추출:$r.items}`.
다음 요청: `{"code":"return $입력.추출","inputs":{"입력":{"$ref":"첫 실행 result_ref.id"}}}`.
후속 계산을 고칠 때 이 참조와 수정한 코드만 다시 보낸다. 모델 호출은 0이며 저장된
입력 판본에 대한 계산이다. 최신 원천이나 새 모델 판단이 필요하면 추출 단계부터 새로 실행한다.

`number()`는 해석 불가·범위 표기·비유한 값을 NUMBER_REQUIRED로 실패시킨다(null 반환 아님).
예: `[try]{return number($표기)}[catch]{return null}`. null로 처리할지 원문을 따로 남길지는
작업 계약으로 정한다. 오류에는 입력 미리보기와 기대 타입이 있으므로 계산을 먼저 작은 값으로 검사한다.

`preserve_rows` 위반은 기대/반환 행수, 누락·중복·잘못된 `_i`와 `model_output_ref.read_args`를
제공한다. 이 참조는 병합 전 파싱된 모델 응답이다. `read_result`로 확인한 뒤 복구 범위를 정한다.

기본 공유 예산은 10만 계산 단계·1만 반복 행·함수 깊이 64다. split 뒤 each와 람다 반복도 합산한다.
수천 문단의 정규식 검색은 `[fn:본문에서찾기]`를 쓰고 `.match_info.total_matches/selected_matches/omitted_matches`로 생략을 확인한다.

## 3. 복잡한 과제를 만드는 법

IBL 해법을 넣지 않은 자연어 요구와 원하는 산출물을 먼저 정한다. 현재 잘 되는
문형이나 IBL 카탈로그에 맞춰 요구를 축소하지 않는다. 훈련자는 쓸 수 있는 과제를 고르기 쉬우므로
사람이 실제로 부탁할 일에서 출발한다. 분야는 조사·문서·생활·업무·제작 등에서 바꾸며,
**저장된 정답 관용구가 없는 새 과제**를 포함한다.

다음은 과제의 예시이며 고정 메뉴나 현재 지원 능력의 보증이 아니다.

- 여러 업체의 견적서와 요구사항을 비교해 항목을 맞추고, 누락·조건별 추천·확인할 질문을
  포함한 보고서를 만든다. 누락된 가격을 0으로 간주하지 않는다.
- 여러 주제의 자료를 수집해 중복과 상충하는 주장을 정리하고, 근거와 미확인 부분을
  포함한 학습 자료를 만든다. 자료 하나를 읽지 못했을 때의 결과도 구분한다.
- 행사 후보 장소와 일정·인원·예산 자료를 결합해 가능한 안들을 비교하고, 인원 조건이
  바뀌었을 때 영향을 받는 부분을 갱신해 새 제안서를 만든다.

한 회차에 모든 문법을 강제하지 않는다. 과제에 필요한 다음 연결을 선택해 난도를 높인다.

| 단계 | 시험할 연결 |
| --- | --- |
| 연속 작업 | 자료 수집 → 정규화·계산 → 판단 → 산출물, 중간 값의 명시적 전달 |
| 여러 갈래 작업 | 독립 수집·병렬 결과 합류·항목별 반복·조건 분기·빈 결과와 부분 실패 |
| 여러 층의 조합 | 지역 함수·기존 관용구의 재조합, 내부 실패 진단, 조건 변경과 부분 재개 |

처음에는 여러 단계가 이어진 과제로 시작하고, 작성·실행 경험을 보고 규모를 키운다.
줄 수·호출 수·함수 깊이는 과제 설명을 위한 보조 정보이며 합격 기준이 아니다.
다음 회차는 이름·행 수만 바꾸기보다 새로운 연결 하나를 선택한다. 이전 수리나 검증된
부품이 다른 분야·입력에서도 우회와 재작업을 줄이는지 관측한다. 이전 과제의 재실행은
회귀 근거로 구분하며, 새 과제에서의 개선을 대신하지 않는다.

## 4. 작성부터 실행까지

### 4-1. 입력과 완료 조건을 고정한다

전체 프로그램 실행 전에 회차 작업 폴더의 `task.md`에 자연어 요구 원문, 실자료/시험자료 구분,
입력 사본 또는 참조, 사용 모델·도구·권한, 산출물과 완료 조건을 남긴다. 완료 조건은 요청에서
도출하며, 미리 계산 가능한 기대값과 변형의 종류·기대도 적는다. 정확한 정답을 미리 알 수 없는
과제는 확인할 근거·품질 조건을 적는다. 반환값뿐 아니라 최종 산출물의 비교 대상·합계·누락 표시·
근거 연결·파일 생성 여부를 확인한다. 예: 합계가 반환됐어도 보고서에 없으면 조건 미충족이다.
실행 후 나온 결과에 맞춰 합격 조건을 낮추지 않는다. 원천 일부를 못 읽는 시험에서는 남은 근거로 구별할 수 없는 정답을 요구하지 않고, 미확인 표시와 추가 확인 대상을 사전에 정한다.

### 4-2. 전체 흐름을 IBL로 작성한다

**요구 → 분해 이유 → 함수별 계약 → 구현 → 최상위 조합** 순서로 작성한다.
각 부품의 입력·반환·실패·외부 효과를 정하고 현재 액션 계약을 조회해 연결한다.
지역 함수는 등록 없이 쓸 수 있으며, 적합한 기존 관용구도 부품으로 사용한다.
문법과 실행 인자는 조합 교재의 현재 계약을 따르고 이 가이드에서 별도 방언을 만들지 않는다.

**기본 작성 조건은 시스템 에이전트가 통상 조회할 수 있는 자료만 사용하는 것이다.**
가이드·공개된 문법·액션 및 함수 계약·허용된 기억과 관용구·과제 자료·실행 진단을 사용하고,
실제로 참고한 자료를 남긴다. 개발 세션의 소스코드·내부 테스트·미공개 구현 지식으로
작성의 빈칸을 채우지 않는다. 이미 내부 구현을 알고 있어 영향을 분리할 수 없으면 그 한계를 밝힌다.

자료만으로 작성이 막혀 내부 코드를 열어야 한다면 **열기 전 초안과 막힌 지점을 보존하고
작성·발견 갭으로 등록한다.** 이후 코드 열람은 원인 진단이나 도움을 받은 시도로 구분한다.
도움 뒤 실행 성공은 기록할 수 있지만 기본 조건에서 쉽게 작성했다고 평가하지 않는다.
실행 기반 결함을 진단하는 코드 열람 자체를 금지하는 것은 아니다.

정할 수 있는 흐름은 가능한 한 한 프로그램에 담는다. 여러 프로그램이 필요하면
각 프로그램의 역할·순서·입출력 참조와 나눈 이유를 명시한다. 탐색 결과나 사용자 판단이
필요한 경계는 드러내고, 아직 모르는 값·도구 동작을 지어내지 않는다.

훈련자가 중간 결과를 손으로 옮기거나 매 단계 다음 호출을 새로 지시했다면 그 개입을 기록한다.
Python·셸로 핵심 조합을 대신한 결과를 긴 IBL 실행 성공으로 세지 않는다. 기존 도구·스크립트를
계약에 따라 IBL에서 호출하는 것은 가능하지만, 과제 전체를 새 스크립트에 숨겨 시험을 우회하지 않는다.

**검수 전 최초 완성 초안을 별도 `.ibl` 파일로 보존한다.** 참고한 교재·계약 조회,
작성 시간, 내부 구현을 읽어야 했던 이유, 우회·도움받은 지점도 간단히 기록한다.
이 기록은 관측 가능한 작성 행동이며 모델 내부 사고의 수집을 뜻하지 않는다.

### 4-3. 검사하고 같은 프로그램을 실제 실행한다

현재 실행 경로의 검사 기능으로 검수한 뒤 실제 실행한다. 최초 초안을 덮어쓰지 말고
수정본과 수정 이유를 남긴다. 작성 오류 수정은 훈련의 일부이며 처음부터 성공한 것으로 세지 않는다.
입력 오류·자료 부족·외부 서비스 장애와 언어/실행기 결함을 구분한다.

훈련 호출에는 실행 경로가 지원하는 `origin: "training"`과 올바른 프로젝트 문맥을 전달한다.
MCP에서는 `execute_ibl(code=..., origin="training")`으로 지정한다. 생략하면 부모 요청의 출처를
상속하므로 수리 턴 안의 훈련 탐침·재실행에도 명시한다. `recover`는 기존 실행의 출처를 바꾸지 않는다.
이는 액션의 문장 인자가 아니라 실행 요청의 메타데이터다. 하위 실행에도 출처가 이어지는지
확인하고, 지원하지 않는 진입점에 임의 옵션을 만들지 않는다. 출처 표식은 격리를 대신하지 않는다.
자료·출력은 회차 작업 공간이나 사본을 사용하고, 외부 효과의 격리·기록 기준은
[상상행동 가이드 §3](imagination_action.md#3-행동을-관찰할-수-있고-실제-세계에-새지-않아야-한다)을 따른다.
훈련 요청만으로 실제 발송·구매·공개·예약을 실행하지 않는다. 시험 환경이나 대역에서
검증했다면 그 범위를 밝히고 실제 서비스 성공과 구분한다.

실행 id, 실행한 소스 버전, 입력, 오류, 결과 참조, 산출물을 연결해 보존한다.
결과를 더 읽기 위해 작업 전체를 다시 실행하지 않는다. 실행 중인 작업은 같은 실행을 회수한다.

### 4-4. 최종 산출물과 변형을 확인한다

**검사 통과 / 실행 정상 종료 / 과제 달성은 각각 판정한다.** 종료 상태만으로 성공을 정하지 않는다.
입력 일부 누락, 순서·출처 소실, 실패한 가지의 정상값 위장, 미생성 파일, 요청 조건 불충족을
실제 산출물과 대조한다. 과제 달성 상태는 **달성 / 부분 달성 / 미달 / 미검증**으로 남긴다.
기존 실행 증거와 결정론적 확인을 우선하고, 매 단계 별도 평가 모델을 붙이지 않는다.

기본 변형은 입력 규모 변경·빈 결과·일부 입력 실패·후반부 조건 변경 중 하나를 고른다.
**같은 프로그램에 다른 입력을 넣는 견고성 시험**과 **요구가 바뀌어 프로그램도 수정하는
변경 용이성 시험**을 구분한다. 전자에서 오류를 고쳤다면 수정 전·후 결과를 모두 남기고,
처음부터 견고했다고 세지 않는다. 후자는 변경 내용·작성 비용을 기록한다.
변형에서 기대하는 결과를 실행 전에 `task.md`에 적는다. 부분 실패를 의도한 경우, 실패를 정확히 드러내고
약속한 결과를 보존한 것이 통과일 수 있다. 항상 정상 종료하도록 실패를 숨기지 않는다.
실서비스 장애를 만들지 말고 통제 가능한 시험자료나 대역을 사용한다.

부분 수정·재개가 필요한 과제에서는 기존 결과 참조와 교재의 재사용 계약을 활용한다.
무엇이 재사용되고 무엇이 다시 실행됐는지, 중복 쓰기가 생겼는지 관측한다. 지원되지 않는
재개를 있다고 가정하지 말고 그 경계를 발견으로 남긴다.

### 4-5. 같은 과제를 시스템 AI에 맡긴다 (두 번째 실행)

**언제.** 모델이 자료를 읽고 머리로 풀 수 없는 규모이거나 반복될 일일 때 넣는다. 파일 몇 개·수십 행
과제는 시스템 AI가 프로그램 없이 읽고 계산해 1분 안에 끝내므로 두 작성자를 가르지 못한다
(7회차: 견적 3곳, 53초·도구 4회). 수천 행 과제에서는 프로그램으로 넘어가며 훈련자와 같은 자리에서
막힌다(8회차: 2,698행, 11분·도구 27회·거절 10회). 작은 과제의 두 번째 실행은 고정 비용 관측용으로만 쓴다.

**무엇을 넘기나.** `task.md`의 자연어 요청 원문에 자료 위치와 저장 위치만 더한 글 하나다.
훈련자의 초안·보고서·분해 방법·함수 이름은 넘기지 않는다. 입력은 정답·생성 스크립트를 뺀 사본 폴더로
주고(기대값 파일이 같은 폴더에 있으면 답이 샌다), 출력은 훈련자 실행과 다른 폴더로 받는다.
훈련자 실행을 먼저 했다면 그 산출물이 시스템 AI가 읽을 수 있는 자리에 있는지도 확인한다.

**어떻게 보내나.** 검증된 진입점은 `POST /system-ai/chat`에 `{"message": 요청문, "origin": "training"}`을 보내는 것이다
(동기 응답, 큰 과제는 10분 이상). 보내기 전 `episode_log`의 마지막 id를 적어 두면 새 에피소드 번호로
증거를 찾는다. 변형은 같은 대화에 후속 요청으로 보낸다(“조건이 바뀌었어…”).
`origin:"training"`은 이 턴을 리허설로 표시한다. 에피소드와 궤적의 source가 `training`이 되어 건강·통계 원장에서
실사용과 갈리고, 요청과 답은 `rehearsal` 대화 스레드와 별도 CLI 세션에 남아 주인의 실제 대화 문맥과 섞이지 않는다.
RED 수리 그랜트와 증류는 없다(리허설은 삶이 아니다). 따라서 **증류가 무엇을 남기는지 보려는 회차는 표식 없이 보내고**
그 혼입(실사용 에피소드·대화 기록·경험 저장 가능성)을 보고서에 적는다. 표식은 외부 행동을 막지 않는다 — 읽기와 회차 폴더
쓰기만 있는 과제로 제한하고, 발송·구매·공개·예약이 낀 과제는 상상행동 가이드 §3의 격리가 확인될 때만 한다.
후속 요청은 앞 턴의 result_ref를 그대로 이어 쓸 수 있다(같은 에이전트·주체의 최근 8턴).
프로젝트 에이전트의 `POST /projects/{project_id}/agents/{agent_id}/command`도 `origin:"training"`을 받는다. 동기·background 모두 리허설 이력과 CLI 세션을 사용한다. background 결과는 기존 메시지 조회에 `rehearsal=true`를 붙여 회수한다. 기본 메시지·주행기록 조회와 자동 대화 요약은 훈련을 제외하며, 주행 조회의 `include_test=true`는 훈련도 포함한다.

**무엇을 회수하나.** `data/world_pulse.db`(읽기 전용)의 `episode_log.total_ms`와 그 에피소드의
`trajectory_event`: `supervision.tool.started/finished`(작성한 IBL·거절·오류), `model.usage`
(`accounting=billable_usage`의 input·cache_read·cache_create·output, 역할별), `supervision.cost.summary`,
`recall.presented/used`, `context.compacted`, (표식 없는 실행이면) `distillation.cost`와 `distill_jobs`의 상태·오류.
산출물은 훈련자 실행과 같은 완료 조건·기대값으로 대조한다.

**무엇을 보나.** 훈련자 실행에서 볼 수 없는 것들이다.

| 볼 것 | 질문 | 수리 계획 연결 |
| --- | --- | --- |
| 풀이 방식 | 프로그램으로 썼는가, 읽고 머리로 풀었는가. 몇 라운드였고 거절·실패는 어떤 부류인가 | R4 |
| 분할·재사용 | 수정할 때 앞 결과 참조·`reuse`를 골랐는가, 처음부터 다시 돌렸는가 | R2·R4 |
| 방법 발견 | 제시된 회상 후보를 썼는가. 문법·계약을 어디서 찾았는가(회상·describe·교재 검색) | R5 |
| 완료 판정 | 조건을 스스로 확인했는가(저장 후 재읽기·미확인 표시). 평가 경로가 돌았는가 | R3 |
| 축적 | 증류가 무엇을 남겼는가. 앞 회차의 검증된 프로그램·관용구를 찾아 썼는가 | R6 |
| 비용 | 벽시계, 역할별 토큰, 자동 압축과 그 뒤 상태 유실, 사용자 재요청 필요 여부 | R4 |

훈련자 실행의 갭이 시스템 AI 실행에서도 밟히는지 대조한다. 밟히면 그 갭의 우선순위 근거이고,
안 밟히면 그 과제 규모에서 그 경로가 쓰이지 않는다는 뜻이다. 두 실행의 달성·시간·호출·토큰을 한 표에
놓되, 훈련자 자신의 토큰이 미측정이면 미측정으로 적는다. 표본 1회 결과를 일반화하지 않는다.

## 5. 무엇을 발견하고 어떻게 평가하는가

| 축 | 남길 관측 |
| --- | --- |
| 작성 용이성 | 첫 초안부터 실행 가능한 버전까지의 시간·수정 횟수, 계약 탐색·코드 열람·수작업 개입·우회 |
| 표현·조합 | 값 전달, 함수 경계, 병렬 합류, 반환 계약, 여러 프로그램 연결이 명시적이고 일관적인가 |
| 실행·복구 | 실패 위치와 원인이 드러나는가, 중간 결과와 근거가 보존되는가, 필요한 부분을 수정·재개할 수 있는가 |
| 결과 품질 | 요청의 정확성·완전성·근거·산출물 사용 가능성, 누락과 사용자 재작업 |
| 비용 | 작성·검수·실행·복구를 포함한 실제 경과 시간, 관측 가능한 전체 모델 입력·출력·캐시 토큰 |

긴 코드인데도 쉽게 작성됐다면 그 사실을 기록한다. 짧아졌어도 계약을 찾기 어렵거나
수작업이 늘었다면 개선으로 단정하지 않는다. 내부 AI·감독·검수·후처리 비용을 숨기지 않고,
미측정은 미측정으로 둔다. 문자 수나 IBL 호출 수를 실제 토큰으로 바꾸어 적지 않는다.
시간·토큰 절감을 주장할 때는 같은 자료·모델·완료 조건의 기준선과 비교하고 조건 차이를 밝힌다.
기준선이 없는 첫 회차도 공백 발견에는 유효하며, 성능 향상을 입증한 회차와 구분한다.

문맥 유지/단절을 비교한다면 격리된 시험에서 **선행 작업 → 같은 문맥 후속 → 문맥 단절** 순으로
실행하여 중간 상태를 되돌리는 일을 피한다. 서로 다른 후속 과제를 비교할 때는 요구·저장 자료의
차이도 기록한다. 동일한 선행 상태의 분기가 필요하면 대화·네이티브 세션·참조·산출물뿐 아니라
과제 원장(pursuit·turn·event)과 작업 상태까지 격리해야 한다. 일부만 복원한 비교는 실행 전에
차단한다. 단절 조건에 warm의 결과가 추가됐다면 그것도 같은 선행 조건이 아니므로 별도 seed가 필요하다.
실행 전 seed 상태 대조와 실행 후 실제 네이티브 세션 연속성을 모두 확인하며, 압축·요약으로
새 세션이 됐으면 문맥 유지 비교에서 제외한다. 산출물이 맞아도 무효인 비교를 유효로 바꾸지 않는다.


발견은 **작성·발견 마찰 / 문법·값 계약 공백 / 구현 결함 / 자료·권한·외부 전제 부족 /
요구 해석 오류 / 과도한 비용**으로 분류한다. 시스템 AI 실행에서는 **발견·학습 문제**(능력이 있는데
설명·회상에서 찾거나 고르지 못함)와 **관측·축적 공백**(판정·증류·기록이 남지 않음)을 더한다.
여러 원인이 함께 있을 수 있다.
결함 의심은 최소 IBL 재현으로 격리하되, 최초의 전체 프로그램과 실행 증거를 함께 보존한다.
이미 알려진 문제면 기존 기록에 증거를 연결하고, 특정 과제의 실패를 언어 전체의 한계로 확대하지 않는다.

### 실행 후 낭비 검토

**달성 여부와 별개로 매 회차 실행 경로를 돌아본다.** 기존 호출·수정 기록과 산출물에서
주요 비용 구간을 골라 다음을 짧게 남긴다. 오래 걸렸거나 호출이 많다는 이유만으로 낭비로 판정하지 않는다.

1. **필요했던 비용** — 자료 수집·판단·검수·복구 중 어떤 일이 결과의 정확성·완전성·근거에 기여했는가.
2. **줄일 수 있었던 일** — 중복 조회·자료 재독·과도한 반환·불필요한 모델 왕복·성공한 단계의
   재실행·기존 기능의 재구현·누락으로 인한 재작업이 있었는가. 재사용으로 이미 피한 비용도 기록한다.
3. **원인과 근거** — 어느 실행·응답·수정에서 관측했으며, 작성자의 선택·계약과 안내·실행기·
   맥락 전달 중 무엇이 원인인가. 확인된 낭비와 추가 확인이 필요한 후보를 구분한다.
4. **다음 개선과 보존할 품질** — 무엇을 생략·통합·재사용할 수 있고, 그래도 어떤 결과·근거·
   실패 표시를 유지해야 하는가. 개선 위치와 확인 방법을 적고 기존 갭이 있으면 연결한다.

예를 들어 정보성 검사 응답의 중복 전달은 요약과 원문 참조로 줄일 수 있지만 오류·경고는
보존해야 한다. 보고서의 합계 누락으로 재작성했다면 산출물 조건을 앞에서 확인하도록 고치며,
누락을 찾아낸 최종 검수 자체를 낭비로 보지 않는다. 필요한 검수·근거·출력 범위를 줄이거나
사용자에게 재작업을 넘겨 얻은 절감은 인정하지 않는다. 찾은 낭비가 없으면 없다고 기록한다.

훈련 대상 과제의 작성·실행·검수·복구 비용과 훈련 운영·회고·후속 시스템 수리 비용을
분리해 기록하되 어느 쪽도 숨기지 않는다. 실제 경과 시간은 병렬 도구 시간의 합과 구분하고,
응답 뒤 후처리는 사용자 대기 시간과 구분한다. 모델 사용량은 입력·출력·캐시 및 내부 호출의
포함 범위를 밝혀 중복 합산하지 않는다. 프로그램 안의 AI 호출이 0이어도 작성자 비용은 0이 아니다.

미측정이어도 관측된 중복·우회는 개선 후보로 삼을 수 있다. 다만 문자 감소나 호출 감소를
전체 토큰·시간 절감률로 환산하지 않는다. 한 축만 좋아지거나 다른 축이 악화되면 그 상충을 남긴다.
모든 개선에 사전 A/B 실험을 요구하지 않으며, 비교 가능한 후속 실행에서 효과를 확인한다.
회고는 기존 증거로 몇 줄이면 충분하다. 매 단계 별도 평가 모델·중복 보고서·관측만을 위한
전체 재실행을 추가하지 않는다. 회고 자체의 시간과 토큰도 운영 비용에 포함한다.

## 6. 보고서와 후속 수리

회차 폴더에는 실행 전 `task.md`, `report.md`, 최초 초안·실행한 수정본·변형 프로그램, 입력 사본/참조,
실행 증거와 최종 산출물을 둔다. 여러 프로그램이면 실행 순서와 명시 입력 연결도 적는다.
비밀 값은 제외하고 민감한 원자료를 git에 넣지 않는다. 보고서는 다음 순서면 충분하다.

1. **과제와 조건** — 자연어 원문, 선정 이유, 입력, 모델·실행 환경, 완료 조건.
2. **작성** — 분해와 계약, 전체 IBL 파일, 최초 초안과 수정 이유, 참조 자료·내부 지식 개입과 기본 조건/도움 뒤 시도의 구분.
3. **실행과 결과** — 실행 id·증거·산출물, 검사/실행/달성의 각 판정, 변형의 기대와 실제 결과.
   시스템 AI 실행을 했으면 에피소드 번호, 두 실행의 비교 표, §4-5의 볼 것 여섯 가지.
4. **발견** — 회차별 갭 ID, 원인 분류, 최소 재현, 영향받은 연결, 확정 사실과 가설.
5. **개선 방향** — 다른 분야에도 통하는 공통 원인·소유 위치·처방, 원래 과제와 새 변형의 재검증 조건.
6. **비용·낭비 검토와 잔여** — 상한과 시간·토큰·수정량, 비용의 포함 범위, 종료 이유·비교 조건.
   §5의 필요한 비용/줄일 일/원인과 근거/다음 개선과 보존할 품질, 미검증 경계·다음 회차 후보를 짧게 적는다.

회차 종료·중단 시 누적 원장의 회차 요약과 갭 표를 갱신한다. 갭 ID는 **`L<회차>-<순번>`**
(예: `L1-1`)이며 원인 분류는 별도 칸에 쓴다. 기존 상상훈련의 `B`·`G` 번호를 사용하지 않는다.
같은 원인의 재발견은 기존 ID에 증거를 더하고, 다른 훈련의 기존 갭이면 원래 ID도 연결한다.
발견이 없으면 갭 0건으로 기록한다. 빈칸을 채우기 위해 문제를 만들지 않는다.

로컬 출력 링크만 남기면 다른 세션·복제본에서 결론을 검토할 수 없다. 누적 원장에는 과제·조건·
관측 결과·판정 근거·미검증을 자체적으로 읽을 수 있게 요약한다. 재현에 필요한 비민감
최소 IBL과 합성 입력은 원장 또는 `docs/experiments/long_sentence_imagination/round_N/`에
보존한다. 민감 자료를 제거해 재현할 수 없다면 그 한계와 필요한 자료 조건을 적는다.

1회차 시범과 후속 회고를 반영해 기대의 사전 기록·변형 구분·종료 기준·낭비 검토를 보완했다.
7·8회차(1·6회차 과제를 시스템 AI에 맡긴 시범)로 §4-5를 더하고 상상행동 절차를 이 가이드로 합쳤다.
근거는 [1회차 보고서](../../docs/experiments/long_sentence_imagination/round_1/report.md)다.
후속 회차에서도 도움이 된 절, 모호하거나 불필요했던 절, 빠진 지침이 있으면 짧게 남긴다.
가이드 작성·검색 검증을 훈련 실행 검증으로 간주하지 않는다.

훈련 중에는 작성한 IBL과 시험자료를 수정하며 관찰한다. **발견한 시스템 결함의 수리는
별도 수리 작업으로 넘긴다.** 훈련을 통과시키려고 라이브 코어·도구 계약을 바꾸거나
적용을 예약하지 않는다. 사용자가 수리까지 명시한 경우에는 최초 관측을 보존하고 훈련 결과와
수리 결과를 분리한다.

**훈련 종료 → 수리 적용 → 수리 후 검증의 순서를 지킨다.** 사용자가 수리까지 맡겼어도,
보낸 주 과제·변형·시스템 AI 독립 실행의 모든 작업 ID·티켓을 기록하고 **모두 종료 상태임을
확인해 산출물·실패 증거를 회수한 뒤** 라이브 코드·설정·어휘를 바꾸거나 reload·apply·적용 예약을 한다.
`data/packages/` 편집도 구현 지문을 바꾸므로 이 순서를 따른다. 기다리는 동안에는 읽기 전용
진단과 라이브에 영향을 주지 않는 격리 사본의 수리안 작성만 한다. 호출 timeout·응답 단절은
작업 종료가 아니다. 기존 작업을 회수해 종료를 확인하고, 확인할 수 없으면 적용을 보류한다.
실패·취소로 끝났다면 성공으로 세지 않고 그 상태와 회수하지 못한 증거를 남긴다.
훈련 전후 코드 리비전과 적용 시각을 기록하며, 수리 검증은 최소 재현뿐 아니라
**원래 전체 프로그램과 새 변형**까지 확인한다. 수리 후 실행을 최초 성능 기준선과 합치지 않는다.
회귀시험은 기본 pytest 수집 경로인 `backend/test_*.py`에 두고 회차 보고서에서 연결한다.
`docs/experiments/` 안에만 둔 시험은 기본 회귀에 포함되지 않는다.

성공한 전체 프로그램은 재실행 가능한 증거로 보존한다. 관용구 등록·해마 시딩은 자동으로
하지 않으며, 검증과 재사용 가치가 확인된 후보만 기존 선정·등록 절차로 넘긴다.
새 어휘를 늘리기 전에 기존 조합·계약·설명·실행기의 공통 개선으로 해결할 수 있는지 본다.

**훈련의 산출물은 실행 가능한 전체 프로그램과 실제 결과, 그리고 품질을 지키며 큰 일을
더 쉽고 적은 시간·토큰으로 끝내기 위해 고쳐야 할 연결과 낭비의 기록이다.**
