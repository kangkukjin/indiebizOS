# 웹 검색 가이드 (Web Search Guide)

일반 웹은 폴백이다 — indiebizOS는 여러 도메인에 *어휘(IBL 액션)*를 가져, 많은 검색을 일반 크롤보다 빠르고 구조적으로 한다. **먼저 어휘, 없으면 웹.**

## 1. 액션 먼저 — 어휘가 있으면 그게 빠르다
- 검색 전에 **이 도메인에 IBL 액션이 있는지 보라.** 있으면 일반 웹검색보다 빠르고·구조화돼 있고·공식 API(권위)다.
- 액션이 흔한 도메인: 구매·가격비교 · 법령·판례 · 논문·연구자 · 통계 · 기업·주가·공시 · 부동산 시세·매물 · 도서·고전 · 공연·전시 · 창업지원·경진 · 맛집·상권·지역 · 뉴스 · 날씨·CCTV · 유튜브·라디오.
- 구체 액션명·파라미터는 IBL 카탈로그(execute_ibl)에 있고, 복잡하면 `read_guide`로 도메인 가이드(예: "법률"·"통계"·"부동산")를 읽어라. **여기서 다시 나열하지 않는다.**
- **일반 웹검색(`[sense:search]{source}`·`crawl`)은** 액션이 없거나, 액션 밖의 맥락·후기·비교가 필요할 때의 폴백. 배운 검색 관습(포식 기억)이 있으면 그걸 우선하라.

## 2. 일반 웹검색을 쓸 때 — 키워드·소스·언어·카테고리
- **키워드 (개인화의 핵심)**: 사용자의 말을 그대로 검색창에 넣지 말고 **문맥에 맞는 키워드를 골라 넣어라** — 사용자의 분야·의도·알려진 맥락·중의성 해소어를 얹어서. 검색창은 맥락을 모르지만 너는 안다 — **그게 일반 검색이 못 이기는 개인화 검색의 강점이다.** 예: 모호한 이름·용어는 분야·소속으로 좁히고, 의도(사기/알아보기/비교)에 맞는 어휘를 더한다.
- **소스**: 한국어·국내는 `search{source: "naver"}`(국내 콘텐츠 압도적), 글로벌·영어는 `search`(기본 ddg). 뉴스=`source: "gnews"`, 기술 동향=`source: "hn"`, 가디언 아카이브=`source: "guardian"`. 전문 사이트가 있으면 홈페이지 말고 *검색어·필터 박힌 결과 페이지*로 바로.
- **언어**: 대상 국가 언어로도 검색하라(일본→일본어, 글로벌→영어). 한국어만으론 현지 정보를 놓친다.
- **카테고리**: 넓게 잡아라("약"→의약품+건강식품+한방약+영양제…). 하나에 갇히면 관련 정보를 놓친다.

## 3. 넓게 → 좁게, 그리고 판단
- **검색어가 여럿이면 한 호출에 묶는다.** 1차 넓게는 검색어·언어·소스를 여러 개 던지는 일이므로 낱개 호출이 아니라 배치다 — 같은 소스는 `queries`, 다른 소스는 `&`. 낱개로 치면 검색어 수만큼 모델 왕복이 생기고 그때마다 문맥 전체가 다시 실린다(ep3854: 26건 낱개).

```ibl
$후보 = [sense:search]{source:"naver", queries:["<국내 검색어 1>","<국내 검색어 2>","<국내 검색어 3>"], limit:5} & [sense:search]{source:"ddg", queries:["<영어 검색어 1>","<영어 검색어 2>"], limit:5}
$후보 >> [table:union]{} >> [table:dedup]{by:"url"} >> [table:select]{fields:["title","url","summary","query"]}
```

  행의 `query` 가 어느 검색어에서 왔는지 말해 준다. 0건인 검색어는 실패가 아니고, 실패한 검색어만 `errors` 에 남는다. 결과를 보고 모자란 각도가 보이면 그때 다음 배치를 던진다 — 한 번에 하나씩 확인하며 좁혀야 하는 추적 검색(앞 결과가 다음 검색어를 정하는 경우)만 낱개가 맞다.
  큰 배치의 모델 미리보기는 검색어별 대표 행을 번갈아 보여준다. 전체 순위가 아니며 `_preview.indices`는 원본의 1기반 위치다. 표시 슬롯보다 검색어가 많으면 `groups_total`과 `groups_shown`을 확인한다. 저장 변수·앱·원문 조회에는 검색 순서와 전량이 보존된다.
- **1차 넓게**(키워드·언어·소스 다양, 검색 요약이면 충분) → **2차 좁게**(유망 후보 2~3개만 `crawl`로 상세 검증). 일반 검색 통화는 `title·url·summary·meta`를 쓰며, 다른 소스는 실제 반환 열을 확인한다. `snippet·description`을 추측해 선택하지 않는다.
- **"없다"고 단정하지 말라**(못 찾은 것일 수 있음). **snippet만으로 확정하지 말고** 핵심은 원본 `crawl`로. **URL·제품명·수치를 지어내지 말라** — 검색으로 확인된 것만.
- 연속 질문에서는 확인한 사실·출처·미확인 조건을 구분하고, 새 질문에서 달라진 조건이나 근거가 부족한 부분을 추가 조사한다. 최신성·모순·출처 부재가 있으면 다시 확인한다. 빠른 도구 호출 수보다 새 판단 없이 반복하는 모델 왕복을 줄인다.
- 추천은 사용자가 원하는 작업 흐름을 기준으로 한다. 직접 조작의 편의와 AI가 조작할 수 있는 범위를 구분하고, 원문에서 확인한 OS·배포판·라이선스·연동 제약 중 실행 가능성을 바꾸는 조건을 답변에 반영한다.

## 4. 웹 랜드마크 — 어디로 가나 (액션 없는 잔여)
액션으로 닿지 않는 비액션 출처(제도·로컬 한국 기관 / AI·경제·외교·과학·지식 국제 권위)의 지도는 **별도 단일 소스** `web_landmarks.md`에 있다. 어디로 가야 할지 막막하면 `read_guide("웹 랜드마크")`로 읽어라. (포식 브라우저는 이 지도를 항상 함께 받는다.)

## 5. crawl이 막혔을 때 — reason을 읽고 행동하라
`crawl`은 내부에서 자동 에스컬레이션한다(curl_cffi TLS 크롬 위장 → Chrome MCP → Playwright JS 렌더링 + iframe 전 프레임 수집). 실제로 실행한 단계와 건너뛴 이유는 실패 응답의 `stages`를 확인한다. 브라우저 연결·세션이 없거나 단계가 시간 초과되면 모두 실행됐다고 단정하지 않는다. 최종 실패 시 `reason`이 온다:
- **`bot_blocked`**: 실행한 단계에서 봇 차단을 감지했다. 같은 조건의 반복 호출보다는 **같은 정보를 다루는 다른 소스**(검색 결과의 다른 후보, 뉴스, 공식 API 액션)로 우회하라.
- **`login_required`**: 도구 한계가 아니라 세션 부재. 두 갈래 — ① 로그인 불필요한 다른 소스로 우회, ② 반복해서 필요한 사이트면 **사용자에게 1회 로그인을 요청**: `browser_navigate`를 `headless: false`로 열어 사용자가 로그인하면 세션이 자동 저장·복원되어(data/browser_cookies/_auto_state.json) 이후 crawl이 통과한다(네이버 카페 등).
- **`insufficient_content`** (success와 함께 올 수도): 짧은 본문은 정상일 수 있으니 내용으로 판단.
- **`http_error`**: 서버가 HTTP 오류를 반환했다. URL·`stages`의 상태를 확인하고 유효한 원문으로 이동한다.
- **`http_status_unverified`**: 브라우저의 HTTP 상태 확인이 불가능했다. 정상 200 응답으로 추측하지 않으며 다른 수집 경로를 시도한다.
네이버 카페·블로그는 본문이 iframe이라 자동으로 브라우저 렌더링을 탄다(로그인돼 있으면 회원 카페 본문도 나옴).


## 6. 검색 실패·원문 보관의 의미

- gnews/hn의 `success:true, items:[]`는 정상 0건이다. 수신·파싱·시간 초과는 실패이며, 배치의 `errors`는 실패한 검색어를 나타낸다. 성공한 다른 검색어의 결과는 `items`에 남으므로 전체를 버리지 않는다.
- gnews/hn 수신은 소켓 대기 5초·수신 경과 20초를 제한하며, 배치 수집 대기는 45초다(큐레이션 시간 제외). 실행 중 소켓 읽기는 설정된 대기 시간 안에서 종료되고, 대기열의 미실행 요청은 취소된다. 시간 초과는 ‘자료 없음’이 아니다.
- 게시일을 제공하는 gnews·hn·guardian·naver(news/blog)는 `date`로 신선도를 판정한다. ddg·일반 웹문서는 게시일을 보장하지 않는다. hn 최신 조사는 `days`를 명시한다.
- crawl은 div 본문·중첩 목록의 부모 문장·그림 설명을 보존하고 요청별 브라우저 탭을 사용한다. HTTP 오류를 정상 원문으로 캐시하지 않는다. `source_ref`는 추출된 전문·문단·링크·메타 관측의 스냅샷이며 원본 HTML·이미지 자체가 아니다.


## 7. 같은 페이지에서 본문·링크·메타정보를 고르기

- `[sense:crawl]{url:"https://example.com",op:"content"}`: 본문(기본 모드). 문단의 `url·paragraph_index`를 보존한다.
- `[sense:crawl]{url:"https://example.com",op:"links"}`: 링크의 `text·url·href·source_url·rel·link_index`. 상대 주소는 해소하고 실행·메일 링크는 제외한다.
- `[sense:crawl]{url:"https://example.com",op:"metadata"}`: 제목·대표 URL·저자·게시/수정 날짜의 관측 목록. `field·value·raw·source·source_url`을 보고 근거를 판단한다. 날짜가 충돌하면 두 관측을 남기며 일반 `<time>`을 게시일로 추정하지 않는다. ISO 형식만 `normalized`에 정규화하고 나머지는 null이다.
- 같은 프로젝트·에이전트의 같은 URL은 모드 사이에서도 15분간 스냅샷을 재사용한다. 갱신은 `refresh:true`. 구조만 읽힌 짧은 페이지는 본문 읽기를 다시 시도한다. `structure_errors`·`partial`은 구조 수집의 누락이며 정상 0건과 구분한다. PDF에는 링크·메타 모드를 제공하지 않는다.

본문에서 조건을 찾을 때는 원문 통화를 그대로 넘긴다:

```ibl
$원문 = [sense:crawl]{url:"https://example.com"}
$원문 >> [fn:본문에서찾기]{패턴:"Example|domain",문맥:1,개수:5}
```

`패턴`은 정규식, `문맥`은 앞뒤 문단 수, `개수`는 문맥을 붙일 일치 수다. URL 경계를 넘지 않고 겹친 문맥을 합친다. 결과 행의 원래 필드와 수집 실패 행은 보존되며 `match_info`로 전체·선택·생략 일치 수와 입력 행 위치를 확인한다. 실패 행은 개수 0에도 남는다. 추가 AI 호출은 없다. 이미 일부 문단만 남긴 입력에서 빠진 문맥을 복원하지는 않는다. 여러 URL은 `[fn:주소마다읽기]`의 결과를 같은 방식으로 넘긴다.

문단 수집의 표시 설정은 `each`·`union` 뒤에도 이어진다. 모든 성공 출력이 문단 표시를 선언했을 때 글자 예산을 쓰며, 여러 페이지의 예산은 더하지 않고 가장 작은 예산을 공유한다. `개수`는 글자 수 제한이 아니므로 긴 문단을 많이 고르면 여전히 미리보기가 될 수 있다. 필요한 대목을 먼저 발췌하고, 생략된 근거가 판단에 필요한 때만 저장 변수나 `read_result`로 더 읽는다.
