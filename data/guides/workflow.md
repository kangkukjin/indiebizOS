# 워크플로우 저장 & 실행 가이드

## 워크플로우란?

IBL 문장에 **이름을 붙여 저장**하고, 나중에 이름과 인자로 실행하는 기능.
저장본은 `data/workflows/{id}.yaml` 이다.

워크플로우는 몸통이 **IBL 문장**이라는 점에서 `[self:script]`(몸통 = 파이썬/셸 코드)와 갈린다.
몸통을 IBL 엔진이 읽을 수 있으므로 워크플로우는 파싱·재개·통화 승격의 대상이 되고,
script 의 몸통은 원리적으로 그게 안 된다(경계는 argv + stdin/stdout JSON 하나).

---

## 언제 이름을 붙일 값어치가 있는가

이름 붙이는 값어치는 **다시 만드는 비용**에 비례한다. 문장 두세 개짜리 파이프는
그때그때 새로 쓰는 편이 싸다 — 저장할 이유가 없다.

이름이 필요한 자리는 **부르는 쪽이 모델이 아닐 때**다:

- 트리거·스케줄이 반복 호출한다
- 앱 버튼·조종실이 고정된 절차를 건다
- 사람이 인자만 바꿔 가며 되풀이한다

그 외에는 저장하지 말고 즉석 실행(`do`)으로 쓴다.

---

## 저장

```
[self:workflow]{op: "save", name: "동네맛집", description: "도시 이름을 받아 맛집을 찾아 연다",
                do: "[sense:search]{query: \"$city 맛집\", source: \"naver\"} >> [limbs:os_open]"}
```

| 필드 | 필수 | 설명 |
|------|------|------|
| name | ✅ | 워크플로우 이름 (run 에서 workflow_id 또는 name 으로 지목) |
| do | ✅ | IBL 문장 또는 문장 배열 (`steps`·`pipeline` 도 같은 자리) |
| description | - | 설명 |
| params_default | - | `{인자이름: 기본값}` — 호출자가 생략했을 때 채울 값 |

저장 시 name 으로 ID 가 자동 생성된다. 등록 시점에 **문법 관문**이 돌아, 몸통이 없거나
깨졌으면 저장 자체를 거부한다(실행 성공 여부는 run 이 판정한다).

## 시그니처 — 몸통의 `$이름` 이 곧 인자다

몸통에서 **할당되지 않은** `$이름`은 호출자가 채워야 할 인자다. save 가 이것을 계산해
`params_required` 로 저장하고 결과에 보고한다.

```
[self:workflow]{op: "save", name: "동네맛집", do: "[sense:search]{query: \"$city 맛집\", source: \"naver\"}"}
→ {"success": true, "params_required": ["city"],
   "message": "... — 인자 $city 를 받습니다. 실행: [self:workflow]{op: \"run\", ...}"}
```

`list`·`get` 도 `params_required` 를 함께 낸다 — 남의 워크플로우를 부르기 전에 무엇을
요구하는지 먼저 본다.

### 인자 누락은 거절된다

```
[self:workflow]{op: "run", workflow_id: "동네맛집"}
→ {"success": false, "params_missing": ["city"],
   "error": "워크플로우 '동네맛집' 인자 누락: $city ..."}
```

인자를 안 주면 예전에는 `"$city 맛집"` 이 **그대로 검색어가 되어** success 로 완주했다.
저장본에는 save 라는 선언 시점이 있으므로 이제 정직하게 거절한다.
즉석 실행(`do`)은 선언 시점이 없어 거절하지 않고 `params_warning` 으로 알린다.

### 한글에서는 괄호로 경계를 긋는다

이름 경계는 파서와 같은 `\w` 라, 조사·단위가 이름에 먹힌다.
**`$n건` 은 변수 `n` 뒤에 글자 `건` 이 아니라 변수 `n건` 하나다.**

괄호 표기가 그 경계를 긋는다 — `$이름` 과 `${이름}` 은 같은 뜻이다:

```
[table:take]{n: "$n건"}      → 인자 이름이 `n건`  (거의 의도한 바가 아니다)
[table:take]{n: "${n}건"}    → 인자 이름이 `n`   + 글자 '건'
```

경로도 괄호 안에 넣는다 — `${r.file}`. 한글 뒤에 붙는 자리는 괄호를 기본으로 쓰고,
어느 쪽이든 save 가 보고하는 `params_required` 로 확인한다.

## 실행

```
[self:workflow]{op: "run", workflow_id: "동네맛집", params: {city: "청주"}}
```

- `params` 는 `{인자이름: 값}` 객체다. 객체가 아니면 침묵 무시가 아니라 거절한다
  (JSON 문자열은 관용 수용).
- 값이 정확히 `"$name"` 하나면 **원시 타입이 보존**된다(`"$count"` + `{count: 5}` → 정수 5).
  문자열 속에 섞이면 문자열로 임베드된다(`"상한 $count 건"` → `"상한 5 건"`).
- 문장 안 할당(`$x = …`)이 호출자 params 보다 **항상 이긴다**.
- `$it`·`$items`·`each` 의 `as` 이름은 런타임 바인더 소유라 주입되지 않는다(경고).
- `params_default` 가 있으면 생략된 인자를 채우고, 호출자 params 가 기본값을 이긴다.

### 반환값

기본은 몸통 **마지막 문장**의 items 통화다. 그래서 파이프로 이어진다:

```
[self:workflow]{op: "run", name: "동네맛집", params: {city: "청주"}} >> [table:take]{n: 5}
```

몸통에 `$return = …` 할당이 있으면 **그 문장의 결과**가 반환값이 된다 — 마지막 문장이
알림 같은 effect 로 끝나도 된다. 몸통이 effect/scalar 로 끝나고 `$return` 도 없으면
통화가 없으므로 하류 변환자가 정직한 에러를 낸다.

## 파이프라인 연산자

### `>>` (순차 실행)

이전 step 의 결과가 다음 step 에 **자동 전달**된다. 통화는 `{items: [...]}` 하나다.

```
[engines:newspaper]{keywords: "AI, 경제"} >> [limbs:os_open]
```

앞 결과를 **골라서** 쓰려면 자동 전달이 아니라 변수를 쓴다:

```
$r = [engines:newspaper]{keywords: "AI"}
[limbs:os_open]{path: "$r.file"}
```

`$이름 = 문장` 으로 할당하고, `$이름` 또는 `$이름.필드` 로 참조한다(괄호형 `${이름.필드}` 도
같은 뜻). 할당된 변수는 파서가 step 결과 바인딩으로 해소하고, 할당되지 않은 `$이름`은 위의
**인자** 자리로 남는다. (`$prev`·`$result` 같은 자동 이름은 없다 — 이름은 직접 붙인다.)

### `&` (병렬 실행)

여러 step 을 동시에 실행하고 결과를 합쳐 다음 step 에 넘긴다.
각 브랜치에 **90초 타임아웃** — 한 브랜치가 멈춰도 나머지 결과는 정상 수집된다.

```
[sense:search]{source: "gnews", query: "AI", count: 7} & [sense:search]{source: "gnews", query: "경제", count: 7}
```

### `??` (폴백)

앞 step 이 실패하면 뒤 step 을 실행한다.

```
[sense:stock]{op: "quote", ticker: "AAPL"} ?? [sense:search]{query: "AAPL stock price"}
```

### 타임아웃

- 개별 도구 실행: **60초**(IBL 엔진 레벨). 초과 시 에러를 내고 다음 동작으로 간다.
- 병렬 브랜치: **90초**. 타임아웃된 브랜치만 에러, 나머지는 정상.

## 재귀·순환은 거절된다

워크플로우가 워크플로우를 부르는 것은 되지만, 사슬에는 두 관문이 있다.

- **순환**: 같은 워크플로우가 사슬에 다시 나타나면 즉시 거절하고 경로를 보여준다
  (`A → B → A`). 직접 자기호출도, 다른 워크플로우를 거친 상호 호출도 같다.
- **깊이**: 워크플로우 중첩이 상한(`MAX_WORKFLOW_DEPTH`)을 넘으면 거절한다.

반복이 필요하면 재귀가 아니라 반복 어휘를 쓴다 — `[repeat:]{times: N}`, `[table:each]`.

> 참고: "문장 안에 문장" 깊이 상한(`MAX_NEST_DEPTH`)은 워크플로우 몸통에서 0 으로
> 재시작한다. 긴 절차를 워크플로우로 빼라는 안내가 유효하려면 그래야 한다. 대신 위의
> 두 관문이 워크플로우 호출 자체를 센다.

## 생각이 필요한 자리

파이프는 데이터를 기계적으로 나른다. 판단이 끼어야 한다면 두 종류로 갈라 본다.

**① 반복 가능한 판단 — 파이프 안에 넣는다**

- `[table:ai]` — items 를 자연어 지시대로 의미 변환(선별·주석·재구성)
- `[table:brief]` — items 를 근거로 짧은 산문(요약·판정·작명)
- `[self:struct]` — 비정형 입력을 스키마 계약의 items 로

규칙으로 적을 수 있으면 `[table:filter]`·`[table:sort]` 가 먼저다(싸고 결정론).

**② 매번 달라지는 판단 — 얼리지 않는다**

무엇을 볼지가 그때그때 달라지는 작업은 워크플로우로 저장하지 말고, 에이전트가 액션을
하나씩 호출하면서 중간에 직접 생각한다.

## 사용 시나리오

### "OOO 워크플로우 만들어줘"
1. 절차를 IBL 문장으로 적는다. 매번 달라지는 값은 `$이름` 으로 비워 둔다.
2. `[self:workflow]{op: "save"}` — 결과의 `params_required` 로 시그니처를 확인해 사용자에게 알린다.
3. 늘 같은 기본값이 있으면 `params_default` 로 함께 저장한다.

### "그 워크플로우 실행해줘"
1. `[self:workflow]{op: "list"}` 로 id 와 `params_required` 를 확인한다.
2. 인자를 채워 `[self:workflow]{op: "run", workflow_id: …, params: {…}}`.
3. 인자가 빠지면 거절되고 무엇이 빠졌는지 알려 준다 — 사용자에게 되묻는다.
