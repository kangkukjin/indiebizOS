# 방법의 지도 — 도구·방법의 이름을 공급하는 사전

IBL의 어휘는 도구를 가리키고, IBL 문장은 도구를 조합해 일을 한다. 방법의 지도는 이번 일에 쓸 수 있는
추가 도구·방법의 이름을 공급한다. AI가 이름에서 자신이 아는 사용법을 떠올리고 기존 실행 수단에 연결하도록 한다.
지도에 있다는 것과 이 몸에 설치·연결되어 있다는 것은 별개의 사실이다.

## 지도를 그리는 단위

`world.yaml`의 각 항목은 **알아볼 수 있는 이름 → 무엇을 할 수 있는가 → 언제 후보가 되는가**를 연결한다.
도구·라이브러리·프로토콜뿐 아니라 이름 붙은 알고리즘·분석법·설계 방법도 이 형식에 들어갈 수 있다.
자료원도 자료를 얻고 비교하는 수단으로서 포함한다. 현재 목록은 기존 도구 지도에서 시작한 첫 범위다.

| 필드 | 편집 기준 |
|---|---|
| `name` | 모델이 정확한 방법·사용법을 떠올릴 수 있는 통용 이름. 새 이름을 임의로 만들지 않는다. |
| `hint` | 어떤 대상에 어떤 연산을 하여 무엇을 얻는지 한 줄로 쓴다. 분야 소개·장점 나열로 채우지 않는다. |
| `aliases` | 이름을 모르는 사용자가 말할 작업·상황·입력·산출물 표현. 넓은 주제어만으로 채우지 않는다. |
| `path` | 방법을 찾아갈 분류. 같은 문제에 쓸 다른 도구가 함께 보이도록 목적·작업을 드러낸다. |
| `source` | 이름·기능·적용 조건을 확인할 근거. 상세 통로와 한계는 원본에서 확인한다. |

예: ‘제약이 많은 인원 배정’ → `OR-Tools` → ‘제약을 만족하는 배치·일정 최적화’.
프롬프트에는 이름과 짧은 기능 설명만 싣고, 설치·호출 통로는 필요할 때 가이드에서 읽는다.

## 제대로 된 어휘를 주는가

평가 질문은 제품명을 숨긴 **실제 작업**으로 만든다. 답의 허용 집합은 그 일을 해결할 수 있는 도구·방법이다.

- 그 이름을 받으면 실행 가능한 방법이 새로 떠오르는가?
- 주제만 비슷하고 해당 연산은 못 하는 도구가 섞이지 않는가?
- 조건이 다른 유사 작업을 구별하는가? 예를 들어 표 추출·문서 변환·스캔 OCR을 같은 일로 보지 않는다.
- 다른 분야의 유용한 방법과 주제 전환을 놓치지 않는가?
- 실제 응답에서 방법 선택·결과가 나아지는가? 이름 언급·도구 호출 횟수만으로 성공 처리하지 않는다.

현재 선택기는 이름·별칭·설명의 로컬 어휘 검색이다. 위 기준을 자동으로 이해하는 의미 판단기가 아니다.
우선 질문→방법의 대응과 잘못 섞인 후보를 검토해 사전을 고치고, 남는 누락을 근거로 검색 개선을 판단한다.
알려진 정답을 모두 통과시키는 별칭 추가만으로 품질이 검증됐다고 하지 않는다.

## 운영

사용자·모델에 보이는 이름은 **방법의 지도**, 주입 블록은 `<method_map>`이다.
기존 설정·사건·파일 경로의 `knowledge_catalog`는 호환성을 위해 유지한다.
정본을 편집한 뒤 `scripts/build_knowledge_catalog.py`로 색인을 만들고 `--check`로 검증한다.
상세 구조·주입 예산·회귀 기록은 [구현 설계](../../docs/KNOWLEDGE_CATALOG_DESIGN_2026_09_16.md)에 있다.
