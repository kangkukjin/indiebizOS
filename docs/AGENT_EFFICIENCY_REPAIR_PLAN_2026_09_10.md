**3. 의식의 예산 문제는 실행 낭비와 별개로 수리해야 한다**

당시 의식 전체의 누적 입력 한도는 300,000, 최종 예약은 80,000이었다. 계획과 중간 감독은 220,000을 공유했다. 계획의 네 요청 입력은 42,102 → 62,156 → 67,037 → 82,669로 합계 253,964였다. 중간 감독에 쓸 몫이 남지 않았다. 최종 두 요청도 합계 64,020을 쓴 뒤 중단 경계에 걸렸다.[^7]

과거 로그의 중단 문구는 일반적인 사용자 취소다. 시간·사용량 수열과 당시 취소 경로를 함께 보면 예산 중단이라는 설명이 강하게 뒷받침된다. 명시적인 과거 `stop_kind=budget` 기록이 있는 것처럼 단정하지 않는다.

의식은 최초 계획·중간 감독·최종 검수마다 이미 새 AI 인스턴스와 빈 히스토리로 시작한다. 역할 전체의 대화가 끝없이 누적되는 구조는 아니다. **한 번의 계획 안에서** 도구 조회가 여러 번 이어지면서 입력이 커지고, **역할 전체의 비용 계수**가 이를 누적한다. 짧은 상태를 주는 것만으로 모든 문제가 해결되는 것은 아니지만 현재 의도와 맞는 방향이다.

현재 수리안은 최종 80,000을 보호하고 큰 감독 도구 결과를 페이지로 반환하며 소유자·도구 접근 오류를 고친다. 동일 과거 입력 수열을 적용하면 최종 두 요청을 허용하는 것으로 바뀐다. 그러나 계획과 중간 감독은 여전히 220,000을 공유하고, 이미 응답이 시작된 뒤 누적 입력을 보고 끊는 경로도 남아 있다. 중간 감독이 정상화됐다고 결론 내릴 수 없다.

의식만 별도로 작은 하드캡을 가질 필연성은 없다. 실행·내부 제작 AI까지 포함한 작업 전체의 자원 제어가 필요하다. 역할별 배분은 추가 탐색의 가치를 판단하는 소프트 기준이어야 한다. 실제 사용자 지출 한도·제공자 한도·취소·무진척 시간은 별도의 하드 조건으로 둔다. 캐시 포함 누적 입력만으로 금액이나 모델 입력 창 한계를 대신하지 않는다.

**4. 권고하는 정상 작업 흐름**

의식은 계획·이정표 감독·최종 승인의 책임을 유지하고, 실행은 산출물을 만든다. 매 스텝 반성 AI를 추가하지 않는다. 공유 로그를 활용하되 의식이 로그 전체를 항상 다시 읽도록 하지 않는다.

| 시점 | AI가 판단할 일 | 프로그램이 처리할 일 |
|---|---|---|
| 시작 | 원문 논지·사용자 조건·압축 전략 | 원문 1회 보관, 현재 제작법·음성·자원 계약 확인 |
| 원고·구성 확정 | 빠진 논지·왜곡·분량·1인칭·인사말 검사 | 글자 수·예상 길이·장별 원고 대응·지문 계산 |
| 제작 | 장별 창작 또는 예외 대응 | 승인 버전의 노트 반영, 음성 작업, 결합, 렌더, 측정 |
| 이상 사건 | 정체·반복 실패·예산 증가·전제 변경 시 재계획 | 경과 시간·진척·오류를 집계해 한 번의 사건으로 알림 |
| 완료 | 실제 산출물이 목표를 달성했는지 판단 | 길이·음량·파일·노트 정합성 증거와 검수 범위 제시 |
| 승인 후 | 필요한 경우 변경 부분만 작성 | 승인한 응답 바이트와 산출물 버전을 그대로 전달 |

이 사례에서는 **원고 확정 후 음성·영상 제작 직전의 의미 검수**가 가치가 크다. 원 실행에서 빠진 ‘작고 연결된 공동체·다원주의’ 논지를 이때 찾으면 제작 후 재생성을 줄일 수 있다. 렌더 단계의 느린 처리는 원문 전체를 읽는 별도 감독보다 실행 시간·완료 청크·최근 진척·예상 종료 범위로 판단하는 편이 적절하다.

공유 상태에는 원래 요청과 변경 이력, 현행 목표·검수 기준, 현재 단계, 확정된 결정, 산출물 ID·지문, 근거 참조와 확인한 범위, 진행 작업 ID·소유자·경과 시간·최근 진척, 비용·남은 의무 검수를 둔다. 최근 사건은 마지막 확인 커서 이후의 변화만 묶는다. 실행 AI가 매번 별도 장문 보고서를 작성할 필요는 없다. 프로그램이 기록할 수 없는 의미상의 선택만 짧게 남긴다.

새 감독은 이 상태로 시작하고 부족한 근거만 조회한다. 한 번의 감독 내부에서는 방금 읽은 근거를 재사용한다. 8천 자 원문처럼 작고 필수적인 자료는 관련 검수 호출에 한 번 충분히 주는 편이 4천 자 고정 페이지를 여러 번 요청하는 것보다 쌀 수 있다. 중간 감독이 매번 원문을 읽어야 한다는 뜻은 아니다. **동일 자료 한 번의 충분한 전달과, 매 요청의 무조건 짧은 전달은 다르다.**

요약만 믿으면 누락된 논지를 영원히 못 찾는다. 내용 검수에는 원문 구간과 원고의 대응 근거를 두고 의식이 원문에 접근할 수 있게 한다. 실행·감독이 같은 자료를 각각 한 번 확인하는 것은 독립 검증에 필요한 비용일 수 있다. 줄일 대상은 무차별 재조회와 기계적인 복사다.

P0-1은 대규모 계측 플랫폼을 새로 만드는 작업이 아니다. 이미 있는 원장과 스냅샷에 부족한 목적·부모 관계와 표시량을 채운다. 정본 프롬프트·결과를 해시로 보관하고 사건에서 참조하며, 전체 자료를 여러 로그에 또 복제하지 않는다. 민감 내용은 기존 접근 제어를 유지하고 계측 결과에는 크기·지문만 둔다.

3377의 `execution_rounds`는 여러 실행 호출의 최대 라운드 번호만 취해 38회를 17회로 표시했다. 호출별 라운드와 턴 전체 응답 수를 구분하고, 응답 ID가 없는 제공자는 호출 경계와 관측 완전성을 기록한다. 도구 호출 수·모델 응답 수·검수 횟수를 같은 수로 취급하지 않는다. 내용의 숫자·URL이 이미 근거에 있었다는 `retyped` 경고도 그대로 낭비 판정에 쓰지 않는다. 사실 인용과 기계적 본문 복사를 구분한다.

P0-2의 `verbose`는 세부 상태를 보라는 뜻으로 유지할 수 있다. 정본 본문을 두 번 보내는 계약까지 유지할 필요는 없다. 현재 미리보기·턴 변수·그림자 저장소와 연결하고 새 결과 저장소를 중복 구축하지 않는다. 참조는 재실행 없이 해소되어야 한다. 진행 작업·최종 승인용 증거를 24시간 후 지워지는 일반 spill 참조에만 맡기지 않는다.

P0-3은 모든 `tools=[]`를 전역적으로 ‘도구 없음’으로 해석하는 변경이 아니다. 주 CLI 실행자는 별도의 MCP 도구를 사용한다. **원샷 호출자가 명시적으로 선언하는 계약**을 공통화하고 유사한 outline·패키지 내부 호출도 감사한다. 현재 원샷의 호출별 사본·동시 실행 제어를 재사용한다. 슬라이드 생성은 공유 provider와 덱 저장을 확인하기 전 무작정 11장 병렬화하지 않는다.

P0-4에서 단계 시작 전 다음 판단의 예상 크기와 남은 의무 검수를 검사한다. 단, 현재 CLI는 한 프로세스 안에서 여러 모델 왕복을 소유하므로 외부 코드가 각 실제 API 요청 직전을 정확히 통제할 수 있다고 전제해서는 안 된다. 우선 단계 단위 입장 제어·소프트 탐색 한도·응답 회수를 구현한다. 엄밀한 요청별 한도가 필요하면 제공자의 지원 훅을 검증하거나 감독의 도구 왕복을 하네스가 소유하도록 별도 변경해야 한다. 관측 후 취소를 사전 비용 통제로 이름만 바꾸면 안 된다.

3377에서는 두 번째 보완 지시 시 최종 몫이 24,671토큰 남았고, 보완 뒤 재검수 첫 요청은 32,479토큰이었다. **재검수까지 마칠 자원 없이 보완 작업부터 시키지 않는 것**을 독립 완료 조건으로 둔다. 예측은 추정임을 표시하고, 소프트 배분은 조정할 수 있게 하되 실제 사용자·제공자 하드 한도는 존중한다. 한도 때문에 승인할 수 없으면 검수 미완료를 보존하며 성공으로 바꾸지 않는다.

중간 지시에는 대상 문제 ID·목표 버전·근거·유효 조건을 둔다. 3377의 공통 revision 69→75처럼 다른 크롤링이나 단계 진척만으로 지시를 버리지 않는다. 해당 문제의 해소·대상 교체·상충하는 사용자 결정이면 폐기하고, 불확실하면 다음 안전 경계에서 변경 상태만 대조한다. 취소·쓰기 지시의 엄격한 신선도 검사는 유지한다. 단순히 stale 방어를 제거하거나 판단마다 실행을 멈추는 변경은 하지 않는다. 로그에는 판단 완료와 실제 적용, 불필요해짐, 충돌·재검증 대기를 따로 남긴다.

P0-5는 감독이 조사 범위까지 책임진다는 뜻이다. 3377의 ‘서로 다른 직역에서 성립 사례 3개’는 사용자 지정 조건이 아니라 의식이 만든 조사 목표였다. 여러 사례를 찾는 것은 유용하지만, 사례의 존재 자체를 보장할 수는 없다. 필수 정확성 조건과 조정 가능한 탐색 목표를 분리하고, 찾지 못했을 때 허용되는 제한적 결론도 계획에 둔다. 재계획은 기준의 출처·이유·버전을 남기며 사용자의 필수 조건을 조용히 낮추지 않는다.

REWORK는 `미해결 기준 → 필요한 변경 → 인정할 증거 → 찾지 못했을 때의 종료 조건`을 한 묶음으로 전달한다. 3377처럼 첫 지시의 ‘1~2건’ 중 1건을 채운 뒤 같은 미달로 또 보완시키는 모호성을 줄인다. 보완 문맥에는 원래 요청·현재 기준·미해결 항목·대상 지문·관련 증거·편집 위치·진행 작업만 선별한다. 이력 전체 재개와 별도 문맥 중 실제 비용·재탐색·시간이 나은 쪽을 검증해 선택한다. 단순 편집 여러 건은 한 패치 묶음으로 실행하되 충돌·부분 실패를 정직하게 반환한다.

P0-6은 도구 이름이 patch인지가 아니라 **실제로 새로 생성한 범위**를 검증한다. 3377은 하나의 블록을 두 번 교체하면서 새 답변의 70.6%·85.3%에 직전 문구가 다시 실렸다. 지문 보호를 유지한 범위·문단 수정과 재조립으로 줄인다. 단순 문자 절단으로 표·코드를 깨거나 블록 ID를 불안정하게 바꾸지 않으며, 삽입·삭제·다중 편집·충돌·커진 블록을 회귀에 포함한다.

P1-1은 권한 축소가 아니다. 허용된 기능을 숨겨 “나는 못 듣는다”는 문제가 재발하지 않게 한다. 이름·짧은 설명·상세 조회 수단은 항상 남기고, 자주 쓰는 작업의 계약은 한 묶음으로 미리 제공한다. 현재 허용 노드/액션 설정은 권한 의미를 유지한다. 매 라운드 시스템 접두부를 새로 정렬하면 캐시를 깨뜨릴 수 있으므로 기본부를 안정화하고 선택 상세는 단계 안에서 재사용한다.

P1-2의 제작법에는 버전·적용 조건·입출력·검증 방법·실패 시 복구만 담는다. 사용자 목소리·인사말·취향은 출처와 범위를 가진 데이터로 남긴다. 오래된 전체 작업 이력을 ‘프로토콜’에 다시 붙이지 않는다. 변경이 확인됐을 때만 해당 계약이나 오류 구간을 열어 본다. 원문·원고·HTML·음성을 모델이 서로 복사하지 않고 참조와 프로그램으로 전달한다.

P1-3은 성공 메시지나 파일 존재만으로 승인하는 변경이 아니다. 산출물 지문뿐 아니라 검사 기준·검사기 버전·검사 범위도 같아야 증거를 재사용한다. 이미지가 같아도 실제 영상의 타이밍·소리·최종 인코딩은 다른 증거가 필요하다. 원고 변경 시 관련 음성·자막·타이밍·최종 영상의 의존 관계를 따라 무효화한다. 최종 응답 `response-vN`의 승인 지문이 현재 바이트와 일치할 때만 그대로 전달한다.

P2는 앞선 변경 이후에도 일반 실행 문맥이 큰 경우 적용한다. 현재 300,000 세션 리셋 기준은 주로 **호출 사이의 재개 시점**에 적용되고, 보완 재개는 실제 로그에서 기존 세션을 유지했다. 한 CLI 호출 내부의 커진 이력을 잘라 주는 기능은 아니다. 임계값만 낮춰도 3364의 22회 내부 루프가 바로 작아지지는 않는다. 먼저 불필요한 결과의 유입을 막고, 3377에서 드러난 보완 경계를 P0-5로 검증한 뒤 일반 단계 교체로 확장한다.

**6. 정상 예산과 절감 목표를 어떻게 정할 것인가**

현재 자료만으로 “영상 한 편은 정확히 몇만 토큰이면 충분하다”는 최소치를 산출할 수 없다. 모델·디자인·음성 조건·실패·검수 범위가 다르고 통제된 재주행을 하지 않았다. 그렇다고 이번 소비를 정상 비용으로 받아들일 이유도 없다. 첫 입력과 정확한 결과 중복처럼 **행동 품질을 희생하지 않고 줄일 수 있는 부분**부터 제거할 근거는 충분하다.

1차 통합 수리의 **설계 목표**는 동급 영상 작업에서 캐시 포함 누적 입력 50% 이상, 캐시 읽기를 제외한 입력과 출력 합계 30% 이상 감소로 둔다. 3364를 산술 기준으로 삼으면 각각 약 347만 입력, 약 50만 비캐시 입력+출력 이하다. 이는 충분히 낮아졌다는 최종 판정선이나 새 실행 하드캡이 아니다. 현재의 명백한 중복과 거대한 시작 입력을 고쳤는지 확인하는 첫 목표이며 아직 달성 실측은 없다. 이를 통과해도 기본 입력·탐색·창작 출력의 남은 비중을 다시 본다.

3377은 다른 작업·모델이므로 영상 기준의 전후 비교 표본으로 합치지 않는다. 3377의 비캐시 입력+출력은 약 62.9만으로 3364 약 71.6만보다 작지만 최종 검수는 또 미완료였다. 조사 작업은 별도의 기준으로 **지시 적용률·근거 충족·보완 횟수·판정 회수·전체 응답 수·캐시를 구분한 비용**을 함께 평가한다. 특히 보완 입력 739만의 대부분은 캐시 읽기이므로, 새 문맥으로 원시 입력만 줄이고 실비·품질을 악화시키면 채택하지 않는다.

한도를 정하는 데이터는 **성공한 동일 품질 작업**에서 얻는다. 역할별 예산이 작다는 이유로 검수를 생략한 싼 실패와 비교하지 않는다. 측정 항목은 누적 입력·캐시 읽기/쓰기·출력/추론·요청 수·최대 문맥·도구 표시량·왕복 수·재작업·경과 시간·실제 얻을 수 있는 비용/한도 정보다. 알 수 없는 구독 차감은 별도 미상으로 둔다.

검증은 다음 순서로 진행한다.

1. 저장된 3364 결과로 중복 제거·페이지 조회·오류 보존을 오프라인 검증한다. 입력 크기만 같게 재생한 예산 검사는 정책 검증이지 새 모델 행동의 증거가 아님을 유지한다.
2. 한 줄 텍스트 원샷·한 장 슬라이드·이미지 입력에서 동일 모델·동일 내용으로 도구 모드와 프롬프트 전후를 비교한다. 실제 요청·결과·사용량으로 숨은 CLI 부하와 문법 발견 손실을 확인한다.
3. 3364의 저장 원문·조건과 대표적인 몇 개의 다른 글로 원고·구성·제작 전 검수를 비교한다. 캐시가 찬 경우와 비어 있는 경우를 분리하고 일부 반복 측정으로 변동을 본다. 기존 TTS/렌더 자산을 재사용할 수 있는 품질 동등성 시험부터 한다.
4. 통합 영상 재주행에서 원문 핵심 논지, 1인칭, 본인 음성 경로, 인사말, 길이, 원고·노트 일치, 잘림·가독성, 음량·클리핑, 실제 오디오/영상 검수와 원격 자원 회수를 확인한다. 후속 수리본의 논지 복원을 품질 체크리스트에 포함하되 과거 원 실행의 성공으로 소급하지 않는다.
5. 느리지만 진행되는 TTS, 진짜 정체, 부분 실패, 원고 수정, 예산 근접, 재개 상황을 넣는다. 필요한 감독은 작동하고 정상 진행에서는 같은 사건으로 계속 호출하지 않는지 확인한다.
6. 3377의 비동기 감독을 재현한다. 무관한 크롤링 진척 중 유효 지시는 다음 안전 경계에 전달되고, 관련 문제가 실제 해소되거나 목표가 바뀌면 폐기되는지 양쪽을 검사한다. 검토 횟수 1과 적용 횟수 0을 혼동하지 않는다.
7. 최종 검수의 보완 계약·남은 재검수 자원·17+11+10 응답 집계·텍스트 블록 확대를 재현한다. 한 번에 알 수 있었던 미달은 묶어 보완하고, 부분 수정 후 ‘유일한 사례’·개수·결론·출처 등 연결된 주장의 불일치를 검사한다. 새로 생긴 결함은 새로운 근거로 별도 기록한다.

검증 실패 시 상세 스키마 선택·표시 축약·문맥 교체를 각각 되돌릴 수 있게 한다. 상태나 오류를 잃는 절감은 채택하지 않는다. 실제 회귀는 동작 변경에 맞춰 수행한다. IBL 표현·계약을 바꾸는 단계는 정본 YAML/문서에서 생성하고 `build_ibl_nodes.py --check` 등 저장소 관문을 통과시킨다. UI에 비용·역할 설정을 노출할 때는 프런트엔드 타입 검사도 포함한다.

**7. 다른 시스템의 방식과 이번 설계의 현실성**

Anthropic의 MCP 효율화 사례는 모든 도구 정의와 중간 결과를 모델 문맥에 싣는 문제를 지적하고, 필요한 정의 조회·프로그램 내부 데이터 처리·참조 전달을 권한다. indiebizOS에는 이미 IBL·변수·스크립트가 있으므로 새 에이전트 프레임워크를 추가할 필요가 없다. 기존 실행 언어의 표시·조회·재사용 경계를 고치는 것이 해당 원칙의 적용이다. 해당 글의 98.7% 절감 예시는 특정 도구 목록 비교이므로 이번 작업의 예상 절감률로 사용하지 않는다.[^8]

효과적인 도구 설계에 관한 다른 Anthropic 자료는 필요한 의미 정보, 간결/상세 출력, 선택 조회와 평가를 강조한다. 여기서는 정확한 오류·증거를 남기면서 중복 본문만 제거하고, 상세를 열기 위해 동작을 반복하지 않는 계약으로 적용한다.[^9]

장기 작업 하네스 사례의 재사용 가능한 준비 절차와 진행 산출물은 매 세션 작업 환경을 재발견하지 않게 하는 참고가 된다. 이번 영상에는 최신 제작법 계약과 버전 있는 원고·작업 핸들이 그 역할을 한다. 코딩 벤치마크의 성과를 영상 제작 성과로 그대로 옮겨 주장할 수는 없다.[^10]

Magentic-One의 계획·진척 장부, LangGraph의 감독 메시지 정책, 관측 가림과 모델 요약의 비용 비교 등은 앞선 심층 진단에 출처와 한계를 정리했다. 공통으로 참고할 점은 감독의 책임을 유지하면서 전달 문맥·추가 호출·종료 조건을 명시적으로 관리한다는 것이다. 매 스텝 새 AI에게 장문 반성문을 쓰게 하는 것은 이번 증거에 맞는 처방이 아니다.[^7]

**현실성 판정은 높다.** 정확한 중복 제거와 원샷 설정은 이미 있는 경계의 결함 수정이고, 제작법 재사용도 기존 IBL·스크립트 구조 안에서 가능하다. 상세 도구의 선택 노출과 단계별 문맥 교체는 기능 발견·캐시·작업 재개에 영향을 주므로 뒤에 검증하며 적용한다. 더 많은 에이전트를 추가하는 것보다 우선할 수리다. 필요한 원고 판단과 제작 전 감독에는 자원을 쓰고, 같은 매뉴얼·로그·본문을 다시 읽고 다시 옮기는 데 쓰는 자원을 줄이는 계획이다.
