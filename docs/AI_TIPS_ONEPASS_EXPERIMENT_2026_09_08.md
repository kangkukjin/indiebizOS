## 실제 수확과 품질

검색 다섯 갈래 → 중복 제거 54편 → 기존 원장 제외 후 49편 → 날짜 확인 49편 성공 → 180일 통과 24편.
선정 4편의 자막 모두 확보 → 1차 제목 후보 31개 → 선정·상세 13개(영상별 3·4·3·3).

기계 검산:

- 13개 팁 모두 저장된 자막에 근거 발췌가 존재한다. 시간 표기도 13개 모두 있으며 timestamp 오류 표식은 없다.
- 복구한 자막 1,527개 구간의 본문이 저장된 원본 JSON과 모두 같다.
- 확인한 영상 ID 집합과 최종 원장 델타 ID 집합이 모두 49개로 일치한다.
- 누적 팁 581→594, 다룬 영상 151, 전체 후보 등재 1,273. 보고서 머리줄과 갱신 후 원장이 일치한다.
- 팁 제목 13개·필수 섹션 6개·로컬 함의 줄 13개. HTML 링크 17개, 변환기의 dropped_lines 13개.
- 기존 운영 원장·팁 DB는 수정하지 않았다.

**근거 발췌의 존재는 방법 전체가 원문에 의해 뒷받침된다는 증명이 아니다.**
영상을 직접 보거나 제안된 명령을 실제로 실행하지 않았다. 작성 결과를 읽어 평가한 품질은 다음과 같다.

1. **출처 추적과 문서 형식은 유용하다.** 원시 오류·회귀 검사·재현 조건·bisect 등의 절차를 팁 단위로 재조직했다.
   명령어가 없는 영상은 없는 그대로 표시했고, 철자가 불확실한 고유명사도 표시했다.
2. **자료 다양성은 미달이다.** 실제로는 네 편 모두 영어다. 선정 AI가 한국어 검색 갈래를 한국어권 영상의 근거로 잘못 썼다.
   회의론 검색에서 나온 강의도 실제 회의론인지 확인하지 않았다. 복구 단계의 작성 지시에 이 한계를 명시하도록 보강했다.
3. **일부 팁은 혼자 따라 하기 어렵다.** MCP 로그 확인·단독 실행 팁에는 핵심 경로·명령이 없다.
   선정 후 본문이 이런 상태이면 해당 팁/영상을 교체하는 관문이 필요하다.
4. **편집의 추론이 과하다.** 적은 시연 건수 자체를 매번 과장으로 비판하거나,
   브라우저 UI 테스트를 하네스에 ‘해당 없음’으로 단정하는 함의는 사용자 맥락을 충분히 이해한 편집이라고 보기 어렵다.
5. **공유판의 개인 맥락 제거도 불완전하다.** `우리 시스템 함의` 줄은 제거됐지만 시도 후보에 현재 작업의 커밋명이 남았다.
   입력 팁에 없던 현재 작업의 구체적 맥락이 산문에 섞인 흔적이다. 정확한 유입 경로는 이번에 규명하지 않았다.
   로컬 실험판만 만들었으며 공유창고에는 등재하지 않았다. `dropped_lines == 팁 수`만으로 공유 적합성을 보장할 수 없다.

따라서 **읽어볼 만한 초안은 생성됐지만, 가이드를 충족하는 무인 발행본은 아니다.**
형식 계수와 근거 앵커 검사가 통과해도 자료 선정·함의·공유 범위를 별도로 평가해야 한다.

## 세 가지 실행 마찰

### 1. 자막의 통화와 본문이 다르다

첫 코드가 자막을 `self:write{format:"json"}`으로 저장해 `{items:[{start,text,…}]}`만 남겼다.
첫 추출은 원래 자막 봉투를 받으므로 성공했지만, 두 번째 `self:struct{file:…json}`는 이를 본문 없는 표로 거절했다.
`grounded`나 `known`을 끄지 않았다. 저장된 구간을 `table:reduce`로 `[MM:SS] 본문`에 모아 txt로 쓰고 재개했다.
이는 내 프로그램의 직렬화 선택과 소비자 계약의 불일치다. ‘어떤 items든 원문’으로 받게 만드는 것은 올바른 수리가 아니다.
시간 구간 자료임을 보존하는 입출력 계약이나, 그 계약을 만족시키는 결정론 관용구가 필요하다.

### 2. 블록의 파싱 실패가 성공으로 위장됐다 — 이번에 차단

`ibl_parser_blocks._parse_block_body()`가 `IBLSyntaxError`를 잡고 `None`을 반환했다.
본문 안에서 바깥 변수로 파이프를 시작하면 안쪽 파서가 그 변수를 못 보고 오류를 냈고,
본문은 빈 분기로 바뀌었다. `check:true`도 이를 통과시켰다.
복구 호출은 조건을 충족했다는 `success:true`만 내고 저장 액션을 전부 생략했다.

이번 수리는 **비어 있는 본문과 해석 실패를 구분해, 해석 실패를 실행 전에 거절**하도록 바꾼 것이다.
기존 try/catch의 문맥 있는 오류 안내는 유지한다. 첫 프로그램을 수리된 파서에 다시 넣자,
AI를 호출하기 전에 `블록 본문 해석 실패: 변수 $정보…`로 거절했다.
**바깥 변수로 시작하는 블록 파이프의 지원까지 구현한 것은 아니다.** 그 조합 능력의 공백은 남아 있다.
이를 구현할 때는 일반 파이프·병렬 분기·중첩 블록·함수 몸의 바인딩을 함께 검증해야 한다.

### 3. each의 예산이 입력의 일부를 남겼다 — 프로그램을 집합 연산으로 변경

49행마다 `filter → reduce → take → compute → select`를 실행하므로 245단계가 필요했다.
`each`의 하위 단계 상한은 200이다. 결과 40행만 나온 채 전체 프로그램은 성공을 반환했다.
봉투에는 예산 초과가 적혀 있었다. 내가 상한을 설계에 반영하지 못했고 저장 직전 동일 ID 집합 검법도 넣지 못했다.
표시에는 ‘입력 41행·8건 미처리’라고 나왔지만 실제 최종 누락은 49−40=9행이었다.

상한을 늘리지 않았다. 팁이 있는 영상은 `join`, 나머지는 `not_in`, 두 집합은 `union`으로 합치고
한 번의 `compute/select`로 원장을 만들었다. 49행 전부 기록됐고 AI 추가 호출은 0회였다.
헤더와 한계 절의 후보 등재 수를 `self:edit`로 바꾸고 등록된 `보고서HTML`로 다시 렌더했다.

## 개선 순서

1. **언어가 코드 일부를 잃어버리지 않게 한다.** 이번 파싱 실패 차단을 시작으로 블록 변수 바인딩을 완성하고,
   실제 보고서의 전체 프로그램을 회귀 재료로 둔다. 개별 액션 테스트만으로는 이 조합 오류가 잡히지 않았다.
2. **완주 조건을 데이터로 집행한다.** 파일 존재뿐 아니라 조회 ID=원장 ID, 팁 수=본문 항목 수,
   누적 수 일치, 미처리=0, 공유 금지 필드=0을 기계로 확인한 뒤 완료를 반환한다.
3. **AI 없는 중간 관용구를 먼저 검증한다.** 시간 구간을 원문으로 보존하기,
   선정 키로 원본 출처를 다시 붙이기, 전체 키를 보존하면서 판정 원장 만들기가 이번에 실수·복구 작문을 만든 단위다.
   보고서 전체나 AI 추출 단계를 상시 관용구로 승격할 이유는 없다.
4. **판정자의 일을 줄이고 판정 재료를 개선한다.** 평가 14회가 입력의 약 42%·85.9초를 썼다.
   수·타입·ID 보존은 기계 검법으로 옮길 후보다. 현재 평가자는 결과 앞 6,000자와 지시 일부를 보며,
   원문 전체와의 의미 대조를 수행하는 구조가 아니다. 비싼 평가 호출이 품질 보증과 같지는 않다.
5. **선정의 증거를 보존한다.** 검색 갈래, 실제 자막 언어, 주제 관련성, 실제 반대 주장 근거를 다른 필드로 둔다.
   정독 후 부실하면 미리 정의한 교체 경로를 타거나 부족하다고 끝내야 한다.

상시 프롬프트에 이름을 더 넣는 실험보다, 위 세 가지 결정론 조합과 완주 검법을 갖춘 뒤
같은 입력·같은 품질 기준으로 반복 비교하는 실험이 다음 순서다. 이번 실행은 개선 여지가 없다는 증거가 아니다.
