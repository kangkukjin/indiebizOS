# Android 연속 제어의 실행 비용 조사와 설계

2026-10-24. 상태: **조사·설계만 완료 대상으로 한다. 아래 제품 기능은 미구현이다.**
앞서 적용한 [중복 관측 축소](ANDROID_CONTROL_OBSERVATION_COST_2026_10_24.md)와 별개다.
목적은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)에 따라 검증 가능한 여러 동작을 한 번에
맡기고, 결과와 부분 실패를 보존하면서 완료 시간과 반복 표현을 줄이는 것이다.

## 1. 판단

**한 작업 안에서 여러 동작을 순서대로 실행하는 방식은 투자 가치가 있다.**
일회용 Python 프로세스는 유지하고, 준비·전송·시작·종료를 짧은 동작 묶음마다 한 번씩만 한다.
현재의 단일 제어 호출은 유지하며, 한 번 누르는 조작까지 기다렸다가 강제로 묶지는 않는다.

첫 제품 범위는 조회와 명시적인 OS 설정 변경이다. 화면을 읽고 새로 판단하는 작업은
그 판단 지점에서 묶음을 끝낸다. 임의 앱의 화면 이동까지 일반화하는 것은 별도 단계다.
프로세스를 계속 살려 두는 최적화는 취소·격리를 다시 설계해야 하므로 이번 권장안에서 제외한다.

예상 규모는 익숙한 개발자 1명 기준 조회 전용 시범 1~2일, 취소·부분 결과·설정 변경까지
제품화 4~7인일이다. UI 연속 제어는 여기에 5~8인일을 더 잡는다. 실측된 개발 일정이 아닌
아래 변경 범위에 근거한 초기 추정이며, 기기별 설치·인수 대기는 별도다.

## 2. 현재 경로에서 반복되는 것

`data/idioms/android_control.ibl`의 한 호출은 다음 순서다.

1. 대상 손발 조회, 등록·연결·Android·실행 계약·Python 준비·화면 문맥 검사.
2. 선택한 primitive 원문 읽기, `data/scripts/android_control.py`로 요청 검증·UUID·지문 생성.
3. 검증기 원문과 primitive를 포함한 Python을 `limbs:guestpc`로 접수.
4. 폰 `limb_client`가 작업을 받아 `phone_remote_execution.execute` 호출.
5. `RemoteExecutionBridge`가 직렬 잠금, 작업 파일, 별도 service/Chaquopy worker를 준비.
6. 실제 OS 호출과 결과 검증. worker 종료·자식 및 자원 회수 확인.
7. 결과 사건을 허브로 보내고, 원래 준비·접수 영수증과 관측을 대조.

호출자가 IBL 한 문장에 `Android제어`를 세 번 적어도 3~7번은 세 번 발생한다.
현재 `PC조회묶음` 역시 대상·원문 준비를 공유하지만 내부 작업은 각각 접수한다.
이를 그대로 복제하면 일부 준비 비용만 줄고 worker 시작 비용은 남는다.

`prepare`는 primitive만 보내지 않고 검증기 자체도 넣는다. 이번 조회 실험의 전송 코드가
약 32 KB였으므로 세 번을 한 번으로 묶으면 코드 전송량도 약 96→32 KB가 된다.
이 바이트 감소를 모델 토큰 절감량으로 환산하지 않는다. 원문이 반드시 모델에 노출되는 것은 아니다.

폰의 기존 `op:ibl`은 상주 백엔드에서 실행한다. 음악 중지→큐 조회처럼 그 경로로 이미
표현되는 조합은 그대로 쓴다. 그러나 현재 실행 중인 동기 IBL은 `limb_client._cancel`에서
중단하지 못한다. 속도만 보고 Android 제어를 상주 IBL에 옮기면 일회용 실행의 취소·격리
계약이 약해지므로 대체 수단으로 채택하지 않는다.

소유 위치:

| 책임 | 현행 소스 |
|---|---|
| 대상·준비·원 영수증 대조 | `data/idioms/android_control*.ibl`, `data/scripts/android_control.py` |
| OS 조작과 관측 | `data/instruments/phone_control.py`, `phone_device.py`, `phone_ui.py` |
| 전송·중복 접수·사건 | `backend/services/resident_pcs.py`, `backend/base/resident_store.py`, `backend/services/limb_client.py` |
| 실행 수명·취소·회수 | `backend/services/phone_remote_execution.py`, APK `execution/RemoteExecutionBridge.kt` |
| worker와 프로세스 간 호출 | APK `execution/RemoteExecutionService.kt`, `app/src/main/python/phone_exec_worker.py` |

## 3. 읽기 전용 실험

### 방법과 한계

연결된 예나폰(Android API 33/arm64), 삼성0(API 36/arm64), 삼성1(API 28/arm32)에서
같은 현행 `run_device`와 `phone_control.py`로 미디어 음량 **조회만** 수행한다.
실제 음량·설정·앱 화면·재생은 변경하지 않는다. 조회 과정의 기존 잠금·작업 기록 파일은 생성된다.

각 폰에서 개별 worker 3개와 worker 하나 안의 3회 조회를 두 차례 비교한다.
순서는 1차 개별→묶음, 2차 묶음→개별로 바꾼다. 총 24개 작업, 36회 조회다.
두 경로 모두 동일한 소스를 보내고 `run_device` 검증을 각 회 수행한다. 원격 작업은
background 접수 후 같은 task_ref를 wait하며, 실패·불명 시 변경 재전송은 하지 않는다.

이것은 **실행 묶음의 비용 분리 실험**이다. 공개 `Android제어`의 대상 선택·준비 영수증·최종
영수증 검증 전체를 벤치마크한 것이 아니다. 제안하는 단계 원장과 취소 관문도 아직 없다.
제품의 최종 지연이나 UI 앱 실행 성능으로 간주하지 않는다. LLM 호출도 없다.

호출자 `monotonic`으로 접수→wait 반환까지 재고, APK의 `elapsed_ms`는 service bind 시작부터
worker·자원 회수까지의 구간으로 읽는다. 두 값의 차이는 전송·큐·폴링·허브 처리 등을 포함하며
전부 네트워크 지연이라고 단정하지 않는다. 폰·허브 벽시계의 차이로 편도 전송 시간을 계산하지 않는다.
내부 `step_seconds`는 primitive 컴파일·브리지 초기 접근·실제 조회·검증을 포함한다.

| 폰 / 설치 APK | 차수 | 개별 3회 합계 | 3회 묶음 | 관측된 단축 |
|---|---:|---:|---:|---:|
| 예나폰 / 0.18 | 1 | 15.46초 | 4.69초 | 69.7% |
| 예나폰 / 0.18 | 2 | 16.63초 | 4.77초 | 71.3% |
| 삼성0 / 0.19 | 1 | 14.51초 | 3.88초 | 73.2% |
| 삼성0 / 0.19 | 2 | 12.38초 | 4.73초 | 61.8% |
| 삼성1 / 0.20 | 1 | 71.72초 | 7.78초 | 89.2% |
| 삼성1 / 0.20 | 2 | 35.86초 | 13.95초 | 61.1% |

24개 작업이 모두 succeeded였고, 36회 조회가 모두 검증됐으며 worker·자원 회수도 확인됐다.
개별 작업의 APK 실행 구간은 예나폰 2.27~2.44초, 삼성1 2.57~2.65초, 삼성0 0.77~0.97초였다.
3회를 묶어도 각각 2.31~2.34초, 2.63~2.65초, 0.78~0.79초로 비슷했다.
첫 조회는 0.026~0.085초, 같은 worker의 다음 조회는 0.005~0.017초 수준이었다.

따라서 worker 반복 제거의 이득은 확인된다. 삼성1은 전체 지연의 변동이 매우 크므로
표의 89.2%를 고정된 효과로 채택하지 않는다. 서비스 밖 대기를 분리 조사할 여지도 있다.
설치 APK 버전이 서로 다르고 새 0.22 설치는 이 실험에서 수행하지 않았다. 이번 경로는
기존 음량 조회이므로 직전 설정 관측 축소 변경의 전후 비교도 아니다.

근거의 로컬 원본은 `outputs/android-sequence-study/measurements.json`이다.
로컬 재현 스크립트는 `outputs/android-sequence-study/probe.py`에 보존했다.
음량 값·키·원격 코드 본문을 제외한 [측정 기록](experiments/android_control_sequence_2026_10_24/measurements.json)은 Git에 보존한다.
반복 수가 적고 통신 상황이 달라 p95나 일반적인 배수 향상은 주장하지 않는다.

### 효과가 생기는 범위

개별 동작 비용을 준비 P, 전송·대기 R, worker 시작·정리 W, 실제 동작 A로 두면
N개 개별 실행은 대략 `N×(P+R+W)+ΣA`, 한 묶음은 `P+R+W+ΣA+단계 기록 비용`이다.
절감의 주된 후보는 `(N−1)×(P+R+W)`다. 앱 로딩이나 외부 서비스 응답 시간은 그대로 남는다.

- 여러 OS 설정을 연속 적용하거나 정해진 점검을 할 때 효과가 크다.
- 음량 버튼 한 번 등 N=1인 조작에는 이 방식 자체의 이득이 거의 없다.
- 화면을 매번 AI가 해석해야 하면 그 사이를 합칠 수 없다. 이미 지원하는 절반 음량처럼
  조회→계산→변경을 한 primitive에서 하는 기능에 다시 쪼갠 조회를 추가하지 않는다.
- 기존 앱 실행 결과에 새 screen이 들어 있으면 별도 snapshot을 붙이지 않는다.
- 최근 TV 에피소드의 잘못된 경로 탐색·반복 실패·모델 판단 시간은 이 최적화로 해결되지 않는다.

## 4. 선택지와 비용

| 선택지 | 줄이는 비용 | 예상 규모 | 판단 |
|---|---|---|---|
| 호출자에서 대상·원문 준비 공유 | 주로 P | 0.5~1인일 | 보조 개선. 권한·연결·화면을 과거 값으로 캐시하면 안 됨 |
| 일회용 worker 하나에 유한한 순차 작업 | P·R·W 반복 | 조회 시범 1~2인일, 설정·복구 포함 4~7인일 | **권장** |
| 같은 worker를 여러 사용자 요청에 계속 재사용 | 단건에서도 W 일부 | 10~20인일 이상, 불확실성 큼 | 초기화·전역 상태·취소·메모리 격리 재설계가 필요하므로 후순위 |

위 수치는 개발·관련 회귀·두 ABI 실기기 인수를 포함하는 범위 추정이다. 단순 반복문은 작지만,
중간 사망 뒤 이미 바뀐 설정을 다시 바꾸지 않는 계약까지 만드는 비용은 훨씬 크다.

## 5. 권장 인터페이스와 실행 계약

새 코어 어휘·파서 문법은 만들지 않는다. 기존 `self:script`와 `limbs:guestpc` 위에
사전 관용구와 등록 스크립트 부품을 둔다. 아래 이름·형식은 **미구현 제안**이다.

```ibl
[fn:Android연속제어]{대상:$폰,요청들:[
  {action:"brightness",value:120},
  {action:"rotation",enabled:false},
  {action:"timeout",seconds:120}
]}
```

초기 지원은 `volume_status`, `status` 조회와 `volume`, `brightness`, `brightness_auto`,
`rotation`, `timeout`의 명시적 설정으로 제한한다. sensor·진동·권한 화면·화면 전원·손전등·
UI 조작·상대 음량 변경과 복원은 첫 범위에서 제외한다. 기존 단건 기능은 그대로 사용한다.

기본 제한 제안은 1~8단계, 작업 전체 30초, 단계별 기존 검증 제한과 전체 남은 시간 중
작은 값이다. 시간 만료는 성공이 아니다. 무한 대기·자동 반복·실행 중 계획 수정은 없다.
대상은 한 폰이며 순차 실행한다. 다른 폰의 독립 작업은 기존 IBL 조합으로 표현한다.

준비는 요청 전체를 먼저 검증하고 원문을 종류별 한 번씩 읽는다. 계획에는 대상 device_id·
등록 generation·sequence_id·순서가 있는 단계 ID·정규화 요청·primitive/helper 지문을 묶는다.
canonical JSON 지문을 접수 request_id와 연결한다. 기존 등록 generation은 재등록된 폰에
옛 요청이 연결되는 것을 막으며, 같은 ID에 다른 내용이면 현행 접수 충돌처럼 거절한다.
장치 관측·권한은 캐시하지 않고 각 단계에서 읽는다.

폰 안에서는 기존 `run_device` 검증을 단계마다 수행한다. 하나가 failed/unknown이면 뒤의
단계는 실행하지 않는다. 모두 끝났을 때만 전체 completed이며, 각 단계의 검증 시점과 값을
보존한다. 뒤의 설정이 앞의 설정을 덮으면 앞의 관측을 최종 상태라고 주장하지 않는다.
부분 성공을 전체 실패로 뭉개지 않고 `completed_steps`, `failed_step`, `not_started_steps`를 반환한다.
자동 롤백은 하지 않는다. 중간에 사람이 바꾼 값을 옛 값으로 덮을 수 있기 때문이다.

## 6. 취소·단계 기록·재조회

현행 worker는 결과 전체를 마지막에 한 번 기록한다. 중간에 죽으면 묶음의 앞 단계가
완료됐어도 결과가 없을 수 있다. 그래서 제품화에는 **worker 밖 부모의 단계 원장**이 필요하다.

APK의 기존 worker→parent IPC에 단계 시작·완료 요청을 붙인다. 별도 Kotlin 부품으로 원장을
분리하며, parent가 실제 job_id·generation·계획 지문에 묶어 처리한다. worker가 보낸 임의
경로를 쓰지 않고 `remote_runs/<job_id>/` 아래 고정 파일만 원자적으로 교체한다.
단계 결과의 지문·크기 제한·flush/fsync와 디렉터리 동기화 실패를 명시적으로 처리한다.

1. 계획을 원장에 먼저 보존하고 그 확인 응답을 받은 뒤 첫 단계로 간다.
2. 부모가 취소 여부와 다음 순서를 같은 잠금 안에서 검사하고 `started`를 영속화한 뒤 허가한다.
3. worker가 한 번 실행·관측·검증하고, 부모가 그 결과를 영속화해 확인해야 다음 단계로 간다.
4. 취소 접수 후 새 단계 허가를 내지 않는다. 이미 허가된 단계는 실행됐을 수 있다.
   기존 프로세스 종료·자원 회수 확인은 유지한다. 취소는 OS 변경의 취소나 롤백이 아니다.
5. 원장 쓰기 실패·확인 응답 유실이면 다음 단계로 가지 않는다. 이미 시작한 단계의 상태는
   재조회 전까지 unknown이다. 시작 기록만 있어도 실제 OS 변경이 일어났다고 단정하지 않는다.

작업 결과에는 짧은 단계 요약과 원장 지문을 담고, 큰 결과는 기존 value_ref/transfer로 회수한다.
현재 64 KiB inline 결과 제한을 넘는 화면 묶음을 그대로 돌려주지 않는다.
원장은 기존 완료 작업 7일 보존·전송 중 pinning과 연결한다. 부모 재시작 때 미완료 작업의
시작 단계는 unknown, 시작되지 않은 단계는 보존된 계획과 연속 원장으로만 판정한다.
손상·만료로 근거가 없으면 임의로 not_started나 completed를 만들지 않는다.

재조회는 원래 task_ref·계획·접수 영수증을 사용한다. 종료가 확인된 원 작업의 원장을 기존
읽기/transfer 경로로 가져와 요청·순서·지문을 재검증한다. 재조회가 실행을 다시 시작하지 않는다.
`unknown` 단계는 재전송하지 않는다. 명확히 미시작인 꼬리도 자동 재개하지 않고 새 관측과
새 계획으로만 시작하며, 원 계획·완료된 앞부분을 참조한다. 현재 값이 같다는 이유만으로
유실된 과거 실행을 성공으로 바꾸지 않는다. 검증기 판본이 달라지면 현행처럼 보수적으로 거절한다.

등록 폐기·연결 단절의 즉시 인지는 보장할 수 없다. 허브에서 취소가 전달된 뒤 새 단계 차단을
보장하고, 끊긴 동안은 이미 승인받은 작업이 전체 deadline까지 진행될 수 있음을 유지한다.
이 한계는 기존 원격 실행에도 있다. 강화하려면 별도의 짧은 lease 설계가 필요하다.

## 7. UI는 왜 다음 단계인가

첫 화면의 snapshot_id/ref를 여러 tap에 붙이면 첫 조작 뒤 나머지가 낡은 화면을 가리킨다.
기존 `PhoneAccessibilityService.doControl`의 최신 화면·포커스·비밀번호 검사를 유지해야 한다.

UI 확장은 각 단계가 직전 결과의 새 화면에서 목표 요소를 유일하게 찾아 현재 snapshot_id와
ref를 만들고, 네이티브가 조작 직전에 다시 대조하도록 한다. 조회된 resource_id·정확한 레이블·
패키지·editable 등의 관측 근거로 제한하고, 0개/여러 개 일치·예상 패키지 변경은 중단한다.
화면 판본이 바뀌었다고 자동 재탭하지 않는다. 새로운 selector 문법을 코어에 넣지 않고
등록 스크립트의 제한된 입력 계약으로 둔다.

후속 조건이 없는 탭, 사용자 판단·로그인·새 팝업·알 수 없는 화면은 묶음 경계다.
UI는 과거 좌표의 빠른 재생이 아니라 단계별 새 관측에 근거한 제어여야 한다.
앱별 전환·IME·오버레이·사용자 동시 터치까지 인수해야 하므로 추가 5~8인일을 추정한다.
임의 앱이 모두 안정적으로 빨라진다는 약속은 범위에 없다.

## 8. 구현 순서와 인수 기준

| 단계 | 변경 내용 | 추정 |
|---|---|---|
| 계획·드라이버 | 기존 검증 부품을 공유, 준비·결과 목록·중단 규칙, 관용구/등록 시드 | 1인일 |
| 부모 원장·취소 관문 | APK 별도 부품, IPC, 원자 기록, 재시작·회수, capability 판본 | 1~2인일 |
| 확인·복구 | 원 영수증 대조, 부분 결과/참조 회수, 미지원 APK 사전 거절 | 0.5~1인일 |
| 검증·실기기 인수 | 아래 장애 주입, Python/Kotlin 관련 회귀, arm32/arm64 | 1~2인일 |
| 교재·발견·배포 | 가이드·의미 검색 시드·APK 발행과 설치 확인 | 0.5~1인일 |

새 기능은 capability로 판별하고 오래된 APK에서는 접수 전에 안내한다. 자동으로 여러
단건을 재전송하는 fallback은 두지 않는다. 부모 원장이 필요한 제품안은 APK 업데이트가 필요하다.
조회 전용 비용 시범이 현재 APK에서 가능했던 것과 구별한다.

필수 인수 항목:

- 2단계 실패 때 1단계 결과 유지, 3단계 호출 0회. 요청 검증 실패는 원격 접수 0회.
- 시작 직전/OS 변경 직후/완료 원장 확인 직전 worker 사망 각각의 unknown 경계.
- 취소 수신과 다음 단계 허가의 경합, native 호출이 남은 경우 cleanup_unconfirmed 보존.
- 연결 유실·중복 배달·폰 재등록·부모 재시작·원장 손상/만료에도 변경 자동 재실행 0회.
- 단계 원장 확인 유실은 조회로만 복구. ID/순서/지문/대상 변조는 완료 판정 거절.
- 같은 폰의 다른 작업과 순서 보존. 사람의 설정 변경은 단계별 실제 관측으로 검증.
- 제품 경로에서 같은 3단계 업무를 개별/묶음 각 10회 이상 교차 측정. 폰·회선·앱 버전 기록.
  목표는 대표적인 짧은 설정 묶음 중앙값 40% 이상 단축, 단건 경로 성능 저하 없음이다.
  이 40%는 구현 인수 목표이며 이번 실험으로 보장한 수치가 아니다.
- 실제 AI 작업에서 호출 수·완료 품질·전체 토큰을 별도로 비교. 호출 감소만으로 토큰 절감을
  보고하지 않고, 시나리오를 바꾼 새로운 조합에서도 발견·사용되는지 확인한다.

원문 캐시나 상주 worker로 범위를 넓히기 전에 이 단계의 계약을 완성한다. 이번 조사는
묶을 수 있는 짧은 작업의 기술적 이득을 확인하는 것이며, 실제 사용 빈도를 측정해 월간
절감 시간이나 비용을 산출한 것은 아니다. 첫 투자 판단은 유리하지만 전체 폰 조작에 대한
일률적인 속도 향상이나 TV 지연의 해결로 확대 해석하지 않는다.
