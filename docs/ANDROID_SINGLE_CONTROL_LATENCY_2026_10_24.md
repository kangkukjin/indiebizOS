# Android 단건 제어 지연 개선

앞선 [묶음 실행 조사](ANDROID_CONTROL_SEQUENCE_DESIGN_2026_10_24.md)에 이어, 요청 하나의
준비·실행·종료·결과 전달 비용을 줄인다. 묶음 실행은 이번에 추가하지 않는다.

## 구현

### 전송

`limb_http_transport.py`가 스레드마다 `requests.Session`을 유지한다. 명령 수신과 결과 보고가
세션 객체를 공유하지 않는다. 응답은 성공·오류 모두 close하며 POST 자동 재시도를 추가하지 않는다.

허브 sync 응답의 `event_push:1`을 확인한 새 폰은 별도 사건 전송 스레드를 사용한다.
`/limb/resident/events`는 기존 등록 인증·사건 ID 중복 제거·ACK·취소를 사용하고 명령을
꺼내지 않는다. 결과를 spool에 원자적으로 기록하면 사건 전송과 수신 대기 신호를 깨운다.
결과 보고는 수신 측의 진행 중인 HTTP long-poll을 기다리지 않는다. 구형 허브는 기존 sync
보고를 유지하며, 신설 endpoint가 없는 경우에도 spool을 지우지 않는다.
응답 유실 때 다시 보내는 것은 같은 사건 ID의 보고뿐이다. 기기 조작을 재접수하지 않는다.

### 일회용 프로세스 종료

`WorkerProcessTree`의 `repeat(8)` 안 `return@repeat`는 다음 반복으로 넘어갈 뿐 종료하지
않았다. `ProcessDescendants`에서 새 자식이 없으면 실제로 탐색을 끝낸다. 루트와 발견된 자식을
멈춘 뒤 탐색하고, PID와 시작 신원을 대조해 종료·회수한다는 기존 규칙은 유지한다.
뒤집힌 자식 순서와 계속 증가하는 트리를 검사하며 최대 8회 상한도 유지한다.

### 설치된 제어 함수의 직접 실행

기존 `Android제어`·`Android제어확인` 인터페이스는 유지한다. `control`은 기존 guestpc의
전송 op이며 새 IBL 액션이나 새 언어 문법이 아니다. 일반 사용자는 저장 함수를 사용한다.

폰 APK가 `android_control` 계약 1과 설치된 verifier/primitive 지문을 보고한다. 허브의
prepare가 선택한 원문 및 verifier 지문과 비교해 일치할 때만 `control`을 선택한다.
새 전송에는 요청·요청 ID·지문만 들어가며 실행 코드·환경·작업 폴더는 받지 않는다.
불일치·구형 폰은 **접수 전에** 기존 일회용 Python 경로를 선택한다. 접수 후 실패·유실에는
다른 경로로 재전송하지 않는다.

`phone_native_control.py`는 APK에 포함된 고정 경로의 `android_control.py`와 세 primitive만
읽어 실행한다. 기존 validation/readback/UI 화면 판본·포커스 검사를 같은 코드로 수행한다.
상주 Python 엔진에서 설치된 제어 함수를 호출하고 Android API에 직접 접근하므로, 별도의
Python worker 시작·종료와 worker↔부모 파일 IPC가 없다. 임의 Python/shell은 계속 일회용
프로세스에서 실행한다. 이 경로를 임의 코드용 상주 실행기로 일반화하지 않는다.

등록 주인·수리 격리 검사는 허브와 폰 양쪽에 남는다. 화면 조작은 허브가 실제 호출 문맥을
검사하고 전송 메타데이터로 싣는다. 호출자가 준 화면 문맥은 덮어쓴다. 폰은 출처를 user
권한으로 승격하지 않고 전달된 화면 가용성과 격리 출처를 확인한다.

`RemoteExecutionBridge.beginControl/endControl`은 임의 프로그램 실행과 동일한 직렬 잠금을
사용한다. 작업 ID별 취소도 같은 active 원장을 사용한다. 네이티브 호출에 들어가기 전의 취소는
실행을 막는다. 이미 들어간 호출은 OS 변경이 일어났을 수 있으므로, 그 호출이 반환되고 잠금을
회수하기 전에는 취소 완료나 성공을 보고하지 않는다. UI 추가 관측마다 취소·deadline을 확인한다.
반환 뒤 deadline 초과·취소·잠금 회수 불명은 unknown으로 남긴다. Android Binder 자체가
블록된 호출을 강제로 안전하게 취소할 수 있다는 보장은 하지 않는다. 이때 다음 일반 제어도
직렬 자리에서 기다리며, info·사건 전송·취소 수신 통로는 별도로 살아 있다.

값과 원 영수증 검증은 기존 계약을 따른다. 직접 실행 계획의 결과는 `execution_mode`도
대조한다. 실행 전 거절이 확인된 결과는 failed, 부작용 가능성이 남으면 unknown이다.
현재 상태의 일치가 유실된 과거 실행의 증명인 것처럼 처리하지 않는다.

## 검증·배포 기록

2026-10-25 최종 전체 backend 회귀 **11,883 통과·18 건너뜀**, 582.40초.
Android 단위 검사 34 통과, arm64/arm32 APK 0.24 빌드·중앙 발행 완료.
IBL 파생/용례 재검토·backend 층 검사 통과. 관련 재검사 111건도 통과했다.
최초 종합 검사에서 발견한 문서 인수 오탐(kwargs의 args 부분), 신규 시험의 직접 실행 진입점,
용례 검토 원장 누락을 수정했다. 기존 회원 셸 번들 검사는 사용자의 활성 화면 판본이 아닌
소스 빌드끼리 대조하도록 격리해, 운영 중인 옛 화면 판본 때문에 실패하지 않도록 했다.
검사의 assertion과 JavaScript 구문 검사는 유지했다.

삼성1의 동일 0.24 APK에서 읽기 전용 volume_status를 각 경로 3회 교대로 실행했다.
기존 Python 경로와 직접 control 경로 모두 실제 결과 검증에 성공했다.

| 측정 구간 (중앙값) | 기존 Python 경로 | 직접 control 경로 |
| --- | ---: | ---: |
| 폰 내부 실행·정리 | 2.557초 | 0.057초 |
| 준비 제외, 접수부터 결과 수신 | 4.757초 | 2.714초 |
| 준비·영수증 검증 포함 전체 호출 | 8.154초 | 6.109초 |

앞의 왕복 측정은 prepare를 측정 밖에서 수행했다. 전체 호출 비교는 동일 Android제어 본문을
요청 안에서 정의하고, 기존 경로에서는 capability 입력만 비워 접수 전 Python 경로를 선택했다.
따라서 전체 호출에는 준비·결과 영수증 검증과 함수 컴파일이 포함된다. LLM 판단 시간은 제외다.
단 3회씩의 작은 표본이며 네트워크 변동이 있다(control 왕복 1.764~5.000초).
폰 내부 비용 감소를 전체 사용자 응답이 같은 비율로 감소한 것처럼 해석하지 않는다.
새 전송·정리 개선도 들어간 **동일 APK 내부의 두 경로** 비교이므로, 이번 모든 개선의
업데이트 전/후 효과를 분리 측정한 것은 아니다.

삼성1·삼성0의 APK 0.24 설치·재접속과 공개 Android제어의 상태·화면 읽기를 확인했다.
삼성1의 공개 음량 조회도 원장 op:control/execution_mode:native_control 및 검증 완료를 확인했다.
삼성0은 OS가 무선 자체 업데이트를 차단해 사용자가 USB로 연결한 뒤 같은 서명의 APK를 설치했다.
삼성0 추가 속도 측정 명령은 사용자 승인 거절로 실행하지 않았다. 상태 조회에서 설정 쓰기 권한이
없어 현재값 유지 설정 변경 시험은 수행하지 않았다. 가짜 bridge 회귀는 변경/readback/취소를 검사한다.
예나폰은 0.23의 직접 제어 능력을 광고하며, 0.24 무선 전송을 사용자 요청대로 기다리는 중이다.

실측: [measurements.json](experiments/android_single_control_2026_10_25/measurements.json).
재현용 읽기 전용 probe 두 개를 같은 디렉터리에 보관한다. 기기별 속도를 보장하지 않으며,
재현 시 연결된 0.24 폰과 정확한 코드 지문을 확인한다.
