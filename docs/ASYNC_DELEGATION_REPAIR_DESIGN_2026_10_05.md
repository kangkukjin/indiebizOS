# 비동기 실행과 조건부 위임 수리 설계

상태: **설계안. 구현과 위임 정책 변경은 아직 적용하지 않았다.**
작성일: 2026-10-05. 조사 기준: 정본 main `3b07ff7e`와 17회차 실행 기록.
독자: 수리 구현자와 설계 검토자. 목적 정본은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)이다.

직접 수행을 기본으로 유지하면서, 독립된 작업의 분업이 품질이나 완료 시간에 도움이 될 때
위임할 수 있도록 한다. 이를 위해 먼저 작업 접수부터 결과 회수까지의 계약과 훈련 격리를
수리하고, 그 위에서 명시적 요청만 허용하던 정책을 조건부 허용으로 바꾼다.
새 위임 횟수나 병렬 작업 수는 성과가 아니다. 결과 품질, 사용자가 기다린 시간, 부모와 자식의
전체 모델 비용으로 판단한다. 이번 문서는 현재 동작의 확인, 제안하는 계약, 구현 순서를 구분한다.

## 문제와 사용자 의도

사용자가 초기 개발 때 자동 위임을 제한한 이유는 AI가 스스로 처리할 수 있는 일까지 다른
에이전트에게 떠넘겼기 때문이다. 이 문제를 다시 만들지 않아야 한다. 동시에 독립적인 조사나
검증을 맡기고 원래 실행자가 다른 필수 작업을 진행하는 분업은 열어 둘 필요가 있다.

현재 문구인 “사용자가 요청하지 않으면 절대 위임하지 마세요”는 위임의 이득 대신 사용자가
위임을 명시했는지를 기준으로 삼는다. 짧은 작업을 떠넘기는 행위와 유효한 병렬 분업을 함께
막는다. 이 문구를 단순 삭제하거나 모든 복잡한 과제를 자동 위임하게 만드는 방법은 채택하지 않는다.

사용자가 이번에 요청한 범위는 조사에 기반한 수리 설계다. 현재 진행 중인 18회차 훈련 결과를
변경하거나, 이 설계의 효과를 이미 측정한 것처럼 기록하지 않는다.

| background 응답은 접수 문구이며 작업 ID를 돌려주지 않는다. | [HTTP 진입점](../backend/surface/api_system_ai.py)의 `ChatResponse`, `chat.background` 분기 | 런처는 이전 메시지 번호보다 새로운 답을 찾아 회수한다. 여러 작업을 구별할 계약이 부족하다. |

| 타 프로젝트 위임은 mode 분기보다 먼저 비동기 위임기로 들어간다. | [라우터](../backend/cognition/routing_system.py)의 `_delegate_unified`, [위임기](../backend/cognition/system_ai_tools.py)의 `_execute_call_project_agent` | 대역 재현에서 `cross + sync`도 접수 응답만 반환했다. 프롬프트의 동기 응답 설명과 불일치한다. |
| 훈련 출처가 타 프로젝트 위임 메시지에 전달되지 않는다. | 같은 위임기의 `msg_dict`, [수신기](../backend/cognition/agent_communication.py)의 `_check_internal_messages` | 대역에서 `origin=training`인 부모의 메시지에 origin이 없고 자식 채널은 `system_ai`였다. 실제 훈련 위임을 실행해 오염량을 측정한 것은 아니다. |
| 기존 task 결과는 전문 반환용으로 충분하지 않다. | [시스템 AI 저장소](../backend/datastore/system_ai_memory.py)의 `complete_task` | `result`를 500자로 줄여 저장한다. 이 필드를 그대로 작업 결과 API의 정본으로 삼으면 안 된다. |

조사는 코드, 과거 궤적, 실 에이전트와 저장소를 대체한 로컬 대역으로 수행했다. 실제 프로젝트에
메시지를 보내거나 유료 모델을 호출하지 않았다. 어떤 제한이 모델의 선택에 얼마나 기여했는지,
새 정책이 몇 초를 줄일지는 아직 측정하지 않았다.

17회차 기본 605.441초, 변형 408.958초는 각 시스템 AI 턴의 경과 시간이다. 이 두 시간을
훈련자 전체 시간에 다시 더하지 않는다. 기존에 겹친 작업을 새 병렬화의 절감으로 세지 않는다.

## 범위와 설계 결정

세 종류의 동시 실행을 분리해서 다룬다.

| 종류 | 이번 수리에서 맡을 책임 |
| --- | --- |
| HTTP 백그라운드 접수 | 연결을 빨리 반환하고, 접수된 작업의 상태와 결과를 정확히 회수하게 한다. |
| 에이전트 위임 | 목표의 일부를 다른 실행자에게 맡기고, 부모가 결과를 합쳐 완료를 책임진다. |
| IBL 내부 병렬 처리 | 기존 `&`, `table:each`의 `parallel`을 사용한다. 새 문법이나 자동 병렬화 규칙을 만들지 않는다. |

기존 `task_id`, 부모와 자식 관계, `run_id`, 결과 참조, 실행 수명 관리와 비용 원장을 재사용한다.
새 범용 작업 관리자나 별도 작업 DB를 만들지 않는다. 시스템 AI와 프로젝트 DB는 기존 소유자가
유지하고, 공통 접수·조회 계약이 각 저장소를 연결한다. 도구 이름이나 업무 주제는 파서에 넣지 않는다.

초기 구현의 위임 대상은 등록된 로컬 프로젝트 에이전트다. 임시 에이전트를 자동 생성하거나
다른 기기의 권한까지 자동 확대하는 것은 이번 범위에 넣지 않는다. 적합한 대상이 없으면 직접
수행한다. 현재 대화의 일을 나눈다는 이유로 전체 대화·비밀·다른 프로젝트의 자료를 자동 복사하지 않는다.

## 조건부 위임 정책

다음은 실행 계약 수리 후 교체할 프롬프트의 제안 문안이다.

> 기본적으로 직접 수행한다. 단순하거나 짧은 작업을 다른 에이전트에게 떠넘기지 않는다.
> 독립된 하위 작업에 충분한 분량이 있고, 전문성·독립 검증·동시 진행의 이점이 위임과 결과 통합
> 비용보다 클 때 위임할 수 있다. 자신이 할 수 있는 일이라는 이유만으로 유효한 분업을 금지하지 않는다.
> 위임할 작업의 입력, 산출물, 완료 조건과 자신의 남은 일을 명확히 한다.
> 기다리는 동안 결과에 의존하지 않는 필수 작업을 진행한다. 같은 일을 중복 수행해 바쁜 척하지 않는다.
> 앞선 결과가 필요한 작업은 그 결과를 받은 뒤 진행한다. 접수 응답을 완료로 취급하지 않는다.
> 원래 실행자는 결과 확인, 통합과 사용자 요청의 완료를 책임진다.
> 사용자가 직접 수행이나 위임을 지정하면 그 의도를 따른다. 위임으로 권한이나 작업 범위를 넓히지 않는다.

판단은 기존 실행자의 계획 안에서 한다. 매 요청마다 별도 위임 판정 모델을 호출하지 않는다.
위임할 때만 짧은 목적과 이득의 근거를 남긴다. 직접 처리하는 모든 도구 호출에 사유 작성을 요구하지 않는다.
전문성이나 독립 검증을 위한 위임은 부모가 동시에 할 일이 없어도 유효할 수 있지만,
시간 단축을 위한 위임이라면 실제로 겹쳐 진행할 필수 작업이 있어야 한다.

| 상황 | 기본 선택 |
| --- | --- |
| 짧은 파일 수정이나 한 번의 조회로 끝나는 일 | 직접 수행 |
| 결과가 서로 독립적인 충분한 분량의 조사 두 개 | 적합한 대상과 예산이 있으면 분담 |
| 생성한 결과를 다른 관점이나 독립 기준으로 검증 | 검증 범위를 분리해 위임 가능 |
| 기본 결과가 필요한 변형 계산 | 기본 결과를 받은 뒤 변형 접수; 기다리는 동안 다른 검증 수행 |
| 적합한 대상이 없거나 전달할 문맥이 작업 자체보다 큰 경우 | 직접 수행 |
| 사용자가 특정 에이전트에게 요청한 경우 | 요청에 맞춰 위임하되 실제 결과까지 회수 |

초기 자동 분업의 운영 기본값은 동시 자식 2개, 자동 재위임 깊이 1로 제안한다. 이는 성능으로
입증된 최적값이 아니라 폭주를 제한할 시작값이며 설정으로 관리한다. 명시적으로 설계된 기존
위임 체인을 전역 깊이 제한으로 중단하지 않는다. 자동 위임 자식은 추가 분업이 필요하면 부모에게
필요성을 반환한다. 작은 일을 여러 자식으로 쪼개 한도를 소모하거나 같은 요청을 서로 재위임하지 않는다.

설정된 시간·모델 사용 예산은 부모와 자식이 공유한다. 위임마다 예산을 새로 발급하지 않는다.
접수 때 자식의 사용 가능 범위를 예약하고 부모의 통합 여유를 남긴다. 남은 예산으로 작업을
완료하기 어렵다면 새 자식을 늘리지 않고 기존 결과와 미완료 범위를 보고한다. 예산이 설정되지
않은 실행에 임의의 비용 수치를 만들어 넣지 않으며 기존 사용량 계측과 한도 정책을 연결한다.

권한 검사는 기존 경계가 담당한다. 자동 분업 정책의 허용이 발송·구매·공개·자기수리의 별도 권한을
부여하지 않는다. 자식은 부모가 허용받은 작업 범위와 대상 에이전트의 권한이 겹치는 범위에서 실행한다.
실제 대상 도구·자료가 이 범위를 충족하는지 서버가 확인할 수 없으면 자동 분업 대상으로 선택하지 않는다.

## 접수와 결과의 공통 계약

아래 필드와 경로는 **제안하는 목표 계약**이며 현재 API로 사용할 수 있다는 뜻이 아니다.
HTTP background와 위임은 같은 형태의 접수증을 반환한다. 기존 동기 응답의 `response`,
`timestamp`, `provider`, `model`은 전환 기간 동안 유지한다.

접수 요청에는 기존 message와 origin 외에 선택적인 `idempotency_key`, 명시적으로 발급된
`conversation_id`를 추가한다. 위임은 인증된 부모 실행에서 parent 참조와 권한을 해소하며,
외부 요청 본문에 임의의 parent ID나 권한을 써서 다른 작업에 합류할 수 없게 한다.
조회는 실행을 만들지 않는 GET으로, 제한 대기는 `wait`와 `after_revision`을 받아 변화가 있거나
시간이 끝나면 현재 상태를 반환한다. 대기 한도는 서버가 제한하고 클라이언트가 무한 대기를 지정하지 못한다.

```json
{
  "accepted": true,
  "task_ref": {"owner": "system", "task_id": "task_example"},
  "run_id": "run_example",
  "state": "queued",
  "status_url": "/system-ai/tasks/task_example"
}
```

프로젝트 작업의 owner에는 해당 프로젝트 식별자를 넣고 조회 경로는
`/projects/{project_id}/agents/{agent_id}/tasks/{task_id}`로 둔다. 기존 `/tasks/...` 스케줄 API와
충돌하지 않는다. owner와 agent는 클라이언트가 전달한 경로를 믿지 않고 저장된 소유권과 대조한다.
ID는 조회 권한이나 재기동 수명 capability를 대신하지 않는다.

상태 조회의 목표 필드는 `task_ref`, `parent_task_ref`, `run_id`, `state`, `revision`, 시작·종료 시각,
`result_ref`, `error`다. 완료 상태와 업무 달성 판정은 분리한다. 정상 종료해도 업무 판정이 UNKNOWN일
수 있고, 일부 자료 실패가 있는 결과도 그 근거를 보존한다. 전문 결과는 기존 결과 저장·참조 체계에
저장한다. 500자 요약과 대화 표시용 발췌는 결과 전문을 대신하지 않는다.

접수는 다음 순서를 따른다.

1. 호출자와 대상, 입력, 권한, 세션, 결과 위치를 검증한다.
2. 실행을 시작하기 전에 task ID와 부모 연결, 중복 접수 키를 영속 저장한다.
3. 기존 실행 수명 관리 아래 작업을 예약한다. 접수 실패는 실패 상태를 남기고 접수 성공을 반환하지 않는다.
4. 동기는 같은 작업의 결과를 기다리고, 비동기는 같은 작업의 접수증을 반환한다.
5. 부모는 task ID로 상태나 완료 통지를 받는다. 통지는 조회를 깨우는 신호이며 상태의 정본은 저장소다.

같은 접수 키와 같은 요청은 같은 task를 반환한다. 같은 키로 다른 요청을 보내면 충돌로 거절한다.
HTTP 응답 유실이나 기다리기 시간 초과를 새 작업 요청으로 처리하지 않는다.
교차 DB 접수는 단일 원자 트랜잭션이라고 가정하지 않는다. 부모에 안정된 child ID를 먼저 기록하고,
자식 저장소는 그 ID로 중복 생성을 막는다. 전달 누락을 복구해도 자식 실행을 중복 생성하지 않는다.
실행의 정확히 한 번 보장을 주장하지 않으며, 상태 변경의 재시도는 각 효과의 재실행 계약을 따른다.

## 기다리기와 완료 상태

공통 투영 상태는 `queued`, `running`, `waiting_children`, `succeeded`, `failed`, `cancelled`,
`interrupted`로 제안한다. 기존 수리의 `waiting_user` 등 대기 상태는 보존하고 무조건 completed로
매핑하지 않는다. 상태 문자열과 기존 소비자의 호환 변환은 저장소 어댑터 한 곳이 소유한다.

동기 위임은 같은 비동기 접수 뒤에 제한 시간 동안 결과를 기다리는 방식으로 구현한다.
기다리기 시간이 끝나면 실행을 실패·취소로 바꾸지 않고 현재 상태와 같은 task ID를 반환한다.
이벤트 루프를 막지 않으며, 다시 기다리거나 다른 일을 진행할 수 있다.

자식 접수 수에서 응답 수를 무조건 빼는 방식은 중복 통지에 취약하다. 부모는 child ID별 최종
결과를 한 번만 반영하고 모든 필수 자식의 상태를 확인한다. 현재 `pending_delegations`는 이
관계의 캐시로 유지하거나 같은 트랜잭션에서 갱신한다. 늦은 응답이나 같은 응답 재전송이 부모를
두 번 완료시키거나 최종 결과를 덮어쓰지 않아야 한다.

취소 요청과 실제 종료는 구분한다. 부모 취소는 미시작 자식의 실행을 막고, 실행 중인 자식에는
협력 취소를 전달한다. 이미 수행한 외부 쓰기의 롤백을 약속하지 않는다. 결과와 완료된 효과는 남긴다.
부모 응답이 끝났어도 실행 중인 자식의 수명 추적은 유지한다. 재기동은 기존 `runtime_work`의
접수·drain 규약을 따르고 task ID로 runtime capability를 새로 만들지 않는다.

재기동 뒤 남은 running 상태는 실행 생존 증거와 대조해 interrupted로 정리한다. 출력이나 외부
효과가 불확실하면 자동 재실행하지 않는다. 복구 가능한 읽기·검사와 상태 변경을 구분해 재개한다.
실패 원인은 작업 조회에서도 보여야 하며 서버 traceback만 남기는 경로를 없앤다.

## 위임 모드와 IBL 표면

기존 `[others:delegate]`와 사전의 mode·scope를 사용한다. 새 위임 액션이나 문법을 추가하지 않는다.
타 프로젝트 위임의 `mode=sync`는 접수 후 같은 task를 기다리도록 고친다. `mode=async`는
접수증을 반환한다. 두 모드가 다른 실행기나 다른 완료 판정을 갖지 않도록 한다.

첫 수리 단계에서 `scope=cross/system`의 `mode=workflow`는 명시적 미지원 오류로 검사와 실행
양쪽에서 거절한다. 구현하지 않은 조합을 자연어 비동기 위임으로 흘려보내지 않는다.
같은 프로젝트의 기존 workflow는 별도 호환 검증을 거쳐 유지하며 이번 자동 분업은 자연어
async/sync 경로만 사용한다. 교재와 enum·variant·오류 안내를 같은 커밋에서 일치시킨다.

결과 조회는 기존 `others:delegate`의 사전 계약에 `op=status/wait`, `task_ref`, 제한된 `wait`를
추가하는 안으로 좁힌다. op 생략은 기존 접수 동작이다. 조회에는 메시지를 다시 요구하지 않으며
대상을 다시 실행하지 않는다. 조회·대기 분기의 읽기 효과와 접수의 쓰기 효과를 구분해 선언한다.
표준 기능어 코어의 계약 확장에 해당하므로 구현 전에 [IBL 명세](../data/system_docs/ibl.md)의
언어 경계와 사전 variant 표현력을 점검하고 필요한 명세 변경을 같이 한다. 파서에 delegate 전용
분기를 추가하는 방식은 채택하지 않는다.

HTTP와 IBL은 같은 서비스의 상태·결과 투영을 사용한다. 화면과 모델이 서로 다른 성공 조건을
추론하지 않게 한다. 기존 접수 문자열을 파싱하는 소비자는 구조화 필드로 전환하고, 전환 기간의
문구는 사람에게 보여주는 용도로만 유지한다.

## 문맥과 훈련 격리

부모가 자식에게 넘기는 봉투에는 부모 task/run 참조, 원래 요청 출처, 허용된 작업 범위,
선택한 입력 참조, 산출물 위치, 완료 조건과 필요한 세션 식별자를 넣는다. 모델이 origin을 임의로
바꾸게 하지 않고 서버가 실행 문맥에서 정한다. `training`은 HTTP, IBL 위임, 큐, 워커,
에피소드와 결과 보고를 지나도 유지한다. 일반 위임의 출처와 사용자 직접 입력 권한은 구분한다.

훈련 자식의 대화와 CLI 세션은 실사용과 분리한다. 자식의 훈련 결과가 실사용 증류·건강 통계에
들어가지 않게 하며, 훈련 내의 자식 비용과 실행 기록은 부모 훈련에서 조회할 수 있어야 한다.
RED 수리 그랜트는 위임 봉투로 승계하지 않는다. 부모가 사용자 요청으로 시작됐다는 사실만으로
자식을 사용자 직접 수리 요청으로 바꾸지 않는다.

기본 실행과 후속 변형은 같은 훈련 대화의 순서를 유지해 자기 결과를 재사용한다. 독립 비교
실행은 서로의 정답·코드를 읽지 못하도록 입력·출력 범위를 구분한다. 같은 CLI 세션을 동시에
resume하지 않으며, 독립 작업에는 서로 다른 세션을 사용한다. 전체 히스토리를 모든 자식에게
복사하는 대신 해당 하위 작업의 입력과 계약만 제공한다.

신규 메시지 번호만으로 결과를 매칭하는 기본 경로, 훈련 표식 없는 위임 메시지다.
새 서버의 조회를 지원하지 않는 구버전 클라이언트에는 기존 response 필드를 유지한다.
새 클라이언트가 구버전 서버에 붙을 때만 메시지 폴링으로 제한적으로 폴백하고, 여러 동시 작업을
정확히 식별할 수 있다고 표시하지 않는다.

아니며, 미완성 실행 계약에 정책만 먼저 열지 않기 위한 구현 순서다. 정책을 되돌릴 때는 신규
자동 위임만 중지하고 이미 접수한 작업의 조회·결과 회수·취소를 유지한다.

## 검증과 성능 평가

회귀는 새 기능의 소유 모듈명 시험 파일에 둔다. 회차 문서는 증거 링크로 사용한다.
실제 모델이나 외부 발송 없이 저장소 대역·임시 DB·가짜 워커로 다음 경계를 먼저 검증한다.

| 검증 묶음 | 반드시 구별할 사례 |
| --- | --- |
| 모드와 결과 | 같은 요청의 async 접수와 sync 결과, wait 시간 초과 후 계속 실행, 미지원 workflow 조합 |
| 식별과 영속성 | 응답 유실 후 동일 키 재접수, 다른 요청의 키 충돌, 서로 다른 프로젝트의 작업 조회, 500자 이상 결과 전문 |
| 동시 실행과 합류 | 두 자식의 역순 완료, 중복 통지, 한 자식 실패, 늦은 응답, 부모가 다른 작업을 진행한 후 합류 |
| 취소와 재기동 | 접수 직후 취소, 실행 중 취소, 부모 종료 중 자식 실행, DB 기록 뒤 큐 전달 실패, 재기동 후 미확정 효과 |
| 출처와 권한 | training과 usage를 동시에 실행, 자식·손자 경계, 실사용 히스토리·증류 격리, RED 그랜트 비승계 |
| 정책 | 짧은 조회·편집은 직접 수행, 충분한 독립 작업은 분업 가능, 앞 결과가 필요한 작업은 순차, 부적합 대상은 직접 수행 |
| 표면 | 다른 작업의 새 메시지를 자기 답으로 회수하지 않음, 실패·진행·업무 UNKNOWN을 구분, 구버전 응답 폴백 |

기존 관련 회귀는 `test_scheduled_delegation.py`, `test_parallel_context_inherit.py`,
`test_long_sentence_remaining_repairs.py`, `test_episode_source.py`, `test_prompt_composition.py`를
참고한다. 구현 변경의 전이 소비자는 `scripts/select_tests.py`로 고르고,
[회귀 규약](REGRESSION_TESTING.md)에 따라 공통 수명 변경에는 종합 회귀와 관련 재기동 검사를 포함한다.
어휘·계약 변경은 IBL 빌드 정합, backend 변경은 Android 몸 번들, frontend 변경은
`npx tsc -p tsconfig.app.json`을 확인한다. 문서만 작성한 현재 시점에 이 검사들을 통과했다고 주장하지 않는다.

실측은 짧은 직접 처리, 충분한 독립 조사, 기본 결과에 의존하는 변형, 독립 검증 과제를 포함한다.
동일 모델·추론 설정·입력·완료 조건으로 반복 비교하고 캐시 조건과 반복 횟수를 보고한다.
결정론적 계산 결과는 전건 대조하고, 주관적 결과는 위임 여부를 가린 평가를 사용한다.

부모와 모든 자식의 모델 사용량은 기존 청구 이벤트를 call ID로 중복 없이 합산한다. 캐시 읽기를
입력에 다시 더하지 않는다. 기존에 겹친 셸 작업도 비교 기준에 포함한다. 전체 경과 시간,
가장 늦게 끝난 필수 경로, 전달·기다리기·통합 시간과 재작업을 분리해 남긴다.
새 자동 위임 사유·부모 연결은 기존 trajectory 사건에 작은 필드로 기록하고 별도 평가 모델을
상시 추가하지 않는다. 자식 선택·재위임·실패 후 직접 재수행 비용도 숨기지 않는다.

기능 완료는 위 계약·격리·표면 검증을 만족한 상태다. 성능 개선은 같은 품질에서 시간과 전체
토큰의 변화를 측정한 결과로 따로 판정한다. 미측정 속도 향상을 출시 설명에 넣지 않는다.

## 구현 착수 때 확인할 잔여 조사

1. task ID와 run ID의 연결을 사용하는 모든 소비자, 수리 대기 상태, 부모 결과 보고의 중복 처리 지점을 목록화한다.
2. 기존 결과 참조의 보존 기간·주체 검사가 장시간 background 결과 회수에 충분한지 확인한다. 부족하면 같은 저장소 계약을 확장한다.
3. 시스템 AI와 프로젝트의 CLI 세션 재사용 범위를 확인해 같은 세션 동시 resume를 막는다.
4. 기존 위임의 자동 활성화와 도구 권한을 점검해 대상 선정 시 부모의 작업 범위와 대조할 수 있는지 확인한다.
5. `others:delegate`의 추가 op별 효과와 variant를 현재 사전·검사기가 표현할 수 있는지 확인한다. 미지원이면 코어에 특정 어휘 이름을 넣지 않는 일반 계약 확장안을 먼저 검토한다.
6. 실제 운영 기본값은 제한된 자동 분업 실측 뒤 조정한다. 이번 기록만으로 Claude Code와의 속도 우열이나 자동 위임의 최적 개수를 정하지 않는다.

이 잔여 조사는 구현의 구체적인 경계를 확정하는 작업이다. 현재 확인된 mode 불일치와 출처 유실의
수리를 미루는 이유로 삼지 않는다. 새로운 사실로 설계를 바꿀 때는 이 문서의 해당 결정을 갱신하고
구현 상태와 검증 결과를 함께 연결한다.
