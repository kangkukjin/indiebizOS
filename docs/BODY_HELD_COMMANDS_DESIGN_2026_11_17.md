# 명령은 몸이 쥔다 — 실행자가 눈 감고 기다리지 않게 (2026-11-17)

상태: 9절의 권고대로 구현했다(2026-11-17, 사용자 "권고대로 구현해"). 구현하며 설계와 달라진 곳과 확인한 것은
12절에 있다. 실제 턴 예행(6절)도 마쳤다(12.5).

## 0. 요약

실행자가 셸 명령을 던지면 지금은 명령이 끝날 때까지 실행자 자신이 멈춘다. 그동안 명령이 일하는 중인지
서 있는지 아는 주체가 없다. 이 설계는 셸 명령을 **몸(백엔드)이 띄우고 쥐게** 한다. 실행자는 명령이 끝나거나
자기가 정한 시간이 지나면 돌아오고, 돌아올 때는 **그 명령이 살아 있는지를 보여 주는 사실**을 함께 받는다.

새로 만드는 장치는 거의 없다. 몸에는 이미 명령을 쥐는 장치(프로세스 세션)와 맡긴 일을 보고 다루는 낱말
(`[self:task]`)이 있다. 빠진 것은 세 가지다. 실행자의 주된 셸이 그 장치를 거치지 않는 것, 그 장치가 살아
있다는 사실을 돌려주지 않는 것, 길지 짧을지를 실행자가 미리 골라야 하는 것.

## 1. 계기

에피소드 6178(집사, "안전하게 지워도 되는 것부터 지워줘, pycache 문제도 고쳐주고", 37분).

- 10:36 실행자가 검사를 돌리는 명령 앞에 `cat >> /dev/null;`을 잘못 넣었다. `cat`은 끝나지 않는 입력을
  기다리며 섰다. 실행자는 제한 시간을 11분으로 줬다.
- 10:46 명령이 "뒤에서 계속 도는 중"으로 돌아왔다. 검사 출력은 한 줄도 없었고 출력 파일은 0바이트였다.
  실행자는 검사가 느리다고 여기고 "끝날 때까지 자는 반복문"으로 9분을 더 기다렸다.
- 그 19분 동안 감독은 한 번도 보지 않았다. 감독 검토는 턴당 2번인데, 둘 다 앞의 정상적인 삭제 작업
  (8분짜리 `rm`)에 쓰였다. 두 번 다 판정은 "계속"이었다.

37분 가운데 19분이 끝날 수 없는 명령을 기다린 시간이었다.

## 2. 근원

### 2.1 시계를 가진 쪽에는 이해가 없고, 이해를 가진 쪽에는 시계가 없다

- 모델은 불릴 때만 존재한다. 실행자는 명령이 돌아올 때만, 의식은 감독이 부를 때만 생각한다.
- 시계는 하네스의 감시 루프만 가진다. 5초마다 돌지만 이해는 없다.
- 그래서 둘을 잇는 것이 고정 숫자가 됐다. 도구가 180초 넘게 돌면 "정체", 검토는 턴당 2번, 검토 간격 240초.
- 고정 숫자는 예상하지 못한 경우에 깨진다. 8분 걸리는 정상 삭제가 검토 2번을 다 쓰면 그 뒤의 진짜 멈춤은
  아무도 보지 않는다.

이 숫자를 조정해서는 끝나지 않는다. 180초를 줄이면 정상 작업에 검토가 더 쓰이고, 2번을 늘리면 비용이
늘 뿐 "일하는 중"과 "서 있음"은 여전히 가려지지 않는다.

### 2.2 숫자가 필요했던 이유: 몸이 실행자의 셸을 느끼지 못한다

최근 200턴의 실행자 도구 호출 2,572건을 세었다.

| 도구 | 호출 | 도구 안에서 보낸 시간 | 30초 넘는 호출 | 최장 |
|---|---|---|---|---|
| Bash (Claude Code 자기 셸) | 921건 (36%) | 263.5분 (56%) | 102건이 시간의 90% | 601초 |
| execute_ibl (몸의 통로) | 1,100건 (43%) | 186.9분 (40%) | 76건이 시간의 63% | 254초 |
| shell (Codex 자기 셸) | 279건 (11%) | 2.1분 | 1건 | 84초 |
| run_command (몸의 셸) | 111건 (4%) | 11.0분 | 7건 | 69초 |

- 5분 넘게 걸린 호출 13건은 전부 Bash였다. 그중 11건이 "끝날 때까지 자는 반복문"이거나 멈춘 명령이었다.
- Bash로 간 명령에 대해 몸이 받는 것은 시작할 때의 명령문과 끝날 때의 출력 글자뿐이다. 그 사이는 비어 있다.
- 감독의 도구 정체 검토는 최근 201턴에서 11번 돌았고 11번 모두 "계속"이었다. 검토는 명령문만 읽고
  "이 정도 걸릴 만한가"를 추측한다.

### 2.3 몸의 통로에는 이미 옳은 원리가 있다

- 몸이 돌리는 뒤 작업은 기록이 늘어나는지와 끝났는지를 모델 없이 읽는다
  (`backend/base/supervision_watch.py`, 첫 줄이 "침묵도 관측하는 값싼 시계"다).
- `[self:task]`의 유한 대기는 "시간 초과는 실패가 아니다(대기자의 사정)"로 이미 정해져 있다
  (`backend/base/task_receipts.py`의 `wait`, 긴문장 26회차 L26-2). 기다리던 쪽이 돌아올 뿐 작업은 계속된다.

같은 원리가 실행자의 셸에만 없다.

## 3. 이미 있는 것

| 있는 것 | 하는 일 | 자리 |
|---|---|---|
| 프로세스 세션 | 명령을 별도 워커가 띄워 쥔다. 상태·출력·종료 코드를 보관하고, 백엔드가 재기동해도 이어진다. 입력 보내기·입력 끝 알리기·중단·취소가 된다 | `backend/services/process_sessions.py`, `backend/base/process_session_worker.py` (2026-11-06) |
| 접수증과 `[self:task]` | 맡긴 긴 일을 보는 낱말 하나. `status`(지금 상태), `wait`(유한 대기), `control`(입력·중단), `cancel` | `data/ibl_nodes_src/self.yaml`, `backend/base/task_receipts.py` (2026-10-05) |
| 몸의 셸 `run_command` | `mode: session`이면 프로세스 세션으로 접수하고 접수증을 돌려준다 | `system_essentials/essentials_command.py` |
| 실행 전 검사 | 셸 구문 검사(확정 오류면 실행하지 않고 진단을 돌려준다) | `backend/base/command_preflight.py` |
| 위험한 명령 승인 | `rm`·`sudo`·`chmod`·`kill` 등이 든 명령은 승인을 받아야 실행한다 | `system_essentials/handler.py`의 `is_dangerous_command` |

지금의 한계는 셋이다.

1. **Claude Code 실행자는 이 문을 쓸 수 없다.** 몸의 셸은 승인된 수리에서만 열리고, 평소에는 자기 Bash뿐이다.
2. **세션이 돌려주는 사실이 상태·출력·종료 코드뿐이다.** 출력이 없는 동안 일하는 중인지 서 있는지는 알 수 없다.
3. **길지 짧을지를 미리 골라야 한다.** `mode: sync`(끝날 때까지 붙잡음, 넘으면 죽임)와 `mode: session`(접수)
   가운데 실행자가 골라야 하는데, 명령이 얼마나 걸릴지는 돌려 보기 전에는 모른다.

## 4. 설계

### 4.1 원칙

1. **미리 고르게 하지 않는다.** 모든 셸 명령은 몸이 쥔다. 빨리 끝나면 결과가 그냥 온다.
2. **기다리는 시간은 기다리는 쪽이 정한다.** 그 시간이 지나면 명령을 죽이지 않고 실행자만 돌아온다.
3. **돌아올 때는 사실과 함께 온다.** 명령이 아직 돌고 있으면 살아 있다는 신호를 함께 준다.
4. **판단은 AI가 한다.** 몸은 "멈췄다"고 판정하지 않는다. 사실만 준다. 끊을지, 더 기다릴지, 입력을 끝낼지는
   실행자가 정한다.
5. **권한은 바꾸지 않는다.** 문을 바꿀 뿐이다. 실행자가 지금 셸로 할 수 있는 일의 범위를 넓히지도 좁히지도
   않는다.

### 4.2 명령의 뜻을 하나로

몸의 셸(`run_command`)에서 `sync`와 `session`의 구분을 없앤다.

- 명령은 언제나 프로세스 세션으로 시작한다.
- 호출은 **명령이 끝났을 때**, 또는 **실행자가 준 `timeout`이 지났을 때** 돌아온다.
- 끝났으면 지금처럼 출력과 종료 코드를 준다.
- 끝나지 않았으면 명령은 계속 돌고, 실행자는 접수증(`task_ref`)과 그때까지의 출력, 4.3의 신호를 받는다.
- `timeout`의 뜻이 "넘으면 죽인다"에서 "넘으면 내가 돌아온다"로 바뀐다. 죽이는 것은 `[self:task]`의
  `cancel`로 따로 한다.
- `mode`와 `yield_ms`는 쓸 일이 없어진다. `lifetime`은 남는다(기본은 턴이 끝나면 함께 끝남, 서버처럼 오래
  둘 것만 `session`).
  (구현에서 바뀜: `mode: session`은 남겼다. 고르는 기준이 걸리는 시간에서 입력을 주고받는가로 바뀌었다. 12.2)

### 4.3 살아 있다는 신호

프로세스 세션의 상태에 아래 사실을 더한다. 명령을 쥔 워커가 자기 자식 프로세스를 직접 재므로 추측이 없다.

| 사실 | 뜻 | 재는 법 |
|---|---|---|
| 마지막 출력 뒤 지난 시간 | 출력이 언제부터 없는가 | 워커가 출력을 받은 시각 |
| 쓴 CPU 시간 | 시작부터, 그리고 지난번 확인 뒤로 프로세스 무리가 쓴 CPU 초 | `psutil` (이미 재기동 제어에서 쓴다. 맥·리눅스·윈도 공통) |
| 살아 있는 프로세스 | 무리 안에서 지금 돌고 있는 프로세스의 이름, 끝 쪽부터 | `psutil` |
| 입력 상태 | 입력 통로가 닫혔는지, 열려 있고 아무것도 안 보냈는지 | 워커가 쥐고 있으므로 안다 |

6178의 멈춘 명령이었다면 이렇게 돌아온다: 출력 없음 600초, CPU 0초, 살아 있는 프로세스 `zsh`·`cat`,
입력 열림·보낸 것 없음. 정상 삭제였다면: 출력 없음 500초, CPU 310초, 살아 있는 프로세스 `rm`.

이 사실들은 `[self:task]`가 돌려주는 `progress` 칸 안에 싣는다. 낱말과 op, 반환 칸 선언은 바꾸지 않는다.

### 4.4 입력 통로의 기본값

지금 세션은 입력 통로를 열어 둔 채 시작한다. 입력을 기다리는 프로그램(`cat`, 비밀번호 묻기, 확인 질문)은
그 상태에서 끝없이 기다린다.

- (구현에서 바뀜: 닫는 것은 몸이 쥐는 명령이고, `mode: session`으로 여는 세션은 `pipe`여도 열려 있다. 12.2)
- `io: pipe`(기본)는 **입력 통로를 닫고 시작한다.** 입력을 기다리는 프로그램은 곧바로 "입력 끝"을 받고
  지나가거나 실패한다. 6178의 `cat`은 즉시 끝났을 것이다.
- 입력을 주고받아야 하는 명령은 `io: pty`로 시작한다. 지금도 있는 선택이다.

이것은 멈춤 하나를 막는 것이지 멈춤 전체를 막는 것은 아니다. 네트워크를 기다리거나 서로 물고 선 명령은
4.3의 신호로 보인다.

### 4.5 기다리기

- 끝나지 않은 명령은 `[self:task]{op:"wait", ref:…, timeout:…}`으로 기다린다. 이미 있는 낱말이다.
- 끝나거나 `timeout`이 지나면 돌아오고, 돌아올 때 4.3의 신호가 있다.
- 한 번에 기다릴 수 있는 시간의 상한은 지금 240초다(`WAIT_MAX_SECONDS`). 그대로 둔다.
- 기다리지 않고 다른 일을 해도 된다. 명령은 몸이 쥐고 있고, 나중에 `status`로 보면 된다.

실행자가 "끝날 때까지 자는 반복문"을 만들 이유가 없어진다. 기다림은 몸의 낱말이 맡는다.

### 4.6 실행자별 문

| 실행자 | 지금의 셸 | 설계 뒤 |
|---|---|---|
| API 실행자 (몸 안에서 도는 모델) | 몸의 셸 `run_command` | 그대로. 4.2~4.4가 적용된다 |
| Claude Code | 자기 Bash | **몸의 셸로 바꾼다** (아래) |
| Codex | 자기 shell | 그대로 둔다 (아래) |

**Codex의 셸은 이미 이 설계와 같은 꼴이다.** Codex의 세션 기록 11개(명령 실행 260건)를 읽었다.

- 명령이 31초 안에 끝나지 않으면 실행 호출이 "아직 도는 중"과 번호를 들고 돌아온다(9건, 그중 7건이 정확히
  31.0초). 명령은 Codex의 실행기가 쥐고 계속 돌린다.
- 모델은 `wait`에 번호와 기다릴 시간을 주어 유한하게 기다린다(11건).
- 그래서 Codex 실행자는 한 번에 31초 넘게 눈을 감지 않는다. 우리 기록에서 Codex의 셸 279건 가운데 30초를
  넘긴 명령은 84초짜리 검사 1건이고, "끝날 때까지 자는 반복문"은 0건이다. Claude Code는 5분 넘는 호출만
  13건이었다.

Codex에 없는 것도 있다. 돌아올 때 받는 것은 지난 시간과 그때까지의 출력뿐이고, 4.3의 신호는 없다.
몸은 그 프로세스를 쥐지 않으므로 몸도 보지 못한다. Codex의 셸은 끌 수 없고 실행 전 훅도 없어서, 몸의
셸로 바꾸는 길(가)은 Codex에는 없다. 긴 명령에서 신호가 필요해지면 Codex도 몸의 셸을 부를 수는 있다.

같은 일을 하는 두 실행자 가운데 한쪽에만 문제가 있다는 것이 이 설계의 근거이기도 하다. 문제는 모델이
아니라 손의 구조에 있다.

Claude Code 실행자에는 두 길이 있다.

- **가. Bash를 빼고 몸의 셸을 준다.** 실행자의 도구 목록에서 Bash를 내리고, 지금 수리에만 열려 있는 몸의
  셸을 평소에도 연다. 모든 실행자가 같은 문을 쓴다. 셸에 관한 한 실행 전 훅이 필요 없어진다(구문 검사는
  몸의 셸 쪽에 이미 있다). 지시 전달도 훅이 도구를 세우는 방식이 아니라 평범한 도구 결과로 간다.
  명령은 셸 문장 그대로다. IBL 낱말로 옮기거나 옮기라고 거절하지 않는다(10절).
- **나. Bash는 두고 실행 전 훅이 명령을 바꿔치기한다.** 훅은 지금도 모든 Bash 명령 앞에 `set -o pipefail`을
  붙여 고쳐 쓴다. 같은 자리에서 명령을 "몸에 맡기고 결과를 받아 오는 작은 프로그램"으로 바꾼다. 실행자는
  Bash를 쓴다고 여기지만 실제로는 몸이 쥔다.

**가를 권한다.** 나는 실행자의 손 위에 번역층을 하나 더 얹는 것이다. 작업 폴더 이어받기, 종료 코드,
환경 변수, 실행자가 준 제한 시간의 뜻이 번역층에서 조금씩 어긋날 수 있고, 그 어긋남이 다음 수리 거리가
된다. 가는 층을 더하지 않고 문을 하나로 줄인다.

가의 위험은 하나다. Claude Code 모델은 Bash에 익숙하다. 다른 이름의 도구로도 같은 솜씨가 나오는지는
6절에서 확인한다. 솜씨가 눈에 띄게 떨어지면 나로 물러난다.

### 4.7 감독에서 없어지는 것

- **도구 정체 검토(`tool_stalled`).** "180초 넘게 도는 도구가 있으면 의식을 부른다"는 규칙을 없앤다. 살아
  있는지는 실행자가 신호로 직접 본다. 최근 201턴에서 11번 돌아 11번 모두 "계속"이었다. 11-16의 심층실행
  점검에서도 같은 결과여서 없앨지가 남은 결정으로 적혀 있었다.
- **검토 2번 한도가 긴 정상 작업에 쓰이는 일.** 정체 검토가 없어지면 남는 방아쇠는 연속 실패와 같은 호출
  반복이다.
- **셸에 대한 실행 전 훅의 일.** 가를 택하면 `pipefail` 붙이기와 훅 쪽 구문 검사는 Bash가 없으므로 쓰이지
  않는다. 훅은 Read·Write·Edit에 대한 지시 전달과 상황 전달에만 남는다.

의식의 일은 방향을 보는 것(심층실행의 되돌아보기)으로 좁아진다. 명령이 살아 있는지는 의식의 일이 아니다.

### 4.8 권한

문을 바꿔도 범위는 같아야 한다.

- 지금 Claude Code의 Bash는 작업 폴더 밖에도 쓸 수 있다(6178은 `~/.cache`와 Homebrew 캐시를 지웠다).
- 지금 몸의 셸 세션은 맥에서 작업 폴더 쓰기 샌드박스 안에서 시작한다.
- 그러므로 Claude Code에 여는 몸의 셸은 지금의 Bash와 같은 범위로 시작해야 한다. 샌드박스를 씌우면
  6178 같은 일이 막힌다.
- 위험한 명령의 승인 절차는 몸의 셸에만 있다. `rm`, `rmdir`, `sudo`, `chmod`, `chown`, `dd`, `kill`,
  `pkill`, `shutdown` 등이 든 명령은 승인 없이는 실행되지 않는다. 지금의 Bash에는 이 절차가 없다.
  문을 그대로 바꾸면 Claude Code가 `rm` 한 줄을 낼 때마다 승인을 기다리게 된다. 6178은 사용자가
  "지워줘"라고 한 턴인데도 그랬을 것이다.
- 원칙 5에 따라 이번에는 Claude Code에 이 절차를 걸지 않는다. 문은 같아지지만 승인 기준과 샌드박스는
  실행자 설정이 정하는 값으로 두고, 지금 각 실행자가 가진 그대로 넘긴다. 실행자 사이의 기준을 맞출지는
  이 설계와 따로 정할 일이다.

### 4.9 수명

- 기본 수명은 턴이다. 턴이 끝나면 그 턴이 맡긴 명령도 끝난다(지금 세션의 `lifetime: task` 그대로).
- 백엔드가 재기동해도 명령은 이어진다. 워커가 백엔드와 따로 돈다(지금 그대로).
- 턴을 넘겨 살아야 하는 것(개발 서버 등)만 `lifetime: session`으로 시작한다.

## 6. 검증

구현 뒤 아래를 본다. 모두 예행(`origin: training`)으로 돌린다.

1. **멈춘 명령.** 6178의 13번 명령을 그대로 낸다. 입력 통로를 닫았을 때 즉시 지나가는지, 일부러 열어
   두었을 때 4.3의 신호가 돌아오는지.
2. **긴 정상 명령.** 임시 폴더에 작은 파일 수십만 개를 만들고 지운다. 실행자가 CPU 신호를 받는지, 감독
   검토가 한 번도 돌지 않는지.
3. **실행자의 솜씨(가의 위험).** 같은 과제 셋을 Bash로 한 번, 몸의 셸로 한 번 돌린다. 과제는 (a) 임시
   폴더에서의 정리와 스크립트 수리·검사, (b) 코드 한 곳 고치고 검사 돌리기, (c) 자료 조사 뒤 파일 쓰기.
   볼 것은 끝까지 갔는가, 호출 수, 걸린 시간, 실패한 호출의 종류다. 몸의 셸 쪽에서 과제를 끝내지 못하거나
   같은 실패가 되풀이되면 4.6의 나로 물러난다.
4. **기존 검사.** 프로세스 세션·셸·감독 검사 묶음과 비system 전수.

## 7. 이 설계가 하지 않는 것

- **실행자가 신호를 보고도 계속 기다리는 경우.** 몸은 판정하지 않는다. 그 경우는 기록에 사실로 남고
  (기다린 호출마다 "CPU 0초"가 찍힌다), 되돌아보기에서 의식이 본다.
- **Read·Write·Edit·Grep.** Claude Code의 자기 도구로 남는다. 바로 끝나는 도구라 기다림 문제가 없다.
- **긴 IBL 액션.** 이미 접수증과 진행 표시가 있다. 최장 254초였다.
- **다른 몸(다른 PC, 폰)의 명령.** 원격 프로세스 세션이 따로 있다. 이 설계는 로컬 몸만 다룬다.
- **설계에 없는 숫자를 구현에 넣는 일.** 심층실행의 상한 5가 그 예였다. 감지와는 다른 문제이고 이 설계로
  막히지 않는다.

## 10. 앞선 결정과의 관계

- **셸을 IBL로 강제하던 관문의 은퇴(2026-10-14, `475adecc`).** "비슷한 어휘가 있다는 이유로 셸 호출을
  거절하거나 번역하지 않는다"가 지금의 정책이다(`backend/base/shell_shadow_gate.py`). 이 설계는 그 정책을
  건드리지 않는다. 명령은 셸 문장 그대로이고, 바뀌는 것은 그 프로세스를 누가 쥐느냐뿐이다.
- **IBL은 이음새의 언어(2026-10-09).** 순수 계산을 IBL로 옮기지 않는다. 맡기기·기다리기·접수증은 사적인
  몸과 닿는 이음새이고, 그 낱말(`[self:task]`)은 이미 있다. 새 낱말과 새 op는 없다.
- **시간 초과는 실패가 아니다(긴문장 26회차 L26-2).** `[self:task]`의 `wait`에 정해진 뜻을 셸 명령의
  `timeout`에도 똑같이 적용한다.
- **AI가 할 일을 고정 프로그램으로 만들지 않는다(2026-09-03).** 몸은 "멈췄다"를 판정하지 않고, 판정용
  임계값도 두지 않는다. 재서 알 수 있는 사실만 준다.
- **도구 정체 검토를 없앨지(2026-11-16, 심층실행 설계 9절 4번).** 이 설계의 4.7이 그 답이다.
- **끝에서 의식을 자동으로 부르지 않는다(2026-11-16).** 이 설계도 의식 호출을 더하지 않는다. 줄인다.

## 11. 확인하지 못한 것

- Claude Code 모델이 Bash 없이 몸의 셸만으로 같은 솜씨를 내는지. 6절 3번에서 본다.
- 몸의 셸을 평소 실행자에게 열 때 지금의 범위 검사(`code_analysis_scope.check`)가 무엇을 막는지.
- `io: pipe`로 입력을 보내는 쓰임이 지금 있는지.
- Codex가 멈춘 명령을 만났을 때 실제로 알아차리는지. 31초마다 돌아오는 구조는 확인했지만(4.6), 우리
  기록의 Codex 턴 30개에는 긴 명령이 1건뿐이고 멈춘 명령은 없었다.
- 명령마다 워커 프로세스를 하나 띄우는 비용. Bash 921건 중 766건이 10초 안에 끝나는 짧은 명령이다.
  명령당 수백 밀리초가 더 들 것으로 보이나 재지 않았다.
- 실행자가 기다리는 동안 깨어나는 횟수가 늘어 드는 토큰. 30초 넘는 Bash 호출이 200턴에 102건이었다.

## 12. 구현 (2026-11-17)

### 12.1 만든 것

- **살아 있다는 신호** (`backend/base/process_session_worker.py`): 도는 세션의 상태에 `signs`를 싣는다.
  `running_s`(시작 뒤 초), `quiet_s`(마지막 출력 뒤 초), `output_seen`, `cpu_s`(프로세스 무리가 쓴 CPU 초),
  `cpu_quiet_s`(CPU 사용이 마지막으로 늘어난 뒤 초), `processes`(살아 있는 프로세스, 끝 쪽부터 8개까지),
  `stdin`·`stdin_bytes`. 워커가 2초마다 재 두므로 보는 쪽이 없어도 "CPU가 마지막으로 움직인 시각"이 남는다.
  `[self:task]`의 `progress` 칸으로 그대로 나온다.
- **쥐고 돌아오기** (`backend/services/process_sessions.py`의 `hold`): 세션으로 시작해 끝나거나 `timeout`이 지나면
  돌아온다. 시간이 지나도 죽이지 않는다. 입력 통로는 닫고, 환경은 걸러 내지 않고, 샌드박스를 씌우지 않는다
  (예전 동기 실행과 같은 범위).
- **몸의 셸** (`system_essentials/essentials_command.py`): 평소 실행은 `hold`를 거친다. 끝난 명령은 예전과 같은
  글자를 돌려주고, 도는 명령은 `timed_out: true`와 접수증·출력·신호를 돌려준다.
- **CLI 실행자의 문** (`backend/surface/api_supervision.py`, `mcp_server.py`): `/ibl/command`. 승인된 수리가 아닌
  턴에서도 그 턴의 실행자가 쓸 수 있다. 감독 작업대를 거치므로 호출이 몸의 기록에 남고, 지시 전달은 평범한
  도구 결과로 간다. MCP 다리는 결과 봉투를 셸이 낸 글자로 펴서 실행자에게 보인다.
- **Claude Code의 도구 목록** (`backend/providers/claude_code.py`): `Bash`·`BashOutput`·`KillShell`을 내리고
  `mcp__indiebizos__run_command`를 올린다. 도구 안내 글에 몸의 셸의 사실을 덧붙인다.
- **도구 정체 방아쇠 제거** (`backend/cognition/conscious_supervisor.py`).

### 12.2 설계와 달라진 곳

| 설계 | 구현 | 이유 |
|---|---|---|
| `io: pipe`는 입력 통로를 닫는다 | 몸이 쥐는 명령만 닫는다. `mode: session`은 `pipe`여도 열려 있다 | 파이프로 입력을 보내는 쓰임이 실제로 있었다(수리 세션, 재연결 뒤 입력 중복 제거 검사). 윈도 로컬은 `pty`가 없어 옮길 곳도 없다 |
| `mode`·`yield_ms` 은퇴 | 남겼다 | 위와 같은 이유. 다만 고르는 기준이 바뀌었다. 길지 짧을지가 아니라 **입력을 주고받을 것인가**다. 실행자가 미리 아는 것이다 |
| (없음) | CLI 실행자의 명령은 사용자의 셸과 그 PATH로 돈다 | 백엔드는 앱이 준 좁은 PATH(`npm`·`/usr/bin`·`/bin`)로 뜬다. 그대로면 `brew`·`adb`·`java`를 못 찾고 `python3`이 시스템 것으로 바뀐다. Claude Code의 Bash는 사용자 셸의 스냅숏에서, Codex는 로그인 셸에서 돌았다. 사용자 셸에서 PATH만 한 번 재어 쓴다(이 기계에서 0.65초, 36항목) |
| (없음) | 세션 기록 거두기 | 명령마다 세션이 생기므로 두면 끝없이 쌓인다. 결과를 다 돌려준 세션은 곧바로 지우고, 접수증을 넘긴 세션은 끝난 뒤 24시간(세션의 기존 수명값) 두었다가 지운다 |
| (없음) | 턴이 끝날 때 두고 간 명령을 끝낸다 | 시간이 지나도 죽이지 않으므로, 대화에 묶이지 않은 실행에서는 명령이 24시간까지 남을 수 있었다. 감독이 턴을 닫을 때 접수증의 공통 취소를 부른다(`lifetime: session`은 제외) |
| (없음) | 문을 고르는 설정 | `data/world_pulse_config.json`의 `{"executor": {"claude_code_shell": "native"}}`. 6절 3번의 비교와 물러날 길에 쓴다. 기본은 `body` |
| 모든 Claude Code 턴 | 감독 작업대가 있는 턴만 | 몸의 셸이 감독 작업대를 거쳐 닿는다. 작업대가 없는 턴은 예전처럼 Bash다. 5900번 뒤 282턴 가운데 1턴이었다 |
| 훅의 셸 전용 부분 정리 | 손대지 않았다 | 설정이 `native`인 경우와 작업대 없는 턴에서 여전히 쓰인다 |

### 12.3 조사하다 드러난 것

- **감사 지문 관문.** `system_essentials` 패키지의 파이썬 파일이 바뀌면 회원에게 열린 액션 넷(읽기·양식 채우기·쓰기·
  스크립트)이 재감사 전까지 닫힌다. 셸 도구는 주인 전용이고 회원은 프로세스가 뜨기 전에 거절된다는 것을 검사로
  확인한 뒤 지문을 갱신했다(`ada0fc226c6f3bf8` → 빌드가 계산한 현재 값).
- **명령 하나에 더 드는 시간.** 직접 실행 0.003초, 몸이 쥔 실행 0.06초(이 기계, `true` 여섯 번).
