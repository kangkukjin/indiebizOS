# 원래 요구의 완수를 중심으로 하는 업무 중 복구·수리

상태: 검토 반영·구현·회귀 및 제한된 실제 모델 인수 완료. 2026-11-10 에피소드 6000의 심층 검토를 반영했다.
목적 정본은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)이다.
기존 설계의 수리 대기·복귀 기반을 유지하면서 수단 선택, 예산 집행, 구현 순서를 수정한다.

## 1. 목표와 실패 뒤의 선택

어휘·관용구는 지름길이다. 사용자 요구가 아직 충족되지 않았다면 수단 하나의 실패로
끝내지 않는다. 이미 확보한 결과와 완료한 효과를 보존하고, 남은 요구를 실제로 해결한다.
기존 표현이 없는 경우도 같은 문제다. 필요한 좁은 함수·일회성 코드를 작성할 수 있다.

실패를 받은 기존 실행자는 다음을 **동등한 해결 방법**으로 비교한다.

| 방법 | 선택 근거 | 확인할 결과 |
| --- | --- | --- |
| 입력·호출 수정, 제한된 재시도 | 호출법 오류 또는 해소 가능한 일시 장애 | 같은 실패를 새 근거 없이 반복하지 않음 |
| 다른 도구·원천·실행 경로 | 필수 범위·품질·신선도·권한을 충족하는 대안 | 이름만 다른 같은 고장 경로인지 확인 |
| 기존 결과 재사용, 지역 함수·일회성 코드 | 필요한 자료·접근이 있고 좁은 변환·조합이 남음 | 공용 등록·교재·배포 없이 원래 결과를 만들 수 있는지 확인 |
| 허용된 구현 수리 | 근거가 있으며 검사·활성화까지 포함해 현재 요구 완수에 유리 | 수리 후 실제 소비 경로와 남은 산출물 확인 |

확실한 코드 결함은 수정의 근거이며 지금 수리가 최선이라는 뜻은 아니다.
다음 행동을 바꾸는 만큼만 진단한다. 정상 빈 결과·404 하나로 코드 오류를 확정하지 않고,
더 조사해도 선택이 바뀌지 않으면 유효한 방법을 실행한다. 새 근거로 재현 범위가 줄어드는
진전과 같은 진단의 재설명을 구분한다. 모든 선택지를 실제 실행해 볼 의무는 없다.

수리가 유일하게 유효한 경로라면 업무에 맞는 수리 몫을 배정할 수 있다. 원래 제약·품질을
낮추거나 검사 생략으로 시간을 맞추지 않는다. 경로가 실제 차단됐거나 취소·전체 예산이
종료되면 확보한 결과와 미충족 조건을 알린다. 가능한 방법의 설명·수리 제안·후속 접수는
실제 결과를 대신하지 않는다.

의미 판단은 기존 실행자가 맡는다. 새 감독 모델·오류별 강제 재호출·코어 어휘를 추가하지 않는다.
실패 기록만으로 종료한 답변을 다시 쓰는 경로는 [현행 원칙](FAILURE_RECOVERY_REPAIR_DESIGN_2026_11_04.md#13-2026-11-07-관측과-종료-판단의-책임-분리)에 따라 유지하지 않는다.

## 2. 수단별 변경 경로

관용구 정의는 기존 원장의 판본·소비자 계약 검사와 새 호출로 고친다. 스크립트는 본문과
등록 계약을 구분한다. 공용 구현 변경은 기존 소유권에 따른 사본·검사·반영을 거친다.
일회성 코드라고 이름만 바꿔 공용 구현이나 보호 코어를 직접 수정하지 않는다.

등록 스크립트 `능력변경`과 `능력변경완료` 관용구를 재사용한다.
[사용법](../data/guides/capability_change.md)의 계획·충돌 확인·저장·새 호출·각인·부분 재개를
사용하며, 이미 실행한 검사를 같은 apply에 반복 첨부하지 않는다.

이번에 추가한 `--plan-files`는 명시 파일의 기존 시험 선택기를 실행하고 검사 명령·전수 여부를
반환한다. 빌드·pytest·등록·반영을 실행하지 않는다. 선택기에도 30초 상한이 있다.
이는 진단 전 완전한 변경 비용 예측기가 아니다. 실제 변경 파일이 준비된 뒤 범위를 미리
보는 기능이며, 활성화 소유자와 교재·용례·번역 정비는 기존 경로에서 확인해야 한다.
시간 추정 근거가 없으면 `estimated_seconds:null`을 반환한다.

설명 변경에 필요한 교재·용례·번역을 빠뜨렸다가 마지막에 빌드·검사를 반복하지 않도록
[어휘 체크리스트](../data/guides/new_action_checklist.md)를 먼저 참고한다. 의미 판단과
기대 결과 작성은 실행자가 맡는다. 단순 복사로 검토를 대체하지 않는다.
회귀 범위는 [기존 회귀 규약](REGRESSION_TESTING.md)이다. 예전 판본의 성공을 현재 전수
통과로 쓰지 않고, 파일 이름만 같은 캐시를 검사 완료 증거로 만들지 않는다.

## 3. 한정 구현 수리의 예산 집행

`self:patch propose(path, reason)`은 수정안 없이 진단부터 맡길 수 있다. 현재 구현은
직접 소유자 업무의 대화·목표·효과·예산을 보존하고 한정 자식이 끝나면 부모를 재개한다.
이번 변경은 이 경로에 **부모와 별개인 수리 몫**을 추가한다.

설정 위치는 기존 `world_pulse` 설정의 `agent_resource_limits.task_repair`다.
모델의 도구 인자나 수정 후보는 한도를 늘리지 못한다. 첫 수리에서 설정을 고정한다.

| 설정 | 초기값 | 의미 |
| --- | --- | --- |
| `seconds` | 90 | 같은 부모 업무의 한정 수리 누적 대기 상한 |
| `tokens` | 500000 | 같은 부모 업무의 한정 수리 관측 입력+출력 누적 상한, 캐시 재합산 없음 |
| `return_fraction` | 0.25 | 원래 남은 시간·토큰 중 업무 복귀에 보존할 비율 |
| `return_seconds` | 10 | 원래 전체 기한이 있을 때 보존할 최소 시간 |

초기값은 실험 설정이다. 최적값·품질 보장·일반 업무 완료시간의 예측값이 아니다.
직접 요청한 수리 업무 전체를 90초로 제한하지 않는다. 기존 지침의 최초 후보 1회 규칙은
채택하지 않는다. 새 증거가 있으면 배정된 몫 안에서 수정할 수 있고, 기존 동일 서명 반복과
한정 수리 요청 횟수 제한은 유지한다.

- 한정 자식 접수 직전부터 사본 준비·대기·모델·검사·인계 시간을 센다. 처음 실패한 순간부터의
  진단 시간을 계측하는 새 상태 기계는 만들지 않는다. 접수 전 진단·직접 작성은 원래 전체
  시간·토큰에 포함되며 실행자가 다음 선택에 필요한 만큼만 수행한다. 기존 제안의 별도
  진단 20초는 강제 규칙에서 제외했다.
- 시간 몫은 설정 상한에서 이전 수리 대기를 뺀 값과 원래 기한에서 복귀 여유를 뺀 값 중 작은 값이다.
  남은 시간이 최소 여유보다 적거나 설정이 0이면 수리 자식을 만들지 않고 다른 수단을 안내한다.
- 토큰 몫도 이전 수리 사용량을 빼고 원래 남은 한도에서 복귀 여유를 보존한다. 별도 전체 한도가
  없어도 수리 자체 상한은 유지한다. 재개·재기동·다른 후보에서 사용량과 한도를 초기화하지 않는다.
- 부모 원장의 전체 기한·토큰 한도를 자식 몫으로 덮어쓰지 않는다. 자식 몫 소진은 사용자 취소
  표식이 아니므로 부모가 남은 자원으로 다른 방법을 실행할 수 있다.
- 실행 중에는 기존 취소 콜백으로 모델·도구의 중단을 요청한다. 현재 자식 실행이 돌아오고
  동기 자식 프로세스 트리가 회수된 뒤에만 부모를 재개한다. 수리 후보는 그대로 보존한다.
- 기존 능력변경 검사도 선택기부터 빌드·pytest까지 하나의 시간 상한과 같은 취소를 사용한다.
  단계마다 1,800초를 새로 주거나 선택기를 무기한 기다리지 않는다.
- 게시 예약 이후의 적용·활성화·복구는 기존 외부 제어자가 일관된 상태까지 진행한다.
  한도 도달을 이유로 게시 도중 부모의 대체 실행을 열지 않는다. 실제 초과 시간도 사용량이다.

현재 제한은 관측된 토큰과 취소를 지원하는 실행 경계에 따른다. 모델 사용량을 호출 끝에만
보고하는 경우 한 번의 호출만큼 토큰이 초과될 수 있다. 취소 불가능한 외부 요청이나
게시·복구 지연까지 포함한 절대 90초, 마무리 성공, 정확한 25% 보존을 보장하지 않는다.
복귀에 필요한 실제 결과 생성·검증·전달 비용과 이 초기값의 적합성은 실측해야 한다.

## 4. 안전한 복귀와 미수리 결함

부모는 자식 종결 영수증 뒤 원래 목표·대화·효과를 유지해 재개한다. 수리 결과에 후보 위치,
적용 세션 상태, 실패·예산 근거, 자동 후속 미접수 상태를 함께 전달한다. 수리 성공은
원래 요구 충족과 다르다. 복귀한 실행자는 현재 대상 상태에서 남은 작업을 수행한다.
응답이 유실된 발송은 효과가 없었다는 뜻이 아니므로 다른 도구로 다시 보내기 전에 조회한다.

이 구현은 모든 결함을 자동 후속으로 접수하지 않는다. 현재 과제를 해결한 뒤 필요성·재발 영향·
수정 비용·유효한 권한과 예산을 보고 기존 수리 경로에서 후속을 선택한다. 접수되지 않았다면
보류로 남기며 자동 실행 예정이라고 말하지 않는다. 현재 가능한 결과 전달을 후속 준비 때문에
미루지 않는다. 이미 끝난 답변을 미수리 결함 때문에 다시 열지 않는다.

부모 종료 뒤 자식을 자동 분리 실행하는 새 경로는 이번 설계의 필수 구현에서 제외한다.
기존 `parent_of`의 새 요청·취소·예산 검사를 완화하지 않는다. 나중에 독립 유지보수가 필요하면
별도 유효한 실행 권한·기한과 안전 인계, 중복 비용 귀속을 먼저 설계해야 한다. 현재 원장에
미완료 후보가 있다는 사실이 그 실행 권한을 자동으로 만들지는 않는다.

## 5. 구현과 검증 순서

1. 기존 실행·수리·부모 복귀 지침에 수단 선택과 원래 요구 확인을 연결한다.
2. `task_repair`의 누적 몫·복귀 여유·안전 중단과 `api_task_repair`의 시작 전 확인을 연결한다.
3. `capability_change_checks`의 계획 조회·공유 시간·취소·프로세스 회수를 연결한다.
4. 후보 보존→자식 종료→부모의 대체 결과 완성, 성공 수리→부모 복귀를 검사하고 실제 모델의
   선택 행동을 별도로 인수한다. 큰 후속 실행 체계를 이 개선의 전제로 두지 않는다.

범위는 기존 한정 구현 자식 수리와 능력변경 검사다. 관용구 관리 연산·일회성 코드·등록 부품의
부모 안 직접 수정에 일률적인 새 자식/타이머를 붙이지 않는다. 이들은 원래 업무 예산과 기존
권한·작업 수명, 확장한 수단 선택 지침을 사용한다. 별도 시간 보장이 있다고 주장하지 않는다.

필수 회귀는 시간·토큰 몫 소진, 후보·원본 보존, 부모 전체 한도 보존, 재개 시 누적 유지,
watchdog 스레드의 관측량 보존, 게시 중 만료, 새 요청·취소와 실제 프로세스 회수다.
계획 조회가 시험·빌드·적용을 실행하지 않는지, 선택기 시간 초과가 빈 성공이 아닌지도 확인한다.
실제 모델은 더 나은 대체 경로, 직접 작성, 수리만 유효한 경우, 진전 없는 반복 중단을 확인한다.

결과 품질·도착 시간·미완료·전체 토큰·불필요한 수리·조기 포기·중복 효과를 함께 본다.
후속 비용을 빼거나 원장 `completed`만 보고 완수율·효율 개선을 주장하지 않는다.
구현 계약 검사와 실제 모델의 선택 능력, 일반적인 성능 개선은 구분해 아래 기록한다.

## 6. 구현·검증 기록

관련 검사 **109개 통과**, 설정 공급의 층 의존을 수정한 뒤 직접 소비자 **80개 통과**했다.
두 묶음은 겹치며 합산하지 않는다. 선택기는 전이 시험 835/894개(93%)와 공통 허브를 지목했다.
최종 backend 전수는 **12,904 통과·24 건너뜀·실패/오류 0**, **452.89초**다. 실제 수리 사본,
재기동·세대 복구를 포함한 system 묶음까지 실행했다. 최초 sandbox 실행의 프로세스·포트·브라우저
환경 실패는 통과로 세지 않고 허용된 환경에서 전수를 다시 실행했다.
전수 이후 커밋 이식성 검사가 새 시험의 프로세스 생존 조회를 지적해 기존 공통 함수로 교체했다.
운영 코드는 그대로이며, 수정한 시험을 포함한 수리·복귀 파일 전체 **61개**를 다시 통과했다.

Android 몸 번들 빌드, IBL 파생 정합, 층 가드, diff 검사가 통과했다. 실제 `--plan-files` 호출은
`task_repair.py` 변경을 전수 대상으로 표시하면서 `behavior_verified:false`를 반환했다.
운영 제어자는 ACTIVE이며 변경 런타임 모듈 **8/8개**가 정본과 바이트 일치했다.

**4/4 통과**, 입력 187,767 + 출력 1,857 = **189,624 토큰**이다. 캐시 153,600은 입력에
포함되어 재합산하지 않는다. 네이티브 도구 시작 사건은 각 3·3·4·4회다. provider의
`total_tool_calls`는 이 네이티브 사건을 집계하지 않으므로 0을 무도구 실행으로 해석하지 않는다.
최초 네트워크 제한 실행은 모델 요청을 완료하지 못했으며 위 수치에서 제외했다.

이 실험은 같은 가상 집계 자료에서 네 가지 선택 조건과 실제 파일 산출물을 확인했다.
운영 도구 장애→자동 수리→재기동→실제 업무 복귀를 모델로 종단 재현한 실험이나,
다양한 업무에서 시간·토큰·품질 개선을 측정한 비교가 아니다. 수리 권한·누적 몫·안전 중단·
부모 복귀는 별도의 회귀/실제 프로세스 검사로 확인했다. [검증 기록](experiments/bounded_task_repair_2026_11_10/validation.json)에 범위와 소스 지문을 남겼다.
