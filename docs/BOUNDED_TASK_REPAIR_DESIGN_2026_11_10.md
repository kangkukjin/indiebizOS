# 본래 업무의 시간을 보존하는 자기수리

상태: **설계 완료·구현 전**. 기존 구현의 존재와 아래 제안을 구분한다.
목적: 수리 가능한 확실한 구현 결함을 발견하면 진단·수리·원래 업무 복귀까지 연결하되,
수리가 업무의 시간·토큰을 소진하지 않게 한다.
판단 기준은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)이다.

## 1. 이번 사례가 보여 준 공백

번개장터의 폐기된 검색 주소를 대체 검색으로 우회하면 당장의 답은 만들 수 있지만,
어댑터 결함은 다음 사용자 작업에서도 반복된다. 반대로 모든 오류를 즉시 끝까지 수리하면
답변 하나를 위해 빌드·회귀·교재 정비·재기동을 기다리게 된다.

이번 번개장터 수리는 주소뿐 아니라 응답 구조·페이지 이동·광고 제외·상태 매핑을 고쳤고,
설명 변경에 따른 교재·번역·검토 기록도 갱신했다. 함께 고친 공유창고 소유권은 공통 경계였다.
두 결함의 최종 전수 검사는 약 467초였다. 이 수치는 번개장터 단독 수리의 필수 비용이나
전체 수리 소요 시간을 뜻하지 않는다. 서로 독립인 변경을 묶으면 검사 영향도 넓어진다.

따라서 비용은 변경 줄 수가 아니라 **영향 범위·검사 범위·활성화 방식**으로 예측한다.
원래 업무 완료와 결함 수리 완료는 별도로 기록한다. 대체 검색 성공이 결함을 해소하지 않는다.

## 2. 이미 있는 것과 추가할 것

| 현재 기반 | 현재 한계 / 이번 제안 |
| --- | --- |
| `self:patch propose(path, reason)`으로 수정안 없이 한정 구현의 진단·수리를 요청 | 실행 중 확실한 결함을 발견했을 때 이 경로를 선택하고 대기 예산을 전달 |
| `task_repair`가 부모를 `waiting_repair`로 두고 수리 종결 후 복귀 | 부모의 수리 대기를 짧게 제한하고, 미반영 후보를 보존한 채 업무에 복귀하는 경로 추가 |
| 부모의 시간·토큰·취소·신원·근거를 자식이 계승 | 전체 예산 안에서 수리에 쓸 몫과 업무 복귀에 남길 몫을 구분 |
| 등록 스크립트 `능력변경`과 관용구 `능력변경완료` | 같은 계획에 비용·활성화 영향·대기 중단 가능 지점을 연결 |
| 기존 선택기·빌더·검사 실행기·수리 영수증 | 필요한 정비를 초기에 펼쳐 보고, 이미 끝난 단계의 불필요한 반복을 줄임 |

현 구현의 `capability_change_checks.check`는 검사 명령마다 최대 1,800초를 허용한다.
이 제한은 원래 업무가 수리에 기다릴 시간의 상한이 아니다. 부모 전체 예산만으로는
수리가 남은 시간을 거의 모두 쓰는 일을 막지 못한다.

현재 `task_repair.parent_of`는 부모의 수리 대기·현재 대화·남은 예산을 요구한다.
따라서 부모를 먼저 끝내고 기존 수리 자식을 그대로 실행하는 것은 지원되지 않는다.
후속 수리는 아래의 명시적 인계 계약을 구현한 뒤에만 가능하다.

## 3. 실행 중의 선택

1. 실패를 받은 기존 실행자가 입력·권한·일시 장애·구현 결함을 구분한다.
   정상 빈 검색 결과는 오류가 아니다. HTTP 404 하나로 코드 결함을 확정하지 않는다.
2. 코드 결함이 유력하면 짧게 진단한다. 예외와 구현 위치, 최소 재현, 현재 원천의 응답 계약
   등으로 **어떤 코드 가정이 틀렸는지** 확인한다. 이미 근거가 있으면 중복 조회하지 않는다.
3. 확실하고 허용된 결함이면 변경·검사·활성화 계획을 얻어 즉시 수리 또는 후속 수리를 선택한다.
   불확실한 경우에는 근거와 미확인을 남기고 원래 업무의 다른 수단을 판단한다.
4. 즉시 수리가 끝나면 원래 실패한 부분부터 새 판본으로 재개한다.
   오래 걸리면 후보와 근거를 보존하고 원래 업무에 복귀한다. 대체 수단이 충분하지 않으면
   부분 결과와 막힌 조건을 알린다. 원래 목표를 임의로 축소해 완료 처리하지 않는다.

의미 판단은 기존 실행자가 한다. 별도 오류 판정 모델·매 호출 감시·새 코어 어휘를 추가하지 않는다.
실패가 없는 경로에는 추가 모델 호출이 없다. 실제 모델이 이 선택을 하는지는 별도 인수한다.
실행 종료 후 실패 기록만 보고 답변을 다시 생성하는 경로는 되살리지 않는다.
관련 경계는 [실패 이후 관측과 종료 판단](FAILURE_RECOVERY_REPAIR_DESIGN_2026_11_04.md#13-2026-11-07-관측과-종료-판단의-책임-분리)을 따른다.

## 4. 시간 예산

첫 실험 설정으로 **진단 최대 20초, 진단을 포함한 업무 중 수리 대기 누적 최대 90초**를 제안한다.
보장된 성능이나 모든 업무의 고정값은 아니다. 즉답 요청은 더 작게, 사용자가 명시한 수리 업무는
그 업무의 예산에 맞춘다. 실패 건별로 90초를 새로 주지 않는다.

- 수리 대기 상한 = 설정된 상한과 원래 남은 시간에서 업무 복귀 여유를 뺀 값 중 작은 값.
  남은 시간이 불명확해도 기본 상한은 둔다. 복귀 여유까지 불명확하면 긴 수리는 시작하지 않는다.
- 토큰도 부모의 누적 장부 안에서 수리 몫을 제한한다. 자식·재개·재기동마다 초기화하지 않는다.
  시간 안에 있어도 수리 토큰 몫이 끝나면 새 진단·수정 호출을 시작하지 않는다.
- 최초에는 한 결함당 후보 한 번을 즉시 수리 대상으로 삼는다. 새 후보가 필요한 재실패는
  남은 예산과 후속 인계로 판단한다. 동일 후보의 중복 실행 제한은 기존 계약을 유지한다.
- 검사·빌드·모델·네트워크 호출에도 남은 대기 시간을 전달한다. 하나의 `timeout=1800`이
  부모의 짧은 대기 상한을 무력화하지 않도록 실행 소유자가 취소와 자식 프로세스 회수를 맡는다.
- 적용 시작 전에는 게시·활성화·안전 복구에 필요한 여유를 확인한다. 미확정이면 후속으로 넘긴다.
  적용 중 만료는 정본 쓰기를 중간에 끊는 명령이 아니다. 기존 제어자가 일관된 상태까지 복구하고
  실제 초과 시간을 기록한다. 외부 호출·복구 지연까지 포함한 절대 90초 보장은 주장하지 않는다.

예상 시간은 기존 실행 기록의 유사한 검사 묶음·활성화 방식에서 얻고 보수적 여유를 둔다.
기록이 없거나 영향이 불명확한 변경은 값싼 수리로 추정하지 않는다.
전체 회귀가 필요하면 그것을 생략해 즉시 수리로 밀어 넣지 않는다.

## 5. 스크립트·관용구가 줄일 일

기존 [능력변경](../data/guides/capability_change.md)을 확장한다.
새 수리 관용구를 여러 개 만드는 대신 현재 계획·실행·재개 경로를 업무 중 수리와 연결한다.

| 변경 | 계획에서 먼저 확인할 일 | 줄일 수 있는 반복 |
| --- | --- | --- |
| 관용구 원장 정의 | 판본·호출자 계약·새 호출 검사 | 같은 판본 재등록, 불필요한 코드 빌드·재기동 |
| 스크립트 본문 | 원본·공유 의존성·등록 계약 변화·동작 검사·소스 각인 | 등록 정보가 같은 본문 수정의 재등록, 이미 성공한 단계 재실행 |
| 어휘의 내부 구현 | 실제 변경 파일·전이 소비자 검사·기존 공개 계약·활성화 방식 | 관련 없는 소스·검사를 작업 범위에 섞기 |
| 어휘 계약·설명 | 선언·오류 도움말·가이드·용례 검토·번역·파생물·소비자 | 커밋 직전에 빠진 정비를 발견해 빌드·검사를 반복하기 |

자동화할 것은 파일·단계·명령 연결, 판본 대조, 기존 선택기의 검사 범위,
영수증 회수와 실패 지점부터의 재개다. 증상 원인, 수정 의미, 기대 결과, 교재의 적합성은
실행자가 판단한다. 바뀐 설명을 그대로 복사한 용례나 번역으로 검토를 대체하지 않는다.

계획에 변경 소유자·명시 파일·검사 범위·파생 정비·활성화 방식·시간 추정의 근거와 미확인을
같이 반환한다. 계획 조회가 빌드·등록·외부 효과를 일으키지 않게 한다.
새 API 인자는 구현 때 정하며, 현재 `능력변경` 호출에 미지원 인자를 넣지 않는다.

현재 후보에서 성공한 단계는 입력·관련 의존성·도구·환경 판본이 그대로일 때 재개 근거로 사용한다.
유효성 범위를 모르면 다시 검사한다. 다른 커밋의 성공을 현재 전수 통과로 옮기지 않는다.
동작 확인의 외부 쓰기는 영수증을 먼저 조회하고, 효과가 불명확하면 무작정 재전송하지 않는다.
이 설계가 새 전역 시험 캐시나 검사 이력에 의한 적용 권한 관문을 도입하지는 않는다.
회귀 범위는 [기존 규약](REGRESSION_TESTING.md), 적용 권한은 기존 소유 경계를 따른다.

## 6. 오래 걸리는 수리를 잃지 않는 인계

확실한 결함의 후속은 메모만 남기는 것으로 끝내지 않는다. 기존 수리 원장·외부 재개 소비자에
**부모 복귀와 분리된 한정 후속**을 추가한다. 새 상주 데몬이나 결함 DB를 만들지 않는다.

- 부모가 살아 있을 때 결함 근거, 소유 구현, 기준 판본, 후보, 남은 검사, 적용 방식,
  남은 수리 시간·토큰, 취소 주체를 기록하고 후속 접수 여부를 확인한다.
- 후속은 원래 허용된 수정 범위를 계승한다. 보호 코어·지침·권한 변경을 열지 않는다.
  별도 후속 한도도 설정하되 원래 허용된 총예산·기한을 늘리는 수단으로 쓰지 않는다.
  허용된 예산이 없거나 소진됐으면 `보류`로 남기고 자동 실행 예정이라고 보고하지 않는다.
- 같은 결함·같은 기준 판본은 한 후보로 합친다. 다른 요청에는 진행 상태와 우회 근거를 돌려준다.
  동시 수정으로 판본이 바뀌면 기존 후보의 적용을 멈추고 한도 안에서 재평가한다.
- 기본은 부모 업무 종료 뒤 실행한다. 원래 작업과 CPU·네트워크를 경쟁하며 전수 검사를 돌리지 않는다.
  새 사용자 작업이 생기면 다음 안전 지점에서 후속을 양보한다. 새 요청·취소의 기존 검사도 유지한다.
- 부모 대기를 풀 때 수리 실행을 정지·접수 확인한 뒤 상태를 원자적으로 인계한다.
  양쪽 소비자가 동시에 같은 수리를 실행하지 않도록 기존 잠금·인계 키를 사용한다.
  인계에 실패하면 후보는 미완료로 보존하고 부모에 그 사실을 전달한다.
- 후속의 성공·실패는 수리 상태에 남긴다. 이미 끝난 원래 대화를 다시 열거나 답변을 교체하지 않는다.
  부모가 수리 결과를 기다리기로 명시한 경우에만 기존 부모 복귀를 사용한다.
- 적용 시점에는 다른 활성 업무와 세대 교체 영향을 다시 확인한다. 허용된 무재기동 교체와
  재기동이 필요한 구현을 구분하고, 후자는 기존 제어자의 안전한 경계에서 반영한다.

지연 수리는 명시적으로 실행·수리 중·완료·실패·보류·취소 상태를 구분한다.
등록 실패나 한도 소진을 숨긴 무한 재예약은 금지한다. 자동 후속이 실행되지 못한 결함은
다음 관련 요청에서 재관측할 수 있지만 옛 업무의 실행 권한을 자동 부활시키지 않는다.

## 7. 번개장터에 적용하면

옛 주소 404 → 공식 웹이 쓰는 새 API와 응답을 확인 → 폐기된 주소와 파싱 가정의 결함을 특정한다.
읽기 전용 최소 재현·수리 범위·검사 계획을 준비한다. 지역 정보·광고·페이지 처리까지 바뀌면
단순 URL 치환으로 처리하지 않는다. 이 정비가 짧은 예산에 맞으면 수리·활성 호출 후 검색을 계속한다.

예산을 넘을 것으로 보이면 현재 검색은 다른 원천으로 이어가고 번개장터 수리는 한정 후속에 접수한다.
검색 품질이 원래 요청을 충족하는지 별도로 판단한다. 수리 후에는 원래 증상과 결과 계약을 확인하되,
이미 제공한 보고서를 재작성하거나 이미 실행한 외부 동작을 되풀이하지 않는다.
공유창고 소유권 같은 별도 보호 경계 변경은 이 후보에 묶지 않는다.

## 8. 구현 순서와 인수 조건

1. **계획·대기 예산**: `capability_changes`, `capability_change_checks`, `task_repair`,
   `component_continuation`의 기존 책임에 연결한다. 전체 예산·취소 계승과 누적 대기,
   검사 중단·프로세스 회수·미반영 후보 보존부터 구현한다.
2. **후속 인계**: `repair_continuation`의 기존 소비자가 한정 후속을 구분하도록 한다.
   부모 복귀·중복 소비·재기동·각인 실패·새 요청에서 상태와 권한이 보존되는지 확인한다.
   이 경로가 준비되기 전에는 오래 걸릴 결함을 자동 수리 예정으로 보고하지 않는다.
3. **실행자의 사용**: 기존 상황 근거와 능력변경 가이드에 선택 기준을 연결한다.
   실제 모델로 오류 관측→진단→즉시 수리 또는 접수→원래 업무 완료를 검증한다.
   보호 정책을 바꾸는 구현 자체는 일반 자식 수리가 아닌 정식 개발 경로에서 반영한다.

필수 사례는 일시 429·정상 빈 결과·코드 원인이 아닌 404의 오진 방지, 명확한 예외의 짧은 수리,
관용구·스크립트 수정과 새 호출, 설명 변경의 교재·번역 영향, 전체 회귀가 필요한 수리의 인계다.
검사 중 한도 소진, 적용 중 만료, 새 요청·취소, 동시 후보 충돌, 같은 결함 중복 접수,
후속 실행 불가, 활성화 성공 뒤 각인 실패, 이미 성공한 쓰기의 중복 방지도 포함한다.

기존 우회 방식·무제한 즉시 수리·이 설계를 같은 모델·과제·예산으로 비교한다.
원래 결과의 품질, 사용자에게 결과가 도착한 시간, 수리로 추가된 대기, 후속을 포함한 전체 시간·토큰,
수리 완료율·재발·오진·중복 효과를 함께 기록한다. 후속 비용을 빼고 빨라졌다고 주장하지 않는다.
현재는 설계 검토만 완료했으며 시간·토큰 절감이나 자동 수리 동작은 아직 검증하지 않았다.
