# 가이드 조회와 재사용 부품의 호출 계약 수리 설계

작성일: 2026-10-18. 상태: **구현 완료. 정본 main 반영·검증 결과는 §8 참고**.

AI가 이미 갖춘 능력을 발견하고, 내부 절차를 다시 작성하지 않고 호출하며, 결과를 다음
작업에 연결할 수 있도록 한다. 정확한 가이드 이름 조회를 먼저 수리하고, 등록 스크립트의
계약과 PC·TV 제어의 재사용 부품을 함께 완성한다. 판단은 호출자에게, 반복 절차는 부품에,
보장은 계약에 둔다. 실행 절차도 진화하지만 그 변경을 호출자가 매번 알아야 하지는 않게 한다.

목적과 평가 기준은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)을 따른다. 하드웨어 부분은
[수동 하드웨어 앱과 AI 공유 실행 설계](HARDWARE_CONTROL_APPS_AND_GUIDES_DESIGN_2026_10_18.md)의
발견·공유 코드·호출 계약을 구체화한다. 장치 기능이나 지원 OS를 새로 늘리는 설계는 아니다.

## 1 수리 범위와 현재 근거

조사 기준은 정본 저장소 main의 `36564d56`과 2026-10-18 현재 작업본이다. 등록 스크립트
수치는 미커밋 원장 변경을 포함한 관측값이며 커밋의 고정 통계가 아니다. 다른 세션의 작업은
구현 착수 시 다시 대조하고, 이미 수리된 항목은 같은 인수 기준으로 확인한 뒤 중복 구현하지 않는다.

| 경계 | 확인된 현재 상태 | 수리 후 성질 |
| --- | --- | --- |
| 이름에서 가이드로 | `python_libraries.md`, `managed_records.md`를 정확히 요청해도 다른 교재를 반환 | 정확한 이름·명시 별칭은 지정 문서 또는 명시 실패로만 귀결 |
| 스크립트에서 계약으로 | 작업본의 등록 34개 중 계약 선언 3개. 나머지는 주로 description 산문 | 이번에 이관한 부품은 입력·반환·효과를 조회하고 실행 경계에서 검사 |
| 의도에서 하드웨어 실행으로 | PC 가이드와 프론트 코드가 prepare·전송·대기·decode 순서를 각각 구성 | 앱·AI가 같은 저장 함수와 등록 스크립트를 호출 |
| 호출 중단에서 후속 확인으로 | PC 예제의 완료 대기 이후 처리를 호출자가 다시 구성 | 기존 작업 참조로 확인을 계속하며 변경 요청은 재전송하지 않음 |

알고리즘 변경, 새 IBL 핵심 액션, 전 하드웨어 통합 플랫폼이다. 포식 기억의 의미 축적은 별도
구체 설계가 필요하다. 실제 실패가 나올 때까지 일반 능력 개선을 보류한다는 뜻은 아니다.

## 3 정확한 가이드 이름 조회

### 3.1 조회 규칙

현재 `_search_guide`의 파일명 빠른길을 다음 순서로 수리한다.

1. 기존처럼 앞뒤 공백·코드 인용 표시만 정리한다. 등록 별칭 또는 `.md` 파일명 요청은
   정확한 참조로 분류하고, 이후 키워드 점수 검색으로 내려가지 않는다.
2. 명시 별칭은 해당 등록 항목의 정본 파일로 해소한다. `ibl_v2.md`가
   `ibl_composition.md`로 연결되는 현재 호환 계약을 유지한다.
3. 등록 파일명은 등록된 그 파일로 해소한다. 별칭의 다른 소유자와 충돌하면 어느 쪽도
   임의 선택하지 않는다. 기존 명시 별칭과 같은 이름의 호환 파일이 있는 경우는 별칭이 우선한다.
4. 등록에 없는 정확한 파일명은 `data/guides/` 아래의 실존 Markdown 파일을 직접 연다.
   주 목차나 검색 결과에 새로 등록하지 않는다. `python_libraries.md`와
   `managed_records.md`는 이 경로로 도달한다.
5. 정확한 참조가 없으면 `GUIDE_NOT_FOUND`, 등록은 있으나 대상이 없으면
   `GUIDE_TARGET_MISSING`, 소유자가 여럿이면 `GUIDE_REFERENCE_AMBIGUOUS`로 실패한다.
   후보를 안내하더라도 다른 문서 본문을 함께 반환하지 않는다.
6. 그 외 자연어 요청만 기존 키워드 검색을 사용한다. 빈 query의 주 목차 목록도 유지한다.

새 오류 코드는 이 수리의 제안이며 현재 구현된 코드가 아니다. 성공 반환은 기존 `file`,
`content`, `guides`, `match` 계열을 유지하고, 미등록 문서에는 `registered:false`를 명시한다.
`read:false`도 같은 대상 해소를 하되 본문은 읽어 반환하지 않는다. 파일명·별칭·실패 응답을
서로 구별할 수 있어야 한다.

파일명 직접 조회는 basename 하나만 받는다. 경로 구분자·절대 경로·`..` 탐색을 거절하고,
심볼릭 링크 해소 후에도 가이드 루트 밖을 읽지 않는다. 파일명 대소문자를 임의 보정하거나
퍼지 검색으로 대체하지 않는다. DB가 없거나 손상된 경우는 별칭 우선순위를 확정할 수 없으므로
카탈로그 오류를 명시한다. 운영 계정의 기존 가이드 접근 경계는 유지한다.

실제로 연 파일은 기존 `search_guide` 후처리를 통과한다. 전체 `catalog_revision`,
본문 `content_hash`, `if_hash`, 절 선택, 해당 문서의 열람 귀속은 유지한다.
API·MCP와 in-process 경로가 같은 응답 의미를 소비한다.

### 3.2 재발 방지

새 검사기를 추가하지 않고 `scripts/iblbuild_guide_wiring.py`를 보강한다. 기존
`build_ibl_nodes.py --check`에서 다음을 검증한다.

- 등록 항목·명시 별칭의 대상 실존, 안전한 파일명, ID·별칭 소유 충돌.
- 가이드의 실제 Markdown 링크가 가리키는 가이드 파일의 실존. 상대 경로와 앵커를 분리하고
  코드 펜스 속 예제·외부 URL을 로컬 파일로 오인하지 않는다. 다른 docs로 향하는 링크는
  파일 실존만 확인하며 `read_guide`의 지원 범위로 주장하지 않는다.
- 링크된 참고 가이드를 고아 경고의 참조 집합에 포함한다. 폴더에만 있다는 이유로 DB 등록을
  강제하지 않는다. 기존 런타임 생성 문서의 예외는 유지한다.

검사 코드와 조회 코드의 동작 일치는 회귀에서 확인한다. 모든 미등록 문서를 목차에 넣거나,
지금의 수작업 메타데이터를 파일명에서 추정해 생성하지 않는다. `guide_registration.md`의
옛 execution_map 설명도 현재 guide_map 계약에 맞춰 정리한다.

## 4 재사용 부품의 계약

### 4.1 기존 선언과 실행기를 사용한다

`callable_contract`의 `params`, `required`, `defaults`, `enums`, `variants`,
`result`, `effects`, `pipe_input`, 자원 선언을 사용한다. 등록 스크립트에는
`adapter.protocol: registered-json/1`을 우선 사용하여 stdin 객체와 stdout JSON 계약을
유지한다. 이관을 이유로 모든 스크립트를 새로운 프로토콜로 바꾸지 않는다.

입력 형식은 실행 전에, 출력 형식은 기존 Script 경계에서 검사한다. op별 필수값과 금지값은
조건부 계약으로 표현하고 지원하지 않는 조합을 조용히 무시하지 않는다. 출력은 후속 부품이
사용하는 핵심 필드를 구조적으로 선언한다. `result: Record`만 붙여 계약 이관을 완료로
세지 않는다. 실제 외부 응답이 변하는 부분만 열린 Record 또는 Unknown으로 남긴다.

단위·시각 기준·성공 의미처럼 기존 타입 체계가 표현하지 않는 것은 가이드와 구현의 검증에
남기고 서로 대조한다. 이 작업에서 단위 타입이나 새 계약 언어를 도입하지 않는다.

효과는 실제 동작을 기준으로 선언한다. 상태 조회가 관측 원장·캐시를 쓰면 이를 무시하고
순수 함수로 선언하지 않는다. 상태 설정은 목표값이 같아도 자동 재시도가 안전하다는 뜻이
아니다. 불명확한 효과는 `unknown`으로 보존하며, 계약 추가가 기존 resume/reuse 정책을
뜻하지 않게 완화하지 않는지 검사한다.

### 4.2 첫 적용 묶음

첫 묶음은 새 하드웨어 부품과 기존 `세계지도`, `이미지변환`, `압축`이다. 기존 세 스크립트는
각각 조회·파일 생성·여러 op의 파일 작업을 다뤄 하드웨어 밖에서도 같은 계약 경계가 작동하는지
확인할 수 있다. 선정은 실패를 기다리는 절차가 아니라 서로 다른 부작용·입출력의 검증 범위다.

각 스크립트의 실제 지원 인수·별칭·기본값을 먼저 확정하고 현재 호출 사례를 유지한다.
옵션 누락·잘못된 값·빈 결과·외부 실패·부분 산출물을 검사한다. `description`의 긴 인수 나열은
구조화된 계약과 중복되는 만큼 줄이고 용도·의미·가이드 포인터를 남긴다. 계약이 없는 나머지는
기존 보수적인 실행을 유지하며 이번 묶음 완료를 31개 전체 이관으로 보고하지 않는다.

이미 계약이 있는 `python_libraries`, `시험`, `의약품허가조회`는 호환 회귀 대상이다.
특히 라이브러리 세션의 ForeignRef 수명과 기존 시험 결과의 업무 판정을 새 봉투로 바꾸지 않는다.

### 4.3 발견과 계약의 연결

기존 `script list/query`와 `reusable_catalog`가 원장의 계약을 그대로 투영한다. 같은 ID를
목록에서 찾고 상세 계약으로 확인한 뒤 호출할 수 있어야 한다. `contract_known`은 선언의
존재이며 실제 환경에서 성공했다는 표시는 아니다. 새 상시 프롬프트에 부품 목록을 덧붙이지 않는다.

PC·TV 가이드에는 공개 호출 이름과 계약 조회 방법을 적는다. 기존 control_guide 포인터는
유지한다. 저장 함수는 기존 이름·서명·호출 계약 조회에 나타나며 본문 전체는 필요한 때만 펼친다.
유효한 가이드와 호출 가능한 부품을 함께 배포한다. 등록 누락을 긴 레시피 자동 재작성으로 덮지 않는다.

## 5 PC와 TV 제어 부품

### 5.1 공개 호출과 내부 분해

다음 이름과 호출은 **구현할 인터페이스**다. 현 시스템에 이미 등록됐다는 뜻은 아니다.

```ibl
#!ibl edition=2
$상태 = [fn:PC제어]{대상:$PC, 요청:{action:"status"}}
$변경 = [fn:PC제어]{대상:$PC, 요청:{action:"volume",device_id:$출력,value:30}}
return $변경
```

PC 등록 ID는 `대상`, 오디오 출력 ID는 `요청.device_id`로 구별한다. 로컬 본체는
기존 UI의 `__local__` 식별자를 명시적으로 사용한다. 공개 호출에서 OS·코드 경로·셸 명령·
소스 본문을 받지 않는다. OS는 선택된 등록 기기 또는 본체에서 확인하고, 해소되지 않으면
실패한다. 별칭이 아닌 ID를 기본으로 하며 가이드가 대상을 고르는 방법을 설명한다.

| 부품 | 책임 |
| --- | --- |
| 등록 Script `PC제어부품` | 기존 contract·prepare·local·decode. 공용 인수 검사와 네이티브 결과 검증 |
| 저장 함수 `PC제어` | 대상 검증, OS별 소스 읽기, prepare, 기존 guestpc 접수, 완료 대기, decode |
| 저장 함수 `PC제어확인` | 이전 호출이 반환한 작업을 같은 task_ref로 확인하고 decode. 새 shell 전송 없음 |
| 등록 Script `TV제어` | 기존 TV run의 등록 호출. 네트워크 설정은 기존 비공개 원장에서 해소 |

PC의 전송을 Python 자식 프로세스에서 임의 HTTP 요청으로 우회하지 않는다. IBL 관용구가
기존 guestpc와 task를 호출하므로 현재 행위자·권한·예산·실행 원장 경계를 유지한다.
현재 외부PC준비·작업확인 관용구와 공유할 수 있는 계약은 재사용하되, 작업폴더 등이 필수인
범용 셸 관용구에 하드웨어 제어를 억지로 맞추지 않는다.

### 5.2 구현 위치와 호환

등록 파일은 `data/scripts/` 안에 있어야 한다. PC·TV 공용 Python 구현을 각각
`data/scripts/pc_control.py`, `data/scripts/tv_control.py`로 옮겨 등록한다. 기존
`data/instruments/` 경로는 과거 호출을 위한 얇은 호환 진입점으로 남긴다. 소스 두 벌을
유지하지 않는다. 호환 진입점은 현재 몸 또는 자기수리 사본의 루트에서 정본 모듈을 읽는다.
임시 폴더로 복사된 기존 호출도 루트를 올바르게 해소하는지 회귀한다.

네이티브 Python·PowerShell 파일은 기존 `data/instruments/` 위치에 유지할 수 있다.
PC 저장 함수가 허용된 OS·action에 따라 고정 경로를 고르고 `self:read`로 읽어 prepare에
전달한다. 이 원문은 모델이 다시 작성하지 않고 실행기 내부 값으로 전달하며, 실제 읽은
바이트의 지문을 계획·영수증에 연결한다. 공개 반환에는 네이티브 코드·stdin 전체를 싣지 않는다.

등록 스크립트와 가져오는 Python 모듈은 기존 `ibl_dependencies.script_snapshot`의
의존성 범위로 추적한다. 네이티브 소스는 파일 읽기 결과와 입력으로 추적한다. 구현·네이티브
파일 중 하나를 바꾼 경우 재개가 오래된 성공을 잘못 재사용하지 않는지 별도로 검증한다.
추적되지 않는 외부 모듈을 동적 로드하는 편법으로 의존성 관측을 우회하지 않는다.

PC 저장 정의는 `data/idioms/pc_control.ibl`, `pc_control_check.ibl`과 대응 seed로 추적한다.
기존 `register_webapp_idioms.py`의 시드 선택·검증 경로를 확장하고 `add_examples_batch`로
멱등 등록한다. 함수 본문의 정본은 `.ibl`이고 seed의 본문은 그 파일에서 읽어 만들거나
동일성을 검사한다. 두 본문을 독립적으로 편집하지 않는다. 같은 이름의 다른 정의는 명시 개정
절차를 따른다. 개인 해마에만 저장해서
새 설치에서는 실행되지 않는 상태를 배포 완료로 보지 않는다. 설치·업데이트의 기능 준비 단계가
등록과 가용성 확인을 수행하며, 실패하면 앱은 해당 호출을 비활성화하고 원인을 표시한다.

원격 대기는 기본 60초, 유튜브 동작은 150초, 명시 대기 인수는 기존 self:task 범위인
0~240초를 따른다. 대기 0은 접수 후 바로 작업을 반환한다. 장치 실행 제한은 현재 기본 동작
30초·유튜브 120초를 유지한다. 대기 제한과 장치 실행 제한을 서로 대신하지 않는다.

### 5.3 완료와 재개

PC 공개 반환은 다음의 작은 Record로 정한다. 아래 필드도 구현 목표다.

| 필드 | 의미 |
| --- | --- |
| `status` | `completed`, `pending`, `failed`, `unknown` |
| `target` | 확정한 PC 식별자 |
| `verified` | 목표 상태를 관측했는지. 미확인은 false이며 completed와 별개 |
| `result` | 성공 결과 또는 보존 가능한 부분 관측. 기존 PC protocol·action·source_sha256 유지 |
| `task_ref` | 원격 접수 뒤 받은 기존 작업 참조. 로컬이면 null |
| `verification` | 요청 ID·OS·정규화 요청·소스 지문 등 decode에 필요한 작은 계획. 원문·stdin 제외 |
| `evidence_ref` | 준비 결과와 접수 호출을 가리키는 기존 실행 영수증 참조. 원래 계약과 계획 대조용 |
| `failure` | 실패 단계·원인·다음 확인 방법. 정상일 때 null |

`completed`는 그 호출의 처리 종료다. open_url·잠금처럼 확인할 수 없는 효과는
`completed, verified:false`이며 사용자 목표 달성으로 승격하지 않는다. OS 음량 재조회도
물리 스피커의 소리 확인을 뜻하지 않는다. 기존 유튜브 검증 조건은 그대로 유지한다.

대기 제한에 도달했으나 작업이 살아 있으면 `pending`과 작업·검증 계획을 반환한다.
후속 호출은 `[fn:PC제어확인]{작업:$변경, 대기:60}`처럼 전체 작은 Record를 전달한다.
이 함수는 원래 task_ref로만 기다리며 prepare·shell을 다시 실행하지 않는다. 원장 조회의
대상과 전달된 대상, 응답 request_id·OS·action·출력 ID를 모두 대조한다. 임의로 바꾼 계획은
원래 호출 근거와 대조하고 불일치하면 검증하지 않는다. 필요한 원문이 만료·소실됐으면
`unknown`으로 남긴다. 최신 코드를 다시 실행해 과거 요청의 결과를 대신 만들지 않는다.

준비 결과와 접수증을 연결하는 참조 투영은 기존 IBL 실행 원장의 책임이다. 현재 공개 반환에
자동으로 들어 있다고 가정하지 않는다. 구현 단계 C에서 기존 run/call 참조를 연결하고,
행위자 접근 검사와 원문 조회를 재사용한다. PC 모듈은 전달된 verification을 정본으로 믿지
않으며 영수증의 준비 결과와 대조한다. 별도 영속화·서명 토큰·하드웨어 실행 원장은 추가하지 않는다.

접수 후 응답을 잃었거나 재시작으로 작업 상태가 불명하면 기존 IBL 영수증·원격 작업 원장에서
복구한다. 접수됐는지 확인할 수 없을 때 새 request_id로 자동 재전송하지 않는다. 이미 완료한
작업은 같은 관측 결과로 확인한다. 계획을 잃은 경우 기존 result_ref로 준비 결과와 접수증을
회수하는 경로를 가이드에 적고, 별도 하드웨어 작업 DB를 만들지 않는다.

현재 decode가 필요로 하는 핵심은 request·platform·source_sha256이다. 이를 소스 본문과
분리하는 것은 공용 PC 모듈의 책임이다. 소스가 변경된 뒤 대기 중 결과를 확인할 때는 원래
요청의 계약과 지문을 사용한다. 호환 검증을 보장할 수 없으면 unknown으로 종료한다.

### 5.4 TV와 UI 소비자

TV는 다음처럼 바로 호출한다.

```ibl
#!ibl edition=2
return [self:script]{id:"TV제어",args:{target:$TV,op:"status"}}
```

TV의 기존 success·verified·reachable·power 의미를 유지하고 PC와 같게 보이도록
억지로 반환 봉투를 바꾸지 않는다. 상태 미응답은 전원 꺼짐이 아니며, 앱 실행 확인은 영상
재생 확인이 아니다. 토글·상대 음량·키 전송은 자동 재시도하지 않는다. IP·MAC·토큰을
공개 인수에 추가하지 않는다. 조회 시 관측 원장 갱신도 계약의 효과 판단에 포함한다.

`frontend/src/lib/pc-control.ts`는 긴 IBL 조립을 없애고 PC 공개 함수의 호출·진행 표시를
소비한다. pending이면 동일 작업 확인, failed·unknown이면 실패와 관측 범위를 표시한다.
TV YAML의 반복 read→write→script 조각은 TV제어 호출로 바꾼다. 소스 선택과 검증 규칙이
UI에 다시 생기지 않게 한다. 화면 캡처는 기존 guestpc screen 경로를 유지한다.

가이드는 대상 선택, 지원 범위, 짧은 호출, 결과 해석, 재개 방법을 남긴다. 내부 연결 골격은
수리·디버깅용 구현 설명으로 옮기고 정상 사용 경로의 필수 교재에서 제거한다. 보고서처럼
과제별로 달라지는 골격까지 기계적으로 부품화하지 않는다.

모의 시험은 절차·권한·입출력·중복 전송을 검증한다. 실제 장치에서는 같은 대상과 같은
완료 조건으로 앱과 AI 호출을 비교하며, 시험 전 상태와 복원 결과를 기록한다. 시험하지 않은
OS·브라우저·물리 출력은 해당 범위의 미검증으로 남기고 모의 통과로 대신하지 않는다.

비용은 기존 레시피와 새 호출을 같은 모델·대상·입력·완료 조건에서 비교한다. 최초 가이드 읽기와
재사용, 정상과 지연/실패를 나누고 실제 완료 시간과 입력·출력·캐시 포함 전체 토큰을 기록한다.
짧은 호출이 내부 작업을 숨긴 것뿐인지도 본다. 등록·학습 비용은 별도로 포함한다.
성능 측정은 구조 수리의 선행 조건이 아니며, 측정 전에는 토큰·시간 절감률을 주장하지 않는다.

완료 보고는 **설계 반영, 계약·조회 구현, 앱·AI 전환, 배포, 실기 확인, 비용 관측**을 구분한다.
이 문서의 커밋은 설계 반영이며 구현 완료가 아니다.

## 8 구현 결과 (2026-10-18)

정본 main에서 A~D를 구현했다. `guide_db.json`의 편집 목차는 유지하며 이름 조회·실존·
소유권·참고 링크를 함께 검사한다. 첫 계약 적용 묶음은 세계지도·이미지변환·압축·PC제어부품·
TV제어다. 계약이 없는 다른 스크립트는 종전의 보수적 실행을 유지한다.

설계 중 아래 세부 사항은 실제 실행 경계에 맞춰 확정했다.

- **배포 함수**: `data/idioms/installed.json`의 이름→원문 경로를 기존 정의 해소기가 읽는다.
  첫 설치의 호출 가용성을 임베딩 모델 다운로드나 개인 해마 데이터에 종속시키지 않는다.
  해마 시드는 `source_file`로 같은 원문을 읽고 기존 add_examples_batch 경로로 의미 검색을
  보강한다. 같은 원문의 색인 사본은 중복 정의로 세지 않으며, 다른 원문이면 충돌을 드러낸다.
  기존 함수 서명 조회와 reusable_catalog가 이 배포 정의도 발견한다. 언어 엔진에 PC·TV 이름은 없다.
- **영수증 투영**: 액션 데이터의 receipt_ref, Script 어댑터의 receipt_ref·receipt_inputs가
  기존 run/call 참조를 연결한다. 영수증 값은 현재 주체·장치·권한·행위자 및 프로젝트 루트
  경계를 확인해 자식 Script의 context로만 전달한다. PC 준비 결과와 guestpc 접수 결과를
  각각 참조하므로 verification·target·task_ref 변조를 원 결과와 대조한다. 새 하드웨어 원장은 없다.
- **PC wire**: 기존 JSON을 그대로 쓰는 세 스크립트와 TV는 registered-json/1이다. PC 내부
  부품은 위 context를 받기 위해 기존 ibl-script/2를 사용한다. 과거 instruments 진입점은
  단일 구현을 읽는 호환 입구이며, 파일 호출의 원래 JSON 인터페이스도 유지한다.
- **편성표 의존성**: TV의 tv_epg도 scripts로 옮겨 정상 Python import로 추적한다. 기존
  instruments 경로는 호환 입구다. 네이티브 PC 소스는 기존 위치에서 IBL이 읽는다.
- **앱 대기**: PC 앱은 pending·관측 불명의 전체 작업을 보존하고 ‘기존 작업 확인’으로
  후속 조회한다. 대기 중 변경 버튼을 비활성화하며, 확인 함수는 prepare·shell을 호출하지 않는다.
  원 요청의 검증기 코드가 달라졌거나 영수증이 만료되면 unknown을 유지한다.

공개 호출은 §5의 형태다. 원격 대기 0~240초와 장치 실행 제한 30/120초를 분리했다.
TV 앱의 반복 read→write→script 연결 28곳을 등록 호출로 바꿨고, PC 앱은 저장 함수를
호출한다. 정상 사용 가이드는 대상 선택·호출·결과 해석·후속 확인을 설명한다.

검증 기록은 아래 완료 기록을 따른다. 구조 변경만으로 시간·토큰 절감률을 주장하지 않는다.

설치 갱신은 기존 userdata_sync 트랜잭션에서 처리한다. 코어 파일과 같은 등록 항목만
YAML 파서로 병합하고, origin:user·다른 파일을 가리키는 개인 항목·기존 lifecycle과 등록 시각은
보존한다. origin:user의 소스도 덮어쓰지 않는다. core_manifest의 idioms 목록은 installed.json에서
파생되어 배포 함수의 원문과 목록을 함께 갱신한다. 이 목록도 빌드가 생성하며 직접 편집하지 않는다.

## 2026-10-24 — 잠재적 어휘의 사용 방식 상호 비교와 공통 경계 수리

형태 전환은 사용자가 결정한다. 빈도에 따른 자동 승격·강등이나 상시 노출 변경은 추가하지 않는다.
이번 변경은 기존 어휘·등록 스크립트·저장 함수·드라이버가 발견·호출·조합·완료·복구에서
이미 가진 정보를 일관되게 사용하도록 한다.

- 발견: 배포 함수의 이름뿐인 설명을 기존 `*_seeds.json`의 intent로 보완한다. alias·원문 파일과
  현재 배포 정의가 일치하는 교재만 사용하고 충돌·외부 경로·다른 원문은 제외한다. 설명 사본이나
  별도 모델 호출은 없다. PC 음량·휴대폰 화면 요구를 기존 함수 이름을 몰라도 후보로 찾는다.
- 계약 신선도: 저장 당시 capability_contract는 후보 소개의 근거로 쓰지 않는다. 선택된 함수만
  실행기와 같은 describe로 현재 정의·의존성·노드 접근을 검사한다. 옛 원문 지문이 같아도
  하위 반환 타입이 바뀌면 현재 타입을 소개하고, 현재 계약 검사 거절은 소개에도 남긴다.
- 오류 보존: PC·Android 제어·확인·PC 묶음 조회는 구조화된 error_code/failure/recovery를
  우선 사용한다. 원 오류는 failure.cause, 복구 지시는 failure.recovery에 보존한다.
  구조화 필드가 잘못된 경우에도 원인은 남기고 기존 안내로 돌아간다. 문자열 코드 추출은
  구조화 코드가 없을 때만 사용한다. pending/unknown의 원 영수증 조회·재전송 금지는 유지한다.
- 스크립트 호출 계약: 보고서HTML의 src/dst·선택 인자·반환 행 구조를 기존 registry.yaml의
  callable_contract로 선언한다. 문자열/목록 drop_lines와 선택 null을 보존하고 효과는 unknown이다.
  HTML 생성·표 구조 보존을 시각 검수나 공개 승인으로 확대 해석하지 않는다.
- 작업 판정: registered-json/1의 명시 operation_outcome 전달을 ibl-script/2의 실행 봉투에도
  적용한다. value 내부 동명 필드는 업무 데이터다. 동기·백그라운드 저장/조회/알림·회원 실행과
  기존 감독 증거에서 판정이 이어지며 같은 작업의 반복 조회는 중복 합산하지 않는다.
  passed/failed만 선언할 수 있고 pending/unknown은 각 부품의 별도 상태 계약으로 남는다.

기존 호출자·예산·권한·자동 재사용 정책은 유지한다. 공유 패키지의 read/fill/write/script 회원
변환 경로를 재감사하고 선언 지문과 파생 사전을 갱신한다. 해마의 기존 배포 정의는 원본 DB를
온라인 백업한 뒤 공식 개정 경로로 갱신하여 옛 본문·실적을 개정 원장에 남긴다.
어휘/스크립트/드라이버의 형태나 always_on은 바꾸지 않는다.

검증은 test_reusable_catalog·test_control_driver·test_script_operation_outcomes·
test_report_html_script와 기존 제어/회원/배포 경계에 둔다. 반환 타입 변화, 모의 실패의
코드·복구 보존, 실제 임시 HTML 생성과 계약 검사, typed 작업 판정의 실제 자식 프로세스→
저장→조회→IBL 조합→감독 전달을 확인한다. 실기기 조작·시간/토큰 비교는 이 변경의 검증에
포함하지 않는다. 계약 없는 나머지 스크립트 전체를 이관한 것은 아니며, 동적 입력과 물리적
완료는 해당 부품의 실행 조건과 관측을 계속 따른다.
