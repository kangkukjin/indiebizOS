# 어휘·스크립트·관용구 변경 절차 수리 설계

작성: 2026-10-31. 상태: **설계 완료·구현 전**. 이 문서는 현재 기능과 제안을 구분한다.
범위: 어휘·등록 스크립트·관용구의 추가·수정·등록 해제·은퇴와 필요한 후속 반영.
목적 정본: [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md),
[변경 대상과 자기수리 경계](SELF_REPAIR_BOUNDARIES_2026_10_31.md).

## 1. 목적과 완료의 뜻

**능력을 추가·수정·제거할 때 결과의 정확성과 기존 소비자의 동작을 유지하면서,
실제 사용 가능한 상태까지 걸리는 시간과 전체 토큰 소비를 줄인다.**
사람과 AI가 매번 파일 위치·등록 방법·검사·기억·교재·빌드·활성화의 연결을 재구성하지
않게 한다. 중요한 변경인 만큼 빠뜨리지 않아야 하지만, 중요하다는 이유로 모든 변경에
모든 절차를 반복해서는 안 된다.

목표는 호출 문장을 짧게 만드는 데 그치지 않는다. 정의와 구현을 고치는 의미 판단은
작성자가 하고, 변경 영향의 수집·필수 단계 선택·기계 검사·반영·재개·완료 확인은
기존 시스템이 책임지는 하나의 경로로 연결한다. 필요한 의미 판단만 근거와 함께 돌려준다.
체크리스트를 또 외우거나 매 변경마다 새 계획서를 작성하게 만들면 수리 목적에 어긋난다.

완료는 다음을 모두 확인한 상태다.

- 의도한 정본에 요청한 변화가 반영됐고, 확인한 판본과 실제 사용되는 판본이 일치한다.
- 영향받는 기존 호출·교재·검색 경로가 현재 계약을 따른다. 제거한 대상은 새 호출에서
  사용할 수 없고, 남겨야 할 과거 정의·실행 증거는 유지된다.
- 변경에 필요한 검사와 활성 확인이 끝났다. 미확인·부분 실패·권한 대기는 완료와 구분한다.
- 원래 사용자 업무를 수리하던 중이라면 그 업무의 완료 조건까지 유지한다.

구현 완료와 비용 개선의 실측은 별도로 기록한다. 아래 목표 구조의 구현을 특정 업무의
성능 비교가 먼저 끝날 때까지 미루지 않으며, 측정하지 않은 시간·토큰 절감률은 주장하지 않는다.

## 2. 현재 기반과 실제 공백

2026-10-31 정본 코드·가이드의 정적 확인이다. 변경 소요 시간과 운영 빈도를 새로 측정한
결과는 아니다. 이미 해결한 기능을 없는 것으로 취급하지 않는다.

| 현재 기반 | 확인한 소유 위치 | 이번 수리에서 할 일 |
| --- | --- | --- |
| 관용구 저장·개정·은퇴, 불변 판본, 충돌 검사, 요청 중복 처리 | `backend/datastore/function_store.py`, `backend/ibl/function_library.py`, `workflow_store.py` | 그대로 사용하고 검사 결과·판본·완료 근거를 연결한다. 원장을 하나 더 만들지 않는다. |
| 저장 관용구와 앱·일정·트리거 등 외부 소비자의 변경 전후 검사 | `backend/ibl/function_consumers.py` | 이미 있는 검사를 영향 보고에 연결한다. 구조적으로 읽는 대상·필드의 범위를 표시하고 미수집 참조를 구별한다. |
| 관용구 정의와 기억의 참조 연결, 코퍼스 행이 없는 활성 정의의 검색 후보 투영 | `backend/datastore/function_memory.py` | 모든 등록에 합성 용례·임베딩을 강제하는 절차를 만들지 않는다. 필요한 검색 경로만 확인한다. |
| 스크립트 등록·갱신·해제와 선언 계약 검사 | `data/packages/installed/tools/system_essentials/script_ops.py` | 같은 소유자 안에 조건부 변경·의존 검사·정확한 반영 결과를 보강한다. 현재 register/remove에는 함수 원장과 같은 expected_revision·호출자 검사가 보이지 않는다. |
| 선언→어휘·도구 정의·fixture·문서 마커 생성과 검사 | `scripts/build_ibl_nodes.py` 및 `scripts/iblbuild_*` | 입력 변화에서 필요한 생성·검사·교재 검토를 선택한다. 두 번째 빌더나 별도 어휘 판정기를 만들지 않는다. |
| 패키지 활성 선택·의존 검사·캐시 갱신 | `backend/ibl/vocabulary_lifecycle.py` | 어휘 정의 변경과 활성 선택을 구분한다. 기존 사람 승인과 프로파일 경계를 유지한다. |
| 공통 수명 조회와 판본별 검증·수리 기록 | `backend/cognition/capability_age.py`, `backend/datastore/capability_history.py` | 실제 검사 영수증을 연결한다. 기록을 썼다는 사실을 검사 수행으로 대신하지 않는다. |
| 반복 검사와 영향 기반 시험 선택 | 등록 스크립트 `빌드검증`, `scripts/select_tests.py` | 기존 실행 결과를 소비하고 중복 실행을 줄인다. 검사 정책은 [회귀 규약](REGRESSION_TESTING.md)을 따른다. |
| 실행 영수증·재개와 구현의 적용·활성화 인계 | `backend/ibl/ibl_run_journal.py`, 기존 자기수리·재기동 경로 | 관리 변경의 단계 결과를 연결한다. 별도 작업 엔진이나 재기동 제어자를 만들지 않는다. |

주된 공백은 **개별 연산의 부재보다 연산 사이의 책임과 완료 조건이 분산된 것**이다.
등록 성공 이후 무엇을 해야 하는지, 수정 때문에 무엇이 무효가 됐는지, 실패 후 어디부터
이어야 하는지를 작성자가 다시 판단한다. 스크립트처럼 소유 연산 자체의 보호가 부족한
부분은 그 연산을 수리하고, 이미 있는 기능은 연결한다.

예컨대 관용구 수정에 코드 적용 절차를 요구하던 문제는 위 자기수리 경계 문서에서 이미
수리됐다. 이번 설계는 그 구분을 유지한다. 또한 관용구의 앱·예약 검사도 이미 있으므로
새 외부 호출자 검사기가 필요하다는 전제에서 시작하지 않는다.

## 3. 같은 입구에서 다루되 반영 계약은 대상별로 유지한다

| 대상 | 추가 | 수정 | 빼기 | 완료에 필요한 반영 |
| --- | --- | --- | --- | --- |
| 관용구 | 정의 검사 후 공식 원장 저장 | 현재 revision을 읽고 명시 개정, 영향 소비자 검사 | 공식 은퇴, 호출자 전환 필요 시 먼저 이행 | 새 원장 판본·새 호출 확인. 정의만 바꾸면 Git·빌드·재기동 불필요 |
| 등록 스크립트 | 본문·입출력 계약 검사와 공식 등록 | 본문/등록 정보의 변경 범위를 구분하고 해당 검사 | 등록 해제, 파일·실행 증거는 보존 | 등록·본문 지문과 새 실행 확인. 추적 소스 변경은 정본 커밋, 구현에 맞는 활성화 |
| 어휘 | 정본 선언·필요한 구현·교재·용례와 빌드 | 계약/설명/구현 차이에 따른 영향 검사 | 선언 은퇴와 소비자·현행 교재·검색 후보 정리 | 파생물·실제 활성 사전·실행부 일치와 관련 검사, 정본 커밋 |

어휘의 **정의 제거**, 패키지의 **잠재우기**, 스크립트의 **등록 해제**, 파일의 **영구 삭제**는
다른 연산이다. 입력이 모호하면 후보와 효과를 보여 주고 필요한 차이만 확인한다. 등록에서
빼라는 요청으로 소스·과거 판본·실행 이력을 연쇄 삭제하지 않는다.

관용구 배포 `.ibl`·시드까지 바꾸는 요청은 운영 정의 개정과 배포 소스 변경을 함께
추적한다. 한쪽 성공을 다른 쪽 성공으로 간주하지 않는다. 새 설치에서만 사용할 배포 변경은
그 범위를 명시하며, 운영 변경을 요구하지 않은 작업에 운영 원장 쓰기를 끼워 넣지 않는다.

## 4. 책임 배치와 사용 표면

### 4.1 변경 조정은 얇게, 검증·쓰기는 기존 소유자에게

공통 처리부는 **현재 상태 관측 → 변경 영향 해소 → 필요한 단계 구성 → 기존 연산 실행 →
완료 대조**를 맡는다. 종류별 연결부는 기존 원장·컴파일러·빌더·코드 적용 계약으로 위임한다.
정의·계약·의존 관계를 복제해서 보관하는 새 중앙 레지스트리는 만들지 않는다.

기계적 준비·검사 묶음은 등록 스크립트 하나로 제공하고, 반복하는 조합은 관용구로 보관한다.
단순 관리 호출로 이미 끝나는 일은 그 호출을 그대로 쓸 수 있다. 보호가 필요한 판본 대조와
호출자 검사는 공통 소유 연산에 둬서 직접 호출도 같은 계약을 따른다. 편의 래퍼를 거치지
않으면 안전성이 사라지는 구조를 만들지 않는다.

스크립트 자식 프로세스가 원장을 직접 편집하거나 내부 권한 객체를 만들어 쓰지 않는다.
쓰기는 기존 IBL/API의 인증된 관리 경계에서 실행한다. 현재 진입점에 필요한 조건부 변경이나
일괄 검사 기능이 없으면 해당 소유 서비스와 기존 연산에 최소 계약을 보강한다. 호출 문맥의
주체·프로젝트·사본·운영 원장·승인 범위를 전달할 수 없는 연결은 쓰기용으로 사용하지 않는다.

초기 구현은 새 코어 어휘를 추가하지 않는다. 등록 스크립트는 준비·검사·조회, 관용구는
기존 관리 연산과의 조합을 담당한다. 아래 이름과 인자는 **설계 예시이며 현재 호출 계약이 아니다**.

```ibl
[self:script]{id:"능력변경",args:{op:"plan",kind:"script",target:"정산",source:"..."}}
[fn:능력변경완료]{요청:"..."}
```

계획·검사·적용·상태 조회는 내부 단계다. 이미 승인된 범위의 평범한 변경은 한 번 맡기면
이어 수행한다. 매 단계마다 별도의 사용자 승인이나 모델의 “다음 단계 진행”을 요구하지 않는다.
단순 등록을 감싼 관용구를 종류별로 무조건 늘리지 않고 실제 반복 조합만 남긴다.

### 4.2 입력은 의도와 변경 내용, 나머지는 파생

필수 정보는 대상 종류·식별자, 추가/수정/은퇴 의도, 새 정의 또는 변경 파일 참조다.
이유·사용 조건·실패를 재현하는 입력·기대 결과는 의미 판단과 검증에 필요한 만큼 받는다.
대상 몸·원장 범위는 실행 문맥에서 해소하되 결과에 드러내고, 다른 몸을 바꾸려면 명시한다.

변경 파일·계약 차이에서 영향받는 경로·검사·활성화 방법을 파생한다. 작성자에게 문서·색인·
캐시·시험 목록을 모두 입력하게 하지 않는다. 기존 코드 수정 작업은 그 작업의 diff와 검사
기록을 입력으로 재사용한다. 변경마다 별도 YAML 명세서나 수리 보고서 작성을 강제하지 않는다.

요청은 기존 실행 ID에 연결하고, 적용 직전 관측한 판본·후보 지문을 붙인다. 동일 요청·동일
내용의 재전송은 이전 결과를 반환하고, 동일 요청 ID의 다른 내용은 충돌로 돌려준다.
관용구의 기존 요청 중복 처리를 재사용하며, 부족한 연산은 그 소유자 안에서 보강한다.

## 5. 영향과 작업량을 줄이는 방법

### 5.1 변화의 내용에 따라 필요한 단계만 선택

| 관측한 변화 | 필요한 처리 | 기본적으로 반복하지 않을 일 |
| --- | --- | --- |
| 설명·사용 조건만 변경 | 관련 검색 소개·교재의 의미 확인, 해당 파생물·색인 갱신 | 전체 실행 회귀·모든 임베딩 재생성·백엔드 재기동 |
| 관용구 본문 변경, 서명 유지 | 컴파일·소비자 검사, 실패 입력과 정상 입력의 새 호출, 판본별 검증 기록 | 코드 사본 적용·전체 어휘 빌드 |
| 인자·반환·효과 계약 변경 | 전이 호출자와 교재·용례 검토, 변경 계약 회귀, 필요한 이행 | 무관한 패키지·자료 전수 실행 |
| 스크립트 구현만 변경 | 구현·의존 지문 대조, 관련 시험, 새 실행 | 등록 정보가 같을 때 무조건 재등록 |
| 어휘 선언·구현 변경 | 기존 빌더와 영향 검사, 관련 교재·용례, 실행부별 활성 확인 | 무관한 원장 재작성·항상 전체 재기동 |
| 등록 해제·은퇴 | 활성 소비자 확인, 현행 발견 경로 제거, 기존 호출 거절 확인 | 과거 사건·실적·원문 삭제 |

설명 수정도 의미가 바뀌면 계약 변경이다. 파일 종류만으로 가벼운 변경이라고 판정하지 않는다.
기계가 구조 차이를 제시하고 의미 검토가 필요한 부분을 한정한다. 현재 계약과 다른 용례를
검토 없이 일괄 승인하거나, 설명을 자동 생성했다는 이유로 검토 완료를 기록하지 않는다.

검사 선택은 기존 빌더의 입력 목록과 `select_tests.py`를 사용한다. 실제 영향이 불명확하거나
언어·격리·공통 허브를 바꾸면 회귀 규약에 따라 넓힌다. 전수 검사를 생략하는 것이 목적이
아니라, 필요한 검사를 같은 후보에 불필요하게 여러 번 돌리지 않는 것이 목적이다.

### 5.2 의존 관계는 기존 구조에서 읽고, 관측 한계를 반환

관용구는 컴파일러의 이름 해소와 `function_consumers`를 사용한다. 스크립트·어휘도 같은
프로그램/선언 소비자를 연결하고, 각 원장의 판본과 출처 위치를 반환한다. 별도 정규식으로
IBL 의미를 재구현하지 않는다. 기존 정규식 기반 수명 수집은 참고 단서이며 변경 허용의 증명이 아니다.

결과는 확정 참조, 문자열·동적 선택 등 후보 참조, 조사하지 못한 범위를 구분한다. 잠든
예약·패키지는 활성 차단 사유와 분리해 나중에 다시 켤 때의 영향을 표시한다. 외부 Python이
동적으로 이름을 조합하는 경우까지 참조가 없다고 보증하지 않는다.

영향 확인 때 사용한 소비자 판본을 적용 직전에 대조한다. 조사 뒤 새 호출자가 생겼으면
해당 범위를 다시 검사한다. 서로 다른 원장에 단일 잠금이 있는 것처럼 약속하지 않으며,
필요한 조건부 쓰기와 순서는 각 소유자가 집행한다. 확인 불가능한 핵심 소비자는 미확인으로
남기고 해당 파괴적 반영을 완료로 처리하지 않는다.

### 5.3 발견·기억·소개는 필요한 것만 갱신

실행 정의의 등록, 검색 후보 편입, 상시 소개 선정, 실제 사용 경험은 구분한다.
관용구의 현행 카탈로그 투영처럼 이미 되는 경로를 재사용한다. 합성 용례가 필요한 경로는
`add_examples_batch`로 넣고 현재 계약으로 확인한다. 관련 설명·용례가 바뀐 범위만 재색인한다.
모든 부품을 상시 프롬프트에 올리거나 가짜 성공 실적을 심지 않는다.

은퇴한 정의의 과거 용례는 역사로 보존하면서 현행 호출 후보에서 제외한다. 바뀐 정의에
옛 판본의 성공을 이월하지 않는다. 현재 검색에서 빠졌는지와 과거 기록을 읽을 수 있는지를
각각 확인한다. 어휘 제거의 교재 정리는 현행 운영 표면을 대상으로 하며 과거 대화·실험의
문자열까지 없애는 전수 치환을 하지 않는다.

### 5.4 같은 후보의 유효한 결과는 재사용

재사용 조건은 후보 내용, 전이 의존 판본, 검사기/빌더 판본, 필요한 환경·권한·몸 범위다.
이 중 관련 입력이 바뀌면 해당 결과와 하류 결과만 무효화한다. 의미 검토도 검토한 원문과
선언 지문에 묶는다. “지난번 통과”나 수정 시각만으로 현재 검사를 대신하지 않는다.

첫 구현은 같은 변경 실행과 그 재개 안에서 중복 제거를 보장한다. 프로세스 간 영속 검사
캐시는 실제 병목과 유효성 계약이 확인된 뒤 선택한다. 캐시를 도입하기 위해 새 인프라를
먼저 만들지 않는다. 실제 외부 효과가 있는 검증 실행은 순수 검사처럼 자동 재생하지 않는다.

## 6. 반영·실패·재개의 계약

한 변경의 경과는 기존 실행 영수증에 단계별 결과로 연결한다. 최소 항목은 대상 범위·요청
참조, 이전/후보/반영 판본, 검사 근거, 적용 결과, 활성 관측, 남은 단계와 실패 이유다.
상세 로그는 기존 저장 위치를 참조하고 모델에는 요약과 필요한 실패 근거만 돌려준다.
새 상시 작업 DB·감독 모델·주기적 순찰은 추가하지 않는다.

| 단계 결과 | 다음 동작 |
| --- | --- |
| 변경 전 검사 실패 | 기존 정의 유지, 오류·영향 소비자·수정해야 할 입력 반환 |
| 조사 이후 판본 충돌 | 덮어쓰지 않고 최신 상태와 충돌 범위 재관측 |
| 반영 전 취소 | 더 쓰지 않고 후보·검사 결과 보존 |
| 반영 성공, 검색/활성 확인 실패 | 반영 사실을 유지해 부분 완료로 보고, 실패한 후속부터 재개 |
| 쓰기 요청 후 응답 유실 | 소유 원장의 요청/판본/적용 영수증을 조회해 대조. 효과 미확정이면 재전송 금지 |
| 재기동 필요 | 기존 적용·재기동 제어자에게 인계하고 같은 요청으로 복귀 |
| 완료 후 동일 요청 재호출 | 같은 영수증 반환, 현재 상태가 달라졌으면 그 사실을 별도 표시 |

함수 원장 안의 묶음 게시처럼 기존 소유자가 원자적으로 처리할 수 있는 범위는 이용한다.
함수 원장·파일·Git·색인·원격 몸 전체가 하나의 트랜잭션이라는 보장은 하지 않는다.
실패하면 정확히 어디까지 반영됐는지 보존하고, 되돌릴 수 있는 단계만 현재 판본을 확인해
복구한다. 동시 작업의 후속 변경을 과거 백업으로 덮어쓰지 않는다.

계약을 깨는 변경은 가능한 경우 **새 정의 준비 → 소비자 전환 → 이전 정의 은퇴**로 진행한다.
임시 이행용 이름은 종료 조건과 함께 관리하며 영구 별칭으로 남기지 않는다. 여러 종류를
함께 바꿀 때는 의존 순서와 안전한 중간 상태를 준비한다. 그것이 불가능하면 기존 적용
경로의 작업 배수·전환 구간을 사용하며 임의의 전역 잠금이나 새로운 중단 제어를 만들지 않는다.

## 7. 권한·활성·이력의 경계

- 관리되는 관용구 정의는 공식 운영 원장에서 개정한다. 실제 구현 파일만 기존 코드 수리
  경계를 따른다. 격리 검사 자식은 독립 원장을 사용하고 검사 성공을 운영 실행으로 기록하지 않는다.
- 새 관리 경로는 기존 승인·주체 검사·회원 제한을 우회하지 않는다. 반대로 이미 허용된
  정의 개정에 새 승인 관문을 추가하지 않는다. 상시 소개 선정과 패키지 활성 선택도 기존 정책을 따른다.
- 본문이나 검사 예제가 외부 전송·삭제를 수행하면 실행 효과에 맞는 기존 권한과 사본을
  사용한다. 단순 import·테스트 실행이 항상 무부작용이라고 가정하지 않는다.
- 어휘 reload가 갱신하지 못하는 패키지 서브모듈·backend는 기존 활성화 경로에 인계한다.
  새 호출이 어느 구현을 사용했는지 확인하고 재기동 호출 성공만으로 완료하지 않는다.
- 중앙 정본 반영과 폰·다른 PC 배포는 별도 범위다. 대상 기기가 포함된 요청이면 그 몸의
  판본·활성 관측까지 필요하고, 포함되지 않으면 다른 몸에도 반영됐다고 보고하지 않는다.
- 추적 파일 변경은 정본 main에서 변경 경로를 한정해 커밋한다. 동시 세션의 변경을 포함하지
  않는다. 관리 원장 개정만 있는 일에는 Git 커밋을 완료 조건으로 붙이지 않는다.
- 회수용 파일과 SQLite 백업은 기존 [백업 규약](../data/_backups/README.md)을 따른다.
  비밀 값은 후보 요약·로그·검사 입력·커밋에 복제하지 않는다.

## 8. 구현 순서와 대체할 기존 절차

| 단계 | 구현과 인수 범위 | 함께 줄이거나 없앨 것 |
| --- | --- | --- |
| 1. 소유 연산의 계약 정리 | 함수·스크립트·어휘 변경 결과를 현재 판본·범위·후속 필요로 해소. 스크립트 조건부 등록/해제와 경합 보호를 소유 모듈에 보강 | 래퍼만 검사하고 직접 호출은 무검사로 남는 경로, 등록 성공=전체 완료의 해석 |
| 2. 영향·검사 계획 | 기존 컴파일러·외부 소비자·빌더·시험 선택 결과를 한 계획으로 연결. 지원한 참조 범위와 미확인을 표시 | 매번 저장소 전체를 검색해 사람이 검사 목록을 다시 조립하는 절차, 중복 의존 목록 |
| 3. 관용구·스크립트 변경 완결 | 등록 스크립트와 기존 관리 연산의 조합, 새 호출 검증, 실패 단계 재개. 단순 작업은 한 요청으로 완료 | 개별 등록 도우미가 소유하던 중복 후처리. 의미가 다른 배포 시드 작성 기능은 유지 |
| 4. 어휘와 혼합 변경 | 정본 선언 변경·빌드·현행 교재/용례·검색·활성화 연결. 여러 종류의 안전한 전환·부분 실패 | 손으로 파생물을 고치는 우회, 같은 빌드/검사의 불필요한 반복, 무조건 재기동 |
| 5. 사용 경로 전환 | 가이드·오류 안내·등록 도우미·자기수리 실행을 같은 완료 계약에 연결하고 실제 모델 인수 | 구 절차를 별도 최신화해야 하는 중복 체크리스트, 상시 프롬프트의 긴 절차 주입 |

각 단계에서 지원한 종류·변경·복구 범위를 명시한다. 아직 지원하지 않는 작업은 기존
절차로 넘기되, 자동 처리한 것처럼 성공하지 않는다. 무기한 이중 경로를 남기지 않도록
소비자 전환이 끝난 중복 구현은 같은 단계에서 제거한다.

`new_action_checklist.md`, `script.md`, `workflow.md`는 현재 계약과 의미 판단 기준을
남기고 기계적으로 실행 가능한 절차는 새 경로의 안내로 바꾼다. 구현 전에는 현행 사용법을
미리 지우지 않는다. 직접 호출 API와 긴급 진단 경로는 유지하되 같은 소유 연산을 사용한다.

새 backend 모듈이 필요하면 기존 책임의 층 안에 두고 층 배정·1500줄 규칙을 따른다.
구체적인 모듈 분할은 구현 시 결정하지만, 정의 소유권·검사 권한·적용 제어권을 조정기나
등록 스크립트로 옮기지 않는다는 책임 배치는 이 설계에서 확정한다.

## 9. 검증과 효율 평가

### 9.1 계약 인수

세 종류 × 추가/수정/제거의 아홉 경로를 각각 격리 원장과 실제 관리 연산으로 검사한다.
효율 기능만 시험하는 모의 조정기로 대체하지 않는다. 기존 모듈별 회귀에 다음 경계를 보강한다.

| 확인할 성질 | 인수 조건 |
| --- | --- |
| 올바른 정본 | 관용구 운영 개정과 구현 사본의 경계를 유지. 시험 자식은 운영 데이터에 쓰지 않음 |
| 소비자 보호 | 저장 함수·앱·예약·스크립트 계약 변화로 새로 깨지는 호출을 찾고 위치를 반환. 기존의 무관한 파손과 구분 |
| 동시성 | 같은 항목 수정 충돌, 서로 다른 스크립트 동시 등록의 유실 방지, 검사 이후 소비자 변경 재확인 |
| 추가의 발견 가능성 | 새 정의가 해당 조회·검색 경로에서 발견되고 계약에 맞게 호출됨. 상시 소개 자동 승격 없음 |
| 수정의 실제 반영 | 기존 실패 입력과 정상 입력을 새 호출로 확인. 이전 컴파일 판본·실적을 새 검증으로 오인하지 않음 |
| 제거의 완결 | 현재 후보·새 호출에서 제외, 활성 소비자 보호, 과거 판본·실행 로그와 원본 파일의 보존 범위 확인 |
| 부분 실패 | 저장 뒤 색인 실패, 커밋 뒤 활성 실패, 응답 유실·취소·프로세스 교체를 주입. 성공 단계 중복 없이 재개 |
| 권한 유지 | 기존 허용 변경은 불필요한 승인 없이 진행, 기존 승인 대상은 우회 불가. 잘못된 몸·소유 범위 거절 |
| 혼합 변경 | 새 스크립트와 호출 관용구 도입, 계약 변경과 호출자 이행, 어휘 제거와 교재 정리를 실제 순서로 검사 |
| 불필요한 작업 제거 | 설명 수정에 무관한 회귀·재기동이 붙지 않고, 동일 후보 재개에서 유효한 검사가 반복되지 않음 |

검사는 [회귀 규약](REGRESSION_TESTING.md)의 관련 검사부터 실행한다. 공통 저장소·권한·실행
경계와 어휘 배포를 바꾼 단계에는 그 규약이 지정한 종합 회귀·system 묶음을 포함한다.
새 관리 경로 자신의 등록·수정·복구도 같은 계약으로 인수하며, 기존 직접 관리 경로로
수리할 수 있어야 한다. 관리 도구 하나의 실패로 모든 정의 개정이 막혀서는 안 된다.

### 9.2 실제 작성 작업의 효율

구현 전후에 같은 시작 상태·목표·변경 난도·완료 기준·모델/기어를 사용한다. 관용구의 작은
수정, 스크립트 계약 수정, 어휘 추가/제거, 여러 종류의 이행과 중단 재개를 포함한다.
기존 영수증·토큰 계측·실행 기록을 사용하고 입력·출력·캐시 사용을 분리해 집계한다.

- 품질: 누락된 후속 처리, 깨진 소비자, 잘못된 성공 보고, 사용자 보정 횟수.
- 시간: 요청부터 반영·활성·필수 확인까지의 실제 경과 시간. 실행 시간과 승인 대기를 구분.
- 토큰: 주 실행·의식·검수·내부 모델·해당 변경의 기억 후처리를 포함한 전체 소비.
- 반복 비용: 모델 왕복, 재검색·재빌드·재검사의 중복 횟수, 복구 중 재실행한 단계.
- 고정 비용: 초기 설치·색인·관리 스크립트 등록 비용과 매 변경 비용을 구분.

한 종류의 평균으로 다른 종류의 퇴행을 숨기지 않는다. 품질을 유지하면서 시간·전체 토큰이
함께 줄었을 때 효율 개선으로 기록한다. 계약 공백을 닫았지만 비용 비교를 하지 않은 단계는
구현 완료·효율 미측정으로 남긴다. 구체적인 절감률은 기준선 측정 후 정하며 지금 만들지 않는다.

## 10. 이번 문서의 반영 범위

이번 변경은 설계와 정문 포인터·변경 이력만 포함한다. 등록 스크립트·관용구·코어 어휘를
추가하지 않았고 운영 원장·등록부·활성 사전은 변경하지 않았다. 후속 구현은 위 순서와
인수 조건을 따르며 구현 기록·측정·잔여 범위는 이 문서에 이어 적는다.
