# 대화 이력의 시간대 표시 수리 — 2026-09-21

## 원인과 변경

학교의 수업보조 에이전트에게 오후 18:23에 현재 시각을 물은 대화가 오전 09:23으로
표시됐다. SQLite `messages.message_time`은 `CURRENT_TIMESTAMP`로 UTC를 저장하지만
API가 `2026-09-21 09:23:32`를 그대로 반환해 JavaScript `Date`가 현지 시각으로 해석했다.
실시간으로 추가하는 메시지는 `new Date()`를 사용하므로 이력을 다시 불러올 때 차이가 났다.

`ConversationDB.message_timestamp`가 이 저장소의 UTC 계약을 읽기 경계에서 적용한다.
시간대 없는 값은 UTC로 해석하고, 이미 오프셋이 있는 값은 같은 순간의 UTC로 변환한다.
반환 예시는 `2026-09-21T09:23:32Z`이며 한국 클라이언트에서는 오후 18:23으로 표시된다.
빈 값·해석 불가 값에 임의 시각을 만들지 않는다.

적용 범위는 일반 메시지 조회, 두 에이전트 사이의 조회, 미전달 메시지, 상대 목록의
마지막 메시지 시각이다. 숫자 ID와 원격의 YAML 에이전트 ID 모두 같은 응답을 사용한다.
AI용 프로젝트 대화 이력에도 현지 시각과 오프셋(`2026-09-21 18:23 +0900`)을 함께 붙인다.
시스템 AI처럼 별도 저장 규약을 쓰는 저장소에는 이 UTC 가정을 전파하지 않는다.
DB 원문 수정·시간 일괄 이동·프런트엔드 재빌드는 필요하지 않다.

## 검증

- `test_conversation_timezone.py`: 기존 UTC·명시 오프셋·소수 초·빈 값, 다섯 API 경로,
  새 메시지·미전달 메시지, 저장 원문 보존, 한국/뉴욕 변환, AI 이력의 현지 시각을 검증한다.
- 대화 시간대·이력 발췌·체크포인트·단일 러너 관련 31개 회귀 통과.
- `npx tsc -p tsconfig.app.json --noEmit` 통과.
- 실제 학교 메시지 312·313의 HTTP 응답에 `Z`가 붙고, 화면과 동일한
  `toLocaleTimeString('ko-KR', {hour:'2-digit', minute:'2-digit'})` 호출이
  두 메시지 모두 `오후 06:23`을 반환함을 확인했다.

이미 열린 창의 이력은 메모리에 있으므로 창을 다시 열어 조회하면 교정된 시각을 받는다.
