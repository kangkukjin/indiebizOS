# 외부사용자 웹앱과 클라이언트 담당 에이전트 개선안

상태: 구현 전 설계안. 이번 작업은 문서 작성만이며 실행 코드는 변경하지 않는다.
기준: 2026-09-15 정본 코드와 사용자 논의. 관련: EXTERNAL_SERVICE_APP_HANDOFF.md, MEMBER_WEB_DEFAULTS_2026_09_14.md, data/system_docs/communication.md.

## 1. 중심 개념

**외부 클라이언트가 IndieBiz OS에 요청하고, 허브 안의 클라이언트 담당 에이전트가 처리하여 요청자에게 결과를 돌려준다.**

클라이언트 담당 에이전트는 허브 내부의 역할이다. 브라우저에 별도의 AI 두뇌를 설치한다는 뜻이 아니다.
주인의 시스템 AI·개인 에이전트와 역할·문맥·권한을 구분한다. 기존 인지·모델·IBL 실행기를 재사용한다.
공통 역할과 정책을 사용하되, 실행 인스턴스·취소 상태·대화·기억은 클라이언트의 세션별로 분리한다.

브라우저 채팅과 앱 버튼은 같은 담당 에이전트에게 요청하는 두 입력 방식이다.
담당 에이전트라는 개념이 모든 클릭에 모델 호출을 요구하지는 않는다. 이미 정해진 앱 동작은 같은 요청 처리 경로 안에서
IBL로 바로 실행할 수 있고, 조사·계획이 필요한 요청만 인지 과정을 거친다.

```text
외부 웹앱: 채팅 / 앱 버튼       향후 허가된 다른 IndieBiz OS
          │                             │
          └──── 각 접속 방식의 인증 ──────┘
                         ↓
           공통 요청 계약 + 인증된 요청자
                         ↓
       클라이언트 담당 에이전트의 세션
          ├─ 허용된 허브 도구 실행
          ├─ 추가 질문·진행 상황·취소 처리
          └─ 필요할 때 클라이언트 도구 요청
                         ↓
              요청자에게 결과 전달·확인
```

## 2. 네 가지를 분리한다

| 판단 | 책임 |
|---|---|
| 누가 요청했는가 | 접속 인증으로 principal을 확정. 클라이언트가 보낸 이름·기기 ID는 인증 증거가 아님 |
| 무엇을 할 수 있는가 | 외부 요청 정책. 지원 기능은 기본 허용, 주인 시스템 개조·관리·사적 자원 접근 제외 |
| 어디서 실행하는가 | 작업이 요구하는 자원과 클라이언트의 실제 능력으로 결정 |
| 누구의 결과인가 | 실행 장소와 관계없이 인증된 요청자의 작업에 귀속 |

허브에서 검색·분석·문서를 생성하는 것은 가능하다. 회원 요청을 주인의 작업·기억·공개 보고서로 저장하는 것은 별개다.
주인 PC의 임시 작업 공간에서 문서를 만든 뒤 회원 기기에 보내는 것은 정상 경로다.
회원이 올린 파일의 변환과 주인의 파일을 읽는 것도 구분해야 한다.

초대 시 사람별 도구 체크리스트를 만들지 않는다. 한 벌의 외부 서비스 정책을 적용한다.
기존 공통 제외 설정·사용량 한도는 유지할 수 있다. 정책을 허용으로 바꾸는 것만으로 미전환 구현을 안전한 외부 기능으로 간주하지 않는다.

## 3. 현재 구현의 출발점과 간극

- `api_member.py`의 `/m/run` → `MemberSessionManager` → `MemberRunner` 경로가 이미 있다. 별도 에이전트 엔진을 새로 만들 필요는 없다.
- `principal.py`·`member_profile.py`·`member_bridge.py`에 신원·실행 관문·회원 기기 작업 전달이 있다. 이를 유지한다.
- 브라우저에는 IndexedDB, 작업 원장, 기기 작업 실행기, 결과 다운로드가 있다. 클라이언트 실행 어댑터로 재사용한다.
- 현재 기능 허용 범위가 좁아 허브의 일반적인 조사·작성 능력을 충분히 쓰지 못한다. 필요한 기능의 실행 경로를 전환해야 한다.
- 현재 보고서 앱은 제공 자료 기반의 별도 작성이다. 주인 보고서의 실제 조사·작성 기능을 외부 요청 문맥으로 실행하는 문제는 남아 있다.
- 일부 앱 요청·산출물 처리 판단이 브라우저에 있다. 예를 들어 output을 서버에 알리지 않고 최종 답변을 파일로 저장한다.
  이 방식만으로는 허브가 약속한 결과의 생성·전달 완료를 관리하거나 다른 클라이언트와 같은 계약을 쓰기 어렵다.
- `/nodes/ask` → `body_ask`는 자연어를 자기 사전으로 번역·실행하는 별도 경로다. 즉시 회원 경로로 교체하지 않는다.
  기존 소유주 장치 간 신뢰·인증과 향후 독립 IndieBiz OS의 인증을 같다고 가정하지 않는다.

## 4. 최소 변경 원칙

**우선 재사용**: AgentRunner/인지 파이프라인, 모델 호출·비용 계측, IBL 문법·실행기, principal, 회원 세션과 저장 격리, 기존 기기 작업 통로.

**집중 변경**: 외부 요청 입구, 회원 러너의 역할과 세션 조정, 외부 도구의 실행 문맥, 산출물 전달, 웹앱의 두 표면.

- 시스템 AI 싱글턴에 회원 모드를 추가하지 않는다. 주인 에이전트와 주인 런처의 기존 동작을 변경하지 않는다.
- `MemberRunner` 등의 전면 이름 변경·폴더 재배치부터 시작하지 않는다. 제품상 역할을 먼저 확정하고 필요한 동작만 분리한다.
- 새로운 IBL 노드·낱말이나 두 번째 도구 엔진을 만들지 않는다. 실행 위치·외부 지원은 기존 선언과 어댑터를 사용한다.
- URL·통신 프로토콜 하나로 모든 클라이언트를 억지로 통일하지 않는다. 인증과 전송은 어댑터, 요청 처리는 공통으로 둔다.
- 코어의 범용 경로·권한 결함이 드러나면 그 공통 지점만 고치고 회귀 검사한다. 외부 기능이라는 이유로 잘못된 우회를 유지하지 않는다.
- 첫 버전에 오프라인 작업 큐·자동 기기 동기화·외부 노드 탐색·연쇄 위임까지 넣지 않는다.

## 5. 공통 요청·응답 계약

필드 이름은 구현 시 기존 계약과 맞추되 의미는 먼저 고정한다.

| 구성 | 최소 내용 |
|---|---|
| 요청 | 버전, 요청 ID, 대화/작업 ID, 메시지 또는 공개 앱 동작 ID와 인자, 첨부 참조, 원하는 산출물 형태 |
| 서버 문맥 | 인증된 principal, 세션, 정책, 수신 시각, 예산. 클라이언트 입력에서 그대로 복사하지 않음 |
| 클라이언트 능력 | 파일 수신·선택 파일 제공·재생·위치 등 지원 기능. 허브 권한을 부여하는 자료가 아님 |
| 이벤트 | 접수, 진행, 사용자 답변 필요, 클라이언트 작업 필요, 결과 준비, 전달 완료, 실패, 취소 |
| 결과 | 설명/구조화 데이터, 산출물 ID·파일명·형식·크기·지문, 작업 및 전달 상태 |
| 회신 | 질문 또는 클라이언트 작업 ID, 현재 세션, 답변/실행 결과/저장 확인 |

클라이언트는 서버의 절대경로나 임의의 저장 위치를 지정하지 않는다. 첨부와 산출물은 요청자 범위의 참조로 다룬다.
브라우저의 상대 저장 경로는 로컬 어댑터가 해소한다. 허브는 산출물의 존재와 전달 상태를 알고 관리한다.
민감한 본문을 서버의 전역 로그나 주인의 기억에 남기지 않는다. 대화·장기 기억의 클라이언트 저장 정책은 우선 유지한다.

같은 요청 ID를 재전송했을 때 변경 작업을 중복 실행하지 않는다. 요청 ID는 인증된 요청자에 종속된다.
계산 완료와 전달 완료는 구분한다. 파일 저장 영수증/기기 수신 확인 전에는 전달 완료를 말하지 않는다.
연결 종료·취소 시 이미 실행된 효과를 되돌렸다고 주장하지 않는다. 결과 불명 상태와 재조회 경로를 제공한다.

첫 버전은 연결 중 작업을 기본으로 한다. 허브만으로 가능한 텍스트 요청에 USB 손발 연결을 요구하지 않는다.
클라이언트 기기 작업이 필요한 시점에만 그 능력과 연결을 검사한다. 끊김 뒤 무기한 작업 지속은 약속하지 않는다.
질문 응답은 같은 작업 ID에 연결하고, 대기 중인 실행기를 무기한 붙들기보다 재개 가능한 대화 상태로 처리한다.

## 6. 구현 순서와 완료 조건

### 1단계 — 담당 에이전트와 요청 입구 정리

MemberRunner를 허브의 클라이언트 담당 역할로 명시하고, 기존 회원 세션 입구를 공통 요청 처리 지점으로 정리한다.
`/m/run`은 호환 어댑터로 유지한다. 채팅과 앱은 같은 인증·주체·작업 ID·취소·이벤트 경로에 들어간다.
공개 앱 동작은 허브가 현재 선언으로 해소한다. 기존 IBL 실행 경로도 외부 실행 관문을 그대로 통과한다.
자연어 요청과 확정된 동작의 실행 방식을 내부에서 구분하되, 별도의 사용자 권한 체계를 만들지 않는다.

완료: 채팅과 앱 요청이 같은 외부 주체로 실행되고, 다른 회원·주인의 상태와 섞이지 않는다.
단순 앱 조회에 불필요한 모델 호출이 없으며, 추가 질문에 대한 답변으로 같은 작업을 이어갈 수 있다.

### 2단계 — 허브 도구와 산출물 전달 정리

각 외부 도구에 요청자·작업·임시 작업 공간·첨부·산출물 등록·클라이언트 작업 채널을 제공한다.
실행 위치는 허브 계산/클라이언트 효과/혼합으로 구분한다. 전체 도구를 감싸는 거대한 대체 엔진은 만들지 않는다.
기존 도구가 주인 전역 경로·로그인 브라우저·캐시·개인 설정을 사용하는 곳은 필요한 인자를 받는 어댑터로 전환한다.
작업 디렉토리만 바꾸고 격리가 됐다고 판단하지 않는다. 실제 호출 경로의 읽기·쓰기와 하위 실행까지 확인한다.

산출물을 등록하면 회원 연결을 통해 전송하고 수신·저장 확인을 받는다. 조회 권한은 요청자·작업에 묶고 파일 경로를 노출하지 않는다.
전달 중 파일은 회원 작업의 임시 자원으로 관리하고 완료·취소·만료 뒤 청소한다. 영구적인 허브 회원 저장소는 이번 단계에서 추가하지 않는다.
브라우저는 받은 바이트를 IndexedDB에 보관하고 내려받기를 제공한다. 폰·네이티브·다른 IndieBiz OS는 향후 같은 전달 계약의 다른 어댑터가 된다.

완료: 허브에서 실제 생성한 파일이 회원 브라우저에 도착하고 지문이 일치한다. 주인의 outputs·공유창고·기억은 바뀌지 않는다.
전송 실패/재시도·중복 요청·회원 B의 A 산출물 조회·취소 후 늦은 회신을 검사한다.

### 3단계 — 정기보고로 처음부터 끝까지 검증

대표 보고서 하나(우선 AI 동향)를 골라 **요청 → 실제 검색 → 근거 확인 → 작성 → 회원 전달**을 완성한다.
주인용 스케줄·시스템 AI 위임을 실행하지 않는다. 재사용할 조사·작성 절차는 소유자 경로와 개인 선호를 제거한 공통 처리로 분리한다.
보고서 종류마다 다른 회원용 미니 앱을 늘리지 않고, 같은 공개 동작과 회원 전용 에이전트 요청을 사용한다.

현재 제공 자료 기반 작성은 별도 기능으로 표시하며 자동 조사와 혼동하지 않는다. 자동 조사 경로가 검증되면 정식 작성 동작으로 교체한다.
도구 부족을 이유로 요청을 임의의 양식 생성으로 축소한 뒤 완료 처리하지 않는다.

완료: 실제 모델과 실제 검색을 사용해 채팅·앱 버튼 양쪽에서 보고서를 받고, 같은 요청자·정책·산출물 전달 절차를 사용함을 확인한다.
주인 PC의 보고서·스케줄·기억에 회원 내용이 남지 않고, 회원 기기에만 최종 보고서가 보존된다.
실제 파일 변환 1종과 기기 재생/위치 1종도 검증해 보고서 전용 구조로 굳어지지 않게 한다.

### 4단계 — 웹앱 표면 완성 및 앱 순차 전환

자율주행은 전용 에이전트 채팅, 앱은 공개 동작을 부르는 화면으로 정리한다. 주인 설정·조종실·시스템 AI 선택기는 없다.
같은 작업의 질문·진행·중단·완료·파일 받기가 두 표면에서 일관되게 보이도록 한다. 내 파일은 보조 도구로 둔다.
초대는 기존 사람 선택 또는 이름 입력 → 초대 발급 → 주소·키 전달로 끝내고 신규 등록·접속 승인 처리를 한 동작에 묶는다.

앱별로 요청 동작, 허브/기기 작업, 사용 자원, 결과 수신 위치, 관리 전용 부분, 전환 상태를 검사한다.
실행 경로가 검증된 앱을 순차 연결한다. 회원 카탈로그에서 숨겼다는 것만으로 전환 완료라고 표시하지 않는다.

완료: 설치 없는 PC·폰 브라우저에서 초대·채팅·앱·파일 받기가 동작하고, 기술 내부 용어나 반복 승인 절차가 일상 흐름에 노출되지 않는다.
OS가 요구하는 위치·파일 선택 권한은 해당 기기의 실제 동작 시점에 따른다.

### 5단계 — 다른 IndieBiz OS 연결을 위한 계약 검증

동일 요청 계약을 사용하는 작은 시험 클라이언트로 텍스트 요청·추가 답변·파일 수신·취소를 시험한다.
새 실행 엔진이나 상대 IBL 사전 공유 없이 같은 담당 에이전트로 처리되는지를 확인한다.
별도 노드는 자기 신원으로 요청한다. 그 뒤의 사람 신원을 대신 주장하려면 추후 명시적 위임 인증이 필요하다.
원격 노드가 넘긴 도구 실행 코드를 신뢰하지 않고 수신 노드가 자기 정책·사전으로 요청을 해석한다.

실제 연동은 이후 `/nodes/ask`의 인증·명함·단발 응답과 새 대화 계약 사이에 버전 협상/호환 어댑터를 붙인다.
기존 주인 장치 간 경로는 검증 전 교체하지 않는다. 허가된 노드라는 이유만으로 owner 권한을 주지 않는다.
완료: 브라우저 특유의 sessionStorage·IndexedDB·limb 연결 없이는 아무 요청도 못 하는 공통 계약이 아님을 시험 클라이언트로 증명한다.

## 7. 변경 위치의 예상 범위

| 위치 | 예상 변경 |
|---|---|
| surface/api_member.py | 기존 HTTP·스트림을 공통 요청/이벤트에 연결하는 어댑터 |
| cognition/member_runner.py, member_session.py | 담당 역할·세션·질문/재개·작업 수명 정리. 큰 새 러너 대신 기존 코드 활용 |
| base 또는 cognition의 작은 공통 모듈 | 필요 시 요청/결과 타입 및 조정 코드 분리. 층 규칙 준수, 전면 이동 없음 |
| ibl/member_profile.py, member_bridge.py, member_files.py | 외부 도구 정책·클라이언트 효과·산출물 전달 공통 지점 |
| 필요한 도구 패키지 | 우선 검색·보고서·문서 변환의 요청 문맥 지원. 관련 구현만 수정 |
| surface/member_* 및 static/member_browser_* | 채팅·앱·파일 수신·질문/진행 표시 |

전역 principal·IBL 엔진의 현재 관문은 유지한다. 변경이 필요하면 구체적 외부 요청 회귀 사례와 함께 최소 지점만 수정한다.

## 8. 배포·검증 방식

한 번에 전체 교체하지 않는다. 1~3단계를 첫 구현 묶음으로 삼고 대표 작업의 실동작을 먼저 검증한 뒤 앱 범위를 넓힌다.
기존 `/m/*` 경로·회원 키·브라우저 저장 데이터를 유지한다. 프로토콜 필드에는 버전을 두고 기존 작업 기록을 지우지 않는다.
기존 회원 요청을 새 경로에 연결한 뒤 이전 중복 분기를 제거한다. 주인용 기능과 `/nodes/ask`는 별도 회귀 범위로 검사한다.

각 단계에 회원 A/B 동시 실행, 질문 후 재개, 취소·연결 단절·중복 요청, 기기 미지원, 산출물 저장 실패를 포함한다.
모의 모델·브라우저 시험과 실제 검색/모델·외부 HTTPS·PC/폰 실기기 시험을 구분해 기록한다.
회원 회귀·관련 주인 회귀, frontend TypeScript, backend 층/파일 크기, IBL·몸/회원 셸 파생물 검사를 수행한다.

**첫 출시 완료 기준은 ‘화면이 열림’이 아니라 ‘외부인이 실제 일을 요청하고 자기 기기에서 결과를 받음’이다.**
