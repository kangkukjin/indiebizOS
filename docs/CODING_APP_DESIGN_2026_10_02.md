# 코딩 앱 설계

작성일: 2026-10-02  
상태: 첫 버전의 **일반 저장소 흐름은 구현·인수 완료**(2026-10-02), **자기수리 연동은 미구현**. 아래 "구현 상태" 참조.  
대상: 코딩 앱을 구현하고 검토할 개발자와 AI 에이전트.

indiebizOS 안에 저장소와 개발 과제를 중심으로 하는 코딩 작업 공간을 만든다. 사용자는 앱에서 AI에게 지시하고, 변경과 검증 결과를 검토하고, 저장소에 반영한다. 실행자는 교체 가능하며 코딩 중 IBL 사용을 강제하지 않는다. 어떤 실행자를 쓰든 작업 맥락·이력·검토 대상은 앱에 남는다.

첫 버전의 완료 기준은 **저장소 열기 → 과제 시작 → 코드 수정 → 실행과 테스트 → diff 검토 → 정본 반영과 커밋**을 앱 안에서 끝내는 것이다. 일반 저장소의 개발 흐름과 indiebizOS 자기수리의 적용 경로를 구분한다.

## 합의한 원칙과 이 문서의 결정

사용자와 합의한 원칙은 다음과 같다.

- 강의 앱처럼 코딩에 필요한 대상·대화·결과를 전용 앱에 모은다.
- 특정 모델이나 Claude Code·Codex CLI에 실행자를 고정하지 않는다.
- 코딩할 때 IBL을 고집하지 않는다. 적합한 네이티브 도구·셸·직접 도구 호출을 사용할 수 있다.
- 셸로 즉석에서 잘 처리하는 일을 관용구로 포장하지 않는다. 유용하고, 매번 정확하게 구성하기 번거로운 복잡한 절차만 축적한다.

이 문서는 이를 구현하기 위한 기본안으로 **diff 중심 화면, 실행 프로필 분리, 과제별 작업 공간, 명시적인 변경 반영 서비스**를 선택한다. worktree 운영 방식과 첫 버전 세부 범위는 설계 제안이며, 이 문서를 쓰는 것으로 기존 저장소 규약이나 실행 권한을 변경하지 않는다.

목적·판단 기준은 [IBL 진화 목적과 개선 판단](IBL_EVOLUTION_PURPOSE.md)을 따른다. 새 어휘 수나 자동화 단계 수 대신 작업 품질·완료 시간·전체 토큰과 사용자의 검토 부담을 본다.

## indiebizOS 안에 두는 이유

코딩 앱은 사용자의 다른 업무에서 얻은 맥락과 개발 작업을 연결한다. 저장소별 기억으로 지난 탐색을 재사용하고, 과제 원장으로 결정과 남은 일을 이어가며, 실행자를 바꾸어도 같은 diff와 검증 기록을 유지한다. 기존 기어와 모델 설정은 실행자 선택의 출발점으로 사용하되, 현재 과제에서 실제 사용할 실행자·모델을 확인하고 고정할 수 있게 한다.

포식 기억은 저장소 탐색을 돕는 단서다. 저장소의 AGENTS.md·CLAUDE.md 같은 현재 규약이나 실제 파일 상태를 대체하지 않는다. 기억에 출처와 확인 시점을 붙이고 변경된 사실은 다시 확인한다. 소스 전체를 상시 프롬프트나 장기 기억에 복사하지 않는다.

폰에서 같은 diff를 보고 반영을 승인하는 흐름은 후속 확장이다. 데스크톱과 동일한 사용자 신원·과제·변경 지문을 사용하며, 별도의 원격 반영 경로를 만들지 않는다.

## 사용자 흐름과 화면

1. **저장소를 연다.** 기존 로컬 Git 저장소를 선택한다. 정본 경로·현재 기준 커밋·기존 변경을 확인한다. 첫 버전은 이미 존재하는 Git 저장소를 대상으로 한다.
2. **과제를 시작한다.** 목표와 반영 대상을 정하고 작업 공간을 준비한다. 실행자와 모델을 고른다. 일상적인 파일 수정과 테스트는 이 작업 권한 안에서 진행한다.
3. **AI와 작업한다.** 선택한 파일·줄·diff·실패 출력을 지시에 첨부한다. AI는 필요한 도구로 조사·편집·테스트하며 진행과 출력을 보여준다.
4. **변경을 검토한다.** 파일별 diff와 검증 결과를 본다. 변경에 의견을 붙여 추가 수정을 지시하거나 간단히 직접 편집한다.
5. **반영한다.** 검토한 변경 묶음과 대상 저장소 상태를 확인해 반영·커밋한다. 충돌이나 자기수리 재기동이 필요하면 그 상태가 계속 표시된다.
6. **이어간다.** 앱을 다시 열거나 실행자를 바꿔도 과제·작업 파일·검증 결과를 복원한다.

화면 우선순위는 **diff 검토 → AI 대화 → 실행·테스트 출력 → 파일 탐색 → 직접 편집**이다. 중앙은 diff를 기본으로 하고 원문 보기로 전환한다. 왼쪽에는 과제·변경 파일·파일 탐색을, 오른쪽에는 대화를, 하단에는 실행별 출력을 둔다. 작은 창에서는 패널을 탭으로 전환한다.

첫 버전의 직접 편집은 텍스트 수정으로 충분하다. 저장할 때 열었던 파일 지문과 현재 지문을 비교하여 외부 수정을 덮어쓰지 않는다. 실행 중인 AI와의 동시 저장도 같은 규칙으로 처리한다. 본격적인 코드 편집기·대화형 터미널·웹 미리보기는 후속 범위다.

선택 맥락은 전송 시점에 `저장소/과제/파일/줄 범위/내용 지문/선택 내용 또는 결과 참조`로 고정한다. 화면 선택을 바꾸었다고 이미 실행 중인 요청의 대상을 바꾸지 않는다. 대화에는 무엇이 첨부됐는지 보여주고, 큰 파일이나 로그는 해당 부분과 원문 참조만 전달한다.

## 실행자와 코딩 프로필

### 모델과 실행자를 구분한다

모델은 추론을 제공하고, 실행자는 도구 호출·작업 루프·중단·상태 보고를 포함한다. 다음 두 경로를 공통 계약으로 연결한다.

| 경로 | 코딩 도구와 작업 루프 | 연결 방식 |
| --- | --- | --- |
| 네이티브 도구를 가진 CLI 또는 외부 에이전트 | 실행자가 가진 검색·편집·셸 도구 사용 | 기존 CLI 수명 관리 위에 어댑터 연결 |
| 일반 API 모델 | 하네스가 도구 호출 루프와 검색·편집·명령 실행 도구 제공 | 기존 프로바이더와 공통 파일·프로세스 구현을 직접 연결 |

API 모델에 제공하는 도구는 코딩 앱의 도구 계약이다. 이를 위해 새 IBL 어휘를 만들지 않는다. 기존 파일·프로세스 구현에서 재사용할 부분을 분리하되 IBL 실행기·통화 변환을 반드시 통과시키지 않는다. 모델이 도구 호출을 지원하지 않는 경우 계획·리뷰 등 지원 가능한 역할을 표시하고, 자동 편집 실행자로 취급하지 않는다.

### 실행자 연결 계약

실행자 어댑터는 다음 정보를 주고받는다. 이름과 전송 형식은 구현 때 기존 공통 인터페이스에 맞춘다.

- **능력 조회:** 스트리밍, 도구 실행, 네이티브 재개, 취소, 진행 중 지시, 사용량 관측, 작업 경로 제한의 지원 여부와 제한.
- **시작:** 과제·실행 ID, 작업 경로, 목표와 선택 맥락, 규약, 권한과 예산, 모델 설정, 이전 작업의 인계 참조.
- **진행:** 텍스트, 실행 시작·종료, 출력 참조, 입력 필요, 사용량, 세션 참조, 오류와 종료 사유.
- **제어:** 지시 추가, 취소, 재개. 지원하지 않는 동작은 미지원으로 반환한다. 지시 추가가 불가능하면 다음 실행 요청으로 대기시킨다.

앱의 공통 사건에는 `task_id/run_id/sequence/type/time`을 둔다. 제공자 원본 사건은 별도 참조로 보존하며, 관측할 수 없는 도구 호출·사용량·검증 결과를 추정해서 채우지 않는다. 파일 변경의 최종 정본은 Git과 실제 파일 상태다.

일반 앱 연결에는 기존 프로필을 유지하고, 코딩 앱은 명시적인 `coding` 실행 프로필을 사용한다. 이 프로필은 네이티브 파일·검색·셸 도구와 직접 도구 호출을 허용하고 IBL 사용 강제 문구 및 중복 도구 차단만 제거한다. 신원 확인·사용자 권한·예산·취소·작업 경로 제한까지 함께 끄지 않는다. 일반 세션의 정책을 전역으로 변경하지 않는다.

프로바이더 캐시와 세션 키에는 실행 프로필·과제·작업 경로·권한 지문을 포함한다. 일반 IBL 세션, 코딩 세션, 의식·평가 세션이 정책이나 이력을 공유하지 않게 한다. 저장소 규약을 네이티브 실행자가 자동으로 읽는 경우 중복 주입을 피하고, 앱이 보충한 규약과 출처를 기록한다.

### 모델 교체와 실행 수명

모델 교체는 한 실행이 끝나거나 중단된 경계에서 한다. 같은 과제의 작업 파일·목표·결정·남은 일·검증 참조를 새 실행자에게 전달한다. 서로 다른 실행자의 내부 세션이나 압축 맥락이 그대로 호환된다고 가정하지 않는다. 네이티브 재개 가능 여부와 앱의 과제 재개 가능 여부를 구분한다.

첫 버전은 작업 공간 하나에 활성 실행자 하나를 둔다. 연결이 끊겨도 같은 실행 ID의 사건을 다시 구독하며 명령을 재전송하지 않는다. 중단은 모델 스트림뿐 아니라 그 실행이 소유한 자식 프로세스까지 포함한다. 중단 확인 전에는 재실행하거나 작업 공간을 정리하지 않는다. 실행자 종료 뒤 남은 명령이 있으면 별도 실행 상태로 표시한다.

일반 코딩 턴마다 의식·평가·증류의 전체 파이프라인을 강제로 추가하지 않는다. 기존 실행·과제·계측의 공통 책임을 재사용하고, 자동 감독이 필요한 작업은 기존 설정과 명시한 완료 기준을 따른다. 자기수리의 검증·적용 계약은 별도로 유지한다.

## 작업 공간과 정본 반영

### 과제별 격리

일반 Git 저장소의 기본안은 **과제별 detached worktree**다. 앱은 저장소의 공통 Git 경로로 동일 저장소를 식별하고, 작업 공간 경로와 정본 경로를 별도로 보관한다. 작업 브랜치는 필수가 아니며 첫 버전은 패치 반영과 정본 커밋으로 흐름을 닫는다.

worktree는 작업 파일과 인덱스를 분리하지만 refs·설정 등 일부 Git 상태를 공유한다. 프로세스 권한·포트·DB·환경변수·외부 서비스도 자동 격리하지 않는다. 테스트용 상태는 과제별 경로를 사용하고, 라이브 DB·토큰·환경 파일을 자동 복사하거나 연결하지 않는다. 필요한 의존성과 실행 설정은 저장소 설정에 명시한다.

시작 기준은 정본 HEAD다. 기존 미커밋 변경은 기본적으로 과제에 가져오지 않고 화면에 표시한다. 그 변경을 이어서 작업해야 한다면 대상 파일을 명시적으로 가져와 시작 스냅샷을 만든다. 이때 기존 변경을 과제가 만든 변경으로 계산하지 않으며, 미추적 파일과 가져오지 않은 의존성도 표시한다. 첫 버전에서 이 가져오기 경로를 지원하지 못하면 깨끗한 HEAD 시작만 제공하고 제한을 명시한다.

**이번 작업의 변경은 worktree의 HEAD 대비 diff만으로 판정하지 않는다.** 시작 스냅샷과 현재 내용의 차이를 사용한다. 실행자가 중간 커밋을 만들어도 시작 기준은 유지한다. 삭제·추가·이름 변경·파일 모드·바이너리와 선택한 미추적 파일을 검토 대상에 포함하고, ignored 파일은 임의로 커밋하지 않는다.

저장소의 직접 main 작업 규약은 이 설계보다 우선한다. indiebizOS의 현재 규약을 이 문서로 해제하지 않는다. indiebizOS 자기수리 격리는 기존 REPAIR 스테이징 정책으로 연결하며, 새 범용 worktree 정책을 자기수리에 적용하려면 해당 규약과 구현 계약을 함께 정리해야 한다. 정본에 반영되지 않은 작업을 완료로 보고하지 않는다.

### 권한과 경로 경계

작업 디렉터리 지정은 쓰기 제한이 아니다. 네이티브 셸도 사용할 수 있으므로 프롬프트만으로 정본 보호를 보장하지 않는다.

API 모델의 파일 도구는 실제 경로와 심볼릭 링크를 확인하고, 셸은 실행자별 샌드박스·쓰기 루트 설정을 사용한다. 정본 적용과 공유 Git 상태의 변경은 별도 반영 서비스가 맡는다. 일반 외부 저장소에서 경로 제한을 보장하지 못하는 실행자는 제한 상태를 드러내며, 완전한 격리로 표시하지 않는다. **라이브 indiebizOS 자기수리에서는 정본 직접 쓰기를 제한할 수 있는 실행 경로만 사용한다.** 지원되지 않으면 그 실행자는 검토 역할로 두거나 제한 가능한 실행 경로로 전환한다.

### 검토와 반영의 계약

검토 대상은 변경 파일 목록·내용 지문·시작 기준·검증 참조를 담은 고정된 변경 묶음이다. 승인 뒤 AI나 사람이 파일을 수정하면 해당 승인은 낡은 것으로 처리한다. 첫 버전의 반영 단위는 변경 묶음 전체이며, 파일·줄 단위 선택 반영은 후속 범위다.

일반 저장소의 반영 서비스는 다음 순서로 실행한다.

1. 실행자와 소유 프로세스가 멈췄는지 확인하고 검토 묶음을 고정한다.
2. 저장소별 반영 잠금을 얻고 정본 HEAD·인덱스·영향 파일 상태를 다시 읽는다. 외부 도구는 앱의 잠금을 따르지 않을 수 있으므로 쓰기·커밋 직전에도 기대 상태를 대조한다.
3. 기준이 바뀌었다면 최신 상태에서 반영 후보를 다시 만들고 diff·필요한 검증을 갱신한다. 충돌은 별도 상태로 남겨 해결하며 남의 변경을 덮어쓰지 않는다. 검토 대상이 달라졌으면 기존 승인을 재사용하지 않는다.
4. 승인된 파일만 반영하고 경로를 한정해 커밋한다. 기존 staged·unstaged 변경을 보존한다. 같은 파일에 겹치는 기존 변경은 자동 합치지 않고 재검토한다.
5. 정본의 실제 커밋·파일 상태를 확인하고 작업 기록에 연결한다. 반영 뒤 커밋 실패는 부분 완료로 남기며, 파일 반영을 다시 수행하지 않고 커밋 단계부터 복구한다.

반영 요청은 고유 ID로 중복 실행을 막는다. Git 전체를 임의의 외부 편집과 원자적으로 묶을 수 있다고 주장하지 않는다. 감지된 동시 변경에서는 멈추고 최신 상태를 보여준다. push·배포는 첫 버전의 자동 완료 조건에 포함하지 않는다.

완료 후에도 작업 공간은 복구 가능한 상태로 보존한다. 진행 중인 실행이나 미반영 변경을 가진 worktree를 자동 삭제하지 않는다. 종료·정리 정책은 과제 기록과 산출물 보존을 확인한 뒤 적용한다.

## indiebizOS 자기수리와의 연결

현재 REPAIR 격리는 IBL 쓰기 관문을 통과하는 경로를 중심으로 적용되며, 네이티브 셸 전체를 가로채는 보편 관문이 아니다. 자세한 한계는 [자기수정 설계](SELF_MODIFICATION_SAFETY_DESIGN.md)와 수리 스테이징의 설명을 따른다. 네이티브 도구를 허용하는 코딩 앱에서는 이 차이가 특히 중요하다.

자기 저장소에 대한 쓰기·검증은 허용된 수리 작업 공간에서 수행한다. 검토가 끝난 변경은 기존 REPAIR 권한과 RED 검증·적용 서비스에 넘긴다. 코딩 앱이 별도의 라이브 복사·재기동·롤백 구현을 만들거나 일반 저장소 반영 서비스를 통해 RED를 우회하지 않는다. 연결에 필요한 공통 서비스를 기존 구현에서 추출할 수 있지만, 새 IBL 액션은 필요하지 않다.

반영부터 재기동 뒤 확인까지는 백엔드 워커의 죽음을 넘는 기존 제어자가 소유한다. 앱은 적용 예약을 완료로 표시하지 않고 **반영 대기 → 적용 → 재기동 → 기능 검증 → 완료 또는 복구 필요**로 보여준다. 현재 `PENDING_APPLY`와 평가 재개 `PENDING_REVIEW`의 의미를 유지하고, 원래 과제의 목표·기준·검증 참조를 [수리 인계](../backend/datastore/repair_continuation.py)에 연결한다.

Git 커밋·적용·실행 중 코드의 활성화는 각각 기록한다. 커밋만 있거나 프로세스가 살아 있다는 이유로 사용자 기능까지 완료했다고 판정하지 않는다. 롤백·커밋 실패·검증 실패도 각각 실제 상태로 남긴다. 재기동 절차의 정본은 [재기동 제어 설계](RESTART_COORDINATION_DESIGN_2026_09_11.md)다.

## 검증 출력과 작업 기억

첫 버전의 테스트는 실행자가 자기 셸이나 제공된 명령 도구로 실행한다. 앱은 명령·작업 경로·시작과 종료·종료 코드·출력 참조·검증 시점의 파일 지문을 수집한다. 실패한 출력의 특정 부분을 선택해 다음 지시에 첨부할 수 있다. 이 출력 뷰는 사용자가 직접 입력하는 터미널과 구분한다.

검증 상태는 통과·실패·미실행·중단·관측 불가로 구분한다. 실행자의 설명만 있고 종료 결과가 없으면 검증 통과로 올리지 않는다. 검증 뒤 파일이 바뀌면 이전 결과를 보존하되 현재 변경의 검증으로 표시하지 않는다. 검사할 범위는 저장소 규약과 변경 영향에 따라 정하고 매 편집마다 전체 테스트를 강제하지 않는다.

코딩 앱의 기록은 다음 역할로 나눈다.

- **앱 작업 상태:** 저장소·작업 공간·기준·현재 검토 묶음·반영 작업·실행자 세션 참조.
- **과제 원장:** 사용자 목표·결정·남은 일·완료 조건. 앱 상태에서 기존 과제 ID를 참조한다.
- **에피소드와 실행 기록:** 실제 실행·시간·사용량·오류·검증 증거. 원본 로그는 참조로 보관한다.
- **저장소 기억:** 반복해서 유효한 구조·개발 관례·주의점. 최신 파일과 규약으로 검증하며 필요할 때만 가져온다.

IBL 호출이 없어도 코딩 실행과 실제 변경을 기록한다. 네이티브 도구로 수행한 일을 가상의 IBL 호출로 바꾸거나 자동 관용구로 등록하지 않는다. 여러 계층에서 같은 모델 사용량을 중복 합산하지 않고 미측정은 미측정으로 남긴다. 로그의 자격 증명 등 민감값은 기존 마스킹 정책을 따르고 장기 기억에 복제하지 않는다.

## IBL과 코딩 관용구의 자리

IBL은 코딩 앱의 필수 실행 언어가 아니다. 필요한 다른 업무 도구나 검증된 복합 절차를 부를 때 선택적으로 연결한다. 앱의 과제·기억 연동도 기존 서비스 API를 사용할 수 있으며, 세션 바깥의 모든 처리까지 IBL로 강제하지 않는다.

셸 명령 몇 개, 단순 파일 탐색, 보통의 테스트 실행, Git 조회를 관용구로 추가하지 않는다. 이미 있는 CLI나 스크립트가 잘 해결하면 그대로 사용한다. 첫 버전에는 코딩 관용구 묶음을 선제적으로 만들지 않는다.

관용구 후보는 실제 작업에서 반복된 절차 중 다음 조건을 충족하는 것만 추출한다.

1. 사용자에게 유용하고 여러 과제에서 다시 쓸 이유가 있다.
2. 상태 관리·실패 분기·격리·증거 수집·재개를 매번 정확하게 구성하기 번거롭다.
3. 기존 CLI·스크립트보다 IBL 조합으로 보관하고 호출할 실익이 있다.
4. 입력·결과·부작용·실패·재개 조건이 명확하고 다른 입력에서도 검증됐다.

복잡한 회귀 원인 추적, 동일 조건의 반복 성능 비교, 여러 단계의 중단·재개는 후보가 될 수 있다. `git bisect` 같은 기존 도구가 충분하면 그것으로 끝낸다. 예시를 개발 필수 목록으로 삼지 않는다.

관용구가 생기더라도 버튼이나 일반 도구 인터페이스로 호출할 수 있게 하여 실행자에게 IBL 문법 학습을 요구하지 않는다. 필요한 후보만 발견·조회하고 전체 목록을 매 코딩 턴에 주입하지 않는다. 효과는 즉석 실행과 같은 품질 조건에서 완료 시간·전체 토큰·복구 부담으로 확인한다.

## 구현 책임과 내부 인터페이스

런처의 독립 코딩 창과 HTTP API를 표면으로 둔다. 아래 이름은 제안이며 실제 파일을 추가할 때 층 규칙·기존 소유자를 다시 확인한다.

| 위치 | 책임 |
| --- | --- |
| `frontend/src/components/CodingWorkspace.tsx`와 하위 컴포넌트 | 과제 선택·diff·대화·출력·간단 편집 |
| `backend/surface/api_coding.py` | 인증된 작업 요청과 사건 구독 |
| `backend/services/coding_workspace.py` | 저장소 식별·작업 공간·변경 묶음·일반 저장소 반영 |
| `backend/services/coding_runs.py` | 실행자 선택·실행 수명·취소·공통 사건 |
| `backend/providers/` | 실행 프로필과 실행자별 연결, 기존 호출 기반 재사용 |
| `backend/datastore/` | 코딩 작업의 최소 영속 상태와 기존 과제·실행 기록 참조 |

API는 저장소 열기, 과제 생성·조회, 실행 시작·사건 구독·중단, 파일 조회·조건부 저장, 변경 묶음 조회, 검토 완료·반영·상태 조회로 구성한다. 브라우저가 임의의 서버 경로를 지정해 작업하도록 하지 않고, 등록된 저장소와 과제 ID로 경로를 해소한다. 입력 필요·권한 요청은 기존 사용자 입력 경로에 연결한다.

영속 상태의 최소 식별자는 `repository_id, task_id, workspace_id, run_id, review_id, apply_id`다. 실행 상태와 반영 상태를 따로 둔다. 실행 종료 후에도 변경은 검토 대기일 수 있으며, 자기수리는 반영 예약 뒤에도 아직 완료가 아니다. 사건 구독은 마지막 sequence 이후부터 이어받고 같은 사건을 중복 표시하지 않는다.

기존 CLI 수명 관리나 과제 원장을 코딩 앱에 복사하지 않는다. 교체가 필요한 IBL 강제 정책은 실행 프로필의 공통 선택점으로 모으고, 일반 경로는 기존 기본값을 유지한다. 새 backend 모듈은 `scripts/check_backend_layers.py`에 배정하며 파일당 1500줄 제한을 따른다.

| 정본 반영·경로 한정 커밋·충돌과 부분 완료 표시 | 개발 서버 지속 관리·대화형 터미널·웹 미리보기 |
| 기존 REPAIR 경로를 통한 indiebizOS 자기수리 연동 | 폰에서 diff 검토와 승인 |
| 과제 이력·최소 기억 연결·모델 교체 인계 | 코딩 관용구의 필요 기반 축적 |

첫 버전에서 두 실행 경로를 실제로 통과시켜 특정 CLI에 결박되지 않았음을 확인한다. 모든 모델 지원을 한꺼번에 구현하지 않으며, 지원 모델의 능력과 제한을 화면에 표시한다. 자기수리 연동이 끝나기 전에는 외부 시험 저장소로 개발 흐름을 검증하고, indiebizOS 자체의 반영 기능을 완성했다고 표시하지 않는다.

## 구현 순서와 인수 조건

### 작업 공간과 반영 계약

먼저 임시 Git 저장소에서 기준 기록·과제 worktree·변경 수집·반영·커밋을 구현한다. 기존 dirty 상태, 미추적 파일, 실행자 중간 커밋, 정본의 동시 변경, 동일 파일 충돌, 커밋 실패, 반영 재시도를 검증한다. 남의 변경이 보존되고 이번 과제의 변경만 반영되어야 한다.

### 실행자와 사건 연결

코딩 프로필과 어댑터를 구현하여 네이티브 실행자 및 일반 API 모델로 같은 작은 수정 과제를 수행한다. 일반 IBL 경로의 정책이 유지되고, 코딩 세션이 섞이지 않으며, 취소·연결 단절·로그 재구독·모델 교체 뒤에도 중복 명령 실행이 없어야 한다. 경로 제한은 실제 실행자로 확인한다.

### 검토 화면과 전체 흐름

저장소 열기부터 diff·실행 출력·간단 편집·커밋까지 연결한다. 오래된 선택 내용, 직접 편집과 AI 편집의 경합, 검토 뒤 파일 변경, 검증 뒤 추가 수정이 화면에 정확히 드러나야 한다. 큰 diff와 바이너리는 생략 사실과 원문 접근을 제공한다. 프런트엔드는 `npx tsc -p tsconfig.app.json`과 실제 화면 조작으로 확인한다.

### 기억과 자기수리 연결

IBL을 사용하지 않은 실행도 과제와 에피소드에서 회수할 수 있어야 한다. 자기수리는 기존 권한·RED 적용·재기동·수리 인계 시험을 확장해 적용 대기, 성공, 롤백, 취소, 중복 재개를 확인한다. 활성 코드와 사용자 기능 검증까지 끝나야 완료로 표시한다.

첫 버전의 최종 인수는 두 실행 경로로 **저장소 열기 → 수정 → 테스트 → diff 검토 → 정본 반영·커밋**을 실제로 끝내는 것이다. 자기수리 경로는 별도 인수 항목이며 외부 저장소 성공으로 대신하지 않는다. 테스트 범위는 [회귀 규약](REGRESSION_TESTING.md)을 따른다.

효용은 같은 과제를 직접 실행자에게 맡기는 경우와 비교한다. 결과 품질, 사용자의 추가 설명·수동 복구, 실제 완료 시간과 전체 모델 사용량을 기록한다. 모든 계측 도구의 완성을 착수 조건으로 삼지 않으며, 측정하지 않은 편의·성능 향상은 구현 사실과 구별한다.

## 구현 상태 (2026-10-02)

- **구현·인수된 것**: 런처 '코딩' 앱(`#/coding`), 저장소 열기·과제별 worktree·간단 편집·검증 명령·검토 묶음·승인·정본 반영과 경로 한정 커밋, 사건 재구독, 취소. 네이티브 실행자(Codex)와 일반 API 모델(DeepSeek) 두 경로로 수정 → 테스트 → 검토 → 반영·커밋을 실제 수행했고(`backend/test_coding_live.py`, `-m system`), 화면 조작으로도 같은 흐름을 끝까지 확인했다.
- **쓰기 경계**: API 모델의 명령은 앱의 macOS 샌드박스 안에서 돈다(작업 공간·런타임만 쓰기, `.git`·네트워크 차단). 네이티브 실행자는 자기 `workspace-write` 샌드박스 한 겹이 경계다 — macOS 는 샌드박스 안에서 샌드박스를 다시 걸 수 없어 바깥을 씌우면 실행자의 모든 명령이 실패한다. 두 경로 모두 작업 공간 밖·Git 메타 쓰기 거절을 실제 실행자로 확인한다(같은 시험 파일).
- **미구현**: indiebizOS 자기 저장소(자기수리 연동). 기존 REPAIR 권한·RED 적용·재기동·수리 인계에 넘기는 연결이 없으므로, 자기 저장소로는 과제를 만들 수 없게 거절한다(일반 반영 경로로 RED 를 우회하지 않는다). 과제 이력의 장기 기억 연결과 효용 비교 측정도 아직 하지 않았다.
- **다른 몸**: macOS 외에서는 쓰기 경계를 보장할 수 없어 실행을 거절한다(`backend/base/coding_process.py` 가 OS 이음매).
