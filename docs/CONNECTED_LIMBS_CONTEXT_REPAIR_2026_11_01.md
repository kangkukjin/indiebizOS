# connected_limbs 존재 안내와 필요 시 드라이버 조회 수리계획

작성일: 2026-11-01. 상태: 계획, 구현 미적용.

**상시 입력에는 하드웨어를 찾아 사용할 수 있다는 사실과 조회 입구만 둔다.**
장치 목록·상태·환경·드라이버 색인·조작 설명은 하드웨어를 실제로 사용할 때 조회한다.
장치가 늘어도 평소 프롬프트가 그 수에 비례해 커지지 않게 한다.

이 계획은 [하드웨어 드라이버 소유 구조 수리계획](HARDWARE_DRIVER_OWNERSHIP_REPAIR_2026_11_01.md)의
발견 경로를 구체화한다. 그 개편에서 연결 중인 레지스트리와 조회 표면을 재사용한다.
[제어 드라이버 설계](CONTROL_DRIVER_DESIGN_2026_10_20.md)의 실행·검증·복구 책임은 유지하고,
[IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)에 따라 사용 가능한 정보와 전체 비용을 함께 평가한다.

## 1 근거와 범위

오늘 #5665의 새 실행 세션 첫 요청에서 `connected_limbs`는 6,613자였다.
장치 11개 행은 2,237자, Android·PC·TV의 제어 요약은 3,579자,
공통 안내·포장 등은 797자였다. 이는 실제 전달 텍스트의 문자 수이며 토큰 수가 아니다.

행마다 정보를 줄여도 장치 수에 비례하는 상시 비용은 남는다. 따라서 이전 계획의
장치별 최소 행과 공통 드라이버 색인 상시 주입, 3,000~3,500자 목표를 대체한다.
에이전트는 존재 안내를 보고 필요성을 판단하며, 시스템이 매 턴 모든 장치를 미리 소개하지 않는다.

다른 에이전트가 드라이버 개편을 진행 중이다. 위 실측은 개편 전 에피소드 입력이므로,
구현 기준선은 그 변경이 반영된 정본에서 다시 고정한다. 개편의 절감량과 이번 변경의 절감량을 구분한다.
수리 대상은 장치 소개 생산자, 필요 시 대상 발견 조회와 기존 드라이버 조회의 연결이다.
게스트 헬퍼 분할·배포 구현, 상황 관측 전달, CLI 세션 보존, v7, 전체 IBL 목록은 이 수리에서 바꾸지 않는다.

## 2 기본 입력에 남기는 것

`connected_limbs`는 장치 배열 대신 짧은 안내만 제공한다. 원래 허용 범위 안에서 본체/등록 하드웨어의
발견 가능성과 기존 조회 입구를 알린다. 등록 여부를 표시한다면 실제 등록 자료에 근거하고,
등록을 현재 접속이나 동작 가능으로 표현하지 않는다. 장치 이름·개수·종류별 목록도 상시 열거하지 않는다.

구현 후 안내의 의미 예시는 다음과 같다. 실제 호출 인자는 아래 조회 계약 구현 후 확정한다.

> 본체와 등록된 하드웨어는 self:limb로 찾을 수 있다. 이름·ID가 있으면 해당 대상을 조회하고,
> 대상이 정해지지 않았으면 간략 목록을 검색한다. 결과에서 필요한 드라이버 계약과 상태를 읽을 수 있다.

길이는 장치 1개·10개·100개·1,000개에서 동일한 고정 문장 수준을 목표로 한다.
별도 모델 호출이나 매 턴의 네트워크 탐침으로 존재 안내를 만들지 않는다.
하드웨어가 있다는 이유만으로 모델에게 목록 조회를 요구하지도 않는다.

## 3 필요할 때 가져올 정보

| 필요 | 조회할 정보 | 기존 소유자 |
| --- | --- | --- |
| 이름·ID가 이미 정해진 대상 | 해당 장치의 식별·상태·실행 범위·드라이버 참조 | 단일 장치 조회와 드라이버 레지스트리 |
| 장소·용도 등으로 대상 찾기 | 검색 결과의 간략 장치 목록과 다음 페이지 | 기존 장치 등록 자료를 읽는 발견 조회 |
| 선택한 동작 실행 | 인자·조건·호출·검증·복구 계약 | 선택한 드라이버 가이드·함수/액션 describe |
| 현재 환경·권한·개체별 관측 확인 | 관측 시각·출처·적용 범위가 있는 상태 | 기존 장치/관측 조회와 드라이버 실행 부품 |
| 설치·업데이트 | 설치 부품·세대·배포 판본·업데이트 계약 | 개편의 hardware_driver_status와 기존 설치 구현 |

장치 식별자·이름·종류/OS·장소/용도·연결 관측·paused·service_scope는 삭제되는 데이터가 아니다.
상시 입력에서 빠지고 대상 발견/상세 조회에 남는다. 사용자 세션과 machine 서비스, 본체의 `__local__`,
동명이인 장치를 구별한다. 등록 정보만으로 관리자 권한·GUI 접근·현재 연결을 확정하지 않는다.
오프라인 장치도 검색 가능하며 설치 전 대상은 기존 설치 가이드 경로에서 발견할 수 있다.

이미 선택한 계약이나 대상 정보가 현재 문맥에 있으면 활용한다. 매 동작마다 다시 조회하는
강제 절차를 추가하지 않는다. 연결·준비 검사·결과 검증은 계속 드라이버가 수행한다.
기존 `callable_control_briefs()`·`surface_control_guide()`처럼 선택한 부품에 계약을 붙이는 경로도 유지한다.

## 4 조회가 새로운 대량 주입이 되지 않도록 하기

현재 `[self:limb]{op:"list",limb:$device_id}`는 이름/ID로 좁힌 장치 상세 조회다.
`target:$device_id`는 관측 목록 조회이므로 둘을 혼동하지 않는다. `limb` 없는 현재 list는 상세 원장을
반환하며, 이 호출을 존재 안내 뒤에 항상 실행하게 만들면 대량 입력이 조회 결과로 옮겨갈 뿐이다.

대상이 정해지지 않은 경우를 위해 **기존 self:limb list에 간략 검색/페이지 조회를 확장**한다.
다음은 새 구현에서 추가할 계약안이며 현재 지원되는 호출로 안내하지 않는다.

- `view:"index"`: 장치 발견용 간략 행만 반환. 기존 기본 list의 상세 반환 계약은 유지한다.
- `query`: 이름·장소·용도·종류 등 기존 등록 정보를 검색. 빈 검색으로도 목록을 탐색할 수 있다.
- `limit`, `cursor`: 제한된 페이지와 이어보기. 결과 잘림/다음 페이지 유무를 명시한다.
- 간략 행: 식별자·이름·종류·구분에 필요한 사용자 설명의 미리보기. 설명 전문은 해당 장치 상세 조회에 보존한다.

이름/ID를 아는 경우 전체 목록부터 읽지 않고 기존 단일 대상 조회로 연결한다.
간략 조회는 필터·페이지 적용 후 행을 만들고, 모든 기기의 설치 상태·드라이버 전문을 먼저 조립하지 않는다.
파라미터는 원본 어휘 선언과 핸들러에 함께 연결하며, 별도 IBL 낱말·검색 서비스·요약 모델은 만들지 않는다.
기존 허용 범위와 등록 자료의 접근 경계를 유지하고 반환 상세를 늘려 비밀 값을 노출하지 않는다.

사용자 질문을 분류하는 새 강제 라우터는 만들지 않는다. 에이전트가 필요한 기능을 선택하며,
불특정 대상 검색도 가능하므로 질문의 단어에 맞지 않는다는 이유로 장치를 발견 불가능하게 하지 않는다.

## 5 이관과 제거

`_connected_limbs()`에서 장치 행 열거·전체 드라이버 색인·control_brief 첨부·긴 절차 note를 제거한다.
현재 control_brief는 이미 가이드 정본에서 읽고 있으므로 새 파일로 본문을 복사할 필요가 없다.
Android·PC·TV 제어 설명은 기존 드라이버 가이드에, 원격 실행·설치는 진행 중인 개편의 해당 가이드에 남긴다.
드라이버 ID와 가이드 절 연결은 guide_db.json 및 guide_registry에서 읽고 별도 수동 사전을 만들지 않는다.

상세 장치 정보를 항상 만드는 작업도 소개 생성 경로에서 걷어낸다. 사용하지 않는 하드웨어의
설치 상태·관측·가이드를 매 턴 수집한 다음 텍스트만 숨기는 구현으로 끝내지 않는다.
소개에서 뺀 장치 목록이나 조작 설명을 다른 상시 문맥 블록으로 옮기지 않는다.

## 6 구현 순서와 변경 위치

| 단계 | 변경 | 완료 조건 |
| --- | --- | --- |
| 1 발견 조회 연결 | 드라이버 개편이 반영된 HEAD에서 기준선 고정. guest-helper 핸들러와 ibl_actions.yaml의 기존 list에 간략 검색·페이지 계약 연결 | 이름/ID 직접 조회 및 장소/용도 검색이 전체 상세 원장을 읽지 않고 대상을 찾음 |
| 2 상시 소개 교체 | associative_recall.py의 _connected_limbs를 짧은 존재 안내와 조회 입구로 교체 | 장치 수·가이드 수가 늘어도 기본 입력의 길이가 늘지 않음 |
| 3 드라이버 소비자 확인 | 단일 대상 조회→드라이버 참조→가이드/describe 연결, 기존 판본 처리 유지 | 필요한 계약·관측을 회수하며 이미 있는 계약의 재조회가 강제되지 않음 |
| 4 교재·검사·측정 | 기존 드라이버 설계와 소유 계획의 소개 설명 갱신, 어휘 파생 빌드와 회귀, 동일 입력 비교 | 정본 선언·조회 결과·실제 모델 입력이 일치 |

드라이버 개편 중인 파일을 별도 사본으로 덮어쓰거나 그 구현을 다시 만들지 않는다.
전환 실패 시 소개/조회 변경만 되돌릴 수 있으며 등록·설치 상태·관측·작업 영수증은 보존한다.

## 7 검증과 완료 조건

기존 test_associative_recall.py, test_guide_registry.py, test_control_driver.py 및
list 조회의 시험을 갱신하고 select_tests.py로 전이 소비자를 확인한다.
장치 행과 요약의 상시 존재를 요구하던 시험은 존재 안내와 필요 시 발견 계약으로 바꾼다.

- 장치 0·1·10·100·1,000개 및 서로 다른 드라이버 수에서 상시 입력 길이가 일정한지 확인한다.
- 하드웨어와 무관한 요청에서는 장치·드라이버 전문 조회가 자동으로 실행되지 않는지 확인한다.
- 이름/ID 직접 조회, 장소/용도 검색, 페이지 탐색, 동명이인, 오프라인·중지·미확인을 확인한다.
- 본체와 원격, 사용자 세션과 machine 서비스, 회원/폐기 장치 경계, 사용자 설명·관측 의미를 보존한다.
- 검색 없는 전체 탐색도 페이지로 가능하며, 미리보기를 전문으로 오인하거나 결과 누락을 숨기지 않는다.
- 간략 조회가 모든 장치의 설치/드라이버 상세 조립을 수행하지 않는지 확인한다.
- 선택한 PC/폰/TV 기능과 원격 설치·전송에서 필요한 계약과 결과 판정이 유지되는지 확인한다.

이전 3,000~3,500자 목표는 폐기한다. 새 목표는 장치 수와 무관한 **수백 자 이내의 짧은 고정 안내**이며,
수치는 실측 전 목표다. 필수 조회 계약을 잘라 맞추지 않고 초기 입력과 실제 추가 조회 비용을 함께 측정한다.

기존 조립 재현 도구에서 비하드웨어 작업, 대상 지정 작업, 대상 탐색 작업, 여러 기기 작업을 나눠 비교한다.
간단한 제어는 초기 입력 절감보다 추가 왕복 비용이 클 수 있으므로 각 작업의 전체 토큰·시간·품질을 기록한다.
같은 목표와 도구 결과의 격리 실행/기록 재생을 사용하며, 끝난 원격 설치·삭제를 측정 목적으로 반복하지 않는다.
캐시·출력·추가 조회·후처리까지 포함하고, 모델 비교가 없는 항목은 문자 절감만 보고한다.

회귀 범위는 REGRESSION_TESTING.md를 따르고 구현 시 어휘 체크리스트·파생 빌드·층 검사·몸 번들을 적용한다.
이 문서 반영은 계획의 완료다. 구현 완료는 고정 크기의 존재 안내에서 필요한 대상과 드라이버를 찾고,
필수 계약·관측을 잃지 않으며 대량 정보가 다른 상시 입력으로 돌아오지 않는 것을 확인한 시점이다.
