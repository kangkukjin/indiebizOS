# connected_limbs 최소 정보와 드라이버 설명 분리 수리계획

작성일: 2026-11-01. 상태: 계획, 구현 미적용.

`connected_limbs`는 사용할 수 있는 대상을 식별하고 적절한 드라이버를 찾는 작은 장치 목록으로 만든다.
동작 인자·호출 예·검증·복구 설명은 드라이버가 소유하고, 선택한 기능을 사용할 때 기존 조회 경로로 제공한다.
에이전트에는 대상과 능력을 판단할 정보를 주며, 장치 목록에 새로운 행동 규칙을 쌓지 않는다.

이 문서는 [하드웨어 드라이버 소유 구조 수리계획](HARDWARE_DRIVER_OWNERSHIP_REPAIR_2026_11_01.md)의
장치 소개 부분을 구체화한다. 그 개편에서 연결 중인 레지스트리와 조회 표면을 재사용한다.
그 문서의 상시 빠른 호출 요약 제공 방침은 **장치 존재만으로는 전문을 붙이지 않고, 선택한 호출에만 제공**하는
방향으로 좁힌다. [제어 드라이버 설계](CONTROL_DRIVER_DESIGN_2026_10_20.md)의 실행·검증·복구 책임은 유지한다.
목적과 평가 기준은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)을 따른다.

## 1 근거와 범위

오늘 #5665의 새 실행 세션 첫 요청에서 `connected_limbs`는 6,613자였다.
장치 11개 행은 2,237자, Android·PC·TV의 `control_brief` 세 블록은 3,579자,
공통 안내·포장 등은 797자였다. 과거 세션의 누적량이나 토큰 수가 아닌 실제 전달 텍스트의 문자 수다.
오늘 #5666·#5667의 입력에도 같은 크기의 장치 소개가 추가됐다.

현재 `_connected_limbs()`는 장치에서 발견한 OS 가이드의 요약을 정본에서 읽어 자동 첨부한다.
같은 조립 안에서 재사용 부품 블록에 실린 요약은 제외하지만, 작업과 무관한 장치의 요약도 발견 대상이다.
따라서 설명을 새로운 파일에 복사하는 수리가 아니라, **장치 발견과 상세 계약 전달의 시점을 분리**하는 수리다.

다른 에이전트가 드라이버 개편을 진행 중이다. 위 실측은 개편 전 에피소드 입력이며,
현재 작업 트리에는 드라이버·가이드·설치 부품·설치 세대 참조가 추가돼 있다. 구현 기준선은 그 변경이
반영된 정본에서 다시 고정한다. 두 변경의 절감량을 합쳐 이 수리 단독 효과로 보고하지 않는다.

수리 대상은 장치 소개 생산자, 드라이버 발견 참조와 그 소비자다. 게스트 헬퍼 문서 분할·배포 구현은
기존 개편이 맡는다. 상황 관측 전달, CLI 세션 보존, v7, 전체 IBL 목록과 시스템 구조 설명은 바꾸지 않는다.

## 2 장치 목록에 남길 정보

| 정보 | 표현과 근거 |
| --- | --- |
| 대상 식별 | `device_id`, 이름. 본체의 `__local__` 식별을 유지하고 같은 이름의 장치를 합치지 않는다. |
| 선택에 필요한 설명 | 장치 종류·OS와 사용자가 적은 장소·용도. 기존 사용자 설명은 임의로 재작성하거나 무음 절단하지 않는다. |
| 현재 사용 가능성 | 연결 관측과 `paused`. 관측 시각은 원천에 있을 때만 함께 제공하고, 없으면 미확인으로 둔다. |
| 실행 범위 | 로컬·원격·네트워크 API 구분과 `service_scope`의 사용자 세션·machine·미확인. 등록 정보만으로 관리자 권한이나 GUI 접근을 추정하지 않는다. |
| 드라이버 참조 | 해당 장치가 사용할 수 있는 드라이버 ID. 여러 조작면은 각각 가리키되 긴 설명은 싣지 않는다. |
| 발견 문제 | 해당 장치에 영향을 주는 매핑 충돌·지원 미확인을 짧게 표시한다. 관련 없는 레지스트리 오류 전문은 제외한다. |

같은 드라이버를 쓰는 장치에는 짧은 참조만 반복한다. 소개 안의 공통 드라이버 색인에는 ID별로
조작면의 짧은 이름과 가이드 파일·입구 절을 한 번 제공한다. 이름·절·매핑은 `guide_db.json`과
`guide_registry`에서 파생하고 별도 수동 사전을 만들지 않는다. 기존 `control_guide` 소비자가 있으면
호환 입력을 유지하며 옮기되, 최종 프롬프트에 같은 매핑을 여러 속성으로 중복 출력하지 않는다.

장치 목록의 짧은 공통 설명은 필드 의미만 설명한다. 사용자 배치 정보는 현재 관측이 아니고,
접속은 동작 가능·관리 권한을 보증하지 않으며, 네트워크 무응답은 전원 꺼짐과 다르다는 의미를 보존한다.
“제어 전 반드시 조회”, “이 순서로 호출” 같은 실행 절차를 장치 목록에 넣지 않는다.

등록된 오프라인 장치, 본체, 기존 허용 범위와 제외 기준을 유지한다. 사용자 질문의 단어만으로
기기를 숨기는 새 필터를 추가하지 않는다. 목록을 줄이는 목적 때문에 대상 발견 능력이 좁아지지 않게 한다.

## 3 상세 정보의 소유 위치

| 현재 장치 소개에 있는 내용 | 앞으로 읽을 위치 |
| --- | --- |
| Android 음량·앱·재생, PC 음량·Chrome, TV 전원·DLNA의 호출 예 | 기존 `android_control.md`, `pc_control.md`, `tv_control.md`의 빠른 호출 및 해당 절 |
| 준비·검증·원 영수증 확인·재시도 조건 | 같은 드라이버 가이드와 기존 실행 부품의 계약. 조건을 삭제하거나 다른 공통 지침으로 복제하지 않음 |
| 원격 셸·전송·장기 작업 | 진행 중인 개편의 `remote_pc_execution.md`와 기존 함수·액션 계약 |
| 설치 부품·설치 세대·배포 판본·업데이트 방법 | 개편의 `remote_pc_installation.md`, `hardware_driver_status` 및 기존 설치 상태 조회 |
| 장치별 관측 본문·환경 상세·host 등 | 기존 장치/관측 조회. 소개에는 선택에 필요한 사실만 남김 |

`control_brief`는 이미 위 가이드에서 읽고 있으므로 새 본문을 만들지 않는다.
`_connected_limbs()`의 전체 발견 가이드 요약 첨부를 제거하고, 여러 단계의 조작 지시가 들어 있는
긴 `note`도 필드 의미 설명으로 교체한다. 옮긴 전문을 다른 상시 입력 블록에 그대로 붙이지 않는다.

설치 세대·부품 상세는 장치 목록에서 빠져도 실제 업데이트의 대상 결속·검증 계약에 그대로 남는다.
기기별 사실을 모든 장치에 적용되는 드라이버 규칙으로 승격하지 않는다.

## 4 필요한 계약을 찾는 경로

1. 에이전트는 짧은 장치 목록으로 대상과 조작면을 고른다.
2. 해당 계약이 현재 문맥에 있으면 활용한다. 없는 내용은 색인이 가리키는 가이드의 해당 절이나
   기존 함수·액션 `describe`로 읽는다. 매 동작마다 가이드를 다시 읽는 절차를 추가하지 않는다.
3. 기존 `callable_control_briefs()`·`surface_control_guide()` 등 선택한 부품에 계약을 붙이는 경로는
   유지한다. 장치가 존재한다는 사실과 호출이 선택됐다는 사실을 구분한다.
4. 대상의 실제 환경·권한·설치 상태가 필요하면 기존 단일 대상 조회를 사용한다.
   현재 `[self:limb]{op:"list",limb:$device_id}`는 장치 상세 조회이고,
   `target:$device_id`는 관측 목록 조회다. 두 계약을 혼동하거나 모든 기기 원장을 기본 조회하지 않는다.

위 순서는 발견 경로의 설명이며 에이전트에 그대로 주입할 강제 절차가 아니다.
새 IBL 어휘·새 검색 서비스·별도 요약 모델을 추가하지 않는다. 오프라인·설치 전 대상도 기존
등록/설치 가이드 경로로 발견한다. 가이드 판본이 바뀌면 기존 지문 처리로 새 계약을 읽을 수 있어야 한다.

## 5 구현 순서와 변경 위치

| 단계 | 변경 | 확인할 결과 |
| --- | --- | --- |
| 1 기준선과 참조 연결 | 다른 드라이버 개편이 반영된 HEAD에서 동일 장치 자료로 조립값 저장. 레지스트리의 드라이버 ID→조작면·가이드 절 연결 확인 | 기존 등록 데이터를 재사용하고 조회할 수 없는 참조가 없음 |
| 2 장치 소개 축소 | `backend/cognition/associative_recall.py`의 `_connected_limbs()`에서 전체 `control_brief` 첨부와 긴 절차 note 제거. 최소 행과 공통 드라이버 색인 출력 | Android·TV가 등록돼 있어도 PC 작업 입력에 그 조작 전문이 자동으로 들어가지 않음 |
| 3 소비자 연결 | `backend/datastore/guide_registry.py` 및 기존 가이드/describe 소비자에서 참조·판본 처리 확인. 필요한 변경만 적용 | 선택한 드라이버의 필요한 계약은 온전히 회수되고 이미 있는 계약의 재조회가 강제되지 않음 |
| 4 교재와 회귀 | `CONTROL_DRIVER_DESIGN_2026_10_20.md`와 하드웨어 소유 계획의 장치 소개 설명을 최종 동작에 맞춤. 관련 시험과 동일 입력 비교 | 운영 설명·등록 데이터·실제 모델 입력이 일치 |

드라이버 개편 중인 파일을 별도 사본으로 덮어쓰거나 그 작업을 다시 구현하지 않는다.
완료 커밋은 이 변경의 경로만 포함한다. 전환 실패 시 소개 조립 방식만 되돌릴 수 있고,
기기 등록·설치 상태·관측·작업 영수증에는 변경이 없다.

## 6 검증과 완료 조건

기존 `test_associative_recall.py`, `test_guide_registry.py`, `test_control_driver.py`와
변경의 전이 소비자를 `select_tests.py`로 확인한다. 장치 소개에 요약이 상시 존재해야 한다는 기존 시험은
새 발견 계약으로 바꾸고, 선택된 호출의 요약을 보존하는 시험은 유지한다.

검증할 성질은 다음과 같다.

- 본체·동명이인·여러 OS·사용자 세션과 machine 서비스·오프라인·일시 중지·미확인 상태를 구분한다.
- 장치 수가 늘어도 동일 드라이버의 상세 설명은 소개에 추가되지 않고 공통 참조만 공유한다.
- 등록·가이드 충돌, 가이드 판본 변경, 관측 시각 없음이 임의의 지원/권한 확정으로 바뀌지 않는다.
- 원래의 허용 범위·회원/폐기 장치 제외·XML 이스케이프와 사용자 설명이 보존된다.
- PC/폰/TV의 선택된 기능, 원격 설치·전송 및 혼합 기기 작업에서 필요한 인자·조건·완료/미완료 의미를 찾는다.

문자 비교의 설계 목표는 오늘 11개 장치 표본에서 6,613자를 대략 3,000~3,500자 수준으로 줄이는 것이다.
이는 실측 전 목표이며 런타임 절단 상한이 아니다. 개편 뒤 증가한 참조와 관측 시각도 포함해 재측정하고,
필수 정보를 빼서 수치를 맞추지 않는다. 개편 반영 전후와 이번 수리 전후를 별도로 기록한다.

기존 조립 재현 도구를 확장해 장치 소개·필요한 가이드 조회·describe 응답을 함께 센다.
간단한 PC/폰 제어에서는 과거에 요약 제공으로 조회를 줄인 효과가 있으므로,
초기 입력만 줄고 추가 조회·라운드가 늘어나는지 별도로 확인한다. 실제 모델 비교는 같은 목표와
도구 결과를 쓰는 격리 실행/기록 재생으로 하고, 이미 끝난 원격 설치·삭제를 측정 목적으로 반복하지 않는다.

결과에는 입력 문자와 모델 토큰을 구분하고 입력·출력·캐시, 추가 조회 수, 전체 완료 시간,
대상 선택과 결과 판정의 품질을 기록한다. 실제 모델 비교를 하지 않은 항목은 문자 절감만 보고한다.
회귀 범위는 `REGRESSION_TESTING.md`를 따르며 backend 구현 변경 시 몸 번들·층·파생물 검사를 적용한다.

이 계획의 완료는 문서 반영이다. 구현 완료는 작은 목록으로 대상과 드라이버를 찾고,
필요한 계약과 관측을 잃지 않으며, 제거한 전문이 다른 상시 입력으로 돌아오지 않는 것을 확인한 시점이다.
