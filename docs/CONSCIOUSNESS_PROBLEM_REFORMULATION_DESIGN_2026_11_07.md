# 의식의 문제 규정과 중간감사 역할 정리

작성: 2026-11-07. **설계 제안이며 아직 구현하지 않았다.**
현행 조사 기준: 정본 `main`의 `7324702d`.
목적 기준: [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md), [비전](../data/system_docs/vision.md).

## 1. 결정 요지

**의식은 사용자의 요구를 실행자가 해결할 수 있는 더 정확한 요청으로 다시 쓴다.
중간감사는 실행에서 얻은 근거로 그 요청이 여전히 적절한지 판단하고 필요하면 고쳐 쓴다.**

이 요청이 기존 `task_framing`이다. 별도의 질문 정제 에이전트·단계·필드는 만들지 않는다.
완료 기준은 이 문제의 해결 여부를 확인하는 표현이고, 연구계획은 이 문제를 푸는 방법이다.
의식의 산출물을 여러 조언의 묶음으로 취급하기보다, **지금 무엇을 해결하라고 맡겼는가**를 중심으로 정렬한다.

사용자가 다른 AI에게 “이 주제를 indiebizOS에 어떻게 심층연구하라고 요청하면 좋을까”라고
물어 얻은 문장을 다시 입력하던 일을 기존 의식 호출이 맡는 셈이다. 연구계획서 작성보다
논리적으로 먼저 하는 판단이며, 모델 호출을 하나 더 앞에 붙이자는 뜻은 아니다.

원래 사용자 발화는 의도·조건·권한의 근거로 보존한다. 실행자의 직접적인 작업 대상은
그 발화를 맥락 속에서 해석한 현재의 `task_framing`이다. 사용자의 목적을 대신 정하는 권한과
그 목적에 맞는 문제를 정교하게 정의하는 책임은 구별한다.

## 2. 현행 구조에서 확인한 것

| 위치 | 현재 동작 | 정리할 부분 |
| --- | --- | --- |
| [의식 프롬프트](../data/common_prompts/consciousness_prompt.md) | 이미 문제·관점·완료 기준의 규정을 임무로 선언한다. `task_framing`은 문제/제약/세상의 방식/탐색/무게·멈춤선/위해/불분명 등의 이름 붙은 줄이다. | 실행 가능한 요청과 방법·주의사항의 설명이 한 필드에 섞여 있다. 다른 AI에게 그대로 맡길 요청을 쓰는 책임으로 모은다. |
| [의식 호출](../backend/cognition/consciousness_agent.py)의 `process` | 초기 규정을 받은 뒤 `research_planning.prepare`에 넘긴다. | 재구성한 문제에서 기준과 계획을 도출하도록 기존 호출의 내용을 바꾼다. |
| [실행 지침 조립](../backend/cognition/prompt_builder.py)의 `compile_user_command` | 사용자 명령 뒤에 “시스템 실행 지침 (의식 보강)”을 붙인다. `task_framing`도 실행 지침이며 출처는 `source=consciousness`다. | 단순 참고 자료만인 것은 아니다. 다만 문제 규정·절차·기준이 모두 보강으로 나열되어 현재 작업 요청의 중심이 덜 분명하다. 출처 표시는 유지하며 역할을 명시한다. |

| [감독 프롬프트](../backend/cognition/supervisor_runtime.py)의 `ROLE_PROMPT`와 [감독자](../backend/cognition/conscious_supervisor.py)의 `review` | 전제를 의심하라고 하지만 결과는 주로 `REWORK/UNKNOWN/CONTINUE`와 교정 지시다. `review`는 교정을 대기열에 넣고 정식 규정은 교체하지 않는다. | 중간감사가 발견한 문제 변경을 자신의 기존 판단 결과로 인계할 수 있어야 한다. |
| [재규정](../backend/cognition/reframe.py), 감독자의 `reframe` | 실행자가 깨진 전제·근거를 보내면 의식이 다시 규정한다. 감독자는 임시 `TurnChannel`에서 받아 `self.framing`을 갱신한다. | 실행자가 발견한 문제를 알리는 통로로 유지한다. 중간감사가 이미 내린 판단을 다시 실행자가 요청하게 만드는 왕복은 없앤다. |
| [파이프라인](../backend/cognition/agent_pipeline.py), [기준·보완 인계](../backend/cognition/supervisor_handoff.py), [최종평가](../backend/cognition/final_evaluator.py) | 파이프라인의 턴 채널과 감독자의 `framing`이 따로 존재한다. 다음 턴 계승은 턴 채널, 감독 평가·보완은 감독자 규정과 고정된 기준 계약을 사용한다. 보완 인계의 `goal`은 원 사용자 메시지다. | 규정을 수정했을 때 모든 소비자가 같은 현재 규정을 보도록 소유와 전달을 통일해야 한다. |

프롬프트에 문제 규정이 없어서 생긴 공백이 아니다. **문제를 규정하는 책임은 이미 선언되어
있지만, 산출물의 중심과 수정 권한·전달 경로가 그 책임에 충분히 맞춰져 있지 않다.**
이것이 이번 설계에서 다루는 구조적 원인이다. 현재 규정 문장의 실제 품질이 얼마나 낮은지,
이 변경으로 연구 품질이 얼마나 높아질지는 별도의 실행 비교가 필요하다.

앞서 조사한 에피소드 5888~5890은 초기 의식을 거치지 않은 EXECUTE 경로였다.
5890의 정상 응답 덮어쓰기는 실패 이력에 따른 후속 호출의 문제로 수리했으며,
그 사례를 의식의 문제 규정 실패나 이 설계의 효과를 입증한 사례로 사용하지 않는다.

## 3. `task_framing`의 뜻을 분명히 한다

`task_framing`은 **실행자에게 그대로 전달할 현재 작업 요청**이다. 사용자의 문장을
예쁘게 요약하거나 더 길게 만드는 것이 아니라, 무엇을 알아내거나 만들어야 하고 그것이
왜 사용자에게 필요한지 분명하게 만든다. 답해야 할 질문, 대상과 범위, 필요한 구분이
실제로 작업을 바꾸는 만큼만 들어간다. 단순 요청은 짧게 유지한다.

문제의 성격에 따라 관점을 선택한다. 원인 조사라면 관측 사실과 원인 가설을 구별하고,
의사결정이라면 무엇을 결정할 수 있어야 하는지 밝히며, 제작이라면 쓰일 맥락과 결과를
정의한다. 이 예시들을 작업 유형별 분기표나 필수 작성 항목으로 구현하지 않는다.
적절한 방법을 떠올리는 사고는 유지하되, 모든 요청에 방법 이름과 탐색 항목을 채우지는 않는다.

기존 필드의 역할은 다음과 같이 모은다.

| 기존 필드 | 맡을 내용 |
| --- | --- |
| `task_framing` | 실행자가 지금 해결할 요청. 중심 질문과 필요한 범위·구분. |
| `assumptions` | 그 요청이 성립하는 데 필요한 미확인 전제. 확정 사실과 섞지 않는다. |
| `achievement_criteria`, `criteria` | 현재 문제를 해결했다는 것을 무엇으로 확인할지. 사용자 명시 조건의 출처를 보존한다. |
| `history_summary` | 이 요청을 이해하는 데 필요한 이전 맥락·결정·관측. 현재 지시를 반복하지 않는다. |
| `capability_focus.hint`, `expert_choice` | 실제로 도움이 되는 방법·의존 관계·분야의 함정. 불필요하면 비운다. |
| 기존 연구계획과 `_research_plan` | 해당 연구의 질문을 어떻게 조사·종합할지와 저장된 계획의 참조. |

`refined_request`, `true_goal`, 별도 목표 원장 같은 병렬 표현을 추가하지 않는다.
필드가 채워졌다는 사실을 좋은 문제 규정의 판정으로 삼지도 않는다.

### 바뀔 수 있는 목표의 범위

사용자의 실제 목적과 명시한 제약을 지키면서 **의식이 도출한 작업 목표 자체는 교체할 수 있다.**
처음 정한 질문을 고정한 채 수단만 바꾸는 것으로 제한하지 않는다. 원문의 전제가 틀리거나
문제의 구분이 부정확하면 “왜 X인가”를 “X가 실제로 있는가, 어떤 조건에서 나타나는가”로
고칠 수 있다. 잘못된 전제를 입증하는 것이 사용자의 목적이라고 취급하지 않는다.

반면 사용자가 요구한 대상·기간·측정량·납품물·권한을 편의상 바꾸고 달성했다고 할 수는 없다.
의식이 임의로 정한 조사량이나 잠정 설명은 수정할 수 있고, 사용자 조건의 미충족은 남은
일이나 한계로 남는다. 기존 `criteria.user_quote`의 출처 구분을 유지한다. 과거 대화의 사용자
결정도 유효한 근거이며, 현재 메시지 안에 직접 인용이 없다고 무시하지 않는다.

매 수정마다 사용자 승인을 받는 단계를 만들지 않는다. 기존 명확화 판단으로 처리할
실제 선택·권한의 공백과, 의식이 책임지고 정교화할 해석을 구별한다. 재규정은 실행 중인
에이전트가 기본 프롬프트나 평가 규약을 자기 편의로 고치는 권한을 부여하지 않는다.

## 4. 기존 역할과 흐름

```text
사용자 요구 + 대화 맥락
        ↓
기존 의식: 실행할 요청(task_framing)을 정의하고 기준·필요한 계획을 도출
        ↓
기존 실행자: 현재 요청을 수행하며 근거·결과를 축적
        ↕
기존 중간감사: 근거에 비춰 문제와 진행을 판단하고 필요할 때 같은 규정을 갱신
        ↓
실행자의 완료 판단 / 선택된 경우 기존 독립평가
```

이는 역할의 설명이며 새 단계도가 아니다. 기존 의식 진입·규정 계승·감사 호출 시점을
유지한다. 모든 EXECUTE 턴에 의식을 강제하거나 매 도구 호출마다 문제를 다시 쓰지 않는다.

**최초 의식**은 사용자가 원한 결과를 맥락에서 복원하고, 더 정확한 요청을 정한다.
그 요청의 달성 기준을 적고 필요한 경우 기존 연구계획 경로로 넘긴다. 충분한 근거 없이
결론을 미리 선택하지 않는다. 모르는 것은 전제나 조사할 질문으로 넘길 수 있다.

**실행자**는 현재 요청을 실제로 해결한다. 검색어·도구·구현 방법·작업 순서는 맡긴 범위
안에서 조정한다. 문제 자체의 변경이 필요하다고 알게 되면 기존 `reframe`으로 관측과
변경 필요를 전달한다. 도구 실패나 가설 하나의 기각이 곧 문제 재규정의 의무는 아니다.

**중간감사**는 같은 의식이 실행 근거를 받은 시점이다. “계획대로 가는가”뿐 아니라
“이 문제를 풀면 사용자의 요구에 답하는가”를 판단한다. 문제가 그대로면 필요한 교정만
기존 `instruction`에 전달한다. 문제가 달라져야 하면 같은 판단 응답에 수정된 기존 규정
필드를 담는다. 새 `REFRAME` 상태나 재규정 전용 심사자를 추가하지 않는다.

중간감사의 `REWORK` 응답에서 변경된 `task_framing`과 관련 기존 필드를 받을 수 있도록
현재 응답 계약을 확장한다. 이것은 새 문제 표현 스키마를 만드는 것이 아니라 최초 의식과
재규정에서 쓰는 계약을 같은 의식의 중간 판단에도 적용하는 것이다. 변경 이유와 근거는
기존 `reason`·`evidence_ids`로 전달한다. `UNKNOWN`인 잠정 의견을 확정 규정으로 채택하지 않는다.
변경된 규정 자체가 실행 지시이므로, 같은 내용을 `instruction`에도 복사해야만 접수되는
조건은 두지 않는다. 단순 실행 교정은 기존 교정 전달 경로를 유지한다.

독립평가는 선택되어 있을 때 **현재 확정된 기준**으로 결과를 판단한다. 문제를 다시
정하거나 기준을 바꾸는 역할은 맡지 않는다. 기준의 존재만으로 평가를 켜지 않는다.

### 심층연구와의 관계

“무엇을 연구하라고 시킬 것인가”가 요청이고, “어떻게 알아낼 것인가”가 연구계획이다.
기존 최초 의식과 계획 보완 호출이 이 관계를 따른다. 보완 과정에서 더 나은 질문이 나오면
같은 호출의 규정·계획을 함께 고친다. 질문 초안만 승인받는 별도 호출이나 파일은 만들지 않는다.

중간감사가 연구 문제를 바꾸면 기존 계획의 유효한 자료·질문은 보존하고 필요한 부분만
수정한다. 기존 keep/patch/revise 저장 경로를 사용하며, 별도 계획 보완이 실제 필요한 경우에만
그 기존 경로를 사용한다. 감사의 결론을 다시 승인받기 위한 의식 호출은 만들지 않는다.
장기 연구 주제의 후속 설명에서는 전체 연구계획과 이번 턴의 요청을 구별한다.

## 5. 현재 규정의 소유와 전달을 하나로 맞춘다

프롬프트만 바꾸면 실행자는 새 문제를 받는데 평가나 다음 턴은 옛 문제를 받을 수 있다.
정식 변경의 수락 경로를 먼저 하나로 모은다. **기존 턴 `TurnChannel.current`를 현재 규정의
소유자로 쓰고 감독자는 이를 참조한다.** 초기화·실행자의 `reframe`·중간감사에서 나온 변경이
같은 갱신 함수를 거치게 한다. 감독자 안에서 임시 채널을 만들어 따로 보유하는 경로는 합친다.
감독이 없는 경로도 같은 채널을 사용한다. 새 영속 DB나 목표 서비스를 만들지 않는다.

갱신 함수는 모델 판단을 다시 심사하지 않는다. 기존 검증·권한·판본 확인과 필드 병합,
저장된 계획의 참조 연결을 맡는다. 실행 중인 도구를 중간에 되돌리지 않으며 기존 실행
경계에서 현재 규정을 바꾸고 실행자에게 알린다. 감사가 읽은 규정과 적용 시점의 규정이
다르면 오래된 수정으로 덮어쓰지 않는다. 기존 조건 지문·취소·교정 수명 처리를 재사용한다.
연구계획 변경도 이 수락 경계 안에서 현재 판본을 확인한 뒤 저장하여, 채택되지 않은
감사 결과가 실행 중인 계획 파일만 먼저 바꾸는 일이 없게 한다.

동작 의미는 다음과 같다.

- 변경되지 않은 필드는 유지하고, 변경한 필드는 새 값으로 교체한다. 완료 기준을 바꾸면
  산문과 구조화된 기준을 함께 맞춘다. 빈 값과 생략은 기존 병합 계약에 따라 구별한다.
- 필요한 연구계획 저장·검증이 끝난 뒤 규정과 계획 참조를 함께 채택한다. 실패하면 이전
  유효 규정을 남기고 실패를 알린다. 새 문제와 옛 계획을 조용히 섞어 실행하지 않는다.
- 최초 인계와 수정 인계는 같은 규정 표현을 사용한다. `source=consciousness`를 보존해
  실행 지시임과 사용자 원문이 아님을 동시에 명확히 한다.
- 실행 프롬프트, 감독 상태, 보완 인계, 최종 기준 계약, 다음 턴 계승이 모두 현재 규정을
  읽는다. 보완 인계의 작업 목표는 현재 `task_framing`에서 얻고 원문은 의도·권한의 근거로
  유지한다. 의식 규정이 없는 경로는 기존 사용자 요청을 사용한다.
- 기준 계약의 캐시는 해당 규정에 속하게 한다. 규정이 정식으로 바뀌면 새 기준을 반영하며
  옛 기준으로 진행된 평가를 새 기준의 승인으로 재사용하지 않는다. 과거 평가 기록은 보존한다.

이미 얻은 결과·출처·작업 ID는 남는다. 새로운 문제에 필요한 부분을 이어서 수행하며 전체
작업을 처음부터 시작하지 않는다. 종료된 턴에 늦게 도착한 감사가 새 실행을 열거나 최종
답변을 교체하지 않는다. 실패 이력만으로 후속 호출을 만드는 제거된 경로도 복원하지 않는다.

## 6. 프롬프트는 추가보다 교체로 정리한다

다음은 구현 시 교체할 핵심 문구의 초안이다. 현행 전문 뒤에 붙이는 부록이 아니다.

### 의식의 역할·`task_framing` 설명 교체안

> 사용자의 요구와 맥락을 읽고, 실행자에게 무엇을 해결하라고 맡길지 더 정확한 요청으로
> 써라. `task_framing`은 그 실행 요청이다. 사용자가 얻으려는 판단이나 결과를 중심으로
> 필요한 구분과 범위를 분명히 하되, 확인되지 않은 전제나 결론을 확정하지 않는다.
> 단순한 요청은 단순하게 유지한다. 완료 기준은 이 요청의 해결 여부에서, 필요한 계획은
> 이 요청을 푸는 방법에서 도출한다. 의식이 정한 문제와 목표는 잠정적이며 실행 근거로
> 수정할 수 있다. 사용자 목적·명시 조건·권한은 그 수정의 근거이자 경계다.

기존 이름 붙은 줄 목록을 의무 형식에서 제거한다. `expert_choice`의 “세상의 방식에 둔다”
같은 상호 참조도 정리한다. 방법 선택·탐색 능력은 `hint` 등 해당 역할에 남기고, 위해·권한은
기존 실행 경계와 해당 작업의 실제 제약으로 표현한다. 같은 내용을 여러 필드에 반복하지 않는다.

### 실행 인계의 앞부분 교체안

> 현재 실행 요청은 아래 `task_framing`이다. 의식이 사용자 요구와 대화 맥락을 해석해
> 작성했으며 사용자 원문 인용은 아니다. 원문과 사용자 결정은 목적·조건·권한을 확인하는
> 근거다. 현재 요청을 수행하고 그 기준으로 결과를 확인하라. 방법은 실행 근거에 맞게
> 조정하며, 문제 자체를 바꿔야 하면 근거를 붙여 기존 재규정 통로로 전달하라.

### 중간감사의 역할 설명 교체안

> 현재 문제를 풀면 사용자의 요구에 답하게 되는지, 실행 근거가 그 문제와 진행을 어떻게
> 바꾸는지 판단하라. 문제가 적절하면 필요한 실행 교정만 전달하라. 문제를 바꿔야 하면
> 그 이유·근거와 수정한 실행 요청을 기존 규정 필드로 반환하고 관련 기준·계획을 맞춰라.
> 의식이 도출한 목표는 교체할 수 있지만 사용자 명시 조건의 미달을 목표 변경으로 지우지
> 않는다. 유효한 결과를 이어 쓰며, 실행자가 이미 해결한 일을 다시 시키지 않는다.

기존 “품질·성공 기준을 낮추지 말라”는 문구는 사용자 조건과 의식의 잠정 목표를 구분하는
설명으로 정리한다. 목표 수정 금지와 재규정 허용을 서로 충돌하는 명령으로 남기지 않는다.
`base_prompt_v7.md`의 임의 목표·기준 변경 금지도 이 역할 구분과 일치시킨다.

## 7. 같은 요구를 어떻게 다루는가

가상의 사용자 요청: **“AI 때문에 청년 채용이 줄었는지 심층연구해줘.”**
이 예시에서는 앞선 대화에서 한국·최근 3년·진로 판단 목적이 확인됐다고 가정한다.
맥락이 없다면 이 조건들을 사용자 결정으로 지어내지 않는다.

의식이 넘길 요청의 예:

> 한국의 최근 3년 청년 신규 채용 변화를 확인하고, 변화가 있다면 AI 도입이 이를 설명하는
> 정도를 경기·산업 구성·채용 방식 변화와 구분해 조사하라. 취업자 수와 신규 채용을
> 구별하고, AI 노출도와 실제 도입을 구분하라. 사용자의 진로 판단에 어떤 결론을 적용할 수
> 있는지, 자료로 확인되는 범위와 아직 판단할 수 없는 부분을 함께 설명하라.

이 요청은 “통계 수집 → 사례 조사 → 보고서 작성” 같은 연구계획보다 앞선다. 계획은
위 구분을 실제로 확인할 자료·방법·질문을 설계한다. 임의의 출처 개수나 확정 결론을
문제 규정에 추가할 필요가 없다.

중간에 일부 직종의 채용 감소와 다른 직종의 증가가 확인됐다면, 감사는 전체 감소의
원인을 찾던 잠정 목표를 **직종별 차이와 그 설명을 가리는 문제**로 바꿀 수 있다.
원래 질문인 전체 변화의 존재 여부도 결과에 답한다. 이미 모은 자료는 재사용하고
불필요해진 가설 검증은 멈춘다. 이 수정에 실행자의 재요청을 다시 받을 이유는 없다.

반대로 채용 자료가 없어 취업자 수만 확보했다면, 그것을 신규 채용 감소의 답으로 바꾸지
않는다. 확보 자료의 한계와 남은 질문을 보존한다. 문제를 정확히 만드는 것과 답하기 쉬운
다른 문제로 바꾸어 성공 처리하는 것은 다르다.

## 8. 구현 범위와 검증

구현은 하나의 변경으로 완료할 수 있는 범위를 다음 책임에 묶는다. 각 항목은 사용자에게
새로 요구할 절차가 아니라 코드와 교재를 함께 맞추기 위한 작업 순서다.

1. 의식·중간감사 프롬프트와 최초/재규정 인계를 위 역할로 교체한다. 기존 필드를 재사용하고
   겹치는 형식 지시를 제거한다. 연구 가이드와 [진화 목적](IBL_EVOLUTION_PURPOSE.md)의
   ‘세상의 방식’ 참조도 같은 의미로 정리한다.
2. `reframe`의 규정 채택 처리를 공통화하고 감독자와 파이프라인의 현재 규정 소유를 통일한다.
   실행·기준 계약·보완·계승 소비자를 연결한 뒤, 중간감사의 기존 응답에서 변경 필드를
   받아 같은 채택 경로에 연결한다. 기존 연구계획 저장 경로도 함께 맞춘다.
3. 계약 회귀로 전달의 일관성을 확인하고 실제 작업 비교로 문제 규정의 질을 평가한다.
   프롬프트 변경만 적용한 상태를 전체 구현 완료로 보고하지 않는다.

계약 검증은 기존 `test_reframe.py`, `test_conscious_supervisor.py`, `test_supervisor_runtime.py`,
`test_research_planning.py`, `test_research_plans.py`, `test_final_evaluator.py`,
`test_framing_inheritance.py`, `test_agent_pipeline.py` 등의 소유 모듈에 둔다.

- 최초 규정·실행자 요청 재규정·감사 재규정이 같은 현재 상태로 이어지는가.
- 문제와 관련 기준·계획을 바꾼 뒤 실행 인계·보완·평가·다음 턴에 옛 규정이 남지 않는가.
- 원 사용자 제약은 보존하면서 의식의 잠정 목표는 실제로 교체할 수 있는가.
- 오래된 감사·계획 저장 실패·취소에서 이전 유효 상태와 완료 결과가 보존되는가.
- 유효 결과를 재사용하며, 단순 요청·정상 진행·이미 해결된 실패에 추가 호출이 생기지 않는가.

의미상의 효과는 단순 요청, 모호한 연구 요청, 잘못된 전제, 사용자 고정 조건, 진행 중
증거에 따른 문제 수정 등에서 본다. 같은 모델·도구·자료 조건으로 현행 규정과 변경 규정을
비교하고, 사용자가 외부 AI에게 재작성시킨 요청도 참고 기준으로 비교할 수 있다.
실행자가 무엇을 풀어야 하는지 분명해졌는지와 실제 산출물이 사용자 요구에 더 잘 답하는지를
함께 본다. 이 비교는 운영 중 모든 작업에 추가하는 평가 단계가 아니다.

완료 시간·전체 토큰·모델 호출 수와 재사용 여부는 기존 에피소드 계측으로 확인한다.
문장 길이·필드 수·출처 수의 증가를 개선으로 판정하지 않는다. 측정은 효과 보고의 근거이며
공통 구조 개선을 시작하기 전에 특정 사례의 성능 입증을 요구하는 관문은 아니다.

현재 완료 범위는 **프롬프트·실행 경로 조사와 이 설계 작성**이다. 런타임·운영 프롬프트는
변경하지 않았으며, 재규정 품질·시간·토큰 개선도 아직 측정하지 않았다.
