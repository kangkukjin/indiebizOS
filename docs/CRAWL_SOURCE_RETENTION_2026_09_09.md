# 크롤 원문 보관과 모델 표시량 분리

## 문제와 결과

ep3286은 문서 6개 중 5개가 10,000자에서 잘렸다. 크롤러가 다운로드와 텍스트 추출을
마친 뒤 나머지를 버려, 추가 읽기가 같은 페이지의 네트워크 재수집을 요구했다.
앞선 [경고 보존 수리](EPISODE3286_TRUNCATION_REPAIR_2026_09_09.md)는 그 손실을
드러냈으나 재조회를 없애지는 못했다. 사용자의 후속 지시로 수집·보관·표시를 분리했다.

공개 `crawl_website`는 정적 HTML·PDF·Chrome·Playwright 추출 단계에 전문 수집을
요청한다. 추출된 텍스트 전문과 문단 `items`를 불변 JSON 파일로 저장하고 전체를
IBL 통화로 돌려준다. `max_length`는 호환 이름을 유지하되 **모델 표시 글자 예산**이
되었다. 기본 60,000은 원문 길이·저장량·후속 IBL 처리량을 제한하지 않는다.
네트워크 응답이나 추출기가 제공하지 못한 내용까지 보존한다는 뜻은 아니다.

## 보관과 재사용

- 파일: 기존 `data/spill/`의 `crawl_source` JSON 스냅샷. `source_ref.path`로 읽는다.
  기존 spill 수명(24시간)을 따른다. 전체가 JSON의 `text`와 `items`에 보존된다.
- URL 캐시: 프로젝트 경로·에이전트·URL별, 기본 900초. 수치는
  `data/lifecycle_policy.yaml:webcrawl_cache.reuse_seconds`에서 정한다.
  결과 `cache`는 `hit`, `fetched_at`, `reuse_until`을 표시한다.
- `refresh:true`만 유효한 캐시를 건너뛰고 새 내용을 수집한다. 갱신은 새 스냅샷을
  만들므로 앞서 받은 `source_ref`를 덮어쓰지 않는다. 갱신 실패를 옛 성공으로 숨기지 않는다.
- 실패·불완전 진단 응답은 재사용하지 않는다. 만료·소실·깨진 캐시는 재수집한다.
  원문 보관 실패는 `source_storage_failed`로 신고한다.
- 같은 프로세스의 동시 호출은 URL별 잠금으로 수집을 공유한다. 캐시 색인은 원자적으로
  교체하며 원문 파일이 먼저 완성된다. 프로세스 재기동 후에도 디스크 캐시를 읽는다.
  별도 프로세스가 동시에 같은 URL을 처음 요청할 때의 중복 수집까지 직렬화하지는 않는다.

## 모델 경계

전문은 턴 변수·앱·IBL 후속 처리에 유지한다. 모델 표시 사본만 기존
`preview_envelope`에서 줄인다. 행 수가 적어도 한 문단이 길 수 있으므로 items/rows의
문자열과 text/content에 글자 예산을 공유한다. 진단·출처 필드는 그대로 남긴다.
생산자는 범용 `_display{max_chars,mirror_fields,limit_rows}`로 표시 정책을 선언한다.
코어는 크롤 액션 이름을 알지 않는다. 문단 items와 중복되는 `text`는 큰 미리보기에서
생략하고 `_preview.omitted_fields`에 적는다. 잘린 데이터 필드는 위치·보인 글자 수·
전체 글자 수를 `_preview.fields`에 적는다. 원형 객체는 바꾸지 않는다.

**첫 표시 확대(2026-09-09 후속)**: 크롤 기본 표시 예산을 60,000자로 올렸다.
`limit_rows:false`인 문단 통화는 일반 표의 앞 8행 제한을 적용하지 않는다. 제목·문단의
문자열 합이 예산에 닿을 때까지 보여주고, 경계 문단은 남은 글자만 표시한다. 뒤쪽 문단은
빈 문자열 행으로 나열하지 않고 `_preview.shown/total`로 생략 개수를 알린다.
6만자 안의 문서는 문단이 많아도 첫 호출에서 읽고, 더 긴 원문은 저장 변수·파일에서
이어 읽는다. JSON 문법·출처·진단 글자는 본문 표시 예산과 별도다.

표시된 본문이 전달 단계에서 다시 16,000자로 잘리던 제한도 함께 맞췄다. API 프로바이더와
MCP는 최종 통화의 `_display` 선언을 읽어 표시 사본·메타데이터가 통과할 예산을 준다.
한 응답의 선언 기반 확대는 기존 자동 스필 임계(200,000자)까지다. 일반 결과의 액션당
예산은 유지한다. 내부 CLI 생성자는 MCP 결과 토큰 한도를 공용 상수로 설정하며,
사용자가 명시한 더 작은 `MAX_MCP_OUTPUT_TOKENS`는 그대로 존중한다. 외부 클라이언트가
별도 표시 상한을 강제하면 그 클라이언트 설정도 필요하다.

`verbose:true`는 이 미리보기를 생략한다. 호스트의 최종 전송 한도는 별도로 남으므로
긴 원문을 전부 채팅에 쏟는 용법보다 같은 호출 안에서 필요한 부분을 처리하는 편이 낫다.

```ibl
$원문 = [sense:crawl]{url:"https://example.com/article"}
$원문 >> [table:filter]{where:"text contains '관심 주제'"}
```

다음 호출에서도 같은 턴의 `$원문`을 그대로 읽을 수 있다. 더 읽을 목적으로 URL을 다시
호출해도 캐시 유효 기간에는 재다운로드하지 않는다. 최신 상태 확인이 목적이면
`[sense:crawl]{url:"https://example.com/article",refresh:true}`로 명시한다.

표시 미리보기는 `truncated/source`가 아니다. 앞선 원천 절단 증거 보존·증류 배제는
실제 누락이 있는 생산자에 계속 적용한다. 원문을 저장했다는 사실과 AI가 전문을 검토했다는
사실도 다르다. 평가·증류가 표시 미리보기를 원천 실패로 오인해서는 안 된다.

## 검증

`backend/test_crawl_retention_2026_09_09.py`: 긴 HTML/PDF/브라우저 추출, 디스크 전문,
작은 표시 예산, 모듈 재로드, 갱신·만료·소실·손상, 프로젝트 격리, 동시 수집,
저장 실패, 실제 IBL 턴 변수에서 뒤쪽 문단 읽기, 앱 전문 전달, 관용구의 같은 프로그램
안에서 뒤쪽 문단 처리, 진짜 절단 증거와 미리보기 구분을 검증한다.
원문 보관 수리 시 전체 회귀 `.venv/bin/python -m pytest backend/ -q -o addopts=''`는
3,368개 통과·1개 건너뜀·116개 경고, 실패 0건(119.59초)이다. 어휘 파생·몸 번들·
층 구조·파일 크기·은퇴 계약 검사도 통과했다. 로그는 `outputs/crawl_retention_full.log`.

전체 검사 중 기존 `test_notebook_memory`의 카드 데몬이 fixture 종료 뒤 실 DB의
source_id=1을 읽어 테스트 이름 `독서` 아래 카드를 만드는 격리 결함을 발견했다.
등록·검색 테스트에서 카드 데몬을 차단했고 카드 생성 자체의 시험은 유지했다.
잘못 생성된 파일 한 개는 `data/_backups/2026-09-09_crawl_retention_test_isolation/`로
옮겼으며 실 노트북 DB는 변경하지 않았다. 수정 후 전체 검사에서 재발하지 않았다.

첫 표시 6만자 확대 후 전체 회귀는 **3,374개 통과·1개 건너뜀·116개 경고, 실패 0건**
(121.93초)이다. 추가 회귀는 문단이 많은 52K/110K 문서의 직접 호출·변수 할당,
API/MCP 전달 시 본문 보존, 저장된 마지막 문단 읽기, 명시한 호스트 한도 존중을
검증했다. 일반 표의 8행 미리보기와 작은 표시 예산·캐시 회귀도 통과했다.
어휘 파생·몸 번들·층 구조·은퇴 계약 검사가 통과했으며 로그는
`outputs/crawl_first_display_60000_full.log`와 `outputs/crawl_first_display_60000_checks.log`다.
