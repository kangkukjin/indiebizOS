**3. 중간 감독은 ‘호출됨’과 ‘개입함’이 달랐다**

반복 실패로 감독이 시작된 동안 실행자는 다른 크롤링을 계속했다. 감독은 검색 질의·소스를 바꾸라는 지시를 만들었지만, `exec_revision`이 **69 → 75**로 바뀌어 그 지시가 폐기됐다. `instruction.delivered` 사건은 없다.[^3]

현재 코드는 성공 도구 결과뿐 아니라 단계 진행 문자열이 바뀔 때도 공통 실행 revision을 올린다. 그 revision이 달라지면 판단 완료 시점과 전달 시점 모두에서 지시를 버린다. 낡은 취소 지시가 회복된 작업을 망치지 않게 하는 보호 의도는 타당하다. 그러나 **다른 자료를 읽은 것과, 지시가 겨냥한 문제를 해결한 것은 다르다.** 비동기 관찰에서 어떤 진척이든 판단을 무효화하면 유용한 감독도 구조적으로 늦은 지시가 될 수 있다.

이번 지시를 적용했다면 반드시 검색 비용이 줄었을 것이라는 반사실은 증명하지 못한다. 감독의 ‘긴 질의가 실패 원인’이라는 해석도 통제된 검색 실험의 결론은 아니다. 확인한 사실은 유용할 수 있는 지시가 관련 문제의 해소 여부와 무관하게 공통 revision 차이로 버려졌다는 것이다.

계획 변경: 지시가 의존하는 목표 버전·문제 ID·작업/산출물·관측 조건을 명시하고, 그 조건이 해소됐거나 바뀌었을 때 폐기한다. 취소·쓰기처럼 위험한 지시는 엄격한 신선도 검사를 유지한다. 불확실하면 다음 안전 경계에서 짧은 변경 상태로 재검증하되 매번 새 감독 호출을 만들지 않는다. `시작/판단/적용/불필요해짐/충돌로 폐기/재검증 대기`를 구분해 집계한다. 과거 판정을 일괄 적용하는 변경은 아니다.

동시에 실행 사건 일부가 `role=execution, phase=review`로 기록됐다. 공통 `self.phase`가 감독 호출 중 바뀌기 때문이다. 호출 목적과 단계는 행위자별 호출 문맥에 묶어야 정확한 비용·효과 분석이 가능하다.

**4. 세 번째 검수를 할 자원이 부족한데 두 번째 보완을 먼저 시켰다**

계획+중간 감독 입력은 131,494였다. 현행 예산 함수가 최종 검수에 허용한 몫은 168,506이다. 첫 두 최종 검수에서 69,351+74,484를 사용해 **24,671**이 남았다. 그 뒤 10회 응답의 보완 실행을 시켰고, 재검수 첫 요청이 **32,479**를 소비하면서 전체 의식 한도를 7,808 초과했다.[^4]

이는 “최종 검수 예산을 보호”하는 것만으로 충분하지 않음을 보여준다. **최종 검수 → 보완 → 재검수 전체를 하나의 종료 절차로 예산에 잡아야 한다.** 보완 지시를 내리기 전에 남은 판정 자원을 확인하고, 소프트 한도라면 판정까지 회수할 수 있게 배분을 조정한다. 실제 하드 한도라면 추가 제작을 먼저 시키고 승인만 못 하는 상황을 피하며 미완료 상태·증거·재개 지점을 남긴다. 근거 없는 자동 승인은 하지 않는다.

기존 P2 ‘단계별 새 문맥’도 보완 경로에는 앞당겨 검토한다. 입력이 커도 캐시 덕에 싼 재개와, 새 문맥을 준비하는 비용을 비교해야 한다. 자동 리셋을 일괄 적용하지 않고, 최초의 큰 이력을 무조건 이어가는 대신 **원래 요청·기준·미해결 항목·대상 파일 지문·편집 위치·관련 증거·작업 핸들**로 보완을 수행할 수 있게 한다. 단순한 파일 편집 여러 개는 먼저 검토한 패치 묶음으로 실행하고 한 번에 결과를 확인한다.

**5. 의식이 세운 조사 목표와 사용자의 필수 조건을 구분해야 한다**

사용자는 ‘서로 다른 직역 세 개’를 지정하지 않았다. 그 숫자는 최초 의식 계획이 만든 `achievement_criteria`다. 여러 직역을 보려는 기준 자체는 합리적일 수 있다. 그러나 사실관계를 알아보는 조사에서 특정 수의 **성립 사례가 반드시 존재한다**고 완료 조건을 정하면, 증거가 부족할 때도 숫자를 채우려고 계속 찾거나 약한 근거를 성립 사례로 승격할 압력이 생긴다.

첫 검수는 농업 외 ‘1~2건’을 보완하라고 했고, 실행은 한 건을 추가했다. 두 번째 검수에서는 여전히 세 직역 미달이라 또 보완을 지시했다. 최초 기준은 세 직역이었으므로 검수 도중 새 기준을 발명한 것은 아니다. **보완 지시와 최종 통과 조건이 충분히 정렬되지 않은 것**이다.

계획 변경: 각 기준에 `사용자 필수 / 시스템 정확성 / 의식의 조사 목표` 출처와 강도를 둔다. 조사 목표에는 합리적인 탐색 범위와 ‘찾지 못했을 때 어떤 결론을 허용하는가’를 같이 둔다. 범위 조정은 이유·기존/변경 기준을 기록하고 숨겨서 낮추지 않는다. 반례나 근거 부족도 정당한 조사 결과가 될 수 있어야 한다.

최종 검수의 REWORK는 미해결 항목을 한 번에 묶고, 항목별 완료 증거·대안·멈춤 조건을 명시한다. 같은 미달을 한 항목씩 뒤늦게 추가해 연쇄 보완하지 않는다. 새 보완으로 생긴 새로운 결함은 별도로 다룬다.

**6. 부분 수정 도구만으로 반복 출력과 일관성 문제가 해결되지 않았다**

저장 응답 v1은 1,801자로 하나의 블록이었다. `patch`는 이 블록 전체를 v2 2,470자, v3 2,778자로 교체했다. 새 텍스트 중 직전 버전과 일치하는 정렬 구간은 각각 **1,745자(70.6%)**, **2,369자(85.3%)**였다. 글자 단위 정렬 비교이며 정확한 절감 토큰은 아니다.[^5]

`put_response`는 처음에만 2,000자씩 나누고 이후 패치가 커져도 나누지 않는다. 따라서 도구 이름은 부분 수정이지만 이 사례에서는 **사용자 답변 전문을 두 번 다시 출력**했다. 지문 확인·버전 보호는 작동했으며, 그 보호를 유지하면서 문단·범위·삽입 단위의 수정과 기계적인 재조립이 필요하다. 고정 문자 절단은 문장·표·코드를 가를 수 있으므로 경계와 안정 ID도 검토한다.

실제 보고서에는 셋째 직역을 추가한 뒤에도 봉제 절의 **‘농업 외 … 유일한 사례다’**가 남아 있다. 서두는 농업·봉제·요식 세 직역이라고 하므로 내부 불일치다. 또 비교 근거의 표제는 2025년과 2026년인데 ‘같은 연도’라고 단정하고, 관찰 사례 비교를 ‘차이는 … 하나였다’는 유일 원인 결론으로 확장한다. 외부 사실 전체를 다시 검증한 것은 아니지만, 현재 문서만으로도 이 표현들은 재검토가 필요하다.[^6]

계획 변경: 변경 부분과 그 영향만 재검수하되, 총괄 개수·유일성·결론·출처·시간 비교 같은 연결된 주장도 영향 범위에 넣는다. 숫자·이름·시점 세 칸을 채우는 것만으로 인과나 일반화가 입증되지는 않는다. 이런 일관성 검수를 없애는 방식으로 토큰을 절감하지 않는다.

**7. 봉투 중복과 메모리 집계도 일반화해 수리해야 한다**

실행 도구 결과 31건의 보존된 표시량은 총 **926,044자**였다. 그중 39,000자 이상인 11건은 모두 `verbose:true`였으며 합계 848,753자였다. 예를 들어 사건 88의 전체 결과는 197,063자인데 최종 값의 JSON 직렬화는 22,282자이고, 사건 280은 전체 53,791자에 최종 값은 1,160자였다. 이 비교의 직렬화 형식은 다르므로 차이를 정확한 절감량으로 계산하지 않는다.[^7]

최종 투영·행 제한이 있어도 `verbose`가 중간 단계의 큰 값을 전부 노출한다. 3364에서 확인한 ‘마지막 결과의 정확한 두 벌’뿐 아니라 **앞 단계 원형을 반복 싣는 방식**도 제거 대상이다. 모든 단계의 오류·불완전 상태와 원형 참조는 남기고, 모델 표시에는 선택한 결과와 필요한 단계 정보만 제공한다.

에피소드 요약의 `execution_rounds=17`은 원장의 여러 실행 호출에서 `round`의 **최댓값**을 취한 결과다. 실제 17+11+10회가 하나의 17회로 보인다. 토큰 합계는 이번 사례에서 실제 원장과 일치하므로 ‘토큰 이중 합산’ 문제와 혼동하지 않는다. 회귀에는 다중 보완·동시 원샷·취소를 넣어 전체 응답 수와 호출별 라운드를 분리한다.[^8]
