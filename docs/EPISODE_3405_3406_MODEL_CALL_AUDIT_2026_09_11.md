계산하고 문서에 넣고, AI는 해석과 출처 관계를 작성하도록 분리하는 실험이 필요하다.
특히 3406에는 증가율 순위 오류와 산술 시나리오를 인과 기여율로 읽은 문제가 있었으므로,
계산을 구조화하는 것은 속도뿐 아니라 검수에 필요한 증거를 만드는 개선이다.

## 지금 이미 고친 것과 아직 검증할 것

[기존 수리 기록](EPISODE_3405_3406_REPAIRS_2026_09_11.md)과 현재 코드를 대조했다.

| 항목 | 현재 확인 상태 |
|---|---|
| 계획자에게 관용구 지도 전달 | `supervisor_runtime.tool_context`가 `available_idioms`를 제공한다. 과거 두 실행에서 미사용이었다는 사실과 분리해야 한다. |
| 짧은 출처 결과의 읽기 기록, 증거 ID 인계 | 수리됨. `conscious_supervisor`·`supervisor_review`에서 읽기 범위와 한정된 출처 재확인을 다룬다. 재확인은 추가 AI 호출일 수도 있으므로 0회로 단정하지 않는다. |
| 보완 시 기존 URL·결과 인계 | `supervisor_handoff.handoff_state`에 artifact·tool_index·증거 ID가 있다. 첫 보완의 재탐색을 줄일 직접 대응이다. |

| 차트 HTML 기본 형식, KOSIS 명시 ALL 전달 | 기존 수리에 반영됐고 KOSIS 코드에서 명시한 추가 차원의 전달을 확인했다. 전체 KOSIS 표의 계약이 검증된 것은 아니다. R3의 metadata 404 해결까지 입증한 것은 아니다. |
| 여러 읽기의 필요한 결과를 함께 반환 | 값 구성·변수로 표현할 수 있다. 현재 기본 봉투는 여전히 중간 `results`의 요약과 `final_result` 중심이다. 실제 작업에 맞는 반환 조립·표시를 검증할 필요가 있다. |
| 이미지 일괄 판독 | 현재 `vision_read.read_image`는 `images=[image]`로 한 장씩 내부 AI를 부른다. 두 IBL 문장을 한 번에 실행하는 것만으로 내부 호출은 줄지 않는다. |
| 해결된 오류에 대한 늦은 감독 지시 | 잔여 위험이 코드에 보인다. 아래 설명처럼 동일 입력 지문 중심의 issue 수명이 대체 성공을 포착하지 못할 수 있다. |

현재 `conscious_supervisor._finish`의 issue 키는 도구 이름 + 입력 증거 hash다.
동일 키가 성공할 때만 해당 issue를 닫는다. `conditions_valid`는 그 issue 상태를 대조한다.
따라서 출력 확장자를 고치거나 대체 통계표로 성공하면 입력 hash가 달라져 과거 실패 issue가
열린 채 남을 수 있다. 이것은 두 에피소드의 늦은 지시와 일치하는 구현상의 설명이다.
**“이 입력이 다시 성공했는가”와 함께 “그 입력이 풀려던 작업 조건을 다른 경로가 이미 충족했는가”를 추적해야 한다.**
단순히 다른 작업이 진행됐다는 이유만으로 모든 지시를 취소하면 필요한 개입도 사라지므로,
산출물·데이터 확보 등 해당 issue의 해결 조건과 연결해야 한다.

## IBL 개선 우선순위

1. **필요한 결과를 한 번에 반환하는 절차.** 조회·변환·저장 후 다음 판단에 필요한
   이름 붙은 데이터 요약, 계산값, 절대 산출물 경로, 원문 핸들을 함께 반환한다.
   중간 결과 전부를 프롬프트에 풀어놓는 방식은 피하고, 작업별로 작은 반환 형태를 정한다.
   문법은 우선 기존 변수·값 구성·함수·`self:script`로 충분한지 검증한다.
2. **재사용 가능한 증거와 검증 결과.** 결과에 출처 URL·조회 조건·hash·관련 범위·계산식을
   연결한다. 보완자는 출처를 재발견하지 않고, 감독은 바뀐 주장과 의존한 수치부터 확인한다.
   파일에 저장됐다는 사실만으로 다음 AI가 바로 활용할 수 있는 상태가 완성되지는 않는다.
3. **오류 복구의 실행 가능한 계약.** KOSIS 차원, 차트 형식, 이미지 경로처럼 결정 가능한
   조건은 호출 전에 검사하고 구체적인 유효 값·다음 읽기를 반환한다. 도구 검색 결과 열도
   `title/meta/summary/url`처럼 실제 반환과 일치해야 한다. 같은 실패의 추측 재시도를 줄인다.
4. **모델을 부르는 어휘의 비용을 드러내고 실제 배치 처리.** `image_read` 같은 어휘는
   내부 AI가 있음을 계획자가 알고 선택하게 한다. 이미지 여러 장의 한 번 판독, 외형 검사
   영수증의 재사용, 결정적 검사 선행을 비교한다. 외부 IBL 횟수만 줄이는 실험은 불충분하다.
5. **작업의 해결 조건에 연동하는 감독.** 위 issue 수명 문제를 먼저 검증한다. 이는
   새 IBL 낱말보다는 실행·감독 하네스의 계약 문제다. 수정 결과 자체를 반환하는 patch도
   별도 읽기 왕복을 줄일 수 있다.

사전 분류·배경 판정 둘은 병합 후보지만 두 사례에서 합계 약 2초 수준이어서 우선순위가 낮다.
별도 계획 호출은 각각 약 70.7초·83.3초였다. 지표 정의·연구 범위를 판단하는 일은 필요하지만,
반드시 실행자와 분리된 모델이 해야 한다고 이 두 기록만으로 입증되지는 않는다. 익숙한
업무에서는 검증된 절차와 측정량 정의를 실행자에게 주는 방식도 비교할 수 있다. 특히
3405처럼 계획자가 채용 흐름과 고용 스톡의 차이를 알고도 완료 기준을 약화한 경우에는
계획 호출의 존재 자체보다 원래 측정량을 유지하는 계약이 더 중요하다.
기억 후처리 3·2라운드는 직접 답변의 필수는 아니어도 사용자의 경험 축적 목적에 기여할 수 있다.
삭제보다 저장된 결과가 다음 작업에서 실제 재사용되는지 평가하는 편이 적절하다.

다음 검증은 같은 자료 스냅샷·모델·목표·검수 기준으로 현재 버전과 위 절차를 비교한다.
새 관용구 수 대신 **추가 읽기 수, 출처 재탐색 수, 내부 AI를 포함한 라운드 수,
캐시를 분리한 입력·출력량, 최종 품질, 사용자 대기 시간**을 기록한다.
3405는 신규 채용 질문의 미해결 여부, 3406은 인과·순위·출처 오류를 외부 기준으로 확인한다.
이 감사에서는 유료 재실행이나 코드 변경을 하지 않았으므로 개선 후 절감률은 아직 미측정이다.
