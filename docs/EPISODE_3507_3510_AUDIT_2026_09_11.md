## 2. P0 — 3510: 점심 질문이 외장 디스크 탐색에 걸렸다

19:54:53에 턴을 열고 실행기억·기억지도·실행지도까지 조회했다. 20:35에도 이벤트는 `request.received`, `task.created`, `cognition.supervisor_selected`, `supervision.turn.opened` 네 개뿐이다. 모델 호출·IBL 실행·종료가 없다. 따라서 긴 추론이나 식당 조사가 진행 중이라는 설명은 맞지 않는다.

로그·네이티브 표본·분리 재현이 같은 원인을 가리킨다. 라이브 Python 프레임을 직접 덤프한 것은 아니므로 정확한 Python 호출 스택 전체를 확보했다고 주장하지 않는다. 당시 `/health`는 응답하고 다른 HTTP 작업도 진행됐다. 서버 전체 정지와 특정 턴의 정지를 구분해야 한다.

감시도 놓친다. `conscious_supervisor.py:453`의 tick은 `phase in {'plan','reframe'}`이면 바로 반환한다. 회상 중에도 초기 phase가 plan이어서 실행 전 대기가 감시 밖이다. 모델 호출의 180초 한도는 모델을 부르기 전의 디스크 대기를 제한하지 못한다.

**수리:** 전경 회상은 캐시된 지도만 읽고, 실제 탐색은 취소·수명 관리가 가능한 별도 작업으로 갱신한다. 캐시 키 해소도 전경에서 디스크를 건드리지 않아야 한다. 느린 볼륨은 일정 기간 재시도를 막고 stale 지도/지도 없음으로 진행한다. 일반 “어디”만으로 디스크 탐색을 켜지 말고 실제 파일 탐색 작업 문맥을 사용한다. 이 판단을 위해 새 AI 분류 호출을 추가하지 않는다. 회상 단계 시작·종료·현재 대기 대상과 경과 시간을 원장에 기록하고 실행 전 대기도 watchdog 범위에 넣는다. 스레드 future의 timeout만 걸어 놓으면 막힌 OS 호출은 남으므로 해결로 간주하면 안 된다.

**통과 조건:** 디렉터리 열기가 무한 대기하는 테스트 대역에서도 식당 질문이 파일 탐색 없이 모델 단계에 도달한다. 파일 질문도 정해진 회상 예산 내 fallback하고, 반복 요청으로 막힌 작업이 누적되지 않으며 취소·재시작 시 소유 작업이 정리된다.

## 3. P1 — 기억을 읽고도 놓쳤고, 과거 사실과 AI 답변을 현재 사실로 만들었다

### 3507의 결함

첫 `self:memory recall`의 실제 반환 본문에 기억 #14의 **체스터톤스 호텔 예약, 최고층 투룸 디럭스 로프트**가 있었다. 그런데 답변은 “속초 숙소 — 확정된 기록이 없습니다”라고 했다. 다만 옛 기억 자체에는 이번 여행 날짜가 명확하지 않으므로 올바른 답은 예약 메모를 인정하고 이번 일정과의 연결 여부를 구분하는 것이다. 옛 메모만으로 현재 예약을 무조건 확정하는 것도 잘못이다.

또 과거 여행 기억의 “사용자·아내·어머니”를 이번 9월 여행의 세 명으로 단정했다. 사용자는 3510에서 사용자·두 형님·어머니라고 바로잡았다. 이전 여행의 동행자 정보가 거짓이라는 뜻이 아니라 **행사와 시점이 다른 정보의 적용 범위가 사라진 것**이다.

3507 종료 뒤 자동 증류는 이 잘못된 답변 표를 기억 #55로 저장했고, 3508은 새 `여행 계획/속초` 가지에서 그 표를 다시 읽었다. 기존 코드가 assistant 출처를 `작업기록`으로 분류하고 source_ref를 보존하는 보호 장치는 있다. 그러나 **출처 보존과 사실 신뢰도 보장은 다르며**, 실제 회상·답변에서 이 구분이 작동하지 않았다.

### 3508의 검색·표시 결함

숙소 검색은 #14를 찾았고 메타데이터 키워드에는 호텔·예약이 보였다. 그러나 `memory_db.py:590`의 본문 앞 100자 미리보기는 전주 숙소 선호 등 이전 내용만 보여 주고 뒤의 예약 문장을 잘랐다. 모델은 해당 ID의 원문을 추가로 읽지 않고 숙소 이름/링크를 다시 요구했다.

복수 IBL 문장 중 첫 검색은 6건을 찾았지만 최종 결과는 마지막의 장소 검색 결과 1건이었다. 그 1건은 남해의 다른 숙소였다. 첫 결과가 완전히 유실된 것은 아니고 step preview로 남았지만 중요한 검색 결과가 최종 표면에서 밀렸다. 3507의 장소 검색 14→0도 도구 실패가 아니라 조회 범위에서의 빈 결과다. 이를 전체 기억에 예약 정보가 없다는 증거로 확대하면 안 된다.

**수리:** 기억을 행사/대상·시점·원 발화자·확정/제안 상태와 함께 반환하고, 사용자 발화/예약 원문과 AI의 권고·회고를 구분한다. 관련 문장 중심 검색 미리보기와 잘림 표시, 원문 ID를 제공한다. “기록 없음”은 조회 범위와 잘린 근거까지 확인한 수준으로 제한한다. 서로 다른 여행·숙소 선호·예약 사실을 하나의 장문 기억에 계속 덧붙이는 병합도 재검토한다. 전문과 같은 행 내용을 중복해서 주입하는 recall 표현은 출처를 보존하는 한 벌로 줄일 수 있다.

**통과 조건:** 호텔 사실이 100자 뒤에 있어도 검색에서 발견하고 원문을 읽는다. 이전 여행의 배우자를 새 여행 참석자로 추정하지 않는다. assistant의 정리 표를 사용자의 확정 발화보다 우선하지 않는다. #55는 다음 수리에서 출처를 남기고 정정 대상으로 처리하며, 감사만으로 무단 삭제하지 않는다.

## 4. P1 — 3508: 짧은 상태 통보가 새 여행 조사로 확대됐다

사용자 메시지는 “숙소 예약되었다.” 9자였다. 한 번의 관련 기억 확인은 유용하지만 실제 실행은 5개 Claude 라운드로 이어졌다. 수원시청→속초시청 경로와 날씨를 조회하고, 기본 3일 예보가 여행 날짜를 덮지 못하자 `days:10`으로 날씨를 다시 조회했다. 첫 예보는 9/11–13, 두 번째 반환은 여행일을 포함한 9/11–17이었다. 장소도 실제 예약 호텔이 아닌 대리 목적지여서 3509에서 호텔 기준 경로를 새로 구했다.

날씨를 조회한다면 처음부터 여행 기간을 요청하는 게 맞다. 이 턴에서는 날짜·날씨·교통 변화가 사용자의 예약 완료 통보에 답하는 데 필요한 새 조사인지부터 판단했어야 한다. “주말 지나고 한 번 더 보겠습니다”라는 답변에는 실제 예약된 후속 작업이 없었다. 약속을 해 놓은 것과 스케줄러에 등록한 것은 구분해야 한다.

**수리:** 상태 통보·정정은 현재 여행의 해당 사실을 갱신하고 필요한 모순만 해소한다. 추가 도구 호출은 어떤 답변 결정을 바꾸는지 명시할 수 있을 때 수행한다. 날짜가 필요한 조회에는 사용자 일정의 범위를 전달한다. 실행 ID/등록 영수증 없이 미래 재확인을 이미 맡은 일처럼 표현하지 않는다. 각 짧은 턴에 검수 AI를 추가하는 방식은 피하고, 기존 증거·작업 상태로 확인 가능한 부분을 먼저 처리한다.

**수리:** 도구의 분 단위 값, 가정한 식사·휴식·여유, 출발/도착을 구조화된 한 계산표에서 산출한다. 합계·차이·단위 변환과 시간표 일치는 코드로 검증하고 모델은 가정의 타당성과 설명을 맡는다. 최초 계획도 이미 명확한 비교 질문에서 장문 여행 설계로 확대하지 않고 핵심 불확실성·조회·계산 계약에 집중한다. 관련 검수를 없애거나 모델 기어를 낮출 필요는 없다.

## 6. P1 — 작은 수정에 큰 실행 세션을 다시 보냈다

두 수정에 입력 **791,067토큰**, 3509 전경 입력의 **52.6%**가 쓰였다. 그중 캐시 읽기는 **768,178토큰(97.1%)**이다. 신규 토큰 79만이라는 뜻은 아니지만 국소 문장 수정에 전체 실행 문맥을 계속 재사용한 구조는 분명하다.

서로 다른 세 문제가 겹친다.

1. 두 REWORK JSON 모두 최상위 `repair_scope`가 없고 instruction 문자열에만 `repair_scope="local"`이 들어 있었다. `supervisor_runtime.py:33`의 산문은 필드를 요구하지만 바로 뒤 JSON 예시에서는 빠져 있다. `parse_decision`이 필드를 삭제한 것은 아니다. `supervisor_handoff.py:67`은 최상위 키를 검사하므로 국소 분기가 열리지 않았다.
2. 필드를 바로잡아도 현재 추정식은 첫 수정 cold 25,606 / resume 12,636, 두 번째 25,596 / 15,140으로 resume를 택한다. 캐시 가중치 .1과 chars/2는 가격·지연 실측이 아니다. 새 객체를 쓰더라도 45,066자 시스템 프롬프트와 도구 문맥을 그대로 복사하는 현재 cold 후보는 충분히 작은 수정 문맥이 아니다.
3. 첫 수정은 `response id="10", offset=0, limit=12000`을 요청했지만 `conscious_supervisor.py:553`은 id를 무시하고 offset/limit만 사용해 **8,613자**를 반환했다. 모델이 ID로 특정 블록을 읽는다고 오해하기 쉬운 계약이다. 두 번째에는 offset=10/limit=400으로 **474자**만 받았다. 각 patch의 영수증도 전체 manifest 2,077자였다.

또 최종 검수마다 `coverage.clear()` 후 `read_response(0,12000)`으로 전체 짧은 응답을 다시 넣는다. 기존 `supervisor_review.content_changes`는 외부 산출물의 변경 구간과 읽기 증거 재사용을 지원하지만 이 채팅 응답 블록에는 적용되지 않는다. 최종 응답 6,368자 중 지도 표시 태그가 4,607자였다. 좌표는 표시 자산으로 유용하지만 산술 한 문장 재검수에 반복 첨부할 필요는 없다. 지도 태그는 자동 첨부 경로가 있으므로 그 길이를 최초 모델 출력 낭비 토큰으로 환산하면 안 된다.

**수리:** REWORK를 구조화된 계약으로 검증하고 수정 범위를 명시적으로 전달한다. 수정 문맥은 목표·바뀔 블록·의존 수치/주장·필요한 증거·버전/해시·최소 도구로 만든다. id와 offset의 의미를 도구 스키마와 구현에서 일치시키고 패치 영수증은 변경 블록과 새 버전을 반환한다. 기존 외부 산출물의 변경 검수 계약을 응답 블록에도 확장하되, 변경 문장의 합계·요약 등 의존 주장까지 재검토하고 원문/기준이 바뀌면 재사용을 무효화한다. 지도 원본은 주소로 유지하고 의미 검수에는 경로 요약·수치·해시를 제공한다. 세션 선택은 토큰 종류별 실측과 지연을 비교해 조정한다.

**통과 조건:** `response id=10`이 정확히 그 블록을 반환한다. 변경 없는 블록은 읽기 증거가 이어지고 변경 블록과 의존 수치는 새로 검수된다. 두 산술 패치 재생에서 전체 대화·지도 좌표를 재전송하지 않아도 동일하거나 더 정확한 판정이 나온다. 파싱 누락 때문에 무조건 resume되지 않는다.

## 7. P1 — 긴 검수를 통과한 최종 답변에도 근거보다 강한 표현이 남았다

식당 영업시간은 식당 검색과 블로그 검색 요약으로 조회했으며 특정 여행일의 직접 영업 확인은 없었다. 그럼에도 “9/16 수요일이라 영업합니다”라고 단정했다. 일반 화요일 휴무 패턴과 날짜별 영업 확정은 다르다. 하단에 블로그 정보의 한계를 써도 본문의 단정을 자동으로 정당화하지 않는다.

경로 안내의 교차로까지 거리와 방향을 긴 “직진” 구간처럼 바꾼 설명, 별도로 확인하지 않은 휴게소 접근성도 실제 확보한 근거와 구분해야 한다. 이는 그 휴게소가 반드시 틀렸다는 판정이 아니라 **검수가 확인한 범위보다 확실하게 서술했다는 결함**이다. 이번 감사에서는 영업 여부를 새 외부 조회로 확인하지 않았다.

**수리:** 시간표·날짜·출발점·출처 시각·추정 여부를 주장 옆에 유지한다. 검색 요약, 본문 열람, 당일 직접 확인을 같은 수준으로 취급하지 않는다. 검수의 범위는 숫자 정합성뿐 아니라 근거가 허용하는 표현의 강도까지 포함한다. 이미 맞는 산술을 여러 AI가 다시 계산하는 시간을 줄여 이 확인에 배분한다.

## 9. 권장 수리 순서와 검증 범위

1. **정지 차단:** 전경 파일 I/O 제거, 회상 감시·대기 원인 표시, 느린 볼륨 작업 수명 관리. 실제 오래 걸리는 모델 호출과 실행 전 정지를 구분한다.

검증은 위 네 에피소드의 저장된 증거를 재생해 사실 정확도·주장 근거·사용자 요구 충족을 유지하는지 먼저 확인한다. 그 뒤 foreground wall time, 모델 라운드, 입력/출력/cache 종류, 수정 반복 수, 백그라운드 저장의 유용성을 비교한다. 외부 서비스 재조회나 모델 기어 하향을 절감 성과로 섞지 않는다. 여기의 개선 제안은 아직 구현하거나 절감률을 실측한 결과가 아니다.
