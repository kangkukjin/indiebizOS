# 검토 지시 전달과 Windows 기동 오류 수리계획

2026-11-01. 상태: 사용자 지정에 따라 결함 1과 2 구현, 결함 3은 보류.
계획 기준 정본은 `7ab13978`이다. 구현 범위와 검증은 아래 구현 기록을 따른다.
목적은 검토가 발견한 유효한 문제를 실행에 연결하고, Windows 설치본의 공백 경로에서
백엔드가 기동하도록 하며, 목표 판본 조건을 최종 평가까지 보존하는 것이다.
5651은 01:09:44 종료됐다. 설치와 health 확인은 성공했지만 목표 판본은 미반영 상태다.
구현 전 이 작업의 종료를 확인했고, 다른 세션의 원격 PC 검증 문서 변경은 보존한다.

## 확인된 결함과 근거

### 검토를 촉발한 조건이 사라지면 결과 전체를 폐기한다

에피소드 5651의 최초 계획은 허브 판본 `7ab13978`과 TV1 판본 `996ed3e6`의 차이를
알고 있었다. 00:06:26 중간 검토도 최신 변경 세 개를 먼저 반영하고 C드라이브에서
빌드하라는 REWORK를 냈다. 같은 시점에 하네스는 `decision.stale`로 결과를 폐기했다.
이후 실행자는 이전 코드에 Windows 경로 수정 하나만 적용하여 빌드했다.

`conscious_supervisor.review_conditions()`는 검토 시작 당시의 목표, 오류, 활성 호출,
작업 상태를 묶는다. `review()`와 `_take_pending()`은 그 조건이 달라지면 지시 전체를
전달하지 않는다. `tool_stalled`를 촉발한 활성 호출의 종료는 목표 판본 불일치를 해결한
증거가 아닌데도, 독립적인 지적까지 함께 폐기되는 구조다.

재현 원장: `data/spill/supervision/f6fd2c9a0e994cf388749cfd1b844aa4/events.jsonl`
의 seq 21(목표), 133–135(검토와 폐기), 347(이전 코드 기반 빌드 명령).
이 원장은 로컬 증거이며, 회귀 시험에는 비밀 정보와 실제 원격 부작용을 제거한 최소 사건만 옮긴다.

### Windows 제어자 실행에서 공백이 있는 경로가 분리된다

TV1 로그에 `can't find '__main__' module in '...\\Roaming\\IndieBiz'`가 기록됐다.
정본 `backend/services/control_launcher.py`는 공백이 있는 제어 기반 경로를 포함하는
argv를 Windows에서도 그대로 `os.execve`에 전달한다. TV1의 설치된 Python으로 한
격리 실험에서 원래 방식은 경로를 `sp`에서 끊었고, 인수 인용을 적용한 방식은 공백
경로와 인수를 온전히 전달했다. 원래 방식은 실험 부모 종료 코드가 0이어도 자식 결과가
없었으므로 종료 코드만으로 기동 성공을 판정하면 안 된다.

로컬 후보는 `outputs/tv1-update-20261101/backend/services/control_launcher.py`,
실험은 같은 폴더의 `exec_quote_check.py`다. TV1 설치 파일에는 후보가 반영됐지만,
정본 소스에는 아직 반영되지 않았다. 01:09:06 health가 healthy였고 제어자/worker가
실행됨을 install-2 결과에서 확인했다. 이것은 목표 판본 일치의 증거와 별개다.

### 목표 판본 조건이 완료 기준으로 옮겨지면서 약해졌다

종료 직후 확인한 seq 594의 최종 평가는 설치본이 `996ed3e6`에 경로 수정 하나를 추가한
판본이라고 명시하면서도 ACHIEVED로 판정했다. 허브의 세 커밋은 사용자 push 결정 대기로
분류했다. 그러나 최초 `achievement_criteria`는 실행 앱이 목표 판본임을 확인하도록 했고,
중간 검토도 push 없이 patch/bundle로 반영하는 경로를 이미 제시했다.

최초 framing의 `criteria` 목록은 이를 '판본 재확인'으로 축약해 목표와의 일치 조건을
표현하지 않았다. `supervisor_handoff.criteria_contract()`는 이 목록이 있으면
`achievement_criteria`를 사용하지 않고, 평가자는 목록만 판정하도록 제한한다.
확정된 실패는 목표 조건의 보존과 최종 판정의 불일치다. 이 경로에서 조건이 약해진 것은
확인됐으며, 수정 검증은 framing 생산부터 평가 입력까지 이어서 수행한다.

  검토 교정은 관측 데이터와 구분해 기존 감독 지시 통로로 보낸다.

이번 수리는 오래된 지시를 무조건 전달하는 되돌리기가 아니다. 검토를 시작할 이유와
검토에서 발견한 개별 문제의 유효성을 분리한다.

## 수리 순서

### 1 기존 실패를 재현하는 시험부터 추가한다

실제 모델을 호출하지 않는 동시성 시험에서 검토 중 호출 A가 끝나고 호출 B가 시작되도록
순서를 고정한다. 검토 결과에 A의 정체에 대한 지적과 독립적인 목표 불일치 지적을 함께
넣는다. 현행 구현이 후자까지 폐기하는 실패를 먼저 확인한다. 게시 후 전달 직전에 상태가
달라지는 경우도 별도로 재현한다.

Windows는 실제 실행 파일과 스크립트 경로에 공백을 넣고 자식이 받은 argv 및 실행 표식을
검사한다. 정본 구현으로 실패하고 후보 구현으로 통과하는 결과를 보존한다.

### 2 검토 결과의 수명과 전달을 고친다

수정 위치는 `backend/cognition/conscious_supervisor.py`, `supervisor_runtime.py`의
검토 출력 계약과 파싱, 기존 `supervisor_review.py` 및 전달 경계다. 크기가 커지면
기존 책임에 맞게 모듈을 나누고 층 검사에 등록한다.

1. 검토 호출의 촉발 조건과 개별 지적의 적용 조건을 다른 값으로 보존한다. 지적에는
   식별자, 목표 판본, 관련 호출/문제/근거 참조, 교정 내용, 해결 확인 조건을 둔다.
   별도의 상위 검토 모델을 기본 경로에 추가하지 않는다.
2. 코드는 존재하는 참조와 구조적 판본을 확인한다. '다른 도구가 성공했다'거나
   '기존 대기가 끝났다'는 사실로 독립적인 의미상의 문제가 해결됐다고 추정하지 않는다.
3. 종료된 호출의 재시도 지시는 폐기할 수 있지만, 같은 목표의 독립적인 지적은 남긴다.
   적용 조건을 확정할 수 없으면 '관측 이후 변경됨, 실행 전 재확인 필요'를 붙여
   실행자가 재확인하게 한다. 오래된 명령을 즉시 수행하라는 형태로 전달하지 않는다.
4. 사용자 취소와 목표 변경은 이전 목표에 대한 행동 지시를 무효화한다. 지적별 근거가
   없거나 기존 형식의 검토가 돌아와도 조용히 삭제하지 않는다. 원문과 변경 사실을 보존한
   재확인 통지로 처리한다. 검토 문장이 사용자 권한이나 최신 요청을 덮어쓰지 않는다.
5. 발행, 변경 감지, 지적별 유지/폐기, 전달을 식별자와 이유로 기록한다. 큐 등록이나
   프롬프트 준비를 실제 행동 교정으로 집계하지 않는다. 같은 판본의 지시는 한 번 전달하고,
   근거가 달라진 경우에만 갱신한다. 전달 실패의 재시도는 기존 경계 계약을 따른다.

실행자에게 보이는 형식은 '목표 → 현재 근거 → 불일치 → 먼저 할 일 → 해결 증거'로
간결하게 만든다. 구조화한 지적 하나를 관측 주입과 감독 주입 양쪽에서 반복하지 않는다.
형식 개선은 전달 결함 수리 뒤에 적용하고, 효과는 실제 행동으로 측정한다.

### 3 Windows 기동 수정을 정본에 반영한다

후보의 Windows 인수 인용 처리를 정본에 통합하기 전에 실제 번들 Python에서 확인한다.
공백, 한글, 따옴표, 경로 끝 역슬래시, 빈 인수를 포함한 argv를 검사한다. POSIX 실행과
승인된 제어 기반 선택, 손상된 checkout을 import하지 않는 복구 성질은 유지한다.

회귀 위치는 `backend/test_control_launcher.py`다. 단순히 인용 함수 호출을 확인하는
모의 시험으로 끝내지 않고 Windows 자식 프로세스의 실제 argv를 확인한다. 실제 설치본의
제어자/worker 실행, 실행 경로, health 및 로드된 코드 지문을 확인해야 기동 인수가 끝난다.
오류가 있는데 부모 종료 코드가 0인 사례도 실패로 검출되는지 확인한다.

### 4 목표 조건을 완료 판정까지 보존한다

`supervisor_handoff.py`, framing 생산/검증 경계, `cognitive_eval.py`와
`final_evaluator.py`의 계약을 함께 확인한다. 목표 대상과 목표 판본, 확인 방법을
하나의 완료 기준에서 실행자와 평가자가 공유하도록 한다. 같은 조건을 두 산문 필드에
따로 작성해 한쪽에서 약화시키지 않는다. 평가자가 임의로 합격 조건을 늘리는 방식은 피한다.

기준 간 충돌은 조건을 조용히 생략해 승인하지 않고, 기존 기준 정립 경로에서 해소한다.
설치 성공·healthy·부분 수정의 성공과 목표 판본 달성을 개별 증거로 기록한다.
목표 판본 미일치는 부분 성과로 보고하며 ACHIEVED로 승격하지 않는다. 사용자가 실제로
범위를 바꿨을 때는 그 변경 근거와 판본을 보존한다. push 허가의 부재가 patch/bundle 등
허용된 다른 전달 방법도 불가능하다는 뜻으로 자동 해석되지 않는지 재현한다.

### 5 교정이 행동까지 이어지는지 확인한다

5651의 빌드 직전 상태를 부작용 없는 재생 환경에 구성한다. 목표 판본 A, 원격 판본 B,
종료된 대기 호출, 아직 유효한 버전 불일치 검토를 준다. 성공 조건은 실행자가 소스 일치를
확인하거나 필요한 변경을 반영한 뒤에만 모의 빌드에 진입하는 것이다. 종료된 원격 작업을
중복 실행하거나 이전 버전으로 빌드하면 실패다.

목표 식별자가 다른 보고서 게시나 파일 배포 사례에도 같은 전달 계약을 검사한다.
TV1, 특정 커밋, 특정 빌드 명령을 하네스의 분기 규칙으로 넣지 않는다. 판본 일치의 실제
검증은 해당 배포 절차가 소유하며, git HEAD만으로 작업 트리의 동등성을 주장하지 않는다.

## 검증과 완료 조건

- 검토 중/검토 후 경합, 혼합 지적, 이미 복구한 동일 문제, 취소, 목표 변경, 잘못된 참조,
  중복 전달, API/네이티브 훅 전달을 검사한다. 기존 오래된 지시 차단 시험을 약화하지 않는다.
- Windows 실제 프로세스 시험과 POSIX 회귀, 승인 기반 복구, 설치본 health/지문을 검사한다.
- 판본 미일치이나 설치/health는 성공한 경우, 목표 판본 일치, 정당한 사용자 범위 변경,
  완료 기준 필드 간 충돌을 framing→계약→최종 평가까지 검사한다. 필수 조건이 남아 있는
  상태에서 ACHIEVED가 나오는 이번 사례를 회귀로 고정한다.
- 저장소 규약대로 `scripts/select_tests.py`의 영향 분석과 관련 검사를 수행한다.
  감독은 핵심 경로이므로 허브 판정 또는 영향 불확정이면 전체 non-system 회귀 및 관련
  system 검사를 수행한다. 어휘·층·몸 번들 등 요구 관문도 통과시킨다.
- 동일한 재생 상태에서 수정 전후 지시 전달 여부, 올바른 행동, 중복 부작용, 모델 호출 수,
  전체 입력/출력 토큰 및 경과 시간을 비교한다. 캐시 입력은 비용과 별개로 표시하고,
  토큰 감소만으로 품질 향상을 주장하지 않는다.
- 정본 main에 변경 범위만 커밋하고, 활성 코드가 새 판본인지 검증한다. 현재 진행 중인
  사용자 작업의 최종 결과 및 미해결 버전 차이를 기록한 뒤 활성화 시점을 정한다.
  문서, 커밋, 런타임 반영과 Windows 인수를 각각 구분해 보고한다.

## 별도 조사 항목

96,009→252,175 입력 토큰의 증가와 약 24분 빌드/약 30분 설치는 관측됐다. 그러나 입력
길이가 이번 누락을 일으켰다는 인과관계, 설치 시간의 병목, 압축 설정 변경의 전체 효과는
아직 확정되지 않았다. 이번 확정 결함 수리에 일괄 프롬프트 축소나 압축 설정 변경을 섞지 않는다.

RECORD_REQUIRED/MISSING_FIELD도 실제 발생했다. 반환 봉투를 잘못 읽은 호출과 생산자의
계약 위반은 구분해야 하므로, 현재 관용구 판본을 고정해 경계 시험으로 확인한 뒤 독립적인
계약 결함이 재현되는 경우에만 수리 범위에 추가한다.

## 결함 1과 2 구현 기록

사용자 지시에 따라 목표 판본 완료 계약과 최종 평가 코드는 변경하지 않았다.

검토 모델은 각 지적의 `scope`를 `trigger` 또는 `goal`로 명시한다. `trigger`는 검토를
촉발한 조건에만 의존하는 교정이고 `goal`은 그 조건이 해소되어도 별도로 확인할 지적이다.
`supervisor_interventions.py`는 검토 완료와 실행 경계 양쪽에서 적용 범위를 확인한다.
기존 복구 감지에 해당하는 trigger 지적은 폐기하면서 goal 지적은 보존한다. 사용자 취소와
목표 변경은 여전히 지시를 무효화한다. 새 검토 모델이나 반복 검토 호출은 추가하지 않았다.

범위가 없는 기존 형식, 불완전한 항목, 확인되지 않은 근거는 자동 재실행 지시로 보내지
않고 재확인 통지로 전달한다. 검토 이후 상태가 바뀌었음을 명시하고 이미 끝난 작업의
중복 실행을 금지한다. 항목별 폐기, 큐 등록, 실제 경계 전달을 다른 사건으로 기록한다.
최종 평가의 `criteria`와 ACHIEVED 판정 경로는 이 변경에 포함되지 않는다.

Windows 런처는 CRT exec에 전달하는 각 인수를 Windows 규칙으로 인용한다. POSIX는 원래
argv를 그대로 넘긴다. 제어 기반 선택과 손상된 checkout을 import하지 않는 경로는 유지했다.
TV1의 설치본을 다시 빌드하지 않고 고유한 임시 폴더에서 정본 후보를 검사했다.

검증 결과:

- 기존 구현에서 검토 도중/전달 직전 대기 종료로 독립 지적이 사라지는 실패를 먼저 재현했다.
  수정 후 관련 222개 검사와 전체 non-system 11,544개 검사가 통과했다(9개 건너뜀).
- 실제 제어자 장애·복구와 실행 세대 교체 system 검사 29개가 통과했다. 층·어휘 파생
  검사도 통과했고 Android 몸 번들 매니페스트를 재생성했다.
- 기존 복구 시험의 판정 조건은 유지하고, 검토 응답 fixture에 trigger 범위를 명시했다.
  네이티브 HTTP 훅과 도구 실행 경계에서 교정이 한 번 전달되고 보류된 도구는 실행되지 않음을 검사했다.
- TV1의 실제 번들 Python으로 실행 파일과 스크립트의 공백·한글 경로, 빈 인수, 따옴표,
  마지막 역슬래시를 검사했다. 원래 방식은 부모 exit=0이어도 자식 결과가 없었고,
  수정된 정본 함수는 모든 인수를 원문대로 전달했다.
- 실제 모델 두 번의 격리 호출에서 goal 지적 생성 → 대기 종료 → 지적 전달 → 소스 동기화
  선택을 확인했다. 모델이 선택한 다음 행동은 `sync_source`였고, 원격 작업은 실행하지 않았다.
  이 단일 합성 사례는 장기 작업 성공률이나 시간 개선의 통계적 증거가 아니다.
- 자동 재기동 후 ACTIVE 세대의 감독·검토 프롬프트·지적 전달·제어자 런처 네 모듈이
  정본 소스와 같은 지문임을 확인했다. Windows 전체 업데이트를 재실행한 것은 아니다.

상세 결과는 `outputs/repair5651/`의 검사 로그·JUnit, `windows-probe.json`,
`model-probe.json` 및 `docs/experiments/episode5651_repair_2026_11_01.json`에 기록한다.
