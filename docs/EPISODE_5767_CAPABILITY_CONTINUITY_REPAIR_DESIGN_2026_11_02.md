## 1. 문제와 목표

에피소드 #5767은 전체 언어 체계의 효과를 연구하고 비교 실험·보고서를 만들었지만,
최종 평가에서 필요한 원문이 생략되었다. 평가자는 원문을 요청했으나 요청 형식이 불완전했고,
하네스는 회수 불가로 종료했다. 필요한 원문은 같은 저장소에 남아 있었다.
능력과 증거가 존재해도 발견·호출·관측·판단·완료를 잇는 경계에서 끊길 수 있음을 보여준다.

수리 목표는 다음 네 가지다.

1. 판정에 부족한 저장 근거를 정확히 회수하여 같은 목표·제출본의 검수를 끝낸다.
2. 현재 사용할 수 있는 능력과 적용 조건을 정확하게 발견하고, 필요한 부분만 펼쳐 쓴다.
3. 검증한 해법의 계약·판본·근거를 보존해 다른 입력과 새 부품의 조합에 재사용한다.
4. 진행 중 필요한 관측·제어만 바꾸고 유효한 결과와 완료 효과를 유지한다.

성공 기준은 품질·실제 완료 시간·전체 토큰이다. IBL 사용 비율·저장 개수·검사 개수는
성과를 대신하지 않는다. 기능의 일반적 성질은 구현·인수하고, 성능 향상은 측정한 범위로
보고한다. 미측정이라는 이유로 일반 능력의 개발을 유예하지 않는다.

### 2.3 현재 코드에서 끊기는 경로

`evaluation_input.evidence_requests`는 요청 부재를 None, 정상 요청을 목록,
JSON/참조/기준/판본/범위 오류를 모두 빈 목록으로 반환한다.
`final_evaluator.invoke`는 증거 부족을 recoverable로 분류한 뒤 빈 목록이면 이를 해제한다.
`conscious_supervisor.finalize`는 그 결정에서 회수·실행자 보완 모두 진입하지 못한다.
현재 정책에는 revision 예시가 이미 있다. 예시 한 줄을 더 넣는 것만으로 해결하지 않는다.

또한 `context_sections`가 만든 표시용 JSON 구획의 지문과, 그 안의 실제 도구 원문 ID는
서로 다른 대상이다. 표시 구획의 revision을 실제 원문 revision으로 복사하게 해서는 안 된다.
허용 참조를 만드는 과정에서 같은 ID의 충돌을 덮어쓰거나 setdefault로 숨기지 않아야 한다.

## 4. R0 — 부족한 근거에서 회수·재판정까지

### 4.1 실제 원문 참조를 한 번 구성한다

평가 packet에 있는 허용 근거에서 읽기 전용 참조 투영을 구성하고 표시와 검증이 함께 쓴다.
필드는 기존 source_ref/evidence_id, revision, total, 문자 좌표 단위, 소속 기준, 원문 가용 상태다.
별도 저장소를 만들지 않는다. 표시용 JSON 구획의 지문은 실제 원문 참조와 명시적으로 구분한다.

- 같은 원문·판본의 중복은 기준 관계를 합친다. 같은 ID에 판본/길이가 충돌하면 모호함으로 남긴다.
- 모델에게는 짧은 원문 참조와 실제로 본 범위·생략 여부를 함께 보여 준다.
- 기준 연결은 하네스가 가진 명시 관계 또는 모델이 제안한 관계임을 구별한다. 단어 일치를 의미 증명으로 쓰지 않는다.
- 저장 원문을 가리키지 않는 파일 첨부/표시 구획은 자동 회수 가능한 참조처럼 소개하지 않는다.

### 4.2 요청 파싱과 검증 결과를 구별한다

현재 None/[]의 중의성을 내부 구조 결과로 바꾼다. 결과는 요청 부재, 유효 요청,
정규화한 요청, 형식/참조 오류를 구분하고 항목별 이유를 남긴다. 외부의 기존 요청 형식은 유지한다.

revision이 **생략된 경우에만**, 같은 평가 packet의 허용 목록에서 원문이 유일하고
불변 내용 주소인 TurnStore ID와 판본의 대응이 확인되면 하네스가 판본을 보충한다.
보충한 사실·원 요청·정규화 결과를 기존 감독 원장에 기록한다. 모델 호출은 추가하지 않는다.

명시했으나 틀린 revision, 상충하는 참조, 다른 턴/주체의 ID, 범위 밖 좌표, 모르는 기준은
자동 수정하지 않는다. 숫자 문자열·음수·bool을 문자 좌표로 묵인하거나 범위를 조용히 자르지 않는다.
파일 경로/URL을 허용 원문 ID로 바꾸지 않는다. 회수 시 실제 저장 바이트의 무결성도 다시 확인한다.

JSON 구문 오류와 잘못된 최상위/항목 타입은 프로토콜 오류 값으로 반환한다.
올바른 JSON이지만 객체 대신 숫자·문자열이 있는 반례도 예외로 전체 턴을 죽이지 않는다.

### 4.3 복구는 현재 예산과 소유권 안에서 끝낸다

| 입력/상태 | 동작 |
| --- | --- |
| 유효 요청 또는 안전하게 판본을 보충한 요청 | 같은 TurnStore에서 읽기 → snapshot 대조 → 같은 제출본·전체 기준 재평가 |
| 정확한 범위가 없는 자유 서술, 보완 가능한 요청 형식 오류 | 기존 evidence 보완 인계로 한 번 전달. 실행자가 허용된 저장 결과를 읽고 keep/patch로 확정 |
| 다른 소유자·판본 충돌·원문 무결성 오류 | 자동 회수 거절. 보완 인계에서도 원래 참조의 권한/판본을 완화하지 않음 |
| 원문 소실·취소·예산 소진·이미 전달한 구간만 반복 요청 | UNKNOWN과 구체적 남은 근거·종료 이유 보존. 무한 재시도/자동 승인 금지 |

직접 회수는 같은 판본의 아직 전달하지 않은 구간이 있을 때 현재 작업 예산 안에서 계속한다.
이미 전달한 구간은 차감하며 다른 기준으로 같은 구간을 요청해도 회수를 반복하지 않는다.
정확한 범위가 없는 실행자 보완은 기존 한 번만 허용하고, 직접 회수 뒤 별도 실행자
회수권을 새로 만들지 않는다. 실제 결함 수정 예산과는 기존처럼 구분한다.
혼합 요청에 오류가 있으면 일부 원문만으로 전체 요청이 충족됐다고 하지 않는다.
정규화로 모두 유효해지면 한 번에 읽고, 그렇지 않으면 항목별 오류와 유효 참조를 한정 보완에 넘긴다.
외부 자료의 재수집은 자동 원문 회수와 다르며 기존 실행자 권한·과제 범위를 따른다.

보완 경로를 선택한 뒤 실제 필요한 예산을 계산한다. 직접 저장 원문을 읽는 경로에 실행자
전체 문맥의 재입력 비용까지 요구하지 않는다. 직접 회수는 재평가와 요청 구간의 입력 예산,
실행자 보완은 실행자·재평가 예산을 확인하며 전체 턴의 hard limit은 그대로 지킨다.

`_final_repair_counts`와 기존 review checkpoint를 사용해 보완권 소비를 인계 전에 영속화한다.
회수 뒤 재시작에도 읽은 원문·제출 snapshot·소비 예산을 계승한다. 원샷 평가의 실제 입력·출력은
감독 예산에도 반영하고 checkpoint의 evaluation_budget으로 복원한다. 전역 비용을 이중 청구하지 않는다.
재시작으로 보완 횟수나 이미 전달한 범위를 초기화하지 않는다.
읽기/모델/실행자 보완 중 취소, 제출본 교체, 초안 지문 변경은 승인으로 넘어가지 않는다.

### 4.4 원문을 읽었어도 다시 잘리면 완료가 아니다

회수한 구간은 같은 판본의 근거로 최종 전송 예산에 포함한다. 필수 사용자 요구·기준을 유지하고,
해당 구간이 실제 평가 입력에서 전부 전달됐는지 기록한다. 예산상 일부만 전달했다면 partial을 유지한다.
판정에 요청된 구간을 전달하지 못했을 때 회수 성공만으로 검수 완료를 선언하지 않는다.
선택기가 핵심 반례를 항상 찾는다고 가정하지 않으며, 모든 자료를 상시 전량 첨부하지 않는다.

### 4.5 인수

- #5767 형태의 3요청을 합성 원문으로 재현: revision 누락만 정규화, 실행자 재조사 없이 1회 회수·재평가.

## 5. R1 — 구현된 능력을 정확히 발견한다

`self:task`의 원본 선언 설명과 steer op 소개를 delegation/ibl_run별 현행 지원에 맞춘다.
정적 설명은 지원 종류·핵심 제약·status에서 실제 경계를 얻는 방법을 제공한다.
동적 실행 가능성은 `status.progress.boundaries`가 소유한다. 정적 설명에 호출 좌표를 복제하지 않는다.

가이드, describe 반환, 핸들러 도움말·오류·독스트링을 같은 지원 계약으로 정합화한다.
파생 YAML/tool.json/문서 마커는 `scripts/build_ibl_nodes.py`로만 갱신한다.
현재 계약에 대한 의미 검사와 실제 호출을 사용하며 옛 문구의 금지어 검사를 만들지 않는다.

능력의 조회는 이름·계약·적용 조건을 우선하고 상세 정의는 수정/진단 시 펼친다.
현행 검색 결과에 계약이 빠졌다면 기존 선언/컴파일 투영에서 보충한다. 사설 기능 목록이나
모든 부품 본문을 넣는 상시 프롬프트는 추가하지 않는다. 검색 부재와 실행 불가도 구분한다.

인수: 기본 소개만 받은 모델이 현재 status를 조회해 조향할 수 있는 종류와 불가 조건을 구분한다.
새 어휘·숨겨진 정답 호출·특정 에피소드 문구를 제공하지 않는다. 코드 검사는 실제 지원 등록과 투영을 대조한다.

## 6. R2 — 저장된 해법을 다시 조합할 수 있게 한다

### 6.1 계약과 검증 근거의 소유권

관용구는 function_store의 불변 판본과 function_library의 검사, 스크립트는 기존 등록부의
callable_contract와 script_mutation의 판본/CAS를 유지한다. function_memory는 정의의 참조만 소유한다.
동일한 계약을 검색용 DB나 메모리에 따로 복제해 수정하지 않는다.

저장/검색/describe/호출에서 다음을 연결한다. 이미 있는 칸은 그대로 투영하고 없는 연결만 보완한다.

- 입력·반환 구조, 파이프 자리·기본값, 적용 조건, 외부 효과·실패 계약.
- 실행 가능한 정의의 ID·판본과 의존 부품 판본.
- 실제 검증의 원문 참조, 입력 조건/판본, 검사 결과와 검증 범위.
- 모델이 쓴 의미 설명, 컴파일러가 확인한 구조, 실제 실행이 확인한 성질의 구분.

검증 기록은 기존 capability_history/실행 원장과 provenance의 참조를 사용한다.
기록이 없는 옛 부품은 미검증으로 남기고, 과거 판본의 성공을 새 판본에 승계하지 않는다.
입력 단위·기간처럼 정적 타입으로 증명할 수 없는 조건은 설명과 실제 입력 검사에 남긴다.
Python 내부 계산의 의미를 하네스가 자동 증명했다고 표시하지 않는다.

### 6.2 부품 작성·개정 원칙

안정된 계산과 변하는 정책을 분리한다. 입력 정규화·행 계산·집계/선정이 서로 다른 재사용 경계라면
이를 함수로 나누고 명시 인자로 연결한다. 모든 작은 계산을 무조건 별도 등록하지 않는다.
다음 소비자가 필요로 하는 구조화 값을 반환하며, 큰 원문은 기존 참조·범위 관측으로 제공한다.
모든 부품에 전체 행을 반환하도록 강제하거나 공통 통화의 별도 변종을 만들지 않는다.

총합만 반환하는 기존 API를 조용히 객체 반환으로 바꾸지 않는다. 호환되는 선택 인자/새 부품
또는 새 이름의 판본을 사용하고 기존 소비자 검사 뒤 이행한다. 주문 계산 예시는 합성 인수 자료이며
업무 이름·단위·기간을 코어의 특별 분기로 넣지 않는다.

인수: 기존 총합 소비자의 결과를 유지하면서 상세 계산을 새 최적화/다른 조합에서 사용한다.
원본 부품의 판본을 보존하고 동적 의존·독립 정답으로 실제 재사용을 확인한다.
등록 개수 증가나 모델의 ‘재사용했다’는 설명만으로 성공 처리하지 않는다.

## 7. R3 — 축적·발견·활용을 끝까지 연결한다

기존 통합 증류의 0/1회 선택, 원문 source_id, task/component 범위와 생략 정책을 유지한다.
UNKNOWN인 전체 연구를 성공 절차로 저장하지 않는다. 독립적으로 확인된 부분은 기존 component
규칙을 통과한 범위만 후보가 된다. 증류 모델이 실행하지 않은 새 코드를 만들어 저장하지 않는다.

선택한 source가 참조한 관용구·등록 스크립트의 판본과 적용 조건을 기존 저장·회상 경로에 연결한다.
등록되지 않은 임시 Python 파일은 자동으로 실행 가능한 관용구가 되지 않는다. 재사용할 파일은
기존 명시 등록·검사 경로를 통과해야 하며, 이후 증류는 검증된 호출 원문과 참조를 선택한다.
임의 셸/Python 전체를 자동 추출·등록하는 새 학습기는 이번 범위에 만들지 않는다.

회상 시 현재 활성 상태·정의 판본을 기존 카탈로그에서 해소한다. 오래된 본문이나 성공 기록으로
현재 유효성을 대신하지 않는다. 상세 계약이 필요한 때 기존 조회를 사용하며 모든 턴에 전문을 주입하지 않는다.
연상 점수는 후보 선택이며 실행 적합성·목표 달성의 증명이 아니다.

기존 회상/능력 이력에서 `저장 → 제시 → 선택/호출 → 결과`를 연결한다.
사용 기록에 원래 판본과 실제 호출 신원이 필요하며 이름 언급을 사용으로 세지 않는다.
실패·미사용·새로 작성·저장 생략을 각각 남기되 보상을 위해 저장·재사용을 강제하지 않는다.

인수는 독립 세션의 세 단계다: 새로운 문제 해결·기존 경로 저장, 변경된 입력에서 검색·적합성 판단,
다른 부품과 새 문제 조합. 모델 입력에 정답 부품 이름/본문/파일 위치를 직접 넣지 않는다.
시험 정답·기대값은 시험 소유자만 보유하고, 실행자가 만든 코드는 정식 저장·검색으로 접근한다.
정식 등록 부품 재사용과 자동 증류로 선택된 용례 회상을
각각 확인하고 둘을 합쳐 자동 생성 능력으로 주장하지 않는다.
폐기/개정/단위 불일치 반례에서 옛 부품을 무리하게 적용하지 않아야 한다.

비교군은 같은 환경에서 해당 축적만 제공하지 않은 독립 저장소다. 같은 모델·자료·권한·예산을 쓰고,
처음 만드는 비용과 후속 비용, 캐시·입력 노출 차이를 보고한다. 하나의 전이 성공으로 장기 성장률을 주장하지 않는다.

## 8. R4 — 부분 관측과 제어를 실제 사용으로 연결한다

관측 확대와 실행 변경은 독립 연산이다. 같은 원문의 구간 확대는 원판본을 유지하고,
최신 상태가 필요하면 새 관측을 생성하여 이전 결과와 연결한다. 읽기만으로 실행 인자나 완료 기준을 바꾸지 않는다.

IBL 실행의 조향은 기존 root_task/plan_hash/node_id/revision/ordinal/scope와 입력 지문 계약을 유지한다.
status가 제공한 경계를 선택하며 모델이 scope나 해시를 발명하지 않게 필요한 계약·입력 참조의
조회 연결을 점검한다. 입력 지문 계산은 기존 digest를 사용하고 별도 알고리즘을 만들지 않는다.
관측 투영은 기존 주체·권한·마스킹을 유지하고 비밀 입력의 원문을 새 status 필드로 노출하지 않는다.
현재 값을 아직 해소할 수 없으면 미해소로 표시하며, 잘못된 기대 인자로 적용을 강행하지 않는다.

지원 범위는 선행 설계 §17이다. 순수 이름 함수의 미시작 본문 변경, 자원이 확인된 다음 호출 변경,
병렬 입장 범위와 resume/repair의 적용 기록 계승을 사용한다. 시작한 호출·효과 불명 쓰기·
종료된 scope는 변경/재전송하지 않는다. accepted/applied/효과 반환/목표 달성도 구분한다.

인수에서는 모델이 실제 접수증·status를 읽고, 자료 조건이 바뀐 한 부분을 선택해 조정하고
같은 실행을 완료하게 한다. 테스트가 완성된 좌표/요청 JSON을 대신 주지 않는다.
완료한 쓰기의 영수증은 전후 동일하고 한 번만 발생하며, 바뀐 순수 계산과 최종 결과는 독립 정답으로 확인한다.
충돌·취소·적용 전후 재시작·미확인 효과의 반례도 포함한다. 이행의 보편적 exactly-once는 약속하지 않는다.

텍스트 및 현재 지원하는 음성 구간/판본 관측은 기존 경로로 인수한다. 이미지 임의 영역과
지원하지 않는 매체 좌표는 지원 여부를 명시하고 후속 매체 어댑터 확장으로 분리한다.
텍스트 회수 성공을 모든 멀티모달 상세 관측의 구현 완료로 세지 않는다.

## 9. R5 — 실험 환경과 완료 비용

실험은 실제 사용자 경로를 사용하고, 연구용 제한 실행 환경의 Python 표준 동작·의존성·
파일/출력 규약을 모델 호출 전에 작은 고정 프로그램으로 확인한다. type() 누락 같은 장치 결함은
실험 실패로 분류하고 수정 전후 기록을 보존한다. 운영 권한을 넓히거나 사용자 환경을 바꾸지 않는다.

모델 호출 단위는 판단 경계로 잡는다. 정해진 읽기·계산·저장은 프로그램에 맡길 수 있고,
새 해석·선택이 필요한 때 다음 모델 판단을 받는다. 모든 행동을 원샷 모델 호출로 쪼개는 pilot을
표준 실행 경로로 만들지 않는다. 일괄 프로그램에서도 도구의 실제 실패·부분 효과·취소를 관측한다.

비용은 기존 실행 신원·parent_call_id와 billable_usage 원장에서 집계한다.
주 실행·하위 실험·의식·재규정·검수·복구·증류를 포함하고 같은 호출의 중복 원장 기록은 한 번만 센다.
공급자가 보고하지 않은 호출·미종료 요청은 개수와 사유를 별도로 남긴다.
캐시 읽기는 입력의 부분집합으로 구별하고 문자 수/호출 수를 토큰으로 대체하지 않는다.
병렬 호출 지연의 합을 사용자의 실제 대기 시간으로 보고하지 않는다.

#5767의 보고서 내 실험 비용 582,160토큰 이상은 연구 전체 비용이 아니다.
종료 시 로그의 턴 토큰도 별도 실험·후처리를 모두 포함하는지 신원 조인으로 확인해야 한다.
총비용 보고는 완료된 원장을 읽어 재집계하고, 재집계를 위해 모델 실험을 재실행하지 않는다.
실제 사용자 수정량은 자동 정답 검사와 별개이며 관측하지 않았으면 미측정이다.

각 단계는 정본 변경과 활성 판본을 확인해 별도 완료할 수 있다. A 완료를 전체 설계 완료로 쓰지 않는다.
확인된 결함을 고치는 동안 B/C의 일반 능력 개선을 성능 비교 결과 대기로 유예하지 않는다.
장기 성장률·일반적인 비용 우위·지원 밖 매체의 능력은 이 설계의 유한 완료 조건이 아니다.

### 검증 절차

- 개발 중 `scripts/select_tests.py`가 고른 전이 소비자 검사를 사용한다.
- R0: `test_evaluation_input.py`, 최종평가/감독/TurnStore 및 재개 검사에 실제 실패 분기를 추가한다.
- R1: 원본 선언·실제 describe/지원 등록·가이드의 현 계약을 검사하고 빌드 파생물을 확인한다.
- R2/R3: 기존 function_store/function_library/소비자·script_mutation·회상/증류/이력 검사에
  판본 충돌·옛 근거·폐기·부분 성공·동일 이름 다른 정의 반례를 추가한다.
- R4: `test_ibl_run_control.py`, `test_ibl_function_control.py`, 접수증·자원·resume/repair 검사를 사용한다.
- 회귀 완료 후 관련 실제 모델 인수를 진행한다. 격리 자료와 기존 권한을 사용하고 기대 답은 숨긴다.
  실행 전 모델·건수·시간/토큰 상한을 해당 실험 manifest에 고정한다. 상한 도달은 미완료로 보존한다.
- 종합 회귀 범위는 [REGRESSION_TESTING](REGRESSION_TESTING.md)을 따른다. 허브 변경은 전수 검사한다.
  backend 변경 시 Android 번들, 어휘/설명 변경 시 IBL 빌드와 --check, 층 검사를 수행한다.

실제 모델 검증에서는 검수 승인만 보지 않는다. 결과 정답, 요청된 구간의 실제 읽기,
현재 판본의 부품 호출, 효과 영수증, 재개 신원, 전체 비용을 함께 대조한다.
회귀 성공은 구조적 계약의 증거이며 실제 모델 활용·성능 수치로 대체하지 않는다.

### 배포·호환·복구

새 내부 파싱 결과의 생산자·소비자·교재를 같은 변경에서 연결하고, 옛 영속 checkpoint는
필드 부재를 미관측으로 읽는다. 과거 UNKNOWN/목표 상태를 새 규칙으로 덮어쓰지 않는다.
기존 명시 revision 요청은 계속 엄격 검증하며 새 정규화는 생략된 불변 판본에 한정한다.
관용구/스크립트 계약 확장은 옛 호출자 검사와 기존 판본 개정을 사용한다.

활성화는 변경 책임에 맞는 기존 게시/재기동 제어자를 사용한다. 필요한 중단 뒤 재개는 영속 인계가 맡는다.
퇴행 시 코드 판본을 기존 수리 절차로 복구하되 신규 원장 기록·완료 효과를 지우거나 재실행하지 않는다.
새 기록을 읽을 수 없는 옛 실행기로 진행 중 작업을 강제 이관하지 않는다.

## 11. 대체되는 복잡성과 남기는 경계

- None/빈 목록으로 요청 오류를 뭉개고 즉시 종료하는 경로는 구조화된 원인과 기존 한정 보완으로 대체한다.
- 표시용 지문과 읽기 가능한 원문 판본을 혼용하는 안내는 단일 허용 참조 투영으로 대체한다.
- 실제 구현과 다른 지원 소개는 현행 계약으로 갱신한다. 별도 능력 목록은 만들지 않는다.
- 정의 본문을 반복 복사하는 기억은 기존 정의 참조·계약 투영으로 연결한다.
- 정해진 행동마다 모델을 다시 부르는 실험 절차는 판단 경계가 있는 프로그램 실행으로 대체한다.

원문·판본·권한·효과 영수증·제출 snapshot 검사는 각자 다른 보장을 하므로 유지한다.
정상 작업에 추가 감독/검수 호출을 상시 붙이지 않으며 작업별 어휘 축소·빈도 기반 비활성화로
발견 문제를 해결하지 않는다. 새 언어 문법이나 업무 특화 코어 분기는 필요하지 않다.
