## 3 R0 프로파일 선택의 기본값을 한곳에서 해석

현재 경로는 `api_vocabulary → run_ibl_as_human → 승인 관문 → ibl_routing._package_op → set_package_active → write_state`다. 저장소는 기존 `data/vocabulary/activation.json`을 유지한다.

`vocabulary_state`에 **전달받은 원장 스냅샷에서 프로파일의 저장 선택을 해석하는 순수 함수**를 둔다. 제안 이름은 `profile_selection(state, package_id, profile)`이다. 내부에서 원장을 다시 읽거나 inventory·권한·캐시를 조회하지 않는다. `profile_active_map`과 setter의 변경 여부 판단이 이 함수를 공유한다.

| 프로파일 | 키 미설정 | 키 true | 키 false |
| --- | --- | --- | --- |
| member | true | true | false |
| 기타 비-owner 프로파일 | false | true | false |

owner의 필수 묶음 보호와 유효 활성 판단은 기존 `_is_active_owner`·`require_optional`에 남긴다. 이 작은 수리에서 모든 권한 판정을 하나의 기본값 함수로 합치지 않는다. 프로파일의 실제 이용 가능 여부는 기존처럼 **주인 활성 ∩ 프로파일 선택**이다.

setter는 `LOCK` 안에서 읽은 `before`의 저장 선택과 요청을 비교한다. 주인이 꺼서 유효 권한이 false라고 해도, 회원의 선택이 기본 true이면 회원 끄기는 반드시 명시 false를 기록한다. 주인이 이후 다시 켰을 때도 회원 거부가 남아야 한다. 반대로 주인이 꺼진 상태의 프로파일 켜기는 현재처럼 거절한다. 이는 실제 사용 가능 여부와 미래에 보존할 선택을 구분하는 계약이다.

미설정 true에 켜기를 반복하면 의미가 같으므로 no-op으로 두고 불필요한 명시 true나 revision을 만들지 않는다. 같은 의미의 요청에서 빈 `profiles` 하위 구조를 저장하지 않는다. owner/no-op 응답, member의 `profile` 필드와 `active`가 선택값을 뜻하는 현재 반환 형태는 유지한다. 이번 수정은 조회·응답 불일치를 바로잡으며 새로운 `effective_active` 필드를 공개하지 않는다.

인수는 미설정/true/false × 주인 켜짐/꺼짐 × 켜기/끄기, 알 수 없는 프로파일, 필수 묶음, 잘못된 boolean, 권한 없는 호출을 포함한다. 성공 변경은 선택 키·revision·조회 결과로, 거절은 원장 바이트 무변경으로 확인한다. `test_vocabulary_state.py`, `test_vocabulary_lifecycle.py`에 계약을 두고 기존 회원 기본 허용·격리 시험을 함께 실행한다.

## 4 R1 선택 변경의 저장과 복구를 공통화

권한·프로파일·의존성 검증과 변경할 위치의 계산은 `set_package_active`가 맡는다. `before`, `after`가 정해지면 같은 모듈의 작은 내부 함수 하나가 저장·갱신·복구를 수행한다. 여러 콜백을 받는 범용 저장 API나 새 클래스를 만들지 않는다. owner/member의 공개 성공 응답 조립은 기존 차이를 유지한다.

정상 순서는 다음과 같다.

1. 기존 `LOCK` 안에서 대상·권한·준비·의존성 검증과 no-op 판정을 마친다.
2. 기존 원장 전체를 복사해 선택 위치만 수정하고 `revision = before.revision + 1`로 저장한다. `write_state`의 임시 파일·fsync·원자 교체를 그대로 사용한다.
3. 기존 `invalidate_runtime_caches()`를 한 번 호출한다. 빈 실패 목록일 때만 성공 응답한다.
4. 실패 목록 또는 예외가 나오면 `before`의 내용으로 복구하되 `revision = after.revision + 1`로 저장하고 캐시 갱신을 한 번 더 시도한다.
5. 복구가 성공해도 최초 요청은 실패로 반환한다. 복구 실패는 최초 오류와 어느 복구 단계가 실패했는지 함께 보존한다. 성공으로 완화하거나 무한 재시도하지 않는다.

| 실패 지점 | 기대 상태와 처리 |
| --- | --- |
| 최초 쓰기 전·원자 교체 전 실패 | 원래 선택 유지, 캐시 갱신 없이 저장 오류 전달 |
| 새 원장 저장 후 캐시 갱신 실패 | 원래 선택을 더 높은 revision으로 복구하고 캐시 복구 시도 |
| 복구 원장 쓰기 실패 | 복구 성공을 주장하지 않음. 원래 오류와 복구 저장 오류를 연결해 실패 전달 |
| 원장은 복구했으나 캐시 재갱신 실패 | 원장 복구와 캐시 불확실성을 구분한 실패. 기존 reload/제어 경로로 회복 |
| 동일 요청의 명시적 재시도 | 복구된 선택에 대해 새 변경으로 수행하고 캐시 갱신 재시도 |

원자 교체 후 예외처럼 저장 효과가 불명확한 경우에는 현재 원장의 판본을 다시 확인하고, 자기 `after` 판본임을 확인한 경우에만 복구한다. 더 새로운 판본을 발견하면 이전 전체 스냅샷으로 덮지 않고 충돌로 보고한다. 기존 `LOCK`은 프로세스 내 직렬화다. 외부 편집자와 여러 프로세스를 포함하는 compare-and-swap 보장은 이번 변경으로 생기지 않는다. 새로운 파일 잠금·영속 복구 작업을 도입하지 않는다.

최초 오류를 복구 예외가 가리지 않도록 예외 연결과 단계 설명을 사용한다. 개인 원장 전체를 오류 문자열에 넣지 않는다. 복구 후 no-op 요청은 이전 캐시 복구 실패를 해소했다는 증거가 될 수 없으므로, 실패 당시의 캐시 불확실성은 해당 reload의 성공 확인 전까지 운영 판단에 남긴다. 새 상태 DB로 이 사실을 관리하지 않는다.

검증은 두 프로파일에 동일한 장애 주입 행렬을 적용한다. 캐시 함수의 실패 목록·예외, 최초 저장 실패, 복구 저장 실패, 복구 캐시 실패, 재시도, 서로 다른 선택 변경의 프로세스 내 직렬화를 확인한다. `test_vocabulary_lifecycle.py`를 중심으로 실제 임시 원장 파일의 바이트·revision과 갱신 호출 횟수를 비교한다. owner/member의 권한·의존성 검사를 공통 저장 함수로 우회하지 않는 것도 인수 조건이다.

저장 형식과 기존 선택은 이전하지 않는다. 코드 복구는 가능하지만 사용자 선택을 과거 백업으로 일괄 되돌리지 않는다. R1 롤백 시에도 R0의 공통 기본값 해석은 유지한다.

## 5 R2 핸들러 참조 캐시를 패키지 단위로 축소

`_tool_handlers_cache`의 선언·빠른 반환·등록·무효화 순회·clear 분기를 제거한다. `_tool_to_package_map`, `_package_handlers_cache`, handler mtime, `Program`은 남긴다. 현재 코드의 패키지 캐시 경로를 유일한 참조 취득 경로로 사용한다.

목표 흐름은 **활성 검사 → 현재 도구 매핑 확인 → 패키지 식별 → handler 판본 확인 → 패키지 참조 취득 또는 적재**다. 캐시의 도구 별칭이 현재 매핑 갱신보다 먼저 반환되는 길을 없앤다. 매핑이 바뀌면 새 패키지의 활성 여부도 확인하고, 도구 소유권이 사라졌으면 이전 참조를 반환하지 않는다. 매핑 조회와 활성 검사는 기존 `vocabulary_state`·loader의 경로를 사용한다.

여기서 inventory와 loader 매핑 전체를 통합하지 않는다. 전자는 두 보관 폴더의 소유권·충돌을 다루고 후자는 활성 도구 정의 형식에 대한 별도 해석을 갖는다. 두 집합이 항상 동등하다는 전제로 반환값을 치환하면 범위가 커진다. 우선 참조 캐시만 제거하고 현행 매핑의 입력·누락 동작을 보존한다.

진행 중 호출이 잡은 지역 참조는 캐시 무효화 후에도 유효하다. 캐시를 읽고 다시 dict에서 꺼내는 두 단계 접근을 하지 않는다. `program_runtime.wrap/load/clear_idle`, 게시 판본 선택, namespace·상태 인계·generator/coroutine 수명은 그대로 사용한다. cache clear를 Program 강제 종료나 `sys.modules` 일괄 삭제로 바꾸지 않는다.

동시 초기 적재·clear와 취득의 경합은 별도 인수 대상으로 삼는다. 기존 `Program` 잠금·수명 계약을 먼저 사용하며, 새 전역 잠금이나 프로그램 실행 전체 직렬화를 단순화의 대가로 넣지 않는다. 기존 경계로 해결되지 않는 경합이 나오면 그 재현을 기준으로 참조 게시 경계만 보완하고, 참조 삭제만으로 동시성까지 해결됐다고 기록하지 않는다.

| 상황 | 필수 관측 |
| --- | --- |
| 같은 패키지의 서로 다른 도구 | 같은 Program 참조를 사용 |
| 동일 도구 이름의 소유 패키지 변경 | 다음 취득이 새 매핑을 확인하고 옛 패키지로 실행하지 않음 |
| 패키지 잠재움·도구 제거 | 따뜻한 캐시가 있어도 실행 허용을 우회하지 않음 |
| handler 변경·검증 판본 게시 | 각각 기존 활성화 계약을 따름. 형제 모듈 직접 편집이 자동 게시된다고 주장하지 않음 |
| 실행 중 clear 및 새 취득 | 기존 호출 완주, 다음 호출 올바른 참조. KeyError·중복 상태 손상 없음 |
| 로드 실패·파일 누락 | 기존 오류/None 반환 계약 보존, 낡은 참조로 조용히 대체하지 않음 |

새 시험은 `test_tool_loader.py`에 둔다. 기존 `test_core8_reliability_2026_09_15.py`의 두 캐시 경합 검사는 내부 dict 설정을 새 경계로 옮기되 현재 호출 보존 assertion을 유지한다. `_tool_handlers_cache`를 직접 다루는 `test_vocabulary_state.py`, `test_vocabulary_archive.py`도 실제 차단·초기화 계약으로 전환한다. `test_program_runtime.py`와 선택된 게시·하위 모듈·상태 인계 시험을 함께 실행한다.

성능 위험은 매 호출의 `build_tool_package_map`이 늘리는 정의 파일 stat이다. 동일한 합성 패키지 집합·따뜻한 캐시·호출 횟수로 파일 조회 수와 반복 실행 지연을 전후 비교한다. 기존 `inventory_scope`를 보존하고 별도 도구별 모듈 캐시를 재도입하지 않는다. 유의미한 반복 지연이 나타나면 이 단계의 삭제를 보류하거나 기존 매핑 조회의 중복만 별도로 줄인다. 측정 없이 속도 개선을 완료 조건으로 보고하지 않는다. 데이터 이전이 없어 해당 단계의 코드만 되돌릴 수 있다.

## 6 R3 소비자가 사라진 가이드 경로 제거

대상은 `tool_loader`의 `_build_tool_guide_map`, `get_tool_guide`, `get_tool_guide_path`, `_load_guide_content` 네 함수와 `_guide_content_cache`, `_tool_guide_map`, `_tool_guide_map_built`, `clear_cache`의 해당 상태 정리다.

삭제 전 추적 코드·배포/등록 스크립트·설치 패키지·확장의 직접 참조, 문자열 기반 getattr/import, 문서의 외부 지원 계약을 확인한다. 함수 이름을 찾은 역사 문서나 이 설계 자체는 실행 소비자가 아니다. 지원하는 실제 소비자가 발견되면 해당 호출을 먼저 현재 가이드 공급 경로로 옮기거나 그 함수의 삭제 범위만 보류한다. 외부 설치본을 전수 관측할 수 없다는 이유로 상주 사용량 수집기를 만들지는 않는다.

`_strip_guide_file_field`, 가이드 원문과 `guide_file` 메타데이터는 유지한다. 현재 `PromptBuilder`·`guide_registry`·`ibl_routing.search_guide`가 공급하는 검색·본문·부분 읽기·지문·신선도 계약을 같은 fixture로 비교한다. 도구 스키마에 `guide_file`을 다시 노출하거나 모든 가이드를 프롬프트에 상시 주입하지 않는다.

검증은 `test_tool_loader.py`, `test_guide_registry.py`, `test_prompt_builder.py`와 선택된 가이드 소비자를 사용한다. 소스 이름 부재만을 성공 조건으로 삼지 않고 현재 가이드가 여전히 전달되는지 확인한다. 가이드 파일 삭제나 저장 형식 이전이 없어 국소 코드 복원이 가능하다.

## 7 R4 공개 실행 옵션의 전달 규칙 공통화

첫 단계에서는 모델용 JSON Schema, `IBLRequest`, MCP 함수 시그니처를 유지한다. 두 전달부가 공유할 필드 목록과 순수 투영 함수를 `backend/base/ibl_request_contract.py`에 둔다. base는 FastAPI·MCP·Pydantic·파일·모델을 import하지 않으며, 새로운 모듈의 층은 폴더로 결정한다. `result_read_contract`가 조회 계약을 소유하듯 전송의 작은 공통 규칙만 소유한다.

공개 필드의 기준 집합은 `code`, `edition`, `composition`, `completion`, `repair`, `function_refs`, `value_protocols`, `inputs`, `check`, `code_edits`, `resume`, `reuse`, `budget`, `describe`, `read_result`다. 목록은 현재 선언과 검사로 대조하고 영구 문서 손목록을 새 운영 정본으로 삼지 않는다.

제안 함수 `project_execution_options(values)`는 **이미 입구가 검증한 값**을 받아 새 dict를 만든다. 함수가 승인·신원·입력 타입 검증을 대신하지 않는다. MCP의 검증된 인자 집합과 REST의 모델 dump를 입력으로 쓰면 각 입구에서 필드별 복사 목록을 다시 만들 필요가 없다. `locals()`를 쓴다면 함수 진입 직후에 잡은 인자 스냅샷만 사용하고, 오직 명시된 공개 allowlist를 투영한다. 컨텍스트·토큰·전송 필드 전체를 로그·해시·payload로 복사하지 않는다.

| 값 | 전달 규칙 |
| --- | --- |
| `code` | 빈 문자열을 포함해 그대로 유지 |
| 선택 필드 미설정 또는 None | 현재 두 전달부처럼 생략 |
| `inputs={}`, `resume={}`, `describe=[]` 등의 빈 컨테이너 | None이 아니므로 그대로 전달. 각 소비자의 유효성 판단에 맡김 |
| `check=False` | 현재처럼 생략. 저장 요청에 명시 false 덮어쓰기를 새로 도입하지 않음 |
| `check=True` | True 전달 |
| 컨테이너 내부 false/null/빈 값 | 재귀 삭제·기본값 채우기 없이 보존 |
| 알 수 없는 입력 키 | 각 입구의 현행 검증 계약 유지. 투영 함수가 일반 옵션의 오타를 허용하는 입구가 되지 않음 |

REST의 `extra='forbid'`와 폐기된 `verbose`의 제한적 수용은 유지한다. MCP의 실제 메타데이터 검증과 네이티브 경계의 현재 처리를 각각 시험한다. 모든 표면이 현재 같은 unknown-key 거절을 한다고 가정하거나, 투영 함수가 독자적으로 공개 거절 정책을 바꾸지 않는다.

MCP에서는 공개 옵션을 투영한 뒤 기존 `authoring_request`를 통해 작성 기본 판본을 보충한다. REST에서는 투영에 판본을 새로 주입하지 않는다. 이 차이는 기존 표면 계약이다. 명시 판본·헤더·빈 코드·`$checked`·`$rejected`의 해소를 기존 소비자와 대조한다. `read_result`의 Pydantic 값은 기존 전송 직렬화와 동등하게 처리하며 새 조회 schema를 복사하지 않는다.

표면 고유 필드는 각 입구에 남긴다.

- REST의 `declared_inputs`는 앱 바인딩으로 `_ti`에 별도 연결한다. 승인 값은 기존 권한 컨텍스트에 전달한다.
- `project_id/path`, `agent_id`, `task_id`, `origin`, `surface`, `episode_id`, `parent_run_id`는 현재 신원·실행 문맥 해소를 따른다.
- `ticket`, `completion_channel`, MCP의 `recover/wait/ctx`는 기존 전송·회수·취소 경로가 소유한다. 공개 실행 옵션에 섞지 않는다.
- 네이티브 `system_tools_ibl`의 실행과 저장 원문 해소는 그대로 둔다. `_SAVED_REQUEST_KEYS`는 재개 의미를 가진 별도 집합이므로 전체 공개 옵션으로 대체하지 않는다.

### 실제 값이 도달하는 검사

기존 `test_surface_param_parity.py`의 이름 포함 검사는 유지한다. 여기에 MCP→HTTP→공통 실행과 REST→공통 실행을 대역 HTTP·대역 실행기로 연결해, 각 필드의 구별 가능한 값이 최종 인자까지 도달하는지 확인한다. 네이티브 표면은 같은 의미의 요청이 공통 실행에서 해석되는 결과와 비교한다. 표면의 허용된 차이는 판본 기본값·신원·앱 바인딩처럼 이름 붙여 한정하고, 차이가 난 모든 값을 광범위하게 제거한 뒤 비교하지 않는다.

검사에는 빈 값/None/check:false, 헤더와 판본, 저장된 검사 요청의 생략·덮어쓰기, 부분 수정, resume/reuse, 조회와 실행의 구분, 공개 필드로 신원·승인 값을 넣으려는 시도, recover의 기존 작업 재조회와 실행 중복 방지를 포함한다. pure helper는 `test_ibl_request_contract.py`에 둔다. 세 표면의 실제 전달 계약이 인수 기준이며 helper 출력만 맞추는 시험으로 대신하지 않는다.

첫 단계의 성공은 두 전달부의 필드별 분기가 한 규칙으로 모이고 기존 값·권한·재개 의미가 보존되는 것이다. 세 선언의 완전 단일화는 이 인수 후 판단한다. 동적 MCP 시그니처·범용 schema 생성기·새 request 객체 공개는 이번 구현 범위에서 제외한다. R4만 되돌릴 수 있도록 공개 JSON과 저장 원문 형식을 바꾸지 않는다.

## 8 추가 실행 비용과 평가 근거 회수

에피소드 5808은 본 실행 28라운드 후 실패 사건 3건을 이유로 후속 9라운드를 수행했다. 원문을 대조하면 세 건은 오류 문자열을 포함한 코드의 오탐이 아니라, 없는 경로를 읽은 `sed`/`rg`와 zsh glob 실패가 포함된 셸 호출이다. 뒤에 올바른 소스를 읽었어도 사건에는 해소 판단이 연결되지 않았다. `cognition.task_continuation` 사건은 `reason=observed_failure`, `incident_count=3`을 기록한다.

이는 [실패 복구 설계](FAILURE_RECOVERY_REPAIR_DESIGN_2026_11_04.md)의 §4가 명시한 비용과 양립한다. 같은 도구의 후속 성공만으로 이전 실패를 지우거나, 최종 응답이 있다는 이유로 모든 실패를 해소하면 원래 미완료 누락 문제가 되살아난다. 이번 단순화 구현에 후속 실행 일괄 비활성화나 새 판단 모델을 넣지 않는다.

후속 개선의 조사 순서는 다음과 같이 제한한다.

1. 기존 감독 검토가 열렸는지와 `incident_assessments` 전달·반영 여부를 확인한다. 유효한 현재 판본의 판단이 있었는데 무시됐다면 기존 소비 연결을 수리한다.
2. 판단 자체가 없었다면 실제 미해소 업무, 다른 경로로 회복한 업무, 정상 빈 검색을 구분해 기존 정책의 추가 호출 비용과 미완료 누락을 비교한다.
3. 그 근거로 기존 경계의 선택적 판단 전달이 필요한지 별도 설계한다. 모든 셸 호출에 구조화 보고를 강제하거나 단순 exit 1을 성공으로 바꾸지 않는다.

최종 평가는 첫 회에 근거 원문 부족으로 UNKNOWN을 반환했고, 요청한 세 원문을 회수한 다음 ACHIEVED가 됐다. 회수 검증은 valid이고 실제 회수 사건도 있다. 이를 아직 고장 난 근거 회수로 재분류하지 않는다. 평가 입력 선택 최적화는 기존 구현의 인과 측정과 함께 다뤄야 하며, 검수 제거로 비용을 낮추지 않는다.

기록된 토큰 4,821,106에는 캐시 읽기 4,313,472가 포함된다. 이 값은 이번 네 후보 수리의 예상 절감량이 아니다. 실제 효과를 측정할 때는 동일 과제·모델·기어·캐시 조건에서 전체 턴, 실행, 감독, 평가, 후처리를 구분한다.

## 9 검증과 반영

구현 중에는 [회귀 규약](REGRESSION_TESTING.md)의 `scripts/select_tests.py`로 전이 소비자를 고르고, 변경한 계약의 실패를 국소 재확인한다. 어휘·캐시·공개 실행 경계를 다루므로 통합 단계에서 기본 종합 회귀와 관련 system 묶음을 수행한다. 선택기가 허브를 이름 부르거나 영향·격리가 불명확하면 전수를 실행한다.

관련 system 묶음은 어휘 활성·배포의 `test_vocabulary_archive.py`, `test_vocabulary_bundle_split.py`, 실행 경계의 `test_python_libraries.py`를 포함한다. 재기동·동시성·프로세스 수명 구현까지 변경한 경우 해당 재기동 시험을 추가한다. 기록만 작성하는 이번 설계에 이 제품 회귀를 실행한 것으로 표시하지 않는다.

backend 구현 변경 시 Android 몸 번들을 재생성한다. 빌드 정합성·층/그림자·파일 크기 등 기존 관문을 통과시킨다. 교재·설명에 반환 계약을 적은 곳은 같은 변경에 맞추며, 파생 마커와 tool.json은 손으로 수정하지 않는다. 새 공개 어휘는 필요하지 않다.

활성화는 현행 자기수리/외부 제어자의 후보 검사·반영·재기동 계약을 따른다. R4의 `mcp_server.py`는 별도 프로세스이므로 백엔드 활성 확인만으로 완료하지 않고 새 MCP 프로세스의 실제 전달도 확인한다. `/packages/reload`가 임의 backend·MCP 소스를 모두 활성화한다고 가정하지 않는다. keeper 표식은 수동 조작하지 않는다.

완료 기록은 단계별 기준 판본, 변경 파일, 검사 범위·결과, 코드 반영과 활성 판본, 필요한 실제 호출 확인, 남은 한계로 남긴다. 데이터 이전은 없으며 사용자의 원장·패키지 선택·가이드 원문을 정리 목적으로 삭제하지 않는다. 캐시 삭제의 지연과 실제 모델의 토큰 절감은 측정한 범위만 보고한다.

## 10 설계 단계 확인 기록

- 기준 HEAD에서 현행 함수의 메모리 격리 실험을 다시 실행했다. 회원 첫 끄기의 무저장·조회 true, member 캐시 실패 후 무복구·재시도 갱신 생략, 도구 캐시의 매핑 갱신 우회를 재현했다.
- 공개 옵션 선언·두 전달부·판본 기본값·원장 원자 저장·Program 수명 경계를 읽고 설계에 반영했다. 운영 원장의 실제 변경이나 프로그램 활성화는 수행하지 않았다.
- 연구 보고서와 코드 참조, 재현 자료를 이 문서에서 연결했다. 후속 구현의 성공 조건과 현재 재현된 결함을 구분했다.
- 제품 pytest·새 구조의 성능 측정은 구현 단계의 인수 사항이다. 이 설계의 존재를 수리 적용 완료로 취급하지 않는다.

## 11 구현과 검증 기록

R0·R1은 `profile_selection`을 조회와 변경에서 공유하고, owner/member의 저장·캐시 갱신·복구를 `_commit_selection`으로 모았다. 원자 교체 전 실패, 교체 후 실패, 원장 충돌, 복구 쓰기·캐시 오류를 구분한다. 두 프로파일의 실패·재시도와 선택 행렬, 동시 변경은 임시 원장으로 검사했다.

R2·R3은 도구별 핸들러 별칭 캐시와 옛 가이드 로더 네 함수를 제거했다. 매핑은 기존 재고·원장 스냅샷의 동일성을 확인해 재사용하고 변경 시 지역 dict를 완성한 뒤 게시한다. 재생성과 clear는 기존 어휘 잠금을 공유한다. 이미 취득한 매핑과 실행 중 Program 참조는 보존한다. handler 파일 소실은 다음 취득에서 낡은 참조를 반환하지 않도록 무효화한다. 실제 가이드 공급 경로와 메타데이터는 유지했다.

R4는 `base/ibl_request_contract.py`의 순수 투영으로 MCP와 REST의 반복 복사를 대체했다. 스키마·입구 검증·권한·전송·저장 요청 해소는 각 기존 경계에 남겼다. 실제 MCP 인자 모델→MCP→HTTP 모델→REST worker→공통 실행 인자의 전달을 검사하고 표면의 판본 기본값 차이도 보존했다.
