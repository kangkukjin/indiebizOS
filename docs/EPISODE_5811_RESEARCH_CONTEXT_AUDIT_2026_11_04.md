# 에피소드 5811의 자료 전달 비용과 개선안

2026년 11월 4일. 조사 및 제안 완료. 운영 코드 변경과 모델 비교 실행은 하지 않았다.

메모리 품귀 연구의 비용은 **누적 실행 문맥의 반복 입력**과 **검수 근거의 불균형한 배분**에서 커졌다. 실행은 매번 더 길어진 문맥을 40라운드 동안 입력했다. 검수는 주소·주장·표시 정보를 여러 형태로 전달하면서, 실제 인용 원문에는 별도의 작은 한도를 적용했다. 먼저 같은 근거를 한 번만 표현하고 필요한 원문을 충분히 전달해야 한다. 조사량이나 반대 근거를 줄이는 방식은 권하지 않는다.

정본의 코드와 당시 활성 세대의 관련 파일 여섯 개가 같음을 확인했다. 기준 커밋은 `1721f48b8527b9e85557c527482a1bd68644b13f`이다. 분석 대상은 `world_pulse.db`의 에피소드 5811, 실행·평가의 실제 CLI 롤아웃, 감독 저장소, 연구 자료실의 읽기 영수증이다. 원문·개인 지침은 보고서나 집계에 복제하지 않았다.

재현: `.venv/bin/python3 scripts/research_episode5811_context.py`.
수치 정본은 [집계 JSON](experiments/episode5811_context_audit_2026_11_04.json), 재현기는 [읽기 전용 집계 스크립트](../scripts/research_episode5811_context.py)다. DB·롤아웃·증거 저장소는 읽기 전용이며 출력 JSON만 쓴다.

## 실행에서 같은 문맥을 계속 입력했다

롤아웃의 40개 `token_usage_record.usage`를 합산하면 에피소드의 실행 집계와 일치한다. 누계 필드를 매번 합산한 계측 오류가 아니다.

- 첫 모델 입력은 **48,751토큰**, 마지막은 **228,227토큰**, 라운드 평균은 **146,079토큰**이었다.
- 이 실행의 롤아웃에는 문맥 압축 사건이 없고 입력이 계속 증가했다.
- 한 번 들어온 자료·도구 결과·지침이 후속 판단 때마다 문맥에 남았다. 캐시가 중복 계산을 일부 덜어도 전체 입력 토큰의 반복 계수는 남는다.
- 따라서 실행 토큰을 줄이려면 첫 입력의 크기, 도구가 추가하는 크기, 판단 왕복 수, 이전 결과를 유지하는 범위를 함께 봐야 한다.

실행 도구 응답의 실제 표시 문자열을 분해한 값은 다음과 같다. **문자 수이며 토큰 수가 아니다.**

| 표시 구성 | 문자 수 | 비고 |
| --- | ---: | --- |
| IBL JSON 30개 | 304,705 | 본문·액션 설명·주소·진단·재개 정보 포함 |
| 상황 관측 30개 | 106,639 | 모두 baseline |
| 가이드·셸·시간 표시 등 | 49,503 | 다른 도구 결과와 포장 문자열 |
| 합계 | 460,847 | 원문 저장소 크기가 아닌 모델에 표시된 문자열 |

상황 관측만 표시 문자열의 **23.1%**다. 144회 관측 항목에 고유 관측 ID는 49개였다. 반복은 실제로 있지만 전달 실패나 문맥 소실을 무시하고 삭제할 수 있는 정보라고 단정하지 않는다.

IBL JSON의 필드 값 직렬화에서는 `value` 220,938자 외에 `result_ref` 11,918자, `continuation` 10,282자, `_preview` 10,041자, `_hint` 4,303자 등이 확인됐다. 키·구분자와 다른 필드도 있으므로 이 값들을 전체 응답의 정확한 분할로 해석하지 않는다. 액션 정의나 읽기 범위처럼 필요한 설명과 매번 같은 사용법을 나눠야 한다.

책임 위치는 [모델 결과 표시](../backend/cognition/model_result_view.py), [MCP 상황 전달](../backend/surface/api_supervision.py), [상황 전달 확인](../backend/base/situation_delivery.py)이다. `situation_context()`는 불투명한 MCP 소비자의 수신을 확인할 수 없어 매번 `baseline=True, compact=True`를 요청한다. 이는 의도적인 안전 계약이다. API 소비자의 확인된 커서처럼 취급하거나 다음 호출이 왔다는 이유만으로 수신 완료를 조작하면 안 된다.

### 같은 본문이 두 필드로 표시된 구체 사례

첫 TrendForce 자료실 읽기의 저장 결과에서 `value.text`와 `value.blocks[0].text`는 같은 7,978자 본문이다. 표시 단계에서는 각각 5,533자와 5,496자를 보여줘 같은 앞부분에 예산을 쓰면서 뒷부분이 빠졌다. 실행자는 뒤에 `read_result`로 해당 본문의 5,400자 이후를 추가 회수했다.

`_fold_twin_fields()`는 동일한 목록·객체, 또는 명시된 `items` 미러를 다루지만 이 문자열과 블록 본문의 관계를 포괄하지 못한다. 단순히 출력 한도를 더 줄이면 이런 재독이 늘 수 있다. **판본·문단 메타데이터를 보존하면서 동일 본문을 한 번만 보이는 것**이 먼저다. 전체 프로그램의 실제 추가 왕복 절감량은 모델 비교가 필요하다.

## 검수는 큰 입력 안에서 필요한 원문을 잘랐다

첫 검수의 실제 사용자 메시지는 **298,385자**였다. `[GoalEval] prompt=256369자`는 제공자 선택·최종 포장 전 길이라 실제 전송량과 다르다. 최종 포장 과정에서 구획 메타데이터와 시스템 프롬프트 등이 더해진다. 두 번째 실제 메시지는 **325,919자**였다.

| 첫 검수 메시지 구성 | 문자 수 |
| --- | ---: |
| 원문 회수 주소 목록 176개 | 58,802 |
| 주장별 구획 57개 | 64,670 |
| 연구 인용 구획 | 62,511 |

| 실행 액션 원장 | 2,659 |

표는 범주별 진단이며 전체의 완전한 분할은 아니다. 나머지에는 기준·초기 및 현재 계획·최종 응답·역할 지침 등이 있다. 주장 구획에는 산출물에 이미 있는 주변 문장과 경로·해시·좌표가, 주소 목록에는 같은 해시가 ID와 판본 등으로 반복된다. 동일 원천이 회수 주소, 도구 근거 목록, 구획 메타데이터로 여러 번 나타난다.

더 중요한 문제는 예산의 중첩이다.

1. `ResearchLibrary.citation_review()`가 `allocate()`의 기본값인 **전체 16,000자, 항목당 최대 2,400자**로 인용 본문을 먼저 잘랐다.
2. 자료 52곳에서 이미 읽은 인용 구간의 원문은 총 **24,472자**였다. 33곳이 부분 인용이 됐다.
3. 그 뒤 `EvaluationPrompt.prepare_request()`는 전체 문맥 한도 안에 들어간다는 이유로 100개 구획을 모두 전달했다. 이 단계의 `complete`는 앞 단계에서 만들어진 구획 전체라는 뜻이며 **인용 원문 전체를 읽었다는 뜻이 아니다**.
4. 결과적으로 큰 주소·주장 목록은 전부 들어가고, 핵심 원문의 부족은 해결되지 않았다.

### 재검수의 직접 원인

평가자는 Micron ¶30·¶33·¶44의 근거가 부족하다고 판단했다. 각 원문은 849·869·956자인데 **모두 348자만** 인용 구획에 들어갔다. 첫 평가가 `UNKNOWN`을 반환한 뒤, 하네스가 이미 저장된 읽기 결과 두 건, 합계 26,434자를 0.010초에 회수했다. 새로운 검색이나 조사 실행은 없었다. 두 번째 평가에서 `ACHIEVED`가 됐다.

이는 조사자가 자료를 못 얻은 실패가 아니라, 확보한 증거를 검수자에게 충분히 전달하지 못한 실패다. 기존 복구는 정상 작동했다. 줄여야 할 것은 이 불필요한 첫 불확실성과 전체 재전송이다. 두 번째 검수의 관측 비용은 **151,312토큰·15.9초**이나, 원문을 더 실은 첫 평가의 비용과 행동도 달라지므로 이를 그대로 절감 보장치로 쓸 수 없다.

## 정보 보존을 확인한 재포장 실험

저장된 첫 검수 입력에서 모든 필드 값과 본문 내용을 보존한 채, 반복 문자열을 사전 참조로 공유하고 메타데이터 열 이름을 한 번만 표기했다. JSON 공백은 정규화했다. 원문을 요약하거나 중요한 주장만 추리는 분류기는 사용하지 않았다. 복원 결과의 객체 동등성을 검사했다.

| 동일 입력의 표현 | 문자 수 | 최초 대비 |
| --- | ---: | ---: |
| 실제 첫 검수 사용자 메시지 | 298,385 | 기준 |
| 필드·내용을 보존한 재포장 | 240,051 | 19.5% 감소 |
| 재포장에 이미 읽은 인용 구간 52곳 전체를 추가 | 269,529 | **9.7% 감소하면서 원문 확대** |

마지막 행은 기존 부분 인용을 그대로 두고 완전한 읽기 영수증을 추가한 보수적인 계산이다. 모든 영수증의 자료 ID·위치·추출 판본·길이를 DB와 대조했다. 이 방식은 표현 중복을 줄이면 원문을 더 넣을 공간이 있다는 증거다. 새로운 형식의 모델 이해도·실제 토큰·시간·연구 품질은 측정하지 않았다. 문자 감소율을 토큰 절감률로 보고하지 않는다. 연구용 재포장 형식을 그대로 새 운영 프로토콜로 도입하자는 제안도 아니다.

## 권장 개선 순서

### 먼저 검수의 원문 배분과 중복 표현을 함께 고친다

기존 `EvaluationPrompt`를 전체 배분의 소유자로 유지한다. 인용 구성 단계가 고정 16,000자에서 원문을 되돌릴 수 없게 자르지 않도록, 읽기 영수증과 원문 참조를 배분기까지 전달한다. 예산이 허용하면 인용된 문단 전체를 먼저 넣고, 큰 자료는 주장과 연결된 여러 구간으로 나누되 날짜·단위·조건·부정·반론이 분리되지 않게 한다. 원문이 크면 전부 넣는 정책이 아니라 **선택 범위와 미확인을 보존하는 하나의 배분**이 필요하다.

자료 ID·판본·위치와 복구 주소는 기존 증거 저장소 한 벌로 연결한다. 각 구획이 같은 긴 주소·해시·회수 설명을 반복하지 않도록 표시 구조를 공유한다. 산출물 본문이 이미 들어가면 `claim_context`의 반복 대신 파일 판본과 정확한 범위로 연결하고, 생략된 산출물 구간에 속한 주장은 필요한 본문을 함께 보여준다. 메타데이터의 복구 가능성과 실제 모델 열람을 계속 구별한다.

이 개선은 전체 토큰의 가장 큰 부문은 아니지만, 캐시 제외 입력이 크고 이번 재검수의 직접 원인을 해결한다. 원문을 덜 읽도록 유도하지 않아 우선 적용하기 좋다. 기존 `UNKNOWN`과 판본 고정 회수는 유지한다. 별도의 평가 모델·새 증거 DB·새 감독자는 필요하지 않다.

### 다음으로 실행 결과의 본문 중복과 반복 안내를 줄인다

`model_result_view`의 기존 표시 경로에서 본문과 블록의 동일성을 원문 기준으로 확인해 한 벌만 보여준다. 저장 데이터와 어느 경로로든 참조하는 계약은 유지한다. 성공 응답마다 반복되는 장문의 재사용 방법은 도구 설명에서 소유하고, 응답에는 실제 인자·상태·원문 위치·변화·복구에 필요한 내용만 남긴다. 마스킹·부분 실패·원문 부족·외부 효과 미확인처럼 판단을 바꾸는 경고는 항상 보여준다.

상황 전달은 별도 문제다. MCP에서는 수신·문맥 유지 확인이 없으므로 현재의 안전한 baseline을 유지하면서, 반복된 불변 근거의 설명과 상세 메타데이터를 작은 참조로 줄이는 것이 첫 단계다. 변경·충돌·미확인 효과·부분 완료는 전면에 남긴다. 전달된 관측을 추후 문맥에서 확인할 수 있는 제공자 경계가 생겼을 때만 기존 커서 계약으로 delta를 사용한다. 단순 서버의 마지막 전송 기록은 소비자의 기억 증명이 아니다.

본문 표시와 상황 표시를 함께 측정해야 한다. 한쪽의 절약이 다른 쪽의 재독·실패로 이동하면 성공으로 세지 않는다.

### 판단 사이의 불필요한 왕복과 문맥 유지 범위를 줄인다

독립 자료 읽기는 기존 `&`·`table:each`로 묶되, 첫 자료의 결과가 다음 탐색을 결정하는 구간은 판단 경계로 남긴다. 이미 여러 병렬 획득을 사용한 이 사례에서 모든 검색을 한꺼번에 미리 정하는 방식은 적절하지 않다. 가이드가 요구하는 계약을 읽는 일을 제거하기보다 필요한 절을 직접 찾고, 파일 존재·링크·해시 확인 같은 결정적인 후처리를 한 번에 구성한다.

긴 실행의 작업 문맥에는 현재 질문, 지지·반대 근거의 판본과 구간, 잠정 판단, 미해결, 다음 판단에 필요한 원문을 남긴다. 오래된 검색 발췌·정상 도구 포장 전체는 자료실 참조로 회수할 수 있게 한다. 기존 연구 질문·계획·자료실을 사용하고 새 요약 원장을 만들지 않는다. 단, 현재 CLI가 이미 보유한 과거 도구 메시지를 MCP 서버가 삭제할 수 있다고 가정하지 않는다. 그 제공자 경계에서 지원되는 문맥 교체·압축을 확인한 뒤 별도 단계로 진행한다.

문맥을 자주 새로 만들면 캐시가 깨지고 오히려 캐시 제외 입력이 늘 수 있다. 전체 토큰과 대기시간 외에 캐시 제외 입력, 회수 횟수, 원문 재확인 누락을 함께 측정한다. 기존 기록만으로 적정 압축 시점을 고정할 수 없다.

### 계획 단계는 시간 절감 후보로 별도 검증한다

첫 규정 뒤 별도 `plan_completion` 호출이 33,153입력·4,987출력, 141.6초를 사용했다. 현재 `research_planning.prepare()`는 기존 입력에 연구 가이드·규정·계획 문맥을 붙이고, 감독 역할 프롬프트도 다시 사용한다. 계획 호출에서 수집하지 않으므로 두 호출 사이에 외부 관측으로 바뀐 판단은 없다.

같은 권한·기준 아래 최초 규정에서 계획까지 작성하는 방식, 또는 두 단계를 유지하되 두 번째 입력을 사용자 원문·확정 규정·계획 가이드·필요한 이력으로 좁히는 방식을 비교할 수 있다. 계획을 짧게 만드는 것은 조사 질문·대안·멈춤 조건을 없애는 것과 다르다. 일반 작업에 연구 가이드를 상시 넣으면 다른 작업의 비용이 늘므로 기존 연구 분기 안에서만 다룬다. 계획 저장 전 수집 금지와 `keep/revise` 및 사용자 정정 계승은 유지한다. 141.6초 전부를 없앨 수 있다고 추산하지 않는다.

## 품질을 유지하는 검증 조건

이 개선의 성공은 짧은 입력이나 `ACHIEVED` 한 번으로 판단하지 않는다. 같은 자료 스냅샷·모델·사용자 요구·달성 기준에서 다음을 확인한다.

| 검증 층 | 통과 조건 |
| --- | --- |
| 참조와 표시 계약 | ID·추출 판본·파일 해시·좌표가 일치하고, 표시 생략과 읽기 부족이 구별된다. 다른 주장·판본·긍정과 반박을 잘못 합치지 않는다. |
| 근거의 실제 전달 | 5811의 Micron ¶30·¶33·¶44가 충분한 문맥으로 처음 검수에 들어간다. 읽기 이력을 새로 만들어 통과시키지 않는다. |
| 판정의 엄격성 | 수치·단위·발표일을 의도적으로 틀리거나 반대 근거를 누락한 비교본을 승인하지 않는다. 주소만 있거나 유료 본문을 안 읽은 경우 미확인을 유지한다. |
| 연구의 내용 | 품목 구분, 수요와 공급의 인과, 경쟁 설명, 상충 전망, 조건부 시나리오, 다음 판별 신호가 유지된다. |
| 복구 | 메시지 전달 실패·문맥 압축·재개·판본 변경·부분 실패에서 필요한 baseline과 원문을 다시 얻는다. 완료된 외부 행동을 중복 실행하지 않는다. |
| 효율 | 요청부터 검수 완료까지의 경과, 입력·출력·캐시·후처리 총토큰, 재독·검수 횟수를 함께 비교한다. 절감 때문에 재실행이 늘어난 경우 포함한다. |
| 범용성 | 메모리 연구 외 상충 자료가 있는 연구, 코드 검사 결과, 긴 표·문서 검수에서도 확인한다. |

현재 측정한 것은 원래 실행 비용과 입력의 재포장·자료 보존이다. 운영 반영과 위 모델 비교는 후속 구현의 인수 조건이다. 추천 순서는 **검수 배분 통합 → 실행 표시 중복 제거 → 제공자별 문맥 관리 → 계획 단계 비교**다. 앞의 두 단계는 기존 책임을 고쳐 정상 경로를 작게 만들며, 뒤의 두 단계는 모델 행동과 문맥 연속성에 더 큰 영향을 준다.

## 관련 연구와 적용 범위

Anthropic은 도구 결과와 대화가 누적되는 문맥을 자원으로 보고, 도구 결과 정리와 필요한 정보 회수를 설계하는 접근을 설명한다. 이 보고서의 원문 보존·표시 축소 방향을 뒷받침하지만 IndieBiz OS의 절감률을 증명하지는 않는다. [Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents).

Liu 등의 연구는 다문서 질의와 키 검색에서 관련 정보의 위치에 따라 장문맥 성능이 달라짐을 보였다. 자료를 많이 넣었다는 사실만으로 충분한 검수를 보장할 수 없다는 검증 설계의 근거다. 5811의 현재 모델에서 같은 위치 효과가 원인이었다고 추정하지 않는다. 이번 재검수의 직접 증거는 실제 인용 구간의 누락이다. [Lost in the Middle](https://arxiv.org/abs/2307.03172).
