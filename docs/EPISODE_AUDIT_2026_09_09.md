## 이번에 고친 네 경로

### 1. 네이버 지역 검색이 다른 동을 고름

ep3223의 `region:"전주 장동"` 조회가 완산구 색장동으로 연결됐다. 현재 API에 같은 질의를 읽기 전용으로 보내 재현했다. `/api/search`는 색장동(`5211114400`)을 첫 번째, 덕진구 장동(`5211313200`)을 두 번째로 반환했고, 기존 코드는 조건 없이 첫 번째를 골랐다.

`tool_naver.py`는 검색 결과의 주소 성분을 대조한다. `전주`→`전주시` 같은 시·군·구·도 약칭은 허용하고 동 이름은 정확히 맞춘다. 맞는 지역이 하나일 때만 조회하며, 불일치나 동명이면 후보와 오류를 반환한다. 잘못된 위치의 0건을 성공으로 보고하지 않는다. 단지 검색 경로는 유지한다. 수정 후 실제 검색에서도 덕진구 장동 코드가 선택됨을 확인했다.

### 2. 단일 할당의 산문·JSON 목록이 턴에 저장되지 않음

ep3219의 원장 전달을 재검사하다 추가 재현했다. `$값 = [self:read]{path:...}` 한 문장으로 목록 또는 텍스트를 읽으면 첫 호출은 내용을 반환했지만 다음 `$값`은 미할당 오류였다. 딕셔너리 봉투에만 변수를 붙이는 단일 액션 경로가 원인이었다.

할당은 한 문장이더라도 기존 workflow 실행기로 보내 `_live_vars`를 받는다. 원본 값과 성공 여부를 한 경로에서 처리하며 별도의 단일 할당 저장 추정을 없앴다. 빈 목록·빈 문자열·0·false·일반 산문도 보존하고 실패한 read는 저장하지 않는다. 첫 read 뒤 원본 파일을 삭제한 회귀에서도 다음 호출이 값을 재사용했다.

### 3. 성공한 관용구에 무관한 턴 오류를 실패로 재귀속

ep3219의 `[fn:직전보고서찾아읽기]`는 성공했다. 뒤에서 `$원장.items`가 실패하자 종료 로그에는 같은 관용구의 호출 실패가 기록됐다. 함수 실행 자리에서 이미 성공을 기록하는데, 턴 종료의 관용구 집계와 top-1 집계가 전체 턴 판정을 다시 적용했다. 성공도 중복으로 셀 수 있었다.

이름으로 실행한 저장 관용구는 실행 자리의 몸 판정만 한 번 기록한다. 성공 시 그 몸의 실행시간을 기록하고, 턴 전체 토큰을 함수 비용으로 덮어쓰지 않는다. 종료 시에는 같은 이름을 두 집계에서 제외하고 회상 캐시를 비운다. 몸 자체의 실패는 계속 실패로 기록된다. 과거 누적 카운터는 호출별 정정 원장이 없어 임의로 역산해 수정하지 않았다.

### 4. 직방 결과가 상세 숫자·식별자를 버림

ep3223의 직방 결과에 `price`를 거는 필터는 없는 열을 거절한 정상 검사였다. 다만 상세 응답에서 이미 읽은 `deposit`, `rent`, `area_m2`, `floor`, `address`, `itemId`까지 최종 items를 만들 때 버리고 있었다. 이 때문에 숫자 필터와 새 매물 ID 대조를 산문에서 해야 했다.

선택한 상세 필드를 같은 items 행에 보존했다. 직방의 `deposit/rent`는 원 API대로 **만원**, 네이버의 `price/rent`는 기존대로 **원**이다. 소스별 이름을 강제로 통일하지 않았다. 직방은 `where:"deposit >= 20000"`로 2억 원 이상 보증금을 고른다. 가이드·패키지 설명·어휘 원본을 갱신하고 어휘를 재빌드했다. 부동산 가이드에 있던 재등록 매물의 실측도 함께 보존했다.
