# IndieBiz OS 180개 에피소드의 비용과 품질 반성

**우선 바꿀 것은 IBL 문장의 수보다, 계획·실행·내부 AI·검토 사이에 판단을 배분하는 방식이다.** IBL은 이미 여러 도구를 묶고 데이터를 모델 밖에서 처리한다. 그러나 그 안에 들어간 의미 판단도 비싼 모델 호출이며, 계획이나 검토가 실행만큼 큰 작업이 되기도 한다. 다음 개선은 이 비용을 줄이면서 필요한 해석·경고·검증을 보존하는 데 집중해야 한다.

다만 **180건만으로 “전체 비용의 대부분이 불필요한 재구성이다”라는 가설은 입증되지 않았다.** 긴 집필, 조사, 영상·음성 생성에는 필요한 비용이 섞여 있다. 과거 수리로 없어진 병목도 많다. 아래 순위는 현재 근거로 정한 **검증 우선순위**이며, 품질을 유지하는 절감률이 이미 증명된 배포 목록이 아니다.

| 순위 | 바꿀 부분 | 기대하는 큰 효과 | 현재 근거와 한계 |
|---|---|---|---|
| 1 | 내부 AI에 맡기는 판단 범위·출력·추론 설정을 명시하고, 주 실행까지 합쳐 순이익을 평가 | 큰 의미 판단을 무심코 추가하거나 여러 번 수행하는 비용 감소 | 내부 AI 비용은 여러 에피소드에서 크다. 그러나 추론 축소의 기존 실험은 품질 손실도 보였다 |
| 2 | 계획·감독이 **현재 해결되지 않은 조건**에만 필요한 깊이로 관여하도록 조정 | 작은 과제의 과도한 사전 계획, 해결된 문제를 다시 검토하는 비용 감소 | 조회·여행·통계·연구에 걸친 근거. 최근 수리 후에도 큰 계획 비용은 남음 |
| 3 | 기존 변수·결과 참조·부분 성공을 전달·복구·학습에서 일관되게 사용 | 큰 과제를 다시 구성하지 않고 변경된 부분만 처리 | 공통 경계의 불일치는 확인. 최신 재조회 몇 회와 학습 유실만으로 큰 절감을 주장할 수는 없음 |

세 가지 모두 **다른 업무에서도 품질 손실 없이 큰 이익을 내는지** 확인해야 한다. 특정 보고서의 순서·선정 수·문구를 고정하거나, 모델 등급을 몰래 낮추거나, 새 감독 AI를 하나 더 붙이는 방향은 근거가 부족하다.

## 1. 자료와 해석 범위

운영 DB `data/world_pulse.db`에서 `source='usage'`, `id<=3546`인 최신 180건을 고정했다. 기간은 2026년 9월 3–12일, ID는 2764–3546이다. trajectory 사건은 최초 추출의 마지막 저장 시각 `2026-09-12T02:52:52.296566`까지로 고정했다. 코드 대조 기준은 정본 main의 `fb0c8378`이다. ID 사이에는 다른 source의 사건이 있으므로 연속 번호 180개가 아니다.

180건의 요청·행동·오류 흐름을 선별 검토하고, 아래 대표 사례는 원문 사건 및 해당 코드·기존 감사와 더 자세히 대조했다. 모든 최종 산출물을 독립적으로 다시 채점한 조사는 아니다. 전체 목록과 비민감 계수는 [180건 목록](experiments/episode_cohort_2026_09_12/cohort.md), [감사 JSON](experiments/episode_cohort_2026_09_12/cohort.json)에 있다.

| 항목 | 관측 |
|---|---:|
| 에피소드 / 에이전트 | 180 / 13 |
| `system_ai` 에피소드 | 96 |
| 정확히 같은 정기 보고서 요청으로 식별한 기록 | 32 |
| 명시적 시험 / 폴더·노트북 조사 | 10 / 9 — 표지는 중복 가능 |

**시간 합은 사용자의 실제 대기 시간이나 낭비 시간이 아니다.** 동시에 진행된 에피소드가 있고, 유용한 작업도 포함된다. p90은 정렬한 174개 값의 아래쪽 최근접 순위다. `model.usage`가 있는 53건 중 8건은 주 실행 usage도 없으므로, 나머지 45건 역시 완전한 청구 원장이라고 가정하지 않았다. 추론 토큰은 출력의 부분집합이며 둘을 더하지 않는다. 내부 AI 지연과 그것을 기다린 주 실행 시간도 더하지 않는다.

자동 ACHIEVED는 독립 품질 점수가 아니다. 평가기가 중간에 바뀌었고, 실제 요구를 덜 충족한 사례도 통과했다. 이 자료는 수리 전후의 서로 다른 업무가 섞인 관찰 자료다. 수리 후 빨라졌다는 사실만으로 수리의 효과를 계산하지 않는다. 모델별 신규 입력·캐시·청구 경로가 불완전하므로 코인이나 달러 절감액도 추정하지 않았다.

## 2. 큰 비용은 어디에 있는가

### 2.1 긴 작업 몇 건이 중요하지만, 원인은 하나가 아니다

영상·설계 작업 3306·3073·2910·2904·2907 다섯 건만으로 기록된 시간 합의 **17.7%**를 차지한다. 여기에는 장시간 생성 작업, 인증 문제, 렌더링, 자료·도구 준비가 섞였다. 오래 걸린다는 이유만으로 주 모델의 생각이 과다했다고 볼 수 없다. 특히 3073의 여러 실패 신호에는 `surface_timeout` 뒤의 작업 계속 진행이 포함된다. 오류 표지 수를 실제 작업 실패 횟수로 세면 병목을 잘못 찾는다.

반대로 조사·보고서는 IBL 실행 오류가 거의 없어도 길다. 2832는 기록상 IBL 실행 실패 신호 없이 18.42분 걸렸다. 최신 3546 역시 17.25분이며, 자료 추출·선별·편집·집필이라는 의미 작업이 크다. **예외 처리 개선은 필요하지만, 오류 수 감소만으로 전체 성능 개선을 설명할 수 없다.**

### 2.2 IBL 호출 감소는 비용 감소의 대리 지표가 아니다

3090과 3176은 같은 `claude-opus-5`, 같은 `effort:high`로 실행됐다. 과거 감사는 원본 응답 ID를 묶어 아래를 확인했다. 자료·지역·작성 내용은 달라 인과 비교는 아니지만, 호출 수만으로 절감을 판단할 수 없다는 반례로 충분하다. [응답 단위 비용 감사](IBL_EPISODE3176_COST_DIAGNOSIS.md)

| 지표 | 3090 | 3176 |
|---|---:|---:|
| 전체 시간 | 609.177초 | 762.162초 |
| IBL 호출 | 31 | 18 |
| 실제 주 모델 응답 | 33 | 19 |
| 주 모델 출력 | 34,235 | 44,326 |
| 그중 추론 | 14,026 | 22,630 |
| 비추론 출력 | 20,209 | 21,696 |

출력 증가분의 **85.3%가 추론 증가**였다. 왕복을 줄였지만 응답당 작업이 커졌다. 3176의 단일 집필 응답은 18,061토큰으로 주 출력의 40.7%를 차지했다. 이 역시 보고서와 DB 내용을 실제로 생성한 것이므로 전부 낭비는 아니다. IBL에 계산을 넣었는지, 결과를 몇 번 받았는지와 별개로 **어느 모델이 얼마나 큰 판단·생성을 했는지**를 보아야 한다.

### 2.3 최신 보고서에서도 내부 AI는 주요 비용이다

3546은 주 실행 38응답 외에 내부 생성 11회, 내부 criteria 평가 6회, 최종 평가 1회, 분류 1회, 의식 계획·검토 3회로 **전경 모델 응답 60회**를 사용했다. 후처리는 별도 2회다. `ibl.started` 37건 중 실제 실행은 27건이며 나머지는 검사 5·설명 4·원문 조회 1건이다. IBL 사건 수와 모델 응답 수가 다른 이유가 드러난다. [3546 세부 감사 §8](TASK_WORK_NOTE_PLAN_2026_09_11.md)

| 역할 | 출력 토큰 | 해석 |
|---|---:|---|
| 주 실행 | 47,410 | 내부 호출의 출력을 제외한 주 모델 출력 |
| 내부 생성 | 38,865 | 전경 출력 94,762의 **41.0%** |
| 의식 계획·검토 | 6,756 | 3회 합산 |
| 내부·최종 평가 | 1,729 | 7회 합산 |
| 분류 | 2 | 1회 |

내부 생성 한 번은 약 123초·9,052출력 토큰이었다. 그러나 원자료 81행을 AI가 전부 다시 썼다는 과거 해석은 틀렸다. 현재 `table:ai`의 색인 병합은 이미 작동하며, 모델은 주로 선택·이유 등 새 판단을 출력했다. **데이터 운반을 줄인 뒤에도 의미 판단 비용은 남는다.** 원샷이 주 모델의 어떤 작업을 대체했는지까지 보아야 순이익을 알 수 있다.

## 3. 우선 변경 후보

### 3.1 내부 AI의 계약을 ‘작은 호출’에서 ‘범위가 명확한 판단’으로 바꾼다

현재 원샷은 짧은 호출 형태를 뜻하지만 작업 난도까지 보장하지 않는다. 선별, 근거 추출, 종합 편집, 품질 판정은 서로 다른 일이다. 이를 같은 원샷 취급으로 묶으면 모델 등급은 같아도 불필요하게 넓은 판단이나 많은 설명을 요구할 수 있다.

추론 내역이 기록된 `oneshot:execution` 87회, 12개 에피소드에서 출력은 227,980, 그중 추론은 113,516으로 **49.8%**였다. 이는 관측 가능한 하위 집단의 비율이며 전체 180건의 비율도, 절감 가능한 비율도 아니다. 데이터 분석·자료 추출·보고서 등에 걸쳐 내부 판단 비용을 검토할 가치가 있다는 근거다. [역할별 집계](experiments/episode_cohort_2026_09_12/cohort.json)

코드의 설정 표현도 실제 공급자 동작과 다르다. [`model_resolver.py`](../backend/base/model_resolver.py)의 원샷 생성은 `disable_thinking=True`를 설정하지만, [`claude_code.py`](../backend/providers/claude_code.py)의 `_build_command`·`_build_env`는 이를 추론 설정으로 번역하지 않는다. 현재 함수만 격리해 실행하면 `disable_thinking=False/default`와 `True/off`의 명령이 동일하다. 상속 환경이나 공급자 기본값까지 통제한 시험은 아니므로, 모든 호출이 high였다는 증거로 확대하지 않는다. 이 불일치는 9월 8일 감사에서도 이미 확인됐다.

**설정을 연결하고 일괄 off로 바꾸는 수리는 오히려 요구에 어긋난다.** 당시 같은 입력을 8회 재생한 실험에서 off는 두 번 모두 오선별을 만들었다. low와 기본 시스템 설명 교체는 명확한 후보 선별을 유지했지만 이상치 경고를 잃었다. 빠른 결과가 간단한 구조 검사를 통과해도 같은 품질은 아니었다. [원샷 지연 실험과 품질 반증](IBL_EPISODE3176_ONESHOT_LATENCY.md)

변경 방향은 다음과 같다.

1. **모델에 맡길 의미 판단을 좁힌다.** 날짜·행 수·정렬·중복 키·결합·이미 판명된 제외 조건은 기존 IBL 데이터 연산으로 처리한다. 모델은 남은 의미 판단과 그 판단에 필요한 근거를 담당한다. 의미상 중복이나 불확실한 속성을 단순 문자열 규칙으로 대체하지 않는다.
2. **반환값은 필요한 결정과 근거의 차이분으로 정한다.** 이미 있는 색인 병합을 활용한다. 모든 탈락 후보의 장문 이유가 실제 검토에 필요한지 구별한다. 선정 근거·반례·불확실성은 보존한다. 제목으로 후보를 좁힌 뒤 원문을 정독하는 단계처럼 품질에 기여하는 분리는 유지한다.
3. **사용자 기어·모델 등급을 유지하면서 요청한 추론 설정과 실제 적용 상태를 확인 가능하게 한다.** 공급자별 미지원은 미지원으로 남긴다. Claude Code는 effort 설정 수단을 제공하지만, 적절한 값은 작업별 검증 대상이다. [Claude Code 모델 설정](https://code.claude.com/docs/en/model-config#adjust-effort-level)
4. **내부 호출을 추가할 때 주 실행까지 포함한 순이익을 검증한다.** 더 많은 원샷으로 주 루프를 잘게 나누거나, 반대로 모든 판단을 주 모델에 몰아넣는 어느 쪽도 기본 정답으로 삼지 않는다. 별도 AI가 매번 이 배분을 결정하게 만들면 그 판단 자체가 새 비용이 된다.

이 후보의 장점은 보고서뿐 아니라 자료 분류·비교·추출·편집에 공통으로 적용된다는 것이다. 가장 큰 위험은 판단 범위를 좁히면서 사용자가 말하지 않은 중요한 이상 징후까지 없애는 것이다. 기존 실험이 그 위험을 실제로 보여 주었으므로, 출력 토큰 감소만으로 채택해서는 안 된다.

### 3.2 계획·감독은 남은 불확실성에 비례하도록 바꾼다

현재 의식 프롬프트는 `task_framing`, `expert_choice`, `achievement_criteria`, `criteria`, `hint`, `imagined_ibl` 등 여러 표현으로 문제와 접근을 구성한다. 문서에는 단순 조회의 기준·초안은 비워도 된다고 이미 적혀 있다. 따라서 ‘단순 작업은 간단히 하라’는 문장을 더 붙이는 것만으로 해결됐다고 볼 수 없다. [현재 의식 프롬프트](../data/common_prompts/consciousness_prompt.md)

최신 부동산 조회 3545에서는 계획 77.883초·4,889출력, 주 실행 69.810초·4,165출력, 최종 평가 22.843초·1,344출력이 기록됐다. 계획만 전체 172.348초의 **45.2%**다. 요구 해석 자체는 필요하지만 계획이 실제 조회보다 무거웠다. 이는 이전 감독 수리 이후에도 관측된 사례다.

계획·검토 비용이 크게 나타난 업무는 하나가 아니다. 3285의 날씨 조회, 3509의 여행 기억 활용, 3405의 통계 차트, 3406의 자료 조사에서도 의식 비용이 크다. 다만 옛 `consciousness` 계수에는 사전 계획과 중간 검토가 함께 들어 있으므로 이를 모두 ‘처음 계획 시간’으로 부르면 안 된다. 3406에서는 검토가 실제 품질 결함을 드러냈으므로 긴 검토를 자동으로 낭비 판정하지 않는다.

바꿀 핵심은 계획의 유무보다 **목표·확인된 사실·미해결 조건을 어느 단계가 소유하는가**다.

- 원 요청이 명확하고 확인된 제약이 충분한 조회는 짧은 규정으로 실행한다. 상세 접근법·전문가 관점·상상 실행은 선택 항목으로 실제 생략 가능해야 한다. 초안 길이를 줄이려 요구 해석의 정확성을 포기하지 않는다.
- 감독은 전체 과제를 새로 설계하기보다, 아직 미달인 조건과 그 조건을 판단할 새 증거를 다룬다. 새 제약이나 실패가 생기면 그 부분에서 깊이를 늘린다. 기존 조건부 감독을 활용하며 상시 감독자를 추가하지 않는다.
- 판단에는 대상 결과의 버전·범위를 연결한다. 다른 방법으로 조건을 충족했다면 이전 도구 오류와 구분하고, 오래된 검토가 새 결과를 다시 만들게 하지 않도록 한다.
- 형식·개수·원문 포함 여부는 검증된 기계 검사 결과를 사용하고, 의미 충실성·인과 주장·불확실성은 모델 검토에 남긴다. 자연어 criteria에서 단어를 찾아 검사를 생략하는 임시 규칙은 만들지 않는다.

현재 [`conscious_supervisor.py`](../backend/cognition/conscious_supervisor.py)의 `_finish`는 도구 이름과 입력 식별자로 문제를 열고, 같은 서명의 성공으로 닫는다. 다른 접근의 성공이 과거 문제를 자동으로 닫지는 않는다. 3405·3406에서는 대체 경로 성공 뒤에도 이전 오류가 검토에 남는 장면이 있었다. 3546에서는 검토 시작 뒤 HTML 생성이 완료됐지만 뒤늦은 REWORK가 생성 필요를 지적했다. **3546의 이 판정이 실행자에게 전달돼 재작업을 일으킨 증거는 없다.** 잔여 정합성 문제로 남길 뿐 그 시간을 절감 가능액으로 세지 않는다.

[`supervisor_review.py`](../backend/cognition/supervisor_review.py)에는 이미 변경 범위·지문·읽기 범위 검사가 있고, [`supervisor_handoff.py`](../backend/cognition/supervisor_handoff.py)에는 국소 보완 인계가 있다. 필요한 것은 별도 감독 구조의 신설보다 이 기존 경계가 조건의 충족과 결과의 신선도를 제대로 이어 주는지 확인하는 일이다.

최신 3546의 criteria 6회 중 여러 조건은 비어 있지 않은 값·인용문의 원문 포함·선정 개수처럼 구조적이다. 인용 접지는 이미 자동 검사하며, [`ibl_quality.py`](../backend/ibl/ibl_quality.py)는 전체 행 계수를 계산한 뒤에도 자연어 criteria를 모델에게 판정시킨다. 이 몇 회의 직접 절감만을 우선 수리로 올리지는 않는다. **어떤 조건을 누가 검사하는지 정리하는 공통 설계**에 포함하고, 그로 인해 큰 재판단·재생성이 줄어드는지를 본다.

반대로 3405에서 원래 요구한 채용과 실제 얻은 취업자 수의 차이는 행 수 검사로 해결되지 않는다. 자동 ACHIEVED를 받았다고 요구 충족이 된 것도 아니다. 검토를 줄이는 개선은 이런 의미 오류를 더 놓치지 않는다는 조건을 통과해야 한다.

### 3.3 IBL이 확보한 값과 성공을 경계마다 다시 구성하지 않게 한다

180건 중 IBL 사건이 있는 에피소드는 162건, 여러 액션을 한 최상위 호출에 묶은 에피소드는 130건이다. 최상위 시작 사건 2,450개 중 여러 액션을 가진 사건은 1,181개다. 검사·설명도 포함된 수치이므로 실행 성공률은 아니지만, **IBL 조합 기능이 사용되지 않는다는 진단은 자료와 맞지 않는다.**

현재 IBL은 이미 디스크에 턴 변수를 저장하고, 부분 성공의 변수와 원문 참조를 복구한다. [`ibl_turn_vars.py`](../backend/ibl/ibl_turn_vars.py)의 보존·만료 정책, [`pipeline_state.py`](../backend/ibl/pipeline_state.py)의 복구 상태, [`model_result_view.py`](../backend/cognition/model_result_view.py)의 `result_ref`가 있다. 메모리만 있거나 체크포인트가 전혀 없다고 보고 새 저장소를 짓는 것은 중복 투자다.

남은 문제는 **보존된 것을 다음 소비자가 필요한 단위로 받아 쓰는가**다. 최신 3544·3545·3546에서는 작은 중간 결과도 첫 항목 요약으로 접혀 모델이 다시 펼쳐 읽었다. [`ibl_envelope.py`](../backend/ibl/ibl_envelope.py)의 `summarize_result`는 중간 단계의 items를 요약한다. 이는 최종 결과의 6,000자 미리보기 정책과 다른 경계다. 3545에서는 새 미리보기 정책이 실제로 17행 전량 전달에 기여했다. 이미 효과가 확인된 수리를 실패했다고 되돌려서는 안 된다. [중간 결과와 최종 미리보기 비교 §6–8](TASK_WORK_NOTE_PLAN_2026_09_11.md)

수리 방향은 모든 중간 결과를 풀어 보내는 것이 아니다. 모델이 다음 판단에 필요한 여러 결과를 **기존 IBL로 이름 붙여 명시적으로 반환**하고, 큰 원본은 참조로 유지하게 한다. 복구 때는 살아 있는 변수·자료·이미 충족한 조건을 인계하고, 바뀐 입력에 의존하는 부분만 다시 처리한다. 원 요청이나 자료가 바뀌면 기존 판단을 무효화할 수 있어야 한다. 이것은 업무 순서를 얼리는 것과 달리, 새 조합을 하면서 재료를 다시 만들지 않게 하는 변경이다.

실행과 학습 사이에도 불일치가 있다. 3546에서 검색·중복 제거와 `$후보` 생성은 성공하고 뒤의 rename이 실패했다. 실행자는 저장된 `$후보`를 재사용해 계속 진행했다. 그러나 [`ibl_usage_rag.py`](../backend/cognition/ibl_usage_rag.py)는 호출 전체의 success로 먼저 걸러서, 실패 호출 안의 성공한 생산 문장까지 증류 후보에서 제외한다. 뒤의 성공 문장이 생산자 없는 외부 변수로 남아 새 패턴 증류가 거절됐다. 실패를 거르는 안전장치를 없애기보다 **성공이 증명된 문장과 의존 관계를 함께 보존**해야 한다. [부분 성공의 실행·학습 차이 §8-2](TASK_WORK_NOTE_PLAN_2026_09_11.md)

이 변경의 보편성은 표 조회·자료 조사·문서 수정 등에서 같은 의존 관계가 생긴다는 점에 있다. 하지만 최신 재조회 몇 회는 작은 비용이고, 학습 보존이 미래 작업을 얼마나 개선할지는 아직 미측정이다. 따라서 이 항목을 가장 큰 즉시 절감책으로 포장하지 않는다. 전체 주행을 의무 절차로 저장하는 대신, 재료와 성공 범위를 정확히 재사용하도록 기존 경계를 고치는 후보로 둔다.

## 4. 다른 하네스에서 가져올 것과 이미 있는 것

공개 자료는 비교 원칙의 근거이며 IndieBiz OS의 절감률 근거가 아니다. 다른 환경의 토큰 절감 수치를 이 시스템에 대입하지 않았다.

| 외부 전략 | IndieBiz OS의 현재 대응 | 필요한 변화 |
|---|---|---|
| 프로그램으로 도구를 묶고, 필터·루프는 모델 밖에서 처리 | IBL `>>`, `&`, `table:each`, 변수·table 변환자 | 이미 핵심 전략을 갖췄다. Python 중심 하네스로 교체하기보다 내부 의미 판단 비용까지 평가 |
| 원문 대신 식별자를 유지하고 필요할 때 조회 | `result_ref`, spill, 턴 변수, 기억 지도 | 저장소 추가보다 중간 결과·복구·검토의 소비 경계 개선 |
| 필요한 만큼만 계획·라우팅·평가 | 기어, 차선, 조건부 감독, 분리된 최종 평가 | 단순 작업에서 실제 계획 부담을 낮추고, 미해결 조건에 검토를 집중 |
| 결정적인 작업은 코드로 수행 | IBL 변환자, 스키마 검사, grounded 인용 검사 | 이미 판정 가능한 조건의 반복 LLM 검사와 설명 생성을 줄일 수 있는지 검증 |
| 상태를 저장하고 실패 지점부터 계속 | 디스크 턴 변수, 부분 성공 복구, 과제 상태 | 실행·인계·학습에서 성공 범위가 어긋나는 부분 연결 |
| 대표 작업·어려운 예외·미사용 과제로 회귀 평가 | 사건 감사, 코드·문장 회귀, 개별 재생 실험 | 여러 작업군의 실제 품질과 총비용을 함께 통과 조건으로 사용 |

Anthropic의 programmatic tool use와 MCP code execution은 모델이 매번 전체 중간 데이터를 읽지 않고 프로그램이 결합·가공하게 한다. 이것은 IBL을 가진 IndieBiz OS가 이미 선택한 방향과 가깝다. 도구 검색 역시 도입 자체가 목적이 아니라, 문맥 절감이 추가 탐색 왕복보다 유리한 상황에서 쓰는 수단이다. [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use), [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)

문맥 관리는 원문을 다 밀어 넣거나 매번 요약 AI를 호출하는 문제로 한정되지 않는다. 가벼운 식별자와 필요한 시점의 조회, 작업 상태의 보존이 핵심이며 기존 변수·참조가 그 역할을 상당 부분 담당한다. LangGraph의 persistence도 실행 상태를 이어 가는 장치다. 이 원칙을 참고하되 다른 프레임워크를 추가할 필요는 없다. [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

OpenAI의 지연 최적화 지침은 출력량·요청 수·병렬화·결정적 코드 사용을 함께 보게 한다. Anthropic의 에이전트 설계 지침도 요구에 충분한 단순한 구성을 출발점으로 둔다. 여기서 가져올 것은 ‘계획기나 평가기를 없애라’는 처방이 아니라, **추가 단계가 만드는 실제 품질 이익과 지연을 함께 검증하는 규칙**이다. [Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization), [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

## 6. 품질을 지키면서 큰 효과만 채택하는 방법

현재 180건은 이미 진단에 사용했으므로 최종 검증용 미사용 자료가 될 수 없다. 기존 결과를 정답으로 고정해서도 안 된다. 과거 출력 자체에 오류가 있고, 동일 요청도 자료가 바뀐다. **새 과제를 포함한 작업군별 비교**가 필요하다. 대표 사례·예외·미사용 자료와 사람의 판단으로 평가를 보정하라는 원칙은 공개 평가 지침과도 일치한다. [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

### 비교 설계

1. **작업군을 나눈다.** 간단한 조회, 여러 출처의 조사·비교, 표의 추출·변환, 파일 생성·수정, 장시간 도구 작업을 포함한다. 도메인별 규칙을 만드는 것이 아니라 서로 다른 비용 구조에서 공통 변경이 견디는지 보기 위한 구분이다.
2. **한 번에 한 축을 바꾼다.** 첫 비교는 내부 AI의 판단·출력 범위, 다음은 계획·검토 범위처럼 분리한다. 추론 설정이나 시스템 설명을 동시에 바꾸면 원인을 분리하기 어렵다. 같은 모델·기어·코드·자료 스냅샷과 실제 앱 경로를 사용한다.
3. **대체된 일까지 잰다.** 원샷이 빨라졌어도 주 모델이 더 많이 읽고 다시 판단하면 손해일 수 있다. 전경 완료·하위 호출·후처리 비용을 구별하고, 병렬 구간은 실제 완료 경로의 시간으로 계산한다.
4. **적응력을 시험한다.** 목표 변경, 새로운 분야, 누락 필드, 모순된 출처, 부분 실패를 포함한다. 같은 과제의 여러 턴은 함께 묶어 개발·검증 사이의 정보 누출을 막는다. 검증 업무군 하나는 설계 과정에서 사용하지 않는다.
5. **같은 품질을 먼저 확인한다.** 원 요청의 조건, 사실·근거, 필요한 경고, 누락, 수정 후 일관성, 실제 파일 내용을 확인한다. 비교를 가린 사람의 검토로 모델 판정을 보정한다. 구조 검사는 보조이며 자동 ACHIEVED만으로 통과시키지 않는다.
6. **여러 업무군의 총효과가 큰 변경만 채택한다.** 중앙값과 긴 작업의 지연, 실제 모델별 입출력·캐시·추론, 실패·보완, 품질을 함께 비교한다. 효과가 작은 변경은 뒤로 미룬다. 특정 업무만 좋아지거나 경고·근거가 줄어든 변경은 일반 정책으로 승격하지 않는다.

현재 계측을 재사용하는 것이 출발점이다. 역할별 usage, 모델 응답 식별자, 원문 참조, 과제·실행 신원을 이미 가지고 있다. 분석 시 요청한 effort와 실제 적용 여부, 누락된 usage의 범위, 최종 사용자가 받은 산출물 버전을 연결하면 된다. 새 모델 평가를 매 실행 단계에 상시 추가하는 방식은 이 목적과 맞지 않는다.

### 첫 변경의 구체적 범위

첫 구현 실험을 하나 고른다면 **내부 AI에 넘기는 판단 범위와 필요한 반환값을 명확히 하는 변경**부터 권한다. 기존 색인 병합·grounding·IBL 변환자를 유지하고, 넓게 재판단하거나 설명하도록 요구하는 부분을 좁힌다. 추론 설정의 실제 적용 여부는 동시에 관측하되, 초기 대조 실험에서는 설정을 유지해 출력 계약의 효과를 분리한다.

그다음 계획이 실행보다 무거운 조회·수정 작업에서 기존 선택 항목을 실제로 생략하도록 비교한다. 그 과정에서 필수 조건·이상치 경고·사실 확인이 빠지면 해당 변경은 중단한다. 결과 전달과 부분 성공 학습은 정확한 경계 수리 후보로 남기되, 몇 초의 재조회 감소만으로 앞의 큰 비용보다 높은 순위를 주지 않는다.

재현 명령은 정본 루트에서 실행한다. 출력은 새 파일이어야 한다. DB는 읽기 전용 트랜잭션으로 열고 backend·provider를 초기화하지 않는다. 추론 플래그 검사는 현재 코드에서 순수 명령 구성 함수만 AST로 추출해 실행하며 외부 모델을 호출하지 않는다.

```bash
python3 docs/experiments/episode_cohort_2026_09_12/audit.py --end 3546 --count 180 --events-through 2026-09-12T02:52:52.296566 --out /tmp/indiebizos-cohort-recheck.json
```

동일 집계는 기존 기록의 값이 유지된 경우 재현된다. DB의 사후 요약 갱신이나 코드 변경이 있으면 차이가 날 수 있다. 로그 SHA와 분석 당시 코드 커밋을 비교할 수 있게 남겼다. 이 스크립트는 원문 의미 검토나 과거 공급자 JSONL의 별도 감사를 대체하지 않는다.
