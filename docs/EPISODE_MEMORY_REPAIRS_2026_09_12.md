# 최근 완료 에피소드의 오류 수리

사용자가 진행 중인 건을 제외한 최근 네 에피소드(3592~3595)를 점검한 뒤, 발견한 오류 전부의 수리를 요청했다.

## 변경

- 호출 계수: SQL·보고서·주석의 `[fn:]` 문자열을 관용구 호출로 세던 오류를 공통 문자열 스캐너로 제거했다. 호환 키 `fn_calls`는 작성 구문 수이며 실행 횟수가 아니다. 지연 문자열·반복 횟수는 별도 실행 기록의 대상이다. 원래 사건 로그는 고쳐 쓰지 않는다.
- 출처 귀속: 인용·펜스·출처 불명 답변형 문서를 개인 사실 후보에서 보류한다. 후보 통과가 저자 증명은 아니므로 증류기도 직접 진술·명시 채택을 확인한다. 포식 주인 모델은 근거 번호를 요구하고 모델이 만든 성향 설명 대신 선택한 사용자 원문을 저장한다. 출처 미상 전달문만 있는 턴은 공간·주인 추측을 증류하지 않는다.
- 실행 회상: 긴 일회성 보고서가 실행 용례에 실려 다음 답의 사실 근거로 재주입되던 경로를 끊었다. 여러 문장·1200자 초과 원문은 자동으로 본문을 싣지 않고 명시 회상 입구를 보여 준다. 원문은 보존한다. 본문을 숨긴 후보의 코드로 반사 실행하지 않는다. 짧은 용례와 이름 있는 함수의 서명은 계속 노출한다.
- 파일 검색→투영: `items`와 번역된 표시 표가 함께 있으면 `items`를 정본으로 삼는다. 없는 `modified`를 요구하면 실제 `mtime` 등 필드를 보여 주고, 올바른 열로 재시도할 수 있다. 순수 표형 입력의 계약은 유지한다.
- 계산→필터: `where` 왼쪽은 필드명이라는 기존 계약을 모델에게 노출되는 짧은 설명에도 명시한다. `len(text)`는 `compute`로 열을 만든 뒤 `filter`한다. 오류 뒤 교정·검증을 끝내도록 실행 안내를 보완했다.

## 기존 기억의 수리

라이브 DB를 SQLite backup으로 보존한 뒤 심층기억 3건을 전달된 AI 의견/작업기록으로 재분류하고 출처·본문·검색 색인·가지 문서를 함께 갱신했다. 같은 답변에서 근거 없이 추론한 공간 단언 3건·주인 모델 3건은 백업에 격리하고 활성 원장·파생 문서에서 제거했다. 사용자 본인이 진술한 앞선 기억은 유지했다. 백업과 기억 원문은 개인정보를 포함하므로 커밋하지 않는다.

## 검증 범위와 한계

회귀는 SQL 내부 호출 예시, 인용 속 1인칭과 사용자 채택, 포식의 근거 없는 성향 추론, 긴 단일 write의 본문 노출, 이중 봉투의 필드 오류/교정, compute→filter 복구를 재현한다. 외부 호출이나 실제 사용자 작업의 재실행 없이 임시 데이터와 모델 대역으로 검증한다.

출처 표지가 없는 임의의 붙여넣기에서 저자를 완벽히 판별하는 기능은 아니다. 불확실한 구조를 보류하는 규칙과 모델의 출처 확인을 함께 사용한다. 긴 원문 노출 상한은 의미에 대한 판정이 아니므로 긴 정상 프로그램도 필요하면 명시적으로 열어야 한다. 모델이 언제나 재시도하거나 사실 검증한다는 보장은 하지 않는다.

## 검증 결과

- 전체 backend 회귀: 4,090 passed, 1 skipped (265초). 기존 경고 116건.
- 새 재현 시험 7건: pytest와 파일 직접 실행 모두 통과. 첫 전체 실행에서 발견된 직접 실행 진입점 누락도 보완했다.
- 어휘 빌드·`--check`, backend 층 가드, 은퇴 계약 가드, Android 몸 번들 생성 통과.
- 활성 기억: 심층기억 3건의 작업기록/외부 출처와 격리 6건의 DB·문서 부재를 재확인.
- 런타임: 수정 중 부팅 산출물 변경으로 멈춘 제어자를 정식 재기동 경로로 복구했다. 활성 소스 digest 일치, ACTIVE, health HTTP 200 확인. 진행 중 에피소드 강제 중단은 없었다.
