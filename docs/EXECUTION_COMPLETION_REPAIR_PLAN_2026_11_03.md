## 1. 판단과 범위

문제는 조합·재사용·검수 기능의 단순 부재가 아니다. 기존 기능을 사용하기 위해
모델이 경로·절차·결과 구조를 다시 찾고, 이미 얻은 근거를 검수 입력으로 다시 조립하며,
검사 환경의 실패와 실제 구현 결함을 구별하는 비용이 크다. 정해진 절차는 기존 실행부가
연결하고 새로운 판단이 필요한 경계에 모델을 둔다.

이 계획은 다음을 구분한다.

- **확인된 결함:** 봉인 세대에서 원장 데이터 루트를 잘못 해소하는 경로와,
  수리 검사 안의 자식 검사가 전역 `/tmp`에 새 작업 공간을 만들다 거절되는 경로.
- **원인 조사 후 수정할 항목:** #5773의 세 번째 회귀 실패인 적용 후 활성 확인.
  앞의 임시폴더 문제와 같은 원인이라고 합치지 않는다.
- **일반 능력 개선:** 검사 범위·근거 전달·부분 재개·완료 표시의 연결,
  판단이 필요 없는 구간의 묶음, 능력 변경 도구의 실제 사용 연결.
- **별도 성과 측정:** 앞의 계약을 구현한 사실과 시간·전체 토큰 개선은 따로 판정한다.

새 문법·코어 어휘·목표 DB·감독 모델·상주 감시를 기본 해법으로 추가하지 않는다.
현재 권한·검수 기준을 낮추거나 모든 작업에 추가 검수를 강제하지 않는다.
원장 데이터 수정, 보고서 재발행, 원격 업데이트, #5773 적용은 이 문서 작성에서 실행하지 않았다.

## 4. R0 — 검사 환경을 먼저 복구한다

**소유:** `backend/base/repair_process.py`, `coding_process.py`, `repair_live_probe.py`,
`backend/cognition/repair_check_runner.py`, `backend/datastore/red_apply.py`의 기존 책임.

1. 같은 OS 격리 안에서 pytest→수리 검사→자식 pytest의 최소 반례를 만든다.
   단독 호스트 실행 통과만으로 중첩 문제를 닫지 않는다.
2. 최상위 runtime과 중첩 runtime의 소유·수명을 구분한다. 중첩 자식은 부모가 이미 허용한
   runtime 안에 자기 임시 공간을 만들고, 최상위는 기존 준비 경로를 사용한다.
   임의 환경변수 하나를 새 쓰기 권한으로 신뢰하지 않으며 실제 소유 경계를 대조한다.
3. Python 임시폴더·캐시·소켓이 자식 환경을 따르는지 확인한다. `/tmp` 전체 허용,
   샌드박스 해제, 정본을 검사 쓰기 대상으로 전환하는 방식으로 해결하지 않는다.
4. 세 번째 실패의 원문에서 적용 영수증·활성 대상·조회 주소·대기 원인을 따로 조사한다.
   실제 활성 검사와 시험용 제어자/브리지의 신원을 대조하고, 원인이 확인된 소유자만 수정한다.
   단순 timeout 증대나 assertion 제거를 해결로 취급하지 않는다.
5. 실행 불가·시간 초과·취소·assertion 실패·검사 도중 후보 변경을 기존 검사 결과에서 구분한다.
   exit 130 하나로 모두 취소라고 판단하지 않고 원래 오류와 JUnit 부재를 함께 보존한다.

**인수:** 위 세 실패와 원래 선택 범위의 미실행 항목 확인; 중첩 readonly 검사·동시 검사·취소·
자식 종료/청소·runtime 밖 쓰기 거절. 신규 계약 시험은 `test_repair_process.py`,
`test_repair_check_runner.py` 등 모듈명 파일에 둔다. 격리 변경이므로 최종 전수 필요.
R0 성공은 #5773 기능의 앱 적용 성공과 별도다.

## 5. R1 — 코드 위치와 데이터 소유 범위를 분리한다

**소유:** `data/packages/installed/tools/system_essentials/ledger_ops.py`와
`backend/base/runtime_utils.py`, `backend/ibl/tool_context.py`, 기존 수리 쓰기 관문.

ledger의 상대 경로는 기존 몸 루트 기준을 유지한다. 이를 프로젝트 기준으로 조용히 바꾸지 않는다.
`~workspace`는 기존 `expand_body_path`의 수리 사본 해소를 유지한다. 데이터·소스·코드 루트의
차이는 기존 get_base_path/get_source_root/get_code_root 및 수리 문맥에서 가져온다.

- `_ROOT = Path(__file__).parents[...]`를 데이터 허용 범위로 사용하는 로컬 추측을 제거한다.
- 대상 path와 items_file에 동일한 해소·범위 검사를 적용한다. 단순 정본 절대경로 허용 목록을 추가하지 않는다.
- 코드 자원용 `__file__` 사용까지 일괄 치환하지 않는다. 같은 데이터 경계 책임을 가진 소비자만 조사한다.
- 실제 경로·심볼릭 링크·존재하지 않는 신규 파일의 부모 경계, 수리 사본과 운영 데이터 구분을 보존한다.

**인수:** 정본 직접 실행/봉인 세대/프로젝트 문맥/수리 사본에서 상대·절대·`~workspace`의
계약 대조. 운영 원장은 읽기 전용 재현만 하고 쓰기 시험은 임시 원장을 사용한다.
원장 밖·링크 탈출·다른 소유자 접근은 계속 거절한다. `test_ledger_ops.py`,
`test_ledger_where_shared.py`와 경로/수리의 전이 소비자를 사용한다.

## 6. R2 — 검증 근거를 다시 조립하지 않게 한다

**소유:** `repair_check_runner.py`, `repair_policy.py`, `final_evaluator.py`,
`evaluation_input.py`, `supervisor_content.py`, 기존 supervisor 저장소와 `research_review.py`.

검사 ID, 보충 관측 ID, 원문 주소는 같은 이름으로 합치지 않는다. 기존 기준별 coverage에
해당 후보·환경·검사 범위와 원문 참조를 연결하고 다음 검수는 그 연결을 직접 소비한다.

1. 시험 선택 결과·실제 수집 목록·통과/실패/미실행을 기존 실행 증거에 남긴다.
   좁은 검사 성공으로 더 넓은 필수 실패를 덮지 않는다. 조건/환경이 바뀌면 재사용을 무효화한다.
2. 같은 후보·명령·환경의 유효한 검사 영수증은 기존 `check` 재사용 경로를 쓴다.
   범위가 다른 명령을 자동으로 동등하다고 간주하는 새 캐시는 만들지 않는다.
3. 구조화 산출물과 실제 본문·지문, 기준별 원문 주소를 첫 평가에 연결한다.
   이미 있는 b3d8cc20 수집을 재구현하지 않고 생산자/소비자별 누락 반례만 보강한다.
4. `UNKNOWN/evidence`는 저장 원문의 한정 회수로, 내용 오류는 해당 내용의 보완으로,
   검사 환경 실패는 R0의 진단으로 잇는다. 회수 때문에 외부 효과를 다시 실행하지 않는다.
5. 큰 원문은 기존 총량 예산과 부분 조회를 사용한다. 생략 범위·판본·회수 주소를 보존하고,
   구간을 읽은 사실을 의미 검토 완료로 바꾸지 않는다. 존재하지 않는 json/output 구조를
   추측하지 않도록 기존 read_args와 값/텍스트 계약을 반환 경계에서 명확히 한다.

**인수:** #5753/#5768 생산자별 본문 전달, #5767 불변 판본 회수, #5773 보완 뒤 REWORK 재생.
정상·모순·오판본·없는 근거·본문 예산 초과·검수 중 파일 변경·재개를 포함한다.
검수의 성공 예만 만들지 않고 #5759와 같은 의미 오류를 계속 잡는지 확인한다.

일반 코드 수리를 관용구 등록으로 포장하지 않는다. 코드 수리는 기존 self:patch 소유다.

- 능력 추가/변경을 발견하는 안내에서 기존 가이드와 호출 계약을 찾을 수 있게 연결한다.
  상시 프롬프트에 전체 절차를 중복 삽입하지 않는다.
- 관리 요청에서 준비→영향 검사→반영→새 호출 검사→각인을 기존 소유 연산으로 잇는다.
  검사·근거 전송 같은 필수 후속은 AI가 별도 도구를 기억해야 수행되는 구조를 피한다.
- `--check-worktree`는 현재 변경 전체를 수집하므로 동시 작업의 검사·각인 범위를
  원래 요청의 files와 혼동하지 않게 한다. 기존 명시 files 경로를 우선 사용한다.
- 부분 성공은 저장·검증·적용·활성·전달을 구분하고 남은 기존 영수증/재개 동작을 반환한다.
  별도 범용 완료 도구나 진행 DB 대신 기존 반환·상황 전달을 보강한다.
- 사용자 최종 응답·주행기록·통합 조회가 같은 관측을 사용하도록 대조한다.
  종료=목표 달성, APPROVED=배포 완료, UNKNOWN=효과 없음으로 표시하지 않는다.
  기존 goal_status/review_status 분리는 유지하며 과거 판정을 소급 개정하지 않는다.

**인수:** 함수 원장 변경에는 불필요한 Git/재기동 없음; 스크립트 등록 성공 후 검사 실패는
등록 재실행 없이 후속 verify; 적용 예약은 미완료; 상태 변경 시 오래된 검사/승인 무효.
