# 작업 대상·실행 수명·검증 근거의 연결 수리 설계

작성: 2026-11-09 · 상태: **R0–R3 구현·검증 완료 — 기존 문서 감사 1건 잔존**

에피소드 5958에서 드러난 환경 오류와 반복 검사의 원인을 기존 실행 구조 안에서 수리한다. 목표는 처음 보는 작업에서도 올바른 대상을 실행하고, 유효한 결과를 보존하며, 새 판단이 필요한 부분에만 시간과 토큰을 쓰게 하는 것이다. 기존 소유권 판정·프로세스 세션·실행 원장을 연결하고, 별도 관리 계층이나 감독 호출은 추가하지 않는다.

이 문서는 코드 변경의 책임 위치와 인수 조건을 정한다. 최초 설계의 기준 소스는 정본 main의 `10be08d8001df229d0bd5fccad9831dee2cd52f5`이며, 후속 구현·검증은 §11에 기록한다. 설계에 적힌 예상 효과와 실제 확인 범위를 구분한다.

## 1. 근본 원인과 수리 방향

**같은 작업의 대상·수명·결과를 각 경로가 서로 다르게 해석한다.** 파일 도구는 대상의 소유권을 따라 정본을 편집하지만 셸은 턴의 REPAIR 권한을 따라 사본을 선택한다. 장시간 실행을 관리하는 세션은 이미 있으나 수리 경로에서는 거절된다. 실행 결과를 보존하는 원장도 있지만, 원래 연산과 후속 변환·검사의 실패를 재시도 판단에서 충분히 구분하지 못한다. 이 틈을 모델이 복사·재기동·재검사로 메운다.

동시에 **이미 받은 사실을 활용하지 못하는 판단 문제도 있다.** 존재하는 수정, 진입할 수 없는 방, 지나치게 긴 검사라는 정보가 있어도 같은 시도를 반복했다. 정보 필드를 늘리는 것만으로 이 문제가 해결된다고 가정하지 않는다. 실행 연결의 결함과 모델의 방법 선택을 각각 검증한다.

| 연결할 대상 | 현재의 단절 | 수리 결정 |
|---|---|---|
| 편집과 실행 | 대상 소유권과 전역 수리 모드가 서로 다른 루트를 선택 | 기존 대상 판정으로 결정한 실행 문맥을 파일·셸·스크립트가 공유 |
| 실행과 관측 | 도구 응답 시간과 자식 프로세스 수명이 묶임 | 긴 실행은 기존 process session의 접수·관측·취소 사용 |
| 실행과 환경 | 실제 프로젝트 대신 수리 저장소 기준으로 런타임 구성 | 선택된 대상과 수명에 맞춰 기존 환경 준비 경로 연결 |
| 효과와 실패 | 수정 성공 뒤 변환 실패, 검사 실패와 정리 실패가 섞임 | 원래 결과와 후속 실패를 기존 원문 참조로 함께 전달 |
| 목표와 검사 | 최초 검사 방법이 환경 변화에도 고정된 절차처럼 남음 | 사용자 조건을 보존하면서 전제·변경 영향에 맞게 방법 조정 |

판단 기준은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)이다. 개별 도구의 성공이나 호출 수 감소를 사용자 목표 달성·전체 비용 개선으로 바꾸어 보고하지 않는다.

## 2. 근거와 인과의 한계

분석 대상은 건물 다섯 곳에 열리는 문을 추가한 에피소드 5958이다. 원자료는 로컬 `data/world_pulse.db`의 `episode_log`·`trajectory_event`, 해당 도구 원문과 산출물이다. 의식의 최초 검사 범위는 `data/spill/supervision/625a12dfb1254971b8017969de6bda54/8a980924deeb787136e252a903d6f2e49da7de39ba3ab406cee8acaafef24af4.txt`에 남아 있다. 운영 DB·spill·개인 웹앱은 이 설계의 코드 배포 의존성이 아니며 다른 설치에 없을 수 있다.

| 확인 내용 | 관측 및 재현 | 해석의 범위 |
|---|---|---|
| 작업 전체 | 시작 `2026-11-09T06:10:06.795708`, 종료 `07:13:41.117930`, 저장된 total_ms=3,814,321 | 약 63분 34초. 전체가 낭비였다는 뜻은 아님 |

| 전제 없는 반복 | 뉴스 로컬 API 503과 대체 화면을 확인한 뒤에도 방 진입을 전제로 긴 대기 반복 | 검사 전제와 결과의 관계를 유지하지 못한 판단 문제 |

원장 집계의 `execution_calls=74`, `execution_failures=19`, `internal_tool_failures=130`은 서로 다른 집계 단위다. 130개의 독립 근본 원인으로 세지 않는다. 병렬 실행을 포함할 수 있는 도구 소요 시간도 벽시계 시간에서 단순 차감하지 않는다.

공유 `openCivic`·`SwingDoor`를 바꿨으므로 기존 입장·이동·경쟁 클릭 검사는 관련성이 있다. 검증 자체를 없애는 것이 목표가 아니다. 이미 실패로 판명된 전제를 계속 기다리는 시간, 소유 경로 불일치로 생긴 복사, 같은 실행을 다시 시작하는 비용을 줄인다.

## 3. 기존 구조의 책임을 유지한다

| 책임 | 사용할 기존 소유자 | 변경 범위 |
|---|---|---|
| 대상 분류·자기 변경 경계 | `backend/base/program_boundary.py` | 분류 단일 소스 유지. 웹앱 이름·확장자 예외 추가 안 함 |
| 신뢰된 작업 범위 | `backend/base/code_analysis_scope.py`, 기존 task/thread context | 기존 binding의 루트·쓰기 권한·세대를 실행 소비자까지 연결 |

새 workspace registry, 환경 관리 서비스, 작업 DAG 엔진, 효과 DB, 검사 승인 게이트를 만들지 않는다. 필요한 작은 공통 함수는 위 소유 모듈 안에 둔다. 기존 모듈의 층 방향과 1,500줄 제한을 따른다.

## 4. R0 — 대상 판정과 실행 경로를 일치시킨다

### 입력과 선택

실행 위치는 **인증된 호출의 기존 작업 범위 + 대상의 소유 경로 + 요청한 위치**로 결정한다. 수리 grant는 허용되는 변경의 조건이며 작업 위치의 단독 결정자가 아니다.

1. 호스트가 발행한 기존 작업 binding 또는 선택된 프로젝트 범위를 먼저 사용한다. `code_analysis_scope.bind/check`의 소유자·루트·쓰기 제한을 유지하고 binding의 세대를 실행 소비자에 전달한다. 이 binding이 없는 호출을 모델의 경로 문자열만으로 신뢰된 binding으로 승격하지 않는다.
2. 요청 위치는 기존 `run_command.cwd`를 PC에도 연결한다. 현재는 폰용 설명이며 PC 경로는 이를 사용하지 않는다. 생략 시 현재 경로의 기본값을 보존한다. 신뢰된 대상이 불명확한 기존 호출은 기존의 제한된 경로를 유지하고 선택된 루트를 결과에 드러낸다. 셸 문자열의 `cd`를 파싱하여 권한이나 대상 소유권을 추측하지 않는다.
3. `program_boundary`의 분류와 기존 경로 검사로 유효 루트를 정한다. 파일 소유 대상은 그 정본 프로젝트에서, 관리되는 수리 구현은 기존 후보에서 실행한다. 명시적으로 후보 경로를 고른 호출은 후보로 남긴다. 코어 금지·관리 연산 전용 대상은 기존 계약을 따른다.
4. 선택한 루트·cwd·쓰기 범위·세대·기존 수리 신원을 호출 문맥에 한 번 결속한다. 파일·셸·등록/임시 스크립트가 소비할 때 grant만 보고 다시 선택하지 않는다. 이 값은 기존 context/receipt에 필요한 만큼만 담고 별도 저장소를 만들지 않는다.

런처 binding이 없는 기존 도구 호출에서도 호스트가 인증된 행위자·업무 권한과 기존 대상 경로 검사를 통과한 cwd를 좁은 실행 범위로 결속할 수 있다. `route=file`이라는 분류만으로 허가하지 않으며, 이미 허용된 작업에 새 프로젝트 등록이나 추가 승인을 요구하지 않는다. 이 결속은 기존 scope 소유 모듈의 공통 함수로 수행하고 소비자마다 경로 판정을 복제하지 않는다.

`cwd`는 위치 선택자일 뿐 권한 부여가 아니다. 외부 경로는 기존 허가 범위가 있을 때만 가능하고, 정본 저장소 전체를 파일 소유 웹앱의 쓰기 범위로 열지 않는다. 심볼릭 링크·하드 링크·경로 탈출·제한된 수리의 delta·취소·activation-only 검사는 보존한다. 여러 소유 경로에 쓰는 명령을 하나의 넓은 권한으로 합치지 않는다. 허용된 호출로 분리하거나 기존 관리 연산을 사용한다.

### 소비자와 호환

`repair_execution_scope.scoped`의 지연 사본 선택, `repair_tool_scope.file_call/run_shell`, `essentials_command.execute_command`, `script_process.run_process`의 암묵적 재포장까지 함께 점검한다. 한 어댑터만 고쳐 다른 경로가 다시 사본을 강제하게 두지 않는다. 일반 업무의 동기 명령 반환 형식은 유지한다.

직결 IBL과 MCP가 같은 계약을 사용해야 한다. 루트 `mcp_server.py::run_command`는 현재 command/timeout/approved만 받고 `/ibl/repair/command`로 전달한다. cwd 및 기존 세션 옵션을 지원하도록 이 래퍼·`backend/surface/api_supervision.py` 뒤의 dispatch까지 연결한다. MCP의 수리 권한·실행자 검사는 유지하며 일반 사용자의 무권한 셸 통로로 확대하지 않는다. `ibl_actions.yaml` 설명을 고치고 기존 빌더로 파생물을 재생성한다.

**사례 인수:** REPAIR 턴에서 정본 웹앱의 파일 편집 직후 같은 루트에서 검사하고, 별도 rsync 없이 그 바이트를 읽는다. 수리 구현은 여전히 후보에서 검사한다. 웹앱 폴더를 git 저장소로 새로 만들거나 자기수리 코드로 재분류할 필요가 없다.

## 5. R1 — 실행 수명과 관측 시간을 분리한다

### 기존 세션으로 연결

짧은 동기 명령은 그대로 둔다. 개발 서버와 긴 검사는 기존 `mode=session`·task_ref·status/control을 사용한다. 도구 응답의 대기 한도는 프로세스 전체 수명이 아니다. 상태 조회가 끝나도 같은 실행이 계속되고, cursor로 새 출력만 회수한다. 긴 명령을 임의로 백그라운드화하거나 실패한 명령을 자동 재실행하지 않는다.

현재 수리 중 session을 일괄 거절하는 분기는 **환경·권한·취소·결과 회수가 연결된 뒤** 제거한다. 거절문만 없애서는 안 된다. 현재 세션 worker는 비밀 이름의 환경변수를 제거하여 환경을 재구성하고, 수리 실행은 별도의 인증·런타임 준비를 한다. 현재 세션과 수리의 네트워크 격리 기본값도 같지 않다.

`process_sessions.start`가 R0의 검증된 문맥을 받아 기존 소유 신원과 함께 보관하고 worker에 전달한다. 기존 `request_id` 중복 제출 판정에는 실행 대상·세대·유효 실행 옵션도 포함한다. 같은 ID와 다른 대상은 충돌이며 기존 프로세스에 붙이거나 새로 실행하지 않는다. 모델이 env·sandbox 플래그로 권한을 넓히는 새 공개 옵션은 만들지 않는다.

### 환경은 대상과 수명에 귀속

`repair_process.prepare`의 공통 준비 부분을 동기 실행과 세션에서 함께 사용한다. IndieBiz 몸에만 필요한 BASE_PATH·bridge·수리 설정은 수리 어댑터에 남기고, 사용자 웹앱을 IndieBiz 몸처럼 구성하지 않는다. 실행 파일 탐색은 실제 대상의 package/lockfile 및 기존 Node 선택 경로를 따른다. 저장소의 `frontend`를 다른 프로젝트의 런타임으로 무조건 선택하지 않는다.

임시·캐시·설정 쓰기는 선택된 프로세스의 기존 runtime 디렉터리에 둔다. 현재 빠진 XDG_CONFIG_HOME 같은 표준 환경도 여기서 일관되게 준비한다. 도구별 추가 설정은 기존 프로젝트 실행 설정·어댑터가 소유한다. core에 Wrangler 오류 문자열별 우회나 호스트 홈 전체 쓰기 허용을 넣지 않는다. 사용자의 인증은 기존 허가 범위 안에서 읽고 필요한 자식에게만 전달하며 일반 환경값을 세션 JSON에 통째로 저장하지 않는다. 기존 세션 제어 토큰과 외부 서비스 자격 증명을 구분한다.

세션 runtime은 해당 실행이 끝날 때까지 유지한다. 정상 종료·취소·실패 뒤 출력과 선언된 산출물 참조를 기존 저장 경로에 남긴 후 정리한다. sync의 임시 디렉터리를 장기 세션에 물려주지 않는다. 기존 세션 출력은 1MiB 보존 한도가 있으므로 오래된 출력 전체가 남는다고 약속하지 않는다. 절단 여부와 cursor를 전달하고, 필요한 검사 보고서는 기존 파일 근거로 보존한다.

### 소유권과 종료

수리 세션은 기본 `lifetime=task`다. 턴·수리 작업·후보 세대와 결속하고, 기존 task 취소·수리 폐기·적용 경계에서 소유 프로세스를 확인한다. 후보를 변경할 수 있는 프로세스가 남은 채 적용하지 않는다. 기존 반영 경로가 소유 세션의 종료·산출물 확정을 확인하며, 종료를 확인할 수 없으면 그 사실을 반환한다. 이것은 검사 합격을 요구하는 새 관문이 아니라 게시 바이트와 쓰기 주체의 일관성이다.

재기동을 넘어야 하는 종료·회수는 기존 외부 worker/keeper가 맡는다. 죽을 프로세스의 후속 계획에 청소를 맡기지 않는다. 재접속은 task_ref·generation·인증된 소유자를 확인하고, PID나 포트만으로 동일 실행이라고 간주하지 않는다. 모든 workerd를 죽이거나 다른 작업의 서버를 재사용하지 않는다. 폰·Windows 등 미지원 조합은 기존 capability 응답으로 밝히며 동기 또는 기존 원격 실행 경로를 유지한다.

## 6. R2 — 효과·실행 오류·검사 결과를 구별해 보존한다

### 정리 오류가 최초 결과를 가리지 않게 한다

`script_process`와 세션 worker는 먼저 최초 결말과 확보 출력을 보존하고, 정리는 독립적으로 끝까지 시도한다. timeout·취소·실행 실패를 cleanup의 PermissionError로 덮지 않는다. 정리 실패를 삼키지도 않는다. 기존 결과의 diagnostics에 단계·errno·종료 확인 여부를 붙여 살아 있을 수 있는 프로세스를 드러낸다. 자식 목록 조회·개별 종료·그룹 종료 각각의 실패가 다른 소유 자식의 정리 시도까지 막지 않게 한다.

`repair_live_probe.failure_kind`의 몇 가지 문자열을 계속 늘리지 않는다. 생성·실행·관측·정리 중 어디서 발생했는지 아는 생산자는 그 구조화된 사실을 내보낸다. 임의 프로그램 stderr만 있는 경우 원문과 미분류 상태를 유지한다. 환경 실패라는 분류가 테스트 통과나 권한 우회의 근거가 되지는 않는다.

### 이미 일어난 효과와 후속 실패

편집 접수증은 해당 편집을 증명하며 뒤의 IBL 변환 성공까지 증명하지 않는다. 변환 실패도 앞선 편집을 취소하지 않는다. 기존 IBL 원장의 completed calls·partial·`details.tool_result`, 파일 변경 영수증, `source_complete`와 원문 참조를 Situation/recovery에 연결한다. 기존 경로에서 소실되는 부분이 재현될 때만 연결을 고친다.

`operation_effects.py`는 생산자의 효과 관측과 미확인을 표현하는 기존 계약이다. 모든 명령의 exit 0을 효과 확인으로 바꾸거나 새 효과 목록을 병렬로 만들지 않는다. [11월 8일 수리 §17](REMOTE_OPERATION_EFFECT_FEEDBACK_DESIGN_2026_11_08.md#17-think-잔여-조회-조사와-표시-경로-단순화-2026-11-08)의 별도 실패 인덱스 제거 방향을 유지한다. 소비자는 기존 원문 참조로 필요한 부분을 읽을 수 있어야 하며, 모든 호출 뒤 재독을 강제하지 않는다.

### 실행 성공과 검사 판정

일반 셸의 exit code는 실행 결과다. 검사의 통과·실패는 실제 검사 생산자의 계약으로 판단한다. 복합 셸의 마지막 `print`가 exit 0이었다는 이유로 앞선 검사가 통과했다고 올리지 않는다. `repair_test_results`가 해석할 수 없는 복합 명령을 unverified로 남기는 것은 올바른 한계다.

기존 pytest/JUnit 등 지원 보고서와 `webapp_work`의 argv 실행·로그·설정 지문을 활용한다. 웹앱 어댑터에는 필요할 때만 선언된 보고서 경로/형식의 해석을 보완한다. 임의 stdout의 PASS 문자열을 코어가 판정하지 않으며, 모든 셸 명령에 공통 테스트 형식을 강요하지 않는다. 보고서가 있으면 실행 exit code와 함께 cases·누락/차단 범위·보고서 참조를 전달하고, 충돌하면 어느 관측이 충돌했는지 남긴다. 기존 status 필드를 무리하게 전역 개명하지 않는다.

프로젝트 검사 생산자는 각 사례 결과를 점진적으로 저장해 중단 때도 완료·실패·미실행을 구분할 수 있게 한다. 한 사례의 timeout 뒤 전체 결과가 사라지지 않도록 기존 테스트 프레임워크의 fixture·reporter를 사용한다. 근거에 실행 ID·대상 판본·입력 방식·환경 전제·검사 구현 판본을 연결한다. 실행 시작 뒤 대상 파일이 변했다면 옛 지문만 붙여 완료 증거로 쓰지 않는다.

`verify_floor_walk.py`·`verify_civic_rooms.py`의 실패/0건 exit code 수리는 기준 커밋에서 이미 별도로 기록됐다. 이를 아직 없는 기능처럼 다시 구현하지 않는다. 새 문 검사처럼 실패를 출력만 하고 exit 0으로 끝나는 생산자는 해당 프로젝트에서 고친다. 복합 셸의 상태 은폐와 중간 보고서 유실은 별도 남은 문제다.

## 7. R3 — 검사를 전제와 변경 영향에 연결한다

사용자의 조건은 유지하고 최초에 고른 검사 방법은 갱신할 수 있어야 한다. 기존 의식 인계의 목표·criteria·접근 힌트와 실행자의 계획/진행에 이 구분을 유지한다. 자동 생성한 검사 목록에 사용자 명시 요구와 같은 권위를 부여하지 않는다. 현재 프롬프트에도 방법의 잠정성은 있으므로 새로운 의무 목록을 덧붙이지 않는다. 실제 인계에서 조건이 강화되거나 출처가 사라지는 경로가 재현되면 그 전달을 수정한다.

검사 전제는 해당 검사 생산자가 소유한다. 페이지 준비, API 응답, 방 진입이 성립하지 않으면 그 전제를 한 번 판정하고 의존 사례를 blocked/미실행으로 기록한다. 독립 사례는 계속할 수 있다. 무조건 기다리는 시간을 늘리기보다 원인이 바뀌었을 때 필요한 부분을 다시 실행한다. 전체 의존 그래프를 core에 새로 만들 필요 없이 프로젝트 fixture·기존 실행 계획으로 표현한다.

5958에 적용하면 문 열림·닫힘을 먼저 확인하고, 공통 입장 코드의 변경 때문에 관련 방 진입·이동 검사를 수행한다. 뉴스 API가 로컬에서 503이면 그 방의 하위 검사는 전제 실패로 남기고, 허용된 다른 환경이나 실제 의존성을 복구한 뒤 확인한다. mock 결과는 mock 범위의 증거이며 실제 서비스 검증을 대신하지 않는다. 정상 방·독립 입력 방식의 유효 결과는 보존한다.

결과 재사용은 근거의 대상·판본·입력·환경 전제·검사 코드가 현재 질문에 유효할 때 가능하다. 일부가 바뀌면 영향 있는 부분만 다시 확인할 수 있도록 참조를 남긴다. 매 명령마다 전체 저장소 해시를 계산하거나 전역 통과 캐시를 새로 만들지 않는다. 기존 `VerificationCache`를 모든 검사 합격의 권위로 확대하지 않으며, 사용자가 명시적으로 다시 검사를 요청한 호출은 실제 실행한다.

모델이 충분한 정보를 받고도 반복한다면 전달 계층 수정의 성공과 판단 개선의 실패를 구분한다. 별도 감독자·자동 재각성·계획 승인 루프를 추가하지 않는다. 목표 충족과 남은 불확실성으로 종료 여부를 판단하는 기존 실행·최종 비교 책임을 유지한다.

## 8. 구현 순서와 제거할 경로

| 순서 | 구현 단위 | 동시에 제거·축소할 것 | 완료 조건 |
|---|---|---|---|
| R0 | 대상 판정부터 모든 실행 소비자까지 문맥 전달 | grant만으로 정한 셸 사본 선택, 서로 다른 기본 루트 설명 | 같은 대상 편집/실행 일치, 기존 권한 회귀 유지 |
| R1 | 기존 세션에 문맥·환경·수명·종료 연결 | 수리 session 일괄 거절, 환경 준비 중복 | 장시간 실행의 관측·취소·적용 경계 입증 |
| R2 | 원출력/효과 보존, 검사 보고서 소비 | cleanup에 의한 최초 오류 은폐, 실행 성공을 검사 성공으로 올리는 분기 | 부분 실패의 원인·효과·미실행 범위 보존 |
| R3 | 검사 전제·부분 결과와 실제 인계 검증 | 전제 부재 뒤의 고정 대기, 재현된 인계의 방법 강제 | 관련 회귀 품질 유지, 처음 보는 작업에서도 선택 개선 확인 |

R2의 오류 보존은 R0/R1과 독립적으로 먼저 구현할 수 있다. R3의 장시간·부분 재개 검증은 R1/R2를 사용한다. 단계별로 실행 가능한 변경으로 끝내고 통합 전 임시 복사·다른 런처를 영구 경로로 남기지 않는다. 현재의 승인·격리·후보 반영 규약을 제거해 속도를 얻지 않는다.

기능 인수와 성능 주장을 분리한다. 연결 결함의 수정은 계약 시험으로 판단할 수 있지만, 시간·토큰 절감률은 실제 비교 결과로만 적는다. 11월 8일 원문 전달 단순화에서도 실제 THINK 평균 비용은 증가했다. 이번에도 스키마 개선만으로 모델의 재조회·오판이 줄었다고 결론 내리지 않는다. 품질 저하가 있으면 성공으로 집계하지 않고, 표본·환경 편차와 미개선 사례를 남긴다.

## 10. 배포·되돌림·현재 완료 범위

이 수리는 권한과 실행 기반에 닿으므로 승인된 외부 개발 경로에서 구현한다. 이 문서를 읽은 작업 중 에이전트가 자기 변경 금지 경계를 우회하는 근거로 삼을 수 없다. 신규 레지스트리나 DB 마이그레이션은 요구하지 않는다. 세션 메타데이터 추가 필드는 기존 저장소에 호환 가능하게 두고 구형 기록은 기존 의미로 읽는다.

새 문맥 계약은 새로 시작한 호출·세션부터 적용한다. 기존 실행을 중간에 다른 루트나 넓은 권한으로 옮기지 않는다. 배포 전 활성 작업을 확인하고 기존 keeper의 전환 절차를 따른다. 되돌릴 때는 새 계약 세션을 소유자 경로로 종료·회수하거나 완료시킨 뒤 코드 판본을 되돌린다. 구형 worker가 새 문맥을 이해하지 못하는 세션을 임의 재시작하지 않는다. 운영 산출물·원장·사용자의 미커밋 파일은 되돌림 대상이 아니다.

최초 설계 커밋은 `87a251e0`이며 런타임 변경이 없었다. 아래 기록은 후속 구현 요청에 따른 변경이다.

## 11. 구현과 검증 기록 — 2026-11-09

### 구현 범위

- **R0:** 기존 `repair_tool_scope`가 명시 cwd와 소유권을 판정하고 `code_analysis_scope`로 결속한다. 정본 파일 프로젝트·현재 후보·이미 발행된 외부 작업 범위를 구분한다. 파일 실행은 상위 수리 사본 문맥을 해제한 좁은 OS 쓰기 범위에서 수행한다. 후보 실행은 명시한 하위 cwd를 검사기에 전달한다. 링크·제한 grant·취소·활성 확인 단계의 경계는 유지했다. 정본 셸의 보호 파일 이름은 `program_boundary` 한 벌에서 파생해 OS 정책에도 적용한다. 내용 전체 지문 대신 필요한 경로·하드 링크 검사를 수행한다.
- **R1:** 수리 session 거절을 제거하고 기존 process worker에 대상·수리 판본·취소 경로를 연결했다. 환경은 기존 `repair_process.prepare`로 준비하고 실제 프로젝트의 Node·표준 캐시/설정 경로를 사용한다. 외부 서비스 자격 증명은 자식 환경에만 전달한다. 짧은 Unix socket 경로의 runtime은 worker가 실행 수명 동안 소유한다. 동일 request_id의 대상/세대 충돌, 출력 cursor, 기존 task 수명과 제어 계약을 유지한다. 적용·폐기에서는 기존 잠금 안에서 해당 후보의 세션 종료를 확인한다.
- **R2:** `script_process.stop_tree`로 종료 처리를 공유하면서 정상 종료 유예·강제 종료·정리 오류를 구분했다. timeout/취소의 부분 출력과 원실패는 정리 실패로 덮이지 않으며 중첩 bridge·검사 영수증에도 전달한다. 종료 미확인이면 runtime을 보존하고 적용을 진행하지 않는다. 임의 stderr만 있는 실패는 unknown으로 남긴다. 웹앱의 기존 argv 검사에는 선택적 JUnit 보고서 소비를 추가했다. 오래된 보고서·0건·전건 건너뜀·보고서와 종료 코드 충돌은 통과로 올리지 않는다.
- **R3:** 기존 수리 교재의 무조건 같은 사본 문구를 대상별 실행 계약으로 교체했다. 사용자 조건·잠정 기준의 출처는 기존 인계가 이미 보존하므로 새 판단 규칙을 추가하지 않았다. 편집 성공 뒤 catch된 변환 실패는 기존 원장·상황 관측에서 회수되는 것을 실제 IBL로 확인했다. 추가 효과 저장소·실패 목록·감독 호출은 만들지 않았다.

개인 웹앱의 기존 세 검사(`verify_civic_doors.py`, `verify_floor_walk.py`, `verify_civic_rooms.py`)에는 프로젝트 안의 작은 `verification_support.py`를 공유하게 했다. 실행 ID·소스 판본·계획 사례와 완료/미실행을 JSON/JUnit에 점진적으로 기록한다. 방 진입이 대체 화면으로 끝나면 하위 검사를 차단 상태로 보존하고 다음 독립 사례로 넘어간다. 문 검사는 실패·0건·페이지 오류를 종료 코드에 반영한다. 이 네 파일은 기존 비추적 개인 프로젝트 `data/outputs/3d-blog/scripts/`에 반영했으며 제품 core·어휘로 편입하지 않았다. 원본 세 파일은 `data/_backups/2026-11-09_execution_context_checks/`에 보존했다.

### 한계와 검증 진행상의 교정

세션은 전경 프로세스의 수명을 관리한다. 설치된 Astro는 에이전트 환경에서 자체 daemon을 만들 수 있어, 로컬 CLI 구현을 확인하고 프로젝트 명령의 `--ignore-lock` 전경 옵션으로 검사했다. 처음 이 검사에서 만든 daemon은 PID·생성 시각·명령·프로젝트를 대조해 정리했다. core에 Astro 예외를 넣지 않았다. 정리 영수증의 범위도 `process_group_and_observed_descendants`로 명시한다. 외부 서비스에 위임하거나 소유 관계를 이탈한 daemon 전체의 종료를 보장하지 않는다.

첫 전수 검사는 파생물 갱신과 코드 편집이 겹쳐 중단했다. 당시 DEFINITION_CHANGED 등 20실패/6582통과/3건너뜀은 최종 결과가 아니다. 후속 고정 판본 전수는 12811통과/24건너뜀/3실패까지 진행했으나, 폐기 경로에 추가한 중복 application 잠금으로 교착되어 중단했다. 호출자가 이미 잡는 기존 잠금을 재사용하도록 중복 획득을 제거했다. 실패 중 두 건은 폐기된 “무조건 같은 사본” 교재 문구를 요구해 승인된 대상별 계약으로 갱신했고, 나머지는 기존 사용자 등록부의 미추적 스크립트 감사 실패다. 이 결과도 최종 완료 증거로 사용하지 않는다. 설계가 줄이려는 낭비를 구현 과정에서도 피하려면 검사 실행의 입력 판본이 먼저 고정되어야 한다는 진행 순서 오류였다.
