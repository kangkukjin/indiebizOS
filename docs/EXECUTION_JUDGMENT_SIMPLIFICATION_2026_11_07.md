# 실행자의 결과 판단과 선택적 독립 검토

사용자 요청(2026-11-07): AI가 판단할 일을 규칙으로 쌓지 말고, 실행자가 결과를 확인하여
마치도록 수정한다. 기준이 존재하면 자동으로 별도 심사를 시작하던 기본값을 제거한다.

## 변경

- `achievement_criteria`와 `criteria`는 실행자가 사용할 완료 기준이다.
  `independent_review`는 의식이 필요성을 판단하여 선택하는 불리언이며 기본 false다.
  주인·회원, 감독 유무, 후속 규정 패치가 같은 선택을 따른다. 도메인·위험도 분류표는 추가하지 않는다.
- 선택하지 않은 작업은 실행 AI의 확인과 응답으로 종료한다. 별도 평가 입력 조립·모델 호출·평가
  재시도가 없고 `review_status=NOT_RUN`을 남긴다. 미검토를 승인·목표 달성으로 기록하지 않는다.
  연구 대화의 보존 자료 준비는 기존 저장 책임으로 유지한다.
- 별도 검토를 선택한 경우 검토자의 자연어 피드백을 보존한다. DEFECTS JSON이 없다는 이유로
  NOT_ACHIEVED를 UNKNOWN으로 바꾸거나 산문을 삭제하지 않는다. 권한 관련 단어와 별도 인용
  서식 부재만으로 UNKNOWN을 REWORK로 뒤집던 재판정도 제거한다.
- 평가 프롬프트의 사례별 판정 지침과 중복 규정을 줄였다. 결과물 가이드에서 고정 검수 절차와
  파일 영수증 작성·판정 서식을 일상 실행자의 의무처럼 설명하던 내용을 걷어냈다.

새 감독자·상태 기계·데이터베이스·도구는 추가하지 않는다. 실행 권한, 취소, 도구 결과와
외부 전달의 기록·무결성, 수리 적용 영수증은 유지한다. 진행 중 검토 checkpoint와 이미
요구된 완료 검토는 기존 판본·재개 계약으로 마친다. 미검토 종료에서 발생한 전달 오류나
PENDING_APPLY/수리 영수증 결과를 파이프라인의 NOT_RUN 기본값으로 덮지 않는다.

## 범위

독립 검토를 선택했을 때의 기존 원샷·불변 원문 회수 경로는 유지한다. 이를 새 도구형 검토
에이전트로 교체하지 않았다. 자동 검토를 제거한 효과와 선택적 검토 자체의 자료 전달 한계는
구분한다. shell stdout의 혼합 JSON 영수증을 파싱하는 새 추정 규칙은 추가하지 않는다.

실행자에게 모든 판단을 맡긴다는 이유로 검증을 생략하도록 지시하지 않는다. 결과 확인의
방법·깊이·보완·종료를 AI가 실제 관측에 맞춰 판단한다. 기존 판정 기록은 수정하지 않는다.

## 검증

실제 파이프라인의 감독 유무와 THINK/EXECUTE 등
각 진입에서 독립 검토 선택 유무를 비교하고, 실패 도구 이력이 자동 심사를 켜지 않는지 확인했다.
혼합 JSON+본문 셸 출력도 별도 제출 증빙을 만들지 않고 종료하며, 자연어 결함 의견은 실행자에게
전달되고 실제 전달 실패·중단된 검토 재개는 보존된다. 이전 응답의 승인 상태를 다음 미검토
응답이 이어받지 않는 것도 확인했다. 마지막 상태 격리 수정 후 직접 관련 293개와 대화·수리
재개 관련 75개 검사를 통과했다.

운영 파이프라인의 훈련 실행(에피소드5881, `task_sysai_2749fb74`)에서 실제 의식이
`independent_review:false`를 선택했다. 실행자는 입력을 계산해 보고서를 저장하고 재읽었다.
전체 달성률 96%(240/250)와 인과 효과를 알 수 없다는 해석을 확인했으며 독립 평가 호출은
0회, 작업은 정상 종료했다. 실행 기록과 결과는
`outputs/diagnostics/2026-11-07-autonomy/execution-evidence.json` 및 `result.md`에 있다.

간결한 검토 지침을 실제 `gpt-6-astra:high`에 적용한 두 시험에서 정상 보고서는 APPROVED,
원문의 '실적 미확인'을 '100건 확정'으로 바꾼 보고서는 REWORK였다. 각각 1회 호출이며
DEFECTS JSON 없이 자연어 결함 의견을 전달했다. 원문은 변경되지 않았다.
증거는 같은 폴더의 `review-results.json`이다. 이는 두 사례의 동작 확인이며 이전 버전과의
동일 과제 성능·비용 비교 또는 일반 정확도 측정은 아니다.

system 포함 전수는 12783통과·24건너뜀·1실패였다. 실패는 수리 테스트의 가짜 제어기에
`evaluation_enabled` 속성이 빠진 것이었다. 실제 제어기와 맞추고 해당 파일 및 수리 재개
86개 검사를 다시 통과했다. 전수 실행을 시작한 뒤 추가한 응답 상태 격리는 위의 293+75개로
검증했다. 마지막 시험 설정 수정 뒤 전수를 다시 돌리지는 않았다.

Android 본문 번들, IBL 정합, 의식 출력 스키마와 backend 층 검사를 통과했다.
운영 백엔드는 07:07 KST에 ACTIVE/healthy이며 변경한 운영 모듈 10개의 활성 소스가 일치했다.
