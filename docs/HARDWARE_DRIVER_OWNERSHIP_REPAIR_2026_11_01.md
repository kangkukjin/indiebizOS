# 하드웨어 드라이버 소유 구조와 프롬프트 수리계획

작성일: 2026-11-01. 구현: 코드·가이드·UI 반영. 검증 범위와 미검증은 §10을 따른다.
아래 §1~9는 계획 시점의 요구사항이며, 구현 결과는 §10에 기록한다. 기기 배포·설치는 수행하지 않았다.

하드웨어의 제어 프로그램, 호출 계약, 사용 설명, 설치·업데이트 정보를 해당 드라이버의 책임으로 모은다.
현재 ‘헬퍼’라고 부르는 프로그램은 대상 기기에서 실행되는 드라이버 구성요소다. 같은 종류의 기기는
구현과 배포물을 공유하고, 설치 판본과 업데이트 완료 여부는 개별 기기에서 확인한다.

이 계획은 [기존 제어 드라이버 설계](CONTROL_DRIVER_DESIGN_2026_10_20.md)의 발견·호출·검증·복구 구조를
설치와 배포까지 연결한다. 목적은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)에 따라 판단에 필요한 정보를
유지하면서 초기 입력, 추가 조회와 반복 작업을 함께 줄이는 것이다. 에이전트의 방법 선택을 절차 목록으로 대체하지 않는다.

## 1 현재 구조와 수리할 지점

| 현재 구현 | 이미 있는 능력 | 수리할 지점 |
| --- | --- | --- |
| guide_db.json, guide_registry.py | OS·조작면·호출명에서 가이드와 빠른 호출 절을 발견 | 제어 설명과 대상 실행 프로그램·업데이트 경로의 소유 연결 |
| associative_recall.py의 장치 소개 | control_guide와 control_brief 제공, 이미 제공한 요약 중복 제외 | 한 장치의 OS 제어·원격 작업·관리 서비스가 공유하거나 달리 갖는 부품 표시 |
| prompt_builder.py | 의식이 선택한 주 가이드 전문을 턴 문맥에 주입 | 원격 작업마다 guest_helper.md 전체가 다시 초기 입력이 되는 구조 |
| resident_pcs.py | OS·아키텍처·구형 Mac 빌드에 맞는 실행파일 선택, 대상 PC별 업데이트 | 드라이버 설명과 배포 상태가 떨어져 있고 선택 규칙 일부가 코드에 고정됨 |
| phone_updates.py | ABI·SDK·서명·판본을 확인하는 대상 폰별 APK 업데이트 | PC와 같은 드라이버 발견·상태 표면으로 연결하되 Android 설치 의미 유지 |
| guide_feedback.py | 사용한 가이드에 실측 기록 자동 추가 | 개별 관측이 매번 주입되는 설명으로 누적되고 기존 본문과 모순될 수 있음 |

PC 업데이트와 폰 업데이트는 이미 기기별이다. 이를 새 기능으로 재구현하지 않는다.
Mac 서명 배포, Windows 교체 감시, Android 설치 승인과 재접속 검증은 기존 구현을 사용한다.

최근 실제 입력에서 guest_helper.md 전문은 약 20,800자, 선택 액션 상세 계약은 약 12,700~15,200자였다.
메타데이터 축약으로 마지막 실행자 입력에서 줄어든 문자는 #5657 0.2%, #5658 2.1%, #5659 1.1%였다.
이는 저장된 동일 결과의 이전 표시 방식을 복원한 문자 비교이며, 전체 비용의 전후 실험은 아니다.
이번 수리는 이보다 큰 가이드 전문과 상세 계약의 선제 주입을 우선 대상으로 한다.

## 2 책임과 저장 위치

| 책임 | 소유자와 정본 |
| --- | --- |
| 무엇을 달성할지, 어떤 방법을 조합할지 | 사용자 목표와 에이전트 판단 |
| 대상 식별·인증·접속·작업 영수증·전송·취소 | 기존 손발 공통 기반: limb_keys, resident_store, phone_jobs, 전송 모듈 |
| 어떤 기기·조작면에서 어떤 부품을 쓸 수 있는지 | 드라이버 등록 데이터와 실제 기기가 보고한 능력 |
| 동작·인자·결과·실패·복구 계약 | 기존 액션·저장 함수·스크립트 정의. 가이드는 사용 이유와 연결 설명 |
| 대상에서 실행할 프로그램과 호환 조건 | 해당 드라이버가 참조하는 배포 매니페스트·설치 어댑터 |
| 설치된 판본·권한·현재 상태 | 기기 ID와 설치 세대에 묶인 기존 등록·관측 원장 |
| 기기별 실측과 적용 조건 | 기존 control_observations와 실행 기록. 검증된 일반 사실만 가이드 개정 |

등록 데이터는 기존 data/guide_db.json을 확장해 드라이버 연결의 단일 출처로 삼는다.
가이드 항목에 연결되는 드라이버 식별자, 조작면/플랫폼·실행 모드 조건, 기존 호출명, 문서 절,
실행 부품 참조, 배포·업데이트 구현 참조를 둔다. 현재 control_platforms·control_callables 등은
호환 입력으로 읽되 새 데이터와 서로 다른 매핑을 손으로 유지하지 않는다. 충돌은 발견 단계에서 드러낸다.

배포 파일의 해시·서명·판본을 guide_db에 복사하지 않는다. 기존 PC release/dist 및 폰 release 매니페스트를
참조하고, 해당 설치 구현이 실제 배포물을 검증한다. 변경 가능한 경로나 임의 셸 명령을 등록 데이터만으로
실행시키지 않고 기존 등록된 실행 부품과 업데이트 구현에 연결한다.

한 기기는 여러 조작면을 제공한다. PC의 OS 제어, 원격 실행·전송, Windows 무인관리는 서로 다른 호출 범위를
가지며 같은 바이너리를 공유할 수 있다. 여러 논리 드라이버가 공유하는 바이너리는 실제 설치 단위로 한 번
갱신하고 그 영향을 함께 표시한다. 기능별로 가짜 독립 판본을 만들지 않는다.
일반 사용자 헬퍼와 무인관리 서비스의 신원·권한·설치 세대는 합치지 않는다.
합치지 않는 것은 이 셋뿐이다. 주인과 AI가 지명하는 단위인 손발은 하드웨어 하나이며, 관리 서비스는
같은 PC의 사용자 세션 등록에 딸린 통로로 묶어 한 행으로 보이고 중앙이 작업을 통로에 나눈다
(2026-11-11 보완 — 두 등록이 손발 둘로 드러나던 결함 수리, `helper/README.md` '한 PC, 손발 하나').

TV처럼 대상에 프로그램을 설치하지 않는 드라이버는 허브 실행 부품만 갖는다. Android 제어 부품이 APK에
묶여 있으면 업데이트 단위는 APK다. 기능별 독립 배포가 필요할 때에만 별도 모듈화를 검토한다.

## 3 guest_helper.md 내용 이관

| 현재 내용 | 이관할 자리 | 초기 입력에 남길 내용 |
| --- | --- | --- |
| 대상·상주/휴대 구분, 연결 상태 해석 | 짧은 공통 입구와 실제 장치 소개 | 선택한 대상의 모드·접속·권한 관측과 조회 경로 |
| 음량·화면·앱·전원·재생 제어 | 기존 pc_control.md, android_control.md, tv_control.md의 해당 조작면 | 기존 빠른 호출 요약 |

| 함수 인자 표·긴 호출 예제 | 기존 describe·스크립트 계약·실행 기억 | 같은 계약을 가이드에 수동 복제하지 않음 |
| 실측 기록 | 대상·드라이버·판본·관측 시점이 붙은 기존 관측/기억 | 관련되는 관측만 필요할 때 조회 |

새 문서명은 구현 시 생성할 예정이며 현재 존재하는 문서로 안내하지 않는다.
공통 원격 실행 설명은 플랫폼마다 복사하지 않고 공유한다. Windows 권한이나 Mac 서명처럼 다른 사실만
해당 설치 절이 소유한다. 본체 설치 프로그램의 업데이트와 원격 제어 부품의 업데이트도 구분한다.

guest_helper.md는 기존 이름으로 찾아오는 호출을 위한 짧은 입구로 유지한다. 기존 링크·가이드 조회가
깨지지 않도록 이관된 설명의 주제와 조회 경로를 제공한다. 전문을 다른 한 파일에 그대로 옮기지 않는다.

## 4 발견과 문맥 전달

장치 소개 → 드라이버의 짧은 호출 요약 → 필요한 동작·설치 절 조회 → 실행 결과의 확인·복구 참조로 연결한다.
장치가 없는 설치 전 단계는 등록/설치 주제에서 같은 드라이버 자료를 발견할 수 있게 한다.
오프라인 장치도 등록된 드라이버 정보를 찾을 수 있지만, 마지막 관측을 현재 접속이나 권한으로 바꾸지 않는다.

guide_registry에 가이드 항목별 전달 방식을 두어 드라이버 소유 문서는 입구·요약을 제공하도록 한다.
prompt_builder는 주 가이드라는 이유만으로 이 문서들의 전문을 주입하지 않는다. 추가 가이드 후보가 전부
펼쳐지지도 않는다. 일반 가이드의 기존 전문 제공 정책은 이번 범위에서 일괄 변경하지 않는다.

선택 액션의 상세 계약도 함께 다룬다. 원격 작업용 큰 액션의 모든 op 정의를 미리 붙이기보다 이미 제공된
드라이버 호출 계약·실제 선택한 op와 그 조회 참조를 전달한다. 인자가 부족한 경우 기존 describe/section
조회가 완결된 계약을 돌려준다. 필수 인자·권한·실패 의미를 문자 수에 맞추어 자르지 않는다.

OS별 드라이버가 있다는 이유로 작업에 불필요한 설치·교체 절까지 싣지 않는다. 여러 기기가 같은 드라이버를
공유하면 소개 안에서는 계약을 한 번 제공하고 대상 정보만 구분한다. 현재 OS별 대표 가이드 한 개 매핑은
호환 유지하면서 조작면별 추가 연결을 허용한다. 과거 문맥 재사용은 기존 지문·판본 대조를 따른다.

초기 입구의 설계 예산은 약 2,000자 이내를 목표로 잡고, 기존 드라이버 요약과의 중복을 제거한다.
이는 검증할 목표이지 설명을 침묵 절단하는 런타임 제한이 아니다. 추가 조회·후처리까지 포함해 실제 절감을 측정한다.

## 5 기기별 업데이트와 관측

장치의 드라이버 정보에서 설치 부품, 현재 관측 판본, 호환되는 배포판, 업데이트 방법과 필요한 OS 승인을
볼 수 있게 한다. 실제 선택은 OS·아키텍처·OS 지원 범위·설치 모드·프로토콜·서명에 근거한다.
지원 여부가 관측되지 않았으면 미확인으로 제공한다. 버전이 다르다는 사실만으로 설치를 자동 실행하지 않는다.

기존 PC update_helper와 폰 phone_updates.submit을 드라이버의 업데이트 진입점으로 연결한다.
호출은 대상 device_id·설치 세대와 배포 지문에 결속한다. 업데이트 도중 재등록·판본 변경이 생기면
예전 대상을 계속 갱신하지 않고 재조회한다. 공개 API와 기존 self:limb 호출은 호환을 유지한다.

전달·설치 승인 대기·교체·재접속·검증을 구분하고, 기기가 보고한 새 판본 및 필요한 동작 확인으로 완료를 판정한다.
PC 교체 감시자의 복구와 Android 설치 상태는 그대로 사용한다. 기기마다 다른 복구 가능성도 드러낸다.
중앙 등록 정보만 새 판본으로 써서 완료시키지 않는다. 공유 바이너리 교체가 진행 작업에 미치는 영향은
그 설치 구현의 대기·인계 계약으로 처리하며, 원격 연결 단절만으로 작업을 재실행하지 않는다.

UI도 선택 기기의 드라이버 구성요소와 업데이트 상태를 같은 응답에서 읽도록 한다.
‘헬퍼 교체’라는 이름 변경보다 실제 대상으로 향하는 업데이트·완료 확인의 일치를 먼저 구현한다.

## 6 실측 기록이 다시 프롬프트를 키우지 않도록 하기

드라이버 소유 가이드의 자동 관찰 추가는 본문 덧붙이기 대신 기존 관측 저장 경로로 보낸다.
기기별 사실은 해당 장치 관측에, 일반 구현 결함·사용 지식은 기존 기억 또는 가이드 피드백 제안에 둔다.
한 기기의 실패를 모든 하드웨어의 금지 규칙으로 승격하지 않는다.

가이드 일반 사실을 개정할 때는 기존 본문과 판본·적용 범위를 대조하고 같은 설명을 교체한다.
현재 guest_helper.md의 ‘UAC 보안 화면을 조작할 수 없다’와 ‘가이드에는 이 제약이 없다’처럼 모순된
실측은 근거를 보존하면서 중복·잘못된 단정을 정리한다. 이관 도중 새로 쌓인 피드백도 원문 지문으로 대조해 누락하지 않는다.

## 7 구현 순서와 완료 조건

## 10 구현과 검증 기록 (2026-11-01)

1~3단계의 코드·가이드·UI를 정본에서 구현했다. 4단계의 호환 회귀와 입력 조립 재생은
아래 범위로 수행했다. 실제 모델의 전체 비용 비교 및 새 배포물의 실기 설치 인수는 별도 미검증이다.
이번 작업은 PC 실행파일·폰 APK를 발행하거나 기기에 설치하지 않았다.

### 연결과 전달

- `guide_db.json`의 `driver`가 플랫폼·어댑터·조작면·호출명·빠른 호출 절을 소유한다.
  `driver_components`가 설치 단위의 구현·배포 참조·업데이트 어댑터·승인 조건을 소유한다.
  기존 `control_*` 입력은 계속 해석하되 새 필드와 충돌하면 경고·충돌 응답을 내고 선택하지 않는다.
  등록 데이터의 명령이나 경로를 실행하지 않는다. 서비스 코드가 기존 두 업데이트 어댑터를 명시 호출한다.
- PC OS 제어·원격 실행·설치는 사용자 세션 부품을 공유한다. Windows 관리 서비스는 별도 설치
  부품이며, 그 행에는 사용자 세션 OS 제어를 소개하지 않는다. Android 두 조작면은 APK 하나,
  TV는 허브 실행 부품 하나다. 오프라인 장치·설치 전 가이드 발견은 접속·권한 확인을 뜻하지 않는다.
- 기존 `guest_helper.md`는 짧은 입구다. 실행·전송은 `remote_pc_execution.md`, 설치·등록·권한은
  `remote_pc_installation.md`, 범용 화면·입력은 `pc_control.md`로 이관했다. 기존 함수의 인자표를
  반복 유지하지 않고 describe 계약을 참조한다. 실행 가능한 예제 9개는 실행 가이드에서 계속 검사한다.
- 드라이버 가이드는 주 가이드여도 지정된 입구 절만 자동 전달한다. 일반 가이드 전문 정책과 명시적
  read_guide/describe의 전체 계약은 유지한다. 큰 원격 액션의 선제 전문은 호출·가이드 조회 참조로 바꿨다.
  파일 본문뿐 아니라 등록 매핑 변경도 catalog_revision을 바꾼다. 절 조회는 fenced code의 `#` 주석을
  제목으로 취급하지 않아 예제 뒤의 실패·복구 조건을 보존한다.

### 업데이트와 피드백

- `resident_pcs.devices`, `self:limb list`, 손발 UI가 같은 `drivers` 응답을 읽는다. 기존 helper·phone_update
  필드는 호환 유지한다. UI는 설치 부품·공유 드라이버·설치 세대·판본·승인 조건과 교체/재접속 단계를 표시한다.
- PC·APK 요청은 device_id·installation_id·generation·현재 호환 관측·배포 지문을 고정하고 전송 후
  접수 잠금 안에서 재검사한다. 바뀌면 `driver_update_changed`로 재조회를 요구한다. UI는 조회한 expected를
  전달하고, 기존 target-only API·IBL도 요청 시작 시점부터 같은 결속을 사용한다. 진행 작업 조회는 설치 세대를
  구분한다. PC의 요청 직렬화와 기존 폰 잠금은 같은 대상의 중복 교체를 막는다.
- PC의 기존 교체 감시·되돌리기, Mac 서명 배포, Android의 ABI·SDK·서명·설치 승인·재접속 신고를 재사용한다.
  기기의 새 지문 신고와 실제 동작 검증은 별도다. 중앙 등록 판본을 임의로 수정해 완료시키지 않는다.
- 드라이버 가이드 피드백은 전문에 자동 추가하지 않는다. 실행 근거에 device_id·설치 세대·판본이 명시된
  구조화 관측은 기존 control_observations에 recheck로 보존한다. 귀속할 수 없는 문자열·일반 개선은
  source_hash·원 피드백·실행 근거를 가진 기존 제안 원장에 보존한다. 검토 도중 본문 지문이 바뀌어도 덮어쓰지 않는다.
  이전 실측과 UAC 모순 근거는 [이관 기록](experiments/hardware_driver_migration_2026_11_01.json)에 보존했다.

등록된 여섯 드라이버와 공유 부품의 호출·실행·업데이트 경계를 대조했다. 기기에 새 명령을

### 설명의 역할

사용자 지시에 따라 드라이버 설명은 이 시스템에서 새로 알려주는 정보를 중심으로 정리했다.
준비된 관용구·인수/단위·지원 범위·결과 의미와 기기별 관측은 남겼다. 일반적인 실패 대응,
고정 조회/실행 순서, 특정 사례의 해결법을 모든 상황에 적용하는 행동 지침은 제거하거나
구현의 실제 효과 설명으로 바꿨다. 예를 들어 TV 토글은 재시도 금령 대신 중복 전달의 반전 효과,
PC/Android의 사후 조회는 AI에게 추가 조회를 금지하는 대신 반환에 포함된 관측으로 설명한다.
사람이 정한 기기별 선택과 OS 권한/실행 제한은 일반 상식과 구별하여 보존했다.

여섯 빠른 안내 합계는 4,538→3,197자(29.5% 감소). 전체 본문은 새 업데이트 계약 추가를
포함해 66,429→63,501자다. 문서 문자 수이며 실제 모델 토큰·시간·목표 달성 개선을 측정한 것은 아니다.
