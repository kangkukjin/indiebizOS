# 긴 IBL 프로그램 작성을 위한 도구 도입·연결 계획

2026-09-23. 상태: 조사·계획. 이 문서 작성 단계에서는 패키지 설치나 런타임 변경을 하지 않았다.
목적 정본: [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md).

## 목표와 선정 결론

AI가 긴 프로그램을 작성하고, 실행 전에 오류를 모아서 수정하고, 한 호출로 의도한 작업을
맡길 수 있도록 한다. 함수·관용구를 여러 층으로 조합해도 계약과 진단이 이어져야 한다.
설치 개수나 편집기 외형 대신 작성 성공률·실행 전 탐지율·전체 완료 시간·전체 토큰으로 판단한다.

도입 순서는 **공통 검사·계약 조회 보강 + Hypothesis → 조종실 CodeMirror → 외부 편집기 pygls**다.
AI가 직접 쓰는 공통 지원은 첫 단계의 필수 범위다. IDE를 설치한 사람에게만 검사가 제공되면 안 된다.
IBL 전용 완성 확장은 이번 공개 검색과 저장소 조사에서 확인하지 못했다. 아래는 설치 가능한
기성 기반이며, IBL 연결 코드는 필요하다. 설치만으로 문법·도구 계약을 이해하지는 않는다.

간단한 실행 없는 탐침에서 `return 1 + 2`는 valid, `return $missing`은 위치가 있는 UNBOUND,
`return 1 + "hello"`는 invalid가 아니라 incomplete였다. 마지막 결과를 곧바로 결함으로
단정하지 않는다. 런타임의 텍스트 숫자 관측 의미론과 대조하여, 확정 오류를 미상으로 넘기는 범위를 조사한다.
이번 탐침은 전체 검사기의 건전성·완전성을 증명하지 않는다.

웹 문서의 latest 버전을 검증 없이 운영 의존성으로 고정하지 않는다.

## 1차: AI 작성 지원과 검사 신뢰성

### 1A. 기준선·회귀 표본과 Hypothesis 설치

- 제안 파일 `backend/requirements-dev.txt`에 검증된 Hypothesis 버전을 고정한다.
  프로젝트 .venv에서 설치하고 현재 pytest와의 호환성을 확인한다. 운영·폰 번들에는 포함하지 않는다.
- 현행 문법의 긴 프로그램을 최소 30개 확보한다. 자료 수집→변환→보고서,
  파일 일괄 처리, 기록 업무, 함수·관용구 다층 조합 등을 포함한다.
  코퍼스 원문은 수정하지 않고 출처·판본·입력을 붙인 격리 fixture로 복사한다.
- 각 표본의 정상형과 오류 변이를 만든다. 미정의 값, 분기 한쪽에서만 정의된 값,
  없는 필드, 함수 인자·반환 불일치, 파이프 충돌, 반복 입력 중복, 동적 계약을 구분한다.
- 구 검사의 각 규칙을 **현재 의미에도 적용 / 의미가 바뀌어 대체 / 해당 없음**으로 분류한다.
  새 each는 기본 전건 처리이므로 옛 기본 limit 경고를 그대로 이식하지 않는다.
- Hypothesis는 작은 순수 프로그램·0/1/N행·중첩 함수·분기를 생성한다.
  단순 참조 계산·고정 계약을 오라클로 사용하고 검사기와 실행기가 같은 버그를 공유하는 비교를 피한다.
  외부 도구는 fixture로 대체하며 생성 시험 중 실제 AI·파일 쓰기·메시지 전송을 하지 않는다.

완료: 각 규칙의 현재 적용 여부, 탐지/미탐/오탐 기준선, 재현 가능한 실패 표본이 남는다.

### 1B. 한 벌의 분석과 계약·심볼 조회

- 기존 파서·컴파일러·사전·저장 함수 로더 위에 공통 분석 인터페이스를 둔다.
  CLI/MCP/HTTP/조종실/LSP는 이 결과만 변환한다. 새 문법이나 내용어 이름 목록을 만들지 않는다.
- 지역 함수→저장 관용구→하위 함수→도구까지 인자·반환 구조와 오류의 호출 경로를 추적한다.
  native 계약과 호환 Record/Unknown 경계를 구분하고, 미상인 이유와 남은 실행 시 검사를 설명한다.
- 리터럴에서 확정할 수 있는 식·필드 오류, 분기 합류·반복·함수 반환의 누락을 우선 보완한다.
  숫자 관측 등의 의미는 런타임·공통 의미론과 공유한다.
- 구 규칙 중 유효한 반복 입력 증폭·미사용 연결 등을 현재 AST/계약으로 분석한다.
  의도에 따라 정당할 수 있는 패턴은 근거 있는 경고로 남긴다. 미측정을 0회·안전으로 표시하지 않는다.
- 진단에 rule, severity, source URI/hash, range, 함수 호출 경로, expected/actual,
  구체적 수정 근거를 제공한다. 오류와 경고·미확정을 분리하고 상한 밖 진단 수도 표시한다.
- AI가 필요한 함수의 서명·반환·효과·관련 정의만 조회할 수 있도록 기존 describe/check 계약을 확장한다.
  액션 조회의 기존 의미를 유지하고 함수·위치 조회는 명시적 선택 입력으로 구분한다.
  전체 어휘·관용구 본문을 매 턴 프롬프트에 싣지 않는다.
- 구문 오류가 하나 나도 독립 구간의 진단·후보 조회를 가능한 범위에서 유지한다.
  편집용 복구는 별도 상태로 표시하며, 복구된 불완전 AST를 실행 계획으로 사용하지 않는다.

완료: 정상 fixture 오차단 0, 확정 오류 표본의 기대 진단 충족, 소비자별 같은 진단,
check 경로에서 외부 실행 0. API·CLI·MCP 모두 함수 호출 내부 위치까지 설명한다.

### 1C. AI의 작성→검사→수정→실행 연결

- 긴 프로그램은 전체 소스를 check에 넘기고, 오류를 묶어 받은 뒤 필요한 부분을 수정한다.
  한 오류마다 전체를 다시 생성하는 방식을 피하도록 진단을 설계한다.
- AI가 참조한 계약·저장 함수와 검사한 소스의 지문을 응답에 남긴다.
  변경 후에는 재검사한다. 검사 통과를 권한 승인·업무 성공·외부 효과 안전의 보증으로 쓰지 않는다.
- 첫 단계에는 검사 캐시를 추가하지 않는다. 중복 검사 비용이 유의하면 소스·판본·inputs 타입/값 의존성·
  프로젝트/활성 사전·전이 함수/스크립트 계약 지문을 포함한 재사용을 별도 설계한다.
- 무조건 추가 평가 모델을 부르지 않는다. 정적 분석과 계약 조회 자체는 모델 호출 없이 동작한다.

완료: 긴 프로그램의 오류 여러 개를 한 검사에서 받아 수정한 뒤 한 실행 요청으로 넘기는
시나리오를 재현하고, 오래된 검사 결과의 사용을 거절한다.

## 2차: 조종실에서 같은 지원 사용

설치 대상: `@codemirror/state`, `@codemirror/view`, `@codemirror/commands`,
`@codemirror/language`, `@codemirror/lint`, `@codemirror/autocomplete`.
frontend 의존성과 package-lock을 함께 기록하며 조종실 진입 시 지연 로딩한다.

- 기존 textarea를 편집 컴포넌트로 교체한다. 오류 밑줄·목록 클릭 이동·행 번호·검색·들여쓰기를 제공한다.
- 공통 분석 결과로 액션/인자/함수/범위 내 변수의 완성과 서명·반환 설명을 제공한다.
  색상화·괄호 같은 편집 기능과 의미 검사는 분리한다. 브라우저에 두 번째 의미 검사기를 만들지 않는다.
- 입력 도중에는 최신 문서 버전만 반영하고 오래된 비동기 응답은 폐기한다.
  검사 실패·서버 미연결·incomplete를 초록 통과로 보여주지 않는다.
- 한국어 IME, 한글 변수·함수, 이모지 앞뒤의 위치 매핑, 편집 취소/다시 실행,
  큰 프로그램 붙여넣기를 검증한다. Python 문자열 위치와 JS UTF-16 위치를 구분한다.

완료: 동일 오류가 AI 응답과 화면의 같은 코드 위치를 가리킨다.
TypeScript 검사 및 실제 Electron 조종실 입력·진단·기존 실행 동작을 확인한다.

## 3차: 외부 편집기용 IBL 확장

설치 대상: Python `pygls`와 호환 `lsprotocol`, 확장 프로젝트의 `vscode-languageclient`.
일반 AI 실행·폰 배포의 필수 의존성으로 만들지 않는다. 분석 코어는 LSP 없이도 호출 가능해야 한다.

- 기본 stdio 서버와 얇은 VS Code 확장을 만든다. 우선 diagnostics, hover, signature help,
  completion, definition, document symbols를 연결한다. 이름 변경·자동 포맷·디버거는 뒤로 둔다.
- 프로젝트 경로·활성 사전·판본과 저장 함수 정의를 명시적으로 선택한다.
  기기에 설치한 확장을 다른 기기나 모든 AI가 자동으로 사용한다고 가정하지 않는다.
- 저장 함수는 URI로 원문을 열 수 있도록 연결한다. 읽기 전용 원장 정의를 파일처럼 직접 덮어쓰지 않는다.
- 설치 산출물은 로컬 VSIX로 검증한다. Marketplace 발행은 이 계획의 완료 조건이 아니다.

완료: .ibl을 열어 같은 진단과 함수 서명·정의 이동을 제공하고, 외부 편집기를 닫아도
AI·조종실 검사가 정상 동작한다. LSP 자체를 설치한 사실을 검사 능력 개선으로 계산하지 않는다.

## 효과 측정과 실행 단위

1차의 표본을 기준선으로 고정하고, 수정에 사용하지 않은 별도 과제를 남긴다.
50/200/500문장 및 함수 깊이 1/3/6은 스트레스 시험 후보이며 실사용 분포를 조사해 조정한다.
측정 항목은 첫 작성 검사 통과율, 실행 전 오류 탐지/정상 코드 오차단,
수정 왕복 횟수, 남은 Unknown 경계, 분석 시간 p50/p95와 최대 메모리다.
정적 통과율 상승이 실제 성공률 상승과 같은 뜻은 아니다.

실제 효과 비교에서는 동일 모델·입력·도구·완료 기준으로 사용자에게 쓸 수 있는 결과까지의 시간과
전체 모델 토큰을 측정한다. 기존 코드 검증·fixture 실행과 실제 모델 작성 비교를 구분해 보고한다.
품질 저하·누락을 줄여 얻은 성과와 비용 성과를 각각 기록한다.
분석 성능의 잠정 목표는 로컬 warm 200문장 p95 500ms 이내이며, 콜드 시작·사전 로딩은 별도 계측한다.
목표 미달 시 상한·취소·위치별 조회를 먼저 검토하고 캐시로 오류를 숨기지 않는다.

구현은 1A → 1B/1C → 2차 → 3차 순서의 독립 커밋으로 나눈다.
첫 구현 범위는 **Hypothesis 도입, 구/신 검사 대응표, 공통 진단·AI 조회 보강**이다.
각 코드 변경 시 관련 회귀·정본 빌드 관문을 실행한다. backend 모듈 추가는 층 배정과 폰 번들
규약을 따르고, frontend 변경은 `npx tsc -p tsconfig.app.json`을 통과해야 한다.
완료된 단계와 남은 단계를 구분해 기록한다.
