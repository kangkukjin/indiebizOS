## 방법과 결과

수리 전에 기대값을 고정한 100개의 IBL 문장을 실제 파서·정적 검사·워크플로 실행기·로컬 파일/표 핸들러에 통과시켰다. 파일·쓰기 원장·DB는 임시 fixture로 격리했고 외부 모델·네트워크는 호출하지 않았다. 성공 플래그뿐 아니라 반환값과 타입을 비교했다. 직접 실행과 `[def:]`/`[fn:]` 호출을 교차했다.

100문장 모두 문법 검사에 통과했다. 기존 계약에서 실패한 36건 중 **28건은 잘못된 값을 반환하면서 성공 표시**, 8건은 실행 오류였다. 새 계약 12건은 기존 동작의 회귀 오류로 세지 않는다. `tail`과 앞쪽 범위가 함께 오면 한쪽을 무시하던 동작을 명시적 오류로 변경한 시험이다. 기대값은 수리 후 변경하지 않았다.

## 수리한 부분

1. **0회 반복이 한 번 실행됨.** `[repeat:0]{[self:read]{path:"없는파일"}}`이 실제 read를 실행했다. 0을 누락 값으로 취급하던 `or 1`을 없앴다. `max:0`도 조건·몸통을 실행하지 않으며 빈 items와 iterations=0을 반환한다. 바깥 변수는 보존하고, 실행하지 않은 몸통에서 변수를 잃었다는 오경고도 만들지 않는다.
2. **상한이 고정 횟수를 덮어씀.** `[repeat:2,max:6]`이 6회 실행됐다. 두 값 중 작은 횟수만 실행한다. 요청보다 일찍 상한으로 멈추면 `halted:"max"`와 실제 실행 횟수를 남긴다. 잘린 고정 반복을 완료처럼 보이게 하지 않는다.
3. **문단 읽기에서 tail 무시.** `[self:read]{path:"note.txt",tail:1,blocks:true}`가 전체 파일을 내던 문제를 고쳤다. 텍스트·문단 모드가 한 범위 계산 함수를 공유한다. tail은 offset/start/start_line/end/end_line/limit와 함께 쓰면 오류다. 빈 문단 범위는 start_line/end_line=null로 표기해 `9–2줄` 같은 역전된 위치를 내지 않는다.
4. **문단 모드의 물리 줄번호 불일치.** 추가 시험에서 `a\u2028b\nc\n`의 2번째 줄을 읽으면 `c` 대신 `b`가 나왔다. `splitlines()`가 유니코드 구분자까지 추가 줄로 세던 원인이다. 일반 읽기와 같은 `readlines()`를 사용하도록 고쳤다. U+2028, U+2029, NEL, 수직 탭, 폼 피드 5종을 검증했다.

새 어휘나 문법을 추가하지 않았다. 반복 명세와 read 카탈로그의 계약을 갱신하고 파생물을 재생성했다. 관용구 정의 자체는 바꾸지 않았다.
