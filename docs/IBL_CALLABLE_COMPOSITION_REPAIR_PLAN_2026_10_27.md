# IBL 호출 계약과 조합 검사 수리 계획

작성일: 2026-10-27. 상태: **0~5단계 구현 완료·정본 main 반영. 검증 이력은 §6, 진행 티켓 후속 수리는 §7 참조**.

후속 구조 수리: [어휘·함수·프로그램의 동등한 부품 조합 계획](IBL_COMPONENT_COMPOSITION_REPAIR_PLAN_2026_10_27.md). 앞선 구현 범위를 넘어 공통 계약·전달·분석·효과 적용을 다룬다.

함수를 변수·인자·반환값으로 전달해도 계약을 보존하고, 작은 함수를 조합해 큰 프로그램을
만들 때 검사량이 불필요하게 폭증하지 않도록 한다. 이 기반 위에서 순수 계산과 파이프의
허용 여부를 구문 모양보다 호출 계약으로 판단한다. 어휘의 파이프 수신율을 높이는 것만으로
이 목표를 대신하지 않는다.

목적은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)의 일반 능력·품질·완료 시간·전체 토큰이다.
[작업 연속성과 조합 계획](IBL_COMPOSITION_REPAIR_PLAN_2026_10_07.md)의 실행 경계 개선을
구체화하며, [재사용 부품 계약 수리](CALLABLE_COMPONENT_REPAIR_DESIGN_2026_10_18.md)의
스크립트·가이드 기능을 중복 구현하지 않는다. [현행 IBL 전환](IBL_CURRENT_ONLY_REPAIR_PLAN_2026_10_25.md)을
따라 현재 컴파일러·실행기를 확장하며 구판 실행 경로나 별도 언어 판본을 만들지 않는다.

## 1 관측 근거와 수리 범위

2026-10-27 정본 작업본에서 명세·코드를 대조하고 인메모리 프로그램 19종과 함수 조합 규모를
검사했다. 계획 작성 시 HEAD는 `c8e1f6ce45436f274f5f1d2b019d97e420fb1293`이며,
컴파일러·어댑터·원장 등에 다른 세션의 미커밋 변경이 있다. 아래 수치는 대화 중 조사 결과다.
구현 첫 단계에서 반례를 현 작업본에 다시 실행하고, 이미 수리된 항목은 중복 구현하지 않는다.

| 확인한 경계 | 관측 | 수리 후 성질 |
| --- | --- | --- |
| 내장 함수의 직접 호출과 변수 호출 | `abs("bad")`는 정적 오류지만 `$f=abs; $f("bad")`는 오류·guards 없이 검사를 통과한 뒤 실행 실패. 정상 인자도 변수 호출의 반환형은 Unknown | 알려진 호출 계약은 전달 방식에 관계없이 검사·반환 추론에 사용 |
| 순수 도구와 함수 포장 | 순수 계약의 `table:take`는 조건에서 직접 부르면 거절, 같은 호출을 함수로 감싸면 허용 | 효과가 같은 순수 호출은 같은 순수 식 자리에서 허용 |
| 순수 함수의 명시 인자와 파이프 | 람다에서 `[fn:inc]{x:$x}`는 허용, `$x >> [fn:inc]`는 거절 | 입력 연결 방식이 순수성 판정을 바꾸지 않음 |
| 함수 값의 호출 형태 | `$r.f(-3)`는 구문 오류, `$f=$r.f; $f(-3)`는 실행 성공. 내장 함수·람다로의 파이프는 PIPE_TARGET | 호출 가능한 값의 계약으로 적용 여부를 판단 |
| 하위 함수의 반복 분석 | 조건 양쪽에 같은 하위 함수를 두면 한쪽만 실행해도 양쪽의 하위 본문을 매번 분석 | 동일 분석 조건의 함수 본문은 한 컴파일 안에서 재사용 |

조건 양쪽에서 같은 하위 함수를 호출하는 비재귀 프로그램의 실측은 다음과 같다.
실제 실행에서는 각 층의 한쪽만 선택한다.

| --- | --- | --- |
| 6 | 6 | 63 |
| 10 | 10 | 1,023 |
| 14 | 14 | 16,383 |

마지막 원문은 810자, 당시 컴파일은 약 0.42초였다. 시간은 환경 의존 관측이며 합격 기준은
분석량의 증가율로 둔다. 업무 완료 시간·토큰 절감의 측정값으로 해석하지 않는다.
관련 기존 `test_ibl_v2_core`, `test_ibl_container_calls`, `test_ibl_run_journal`,
`test_execution_capacity`의 126개 검사는 조사 시 통과했다. 새 설계의 인수 검사는 별도다.

범위는 호출 계약·함수 분석·순수성·호출 구문·파이프·해당 교재와 사전 입력 선언이다.
재귀, 임의 제어 블록을 파이프 수신자로 허용하는 문법, 함수 값의 외부 JSON 전송,
새 비동기 원장, 영속 컴파일 캐시, 자동 실행 결과 캐시는 이번 범위에 넣지 않는다.

## 2 유지할 실행 성질

- 기존에 유효한 프로그램의 값·외부 호출 순서·호출 횟수·실패와 재개 의미를 보존한다.
  확정적으로 잘못된 호출을 더 일찍 거절하는 것은 수리된 검사 동작으로 명시한다.
- 조건·단락 평가·람다·기본값의 순수 경계는 유지한다. read_external도 pure가 아니며,
  unknown을 pure로 승격하지 않는다. 순수 계산도 실패·예산 소진은 가능하다.
- 도구의 권한·승인·취소·공유 예산·호출 신원·실행 근거·영수증은 현재 실행 경로가 소유한다.
  호출 계약을 공통화한다고 도구 실행기를 일반 콜백으로 우회하지 않는다.
- `??`의 실패 한정 복구, 빈값의 정상 의미, 병렬 결과 순서, each의 실패 수집과 부분 근거를 유지한다.
- `pipe_in`·`pipe_text`·명시 계약은 이미 레지스트리에서 실행 계약으로 모인다.
  새 병렬 레지스트리나 낱말별 파서 분기를 만들지 않는다.

## 3 단계와 의존 관계

구현 순서는 **0단계 반례 고정 → 1단계 계약 보존 → 2단계 분석 재사용 → 3단계 순수 조합 →
4단계 호출과 파이프 확장 → 5단계 사전과 교재 연결**이다. 각 단계는 정본 main에 검증 가능한
단위로 반영한다. 문법 허용 범위를 바꾸는 3·4단계는 구현과 명세 개정을 같은 변경으로 묶는다.
아래는 구현의 기준이며 실제 적용 범위와 검증 결과는 §6에 기록한다.

### 0단계 현재 반례를 회귀 검사로 고정

소유 위치: 기존 `backend/test_ibl_v2_core.py`, `test_ibl_container_calls.py`와
컴파일러·타입·파서에 대응하는 테스트 파일. 회차별 새 검사 프레임워크는 만들지 않는다.

위 19종의 핵심 쌍과 조건 분기 조합 생성기를 pytest 사례로 옮긴다. 실제 등록 도구의
계약을 사용하는 사례와 임의 이름의 어댑터 사례를 함께 두어 낱말 이름 특례로 해결하지 못하게 한다.
조합 검사에는 타입·효과·오류 위치·외부 호출 수·실행 값의 기대값을 둔다.

**완료 조건:** 확인된 비대칭과 반복 분석을 재현하고, 기존 실행 보존 기준선이 준비된다.
목표 동작 검사는 해당 수리와 함께 통과시킨다. 정상 브랜치에 의도적 실패 검사를 남기지 않는다.

### 1단계 함수 값에 호출 계약을 보존

소유 위치: `backend/ibl/ibl_v2_types.py`, `ibl_v2_compile.py`, `ibl_v2_analysis.py`,
`backend/common/expression_ops.py`, `expression_functions.py`, `expression_eval.py`.

내부 Callable 타입에 인자 수·인자 계약·반환 관계·효과를 표현한다. 내장 함수는 현재의
허용 타입과 변환 규칙을 가져오며, 새 사설 함수 목록이나 추정 규칙을 만들지 않는다.
람다는 본문·캡처한 값의 타입·실제 인자 타입으로 분석한다. 변수·레코드·목록·함수 인자·
반환값을 거쳐도 이 정보를 전달한다. 사용자에게 전면적인 타입 주석을 요구하지 않는다.

함수의 반환형은 필요한 경우 입력 타입과의 관계를 보존한다. 여러 특수화 결과가 다르다는
이유만으로 계약 전체를 Unknown으로 접지 않는다. 서로 다른 함수가 합쳐지는 분기는 가능한
계약 집합으로 처리하고, 모든 후보가 인자를 받는지 검사한다. 집합이 커지면 보수적으로
정밀도를 낮추되 미확정 검사와 사유를 보고한다.

호출 계약을 모르는 값은 현행 실행 경계의 검사를 유지하고 `incomplete` 및 runtime_checks로
알린다. 정적으로 아는 잘못된 인자 수·타입은 실행 전에 거절한다. 반환 타입만 미확정인 것과
호출 자체의 적합성이 미확정인 것을 구별한다. Callable은 계속 실행 내부 값이다.

**완료 조건:** 직접 호출과 별칭·컨테이너·함수 왕복 호출의 인자 검사가 일치한다.
`abs(-3)`와 `$f=abs; $f(-3)`의 반환 추론이 같고 잘못된 입력도 같은 단계에서 거절된다.
다른 캡처·서명·효과를 가진 함수가 합쳐져도 잘못된 pure 판정이나 계약 혼합이 없다.
describe·check·관용구 계약 소비자는 같은 구조화된 정보를 읽는다.

**대체할 경로:** 구문에 내장 함수 이름이 직접 있을 때만 정확한 검사, 전달 직후 정보 없는
Callable로 축소하는 처리. 새 이름 있는 함수 참조 문법은 이 단계의 선행 조건이 아니다.

### 2단계 동일 조건의 함수 분석을 재사용

소유 위치: `backend/ibl/ibl_v2_compile.py`의 함수 분석, `ibl_v2_preflight.py`,
`ibl_dependencies.py`와 함수 계약 소비자. 1단계 계약을 분석 요약의 공통 기반으로 쓴다.

함수 본문 분석과 호출 지점에 결과를 적용하는 일을 분리한다. 요약에는 반환 타입·효과·
호출 도구·쓰기 자원·의존성·필요한 실행 시 검사·진단을 포함한다. 컴파일러의 전역 가변 상태를
그대로 캐시에 넣지 않고, 호출자가 합성할 수 있는 결과로 만든다.

재사용 범위는 한 컴파일로 한정한다. 키에는 정의와 어휘 계약의 판본, 어휘 범위 해소,
입력 타입 및 분석에 영향을 주는 정적 값·Callable 계약·캡처 정보를 포함한다.
표시용 타입 문자열은 손실이 있으므로 키로 사용하지 않는다. 자원 경로나 op 같은 정적 값을
생략해 효과·쓰기 대상을 섞지 않는다. 완료 전 분석은 재사용하지 않으며 재귀 거절은 유지한다.

요약의 진단은 정의 내부 위치로 보관하고 호출마다 call_path를 결합한다. 같은 함수를
병렬 두 가지에서 부르더라도 각 호출의 쓰기 자원·실행 횟수·AI 방문 상한을 합성한다.
본문 분석 횟수를 줄이는 일이 실제 호출 수를 하나로 접는 결과를 내서는 안 된다.
AST의 symbol·specialization 같은 가변 정보가 호출마다 달라지는 경로도 함께 분리한다.
가능한 모든 호출 경로를 문자열 목록으로 펼쳐 같은 폭증을 재현하지 않는다. 경로는 공유
구조로 보관하고 보고서에는 대표 위치·경로와 생략량을 제한해 표시한다. 확정 오류의 종류와
원문 위치는 보존하며 상세 조회도 범위를 제한한다. 호출 상한은 요약의 합성과 곱으로 계산한다.

**완료 조건:** 동일 입력 조건의 분기 조합에서 각 함수 본문의 분석은 한 번이며 요약 적용은
고유 호출 간선에 비례한다. 6·10·14개 함수 외 더 깊은 생성 사례도 확인한다. 서로 다른 타입·
정적 경로·op·캡처는 필요한 만큼 따로 분석한다. 반복 분석을 끈 기준선과 값·효과·오류 판정·
병렬 쓰기 충돌·호출 상한·계획 의존성이 일치한다. 다른 컴파일로 결과가 새지 않는다.

**대체할 경로:** 호출마다 하위 본문을 끝까지 다시 방문하는 처리. 분석 캐시는 사용자 옵션이나
상시 서비스로 노출하지 않으며 도구 실행 결과를 캐시하지 않는다.

### 3단계 순수성 판정을 효과 기준으로 완성

소유 위치: `ibl_v2_compile.py`의 pure 검사와 호출 효과 분석, 현재 Runtime·ExpressionEvaluator.

순수 식 자리에서 도구 호출·파이프라는 이유만으로 먼저 거절하지 않고, 식 전체의 효과를
합성해 판단한다. pure 계약의 도구, 순수 함수, 순수 Callable, 그 파이프 조합을 허용한다.
인자·파이프 원천·캡처와 하위 호출까지 검사하여 외부 효과나 미확정 효과를 숨기지 못하게 한다.
순수 도구라도 도구 경계의 권한·예산·실행 근거 검사를 그대로 지난다.

같은 표현 코어를 쓰는 `ValueEvaluator` 등 값 전용 호스트는 도구를 실행할 능력이 없다.
IBL Runtime의 허용 확장이 이 소비자에 외부 실행 권한을 주지 않도록 호스트 경계를 검사한다.
제어 블록을 값 자리에 넣는 새 문법은 추가하지 않는다.

**완료 조건:** 순수 도구 직접 호출과 함수 포장, 명시 인자와 파이프의 허용 결과가 일치한다.
조건·and/or·람다·기본값의 미선택 가지는 실행하지 않고 각 자리의 호출 횟수를 지킨다.
외부 읽기·쓰기·모델·unknown 효과는 직접·간접 모두 실행 전에 거절한다. 순수 계산의
실패·취소·예산·근거 전달과 값 전용 호스트의 실행 한계를 보존한다.

**대체할 경로:** `[fn:]`에만 효과 검사를 허용하는 예외와 순수 계산을 감싸기 위한 교재 우회.

### 4단계 호출 가능한 값과 파이프의 규칙을 일치

소유 위치: `backend/common/expression_parser.py`, `expression_eval.py`,
`backend/ibl/ibl_v2_compile.py`, `ibl_v2_runtime.py`, `ibl_callable_contract.py`.

필드·인덱스·함수 반환에서 얻은 Callable도 직접 호출한다. 비호출 값은 정적으로 알면
검사에서, 미확정이면 실행 경계에서 거절한다. 별도 도구 호출 문자열이나 두 번째 호출 엔진은 만들지 않는다.

위치 인자를 받는 내장 함수·람다의 파이프는 첫 인자에 주입한다. 예를 들어 `-3 >> abs()`는
`abs(-3)`, `값 >> f(다른값)`은 `f(값, 다른값)`의 인자 연결이다. 명명 인자를 받는 도구·
`[fn:]`는 현재 선언된 receiver와 중복 명시 거절을 유지한다. 가변 인자·기본값도 최종 인자
목록으로 같은 계약 검사를 받는다. 첫 인자를 받을 수 없는 호출은 거절한다.

파이프는 원천 → 수신 Callable → 명시 인자 → 호출 순서로 한 번씩 평가한다.
일반 확장 호출은 Callable을 구한 뒤 인자를 원문 순서로 평가한다. 기존 `pure_call`의
인자 우선 평가와 비교하여 기존 유효 원문의 실패·효과 순서에 변화가 없는지 확인한다.
기존 형태에서 차이가 발생하면 기존 의미를 보존하도록 적용 범위를 조정하고 명세에 반영한다.
연산자 우선순위와 자동 병렬 여부는 바꾸지 않는다.

**완료 조건:** 직접·별칭·필드·인덱스·반환 Callable의 호출과 파이프가 같은 인자·결과를 낸다.
인자 수, 중복 입력, 호출 불가 값, 실패 중단, 캡처, 중첩 콜백과 호출 횟수를 검사한다.
확장된 위치에서도 동일 코드 재개가 완료 효과를 반복하지 않으며 서로 다른 호출 위치의
영수증을 합치지 않는다. 수정 코드의 재사용 자격은 기존 의존성 정책을 따른다.

**대체할 경로:** 호출 대상 AST 종류가 ref/builtin/lambda뿐인 제한과 파이프 RHS가
도구·이름 있는 함수 호출뿐인 제한. 괄호 사슬·임의 블록을 자동 함수로 해석하지 않는다.

### 5단계 사전 입력과 작성 표면을 연결

소유 위치: `data/ibl_nodes_src/`, 패키지 `ibl_actions.yaml`, 기존 계약 빌더·describe·카탈로그,
`ibl.md`, 조합 교재, 어댑터 가이드, 새 액션 체크리스트.

파이프 수신이 없는 액션을 자연스러운 주 입력이 있는 경우, 다중 입력이라 명시가 필요한 경우,
입력이 필요 없는 경우로 구분한다. 첫 부류만 기존 데이터 선언으로 보완한다. op별 입력이

분류를 파서의 낱말 목록으로 옮기지 않는다.

describe에는 실제 해소된 입력 자리·타입·반환·효과를 노출하고, 체크리스트에는 주 입력
판정과 파이프/명시 입력 동등성 검사를 연결한다. 어댑터 문서에 이미 있는 flow 요구는
새 규약처럼 중복 작성하지 않는다. 중첩 병렬 설명은 현재 공유 용량과 여유 슬롯 대여 동작에 맞춘다.
교재·도움말·오류 안내에서 수리로 불필요해진 포장·중간 변수 우회를 제거한다.

**완료 조건:** 보완한 액션은 파이프와 명시 인자의 값·빈값·타입 오류·부분 실패 근거가 같고,
describe·검사·실행이 같은 계약을 사용한다. 수신율 자체를 성과나 합격 기준으로 쓰지 않는다.

후속 비system 전수의 테스트 집계는 **10,641통과·9생략·시험 실패 0**(830.92초)이다.
다만 실행 중 이 계획서에 §7을 작성하여 `live-store` 종료 가드가 이 문서 하나의 변경을
감지했고 **명령 종료 코드는 1**이었다. 코드/테스트 변경이나 테스트 실패가 아니라 작업자의
문서 편집으로 인한 종료 검사 실패이며, 명령 전체를 종료 코드 0으로 보고하지 않는다.
전수 실행 중 코드는 수정하지 않았다. 원래 진행 티켓 실패와 용례 원장 실패는 이번
전수의 테스트 집계에서 모두 해소됐다. 전체 system·frontend 빌드는 실행하지 않았다.

문서 기록 후 파일을 변경하지 않고 직접 관련 5개 파일을 다시 실행해 **74통과·종료 코드 0**을
확인했다(22.19초). 문서 변경 감지 원인은 해소됐으며 비system 전수 자체는 재실행하지 않았다.
