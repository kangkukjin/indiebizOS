# IBL 어휘·함수·프로그램의 동등한 부품 조합 수리 계획

작성일: 2026-10-27. 상태: **구현·인수 검증 완료**.
기준: 정본 main `82e8eb129bae200b7276a2f107cce6eb0c722163`와 현재 작업본.

구현 후 조합 설계 재감사와 다음 범위는
[후속 수리계획](IBL_COMPOSITION_DESIGN_GAPS_REPAIR_PLAN_2026_10_27.md)에 있다.
이 문서의 인수 완료는 IBL 전체 설계에 중대한 잔여가 없다는 판정이 아니다.

## 1 목적과 이번 계획의 책임

목적은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)에 따라, 처음 보는 요구를 의미 있는
부품으로 분해하고 그 부품으로 더 큰 프로그램을 만든 뒤, 그 프로그램을 다시 다음 조합의
부품으로 쓰는 일반 능력을 강화하는 것이다. 품질·근거·부분 실패를 보존하면서 실제 완료
시간과 전체 모델 토큰을 줄이는 방향으로 설계한다. 개별 업무의 실패나 성능 측정을
기다려야만 이 구조를 개선할 수 있는 것은 아니다. 미측정 비용 개선은 성과로 주장하지 않는다.

[앞선 호출 계약 수리](IBL_CALLABLE_COMPOSITION_REPAIR_PLAN_2026_10_27.md)는 별칭·컨테이너의
Callable 정보, 이름 있는 함수의 분석 재사용, 순수 호출과 파이프를 개선했다. 이 계획은
그 성과를 유지하면서 **호출 대상의 종류와 전달 표현에 따라 달라지는 계약·분석·실행 규칙을
공통 구조로 수렴**시킨다. 람다 캐시 하나나 get 예외 하나를 추가하는 것으로 끝내지 않는다.

‘동등한 부품’은 입력 방식·효과·권한·실행 위치가 모두 같다는 뜻이 아니다. 어휘, 내장 함수,
지역/저장 함수, 람다, 명시 입력·반환을 가진 프로그램이 **같은 계약 조회·전달·검사·적용
규칙에 참여**한다는 뜻이다. 교체 가능 여부는 해당 계약의 적합성으로 판단한다.

| 일반 능력 | 완료 후 보장할 성질 |
| --- | --- |
| 부품 전달 | 변수·필드·목록·조건 선택·인자·반환을 거쳐도 알려진 계약을 보존한다. |
| 부품 교체 | 같은 요구 계약을 만족하는 다른 구현을 넣어도 조합 절차를 복사하지 않는다. |
| 다시 부품화 | 지역 프로그램을 명시 입력·반환 함수로 만들고, 필요하면 기존 저장 경로로 축적한다. 저장은 조합의 선행 조건이 아니다. |
| 효과 보존 | 부품의 생성·전달과 실제 호출을 구별하고, 호출 시 효과·권한·자원·실행 근거를 합성한다. |
| 규모 확대 | 동일 특수화의 본문을 공유하며, 분석·진단·계약 표현 자체도 공유 구조를 불필요하게 펼치지 않는다. |
| 실행 연속성 | 작은 부품을 큰 부품으로 감싸도 승인·취소·완료/불명 영수증·재개 의미가 보존된다. |

현재의 [표준/사전 경계](../data/system_docs/ibl.md#언어의-경계--표준과-사전-헌법-조항)를
유지한다. 업무명·특정 액션명을 파서나 분석기 조건문에 넣지 않는다. 문법 개정과 공통 계약은
표준의 책임이며, 도구 의미·업무 정책·사용자 부품은 기존 사전·함수·스크립트의 책임이다.

## 2 관측한 부족함과 공통 원인

아래는 2026-10-27 수리 후 코드에서 재현한 관측이다. 실제 외부 서비스는 호출하지 않았다.
작업본의 별도 진행 표시·spill 변경은 존재하며, 이번 관측은 그 변경의 완료 선언이 아니다.

| 관측 | 현재 결과 | 구조적 원인과 수리 방향 |
| --- | --- | --- |
| 같은 하위 함수를 조건 양쪽에서 부르는 람다 사슬 | 깊이 6/10/14에서 Callable 분석 63/1,023/16,383회. 깊이 14 실제 실행은 14회 | 분석 요약이 이름 있는 함수 경로에 한정된다. 모든 호출 부품의 본문/계약 분석과 호출 지점 적용을 분리한다. |
| `{f:abs}`의 `.f`와 `get(...,"f")` | 둘 다 실행 결과 3. 전자는 valid/Number, 후자는 incomplete/Unknown/unknown 효과 | 데이터 연산이 값의 계약 관계를 일관되게 전달하지 못한다. 공통 구조 타입 전달 연산을 둔다. |
| 위 get 호출을 람다 본문에 둠 | `PURE_EXPRESSION`으로 거절 | 정보 손실이 실제 효과와 무관한 조합 금지로 전파된다. 정밀도 손실과 호출 효과를 구분한다. |
| 작업을 인자로 받는 함수에 외부 읽기 람다를 전달 | 같은 구조의 순수 작업은 통과, read_external은 람다 본문 규칙에서 거절 | Callable 생성과 호출 효과를 분리하지 않고 람다 자체에 순수성을 요구한다. 효과를 가진 부품을 실행 가능한 자리에서 적용하는 계약을 도입한다. |

최소 반례의 현행 원문은 다음과 같다. 오류 예제는 운영 교재의 성공 예제가 아니다.

```text
$r={f:abs}; return $r.f(-3)
$r={f:abs}; return get($r,"f")(-3)
$r={f:abs}; return (($x)=>get($r,"f")($x))(-3)

[def:apply]($op,$x){return $op($x)}
return [fn:apply]{op:($x)=>[test:read]{x:$x},x:1}
```

마지막 예제의 test:read는 Number→Number, read_external 계약의 임의 이름 시험 어댑터다.
람다 사슬은 `$f0=($x)=>$x`에서 시작하여 각 `$fN`이
`($x)=>($x>0 ? $f직전($x) : $f직전($x))`를 반환하도록 만들고 마지막 함수를 한 번 호출한다.
확정 분기의 상수 접기를 성과로 세지 않도록 양쪽 분기를 분석하는 입력 조건을 함께 사용한다.

세 관측은 서로 독립된 낱말 오류 목록이 아니다. **대상 계약 → 값의 흐름 → 분석 요약 →
적용 위치의 효과 요구 → 실제 호출 경계**가 하나의 연결된 구조여야 한다는 요구를 드러낸다.

## 3 공통 부품 모델

### 3.1 정의·값·호출 인스턴스를 분리한다

새 개념의 이름은 아래 설계 설명용이며 별도 사용자 어휘나 저장소를 뜻하지 않는다.
기존 Callable 타입·어댑터 계약·함수 정의/판본을 확장한다.

| 개념 | 보관할 내용 | 섞지 않을 내용 |
| --- | --- | --- |
| 부품 정의/계약 | 정의 신원·판본, 입력 서명, 반환 관계, 호출 효과, 자원 관계, 의존성, 지원 호스트/전송 경계 | 실행 중 호출 횟수·승인 토큰·영수증 |
| 부품 값 | 정의 참조와 어휘/지역 범위 해소, 캡처한 Binding, 적용 가능한 계약 참조 | 핸들러 직접 실행 권한, 임의 문자열 eval, 실행된 결과 |
| 분석 특수화/요약 | 입력·캡처의 추상 값에 따른 반환·효과·자원·호출 관계·진단·미확정 검사 | 호출자 전역 가변 상태, 실제 작업 결과 |
| 호출 인스턴스 | 호출 위치, 반복/병렬 경로, 실제 대상 판본·인자·근거·주체, 승인·예산·영수증 | 다른 위치의 동일 인자 호출과 공유한 실행 신원 |

어휘의 정본은 기존 YAML→레지스트리, 내장 함수는 기존 구현/계약, 지역 함수·람다는 AST와
범위, 저장 함수는 `function_store`의 정의·판본이다. 정본을 복제한 별도 callable 사전을
만들지 않는다. 각 정본을 **한 내부 계약 표현으로 정규화**하고 모든 소비자가 이를 읽는다.
단순 타입/효과 선언은 그대로 수용하며 필요한 관계 정보만 확장한다.

### 3.2 공통 계약에 필요한 관계

입력 계약에는 위치/명명 인자 지원, 필수·기본값·별칭·조건부 op, 파이프 수신 자리와
중복 입력 판정이 포함된다. 반환은 Number 같은 타입뿐 아니라 ‘입력 목록의 원소형’,
‘선택한 필드형’, ‘콜백 적용 결과’ 같은 관계를 표현한다. 호출 효과와 읽기/쓰기 자원도
입력과 콜백 계약에 의존할 수 있다. 기존 `flow`·조건부 계약·자원 선언을 이 표현으로
연결하며 같은 정보를 새 표에 다시 적게 하지 않는다.

효과를 매번 사용자에게 주석으로 적게 하지 않는다. 알려진 부품은 선언/본문에서 추론하고,
`apply(op,x)` 같은 함수는 op의 계약을 받아 특수화한다. 설명상 `effects(apply)=effects(op)`인
관계를 지원하되 이 수식을 새 사용자 문법으로 먼저 도입하지 않는다. 반환형·호출 적합성·
효과·자원 중 무엇이 미확정인지 각각 보고한다. 반환형 미확정만으로 효과까지 unknown으로
만들거나, 효과 미확정을 pure로 취급하지 않는다.

외부 원시 구현의 효과는 검토된 기존 선언이 기준이다. 임의 Python/셸/동적 import의 의미를
자동으로 완전히 증명하려 하지 않는다. 타입 적합성은 업무 결과의 정확성·전건 완료 보증과도 구분한다.

### 3.3 프로그램은 기존 함수 경계로 다시 부품화한다

명시 입력·반환을 가진 여러 문장의 프로그램은 기존 `[def:]` 본문으로 구성한다. 외부 값은
명시 인자 또는 명시적으로 보존되는 렉시컬 캡처이며, 호출자 지역 변수를 이름으로 몰래 찾지
않는다. 제어 블록·return·try/finally의 범위는 해당 함수 경계를 따른다. 전체 Plan 객체나
살아 있는 Runtime/Journal을 함수 값으로 전달하지 않는다.

이렇게 만든 부품은 지역에서 바로 전달·반환·재조합할 수 있어야 한다. 반복 가치가 생기면
기존 함수 저장·판본·회상 경로에 명시 입력과 의존 정의를 함께 보관한다. 실행 중 캡처한
세션/외부 참조를 영구 저장한 것으로 간주하지 않으며, 저장 불가능한 캡처는 매개변수로
분리하거나 이유를 밝혀 거절한다. 지역 조합 → 저장 → 회수 → 상위 조합에서도 같은 계약을 쓴다.

## 4 값 전달과 계약 보존의 공통 규칙

`ibl_v2_types`의 구조 타입과 기존 분석을 바탕으로 필드 선택, 인덱스 선택, 대안 합치기,
타입 변수 대입, 컨테이너 재구성의 공통 전달 연산을 만든다. `.f`, `get`, 목록 접근,
map/filter/reduce, table의 행 변환, Result의 수집/unwrap은 이 연산을 소비한다.
내장 함수의 고유 의미는 기존 내장 함수 계약 위치에 두고 도구 이름 분기를 추가하지 않는다.

| 값 흐름 | 계약 전달 규칙 |
| --- | --- |
| 알려진 키/위치 선택 | 실제로 선택하는 값의 타입·Callable 계약·캡처/판본 참조를 보존한다. |
| get의 기본값 | 키 부재 가능성에만 기본값을 합친다. 존재하는 null과 부재를 혼동하지 않는다. |
| 동적 키·인덱스 | 유한 후보를 알면 후보 계약의 합집합, 열린 영역이면 미확정 부분과 이유를 남긴다. |
| 레코드 spread·목록 재구성 | 덮어쓰기 순서·알려진 위치·열린 필드를 보존하며 불명 덮어쓰기는 보수적으로 반영한다. |
| 분기·고차 적용 | 후보별 인자 적합성과 반환/효과를 계산한다. 증명된 분기 좁히기 외에는 안전한 후보만 임의 선택하지 않는다. |
| map/filter/reduce·행 변환 | 원소/누적형과 콜백 입력·반환 관계를 합성한다. 빈 목록·초깃값·0회 호출을 별도로 반영한다. |
| Result·부분 실패 | 성공 값 안의 계약과 실패/근거를 함께 보존한다. 실패를 빈 성공 값으로 바꾸지 않는다. |
| JSON/외부 전송 | 내부 Callable을 평문 객체로 위장하지 않는다. 전송 불가 위치와 해당 경계를 명시한다. |

알려진 키의 get만 특별 취급하는 수리로 종료하지 않는다. **같은 값을 같은 조건에서
선택하는 표현은 같은 계약을 얻는다**는 성질을 축으로 전달 연산 전체를 검사한다.
실제로 정보가 없는 키, 무한/과대한 후보, 외부 스키마 미상은 정직하게 불완전 상태를 유지한다.

## 5 모든 호출 부품에 대한 분석 요약

이름 있는 함수와 람다에 별도 캐시를 하나씩 두지 않는다. 공통 부품 분석 입구가 정의를
해소하고 특수화 요약을 얻으며, 호출 지점은 그 요약을 자신의 문맥에 적용한다. 원시 어휘와
내장 함수는 계약 전달 요약, 함수·프로그램·람다는 본문에서 유도한 요약을 같은 틀에 담는다.

요약 키는 한 컴파일의 정의/어휘 판본·렉시컬 해소·입력 추상 값·캡처 추상 값·도달 가능성 등
분석 결과를 바꾸는 조건을 포함한다. op·자원 경로·기본값 분기·Callable 후보를 섞지 않는다.
표시용 문자열이나 대상 이름만 키로 쓰지 않는다. 우선 완전한 구조 키를 사용하고, 불필요한
특수화를 줄이는 추상화는 자원·효과의 구분을 보존한다는 별도 검증 후 도입한다.

- 요약은 반환 관계, 효과, 자원, 의존성, 호출 간선/횟수 관계, 필요한 실행 검사와 정의 내부
  진단을 포함한 불변 값이다. 컴파일러의 임시 전역 집합·AST 호출자 메타데이터를 공유하지 않는다.
- 캡처와 Callable 대안은 공유 그래프의 참조로 보관한다. 키 해시·타입 동등 비교·describe·진단
  직렬화가 다시 하위 그래프를 전개해 같은 폭증을 만들지 않도록 고유 노드 단위로 계산한다.
- 진행 중 요약과 완료 요약을 구분한다. 재귀는 현재 거절 정책을 유지하며 순환 참조를
  완료된 요약으로 오인하지 않는다. 중단된 분석의 가변 결과를 재사용하지 않는다.
- 형 검사와 preflight가 별도로 본문을 반복 전개하지 않는다. 공통 호출 그래프/요약에서
  각자 필요한 정보를 투영한다. 실행 횟수·모델 방문 상한·승인 안내는 호출마다 합성한다.
- 진단의 정의 위치와 호출 지점 관계를 보존하되 모든 경로를 문자열로 펼치지 않는다.
  대표 경로·전체/생략 수·미확정 사유를 표시하고 상세 조회도 크기를 제한한다.

비재귀 DAG의 동일 특수화에 대해 본문 분석 횟수는 **고유 특수화 수 U**, 요약 적용과 관계
합성은 **고유 간선 E와 제한된 계약/진단 크기**를 기준으로 검증한다. 서로 다른 캡처·인자로
U 자체가 늘어나는 경우를 ‘항상 선형’이라고 주장하지 않는다. 특수화·대안·분석 자원 예산을
넘으면 원인과 범위를 명시해 incomplete로 내리고 해당 실행 경계를 유지한다. 필요한
안전 판정이 불가능한 위치는 거절하며, 예산 초과를 유효·무효과·0회 호출로 바꾸지 않는다.

분석 재사용은 한 컴파일 안에 한정한다. 영속 컴파일 캐시와 도구 결과 캐시를 추가하지 않는다.
기존 resume/reuse의 실행 영수증 재사용 정책은 별개의 소유자에게 남긴다.

## 6 효과 있는 부품의 생성·전달·호출

### 6.1 잠재 효과와 현재 평가 효과를 나눈다

부품 값은 ‘호출하면 생길 효과’를 계약으로 가진다. 참조를 만들거나 이미 만들어진 부품을
목록에 넣는 것만으로 그 효과가 발생하지 않는다. 다만 참조/캡처/인자를 구하는 표현 자체가
수행한 효과는 현재 표현의 효과로 합성한다. 캡처한다고 외부 호출을 숨기거나 뒤로 미루지 않는다.

람다는 표현 본문의 형태를 유지하되 본문 자체에 일괄 pure를 강제하는 경로를 대체한다.
본문의 효과는 Callable의 잠재 효과로 추론하고, **실제 적용 위치의 효과 요구**와 대조한다.
여러 문장·제어 블록의 작업은 기존 명시 함수로 표현한다. 블록을 임의 값으로 해석하지 않는다.

| 위치 | 허용 계약 |
| --- | --- |
| 일반 실행 문장·함수 본문·each 본문의 호출 | 현 실행 정책 안에서 효과 있는 부품도 적용. 기존 도구 권한/승인 경계를 통과한다. |
| 조건·조건 값·and/or의 순수 식·기본값 | 그 자리에서 실제 평가하는 효과가 pure로 확인돼야 한다. |
| map/filter/sorted/reduce 등의 순수 콜백 요구 | 콜백의 잠재 호출 효과도 pure여야 한다. 외부 작업은 기존 each 등 실행 문맥으로 구성한다. |
| 부품을 선택하거나 반환하는 순수 함수 | 선택/반환 자체의 효과와 반환된 부품의 잠재 효과를 구별한다. |
| 호출 적합성/효과 미확정 | 일반 호출은 명시 실행 검사, 순수성이 필요한 적용은 증명하지 못하면 거절한다. |
| ValueEvaluator 등 값 전용 호스트 | 호스트가 지원하는 값 계산만 실행. pure라고 선언된 도구라도 도구 실행 능력을 새로 얻지 않는다. |

고차 함수의 효과와 자원은 실제 콜백 계약을 대입해 계산한다. 콜백을 받기만 하고 호출하지
않는 함수, 한 번/여러 번/조건부 호출하는 함수, 콜백을 반환하는 함수를 구별한다.
권한은 계약이나 캡처에 저장되는 권능 토큰이 아니다. 실행 주체의 현재 권한을 잎 호출에서
확인하며, 외부 부품으로 감싸도 승인·취소·공유 예산·실행 위치 제약이 사라지지 않는다.

### 6.2 참조와 적용의 최소 문법 제안

아래는 **구현할 문법 제안**이며 현재 지원 문법으로 안내하지 않는다. 1단계에서 파서 충돌과
기존 평가 순서를 확인해 명세로 확정한다. 표기 조정이 필요해도 참조/적용 분리와 공통 계약은
바꾸지 않으며 여러 경쟁 문법이나 우회용 실행 어휘를 함께 도입하지 않는다.

```text
$읽기 = &[self:read]           # 실행하지 않고 현재 어휘 범위의 정의를 참조
$절차 = &[fn:수집하고저장]      # 지역/저장 함수의 고정된 정의를 참조
$값 = $읽기{path:$경로}        # 명명 인자 적용
$값 = $r.worker{path:$경로}    # 선택한 부품도 같은 명명 인자 적용
$값 = -3 >> abs()             # 기존 위치 인자 적용
$값 = $경로 >> $읽기{}        # 계약에 선언된 수신 자리가 있을 때만 허용
```

접두 `&[대상]`은 참조, 기존 두 문장 사이 `&`는 병렬이다. 참조 뒤에 호출 인자나 본문을
붙여 암묵 실행/부분 적용으로 해석하지 않는다. 필요한 고정 op·인자 묶음은 명시 함수에서
표현한다. 참조 대상의 이름은 기존 렉시컬/사전 해소를 따르며 문자열에서 코드를 실행하지 않는다.
동적 선택은 참조 값들의 Record/List와 기존 선택 연산으로 수행한다.

목표 사용 형태는 다음과 같다(같은 제안 문법). load/save는 각각 source/value 입력 계약을
맞춘 지역 함수 또는 어댑터 함수다. 서로 다른 원시 도구 서명을 자동으로 같게 만들지 않는다.

```text
[def:처리]($source,$load,$check,$save){
  $자료 = $load{source:$source}
  $검사값 = $check($자료)
  return $save{value:$검사값}
}
[def:여러건]($sources,$job,$load,$check,$save){
  return $sources >> [table:each]{
    return $job{source:$it,load:$load,check:$check,save:$save}
  }
}
return [fn:여러건]{sources:$입력목록,job:&[fn:처리],
                  load:$선택한수집기,check:$검사함수,save:$선택한저장기}
```

수집기·저장기를 바꾸어도 처리 본문을 복사하지 않으며, 완성된 처리 프로그램 자체가
다음 프로그램의 job 입력이 된다. 실제 읽기/쓰기의 권한과 승인·실패는 각 호출에서 보존한다.

`(...)`/`{...}`는 각 계약이 지원하는 위치/명명 인자 방식이다. 도구의 인자 순서를 추측해
위치 인자로 받지 않는다. 명명 함수·도구의 파이프는 기존 receiver 선언, 위치 함수는 첫
위치 인자 규칙을 따른다. 별칭 정규화·기본값·op 선택·중복 입력·필수/금지 인자 판정은
직접 호출과 간접 호출이 같은 바인더를 사용한다. 인자 방식이 다른 부품의 교체에는 명시
어댑터 함수가 필요하며, ‘동등한 부품’을 모든 서명의 무조건 호환으로 해석하지 않는다.

기존 유효 원문의 인자/대상 평가 순서는 보존한다. 새 명명 적용은 대상→명시 인자 순서,
파이프는 원천→대상→명시 인자 순서로 각 표현을 한 번만 평가한다. 기본값의 평가 시점과
범위도 기존 정의 계약을 따른다. 참조 생성 중 기본값이나 도구를 실행하지 않는다.

### 6.3 같은 실행 경계에 도착시킨다

직접 호출과 간접 적용은 공통 적용 요청(대상 계약·인자·현재 호출 위치·문맥)으로 모인다.
내장 계산, 함수 본문, 도구 어댑터의 실제 구현은 각 소유자에 남기되 일반 콜백이 도구
핸들러를 직접 호출하는 우회로를 만들지 않는다. `_invoke`의 계약·권한·승인·예산·의존성·
근거·Journal 경계를 그대로 사용하거나 공통 적용 경계로 이동하고 옛 중복 경로를 제거한다.

호출 신원에는 현재 호출 위치와 반복/병렬 경로, 실제 선택 대상/판본·캡처·인자 의존성이
반영돼야 한다. 같은 부품을 두 위치에서 호출한 영수증은 분리한다. 동일 실행의 재개에서
대상이나 캡처가 바뀌면 기존 지문/분기 불일치로 드러나야 한다. 분석 요약의 신원을 호출
신원으로 쓰지 않는다. 정의 위치와 호출 위치를 둘 다 진단에 남긴다.

IBL 내부 부품을 감쌀 때 별도 최상위 실행·Journal·예산을 시작하지 않는다. 외부 Script·
위임 등 이미 독립 수명이 있는 경계는 기존 자식 작업/영수증 연결을 유지한다. 완료된
외부 효과의 중복 방지, 효과 불명, suspended의 catch/finally 제외, 취소·공유 용량을
보존한다. 보편적 exactly-once를 약속하거나 unknown 효과를 자동 재시도하지 않는다.

Callable은 계속 실행 내부 값이다. HTTP/MCP/Script JSON으로 클로저를 보내거나 되살리는
기능은 이번 범위가 아니다. 공개 보고서는 계약과 정의 참조만 내보내고 캡처 실제 값·비밀·
권한 토큰은 내보내지 않는다. 호출 계약이 호환돼도 호스트/전송 수명이 다르면 해당 경계에서
명시적으로 거절한다. 기존 ForeignRef의 소유자·세션 수명은 유지한다.

## 8 구현 순서와 단계별 완료 조건

1. **기준선과 변환 관계 고정.** 세 반례와 직접/간접·지역/저장·이름 함수/람다 조합의
   생성 시험을 모듈별 pytest에 둔다. 기존 값·실행 순서·거절·영수증의 기준선을 기록한다.
   실패 중인 기대 동작을 main에 남기지 않고 각 구현과 함께 시험을 활성화한다.
2. **공통 계약과 적용 입력 모델.** 정의/값/특수화/호출 신원을 분리하고 기존 모든 생산자의
   계약을 정규화한다. 참조/명명 적용 문법과 평가 순서도 이 단계에서 확정한다. 기존 호출만으로
   describe·check·실행 계약이 일치해야 다음 단계로 간다. 사용자에게 새 문법을 아직 노출하지 않는다.
3. **값 전달과 분석 요약 통합.** §4의 전달 연산과 §5의 부품 공통 요약을 연결한다. get 하나,
   람다 하나가 아니라 전체 전달/대상 조합으로 닫힘을 확인한다. 이 둘은 2단계 뒤 독립 작업이
   가능하나 병합 시 동일 계약 ID·대안·특수화 규칙을 소비해야 한다. preflight의 호출 수/승인
   안내도 같은 그래프에 연결한다. 요약 사용/미사용의 판정과 실행 결과가 일치해야 한다.
4. **효과를 가진 부품의 생성·적용.** 잠재 효과와 현재 평가 효과, 콜백 요구 효과를 도입한다.
   도구·함수 참조와 명명 적용을 Runtime의 기존 경계에 연결한다. 파서만 먼저 열거나
   람다의 pure 검사만 제거하지 않는다. 순수 호스트·권한·승인·중첩 재개 인수와 언어 명세를
   같은 변경 묶음으로 통과시킨 뒤 문법을 노출한다.
5. **프로그램의 재부품화와 소비자 연결.** 지역 프로그램→함수 값→상위 조합→기존 저장→회수→
   다시 조합의 전체 고리를 검증한다. 함수 본문 상시 노출 없이 계약으로 선택할 수 있고,
   정의 변경/비활성화/범위·권한 변화는 현재 판본 검사로 드러나야 한다. HTTP/MCP·앱·조종실·
   작성 프롬프트와 기존 Script 경계까지 연결한다. 새 저장소나 상시 AI 검수 호출을 만들지 않는다.
6. **일반화 인수와 정본 반영.** 아래 행렬과 소비자 회귀·빌드가 통과하고 중복 분석/호출 경로를
   제거한 뒤 완료로 판정한다. 단계별 결과·잔여를 이 문서와 changelog에 기록하고 정본 main에
   pathspec으로 커밋한다. 특정 반례 세 개만 통과하면 이 단계는 미완료다.

구현 의존은 1→2→3→4→5→6이다. 새 어휘/문법을 별도 판본 엔진으로 우회하지 않는다.
기존 유효 프로그램의 값·실패·호출 순서·실행 횟수는 유지한다. 확정 오류의 더 이른 거절과
새로 허용하는 조합은 명세에 명시한다. 이전 resume을 무조건 호환시키지 않으며 정의/코어
의미 변경 시 기존 명시 오류·새 검사/reuse 정책을 따른다.

## 9 개별 반례를 넘는 인수 기준

### 9.1 조합 변환 행렬

시험 축을 교차해 생성하되 같은 축 이름을 코드에 특별 취급하지 않는다. 전 조합이 같은
결과를 내야 한다는 뜻은 아니며, **같은 계약·효과·값·범위·평가 순서가 성립하는 변환**만
동등성을 요구한다. 예를 들어 필드가 존재할 때 `.f`와 get은 같지만 키 부재 의미까지 같지는 않다.

| 축 | 반드시 포함할 변형 |
| --- | --- |
| 부품 출처 | 내장 함수, 순수/외부/모델/unknown 어휘, 람다, 지역 함수, 저장 함수, 여러 문장 프로그램 |
| 운반 | 직접, 별칭, 필드/get, 알려진/동적 인덱스, spread, 유한 조건 선택, 인자, 반환, Result |
| 적용 | 위치/명명/파이프, 기본값·별칭·op, 누락/중복/잘못된 타입, 잘못된 후보가 섞인 합집합 |
| 효과 문맥 | 생성/전달만 함, 실제 호출, 호출 없는 고차 함수, 0/1/N회·조건부 호출, 순수 요구 위치 |
| 분석 차이 | 같은 입력 공유, 다른 타입·캡처·경로·op, 알려진/열린 형태, 후보/특수화 예산 초과 |
| 실행 경계 | each/병렬/중첩, 승인·재전송·취소·중단·효과 불명, 같은 코드 재개, 수정 코드 reuse |
| 소비자 | check/describe/실행, 저장/회상, HTTP/MCP, 값 전용 호스트, 앱, 로컬/PC/Android의 지원 경계 |

값·반환 계약·효과·자원·오류 종류/정의 위치·실제 잎 호출 순서/수·근거 보존을 비교한다.
표현을 고친 서로 다른 프로그램의 내부 call_id가 같다고 요구하지 않는다. 각 프로그램의
재개에서 호출 신원이 안정적이고 서로 다른 실제 호출을 합치지 않는지 별도로 확인한다.

### 9.2 규모·제한·분석과 실행의 분리

이름 있는 함수·람다·혼합·반환 부품·컨테이너 선택 사슬에 동일한 분기 DAG를 적용한다.
깊이 6/10/14/30과 생성된 더 큰 비재귀 사례에서 본문 분석·요약 적용·키/계약 노드 수·
진단 출력량을 계측한다. 같은 특수화의 두 번째 본문 분석은 없어야 한다. 서로 다른 캡처와
정적 자원은 별도 특수화여야 하며 섞인 효과/쓰기 자원/오류 위치가 없어야 한다.

요약을 끈 작은 기준선과 결과·오류·효과·자원·의존성을 대조한다. 실제 호출 횟수와 모델
방문 상한이 분석 재사용 때문에 줄어들면 실패다. 거대한 고유 특수화·재귀·열린 후보를
주입해 제한의 사유·생략 수·실행 검사/거절을 확인한다. 시간 하나만 합격 기준으로 쓰지 않는다.

### 9.3 큰 프로그램을 다시 조합하는 인수

저장된 정답 관용구가 없는 두 종류 이상의 과제에서, 명시 계약을 가진 부품을 그 자리에서
구성한다. 예시는 자료 수집/정규화/검증/출력과 장치 관측/판정/조작/회수다. 업무명·구체
어휘는 시험 데이터이며 코어 분기의 근거로 쓰지 않는다.

각 과제에서 수집기·변환기·출력기를 교체하고 완성 프로그램을 다시 다른 프로그램의
인자로 전달한다. 첫 실행은 지역 정의만으로 가능해야 한다. 그 뒤 기존 저장/회수 경로로
되가져와 다른 입력·다른 부품과 합성한다. 입력/결과/효과 계약이 맞는 교체에 절차 본문을
복사할 필요가 없어야 한다. 계약 불일치·부분 실패·승인 대기·원천 누락도 포함한다.
기능어·어휘의 수, 파이프 수신율, 코드 길이는 이 인수를 대신하지 않는다.

### 9.4 회귀와 작성 표면

개발 중 `scripts/select_tests.py --files … --explain`과 직접 경계 시험을 사용한다.
새 시험은 기존 `test_ibl_v2_call_analysis.py`, `test_ibl_v2_types.py`, `test_ibl_v2_preflight.py`,
`test_ibl_run_journal.py`, 함수 저장/실행 등 책임 모듈 시험에 둔다. 별도 회차 시험 엔진을 만들지 않는다.

공통 언어/실행 변경의 최종 검증은 [회귀 절차](REGRESSION_TESTING.md)에 따라 비system 전수와
관련 system 묶음을 실행한다. Python 라이브러리, 어휘 배포/분할, 긴문장 전체 실행·재개 등
해당 경계를 포함한다. 어휘/교재 파생물은 `build_ibl_nodes.py`로 재생성하고 `--check`,
Android 번들·층·파일 크기와 변경한 frontend가 있으면 실제 tsc를 검사한다.
전수 실행 중에는 문서를 포함한 추적 파일을 편집하지 않고, 시험 집계와 명령 종료 코드를
모두 확인한다. 전체 통과를 소비자/외부 환경의 무제한 호환으로 표현하지 않는다.

## 10 범위와 완료 판단

이번 범위에 넣지 않는 것은 무제한 재귀, 살아 있는 실행 스택의 저장/전송, Callable의
외부 JSON 직렬화, 일반 분산 워크플로 엔진, 새 권한/승인 원장, 영속 분석 캐시,
자동 업무 어휘 생성, 임의 외부 코드의 완전한 효과 증명이다. 이 제한은 새 실패 때마다
편의상 넓히지 않으며 필요하면 별도의 목표·호환성 근거로 재검토한다.

반대로 공통 계약·전달·요약·효과 적용·프로그램 재부품화 중 하나라도 특정 표현에서만
작동하면 이 계획의 설계 수리는 완료가 아니다. 기존 경로의 별칭을 늘려 새 경로의 공백을
숨기는 것도 완료로 세지 않는다. 지원 경계 밖은 위치·이유·대안을 구체적으로 보고한다.

구현 인수 후에는 같은 모델·자료·권한·완료 조건에서 새로운 과제들의 품질, 검수/수리/복구를
포함한 실제 완료 시간과 전체 토큰을 비교한다. 이것은 일반 구조 구현을 미루는 선행 조건이
아니며, 계약 보존·분석 규모 개선과 실제 업무 비용 개선의 주장을 구분하는 후속 평가다.

## 11 계획서 작성 시 검증 상태

현재 구현·기존 설계·진화 목적과 소유 경계를 대조했으며 §2의 세 관측은 직전 조사에서
현재 컴파일러/Runtime으로 재현했다. 이 문서의 참조·명명 적용·효과 모델·공통 요약 확장은
아직 구현되지 않았다. 이번 문서 작성으로 기존 운영 명세가 개정되거나 실행 기능이
추가됐다고 해석하지 않는다. 구현 단계에서는 기준선과 다른 세션의 변경을 다시 확인한다.

작성 검증: 관련 문서 링크·현재 소유 모듈 경로·코드 블록/제목 구조·diff 공백 검사를
확인했다. 이번 변경은 계획서와 연결/이력 문서뿐이며 backend 코드·운영 어휘는 수정하지
않았다. 제안 기능의 인수 시험과 backend 전수는 이번 계획서 작성에서 실행하지 않았다.


## 12 구현과 검증 기록 (2026-10-27)

- 함수·람다 본문, 내장·어휘 계약 전달을 공통 컴파일 요약 경계로 연결했다. 정적 입력·캡처·
  도달 가능성을 키로 삼고 호출별 효과·자원·진단을 합성한다. preflight는 같은 컴파일의 정의와

- `&[node:action]`, `&[fn:이름]`, 명명 적용·파이프를 기존 직접 호출의 바인더와 Runtime 관문에
  연결했다. 람다 생성과 적용의 효과를 분리하고 순수 위치·값 호스트 경계를 유지했다.

- 호출 위치·반복 경로는 영수증 신원, 대상·캡처는 요청 지문으로 나눴다. 캡처가 바뀌었다고
  새 영수증으로 실행하지 않으며 기존 재개의 불일치로 거절한다. 병렬 작업에도 해당 문맥을 전달한다.

  캡처 값을 내보내지 않는다. 실제 외부 서비스·장치의 동작과 모델 토큰 절감은 별도 평가 대상이다.
