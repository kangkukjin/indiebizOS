## 1. 병렬 가지가 3개 이상이면 후속 타입 검사가 틀린다

```ibl
#!ibl edition=2
$x = {n:1} & {n:2} & {n:3}
return $x[0].n
```

기대값은 `1`이지만 `FIELD_TYPE`으로 실행 전 거절한다. 2개 가지는 통과하고 3/4/8개는 실패한다.
세 목록을 병렬 수집한 뒤 `flat_map`하고 각 행의 필드를 읽는 더 실용적인 조합도 같은 이유로 실패한다.

원인: `backend/ibl/ibl_v2_compile.py:304`는 이항 AST의 왼쪽 병렬식 자체를 한 목록 원소로 추론한다.
반면 `backend/ibl/ibl_v2_runtime.py:218`은 연속 병렬 노드를 모두 펼쳐 가지별 결과 목록을 만든다.
결과적으로 검사기는 실제 존재하지 않는 중첩 목록 타입을 후속 문장에 전달한다.

영향: 검색원·문서·함수 호출을 3개 이상 묶는 순간, 각 가지 자체가 정상이어도 후속 조합이 막힌다.
우선 수리 대상이다. 검사에서도 실행기와 같은 가지 열거 규칙을 사용하고,
쓰기 충돌 검사를 유지한 채 2/3/4/8개와 괄호 조합을 함께 검증해야 한다.

## 2. case에서 반환한 가지까지 이후 변수 검사에 합친다

```ibl
#!ibl edition=2
[def:f]($choice) {
  [case:$choice] {
    [when:1] { return {n:1} }
    [else] { $y = {n:2} }
  }
  return $y
}
$r = [fn:f]{choice:2}
return $r.n
```

기대값은 `2`지만 `$y`가 없다는 `UNBOUND`로 거절한다. choice=1에서도 동일하게 거절한다.
같은 내용을 `if/else`로 작성하면 두 입력 모두 통과한다.

원인: `backend/ibl/ibl_v2_compile.py:388`은 모든 case 가지의 환경을 교집합으로 합친다.
이미 return하여 뒤 문장에 도달하지 않는 가지도 포함한다. 바로 위 if 검사에는
`returns_unconditionally`를 이용하는 분기가 있지만 case에는 없다.

영향: 예외적인 분류는 즉시 반환하고 정상 분류만 후처리하는 문장을 함수로 묶기 어렵다.
후속 문장에 실제로 도달하는 가지들만 변수 환경 합성에 참여시켜야 한다.

## 3. catch가 즉시 반환해도 try의 성공 변수를 잃는다

```ibl
#!ibl edition=2
[def:f]($divisor) {
  [try] { $x = {n:8/$divisor} }
  [catch] { return {n:0} }
  return $x
}
$r = [fn:f]{divisor:1}
return $r.n
```

기대값은 `8`이지만 `$x`에 대해 `UNBOUND`로 거절한다. divisor=0의 복구 경로도 실행되지 못한다.
`$x=[try]{{n:8/$divisor}}[catch]{{n:0}}; return $x`로 쓰면 두 입력 모두 통과한다.

원인: `backend/ibl/ibl_v2_compile.py:429`는 catch가 있으면 정상/예외 환경을 무조건 교집합으로 합친다.
예외 경로는 이미 함수를 반환했으므로 뒤 문장의 `$x` 존재 여부와 무관하다.

영향: 실패한 분기는 즉시 종료하고 성공한 값으로 긴 후처리를 계속하는 일반적인 조합이 막힌다.
2번과 같은 제어 흐름 문제이나 try/finally는 정리 실행과 오류 전파까지 고려해 별도로 검증해야 한다.

수리 순서는 병렬 가지 타입 일치 → case/catch의 반환 이후 변수 분석 → 이번 재현의 회귀 편입이다.
그 뒤에는 분야가 다른 자연어 과제에서 실제 작성·실행·복구를 비교해야 한다.
이번 결과만으로 어휘를 늘리거나 프롬프트를 더 길게 만드는 처방을 정당화하지 않는다.
