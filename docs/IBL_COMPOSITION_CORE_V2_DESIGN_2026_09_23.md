## 1. 결정 요약

목표는 **AI가 처음부터 큰 프로그램을 정확히 작성하고, 검증한 부분을 함수·반복·병렬 안에 옮겨도 다시 배울 예외가 생기지 않게 하는 것**이다. 디버깅·재개·프로파일링은 이 기반을 공유하는 후속 소비자다.

권고안은 **명시적 판본을 가진 작은 조합 언어 + 형식화한 공통 실행 핵심**이다. 이하 제안 판본을 `edition: 2`라 부른다. 현재 무표식 프로그램은 `edition: 1`로 보존한다. 새 이름의 어휘를 늘리는 계획이 아니다.

| 결정 | 작성자가 얻는 규칙 |
| --- | --- |
| 값과 실행 상태·진단·출처를 분리 | `$x`는 언제나 그 값이다. 빈 목록이나 메타정보 때문에 봉투로 변하지 않는다. |
| 순수 식 한 벌과 명시적 실행문 | 문자열은 문자열이다. 식·코드가 필요한 자리에 문자열을 다시 해석하지 않는다. |
| 함수 계약을 본문 밖에 명시 | 내부를 리팩터링해도 인자·파이프 입력 자리가 저절로 변하지 않는다. |
| 반복은 map / flat_map / effect를 명시 | 반환값의 모양으로 결과 수집 방식을 추측하지 않는다. |
| 컴파일 결과에 의존 버전·소스 위치 보존 | 검사·실행·재현이 같은 프로그램과 계약을 본다. |
| 판본별 프런트엔드, 공통 실행 핵심 | 기존 자산을 유지하면서 규칙을 바꿀 수 있다. |

앞으로 어떤 기능도 바꾸지 않을 것이라는 보장은 할 수 없다. **값의 의미·조합 법칙·호환 경계는 고정하고, 기능 추가가 그 법칙 안에서 일어나게 하는 것**을 장기 안정성의 기준으로 삼는다. 아래 의미론은 권고 결정이며, 표기의 채택은 12절의 생성 실험을 통과해야 한다.

## 2. 현재 기반과 실제 마찰

새로 만들 필요가 없는 기반: `ibl_code_ir.py`의 Code/Ref/Literal, `ibl_typecheck.py`와 `ibl_value_types.py`, 공용 `value_semantics.py`, `ibl_traceback.py`, `pipeline_state.py`의 재개, `model_call_context.py`와 `execution_trace.py`의 관측이다. 최근 preflight와 AI 경계 계약도 유지한다.

| 관찰한 위치 | 현재 동작 | 설계상 문제 |
| --- | --- | --- |
| `backend/ibl/workflow_binding.py::_v4_var_payload` | 내용에 따라 message/items/원 봉투를 선택 | 같은 종류의 결과라도 빈값·형제 메타정보에 따라 전달 구조가 변한다. |
| `backend/ibl/ibl_exec_each.py::_each_success_rows` | 목록은 펼치고, 비통화 결과면 원 행 통과 | 몸의 반환 타입을 바꾸면 반복의 뜻도 달라진다. |
| `backend/ibl/workflow_contract.py::_free_vars`, `pipe_input_param` | 자유 변수로 서명을 만들고 첫 파이프 형태에서 입력 슬롯 추론 | 내부 편집이 공개 호출 계약을 바꿀 수 있다. |
| `backend/common/safe_expr.py`, `ibl_predicates.py` 및 식 슬롯 | 일반 값 구성과 문자열 식·조건이 공존 | 같은 계산도 위치에 따라 인용·이름 참조 규칙을 알아야 한다. |
| `backend/ibl/ibl_typecheck.py::_type_fn_call` | 외부 함수 본문 해시로 반환형 캐시 | 하위 정의 변경을 반영하지 못하는 경우를 격리 재현했다. |
| `backend/ibl/ibl_value_types.py`, `common/currency.py` | 업무 값·봉투·함수 반환을 여러 경로에서 해소 | 값 자체의 필드와 실행용 필드의 경계를 소비자들이 알아야 한다. |

격리 재현 결과: `{items:[행],success:true}`는 목록, 빈 items는 봉투, 같은 행에 provenance 객체를 붙인 결과도 봉투로 추출됐다. 전체 실행 경로 모두가 그렇다는 주장이 아니라 **해당 공용 함수의 실제 동작**이다.

함수 A가 B를 부르고 B의 반환을 a열에서 b열로 바꾸면, 따뜻한 캐시는 a열 소비를 통과시켰고 캐시를 비우면 거절했다. 생산자·운영 DB를 바꾸지 않은 메모리 실험이다. 이는 학습량으로 해결할 문제가 아니다.

이 근거가 IBL과 Python의 전체 작성 능력 차이를 설명하지는 않는다. [기존 조합 조사](IBL_COMPOSITION_DIRECTIONS_2026_09_23.md)는 교재 공급·입력 규모·재사용 부품의 범위도 지적한다. 이미 수정한 [함수 반환 결함](IBL_IDIOM_EXPOSURE_REPAIRS_2026_09_09.md)을 현재 미해결로 다시 세지 않는다.

## 3. 대안 검토와 기성 언어에서 가져올 것

| 대안 | 장점 | 비용·결정 |
| --- | --- | --- |
| 현행 형식 유지, 교재·예외 처리만 보강 | 이행 비용이 작음 | 내용 의존 추출·함수 계약 추론까지 안정시키지는 못한다. 호환판 유지에 사용한다. |
| Python/TypeScript로 전면 교체 | 모델의 기존 코드 작성 지식·생태계 활용 | 같은 도구·효과·출처·부분 실패·분산 실행 계약은 여전히 필요하다. 비교 기준으로 반드시 포함하되 우월성을 미리 가정하지 않는다. |
| Starlark 등 기성 제한 언어를 통째 채택 | 명시적 평가·값·함수 설계를 재사용 | 도구 효과·병렬·재개·회원 기기와 현재 IBL 자산을 연결할 비용이 크다. 원리를 참고하고 엔진 교체는 보류한다. |
| **IBL의 의미론을 고정하고 얇은 표기를 연결** | 기존 실행 자산을 활용하면서 예외를 줄임 | 값/봉투 경계와 판본 이행이 필요하다. **권고안**이다. |

참고한 일차 자료와 채택 범위:

- [CEL](https://cel.dev/overview/cel-overview): 환경에 대해 parse→check→evaluate하고 검사한 AST를 반복 사용한다. IBL의 모든 식 슬롯이 같은 컴파일 경로를 사용하도록 한다. CEL 자체의 문법·숫자·함수 의미를 그대로 수입하는 결정은 아니다.
- [Starlark 명세](https://github.com/bazelbuild/starlark/blob/master/spec.md): 값 전달·이름 범위·불변성의 명시성을 참고한다. IBL은 외부 효과를 수행하므로 동일한 결정성을 주장하지 않는다.
- [Rust Result](https://doc.rust-lang.org/std/result/): 성공 값과 오류를 별개로 표현한다. IBL 작성자가 매 호출마다 포장을 벗기게 하는 대신 실행기가 전파하고, 복구할 때 명시적으로 다룬다.
- [TypeScript 구조적 타입](https://www.typescriptlang.org/docs/handbook/type-compatibility): 업무마다 새 명목 타입을 만들지 않고 필요한 필드 구조로 조합을 검사한다. TypeScript 전체 기능이나 그 비건전성까지 답습하지 않는다.
- [Rust 증분 계산](https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation.html): 의존관계와 지문을 함께 기록한다. 외부 조회·AI·쓰기를 순수 계산처럼 자동 캐시하지 않는다.
- [Rust editions](https://doc.rust-lang.org/book/appendix-05-editions.html): 새 규칙을 명시적으로 선택하고 기존 소스의 뜻을 유지한다. IBL의 실제 하위 호환 범위는 10절에서 별도로 정한다.

가장 큰 투자 대상은 아래 핵심 의미론이다. 생성 실험에서 익숙한 Python 표기가 더 유리하다고 나오면 그 결과를 수용할 수 있도록, 핵심 실행 계약을 대괄호 표기와 분리한다. 단, 임의 Python/TypeScript를 같은 IR로 자동 변환할 수 있다고 약속하지 않는다. 그 경우에도 제한된 새 프런트엔드 또는 기존 script 경계 중 하나를 명시적으로 선택해야 한다.

## 4. 바뀌면 안 되는 조합 법칙

관찰 동등성은 **값·성공/실패·완전성·선언한 외부 효과**를 기준으로 한다. 로그 ID, 함수 추출로 늘어난 스택 프레임, 실행 시간은 동일성에서 제외한다. 병렬 효과의 순서는 선언한 의존 순서 안에서 비교한다.

1. **값 보존**: `let x = C; use(x)`에서 C는 한 번 실행되고 x는 결과 값 그대로다. 빈 목록·빈 문자열·null도 동일하다.
2. **메타정보 비간섭**: 동일한 성공 값에 출처·시간·표시 힌트를 붙여도 일반 연산의 입력 타입과 값이 변하지 않는다. 명시적 진단 조회는 예외다.
3. **함수 추출 보존**: 자유 입력을 명시 인자로 옮기고 실행 순서를 보존하면, 본문을 함수로 추출해도 호출자의 관찰 결과가 같다. 효과가 있는 코드를 복제하거나 생략하는 법칙은 아니다.
4. **파이프/명시 호출 동등**: `C >> F{p}`는 C를 한 번 평가해 F의 선언된 입력 인자로 전달한 것과 같다. 수신 인자가 겹치면 오류다.
5. **이름 변경 보존**: 바인딩과 참조를 함께 바꾸는 지역 변수 이름 변경은 결과에 영향을 주지 않는다. 텍스트 치환이 아니라 기호로 수행한다.
6. **map 법칙**: 항등 map은 값·순서를 보존한다. 중첩 목록을 임의로 펼치지 않는다. map 합성 최적화는 순수성·오류 순서가 같을 때만 가능하다.
7. **반환 보존**: 값은 지역 함수·등록 관용구·저장 워크플로를 거쳐도 같은 값이다. 빈값을 반환 누락으로 취급하지 않는다.
8. **전송 보존**: 지원되는 값·실행 계획을 저장/전송/복원하면 타입과 값이 같다. 사용자 레코드 키로 내부 태그를 추측하지 않는다.
9. **검사 일관성**: 정의·사전·판본이 같으면 차가운 검사와 캐시 검사가 같은 진단을 낸다. 검사와 실행이 같은 계약을 사용한다.
10. **규모 보존**: 처리 한도 때문에 남긴 항목을 성공한 전체 처리로 표현하지 않는다. 명시적 선택과 자원 고갈을 구별한다.

파이프의 결합 법칙은 입력 바인딩과 효과 순서가 같은 경우에 한정한다. 실패를 잡거나 출처를 조회하는 문맥까지 무조건 재배치하지 않는다. 일반적인 부작용 프로그램의 참조 투명성을 주장하지 않는다.

## 5. 값·실행 결과·증거의 세 층

### 5.1 언어의 값

일반 데이터 값은 `Null | Bool | Number | Text | List<Value> | Record<Text,Value>`다. 이에 명시적 제어 값 Unit·Result와 컴파일된 Callable을 구분해 지원한다. `Unit`은 의미 있는 반환값이 없음을 뜻하며 null·빈 목록과 다르다. Result는 6.4절의 오류 수집에만 명시적으로 나타난다. 내부 실행 기록 전체는 Value가 아니며, 제어 값과 Callable도 일반 JSON 데이터로 위장하지 않는다.

- `$x`는 값 그 자체를 읽는다. `$x.items`는 x가 실제로 items 필드를 가진 Record일 때만 가능하다.
- List의 0/1/N건은 항상 List다. 문자열이 길거나 개행을 가졌다는 이유로 다른 값을 선택하지 않는다.
- 사용자 데이터의 `success`, `error`, `value`, `items`, `final_result`는 평범한 필드다.
- 레코드/목록은 언어 수준에서 불변이다. 변수 재바인딩은 가능하지만 함수나 병렬 분기가 인자로 받은 객체를 제자리 수정할 수 없다.
- 숫자·문자열·날짜의 관측·비교는 현재 `common/value_semantics.py`의 명시적 공용 정책을 사용한다. 이 개정에 별도의 숫자·날짜 해석기를 섞지 않는다. 복사한 `"007"`은 계속 문자열이다. 산술 자리의 숫자 관측과 데이터 저장 타입은 구별해 명세·지문에 포함한다.
- 결측 필드는 엄격 접근에서 오류다. `has(record,key)`와 `get(record,key,default)`로 결측을 명시 처리한다. null은 존재하는 값이므로 결측과 합치지 않는다.
- 문자열/목록 길이는 `len(value)`로 읽는다. 문자열의 `.message` 별칭이나 목록의 가상 `.items`는 새 판본에 없다.

기존 컬렉션 교환 규약 `{items:[...]}`는 **도구 어댑터의 외부 규약**으로 유지할 수 있다. 언어 내부에서는 그 컬렉션을 `List<Record>`로 받는다. 새 통화 종류를 여러 개 만드는 것이 아니라 **통화의 외부 포장과 언어의 값을 구분**한다. 스칼라·효과·map_data 등의 기존 UI 사용처는 명시적인 어댑터·첨부 결과로 보존한다.

### 5.2 실행 결과

내부 개념 모형(구현 클래스 이름을 강제하지 않는다):

```text
Outcome<T> = Ok(value:T, evidence:Ref)
           | Fail(error:Diagnostic, partial:Optional<T>, evidence:Ref)

Binding<T> = {value:T, evidence:Ref}
Diagnostic = {code, kind, message, source_span, frames, details_ref}
```

값 계산·할당·파이프·함수 호출은 Ok에서 T만 바인딩한다. 증거 참조는 같은 바인딩의 실행기 측 연결로 보존한다. `.success`를 소비자마다 확인하고 벗기는 코드를 작성하지 않는다. Fail은 현재 계산을 중단하며 catch나 명시적 수집 정책이 받는다.

효과와 반환형은 독립이다. 파일 쓰기가 선언된 영수증 Record를 반환할 수도, 알림이 Unit을 반환할 수도 있다. 둘 다 효과가 있다는 사실은 함수 계약의 effects에 남는다. Unit을 빈 items나 입력 행으로 바꾸지 않는다.

부분 성공은 기본적으로 `Fail(kind:partial, partial:성공한 값)`이다. 상류 일부 실패·처리 누락이 완전한 성공으로 연결되지 않는다. 의도한 take/filter 선택이나 표시 미리보기 절단은 이 실패가 아니다. 기존 정직 계약이 구분하는 원천 누락·미처리만 대상으로 한다.

`[catch]`의 `$error`는 Diagnostic 필드와 `has_partial`, `partial`, `evidence`를 가진 고정 FailureView다. 부분 자료가 업무적으로 유효한 경우 `has_partial`을 확인하고 `$error.partial`을 명시적으로 사용할 수 있다. 그 선택은 증거에 `handled_partial`로 남고 원천의 불완전성은 지워지지 않는다. partial 부재와 실제 null 부분값은 has_partial로 구분한다. 복구 후 제어 흐름의 성공과 사용자 작업의 전건 완료는 서로 다른 판정이다. Result의 `error_of`도 같은 FailureView를 반환한다.

취소·권한 거절·자원 예산 고갈은 보통 도구 오류와 다른 kind다. 기본 폴백으로 삼키지 않는다. 특히 취소는 catch가 성공으로 바꾸지 못하며 finally의 제한된 정리만 수행한다. 이미 발생한 외부 쓰기를 예외 처리만으로 되돌렸다고 표시하지 않는다.

### 5.3 진단·출처가 사라지지 않는 규칙

값만 넘겨 진단을 잃는 변경은 허용하지 않는다. 순수 식도 입력 바인딩의 evidence 참조를 결과에 연결한다. 조건 결과로 실행 경로가 선택되면 그 조건의 증거도 연결한다. 함수가 만든 내부 실행 기록은 값과 별도로 추적하며, 표시용 요약은 원본을 바꾸지 않는다.

기본 증거 전파는 의존 참조의 보수적인 DAG다. 정확한 행별 출처 추적까지 완료했다고 주장하지 않는다. `partial`, `truncation`, 출처 부재 등 기존 정직 표지는 작은 참조로 끝까지 회수 가능해야 한다. 증거를 읽기 위해 업무 데이터에 키를 복사하지 않는다.

표준 내장 함수 `evidence($x)`는 해당 값의 고정된 공개 증거를 읽기 전용 Record로 투영한다. 일반 필드 접근과 구별한다. IR에서는 InspectEvidence로 내리고 **value 해시뿐 아니라 evidence 지문에도 의존하는 관측**으로 기록한다. 외부 효과는 없지만 일반 값 전용 순수 캐시와 같은 키를 쓰지 않는다. 파일·원문 전문은 기존 권한/보관 정책의 참조로 제공한다. metadata를 추가해도 value의 해시와 일반 순수 계산 결과는 변하지 않지만, 이 관측과 재사용 적합성을 결정하는 증거 지문은 달라질 수 있다.

## 6. 표현식·함수·제어의 정규 작성법

아래 `ibl-v2`는 **판본 2 문법**이다. 무표기 판본 1 파서에 보내면 안 된다. API에서는 `edition:2`를 지정하고, 파일에는 `#!ibl edition=2`를 사용한다. 둘이 충돌하면 실행 전에 거절한다.

### 6.1 식 한 벌, 문자열 한 뜻

```ibl-v2
#!ibl edition=2
$배수 = 2
$행 = {id:"007", price:3, qty:4}
$결과 = {id:$행.id, total:$행.price * $행.qty}
$제목 = f"${행.id}: ${결과.total}"
$계산 = ($r) => $r.price * $r.qty * $배수
```

일반 문자열은 문자 그대로다. 보간은 f 문자열에서만 한다. 보간은 Text·Number·Bool만 규정된 방식으로 표시하고 구조값·null·Unit은 암묵 문자열화하지 않는다. 구조값은 `json(value)`, null 처리는 조건식/명시 기본값으로 작성한다. `${…}`는 한 번 해석하며 값 안의 `$`·중괄호를 재해석하지 않는다.

객체·목록·함수 인자·할당·조건 모두 같은 Expr AST를 쓴다. 값 배열과 코드 배열을 내용으로 추측하지 않는다. 파라미터 객체의 평가 순서는 소스 순서이고 부작용은 없으며, 중복 키·인자는 오류다.

`($r) => expression`은 순수 콜백이며 매개변수와 생성 시점의 바깥 값을 캡처한다. 이후 바깥 변수 재바인딩은 이미 만든 콜백을 바꾸지 않는다. `where`, `set`, `reduce` 등은 사전에서 Callable 인자로 선언한 자리에 이를 받는다. 임의 문자열을 식으로 다시 파싱하지 않는다.

예: `[table:filter]{where:($r) => $r.score >= $최소}`. 기존 `where:"score >= 5"`와 구조 조건 객체는 edition 1의 작성법이다. 마이그레이터가 해석 가능한 경우에만 같은 Expr로 번역한다.

순수 식은 읽기 전용 값 처리와 허용 내장 함수만 수행한다. 도구·AI·파일 접근은 Computation이다. 이를 문자열 보간이나 순수 콜백 안에 숨기지 않고 앞 문장에서 호출해 값을 받는다. 이것은 의도적인 두 종류의 구문이며, 같은 종류 안에서만 치환·추출 법칙을 적용한다.

### 6.2 함수는 명시적인 입력과 한 반환 의미를 가진다

```ibl-v2
[def:가중점수]($목록, $배수=2) {
  $목록 >> [table:each]{mode:"map"} {
    return {id:$it.id, weighted:$it.score * $배수}
  }
}
$목록 = [{id:"a",score:7},{id:"b",score:5}]
$결과 = [fn:가중점수]{목록:$목록,배수:3}
return $결과
```

- 명시 인자 목록이 서명이다. 본문의 미바인딩 변수는 오타/누락 오류이며 자동으로 새 인자가 되지 않는다. 기본값은 불변 리터럴/순수 상수식이며 도구를 호출할 수 없다.
- 이름 붙은 함수는 호출자의 지역값을 암묵 캡처하지 않는다. 필요한 값은 인자로 받는다. 참조하는 다른 함수는 컴파일 때 기호·개정으로 연결한다.
- 함수/프로그램/each 콜백/병렬 가지의 `return`은 가장 가까운 해당 실행 프레임에서 즉시 반환한다. if/try 블록만으로는 새 반환 프레임이 생기지 않는다. finally는 실행하되 그 안의 return은 금지한다.
- return이 없는 블록은 마지막 문장의 값을 반환한다. 빈 블록·함수 정의·할당 문장은 Unit이다. 저장 뒤 앞에서 만든 값을 반환하려면 명시 return을 쓴다. 마지막 값 규칙은 함수·프로그램·조건 블록에 동일하게 적용한다.
- 함수·each·람다는 지역 범위를 만든다. if/try/repeat는 현재 프레임을 사용한다. 분기에서만 할당한 변수는 모든 도달 경로에서 초기화됐을 때만 확정 바인딩이다.
- 순차 repeat는 현재 프레임 변수를 재바인딩할 수 있다. each는 읽기 전용 바깥 캡처와 자기 지역값만 가지며 바깥 변수를 재바인딩할 수 없다. 병렬 분기는 독립 프레임이다.
- 사용자 함수의 첫 번째 선언 인자가 파이프 입력 자리다. 순서를 바꾸면 공개 계약 변경이다. 인자 없는 함수는 파이프를 받지 않는다. 도구는 사전의 `pipe_input`을 사용한다.

지역 함수·등록 관용구·저장 워크플로는 동일한 Callable 계약으로 링크한다. `[self:workflow]`는 저장·관리 경계로 남으며 저장본을 `[fn:]`으로 부를 때 별도의 반환 해제 규칙이 생기지 않는다.

함수 정의는 해당 프레임의 기호 표에 먼저 등록하므로 같은 범위의 앞으로 나온 함수를 참조할 수 있다. 같은 범위의 중복 정의는 오류, 지역 정의는 등록 사전보다 우선이다. 이 선택을 compile plan에 고정한다. 예약 바인딩 `$it`·`$error`·`$i`는 각 실행 프레임에서만 존재하며 인자 이름으로 덮어쓰지 않는다. 일반 사용자 Record의 같은 이름 필드는 제한하지 않는다.

return은 실행 오류가 아닌 별도의 제어 신호다. catch가 가로채지 않으며 finally를 거친 뒤 해당 반환 프레임까지 전달된다. finally가 실패하면 성공/return을 완료로 보고하지 않고 cleanup 실패를 반환한다. 앞선 실패가 있었다면 원인과 cleanup 실패를 함께 보존한다. 병렬 가지의 return은 그 가지를 끝낼 뿐 다른 가지나 바깥 함수를 반환시키지 않는다.

프로그램 최상위의 외부 값도 명시적인 입력 환경이다. 제안 API의 `inputs`에 선택한 이름→값/타입 있는 참조를 넘기며, 컴파일러는 이를 서명으로 검사한다. 이전 턴의 모든 변수를 암묵 주입하지 않는다. 기존 turn_vars 저장소는 재사용하되 edition/value-version을 확인하고 선택한 바인딩만 가져온다. 없는 이름을 과거 대화에서 추측하지 않는다.

첫 도입에서는 현재의 재귀 금지를 유지한다. 다층 비순환 조합은 함수마다 정한 임의의 3/5단 제한 대신 공통 실행 예산으로 관리하는 것을 목표로 한다. 실제 지원 깊이와 자원 한도는 실행 프로파일에 명시하며 무제한을 약속하지 않는다.

### 6.3 파이프·순서·분기

```ibl-v2
$목록 >> [fn:가중점수]{배수:3}
# 위와 동등: [fn:가중점수]{목록:$목록,배수:3}
```

왼쪽 계산은 한 번만 실행한다. 수신 입력 인자를 오른쪽에 동시에 주면 빈값 여부와 무관하게 충돌 오류다. 입력을 받지 않는 명령에 파이프를 연결하면 조용히 버리지 않고 거절한다. 독립 순차 실행은 다음 문장으로 작성한다.

`??`는 catchable 실패에만 동작한다. `[]`, `""`, null은 성공 값이므로 폴백 조건이 아니다. `>>`는 성공 값 전달이다. `&`는 각 가지를 독립 실행하고 **가지 순서의 값 목록**을 반환한다. 목록 가지를 자동 펼치거나 Unit 가지를 삭제하지 않는다.

`&`에서 어느 가지가 실패하면 전체는 Fail이며, 이미 끝난 값과 효과는 보존한다. 시작하지 않은 작업은 중단하고 실행 중인 작업은 가능한 취소를 요청하되 취소 완료를 가정하지 않는다. 각 가지의 종료/미확정 상태가 확인되기 전에는 같은 효과를 재시도하지 않는다. each의 병렬 실패도 같은 정책이다. partial 목록에는 실제 성공 값만 입력 순서로 담고, 원 입력 인덱스·미처리 범위·진행 중 작업은 evidence의 coverage로 보존한다. null 자리표시자로 실패를 위장하지 않는다.

우선순위는 괄호 > `&` > `>>` > `??`다. `A & B >> C`는 `(A & B) >> C`다. 줄바꿈은 문자열/괄호/연결 연산자 문맥 밖에서 문장을 구분한다. v2 교재에는 동일 의미의 `| take:` 단축 표기를 추가하지 않는다.

순차 문장은 기본 fail-fast다. 독립 문장을 계속 실행하려면 해당 실패를 try/catch로 처리한다. if는 Bool 조건만 받으며 비어 있는 else는 Unit이다. AI 의미 판단은 명시 액션으로 Bool/선택 결과를 얻은 뒤 분기한다. 같은 if 표기가 묵시적인 모델 호출을 만들지 않는다.

### 6.4 반복의 뜻을 결과 모양에서 추측하지 않는다

| mode | 몸의 반환 | 전체 결과 |
| --- | --- | --- |
| `map` (v2 기본) | T | 입력 순서의 List<T>. 목록을 반환하면 중첩 목록이다. |
| `flat_map` | List<T> | 정확히 한 겹을 펼친 List<T>. 비목록 반환은 오류다. |
| `effect` | 반환값 사용 안 함 | Unit. 수행 효과·영수증은 실행 기록에 남는다. |

빈 입력은 map/flat_map에서 `[]`, effect에서 Unit이며 몸을 호출하지 않는다. `parallel:n`은 실행 동시성만 바꾸고 결과 순서를 바꾸지 않는다. 함수 추출은 이 정책을 바꾸지 않는다.

`on_error:"stop"`이 기본이다. 수집이 필요한 경우 **map에서만** `on_error:"collect"`를 허용하며 각 입력마다 명시적 `Result<T>` 값을 하나 낸다. Result는 `Ok(T)` 또는 `Err(Diagnostic, partial?)`라는 태그 값이며 사용자 Record의 error 키와 구별한다. `is_ok(r)`, `unwrap(r)`, `error_of(r)`가 표준 순수 접근이다. Err의 unwrap은 실패다. flat_map/effect의 collect는 금지하고 map으로 수집 후 선택·펼치도록 안내한다.

map에서 Unit을 반환하면 List<Unit>이며 원 행으로 바꾸지 않는다. 원 행이 필요하면 몸이 `return $it`를 명시한다. 기존 keep·collect의 `_2` 필드 자동 병합은 v2 핵심에서 하지 않는다. `{source:$it,result:$결과}`처럼 업무 레코드를 작성한다.

v2의 each는 입력 전체가 의미상 대상이다. `limit`로 암묵 선택하지 않는다. 일부만 원하면 먼저 take/filter를 사용한다. 실행 프로파일의 행/시간 예산을 넘으면 남은 범위와 부분 결과를 가진 자원 오류다. 한도를 없애거나 자동으로 오래 실행한다는 뜻은 아니다.

### 6.5 파서가 공유할 골격

아래는 전체 생성 문법을 대신하는 것이 아니라 구현 시 여러 파서가 다른 경계를 만들지 않게 하는 골격이다. P0에서 토큰/우선순위/위치 규칙을 실행 가능한 문법 명세로 확정한다.

```text
Program       := EditionHeader? Statement*
Statement     := FunctionDef | '$name' '=' Computation | 'return' Computation | Computation
FunctionDef   := '[def:name]' '(' Parameters? ')' Block
Computation   := Fallback
Fallback      := Pipeline ('??' Pipeline)*
Pipeline      := Parallel ('>>' Call)*
Parallel      := Term ('&' Term)*
Term          := Expr | Call | ControlBlock | '(' Computation ')'
Call          := '[node:action]' ArgumentRecord? CallbackBlock?
Expr          := Literal | Ref | Field | Index | Record | List
               | UnaryExpr | BinaryExpr | PureCall | Lambda | FormatText
Lambda        := '(' '$name' (',' '$name')* ')' '=>' Expr
Block         := '{' Statement* '}'
```

ControlBlock은 기존 if/else·case·try/catch/finally·repeat의 구획을 재사용하되 조건은 동일 Expr다. case는 한 Expr를 한 번 평가하고 공용 동등성으로 소스 순서의 첫 일치 가지를 고른다. repeat의 N은 0 이상 정수, while은 회차 전, until은 회차 후에 Bool을 검사한다. `$i`는 0부터 시작하는 읽기 전용 회차 값이며 repeat의 일반 결과는 Unit이다. 누적값은 같은 프레임의 명시 변수로 만들거나 reduce를 쓴다. 자원 중단은 정상 반복 종료와 구별한다.

Expr의 우선순위와 연산자 집합은 하나의 명세/컴파일러가 소유한다. 파라미터 Record를 먼저 JSON5로 읽어 참조·콜백의 구분을 잃은 다음 정규식으로 복구하는 경로는 v2에 두지 않는다. 원문 토큰·SourceSpan을 유지한 뒤 Expr/Code로 구분한다. `[table:each]`의 뒤 블록은 사전/코어에 선언된 고차 실행 자리이며 일반 데이터 객체와 내용으로 구별하지 않는다.

v2의 파이프 오른쪽은 입력을 선언한 Call이다. 조건·try 블록으로 입력을 나눠 전달하려면 먼저 변수에 받거나 명시 함수로 묶는다. 블록 안의 어느 변수에 앞 값을 넣을지 추측하지 않는다. 이 제약도 첫 생성 실험의 대상이며, 블록 입력 표기를 바꾸더라도 공통 핵심의 명시 인자 의미는 유지한다.

## 7. 도구·스크립트와의 경계

### 7.1 결과를 어댑터에서 한 번만 해석한다

사전의 액션/op 계약에 아래 정보가 필요하다. 기존 returns/flow를 폐기하고 손으로 두 벌 유지하지 않고, 빌더가 호환 표현을 파생하게 한다.

```yaml
# 지원 스키마 예시 — ibl_actions.yaml 원천에서 선언하고 빌더가 검증한다.
callable_contract:
  version: 1
  params: {query: Text}
  pipe_input: query
  result: List<Record>
  effects: [read_external]
  nondeterministic: true
  adapter:
    protocol: legacy-envelope
    value_path: /items
    completion: declared-envelope
```

value_path는 결과가 비었는지에 관계없이 고정이다. 필요하면 op/source별 명시 변형을 선언한다. 실패·partial·truncation의 해석은 기존 공용 정직 계약과 어댑터 선언을 사용한다. 임의 데이터에 error 키가 있다는 이유만으로 실패로 바꾸지 않는다.

정적 입력으로 변형을 정할 수 없으면 합집합/Unknown으로 유지하고 경계에서 검사한다. 액션 이름별 분기를 파서에 넣지 않는다. v2 어댑터가 없는 도구는 v2에서 unsupported이며, 결과를 보고 그럴듯한 payload를 추측하지 않는다.

복수 산출물은 선언된 Record로 값에 둔다. 시각 렌더링 데이터·표시 지침·실행 영수증은 별도 첨부 채널로 보존할 수 있다. GUI·지도·회원 기기 소비자 검증 없이 봉투 키를 삭제하지 않는다.

경로·몸 별칭 해소는 도구 계약에서 지정한 경로 인자에만 기존 공용 해소기를 적용한다. 모든 Text나 사용자 객체를 순회하며 `~workspace`·`$` 모양을 바꾸지 않는다. 일반 업무 문자열의 보존과 호출 대상 경로 해소를 구별한다.

### 7.2 script는 기성 언어와 연결하는 공통 호출이다

현재 Python/Bash/Node 실행기와 등록 경로는 유지한다. 기존 JSON stdin/stdout 계약은 v1 어댑터로 지원한다. v2 script 등록에는 인자/결과/효과/프로토콜 개정을 선언한다. 파이프 입력은 등록 계약의 지정 인자에 값으로 전달한다.

원 봉투가 필요한 기존 script의 input_as 계약은 v1에 남긴다. v2 script 프로토콜에서는 업무 args와 실행 context/evidence를 분리한다. 자식 프로세스가 명시한 v2 프로토콜에서만 별도 최상위 transport 영역을 사용하며, 기존 args를 몰래 감싸지 않는다. 원문/출처가 업무 입력이면 args에 명시하고, 실행 진단은 context로 제공한다.

스크립트의 내부 자유 계산은 해당 언어가 맡는다. 반환 경계만 v2 Value/Outcome으로 검증한다. 프로세스 종료 코드·JSON 오류·계약 위반은 같은 실패 모델에 연결한다. 현재성·부작용·재시도 적합성을 선언하지 않은 script는 Unknown effect이며 자동 재실행/캐시 대상이 아니다.

## 8. 컴파일과 검사

```text
소스 + edition + 사전/관용구 스냅샷
  → 판본별 parse (원문 범위 유지)
  → name resolution (명시 인자·지역 기호·정의 연결)
  → typed core IR (Value / Expr / Computation 구별)
  → 구조·효과·규모 검사
  → ExecutionPlan + 계약/의존 지문 + 소스맵
  → 실행 / 디버깅 / 재현 / 재개
```

핵심 IR의 개념 노드는 Literal, Ref, Record, List, PureCall, InspectEvidence, Lambda, Invoke, Bind, Sequence, Return, If, Try, Repeat, Each, Parallel, Fallback이다. 정의·루프 몸을 문자열로 되돌려 행마다 파싱하지 않는다. 기존 Code/Ref/Literal을 확장하고 두 번째 완전한 실행기를 영구 운영하지 않는다.

컴파일 계획에는 edition, IR/값 프로토콜 버전, 의미론 버전, 심볼 ID, 원문 범위, 루트/참조 정의의 해시, 어댑터 계약 버전, 필요 capability를 포함한다. source span은 소스 해시·개정·시작/끝 offset이며 줄/열을 파생한다. 호출 지점과 정의 지점을 모두 남긴다.

검사와 실행 사이에 관용구가 개정돼도 실행 중 다른 몸통으로 바뀌지 않게 정의 스냅샷을 고정한다. 시작 시 필요한 버전이 없으면 효과 발생 전에 거절한다. 실행 중 일부 동적 참조가 꼭 필요하면 그 경계에서 같은 검증을 수행하고 동적 의존임을 기록한다.

스냅샷은 해시만 적는 것으로 충분하지 않다. 해당 해시의 실제 본문/IR·어댑터가 회수 가능하거나 현재 프로세스에 고정돼 있어야 한다. 핸들러 리로드와 프로세스 재시작 뒤 그 구현을 복원하지 못하면 재개를 거절한다. 일반 파일 경로가 존재한다는 사실을 같은 구현의 증거로 삼지 않는다.

### 8.1 타입 계약

List<T>, 구조 Record, 선택 필드, Union, Unit, Result<T>, Callable을 지원 범위로 둔다. 가능한 타입은 추론하고 공개 인자·결과 계약은 저장한다. 전체 업무 필드를 공통 강제 스키마로 만들지 않는다.

Unknown은 안전이 증명된 Any가 아니다. 확인하지 못한 경계와 필요한 실행 시 검사를 계획에 남긴다. 선언된 사실·리터럴 추론·관측 예시는 신뢰 등급을 구분한다. 관측한 한 번의 검색 결과로 다음 검색의 필수 열을 확정하지 않는다.

검사 응답은 `valid | invalid | incomplete | failed`를 구분한다. 검사기 예외를 ok:true로 바꾸지 않는다. 알려진 오류는 차단하고, incomplete는 실행 경계 검사를 포함한 계획일 때만 실행 가능하다. 품질·원문 근거·AI 판단의 정확성은 정적 타입 통과로 보증하지 않는다.

### 8.2 효과·의존성

효과는 결과형과 별도로 `pure`, `read_external`, `write_external`, `model`, `unknown`의 집합과 비결정성 정보로 기록한다. 이 이름은 예시 표시이고 최종 필드는 하나의 공용 선언 스키마가 소유한다. 외부 읽기·모델·시간/난수는 pure가 아니다.

함수 계약은 본문 및 하위 호출의 효과를 합성한다. Unknown이 있으면 순수성 최적화를 하지 않는다. 서로 같은 파일·원장에 쓰는 병렬 호출은 정적 충돌을 알 때 거절하고, 모르면 안전한 독립성의 증명으로 표시하지 않는다.

캐시 키는 본문 해시만으로 만들지 않는다. 판본·공용 의미론·계약·참조 함수 및 사전 변형의 의존 지문을 포함한다. 하위 변경은 관련 검사 결과를 무효화하며 따뜻한/차가운 검사의 동등성을 시험한다. 첫 구현은 판본/레지스트리 revision 전체 무효화로 정확성을 얻어도 된다. 정밀 무효화는 성능 근거가 생긴 뒤 한다.

순수 계산의 실행 결과 재사용과 성공한 외부 호출 영수증 재사용은 별개다. 후자는 주체·run·입력·구현·모델/판정 기준·현재성·효과 영수증을 검증해야 한다. 계획 DAG만으로 외부 exactly-once가 성립하지 않는다.

## 9. 프로토콜·진단·자원 계약

- Value와 Record의 내부 키 충돌을 피하기 위해 기존 IR pack처럼 모든 컨테이너를 타입 태그로 감싼 버전된 전송 표현을 사용한다. Unit·Result·Callable은 명시 태그다. 사용자 dict의 특정 키 조합으로 이를 인식하지 않는다.
- 메모리의 숫자·불변 값·식 캡처를 JSON으로 전송할 때의 의미를 고정한다. 숫자 정밀도를 보존하지 못하는 몸은 지원하지 않는 값으로 거절하며 조용히 반올림하지 않는다. 큰 원문은 타입·해시·소유 범위를 가진 참조로 보내되 의미상 같은 값이다.
- 호스트·회원 기기는 edition/IR/value/adapter capability를 협상한다. 오래된 기기에 v2 코드를 v1로 재해석해 보내지 않는다. 지원 몸으로의 명시 실행 요청 또는 지원 불가 응답을 사용한다.
- 동일 계획의 검사·실행·재현은 node_id와 invocation_id를 구분한다. each의 각 행은 같은 소스 노드이지만 다른 실행이다. 모델 사용량과 부모/자식 호출을 이 실행 ID에 연결한다.
- 저장된 외부 응답 재생은 요청·정의·입력 지문이 맞을 때만 가능하다. 바뀐 프롬프트에 옛 응답을 사용하지 않는다. 기록 없는 요청은 재현 모드에서 실패한다.
- row 수·시간·call depth·AI 비용 제한은 ExecutionBudget이며 문법의 데이터 변환 규칙이 아니다. 한도 중단은 Fail과 보존된 부분 결과/미처리 범위를 남긴다. 상위 예산을 하위 함수가 초기화하지 않는다.
- 로그·증거 실패가 도구를 두 번 실행하게 하지 않는다. 대용량 보관·권한·보존 기간은 기존 소유 모듈을 재사용한다. 별도 전역 상태 DB 도입을 전제로 하지 않는다.

## 10. 판본과 마이그레이션

### 10.1 기존 자산의 의미를 먼저 고정

무표식 기존 IBL, 저장 워크플로, 관용구, 트리거, 스케줄, 앱, 해마 예제는 v1이다. DB에 판본 필드가 없으면 v1로 해석한다. 새 파일 헤더는 v2를 선택하는 명시적 선언이며 parser가 무시하는 주석으로 취급하지 않는다.

실행 API의 edition, 저장 정의의 edition, 파일 헤더는 일치해야 한다. 다른 판본 호출은 10.2의 계약 경계를 사용한다. 프롬프트/describe/검사 오류는 현재 작성 판본을 표시하고 해당 판본의 예제만 기본 제공한다. 복원된 턴 변수·스필·재개 티켓에도 값/언어 판본을 기록한다. 무판본 옛 자료는 v1 경로로만 복원한다.

edition 1의 기존 뜻을 그대로 유지한다는 목표와 알려진 오류를 고친다는 목표는 구별한다. 버그 수정도 기존 회귀·실행 결과를 대조하고 별도 변경으로 기록한다. v1 코드를 사용자가 요청하지 않은 v2로 자동 변환해 실행하지 않는다.

### 10.2 두 판본의 공존

v1 프런트엔드는 기존 추출·문자열 식·반복/파이프 정책을 명시적인 LegacyAdapter 노드/호환 모듈로 내린다. v2 런타임 곳곳에 `if old_mode`를 흩뿌리지 않는다. 완전한 v1 lowering 전에는 기존 실행 경로를 어댑터로 감싸 보존해도 된다.

v2에서 v1 관용구를 부르려면 개정에 묶인 인자·반환·효과 어댑터가 있어야 한다. 값/봉투의 형태가 불명인 경우 호출 가능으로 추측하지 않는다. v1에서 v2를 부르는 것도 명시 어댑터가 있는 등록 정의만 허용하며, v1의 결과 표시 계약을 재구성한다. 순수 콜백 자체를 옛 실행기로 넘기지 않는다.

전환은 leaf 관용구부터 호출 그래프 순서로 수행한다. 동일한 공개 이름을 유지할지는 원장의 edition+revision 연결로 결정하며 런타임이 임의로 최신판을 고르지 않는다. 기존 호출자는 이전 개정/어댑터를 계속 가리킨다. 본문·실적·교재의 개정 이력은 기존 원장에 보존한다.

### 10.3 자동 전환 가능한 것과 검토가 필요한 것

| v1 패턴 | 전환 방식 |
| --- | --- |
| 자유 변수 기반 함수 서명 | 컴파일러가 발견한 서명을 명시 인자로 만들고 작성자가 확인. 내부 오타를 정상 인자로 고정하지 않는다. |
| 첫 파이프에서 추론한 입력 | 실제 pipe_input을 첫 인자로 명시. 기존 호출자 인자와 대조한다. |
| do 문자열·단순 문자열 식 | 소스를 해석해 Code/Lambda로 옮긴 뒤 원문/변수 범위 대조. 문자열 치환으로 변환하지 않는다. |
| `$return = ...` | 이후 실행 유무를 확인. 조기 return으로 일괄 치환하지 않는다. 뒤 효과가 있으면 임시값 저장 후 마지막 return으로 옮긴다. |
| each의 자동 펼침/원 행 통과/collect | 반환 계약과 효과를 조사해 map/flat_map/effect 또는 명시 Record 구성으로 변환한다. |
| `$x`의 내용 의존 값 추출 | 가능한 모든 반환 변형을 확인해 명시 decoder/필드 접근으로 옮긴다. 불명은 수동 판정이다. |
| 문자열 자동 보간·산문 별칭 | 의도된 보간만 f 문자열로 전환. 원문 `$` 문자를 보간으로 바꾸지 않는다. |
| `.count`, `.items`, 빈값 폴백 | 실제 데이터 필드인지 가상 접근인지 판정 후 len/직접 값/조건식으로 변환한다. |

전환 전후 비교는 고정 외부 응답과 임시 파일/DB로 수행한다. 생산자 호출·발행·송신을 두 번 실행해 비교하지 않는다. 등가임을 입증하지 못한 정의는 v1에 남긴다. v2의 의도된 의미 변경을 기존 동작과 같다고 표시하지 않는다.

### 10.4 되돌리기

각 정의의 전환 전 소스·edition·계약·호출자 링크·시험 결과를 보존한다. 기능 스위치는 새 v2 진입을 중단할 수 있어야 한다. 진행 중 실행은 시작한 계획을 유지한다. v2 전용 자료를 v1로 오독시키는 rollback은 금지한다.

rollback은 새 계획 선택을 이전 검증본으로 되돌리는 것이다. 이미 발생한 외부 쓰기를 취소했다는 뜻이 아니다. 되돌린 정의의 후속 호출자가 요구하는 계약을 확인하고, 불일치면 실행을 보류한다. 옛 코퍼스·정의를 삭제하는 작업은 이 설계에 없다.

## 11. 구현 단위와 정본 반영

| 단계 | 실제 산출물 | 완료 기준 |
| --- | --- | --- |
| P0 의미론 확정·재현 묶음 | 핵심 법칙의 실행 명세, v1 사용처/변환 위험 인벤토리, 제안 예제의 의미 오라클 | 값/봉투·return·each·scope·partial·취소에 모순 없는 정답. 미구현을 성공으로 보고하지 않음 |
| P1 값/Outcome 핵심과 어댑터 | 중앙 값 모형·버전 codec, 적은 수의 선언된 도구 경계, 순수 reference evaluator | 빈값·사용자 키 충돌·JSON 왕복·진단 보존. 기존 v1 사용처 불변 |
| P2 명시 호출과 공통 IR | v2 parser/lowering, 함수·식·반복·검사, 소스맵·의존 지문 | 법칙 기반 변형 시험 통과. cold/warm 검사 일치. 예제의 실제 실행 |
| P3 독립된 세 업무의 수직 적용 | 표 처리, 문서 추출/근거 보존, 파일 처리/부분 실패 | 직접/함수/중첩/반복 형태의 동등 결과. 라이브 원장·송신 없이 평가 |
| P4 첫 작성 실험 | v1/v2/Python 동일 도구 비교, 복구 이전 성적, 보류 과제 결과 | 12절의 품질/비용 채택 판단. 불충분하면 기본 언어 전환 보류 |
| P5 검증된 자산부터 이행 | 관용구·워크플로·앱·회원 기기·교재/회상의 edition 연결 | 원문·호출자·결과·출처 보존, 개별 되돌리기 확인 |

큰 변경을 동시에 켜지 않는다. 각 단계는 다음 단계의 증거를 제공하되, 사용자에게 동일 기능의 설정/언어 선택지를 무작정 늘리지 않는다. 초기 v2는 개발 평가 경로에서만 사용한다.

예상 소유 위치:

- `backend/common/`: Value/Outcome codec 및 값 의미론의 공용 부분. 패키지가 backend 상위 층을 import하지 않도록 독립 계약으로 둔다.
- `backend/ibl/`: 판본별 lowering·공통 IR·이름 연결·타입/효과·실행/반복·바인딩. 파일 1500줄 제한과 LAYERS 배정을 따른다.
- `backend/datastore/`: 정의 판본/개정·의존 정보, 기존 원장 스키마의 additive migration.
- `backend/cognition/`: execute_ibl 진입·턴 변수·교재/describe/회상·관용구 노출의 판본 전달.
- `backend/surface/` 및 frontend: 검수·실행 API·오류 위치·판본 불일치 표시. 최초 적용에 새 IDE를 만들 필요는 없다.
- `data/ibl_nodes_src/`, 각 `ibl_actions.yaml`: 도구/op 선언·어댑터 계약. 빌더가 tool.json·카탈로그·문서 마커를 파생한다.
- 원격/회원 실행·몸 번들: edition/IR/값 codec 협상과 공통 테스트 벡터. desktop만 통과했다고 전체 배포 완료로 보지 않는다.

실제 구현을 채택하는 단계에서 `ibl.md`의 언어 경계·변수·함수·파이프·코드/값, 통화 계약, 작성 가이드, compact/full 프롬프트, grammar/fixture/은퇴 계약을 함께 개정한다. 이번 문서만으로 현행 명세를 바꾸지 않는다. `self/others/table` 코어 노드 집합은 이 설계에서 늘리지 않는다. `STANDARD_CORE_NODES`의 실제 값이 유지되는지 검사하고, 노드 집합 변경이 필요하면 별도 언어 개정으로 명시한다.

## 12. 검증 — 처음부터 잘 작성하는가

### 12.1 먼저 자동으로 증명할 조합 성질

현재 IR 시험의 값/프로그램 변형을 확장한다. [Hypothesis의 상태 기반 시험](https://hypothesis.readthedocs.io/en/latest/stateful.html)처럼 값과 행동 순서를 생성해 단순 reference evaluator와 실제 엔진을 비교하고, 실패를 작은 반례로 줄인다. 새 평가기가 실제 엔진 구현을 그대로 호출해 정답으로 삼지 않는다.

필수 축: 0/1/N행, null/결측/빈 문자열, 사용자 items/error/value 키, 중첩 목록·레코드, 숫자처럼 생긴 문자열, 명시 반환 후 효과, 인자 기본값, 조건 미할당, 콜백 캡처 후 재바인딩, partial·취소·자원 고갈, 함수 추출/이름 변경, 병렬 1/N, 코드·값 전송 왕복, 하위 정의 개정과 캐시.

정상 값만 같아서는 부족하다. 외부 호출 횟수, 효과의 허용 순서, 성공/실패/완전성, 출처·진단 회수 가능성까지 비교한다. 효과 대역은 이벤트를 기록하는 별도 모델로 두고 자동 중복 실행을 검출한다.

P0 정답 벡터의 최소 예(아직 v2를 실행한 결과가 아니다):

| 입력/변형 | 요구되는 값·행동 |
| --- | --- |
| `[]`를 인자·변수·파이프·함수 반환으로 전달 | 네 경로 모두 `[]`; 외부 봉투가 되지 않음 |
| `{items:[],error:"업무 필드",value:7}` 리터럴 | 세 키를 가진 Record 그대로; 실행 실패로 해석하지 않음 |
| map 몸이 `[1,2]`를 반환, 입력 2행 | `[[1,2],[1,2]]`; flat_map은 `[1,2,1,2]` |
| map 몸이 `7` 반환, 입력 2행 | `[7,7]`; 원 행으로 대체하지 않음 |
| 파이프와 명시 인자에 같은 수신 슬롯 제공 | 실행 전 오류; 명시값이 빈 목록이어도 동일 |
| 함수의 `return []` 뒤에 쓰기 호출 | 반환은 `[]`, 쓰기 호출 0회 |
| 배수 2를 캡처한 콜백 생성 후 바깥 배수를 3으로 재바인딩 | 기존 콜백은 2를 사용 |
| 실패 행을 collect한 뒤 정상값만 선택 | 정상값 선택은 가능; 원래 실패의 처리 이력이 증거에 남음 |
| value 동일, 출처만 변경 | 일반 값 계산은 동일; evidence 조회 및 증거 의존 캐시는 변경을 인식 |
| 하위 함수 반환 계약 개정 | warm/cold 검사·실행 계획이 같은 새 결과 또는 같은 무효화 오류 |

### 12.2 모델의 첫 작성 능력 비교

비교군: **현재 v1 + 현재 교재**, **v2 + 정규 교재**, **Python + 동일 도구 계약의 얇은 호출 라이브러리**. 모델·기어·도구의 능력·입력 데이터·완료 기준·시간/토큰 예산을 맞춘다. 한쪽에만 완성 정답 관용구나 편리한 어댑터를 주지 않는다. 문법 자료의 길이 차이와 조회 비용은 숨기지 않는다.

1차는 12개 의미 과제(설계용 4, 보류 8) × 3조건 × 3반복 = **108개 첫 생성**으로 예산을 제한한다. 과제에는 직접 조합, 함수 추출, 중첩 호출, 각 항목 처리, 분기/병렬, 부분 실패를 균형 있게 배치한다. 모든 과제를 같은 보고서의 변형으로 만들지 않는다. 필요하면 결과를 본 뒤 새 계획으로 확대하며 사후 변경을 기록한다.

첫 성적은 생성 뒤 외부 피드백·수리 없이 평가한다. 별도 1회 수리 성적은 보조 지표다. 파싱 통과, 실행 통과, 요구 결과 충족, 출처/부작용 정합을 따로 기록한다. 빠른 실패를 시간 개선으로 세지 않는다.

핵심 지표는 **첫 요구 충족률과 조합 깊이에 따른 하락**, 최초 유효 프로그램까지의 전체 토큰/시간, 필요한 경계 변환 수다. 길이·어휘 호출률만으로 채택하지 않는다. 과제별 짝 비교와 불확실성 구간을 남기며 작은 표본으로 우월성을 확정하지 않는다.

채택 조건:

- 결정론적인 조합 법칙·값/진단/효과 보존에 알려진 반례가 없어야 한다.
- 보류 과제에서 첫 요구 충족률이 일관되게 개선되고, 품질·전체 비용의 큰 퇴행이 없어야 한다. 증거가 불충분하면 표기와 기본 판본 전환을 보류한다.
- Python이 동일 계약에서 지속적으로 더 잘 작성된다면 이를 IBL의 실패로 숨기지 않는다. 공통 핵심을 유지하며 기성 표기/스크립트 활용 비중을 다시 결정한다.
- 정적·고정 응답 시험을 통과한 뒤, 후속 평가 단계에서 실제 모델/외부 자료를 연결한 세 업무의 완료 품질·시간·총토큰을 확인한다. 이번 설계 작업에서는 모델 실험·운영 발행을 실행하지 않는다.

## 13. 이번 설계에서 확장하지 않는 범위

JIT·기계어 컴파일, 전면 IDE/LSP, 범용 패키지 관리자, 임의 Python 자동 변환, 무제한 재귀, 모든 효과의 자동 캐시·재시도, 전체 원장 통합은 초기 범위가 아니다. 새 기능을 보류하는 이유는 각기 별도 언어·운영 복잡성을 더하기 때문이다.

특히 전역 모나드/효과 타입 표기를 작성자에게 강요하지 않는다. 내부 Outcome과 효과 검사는 필요하지만, 정상 프로그램은 값·함수·순서·반복으로 읽혀야 한다. 새 업무별 예외를 코어에 넣는 대신 사전·명시 계약·등록 script가 담당한다.

## 14. 설계 검토 질문과 현재 검증 상태

구현자는 다음 질문에 구체적 실행 예로 답해야 한다: 빈 결과가 생겨도 변수의 뜻이 같은가? 본문을 함수로 추출해도 인자와 반환이 같은가? 함수 안 each와 each 안 함수가 같은 값/오류 정책을 따르는가? 메타정보를 추가해도 업무 값이 같은가? 부분 결과 사용의 사실을 최종 소비자가 알 수 있는가? 하위 정의가 바뀌면 검사와 재개가 같은 변경을 보는가? v1/v2를 오가며 사용자 키를 오해하지 않는가?

이번 산출물은 이 문서와 코드 지문을 포함한 격리 재현 JSON이다. **제안 문법은 파싱·실행 검증하지 않았다.** 현행 값 추출의 세 경우 및 함수 캐시의 warm/cold 차이를 재현했으며, 이것을 v2 구현 검증으로 세지 않는다. 전체 언어 구현·운영 전환·첫 생성 모델 실험은 후속 작업이다.
