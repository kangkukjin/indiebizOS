G1과 B1은 직전 수리의 공통 계약 경계를 더 닫아야 한다는 증거다. G2는 정적 검사 범위를

기존 제한이 명세대로 동작한다는 사실과 설계를 개선할 필요가 없다는 판단을 구별한다.

## 2. 조사 방법과 한계

기존 목적·언어 명세·저장/조회·컴파일러·Runtime·Journal·관측 확정의 실제 경로를 대조했다.
이전 [구조 수렴 설계](IBL_SYSTEM_CONSOLIDATION_DESIGN.md) §6.1도 읽었다. 이미 존재하는
불변 함수 판본, 읽기/모델 reuse, 결과 참조, 근거 그래프, 승인·권한 검사, 관측 확정을
없는 기능처럼 다시 제안하지 않는다.

재현 원문과 실행 절차는 [probe.py](experiments/ibl_composition_design_audit_2026_10_27/probe.py),
관측 결과는 [results.json](experiments/ibl_composition_design_audit_2026_10_27/results.json)에 있다.

```bash
.venv/bin/python3 docs/experiments/ibl_composition_design_audit_2026_10_27/probe.py
```

실제 컴파일러·Runtime·함수 등록 검증자·Journal을 사용했다. 어휘는 메모리 안의 합성
Adapter이며, 저장 원장과 Journal은 임시 디렉토리에만 썼다. 실제 외부 발송·파일 변경·
계정 조작·모델 호출은 하지 않았다. 다른 세션의 진행표시 관련 미커밋 수정이 있는 작업
트리에서 실행했으며 그 변경은 이번 문서 커밋에 포함하지 않는다.

이는 현재 행동을 기록하는 조사 스크립트다. 제안 설계의 인수 시험이나 실서비스 피해
재현이 아니다. 특히 G2는 공통 실행 경계의 허용을 증명하며 모든 실제 핸들러가 자기
잠금도 없이 동작한다고 주장하지 않는다. G4의 합성 원천 둘은 같은 값을 주지만 현재
언어가 둘의 의미적 동등성을 증명했다고 해석하지 않는다.

이번 조사는 전체 설계의 무결함 증명이 아니며, 실제 업무의 토큰·완료 시간 개선도 측정하지 않았다.
일반 능력의 목표 구조에서 개선 순서를 정하고, 구현 후 기능 보장과 비용 개선을 별도로 검증한다.

## 3. G1 — 부품의 요구 조건을 부품 자체의 계약으로 만들기

### 3.1 관측

다음 함수는 순수한 판정기를 함께 넘겨 호출하면 검사·실행이 성공하고 `2`를 반환한다.

```ibl
[def:choose]($x,$pred){
  [if:$pred($x)]{return $x}[else]{return null}
}
return [fn:choose]{x:2,pred:($v)=>$v>0}
```

그러나 **같은 정의만 독립 검사하면 `PURE_EXPRESSION`이며 실제 저장 관문도 거절한다.**
`$pred`가 Unknown이므로 순수 여부를 알 수 없는데, “이 인자는 순수 판정기여야 한다”는
요구 조건으로 보존할 길이 없다. 이는 순수 검사를 없애야 한다는 증거가 아니다.

`[def:absolute]($x){return abs($x)}`의 공개 입력 계약도 `x: Unknown`이다. 본문에는
Number 실행 검사가 남지만, 함수 입구의 요구 조건으로 승격되지 않는다. 호출이 주어진
특수화에서는 정밀해지나 호출자가 없는 계약 조회·저장·발견에서는 본문 재분석과 개별
guard 해석에 의존한다. 모든 고차 함수가 저장 불가한 것은 아니다. 예를 들어 `map`은
자기 순수 콜백 경계를 갖고 있으며, 일반 고차 적용도 unknown으로 저장될 수 있다.
문제는 함수의 같은 요구를 표현 위치마다 일관된 인터페이스로 갖지 못하는 데 있다.

근거 소유자:

- `backend/common/expression_parser.py`: def 매개변수는 이름·기본값이며 별도 조건 표현이 없다.
- `backend/ibl/ibl_v2_compile.py`: `_function`은 실제 인자 또는 Unknown으로 분석하고,
  `param_contracts`는 관측된 입력 타입을 기록한다. 미사용 정의도 Unknown으로 검사한다.
- `backend/ibl/ibl_v2_call_analysis.py`: `check_purity`는 미확정 효과를 즉시 오류로 만든다.
- `backend/ibl/function_library.py`: 저장 검증자가 같은 독립 컴파일 결과를 사용한다.
- `backend/ibl/ibl_v2_store.py`: describe도 독립 컴파일을 사용한다.

### 3.2 목표 구조

부품 계약에 **요구 조건과 그 입력에 따른 결과·효과 관계**를 갖춘다. `Unknown` 하나로
“아무 값이나 가능”, “아직 모름”, “호출자가 만족시켜야 함”을 대신하지 않는다.
다음은 설계 표기이며 실행 가능한 새 문법이 아니다.

```text
choose<A>(x:A, pred:Callable(positional=[A], result=Bool, effects=pure)) -> A|Null
absolute(x:Number) -> Number
compose(f:A->B !E1, g:B->C !E2) -> (A->C !(E1 ∪ E2))
```

구현은 기존 Type·Callable 계약·CallAnalysis에 다음을 연결한다.

1. 매개변수의 값/형태/인자 방식/효과 요구를 작은 제약으로 추론한다. 추론되지 않는 의도는
   선택적인 명시 계약으로 표현한다. 정적 의미는 같은 계약 데이터가 소유하고, 표기만 다른
   두 타입 시스템을 만들지 않는다. 모든 함수에 장황한 타입 선언을 의무화하지 않는다.
2. 독립 정의는 “이 조건하에서 유효”로 검사·저장할 수 있다. 실제 호출에서는 제약을 대입해
   확정 불일치를 거절한다. body를 분석하지 않고 저장만 허용하는 느슨한 우회가 아니다.
3. 생성 효과와 적용 효과를 계속 분리한다. 순수 콜백 요구·결과 관계·읽기/쓰기 효과가
   람다·명명 함수·어휘·반환 함수·컨테이너·Result를 지나도 남는다.
4. 알려진 모순, 미확정 의무, 실행 시 검사 가능한 조건, 실행해도 증명 불가한 조건을 구분한다.
   후보/특수화 한도를 넘으면 의무를 남긴다. 분석 중단을 순수/무자원으로 간주하지 않는다.
5. describe·저장·호환 개정·회상은 같은 요구 조건을 소비한다. 기존 검색의 이름·설명 후보
   선별은 유지하되 선택된 부품의 적용 가능성을 계약으로 설명한다. 새 저장소·상시 AI
   검수·영속 분석 캐시를 이 기능의 선행 조건으로 만들지 않는다.

전체 종속 타입 언어나 임의 프로그램의 순수성 증명이 목표가 아니다. 닫힌 구조·타입 변수·
콜백 인자/반환 관계·유한 효과 집합·명시된 자원 관계부터 지원하고 한계를 계약에 밝힌다.
입력 역추론이 불확실하면 넓은 조건/실행 검사로 남기며, 한 호출의 관측을 보편 조건으로 굳히지 않는다.
분기별 요구를 무조건 모든 호출에 적용하지 않으며 경로 조건·미실행 본문의 효과도 구분한다.

### 3.3 B1 — 결과가 도착할 경계도 요구 조건이다

```ibl
[audit:send]{}
return {callback:abs}
```

합성 write 어휘로 실행한 결과, 검사 오류는 없었고 **쓰기 1회 후 `VALUE_PROTOCOL`로 실패**했다.
반환 계약은 컴파일 때 이미 `Record{callback:Callable}`이었다. Callable 외부 직렬화가
지원되지 않는다는 경계 자체는 옳지만, 확정적인 경계 불일치가 너무 늦게 발견된다.

`compile_program`의 내부 함수 분석과 최상위 HTTP/MCP/앱 반환을 구분해 소비자 요구를 받는다.
내부 반환 Callable은 유효하며, 지원 wire로 전송해야 하는 최상위 값은 재귀적 전송 가능성
의무를 검사한다. 전송 불가가 확정된 값은 위치·경로·소비자 프로토콜을 담아 **어떠한 잎 효과보다 먼저
거절**한다. 런타임에서만 드러나는 값은 의무를 안내하고 실제 전송 검사도 유지한다.
부작용 이후에야 정해지는 모든 값을 미리 보장한다고 약속하지 않는다.

Callable을 JSON으로 위장하거나 캡처·권한을 직렬화하는 기능은 추가하지 않는다.
함수 저장/describe 같은 분석 소비자는 외부 결과 전송 정책을 잘못 물려받지 않아야 한다.

## 4. G2 — 읽기·쓰기 자원 관계를 합성하고 미확정을 실행 경계까지 운반하기

### 4.1 관측

합성 어휘에 정상적인 `write_resources: {record: key}`를 선언했다.

- 리터럴 `key:"same"`을 쓰는 두 병렬 호출은 `PARALLEL_WRITE_CONFLICT`로 거절된다.
- 같은 자원의 읽기와 쓰기를 병렬로 묶으면 검사 오류가 없다.
- `$keys`를 다른 어휘에서 받아 두 함수에 넘기면 실제 키가 모두 `"same"`이어도 검사 오류가 없다.
  메모리 안의 쓰기 두 호출이 동시에 진입했고 최대 동시 쓰기 수는 **2**였다.

```ibl
$keys=[audit:keys]{}
[def:save]($key){return [audit:write]{key:$key}}
return [fn:save]{key:$keys[0]} & [fn:save]{key:$keys[1]}
```

`ibl_v2_compile.py`는 `write_log`만 병렬 비교한다. 정적 자원 값이 미확정이면
`resource_values`가 None을 반환하고 그 접근은 로그에 남지 않는다. Runtime의 자원
대조는 주로 영수증 reuse 무효화에 쓰이며, 이 미확정을 병렬 실행 전 검사할 의무로
받지 않는다. 개별 핸들러의 잠금이나 외부 서버의 원자성은 이 공통 경계를 대신하지 않는다.

### 4.2 목표 구조

기존 `read_resources`·`write_resources`·자원 해소기를 **한 접근 요약**으로 수렴한다.
새 업무별 자원 이름을 엔진에 하드코딩하지 않는다.

- 함수의 접근은 `reads(record, $key)`, `writes(record, $key)`처럼 인자에 대한 관계를
  남긴다. 미지 자원은 `없음`과 다른 상태다. 호출·분기·루프·요약 재사용에서 같은 관계를 대입한다.
- R/R은 허용한다. W/W와 R/W는 순서·독립성·명시된 동시 접근 계약이 필요하다.
  같은 경로/부모 경로/별칭/실제 inode를 해소하는 기존 소유자를 사용한다.
- 컴파일 때 확정된 충돌은 지금처럼 먼저 거절한다. 실행에서 정해지는 키는 외부 효과
  직전에 같은 판정기로 해소한다. 승인·권한 검사와 자원 검사 양쪽을 통과해야 잎에 도착한다.
- 실행 중 겹칠 수 있는 가지의 예약과 수명을 관리한다. 개별 호출에 짧은 mutex만 붙여
  `읽기→계산→쓰기` 전체가 안전해졌다고 주장하지 않는다. 가지/명시 구간의 접근을 확보할
  수 있을 때만 동시 실행하고, 확보 불가한 계획은 순서 명시를 요구하거나 안전하게 거절한다.
- 충돌을 임의 실행 순서로 숨기지 않는다. 순차화 정책을 지원하면 호출자가 그 의미를 선택하고
  계획에 표시한다. 독립 자원의 병렬성은 보존한다. 잠금 순서·교착·취소·승인 대기 해제도 계약에 둔다.
- `stateful` 외부 세션과 기존 네이티브 잠금은 수명 소유자에 남긴다. 원격 자원은 로컬 예약만으로
  다른 프로세스의 변경을 막았다고 하지 않는다. 필요한 조건부 쓰기/버전 검사 가능성은 어댑터가 선언한다.

컴파일 `write_log`, preflight, Runtime의 충돌 의무, Journal의 무효화가 동일 접근 요약을
소비해야 한다. 목적은 새 분산 트랜잭션 관리자가 아니라 선언된 관계가 조합 중 사라지지 않는 것이다.

## 5. G3 — 코드를 고친 뒤 완료된 효과를 계승하는 제한적 수정 재개

### 5.1 관측

```ibl
$sent=[audit:send]{id:"delivery"}
return 10 / $divisor
```

`divisor:0`으로 실행하면 쓰기 1회 뒤 계산이 실패한다. 같은 코드의 resume은 계산 실패를
반복하지만 쓰기는 다시 실행하지 않는다. 마지막 식만 `10 / ($divisor + 1)`로 고치면:

- 같은 resume은 `RESUME_CHANGED`로 거절한다.
- 수정 코드의 reuse는 성공하지만 쓰기도 다시 실행하여 누적 쓰기가 **2회**가 된다.

이는 현재 명세대로다. 기존 시험 `test_ibl_v2_incremental_2026_09_26.py`도 수정 실행에서
쓰기 재실행을 요구한다. 그러나 이미 발송·공개·장치 조작을 한 큰 프로그램의 뒤쪽만
고칠 때 사용자가 앞부분 제거와 결과 이식을 직접 설계해야 하는 한계가 남는다.

원인은 버그성 중복 실행만이 아니다. 동일 원문/입력/의존/권한 지문의 resume과 읽기/모델
영수증 reuse 사이에 **검사한 수정 계획으로 동일 업무의 이미 완료된 효과를 계승하는 계약**이 없다.
현재 호출 ID는 원문 위치·반복 경로에 묶여 편집을 넘는 업무 신원도 제공하지 않는다.

### 5.2 목표 구조와 금지할 지름길

기존 Journal·불변 함수 판본·의존 지문 위에 명시적 수정 재개 계획을 추가한다. 기존
`resume`/`reuse`의 뜻은 그대로 둔다. “인자가 같으니 쓰기도 캐시 hit”는 금지한다.

1. 원 실행·현재 주체·수정 코드에 묶인 계획을 먼저 계산한다. 이전 호출을 `완료 효과 계승`,
   `새 계산`, `명시 재실행 필요`, `효과 불명/판정 불가`로 분류하고 근거와 영향을 표시한다.
2. 효과에 안정된 **논리 작업 신원 + 실행 계보 + 반복 항목 신원**을 부여한다. 원문 offset이나
   액션·인자 해시만으로 신원을 추측하지 않는다. 서로 다른 의도적 동일 발송은 별개다.
   자동 대응은 명확한 경우에만 하고, 모호한 대응은 명시 선택/중단으로 남긴다.
3. 기존 영수증·대상·정규화 인자·캡처·계약·구현·권한·근거 의존·완료 상태가 부합할 때만
   완료 사실을 계승한다. 과거에 쓴 사실과 현재 외부 상태가 여전히 같은지는 별도다.
   현재 상태가 필요하면 검증 읽기/어댑터의 버전 계약을 요구한다.
4. 계승된 효과는 다시 실행하지 않는다. 새 효과에는 현재 권한·승인·예산을 적용한다.
   옛 승인 토큰을 새 요청에 재사용하지 않는다. 원 실행 접근이 철회되면 영수증 계승도 거절한다.
5. 효과 불명은 자동 재시도/완료 추정 금지. 어댑터의 결과 조회·멱등 키·조건부 실행이 있는
   경우에만 그 명시 계약으로 해소한다. 없는 도구는 수동 확인/새 업무 시작 경계로 남긴다.
6. 수정 재개 계획 자체도 지문·CAS·배타 실행으로 고정한다. 동시 재개·응답 유실·worker 손실
   후에도 새 효과가 두 번 시작되지 않게 기존 Journal의 확정/미확정 규칙을 연결한다.
7. 계승 결과·근거·coverage를 G4의 완료 의무로 잇는다. 사용자에게는 어느 단계가 이미
   끝났고 어디부터 새로 실행되는지 보인다. 새 워크플로 원장·별도 권한 저장소를 만들지 않는다.

임의 코드 편집의 자동 동일성 판정, 외부 효과의 자동 롤백, 보편적 exactly-once는 목표가 아니다.
명확한 후미의 순수 계산 수정부터 시작하고, 가지 추가·반복 재정렬·부품 교체는 인수 조건을
만족하는 범위만 넓힌다. 지원 불가한 변경이 조용히 새 실행으로 바뀌어서는 안 된다.

## 6. G4 — 실패 이력과 결과의 완료 의무를 분리하여 합성하기

### 6.1 관측

```ibl
$r=([audit:primary]{} ?? [audit:mirror]{})
return $r
```

첫 원천은 실패하고 대체 원천은 완전한 `[1,2]`를 반환한다. 실행은 성공하지만
`source_complete:false`이며 대체 원천이 예약한 로컬 관측 확정은 `not_committed`다.
대체 원천만 직접 호출하면 같은 값으로 `source_complete:true`, `committed`다.

Runtime은 전체 trace에 incomplete 사건이 하나라도 있으면 최상위 source_complete를
false로 만든다. 실패를 catch해도 흔적을 지우지 않는 것은 올바르다. 문제는 **실패한 시도가
있었다는 사실과 지금 선택한 산출물이 요구 근거를 충족했다는 판단을 별도로 표현할 수
없다는 점**이다. 값의 `complete:true` 같은 자기 신고를 믿어 해결해서는 안 된다.

현재 근거 그래프와 Result·partial·recovered 사건은 이미 있다. 기존 구조 수렴 문서도
필드 선택에 전체 실행의 불완전성을 보수적으로 계승한다고 명시한다. 따라서 새 증거
엔진을 만들기보다 이 증거에 결과/요구 범위의 연결을 추가할 문제다.

### 6.2 목표 구조

- 실패·시도·외부 효과·취소의 기록은 불변으로 유지한다. 기존 `source_complete`를 아무
  조건 없이 true로 덮지 않는다. 새 완료 계약이 없는 호출은 현재 보수적 정책을 유지한다.
- 부품의 **필수 근거/산출물 의무**, 각 의무의 증거, 선택된 결과와 그 의존성을 명시한다.
  상태는 충족/미충족/미판정이며, 선택 분기·대체·부분 집합·반복의 합성 규칙을 둔다.
- 대체 원천 성공만으로 동등성을 추정하지 않는다. 원천 범위·대상 판본·누락 기준 등
  해당 의무의 판정기를 만족할 때만 같은 의무를 충족한다. 결정론 검사를 우선하며 의미
  평가가 필요한 경우 기존 선택적 평가 경로를 쓰고 상시 AI 검수를 추가하지 않는다.
- 업무 값에 섞인 성공 플래그는 증거가 아니다. 판정 결과는 실행 봉투에 조건 지문·값 지문·
  근거 참조와 함께 보존한다. 외부 입력이 만든 임의 JSON으로 의무를 지울 수 없어야 한다.
- 선택된 값만의 근거와 실행 전체의 감사 이력을 각각 조회할 수 있게 한다. 결과의 필드 선택을
  이유로 그 값을 결정한 제어 의존·검증 실패·실제 일어난 쓰기를 삭제하지 않는다.
- `CommitScope`는 각 예약 확정이 의존하는 의무를 알고 해당 범위가 충족됐을 때만 확정한다.
  전체 실패 비트를 무조건 무시하는 변경이 아니다. 독립 관측의 확정과 사용자 업무의
  완료·공개 확정은 기존 소유자를 유지한다. 원격 효과까지 원자적으로 롤백하지 않는다.
- describe/check·Result·read_result/입력 참조·저장 함수·최종 모델 응답·앱이 같은 완료
  범위를 보존한다. 단순 함수 포장이나 값 전달 때문에 미판정이 충족으로 바뀌면 실패다.

## 8. 구현 순서와 단계별 완료 조건

**우선순위는 G1/B1과 G2가 먼저다.** 전자는 부품의 공통 요구를 드러내고 후자는 효과의
잘못된 동시 조합을 막는다. 이어 G4의 결과/의무 신원을 만든 뒤 G3의 수정 계승을 연결한다.

1. **현행/목표 경계 고정.** 이번 조사 원문을 책임 모듈 시험의 입력으로 옮긴다. 각 실패를
   구현 결함·새 계약·의도된 제한으로 표시한다. 기존 코드/명시 저장 판본의 의미가 바뀌는
   곳은 판본·기능 협상 또는 명시 opt-in을 정한다. 계속 실패하는 시험만 main에 남기지 않는다.
2. **G1/B1 계약 데이터와 적용.** 추론 제약·명시 요구·특수화·경계 의무를 Type/CallAnalysis에
   연결한다. `choose`가 지역/저장 양쪽에서 유효해지고 비순수 pred는 거절돼야 한다.
   공개 반환의 확정 전송 오류는 잎 효과 전에 거절해야 한다. 저장/describe/회상/개정 검증이
   같은 계약을 소비한 뒤 표기를 공개한다. 관측 계약과 선언 요구를 이행 시 구분한다.
3. **G2 접근 요약과 실행 의무.** R/R·R/W·W/W·미지 자원을 같은 모델로 합성한다.
   먼저 명시 자원 어댑터를 연결하고 미선언은 unknown으로 둔다. 동적 같은 자원의 동시
   효과는 통과하지 않아야 하며, 다른 자원은 기존 병렬성을 유지해야 한다. 조용한 전역
   직렬화나 스레드 수 감소로 시험을 통과시키면 완료가 아니다.
4. **G4 완료 범위 연결.** 실패 이력을 보존하면서 판정한 대체 충족을 별도 표현한다.
   분리된 의무·지문이 없는 과거 기록은 보수적으로 읽는다. 관측 확정·Result·결과 참조·
   UI/모델 표면의 소비를 함께 갱신한다. `source_complete`만 치환해서는 완료가 아니다.
5. **G3 제한적 수정 계승.** 같은 업무의 명시 수정 계획을 기존 Journal에 연결한다.
   순수 후미 수리→명확한 독립 부품 교체→반복/병렬 순서로 지원을 넓힌다. 불명 효과·
   권한 변화·중복 논리 ID·의미 변경은 판정 불가/거절로 남겨야 한다.
6. **합성 인수·이행·정본 반영.** 아래 변환 행렬과 전체 소비자 회귀를 통과하고, 대체된
   분기·교재를 제거한다. 각 단계의 실제 완료 범위를 이 문서와 changelog에 적는다.
   전수 초록만으로 새 계약의 인수가 끝났다고 하지 않는다.

의존 관계: 1→2→3, 2→4, 2·3·4→5→6. G3는 안전 조건이 갖춰진 범위만 활성화한다.
모든 단계에서 참조 생성은 권한 획득이 아니며 실제 잎·영수증 접근의 권한을 재검사한다.

| 완료 | 완전 대체/부분 대체/잘못된 대체, 선택·폐기 값, 제어 의존, 필수/선택 의무, 실패 이력 보존, JSON 위조 거부, 범위별 확정 |
| 수정 계승 | 순수 후미 수정·호출 앞 공백/순서 변화·부품 판본/캡처/대상 변경·행 재정렬·중복 항목·별개 의도적 동일 발송 |
| 안전 경계 | 같은 주체/권한 변경/소유 범위 변경/승인 만료, 동일 재개 중복 요청·동시 수정 계획·영수증 유실·효과 불명 |
| 소비자 | check/describe/저장/회상/HTTP/MCP/앱·조종실/PC·Android의 지원/거절 경계, 이전 기록의 보수적 해석 |
| 규모 | 공유 DAG 깊이 6/10/14/30, 다른 캡처·제약 대입, 분석 한도·결과/진단 크기, 요약 사용/미사용 동등성 |

이름·도메인이 아닌 변환 성질을 검사한다. 정상 변환에서는 값·잎 호출 순서/횟수·요구 계약·
효과·근거·판정 상태가 보존돼야 한다. 명시적으로 실행 정책이나 완료 조건이 바뀐 변환은
동등하다고 우기지 않고 차이를 확인한다.

두 종류 이상의 새 과제로 전체 고리를 검증한다. 예를 들어 자료 취득→검사→발행과
상태 관측→판정→조작→확인이다. 수집기·판정기·저장기를 바꾸고 전체 프로그램을 다시
부품으로 전달한다. 중간 실패와 뒤쪽 수정도 넣는다. 업무 이름은 fixture이며 엔진 분기의
근거가 아니다. 이미 저장된 정답 관용구가 있어야만 통과하는 평가로 만들지 않는다.

회귀는 [REGRESSION_TESTING.md](REGRESSION_TESTING.md)에 따른다. 개발 중에는 선택기와
책임 모듈 시험을 쓰고, 공통 언어/실행 변경 완료 시 비system 전수와 관련 system 묶음을
실행한다. 어휘/문법 변경 시 선언·교재·어댑터 오류문·소비자·파생 빌드·Android 번들·층·크기
검사를 함께 수행하고, frontend가 바뀌면 실제 tsc를 실행한다. 시험 집계와 종료 코드를 구분한다.

## 10. 설계 작성 당시의 결과와 미실행

아래는 구현 전 조사 기록이다. 구현 후 현황은 §11을 따른다.

현재 구현에서 G1~G4/B1 다섯 조사 묶음을 두 번 실행해 같은 JSON 결과를 얻었다(두 명령 모두
종료 0). 관측값 13개를 단언으로 대조했고, 계획서·재현 자료의 구조/링크·범위·공백을 검사했다.
이는 현행 동작의 재현 확인이며 제안 설계의 합격 시험이 아니다. 이번 변경은 설계 문서와 조사 자료뿐이다.

새 언어 계약·자원 실행 조정·완료 의무·수정 계승은 **아직 구현하지 않았다**. backend 전수나
새 설계의 인수 시험을 실행했다고 주장하지 않는다. 실제 서비스의 의미적 대체 판정·외부
상태 원자성·토큰/완료 시간 개선은 미검증이다. 이 한계들은 구조 개선 착수의 선행 대기 조건이 아니다.

무제한 재귀·외부 Callable 직렬화·실행 스택 이식·범용 분산 트랜잭션·새 기능어 대량 추가는
이번 계획에 넣지 않는다. 제약을 모두 없애는 것이 아니라, 조합에 필요한 조건과 의무가
각 부품의 경계에서 드러나고 더 큰 프로그램에도 그대로 전달되는 것을 완료 기준으로 삼는다.

## 11. 구현 범위와 검증 기록

2026-10-27 정본 main 작업. G1/B1의 조건부 요구·명시 매개변수 계약·소비자 wire 경계,
G2의 공통 접근 요약/병렬 구간 입장 검사, G4의 명시 완료 봉투/선택 근거/범위별 관측 확정,
G3의 기존 Journal 기반 순수 후미 수정 계승을 연결했다. HTTP·MCP·저장/describe·결과 참조도
같은 데이터를 전달한다. 지원 요청과 제한은 `data/system_docs/ibl.md`의
「부품 요구·병렬 자원·완료·수정 계승」이 현행 계약이다.

G1의 추론은 입력 변수·콜백 적용 인자/반환·순수 요구와 조건부 요구를 기록한다. 명시 계약은
기존 Type/CallAnalysis로 검사한다. 범용 종속 타입 추론·임의 의미적 동등성 판정은 하지 않는다.
G2의 미선언 사전은 명시 composition opt-in으로 엄격 검사하며, 선언 자원의 충돌 수리는
기본 적용한다. 자원을 가지 시작 전에 확보할 수 없으면 순서 명시를 요구한다.
G4는 명시 원천/대상·순수 결정론 판정으로 최종 값의 의무를 인증하며, 임의 부분 선택·변환에
같은 인증을 자동 이식하지 않는다. 원천 미완전성과 감사 실패를 지우지 않는다.
G3는 순수 후미 수리와 그 앞의 불변 부품/반복 경로만 지원한다. 새 효과·가지 삽입,
반복 재정렬·모호한 대응은 거절한다. 다른 프로세스의 상태나 외부 exactly-once를 보장하지 않는다.

책임 모듈 인수 시험은 `backend/test_ibl_v2_{requirements,access,completion,repair}.py`.
등록/회수·명시 콜백 계약·전송 경계, 동적 충돌·독립 병렬·R/W·each·hardlink,
완전/부분 대체·버린 값·JSON 위조·관측 확정, 지문/CAS·응답 유실·공백·함수/반복 신원,
