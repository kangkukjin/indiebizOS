# IBL 조합 능력 개선 방향 — 새 문제를 실행 가능한 프로그램으로 만들기

2026-09-23 조사 시점의 진단·제안이다. 이후 교재·가이드 연결과 검증 API 정합을
[1차 개선](IBL_COMPOSITION_TEACHING_2026_09_23.md)으로 반영했다. 아래 수치는 개선 전 스냅샷이다.

## 목표와 판단

목표는 새로운 사용자 요구를 AI가 긴 IBL 프로그램으로 구성하고, 필요한 내용 판단만
프로그램 내부의 AI 단계에 남겨 같은 품질에서 왕복·시간·총토큰을 줄이는 것이다.
저장된 보고서 함수를 호출하는 능력은 그 일부다. 배운 부품을 새로운 순서·조건·자료에
연결하는 능력과, 기존 예제가 없는 프로그램을 만드는 능력을 별도로 측정해야 한다.

현재 병목은 모델 하나로 설명되지 않는다. 압축 교재의 조합 예제 부족, 관용구의 구조적
범위 편중, 데이터·진단 봉투의 복잡한 연결, 실행 규모·재개 경계의 늦은 검증이 함께 있다.
새 낱말을 늘리기 전에 기존 문법의 발견 가능성과 일관된 입출력을 개선하는 것이 우선이다.

에피소드 4005의 후보 선정 입력은 신규 후보 18개와 기존 팁 647개를 합쳐 153,360자였다.
기존 팁 부분만 149,577자이며 등록 스크립트의 상한은 57,000자다. 편집·최종 검수도
기존 팁 전체를 다시 넣는다. 이는 입력을 어떤 규모로 구성했는지의 문제이며 IBL에
분할 표현이 없어서 생긴 실패가 아니다. 검색 한 층의 0건이 전체 실패로 전파되는 것도
복구 경로를 구성하지 않은 문제다. 최초 시범 실행은 기존 팁 0개로 수행되었다.

별도 설계 마찰도 있다. 보고서 IBL은 스크립트 호출마다 items·success·partial·오류·잘림 등
많은 필드를 반복 복사한다. AI가 업무와 함께 봉투 운반 규칙까지 재작성하는 형태다.
이것이 모든 호출에서 필수인지 공용 통화 전달 경계를 재현 시험으로 확인해야 한다.
진단을 지우거나 items만 전달하는 축약은 해결책이 아니다.

## 1. 교재: 문법 목록과 완성 프로그램을 연결한다

기본 압축 교재를 상세 전문으로 통째 교체하지 않는다. 짧은 조합 핵심과 정확한 파일
포인터를 두고, 상세 문법과 실행 가능한 작성 예제를 필요할 때 한 번 읽게 한다.

- 핵심에 변수 전달, 함수 정의·호출, each의 행 반환, 빈 결과 분기, 실패 복구, 분할 처리의
  최소 예를 둔다. 장문의 변경 이력과 과거 사고 설명은 설계 문서로 분리한다.
- 표기는 우선 한 가지를 가르친다. 행 생성은 `$return=[{...}]`, 원문 보존은 파일/참조,
  독립 실행은 `A & B`, 후속 전달은 파이프/변수로 통일된 입문 예를 만든다.
- 동일 과제를 단발 호출 → 변수·파이프 → 반복·분기 → 함수·관용구 재조합으로 확장한다.
  각 단계에서 모델 왕복이 어디서 없어지는지, 내용 판단은 어디에 남는지 설명한다.
- 완성 예제에는 정상 입력만 두지 않는다. 빈 결과·한 항목 실패·상한 초과·재개 입력을
  붙여 무엇이 달라지는지 보여 준다. 입력·기대 결과는 실행 가능한 fixture가 소유한다.
- 압축 교재의 “오류는 행의 _error가 아닌 봉투에 있다”는 설명은 기본 동작과
  `each on_error:"keep"`의 예외를 구분해야 한다. keep은 실패 행의 _error를 보존한다.
  실제 의미는 backend/ibl/ibl_exec_each.py가 소유한다.

제안: 가이드 목차에 긴 프로그램 작성의 정확한 입구를 하나 연결하고, compact/full/
카탈로그/오류 도움말에서 같은 예제를 재사용한다. “좋은 가이드가 존재함”과 “이번 실행에
그 가이드가 공급됨”을 별도 관측한다.

## 2. 관용구: 호출 절약과 새로운 조합 학습을 분리한다

관용구는 두 역할이 있다. 검증된 절차를 짧게 호출하는 실행 부품, 그리고 그 절차를
새 문제로 변형하도록 보여 주는 교재다. 이름만 제공하면 첫 역할의 이득은 얻어도
새로운 조합으로 전이되는 능력까지 입증할 수 없다.

제안하는 노출 구성:

1. 상시: 여러 업무에서 쓰이는 소수의 검증된 부품을 현재의 호출 카드 형식으로 제공.
2. 과제별: 기존 회상에서 관련 부품·작업 구조 예제 1~3개를 예산 내 선택. 별도 계획 AI를
   매번 추가하기보다 기존 검색·계획의 정보와 메타데이터를 먼저 활용.
3. 작성·변형 시: 선택한 것만 본문을 열어 지역 def로 조합. 모든 본문을 매 턴 싣지 않음.

선정 기준은 호출 빈도에 더해 구조적 활용 범위·전제·실제 품질·총비용을 본다.
현재 읽기 중심 항목에 더하여 다음 구조를 후보로 검증한다. 새 이름·액션의 도입을
미리 확정하지 않으며, 기존 비상시 관용구와 일반 문법 예제를 먼저 조사한다.

| 구조 | 조합을 배울 자리 | 반드시 포함할 조건 |
| --- | --- | --- |
| 여러 출처 수집·통합 | 병렬과 출처 보존 | 일부 출처 실패를 누락과 구분 |
| 미처리 항목만 실행 | 조회→대조→행동 | 처리 이력·중복 부작용 |
| 실패 항목만 재시도 | 반복과 분기 | 빈 결과/장애 구분·유한 재시도 |
| 큰 자료 분할·판정·통합 | 규모에 따른 분해 | 전량 처리 여부·ID 보존·전역 비교 |
| 결과 검증 후 저장 | 판단과 효과의 연결 | 동일 검수 대상·중복 쓰기 방지 |
| 성공 결과에서 재개 | 부분 실행의 재사용 | 입력 변경 시 무효화할 범위 |

각 카드는 언제/입출력/실패·빈값/부작용/내부 AI 비용/생산자와 소비자를 붙인 예를 갖는다.
각각을 전역 프롬프트에 다 풀어 쓰기보다 짧은 상시 서명과 상세 교재를 나눈다.
AI를 포함한 관용구는 내부 호출 수·입력 규모를 숨기지 않는다. 분할하면 품질과 처리
가능성이 나아져도 AI 호출은 늘 수 있으므로 전체 비용으로 비교한다.

## 3. 언어·실행 구조: 연결할 때 외워야 할 예외를 줄인다

IBL에는 이미 def/fn, if/case, repeat, try/catch, each, chunk, 턴 변수와 재개 기능이 있다.
이를 없는 기능처럼 새로 추가하지 않는다. 조합 경계의 일관성을 우선 점검한다.

- each의 객체/행 목록/스칼라 반환, 함수 반환, script 결과, 일반 파이프가 같은 데이터를
  어디에 두는지 대조한다. 기본 작성 경로를 명확히 하고 호환 경로는 별도로 설명한다.
- 관용구·스크립트를 넘어갈 때 원자료와 실패·잘림 진단이 공용 규약으로 전달되도록 한다.
  작성자가 매번 수십 개 메타 필드를 복사하지 않아도 되는지 검증한다.
- 빈 items와 장애를 구분하고, 부분 실패가 있어도 성공분과 실패분을 명시적으로 다룰 수
  있게 한다. 품질 미달을 성공으로 바꾸거나 자동으로 무시하는 기본값은 도입하지 않는다.
- 반환 열이 입력 열을 보존하는 함수는 그 관계를 검사기가 알 수 있도록 한다.
  고정되지 않은 열을 허위로 확정하는 대신 입력 의존 관계와 unknown을 구분한다.
- 효과가 있는 단계는 자동 재시도 가능 여부를 명시한다. 임의 스크립트까지 포함해
  실행기가 보편적인 exactly-once를 보장한다고 가정하지 않는다.

언어 변경은 구현 부족과 표현 불가능을 재현한 뒤 선택한다. 내용어 이름이나 특정
보고서의 규칙을 파서·엔진에 넣지 않고, 문법/기능어 코어와 개인 사전의 경계를 지킨다.

## 4. 검사·재개: 수리를 작은 범위로 끝내게 한다

현재 check:true는 문법·형태 검사에 유용하지만 실행 중 생성될 데이터의 크기와 실제
품질을 보장하지 않는다. 통과를 긴 프로그램 전체의 성공 증거로 가르치면 안 된다.

- 알려진 파일·고정 입력에 대해 read-only 사전 점검으로 요청 크기·행 수를 계산한다.
  실제 런타임에서만 아는 크기는 AI 호출 직전 확인한다. 정적 확정/경고/미상을 구분한다.
- 처리 상한과 전달해야 할 데이터가 충돌하면 필요한 분할 단위·미처리 범위를 구조적으로
  반환한다. 상한을 풀거나 조용히 take로 자르지 않는다.
- AI 결과 검증·보존과 다음 단계 요청 구성을 분리한다. 후자의 실패가 전자의 성공을
  지워 같은 추출을 다시 지불하게 하지 않는다. 입력·코드·검수 기준 변경 시의 재사용
  유효성도 함께 정의한다.
- 뿌리 실패와 그로 인해 실행되지 못한 후속 단계를 나누고, 원인·저장 결과·재개 위치를
  작게 반환한다. 모델이 프로그램 전체를 다시 쓰지 않아도 되게 한다.

## 5. 개선의 효과를 분리해서 측정한다

저장소의 [관용구 가치 실험](IBL_IDIOM_VALUE_2026_09_08.md)은 마지막 비교에서
지도 제공 조건의 첫 성공 16/16, 미제공 9/16, 생성 출력 1,326 대 5,757토큰을 기록했다.
한 모델·8과제·2회 반복이며 선정 부품에 맞는 과제와 변형이 포함되어 있다.
이것은 국소 재사용 효과의 근거이지 새로운 업무 전반의 조합 능력이나 총비용의 증명이 아니다.
이번 조사에서 해당 모델 실험을 새로 실행한 것은 아니다.

시험은 다음 세 종류를 따로 둔다.

- 부품 사용: 적합한 관용구를 골라 호출하며 부적합하면 사용하지 않는가.
- 새 조합: 알려진 부품을 처음 보는 순서·조건·도메인에서 연결하는가.
- 새 구성: 정확히 대응하는 관용구가 없어도 기존 문법으로 프로그램을 만드는가.

먼저 여섯 구조의 정상/빈값/부분 실패/규모 초과·재개 fixture를 만든다. 외부 응답을 고정해
실행기·교재 오류를 분리하고, 별도의 실제 AI 내용 판단 시험으로 품질을 평가한다.
초기 표본의 과제·답안을 교재와 함께 만들어 놓고 같은 과제로 일반화를 주장하지 않는다.
평가용 미노출 조합·도메인·규모를 따로 남긴다.

모델·도구·자료·품질 기준·수리 기회를 고정한 채 기존 교재 / 개선 교재 /
개선 교재+관용구 카드 / 개선 교재+카드+선택 본문 예제를 비교한다.
관용구 사용 횟수 자체를 합격 조건으로 삼지 않는다. 이후 동일 조건에서 모델을 바꿔야
환경을 고친 효과와 모델 차이를 구분할 수 있다.

지표는 전체 과제 품질, 최초 완주, 수리 횟수, 바깥 모델 개입, 내부 AI 호출, 전체 입력·
캐시·출력 토큰, 벽시계, 중복 실행·누락이다. 작성·정적 검사·수리 비용도 포함한다.
현재 scripts/ibl_composition_cost_metrics.py의 first_program_success는 첫 호출의
action_count>=2와 실행 success로 계산된다. describe/check나 단일 fn 호출이 섞이는
경우 완주·품질과 다르므로 이번 평가의 대표 지표로 그대로 쓰지 않는다.

## 우선순위

1. 압축 교재의 정확한 문법 입구·핵심 조합 예·실패 설명 정합을 보강한다. 같은 fixture로
   교재의 문장을 실행해 검사한다. 총 프롬프트 크기도 함께 제한한다.
2. 현재 7개 노출을 무작정 늘리지 않고 부족한 작업 구조 예제와 선택 본문을 공급해
   새 조합 시험을 수행한다. 빈도 외의 활용 범위·적합성도 노출 평가에 포함한다.
3. 드러난 언어/실행 경계 마찰을 공용 통화·진단·크기 점검·재개 쪽에서 수리한다.
4. 충분히 다양한 성공·실패 수리 궤적을 모은 뒤 모델별 학습·미세조정을 검토한다.
   해마 임베딩 학습은 회상을 개선하며 생성 모델의 IBL 문법 능력을 직접 훈련하는 것과
   다르다. 교재·언어 계약이 흔들리는 동안 생성 모델부터 학습하지 않는다.

## 외부 연구와 적용 한계

- [CodeAct, ICML 2024](https://arxiv.org/abs/2402.01030): 실행 가능한 코드로 도구 행동을
  묶는 접근과 실행 피드백의 효용을 보인다. IBL의 실행 프로그램 중심 방향을 지지하는
  인접 근거이며 Python에서의 결과를 IBL 절감률로 옮길 수는 없다.
- [LLM-Guided Compositional Program Synthesis, 2025](https://arxiv.org/abs/2503.15540):
  실패한 문제를 작은 하위 문제로 나누어 합성하는 방식이 자기반성만으로 풀리지 않던
  일부 예제 기반 프로그램 합성 과제를 해결한다. IBL의 부분 수리 설계에 참고하되
  추가 모델 호출의 비용까지 따로 측정해야 한다.

두 연구는 본 개선안의 효과를 입증하는 시험이 아니다. 가장 직접적인 검증 대상은
현재 IndieBiz OS의 실행기·교재·실제 누적 데이터로 구성한 미노출 과제다.
