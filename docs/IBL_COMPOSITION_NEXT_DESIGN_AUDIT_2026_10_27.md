## 1. 수리의 중심과 완료 조건

> **연결 조건을 만족하는 부품들을 합성하면, 그 결과도 같은 종류의 계약을 가진 부품이 된다.
> 이를 이름 붙이고 저장하고 더 큰 부품에 넣어도 요구·효과·실패·완료·계승의 의미가 보존된다.**

이 성질을 여기서는 **계층 상승에 대한 계약의 닫힘**이라고 부른다. 모든 어휘의 인자와 동작을
같게 만드는 뜻이 아니다. 어휘·등록/파일 스크립트·지역 함수·저장 관용구·그것들을 합친 더 큰
관용구가 **같은 계약 문법, 같은 연결 판정, 같은 실행 결과 해석**을 사용해야 한다는 뜻이다.

수리 단위는 다섯 반례가 아니라 **부품 생성 → 적용 → 합성 → 요약 → 부품으로 승격 → 저장/회수 →
재합성**의 고리다. D1~D5는 이 고리가 끊어진 관측 지점으로 보존한다(§10, 부록 A).
이 문서의 이전 항목별 수리 순서는 아래 공통 기반·수직 인수 순서로 대체한다.

성공 기준은 “다섯 탐침이 통과한다”를 넘어 다음 모두다.

1. 모든 생산자가 같은 계약으로 진입한다. 스크립트도 별도 우회 인터페이스가 되지 않는다.
2. 합성 규칙의 출력도 같은 계약이다. 상위 계층에 새 전용 실행기·완료 검사기를 만들지 않는다.
3. 함수 추출·인자 포장·저장·회수 때문에 작성자가 하위 구현을 펼쳐 계약을 다시 작성하지 않는다.
4. 연결 불가능·미확정·권한/수명 제한은 공통 계약으로 설명한다. “고차 관용구라서” 특별히 실패하지 않는다.
5. 실제 값·외부 효과·근거·실패·완료·복구의 보존을 검사하고, 분석 규모도 제한 안에서 유지한다.

목적은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)과 [vision.md](../data/system_docs/vision.md)를
따른다. 실제 품질·시간·전체 토큰 개선은 별도 계측한다. 측정을 일반 능력 설계의 선행 대기
조건으로 삼지 않으며, 계약 인수 통과만으로 비용 개선을 주장하지 않는다.

## 2. ‘같은 계약’의 정확한 뜻

### 2.1 부품, 정의, 호출, 결과를 구분한다

기존 [공통 Callable 모델](IBL_COMPONENT_COMPOSITION_REPAIR_PLAN_2026_10_27.md)의 구분을 유지한다.
아래 이름은 내부 설계 개념이며 새 어휘/저장소/실행 엔진을 뜻하지 않는다.

| 대상 | 담을 것 | 담지 않을 것 |
| --- | --- | --- |
| 부품 정의의 계약 C | 입력/결과 관계, 잠재 효과·접근, 실패·완료·수명·계승 조건, 정의/의존 판본 | 특정 호출의 승인 토큰·영수증·성공 판정 |
| 부품 값 | 정의 참조, 명시 캡처, C를 실제 인자로 특수화할 관계 | 핸들러 직접 실행 권한, 살아 있는 Runtime/Journal |
| 호출 인스턴스 I | 실제 인자/캡처/대상, 주체·권한·예산, 호출/반복 신원, 현재 의무 | 동일 인자의 다른 의도적 호출과 공유한 실행 신원 |
| 실행 산출 O | 업무 값 또는 실패/접수/중단 상태, 값의 부분 근거, 의무 판정, 효과 영수증 | 업무 JSON이 스스로 발급한 인증·실행 권한 |

`C`는 능력과 조건, `O`는 실제 발생 사실이다. 계약이 있다고 성공한 것이 아니며, 한 번 성공했다고
계약이 증명된 것도 아니다. 업무 값은 기존 `value/value_wire`에 두고 근거·판정은 기존 sidecar/
실행 봉투에 둔다. 모든 반환값을 새 업무 JSON 형태로 감싸거나 한 가지 입력 타입으로 강제하지 않는다.

### 2.2 공통 계약의 최소 의미 축

구현은 기존 `callable_contract`, Type, 함수 계약·분석 요약을 확장한다. 아래는 **제안 의미 스키마**이며
지금 입력할 수 있는 JSON/IBL 문법의 선언이 아니다. 구현 1단계에서 버전 있는 정규형을 확정한다.

| 축 | 모든 부품이 같은 방식으로 말할 내용 | 합성 시 보존할 핵심 |
| --- | --- | --- |
| K1 신원·판본 | 정의/구현/계약 판본, 의존 정의·자산, 언어/호스트 계약 판본 | 오래된 요약·다른 구현의 증거를 섞지 않음 |
| K2 호출·입력 전제 | 명명/위치 인자, 파이프 자리, 필수/기본값/별칭/op, 조건부 요구 | 기존 인자 해소 한 벌로 정규화하고 숨은 호출자 문맥을 입력으로 승격 |
| K3 값·관계 | 입력/캡처/투영 경로/각 적용 결과의 타입과 관계, 정상 반환 형태 | 동일 값 별칭과 서로 다른 호출 결과를 구분; 조합 중 변수 관계가 끊기지 않음 |
| K4 효과·자원 | 현재 평가 효과와 잠재 호출 효과, 읽기/쓰기 대상 관계, 미선언·미해소 상태 | 폐기한 반환값이 이미 발생한 효과를 지우지 않음 |
| K5 실패 | 알려진 실패 대안, open/unknown, 원인·partial·효과 불명·복구 가능 조건 | 실패 관찰/수집/복구/재전파의 차이를 보존 |
| K6 완료 | 명시 완료 의무 템플릿, 적용 조건·범위·허용 근거·필수/선택·복구 대안 | 호출마다 인스턴스화, 포장·저장으로 의무가 소실되거나 인증이 생기지 않음 |
| K7 실행·수명 | 동기 값/비동기 접수의 구분, 취소/중단, 세션·외부 참조·호스트·전송 제한 | 접수를 완료로, 지역 핸들을 영속/원격 값으로 승격하지 않음 |
| K8 재사용·수정 | 의존/작업 신원, 재사용/계승의 조건과 가능한 경계 | 완료 효과 비반복과 현재 외부 상태의 유효성을 구분 |
| K9 근거·판정 상태 | 선언/도출/관측/미상이라는 정보 출처, 해소된 조건·실행 의무·거절 이유 | 정보가 없음을 pure/성공/안전으로 해석하지 않음 |

관계는 유한 기호식으로 표현한다. 입력 신원, 고정 경로/유한 선택 경로, 조건, 적용 인스턴스,
캡처와 반환 관계를 같은 표현으로 사용한다. effects/accesses/completion/recovery가 각각
별도의 변수·경로 해석기를 만들지 않는다. 동적 해소와 분석 한도를 넘은 부분은 미확정으로 남긴다.

정보 출처와 충족 여부는 별개다. 핸들러 선언은 명시된 공급자 계약으로 검사하되 실행 사실의
증명은 아니다. 관측된 필드/과거 성공은 보조 정보이며 보편 계약으로 자동 승격하지 않는다.
서로 다른 축의 미확정을 구분한다. 반환형이 미상이라고 알려진 자원 대상까지 버리지 않는다.

### 2.3 연결과 대체 가능성

같은 접촉부는 무조건 연결 가능하다는 뜻이 아니다. 연결 판정은 다음 셋 중 하나로 남긴다.

- **정적 충족**: 입력·효과·수명 등 필요한 관계가 확인돼 연결할 수 있다.
- **조건부 연결**: 실행 때 확인할 수 있는 의무를 남긴다. 값이 확정되는 경계에서 검사하고,
  그 증명이 필요한 외부 효과/관측 확정 전에 통과시킨다.
- **거절**: 계약이 모순되거나 필요한 보장을 해당 경계에서 확인할 수 없다. 이유와 위치를 제공한다.

대체 부품은 기존 허용 입력에 더 강한 전제를 몰래 요구하지 않고, 요구된 출력·완료 보장을
약화하지 않으며, 허용 효과/접근/권한/실패·수명 범위를 넓히지 않아야 한다. 이를 증명할 수 없는
교체는 미확정/재검사로 남긴다. `unknown` 스크립트와 순수 함수는 반환형이 같다는 이유로 대체 가능하지 않다.
내부 구현이 같거나 임의 의미가 동등하다고 자동 판정하는 체계는 아니다.

## 3. 네 종류의 부품을 같은 입구로 연결한다

| 생산자 | 현 정본·소유자 | 공통 계약으로 올리는 방법 |
| --- | --- | --- |
| 어휘/내장 함수 | YAML·패키지 선언 → registry/Adapter, 기존 순수 값 라이브러리 | 선언·인자 변형·효과·접근·호스트 제약을 C로 정규화; 호출자는 생산자 종류로 재판정하지 않음 |
| 등록 스크립트 | `data/scripts/registry.yaml`, `ibl_dependencies.script_contract`, script runner/session | 등록된 callable_contract와 파일/환경 지문을 대입; args의 안/바깥 op·별칭·파이프 관계도 같은 해소기를 사용 |
| 파일/동적/비동기/세션 스크립트 | `ibl_file_script`, `ibl_script_session`, 기존 task_receipts·ForeignRef | 선언 가능 범위만 제공하고 나머지는 명시 미상; 실제 실행·소유권·수명·접수 상태를 공통 O로 투영 |
| 지역 함수·람다·관용구 | AST/CallAnalysis, `function_library`/`function_store` 불변 판본 | 하위 C와 지역 IR을 합성하여 같은 C를 도출; 명시 입력/캡처와 완료 선언을 검사 |
| 더 큰 관용구 | 위 관용구를 인자로 받거나 호출하는 동일 함수 경계 | 별도 ‘상위 관용구’ 타입을 만들지 않고 같은 도출·등록·호출 경로를 반복 |

정규화는 소유자를 복제하지 않는 어댑터다. 전 부품을 넣는 새 전역 사전/DB는 만들지 않는다.
현재 `ibl_dependencies.script_contract`는 등록 스크립트의 값/효과를 해소하며, 동적·원격·파일 호출은
보수적 바깥 계약을 유지하고 background는 접수증을 반환한다. 이 경계를 없애지 않고 K1~K9로 완성한다.

**불투명한 스크립트의 기준**: 임의 Python/셸 본문을 읽어 모든 효과·실패·자원·부분 재개를
증명한다고 가정하지 않는다. 알 수 없는 것은 C에 남겨 순차 호출은 가능한 계약대로 허용하고,
순수 조건/독립 병렬/완료 효과 계승처럼 더 강한 보장이 필요한 자리는 거절하거나 추가 선언·검증을 요구한다.
스크립트를 함수로 한 번 감싼다고 미상이 사라지지 않는다. 검토된 선언과 실행 경계의 검증을 구분한다.

복구의 상세도도 계약이다. 불투명 스크립트는 검증된 전체 호출 영수증 단위로만 계승할 수 있고,
내부 단계의 증거를 제공하지 않으면 중간 지점으로 들어가 재개할 수 없다. IBL로 구성한 부품은
내부 의존 그래프를 유지할 수 있다. 둘은 같은 접촉부를 가지되 가능한 복구 범위가 다르다.
단독 셸/파일 작업을 모두 IBL로 강제 변환하지 않는다. 조합 경계에 들어온 경우 이 계약으로 잇는다.

## 4. 합성 규칙 — 출력도 반드시 같은 계약이다

설명상 `contract(compose(P,Q)) = compose_contract(CP,CQ,지역 연결)`이다. 실제 언어에
compose라는 새 어휘를 추가한다는 뜻이 아니다. 각 문형은 **같은 계약 정규형을 받아 같은 정규형을 반환**한다.

| 문형/경계 | 입력·값 관계 | 효과·실패·완료·계승 규칙 |
| --- | --- | --- |
| 순차·파이프 | 앞 반환을 뒤 인자로 대입; 뒤 요구 중 충족되지 않은 전제를 외부 입력/실행 의무로 남김 | 실제 순서 보존; 앞 효과/미확정은 뒤 반환만 골라도 유지; 앞 실패 시 미실행 뒤 호출을 실행 사실로 세지 않음 |
| 함수 적용·고차 인자 | 인자/캡처의 C를 적용 위치에 특수화; 반환 콜백도 같은 C를 가짐 | 부품 값 생성·전달에는 잠재 효과를 실행하지 않음; 적용 시 기존 권한·예산·영수증 경계를 한 번 통과 |
| Record/List/Result 포장·선택 | 부분 경로·별칭·실패/정상 대안을 보존; 선택 결과의 C와 기호 관계를 추출 | 값/제어/구조 의존을 구분; 불완전한 형제의 무조건 전염과 반복 범위 근거 삭제를 모두 막음 |
| 분기·단락 | 조건 아래의 요구/반환을 합성; 서로 배타적인 요구를 무조건 교집합하지 않음 | 실행되지 않은 가지의 호출 의무는 활성화하지 않음; 선택에 사용한 제어 근거는 남김 |
| 병렬 | 각 가지의 입력/자원 관계를 특수화하고 구간 전체의 독립성을 확인 | R/R·확인된 독립 자원만 동시 허용; unknown write를 독립으로 간주하지 않음; 실패/취소 후 이미 시작한 효과를 보존 |
| 반복·each | 원소/인덱스/누적 값에 관계를 대입; 반환 목록과 항목 신원을 보존 | 호출별 의무·실패를 인스턴스화; 빈 반복·필터·상수 콜백도 범위 근거를 보존; 전개 수/예산 제한 |
| catch·fallback·collect | 알려진 실패 대안과 처리되지 않은 실패를 구분; collect의 Result도 공통 값 | 승인된 복구 대안만 의무를 해소/대체; 실패 이력·불명 mutation은 지우지 않음; 원형 전파 경로 제공 |
| 접수·대기·중단 | task_ref와 최종 결과의 단계를 구분; 호출의 현재 상태를 C/O에 표현 | background 접수는 최종 값/완료가 아님; 유한 대기/취소·재조회는 기존 task 소유자 사용, 암묵 재발송 금지 |
| 이름 붙이기·저장·회수 | 지역 입력/캡처를 공개 서명으로 닫고 의존 판본에 묶음 | 같은 C를 다시 호출 가능하게 함; 실행 중 권한/세션을 영구 인증으로 저장하지 않음 |
| 부품 교체·수정 | 계약 호환성과 실제 변경 의존 부분을 계산 | 미영향 완료 효과만 근거로 계승; 새 효과는 현재 검사, 불명 효과는 추측 재시도 금지 |

순차 합성은 형식만 맞추는 일이 아니다. 하위 보장으로 해결된 전제는 상위의 불필요한 입력으로
다시 요구하지 않고, 해결되지 않은 조건은 상위 계약에 남긴다. 임의 논리 함의/SAT를 완전히
풀려 하지 않는다. 지원하는 유한 조건과 기호 관계만 증명하고 나머지는 이유 있는 미확정이다.

### 4.1 외부 요약과 내부 계보를 함께 유지한다

호출자는 공개 C로 조합하며 하위 본문을 매번 펼치지 않는다. 내부 호출/의존/근거 그래프는
진단과 부분 수리를 위해 유지한다. 공개 요약에서 지역 신원을 숨길 때는 외부 입력/결과와의
관계만 남기고, 내부 계보로 되돌아갈 참조를 보존한다. 스크립트의 불투명 내부를 지어내지는 않는다.

특수화가 필요하면 하위 C를 대입한다. 유한 정밀화가 불가능할 때의 미확정/추가 분석을 구분하며,
상위 함수를 만드는 매 단계마다 모든 하위 본문 재전개를 기본 방식으로 삼지 않는다.
요약 캐시는 계약 판본·기호 인자/캡처·의존 지문을 키로 삼고 호출자 조건을 재생한다.
새 공통 계약과 구 계약 캐시를 혼용하지 않는다.

### 4.2 부품을 다시 만드는 닫힘 조건

1. 원래 프로그램의 자유 입력과 캡처를 명시한다. 함수 경계의 return/try/finally 의미를 보존한다.
2. 하위 계약과 지역 연결에서 C를 도출하고, 제작자의 명시 선언과 대조한다.
3. 내부 지역 신원을 외부 매개변수/반환 관계로 정규화한다. 정상 부품이면 같은 정규형 C를 얻는다.
4. 지역에서 즉시 호출/전달한다. 저장은 부품화의 전제가 아니다.
5. 재사용 가치가 있을 때 기존 함수 판본 저장소에 정의·의존·선언을 등록한다. 계약 뷰는 파생한다.
6. 회수한 부품에 1~5를 다시 적용한다. ‘몇 층째’라는 특별 분기는 없어야 한다.

이 과정은 계약의 조건부 닫힘이다. 수명이 끝난 ForeignRef나 저장 불가 캡처는 명시 입력으로
분리/변환하거나 저장을 거절한다. 무제한 재귀·분석 한도 무시·모든 값의 외부 직렬화를 약속하지 않는다.

## 5. 완료·실패·복구를 공통 실행 의미로 묶는다

### 5.1 완료 의무의 소유권과 적용 범위

완료 선언의 정본은 부품 정의의 명시 선언이다. 제작자의 업무 정책은 데이터/함수에 두고
compiler가 검사하여 C에 포함한다. 등록 row/describe/회상에는 같은 판본의 파생 뷰를 제공한다.
상위 요청 completion은 이 의무를 연결·강화하는 계약이며 매번 내부 원천 이름을 다시 적는 자리가 아니다.
하위 원천과 외부 보장 사이의 대응은 하위 계약이 소유하고 실제 인증은 호출 근거를 참조한다.

템플릿은 입력·반환 부분·원천/대상 관계와 함께 **활성화 조건**을 가진다. 정상 반환의 보장,
선택된 산출물의 의무, 이미 시작한 외부 효과의 의무를 구별한다. 호출/반복 인스턴스에 대입한
신원으로 판단한다. 아직 호출하지 않은 가지, 선택 의무, 필수 의무를 섞지 않는다.

- 함수가 정상 반환하며 약속한 필수 보장은 상위 포장/값 폐기로 없앨 수 없다.
- 선택 산출물의 의무는 선언된 선택 규칙을 따른다. 단순히 선택하지 않았다는 이유로 시작한
  mutation의 미확정이나 필수 전달 의무까지 지우지는 않는다.
- 실패한 경로의 의무는 계약에 허용된 복구 대안과 그 근거로 해소/대체할 수 있다. 오류를
  catch했다는 사실만으로 충족된 것은 아니다. 미해결 의무와 실패 감사는 남긴다.
- 각 반복 의무를 전부 최상위 요청의 평평한 목록에 손으로 펼치지 않는다. 템플릿·인스턴스
  요약·상세 참조를 사용하며, 표시 생략을 검사 생략으로 바꾸지 않는다.

`satisfied/unsatisfied/undetermined`와 적용 여부는 구분한다. 미실행/비적용 의무를 satisfied로
만들지 않는다. `source_complete` 감사, 실제 실행 성공, 업무 완료는 별도 축으로 유지하고
공통 소비자가 함께 해석한다. 원천 이름·같은 값·업무 JSON·과거 성공만으로 인증하지 않는다.

### 5.2 실패를 관찰하거나 전달하는 공통 경계

Fault/Result를 새 실패 저장소와 이원화하지 않는다. 런타임이 만든 실패 신원·원인·kind/code·
partial·위치·근거·효과 불명 상태를 보존한다. 알려진 실패 대안과 미상 실패를 같은 C로 요약한다.
선택적 복구와 원형 재전파를 제공하되 기존 `unwrap(Err)`의 UNWRAP_ERR 의미는 유지한다.
관찰용 `$error` Record가 자동으로 실행 권한/인증을 가진 실패 객체가 되지는 않는다.

collect는 실패를 명시적으로 값으로 다루는 정책이다. 모든 Result.Err을 프로그램 실패로
재해석하지 않는다. 수집의 성공과 업무 완료는 C의 의무에 따라 따로 판정한다. 반대로
권한·취소·예산·suspended·protocol의 비복구 경계는 collect/포장으로 약화할 수 없다.
finally의 정리 실패와 병렬의 복수 실패도 동일 원인 계보에 보존한다.

### 5.3 의미에 따른 부분 수정과 계승

현재 구문별 `pure_tail` 판정은 공통 효과/의존 요약으로 대체한다. 직접 식을 지역 바인딩이나
순수 함수로 추출해도 같은 계산 부분 그래프로 수리한다. 단지 함수 전체 본문 지문이 달라졌다는
이유로 독립 완료 효과를 모두 무효화하지 않는다.

기존 Journal의 영수증·CAS·실행 계보를 이용해 완료 효과 계승, 새 계산, 검증 읽기 필요,
명시 재실행 필요, 불명 효과를 분류한다. 논리 작업 신원은 부품/반복 인스턴스에 묶고,
같은 액션/인자 해시를 같은 의도로 취급하지 않는다. 명확한 대응만 자동 인정한다.

효과별 입력/캡처·대상·구현·계약·근거 의존을 대조하며, 주체/소유 범위·언어 의미·현재 권한·
승인 검사는 유지한다. 새 작업은 새 승인/예산을 사용한다. 재개가 의미하는 것은 과거 실행의
계승이지 현재 외부 상태의 자동 유효성이나 롤백/보편적 exactly-once가 아니다.

## 6. 같은 보장을 유지하기 위한 공통 규율

| 규율 | 구현과 인수에서 금지할 우회 |
| --- | --- |
| 정보 손실 없는 포장 | 요구/실패/완료/수명 중 구현하기 어려운 필드를 Unknown 또는 누락으로 바꾸어 합격시키기 |
| 정직한 미확정 | 미선언 자원·효과를 없음으로, 수집된 오류를 삭제로, 접수를 완료로 취급하기 |
| 권한 비증폭 | 함수/스크립트 포장이 주체·실행 호스트·노드 권한·승인을 확대하기 |
| 수명 비연장 | 세션 객체·ForeignRef·지역 캡처가 저장/전송을 지나 자동으로 살아 있다고 가정하기 |
| 호출의 단일성 | check/describe/요약/저장을 위해 실행하거나, 부품 승격으로 잎 효과를 한 번 더 호출하기 |
| 조건과 의무의 보존 | 서로 다른 호출 결과를 합쳐 모순 판정하거나 필수 의무를 optional로 바꾸어 통과시키기 |
| 책임의 단일성 | 화면/감독/스크립트 러너가 별도 성공·효과·경로 판정기를 유지하기 |

미선언 자원의 정책은 이 규율의 일부다. 새 보장 계약에서 unknown write가 있는 병렬 구간은
독립성이 확인되지 않으면 거절하거나 작성자가 명시한 순차 구간으로 처리한다. 조용히 순차화해
순서·지연의 뜻을 바꾸지 않는다. R/R과 확인된 독립 자원의 병렬성은 유지한다.

하위 계약의 보장 정책은 상위 포장으로 약화되지 않는다. 기존 요청의 composition opt-in과
미선언 어댑터는 이행 대상이며, 호환 정책으로 실행한 경우 새 보장을 표시하지 않는다.
요청 안의 병렬 비교, 같은 프로세스의 다른 요청, 외부 프로세스/서버의 원자성은 별도 범위다.
현재 admission 통과를 요청 간 잠금이나 분산 원자성으로 부르지 않는다.

## 7. 소유자·정본·이행과 제거할 경로

### 7.1 구현 소유자

| 책임 | 확장할 기존 소유자 | 수렴 결과 |
| --- | --- | --- |
| 정규형과 관계 | Type, `ibl_callable_contract`, requirements, analysis/access_type, CallAnalysis | 입력 경로·적용 결과·조건·효과·접근·완료 관계의 해석 한 벌 |
| 어휘·스크립트 진입 | `ibl_v2_adapters`, `ibl_dependencies`, script runner/file/session, 기존 선언 | 같은 C의 생산자 어댑터; 공급자별 실행·환경·권한은 유지 |
| 합성·추상화 | compiler, 함수 계약/요약, 기존 AST | 모든 문형의 합성 결과가 같은 C; 지역 본문을 반복 전개하지 않는 요약 |
| 값·근거·실패·수명 | Binding, Runtime, Fault/Result, task_receipts, ForeignRef, value wire/result refs | 공통 O와 검증된 계보; 생명주기/전송 제한 보존 |
| 저장·발견 | function_library/store, describe/회상, 의존 지문 | 선언/판본이 정본, 요약은 파생; 계약으로 찾고 호출하고 필요할 때 본문 열기 |
| 관측 확정·복구 | execution_commit, Journal, repair | 인스턴스 의무별 확정과 의존 부분 그래프의 수정/CAS |
| 소비 | HTTP/MCP, model_result_view/감독, 공통 앱 JS/TS·조종실·PC/Android | 같은 판본·같은 상태 해석; 전송에는 필요한 요약/참조만 포함 |

어휘는 YAML, 등록 스크립트는 기존 registry와 파일, 함수는 정의/불변 판본이 각각 정본이다.
compiler/정규화기에서 나온 계약 뷰를 별도로 손 편집하지 않는다. 계약 변경은 구현·의존 지문과
함께 무효화하고, 과거 영수증/미지원 소비자에는 보수적 구 계약 처리를 유지한다.
언어 표기나 표준 기능을 바꿀 때는 `ibl.md`와 표준 코어 정의를 함께 개정한다.

### 7.2 대체·제거할 중복과 임시 경로

- 단순 매개변수 이름만 아는 origin과 별도 자원 변수 관계를 공통 기호 경로/적용 결과 관계로 수렴한다.
- 함수 경계마다 완료 조건을 최상위 요청에 재작성하는 관례를 부품 템플릿/인스턴스 계약으로 대체한다.
  요청 completion 자체는 상위 요구를 표현하는 정식 경계로 유지한다.
- 구문 허용 목록으로 별도 판단하는 pure_tail은 compiler의 같은 효과/의존 판정으로 대체한다.
- 미선언 자원을 독립으로 간주하는 호환 경로는 사용 여부를 드러내 이행한다. 모든 어댑터에
  허위 pure/독립 선언을 달아 관문을 우회하지 않는다.
- 어휘·스크립트·함수 소비자의 같은 계약 해석은 공유한다. 실제 권한 검사, 프로세스 수명,
  업무 확정, 공개 확정처럼 책임이 다른 경계는 지우지 않는다.
- 전체 소스 상시 프롬프트 주입·사설 실패 포장 해석으로 잇던 지침은 공통 계약 소비가 완성되면 제거한다.

## 8. 구현 순서 — 공통 고리를 한 단계씩 완성한다

다음 단계는 D1~D5별 별도 기능 릴리스가 아니다. 각 단계에서 어휘·스크립트·함수·합성 함수의
같은 경로를 함께 통과시키는 수직 인수를 만든다. 아직 없는 축을 있거나 완료됐다고 표시하지 않는다.

| 단계 | 구현 묶음 | 다음 단계로 가는 완료 조건 |
| --- | --- | --- |
| P0 계약 고정 | K1~K9 정규형/판본·정보 출처·상태·관계 한도·소유자 확정; 현재 생산자/소비자 이행 목록 | 모든 생산자를 표현 가능하며 미상을 숨기지 않음; 문형별 합성 규칙·오류/호환 정책·시험 오라클 합의 |
| P1 관계와 생산자 연결 | 어휘/등록·파일·세션 스크립트/함수의 C 정규화, 기호 경로/적용 결과/조건, 공통 인자 해소·요약 | 네 층의 직접/고차 호출이 같은 입력·효과·수명 검사를 사용; D1 정상·모순 대조와 캐시 켬/끔 일치 |
| P2 합성·추상화·승격 | §4 문형의 C 합성, 지역 입력/캡처 닫기, 내부 그래프/외부 요약, 저장·회수·개정 검사 | 어휘+스크립트→F1→저장/회수→F2→다시 저장/회수→F3가 같은 계약 생성/호출 경로로 실행 |
| P3 실행 의무와 산출 | 완료 템플릿/활성화/인스턴스, 실패 재전파, unknown 자원 정책, 비동기/세션 상태, 부분 관측 확정·소비 | P2 고리에 정상·부분 실패·취소·미확정·fallback을 넣어도 의무/효과/실패가 보존되고 모든 소비자 판정 일치 |
| P4 수정·교체 | 같은 요약 기반 순수 후미와 독립 계산 부품 수리, 효과별 계승·신원·CAS·현재 권한 | 직접 식/함수/지역 바인딩 수리 동등성, 두 단계 이상 상위 부품 안 수정, 잎 쓰기 비반복; 모호한 대응 안전 거절 |
| P5 이행·최종 재감사 | 옛 경로 제거/명시 호환, 가이드·오류 도움말·파생물·폰/PC, 전수/관련 system | §9 모든 필수 인수와 D1~D5 추적표 확인; 미지원·미검증 구분; 정본 main 반영 |

P1~P2에서도 실패/완료 등의 슬롯을 누락하거나 가짜 성공으로 채우지 않는다. 아직 해소하지
못한 의무로 전달하며, 실행부와 소비자까지 연결되는 P3 전에는 새 완료 합성을 지원한다고 말하지 않는다.
임의 부품 교체·반복 재정렬은 P4의 신원/의존 인수가 확인한 범위만 넓힌다. 예전 기록에 새 증거를 소급 발급하지 않는다.

## 9. 검증 기준 — 반례 목록보다 조합 성질을 먼저 검사한다

### 9.1 기준 관측과 대조 방식

각 실행에서 다음을 비교한다. 바이트 동일한 trace나 우연히 같은 호출 ID만 요구하지 않는다.

| 관측 | 비교 규칙 |
| --- | --- |
| 업무 값·실패 | value_semantics의 동등성, 정상/Result/실패 대안·원인·partial 보존 |
| 실행 효과 | 합성 어댑터의 실제 시작/완료/불명 횟수, 인자·대상, 의존하는 호출 순서; 독립 병렬은 허용된 부분 순서로 비교 |
| 계약 | 기호 지역 이름 정규화 후 요구/결과/효과/접근/수명/정책·실행 의무 대응; 새 미확정이나 누락이 생겼는지도 확인 |
| 완료·근거 | 논리 의무와 실제 호출/선택 경로를 대응시켜 상태·허용 원천·범위별 관측 확정 비교 |
| 권한·수명·복구 | 주체/소유자/호스트·승인 결과, 참조 수명, 재개 허용/거절, 재발송 횟수; 이 차이는 정규화로 지우지 않음 |
| 비용·규모 | 요약 수·크기·분석/평가 예산·trace 성장과 명시 한도; 테스트의 시간/토큰 추정치를 실서비스 개선으로 읽지 않음 |

동등성 변환은 평가 순서·자유 입력/캡처·조건·권한·의무를 보존하도록 생성한다. 관리용 프레임/ID,
표시 위치와 소액 실행 오버헤드는 달라질 수 있다. 동일 예산 내에서 비교하고 한도 경계는 별도 시험한다.
효과 호출을 재정렬하거나 fallback/collect/비동기 정책을 바꾼 경우는 동등 변환으로 우기지 않고
**명시된 계약 변화**와 그 결과를 검사한다.

### 9.2 반드시 통과할 성질

| ID | 성질 | 인수와 반대 대조군 |
| --- | --- | --- |

전 조합을 무작정 전개하기보다 필수 경계 교차표와 재귀 생성기를 사용하고 빠진 셀을 보고한다.

### 9.3 무한 반복을 유한 시험만으로 주장하지 않는다

논거는 **기초 부품이 C를 제공하고, 각 합성 규칙이 C에서 C로 닫히며, 승격/저장 경계가 이를
보존한다**는 구조와 규칙별 검사다. 깊이 몇 개 통과만으로 임의 프로그램의 무결함을 증명하지 않는다.

책임 모듈의 회귀에 한 단계 규칙, 재귀적으로 생성한 혼합 부품의 변환 시험, 캐시 켬/끔과 직접
실행의 대조를 둔다. 깊이 6/10/14/30 공유 DAG, 다른 캡처·조건·적용 특수화·빈/큰 반복,
분석 예산 초과를 검사한다. 예산 초과 시 계약을 날리거나 무한 전개하지 않고 명시 미확정/거절을 반환해야 한다.
이전 D1~D5 탐침은 고정 감사 증거로 남기고, 새 기대 성질은 `backend/test_<책임 모듈>.py`에 추가한다.

### 9.4 서로 다른 전체 업무를 계층 상승시킨다

두 흐름 모두 저장된 정답 관용구 없이 작은 부품에서 시작하고, 등록 스크립트와 어휘를 섞어
F1을 만들고, 회수한 F1로 F2를 만들고, 다시 회수해 F3의 부품으로 사용한다. 이름만 바꾼
동일 프로그램을 두 과제로 세지 않는다. 엔진은 업무 이름을 분기 조건으로 알지 못한다.

- **자료→검사→발행**: 어휘로 여러 판본 자료 취득, 스크립트로 정규화, 판정 콜백으로 필수 표/
  선택 주석 분리, 관용구로 행별 완료/집계, 상위 관용구로 발행·검증. 일부 원천 실패와 대체,
  출력 경로 이동, 발행 뒤 렌더 부품 수정에서 범위별 관측 확정·발행 비반복을 확인한다.
- **상태→판정→조작→재관측**: 상태 어휘와 계산 스크립트, 정책 콜백, 비동기 조작 접수·유한 대기,
  재관측 부품을 구성한다. 접수를 업무 완료로 보지 않고, 확인 부품만 고칠 때 재발송하지 않으며,
  효과 불명은 자동 재시도하지 않는다. 세션 참조를 바깥으로 꺼내려는 경우 수명 제한도 검사한다.

먼저 합성 어댑터·임시 원장·실제 공용 러너로 계약을 검사한다. 실제 외부 서비스/기기 동작과
에이전트의 작성 품질·수정량·전체 토큰·완료 시간은 별도 검증 상태로 기록한다.

### 9.5 회귀·최종 인수 산출물

현재 존재하는 `test_ibl_v2_requirements`, `test_ibl_v2_call_analysis`, `test_ibl_v2_access`,
`test_ibl_v2_completion`, `test_ibl_v2_repair`, `test_ibl_honesty`, `test_ibl_dependencies`,
`test_callable_component_contracts`, `test_function_store`, `test_model_result_view`,

언어/값/스크립트 변경은 Python 라이브러리, 원장/재사용 변경은 지정 긴문장 전체 재생,
어휘/배포 변경은 archive/bundle 묶음을 포함한다. frontend tsc, 어휘/문서 파생·Android 몸/앱 셸,
층·파일 크기 검사도 해당 변경에서 수행한다.

최종 보고에는 K1~K9 생산자/소비자 대응표, L1~L11의 실제 실행 항목·결과·미검증,
F1→F2→F3의 계약/잎 호출/실패/완료/계승 비교, D1~D5 재대조, 삭제한 중복 경로와 남은 호환
경로를 함께 남긴다. 새 상시 프롬프트/모델 호출/별도 원장으로 비용을 넘기지 않았는지도 확인한다.

## 10.1 에피소드 5557 — 실행 산출의 관계와 소비 인수

마지막 순수 계산을 수리해도 외부 읽기·발행·발송·대기는 다시 호출하지 않는다. 순수 스크립트
계산은 재실행된다. 완료 판정은 접수값이 아닌 재관측에 묶인다. 접수/대기는 합성 모형이며,
실제 서비스 작업 수명은 기존 task receipt 시험으로 별도 검증한다. 실제 외부 서비스 발행이나
실기기 동작을 이 시험의 성공으로 주장하지 않는다.

재대조 중 발견한 실패 계승 경계도 공통 영수증 계약으로 보강했다. 명시적 read_external의
완결된 실패 영수증은 같은 실행·동일 효과 접두부에서 원래 Fault로 복원해 같은 복구 분기를
지난다. 실패한 write/model/unknown, 승인 대기, 완료 불명 및 효과 증거 없는 옛 실패 영수증은
자동 계승하지 않는다. 읽기 실패를 새 성공값으로 바꾸거나 원천을 재호출하는 기능이 아니다.

불투명한 파일 스크립트·task 제출·TV 준비의 병렬 예시는 명시 순서로 이행했다. 독립 자원이
선언된 쓰기와 실제 작업의 동시 진행은 유지한다. 엔진이 모르게 직렬화하거나 불명 스크립트를
순수하다고 허위 선언하는 우회는 두지 않았다.

### A1. D1 — 변수 이름을 넘는 관계 계약

```ibl
[def:f]($x){return abs($x)}
[def:g]($x){return abs($x.n)}
```

첫 정의의 requirements에는 `x:Number`가 남는다. 둘째는 guard가 생기지만 requirements는
빈 Record다. `$x.n`에서 원래 매개변수와 부분 경로의 관계가 끊어진다. 다음 정의도 독립
검사에 문제가 없다고 나오고 **실제 임시 함수 등록에 성공**한다.

```ibl
[def:f]($x){$a=abs($x.n);return not $x.n}
```

같은 필드가 무조건 Number와 Bool이어야 한다. IBL은 Bool을 Number로 취급하지 않는다.
구체적인 잘못된 인자를 적용하면 검사/실행 경계가 거절할 수 있지만, 그것이 불가능한 독립
정의를 저장 전에 구별하는 계약을 대신하지는 않는다.

역방향도 있다. 아래 첫 정의는 독립 검사에 통과하고 두 번째는 `PURE_EXPRESSION`으로 거절된다.
두 번째에 실제 순수 콜백을 주어 함께 컴파일하면 값 1을 정상 반환한다. 중첩 명시 콜백 타입을
직접 적으면 독립 검사도 통과한다. 즉 실행 불가능한 함수가 아니라 **추론·독립 저장의 경계**다.

```ibl
[def:f]($p){[if:$p(1)]{return 1}[else]{return 0}}
[def:g]($cfg){[if:$cfg.p(1)]{return 1}[else]{return 0}}
```

같은 끊김은 자원 관계에도 나타난다. `[t:write]{key:$key}`를 감싼 함수의 접근 요약에는 입력
관계가 있지만, `key:$cfg.key`로 묶으면 relations가 비어 있다. 이번 탐침은 관계 소실을 확인한
것이며, 선언 자원의 구체 실행 충돌 검사가 모두 무력화된다는 주장은 아니다.

콜백 결과도 값 하나의 신원이 없다.

```ibl
[def:f]($p){$x=$p(1);$a=abs($x);return not $x}
```

requirements에 결과의 Number/Bool 요구가 모두 기록되지만 독립 검사는 거절하지 않는다.
서로 다른 콜백 적용의 반환 타입을 함부로 합치지 않으려고 모든 result 요구의 교집합 검사를
생략한 구조가, **한 번 계산해 같은 `$x`로 보관한 결과**의 모순까지 구별하지 못한다.

- `ibl_v2_analysis.py:351`의 `access_type`은 Unknown의 필드/인덱스 선택 뒤 일반 UNKNOWN을 반환한다.
- `ibl_v2_requirements.py:14`의 origin은 `(parameter|application, sid, name)`만 식별한다.
  `application`은 적용 위치/인자를 결과 신원에 넣지 않는다(:36).
- `finish`는 result 요구를 모두 모순 검사에서 제외한다(:253).
- 조건 정보도 현재는 `conditional:bool`이다. 어떤 입력 조건 아래의 요구인지 독립 계약만으로
  재대입할 수 있는 유한 조건식이 아니다. 이 사실은 코드로 확인했으며 별도 조건식 반례는 세지 않았다.

### A2. D2 — 완료 계약의 부품 소유권

```ibl
[def:fetch](){return [t:down]{} ?? [t:good]{}}
```

`t:down`은 실패하고 `t:good`은 완전한 2와 로컬 관측을 만든다. 저장 라이브러리 정의처럼
이 함수를 불러, 요청에 `predicate:$value==2`와 원천 `t:good`을 선언하면 satisfied와 관측
확정이 된다. 같은 함수에 최상위 completion을 주지 않으면 실행/값은 성공하지만
`source_complete:false`, completion 없음, 관측은 not_committed다.

후자는 계약이 없으므로 보수적으로 처리한 올바른 현행 동작이다. 공백은 **함수 제작자가 이미
정한 완료 조건을 함수 판본과 함께 선언하고 호출마다 재사용할 자리**가 없다는 점이다.
호출자는 내부 대체 원천 이름과 대상, 출력 포장 경로를 다시 알아야 한다.

현재 `function_contracts`에는 requirements/result/effects/accesses 등이 있지만 completion은
없다(`ibl_v2_compile.py:366`). 완료의 소유자는 요청과 Runtime
(`ibl_v2_entry.py:54`, `ibl_v2_completion.py:9`)이다. `function_library.register`(:83)의 정식
등록 계약에도 완료 선언은 없다. 임의 provenance 필드에 적는 것은 실행 계약을 강제하지 않는다.

또한 요청은 의무 1~32개와 고정 scope 경로를 받는다. 33개의 서로 다른 의무 선언은 거절된다.
이 제한 자체를 없애자는 뜻은 아니다. 동적 each의 각 호출에 같은 완료 계약을 대입하려면
최상위에서 의무를 펼치거나 하나의 전체 판정으로 바꿔야 하며, **템플릿→호출별 의무** 모델이 없다.
직전 수리의 검증된 결과 참조 인증 이식은 유지되지만, 새 함수 호출이 자신의 계약을 갖는 것과는 다르다.

### A3. D3 — 수정 재개의 구문 종속

외부 쓰기 한 번 뒤 `n:0`으로 실패시킨 세 프로그램의 마지막 계산을 고쳤다.

| 수정 위치 | 원래 계산 → 수정 계산 | check의 수정 계승 판단 |
| --- | --- | --- |
| 마지막 직접 식 | `return $sent/$n` → `return $sent/($n+1)` | ready; 실제 재개 성공, 누적 쓰기 1회 |
| 순수 지역 함수 호출 | `return [fn:calc]{x:$sent,d:$n}` → `d:$n+1` | REPAIR_UNSUPPORTED, 쓰기 1회 유지 |
| 순수 지역 바인딩 | `$v=$sent/$n;return $v` → `$v=$sent/($n+1);return $v` | REPAIR_UNSUPPORTED, 쓰기 1회 유지 |

세 경우는 같은 입력·원래 쓰기·계산 의도를 가지며 calc 본문은 `$x/$d`다. 거절은 안전하고
쓰기 재실행도 하지 않았다. 그러나 **부품화하면 부분 수정 능력이 약해진다.** 이는 큰 조합을
다시 더 큰 부품으로 키우려는 목적과 직접 충돌하는 지원 한계다.

`ibl_v2_repair.py:39`는 순수성을 compiler 효과 요약 대신 구문 허용 목록으로 판단한다.
`propose`(:95)는 마지막 return 이전 AST가 동일해야 하며, 전역 부품/문맥 지문도 동일해야 한다.
이미 고친 마지막 식을 지원하는 현재 기능을 부정하는 것이 아니라 그 밖의 확대가 필요하다.

### A4. D4 — 미선언 자원의 병렬 정책

아래는 **§11 수리 이전의 관측**이다. 현행 계약은 opt-in과 무관하게 미해소 R/W·W/W를
시작 전에 거절한다(§11.3 D4, `ibl.md`의 병렬 자원 규약). `composition`은 호환 표기이며
보장 스위치가 아니다. 10-28 재감사에서 효력이 없던 `conflicts(strict=)` 내부 인자도 제거했다.

```ibl
[t:write]{key:"shared"} & [t:write]{key:"shared"}
```

합성 어댑터는 write_external을 선언하지만 자원 선언은 없게 했다. 내부의 같은 공유 자원에
대한 쓰기를 Barrier로 맞췄을 때 기본 Runtime은 성공했고 **최대 동시 쓰기 수 2**였다.
같은 요청을 strict composition으로 실행하면 두 쓰기 모두 시작 전에 거절된다.
`write_resources:{record:key}` 선언을 넣으면 기본 검사에서도 충돌로 거절된다.

권한 우회나 모든 실 어휘의 데이터 손상을 입증한 실험이 아니다. 선언 없는 어댑터를 다른
부품으로 치환했을 때 **독립성을 모른다는 정보가 기본 병렬 실행을 막지 않는다**는 사실이다.

`ibl_v2_access.py:54`의 conflicts는 미해소 자원을 strict 또는 양쪽 선언이 있는 경우에만
실행 충돌로 취급한다. strict는 최상위 request의 composition 값으로 정한다
(`ibl_v2_entry.py:160`). 앞선 G2의 명시된 이행 한계이며, 새 발견인 것처럼 세지 않는다.
하지만 새 상위 프로그램이 정책을 다시 켜지 않으면 보장이 약해지는 구조는 개선 대상이다.

### A5. D5 — 실패의 관찰과 원형 전파

`t:read`가 SOURCE_MISSING을 발생시킨다. 직접 호출을 catch하면 `$error.code`는
SOURCE_MISSING이다. 같은 호출을 each의 collect 모드로 값화한 다음 `unwrap($r[0])`을
catch하면 UNWRAP_ERR다. **원래 오류는 `$error.details.code`에 남아 있다. 정보 유실은 아니다.**

현재 Result는 is_ok/unwrap/error_of로 검사·관찰할 수 있다
(`common/expression_ops.py:230`). 그러나 unwrap은 실패를 원형 재전파하는 연산이 아니라
Err을 잘못 열었다는 새 오류를 만든다. catch는 `$error` Record를 제공하고
(`ibl_v2_runtime.py:654`), 언어에는 일부 오류만 처리하고 나머지 원형 Failure를 그대로
재전파하는 명시 경로가 없다. assert로 다시 실패시키면 ASSERTION_FAILED로 뜻이 달라진다.
함수 계약에도 정상 result/effects 외에 실패 대안/전파 조건의 요약은 없다.

큰 프로그램의 한 부분을 “실패를 모으는 부품”으로 바꾸면 호출자는 중첩된 details의 구조까지
다시 알아야 한다. error_of로 수동 분기하는 우회는 가능하지만, 재사용 가능한 선택적 복구와
원형 전파의 공통 계약을 대신하지 못한다. 함수가 던질 모든 외부 오류를 정적으로 예측하자는
것이 아니라, **알려진 실패와 미상 실패, 관찰과 전파를 구별하는 인터페이스**가 필요하다.

| 표 반환·열 관계의 분열 | 사용자 재현과 `core-table/2`/호환 어댑터·`row_flow_type`의 경계 | 각 op/옵션의 실제 반환·메타데이터·빈 입력, 새 설치와 활성 판본의 일치 |
| 콜백 행 타입 손실 | `ibl_v2_analysis.row_flow_type`가 `row.observed`가 아니면 콜백 인자를 Unknown으로 낮춤 | 닫힌 리터럴·선언·관측·혼합 행별 최초 실패 시험과 의도된 보수성 |
| 스크립트 계약 결손 | `ibl_dependencies.script_contract`는 등록 계약이 없으면 보수적 바깥 계약을 유지 | 보고된 40개/12개/28개의 최신 목록과 각 본문·의존성의 실제 효과 |
| 잘못된 `.items` 힌트 | compile/types 양쪽이 List 기대 + Record 실제만으로 같은 안내를 만듦 | 실제 items 유무·타입에 따른 공통 진단 인수 |
| 자료 보존 중단 | 런타임 로그의 `self:write path:~turn/idioms.json` 뒤 홈 해소 오류, 뒤의 thread_messages 차단 | 최초 호출의 전체 예외 경로·쓰기/보존 단계별 완료 상태 |

미관측 78개, 필드 타입 Unknown, 관용구 그래프 60개/깊이 3, 전후 6주행 통계는 사용자 보고의
측정값이며 이번에 재계수하지 않았다. 미관측은 계약 위반과 같지 않고, 선언은 실행 관측과 같지 않다.
현재 결합자 검사에서 결함이 없었다는 보고를 모든 어휘·설치·판본의 무결성으로 확대하지 않는다.

### 12.2 하나의 수리 단위와 불변 조건

수리 단위는 **생산자 계약 → 실제 인자 특수화 → 콜백 적용 → 결과 관계 → 함수 요약 → 저장/회수
→ 상위 재조합**이다. 표 op별 if 문, 스크립트 이름별 병렬 예외, HOME 상수 주입으로 막지 않는다.
기존 `callable_contract`, Type/requirements/CallAnalysis, effects/accesses, dependency 지문을 확장한다.
새 문법·어휘·별도 타입 검사기·상시 모델 호출·진단 전용 원장은 추가하지 않는다.

| 위반 경계 | 공통 계약 | 기존 주 소유자 | 보존해야 할 성질 |
| --- | --- | --- | --- |
| 표 입력에서 출력 열·값으로 | K2/K3/K9 | `ibl_v2_analysis`, `ibl_v2_types`, `ibl_v2_adapters`, data-ops 선언 | L1/L2/L4/L6: 값·열 관계·정보 출처와 미확정 보존 |
| 콜백 적용과 함수 특수화 | K2/K3/K4/K9 | Compiler의 `apply_callable`, requirements/CallAnalysis | L3/L4/L11: 같은 실제 인자의 관계, 효과 없는 분석, 유한 요약 |
| 등록 스크립트 정의에서 호출로 | K1/K4/K7/K9 | `ibl_dependencies`, `ibl_v2_access`, `script_ops`/`script_runtime`, registry | L1/L6/L7/L9: 정의 판본·효과·자원·수명·계승 보존 |
| 실행 뒤 자료 보존과 실패 전달 | K5/K6/K7/K9 | `research_context`, `research_capture`, 공통 경로 해소·기존 실행 영수증 | L8/L10/L11: 최초 실패·부분 효과·귀속·보존 상태를 구별 |

정보 출처는 검사 보장의 강도와 분리한다. 정적 닫힌 리터럴/검증된 값, 공급자 선언, 표본 관측,
미상 각각에 대해 필드 존재·선택성·값 타입·열린 행 여부를 보존한다. 이를 단일 `observed` 참/거짓으로
정적 허용/거절과 동일시하지 않는다. **관측을 보편 보장으로 승격하지 않고, 확정된 정보를 지우지도 않는다.**
기존 Type/계약 요약의 표현을 우선 사용하고 필요한 출처만 확장한다. 새 플래그를 별도 해석하는 병렬 체계를 만들지 않는다.

### 12.3 표 연산과 콜백: 같은 관계 전달 구조

1. data-ops의 `ibl_actions.yaml`과 기존 core-table 선언을 실제 handler/adapter 결과와 대조한다.
   `join/rename/union/groupby/reduce/dedup/chart/brief`를 이름만으로 같은 반환 종류로 취급하지 않는다.
   실제 결과를 행 변환, 집계 결과, 문서/시각화/효과로 분류하고 입력·결과·실패·메타데이터 계약을 적는다.
   결과 모양 감사와 열 관계 감사를 분리해, 열 정보 보완 때문에 불필요한 wire 변경을 만들지 않는다.
2. 행을 내놓는 연산에는 공통 행 관계 전달 규칙을 둔다. 기존 `analysis.flow`와 특수화 경로를 확장해
   보존/투영/추가/개명/결합/집계가 입력 타입과 리터럴 인자에서 출력 타입을 도출하게 한다.
   어휘 이름을 검사기에 열거하지 않고 선언이 선택한 유한 관계 연산을 해석한다.
   `dedup`은 행 관계 보존, `rename`은 이름 대응과 충돌, `union`은 대안·누락 가능성,
   `join`은 키/충돌 정책·결합 종류에 따른 누락/null 가능성, `groupby`는 by·agg의 실제 출력명을 다룬다.
   `reduce`는 실제 누산/결과 계약을 따르며 수치 집계 의미는 `common/value_semantics.py`와 일치시킨다.
3. 판본 2의 행 값 표면은 기존 native 어댑터의 List를 기준으로 정리한다. 다만 호환 봉투는
   **명시된 어댑터 경계에서만** 행을 꺼내며 임의 Record를 자동으로 목록으로 바꾸지 않는다.
   봉투의 업무 메타데이터는 버리지 않는다. 기존 evidence/sidecar에 속할 정보와 사용자 업무 값을
   먼저 구별하고, 업무 정보가 남아야 하는 결과는 Record+명시 items 관계를 유지한다.
   `chart/brief` 등 다른 종류의 산출을 List로 강제하지 않는다.
4. 이미 공개된 op의 결과 모양을 바꾸기 전 `.items`/인덱스 소비자, 저장 함수 의존 지문, Python·HTTP·MCP,
   앱 표시·문서·설치 번들을 조사한다. 기존 판본 경로는 기존 의미를 유지하거나 명시적인 재검사/이행을
   요구해야 한다. 옛 저장 함수·영수증을 새 반환형으로 조용히 재해석하지 않는다. 독자가 남아 있는
   호환 어댑터는 책임·은퇴 조건을 기록하고, 중복 실행 경로는 소비자 이행 후 제거한다.
5. 콜백은 동일 `apply_callable`에 입력 행 타입을 전달한다. 함수/관용구를 거친 리터럴 열 인자와
   반환 부품도 기존 기호 관계·부분 특수화로 연결한다. 현재의 blanket Unknown 하향을 없애되,
   열린/혼합/표본 행에는 조건부 필드와 runtime guard를 남긴다. `get`·존재 확인·분기 narrowing도 보존한다.
   닫힌 `{a:1}`의 `$r.b`는 직접 접근과 콜백 모두 동일하게 검사에서 거절하고, 유효한 `$r.a`는 통과한다.
   filter의 Bool, compute/select의 반환 관계, 고차 함수의 효과 제약을 같은 적용 경로에서 검사한다.
6. 특수화는 실제 리터럴·정적 기호만 사용한다. 동적 열 이름은 정확히 그 부분만 Unknown/열린 행으로
   남기고 알려진 열·효과·자원까지 없애지 않는다. 요약 캐시 키에는 입력 관계·정의/계약 판본·의존을
   포함한다. 기존 분석 예산을 유지하며 저장 시 도구/콜백/Python 본문을 실행해 타입을 알아내지 않는다.

List 기대 오류의 안내도 이 구조의 소비자다. `.items`가 실제로 List임을 계약으로 확인할 때만 그
투영을 안내한다. 효과/Unit/임의 Record에는 그런 힌트를 내지 않는다. compile/types의 중복 안내는
공통 타입 진단으로 모으고 교재와 함께 갱신한다.

### 12.4 등록 스크립트: 선언 채우기와 검증을 한 경로로

정본은 `data/scripts/registry.yaml`과 스크립트 본문이다. `script_contract`의 check/run 공통 특수화,
`script_dependency`의 지문, 실행기의 입력/출력 검증을 재사용한다. 외부 Python 전체의 효과를
정적으로 완전 추론할 수 있다고 가정하지 않는다.

- 전 항목을 최신 목록으로 감사해 본문·호출 의존·환경·권한·effect/access/결과·background/session
  상태를 구분한다. IBL/이미 검증된 하위 계약에서 도출 가능한 관계는 합성하고, 불투명 외부 코드는
  근거 있는 공급자 선언과 검수·제한된 실행 인수를 요구한다. 분석 불가는 명시 unknown으로 남긴다.
- `에피소드통계`, `폴더변화` 등 읽기 후보부터 구현·숨은 기록 쓰기·모델/자식 프로세스 호출을 확인한다.
  내부의 업무 쓰기와 시스템 실행 기록도 구별해 기존 효과 계약과 맞춘다. 이름·성공 이력만으로 pure/read를 붙이지 않는다.
  선언은 본문/의존 판본에 묶고 변경 뒤 낡은 효과 보장이 재사용되지 않게 한다.
- 효과 종류뿐 아니라 인자에 따른 자원 접근을 같은 K4 표현으로 낸다. R/R·입증된 독립 자원은 병렬
  허용, 미상 쓰기·같은 자원의 충돌은 기존 admission에서 거절한다. read라고 선언됐다는 이유로
  권한·수명·thread safety·단일 세션 제약을 생략하지 않는다. 미상 파일 스크립트의 기존 정책은 유지한다.
- foreground 값, background 접수증, session handle은 같은 결과형으로 위장하지 않는다.
  read 허용을 전역 캐시/자동 재사용 허용으로 확대하지 않고 기존 영수증·per_run·수명 조건을 따른다.
- 감사 산출은 등록부의 검증된 선언과 기존 시험이다. 별도 40개 예외 목록을 엔진에 만들지 않는다.
  잔여 unknown은 항목·이유·사용 제한을 명시한다. 40개 모두를 억지로 확정하거나 12개만 고치고
  전체 이행 완료라고 보고하지 않는다. 실행 표본만으로 모든 외부 효과 부재를 증명하지 않는다.

### 12.5 자료 보존: 최초 원인과 부분 실행을 먼저 확정

설계 중 읽기 조사에서 더 좁은 후보를 확인했다. `research_capture.capture`는 params의 path와
반환 artifact 경로에 `Path(...).expanduser()`를 직접 적용한다. 반면 `runtime_utils.expand_body_path`
는 `~turn`을 `script_workspace.expand`로 해소한다. 현재 환경에서 파일 쓰기 없는 최소 탐침은
`Path('~turn/idioms.json').expanduser()` → 기록과 같은 `RuntimeError: Could not determine home directory.`,
`Path('~/idioms.json').expanduser()` → 성공이었다. **HOME 누락은 확정 원인이 아니며, 경로 토큰의
일반 사용자 홈 해석이 유력 후보다.** 원 호출의 traceback까지 확보한 것은 아니므로 최종 원인 판정은 남겨 둔다.

런타임 로그(조사 당시 43748/43751행)는 ~turn 쓰기 요청과 이 오류를 연결하고, 43772/43775행의
thread_messages는 뒤의 보존 실패 차단이다. 로그는 순환하므로 구현 인수에서는 해당 요청의 신원과
예외 단계·재현 fixture를 기록한다. `research_context.observe`가 capture의 모든 예외에
`capture_failed`를 세우고 `before`가 이후 호출을 막으므로, 후속 차단 문구를 최초 원인으로 삼지 않는다.

구현 첫 단계의 조사·수리 순서:

1. 실행 task/turn·project/thread·epoch·활성 세대/구현 지문을 맞춰 첫 요청을 추적한다.
   HOME 등은 필요한 환경 키의 유무와 해소 결과만 확인하며 전체 환경/비밀값을 로그에 남기지 않는다.
   원문 보존, artifact 경로 해소, 첨부 보존 중 어디서 실패했는지와 이미 수행된 쓰기/DB 반영을 구별한다.
2. 실제 연구 capture를 임시 연구 저장소·실제 turn scope에서 호출하는 최소 회귀를 먼저 만든다.
   원문의 보존이 끝난 뒤 artifact 해소만 실패했는지, self:write 자체가 실패했는지 확인한다.
   파일 존재·내용 해시·기존 영수증으로 판정하고 실패 메시지 하나로 “라이브 무변경”이라 쓰지 않는다.
3. 확인된 우회 경로를 기존 단일 경로 해소점으로 연결한다. **해소는 권한 부여가 아니다.** 해소 후
   프로젝트/turn 소유권·허용 루트·symlink/traversal·수명·epoch를 기존 소유자에서 검사한다.
   project 밖의 turn artifact가 필요한 경우 기존 승인된 턴 산출물 계약과 보존 정책에 명시적으로
   연결한다. 허용 정책 없이 경로 범위를 넓히거나, 사라진 턴을 홈/정본 경로로 대체하지 않는다.
4. 최초 실패의 종류·단계·안전한 원인 참조·이미 발생한 효과/보존 영수증을 기존 Fault/실행 기록에
   유지한다. 보존 실패를 감추지 않으며 후속 차단은 그 원인을 가리킨다. 저장 공간/권한은 해당
   예외가 있을 때 안내하고, 모든 예외의 원인으로 단정하지 않는다.
5. 재시도는 원 업무 효과의 재실행과 자료 보존의 재시도를 구분한다. 쓰기가 이미 성공했으면
   이를 다시 실행하지 않고 기존 자료·동일 호출 신원으로 보존 복구 가능성을 판정한다. 실패 표식은
   복구 확인 전 지우지 않는다. 원인을 고친 뒤 허용된 재개/새 연구 턴에서만 질문 저장을 재시도한다.
6. 질문 `f545467ff51e4a4da1fccf0e72b873f8`은 최신 revision·현재 내용을 읽어 미반영 여부부터 확인한다.
   기록하려던 실제 내용을 복원할 수 있을 때 CAS로 갱신하고 다시 읽어 검증한다. 이미 반영됐거나
   원문이 없으면 중복 갱신/추정 문장을 저장하지 말고 남은 복구 필요를 보고한다.

이 수리는 표/콜백의 의미 변경과 별도 원인·커밋으로 처리할 수 있지만 K5/K6/K9와 동일 인수표로 연결한다.
HOME 강제 설정, ~/. 대신 절대경로 하드코딩, 보존 실패 후 계속 진행, 업무 쓰기 자동 재실행은 해법이 아니다.

### 12.6 반복 조합 인수와 반대 대조군

아래는 **실행할 시험**이며 현재 통과 기록이 아니다. 개별 op의 정상 예제만으로 완료하지 않는다.
책임 모듈의 기존 시험(`test_ibl_v2_compile_rows`, `test_ibl_v2_analysis`, `test_ibl_v2_types`,
`test_ibl_v2_adapters`, `test_ibl_dependencies`, `test_script_ops`, `test_ibl_v2_access`,
`test_ibl_v2_component`, 연구 library/runner/threads 시험)에 추가한다. 새 책임 시험이 필요하면
모듈 이름으로 만들며 이번 사건 전용 중복 검사기를 만들지 않는다.

| ID | 필수 입력·변환 | 독립 판정 기준 / 막아야 할 반례 | 연결 |
| --- | --- | --- | --- |
| E1 표 관계 | 각 행 op의 빈/단일/혼합 행, 리터럴/동적 열, join 충돌·누락, groupby agg | 실제 행·열·타입을 수작업 oracle과 대조. 확정 출력에 없는 열 sort는 검사 거절, 미상 입력은 guard와 실행 실패를 정직하게 유지 | K3/K9, L1/L4/L6 |
| E2 콜백 | 직접 `$x.b` ↔ filter/compute/select 콜백 ↔ builtin map/filter ↔ 저장 고차 함수 | `{a:1}`의 b는 동일 거절, a는 통과. 열린/표본/nullable/혼합 행과 get/분기 보호는 과잉 거절하지 않음. 잘못된 반환형·효과도 검사 | K2/K3/K4, L2/L4 |
| E3 특수화 | 열 인자를 literal→지역 함수→F1→F2→F3로 전달, 동적 열도 대조 | 확정 열 정보 보존, 동적 부분만 미확정. 캐시 켬/끔·인자 변경·다른 동일값/별칭의 계약 일치 | K1/K3/K9, L3/L4/L7 |
| E4 스크립트 | 실제 등록 임시 Python 프로세스, 순수/읽기/쓰기/불명, R/R·R/W·W/W·독립 자원 | 허용/거절과 잎 호출 수 대조. unknown/권한/세션 제약을 포장으로 없애지 않음. 본문/의존 변경 시 재검증·계승 거절 | K1/K4/K7, L1/L6/L7/L9 |
| E5 표면·호환 | List/Record{items}/효과 Record, 직접·저장 함수·HTTP/MCP·배포 설치 | 실제 결과와 계약·메타데이터 일치. effect에 가짜 items 힌트 없음. 옛 판본을 새 의미로 묵시 해석하지 않음 | K1/K3/K9, L10 |
| E6 첫 보존 실패 | turn scope 유/무·만료, HOME 유/무, 프로젝트/턴/외부 경로·symlink, 디스크/권한/DB/CAS 실패 주입 | 정상 경로 보존, 이탈 거절, 첫 오류와 후속 차단 구별. 원 쓰기·자료 보존의 부분 완료가 보이며 재개로 쓰기/자료를 중복 생성하지 않음 | K5/K6/K7/K9, L8/L9/L11 |

E1~E5의 핵심 정상/거절 사례를 하나의 공통 혼합 프로그램으로도 묶는다:
**자료 읽기 → 등록 스크립트 정규화 → 표 결합/집계 → 콜백 선택 → 결과 검증**을 F1로 저장하고,
F2에서 서로 다른 인자·원천으로 재조합, F3에서 F2를 반복·병렬·실패 대체 경로로 조합하여 저장/회수한다.
원 업무 이름을 바꾼 둘 이상의 영역과 아직 저장되지 않은 새 입력을 포함한다. 같은 순서·범위·정책을
유지한 함수 추출/안전한 재묶음도 비교한다. `>>`, `&`, `??`, each의 정리·단락·수명 경계를 바꾸는
변환에 무조건 동등성을 요구하지 않는다.

직접/1/3층의 혼합 경계는 필수다. 기존 생성기를 재사용해 6/10/14/30층에서 관계·출처·효과·실패·완료
의무가 유지되고 분석량이 제한됨도 확인한다. leaf/계약 oracle은 구현의 요약 함수를 그대로 호출해서
만들지 않는다. 검사/describe/저장에서는 잎 0회, 실행에서는 필요한 횟수만 호출하며 빈 반복도 의무를
허위 완료시키지 않는다. 순수 후미 수정→repair→재수정에서 효과 비반복과 바뀐 의존의 거절을 확인한다.
유한 깊이 통과를 무한 닫힘 증명으로 부르지 않는다.

### 12.7 구현 순서·완료 판정·다음 세션 인계

| 단계 | 작업 | 다음 단계로 넘어갈 근거 |
| --- | --- | --- |
| P0 판본/첫 실패 | 동시 작업 재확인, HEAD/dirty diff/활성 세대 지문 분리, 원 요청·첫 capture 실패 재현 | 코드/활성 불일치 여부, 실패 단계·이미 발생한 효과, 새 설치 fixture 기준선 기록 |
| P1 공통 관계 | 출처/열린 행/필드 타입 규칙 확정, 공통 행 전달·콜백 적용·진단 수리 | E1/E2 수정 전 실패와 수정 후 통과, 정상/미상 대조와 분석 잎 0회 |
| P2 생산자 이행 | 표 선언·어댑터·소비자, 스크립트 계약 감사·지문·자원 연결 | E3/E4/E5, 실제 결과 모양·기존 독자·잔여 unknown/호환 경로 목록 |
| P3 보존 복구 | P0에서 확정한 경로/실패 전달 수리, 질문 저장 상태 확인·복구 | E6, 최초 원인 증거와 부작용 비반복·보존 상태·CAS 재조회 |
| P4 반복 인수 | F1→F2→F3·깊이·계승·다른 영역, 실제 소비 표면·신규 설치 | E1~E6 및 L1~L11별 실행 node ID/결과/미검증, 계약과 실제 값의 대조 |
| P5 최종 계획 대조 | 변경의 소유자·제거한 중복·남은 호환/unknown과 테스트 결과 기록 | 구현 항목별 K/L 대응, 새 회귀·전수·관련 system·빌드 종료 코드, 정본 main 선택 커밋 |

P1/P2와 P3는 원인별로 구분하되 최종 P4/P5에서 함께 대조한다. 구현은 정본 main에서 수행하고,
타 세션 변경은 pathspec 커밋으로 제외한다. runtime 기본 예산 변경은 이 계획의 성과로 세지 않는다.

검증은 [REGRESSION_TESTING.md](REGRESSION_TESTING.md)를 따른다. 개발 중 선택기로 전이 소비자를
실행하고, 공통 타입/검사/효과 허브 변경 후 비system 전수와 `test_python_libraries.py`를 실행한다.
어휘/설치 이행에는 vocabulary archive/bundle, runtime/repair 변경에는 지정 긴문장 재생,
공통 저장소/동시성 변경에는 관련 restart_process 묶음을 추가한다. 각 변경에 해당하는 어휘 빌드·
`--check`, Android 몸 번들·층·1500줄·경로 해소 관문을 통과시킨다. frontend를 바꾼 경우 tsc도 실행한다.
검사 중 코드가 바뀌거나 작업트리 감시가 종료 1을 내면 해당 실행을 최종 통과로 세지 않는다.

최종 보고는 계약 인수와 실사용 효과를 분리한다. 새 설치·미관측 op 전부·과거 실패 109건 분류·
활성 런타임 전수 검증은 실제 수행한 범위만 적는다. 수리 효과를 6주행의 비율이나 관용구 수로 추정하지 않는다.
정확성·실패 은폐·부작용 횟수는 인수로 확인하고, 시간/전체 토큰은 비교 조건을 맞춘 경우에만 보고한다.
이 문서 작성 단계에서는 코드·등록부·연구 질문을 변경하지 않았고 실행 인수도 수행하지 않았다.
