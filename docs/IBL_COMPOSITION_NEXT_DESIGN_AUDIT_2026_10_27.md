업무 비용 실측을 개발의 선행 조건으로 두지 않으며, 측정하지 않은 시간·토큰 절감을 주장하지 않는다.

## 3. D1 — 변수 이름을 넘는 관계 계약이 필요하다

### 3.1 관측

```ibl
[def:f]($x){return abs($x)}
[def:g]($x){return abs($x.n)}
```

첫 정의의 requirements에는 `x:Number`가 남는다. 둘째는 guard가 생기지만 requirements는
빈 Record다. `$x.n`에서 원래 매개변수와 부분 경로의 관계가 끊어진다. 다음 정의도 독립
검사에 문제가 없다고 나오고 **실제 임시 함수 등록에 성공**한다.

```ibl
[def:f]($x){$a=abs($x.n);return not $x.n}
```

같은 필드가 무조건 Number와 Bool이어야 한다. IBL은 Bool을 Number로 취급하지 않는다.
구체적인 잘못된 인자를 적용하면 검사/실행 경계가 거절할 수 있지만, 그것이 불가능한 독립
정의를 저장 전에 구별하는 계약을 대신하지는 않는다.

역방향도 있다. 아래 첫 정의는 독립 검사에 통과하고 두 번째는 `PURE_EXPRESSION`으로 거절된다.
두 번째에 실제 순수 콜백을 주어 함께 컴파일하면 값 1을 정상 반환한다. 중첩 명시 콜백 타입을
직접 적으면 독립 검사도 통과한다. 즉 실행 불가능한 함수가 아니라 **추론·독립 저장의 경계**다.

```ibl
[def:f]($p){[if:$p(1)]{return 1}[else]{return 0}}
[def:g]($cfg){[if:$cfg.p(1)]{return 1}[else]{return 0}}
```

같은 끊김은 자원 관계에도 나타난다. `[t:write]{key:$key}`를 감싼 함수의 접근 요약에는 입력
관계가 있지만, `key:$cfg.key`로 묶으면 relations가 비어 있다. 이번 탐침은 관계 소실을 확인한
것이며, 선언 자원의 구체 실행 충돌 검사가 모두 무력화된다는 주장은 아니다.

콜백 결과도 값 하나의 신원이 없다.

```ibl
[def:f]($p){$x=$p(1);$a=abs($x);return not $x}
```

requirements에 결과의 Number/Bool 요구가 모두 기록되지만 독립 검사는 거절하지 않는다.
서로 다른 콜백 적용의 반환 타입을 함부로 합치지 않으려고 모든 result 요구의 교집합 검사를
생략한 구조가, **한 번 계산해 같은 `$x`로 보관한 결과**의 모순까지 구별하지 못한다.

### 3.2 공통 원인

- `ibl_v2_analysis.py:351`의 `access_type`은 Unknown의 필드/인덱스 선택 뒤 일반 UNKNOWN을 반환한다.
- `ibl_v2_requirements.py:14`의 origin은 `(parameter|application, sid, name)`만 식별한다.
  `application`은 적용 위치/인자를 결과 신원에 넣지 않는다(:36).
- `finish`는 result 요구를 모두 모순 검사에서 제외한다(:253).
- 조건 정보도 현재는 `conditional:bool`이다. 어떤 입력 조건 아래의 요구인지 독립 계약만으로
  재대입할 수 있는 유한 조건식이 아니다. 이 사실은 코드로 확인했으며 별도 조건식 반례는 세지 않았다.

### 3.3 수리 설계

현재 Type/CallAnalysis/requirements를 확장해 **유한 기호 관계**를 한 곳에서 소유한다.
새 업무 전용 타입 검사기를 추가하지 않는다.

- 입력 신원, 고정 필드/인덱스의 투영 경로, 각 적용의 결과 신원, 값 별칭을 표현한다.
  바인딩으로 같은 값이 된 경우와 같은 함수를 다른 인자로 다시 적용한 경우를 구분한다.
- Record/List/Result 선택·get·인자 대입·반환·캐시 재생에서 이 관계를 보존한다.
  동적 키는 가능한 키 집합/미확정으로 남기고 임의 경로를 추측하지 않는다.
- 요구는 `(기호 값, 조건, 타입/효과 요구)`에 붙인다. 한 기호 값에 동시에 성립하는 요구만
  교집합 검사한다. 분기·복구의 유한 조건을 대입하고, 분석 한도를 넘으면 원인 있는 미확정으로 남긴다.
- 접근 요약의 대상 관계도 같은 기호 경로를 사용한다. 자원 이름의 별도 해석기를 만들지 않는다.
- 명시 계약은 추론의 보완·공개 인터페이스이며 우회로가 아니다. 추론과 명시 검사가 같은 적용
  엔진·효과 판정·저장 관문을 쓰게 한다.

인수: Record/중첩 Record/List/Result/반환 콜백 포장 전후의 requirements와 허용/거절이 대응해야
한다. 같은 결과의 모순은 거절하고, 서로 다른 호출 결과나 배타 분기는 과잉 거절하지 않아야 한다.
캐시 켬/끔, 깊이 6/10/14/30 공유 DAG, 실제 독립 등록·describe·구체 호출을 함께 검사한다.

## 4. D2 — 완료된 부품의 완료 계약을 다시 조합할 수 있어야 한다

### 4.1 관측

```ibl
[def:fetch](){return [t:down]{} ?? [t:good]{}}
```

`t:down`은 실패하고 `t:good`은 완전한 2와 로컬 관측을 만든다. 저장 라이브러리 정의처럼
이 함수를 불러, 요청에 `predicate:$value==2`와 원천 `t:good`을 선언하면 satisfied와 관측
확정이 된다. 같은 함수에 최상위 completion을 주지 않으면 실행/값은 성공하지만
`source_complete:false`, completion 없음, 관측은 not_committed다.

후자는 계약이 없으므로 보수적으로 처리한 올바른 현행 동작이다. 공백은 **함수 제작자가 이미
정한 완료 조건을 함수 판본과 함께 선언하고 호출마다 재사용할 자리**가 없다는 점이다.
호출자는 내부 대체 원천 이름과 대상, 출력 포장 경로를 다시 알아야 한다.

현재 `function_contracts`에는 requirements/result/effects/accesses 등이 있지만 completion은
없다(`ibl_v2_compile.py:366`). 완료의 소유자는 요청과 Runtime
(`ibl_v2_entry.py:54`, `ibl_v2_completion.py:9`)이다. `function_library.register`(:83)의 정식
등록 계약에도 완료 선언은 없다. 임의 provenance 필드에 적는 것은 실행 계약을 강제하지 않는다.

또한 요청은 의무 1~32개와 고정 scope 경로를 받는다. 33개의 서로 다른 의무 선언은 거절된다.
이 제한 자체를 없애자는 뜻은 아니다. 동적 each의 각 호출에 같은 완료 계약을 대입하려면
최상위에서 의무를 펼치거나 하나의 전체 판정으로 바꿔야 하며, **템플릿→호출별 의무** 모델이 없다.
직전 수리의 검증된 결과 참조 인증 이식은 유지되지만, 새 함수 호출이 자신의 계약을 갖는 것과는 다르다.

### 4.2 수리 설계

- 함수 정의의 명시 선언에 완료 계약 템플릿을 두고 compiler가 검사한다. 원문 선언을 정본으로
  삼고, 저장된 contract/describe/회상은 그 판본의 파생 뷰로 만든다. 독립적인 두 수정 경로를 만들지 않는다.
- 입력·반환 부분과 원천/대상 관계를 D1의 기호식으로 표현한다. 호출 시 실제 인자, 함수 판본,
  호출 인스턴스에 대입한다. `id` 문자열이 같은 다른 호출의 인증을 공유하지 않는다.
- 런타임의 값/근거 sidecar에 **그 호출의 의무와 판정**을 보존한다. 상위 함수는 하위 보장을
  요구하거나 강한 새 의무를 추가할 수 있지만, 필수 의무를 무시하는 포장으로 약화할 수 없다.
- source_complete 감사 축은 그대로 둔다. 반환값 선택·폐기, 제어/구조 의존, 실패한 mutation의
  전역 위험도 기존 소유자가 판단한다. 원천 이름이나 같은 값만으로 인증하지 않는다.
- each는 템플릿을 반복 인스턴스별로 대입한다. 필수/선택·부분 성공 집계와 관측 확정은 각
  인스턴스에 묶는다. 전개 수·평가 예산은 제한하고, 봉투는 요약/참조로 전달한다.
- 기존 요청 completion은 계속 지원한다. 부품 의무를 연결·강화하는 상위 계약으로 합성한다.
  오래된 함수에는 보장이 없는 것으로 표시하고, 과거 성공 횟수로 새 계약을 자동 발급하지 않는다.

인수: 지역→저장→회수→상위 함수→각 반복→Record/List/Result→검증된 결과 참조에서 동일한
의무를 다시 작성하지 않아도 보존돼야 한다. 부분 필드의 이동, 같은 값의 다른 출처, 일부 행의
실패, 빈 목록, 상수 콜백, 취소·예산 소진, 관측 확정의 부분 성공까지 대조한다.

## 5. D3 — 수정 재개가 함수 추출과 지역 바인딩에 닫혀 있지 않다

### 5.1 관측

외부 쓰기 한 번 뒤 `n:0`으로 실패시킨 세 프로그램의 마지막 계산을 고쳤다.

| 수정 위치 | 원래 계산 → 수정 계산 | check의 수정 계승 판단 |
| --- | --- | --- |
| 마지막 직접 식 | `return $sent/$n` → `return $sent/($n+1)` | ready; 실제 재개 성공, 누적 쓰기 1회 |
| 순수 지역 함수 호출 | `return [fn:calc]{x:$sent,d:$n}` → `d:$n+1` | REPAIR_UNSUPPORTED, 쓰기 1회 유지 |
| 순수 지역 바인딩 | `$v=$sent/$n;return $v` → `$v=$sent/($n+1);return $v` | REPAIR_UNSUPPORTED, 쓰기 1회 유지 |

세 경우는 같은 입력·원래 쓰기·계산 의도를 가지며 calc 본문은 `$x/$d`다. 거절은 안전하고
쓰기 재실행도 하지 않았다. 그러나 **부품화하면 부분 수정 능력이 약해진다.** 이는 큰 조합을
다시 더 큰 부품으로 키우려는 목적과 직접 충돌하는 지원 한계다.

`ibl_v2_repair.py:39`는 순수성을 compiler 효과 요약 대신 구문 허용 목록으로 판단한다.
`propose`(:95)는 마지막 return 이전 AST가 동일해야 하며, 전역 부품/문맥 지문도 동일해야 한다.
이미 고친 마지막 식을 지원하는 현재 기능을 부정하는 것이 아니라 그 밖의 확대가 필요하다.

### 5.2 수리 설계와 단계

1. **의미상 순수 후미**: compiler의 효과/접근/값 의존 요약을 사용한다. 순수 함수 호출과
   지역 바인딩으로 추출한 계산도 같은 의존 부분 그래프로 취급한다. 구문별 두 번째 순수성
   정의를 없앤다. 실행 불확실한 콜백은 순수하다고 가정하지 않는다.
2. **부품 단위 수정 계획**: 기존 Journal의 호출 영수증과 함수 불변 판본에 의존 그래프를 연결한다.
   변경의 영향을 받지 않는 완료 효과, 새 계산, 확인/명시 재실행 필요를 분류한다. 단순히 전체
   함수 본문 지문이 달라졌다는 이유로 독립 완료 효과를 모두 버리지 않는다.
3. **논리 작업 신원**: 실행 계보·부품 인스턴스·반복 항목 신원을 사용한다. 명확한 구조 대응만
   자동 인정하고, 재정렬/중복 항목에는 명시 신원 또는 안전한 거절을 요구한다. 같은 액션/인자
   해시를 같은 의도로 취급하지 않는다.
4. **현재 권한과 CAS**: 입력/캡처·소스 관측·계약·어댑터 구현·실제 대상·권한을 효과별로 대조한다.
   주체/소유 범위, 언어 의미, 승인 검사는 전체 실행에서도 유지한다. 새 효과는 현재 승인/예산을
   사용하고, 동시 계획·응답 유실·불명 효과는 기존 Journal/CAS 소유자가 차단한다.
5. **완료로 연결**: D2의 인스턴스 의무에 계승 근거와 새 근거를 연결한다. 과거 실행 완료와
   현재 외부 상태의 유효성을 구분한다. 후자가 필요하면 검증 읽기/버전 조건을 요구한다.

첫 단계의 완료 조건은 표의 세 형태가 동일하게 수리되는 것이다. 이후 독립 가지의 순수 부품
교체를 지원하고, 반복 재정렬은 명시 신원 인수가 통과하는 범위만 확장한다. 기존 실행에서
해당 증거를 기록하지 않았다면 자동 계승하지 않는다. 임의 편집 동등성, 효과 자동 롤백,
보편적 exactly-once는 목표가 아니다.

## 6. D4 — 보장 없는 병렬 실행이 기본 정책으로 남는다

### 6.1 관측

```ibl
[t:write]{key:"shared"} & [t:write]{key:"shared"}
```

합성 어댑터는 write_external을 선언하지만 자원 선언은 없게 했다. 내부의 같은 공유 자원에
대한 쓰기를 Barrier로 맞췄을 때 기본 Runtime은 성공했고 **최대 동시 쓰기 수 2**였다.
같은 요청을 strict composition으로 실행하면 두 쓰기 모두 시작 전에 거절된다.
`write_resources:{record:key}` 선언을 넣으면 기본 검사에서도 충돌로 거절된다.

권한 우회나 모든 실 어휘의 데이터 손상을 입증한 실험이 아니다. 선언 없는 어댑터를 다른
부품으로 치환했을 때 **독립성을 모른다는 정보가 기본 병렬 실행을 막지 않는다**는 사실이다.

`ibl_v2_access.py:54`의 conflicts는 미해소 자원을 strict 또는 양쪽 선언이 있는 경우에만
실행 충돌로 취급한다. strict는 최상위 request의 composition 값으로 정한다
(`ibl_v2_entry.py:160`). 앞선 G2의 명시된 이행 한계이며, 새 발견인 것처럼 세지 않는다.
하지만 새 상위 프로그램이 정책을 다시 켜지 않으면 보장이 약해지는 구조는 개선 대상이다.

### 6.2 수리 설계

- 접근 요약에서 `없음`, `알려진 접근`, `미해소 대상`, `미선언 효과`를 구별한다. 허용된 효과
  집합과 자원 독립성의 증명은 서로 다른 계약이다. 선언이 없다는 것을 비충돌로 읽지 않는다.
- 함수/패키지의 요구하는 조합 정책을 계약으로 전달한다. 상위 호출이 하위 요구를 약화할 수 없고,
  검사 결과에는 보장한 범위와 미해결 의무가 표시된다.
- 새 보장 계약에서 unknown write가 있는 병렬 구간은 기본적으로 거절하거나 호출자가 명시한
  순차 구간으로 실행한다. 조용히 순차화해 의미와 지연을 바꾸지 않는다. R/R과 확인된 독립
  자원의 동시성은 보존한다.
- 기존 read_resources/write_resources 선언·실제 대상 해소기를 확장한다. D1의 경로/인자
  관계를 재사용하며, 동적 대상은 효과 직전뿐 아니라 해당 병렬 구간 전체의 접근 범위와 대조한다.
- 이행은 어댑터별 선언 충족도를 빌드/describe에서 드러내고, 기존 프로그램의 호환 정책을
  명시하는 방식으로 한다. 옛 정책을 사용하는 실행에 새 독립성 보장을 표시하지 않는다.
  전 어휘를 막연히 pure/독립으로 선언해 검사를 통과시키지 않는다.
- 보장 범위를 요청 안의 병렬 가지, 같은 프로세스의 다른 요청, 외부 프로세스/서버로 구분한다.
  이번 반례는 첫 범위다. 현재 admission은 같은 실행 안의 비교이며, 그 통과를 요청 간 잠금이나
  분산 원자성으로 확대 해석하지 않는다. 필요 시 요청 간 예약은 별도 수명 설계/인수로 확대한다.

인수: 선언/미선언 혼합, R/R·R/W·W/W, 중첩 함수·각 반복·동적 경로·alias/inode,
read→compute→write 구간, 취소/승인 대기/예산 종료, 독립 자원 동시성, 정책이 다른 부품의
교체를 검사한다. 기존 엄격 검사 통과만으로 기본 정책 이행이 끝났다고 하지 않는다.

## 7. D5 — 실패도 부품의 결과 경계에서 보존·재전파할 수 있어야 한다

### 7.1 관측과 현행 의미

`t:read`가 SOURCE_MISSING을 발생시킨다. 직접 호출을 catch하면 `$error.code`는
SOURCE_MISSING이다. 같은 호출을 each의 collect 모드로 값화한 다음 `unwrap($r[0])`을
catch하면 UNWRAP_ERR다. **원래 오류는 `$error.details.code`에 남아 있다. 정보 유실은 아니다.**

현재 Result는 is_ok/unwrap/error_of로 검사·관찰할 수 있다
(`common/expression_ops.py:230`). 그러나 unwrap은 실패를 원형 재전파하는 연산이 아니라
Err을 잘못 열었다는 새 오류를 만든다. catch는 `$error` Record를 제공하고
(`ibl_v2_runtime.py:654`), 언어에는 일부 오류만 처리하고 나머지 원형 Failure를 그대로
재전파하는 명시 경로가 없다. assert로 다시 실패시키면 ASSERTION_FAILED로 뜻이 달라진다.
함수 계약에도 정상 result/effects 외에 실패 대안/전파 조건의 요약은 없다.

큰 프로그램의 한 부분을 “실패를 모으는 부품”으로 바꾸면 호출자는 중첩된 details의 구조까지
다시 알아야 한다. error_of로 수동 분기하는 우회는 가능하지만, 재사용 가능한 선택적 복구와
원형 전파의 공통 계약을 대신하지 못한다. 함수가 던질 모든 외부 오류를 정적으로 예측하자는
것이 아니라, **알려진 실패와 미상 실패, 관찰과 전파를 구별하는 인터페이스**가 필요하다.

### 7.2 수리 설계

- 기존 Fault/Result/근거 그래프에서 하나의 실패 신원을 소유한다. 원인·kind/code·partial·
  발생 위치·효과 불명·근거·재시도 조건을 보존한다. 포장 횟수로 소비자의 분기 깊이가 늘지 않게 한다.
- 명시적인 실패 재전파/선택적 복구 경로를 마련한다. 기존 unwrap(Err)의 UNWRAP_ERR는
  호환성을 위해 유지한다. 최종 표기는 언어 개정 단계에서 기존 문법/값 기능의 최소 확장으로 정하고,
  오류 종류별 새 어휘를 늘리지 않는다.
- 재전파 권한은 런타임이 만든 실패/검증된 Result 계보에 묶는다. 업무 JSON의 `code`·`success`
  필드가 실행 오류나 인증 근거를 만들지 못하게 한다. 취소·권한·예산·suspended·protocol의
  기존 비복구 경계가 collect/catch/저장·참조 포장으로 약해지면 안 된다.
- 함수의 failures 요약은 알려진 대안 + open/unknown을 구별한다. 선언은 발생 가능한 모든
  세상 오류의 완전한 열거가 아니다. 실제 Fault가 최종 사실이며 알려지지 않은 것은 그대로 전파한다.
- D2의 완료 판정은 처리된 실패 이력과 현재 산출물 실패를 구분한다. D3의 복구 판단은 이
  실패 신원·효과 불명 상태를 사용해 “다시 계산”과 “다시 실행하면 안 되는 효과”를 분리한다.

인수: 직접 호출→함수→Result collect→Record/List→저장/회수 뒤 선택적 복구/전파에서
원래 실패를 식별할 수 있어야 한다. 이중 포장, partial, finally의 2차 실패, 병렬 여러 실패,
취소·권한·예산·효과 불명은 각기 다른 대조군으로 검사한다. 기존 unwrap 호출자의 오류 코드는 유지한다.

## 8. 목표 구조와 구현 순서

새 워크플로 엔진이나 독립 계약 저장소를 만드는 계획이 아니다. 기존 소유자를 다음과 같이 잇는다.

| 공통 책임 | 기존 소유자 | 바꿀 관계 |
| --- | --- | --- |
| 기호 입력/결과·조건·효과 요구 | Type, analysis/access_type, requirements, CallAnalysis | 변수 이름 → 유한 경로/적용 결과/조건의 그래프 |
| 부품 판본·검사·발견 | function_library/store, compile function_contracts, describe/회상 | 값 타입만이 아닌 요구·완료·실패·정책까지 같은 판본으로 |
| 값/실패·근거 전달 | Binding, Fault/Result, Runtime, value wire/result refs | 값과 그 인스턴스의 의무·실패 계보를 함께 보존 |
| 접근 조합 | ibl_v2_access, resource_values/call_resources, admission | 미선언을 미확정으로 전달하고 보장 정책을 하위에서 상위로 합성 |
| 수정·관측 확정 | 기존 Journal/repair, execution_commit | AST 후미 → 증거가 있는 의존 부분 그래프; 의무별 확정 |
| 외부 소비 | HTTP/MCP, 감독, 앱/조종실, PC/Android | 한정 보장·미확정·실패·완료를 같은 계약으로 읽기 |

구현 순서는 의존 관계로 정한다.

1. **D1 관계 표현과 D4 정책 모델 확정.** 현행 반례를 책임 모듈의 회귀로 옮기고 기호 값,
   조건, 미해소 접근을 같은 요약으로 표현한다. 선언/캐시/저장/describe가 일치해야 다음 단계로 간다.
2. **D4 이행과 D5 실패 경계.** 보장 없는 병렬을 표시·격리하고 typed failure의 관찰/전파를
   정의한다. Fault/Result를 이원화하지 않는다. 언어 변경은 ibl.md와 코어의 표준 계약을 함께 개정한다.
3. **D2 함수 완료 템플릿과 인스턴스.** 정의·호출·반환·반복·저장·참조·관측 확정·소비자를
   한 번에 연결한다. 최상위 요청만 필드를 늘리는 중간 상태를 완료로 세지 않는다.
4. **D3 증명 가능한 부분 수정.** 우선 함수/지역 바인딩으로 추출한 순수 후미, 다음으로 독립
   부품 교체. 효과의 신원 대응·현재 권한·CAS·완료 근거를 모두 확인한 범위만 넓힌다.
5. **변환 인수·이행 문서·정본 반영.** 공개 언어/요청 계약, 저장 판본, 가이드/오류 도움말,
   파생물, 소비자, 회귀를 함께 대조한다. 예전 기록에 새 보장을 소급해 만들지 않는다.

이 계획은 기존 [조합 설계 수리계획](IBL_COMPOSITION_DESIGN_GAPS_REPAIR_PLAN_2026_10_27.md)의
G1/G2/G3/G4를 폐기하지 않는다. D1은 G1의 관계 모델, D2는 G4의 모듈 소유권,
D3는 G3의 확대, D4는 G2의 기본 보장/이행을 구체화하고 D5로 실패 합성의 경계를 보충한다.

서로 이름만 바꾼 동일 프로그램을 두 과제로 세지 않는다. 후속 구현에는 다음 두 합성 업무를
실제 다른 데이터 흐름과 실패 위치로 작성해 전체 고리를 검증한다. 엔진은 그 업무 이름을 모른다.

- **자료→검사→발행**: 판본 있는 여러 자료, 필수 표와 선택 주석, 수집/정규화 콜백 교체,
  행별 완료 계약, 발행 뒤 순수 렌더 부품 실패와 수정. 부분 확정과 발행 비반복을 확인한다.
- **상태→판정→조작→재관측**: 상태 자료, 조건 판정 부품, 비동기 접수증/유한 대기와 실제
  재관측을 구분한다. 확인 부품만 수정할 때 명령을 재발송하지 않고, 효과 불명은 자동 성공/재시도로
  바꾸지 않는지 확인한다. 실제 장치 없이 합성 어댑터로 계약을 먼저 검증한다.

검증은 [회귀 규약](REGRESSION_TESTING.md)에 따라 관련 모듈→비system 전수→관련 system을
실행한다. frontend/문법/어휘/배포 경계 변경에는 tsc·파생 빌드·몸 번들·층/크기 검사도 붙인다.
수리 뒤 이 문서의 D1~D5와 위 변환 행렬을 다시 대조하고, 미지원 항목과 시험하지 않은 항목을 분리한다.
실제 에이전트의 작성 비용·완료 시간·전체 토큰 개선은 별도 계측하며, 유한 인수로 무결함을 선언하지 않는다.
