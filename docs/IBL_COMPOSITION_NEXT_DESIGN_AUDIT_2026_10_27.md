## 1. 다시 정한 목적과 설계 판정

**작은 능력으로 큰 능력을 만들고, 그 큰 능력을 다시 하나의 부품으로 축적해,
이미 쌓은 능력 덕분에 새로운 큰 일을 더 쉽게 구성·변경·완료할 수 있어야 한다.**

따라서 핵심 성과는 오류 수나 관용구 수의 감소·증가가 아니다. 작성자가 하위 구현과 예외를
다시 배워야 하는 양이 줄고, 새 요구를 기존 능력의 의미 있는 조합으로 표현할 수 있어야 한다.
검사·실행·복구가 그 추상화를 깨뜨리지 않아야 하며 결과 품질, 완료 시간, 전체 토큰은 별도로 관측한다.
모든 조합의 실행량이 줄어든다고 약속하지 않는다. 실제 읽기·모델 호출·외부 작업 비용은 남는다.

**판정: 현재 IBL의 함수·값·제어 흐름과 실행 근거 기반은 이 목적에 적합하다.
그러나 현재의 공통 계약은 능력 축적의 중심 추상화로 충분히 완성돼 있지 않다.
생산자별 분석을 모아 정규화하는 구조를 넘어, 부품의 의미를 독립적으로 적용할 수 있는
인터페이스가 검사·합성·저장·회수의 기준이 되도록 핵심 경계를 재설계한다.**

이것은 기존 설계를 유지한 채 선언을 더 채우는 계획도, 모든 코드를 폐기하는 계획도 아니다.
보존할 대상은 이미 성립한 언어 의미와 실행 보장이다. 그것을 구현하는 현재 클래스·파일·분석 경로는
교체할 수 있다. 새 구현이 같은 판단을 두 번 하게 만들면, 공통 구조라는 이름을 붙여도 채택하지 않는다.

## 2. 현재 설계의 적합성과 구조적 한계

현재 IBL에는 명시적인 함수와 렉시컬 값, 조합·제어 흐름, 불변 함수 판본, 검사와 실행의 연결,
효과·권한 경계, 실행 영수증과 수정·재개가 있다. 처음부터 모든 것을 만드는 상황이 아니다.
이 기반은 능력을 쌓는 데 필요한 자산이며, 이번 재검토에서 이를 버려야 할 근거는 찾지 못했다.

문제는 부품의 외부 의미가 어디에서 결정되는가이다. 소스 조사에서 다음 경계를 확인했다.

| 현재 코드의 사실 | 설계상 의미 |
| --- | --- |
| `ibl_v2_compile.compile_program`은 타입·효과·preflight 분석 뒤 `compiled_contracts`로 `plan.components`를 만든다. 이 결과는 보고·저장·완료 실행에도 쓰인다. | 공통 계약이 실제 기능을 갖고 있지만, 값·효과 합성 전체를 결정하는 단일 의미 기반은 아니다. |
| `ibl_v2_component.normalize`는 타입·requirements·accesses·adapter 등의 결과를 같은 형식으로 모은다. | 같은 형식의 계약을 보여 주는 것과 같은 규칙으로 계약을 계산하는 것은 아직 다르다. |
| `CallAnalysis.summary`는 컴파일 내부에서 실제 추상 인자별 본문 분석을 캐시한다. `function_library.definitions`는 저장 본문을 공급하고 `ibl_v2_store._describe`는 다시 컴파일한다. | 분석 중복을 줄인 성과는 있지만, 독립적으로 검증·저장한 의미 인터페이스를 연결하는 모듈 경계가 주 경로는 아니다. |
| 표의 `row_flow_type`, builtin 분석, 어댑터, 관측 필드가 각각 관계 전달에 관여한다. 콜백 전달에는 `row.observed`에 따른 Unknown 하향이 있다. | 생산자와 전달 경로에 따라 같은 정보가 다른 강도로 취급될 여지가 남아 있다. |
| 등록 스크립트는 `script_contract`로 특수화되지만 계약이 없는 경우 보수적 바깥 계약으로 남는다. | 외부 구현이 공통 인터페이스를 제공하는 입구는 있다. 선언의 충실도·판본 검증과 일반 부품 합성을 연결하는 이행은 덜 끝났다. |

여러 분석 모듈이 있다는 사실 자체가 잘못은 아니다. 타입·효과·권한은 질문이 다르다.
문제는 같은 입력·결과·호출 관계를 서로 다른 의미로 다시 해석하는 것이다.
재설계는 모든 코드를 하나의 거대한 검사기로 합치지 않고, **하나의 의미 표현과 적용 규칙을
여러 분석·실행 소비자가 공유하는 구조**를 만든다.

본문 재분석 자체도 나쁜 설계의 증거는 아니다. 인자별 특수화에 본문을 이용하는 것은 합리적일 수 있다.
사용자에게 본문을 숨기는 일과 컴파일러가 본문을 읽지 않는 일은 다르다. 이번 재설계는 소스 읽기 횟수를
줄이기 위해 시작하는 것이 아니다. 하위 구현의 분석 방식에 따라 상위 계약이 달라지거나, 같은 의미를
각 소비자가 재구성해야 하는 의존을 끊기 위해 독립 인터페이스를 채택한다.

현재 관용구를 호출 그래프의 한 노드로 저장할 수 있다는 점도 유지한다.
다만 이름과 본문이 쌓이는 것만으로 작성자의 추상화 부담이 줄어들지는 않는다.
호출자가 필요한 입력·반환·효과·완료 조건을 짧은 인터페이스로 이해하고, 내부 구현을
보지 않은 상태에서도 다음 능력에 연결할 수 있어야 축적이 성립한다.

## 3. 선택한 방향과 선택하지 않은 방향

어휘·콜백·스크립트에 빠진 선언을 각각 채우는 방법은 즉각적인 실패를 줄일 수 있다.
하지만 서로 다른 의미 판단을 남긴다면 다음 생산자나 전달 경로에서 다시 공백이 생긴다.
이번에는 이것을 주된 설계로 선택하지 않는다.

모든 조합을 Python으로 옮기는 선택도 검토 대상이다. Python은 복잡한 계산과 라이브러리
사용에 강하므로 계속 구현 언어로 활용한다. 그러나 IBL을 문자열 명령의 나열만으로 줄이면
권한·효과·근거·완료·재개를 호출자마다 다시 연결하게 될 수 있다.
반대로 Python 자체의 전체 의미와 효과를 IBL이 증명하려 하면 목표보다 훨씬 큰 문제를 떠안는다.

따라서 **IBL은 실제 작업을 조합하는 언어로 유지하고, 그 중심을 ‘호출 방법이 알려진 도구’에서
‘외부 의미가 독립적으로 적용되는 능력’으로 옮긴다.** 구현은 IBL 함수, Python, 외부 도구일 수 있다.
도구 호출 표면과 기존 문법은 유지할 가치가 있지만, 내부 계약·요약 표현은 새 의미 경계에 맞게
교체한다. 새 사용자 문법을 먼저 늘리지 않고, 기존 작성으로 추론되는 부분을 넓힌다.

이 선택의 근거는 IBL이 이미 가진 작업 실행 보장이다. 선택의 성공은 아래 수직 구현으로 검증한다.
같은 요구를 직접 구성한 경우보다 인터페이스를 이용한 재조합이 지속적으로 더 복잡하고,
본문 재분석·추가 래퍼를 피하지 못한다면 계약 필드를 더 붙여 연명하지 않는다.
표현 범위를 좁히거나 Python과 IBL의 책임 경계를 다시 정한다. 전면 재작성의 규모를 성과로 세지 않는다.

## 4. 새 중심 추상화: 의미 인터페이스를 가진 능력

능력은 **매개변수화된 의미 인터페이스, 구현, 불변 판본**으로 구성된다.
인터페이스는 “이 함수를 어떻게 부르는가”에 더해 “이 입력과 하위 능력으로 무엇을 얻으며,
어떤 효과·성립 조건·남은 의무가 생기는가”를 표현한다.

예를 들어 ‘자료 모으기’는 자료의 모든 열을 미리 고정할 필요가 없다.
읽기 부품이 돌려주는 행의 형태와 실패를 인자로 받아, 그 행과 출처·실패 정보를 보존한다고
표현할 수 있어야 한다. ‘선택하기’는 입력 행의 형태를 유지하고, ‘열 바꾸기’는 명시한 이름
대응만 바꾼다고 표현한다. 이 관계는 직접 호출·콜백·저장 함수에서 같은 의미다.
읽기 부품을 바꾸면 그 부품의 결과와 효과가 대입되며, 호출자가 상위 함수의 계약을 손으로 고치지 않는다.

내부 표현에는 값의 구조와 관계, 호출 효과와 자원, 실패·완료·수명 조건을 매개변수로 남길 수 있어야 한다.
기술적으로는 열린 행 타입, 타입·효과 변수, 인자에 의존하는 유한 관계와 조건의 표현이 필요하다.
현재의 Type/requirements/effects 표현이 이를 일관되게 담지 못하는 부분은 교체한다.
`Type.item`에 종류마다 다른 의미를 계속 얹거나 같은 관계를 flow와 별도 표에 중복 기록하는 방식은
완성된 구조로 인정하지 않는다. 기존 표현을 재사용할지는 이 의미를 명확히 담을 수 있는지로 판단한다.

이 인터페이스는 설명용 JSON을 하나 더 만드는 작업이 아니다.
부품을 적용할 때 입력 관계를 대입하고 결과·효과·의무를 얻는 계산의 기준이다.
지역 IBL 함수의 인터페이스는 본문에서 도출하고, 외부 원시 구현은 검토된 선언과 실행 경계 검증을 통해
제공한다. 선언·도출·관측·실행 증거는 출처가 다르므로 구별한다.
관측된 표본을 보편 보장으로 바꾸지 않으며, 실행 영수증이나 승인 권한을 정의 인터페이스 안에 넣지 않는다.
일상적인 작성자가 이 의미 표현을 직접 작성하게 하지 않는다. 함수의 입력·본문·반환에서 도출되는
관계는 시스템이 맡고, 도출할 수 없는 외부 약속과 업무 완료 기준만 해당 부품의 소유자가 명시한다.

```mermaid
flowchart LR
  A["어휘·외부 구현의 검증된 선언"] --> C["능력의 의미 인터페이스"]
  B["지역·저장 함수 본문 분석"] --> C
  C --> D["실제 인자·하위 능력으로 적용 및 합성"]
  D --> E["더 큰 능력의 의미 인터페이스"]
  E --> F["판본과 함께 저장·발견·재사용"]
  F --> D
  D --> G["실행 계획"]
  G --> H["권한·효과 실행·완료 관측·영수증"]
```

합성 결과를 다시 같은 합성의 입력으로 쓸 수 있는 것이 중심 성질이다.
기존 K1~K9는 이 인터페이스와 실행 결과가 보존할 질문을 점검하는 분류로 남긴다.
아홉 칸을 채웠다는 사실을 의미 모델이 완성됐다는 판정으로 사용하지 않는다.

## 5. 추상화 경계를 실제로 만드는 두 변화

### 값의 관계와 호출의 관계를 같은 적용에서 다룬다

표·레코드·함수 값이 어떤 경로를 지나왔는지 때문에 이미 알려진 관계가 사라져서는 안 된다.
표 연산은 목록과 행의 관계를 바꾸는 기본 연산으로 표현하고, 콜백은 같은 능력 적용으로 해석한다.
기본 라이브러리에 고유한 의미 규칙이 필요한 것은 정상이다. 그러나 그 결과를 전달·포장·적용하는
규칙은 생산자의 이름을 몰라야 한다. 새 업무 어휘를 추가할 때 검사기에 그 이름을 추가하지 않는다.

값은 List, Record, scalar, Result, 수명 있는 참조 등 의미에 맞는 형태를 가진다.
`{items}`라는 외부 도구 봉투를 모든 업무 값의 보편 모델로 삼는 전제는 내려놓는다.
호환 봉투는 도구 경계에서 해석하고, 메타데이터도 실제 의미에 따라 보존한다.
표의 행 값은 목록으로 일관되게 다루되 문서·집계·접수증까지 목록으로 위장하지 않는다.
봉투 변환 때문에 업무 정보가 사라지는 변경은 허용하지 않는다.

효과도 반환 타입 옆의 고정 라벨만으로 끝나지 않는다. 고차 함수가 인자로 받은 능력을 호출하면
그 능력의 효과와 자원 관계가 합성돼야 한다. 전달만 하는 경우와 실제 호출은 구별한다.
이렇게 얻은 결과를 기존 권한·병렬 admission·재사용 경계가 소비한다.
정적 합성은 실행 권한을 발급하지 않으며, 실제 호출 때 현재 주체와 상태를 다시 확인한다.

동적 선택이나 외부 구현 때문에 모르는 부분은 남을 수 있다. 그 부분을 런타임 의무나 명시적인
제한으로 표현하고, 알려진 다른 관계까지 지우지 않는다. 모든 Python의 효과나 모든 업무 성공을
자동 증명하려 하지 않는다. 특히 미상 쓰기를 포장하거나 저장했다고 병렬 허용으로 바꾸지 않는다.

### 저장의 단위를 본문에서 검증된 모듈 경계로 확장한다

현재의 불변 함수 판본·카탈로그·CAS 저장은 유지한다. 여기에 그 판본의 검증된 의미 인터페이스와
의존 판본을 함께 연결한다. 검증되지 않은 외부 JSON이 인증된 인터페이스가 되지 않도록 출처와
컴파일러/언어 의미 판본을 확인한다. 별도 관용구 DB나 경쟁하는 등록부는 만들지 않는다.

최초 등록과 본문·의존 의미 변경 시에는 본문을 검사한다. 이후 호출자는 원칙적으로 저장된
인터페이스를 대입해 검사하고, 실행기는 해당 판본의 구현을 실행한다.
**실행할 본문이 필요하다는 것과 호출의 적합성을 판단하려고 본문을 다시 펼쳐야 한다는 것을 구별한다.**
조회·상위 작성에 하위 소스를 전부 공급하는 것을 기본 경로로 삼지 않는다.

현재 컴파일 내부 메모이제이션은 이행 중 사용할 수 있다. 목표는 그 캐시를 디스크에 덤프하는 것이
아니라, 호출 지점의 가변 상태에 의존하지 않는 의미 인터페이스다. 타입·효과 변수에 실제 인자를
대입하는 작업은 허용하며, 합성된 인터페이스도 같은 표현으로 저장한다.
모델이 실행해서 얻은 값이나 임의 콜백 실행으로 인터페이스를 추측하지 않는다.
구현 최적화를 위한 추가 본문 특수화는 가능하지만, 그것이 없어도 지원 범위의 호출 의미와
기본 적합성 판정은 인터페이스로 성립해야 한다. 디스크 캐시 도입만으로 이 목표를 달성했다고 하지 않는다.

표현 범위를 넘는 정의에는 미확정 이유와 실행 경계 의무를 보존한다.
정적 분석을 지원하지 않는 부품을 순수·완료 보장 부품으로 승격하지 않는다.
요약을 유지할 수 없어서 본문 분석이 필요한 경우는 명시하고, 지원 대상의 대표 고차 조합이
늘 그 예외로 빠진다면 별도 컴파일 목표를 달성하지 못한 것으로 판단한다.

스크립트의 효과 선언을 채우는 일과 표 op의 반환 계약을 정리하는 일은 이 구조로 옮기는 이행 작업이다.
어휘마다 특별 계약을 새로 만드는 프로젝트로 분리하지 않는다.
반면 실행 원장, 업무 자료 보존, 검수 후 전달은 책임이 다르므로 하나의 저장소로 무리하게 합치지 않는다.

## 7. 큰 능력이 쌓이는 모습을 먼저 구현한다

첫 구현은 타입 표현 전체를 먼저 완성한 뒤 사례를 찾는 순서로 진행하지 않는다.
서로 다른 생산자가 실제로 같은 모듈 경계를 통과하는 하나의 수직 경로를 만든다.

‘자료 모으기’는 원천 목록과 읽기·정규화 능력을 받아 자료와 출처, 부분 실패를 반환한다.
읽기는 어휘, 정규화는 실제 등록 Python, 행 변환은 표 연산, 선택은 인자로 받은 함수로 구성한다.
이를 하나의 능력으로 저장한다. 다음 ‘판정 자료 만들기’는 저장된 자료 모으기를 사용하고
집계·선택 정책을 인자로 받아 새 능력이 된다. ‘변경 점검하기’는 저장된 판정 자료 만들기를
새 자료와 이전 결과에 적용해 달라진 근거를 만들고, 필요한 발행 능력을 연결한다.
이 이름들은 시험 업무 이름이며 코어에 넣지 않는다.

작성자는 상위 단계에서 읽기 도구의 봉투, 스크립트의 실행 프로토콜, 하위 콜백의 특별 규칙을
다시 다루지 않아야 한다. 대신 원천·정책·발행 능력을 바꿔 새 일을 표현한다.
외부 효과가 있으면 기존 승인과 완료 관측이 유지되고, 계산 일부를 수정할 때 이미 끝난
외부 효과를 반복하지 않는다. 실제 업무 의미가 바뀌는 입력은 필요한 부분을 다시 실행한다.

같은 저장 부품을 자료 조사와 파일/작업 상태 점검처럼 다른 원천·요구에 재사용한다.
한쪽에 맞춰 만든 어휘 이름이나 열 이름을 코어에 추가해서 다른 쪽을 통과시키지 않는다.
처음부터 준비한 정답 하나의 긴 프로그램을 실행하는 데서 끝내지 않고, 저장 이후에 주어진
새 요구와 부품 교체를 상위 인터페이스만 보고 작성할 수 있는지 확인한다.
작성자/평가자가 본문을 못 보는 조건에서도 상위 검사·작성은 가능해야 한다.
실행기는 물론 해당 구현을 사용할 수 있다.

이 사례의 목적은 더 긴 문장이나 더 깊은 함수가 아니다.
**이미 만든 능력이 다음 작업에서 실제로 생각하고 작성해야 할 단위 하나가 되는지**를 확인하는 것이다.

## 8. 이행 계획: 한 경계를 완성하고 넓힌다

첫 구간에서는 §7의 수직 경로를 대상으로 의미 인터페이스와 적용 규칙을 구현한다.
원시 어휘, 등록 스크립트, 지역·저장 함수가 같은 적용 경계에 도달하고 합성 결과가 다시 저장돼야 한다.
기존 `compiled_contracts` 형식을 입력으로 받아 외형만 통일하는 것으로 끝내지 않는다.
현재 Type/requirements/CallAnalysis 중 재사용하는 부분과 교체하는 부분은 이 구현에서 결정하고,
새 의미를 소비한 경로의 옛 판단은 제거한다. 이 경계가 성립하지 않으면 생산자 전수 이행을 시작하지 않는다.

두 번째 구간에서는 현재 지원하는 생산자 종류를 그 경계로 이행한다.
표 연산과 고차 콜백은 관계 의미를, 등록 스크립트는 효과·자원·판본을 제공한다.
새 설치와 현재 설치의 선언·핸들러·어댑터가 일치해야 한다.
구형 저장 정의와 공개 반환형은 명시적인 재검사/이행 또는 경계 호환으로 처리한다.
호환 경로는 특정 독자를 지원하는 좁은 입구로 남기고, 옛 합성 규칙의 병행 운영으로 만들지 않는다.
기존 입력·반환을 조용히 다른 의미로 바꾸거나 사용자 자료를 일괄 재작성하지 않는다.

마지막 구간에서는 저장·발견·상위 작성·소비 표면을 연결한다.
새 능력을 찾고 적용하는 데 필요한 설명은 같은 인터페이스에서 나오며, 본문 조회는 별도 선택이다.
실제 HTTP/MCP·모델 결과·앱 표시·완료 판정이 그 의미와 모순되지 않아야 한다.
이때 제거한 중복 판정과 남긴 호환 경계를 함께 결산하고 계획을 닫는다.
핸들러 수나 계약 필드 수를 늘렸다는 사실은 구간 완료의 근거가 아니다.

코드 소유의 출발점은 `ibl_v2_compile/call_analysis/types/requirements/analysis/component`와
`ibl_dependencies`, `function_library/ibl_v2_store/function_store`다.
이 파일들을 유지해야 한다는 뜻은 아니다. 표면 registry와 저장소에는 변환·저장 책임을,
의미 계층에는 적용·합성 책임을 둔다. 실행기와 권한·영수증 계층은 실행 책임을 가진다.
핵심 의미를 어휘 YAML과 엔진 코드가 서로 다르게 정의하지 않도록 선언과 컴파일 산출의 소유를 분명히 한다.

## 9. 무엇이 확인되면 이번 재설계를 끝내는가

종료 판정은 세 가지 큰 질문으로 한다.

**쌓은 능력이 다음 작업을 쉽게 만드는가.** 저장한 하위 부품의 구현을 다시 펼치지 않고 새 요구를
구성하고, 서로 다른 구현을 인터페이스로 교체할 수 있어야 한다. 직접 구성과 재조합의 결과 품질,
작성·수정 부담을 비교한다. 실제 모델을 이용한 비교는 조건과 전체 비용을 기록하며,
모델 없이 수행한 구조 시험을 모델 생산성 향상의 증거로 바꾸지 않는다.

**조합 뒤에도 같은 능력으로 남는가.** 인자·콜백·포장·반복·병렬·실패 대체·저장/회수 이후 값의 관계와
효과·실패·완료·수명이 보존돼야 한다. 직접/한 층/두 번 이상 승격을 같은 독립 oracle로 대조하고,
기존 깊이 6/10/14/30 생성 시험은 분석 규모와 퇴행을 확인하는 보조 인수로 사용한다.
검사·저장은 잎을 실행하지 않고, 순수 후미 수정은 완료된 효과를 반복하지 않아야 한다.
상위 검사에서 하위 본문 재분석을 차단한 시험도 통과해야 한다. 이를 30층 실행 성공으로 대체하지 않는다.

**지원 범위 안의 새 능력을 코어 수정 없이 넣을 수 있는가.** 구현 때 사용하지 않은 어휘/스크립트와
새로운 조합을 선언·정의만으로 연결해 본다. 새 이름별 분기나 상위 전용 어댑터가 필요하면 경계가 덜 완성된 것이다.
정말 새로운 의미 연산·효과 종류는 별도의 언어 확장으로 식별하고, 이미 지원하는 관계의 새 사례와 구별한다.
현재 지원 대상 전체의 이행 상태와 명시적인 미확정·제한을 결산하면 이번 작업을 닫는다.
모든 외부 도구의 모든 미래 오류가 없어져야 끝나는 작업으로 만들지 않는다.

이전 L1~L11의 보존 성질은 구현 인수로 계속 사용하지만, 이 세 질문의 성공을 대신하지 않는다.
계약 인수와 문서·정합 관문, 비system 전수 및 관련 system 묶음은
[회귀 규약](REGRESSION_TESTING.md)에 따라 실행한다.
변경된 언어/어휘/저장/실행 경계에 맞는 Python 라이브러리, vocabulary archive/bundle,
긴문장 재생·공통 저장소 시험을 선택한다. 어휘 생성물과 Android 몸 번들, 층·크기 검사도 갱신한다.
검사 중 코드가 달라진 실행을 최종 결과로 세지 않는다. frontend 변경에는 tsc를 포함한다.

## 10. 이전 수리와 남은 사건을 이 계획에서 어떻게 다루는가

기존 공통 분석·완료·실패 전파·수정 재개 수리는 기반으로 남는다.
`6eca5414`의 기존 조합 인수, `150fd07d`의 세대 증거/스캔 수리,
`bd98b88b`의 후속 설계는 각각 그 범위의 기록이다.
과거 10,920/10,945개 회귀와 30층 시험을 이번 재설계의 검증 결과로 재사용하지 않는다.

## 12. 첫 수직 경계의 구현 결산 (2026-10-28)

§1~§11의 목적과 종료 조건을 바꾸지 않는다. 아래는 이 계획 전체의 완료 선언이 아니라
첫 수직 경계를 실제 코드와 실행에 연결한 범위다. 구현은 `ibl_v2_semantic.py`와
`ibl_v2_semantic_store.py`, 인수는 `backend/test_ibl_v2_semantic.py`에 있다.

### 의미 경계와 제거한 의존

- `ibl-semantic/1`은 실제 입력을 관측한 분석 캐시가 아니라 입력·레코드·목록·투영·스칼라
  연산·능력 값·능력 적용·순차 map/collect의 유한 관계 DAG다. 지역 바인딩은 대입으로
  제거되고, 반환에 쓰이지 않은 계산의 성립 조건과 호출의 효과는 별도 뿌리로 남는다.
  입력의 열린 행과 콜백의 결과·효과는 적용 시 대입한다. 값 자체나 콜백을 실행하지 않는다.
- 저장 관문은 본문 검사 뒤 관계식을 도출한다. 동일한 기존 함수 판본 파일에 의미 판본,
  원문 지문, 직접 의존의 원문 지문/함수 참조, 원시 계약 지문과 함께 저장하고 CAS 해시에
  포함한다. 변경 요청이 제출한 인터페이스는 신뢰하지 않고 관문이 다시 만든다.
- 지원되는 저장 함수의 상위 적용에서는 `resolve_function`의 본문 파싱과 `_function`의
  본문 분석을 사용하지 않는다. `Library.interfaces_only()`는 본문을 제거한 작성·검사 뷰다.
  하위 본문 없이 새 상위 정의를 저장할 수 있다. `describe`와 회수 후보도 이 인터페이스를
  소비한다. 옛 `callable_contract`는 관계식 적용에서 나온 호환 뷰로 남긴다.
- 원시 값/효과 전달은 컴파일러의 `_named_target`에서 의미 적용 계층의
  `apply_primitive`로 옮겼다. 생산자 이름별 새 분기는 없다. 기존 원시 선언·선택·어댑터는
  좁은 입구로 유지하며, 표 관계와 builtin의 의미 규칙은 아직 기존 라이브러리 커널을 쓴다.
  표 콜백에서 선언 행을 `Unknown`으로 낮추던 분기를 제거했다.
- `Type`은 구체적인 구조·관측·와이어 경계의 표현으로 유지한다. 매개변수화된 관계를
  `Type.item`의 새 Unknown 변종이나 관측 캐시에 싣지 않는다. 기존 `requirements`는
  미이행 본문 검사와 공개 호환 뷰에 남고 새 저장 의미의 정본이 아니다.

### 실행과 작성의 분리

실행·수정·재개를 요청할 때만 `execution_plan`이 해당 정의들의 실행 계획을 준비한다.
현재는 기존 컴파일러를 구현 바인더로 재사용한다. **실행 시 본문 특수화까지 제거한 것은 아니다.**
일반 상위 작성·적합성 검사는 이 바인더 없이 성립하며, 수정 재개의 구현 좌표·영수증 검사에는
구현이 필요하다. 평범한 check와 실행 준비를 혼동하지 않는다. 실행 비용 상한은 저장 관계식에서
증명하지 않고 preflight에 미확정으로 남긴다. 승인·영수증·완료 증거·외부 참조 소유권은
기존 실행 계층이 소유한다. 정의의 완료 약속은 실행 성공 증거로 승격하지 않는다.

### 수직 인수와 새 요구

인수는 실제 함수 저장소와 등록 Python runner를 사용한다. 원천 읽기 어휘 → Python 정규화 →
표 filter와 전달받은 정책 → 출처/부분 실패를 보존한 gather → decide → recheck를 저장한다.
검사 때 하위 `_function`을 실패하도록 막거나 라이브러리에서 본문 자체를 제거한다.
그 뒤 새 상위 audit를 저장하고, 저장 이후 추가한 파일 읽기 어휘와 다른 등록 Python의
새 열(bytes)에 맞는 정책으로 교체한다. 이 시험 업무의 이름/열은 코어에 들어가지 않는다.

외부 읽기와 Python 호출이 검사·저장 중 0회인지, 반환 행·출처·이전 값·Result가 보존되는지,
없는 필드를 상위에서 거절하는지, 전달받은 발행 능력의 쓰기 효과가 드러나는지 검사한다.
발행 이후 순수 후미 실패를 수정·재개했을 때 완료된 발행은 1회다. 완료 관측과 부분 실패,
ForeignRef의 전송 제한, 미상 효과 비승격, 버려진 중간 계산의 요구도 별도로 검사한다.
이것은 구조·실행 인수다. 실제 모델의 작성 시간/토큰 감소나 실제 외부 서비스 생산성 비교를
측정한 결과로 사용하지 않는다.

### 미이행 경계와 남은 판단

관계식 도출은 현재 직선 본문·상수 기본값·렉시컬 람다·함수/어휘/내장 호출·순차 each
(map/flat_map/effect, collect)을 지원한다. 조건에 따른 세밀화, try/fallback, 반복 상태,
병렬 each의 입장 증명, 동적 projection, record spread, 명시 annotation 및 원격 target의
관계식 도출은 남았다. 이런 정의와 구형 저장본은 `semantic_limit`이 있는 본문 검사 경로다.
본문이 없는 뷰에서 이를 호출하면 명시적으로 거절한다. 자료의 일괄 재작성은 하지 않는다.
현재 의미 판본이나 직접 의존/원시 계약이 바뀌면 재검사 경로로 돌아간다.

따라서 표 op 전수의 관계 의미 이행, 구형 저장본 재인증, 실행 바인더의 기존 분석 의존 제거,
HTTP/MCP/앱의 전체 소비 표면 이행, 실제 서로 다른 업무의 모델 비교는 완료되지 않았다.
이 잔여를 성공한 수직 시험의 통과 수나 중첩 깊이로 대신하지 않는다. `~turn` 자료 보존 사건도
이번 변경에 섞지 않았다. 첫 경계는 후속 확장의 출발점이며 §9의 전체 종료 조건은 아직 열려 있다.

추가 경계 검사에서는 소수 상수/기본값을 기존 값 wire로 무손실 저장하고, 본문을 펼친 실행 계획도
검사한 계획 신원을 유지한다. 검사 뒤 실행 의존 자산 또는 함수 원문이 바뀌면 첫 외부 효과 전에
거절한다. 고정 함수 참조의 인터페이스는 현재 라이브러리가 아니라 해당 고정 뷰에서 해소한다.
실적 소비자는 실행 사건의 고정 함수 참조를 사용하며, 새 경로에서는 하위 본문 좌표 조회를 제거했다.

표 콜백의 알려진 누락 필드/nullable Bool 오류는 이제 컴파일 때 거절한다. 기존 런타임 진단 시험은
이 조기 거절도 확인하고, 입력 타입이 미확정인 경로에서 원래의 행 번호·연산·누락 필드 검사를 유지한다.

읽기 전용 설치 조사에서는 활성 정의 59개 중 본문 관계식 도출 가능 21개, if 25개, try 5개,
assert 3개, format 3개, 병렬 each 2개였다. 의존 폐포 인증이나 설치 자료 이행 수가 아니며,
사용자 라이브러리를 일괄 재등록하지 않았다.

## 13. 조건부 능력의 의미 인터페이스 이행 (2026-10-28)

§12 다음 구간이다. 첫 경계를 넓히는 대상으로 조건에 따른 결과·요구·효과의 변화를 골랐다.
선택 필드와 null을 다루는 정책, 조건부 발행이 저장 이후 매번 본문 검사로 돌아가면
작성자는 직선적인 능력만 축적할 수 있기 때문이다. 문법이나 업무별 이름을 추가하지 않는다.

### 유지·교체·제거

- 문장 if/else, 조건 값, 단락 and/or의 의미를 유한한 `choose` 관계와 가지별 하위 관계로 도출한다.
  가지 뒤의 후속 문장은 해당 가지의 바인딩으로 연결하며, 조기 return은 그 경로를 종료한다.
  후속 관계는 잠재 능력으로 한 번만 도출하고 가지별 값으로 적용한다.
  조건은 함수의 실제 인자에 대입한다. 필드 존재·null/Bool·유한 모양으로 증명할 수 없는
  조건은 두 경로를 보존한다. 임의 콜백 실행이나 도구 관측으로 조건을 추측하지 않는다.
- `ibl_v2_narrow`의 AST 직접 판단을 유한 가드 표현에 대한 공통 세밀화·도달 가능성 규칙으로
  교체했다. 본문 검사와 저장 관계 적용이 같은 규칙을 쓴다. AST는 이 표현을 도출하는 입구다.
  같은 null/선택 필드 판단을 별도의 저장 함수 검사기에 복제하지 않았다.
- 컴파일러와 저장 관계에 중복돼 있던 스칼라 전달을 `scalar_type`으로 모았다.
  숫자 관측은 기존 `value_semantics`를 유지한다. 저장 투영은 필드와 인덱스를 구분해
  목록 첫 행과 조건부 필드 접근도 기존 공통 접근 규칙을 적용한다.
- 본문 검사도 증명된 비선택 가지의 효과·반환·콜백 순수성 요구를 호출에 섞지 않는다.
  비선택 소스의 이름/문법/타입 진단과 기존 변수 정의 규칙은 유지한다.
  조건 미정의 함수 선택은 모든 가능한 대상의 인자 적합성을 계속 요구한다.
- 기존 불변 저장소·권한·완료 관측·수명·영수증은 유지한다. 의미 판본에 가드/컴파일 규칙도
  포함하여 이전 의미로 인증된 인터페이스를 새 의미로 조용히 재사용하지 않는다.

### 인수와 한계

선택 필드/nullable 정책을 저장하고 report→review로 재저장한 뒤 본문 없는 라이브러리에서
검사한다. 직접 구성·저장 부품·재조합 결과를 독립 기대값으로 비교한다. 조건부 발행은
선택한 능력의 효과와 반환을 보존하고, 미정 효과를 순수하다고 승격하지 않는다. 순수 조건 값에
쓰기 콜백이 실제로 도달하면 거절한다. 조건 때문에 도달하지 않는 콜백을 전달하는 호출은
인터페이스 검사와 실행 준비 양쪽에서 성립해야 한다.

읽기→실제 등록 Python→표/정책→조건부 발행→후미 실패를 저장 능력으로 조합해 수정·재개한다.
검사/저장 중 도구 실행은 없고, 완료된 읽기·발행은 반복하지 않는다. 순수 정규화 재계산은 허용한다.
완료 의무를 선언만으로 충족한 것으로 바꾸지 않는다.

조건에 관한 §12의 미이행 범위 중 위 형태를 이행했다. if를 값 블록으로 받는 형태(비지역 return 포함),
case, try/fallback, 반복 상태, 병렬 each, 동적 projection, record spread, annotation,
format은 아직 관계 도출 범위 밖이다. 일반적인 수학 정리나 콜백 반환값으로 조건의 참을
증명하지 않는다. 관계 전개가 4,096개 항을 넘으면 이유를 붙여 본문 검사 경계로 돌린다.
이 제한은 등록/검사 비용 한계이며 능력의 성공 판정이 아니다.

읽기 전용 설치 조사에서 활성 59개 중 본문 관계식 도출 가능 27개였다. 나머지 최초 제한은
record spread 9, dynamic projection 5, try 7, assert 3, format 4, parallel each 4다.
§12의 21개보다 도출 범위가 넓어졌지만, 의존 폐포 인증·실제 재등록 수는 아니다.
사용자 정의를 일괄 재작성하지 않았다. 실제 모델의 시간·토큰 개선, 라이브 활성화 및 모든 소비 표면
이행은 여전히 미검증이며, 실행 바인더의 본문 분석 의존도 남는다.

초기 구현은 후속 문장을 양쪽 가지에 복제해 연속 분기 9개에서 관계 예산을 넘었다.
이를 지원 범위 예외로 닫지 않고 후속 관계를 공유하는 잠재 능력으로 교체했다. 6→12개 분기의
인터페이스 크기는 선형으로 늘고, 독립 Bool 조건의 합성도 같은 추상 인자에 대한 관계 적용을
재사용한다. 이는 저장 분석 캐시가 아니라 유한 관계 DAG의 공유이며, 실행 결과·영수증은 캐시하지 않는다.

최초 전수에서 확정 조건에도 양쪽 후보를 합치던 기대 14건이 실패했다. 해당 시험의 미정 Bool
경로와 원래 오류/런타임 의무 검사를 유지하고, 확정 참/거짓의 판정을 추가했다. 조건이 확정되면
불가능한 반환 후보 때문에 올바른 부품 호출을 거절하지 않으며, 알려진 와이어 불가 반환은
앞선 외부 효과 전에 거절한다. 런타임 조건 미정은 기존 실행 경계 의무를 유지한다.

최종 검증:

- 관련 13개 파일 묶음: **550 통과, 5 경고, 17.28초**.
- `pytest backend/ -n auto --dist loadfile`: 시스템 검사를 포함한 전체
  **11,182 통과, 22 건너뜀, 80 경고, 877.75초**. 최초 전수의 실패 기대를 수정하고
  관계 공유까지 반영한 뒤 실행 코드를 고정한 채 다시 실행했다.
- Android 몸 번들 재생성/일치, 층 구조, 파일 크기, diff 정합 검사 통과.
  커밋 관문에서도 최종 어휘·파생물·이식성 등 저장소 규약을 검사한다.
- 미검증 범위는 위에 명시한 라이브 활성화·모델 비용·미이행 언어/소비 표면이다.
  이 결과를 전체 재설계의 종료나 실제 업무 생산성 개선으로 확대하지 않는다.


## 14. 자료 구조를 보존하는 가공 능력의 이행 (2026-10-28)

저장한 가공 능력이 새 원천의 열과 메타데이터를 받도록 레코드 확장(`**`), 인자로 정하는
필드/목록 접근, f 문자열 보간을 의미 관계로 이행했다. §13 다음 구간이며 전체 종료 선언은 아니다.
열 이름이나 업무별 어휘를 코어에 추가하지 않고, 실제 입력 구조·선택자·콜백을 대입한다.

### 유지·교체·제거

- 레코드 관계를 고정 필드 사전에서 순서 있는 확장/필드 관계로 교체했다. 입력의 알려진 필드와
  호출 가능 값·참조를 보존하며, 뒤의 열린 확장이 앞 필드를 덮을 수 있다는 불확실성도 보존한다.
  그 뒤에 명시한 필드는 다시 확정된다. 조건에 따른 닫힌 레코드 후보도 보존한다.
  이를 명명 인자로 펼칠 때 함수·람다·원시 호출도 후보별로 검사한다. 기존 호출기의 단일
  Record 가정으로 돌아가 후보의 인자·효과를 지우는 소비 경로를 함께 이행했다.
- 본문 검사에 있던 레코드 확장 판단과 보간 타입/정적 문자열 판단을 `record_type`·`format_type`으로
  옮겼다. 본문 검사와 저장 관계가 같은 커널을 소비하고, 컴파일러의 옛 판단은 제거했다.
  미지정 표면 입력의 인자 생략/빈 보간과 원문 경고는 소스 입구에 유지한다.
- 투영의 선택자를 고정 키에서 입력 관계로 바꿨다. 기존 `access_type`·`select_type`을 양쪽에서
  사용하므로 선택된 필드의 콜백 계약·효과도 같은 적용으로 이어진다. 알 수 없는 선택자는
  후보와 실행 경계 의무를 남긴다. 버려진 레코드 확장·투영·보간의 적합성 요구도 검사한다.
- 기존 Type·값 wire·불변 저장·권한·완료 관측·수명·실행 영수증은 유지한다. 새 내부 계약을
  작성자에게 요구하지 않는다. 의미 판본이 달라진 기존 저장본은 종전처럼 재검사가 필요하며,
  사용자 라이브러리를 일괄 재작성하지 않았다.

### 재조합 인수와 실제 범위

읽기 → 실제 등록 Python → 전달받은 열 이름/정책으로 각 행 확장 → 저장 prepare → 저장 review의
경로를 만든다. review를 등록할 때 하위 본문 조회를 차단한다. 직접 구성·한 층 저장·두 층 저장을
독립 기대값과 대조한다. 저장 이후 새 파일 원천과 등록 스크립트로 교체하여 score 대신 bytes를
측정하고, 새 revision/owner 메타데이터를 상위가 다시 나열하지 않아도 보존하는지 검사한다.
본문 없는 뷰에서 새 요구를 검사하며, 없는 열은 도구 실행 전에 거절한다. 정상 실행의 Python
완료 관측도 확인한다. 검사와 저장 중 잎 호출은 0회다.

별도 경계 인수는 확장 순서·열린 덮어쓰기·조건 후보·ForeignRef 전송 제한·선택된 콜백의 효과와
인자 요구·미상 효과 비승격·버려진 계산의 요구를 확인한다. 보간으로 만든 쓰기 자원은 같은 경로의
병렬 충돌을 거절하며, 서로 다른 경로는 구별한다. 쓰기 뒤 순수 계산 실패를 수정·재개한 결과
이미 완료한 쓰기는 한 번만 남는다. 실제 외부 서비스 쓰기 대신 격리 어댑터를 사용했다.

후보가 64개를 넘는 레코드 확장은 공통 필드만 열린 레코드로 보존하고 `RECORD_RELATION_LIMIT`을
보고한다. 임의의 필드 존재나 덮어쓰지 않음을 보장하지 않는다. 기존 유한 관계 예산도 유지한다.
읽기 전용 조사에서 활성 정의 59개 중 본문 관계식 도출 가능은 38개, 최초 제한은 try 12,
assert 3, 병렬 each 5, slice 1이다. 이 수는 의존 폐포 인증이나 실사용 재등록 수가 아니다.

남은 경계: try/fallback·반복 상태·병렬 each·slice·annotation·원격 target 등의 관계 이행,
표 생산자 전체 이행, 실행 바인더의 본문 분석 의존 제거, 구형 정의 재인증과 HTTP/MCP/앱 전체 소비
표면은 아직 열려 있다. 실제 모델의 작성 시간·토큰·업무 생산성, 라이브 활성화는 미검증이다.
`~turn` 사건은 이번 변경과 별개다.

첫 종합 회귀를 소비 경로 검토 중 중단했다. 이 실행에서 발견한 새 제한 진단의 도움말 누락은
전용 도움말을 추가해 해결했다. 중단한 실행은 전수 통과로 세지 않는다.

최종 검증:

- 관련 7개 파일 묶음: **267 통과, 29.00초**. 새 인수는 모듈명 시험 파일에 포함했다.
- 선택기: 변경 backend 모듈 4개가 전이 시험 **743/801개(93%)**에 닿으며 네 모듈 모두
  허브로 판정됐다. 이에 `pytest backend/ -n auto --dist loadfile` 전수를 실행했다.
- 시스템 검사 포함 전체: **11,197 통과, 22 건너뜀, 80 경고, 908.54초**.
  최종 실행 시작/종료의 변경 코드 지문이 일치한다. 중단한 앞선 실행은 이 결과에 합산하지 않았다.
- Android 몸 번들 재생성, 층 구조·파일 크기·diff 정합 검사 통과. 어휘/파생물 정합은
  검사와 최종 커밋 관문에서도 확인한다. 기존 비차단 경고는 남아 있다.

이 구간의 판단: 저장한 가공 능력이 새로운 열·원천·정책에 그대로 적용되고, 재조합 결과도 같은
의미 인터페이스를 가지며, 새 업무 이름을 코어에 추가하지 않았다. 반면 실제 작성 비용 개선과
위에 남긴 언어/실행/공개 소비 경계 전체는 증명하지 않았다. §9의 종료 조건은 계속 열린다.


## 15. 독립 작업 묶음의 의미 인터페이스 이행 (2026-10-28)

병렬 each와 `&`를 저장 관계로 도출한다. 순차 수집만 축적할 수 있던 경계를 넓혀,
같은 수집 능력에 새 원천·등록 Python·정책을 넣고 상위 능력으로 재저장한다.
병렬화를 허용하는 권한이나 미상 효과의 처리 정책은 바꾸지 않는다.

### 유지·교체·제거

- `map` 관계의 병렬 제한을 제거하고 옵션·행·콜백을 실제 인자로 대입한다. `parallel` 관계는
  각 가지의 잠재 능력을 독립 프레임으로 적용해 결과 위치와 효과·자원 관계를 보존한다.
- 본문 검사의 each와 병렬 가지 판단을 `iteration_type`·`parallel_type`·`frame_summary`로
  옮겼다. 반환 프레임·효과/자원 축적·모드별 결과·정적 충돌/미상 효과 판단을 소스와 저장
  관계가 공유한다. 컴파일러의 해당 판단과 저장 map의 별도 반환 판단을 제거했다.
- 관계 적용에서 검사 뿌리를 효과보다 먼저 일괄 계산하던 순서를 도출 순서로 교체했다.
  먼저 읽은 값을 후속 병렬 가지가 캡처한 반례에서 읽기가 가지 내부 효과로 잘못 이동하여
  순차 읽기 뒤 병렬 쓰기를 거짓 충돌로 거절했다. 값의 공유와 효과의 프레임 소유를 구분한다.
- 원문 정적 옵션·readonly·이름 검사는 소스 입구에 유지한다. 행 봉투 해소는 기존
  `rows_type` 하나를 사용하고 `_rows_of` 중복 래퍼를 제거했다. 그 래퍼를 직접 부르던
  기존 인수는 공통 함수로 이행했으며 assertion은 유지했다.
- 기존 실행 admission·승인·유한 병렬 스케줄러·Result/Fault·수명·완료 관측·영수증은 유지한다.
  정적 검사는 실제 자원 입장 검사를 대체하지 않는다. 미상 효과를 저장했거나 묶었다는 이유로
  순수/독립 효과로 승격하지 않는다. 빈 목록의 효과/결과 정밀도는 기존 보수적 요약을 유지한다.

### 새 요구와 검증 경로

어휘 읽기 → 실제 등록 Python → 표 filter/전달 정책의 병렬 gather를 저장하고 decide·recheck로
재조합한다. 이후 새 파일 읽기 어휘·등록 스크립트·bytes 정책으로 바꾸고 audit를 다시 저장한다.
상위 등록의 하위 본문 조회와 상위 검사의 `_function`을 차단한다. 검사/저장 중 잎 호출은 0회다.
동시 시작 장벽을 둔 읽기와 실제 Python 실행으로 직접 구성·한 층/두 층 저장을 독립 기대값과
대조한다. 성공 둘, 성공+원천 실패의 두 경우를 확인하며 순서·새 열·Result 오류를 보존한다.

같은 경로의 읽기/쓰기 가지는 정적으로 거절하고 서로 다른 경로는 구별한다. 항목 수가 0/1인
경우와 여러 항목의 고정 쓰기를 구분하며, 실제 입력이 같은 자원을 가리키면 실행 admission에서
첫 쓰기 전에 차단한다. 미상 효과의 병렬은 경고를 보존하고 실제 입장에서 거절한다.
map/flat_map/effect의 결과, ForeignRef 전송 제한, collect로도 회수할 수 없는 권한 실패를 검사한다.

바깥 순수 후미 수정·재개에서는 완료된 병렬 쓰기 두 건이 각각 1회로 남는다. 병렬 수집의
성공/실패 읽기 관측도 기존 영수증으로 재생하며 다시 읽지 않는다. 순수 Python 재계산은 허용한다.
실제 외부 서비스 대신 격리 어댑터를 사용했고, Python은 실제 등록 runner로 실행했다.

### 당시 발견한 복구 경계의 반례 — §16에서 후속 이행

두 병렬 가지가 모두 쓰기를 마친 후 한 가지의 순수 계산이 실패했다. 그 계산을 지역 함수
본문에서 수정하면 당시 복구 검사는 `REPAIR_UNSUPPORTED`로 거절했다. 거절 뒤 이미 완료된 쓰기는
반복하지 않았지만, **이 구간에서는 함수 내부 수정 후 완료까지 이어지는 능력이 성립하지 않았다.**
성공적인 부분 복구로 세지 않고 제한 검사로 남겼으며, §16에서 실제 수정·완료 인수로 이행했다. 기존 성공 인수를 약화하지 않았다.

당시 `ibl_v2_repair_graph`는 효과 접두부에서 참조한 정의 전체를 고정하고, 계산된 콜백은 모든
정의에 의존할 수 있다고 보았다. 이를 단순히 해제하면 수정한 반환값이 뒤의 외부 효과 입력·선택을 바꾸는
경우까지 허용할 수 있다. 복구를 넓히는 다음 경계는 **효과가 의존하는 계산/조건과 결과만 만드는
계산을 구분하는 의미 관계**여야 한다. 함수 이름이나 특정 병렬 예제에 대한 예외를 추가하지 않았다.
실행 영수증의 좌표/신원 연결과 함께 판단해야 하며, 불변 판본을 약화해서 해결하지 않는다.

읽기 전용 설치 조사: 활성 59개 중 본문 관계식 도출 가능 39개, 최초 제한 try 16·assert 3·slice 1.
병렬 제한 뒤에 가려졌던 try가 드러났으며, 의존 폐포 인증이나 사용자 정의의 실제 재등록 수가 아니다.
try/fallback·반복 상태·annotation·원격 target, 표 생산자 전체, 실행 바인더의 본문 분석 의존,
구형 정의 재인증·전체 공개 소비 표면과 실제 모델 비용은 여전히 미이행/미검증이다. `~turn`은 별개다.

첫 전수는 관계 적용 순서의 반례를 확인해 중단했다. 중단한 실행은 전수 통과로 세지 않는다.

## 16. 효과 의존과 내부 결과 계산의 수정 경계 (2026-10-28)

§15의 반례를 다음 인수로 삼았다. 저장한 병렬 fanout에 전달한 지역 함수가 각 쓰기 뒤 순수
계산에서 실패한다. 그 함수의 순수 계산을 수정한 뒤 저장 능력의 호출을 그대로 재개하여 결과를
완성하되, 두 쓰기는 각각 한 번만 남아야 한다. 이 절은 전체 재설계의 종료 선언이 아니다.

### 유지·교체·제거

- `ibl_v2_repair_graph`의 효과 접두부·참조 정의 전체 잠금을 **효과 의존 투영**으로 교체했다.
  검사된 실행 계획의 효과 정보를 소비하며 별도의 타입/효과 판정기나 실행기를 만들지 않는다.
  값에 그 값을 만드는 소스 좌표 의존을 연결하고, 외부 효과가 요구하는 인자·호출 경로·앞 계산의
  완료 조건만 고정한다. 함수 호출은 인자를 대입하고 렉시컬 콜백의 실제 대상을 따라간다.
  결과 계산은 호출 결과가 뒤 효과의 입력·조건·도달에 필요한 경우에만 효과 의존에 들어간다.
- 함수 이름과 업무 이름에 따른 예외는 없다. 이름으로 참조한 모든 정의를 잠그거나 계산된 콜백을
  무조건 모든 정의에 연결하던 지원 경로의 판단을 제거했다. 미해석 제어/대상은 전체 구현과
  전이 참조를 보존하는 보수적 경계다. 순수성·자원·권한·완료의 의미 자체는 기존 검사/실행 계층이
  소유하며, 이 투영은 **복구 시 구현 좌표를 대응하는 증명**이다. 저장 능력의 의미 인터페이스를
  실행별 의존 캐시로 대체하지 않는다. 기본 상위 적합성 검사는 여전히 하위 본문 없이 성립한다.
- 효과/제어 노드의 논리 위치가 같아야 한다. 매개변수·기본값 평가·캡처·호출 경로와 효과의
  삽입/삭제/재정렬은 결과 계산 수정으로 간주하지 않는다. 같은 정의를 여러 번 사용하면 모든
  사용의 의존을 합친다. 한 사용만 효과 결과를 요구해도 그 정의의 해당 계산은 고정된다.
- 기존 Journal의 실행 신원·인자/구현 지문·배타 잠금·CAS·불변 함수 판본·완료 관측을 유지한다.
  재개할 때 실제 요청을 영수증과 다시 대조하며, 원 실행에 없던 외부 호출은 새로 실행하지 않는다.
  완료 불명·실패한 쓰기·승인 대기 영수증은 자동 재실행하지 않는다. 실패한 읽기는 고정된
  복구 분기에서 기존 실패 관측으로 재생한다. 두 번째 수정과 같은 요청의 재개도 최초 계보를 잇는다.
- 이 구간의 내부 복구 증명을 `ibl-repair-frontier/2`로 구분했다(§17은 판본 3). 구형 증명은 새 수정 권한으로 승격하지 않는다.
  의존 탐색은 8,192 방문 예산이며 초과/재귀 한계면 복구 불가로 남는다. 일반 실행 결과를 잘라내거나
  모르는 관계를 순수하다고 가정하지 않는다. 새 내부 계약을 작성자가 수동으로 작성할 필요가 없다.

### 인수와 반례

- §15에서 제한으로 남겼던 병렬 fanout 시험을 성공 인수로 바꿨다. 두 쓰기 완료 장벽 뒤 한 가지의
  나눗셈 실패 → 내부 함수 분모 수정 → `[10, 10]` 완료 → 같은 실행 resume까지 쓰기는 두 건 그대로다.
- 내부 후속 계산에 새 바인딩·레코드 결과를 추가하고, 여러 함수 층을 거쳐 두 번 수정·재개한다.
  새 결과와 원래 발행 영수증을 함께 반환하며 외부 쓰기는 한 번만 남는다. 레코드로 전달한
  렉시컬 콜백의 캡처도 보존한다.
- 저장한 발행 → report → review 세 능력의 하위 발행 판본을 수정하고 새 `function_refs`를 명시한다.
  저장/검사 중 쓰기는 없고, 복구 CAS 뒤 새 결과를 얻으며 일반 resume도 새 불변 판본을 사용한다.
  기존 판본을 덮어쓰거나 활성 판본만 보고 영수증의 소유를 바꾸지 않는다.
- 반대 인수: 내부 반환을 뒤 쓰기 인자/조건에 쓰는 경우, 반환을 버려도 다음 쓰기의 도달에 필요한
  경우, 같은 정의의 다른 사용이 효과에 연결되는 경우, 기본값·캡처 변경, 효과 삽입/삭제·대상 변경은
  첫 추가 효과 전에 검사에서 거절한다. 완료 불명·잠금 경합·오래된 CAS/증명 등의 기존 경계도 유지한다.
- 실패한 읽기와 고정된 catch의 쓰기 뒤 내부 순수 계산을 수정하면 읽기·복구 쓰기를 반복하지 않는다.
  오류를 성공으로 바꿔 저장하는 것이 아니라 원래 Fault를 같은 복구 경로로 전달한다.

### 지원 범위와 남은 경계

직선 지역/저장 함수·렉시컬 콜백·명명 적용·레코드 전달·독립 병렬 가지와, 항목 수가 정적으로
알려져 한 배치에 들어가는 each에서 내부 결과 계산을 분리한다. 실행에는 원래 구현이 필요하며
복구의 소스 좌표 증명은 실행 준비 단계에 속한다. 실제 서비스 대신 격리 어댑터로 쓰기를 관측했다.

순차 반복 또는 여러 배치의 each는 앞 회차의 순수 계산 성공도 뒤 효과의 도달에 영향을 주므로
본문의 완료 계산을 보수적으로 고정한다. 알려지지 않은 항목 수도 같은 경계다. 이 구간에서는
try/if/repeat 등 미해석 제어 구간 내부와 동적 대상, 명시 annotation·정의 소유 완료 선언의 본문을
전체 고정했다. 문장 if/else는 §17에서 후속 이행했다.
고정된 try 바깥의 순수 후속 계산 수정은 지원한다. 수학적으로 같은 식임을 증명하거나 이미
실행되지 않은 외부 효과까지 이어서 새로 시작하는 기능은 이번 범위가 아니다.

§9에 대한 판단: 쌓인 능력 내부의 결과 계산을 고쳐도 상위 조합과 완료된 발행을 다시 만들 필요가
없어졌다. 수정한 저장 능력도 같은 의미 인터페이스·불변 판본으로 다시 조합된다. 새 어휘 이름을
코어에 추가하지 않았다. 다만 나머지 제어/반복·생산자·공개 소비 표면 전체의 이행, 실제 모델의
작성 시간/토큰 개선과 라이브 활성화는 미검증이며 `~turn` 사건은 이 변경과 별개다.

검토 중 동적 목록 인덱스/each로 콜백 대상을 잃으면 콜백 본문의 의존도 함께 사라지는 반례를
찾았다. 쓰기 대상 변경을 검사에서 허용하는 것을 재현했다. 대상이 불명확해지는 경계에서
컨테이너에 담긴 호출 가능 구현의 의존을 보존하도록 고쳤고, 각각의 거절 인수를 추가했다.
앞선 전수는 중단했으며 7,168 통과·2 건너뜀·72 경고/328.88초를 최종 전수 통과로 세지 않는다.

최종 검증:

## 17. 조건부 경로의 결과 수정과 효과 보존 (2026-10-28)

§16의 직선 함수 내부 수정 경계를 문장 if/else로 넓힌다. 이미 저장해 쓴 능력의 조건별 결과
계산을 고치기 위해 상위 조합과 발행을 다시 작성/실행할 필요가 없어야 한다. 조건부 의미
인터페이스 자체는 §13의 관계를 유지하며, 그 능력을 실행한 뒤 수정하는 구현 의존 경계를 이행한다.

### 유지·교체·제거

- `ibl_v2_repair_graph`에서 문장 if/else 전체를 불투명 구현으로 고정하던 경로를 제거했다.
  각 가지의 **반환으로 끝남 / 계속 진행함**을 구분하고 조건의 값 의존을 연결한다. 이어지는
  문장은 계속 진행하는 가지의 환경과 완료 의존만 합류한 뒤 한 번 분석한다.
- 반환으로 끝난 가지의 순수 후속 계산은 다른 가지의 다음 효과를 실행하는 조건이 아니다.
  그 계산을 다음 효과의 의존에 섞지 않는다. 반대로 함수 호출자에서 반환을 외부 효과의 입력으로
  쓰거나 그 호출의 완료 뒤 다음 효과를 실행하면 반환 계산도 고정된다. 관측한 한 가지를 보편
  보장으로 올리거나 조건을 실제로 실행하지 않으며 가능한 양쪽 경로를 보존한다.
- 분기 안 바인딩은 계속 진행하는 환경들에서 합류한다. 합류 값을 뒤 효과가 소비하면 양쪽 계산을
  모두 보존한다. 합류 후 호출 대상을 확정할 수 없으면 가능한 호출 구현의 의존을 보존한 채
  기존 불투명 경계로 남긴다. 함수/어휘 이름별 예외와 새로운 작성자 계약 필드는 없다.
- 순차 문장의 이전 계산·실패 도달 의존과 함수/콜백 인자 대입, 원래 호출 좌표·영수증·권한·CAS·
  불변 판본·완료 관측은 유지한다. 조기 반환 제거로 아직 수행하지 않은 효과를 새로 여는 수정은
  검사에서 거절하며 실행 Journal의 미기록 호출 차단도 유지한다.
- 내부 증명은 `ibl-repair-frontier/3`이다. 이전 판본 1/2를 새 경로 증명으로 자동 승격하지 않으며
  양쪽 증명의 판본도 대조한다. 기존 8,192 방문 예산을 유지한다. 분기 뒤의 문장을 가지마다
  복제하지 않아 연속 40개 조건문도 의존 분석을 마치고 결과 수정·재개할 수 있다.

### 인수와 현재 범위

참/거짓 가지 각각에서 쓰기 뒤 결과 계산 실패를 만들고, 같은 함수 내부의 계산만 수정해
각각 10/20으로 완료한다. 양쪽 조기 반환, 분기 바인딩의 합류, 한쪽 조기 반환 후 다른 경로의
후속 효과를 각각 확인한다. 호출자는 같은 능력을 사용하며 선택된 쓰기는 한 번만 남는다.

저장된 병렬 fanout에 조건문으로 발행과 결과를 나누는 콜백을 전달한다. 두 쓰기 완료 장벽 뒤
한 가지가 실패하고, 내부 분모 수정 뒤 `[10,10]`으로 완료한다. 같은 실행의 resume에서도
쓰기 두 건이 반복되지 않는다. §15/§16의 조건 값 표현을 쓴 기존 인수도 함께 유지한다.

조건부 발행 능력과 이를 호출하는 상위 review를 저장하고 하위 본문을 제거한 뷰에서
`Compiler._function`을 막은 채 상위 적합성을 검사한다. 이후 하위 능력의 새 불변 판본을
등록하고 명시적 함수 참조와 복구 CAS로 계승한다. 검사/등록 중 도구 호출은 없고, 새 결과와
기존 발행 접수증을 반환하며 일반 resume도 같은 판본과 영수증을 쓴다.

반대 인수는 효과를 선택하는 조건 변경, 분기 합류 값/호출자에게 반환한 값을 통한 효과 입력
변경, 조기 반환 제거로 미기록 효과를 활성화하는 변경을 검사에서 거절한다. 새 인수는 기존
모듈명 시험에 포함했고 별도 업무 이름 분기나 별도 시험 러너를 추가하지 않았다.

문장 if/else를 이행한 범위이며 try/fallback·반복 상태, 값 블록 속 비지역 반환, 대상 미확정
콜백과 명시 annotation/정의 완료 선언의 내부 수정은 여전히 보수적 경계다. 구형 정의 재인증과
실행 바인더/공개 소비 표면의 이행도 남아 있다. 실제 외부 서비스·라이브 활성화·모델의 작성 비용은
측정하지 않았다. `~turn` 사건은 이 변경과 별개다.

§9에 대한 판단: 조건이 있는 저장 능력도 결과 일부를 수정해 원래 효과와 함께 완료할 수 있고,
수정한 판본은 같은 의미 인터페이스를 가진 부품이다. 이 범위에서 상위 작성자가 하위 분기와
발행을 다시 구성할 필요가 줄었다. 전체 생산자·제어 흐름 이행 또는 모델 생산성 향상을 입증한
것으로 확대하지 않는다.

최종 검증:

- 관련 7개 파일 묶음 **190 통과, 24.44초**.
- 선택기: 변경 모듈 `ibl_v2_repair_graph`는 허브, 전이 시험 **744/802개(93%)**로 판정해
  시스템 포함 backend 전수를 실행한다.
- 첫 전수의 시험은 **11,248 통과·22 건너뜀·80 경고, 893.08초**였지만 종료 코드는 1이다.
  구현·시험 지문은 유지됐으나 실행 중 작성한 가이드 2개와 이 계획 문서가 저장소 변경 감시
  관문에 걸렸다. 시험의 실 저장소 쓰기로 오인하지 않고 작성 작업의 동시 변경으로 식별했다.
  이를 최종 전수 통과로 세지 않으며 문서까지 고정한 상태로 재실행한다.
- 최종 `pytest backend/ -n auto --dist loadfile`: 시스템 포함 **11,248 통과·22 건너뜀·80 경고,
  901.26초**, 종료 코드 **0**. 구현·시험·문서 6개 파일의 시작/종료 지문이 일치했고 저장소 변경
  감시도 통과했다. 최종 수치 기록은 이 실행이 끝난 뒤 작성했다.
- Android 몸 번들 재생성, 어휘/파생 문서 정합, 층 구조·파일 크기·diff 검사 통과.
  기존 비차단 경고는 유지한다. 최종 커밋 관문에서도 저장소 규약을 확인한다.


## 18. 저장 능력의 실패·복구와 내부 결과 수정 (2026-10-28)

§17 다음 경계다. 읽기 실패의 대체 경로를 가진 능력도 저장한 뒤 새 읽기·정규화·정책으로
재조합할 수 있어야 하며, 그 내부 결과 계산을 고칠 때 완료된 발행을 다시 수행하지 않아야 한다.
성공·복구 경로의 의미를 인터페이스에 담는 작업과 실행 기록의 계승 증명은 책임을 구분한다.

### 유지·교체·제거

- 저장 관계에 `fallback`, `recover`, 정상 종료/함수 반환과 후속 적용을 추가했다. try 본문과
  catch·finally의 관계는 실제 입력·콜백에 대입하며, 후속 문장은 보호 영역 밖에서 한 번
  적용한다. 반환은 후속을 건너뛰고 정리는 거친다. 내부 종료 정보는 분석의 값으로 구별하며
  공개 Type.item에 다른 뜻을 덧씌우거나 관측한 실패를 보편 조건으로 저장하지 않는다.
- `ibl_v2_recovery`가 조건부 요구, 값 오류의 실행 검사, 부분 대입의 미확정 상태, 정상 경로
  합류와 정리 후 바인딩을 소유한다. 컴파일러의 기존 try/fallback 판단을 제거하고 본문 검사와
  저장 관계 적용이 같은 전달 함수를 소비한다. 파싱·이름/readonly 검사와 실제 Fault의 catch
  가능 여부·정리 실패 우선순위는 각각 기존 소스 입구와 실행기에 유지한다.
- 효과 의존 투영은 try/fallback 전체 고정을 제거했다. 보호된 계산의 가능한 완료/반환 의존이
  복구 효과의 선택 조건이다. 따라서 그 원인은 보존하고 복구 효과 뒤의 결과 계산은 분리한다.
  하위 함수를 실제 인자로 적용한 의존을 사용하므로 콜백 호출이라는 이유로 모든 정의를 고정하지
  않는다. 본문/복구 결과가 뒤 효과의 입력 또는 도달 조건이면 계속 고정한다.
- finally는 반환·실패에도 실행된다. 본문 결과와 독립적인 정리 효과는 결과 수정 뒤 같은 영수증을
  사용한다. 정리가 부분 대입을 읽으면 가능한 본문/복구 계산을 보수적으로 보존한다. 정리 내부의
  효과 뒤 순수 계산 실패도 수정할 수 있다. 실행기의 suspended·취소/예산 정리 정책은 바꾸지 않는다.
- 불변 판본·권한·CAS·Journal 잠금·호출 좌표·완료 관측은 유지한다. 완결된 읽기 실패 영수증은
  원래 Fault로 재생하고, 실패한 쓰기·승인 대기·완료 불명은 자동 계승하지 않는다. 내부 증명은
  `ibl-repair-frontier/4`로 구분하며 구형 1/2/3을 새 권한으로 자동 승격하지 않는다.
- 의미 판본 지문에 공통 복구 커널을 포함한다. 작성자용 수동 계약·새 어휘·업무별 이름 분기는
  추가하지 않는다. 기존 정의의 일괄 재등록이나 사용자 자료 변경은 수행하지 않는다.

### 인수와 한계

직접 구성과 저장 recover→report→review를 독립 기대값으로 대조한다. 정상/복구 반환,
분기 속 조기 반환, 중첩 복구, 부분 대입, 값으로 받는 try, finally 대입과 중첩 `$error` 복원을
확인한다. 상위 검사에서 하위 `_function`을 막고 본문 없는 라이브러리를 사용한다.

실패 대체 읽기를 기존 gather·등록 Python·표 정책에 연결해 resilient→audit로 저장한다.
상위 등록 때 하위 본문 조회를 차단한다. 저장 후 새 이름의 원천/대체 읽기와 새 등록 Python,
bytes 정책으로 교체한다. 검사/등록의 잎 호출은 0회이며 실제 Python runner와 반환 행의
새 열을 확인한다. 알려진 누락 열은 인터페이스 검사에서 거절한다.

읽기 실패 뒤 발행과 순수 계산 실패가 있는 저장 능력을 두 층 위에서 호출한다. 하위 판본의
결과 계산만 고쳐 명시 함수 참조·복구 CAS로 이어가고, 일반 resume에서도 읽기·쓰기가 각각
한 번만 남는다. 지역 함수·fallback·전달 콜백·중첩 catch·독립 finally와 정리 내부 실패를
각각 검사한다. 실패 선택 원인·발행 대상·호출자 효과에 쓰이는 반환·정리의 부분 대입 입력을
바꾸는 수정은 거절한다. 실패가 catch 뒤 후속 문장에서 발생하면 앞선 catch로 되돌아가지 않는다.

권한·예산·취소·protocol 실패를 catch/fallback의 성공으로 바꾸지 않고, 정리 실행을 확인한다.
부분 실패의 원래 code/kind/partial과 재전파 capability, ForeignRef의 공개 전송 제한도 유지한다.
완료 의무는 기존 런타임 관측을 사용하며 복구가 성공했다는 이유로 의무를 충족시키지 않는다.

보수적 범위: 실패 지점별 대입의 정확한 상태나 임의 계산의 무실패를 증명하지 않는다. try의
부분 대입 타입은 미확정으로 넓히며 복구 효과를 선택하는 보호 계산은 전체 가능한 의존을 보존한다.
비지역 반환이 있는 값 블록, fallback 피연산자에서 바깥 바인딩을 변경하는 형태는 관계 도출
제한을 명시한다. 반복 상태·여러 배치·미확정 콜백·명시 annotation/정의 완료 선언의 내부 수정,
구형 정의 재인증·실행 바인더·공개 소비 표면 전체 이행은 남았다. 실제 외부 서비스와 라이브
활성화·모델의 작성 시간/토큰 개선은 미검증이며 `~turn` 사건은 별개다.

§9 판단: 지원 범위에서는 실패 대체 능력도 하위 본문 없이 새 요구에 적용되고 재조합 결과가
같은 인터페이스로 저장된다. 내부 결과를 수정할 때 상위 작성과 완료된 발행을 다시 만들 필요가
줄었다. 새 부품 이름은 선언만으로 연결한다. 이는 구조·실행 근거이며 전체 재설계나 실제 모델의

## 19. 반복 상태와 회차 사이의 완료 의존 (2026-10-28)

반복하는 능력도 입력·하위 능력에 따라 결과를 전달하는 부품으로 저장하고 재조합한다.
회차 내부의 결과 계산을 수정하기 위해 앞선 외부 효과를 다시 수행하지 않아야 한다. 이번 구간은
§18 다음 경계를 구현한 것이며 §9의 전체 재설계 종료 선언은 아니다.

### 유지·교체·제거

- `repeat` 관계는 횟수/while/until, 본문과 조건의 잠재 인터페이스, 입력 상태를 저장한다.
  공통 `ibl_v2_repeat` 전달 규칙에 실제 입력·콜백을 대입한다. 본문 검사의 기존 한 번 분석과
  모든 변경 변수의 일괄 Unknown 처리를 제거했다. source와 저장 관계가 같은 상태 합류·확대,
  정상 종료/반환·인덱스 범위 복원을 소비한다. 0회는 실행 효과를 만들지 않으며 죽은 소스의
  이름·구문 검사는 유지한다. 1회는 정확한 후속 상태를, 나머지는 보수적인 반복 불변 상태를 쓴다.
- 반복 상태는 사업 값을 실행해 구하지 않는다. 변화하는 scalar 상수/목록 길이를 넓히되 안정된
  레코드 열·콜백·참조 관계는 보존한다. 빈 목록은 요소가 없으므로 누적된 행을 Unknown으로
  지우지 않는다. 상태 전달은 최대 10회, 구조 확대 깊이는 8이며 수렴하지 않는 상태는 Unknown으로
  넓힌다. 이것은 실행 회수나 종료 증명이 아니다. 실제 반복·예산·완료 관측은 실행기의 책임이다.
- 수정 투영에서 repeat 전체 잠금과 순차/여러 배치 each의 결과 전체 잠금을 제거했다.
  회차를 통해 전달되는 상태의 소스 의존이 안정될 때까지 전파하고, 효과 인자·횟수·종료 조건·
  조기 반환 선택이 요구하는 부분을 고정한다. 결과만 만드는 누적 상태는 고정하지 않는다.
  원래 8,192 방문 한계는 유지하며 넘는 증명은 지원 불가로 남긴다.
- 중첩 반복 인수에서 이전 누적값을 읽는 것을 그 생산 계산의 재실행으로 간주하는 반례를 찾았다.
  값의 의존과 현재 식의 평가 의존을 구분했다. 참조 읽기·레코드/목록 조립·피연산자 평가 순서가
  이 구분을 소비한다. 같은 회차에서 실제로 먼저 계산하는 식의 실패/도달 의존은 유지한다.
  함수·each·병렬 가지의 지역 반환은 바깥 반복의 종료로 오인하지 않는다.
- 실행 좌표에 반복 사이트·진입 순번·회차를 연결하고 회차마다 호출 순번 범위를 분리했다.
  완료된 영수증은 원래 좌표와 실제 요청 지문으로 대조한다. 수정 후에도 앞 회차의 순수 계산을
  실제로 마쳐야 다음 회차로 넘어간다. 계산이 다시 실패하면 이후 효과는 시작하지 않는다.
- 새 증명 `ibl-repair-frontier/5`에는 원래 반복과 효과 사이트의 대응이 포함된다. CAS와 원장 잠금
  아래 이 증명이 일치한 호출만 미실행 회차에서 새로 진행할 수 있다. 반복 밖의 미기록 효과,
  효과 삽입/삭제·입력/조건/순서 변경, 실패한 쓰기·승인 대기·완료 불명의 자동 계승은 계속 거절한다.
  `repair.new_effects`가 이 제한을 보고한다. 과거 판본 1~4를 새 권한으로 승격하지 않는다.
- 불변 함수 판본·권한·완료 의무·외부 참조 수명·실패 영수증은 유지한다. 하위 판본을 바꾸면
  상위 인증을 다시 만드는 경계도 유지한다. 상위 정의를 바꾸거나 내부 계약을 수동으로 채우지
  않고 새 하위 인터페이스를 이용해 재인증한다. 새 업무/어휘 이름별 분기나 사용자 문법은 없다.

### 재조합과 수정 인수

읽기 어휘 → 실제 등록 Python → 표 filter/전달 정책 → 발행 → 결과 누적의 rounds를 저장하고,
report→review로 다시 저장한다. 상위 등록 때 하위 본문 조회를 차단하고, 기본 검사에는 본문 없는
라이브러리와 `_function` 차단을 사용한다. 검사·저장 중 도구 실행은 0회이며 누적 행의 열과
읽기/쓰기 효과가 인터페이스에 보존된다.

두 번째 회차의 발행 후 순수 계산이 실패한다. 하위 rounds의 계산만 새 불변 판본으로 저장하고
명시 함수 참조·복구 CAS로 계속하면 이미 끝난 두 읽기·발행은 재생하고 마지막 회차만 실행한다.
일반 resume에서도 외부 효과는 반복되지 않는다. 실제 Python은 순수 재계산할 수 있다.
하위 변경으로 무효화된 report/review 인증도 하위 본문 없이 다시 만든다. 저장 이후 새 이름의
파일 읽기·등록 Python·bytes 정책으로 교체하여 새로운 열을 보존하고 없는 열은 검사에서 거절한다.

추가 인수는 직접/두 층 저장의 독립 기대값, count/while/until·0/1회·중첩 인덱스 복원·조기 반환·
try와 부분 대입, 중첩 함수의 결과 수정, 연속 두 번 수정과 resume, 순차/여러 배치 each·동적 항목을
확인한다. 실패를 고쳤다고 제출해도 여전히 실패하면 다음 회차 효과는 시작하지 않는다.
회차를 두 번 건너 전달되는 효과 입력, 종료 상태 변경, 조기 반환 선택, 반복 뒤 효과가 소비하는
결과/완료의 변경은 거절한다. ForeignRef 전송 제한, 미상 콜백 효과, 하위 완료 의무 미충족도 보존한다.

### 판단과 남은 범위

지원 범위에서는 반복 능력을 하위 구현 없이 새 요구에 적용·저장하고, 내부 결과 수정을 같은
상위 조합으로 완료할 수 있다. 기존 회차의 외부 효과를 반복하지 않고 남은 원래 회차를 마친다.
새 부품은 선언/함수 정의로 연결하며 코어의 업무 이름별 분기가 필요하지 않았다.

임의 수학적 동등성·반복 종료·정확한 회차별 타입/부분 실패 상태는 증명하지 않는다. 관련 필드를 한 상태로 묶었거나 동적 선택으로 정밀도를 잃으면 그 상태를 함께 고정할 수 있다.
효과 좌표와 그 의존을 바꾸는 수정, 불투명 대상·명시 annotation/정의 소유 완료 선언의 내부 수정은 보수적인
경계를 유지한다. 비지역 반환이 있는 값 블록, 나머지 생산자 이행, 구형 저장본 재인증,
실행 바인더와 HTTP/MCP/앱 전체 소비 표면은 여전히 남았다. 실제 서비스 대신 격리 어댑터를 사용했고
Python만 실제 등록 runner를 실행했다. 라이브 활성화·모델 작성 시간/토큰 개선은 미검증이다.
`~turn` 사건은 이 변경에 섞지 않았다.

  종료 4였던 수집 시도는 검사 결과에 세지 않았다. 중첩 누적값 반례와 과거 순차 each 제한 인수를
  실제 수정·완료 인수로 이행한 뒤 실행했다.

  이번 커밋에 포함하지 않는다.


## 20. 값 블록의 비지역 반환과 정상 후속 계산 (2026-10-28)

값을 얻는 블록 안의 `return`도 현재 함수 프레임을 끝낸다. 그 반환값을 대입 결과로 쓰거나,
뒤 문장으로 보내거나, catch/fallback이 복구할 실패로 취급하지 않는다. 이번 구간은 이 의미를
저장된 매개변수 관계와 수정 의존에 연결한다. §9의 전체 재설계 종료 선언은 아니다.

### 유지·교체·제거

- 정상 값·정상 경로의 바인딩과 비지역 반환을 별도로 전달하는 `ibl_v2_exits`를 도입했다.
  정상 경로에만 대입·파이프·호출·다음 문장을 적용하고, 함수/each/병렬 가지의 프레임 끝에서만
  반환과 정상 결과를 합친다. 원문 검사의 return은 정상 흐름에 Never를 돌려주며 실제 반환 타입은
  프레임에 별도로 전달한다. 가능한 가지가 없으면 일반 타입이 아니라 출구 없는 흐름을 전달한다.
  따라서 반환 레코드와 정상 목록이 대입 변수의 타입으로 섞이지 않는다.
- 프레임 결과에서 정상 Unit을 지우던 옛 return 합류 규칙도 제거했다. 정상 종료가 남으면
  Unit이 실제 결과 가능성으로 보존된다. 삼항식·단락 논리는 출구가 아니라 그 안의 순수 값 선택이다.
  기존 유한 가드 증명을 Bool 값에 전달하여, 빈 목록 등으로 증명한 조건이 대입 후에도 유지된다.
  원문과 저장 관계가 같은 규칙을 쓰며 사업 값·콜백·도구를 실행해 추론하지 않는다.
- try/repeat의 중복된 source 반환 수집·내보내기를 공통 전달로 교체했다. 정상 결과에 반환 타입을
  합쳐 대입으로 흘리던 판단, 옛 fallback 타입 합류, 값 블록의 return 탐색에 의한 일괄 거절을 제거했다.
  저장 관계의 if 전용 가지별 후속 본문 복제·특수 continue_call도 제거했다. 이제 일반 continue가
  정상 출구에만 하나의 잠재 후속 인터페이스를 적용한다. 기존 복구·반복 관계는 이를 소비한다.
- fallback은 부분 대입 후 실패를 보수적으로 전달한다. 기존 바인딩 중 왼쪽에서 수정될 수 있는
  값은 복구 경로에서 Unknown으로 넓히며, 정상적으로 이어지는 경로의 상태만 후속에 내보낸다.
  정확한 실패 시점·가능성 자체를 추론하거나 반환을 실패로 변환하지 않는다.
- 수정 투영의 비지역 반환 값 블록 전체 고정을 제거했다. 대입되지 않은 경로는 이전 바인딩을
  유지하고, 반환 경로는 후속 효과를 활성화하지 않는다. 반환값이 호출자 효과에 쓰이면 그 계산은
  고정한다. 파이프의 전달 인자도 호출 효과 의존에 포함한다. finally가 부분 대입 변수를 읽으면
  원래 값과 가능한 변경 계산을 함께 고정한다. 결과만 바꾸는 계산은 기존 영수증으로 이어 간다.
- 수정 증명은 `ibl-repair-frontier/6`이다. 과거 판본 1~5를 새 증명으로 승격하지 않는다.
  CAS·원장 잠금·요청 지문·회차 좌표·원래 효과 사이트 제한·불변 함수 판본은 유지한다.
  실패한 쓰기·승인 대기·완료 불명 영수증을 자동 성공으로 바꾸지 않는다.
- 실행기의 Returned/Fault 구분·finally 우선순위·프레임 범위는 유지했다. 반환값은 정리 전에
  평가되고, 정리 실패는 그 반환보다 우선한다. return이 대입을 건너뛰면 정리는 이전 값을 읽는다.
  finally 안 return 금지와 컨테이너/순수 조건의 문법 제한도 유지한다. 문법이나 업무 이름별 분기,
  작성자가 수동으로 채우는 계약 필드를 추가하지 않았다.

### 재조합과 수정 인수

읽기 어휘 → 실제 등록 Python → 표 filter/인자로 받은 정책 → 게시 → 값 블록 안 조기 반환 →

실행하지 않는다. 하위 읽기와 정책에 따른 행의 열이 상위 반환 레코드까지 전달된다.

게시 뒤 반환 레코드의 순수 계산이 실패해도 정리 효과는 이미 끝난다. prepare의 계산만 새 불변

일반 resume도 같은 결과와 완료 의미를 보존한다. 실제 등록 Python의 순수 재계산은 허용한다.

저장 이후 새로운 파일 읽기 이름·등록 Python·bytes 정책을 넣어 새 열을 보존하고 실행한다.

건너뛴 대입, 하위 완료 의무 미충족, ForeignRef 전송 제한을 확인한다. 반환을 정상 블록 값으로
바꾸어 새 효과를 활성화하거나, 호출자/정리 효과가 읽는 반환·이전 값을 바꾸는 수정은 거절한다.

## 21. case의 첫 일치 선택·반환·완료 경계 (2026-10-28)

저장 능력의 다중 선택도 입력·하위 콜백에 적용하는 관계로 보존한다. 이미 게시한 능력의
분기 내부 결과를 수정할 때 하위 선택 로직을 상위에 다시 쓰거나 게시를 반복하지 않아야 한다.
§20 다음 구현이며 §9의 전체 종료 선언은 아니다.

### 유지·교체·제거

- `ibl_v2_case`의 공통 전달이 선택값 한 번, 순서 있는 비교, 첫 일치 가지와 남은 불일치 경로를
  구별한다. 비교와 가지는 잠재 인터페이스이므로 앞에서 일치가 증명되면 뒤의 요구·효과를
  적용하지 않는다. 소스와 저장 관계는 같은 전달을 사용한다. 컴파일러의 모든 비교를 무조건
  검사하고 모든 결과를 합치던 case 판단을 제거했다. 죽은 소스의 이름·문법과 렉시컬 대입
  진단은 소스 입구에 유지하며, 작성자용 계약 항목은 추가하지 않았다.
- 정상 값·바인딩과 비지역 반환은 기존 Exits로 전달하고 정상 경로에만 후속 관계를 적용한다.
  else 없는 불일치는 Unit이며, 반환 경로를 정상 대입에 섞거나 정상 Unit을 제거하지 않는다.
  후속 관계의 자유 입력 계산도 case의 가지별 대입/반환을 소비한다. 단순 분석 결과 캐시를
  저장하지 않고 실제 입력과 하위 능력에 독립 적용하는 의미 관계를 저장한다.
- 기존 유한 가드와 공통 값 의미를 사용한다. null·Bool·유한 모양의 세밀화와 알려진 비교는
  보존하고, 증명할 수 없는 비교는 가능한 경로를 남긴다. 실제 콜백·도구를 실행하거나 임의
  숫자 계산을 접어 분기를 추측하지 않는다. 선택값 타입의 스냅샷을 사용해 생산자를 재실행하지 않는다.
- 수정 투영에서 case 전체 구현 고정을 제거했다. 각 효과는 선택값과 그 가지까지의 앞선
  비교·완료 의존을 보존한다. 가지의 반환값은 다른 가지의 정상 후속 효과에 섞지 않는다.
  결과만 만드는 계산은 수정할 수 있지만, 호출자 효과의 입력·도달 또는 실패 복구 효과에
  쓰이는 계산은 고정한다. 기존 반복의 회차 의존과 정리의 부분 대입 규칙도 유지한다.
- 수정 증명은 `ibl-repair-frontier/7`이며 과거 1~6을 자동 승격하지 않는다. CAS·원장 잠금·
  요청 지문·회차 좌표·원래 효과 사이트·불변 함수 판본과 완료 관측은 유지했다. 실행기의
  첫 일치 선택·Returned/Fault 구분·finally 우선순위는 변경할 이유가 없어 유지했다.
  실패한 쓰기·승인 대기·완료 불명을 자동 재실행하지 않는다. 업무/부품 이름별 코어 분기는 없다.

### 재조합과 수정 인수

어휘 읽기 → 실제 등록 Python → 표 filter/전달 정책 → 게시 → case의 조기 반환 → 정리의
prepare를 저장하고 report→review로 다시 저장한다. 상위 등록의 하위 본문 조회와 기본 검사의
하위 함수 분석을 차단한다. 검사·저장 중 도구 실행은 없고 행의 열·반환·효과를 인터페이스로 전달한다.

게시 뒤 반환 계산 실패를 prepare의 새 불변 판본으로 수정하고 명시 함수 참조·repair CAS로
계승한다. 일반 resume도 새 결과와 원래 영수증을 보존하며 완료된 읽기·게시·정리는 각각 한 번이다.
상위 정의는 그대로 새 하위 인터페이스로 재인증한다. 저장 이후 새 읽기 어휘·등록 Python·bytes
정책을 넣어 새 열을 보존하고 없는 열을 검사에서 거절한다. 실제 Python의 순수 재계산은 허용한다.

추가 인수는 직접/세 단계 저장 결과, 첫 일치와 중복 when, Bool/숫자 구분·십진수·문자열 정규화,
선택자 한 번 평가·뒤 비교 생략, 조건부 콜백 순수성, null/필드 존재 세밀화, no-match Unit,
가지 바인딩 합류·비지역 반환·파이프·each 프레임·반복 후속 회차를 확인한다. 앞선 비교 실패 뒤
복구 효과, 반환을 건너뛰지 않는 정리, 정리 실패 우선순위, ForeignRef 전송 제한과 미충족 하위
완료 의무도 확인한다. 선택 조건·앞 비교·효과 입력·반환 이후 도달 효과를 바꾸는 수정은 거절한다.

### 판단과 남은 범위

지원 범위에서 저장한 선택 능력을 본문 없이 새 입력/부품으로 조합하고 같은 의미 인터페이스로
축적할 수 있다. 내부 결과 계산만 바꾸어 완료하므로 상위 선택과 완료한 게시를 다시 만들지 않는다.
새 원천·스크립트는 선언으로 연결했으며 코어에 그 이름을 넣지 않았다. 이는 작성 부담을 줄이는
구조적 근거이며 모델의 실제 작성 시간·토큰 감소를 측정한 결과는 아니다.

임의 비교의 참/거짓, 실패 시점별 정확한 상태, 수학적 동등성은 증명하지 않는다. 수정 투영은
관측한 한 가지로 범위를 좁히지 않아 가능한 다른 가지가 같은 계산을 효과에 쓰면 함께 고정할 수 있다.
미확정 호출 대상·명시 annotation/정의 소유 완료 선언의 내부 수정, 나머지 생산자·언어 형태,
구형 저장본 재인증과 실행 바인더·HTTP/MCP/앱 소비 표면 전체 이행은 남는다. 실제 서비스 대신
격리 어댑터를 사용했으며 Python만 실제 등록 runner를 실행했다. 라이브 활성화는 미검증이다.
`~turn` 사건과 다른 세션의 미커밋 변경은 이번 범위에 섞지 않았다.
