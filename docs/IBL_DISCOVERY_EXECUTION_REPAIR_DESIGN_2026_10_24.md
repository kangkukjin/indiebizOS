# 호출 정보의 전달과 확정 코드 실행 수리 설계

작성: 2026-10-24. 상태: **발견·호출 수리(§9)와 확정 코드 위임의 직접 실행(§10) 구현. 나머지는 참고 설계이며 구현 의무가 아니다.** 최초 정본 main 조사 기준 `0573c9bf`.
목적은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)의 품질·완료 시간·전체 토큰 개선이다.
[구조 수렴 설계](IBL_SYSTEM_CONSOLIDATION_DESIGN.md)의 책임 원칙과
[재사용 부품 계약 수리](CALLABLE_COMPONENT_REPAIR_DESIGN_2026_10_18.md)를 이어받는다.
이 문서는 두 최근 수리에서 일반화할 부분을 정한다. 기존 완료 작업을 다시 구현하거나,
다른 수리 계획 전체의 우선순위를 교체하지 않는다.

사용자 후속 판정: 꼭 필요한 수리는 사용법 자체의 부족과 전달 단절을 없애는 것이다.
아래 전체 공통화 계획을 일괄 수행하지 않는다. 실제 구현 범위는 §9와 후속 요청의 §10이 소유한다.

## 1. 결정

**능력을 발견한 자리에서 사용에 필요한 정보를 잃지 않고, 코드로 확정한 의도는 실행까지
그대로 전달한다. 이미 부품이 맡는 준비·검증·복구를 호출자가 매번 다시 조립하지 않는다.**

공통화는 기존 호출 설명의 투영과 기존 실행 경계의 계약에 한정한다. 새 능력 원장, 통합 실행
프레임워크, AI 라우터, 범용 작업 상태 머신은 만들지 않는다. 장치별 검증과 업무 완료 기준은
각 구현에 남긴다. 모든 부품을 동일한 반환 봉투로 바꾸지도 않는다.

이번에 채택하는 후속 수리는 다음 세 가지다.

1. 선택·발견된 부품의 설명을 기존 소유자에서 얻어 공통으로 축약하고, 소비자가 필요한 필드를
   버리지 않게 한다. 길이가 큰 계약 때문에 부품 이름까지 사라지는 문제를 고친다.
2. 드라이버에 적용한 가이드 요약 연결을 같은 기존 경로로 일반 부품에도 사용할 수 있게 하고,
   선언 계약·사용 예·관측 결과·실시간 상태를 구별한다. 부족한 계약은 필요한 부품부터 보완한다.
3. 확정 코드의 입구들이 원문·입력·신원·결과를 보존하는지 공통 회귀로 확인한다.
   최근 예약 수리는 완료된 기반으로 유지한다. 작업계획서의 실행 방식 자동 변경은 하지 않는다.

보편화할 수 있는 것은 **전달·축약·조회·실행 경계의 규칙**이다. 새로운 도구의 단위나 성공
조건까지 자동으로 만들어낼 수는 없다. 그 의미를 한 곳에 정의하면 여러 표면이 함께 사용하는
구조를 목표로 한다.

### 2.1 재현한 두 전달 공백

- `build_execution_memory_from_hint`는 describe 응답의 첫 `definition`만 가져오므로 최상위
  `control_briefs`를 버린다. definition을 다시 투영할 때 `authoring_examples`도 제외한다.
  모델에 필요한 정보가 이미 조회됐어도 선택 액션 문맥에는 도달하지 않는다.
- `_reusable_capabilities`는 후보의 전체 계약 JSON이 5,000자를 넘으면 뒤에서 후보를 제거한다.
  후보가 하나이고 계약이 큰 경우에는 그 후보까지 없어져 블록 자체가 사라진다.
  검색 적합성과 계약의 길이는 다른 문제인데 현재는 긴 계약이 발견을 막을 수 있다.

2026-10-24 프로세스 한정 대체 입력 탐침에서, 선택 액션 응답에 넣은 요약·예제 표식 둘 다
생성 문맥에서 빠졌고, 5,100자 계약 설명을 가진 단일 후보는 None이 됐다. 실제 부품의 발생
빈도나 모델 성능을 측정한 결과는 아니다. 후속 구현에서는 이 두 조건을 정식 회귀로 옮긴다.

## 3. 호출 설명의 공통 전달

### 3.1 책임은 기존 소유자에게 둔다

| 정보 | 소유자 | 공통부의 역할 |
| --- | --- | --- |
| 이름 해소·허용·활성·지역 함수 우선순위 | 기존 액션/함수/Script 조회 경계 | 허용된 대상을 입력받음. 이름 문자열만으로 우회 조회하지 않음 |
| 입력·기본값·조건부 계약·반환·효과 | 실행 계약, 함수 컴파일 결과, Script 원장 | 같은 결과를 표시용으로 투영. 타입이나 효과 재추론 금지 |
| 언제·단위·호출 예·검증 범위·복구 안내 | 기존 설명·authoring_examples·관용구 교재·연결된 가이드 절 | 선택된 부품에 연결. 의미를 복사해 새 원장에 저장하지 않음 |
| 실제 반환 모양 | 기존 관측 반환 기록 | 선언과 구분해 표시. 과거 관측을 항상 보장되는 필드로 바꾸지 않음 |
| 현재 연결·권한·장치 상태 | 실행기의 준비·검증 | 소개만으로 통과했다고 간주하지 않음 |

공통 투영은 `backend/ibl/reusable_catalog.py`의 작은 순수 함수로 시작한다. 이 함수는 이미
해소된 설명·계약·교재를 받아 표시한다. cognition 모듈을 역으로 import하지 않고, 가이드
검색·원장 쓰기·모델 호출·실행 여부 판단을 하지 않는다. 파일 크기나 의존성 때문에 분리가
필요할 때만 기존 층 안에 형제 모듈을 둔다. 새 서비스와 저장 스키마를 만들지 않는다.

### 3.2 소개의 깊이를 목적에 맞춘다

전체 사전은 현재의 짧은 목차를 유지한다. 모든 액션 계약을 매 턴 펼치지 않는다.
기존 검색·명시 선택으로 좁혀진 후보에는 다음을 제공한다.

- 정확한 호출 이름, 용도, 필수·선택 입력과 핵심 반환, 효과의 미확정 여부.
- 기존에 있는 호출 예와 필요한 가이드 요약. 객체 인자는 예에서 내부 모양을 보여준다.
- 이 호출이 내부에서 확인하는 범위와 호출자가 별도로 결정해야 하는 부분.
- 요약 밖의 동작·생략된 계약을 여는 기존 describe 또는 Script list의 정확한 인수.

별도의 `ready:true` 같은 사용 가능 인증은 만들지 않는다. 계약 있음·소개됨·실행 가능·업무 완료는
서로 다른 사실이다. 이름만 알거나 계약이 없으면 그 상태와 확인 경로를 표시한다.

명시 describe와 Script 상세 조회는 기존 전체 계약의 접근성을 유지한다. 요약 도입을 이유로
상세 필드를 제거하지 않는다. 함수 정의의 본문은 지금처럼 필요할 때만 연다.

### 3.3 예산은 정보 단위로 적용한다

현재 후보 블록의 5,000자, 가이드 요약의 절당 1,800자·합계 4,000자 상한을 우선 유지한다.
새 상시 블록이나 별도 예산을 추가하지 않는다.

1. 검색 순위대로 후보의 이름·짧은 용도·상세 조회 경로를 먼저 확보한다.
2. 남은 예산에 계약 요약, 예제, 가이드 절을 보충한다. 중복 가이드는 기존 방식으로 한 번만 싣는다.
3. 긴 계약 때문에 단일 최상위 후보 전체를 버리지 않는다. 기본 소개도 예산을 초과하는 경우에는
   더 낮은 후보를 생략하며, 계약 상세가 생략됐음을 알린다.
4. JSON 문자열·코드 예·가이드 절의 중간을 자르지 않는다. 조건·효과·복구 설명 일부를 떼어
   안전한 전체 계약인 것처럼 보이지 않는다. 완결된 단위로 넣거나 통째로 생략하고 조회 경로를 남긴다.
5. 특정 op가 명시됐을 때만 기존 `ibl_callable_contract.selected` 의미로 조건부 계약을 고른다.
   자연어에서 op를 추측하거나 첫 variant를 기본 호출법으로 가르치지 않는다.

예산의 최종 판정은 실제 직렬화한 블록 크기로 한다. 후보 배열만 재고 덧붙인 필드를 빠뜨리지
않는다. 문자 예산은 토큰 절감의 증명이 아니며 모델 비용은 별도로 측정한다.

### 3.4 소비자를 연결하는 순서

1. `model_result_view.describe_actions`의 설명과 최상위 부가 정보를
   `ibl_usage_rag.build_execution_memory_from_hint`가 함께 소비하게 한다.
   `authoring_examples`도 현재 계약에서 가져온다. 거절된 액션·동명 지역 함수에 외부 교재를 붙이지 않는다.
2. `reusable_catalog.candidates`는 지금처럼 기존 정의에서 검색하고 계약을 해소한다.
   `_reusable_capabilities`의 전체 계약 크기 기반 pop을 공통 요약·예산 처리로 교체한다.
   모든 후보를 사전 컴파일하거나 별도 의미 검색 모델을 도입하지 않는다.
3. 관용구 회상·상시 교재는 이미 있는 호출·언제·반환·연결 표시를 유지한다. 같은 필드를
   새 공통 함수가 다시 추론하지 않도록 투영 결과를 연결한다. 상시 소개에는 상세 계약을 추가하지 않는다.
4. `script_ops.op_list`의 명시 id/query 및 기존 장치·조작면 소개는 같은 가이드 절과 계약을
   소비한다. 전체 Script 목록의 기본 응답에 모든 가이드 본문을 늘어놓지 않는다.

기존 `guide_registry.control_briefs`와 `callable_control_briefs`는 이미 호출명→가이드 절을
데이터로 해소하므로 일반 부품에도 재사용할 수 있다. 첫 구현에서는 기존 `control_callables`·
`control_brief_section` 필드를 그대로 쓴다. 이름이 좁다는 이유만으로 새 동의 필드나 두 번째
색인을 만들지 않는다. 이름 정리가 필요해지면 모든 소비자와 데이터를 한 번에 이관하는 별도
범위로 판단한다. 기능 수리의 선행 조건은 아니다.

## 4. 내부 의미가 부족한 부품의 보완

`Android제어(대상, 요청)`의 요청이 Record라는 사실만으로 action·단위·결과 확인법은 알 수
없다. 일반 Script의 설정 객체도 같은 문제를 가진다. 공통 전달 수리와 의미 보완을 구별한다.

첫 비교 표본은 기존 Android/PC 드라이버, 일반 IBL 액션 하나, 명시 입력·반환을 가진 관용구,
단순 파일/자료 처리 Script로 잡는다. 계약이 이미 충분한 부품은 수정하지 않는다. 계약이 없는
부품은 실제 입력·반환·효과를 확인한 범위만 기존 callable_contract에 넣고 같은 실행 경계에서
검사한다. description만 읽어 자동 계약을 생성하지 않는다.

동작별 입력·반환을 현재 params/variants로 표현할 수 있으면 그 계약을 사용한다. 중첩 요청의
단위·전제·물리 검증을 위해 새 타입 체계를 만들지는 않는다. 해당 의미는 짧은 예제와 가이드에
남기고 구현의 검사와 대조한다. 단순 `Record → Record` 등록은 정보 부족 해결로 세지 않는다.

드라이버 내부의 현재값 조회·권한 검사·재검증을 호출자가 반복할 필요가 없는 범위는 기존
가이드 절에 명시한다. 반대로 사용자가 선택할 출력 장치, 목표값 계산에 필요한 조회, 독립적인
업무 검수는 유지한다. “조회 횟수를 줄여라”라는 일괄 최적화는 하지 않는다.

새 부품마다 반드시 남는 일은 실제 의미 정의와 검증이다. 공통화로 없애는 것은 같은 계약을
소개·조회·실행 표면마다 별도로 다시 작성하고 고치는 일이다.

## 5. 확정한 의도의 직접 실행

### 5.1 두 실행 요청의 경계

| 요청의 계약 | 실행 | AI의 자리 |
| --- | --- | --- |
| 코드·판본·명시 입력이 실행 대상으로 확정됨 | 기존 실행 경계로 원문과 값을 전달 | 코드 안에 명시된 판단·생성·위임, 또는 사용자에게 승인된 수정 |
| 목표·지시를 해석해 방법을 결정해야 함 | 기존 에이전트 위임 경로 | 계획·작성·판단을 수행 |

코드를 포함한 채팅이라고 자동 실행으로 바꾸지 않고, 소유 에이전트가 있다고 코드를 채팅으로
되돌리지 않는다. 분류는 기존 API·저장 항목의 명시 계약을 따른다. 새 AI 분류기나 `auto` 모드는 없다.

### 5.2 공통 불변조건과 서로 다른 실행 문맥

- 코드·판본·inputs를 보존한다. 채팅용 문자열로 포장해 다시 작성하게 하거나 입력을 산문에서 복원하지 않는다.
- 실행 소유자·프로젝트·권한·origin·task ID를 기존 표면의 해소 경로로 유지한다.
  입력에 적힌 신원만 믿어 권한을 새로 주지 않으며, 앱 실행을 scheduler로 위장하지 않는다.
- 실행 전 구문·타입·권한·현재 상태 검사, 기존 승인·감독·취소는 유지한다.
  직접 실행은 검사를 생략하거나 내부 모델 호출을 0으로 만든다는 뜻이 아니다.
- 접수·진행·종료·업무 확인을 구별하고 실행 결과·원 작업 참조를 보존한다.
  위임 접수 성공을 위임 목표 달성으로 바꾸지 않는다.
- 표시·알림 실패, 응답 유실, 불명확한 변경을 다른 통로의 새 실행으로 대체하지 않는다.
  기존 resume·작업 조회·실패 안내를 사용한다. 이 원칙을 분산 환경의 exactly-once 보장으로 주장하지 않는다.

이를 위해 새 실행 래퍼를 모든 곳에 끼우지 않는다. 예약은 `ibl_scheduled.execute_scheduled`,
앱·수동 표면은 `/ibl/execute`, 저장 함수는 기존 런타임 경로를 유지한다. 이들이 이미 공유하는
`ibl_v2_entry`와 실행 계약을 사용하며, 중복된 처리에서 실제 의미 차이가 확인될 때만 그
작은 부분을 기존 소유자로 옮긴다. 표면별 신원·승인·수명 처리는 별도 책임이다.

### 5.3 작업계획서의 선택

현재 계획서는 지시·코드·이전 결과를 에이전트에게 주고, 완료 텍스트를 받아 다음 단계를
진행한다. 코드만 실행하도록 바꾸면 description의 추가 의무, 이전 결과의 해석, 완료 콜백과
실패 처리가 사라질 수 있다. `pipeline != ""`만으로 경로를 바꾸는 수리는 하지 않는다.

이번 선택은 **현행 계획서를 판단 위임으로 유지하고, 확정 코드 절차는 기존 IBL 프로그램·
저장 함수·예약으로 표현**하는 것이다. 새 작성 교재의 해당 설명을 이 경계에 맞춰 교체한다.
판단이 필요한 중간 단계는 IBL의 기존 명시 위임을 사용한다. 기존 계획서의 자동 변환은 없다.

혼합 계획서 자체가 직접 코드 단계를 반드시 소유해야 하는 요구가 확인되면 후속 설계에서만
명시 실행 종류, 판본·inputs, 구조화된 결과, 완료·재개 수명을 함께 다룬다. 이는 조건문 하나의
수리가 아니므로 이번 최소 수리 범위에서 제외한다. 텍스트 접두어로 완료를 판단하는 현 콜백도
그 후속 검토 대상이며, 코드 재해석 문제를 이유로 계획서 전체 엔진을 재작성하지 않는다.

### 7.2 효과 확인과 복잡성 제한

같은 요구·초기 상태에서 일반 부품과 드라이버의 첫 호출까지 추가 조회·실패·모델 왕복,
최종 결과 품질, 완료 시간, 전체 토큰을 비교한다. 예약은 순수 코드의 실행 시작 전 모델 호출
유무와 창 비가용 시 동작을 별도로 본다. 소개가 길어져 다른 작업 비용이 증가하는지도 확인한다.
조회 0회 자체를 목표로 삼지 않는다. 미상 계약의 정당한 조회는 남겨야 한다.

다음 비용이 필요해지면 범위를 줄인다.

- 일반적인 중첩 타입 추론기·자동 계약 생성기·새 검색/선택 모델이 필요함.
- 기존 원장 옆에 같은 의미의 새 원장을 유지해야 함.
- 표면별 실행 수명을 하나로 합쳐야만 적용할 수 있음.
- 모든 스크립트·계획서를 선행 이관해야 작은 공통 수리가 작동함.

그 경우 1단계 전달 수리와 기존 호출 요약 재사용까지만 진행한다. 남은 의미는 원 부품의 짧은
가이드에 두고, 계획서 자동 직접 실행은 계속 보류한다. 복잡한 일반화보다 책임이 분명한 작은
공통부를 선택한다.

## 8. 이번 설계에서 확인한 범위

최근 수리 `240975df`·`95d8a521`·`0573c9bf`와 위 호출 경로를 읽었다. §2.1의 대체 입력
탐침 두 가지를 수행했다. 앞선 비교 단계에서 예약·현재 문법 표면 관련 기존 시험 17개는
통과했다. 이는 이번 후속 설계의 구현 완료나 전체 실행 표면 검증을 뜻하지 않는다.
새 장치 실기·모델 비교·전체 토큰 측정·전수 회귀는 수행하지 않았다.

최초 설계 단계의 산출물은 문서와 기존 설계 허브의 연결이었다. 그 단계에서는 런타임·어휘·
원장·사용자 데이터를 수정하지 않았다. 이후 사용자가 좁힌 구현 범위와 검증은 §9에 기록한다.

## 9. 발견에서 호출까지의 최소 수리 (2026-10-24)

이번 구현은 새 통합 설명 체계를 만들지 않고 두 전달 공백과 일반 부품의 호출 안내를 고친다.

- 선택 액션: 기존 describe 응답의 `authoring_examples`, 관측 반환·관측 표시와 최상위
  `control_briefs`를 선택 문맥에 보존한다. 조회가 거절되면 요약도 제공하지 않는다.
- 부품 후보: `reusable_catalog.discovery_payload`가 기존 선택 후보의 이름·정확한 상세 조회
  인수를 먼저 확보한다. 5,000자 JSON 예산 안에서 짧은 가이드 절을 먼저, 설명·전체 계약·호출
  골격을 이어 제공한다. 맞지 않는 상세는 통째로 생략하고 `details_omitted`에 표시한다.
  계약 일부만 잘라 필수 조건을 감추지 않는다. `contract_known`은 원 계약 존재 여부 그대로다.
- 일반 Script: `폴더변화`를 기존 `folder_survey.md`의 빠른 호출 절에 연결했다. 입력 예,
  items/count/omitted의 구분, 첫 조회의 기준 생성, commit:false의 상태 쓰기, ack 전 재조회와
  완료 후 승인 조건을 한 번에 제공한다. 새 계약을 자동 생성하거나 Script 원장을 변경하지 않았다.
- 받은 계약·요약만으로 충분한 범위는 그대로 호출하며, 빠진 입력·조건만 상세 조회한다.
  스크립트별 구현, 관용구 상시 소개, 전체 액션 목차, 예약·계획서 실행 경로는 바꾸지 않았다.

직접 관련 시험 99개 통과: 선택 액션의 예제·가이드 전달과 거절, 긴 계약의 후보 보존·정확한
조회·완결된 계약, 예산·후보 순위, 드라이버/일반 Script 예제 컴파일, 실제 폴더변화 부품을
임시 폴더·임시 상태 원장에서 실행한 초기 기준→변화/생략→재조회→ack 의미를 확인했다.
선택기는 관련 시험 파일 715/774개(92%)와 `guide_registry` 허브를 지목해 일반 종합 회귀를
실행했다. `.venv/bin/python3 -m pytest backend/ -m "not system" -n auto --dist loadfile`:
11,612 통과·1 건너뜀(214.22초). `build_ibl_nodes.py --check`(가이드 배선·파생물 포함),
`check_backend_layers.py`, Android 몸 번들 재생성도 통과했다.
실행기·언어·어휘 계약은 변경하지 않아 별도 `system` 묶음은 재실행하지 않았다. 실제 모델의
조회 횟수·전체 토큰·완료 시간 개선은 측정하지 않았으며 일반 Script 전체 계약 이관으로
보고하지 않는다.

## 10. 확정 코드 위임의 직접 실행 (2026-10-24)

후속 확인에서 공개 어휘 `others:delegate`의 `mode:workflow`가 코드를 자연어 메시지로
포장해 다시 AI에 맡기는 결함을 확인했다. 이 모드의 실행 의도는 이미 확정되어 있으므로
추가 분류기·실행기를 만들지 않고 기존 접수·큐·원장을 유지한 채 수신 분기를 수리했다.

- `routing_system`은 원문을 변경하지 않고 판본을 헤더/작성 문맥에 고정해 명시 inputs와 함께
  기존 `execute_call_agent`에 전달한다. 배열은 판본 1이며 v2 입력과 섞지 않는다.
- 기존 자식 task 생성·순환 차단·봉투를 재사용한다. 원문과 실행 주체, 수리 작업공간은 같은
  `tasks.delegation_context`에 보존하고 큐에는 명시 실행 종류만 추가한다. 새 원장·스레드는 없다.
- 대상 상주 러너가 호출자·요청·대상 권한의 교집합에서 직접 실행한다. 순수 코드에는 AI·창
  연결이 필요 없다. v2 실패를 v1이나 AI로 폴백하지 않는다. v2 실행 중 취소 콜백과 기존 작업
  취소 상태를 잇는다. v1 배열은 기존 실행기를 유지하므로 실행 중 개별 도구의 취소 지원은
  기존 한계 그대로이며 시작 전 취소는 두 판본 모두 확인한다.
- 결과·실행 영수증을 보고보다 먼저 저장한다. 중복 배달은 결과만 재보고한다. 시작 표식만
  있고 결과가 없으면 효과가 불명확하므로 자동 재실행하지 않는다. 기존 큐를 재기동 후
  자동 재접수하는 새 복구기는 만들지 않았다.
- `message`는 기록용 설명이며 실행 지시가 아니다. 명시 AI 위임은 실행 코드 안에서 한다.
  동기 위임은 코드가 결과를 기다리고, 비동기 자식은 접수증으로 별도 조회한다. 비동기 보고를
  수신했다고 원 프로그램을 재실행하거나 대상 AI를 암묵적으로 호출하지 않는다.
- 예약/위임 가이드의 자연어 pipeline·창 의존 안내를 정렬하고 은퇴 문구 관문에 등록했다.
  작업계획서의 비공개 잔여 구현과 cross/system/task workflow 미지원 계약은 변경하지 않았다.

검증: 새 실행 경계 시험 13개를 포함한 관련 시험 81개 통과. 선택기는 전이 시험
239/775개(31%)를 골랐으며, 공통 러너·권한 전달 변경이라 일반 종합 회귀까지 실행했다.
최초 종합 검사에서 용례 재검토 원장과 새 시험의 직접 실행 진입점 관문 2건이 실패했다.
용례 55건을 읽고 같은 프로젝트의 한정 이름 처리를 검증했으며, 원장과 pytest 진입점을
갱신한 뒤 최종 일반 회귀 **11,625 통과·1 건너뜀(197.94초)**.
`test_python_libraries.py`, `test_vocabulary_archive.py`, `test_vocabulary_bundle_split.py`,
