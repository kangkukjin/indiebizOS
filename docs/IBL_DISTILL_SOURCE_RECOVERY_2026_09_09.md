# 증류 구문 실패를 성공 원문으로 복구

## 문제와 원인

2026-09-09 에피소드 3219(AI 동향), 3223(부동산), 3224(유튜브 팁)는 모두
GoalEval `ACHIEVED`였지만 대표 용례 증류가 구문 관문에서 끝났다.

- 3219: 반성기가 액션 호출 뒤에 `.phrases`를 직접 붙였다. 원문은 변수에
  할당한 뒤 다음 문장에서 그 변수의 필드를 읽었다.
- 3223: 뒤 문장의 `$m덕진` 참조는 남겼지만 그 변수를 생산하는 호출을 빼었다.
- 3224: `each.do` 안의 중첩 코드 문자열을 다시 작성하다 따옴표를 깨뜨렸다.

실행기의 실패가 아니라 **성공 코드를 다시 쓰는 증류기의 손상**이다. 기존 할당
앞점 복원은 좌변만 떨어진 경우를 다뤄, 이 세 형태를 고치지 못했다. 구문 검사는
오염된 코드의 적재를 올바르게 막았지만 오류를 돌려주고 복구하는 경로가 없었다.
또 `check:true` 호출은 실행되지 않았는데도 `success:true`여서 성공 사례에 섞였다.

주행 기록은 이미 별도로 남았다. 이 사건을 메모리 전체의 유실로 읽으면 안 된다.

## 변경

`ibl_usage_rag.distill_experience`의 정상 증류와 기존 적재 관문은 유지한다.
입력 필터에서는 `check:true`를 빼고, 최초 프롬프트는 변수 생산자·액션 뒤 필드
접근·중첩 따옴표 보존을 명시한다.

구문 오류가 기존 복원으로 해결되지 않으면 `ibl_distill_gates._recover_distill_selection`이
경량 모델에 **한 번만** 원문 선택을 묻는다. 응답은 코드가 아니라 `call_ids`다.
번호가 가리키는 성공 호출 전체를 원래 순서의 독립 문장으로 연결한다. 모델이
`code`를 함께 보내도 사용하지 않는다. 번호의 범위·형식·중복·순서도 검사한다.

복구본은 다시 파싱하고, 공개 호출 서명 API(`workflow_contract.call_signature`)로
미할당 인자 변수를 검사하며, `files`가 필요한 참조도 거절한다. 이어 기존 머리
접지·합성 접지·어휘 실존·인자·원장 입구 관문을 모두 지난다. 자동 작명은 하지 않는다.

동일한 의도를 독립적으로 충족할 원문이 없으면 빈 선택으로 끝낸다. 준비·알림만
하는 코드를 보고서 작성 용례로 등록하거나, 검사를 느슨하게 하여 성공으로 만들지 않는다.
정상 증류에는 추가 모델 호출이 없다. 복구 실패도 반복 호출하지 않는다.

  복구 뒤 접지·인자 거절, 정상 경로의 추가 호출 없음.
