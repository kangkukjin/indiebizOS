# 에피소드 3176의 시간·토큰 재진단

2026-09-08. 사용자의 질문: "왜 제대로 진단을 못하는가, 로그가 부족한가, 계속 고쳐도 왜 좋아지지 않는가?"

## 앞선 설명의 정정

44,326 출력 토큰을 주로 받아쓰기·본문 작성 증가로 해석한 것은 잘못이었다. 그중 22,630은 추론 토큰이다. `table:ai`가 원본 행을 다시 작성한다고 지적한 것도 기존 색인 병합 구현과 실제 `_merge:index` 결과를 먼저 확인하지 않은 오진이었다. 주 모델이 후속 계산용 행을 다시 작성한 사실은 있지만, 그것으로 총시간 증가를 설명할 수는 없다.

총계에서 바로 원인을 추정하고, 실행 원문·프로바이더 응답·기존 수리를 끝까지 연결하지 않은 진단 과정의 문제다. 로그 결함은 아래에 별도로 기록한다. 로그 부족만을 이유로 삼지 않는다.

## 동일 모델·설정에서 실제로 관측한 것

두 세션은 `claude-opus-5`, `effort:high`다. 원본 Claude JSONL을 응답 ID별로 묶고, 반복되는 usage의 최댓값을 취했다. 합계는 각각 에피소드의 주 모델 usage와 정확히 일치했다. 본문·비공개 추론은 감사 산출물에 저장하지 않았다.

추론 토큰은 모델이 보고한 계수다. 추가 추론이 필요한 조사·해석인지, 구조 혼란·반복 검토인지 세부 원인은 이 계수만으로 판정할 수 없다. 내용은 비공개이며 추정해서 복원하지 않았다. 시각은 클라이언트에서 완료된 블록을 받은 시각이다. 서버 대기·첫 토큰·순수 추론 시간을 분리하는 시계가 아니다.

## 58초 단계와 4분 작성 구간

최신 호출 event 50의 IBL 전체는 58.354초, 내부 `table:ai` step은 58.177초다. 에피소드에는 없던 하위 호출 로그가 `data/backend_keeper.log`에 남아 있었다. 해당 IBL 코드 앞뒤의 연속 로그에서:

- 원샷 생성: **53.379초**, 출력 **4,248토큰**. 입력 신규 2 + 캐시 생성 19,514. 시스템 설명 391자·사용자 메시지 23,227자.
- criteria 평가: **3.976초**, 출력 **154토큰**. 입력 신규 2 + 캐시 생성 8,911. 판정 pass, 재시도 없음.
- 나머지 로컬 처리·호출 준비 등은 두 모델 시간과 step 시간 차이인 약 0.822초다. 세부 원인은 미분리.
- 결과는 `_merge:index`, 60행→15행. 원본 행 보존 경로가 동작했다. 색인 모드만으로 모델이 불필요한 필드를 단 하나도 출력하지 않았다고까지 증명하지는 않는다.

위 4,402 출력 토큰은 주 실행 모델의 44,326토큰 **밖**이다. IBL 실행 시간은 주 실행 루프 시간 **안**이다. 모델 토큰은 주체별로 더할 수 있지만 중첩 시간은 더하면 이중 계산이다. 원샷의 추론/비추론 내역은 이 산문 로그에 없다.

계산 결과를 받은 17:50:11 무렵부터 보고서·지역 DB 저장 호출이 도착한 17:54:12까지 약 4분이 걸렸다. 해당 단일 주 모델 응답은 **18,061토큰(추론 5,833 + 비추론 12,228)**으로 전체 출력의 40.7%다. 첫 추론 블록 수신은 17:51:51, 도구 인자 완성은 17:54:12였다. 저장 도구의 파일 쓰기가 4분 걸린 것이 아니다. 이 구간을 전부 낭비라고 판정할 근거도 없다. 보고서 작성과 DB 내용 생성이라는 실제 산출이 포함된다.

## 로그의 실제 결함과 이번 수리

1. **블록을 라운드로 집계:** Claude의 `assistant` 이벤트는 같은 응답 ID로 thinking·text·tool_use 블록을 나눠 보냈다. 어댑터가 각 이벤트를 새 라운드로 세었다. ID별 한 번만 집계하고 턴 경계에서 ID 집합을 초기화한다. ID 없는 옛 이벤트는 종전대로 개별 계수한다.
2. **추론 내역 소실:** 벤더가 제공한 추론 계수를 정규화 단계가 버렸다. 공용 usage 정규화에서 `reasoning`을 선택적 출력 부분집합으로 보존한다. 부재는 0으로 추정하지 않는다. Claude 응답별 `model.response_snapshot`에 ID·모델·역할·블록 종류·입출력·캐시·추론 계수를 기록한다. 본문은 기록하지 않는다.
3. **MCP 재진입 원샷 누락:** `/ibl/execute`는 부모 episode ID를 trajectory로 복원하지만 메모리상의 `_Episode` 객체는 없다. `notify_round/notify_usage`가 그 객체가 없다는 이유로 기록을 건너뛰었다. 이제 메모리 steps 추가와 영속 trajectory 기록을 분리해 같은 에피소드에 남긴다.

스냅샷은 누적값이므로 `(run_id, provider, role, response_id)`로 묶어 각 계수의 최댓값을 읽는다. 스냅샷끼리 또는 기존 `model.usage`와 합산하지 않는다. 중단 전까지 받은 내역도 남지만 마지막 수신값이 서버 최종 사용량이라고 보장하지 않는다. 기존 턴 토큰 합산기를 스냅샷으로 다시 적립하지 않았으며, 프로세스별 in-memory 합계는 전체 작업 총비용이 아닐 수 있다. 전체 작업 감사에는 연결된 `model.usage`를 주체별로 읽는다.

과거 DB의 라운드·usage를 추정치로 덮어쓰지 않았다. 원본 보존 + 별도 정정 감사다. 이번 변경은 계측만 바꾸며 프롬프트·모델·관용구·업무 절차는 변경하지 않는다.

## 왜 수리와 전체 개선이 연결되지 않았나

- 언어 오류 제거는 재현된 문장의 정확성을 개선한다. 실제 업무 전체 시간의 큰 비중은 주 모델의 판단·생성에 있으며, 문장 회귀 통과가 그 비용 감소를 보장하지 않는다.
- 작은 관용구 비교는 프로그램 전체 생성·수리 시험이었다. 실제 앱의 다단계 자율 실행과 다르며, 실험의 medium과 이번 실전의 high도 다르다. 상시 제공의 순효용을 입증한 실전 비교는 없다.
- 서로 다른 도시·자료·작성 내용을 가진 오전/오후 보고서를 변경 전후 대조군처럼 사용했다. 실제 응답 수 감소는 관측되지만 특정 수리의 인과 효과는 분리할 수 없다.
- 총계와 자동 `ACHIEVED` 중심의 해석은 비용 증가 위치와 결과의 근거 오류를 놓친다. 수정된 층에서 실제 비용이 줄었는지 확인하는 절차가 부족했다.

이 기록은 IBL이 무의미하다는 증거도, 수리가 전부 무효라는 증거도 아니다. 정확성·왕복·생성·결과 품질을 서로 대신 사용한 평가가 문제였다. 다음 개선은 같은 자료·같은 앱 실행 경로·같은 모델 설정에서 한 요소씩 바꾸고, 설계에 쓰지 않은 여러 종류의 과제에서도 품질·전체 시간·추론/비추론·캐시·하위 AI를 비교해야 한다. 추론량이 늘었다는 이유로 무조건 추론을 줄이거나, 호출률을 올리려 관용구를 강제하지 않는다.
