# ep3176 원샷 지연 원인과 8회 재생 실험

2026-09-08. 질문: 원샷이 왜 53초나 걸리는가, 이대로면 쓰는 것이 손해 아닌가?

## 판정

주된 시간은 CLI 기동이나 원본 행 받아쓰기가 아니라 **별도의 Opus 5 의미 판단·추론**에 쓰였다. 원샷은 API 응답 한 번이라는 뜻이지, 작은 연산이라는 뜻이 아니다. 60행을 판별하는 모델 작업이 IBL 문장 안으로 이동했다. 이를 주 모델이 직접 처리했을 때보다 싼지는 이번 실험만으로 판정할 수 없다.

추론 강도와 시스템 프롬프트 구성에 줄일 수 있는 비용이 있었다. 그러나 추론을 끄는 방법은 실제 선별 오류를 만들었고, 다른 빠른 설정도 이상치 경고를 잃었다. 사용자 목표가 **품질을 유지하는 시간·토큰 절감**이므로 제품 설정을 일괄 변경하지 않았다. 부동산 전용 어휘·분기·프롬프트 규칙도 추가하지 않았다.

## 원본 세션 확인

원본 세션은 `~/.claude/projects/-Users-kangkukjin-Desktop-AI-indiebizOS-backend/ecc515b4-5037-4873-8607-08d9990c0f08.jsonl`이다. 생성과 평가의 비용을 구별한다.

| 원본 단계 | 벽시계 시간 | 출력 | 추론 | 비추론 |
|---|---:|---:|---:|---:|
| 60행 → 후보 15행 생성 | 53.379초 | 4,248 | 3,436 | 812 |
| criteria 평가 | 3.976초 | 154 | 0 | 154 |

생성 출력의 **80.9%가 추론**이다. 실제 출력 JSON의 모든 행은 `_i`, `reason` 두 필드만 가졌다. 원본 title/meta/url 등을 AI가 다시 쓰지 않았고 기존 색인 병합이 정상 작동했다.

원본 사용자 메시지 시각부터 추론 블록 완료까지 46.065초, 그 후 텍스트 완료까지 7.064초였다. 앞 구간에는 초기 대기·입력 처리도 포함되므로 46초 전부를 순수 추론 시간이라고 부르지 않는다. 전체 `table:ai` step 58.177초에서 생성·평가 시간을 빼면 0.822초다. 이 호출의 큰 지연을 원샷 전역 잠금 대기로 설명할 여지는 없다.

`model_resolver._provider_from_desc(..., oneshot=True)`는 `disable_thinking=True`를 설정하지만 Claude Code 어댑터는 이 속성을 해석하지 않는다. 주석도 지원하는 공급자만 해석한다고 적혀 있다. 실제 Claude 설정은 `high`였다. 따라서 내부의 “짧은 JSON 원샷” 가정이 모든 공급자의 실제 추론 설정을 설명하지 못했다. 그렇다고 이제 이 플래그를 모든 원샷에 강제하는 것이 올바른 수리는 아니다. 아래 품질 저하가 그 반증이다.

## 실험 방법

**앱 전체 보고서를 다시 실행한 실험이 아니다.** 원본의 23,227자 사용자 메시지, 60행, 지시, 391자 시스템 메시지를 고정하고 원샷 생성 부분만 재생했다. 외부 검색·행 수집·주 모델·후속 보고서 작성·criteria 평가는 재생하지 않았다.

- 모델 `claude-opus-5`, Claude Code 2.1.260, 앱과 같은 중앙 OAuth 인증 경로·backend cwd.
- 앱의 `ClaudeCodeProvider._build_command(stream=True, tools_mode="none", system_prompt_file=...)`와 `_build_env()`를 사용. 내장 도구와 MCP 목록 모두 빈 배열임을 init 이벤트로 확인.
- 모든 조건에 `--include-partial-messages`를 추가해 수신 시각을 단조 시계로 기록. 결과 본문·비공개 추론은 커밋하지 않는다.
- 기본 비교 조건은 `CLAUDE_CODE_EFFORT_LEVEL=high`, `MAX_THINKING_TOKENS` 미설정. 낮은 추론 조건만 effort `low`, 비활성 조건만 `MAX_THINKING_TOKENS=0`.
- 프롬프트 교체 조건은 high를 유지하고 `--append-system-prompt-file`을 `--system-prompt-file`로 바꿨다. 앱이 준 시스템 메시지 자체는 그대로다.
- 순서: off1 → baseline1 → off2 → baseline2 → high_replace1 → low1 → low2 → high_replace2. 순차 실행, 조건별 2회. 순서는 무작위화하지 않았다. 각 조건의 첫 회는 입력 캐시 생성, 둘째는 캐시 읽기였다.
- 공급자 `duration_api_ms`가 일부 실행에서 로컬 전체 시간보다 크므로 단계 합산에 쓰지 않는다. 시간 비교는 한 로컬 단조 시계의 값이다.

[감사 JSON](experiments/episode3176_oneshot_latency.json)에 원본/프롬프트 SHA, 실행 순서, 세션 ID, 계수, 수신 시각, 선택 색인과 검사 결과를 보존했다. 로컬 재생 도구는 `outputs/probe_oneshot_latency.py`, 원본 이벤트는 `outputs/oneshot_latency_probe/`에 있다(ignored, 커밋 대상 아님). 각 재생 세션은 Claude 원본 세션 저장소에도 남는다. 원본 입력을 확보하지 않은 환경에서 동일 입력 재생이 가능하다고 주장하지 않는다.

## 결과와 품질

| 설정 | 시간 2회 | 출력 토큰 2회 | 그중 추론 2회 | 관찰한 품질 |
|---|---|---|---|---|
| 기존 high + 기본 설명 추가 | 37.135 / 42.043초 | 2,906 / 3,326 | 2,119 / 2,459 | 명확한 13항목 모두 포함, 애매한 항목 선택은 서로 다름. 면적 이상 확인 경고 유지 |
| 추론 비활성 | 9.574 / 9.257초 | 570 / 584 | 0 / 0 | 두 번 모두 명확한 오선별. 첫 회 필수 항목 1개 누락 |
| low + 기본 설명 추가 | 15.603 / 13.672초 | 1,096 / 969 | 638 / 505 | 명확한 13항목 선별 일치. 면적 이상 확인 경고 소실 |
| high + 앱 시스템 메시지로 교체 | 27.629 / 29.744초 | 2,125 / 2,245 | 1,484 / 1,661 | 명확한 13항목 선별 일치. 면적 이상 확인 경고 소실 |

기존 설정 재생에서 첫 추론 delta 수신은 2.947 / 3.230초, 추론 delta부터 첫 텍스트 delta까지 25.711 / 30.068초, 텍스트 구간은 약 8초였다. CLI init은 약 0.2초, 모델 message_start는 약 2초였다. **수십 초의 CLI 준비 지연이 아니라 생성·추론 구간이 지배적**이다. 네트워크 수신 시각으로 서버 내부 계산을 완전히 분해할 수는 없다. 원본 53초와 재생 37~42초의 차이 또한 같은 설정에서도 추론량·지연이 달라진다는 증거다.

프롬프트 교체는 총 입력을 **19,519 → 16,149토큰**으로 3,370토큰(17.3%) 줄였다. 원샷 시스템 지시가 391자라고 해서 전체 시스템 문맥이 391자인 것은 아니었다. 토큰 감소는 직접 확인했지만, 두 번의 시간 감소가 모두 이 입력 감소의 인과 효과라고 단정하지 않는다. 함께 생성된 추론량도 달라졌고 프롬프트는 모델 행동에 영향을 준다.

### 품질 오라클의 범위

원래 선택된 15행을 정답으로 삼지 않았다. 입력의 명시적 면적·테라스 표지로 13항목을 우선 포함 대상으로 정하고, 베란다/마당의 의미가 애매한 색인 0·24·39는 정오 점수에서 제외했다. 면적은 실제 검증값이 아니라 입력 표기값 기준이다. 이 판정은 도메인 전문가의 블라인드 평가가 아니다.

- off1: 전용 99㎡인 색인 46을 누락하고, 전용 65㎡이며 테라스·주인세대 표지도 없는 44를 추가했다.
- off2: 같은 44와 조건 근거가 없는 56을 추가했다. reason 본문에서도 기준 미달을 말하면서 결과에 포함했다.
- 원본과 baseline 두 회는 색인 8의 `311/564㎡` 역전·큰 면적 표기에 확인 필요를 명시했다. low/교체 두 회씩에서는 이 경고가 없었다. 교체 첫 회는 “단독 건물 기준”이라는 확인되지 않은 설명도 덧붙였다.
- 그러므로 “빠른 설정도 13개를 맞혔다”는 것은 **선별 부분 검사 통과**일 뿐, 동일 품질 증명이 아니다. 원본도 베란다 항목 선택이 일관되지 않아 완전한 기준 출력이 아니다.

기존 criteria는 meta/url/reason의 존재와 원본 포함 여부를 요구했다. 조건 충족 항목의 누락·제외 대상의 잘못된 포함·이상치 경고 보존 전체를 검사하는 기준이 아니다. 그 평가의 pass를 전체 품질 보증으로 읽으면 안 된다. 이번에는 해당 평가를 재실행하지 않았으므로 새 잘못된 결과가 실제로 pass를 받았다고 주장하지 않는다.

## 일반 하네스에 대한 의미

1. **코드의 데이터 운반 비용과 모델의 의미 판단 비용을 분리해야 한다.** 색인 병합은 원본 재작성을 줄였다. 이번 큰 지연은 그 수리가 실패한 것이 아니라 모델이 별도의 의미 판단을 수행한 비용이다.
2. **원샷이라는 호출 형태만으로 추론을 끄지 않는다.** 분류·검수와 실행 축의 의미 변환·종합을 모두 “짧은 JSON”으로 간주하는 가정은 맞지 않는다. 실행 축의 품질을 유지한다는 원래 설계 의도를 지켜야 한다.
3. **도구 없는 호출의 불필요한 기본 문맥을 줄이는 것은 일반적인 개선 후보다.** 하지만 이 실험은 단일 입력이므로 프롬프트 교체를 전체 원샷에 배포하지 않았다. 형식·선별뿐 아니라 근거·불확실성의 보존도 평가해야 한다.
4. **순이익은 대체된 주 모델 작업까지 포함해 측정해야 한다.** 53초가 추가된 사실만으로 원샷이 항상 손해라고 결론 내릴 수 없다. 원샷이 없는 동일 자료·동일 산출 기준의 주 루프와 비교해야 한다. 반대로 호출 수 감소만으로 이득이라고 주장할 수도 없다.

이번 변경은 감사 기록뿐이다. 제품 코드·기어·추론 설정·보고서 가이드·관용구를 바꾸지 않았다. 모델 품질 저하를 속도 개선으로 배포하지 않기 위한 결정이다.

## 설정 근거

Claude Code 공식 [환경 변수 문서](https://code.claude.com/docs/en/env-vars)는 Anthropic 경로에서 `MAX_THINKING_TOKENS=0`이 추론 비활성 요청이며 단순 `CLAUDE_CODE_DISABLE_THINKING`은 파라미터 생략이라고 구분한다. 이 실험에서도 전자는 실제 thinking_tokens=0이었다. 설치된 CLI의 `--help`로 effort와 시스템 프롬프트 교체 인자 지원을 확인했다. 공급자·모델별 제약은 다를 수 있다.
