## 실제 실패와 근본 원인

원문 3건과 SHA-256을 [재생 자료](experiments/episode3176_failures.json)에 보존했다. 테스트는 원문을 바꾸지 않고 필요한 선행 변수와 외부 응답을 고정 자료로 공급한다.

### 1. 회상 결과의 계약과 함수 발견 범위

event 13에서 실행기억을 회상하고 `success_rate` 열을 선택하다 실패했다. 검색 XML은 성공률을 보여 주지만 주제 회상의 행에는 성공/실패 횟수만 있었다. 두 표면은 이제 `execution_success_rate` 한 계산을 공유한다. 무시도(-1)와 전부 실패(0)를 구별한다.

더 큰 발견 문제도 있었다. `보고서/부동산 발굴`에는 이름 없는 용례 4건만 있었고, 상위 `보고서`의 이름 있는 함수 6건은 회상 범위 밖이었다. “이름을 보고 부르라”는 안내에 비해 실제 가지 결과가 부족했다. 이제 `items`에 현재 가지의 용례·관용구와 조상의 이름 있는 함수 카드를 함께 제공한다. 가까운 정의가 우선하며, 다른 가지·조상의 무명 용례·주행 본문은 추가하지 않는다. 코드 전문은 요청할 때 연다.

`count`는 전체 `items` 수로 맞췄고, 기존의 지역 용례 수는 `example_count`, 지역 관용구 수는 `phrase_count`, 상속 함수 수는 `inherited_function_count`로 명시했다. 기존 `phrases`는 유지한다. 성공한 실행이 자동으로 이름을 받는다는 오래된 안내도 제거하고 은퇴 관문에 등록했다.

라이브 회상에서 공통 함수 6건이 실제로 노출됐다. 그중 실행 성적이 있는 것은 `직전보고서찾아읽기` 한 건(성공 1회)이며 나머지 5건은 미검증이다. 발견 가능성을 고쳤다는 사실과, 이 함수들이 실작업의 판단·재작성을 줄였다는 증명은 별개다. 새 함수를 무더기로 등록하거나 호출을 강제하지 않았다.

### 2. 별칭을 거치면 목록이 실행 진단 봉투가 됨

event 27의 `$q = $rot.queue; $q >> filter`는 실패했고 `$rot.queue >> filter`로 직접 연결하면 성공했다. 식 대입의 `value/message/assigned` 봉투를 파이프가 사용자 데이터로 오인했다. 이전의 지연 문장 수리는 이 일반 대입 경계를 덮지 못했다.

대입 결과에 명시적인 내부 값 표식을 두고, 변수 방출·보간·조건·식이 같은 원형 값을 읽게 했다. 목록은 방출 시 `items` 통화가 된다. 사용자 객체의 `value/message/items` 키는 원형 그대로 보존하며, 실제 데이터 키가 기존 진단 필드와 충돌하면 데이터가 우선한다. 표식 없는 사용자 객체를 임의로 벗기지 않는다.

확장 시험에서는 목록 안의 문자 `$items`를 `items:$q`로 전달하면 다시 변수로 해석되는 문제도 발견했다. 일반 파이프의 step 참조 치환을 지연 실행과 같은 IR 바인더로 옮겨, 작성된 참조와 삽입된 문자 데이터를 구별한다. 특정 예약어를 문자열 이스케이프하는 예외 처방을 추가하지 않았다.

### 3. 동일한 파일이 조회 액션마다 다른 필드로 반환됨

event 36의 `self:list >> table:select{columns:["name"]}`가 실패했다. `file_find`는 `name/path/size/mtime/dir/is_dir`를 주지만 `list`는 표시 카드와 한글 표만 제공했다. 파일 조회 두 액션이 공통 `_file_views` 생산자를 사용하도록 합쳤다. 기존 카드·한글 표는 유지하고 기계가 읽는 필드를 일치시켰다. `list`에 없는 재귀 옵션을 가르치던 카탈로그도 바로잡았다.

## 증류의 거절은 유지

종료 후 주행에는 성공 문장 15건이 저장됐다. 별도로 생성된 후보는 `$rot`의 선행 정의를 빠뜨려 구문 관문에서 거절됐다. 이는 전체 주행 기억 유실과 다르다. 선언되지 않은 변수를 가진 조각을 자산으로 등록하도록 검사를 느슨하게 만들지 않았다.
