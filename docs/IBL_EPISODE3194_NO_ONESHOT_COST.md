# 원샷 차단 후 ep3194 보고서 비용 감사

2026-09-08. 사용자 질문: 최신 에피소드를 보니 시간이 또 늘었다.

**늘어난 47초 중 28.537초는 사전 계획(+17.370초)과 최종 평가(+11.167초)다. 주 실행 루프 증가는 18.796초다.** 나머지 주변 처리 차이는 −0.179초. 따라서 총시간 증가 전부를 IBL 원샷 제거 탓으로 설명할 수 없다.

IBL 실행에서 **54.870초가 감소**했다. 반면 주 실행 루프에서 IBL을 뺀 구간은 662.913→736.579초, **73.666초 증가**했다. 이 두 변화가 합쳐져 주 실행이 약 19초 길어졌다. 전체 시간과 중첩된 IBL 시간을 더하지 않는다.

## 차단이 실제로 지켜졌나

- 42개 `ibl.started`의 `allow_agent_tool_oneshot`은 모두 false.
- 차단 대상 원샷 액션 호출 및 `ai.policy_blocked` 사건 없음. 막힌 원샷을 반복 수리하다 시간이 늘어난 실행이 아니다.
- 원본 Claude 세션의 네이티브 도구는 `mcp__indiebizos__execute_ibl` 42개뿐이다. 셸/API로 모델 호출을 우회한 네이티브 도구 실행은 없었다. 스크립트는 기존 보고서HTML 렌더 경로였다.
- 도구 밖의 최초 분류·최종 평가·종료 뒤 기억 처리는 유지되었다. 이 원샷들은 이번 차단 범위 밖이다.
- `[fn:]` 호출은 두 실행 모두 0. 등록 스크립트 보고서HTML은 재사용했지만 관용구 선택이 개선되었다고 볼 근거는 없다.

## 주 모델의 시간이 늘어난 자리

원본 Claude JSONL에서 실제 응답 ID별로 묶었다. 응답 구간은 직전 user/tool_result 이벤트부터 마지막 assistant 블록까지다. 네트워크·서버 대기·입력 처리·추론·생성을 포함한다. 순수 추론 시계가 아니며, 아래 구간 합이 전체 실행과 조금 다른 것은 도구 전달/준비 등 사이 구간 때문이다.

| 응답 구간 | 이전 시간 / 응답 수 | 이번 시간 / 응답 수 |
|---|---:|---:|
| 조회·판단(보고서/지역 DB 작성 전) | 312.255초 / 14 | 385.523초 / 31 |
| 보고서·지역 DB 작성 | 241.858초 / 1 | 224.519초 / 2 |
| 연구노트·원장·HTML·기억·최종 답변 등 후처리 | 108.058초 / 4 | 125.351초 / 10 |

조회·판단은 **+73.268초**, 보고서/지역 DB 작성은 **−17.339초**, 후처리는 **+17.293초**다. 원샷을 제거했더니 최종 보고서 작성이 더 오래 걸렸다는 설명은 이번 기록과 맞지 않는다.

실제 사용 양태:

- 이전에는 큰 조합으로 모아 처리하던 조회·선별·확인이 이번에는 여러 응답으로 나뉘었다. 실거래 자료 수집 뒤 전세 비중·대형 전세·매매 집계·주택 전세를 각각 확인하고, 호가·상권 집계도 후속 호출로 나누어 읽었다.
- 원샷 유무 외에 **조사량도 다르다**. 뉴스 검색은 2→9회, 장소 조회 1→4회, 상권 조회 1→2회다. 이번에는 역지오코딩 3회도 있다. 공주의 BRT·입주장·의료 접근성·자가층 부재를 확인하는 내용이 추가되었다. 모두 낭비라고 분류할 수 없다.
- 연구노트 수정은 2→5액션으로 늘었고 여러 턴에 걸쳐 진행됐다.
- 이번 보고서 본문은 10,355자로 이전 8,043자보다 28.7% 길다. 길이 자체를 품질 향상으로 보지는 않는다. 이 수치는 셸 `wc -m`의 글자 수이며 토큰과 다르다.
- 유일한 오류는 `&`의 결과를 `union`으로 합친 뒤 다시 `union`을 붙인 것. 두 번째 union에 병렬 입력이 없어 실패했다. 다음 호출에서 수정되었고, 긴 지연의 지배적인 원인이 아니다.

자료 반환 총량은 약 5% 줄었는데 주 모델 누적 입력은 **2.32배**가 됐다. 새로 반환된 자료가 더 많아서가 아니라, 더 많은 응답에서 누적 문맥을 반복 입력한 결과와 부합한다. 대부분 캐시 읽기이므로 비용이 2.32배라는 뜻은 아니다. 첫 토큰 시계가 없어 74초 증가 중 몇 초가 순수 왕복/입력 처리인지까지 분리하지 않는다.

## 토큰을 정말 더 썼나

주 모델 출력만 보면 44,326→44,102로 거의 같다. 하지만 이전 실행은 별도 도구 원샷 생성/검증 출력 **4,402토큰**이 더 있었다. 이를 포함한 실행 작업 출력은 **48,728→44,102로 약 9.5% 감소**했다.

사전 분류·의식과 최종 평가까지 포함하고 종료 후 백그라운드 기억 처리는 제외하면 출력은 **50,581→47,866으로 약 5.4% 감소**다. 반면 누적 입력은 늘었다. 시간·출력 토큰·캐시 입력을 한 지표로 섞어 “전부 나빠졌다” 또는 “효율이 좋아졌다”고 말할 수 없다.

## 해석

이번 실전에서는 **원샷 대기 감소보다 주 모델의 여러 차례 조회·판단·후처리와 사전/사후 판단 비용 증가가 컸다.** 원샷 제거의 순수 인과 효과는 아니다. 도시와 자료가 다르며, 원샷 차단 외에 이전에 수리된 코드도 반영된 실행이다.

입증된 것은 IBL 실패 감소와 도구 내 모델 비용 감소다. 전체 시간 개선은 입증되지 않았다. 이번 결과만으로 원샷을 다시 켜야 한다거나 완전히 폐기해야 한다고 판단하지 않는다. 언어가 계산/운반을 맡아도 주 모델이 얼마만큼 조사하고 몇 차례 결과를 확인할지는 여전히 모델의 실행 선택이다.

다음 인과 비교는 같은 도시의 고정 자료, 같은 모델·초기 기억·품질 기준에서 전체 루프를 반복해야 한다. 실전 한 건의 총시간 변화에 맞춰 언어를 추가 개정하거나 보고서 전용 절차를 강제하면 이번에 구분한 원인들을 다시 섞게 된다. 이 감사에서는 제품 코드·원샷 차단 설정을 변경하지 않았다.
