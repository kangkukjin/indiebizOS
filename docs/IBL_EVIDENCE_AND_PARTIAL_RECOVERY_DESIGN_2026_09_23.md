보존 자료는 `outputs/idiom_trials/ai_tips_rebuild_20260923/_runs/live-v3/`에 있다.

설계의 중심은 다음 네 가지다.

1. 후보가 실제로 말하는 방법과 근거를 먼저 확정한 뒤 기존 자료와 비교한다.
2. 근거가 부족하면 무엇이 부족한지 기록하고 보존 원문의 필요한 범위만 보완한다.
3. 독립적인 판정은 검증되는 즉시 저장하며, 미완료 항목만 다시 요청한다.
4. 최종 완전성·독립 검수는 유지한다. 부분 수용을 전체 완료로 표시하지 않는다.

## 2. 처리 순서 — 기존 두 번째 추출을 앞으로 옮긴다

현재:

```text
수집 → 자막 → 제목·시점 추출 → 원장 비교 → 후보 선정 → 구체 방법 추출
     → 원문 전체 독립 검토 → 편집 → 최종 검수
```

제안:

```text
수집 → 자막 → 제목·시점 추출 → 후보별 방법·조건·근거 추출
                              ↕ 부족한 근거만 보완
     → 확정된 후보의 원장 비교 → 후보 선정 → 원문 전체 독립 검토
     → 편집 → 최종 검수
```

항상 실행되는 별도 심사 모델을 추가하는 대신 기존 두 번째 grounded 추출을 이동한다.
영상별로 후보를 묶어 기존 보존 자막 전문에서 구체적인 방법과 여러 근거 구간을 얻는다.
첫 추출과 두 번째 추출은 유지하고, 선정 뒤에는 저장한 상세 결과를 선택하여 재사용한다.
같은 원문을 보며 추출한 결과는 독립 검수를 통과한 결과와 구분한다.

비용 상충은 명시한다. 종전에는 선정된 후보만 상세 추출했지만 새 순서는 비교 대상 후보 모두를
상세 추출한다. 탈락 후보가 많은 작업에서는 비용이 증가할 수 있다. 영상별 호출을 공유하되
실제 입력·출력·호출·재시도 비용으로 평가한다. 이번 19후보 사례의 유리함을 모든 과제에 일반화하지 않는다.
미리 근거가 확인된 입력을 받는 다른 관용구는 이 추출을 반복하지 않고 호환되는 영수증을 검사한다.

보고서의 논리 단계는 `candidates → details → compared → chosen → reviewed → draft → finish`로 바뀐다.
근거 보완과 판정 재시도는 details/compared 내부의 제한된 작업이다. 단순히 STAGES 순서만 바꾸지 않고
`stage_chosen`, `stage_details`, `review_tasks`, `next_output`, `revise`의 의존 조건도 수정해야 한다.

## 3. 근거 계약 — 인용 존재와 주장 지지를 분리한다

아래는 제안 데이터 계약이며 새로운 IBL 문법이나 어휘가 아니다.

```text
candidate:
  id, revision, source_id, source_hash
  method: {action, steps[], tools[], conditions[], limits[]}
  claims[]: {id, text, evidence_refs[], disposition, reason}
  evidence_refs[]: {source_id, source_hash, segment_ids[], quote}
  missing[]: {claim_id, question, anchor_refs[], suggested_terms[]}
  status: ready | needs_source | needs_external | rejected
  method_hash, evidence_hash, contract_version
```

소스 어댑터가 자막 구간·문서 문단·코드 범위에 안정적인 ID와 원문 지문을 붙인다.
시간이나 줄번호만으로 동일 원문이라고 판단하지 않는다. 읽기 단위는 소스 manifest가 소유한다.
근거 참조는 존재·원문 지문·인용 일치·구간 순서·허용 출처를 코드로 검증한다.
공통 직렬화·값 비교에는 기존 `common.value_semantics` 규약을 사용한다.
현재 `grounded()`가 검사하는 대표 `_quote`와 시점 계약은 유지한다. 새 복합 근거는 추가 필드로
받아 소비자가 각 인용·위치를 따로 검사한다. 기존 grounded 플래그 하나를 복합 주장의 보증으로 확대하지 않는다.

모델은 각 행동·조건을 어느 근거가 뒷받침하는지 제안한다. 코드가 인용이 존재한다는 이유만으로
문장 전체의 의미를 입증했다고 간주하지 않는다. `ready`는 비교 입력으로 수용됐다는 뜻이며,
‘독립 검수 완료’가 아니다. 필수 행동에 근거가 없으면 ready로 바꾸지 않는다.
복합 절차는 여러 구간을 연결한다. 제목의 한 시점 근처 인용 하나로 전체 절차를 증명하지 않는다.

비교 모델에는 `id, revision, method, method_hash`와 필요한 짧은 근거를 보낸다.
method에는 비교에 필요한 행동·대상·조건·순서·도구 차이를 보존한다. 단순 제목·임의 요약으로
대체하거나 길이를 맞추기 위해 필드를 자르지 않는다. 긴 원문은 저장소에 있고 해당 판정이 요구할 때만 읽는다.
구체적인 방법이 다른 짧은 표현으로 바뀌면 별도 revision이며 기존 신규성 판정을 그대로 쓰지 않는다.

## 4. 근거 보완 — 고정 시간창의 무조건 확대를 없앤다

첫 상세 추출은 이미 확보한 자막 전문을 사용한다. 기존 50,000자 자막 상한을 이번 변경에서
몰래 올리거나 원문을 자르지 않는다. 그 범위를 넘는 문서의 전량 분할 검토는 별도 경로다.

남은 `missing`에 대해 다음 순서로 처리한다.

1. 같은 출처의 미확인 주장들을 모은다. 원문 구간을 합쳐 중복 읽기를 제거한다.
2. 앵커 뒤의 연속 절차, 문단·절의 경계, 관련 문자열로 추가 구간을 찾는다.
   검색은 위치 찾기이며 근거가 없다는 판정은 아니다. 반대·취소 조건도 함께 읽는다.
3. unresolved claim과 이전에 읽은 범위, 새 구간만 모델에 보내어 근거 연결 또는 보완 요청을 받는다.
4. 다시 부족하면 남은 원문 범위를 예산 안에서 연속 탐색한다. 전체를 못 읽었으면
   `searched_ranges`와 `remaining_ranges`를 남기고 needs_source를 유지한다.

추가 구간은 모델이 요청할 수 있으나, 실제 파일·구간·지문 검증과 읽기는 코드가 수행한다.
이미 읽은 범위와 같은 질문을 반복 요청하면 진전 없는 재시도로 세고 멈춘다.
처음부터 문서 전체가 전달됐어도 모델이 해당 연결을 놓칠 수 있으므로, 동일 전체 입력 재전송보다
미확인 주장과 관련 구간을 집중해서 다시 읽도록 한다. 긍정 답을 얻을 때까지 반복하지 않는다.

c14에서는 질문 추출·질문별 답변·결합·전송을 각각 주장으로 나누고, 같은 보존 자막의
후속 구간까지 연결할 수 있어야 한다. 22:35나 추가 탐색 길이를 코드에 특례로 넣지 않는다.
반대 회귀 사례로 실제 결합 단계가 없는 자막을 넣어, 같은 제목을 보고 방법을 지어내지 않는지 확인한다.

기본 복구 한도 제안은 후보별 추가 의미 보완 2회, 형식/누락 복구 1회다. 업무 설정으로 명시하고
회차 영수증에 누적하여 재진입으로 초기화되지 않게 한다. 동시에 run의 요청 수·추가 입력 문자·
경과시간 한도를 적용한다. 한도 초과는 `budget_exhausted`이며 근거 부족과 구별한다.
문자 한도는 토큰 한도가 아니다. 제공자별 토큰 사전 계산이 없으면 정확한 총토큰 제한을 약속하지 않고
실사용 원장으로 사후 측정한다. 진행 중 호출은 취소 능력에 따라 종료가 늦을 수 있음을 기록한다.

외부 문서가 필요하면 needs_external로 구분한다. 기존 권한과 소스 정책 안에서 읽기 요청을 만들고,
접근 불가·예산 부족·출처 확인 불능을 숨기지 않는다. 이 보고서의 최초 구현은 보존 자막 보완까지다.
근거 없이 ‘새로운 팁’으로 통과시키거나, 회차 성공을 만들기 위해 unresolved 후보를 자동 삭제하지 않는다.
명시적인 부적합·모순 판정에 따른 reject는 사유를 남길 수 있다. unresolved가 남으면 기본적으로 미완료다.

## 5. 원장 비교 — 전건 범위를 유지하면서 원문 반복을 줄인다

655개 등의 기존 자료는 정확한 ID와 필요한 필드를 유지한다. 검증되지 않은 유사도 상위 N개로
전건 비교를 대체하지 않는다. 이전 자료가 자체적으로 불완전하면 해당 항목의 추가 자료를 요청한다.

비교 작업은 `후보 revision × 고정된 기존 자료 ID 묶음`으로 식별한다. 여러 후보의 작업을 한 모델
요청에 묶을 수 있으나, 수용·재시도의 단위는 후보별 판정이다. 입력 상한에 맞추어 후보 축과
기존 자료 축을 모두 분할할 수 있다. 필수 의미 정보를 삭제하여 4배치로 맞추는 목표를 두지 않는다.
작업 manifest가 필요한 후보×기존 자료 범위를 정의하고 최종 통합기가 누락·중복·범위 이탈을 검사한다.

비교 결과는 아래처럼 원인을 나눈다.

| 결과 | 다음 처리 |
| --- | --- |
| novel_in_scope | 해당 자료 묶음에 한해 수용한다. 전체 범위 완료 전에는 novel로 확정하지 않는다. |
| duplicate | 실제 비교 범위의 known_id와 차이·중복 이유를 검증해 수용한다. |
| needs_source | 후보 근거 보완으로 돌린다. 같은 후보에 대한 요청을 합쳐 중복 보완하지 않는다. |
| needs_comparison_evidence | 모호한 기존 자료·비교 쌍만 확대한다. 후보 자체의 근거 부족과 구분한다. |
| invalid_response / missing_result | 형식 오류·빠진 후보만 제한 재요청한다. |

같은 후보의 근거 부족이 확인되면 아직 시작하지 않은 그 후보의 비교 작업을 보류한다.
이미 병렬로 진행 중인 작업까지 비용이 0이 된다고 가정하지 않는다. 다른 후보의 독립 작업은 계속 수용한다.
최초 구현은 모든 필수 비교를 완료하는 기존 정책을 유지한다. 중복 발견 뒤 나머지를 생략하는
최적화는 비교 범위 계약 변경이므로 별도 평가 없이 도입하지 않는다.

## 6. 부분 수용·재개 — 배치 성공과 전체 성공을 구별한다

현재 `preserve_rows:true`는 task 행의 보존을 검사하지만 `result.decisions`의 완전성은 검사하지 않는다.
새 공통 엔진 옵션을 바로 추가하지 않고, 먼저 소비자의 계약 검사에서 두 경계를 모두 검증한다.

수용 순서는 다음과 같다.

```text
응답 원본 보존 → 작업/입력 식별 확인 → 각 독립 판정 검증
            → 유효 판정별 영수증 저장 → 미완료 작업 목록 갱신 → 다음 요청 준비
```

- b19처럼 19개 중 c1만 유효하면 c1을 저장하고 나머지 18개를 다시 요청한다.
- 잘못된 JSON, 다른 request ID, 잘린 응답은 내부 일부 문자열을 임의 복원하여 수용하지 않는다.
- 알 수 없는 ID·중복 ID·잘못된 출처·변경된 입력 지문은 해당 판정을 격리하고 이유를 기록한다.
  다른 행이 독립임을 manifest로 증명할 수 있을 때만 나머지 행을 수용한다.
- 후보 간 순위·전체 선발처럼 서로 의존하는 판단은 행 단위로 쪼개 수용하지 않는다.
  작업 manifest에 `acceptance_unit=row|request`와 기대 ID·범위를 명시한다.
- 부분 결과는 부분 상태 그대로 남긴다. 필요한 모든 작업이 확정돼야 단계 영수증과 완료 상태를 만든다.

제안 영수증 식별에는 `run_scope`, 작업 종류, 대상 ID/revision, 원문/자료 snapshot,
비교 범위 ID 목록, 실제 요청 hash, prompt/schema/검증기 버전, 모델·기어와 명시적 의존 영수증이 들어간다.
출력 hash, 원본 응답 참조, accepted 시각, attempt도 저장한다. 요청 메타데이터는 실행자가 붙이며
모델이 스스로 출력한 hash만 믿지 않는다. 다른 run의 결과를 무단으로 공유하는 전역 캐시가 아니다.

원본 응답과 판정별 영수증은 별도 파일로 원자 저장하고, 작업별 잠금과 충돌 검사를 사용한다.
모델 실행 동안 전체 state 파일의 잠금을 잡지 않는다. 병렬 워커가 같은 state 사본을 덮어쓰지 않게
manifest는 불변으로 두고 상태 집계는 수용 영수증에서 재구성한다. 동일 요청에 다른 유효 응답이
경합하면 먼저 수용된 결과를 유지하고 나머지는 이력으로 남긴다. 다시 판정하려면 새 attempt/revision이다.

각 each 워커 안에서 모델 응답 직후 저장한다. each 전체가 끝난 뒤 한꺼번에 저장하면 중도 종료 시
부분 복구가 되지 않는다. 실패 응답도 try/catch 또는 on_error 계약으로 기록하며, 전체 failure를
성공으로 덮지 않는다. 모델 응답이 저장 전에 유실된 구간의 재호출은 남을 수 있다. exactly-once 보장이 아니다.

## 7. 의존 관계와 무효화

| 변경 | 무효화 범위 |
| --- | --- |
| 같은 원문의 추가 구간 확인, 방법 불변 | 새 evidence revision 저장. 해당 근거를 요구했던 미완료 판정만 재요청; 이미 확정된 판정은 계약과 방법 지문이 같을 때 유지 |
| 후보의 방법·조건·도구 변경 | 해당 후보의 비교 판정 전부와 그에 의존하는 선정·검수·편집 무효화 |
| 원문 bytes/hash 변경 | 그 원문에 의존하는 후보·판정·후속 결과 무효화 |
| 기존 원장 snapshot 변경 | 현재 run의 비교·게시 확정 중단. 새 snapshot/run으로 재계획 |
| 모델·prompt·검증 기준 변경 | 호환을 명시적으로 증명한 경우 외에는 해당 판정 재사용 금지 |
| 최종 검수에서 내용 수정 | 수정 필드가 근거/신규성 계약에 영향을 주면 해당 경계부터 재검토 |

추가 근거가 기존 판정과 모순되면 ‘방법 불변’ 예외로 재사용하지 않고 해당 후보의 판정을 철회한다.
검토자가 how·조건을 고친 뒤 과거 신규성 판정을 그대로 달고 발행하지 않는다. 최종 검수에는
최종 method_hash와 근거·비교 coverage 영수증을 연결한다. 독립 검토에는 현재처럼 자막 전문을 제공한다.
최종 내용 보완 1회 기능은 유지하되, 보완 중 바뀐 방법은 비교 의존성까지 되돌린다.

## 8. IBL에 연결하는 위치와 구현 범위

파서·언어 표준·새 액션을 바꾸지 않는다. `self:struct`, `table:ai`, `input_fields`, `input_as`,
`def/fn`, `each`, `try/catch`, 제한 반복으로 구성한다. 아래는 흐름 의사코드이며 실행할 IBL 본문은 아니다.

```text
prepare_pending(run, stage) → 대기 작업 manifest/요청
각 작업: 원본 해소 → 기존 AI 액션 → accept_task(run, task_id, 실제 응답 봉투)
collect_status(run) → accepted / retryable / blocked / complete + 참조
retryable만 예산 내 재계획; complete일 때 다음 단계
```

루프는 등록 스크립트의 결정론 계획과 IBL 내부 조합으로 처리한다. 주 실행 모델이 작업마다
state 전체를 읽고 다음 도구를 다시 작성하는 방식을 기본 경로로 삼지 않는다. 바깥에는 완료 수·
미완료 ID·원인·새 상태 변경·근거 참조를 반환한다. 전체 원문과 반복된 비교 입력은 참조로 남기되
실행용 데이터는 잘라내지 않는다. 큰 상태 파일을 반복 polling하는 비용도 평가에 포함한다.
실제 IBL 작성 때에는 파서/인자 검사에 더해 빈 작업, 부분 실패, 함수 반환 봉투, each 내부 조기 저장의
조합을 고정 응답으로 확인한다. 단순히 위 의사코드를 실행 가능한 관용구라고 등록하지 않는다.

| 수정 위치 | 책임 |
| --- | --- |
| `data/scripts/ai_tips_report.py` | 단계 순서·업무 판정·최종 완전성·기존 저장/게시 계약 연결 |
| 제안 `data/scripts/ai_tips_evidence.py` | 자막 어댑터, claim·근거 위치 검사, 상세 추출/국소 보완 요청 구성 |
| 제안 `data/scripts/ai_tips_comparison.py` | 전건 비교 작업 분할, 후보별 판정 수용과 coverage 계산 |
| 제안 `data/scripts/ai_tips_receipts.py` | 작업 manifest·원본/영수증 원자 저장·잠금·재개·예산 누적 |
| `data/idioms/ai_tips_report.ibl` | 두 번째 추출 이동, 워커 내부 수용, 미완료 항목 복구 조합 |
| `data/scripts/test_ai_tips_report.py`와 분리 시험 파일 | 정상·오류·재개·비용 계수 회귀; 파일 1500줄 이내 |
| 보고서 가이드·등록 설명·조합 가이드 | 실제 구현 후 새 계약과 재사용 예제 반영 |

범용 개선은 `원문 위치 → 주장 → 판정 → 영수증 → 의존 무효화`라는 계약과 조합법에 있다.
문서 업무에는 paragraph ID, 코드 검토에는 파일 hash+범위 어댑터로 대응한다. 이런 자료에서도
‘원문을 더 읽으면 해결되는 부족’과 ‘외부 지식/실행 검증이 필요한 부족’을 혼동하지 않아야 한다.
유튜브 시간창·팁 신규성·선정 수·게시 규칙은 보고서에만 둔다.

처음부터 범용 근거 엔진·전역 상태 DB를 만들지 않는다. 문서 주장 대조 또는 코드 변경 검토 중
두 번째 실제 소비자가 같은 계약을 쓰고 비용 개선을 보일 때, 중복되는 영수증 저장을
`backend/datastore` 등 적절한 층으로 추출한다. 그때 층 배정·어휘/회원 경계가 필요한지 별도 검토한다.
다른 주제로 이름만 바꾼 AI 팁 보고서를 보편성 검증으로 세지 않는다.

## 9. 호환성과 적용 순서

1. **작업별 영수증·부분 수용부터 구현**한다. 현재 비교 절차에서도 성공 결과를 잃지 않게 한다.
2. **두 번째 추출 이동·근거 계약·국소 보완**을 구현한다. 기존 단계와 비교 가능한 별도 후보로 둔다.
3. **확정된 방법으로 비교 입력 구성**, 두 축 분할과 의존 무효화를 연결한다.
4. **다른 분야의 소비자와 같은 기준으로 평가**한 뒤 공통 코드 추출 및 운영 채택을 판단한다.

외부 호출 이름과 `$설정` 입력, 최종 결과의 status/report/evidence 등은 유지한다.
내부 상태 버전은 3으로 올리고, 기존 v2 run을 새 순서로 암묵 재개하지 않는다.
기존 실행은 보존하며 구버전 경로로 완료하거나, 명시적인 새 run에 지문을 재검증한 원문·메타데이터만
가져온다. 4006의 관측 원본은 변경하지 않는다. 수입한 자료의 출처 run도 남긴다.
새 의미 계약을 만족한다고 확인하지 않은 옛 비교 판정을 새 판정으로 승격하지 않는다.
운영 등록은 아래 검증 이후이며, 이번 설계 작성에서 코드 수정·등록·실행은 하지 않는다.

## 10. 검증과 채택 기준

먼저 외부 호출 없는 계약 시험을 한다. 다음은 예정 항목이며 이번 설계에서 실행하지 않았다.

- c14의 필요한 근거가 최초 발췌 밖에 있지만 원문에는 있는 경우의 국소 보완과 근거 연결.
- 원문에 실제로 후속 단계가 없거나 반대 조건이 나오는 경우의 unknown/reject 유지.
- b19의 1/19 응답은 1건 수용·18건 재요청. 중복·가짜 ID·깨진 JSON·잘린 응답은 정직하게 구분.
- 한 배치의 형식 오류가 다른 배치의 유효 영수증을 지우지 않음. 재진입 시 완료 모델 호출 0회.
- 병렬 두 워커·저장 직전/직후 종료·응답 충돌·run 종료 후 늦은 응답·재시도 예산 유지.
- 후보 수정은 해당 후보만 무효화. 전역 선정·최종 본문처럼 의존하는 결과는 반드시 무효화.
- 원문/원장 변경·영수증 변조·근거 참조 만료·과대 단일 후보/기존 자료·비교 범위 누락.
- 제목은 비슷하지만 방법·조건이 다른 후보를 compact method가 합쳐버리지 않음.
- 문서의 멀리 떨어진 예외 조항, 코드의 다른 함수에 있는 전제 등 비자막 입력의 같은 계약 검증.

고정 응답 시험은 의미 품질의 증명이 아니다. 이후 동일 모델·기어·자료 snapshot·완료 기준으로
현재본과 후보를 비교한다. 조사/개발 비용과 반복 실행 비용을 분리하고, 성공한 부분만의 시간을
실제 완료 시간이라고 보고하지 않는다. 현행이 실패하면 두 쪽 모두 사용 가능한 결과에 도달하기까지의
복구 비용을 포함하거나 미완료로 명시한다. 지금까지의 23분 12초는 개발을 포함하므로 성능 기준선으로 쓰지 않는다.

| 축 | 채택 판단 |
| --- | --- |
| 품질 | 필수 주장·조건·출처 유지, 최종 독립 검수 통과, 미확인을 확정으로 바꾸지 않음. 단순 팁 개수 감소로 성공하지 않음 |
| 시간 | 요청부터 필요한 복구·검수를 거쳐 결과가 준비될 때까지. 모델 지연의 병렬 합산과 구분 |
| 비용 | 외부 주 실행+내부 추출/판정+보완+검수+후처리 전체 input/output/cache. 새 근거 추출·영수증 IO 비용도 포함 |
| 복구 | 완료 판정 재호출 수, 추가 근거 조회 수, 미완료 셀 수, 재사용 적중과 잘못된 재사용 0건 |
| 범위 | 4006 재현 외에 작은/큰 원장, 미보유 근거, 부적합 후보 다수, 문서/코드 소비자 등 미사용 과제 |

기존 trajectory/model.usage에 run/task/stage/candidate revision을 연결해 실제 비용을 귀속시킨다.
새 계측이 별도 모델을 호출하지 않으며 billable 기록만 합산한다. 입력 원문을 계측 로그에 또 복제하지 않는다.
작은 입력에서의 추가 비용과 큰 입력에서의 이득을 따로 보고, 한쪽의 평균으로 다른 쪽의 퇴행을 숨기지 않는다.

기대 효과는 긴 근거의 반복 전달, 같은 문제의 반복 판정, 실패 뒤 성공 작업 재수행의 감소다.
**27배치가 반드시 4배치로 줄거나 특정 토큰 절감률을 달성한다고 약속하지 않는다.** 필수 의미 정보를
유지하고 실제 품질·완료 시간·전체 토큰이 함께 개선되는 조건을 확인한 뒤 채택한다.
