# IBL 진화 목적과 개선 판단

목적 정본: [vision.md — IBL과 주변 시스템의 진화 목적](../data/system_docs/vision.md#ibl과-주변-시스템의-진화-목적).
이 문서는 그 목적을 설계·구현·실험에 적용하는 기준이다. 개별 설계의 범위나 성공 사례가 이 목적을 좁히지 않는다.

## 목적과 개선 대상

**도구를 어휘로 포함하는 IBL과 주변 시스템을 진화시켜, AI가 실행 의도를 쉽고 정확하게 표현하고 다양한 작업에서 결과 품질을 유지·향상하면서 실제 완료 시간과 전체 토큰 소비를 줄인다.**

Python·TypeScript로도 도구를 조합할 수 있다. 문제는 외부 도구 사이의 이음매다.
IBL은 호출·통화·조합·실패의 계약을 언어와 실행 시스템의 공통 구조로 다루며,
그 구조를 지속적으로 개선할 수 있게 한다. 자연어 스킬이나 일반 언어도 개선 가능하지만,
IBL은 여러 작업에 걸친 개선의 대상과 검증 단위를 명시적으로 갖추려 한다.

IBL은 셸·도구 사이의 값 전달·실패 처리·재개를 조합해 추가 모델 호출을 줄이기 위한 언어다. 비슷한 어휘가 있다는 이유로 셸이나 네이티브 파일 작업을 강제 변환하지 않는다. 단독 명령은 그 의미를 보존해 직접 실행하고, 조합·재사용이 왕복과 토큰을 줄이는 곳에서 IBL을 선택한다. 자기수리 격리·대상 권한·위험 명령 승인은 실행 수단과 별도로 유지한다.

개선 대상에는 어휘·문법·통화뿐 아니라 실행기·도구 어댑터·맥락 전달·기억과 회상·재사용·검수·복구·계측이 포함된다.
새 문법이나 새 어휘가 없어도 주변 시스템의 공통 마찰을 줄이면 목적에 기여할 수 있다.
반대로 문장이 짧아지거나 관용구가 많아져도 품질·시간·전체 토큰의 개선은 별도로 확인해야 한다.

## 개발 계획은 일반 능력의 목표 구조에서 도출한다

현재 단계의 개발은 처음 보는 요구의 표현·분해, 부품의 조합과 추상화, 결과와 근거의 보존,
부분 수정과 재개, 능력의 축적과 발견을 보편적으로 강화하는 방향으로 계획한다.
목표 구조와 현재 구조의 간극, 능력 사이의 의존 관계가 개발 내용과 순서를 정한다.
개별 업무의 실패 발생이나 전후 측정을 기다려야만 일반 능력을 개선할 수 있는 것은 아니다.

아래의 사례 분석과 결과 평가는 반례를 찾고 관측한 성과를 설명하는 기준이다. 특정 사용자
업무 몇 가지의 측정을 다음 설계·구현의 선행 조건으로 삼거나 그 업무에 대한 적응으로
일반 능력의 향상을 대신하지 않는다. 구현 검증은 설계한 계약과 조합 성질을 확인하는 데 둔다.
측정하지 않은 성능 향상은 주장하지 않되, 측정 대기로 목표 구조를 향한 개발을 유예하지 않는다.

## 신경계 비전을 개발에 적용하기

목표 정본은 [감각과 행동을 잇는 신경계](../data/system_docs/vision.md#감각과-행동을-잇는-신경계)다.
감각·조합·주의·제어를 함께 개선하며, 전체 작업을 유지한 채 필요한 부분의 관측과 제어를
세밀하게 바꾸고 다시 맡기는 능력을 지향한다. 개별 어휘를 모두 크게 만드는 것으로 대체하지 않는다.

현재 기반에는 함수·관용구·Script의 조합, 원문 참조, 실행 근거, 부분 재사용과 재개가 있다.
[실행 상황 인식](EXECUTION_SITUATION_AWARENESS_DESIGN_2026_10_31.md)은 관측·판본·미확인의
전달을, [구조 수렴 설계](IBL_SYSTEM_CONSOLIDATION_DESIGN.md)는 계약·조합·부분 수정의 연결을 다룬다.
이 기반의 존재와 일반적인 실행 중 부분 개입·관측 및 제어의 독립 조절이 실제로 되는지는 구분한다.
후속 개발은 각 소유 경로의 현재 계약과 소비자까지 대조하여 비전과의 공백을 정한다.

의존 관계에 따라 다음을 연결한다. 모든 작업에 고정 순서나 추가 모델 호출을 강제하는 절차는 아니다.

1. **감각의 연속성**: 대상·시점·범위·판본·근거·미확인을 조합과 표시 뒤에도 보존한다.
   같은 대상에 속한 정보와 행동 전후를 연결하고, 필요한 상세는 확보된 원문·구조·이미지에서 회수한다.
2. **협응과 피드백**: 진행·의존·공유 자원을 맞추며, 접수·실행·효과·목표 충족을 구분한다.
   목적에 필요한 관측과 정해진 조정은 기존 실행부가 맡고 새로운 판단이 필요한 경계를 드러낸다.
3. **주의와 부분 제어**: 관측을 자세히 하는 것과 실행 방식을 바꾸는 것을 분리한다.
   전체 목적·유효한 결과·효과 영수증을 유지하며 부분 관측·조정·재위임을 연결한다.
   즉시 바꿀 수 없는 동작은 적용 가능한 경계와 미확인 효과를 알리고 완료된 행동을 중복 실행하지 않는다.
4. **추상화의 선택과 축적**: 기존 부품 사용·부분 수정·즉석 코드 작성을 같은 목표 안에서 선택한다.
   찾기·이해·적응·실행·결과 확인·복구를 포함한 비용을 비교하며 저장과 등록은 필요할 때 한다.

에피소드는 필요한 사실을 얻지 못했는지, 얻었지만 관계·범위를 잃었는지, 기능을 발견하지 못했는지,
정확히 관측하고도 판단을 잘못했는지, 관측한 대상을 조작하는 연결이 끊겼는지 구분하여 읽는다.
실패가 없는 새 과제에도 필요한 일반 능력을 설계할 수 있으며, 과거 사례는 반례와 검증 자료로 쓴다.
개별 접근의 결함은 해당 어휘에서, 반복되는 관측·전달·제어의 공백은 공통 책임에서 고친다.
새 코어 어휘·별도 감독·상시 감시를 기본 해법으로 삼지 않는다. 정상 수행뿐 아니라 상태 변화와
부분 개입에서 목표·근거·효과가 보존되는지 검증하고, 속도·토큰 개선은 실제 측정 범위로 보고한다.

연구 결과를 현행 구현의 수리 순서와 인수 조건으로 연결한 문서는
[여러 언어의 감각·행동·검수 경계 수리 설계](LANGUAGE_BOUNDARY_REPAIR_DESIGN_2026_11_02.md)다.
평가 입력 총량의 확인된 결함과, 의미 보존·적합성·상세 관측·부분 개입의 확장을 구분한다.
설계의 존재를 구현·활성화·성능 개선의 완료로 읽지 않는다.

수리 후 실제 연구에서 드러난 근거 회수 중단·능력 설명 불일치와 재사용·회상·부분 제어의
소비 연결은 [에피소드 5767 후속 수리 설계](EPISODE_5767_CAPABILITY_CONTINUITY_REPAIR_DESIGN_2026_11_02.md)를 따른다.
해당 문서는 구현 전 설계이며, 확인된 결함과 일반 능력의 확장·인수 범위를 구분한다.

## 아직 어휘화되지 않은 방법의 선택

의식의 ‘세상의 방식’과 ‘탐색’은 사용자가 이름을 말하지 않은 방법·도구도 과제에 맞게 검토한다.
필요한 최신 지식은 검색하고 설치·접근 권한은 실행자가 확인한다. 이미 적절한 접근과 직접 구현이
목적인 과제를 존중한다. 별도 방법 목록의 자동 주입이나 추가 모델 호출을 기본 절차로 두지 않는다.
세계의 지도는 2026-10-22 은퇴했으며 수집 자료는 [기록](world_map/retired_2026_10_22/README.md)으로만 남긴다.

## 작업 중 수단을 만들고 고치며 능력을 축적한다

현재 저장된 어휘·관용구는 작업의 출발점이며 능력의 고정된 한계가 아니다. 에이전트는
맡긴 범위와 권한·예산 안에서 적합한 층을 선택한다. 기존 표현이 없거나 수단이 실패하면
정의를 살피고, 셸·Python 등으로 필요한 스크립트를 만들거나 허용된 구현을 수리한다.
모든 층을 정해진 순서로 거칠 필요는 없다. 방법의 실패는 다음 행동의 관측이며, 원래
사용자 목표와 유효한 결과를 보존해 다른 방법을 실제로 수행하고 업무로 돌아온다.
검증하고 재사용할 가치가 있는 해결은 입력·결과·적용 조건과 함께 저장해 다음 조합에 쓴다.

사람과 AI는 언어와 몸의 설계도 함께 발전시킬 수 있다. 다만 맡긴 목적, 기본 프롬프트·
명령지침, 권한과 완료·평가 기준은 작업 중인 에이전트가 임의로 바꾸지 못한다. 이 핵심의
변경은 사용자·개발자의 명시적인 외부 통제 아래 둔다. 보호 범위는 파일명이 아니라
실제 책임으로 정하며, 도구·스크립트에서 핵심을 우회하거나 약화하는 변경도 포함한다.

변경 권한과 반영 절차를 구분한다. 관리되는 정의·데이터는 소유 관리 연산으로 개정하고,
구현은 영향 범위에 맞게 격리·검사·활성화한다. 작은 수리에 전체 재기동을 기본값으로
요구하지 않는다. 중단이 필요한 변경은 기존 외부 제어자가 반영·복구하고 업무를 잇는다.
원칙은 [비전의 자기수정 경계](../data/system_docs/vision.md#두-개의-고리와-자기수정의-경계),
대상별 계약은 [변경 대상과 자기수리 경계](SELF_REPAIR_BOUNDARIES_2026_10_31.md),
현재 구현·검증 범위는 [작업 지속·부분 수리](TASK_CONTINUOUS_REPAIR_DESIGN_2026_10_31.md)를 따른다.
이 방향을 모든 구현의 무중단 교체나 모든 작업의 자동 복구가 이미 지원된다는 뜻으로 읽지 않는다.

## 조합을 축적해 한 번에 맡길 수 있는 일의 크기를 키운다

출발점은 저장된 관용구의 존재가 아니라 **사용자 요구 → 분해 이유 → 함수별 계약 → 구현 → 최상위 조합**이다.
새로운 작업도 현재 프로그램 안에 작은 지역 함수들을 정의하고 호출하여 전체를 구성한다.
기존 관용구가 적합하면 부품으로 쓰고, 새로 만든 정의는 검증 후 반복 사용 가치가 있을 때 저장한다.
교육·평가에는 저장된 정답 관용구가 없는 과제를 포함한다. 함수 수를 늘렸는지가 아니라
의미 있는 분해·명시적 값 전달·완료 조건 충족을 확인하고, 실제 에이전트의 작성 행동과 비용은 별도로 측정한다.

성장 단위는 **어휘 → 문장·프로그램 → 관용구 → 관용구를 조합한 더 큰 프로그램**이다.
큰 프로그램도 검증 후 다시 관용구로 보관하여 다음 조합의 부품으로 삼는다.
정리들을 조합해 더 큰 정리를 세우고 단순한 개념으로 복잡한 개념을 정의하는 것처럼,
확보한 능력을 다시 표현의 단위로 써서 언어 시스템을 키운다.

간결함은 단계마다 필요한 표현과 이음매가 작다는 뜻이며, 프로그램 전체가 짧아야 한다는 뜻은 아니다.
필요한 절차를 길게 구성해도 값 전달·분기·검수·실패 처리의 뜻이 일관되어야 한다.
“한 번에 실행”은 정해진 절차를 한 호출로 맡기는 것이다. 내부 도구·AI 호출과 반복은 남고,
그 실행 비용까지 포함해 기존 방식과 비교한다.

이 방향의 개선을 설계할 때는 다음을 확인한다.

- **다시 조합할 수 있는 결과**: 관용구의 입력·반환·적용 조건·부작용·실패가 드러나고, 결과가 다음 부품으로 연결되는가.
- **정의를 반복하지 않는 사용**: 필요한 관용구를 찾아 계약으로 호출하고, 수정·진단할 때 해당 정의를 펼칠 수 있는가. 모든 관용구의 본문을 상시 맥락에 싣지 않는가.
- **층을 넘는 검증과 복구**: 내부 실패의 위치와 이미 얻은 결과를 알 수 있어, 큰 조합에서도 필요한 범위를 보완할 수 있는가.
- **훈련으로 커지는 능력**: 익힌 관용구를 다른 입력·다른 부품과 조합한 새로운 과제에서 사용하고, 발견한 공백을 공통 구조에 환류하는가.

현재 중첩·호출 깊이와 재귀 제한은 구현 계약을 따른다. 여기서 말하는 층의 성장은 설계 방향이며,
무제한 중첩이나 재귀 실행이 이미 지원된다는 뜻은 아니다.
관용구 수·문장 길이·조합 깊이는 성장의 흔적이다. 더 큰 일을 안정적으로 맡기는 능력과
품질·시간·전체 토큰의 개선이 성과다. 작성 예제는 [IBL 조합 가이드](../data/guides/ibl_composition.md)를 따른다.

작성 행동과 결과 전달을 개선하기 위한 구체적 제안은
[작업 분해와 결과 전달 설계](IBL_TASK_DECOMPOSITION_DESIGN_2026_09_26.md)를 참고한다.
해당 문서에서 의식·실행 지침의 적용 상태와 교재·비교 실험의 후속 제안을 구분한다.
지침 반영만으로 효과 검증이 완료된 것은 아니다.

## 사례를 공통 개선으로 연결하는 법

개별 사례는 문제를 발견하고 재현하는 출발점이다. 설계에는 다음을 설명한다.

1. **실행 의도와 마찰**: AI가 무엇을 표현·실행하려 했고 어디에서 막히거나 반복 비용을 냈는가.
2. **공통 원인과 소유 위치**: 표현·통화·실행·도구 계약·맥락·기억·검수 중 무엇을 고쳐야 하는가.
3. **다른 작업으로의 적용**: 업무 이름·주제·편수 등을 바꿔도 같은 원인과 해결이 성립하는가.
4. **품질과 비용의 근거**: 어떤 기준선·입력·완료 조건으로 전후를 비교하는가.

업무의 내용과 개별 정책은 사전·데이터·함수·스크립트에 둔다.
코어는 그 업무가 드러낸 공통 표현·실행 문제를 맡는다. 표준/사전 경계는
[ibl.md의 언어의 경계](../data/system_docs/ibl.md#언어의-경계--표준과-사전-헌법-조항)를 따른다.
한 사례의 편의를 이유로 도메인 분기를 파서·엔진에 넣거나 새 어휘를 늘리지 않는다.
필요한 경우 기존 계약을 수리하고, 서로 다른 소비자가 실제로 공유하는 부분을 추출한다.

개별 업무의 수리와 특화도 필요할 수 있다. 다만 그 성과의 범위를 그대로 기록하며,
그것만으로 IBL 전체가 보편적으로 개선됐다고 주장하지 않는다.
보편성은 모든 과제에서 무조건 우월하다는 선언이 아니라,
**서로 다른 분야·도구·규모와 아직 굳히지 않은 새 과제에도 개선이 전달되는 방향**이다.

## 결과로 판단하는 법

| 축 | 비교할 것 |
| --- | --- |
| 품질 | 같은 사용자 목표와 달성 기준에서 정확성·완전성·근거·사용 가능성. 누락·실패 은폐·사용자 수정량도 확인한다. |
| 시간 | 요청부터 필요한 검수·복구를 거쳐 사용 가능한 결과가 준비될 때까지의 실제 경과 시간. 병렬 호출 시간의 단순 합과 구분한다. |
| 토큰 | 주 실행·내부 AI·감독·검수·수리·해당 작업이 유발한 증류 등 전체 모델 사용량. 입력·출력·캐시 사용을 구분하고 중복 합산하지 않는다. |
| 적용 범위 | 서로 다른 작업과 미사용 사례, 작은 입력과 큰 입력, 정상 실행과 부분 실패에서 효과·퇴행이 어떻게 달라지는가. |

모델·자료·권한·완료 조건 등 비교 조건을 맞추거나 차이를 밝힌다.
문자 수·요청 크기·호출 횟수를 실제 토큰으로 간주하지 않으며, 미측정은 미측정으로 남긴다.
후처리 비용은 사용자 대기 시간과 구분해 기록하되 총토큰에서 숨기지 않는다.
새 상시 프롬프트·소개·관리 절차가 다른 작업에 더하는 비용도 확인한다.
학습·등록·사전 계산 비용은 매회 실행 비용과 구분해 재사용으로 회수되는 조건을 밝힌다.

품질을 유지·개선하면서 시간과 토큰을 함께 줄였을 때 목적에 부합하는 개선으로 평가한다.
한 축만 개선되거나 다른 축이 악화되면 부분 성과·상충 관계로 기록한다.
능력 공백을 닫거나 실패를 정직하게 드러낸 변경도 가치가 있지만, 아직 비용 개선까지 입증한 것은 아니다.
일부 평균의 이득이 다른 작업의 품질 저하나 큰 퇴행을 가리지 않도록 결과를 작업별로 남긴다.

이 기준은 설계와 실험의 판단 기준이다. 매 실행마다 별도 평가 AI나 감독 호출을 추가하라는 지시가 아니다.
검증 자체의 비용을 포함하여, 목적에 필요한 만큼의 관측과 비교로 개선을 입증한다.

## 큰 방향을 유지하면서 복잡성을 줄이는 법

기능 개선은 같은 사실을 판단하는 곳과 작성자가 알아야 할 특별 규칙을 불필요하게 늘리지 않아야 한다.
새 기능의 책임 소유자·영향을 받는 소비자와 함께, 대체되어 없어질 기존 경로·임시 지침을 밝힌다.
같은 핵심 계약은 생산자·소비자·교재·회귀까지 연결한 뒤 그 위의 기능을 정교하게 만든다.
상상훈련의 발견은 현 계약의 구현 결함, 계약의 공백, 업무별 선택을 구분해 처리한다.

코드 줄 수·파일 수 감소를 단순화의 대리 목표로 삼지 않는다. 실행 기록·업무 확정·공개 확정처럼
보장하는 것이 다른 책임은 유지하며, 같은 판단의 중복과 전환 뒤 남은 임시 경로를 줄인다.
현재 구조의 유지·통합·은퇴와 변경 순서는 [구조 수렴 설계](IBL_SYSTEM_CONSOLIDATION_DESIGN.md)를 따른다.
해당 문서는 설계안이며, 구현·실제 능력·비용의 검증 상태는 구분한다.
변경의 목적·소유자, 계약·소비자, 대체·제거, 검증·잔여는 기존 커밋 본문에 담고
changelog에는 결과 상태를 남긴다. 별도의 기록 문서나 새 검사기를 매 변경마다 만들지 않는다.
