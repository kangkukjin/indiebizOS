# IBL 진화 목적과 개선 판단

목적 정본: [vision.md — IBL과 주변 시스템의 진화 목적](../data/system_docs/vision.md#ibl과-주변-시스템의-진화-목적).
이 문서는 그 목적을 설계·구현·실험에 적용하는 기준이다. 개별 설계의 범위나 성공 사례가 이 목적을 좁히지 않는다.

## 목적과 개선 대상

**도구를 어휘로 포함하는 IBL과 주변 시스템을 진화시켜, AI가 실행 의도를 쉽고 정확하게 표현하고 다양한 작업에서 결과 품질을 유지·향상하면서 실제 완료 시간과 전체 토큰 소비를 줄인다.**

Python·TypeScript로도 도구를 조합할 수 있다. 문제는 외부 도구 사이의 이음매다.
IBL은 호출·통화·조합·실패의 계약을 언어와 실행 시스템의 공통 구조로 다루며,
그 구조를 지속적으로 개선할 수 있게 한다. 자연어 스킬이나 일반 언어도 개선 가능하지만,
IBL은 여러 작업에 걸친 개선의 대상과 검증 단위를 명시적으로 갖추려 한다.

개선 대상에는 어휘·문법·통화뿐 아니라 실행기·도구 어댑터·맥락 전달·기억과 회상·재사용·검수·복구·계측이 포함된다.
새 문법이나 새 어휘가 없어도 주변 시스템의 공통 마찰을 줄이면 목적에 기여할 수 있다.
반대로 문장이 짧아지거나 관용구가 많아져도 품질·시간·전체 토큰의 개선은 별도로 확인해야 한다.

## 세계의 지도는 아직 실행 어휘가 되지 않은 가능성을 상기시킨다

IBL의 어휘가 모든 도구를 직접 포함할 수는 없다. 세계의 지도는 가능한 한 많은 도구·방법·개념의
이름과 관계를 갖추고, 그중 과제에 맞는 것을 제공하여 사용자가 언급하지 않은 수단도 상기시킨다.
모델이 지식을 갖고 있다는 사실과 현재 과제에서 그 지식을 꺼내 선택한다는 사실은 구별한다.

좋은 웹페이지·웹앱 화면을 요청받았다면, 전문가가 고려할 방법과 재사용 가능한 자원을 선택하는 것도
작업의 일부다. 사용자가 도구 이름을 말하지 않았다는 이유로 익숙한 구현만 반복하거나,
이미 가져다 쓸 수 있는 것을 불필요하게 다시 만드는 경로에 갇히지 않도록 한다.
직접 구현이 사용자의 목적·제약인 경우와, 적절한 수단을 떠올리지 못해 직접 구현하는 경우는 다르다.

지도는 **과제에서 검토할 수 있는 가능성의 범위**를 넓히고, IBL은 연결된 능력을 실행·조합하는 비용을 낮춘다.
지도 등재는 설치·접근 권한·실행 가능성의 보증이 아니며, 모든 지도 항목의 IBL 액션화를 요구하지 않는다.
이름으로 전문지식을 회상하고, 필요한 검색·확인을 거쳐 현재 활용할 수 있는 수단을 선택한다.

평가에서는 사용자가 수단 이름을 주지 않은 과제를 포함한다. 관련 이름이 공급됐는지만 보지 않고,
더 적절한 방법을 실제 선택했는지, 불필요한 재구현을 줄였는지, 그 결과 품질·완료 시간·전체 토큰이
어떻게 달라졌는지 확인한다. 지도 검색·주입·추가 탐색의 비용도 포함한다. 현재 접근이 적절한 과제와
직접 구현이 목적인 과제에서는 불필요한 전환을 유도하지 않는지도 본다.

## 조합을 축적해 한 번에 맡길 수 있는 일의 크기를 키운다

성장 단위는 **어휘 → 문장·프로그램 → 관용구 → 관용구를 조합한 더 큰 프로그램**이다.
큰 프로그램도 검증 후 다시 관용구로 보관하여 다음 조합의 부품으로 삼는다.
정리들을 조합해 더 큰 정리를 세우고 단순한 개념으로 복잡한 개념을 정의하는 것처럼,
확보한 능력을 다시 표현의 단위로 써서 언어 시스템을 키운다.

간결함은 단계마다 필요한 표현과 이음매가 작다는 뜻이며, 프로그램 전체가 짧아야 한다는 뜻은 아니다.
필요한 절차를 길게 구성해도 값 전달·분기·검수·실패 처리의 뜻이 일관되어야 한다.
“한 번에 실행”은 정해진 절차를 한 호출로 맡기는 것이다. 내부 도구·AI 호출과 반복은 남고,
그 실행 비용까지 포함해 기존 방식과 비교한다.

이 방향의 개선을 설계할 때는 다음을 확인한다.

- **다시 조합할 수 있는 결과**: 관용구의 입력·반환·적용 조건·부작용·실패가 드러나고, 결과가 다음 부품으로 연결되는가.
- **정의를 반복하지 않는 사용**: 필요한 관용구를 찾아 계약으로 호출하고, 수정·진단할 때 해당 정의를 펼칠 수 있는가. 모든 관용구의 본문을 상시 맥락에 싣지 않는가.
- **층을 넘는 검증과 복구**: 내부 실패의 위치와 이미 얻은 결과를 알 수 있어, 큰 조합에서도 필요한 범위를 보완할 수 있는가.
- **훈련으로 커지는 능력**: 익힌 관용구를 다른 입력·다른 부품과 조합한 새로운 과제에서 사용하고, 발견한 공백을 공통 구조에 환류하는가.

현재 중첩·호출 깊이와 재귀 제한은 구현 계약을 따른다. 여기서 말하는 층의 성장은 설계 방향이며,
무제한 중첩이나 재귀 실행이 이미 지원된다는 뜻은 아니다.
관용구 수·문장 길이·조합 깊이는 성장의 흔적이다. 더 큰 일을 안정적으로 맡기는 능력과
품질·시간·전체 토큰의 개선이 성과다. 작성 예제는 [IBL 조합 가이드](../data/guides/ibl_composition.md)를 따른다.

## 사례를 공통 개선으로 연결하는 법

개별 사례는 문제를 발견하고 재현하는 출발점이다. 설계에는 다음을 설명한다.

1. **실행 의도와 마찰**: AI가 무엇을 표현·실행하려 했고 어디에서 막히거나 반복 비용을 냈는가.
2. **공통 원인과 소유 위치**: 표현·통화·실행·도구 계약·맥락·기억·검수 중 무엇을 고쳐야 하는가.
3. **다른 작업으로의 적용**: 업무 이름·주제·편수 등을 바꿔도 같은 원인과 해결이 성립하는가.
4. **품질과 비용의 근거**: 어떤 기준선·입력·완료 조건으로 전후를 비교하는가.

업무의 내용과 개별 정책은 사전·데이터·함수·스크립트에 둔다.
코어는 그 업무가 드러낸 공통 표현·실행 문제를 맡는다. 표준/사전 경계는
[ibl.md의 언어의 경계](../data/system_docs/ibl.md#언어의-경계--표준과-사전-헌법-조항)를 따른다.
한 사례의 편의를 이유로 도메인 분기를 파서·엔진에 넣거나 새 어휘를 늘리지 않는다.
필요한 경우 기존 계약을 수리하고, 서로 다른 소비자가 실제로 공유하는 부분을 추출한다.

개별 업무의 수리와 특화도 필요할 수 있다. 다만 그 성과의 범위를 그대로 기록하며,
그것만으로 IBL 전체가 보편적으로 개선됐다고 주장하지 않는다.
보편성은 모든 과제에서 무조건 우월하다는 선언이 아니라,
**서로 다른 분야·도구·규모와 아직 굳히지 않은 새 과제에도 개선이 전달되는 방향**이다.

## 결과로 판단하는 법

| 축 | 비교할 것 |
| --- | --- |
| 품질 | 같은 사용자 목표와 달성 기준에서 정확성·완전성·근거·사용 가능성. 누락·실패 은폐·사용자 수정량도 확인한다. |
| 시간 | 요청부터 필요한 검수·복구를 거쳐 사용 가능한 결과가 준비될 때까지의 실제 경과 시간. 병렬 호출 시간의 단순 합과 구분한다. |
| 토큰 | 주 실행·내부 AI·감독·검수·수리·해당 작업이 유발한 증류 등 전체 모델 사용량. 입력·출력·캐시 사용을 구분하고 중복 합산하지 않는다. |
| 적용 범위 | 서로 다른 작업과 미사용 사례, 작은 입력과 큰 입력, 정상 실행과 부분 실패에서 효과·퇴행이 어떻게 달라지는가. |

모델·자료·권한·완료 조건 등 비교 조건을 맞추거나 차이를 밝힌다.
문자 수·요청 크기·호출 횟수를 실제 토큰으로 간주하지 않으며, 미측정은 미측정으로 남긴다.
후처리 비용은 사용자 대기 시간과 구분해 기록하되 총토큰에서 숨기지 않는다.
새 상시 프롬프트·소개·관리 절차가 다른 작업에 더하는 비용도 확인한다.
학습·등록·사전 계산 비용은 매회 실행 비용과 구분해 재사용으로 회수되는 조건을 밝힌다.

품질을 유지·개선하면서 시간과 토큰을 함께 줄였을 때 목적에 부합하는 개선으로 평가한다.
한 축만 개선되거나 다른 축이 악화되면 부분 성과·상충 관계로 기록한다.
능력 공백을 닫거나 실패를 정직하게 드러낸 변경도 가치가 있지만, 아직 비용 개선까지 입증한 것은 아니다.
일부 평균의 이득이 다른 작업의 품질 저하나 큰 퇴행을 가리지 않도록 결과를 작업별로 남긴다.

이 기준은 설계와 실험의 판단 기준이다. 매 실행마다 별도 평가 AI나 감독 호출을 추가하라는 지시가 아니다.
검증 자체의 비용을 포함하여, 목적에 필요한 만큼의 관측과 비교로 개선을 입증한다.
