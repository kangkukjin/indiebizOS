## 2. 근거와 재현 범위

에피소드 4005와 그 실행 폴더를 읽기 전용으로 조사했다. 등록된 관용구 본문은 `data/idioms/ai_tips_report.ibl`과 일치한다.

- 전체 19분 5초, 주 모델 응답 54회. billable_usage 기준 입력 5,235,767토큰(캐시 읽기 4,802,912 포함), 출력 37,351토큰. 내부 호출 22회가 포함된 수치이며 바깥 응답 수와 내부 호출 수는 별개다.
- 관용구는 두 차례 실제 실행 모두 미완료. 첫 검색 보완 뒤 재진입했고, 다음에는 후보 비교 입력 상한에서 중단했다. 최종 산출물은 주 실행자가 별도 IBL로 완성했다. check:true 호출을 실행 성공으로 세지 않는다.
- 저장된 state와 input-candidates를 현재 `stage_candidates`에 넣어 외부 호출 없이 상한 실패를 재현했다. 신규 후보 18개는 3,476자, 기존 647개 비교 자료는 149,577자, 지시를 포함한 요청은 153,360자다. 제한은 57,000자다.
- 같은 기존 자료의 tip/how만으로도 140,484자다. 편집·최종 검수에도 이 자료를 다시 넣으므로 첫 상한만 늘리는 수리는 불충분하다.
- 실제 시범은 기존 팁 0개에서 최종 검수 탈락 후 일부를 제외하여 11개 팁 초안으로 완주했다. 운영 규모의 검증과 구별한다.
- 최종 8개 팁은 보존 자막과 인용·시각을 결정론적으로 대조해 통과했다. 내용·편집 검수는 유지할 근거가 있고, 편집 검수는 미확인을 적용 불가로 단정한 표현을 적발했다. 의미 품질 전부를 이번 조사에서 독립 채점한 것은 아니다.
- 두 차례 추출은 원래 품질 절차다. 이를 불필요한 중복 호출로 계산하지 않는다. 모델·자료가 다른 과거 회차와의 단순 시간 차이를 개선 효과로 삼지 않는다.

### 값 전달 축약의 격리 실험

기존 `test_ai_tips_report.py`의 실행 fixture(실제 파서·엔진, 외부 응답 대역, 임시 디렉터리)를 사용했다. 운영 관용구·원장·본문은 바꾸지 않았다.

1. 명시적인 `data:{items:${변수.items?}, ...}` 15곳을 전부 `data:$변수`로 바꾸면 9,195→3,544자로 짧아지지만 자막 단계에서 실패한다. 봉투여야 하는 자리에 행 목록이 도착한다.
2. each 내부 4곳을 남기고 바깥 11곳만 바꾸면 5,367자로 줄고 정상 fixture는 통과한다. **부분 실패·잘림 진단 보존은 이 통과로 입증되지 않는다. 배포 가능한 축약으로 취급하지 않는다.**
3. 원인은 `workflow_binding._v4_var_payload`의 기존 값 추출 계약과 관계있다. `$변수`는 봉투 전체라는 뜻이 아니다. 이를 전역 변경하면 write·산문·표 전달 호환성을 깨뜨릴 수 있다.

따라서 새 봉투 문법부터 추가하거나 `$변수`를 전역 재해석하지 않는다.

## 3. 설계 결정 A — AI에 보낼 자료와 보존할 자료를 구분

### A1. 기존 table:ai에 선택 인자 두 개를 추가하는 안

아래는 **제안 인자이며 아직 지원하지 않는다**. 새 액션·파서 문법은 추가하지 않는다.

| 인자 | 제안 계약 |
| --- | --- |
| `input_fields` | 모델에 보낼 원 행의 최상위 필드 목록. 생략하면 현재와 동일하게 전 필드. 지정 시 비어 있지 않은 중복 없는 문자열 목록. 초기 구현은 최상위 필드만 지원해 별도 경로 문법을 만들지 않는다. |
| `preserve_rows` | 기본 false로 기존 선별·증식 동작 유지. true이면 모든 원 행 색인이 정확히 한 번 있어야 하며, 누락·중복·추가·범위 밖 색인과 색인 없는 전체행 폴백을 오류로 반환한다. 입력 순서로 병합한다. |

`fields`는 기존대로 **병합 뒤 출력 필드**다. input_fields와 의미를 바꾸거나 통합하지 않는다.
입력 투영은 모델용 사본에만 적용한다. 전체 원 행은 실행기에 남기고, 기존 색인 병합으로 결과를 붙인다. 내부 색인은 투영 뒤 실행기가 넣는다.
투영에서 제외한 기존 필드의 변경을 모델이 반환하면 거절한다. 새 출력 필드·명시적으로 공급된 필드의 갱신은 기존 schema/fields 계약을 따른다.
요청한 필드가 모든 행에 없으면 호출 전 오류, 일부 행에서만 없으면 해당 행에서 결측을 유지한다. null과 결측을 자동으로 같게 만들지 않는다.
preserve_rows는 필드 값의 진실성·불변성을 보장하지 않는다. 식별자 같은 불변값은 기존 결정론 소비자 검사 또는 모델 출력에서 제외한 원 행 병합으로 보호한다.

크기 검사는 투영·색인 삽입 후 실제 직렬화본에 대해 수행한다. 입력 한도를 토큰 수로 위장하지 않고 chars/bytes/token_estimate를 구별한다.
기존 `_items_payload` 오류에 실제 크기·한도·행 수를 구조적으로 덧붙이는 쪽으로 구현한다. 예산 때문에 자동 take하거나 요약하지 않는다.
모델 등급·기어는 유지한다. 다른 제공자 판정으로의 자동 교체는 범위 밖이다.

소유: `data/packages/installed/tools/ai-ops/handler.py`, 같은 패키지 `ibl_actions.yaml`.
schema 검사는 `backend/common/record_schema.py`를 사용한다. 옵션의 타입·출력 열 추론은 사전 선언과 기존 검사기를 통해 연결한다.

### A2. 큰 집합의 판단은 작업 성질에 맞춰 구성

input_fields만으로 한 행 안에 든 큰 자료가 작아지지는 않는다. 요청 작성자가 판단을 분리해야 한다.

- 각 행이 독립인 추출·분류: 기존 chunk/each를 사용하고 원 행 ID와 미처리 범위를 보존한다.
- 전체에서 선정·비교: 전체를 보지 않고 독립 분할 결과를 곧바로 최종 판정으로 쓰지 않는다. 분할 비교 결과의 통합 기준을 명시한다.
- 누적 기록: 비교에 필요한 후보를 찾고, 판단한 ID·근거·원문 참조를 남긴다. 제목만 보고 의미 중복이 없다고 확정하지 않는다. unknown은 원문으로 확대한다.
- 검색 기반 축소는 재현율·누락을 별도로 검증한 뒤 사용한다. 검증 전의 기준 경로는 전체 자료 분할 비교다. 분할은 처리 가능성을 보장하는 방법이지 그 자체로 토큰 절감의 증거가 아니다.
- 편집은 채택 결과와 필요한 비교 근거를 받는다. 독립 내용 검수는 원문을 대조한다. 같은 목적의 전체 원장 재전송과 판단 반복만 제거한다.

이 패턴은 먼저 기존 조합 가이드와 서로 다른 두 업무의 함수로 표현한다. 한 보고서의 주제·편수·분류를 코어 계약으로 승격하지 않는다.

## 4. 설계 결정 B — 성공 결과의 확정과 다음 요청 준비를 분리

현재 보고서 helper는 입력 검증·결과 수용·다음 AI 요청 작성이 한 stage 함수에 묶인다.
마지막 요청 작성이 실패하면 검증한 중간 결과도 해당 단계의 완료 영수증을 얻지 못한다. 입력 파일은 남지만 다시 사용할 위치를 주 실행자가 해석해야 한다.

제안하는 내부 단계 경계:

```text
외부/AI 결과 → 수용 검사 → 원본·수용 결과·근거를 원자적으로 저장
                         ↓
                    다음 요청 준비 → 크기/자료 부족이면 보완 필요 반환
                         ↓
                    다음 단계 실행
```

수용 영수증과 요청 준비 결과는 별개다. 다음 요청 준비 실패가 수용 영수증을 지우지 않는다.
재실행은 완료된 외부 호출을 스킵하고, 남은 **요청 준비**부터 수행한다. 이미 저장한 AI 결과를 읽는 것에 criteria 모델을 다시 호출하지 않는다.

영수증은 실행 범위(주체·프로젝트·run), 단계와 구현 버전, 입력·출력·근거·기준 지문, 산출물 참조, 수용 시각을 가진다.
AI 단계에는 실제 모델·기어·지시·schema 식별자를 함께 남긴다. 같은 데이터라는 이유만으로 다른 기준·다른 사용자 작업의 결과를 전역 캐시하지 않는다.
같은 입력과 기준의 수용 결과를 재개에 사용하며, 새 관측·재판정 요청은 새 시도다. 읽기 결과도 현재성이 요구되는 작업에서는 갱신 여부를 명시한다.
입력·코드·기준 변경은 의존하는 후속 결과를 무효화한다. 처음에는 절차에 선언된 선후 관계만 사용하고 임의 프로그램의 의존 그래프를 추측하지 않는다.

보완 응답의 내부 최소 정보는 `blocked_stage`, `reason_code`, `accepted_refs`, `needed`, `continuation`이다.
reason은 empty/source_failure/input_limit/needs_evidence/quality_failure/conflict를 구별한다. 보완 중은 완료 성공이 아니다.
continuation은 소유 실행과 지문에 묶인 참조다. 보완값도 동일한 수용 검사를 통과한 뒤 후속 단계로 이어진다.
새 문법이나 일괄 자동 재시도는 도입하지 않는다. 기존 script의 명시 op와 IBL if/try/변수·resume를 사용한다.

보고서에서는 `candidates`가 검증한 추출 결과를 먼저 저장하고, `chosen` 요청 준비를 분리하는 것이 첫 적용이다.
현행 영수증은 보존한다. 새 버전으로 재개할 때 원본·구현·검수 계약 호환을 확인할 수 있는 완료 단계만 수용하고 불명은 보류한다. 현재 4005의 운영 원장에 자동 재적용하지 않는다.
기존 수리 경로(revise)와 전후 쓰기 저널은 유지한다. 임의 외부 쓰기의 exactly-once를 보장한다고 확대하지 않는다.

이 계약은 먼저 기존 helper의 작은 내부 함수들로 구현하고, 별도 표 처리 fixture에도 적용해 공통성을 검증한다.
두 소비자가 실제로 공유하는 파일 영수증 코드만 추출한다. 필요 시 소유 위치는 `backend/datastore/`이며 기존 잠금·원자적 저장 규약을 재사용하고 층 배정을 추가한다. 전역 워크플로 엔진 교체는 하지 않는다.

## 5. 설계 결정 C — 구조 검사와 의미 검수의 책임 분리

- `schema`·원 행 색인·필수 ID·인용 존재·시각 대응은 기존 코드와 A1의 보존 계약이 검사한다.
- `criteria`는 근거 충분성·실행 가능성·과장·해석 오류 같은 의미 기준에 쓴다. 자연어 criteria를 정규식으로 분류해 자동 제거하지 않는다.
- 해당 관용구의 순수 구조 criteria를 개별 검토하여 코드 계약으로 옮긴다. schema_fields는 단일 자유 라벨과 중첩 result 객체 구조를 전부 검사하는 JSON Schema 검증기가 아니다. 그 빈틈은 기존 `answer/keyed` 등 결정론 소비자 검사로 덮어야 한다.
- 0행이어도 의미 기준이 “최소 한 건”이면 실패가 맞다. 빈 결과·캐시라는 이유로 엔진의 모든 criteria를 생략하지 않는다.
- 원문 검수와 편집 검수를 유지한다. 검토된 자료·기준 지문이 같을 때 결과를 재사용하고, 수정된 주장과 영향을 받는 근거만 재검토한다. 해석이나 선정 기준이 바뀌면 해당 범위는 다시 본다.

4005의 criteria 호출 7회는 후보 조사 대상이다. 모두 불필요하거나 그 지연 합계가 곧 벽시계 절감이라고 주장하지 않는다.
소유: ai-ops 출력 검사, 개별 IBL criteria 작성, 기존 `ibl_quality.py`의 의미 판정. 별도 감독 AI는 추가하지 않는다.

## 6. 설계 결정 D — 스크립트로 원본 봉투를 명시적으로 전달

`HONESTY_KEYS`와 원본/표시 분리는 이미 존재한다. 새 키 목록을 소비자마다 복사하지 않는다.
`$변수`의 값 추출 규약은 유지한다. 15곳을 단순 치환하는 실험이 실패했으므로 그 축약을 적용하지 않는다.

첫 구현 후보는 **기존 self:script의 선택 인자 `input_as`**다(아직 미지원).

```ibl
# 제안 표기: args는 작은 설정, 앞 통화의 원본 봉투는 stdin의 data에 주입
$결과 >> [self:script]{op:"run",id:"등록된처리",args:{op:"accept"},input_as:"data"}
```

- 생략 시 현재 동작 그대로. run에서만 사용하며 input_as는 비어 있지 않은 최상위 인자 이름이다.
- args에 같은 키가 있거나 args_file을 함께 주면 호출 전 거절한다. 암묵적으로 덮어쓰지 않는다.
- 실제 실행용 앞 결과를 기존 파이프 통화 정규화 규약으로 읽는다. 모델 표시 사본·미리보기를 원본으로 사용하지 않는다. items와 원천·진단을 함께 전달한다.
- 앞 결과 없음과 정상 빈 items를 구별한다. 실패 통과 정책은 기존 파이프 규약을 바꾸지 않는다. 정상 통화에 딸린 부분 실패는 소비자가 명시적으로 판정한다.
- 원본 봉투는 값 전달의 별도 출처이며 새 내부 표식이 사용자 객체의 value/data 키와 충돌하지 않게 한다. 접근 주체·경로 제한은 기존 script 실행 경계를 따른다.
- 함수/each/원격 전달에서 원형과 진단이 보존되는 시험을 먼저 만든다. 필요시 기존 ibl_honesty·공용 통화 함수를 사용하고 필드 목록을 재복제하지 않는다.

소유: system_essentials의 `script_ops.py`와 `ibl_actions.yaml`. parser에 script 이름을 넣지 않는다.
이것으로 바깥 연결부터 줄인다. each 내부 4곳의 구조까지 없애려고 새 봉투 문법이나 subprocess 호출을 늘리지 않는다. 남은 부분은 보존하고 추가 일반화는 별도 비용 비교 후 결정한다.

기능별 시험 행렬:

- 데이터: 0/1/여러 행, 입력 순서, 일부 결측/null, 큰 원문, 중첩 값, 사용자 데이터의 value/items 키.

- 쓰기: 이미 반영한 효과를 무조건 재호출하지 않음, 원장 충돌 보류, 새 run과 기존 완료 결과 혼동 방지.
- 독립 업무: 보고서 외에 다수 문서의 근거 추출·대조, 표의 행별 분류·후속 변환, 파일 처리의 일부 실패·재개. 평가용 새 조합 하나는 교재·설계에서 제외.

### 비용과 품질의 채택 기준

같은 모델·기어·입력 스냅샷·품질 기준·수리 기회로 기존/개선 경로를 비교한다. 한 축씩 바꾸고 반복 실행한다.
자료·판정 기준·입력 크기는 미리 고정하며 결과가 마음에 들도록 뒤에서 기준을 바꾸지 않는다.
정확성·근거·완전성·사용자 요구 충족을 먼저 통과시킨다. 독립 의미 평가의 변동은 사람의 표본 검토로 확인한다.
재현 가능한 정확성·누락·중복 부작용 회귀는 허용하지 않는다. 작은 표본의 평균 점수만으로 전체 품질 동등을 주장하지 않는다.
시간은 사용자에게 검수된 결과가 준비되는 시점까지, 토큰은 주 실행·내부 생성·criteria·필수 수리를 포함해 집계한다. 캐시 입력·신규 입력·출력을 분리하고 추론 토큰을 출력에 다시 더하지 않는다.
동일 call/response 원장을 중복 합산하지 않고 병렬 내부 지연을 바깥 벽시계에 더하지 않는다. 증류 등 후처리는 별도로 보고한다.
`first_program_success`의 action_count>=2 규칙은 단일 fn 호출·describe/check와 맞지 않으므로 대표 합격 지표로 쓰지 않는다.
품질을 지켰으나 시간 또는 토큰이 늘면 그 변경은 사용자 조건을 충족한 개선으로 채택하지 않는다. 예외 복구 능력만 좋아진 결과는 별도로 표시한다.
