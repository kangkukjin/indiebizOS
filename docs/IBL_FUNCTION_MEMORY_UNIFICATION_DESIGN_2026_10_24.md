# IBL 저장 함수와 관용구의 통합 설계

작성일: 2026-10-24. 상태: **설계 완료, 구현·데이터 이전 전**.
조사 기준: 정본 main `3b6dafee`와 현재 코드. 구현 착수 시 이후 변경을 대조한다.

저장 함수와 관용구를 **하나의 재사용 가능한 IBL 함수 체계**로 통합한다. 함수의 정의·검사·
저장·개정·호출은 공통 계약으로 모으고, 해마는 그 함수를 발견하고 경험과 연결한다.
작은 함수와 큰 작업 절차는 같은 종류이며, 조합한 결과를 다시 같은 방식으로 저장한다.
완료 조건은 통합 목록의 제공이 아니라 **해마·배포 파일에서 실행 본문을 따로 해소하거나
수정하는 경로의 제거**다.

목적은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)의 품질·완료 시간·전체 토큰과
[조합의 축적](../data/system_docs/vision.md#조합의-축적--더-큰-행위를-한-번에-표현하는-언어)을 따른다.
[구조 수렴 설계](IBL_SYSTEM_CONSOLIDATION_DESIGN.md)의 책임 원칙을 함수 정의에 구체화한다.
이 문서의 자료 구조·인터페이스는 구현할 목표이며 현재 API로 안내하지 않는다.

## 1 결정과 범위

1. 실행 가능한 영구 정의는 **함수** 한 종류다. 관용구는 익혀 재사용하는 함수를 부르는 말이고,
   워크플로우는 여러 단계를 수행하는 함수의 용도를 설명한다. 둘을 저장 형식·실행 분기의 키로 쓰지 않는다.
2. 함수 정의의 정본은 하나다. 기억·검색 색인·프롬프트·배포 교재는 정의를 참조한다.
   역사적 코드와 용례 원문은 보존하되, 이름으로 호출할 현재 정의를 결정하지 않는다.
3. 함수의 지속적인 식별자와 불변 판본을 도입한다. 실행 중인 정의·성적·검증 근거를
   이름이나 현재 코드의 문자열 일치로 추정하지 않는다.
4. 지역 함수는 저장 없이 작성·조합한다. 저장은 재사용할 필요가 생겼을 때 수행한다.
   함수 등록, 발견 가능성, 상시 소개, 실행 권한은 서로 독립된 질문이다.
5. 기존 IBL 컴파일러·런타임·권한·재개·증류·사건 원장을 확장한다. 새 실행 언어나
   범용 능력 관리 프레임워크, 모든 호출에 붙는 평가 AI를 만들지 않는다.

등록 Script는 별도 구현 경계로 유지한다. Python 실행 파일과 IBL 본문은 실행 의미가 다르다.
함수가 Script를 호출할 수 있고 발견 목록을 함께 보여 줄 수 있지만, 이번 통합을 이유로
Script를 함수 본문으로 복제하거나 모든 Script에 래퍼 함수를 만들지 않는다.

## 3 정의와 기억과 실행의 관계

```mermaid
flowchart LR
    A[직접 작성과 경험 후보] --> B[공통 등록과 개정 검사]
    P[배포 함수 설치] --> B
    B --> C[함수 원장과 불변 판본]
    C --> D[컴파일과 실행 계획]
    D --> E[기존 런타임]
    C --> F[해마의 함수 참조와 발견 색인]
    F --> G[계약 조회와 조합]
    G --> D
    E --> H[기존 실행 기록과 검증 근거]
    H --> F
```

### 함수의 정체성과 판본

`function_id`는 소유 범위 안에서 지속되는 불투명 ID다. 이름·파일명·DB 행 번호를 ID로 쓰지 않는다.
주인과 회원의 범위를 합친 전역 원장을 만들지 않는다. `scope_id`는 서버가 신뢰할 수 있는
현재 주체·저장 범위에서 정하며, 사용자가 임의 입력한 값으로 다른 원장을 선택하지 못한다.

| 정보 | 소유자와 뜻 |
| --- | --- |
| `scope_id`, `function_id` | 함수의 식별과 소유 범위. 출처가 달라도 동일한 관리 계약을 쓴다. |
| `name`, 현재 `revision`, 상태 | 현재 호출 이름과 공개된 판본을 정하는 원장 카탈로그. |
| `revision`, `edition`, `source`, `source_hash` | 불변 정의. 판본은 정규 직렬화한 정의 레코드의 지문이며 언어 판본인 edition과 구별한다. |
| 설명·적용 조건·명시 완료 조건 | 작성자가 선언한 함수 메타데이터. 변경도 판본으로 보존한다. 완료 조건의 유무를 숨기지 않는다. |
| 입력·반환·효과·의존 관계 | 해당 정의와 의존성으로 컴파일러가 파생한다. 독립 수기 계약으로 이중 소유하지 않는다. |
| 출처·배포 소유·기원 | 사람이 작성했는지 경험 후보에서 등록됐는지, core/user인지 기록한다. 호출 종류를 나누지 않는다. |
| 주제·사용 경험·검색 표현·상시 소개 선정 | 해마의 참조 메타데이터. 함수 본문과 분리한다. |
| 실행·검증·수리 증거 | 기존 실행 기록과 `capability_history`의 사건. 함수 판본과 실제 의존 지문에 연결한다. |

명시 완료 조건은 함수 반환 성공과 별개다. 현재 타입 체계가 보장하지 못하는 의미는 산문과
실제 검증 근거로 남기며, 관측 반환 필드를 선언 타입으로 자동 승격하지 않는다.

### 정본의 물리 저장

기존 `data/workflows/`를 함수 원장의 거처로 발전시킨다. 저장 경로 이름을 바꾸는 일을
통합의 선행 조건으로 삼지 않는다. 목표 구조는 다음과 같다.

```text
data/workflows/
  catalog.json                     # 이름과 ID와 현재 판본, generation, 은퇴 상태
  revisions/<function_id>/<revision>.yaml  # 불변 정의와 메타데이터
```

카탈로그는 실행할 본문을 복제하지 않는다. 불변 판본 파일이 본문의 유일한 정본이고,
카탈로그는 활성 판본을 선택한다. 검색 DB·컴파일 캐시·배포 묶음은 이 정본과 역할이 다르다.
새 범용 객체 저장소를 만들지 않고 `workflow_store`의 파일 잠금·원자 교체를 확장한다.
저장 영역이 다른 회원도 같은 자료 계약을 사용하되 현재 회원 저장 소유자 안에 둔다.

이 선택은 원문을 파일로 검토·백업하는 기존 장점을 유지하면서 여러 정의의 공개를 하나의
확정점에 묶기 위한 것이다. DB 원장과 파일 원장을 동시에 정본으로 두지 않는다. 사람이
판본 파일을 직접 고쳐도 지문 검사에서 거절되며, 수동 작성 파일은 공통 등록의 입력으로 받는다.
revision 지문에서는 revision 필드 자체와 파생 계약·실적을 제외하고, 정규 직렬화 규칙을
저장 형식 버전으로 고정한다. 실행 의미와 메타데이터의 변경을 source_hash와 revision으로 구분한다.

원장의 모든 쓰기는 같은 잠금과 다음 순서를 사용한다. 기대 generation·기대 revision 확인,
변경 후 전체 이름 공간 구성, 영향받는 호출자 검사, 새 판본 파일 기록·fsync,
새 카탈로그 기록·fsync·원자 교체·상위 디렉터리 동기화 순이다. 카탈로그 교체가 확정점이다.
여러 함수의 동시 개정도 판본 파일들을 준비한 뒤 카탈로그 하나를 교체한다.
응답 유실 후 재시도는 같은 변경 요청 ID와 내용 지문으로 기존 확정 결과를 돌려준다.

읽기는 카탈로그를 한 번 읽고 그 판본들만 사용한다. 쓰기 중단으로 남은 미참조 판본은
호출되지 않으며, 없는 판본·잘못된 지문을 옛 DB로 우회하지 않는다. 해당 함수의 손상을
진단하고 무관한 정상 함수를 계속 사용할 수 있게 한다. 카탈로그 자체가 깨지면 명시 실패한다.
보존 판본의 정리는 현재 정의·의존 참조·재개 가능한 실행·검증 근거를 확인하는 별도 보존 정책이며,
이 설계의 이행에서 옛 증거를 자동 삭제하지 않는다.

## 4 하나의 관리 계약

공통 소유자는 다음 의미를 제공한다. 아래 이름은 내부 책임을 설명하며 새 IBL 어휘 제안이 아니다.

| 연산 | 계약 |
| --- | --- |
| 목록과 상세 | 범위 안의 함수 ID·이름·현재 판본·사용 가능 여부·이유를 돌려준다. 손상·은퇴 항목을 없는 것으로 숨기지 않는다. |
| 등록과 개정 | 명시 정의를 컴파일하고 기대 판본·이름 충돌·전이 호출자의 개정 전후 상태를 검사한 뒤 원자 확정한다. |
| 이름 변경 | ID는 유지한다. 정의 머리·호출자·앱·예약 참조를 함께 이행하거나 명시 충돌로 막는다. 문자열 치환으로 코드를 고치지 않는다. |
| 은퇴 | 새 이름 호출에서 제외하되 정의·이력은 남긴다. 활성 호출자·예약·앱 참조가 있으면 영향을 표시하고 이행 전 은퇴를 거절한다. |
| 계약 조회 | 컴파일러가 계산한 입력·반환·효과·실행 전 확인 조건과 함수 참조를 돌려준다. |
| 발견 | 기억 색인에서 후보 참조를 찾고 현재 원장·권한·계약으로 확인한다. 검색 적합도는 실행 가능성의 증명이 아니다. |

은퇴한 함수는 pinned를 포함한 새 실행에서 거절한다. 이미 실행 중인 계획은 현재의
취소·권한 규칙을 따르며, 은퇴를 외부 작업의 강제 취소로 취급하지 않는다. 역사 조회는 유지한다.
기존 코퍼스의 hold·quarantine·invalid 상태는 이전 과정에서 활성 함수로 바뀌지 않는다.
정의 상태와 기억의 노출 자격을 따로 보존하고, 재활성화는 이유와 검사를 갖춘 명시 개정으로 수행한다.

현재 `[self:workflow]`의 save/list/detail/run/delete와 `[fn:이름]`을 공통 계약의 입구로 쓴다.
화면·교재의 기본 명칭은 ‘함수’로 정리하되 어휘명을 바꾸기 위한 `self:function`을 추가하지 않는다.
`delete`의 은퇴·물리 삭제 차이는 응답과 교재에 명시하며 과거 의미를 조용히 바꾸지 않는다.
추가되는 함수 참조·기대 판본 필드는 YAML 정본과 가이드·핸들러 안내를 함께 갱신한다.

함수 등록의 필수 조건은 언어 유효성, 닫힌 입력, 이름·소유권, 의존 계약이다.
무인자 함수도 유효하다. 기존 관용구의 12자 이름·슬롯 개수·문장 수 같은 휴리스틱은
컴파일·저장의 자격 조건에서 제거한다. 소개 품질 판단에 유용하면 비차단 안내로 남긴다.
개인 자료가 포함된 정의의 공개·배포 제한은 별도로 유지하며 휴리스틱 제거로 풀지 않는다.

수정 허용은 정적 호환을 뜻한다. 같은 입출력으로 업무 의미를 바꾼 경우까지 자동으로
안전하다고 주장하지 않는다. 새 판본의 검증 근거와 변경 설명을 보존하고, 고정 판본을
선택한 호출자는 자동 전환하지 않는다. 호출자 변경 묶음을 한 번에 검사할 수 있게 하되
새 함수 이름을 만들어 점진적으로 전환하는 기존 방법도 유지한다.

## 5 호출과 판본 선택

기본 `[fn:이름]`은 **컴파일 시작 때의 원장 스냅샷**에서 현재 판본을 선택한다.
지역 `[def:]`가 같은 이름을 가리는 기존 규칙은 유지한다. 컴파일된 계획에는 호출되는
함수 ID·revision·연결된 소스 위치·전이 의존성 지문을 기록하고 실행 중 다시 해소하지 않는다.
현재 본문의 변경은 실행 중인 계획을 바꾸지 않는다.

직접 이름 호출은 최신 정의를 조합하는 방식이다. 앱·예약 등 지속 소비자는 참조에
`selection: current|pinned`를 명시한다. `current`는 실행 시작 때의 스냅샷,
`pinned`는 저장된 함수 판본과 함수 의존성 묶음을 선택한다. 기본 이행은 기존의 최신 저장본
실행 의미에 맞는 current이고, 임의로 모든 예약을 고정하지 않는다. pinned는 패키지·장치·
외부 서비스 환경까지 동결한다는 뜻이 아니다. 해당 의존의 변경·부재는 기존 실행 검사로 드러낸다.

재개는 원래 계획과 영수증이 가진 판본·의존 정보를 사용한다. 보존 자료가 없거나 의존
조건이 맞지 않으면 재개 불가로 남긴다. 최신 함수로 조용히 바꾸거나 완료된 쓰기를 반복하지 않는다.
권한·주체·취소·예산은 실제 실행 시에도 확인한다. 과거 판본을 보유한 사실은 현재 권한이 아니다.

current/pinned 선택은 저장 소비자의 참조와 기존 실행 요청 메타데이터에서 전달하고,
IBL 호출 문법에 새로운 판본 문법을 추가하지 않는다. pinned 묶음은 루트와 전이 함수의
ID·revision 및 이름 바인딩을 포함한다. 컴파일러가 그 묶음을 하나의 라이브러리로 검증하며,
누락된 하위 함수를 현재 카탈로그에서 임의 보충하지 않는다. 코드에 직접 쓴 이름과 저장
참조가 다르면 명시 충돌이며, 참조를 코드 문자열에 삽입해 실행하지 않는다.

저장 호출자 검사는 컴파일러가 해소한 전이 의존 관계를 사용한다. 앱·예약·위임의 저장된
프로그램은 각 원장의 기존 읽기 경로에서 함수 참조를 추출해 검사한다. 동적으로 구성된 이름이나
외부 클라이언트 코드를 모두 발견할 수 있다고 주장하지 않는다. 미해소 참조는 별도 목록과
실행 시 진단으로 남기고, 확인된 참조의 이행 완료를 전체 외부 호환의 증명으로 쓰지 않는다.

## 6 경험에서 함수로 이어지는 경로

경험·후보·등록 함수는 같은 것이 아니다. 기존 용례와 주행 원문은 계속 보존한다.
이름 없는 성공 프로그램은 자동으로 함수 원장이 되지 않는다. 재사용 가치가 있는 후보는
입력·반환·적용 조건·실행 근거를 갖추어 공통 등록 관문에 제출한다. 등록 주체가 사람인지
기존 증류 경로인지는 출처로 기록하고, 이번 통합으로 자동 추출 정책을 새로 켜지 않는다.

해마의 함수 카드는 `function_id`와 근거 판본을 참조한다. 검색 표현·주제·실적·경험의
정본과 현재 함수의 설명·계약을 구분한다. 판본이 바뀌면 과거 경험을 보존하면서 ‘이전 판본의
근거’로 표시하고 현재 계약을 다시 해소한다. 이름·본문이 비슷하다는 이유로 과거 검증을 복사하지 않는다.
함수의 본문을 검색용으로 색인하더라도 그 사본으로 실행하거나 정의를 복구하지 않는다.

기존 해마 문서의 함수 절은 참조 카드·주석의 편집면으로 바꾼다. 카드 삭제는 기억 연결만
해제하며 함수 삭제가 아니다. 본문을 펼쳐 보는 것은 허용하되, 수정은 기대 revision을 포함한
공통 함수 개정으로 명시한다. 과거 문서에서 본문이 달라졌다면 자동 덮어쓰기 대신 개정 후보로
보존하고 차이를 보여 준다. 이름 없는 용례·주행 원문의 편집 규약까지 바꾸지 않는다.

정의 확정과 검색 색인의 갱신을 분산 트랜잭션으로 묶지 않는다. 카탈로그 generation을
기준으로 기존 증류 영수증·투영 복구 경로가 색인 갱신을 재시도한다. 누락은 목록과 원장
대조로 재생성할 수 있어야 한다. 색인 실패 후에도 정확한 함수 호출·목록·상세는 가능하고,
오래된 검색 후보는 사용 전 원장과 대조한다. 지연 중인 회상은 오래된 계약을 현재 계약처럼 내놓지 않는다.

상시 소개는 기존의 명시 선정 정책을 유지한다. 함수 등록이 자동으로 프롬프트를 늘리지 않는다.
`always_on`과 curated 용례는 함수 참조에 연결하고, 계약은 원장으로부터 파생한다.
호출 용례 시딩은 기존 `add_examples_batch` 경로를 유지한다. 함수 정의를 심기 위해 별도
해마 코드 사본을 생성하는 관행은 제거한다.

## 7 실적과 검증의 귀속

컴파일의 소스 지도에 함수 참조를 싣고, 런타임의 기존 함수 결과 사건에 `run_id`, 호출
식별자, 함수 ID·revision·의존 지문을 연결한다. 사건을 재수집해도 같은 호출은 한 번만 집계한다.
중첩·반복 호출은 각 호출을 구별하며, 판본을 확정할 수 없는 옛 성적은 `legacy_unattributed`로
보존한다. 같은 코드라는 이유로 서로 다른 함수의 실적을 합치지 않는다.

다음 사실은 각각 기록한다.

- 함수가 반환했는가, 실패·취소·부분 결과가 있었는가.
- 원천 자료가 완전했는가, 외부 효과가 확정됐는가.
- 명시된 업무 완료 조건을 충족했는가. 평가하지 않았다면 미판정이다.
- 어떤 정의·의존 판본을 어떤 근거로 검증하거나 수리했는가.

현재의 `capability_history`와 실행 증거에 참조를 추가한다. 별도의 전역 성공 점수나 새 사건
원장을 만들지 않는다. 함수의 지문과 도구 의존 지문을 함께 보존해 본문이 같아도 의존 변경을
드러낸다. 검색용 집계는 이 사건에서 재구축하며, 함수 정의 저장소가 성적 원장까지 소유하지 않는다.

## 8 배포와 소유 범위와 보안

배포 `.ibl`과 manifest는 설치 입력이다. 설치기가 안정적인 배포 ID와 원천 지문을 확인하고
공통 원장에 등록한 뒤에만 호출 가능해진다. 런타임은 해마 시딩 여부나 배포 파일 직접 읽기로
빠져나가지 않는다. 임베딩 모델 없는 첫 부팅·오프라인 재시작에서도 설치된 함수는 실행한다.
core/user 경계와 개인 함수의 배포 제외는 `core_manifest`·dist filter에서 계속 집행한다.

업데이트는 현재 판본이 직전 설치 기준과 같은 경우에만 호환 검사를 거쳐 갱신한다.
사용자 개정이 있으면 새 배포 판본을 미활성 상태로 보관하고 충돌을 알린다. 같은 이름에
대한 조용한 덮어쓰기·최신 행 우선 선택을 하지 않는다. 병합은 명시 개정이며, 패키지 제거는
호출 의존을 검사하고 실행 근거에 연결된 과거 정의까지 지우지 않는다.

회원의 호출 내 정의는 현재 `ibl_member_library` 문맥을 유지한다. 영구 저장을 제공하는
소비자가 있으면 그 소유자 저장소에서 동일한 계약을 적용한다. 주인·프로젝트·회원 범위의
현재 접근 권한을 통합이라는 이유로 넓히지 않는다. 검색·describe·상세·소스 지도·캐시도
같은 범위를 따라야 한다. 수리 작업공간과 몸별 사전 활성 상태도 기존 해소 문맥을 유지한다.
몸 간 배포 ID가 같아도 설치 revision과 실행 가능성은 그 몸에서 확인한다.

컴파일 캐시는 함수 전이 판본·어휘/도구 계약 지문·컴파일러 판본·범위와 권한 문맥으로
구분한다. 기억 색인의 신선도나 이름만으로 캐시를 유효하다고 판단하지 않는다.

## 9 데이터 이전과 복구

이행 단위는 소유 범위의 함수 라이브러리와 그 호출자다. 함수 하나만 신원장으로 옮기고
나머지를 옛 DB에서 무기한 합치는 운영은 완료 상태로 인정하지 않는다.

1. **읽기 전용 재고 작성.** workflow 파일, 이름 있는 해마 행, 가지 문서, installed 정의,
   curated·seed 자료와 앱·예약·위임·회원 호출자를 조사한다. 원문 지문·판본·실제 해소 결과·
   출처·충돌·손상·미해소 참조를 남긴다. 정의 개수뿐 아니라 참조 수와 미확정 항목을 대조한다.
2. **안정적인 대응표 준비.** `(소유 범위, 기존 저장 종류, 기존 ID, edition, 원문 지문)`을
   새 함수 ID·revision에 대응시킨다. 같은 원천 배포 정의와 색인 사본임을 증명한 경우만 합친다.
   서로 다른 이름의 동일 코드, 별도 사용자 함수는 자동 합치지 않는다. 같은 이름의 다른 본문은
   임의 최신본을 택하지 않고 충돌로 남긴다. 재실행은 기존 대응표를 재사용한다.
3. **이전 전 백업과 변경 관문.** `data/_backups/YYYY-MM-DD_함수통합/`에 manifest와 파일을
   보존하고 라이브 SQLite는 `.backup`/`VACUUM INTO`로 복사한다. 구형 정의 쓰기는 짧은
   전환 구간 동안 막고 기존 실행은 이미 확보한 계획으로 계속한다. 실행 중 정의를 다시 찾는
   구형 작업은 종료를 기다리거나 시작 시 해소한 스냅샷을 제공할 수 있을 때만 전환한다.
   구형 writer 프로세스가 남아 있지 않은지 확인하고 최종 입력 지문을 재확인한다.
4. **비공개 원장 구성과 대조.** 새 카탈로그를 준비하고 이름 해소·계약·의존 관계·참조·권한을
   구형 결과와 비교한다. 실제 부작용 작업을 두 번 실행하는 shadow 실행은 하지 않는다.
   차이는 수정 또는 명시적 이행 결정으로 해소한다. 충돌 항목과 그 의존 소비자는 차단하되
   무관한 함수를 옛 경로로 되돌려 실행하지 않는다.
5. **한 번의 전환.** 런타임 해소기·공통 쓰기 경로·소비자 버전이 준비된 상태에서 카탈로그를
   확정한다. 이후 옛 저장소는 역사 자료 또는 명시 이행 입력이다. 실시간 이중 쓰기와 실패 시
   옛 원장 재조회는 금지한다. 오래된 등록 스크립트는 공통 경로로 전달하거나 명시적으로 거절한다.
6. **참조와 투영 재구축.** 해마 카드·curated·seed·앱·예약·성적에 대응표를 적용한다.
   기억 투영 지연은 복구하지만 정확 호출을 막지 않는다. 이전 전후 참조와 동작을 검증한다.
7. **구형 소유 경로 제거.** §11의 제거 조건을 충족한 코드와 교재를 삭제·은퇴 처리한다.
   남아 있는 호환 소비자는 대상과 사유·종료 조건을 구체적으로 기록한다.

판본 1의 본문은 edition을 유지한 불변 정의로 수용하고 기존 언어 호환 어댑터로 실행한다.
같은 이름의 판본 1·2가 함께 있는 경우, 옛 호출 문맥의 edition과 기존 ID를 명시 호환 참조에
매핑한다. 새 작성의 기본 이름은 현재 정의 하나로 해소한다. 원문 헤더만 바꾸거나 입력·반환
의미를 추정해 판본 2로 승격하지 않는다. **저장소 통합과 언어 판본 이전은 별개의 완료 조건**이다.
판본 1 소비자가 남으면 그 어댑터는 유지하되 별도 관용구 저장소는 유지하지 않는다.

전환 전 실패는 준비 산출물만 남기고 옛 활성 원장을 유지한다. 전환 후 실패는 이전 카탈로그
generation과 호환되는 코드로 되돌리며, 새로 생성된 함수·판본·참조를 보존한 채 쓰기를 잠시
막고 복구한다. 새 쓰기가 생긴 뒤 구형 DB 백업을 그대로 덮어쓰는 롤백은 금지한다.
구형 런타임으로의 복귀는 이후 변경을 변환·보존할 수 있을 때만 허용한다. 실행한 외부 효과는
원장 롤백으로 취소되지 않으므로 기존 영수증과 불명확 효과 판정을 유지한다.

## 10 구현 순서와 인수 기준

| 단계 | 구현 범위와 주요 소비자 | 이 단계의 완료 조건 |
| --- | --- | --- |
| 1 정체성과 읽기 스냅샷 | `workflow_store`, `ibl_v2_store`, 컴파일 소스 지도. 재고·대응표 도구. | ID·revision·generation이 명확하고 이름 충돌·손상을 진단한다. 운영 읽기는 아직 전환하지 않는다. |
| 2 공통 쓰기와 판본 확정 | 저장·개정·이름 변경·은퇴·배포 import. 모든 구형 쓰기 진입점 목록. | 동시 개정 충돌, 다중 정의 원자 확정, 중단 복구, 전이 호출자 검사를 통과한다. |
| 3 실행과 지속 소비자 | `ibl_v2_store`, `workflow_engine`, `ibl_member_library`, 예약·앱·직접 위임·재개. | 한 계획의 전이 판본이 고정되고 current/pinned·권한·실패 의미가 유지된다. |
| 4 기억과 실적 연결 | `ibl_usage_db`, `hippo_tree`, `ibl_name_search`, `ibl_access`, `reusable_catalog`, `ibl_v2_learning`, 증류·수명 원장. | 정의 본문 쓰기 제거, 판본별 실적 귀속, 색인 지연·재구축, 명시 상시 노출 정책을 검증한다. |
| 5 실제 이전과 설치 검증 | 전체 후보 재고, core manifest·배포 필터·폰 번들·수리 작업공간·회원 소비자. | §9의 전환과 참조 대조 완료. 임베딩 없는 첫 설치·업데이트·개인 개정 충돌·재시작을 검증한다. |
| 6 중복 경로 제거와 교재 정렬 | 아래 제거표, 관련 가이드·프롬프트·빌드 가드·시험. | 실행 정의의 소유자가 하나이며 옛 경로를 끈 상태에서 전체 인수 기준이 통과한다. |

1~4는 테스트 환경에서 준비한 후 5에서 함께 전환한다. 중간 커밋마다 운영 상태를
신구 혼합으로 전환하지 않는다. 함수 저장은 `backend/ibl`의 기존 소유자를 확장하고,
기억·성적 저장은 `datastore`, 후보 선정은 `cognition`, 앱·HTTP는 얇은 `surface` 경로를 따른다.
새 모듈이 필요하면 층 배정과 1500줄 규칙을 지킨다. 명령 스크립트는 `import boot_paths`를 쓴다.

## 11 제거할 경로와 남길 경계

| 대상 | 최종 상태 | 제거 또는 유지의 증거 |
| --- | --- | --- |
| `definitions()`의 해마 SQL·workflow glob·installed 병합 | 공통 스냅샷 조회로 대체 | 기존 공급자를 끊어도 현재 함수 전체의 호출·describe가 같은 참조로 해소된다. |
| `register_idiom.py`의 정의 직접 쓰기·별도 자격 규칙 | 공통 등록으로 대체 후 내부 소비자 이행. 노출 선정 기능은 유지 | 기존 생산자 전부 전환, 금지된 DB 본문 수정이 없다. |
| `hippo_tree.sync_topic`의 함수 본문 갱신·삭제 | 참조 카드 편집만 유지 | 카드 편집·삭제가 함수 revision과 호출 가능성을 바꾸지 않는다. |
| 배포 정의의 런타임 직접 공급·중복 시딩 | 설치 import와 참조 기반 시딩 | 최초 설치부터 임베딩 없이 호출, 업데이트도 공통 개정 검사를 통과한다. |
| 본문 문자열 기반 성적 귀속 | 함수·판본·호출 사건 참조 | 동일 코드의 다른 함수·개정·재수집·중첩 호출을 구별한다. |
| 출처별 검색·계약 생성 | 공통 함수 참조와 컴파일 계약 | 이름 조회·검색·상시 소개가 같은 판본의 같은 계약을 보여 준다. |
| 구형 workflow ID·phrase alias 변환 | 명시 호환 참조로만 한정 후 소비자별 제거 | 저장 소비자 이행·호출 관측·외부 계약 공지 범위를 확인한다. 일정 기간 무호출만으로 삭제하지 않는다. |
| 판본 1 언어 어댑터 | 남은 판본 1 소비자 동안 유지 | 개별 의미 이전·호출자 검증 후 제거. 저장소 분리를 정당화하는 근거로 쓰지 않는다. |
| 기존 경험·주행 원문·검증 증거 | 보존 | 현재 정의의 공급자가 되지 않으며 과거 판본의 근거로 열람 가능하다. |

`workflow_engine` 전체나 `ibl_usage_db` 전체를 삭제 대상으로 삼지 않는다. 전자는 구형
프로그램 실행·스케줄 호환을, 후자는 용례·경험을 계속 소유한다. 제거 대상은 그 안의
중복된 **함수 정의 소유·해소·변경** 경로다. 종료된 계약은 `data/retired_contracts.yaml`에
등록하고 핸들러 도움말·오류·독스트링까지 정렬한다.

## 12 검증과 완료 판정

| 불변조건 | 필요한 검증 |
| --- | --- |
| 출처와 무관한 하나의 함수 | 직접 저장·경험 후보·배포 설치가 동일한 등록·개정·삭제 관문을 통과한다. 무인자·긴 함수도 같은 문법 규칙을 쓴다. |
| 이름과 소유 범위 | 같은 범위의 충돌 거절, 지역 정의 우선, 회원·주인·수리 작업공간 간 정의·계약·캐시 유출 차단. |
| 원자성과 복구 | 판본 기록 전후·카탈로그 교체 전후 중단, 두 writer의 기대 판본 충돌, 응답 유실 재시도, 다중 함수 개정 중단. |
| 개정과 호출자 | 직접·전이 호출자, 이름 변경, 삭제, 이미 깨진 무관 호출자, 앱·예약·위임의 저장 참조와 미해소 동적 참조. |
| 실행 판본 고정 | 실행 중 개정, 하위 함수 개정, pinned 의존 묶음, 재개·취소·권한 철회, 부분 결과와 불명확 효과. |
| 기억의 독립성 | 색인 비움·지연·실패·재구축에도 정확 호출 가능. 해마 문서 삭제가 함수 삭제로 이어지지 않음. |
| 실적의 정직성 | 판본별·호출별 귀속, 중복 수집 방지, 과거 미귀속 보존, 반환 성공·자료 완전성·업무 검증 분리. |
| 설치와 이전 | 같은 배포본 재설치의 멱등성, 개인 개정 보존, 구형·신형 동명 자료, 손상·충돌·참조 누락, 신규 쓰기 후 복구. |
| 제거의 실효성 | 구형 본문 공급·쓰기 경로 없이 모든 현재 소비자 동작. 과거 문법 호환은 공통 원장의 명시 정의만 소비. |

개발 중 검사는 `scripts/select_tests.py`와 [회귀 규약](REGRESSION_TESTING.md)을 따른다.
공통 함수 해소·권한·원장 이행은 허브 변경이므로 최종 단계에서 backend 전체 비system 회귀와
관련 system 묶음을 실행한다. 기존 함수·관용구·해마·회원·예약·배포·재개 시험의 불변조건을
보존하면서 정렬하며, 신규 시험은 실제 중단·충돌·이전 경계를 검증한다. 변경 관련 frontend는
`npx tsc -p tsconfig.app.json`, 어휘·문서 파생은 `build_ibl_nodes.py --check`, backend 변경은
폰 번들·층 검사까지 완료한다. 실제 장치 부작용 시험은 필요한 범위와 결과를 따로 기록한다.

성능은 함수 깊이·라이브러리 크기·검색 유무·새 작업 조합을 달리하여 컴파일 시간, 호출부터
완료까지의 시간, 회상·증류·검수까지 포함한 모델 토큰, 저장·색인 비용을 비교한다.
함수 개수 감소나 코드 줄 수 감소를 성과로 대신하지 않는다. 통합의 구조적 완료와
실제 시간·토큰 개선의 측정 결과는 별도로 보고한다.

최종 인수는 **정의의 유일한 소유, 판본이 고정된 실행, 참조 기반 기억, 증거가 보존되는 이전,
중복 경로의 제거**가 모두 성립할 때다. 통합 검색만 구현하거나 구형 해소기를 뒤에 남긴 채
‘완료’로 표시하지 않는다.
