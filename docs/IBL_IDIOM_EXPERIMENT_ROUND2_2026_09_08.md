**결론: 관용구의 이득을 다시 관측했다. 이번에는 내부 실행 기록이 최종 반환 봉투 안에 중복되는 비용을 줄였고, 조합 과정의 문자열 경로 전달 오류를 고쳤다. 관용구 이름·본문·전역 제공 방식은 그대로 유지했다.**

## 동일 비교 두 번

8과제 × 4조건 × 2반복을 수리 전 64건, 수리 후 새 모델 생성 64건으로 실행했다. 모델 설정은 `claude_code/opus`, 실제 응답은 `claude-opus-5`, effort medium. 최대 1회 수리, 섞는 seed 20260908, 동시 실행 2개. 두 실행의 32개 프롬프트 해시가 전부 같다. 수리 전후에 카탈로그와 과제도 바꾸지 않았다.

과제·오라클·격리 방식은 첫 실험과 같다. 실제 파서·함수·표 변환·파일 도구를 실행하고 웹 응답과 요약 추론만 고정했다. 최종 결과와 생성량은 전체 업무 또는 실제 보고서 품질의 지표가 아니다. `scoped` 후보는 정답에 가까운 사전 지정이며 검색 비용이 제외된다.

| 제공 조건 | 수리 전 첫 성공 | 수리 전 최종 성공 | 수리 시도 | 생성 출력 토큰 | 수리 후 첫 성공 | 수리 후 최종 성공 | 수리 시도 | 생성 출력 토큰 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 없음 | 10/16 | 12/16 | 6 | 7,801 | 10/16 | 12/16 | 6 | 6,928 |
| 현재 지도 | 14/16 | 15/16 | 2 | 2,638 | 14/16 | 16/16 | 2 | 2,636 |
| 짧은 지도 | 16/16 | 16/16 | 0 | 1,870 | 16/16 | 16/16 | 0 | 1,528 |
| 후보만 | 15/16 | 16/16 | 1 | 2,087 | 15/16 | 16/16 | 1 | 2,097 |

토큰은 주 응답의 `usage.output_tokens`이며 실패·수리를 포함한다. 보조 Haiku 사용량·입력·캐시 사용량·CLI 시간은 별도 감사 기록에 남겼다. 실제 요금이나 과제 전체 소요 시간을 뜻하지 않는다. 없음 조건의 최대 단일 출력은 수리 전 3,633토큰, 후 1,948토큰으로 길게 생각한 일부 실패의 영향이 크다. 토큰 합계의 감소율을 일반적인 비용 절감률로 취급하지 않는다.

이번에도 관용구를 제공한 각 조건의 적합한 12개 첫 시도는 모두 관용구를 호출했고, 부적합 대조 4개는 기본 액션을 조합했다. 짧은 지도는 두 실행에서 좋은 결과를 냈지만, 첫 실험에서는 일부 대조 과제가 더 나빴다. 같은 작은 과제를 반복한 결과이므로 서로 다른 새 과제로 일반화가 확인되기 전까지 전역 지도 형식을 바꾸지 않는다.

## 수리 1: fn 안에 중복된 실행 기록

기존 `diet_envelope`는 최상위 `results[]`만 요약했다. 최종 step이 함수 호출이면 `final_result` 안에 또 `results[]`가 있어 내부 원본 결과가 모델에게 그대로 돌아왔다. 코드 작성량은 줄였지만, 결과를 읽는 부담이 붙는 구조였다.

수리 범위는 모델 반환 경계다. `fn_source`, `fn`, `steps_total`, `results`를 갖춘 함수 실행 봉투의 최종 값 경로만 따라가 내부 실행 기록에도 기존 요약 규칙을 적용한다. 업무 items/rows를 임의로 순회하지 않는다. 실제 최종 데이터·함수 이름·정의·오류·traceback·경고는 유지한다. 실행 중 값과 턴 변수 원형은 바꾸지 않으며 `verbose:true`는 전체 기록을 반환한다. 순환·과도한 깊이에서는 더 요약하지 않고 원형을 둔다.

수리 전 64건의 **동일 실행 결과 73개**(수리 포함)에 수정 전후의 `diet+preview`를 적용했다. `dumps_public_result(indent=2)` 기준의 문자 수다. 턴 변수 안내 등 상위 호출 메타데이터는 제외되며 실제 모델 입력 토큰을 측정한 값은 아니다.

| 제공 조건 | 이전 반환 문자 | 수정 후 반환 문자 | 감소 |
|---|---:|---:|---:|
| 없음 | 95,293 | 95,293 | 0% |
| 현재 지도 | 120,035 | 95,827 | 20.2% |
| 짧은 지도 | 104,164 | 79,956 | 23.2% |
| 후보만 | 110,684 | 86,476 | 21.9% |

예를 들어 현재 지도의 최신 파일 읽기는 10,604→6,800자, 각각 읽기·요약은 14,515→9,162자였다. 단순 중복 제거는 3,817→3,566자로 이득이 작았다. 73개 모두 실행 기록을 제외한 반환 데이터와 봉투 메타데이터의 동등성을 확인했다. 추가 테스트로 중첩 실패의 오류·정의·traceback, 일반 업무 데이터, 복사본 처리, 멱등성, verbose 원형을 검증했다.

이 실험 러너는 모델에 결과 전문 대신 판정/오류를 피드백하므로 **위 반환량 감소가 새 모델 생성 토큰을 얼마나 줄이는지는 실험하지 않았다.** 반환량 비교는 저장된 동일 결과를 이용한 별도 비교다.

## 수리 2: 문자열 식 할당에 새는 `_v0`

실제 실패 코드:

```ibl
$최신 = [self:file_find]{path: "reports", pattern: "*.md"} >> [table:sort]{by: "mtime", desc: true} >> [table:take]{n: 1}
$경로 = "${최신.items.0.path}"
$본문 = [self:read]{path: "$경로", start_line: 1, end_line: 220}
$본문
```

식 평가기는 `$참조`를 내부 변수 `_v0`로 바꿔 값을 바인딩했는데, 따옴표 안에서도 같은 처리를 했다. 그 결과 경로 대신 문자열 `_v0`가 저장되어 다음 파일 읽기가 실패했다.

따옴표 안에서는 실제 값을 텍스트로 보간하고, 따옴표 밖은 종전의 값 바인딩을 유지하도록 고쳤다. 작은따옴표·큰따옴표·백슬래시·제어 문자를 이스케이프하며, `007` 같은 문자열은 숫자로 바꾸지 않는다. 없는 참조는 계속 오류다. 새 함수나 어휘는 추가하지 않았다.

수리 전의 첫 생성 코드 64개를 현재 엔진에 재생했다. 현재 지도 조건에서 실패했던 전체 파일 읽기 2건이 코드 변경 없이 성공했다(첫 성공 14→16). 나머지 조건은 없음 10→10, 짧은 지도 16→16, 후보만 15→15로 변화가 없었다. 재생과 새 모델 생성 성적은 다르다. 새 생성에서는 현재 지도의 첫 성공 수가 14로 같고 수리도 두 번 필요했으므로, 재작성 부담까지 더 줄었다고 주장하지 않는다.

## 가치 판단과 검증

이번에 적용한 개선 방법은 **이미 검증된 행동 단위의 출력 중복을 줄이고, 그 앞뒤의 값 연결을 안정화하는 것**이다. 새로운 이름을 늘리거나 특정 관용구를 강제로 선택하게 하지 않았다. 관용구 없이 조합한 코드에도 문자열 전달 수리가 똑같이 적용된다. 같은 품질에서 판단과 재작성을 줄인다는 기준은 유지하되, 반환량을 별도 지표로 추가했다.

회귀검사 `pytest backend/ -o addopts='' -q`: 2,158개 통과, 2개 건너뜀. 새 검사들은 수정 전 중첩 봉투 4건·문자열 참조 9건 실패를 확인한 뒤 수정 후 통과했다. Android 몸 번들 재생성 및 어휘 빌드 신선도도 검사했다.
