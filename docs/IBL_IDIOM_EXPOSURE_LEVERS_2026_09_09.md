## 집행한 지렛대

[직전 실험](IBL_IDIOM_EXPOSURE_RESULT_2026_09_09.md)의 갈림 — 자족형 관용구 둘(원장에누적·최신범위읽기)은 6/6, 앞 통화를 파이프로 받는 위치마다읽기는 1/6 — 에서 네 가지를 집행했다. 문법·연산자·코어 노드는 바꾸지 않았다.

1. **자족형 서명**(위치마다읽기): `$위치` 명시 슬롯을 받는 몸으로 개정(`{위치, 개수, 줄수}`). `register_idiom.py --update --resign` 신설 — 서명이 달라지는 개정은 명시 플래그로만, 옛 서명으로 부르는 코퍼스 용례를 이름으로 짚어 준다. 옛 본문·실적은 `ibl_idiom_revisions` 보존, 옛 서명 용례 #4574 는 새 서명으로 고쳤다.
2. **'언제'는 입력 모양으로**: "grep으로 찾은 위치 목록" → "파일·줄번호 열이 있는 위치 목록(grep 결과·JSON 파일·filter 결과)". 입력 설명도 같은 방향.
3. **생산자가 다른 조합 용례**: 선정집 `examples[]`(선정집 검증기가 대표 용례와 같은 관문으로 검사) — 관용구마다 2건, JSON 읽기·filter/sort·sense:search 등 생산자를 달리해 해마 코퍼스에 심었다. 손 조합 변형 행은 `fn_recognizer.variant_of` 로 전수 스윕했더니 관용구 자신의 정의 3행 외 0건 — 눈으로 골랐던 후보(4361·4427)는 관문이 변형으로 보지 않아 두었다.
4. **어휘 목록 병기**: 관용구는 어휘이므로 부록 `<ibl_idioms>` 만이 아니라 대체하는 **잎 액션 줄 바로 아래** `↳ 관용구 [fn:이름]{슬롯…} → 반환 :: 언제` 한 줄로 선다. 어느 낱말 옆인지는 몸의 마지막 잎 액션에서 파생(`_anchor_action`, 코드에 이름 없음). `build_environment(expose_idioms=False)` 가 병기·부록을 함께 끈다.

노출 조건의 추가 입력은 2,324자(직전 1,553자). 지렛대 3(코퍼스)은 새 세션 CLI 실험에는 보이지 않는다 — 이번 이득은 1·2·4 와 함수 반환 수리의 묶음이다.

## 어떻게 읽는가

- **선택 문제는 서명·자리의 문제였다.** 위치마다읽기는 몸을 바꾸지 않고 앞 통화를 명시 슬롯으로 받게 하고, 잎 액션 옆에 세우고, 입력 모양으로 '언제'를 쓰자 1/6 → 6/6. 세 지렛대의 몫을 이 실험으로 가를 수는 없다(묶음 집행).
- **절약은 타이핑이 아니라 판단이다.** 비사고 출력은 19.8K → 6.6K 이지만 사고는 183K → 36K 다. 검증된 계약을 이름으로 부르면 모델이 계약을 다시 조립하는 사고가 빠진다. 벽시계는 출력 토큰을 따라간다.
- **입력 세금은 상쇄됐다.** 노출 프롬프트가 2.3K자 길지만 수리가 사라져 전 시도 입력 합이 오히려 31% 적다. 첫 시도만 보면 입력은 +2,029토큰/회.
- 한계는 직전과 같다: 과제 틀 9개·모델 하나·새 세션 단일 프로그램·수리 1회. 실제 업무의 적용 빈도(운영 원장 09-08 이후 실사용 2,409액션에 fn 호출 0·우회 0)가 상시 노출의 경제성을 최종 결정한다. 지렛대 3(회상 채널)의 효과는 실사용 관찰 대상.

## 실패 전수 분류와 수리 셋

두 조건의 실패 시도 29건(비노출 28·노출 1)을 코드·오류·산출물로 전부 분류했다. 모델 실수(반환 대신 파일 저장, 존재하지 않는 rename 별칭 지도, 격리 실험이 막은 `self:mkdir`)가 대부분이고, 엔진 쪽 결함이 셋 나와 같은 날 수리했다(`backend/test_idiom_exposure_v3_repairs_2026_09_09.py`).

1. **옵셔널 결측이 "None" 글자로 찍혔다.** `$ln = "${it.줄번호?}${it.line?}${it.line_no?}"` 가 "4NoneNone" 이 돼 뒤 산술 `$ln + 4` 가 TypeError 로 죽었다(direct_context_2, 위치마다읽기가 없는 조건의 3건 전부 실패). 규약은 "결측은 빈 값"이다 — 식 할당의 따옴표 안 보간이 None 을 "" 로 찍는다.
2. **읽기 산문이 JSON 으로 오인됐다.** `[self:read]` 결과는 `[줄 11-22 / 전체 80줄]` 머리로 시작해 `[` 로 열리므로 JSON 파싱을 시도하다 실패했고, 09-04 의 산문 규칙(`.text`/`.message` 는 그 산문)이 한 번도 돌지 않았다. `${doc.text?}` 가 빈 값이 되고 `${doc.content}` 는 정직 오류로 죽었다. 파싱이 안 되면 산문이다.
3. **`content` 도 산문의 이름이다.** 모델이 `${본문.content}` 를 7회 짚었다 — `[self:write]{content}` 가 받는 이름을 읽기 산문에 물으면 같은 것(같은 이름=같은 것, 09-04 규칙의 연장). 다른 이름(`.body`)은 종전대로 정직 오류다.

수리 뒤 확인: 격리 실행기에서 ①이 `{ln:"4", end:8}`, ②③이 세 이름 모두 같은 본문, `[self:write]{content:"${doc.content}"}` 가 본문을 저장한다. 회귀 3,239 통과. 비노출 조건의 점수는 소급 재계산하지 않았다(실험 뒤 수리).

수리하지 않고 남긴 것(언어 한계, 사용자 판정 자리): 값 구성 리터럴을 파이프 머리로 쓰는 `[{…}] >> [self:write]`(현재는 `$x = [{…}]` 로 할당해야 한다) · 폴백 `??` 의 괄호 가지에 `$변수 >>` 머리(병렬 분기는 09-01 개정으로 열렸고 폴백 자리는 미개방) · `[table:rename]` 이 없는 열의 별칭 지도까지 충돌로 세는 순서(없는 이름은 어차피 명시 오류라 결과는 같다).
