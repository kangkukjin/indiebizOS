# 상시 관용구 노출 실험 — 생성 전 고정 계획

2026-09-09. 현재 언어·어휘·관용구 본문·운영 설정을 변경하지 않는다. 질문은 상시 관용구를 소개하면 모델이 자연스럽게 선택하는지, 그리고 정확한 결과를 얻는 데 필요한 시간·토큰이 줄어드는지다. 저장 후 회상하는 관용구는 이번 대상에서 제외한다.

## 기존 실험에서 확대 해석할 수 없었던 부분

- 과제 대부분이 관용구의 직접적인 기능과 범위 변형이었다. 큰 프로그램 안에서 적용 구간을 발견하는 일은 약하게 다뤘다.
- 허용 액션에서 `self:ledger` 등 실제 업무의 대안을 제외했다.
- 8개 과제에서 반복 2회였고, 주된 보고 지표인 생성 출력 절감은 소개 입력·보조 모델·전체 지연의 절감과 같지 않다.
- 성공 기준에 정확한 읽기 호출 횟수가 포함된 과제가 있었다. 호출을 더 해도 동일한 사용자 요구를 충족할 수 있는 경우 비용으로 평가해야 할 것을 실패로 처리할 수 있었다.
- 현재 실험 준비 중 `최신범위읽기 >> self:write`가 본문 대신 실행 봉투를 저장하는 것을 재현했다. 이전의 최종 반환값을 풀어서 보는 검사만으로는 이 조합 차이가 드러나지 않는다. 기존 실험의 모든 수치가 무효라는 주장은 아니다.

## 조건

- hidden: 상시 소개 블록 없음.
- exposed: 현재 `_idioms_block(None)`의 실제 결과를 그대로 제공. 현재 `위치마다읽기`의 입력·예제가 빠진 상태도 유지한다.
- **양쪽 실행기의 등록 함수는 동일한 세 개다.** 노출 유무만 바꾼다. 몸은 `curated.json`이 아니라 운영 DB를 읽기 전용으로 열어 스냅샷한다.
- 기본 프롬프트와 IBL 문법·전체 어휘 카탈로그는 동일하다. 실행 가능한 격리 액션은 파일 읽기/검색/목록/수정/쓰기, JSON 원장, 결정론적 table 변환이다. 외부 서비스·셸·AI 호출·운영 기억 조회는 양쪽 모두 없다.
- 현재 실행 모델의 설정된 이름(`claude_code/opus`), effort high를 고정하고 실제 응답 모델명을 기록한다. 새 CLI 세션으로 생성하며 도구 사용을 끈다. 전체 앱의 의식·회상·다중 도구 왕복 실험은 아니다.

## 과제와 순서

9개 과제 × 2조건 × 3반복 = **54회**. 직접 과제 3개, 앞뒤 처리와 결합한 과제 3개, 비슷하지만 해당 관용구를 쓰면 요구와 어긋나는 대조 과제 3개다. 각 과제의 이름·분류·해당 관용구는 분석용이며 모델에게 보여주지 않는다. 과제 본문에 관용구 이름이나 정답 코드를 넣지 않는다.

각 짝은 같은 seed의 파일 데이터를 사용한다. 파일 내용은 seed에 따라 바뀌고 프롬프트에는 포함하지 않는다. 과제/반복의 순서를 섞은 뒤 짝 안의 노출 순서를 교차한다. 모델 프로세스는 동시에 하나만 실행한다. 프롬프트·본문·과제·러너의 해시와 전체 순서는 모델 호출 전에 manifest로 고정한다.

첫 실패 때 실행 결과를 주고 **한 번** 수정할 수 있다. 재실행은 같은 초기 파일에서 시작한다. 오류·시간 초과·미사용·미완료도 결과에 남긴다. 생성 도중 교재·본문·엔진·과제를 고쳐 성적을 섞지 않는다.

## 성공 판정과 비용

- 실제 엔진에서 실행하고 파일 내용·행·순서·중복 정책·입력 보존·오류 위치를 검사한다. 함수 호출 여부는 성공 조건이 아니다.
- 각 과제는 이름 호출 기준 코드와 직접 조합 기준 코드로 미리 검증한다. 의미가 틀린 코드가 탈락하는 음성 대조도 확인한다. 기존 scalar 함수의 봉투 문제는 원문 관측에 남기고, `.final_result`를 명시해 같은 과제를 수행할 수 있음도 확인한다. 이 우회 코드는 모델에게 알려주지 않는다.
- 함수의 **작성 시도**와 실제 호출을 따로 기록한다. 전체 파싱 실패 때문에 호출까지 가지 못한 경우를 미선택으로 숨기지 않는다.
- 첫 성공·최종 성공·수리 횟수, 모델 프로세스 벽시계·API 시간·실행 시간, 주/보조 모델의 출력, 신규/캐시 생성/캐시 읽기 입력을 별도 기록한다. 기록이 없는 값은 0으로 보지 않는다.
- 주 비교는 배정된 조건 전체의 **exposed−hidden 짝 비교**다. 관용구를 쓴 표본만 골라 안 쓴 표본과 비교하지 않는다. 직접/복합/부적합 과제를 분리한다.
- 과제 단위 재표집 구간을 보조로 제공하되 9개 과제에서 보편적인 운영 효과나 인지 원인을 확정하지 않는다. 현재의 선택·비용 효과와 미래의 완벽한 관용구 개념은 구분한다.

## 본 실험 도중 사전 고정한 별도 진단

현재 `위치마다읽기`의 언제 설명은 “grep으로 찾은 위치 목록”이다. 본 과제의 저장된 JSON 위치 목록과 구조적으로는 호환되지만, 소개한 사용 맥락과의 일치는 별도 확인이 필요하다. 이 문제를 관찰한 뒤 설계했으므로 **탐색적 진단**이며 원인을 확증하는 무작위 비교가 아니다.

본 54회를 바꾸지 않고, 완료 후 같은 세 `direct_context` seed에서 노출 조건만 새 세션으로 세 번 생성한다. **실제로 notes/*.txt를 grep한 뒤 파일·줄번호 순 앞 세 위치의 5줄 본문을 읽는 과제**다. 같은 notes 파일을 쓰고, 내부 오라클의 세 목표 위치만 실제 grep 순서에 맞춘다. 첫 선택만 보고 수리는 하지 않는다. 소개문 자체를 개선하거나 이름을 과제에 지정하지 않는다. 원본은 `outputs/idiom_exposure_2026_09_09_grep_probe/`이다. 이 결과는 54회 합계·비용 비교에 섞지 않고, 소개한 맥락에서 선택이 가능한지를 확인하는 보조 자료로만 보고한다.

진단 모델 호출 전 계획 수정: 처음에는 저장된 JSON의 출처만 앞선 grep이라고 명시하려 했으나, 소개한 사용 상황과 직접 맞추려면 실제 grep→본문 읽기가 더 적절해 위 과제로 고정했다. 변경 사유·이전 과제·시각을 보조 manifest의 `pre_generation_amendments`에 보존한다. 본 54회의 과제·순서·설정은 수정하지 않았다.

## 실행·판정의 추가 감사

원래 점수는 오류 없는 실행과 정해 둔 결과 비교를 모두 요구한다. 실행 관문의 별칭·스키마·기본값·공개 봉투 처리를 그대로 둔 별도 격리 경로로 완성 코드를 재생해 판정 차이를 검사한다. 생성·수리에는 이 감사 결과를 전달하지 않는다.

별도의 **요구 충족 감사**도 병기한다. 불필요한 부수 단계가 실패했어도 요구한 파일·본문·입력 보존이 맞는지는 따로 확인한다. 본문 반환의 동등한 items 표현과 한국어 `오류` 필드도 받아들인다. 내용은 seed로 생성한 실제 줄·행과 대조하므로, 빈 본문·다른 문서·누락 행은 계속 탈락한다. 이는 초기 오라클의 표현 제약과 실행 오류 조건을 검토하는 사후 분석이다. 실제 수리 정책·시도 횟수·측정 시간·토큰을 소급해서 바꾸지 않으며, 초기 점수와 구분한다.
