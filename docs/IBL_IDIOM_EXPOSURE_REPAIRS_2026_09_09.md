# 관용구 노출 실험에서 확인한 결함 수리

2026-09-09. 사용자 지시 “원인을 아는 건 수리해”에 따라 세 가지를 수리했다. 문법·어휘·운영 DB의 관용구 본문·서명·상시 노출 대상은 유지했다. `위치마다읽기`의 낮은 선택률 자체는 원인을 확정하지 못했으므로 해결됐다고 판정하지 않는다.

## 함수의 본문이 하류로 전달되도록 수리

수리 전 `[fn:최신범위읽기]{…} >> [self:write]{…}`는 305자의 본문 대신 11,066자의 실행 기록을 저장했다. 함수의 scalar 반환값이 호출 봉투 안에 갇혀 있었기 때문이다.

실행기가 함수 결과에 내부 표식을 붙이고, 공통 값 추출기가 반환값을 읽도록 했다. 특정 관용구 이름이나 파일 도구에 예외를 넣지 않았다. 같은 프로그램의 정의·등록 관용구·저장 워크플로를 fn으로 부르는 경로가 같은 처리를 쓴다. 반환값은 기존 `final_result`에만 보존하여 별도 `value` 필드에 본문을 복제하지 않는다.

- 파이프 연결, 변수에 담은 뒤 파이프 연결, `content:"$변수"`, 본문의 `.text` 접근, 중첩 함수가 올바른 본문을 전달한다.
- 기존 명시적 `.final_result` 접근과 `results[]`의 함수 실행 기록은 보존한다.
- 빈 본문·빈 items·목록·효과 반환을 그대로 전달한다. 실패 봉투와 트레이스백은 벗기지 않는다. 일반 사용자 데이터에 있는 `fn`·`final_result` 이름만으로는 실행 봉투라고 간주하지 않는다.
- 직접 `[self:workflow]{op:"run"}`의 기존 합성 규약이나 문법을 변경한 작업은 아니다. fn 호출 경계의 기존 반환 약속을 복구했다.

실제 별칭·스키마·핸들러 관문을 보존한 격리 실행에서 **이름 호출, 정확한 등록 몸 전개, 명시적 반환값 추출** 세 가지가 모두 같은 305자를 저장했다. 실행 중인 백엔드의 `/ibl/execute`에서도 임시 파일에 읽기 함수를 정의하고 쓰기에 연결해 원문 저장을 확인했다. 라이브 검증은 절대 경로를 사용했으며 운영 업무 파일은 사용하지 않았다.

## 현재 몸에 맞는 교재 복원

`위치마다읽기`의 운영 DB 몸은 each 블록 문법인데 `data/idioms/curated.json`은 이전 do 문자열 문법이었다. 소개기는 몸이 다른 교재를 제외하므로 입력 설명·조합 예제가 빠졌다.

교재에 보관된 몸을 **현재 운영 DB 몸과 동일하게** 맞췄다. 운영 몸을 옛 문법으로 되돌리지 않았고, 교재 일치 검사도 완화하지 않았다. 실제 소개 생성에서 기존 입력 설명과 예제가 다시 표시됨을 확인했다. 이것이 모델의 선택률을 높였다는 새 측정은 하지 않았다.

## 실험의 불필요한 수리 방지

실험 실행기가 요구 결과 충족 `quality_ok`와 무오류 실행 `runtime_ok`를 별도로 기록한다. 요구한 결과와 입력 보존이 맞으면 부수 오류만으로 다시 생성시키지 않는다. 원형 오류는 기록에 남는다.

본문 반환은 산문과 동등한 items/value·본문 필드 표현을 허용한다. 위치별 실패의 한국어 `오류` 필드도 인식한다. 본문의 실제 줄·순서는 그대로 비교하고 추가 줄·다른 문서·실행 기록 속 정답만 있는 경우는 탈락시킨다. 실제 한국어 오류 사례 재생과, 부수 오류를 남긴 올바른 결과에서 모델 수리 호출이 추가되지 않는 검사를 포함했다.

새 실행 기본 폴더·manifest는 v2다. 기존 54회와 보조 3회의 프롬프트·생성 코드·시도·점수는 덮어쓰지 않았다. 당시 소스도 기존 증거의 `frozen_sources.json`에 남겼다. 이번에는 새 모델 생성 실험을 돌리지 않았다.
