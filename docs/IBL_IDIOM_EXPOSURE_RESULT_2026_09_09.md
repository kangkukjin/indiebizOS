## 1. 실제로 선택했는가

적용 가능한 과제에서 **첫 응답에 작성한 이름 호출**을 세었다. 직접 과제 3회와 복합 과제 3회가 관용구 하나의 분모 6이다.

| 노출 관용구 | 첫 응답의 호출 작성 | 첫 실행에서 실제 호출 | 수리까지 포함해 한 번이라도 호출 작성 |
|---|---:|---:|---:|
| 원장에누적 | **6/6** | 5/6 | 6/6 |
| 최신범위읽기 | **6/6** | 6/6 | 6/6 |
| 위치마다읽기 | **1/6** | 1/6 | 3/6 |

`원장에누적` 한 건은 모델 응답에 호출을 작성했으나, 바깥 JSON의 줄바꿈 이스케이프 오류 때문에 IBL 실행까지 가지 못했다. 이를 “관용구를 떠올리지 못함”으로 세지 않았다. 생성 코드에서 관용구 몸을 새로 정의한 사례는 없었다. 비노출 조건에서는 이름 호출이 없었다.

부적합 대조 과제에서는 노출 조건 9회 모두 수리까지 포함해 관용구를 호출하지 않았다. 이 표본에서는 단순히 소개의 지시를 따라 아무 데나 사용하는 양상이 아니었다.

**따라서 “AI는 직접 조합하는 편이 쉬워서 관용구를 전반적으로 쓰지 않는다”는 설명은 이 세 관용구 모두에 적용되지 않는다.** `위치마다읽기`에는 선택 문제가 남지만, 다른 두 개에는 같은 설명이 맞지 않는다.

`위치마다읽기`의 세 번의 실제 사용은 모두 요구한 위치별 본문을 만들었다. 한 번은 별도의 불필요한 디렉터리 생성 오류 때문에 수리에 들어갔고, 수리에서 직접 조합으로 바꾸면서 본문이 틀려졌다. 사용 횟수가 적다는 사실과, 사용한 몸의 결과가 쓸모없다는 주장을 구분해야 한다.

## 3. 가장 명확하게 드러난 문제: 접은 표현의 결과가 달라진다

`최신범위읽기`는 선택 자체에는 문제가 없었다. 단독 본문 반환 과제는 노출에서 첫 응답 3/3이 맞았다. 그러나 본문을 파일에 저장하는 복합 과제는 노출·비노출 모두 0/3이었다.

다음 자연스러운 조합을 현재 엔진에서 재현했다.

```ibl
[fn:최신범위읽기]{폴더:"drafts",패턴:"*.md",시작줄:11,줄수:12}
>> [self:write]{path:"outputs/excerpt.txt"}
```

실행기는 성공이라고 응답하지만, 저장 파일에는 원하는 본문 대신 **11,066자의 함수 실행 기록**이 들어갔다. 같은 등록 관용구 몸을 그대로 펼치고 `$return`을 쓰기에 전달하면 **305자의 올바른 본문**이 저장됐다. 이름 호출 후 아래처럼 내부 반환 필드를 명시해도 같은 305자가 저장됐다.

```ibl
$part = [fn:최신범위읽기]{폴더:"drafts",패턴:"*.md",시작줄:11,줄수:12}
[self:write]{path:"outputs/excerpt.txt",content:$part.final_result}
```

원인은 [함수 반환 처리](/Users/kangkukjin/Desktop/AI/indiebizOS/backend/ibl/ibl_control_blocks.py:348)가 `final_result`의 items/목록은 바깥에 전달하지만 scalar는 같은 방식으로 전달하지 않는 데 있다. 공통 [워크플로우 반환 처리](/Users/kangkukjin/Desktop/AI/indiebizOS/backend/ibl/workflow_engine.py:1380)에도 items 승격 중심의 기존 규약이 남아 있다. 현재 소개는 이 관용구의 반환을 본문 문자열로 설명한다.

세 비교 모두 실제 별칭·스키마·공개 결과 처리를 보존한 별도 실행 경로에서 확인했다. 본문을 편리하게 고친 뒤 비교한 것이 아니라 **등록된 원문에 슬롯 값만 대입해서** 비교했다. [코드와 실제 저장 결과](/Users/kangkukjin/Desktop/AI/indiebizOS/docs/experiments/idiom_exposure_2026_09_09/composition_contract_audit.json)를 보존했다.

이는 사용률과 독립적인 문제다. **이름으로 접은 표현이 펼친 표현과 같은 값을 다음 문장에 전달해야, 모델이 접힌 표현을 안심하고 조합할 수 있다.** 현재는 모델이 실행 기록의 내부 필드를 알아야 한다. 사용자가 말한 “복잡함을 언어 구조가 담당한다”는 기준에서 가장 먼저 검토할 지점이다. 이번 실험에서는 이를 고치지 않았다.

## 4. 위치마다읽기는 왜 선택되지 않았는가

이번 증거로 원인을 확정할 수는 없다. 확인한 사실은 세 가지다.

1. 첫 선택은 1/6이지만, 수리 중 사용까지 합친 세 번의 몸은 필요한 본문을 만들었다. 선택되지 않는 이유를 몸의 효용 부재로 바로 설명할 수 없다.
2. 현재 이 관용구의 소개에는 다른 두 개와 달리 입력 설명과 조합 예제가 빠져 있다. DB 몸의 블록 문법과 `curated.json`의 옛 몸이 달라 [교재 일치 검사](/Users/kangkukjin/Desktop/AI/indiebizOS/backend/ibl/ibl_access.py:647)가 교재를 제외한다. **누락은 확인했지만, 복원하면 선택률이 오른다는 인과관계는 실험하지 않았다.**
3. 본 과제는 JSON 위치 목록을 사용했다. 소개의 “grep으로 찾은 위치”와 맞추기 위해 실제 grep → 앞 세 위치 → 각 5줄 읽기를 별도로 세 번 생성시켰다. **선택 0/3, 정답 0/3**이었다. 같은 소개 맥락을 제공하는 것만으로는 이 소표본에서 선택이 회복되지 않았다.

보조 진단은 본 결과를 본 뒤 설계한 탐색적 확인이다. 무작위 대조가 없고 수리도 하지 않았으므로 본 실험에 합치지 않는다. [진단 계획·코드·결과](/Users/kangkukjin/Desktop/AI/indiebizOS/docs/experiments/idiom_exposure_2026_09_09/grep_probe.json)에 모두 남겼다.

따라서 “소개가 틀렸으니 소개를 고치자”는 처방을 다시 정답처럼 제시할 근거는 없다. 입력 자료에서 적용 구간을 알아보는 부담, 입력·출력 계약의 이해, 기존 each 조합의 생성 습관 등은 남아 있는 가설이다. 모델이 실제로 무엇 때문에 그 선택을 했는지는 사용 기록만으로 구별되지 않는다.

## 5. 이전 실험이 석연치 않았던 이유와 이번 판정의 문제

단독 사용 과제만 주면 이름을 부르는 능력은 보여도, 더 큰 작업 속에서 찾아 쓰고 하류에 연결하는 능력은 놓친다. 특정 도구 대안을 빼거나 정확한 읽기 횟수를 정답 조건으로 넣으면 유효한 다른 풀이가 탈락한다. 출력 절약만 보면 소개 입력을 지불하고도 이득인지 알 수 없다. 최종 반환값만 풀어 비교하면 위의 파일 저장 실패를 놓친다. 이것들은 실험 설계상 구체적인 편향이며, 과거 측정값 전부가 무효라는 뜻은 아니다.

**이번 초기 오라클에도 같은 계열의 문제가 일부 남아 있었다.** 오류 없는 실행과 제한된 출력 표현을 함께 요구해 실제 요구 결과가 맞는 11개 시도를 실패로 처리했다. 그중 첫 응답 8개가 불필요한 수리를 받았다. 7개는 부수 단계 오류, 1개는 동등한 본문 표현 문제였다. 그 결과 노출의 맞던 첫 결과 2개가 수리 후 틀려졌다.

예를 들어 `embedded_context_1_exposed`는 관용구가 본문을 올바르게 저장했는데 별도의 디렉터리 생성이 실패했다. 수리가 관용구 호출을 직접 each 조합으로 바꾸면서 본문을 잃었다. `counter_latest_2_exposed`는 올바른 본문을 items 안에 반환했지만 scalar만 받는 초기 비교에서 탈락했다. 또 다른 수리 결과에서는 한국어 `오류` 필드를 초기 비교가 인식하지 못했다.

이를 감추기 위해 기존 점수를 덮어쓰지 않고, **요구 결과 충족**과 **초기 무오류·형식 판정**을 따로 보존했다.

| 판정 기준 | 비노출 첫 응답 | 노출 첫 응답 | 비노출 마지막 | 노출 마지막 |
|---|---:|---:|---:|---:|
| 생성 전 고정한 초기 오라클 | 6/27 | 11/27 | 11/27 | 18/27 |
| 사후 요구 결과 감사 | 9/27 | 16/27 | 12/27 | 20/27 |

사후 감사는 실제 본문·행·순서·입력 보존을 여전히 검사한다. 동등한 결과 표현과 부수 오류를 구분하는 조건만 보완했고, 빈 본문·다른 문서·잘못된 행을 탈락시키는 대조도 확인했다. 모든 실행 가능한 코드 87개를 스키마 관문을 보존해 재생했으며, 초기 실행 판정의 차이는 0건이었다. 실행할 코드가 없는 4개도 실패 시도로 남겼다. 즉, 판정 교정은 격리 실행기의 스키마 생략 때문에 발생한 차이가 아니다.

## 어디까지 판단할 수 있는가

- **노출 묶음의 효과다.** 현재 소개에는 짧은 이름뿐 아니라 사용 권고·계약·예제가 포함된다. 같은 정보를 펼친 코드로 제공하는 조건이 없으므로, 이 이득 전체가 이름 압축 자체에서 왔다고 분리해 말할 수 없다.
- **실제 업무 빈도가 아니다.** 관용구를 쓸 기회가 있는 과제를 2/3 넣었다. 이것으로 일상에서 상시 노출의 입력 비용을 회수하는지 결정할 수 없다. 원장에누적의 적용 과제에서는 효용이 관찰됐지만, 상시 노출 유지의 경제성은 그 일의 실제 빈도에도 달렸다.
- **모델 하나, 과제 틀 아홉 개다.** 54회가 서로 독립적인 업무 54종은 아니다. 과제 틀을 단위로 5,000회 재표집한 첫 시간 차이의 95% 구간은 −51.97~+0.17초, 첫 출력 차이는 −3,772~+146토큰이다. 모두 0을 포함하므로 일반적인 절약을 확정하지 않는다.
- **전체 앱의 속도가 아니다.** 이 실험은 새 세션·고정 effort·단일 프로그램 생성과 한 번의 수리다. 운영의 회상·도구 왕복·재개 세션·사용자 상호작용을 측정하지 않았다. 수리 피드백도 결과의 앞 6,500자로 제한했다.
- **빠른 실패는 능력 향상이 아니다.** 특히 최신범위읽기의 복합 실패를 성공적인 효율 개선으로 세면 안 된다. 여기서는 조건 전체의 비용과 요구 결과 충족을 나란히 제시했고, 관용구를 쓴 성공 사례만 골라 비용을 비교하지 않았다.

## 우선순위에 대한 판단

**첫째, 관용구 호출과 본문 전개의 결과가 하류에서 같아지는지를 먼저 보장해야 한다.** 이미 이름을 잘 선택하는 최신범위읽기에서도 이 경계가 실패한다. 선택을 더 독려해도 이 실패는 해결되지 않는다. 문법·어휘 확대에 앞서 현재 반환 약속과 구현을 대조할 문제다.

**둘째, 세 관용구를 하나의 성패로 묶지 않는다.** 원장에누적은 적용 과제에서 첫 요구 충족이 비노출 3/6 → 노출 5/6, 마지막은 4/6 → 6/6이었고 작성 시간도 줄었다. 최신범위읽기는 선택보다 조합 문제다. 위치마다읽기는 몸의 결과와 초기 선택이 갈린다. 이 관찰은 전체 폐기를 지지하지도, 세 개를 무조건 같은 노출 지위에 둘 근거가 되지도 않는다.

**셋째, 이후 판정에서는 ‘선택·요구 충족·총 비용’을 함께 기록한다.** 호출 증가만으로 개선이라 하지 않고, 소개·사고·수리를 포함한 비용과 실제 결과를 본다. 맞던 결과를 불필요한 수리가 망치는지도 포함한다. 일상 상시 노출의 최종 판단에는 실제 업무 빈도에 맞춘 비교가 추가로 필요하다.

현재 가장 강한 결론은 “AI에게 관용구는 필요 없다”가 아니다. **사용할 가치가 있는 축약은 관찰됐고, 그 가치를 막는 지점 중 하나는 언어의 실행 경계에서 직접 재현됐다.** 위치마다읽기의 낮은 선택률을 설명하는 원인은 아직 미결이다.
