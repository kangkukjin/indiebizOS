### 뿌리 한 문장
증류기(`backend/cognition/ibl_usage_rag.py` `_build_distill_prompt` 규칙 3)와 접지 관문
(`_composition_grounded`)이 **"관용구 = 합성 연산자(`>>`·`&`)가 든 문장 하나"** 로 정의한다.
그 정의 아래서는 *별개 호출로 이어진 성공 순서*(찾기→읽기→고치기→검사)는 관용구가 될 수 없다:
`>>` 로 봉합하면 거짓 파이프라 관문이 막고(옳다 — `>>` 는 데이터 흐름이다), `;` 도
`_FLOW_OP_RE` 에 묶여 "실행된 한 호출 안에 있었어야" 통과한다. 그래서 프로그램급 주행은
대표 문장 없음(스킵) 아니면 녹취록(주행 절) 둘 중 하나로 떨어진다. **순서는 흐름이 아니다** —
`;` 의 접지 규칙이 `>>` 와 같은 것이 관용구 층을 막고 있는 자리다.

## 1. 관용구란 무엇인가 (이 문서의 정의)

| 층 | 단위 | 자리표 | 실행 방식 | 지금 있나 |
|---|---|---|---|---|
| 낱말(용례) | 액션 1개(또는 한 호출의 합성문) | 값 그대로 | 모델이 골라 고쳐 씀 | ✅ 해마 코퍼스 |
| **관용구** | **독립 문장 3~8개, 순서 있음** | **`${슬롯}`** | **모델이 슬롯을 채우고 필요하면 문장을 빼거나 더해 씀** | ❌ |
| 워크플로 | 문장 n개, `params` | `${param}` | 그대로 실행(`op:"run"`) | ✅ `[self:workflow]` |
| 가이드 | 산문 + 골격 예시 | 자리표 | 읽고 새로 조립 | ✅ `data/guides/` |

관용구는 **얼린 프로그램이 아니다.** 워크플로는 그대로 돌리는 것이고, 관용구는 읽고 고쳐 쓰는
것이다(주행 절의 "용례다" 규약과 같다). 다른 점은 단위와 자리표: 사건 하나가 아니라 되풀이될
**모양**이고, 구체값은 `${슬롯}` 으로 비어 있다. 문법 요소는 이미 있다 — 독립 문장 연산자 `;`,
변수 `${이름}`. 새 문법이 필요 없다.

효과: 57문장 프로그램이 관용구 5개로 접히면 모델의 작업 기억이 그 5개를 한눈에 들고 있을 수
있고, 에러의 자리도 문장 사이가 아니라 관용구 사이로 좁혀진다. IBL 이 파이썬 위의 층이듯
관용구는 IBL 위의 층이다 — 다음 층의 낱말.

## 2. 설계 — 네 자리

### 2-a. 단위와 저장
- 코퍼스 `ibl_examples` 에 `category='phrase'`(기존 컬럼 재사용, 기본 `'single'`). 코드 형태는
  `;` 로 이은 독립 문장 열 — 문장 안 `${슬롯}` 은 IBL 변수 표기 그대로. `topic` 필수.
- 정본은 가지 문서 `data/hippocampus_tree/<가지>/memory.md` 의 **`## 관용구` 절**(주행 절과
  같은 규약: 사람이 고친 줄은 구문 관문(`test_hippo_syntax_gate`)을 거쳐 DB 색인 반영). 한 관용구 =
  `### 의도 한 줄 · 문장 n · 슬롯 {…}` 머리 + 번호 목록 + `근거: 주행 날짜` 한 줄.
- `## 주행` 절은 그대로 둔다 — 관용구의 **증거**다(관용구 머리의 `근거:` 가 가리킨다). 지도
  `<execution_map>` 에 `관용구 n` 을 더한다(`주행 n` 과 같은 자리).

### 2-b. 증류 — AI 가 한다, 코드 분류기 금지
- `_build_distill_prompt` 에 두 번째 질문을 얹는다: 「이 주행에서 **되풀이될 모양**은 무엇인가 —
  성공한 문장들 가운데 3~8문장을 실행 순서대로 고르고, 이 주행에만 속하는 값(경로·이름·질의어·
  날짜)을 `${슬롯}` 으로 비워라. 되풀이될 모양이 없으면 빈 목록.」 출력 JSON 에 `phrase:
  [문장…]`, `slots: {이름: 이번 값}` 을 더한다(★자리표 형태를 스키마에 두지 말 것 — ep2777·2806,
  `pitfall_prompt_placeholder_collides_with_param_name`).
- **접지 관문(기계)**: 관용구의 각 문장은 (슬롯을 `slots` 의 이번 값으로 되돌렸을 때) 이 주행의
  실행 호출과 **머리·인자 키가 일치**해야 하고, 문장 순서는 실행 순서의 **부분열**이어야 한다.
  슬롯 치환은 값→`${이름}` 만 허용(머리·키 불변). 이것이 `;` 의 접지 규칙이다 — `>>`·`??` 는 종전
  그대로(한 호출 안), `&` 는 종전 그대로(가지마다 실행에 있었으면), `;` 는 **순서 보존 부분열**.
  `_FLOW_OP_RE` 에서 `;` 를 떼어내는 것이 코드 변경의 핵이다.
- 대표 문장(낱말) 증류는 그대로 — 관용구는 대체가 아니라 층 하나다. 한 주행에서 낱말 0~1 +
  관용구 0~1 이 나온다.
- 문장 하나짜리 관용구는 거절(그건 낱말). 슬롯 0개짜리 관용구는 허용하되 표시(`slots:{}`) —
  "매번 똑같이 도는 모양"도 관용구다(정기 보고서).

### 2-c. 회상 — 채널 하나 더
- `IBLUsageRAG.get_references` 가 낱말 Top-5 옆에 **관용구 Top-2** 를 따로 검색해(`category='phrase'`
  필터, 같은 hybrid) `<ibl_references>` 안에 `kind="phrase"` 로 싣는다. 본문은 번호 목록 CDATA.
  note 에 한 문장: "관용구는 슬롯을 채우고 문장을 빼거나 더해 쓰는 골격이지 그대로 돌리는
  프로그램이 아니다."
- 예산: 관용구 2건 ≈ 문장 16개 ≈ 낱말 5건의 2~3배 토큰. 낱말 임계(`MIN_SCORE`)와 같은 임계를 쓰되
  관용구는 저신뢰 폴백(`LOW_CONF_FLOOR`) 없음 — 틀린 골격이 낱말보다 해롭다.
- **회상 귀속**(`_recall_was_used`·`record_recall_outcome`): 낱말은 머리 집합 교집합이지만
  관용구는 **문장 머리 열의 순서 보존 부분열이 실행 궤적에 절반 이상 등장**했을 때 '사용'.
  success/fail 카운트·avg_ms·avg_tokens 는 같은 루프. ★학습은 저장 건수가 아니라 회상 귀속으로
  잰다(`project_distill_runs_section`).

### 2-d. 측정과 관문 — 세지 말고 실패시켜라
- 트레이너(`backend/ibl_embedding_trainer.py`)의 `normalize_code_to_pattern` 이 관용구를
  **머리 열**(`[a:b];[c:d];…`)로 패턴화하고, `balance_by_action` 이 관용구를 별도 버킷으로 센다.
  평가(`_eval_on_test`·`cloud_training/compare_models.py`)는 **낱말 Top-5 와 관용구 Top-5 를 분리
  보고**하고, 채택 조건에 "관용구 회귀 없음"을 더한다(`feedback_model_portable_optimization` —
  회귀 고정물이 관문).
- 관용구 회상 귀속 벤치: `probe_turn_budget` 과 같은 자리에 고정물 하나 — 관용구가 든 가지에서
  같은 의도의 질의를 던져 관용구가 Top-2 에 오는지.
- 은퇴: 회상 귀속 0 인 관용구는 낱말과 같은 **판정 큐**(`component_lifecycle` 의 낱말 은퇴 큐)로 —
  자동 삭제 금지(사용자 판정). 카운터를 심어 두고 보지 않는다(`feedback_no_counter_watch`).
- 증류 거절 로그: 관용구가 접지 관문에 걸리면 사유(어느 문장·어느 규칙)를 `distill_skip` 과
  같은 자리에 남긴다 — 프롬프트를 고칠 근거.

## 3. 하지 말 것 (헌법 대조)
- 관용구 추출을 코드 분류기(n-gram 빈도·패턴 마이닝)로 만들지 않는다 — AI 가 할 일
  (`feedback_ai_work_not_fixed_program`). 기계는 접지·순서·슬롯 되돌림만 검증한다.
- 관용구를 워크플로로 **자동** 얼리지 않는다 — 결정화 사다리의 다음 칸은 빈도가 증명하고
  사용자가 판정한다(`principle_crystallize_workflow`).
- 가이드에 관용구를 완성 처방으로 옮기지 않는다(`feedback_no_concrete_sentences_in_guides`) —
  가이드는 문법책, 관용구집은 해마.
- `>>` 봉합 금지는 그대로. 관용구의 이음은 `;`(순서)이지 `>>`(흐름)가 아니다.
- 관용구 본문에 개인 명사(경로·이름·질의어)를 남기지 않는다 — 슬롯으로 비우는 것이 곧 개인
  명사 관문(`project_empty_body_private_nouns_gate`)이다. 주행 절(녹취록)은 gitignore 안이므로
  종전대로.

   (★`pitfall_test_writes_to_real_store` — 트리 경로·DB 둘 다 임시화, 실 문서 백업 먼저).

   슬롯 되돌림) + `category='phrase'` 저장 + 거절 로그.
3. `ibl_usage_rag.py`·`ibl_usage_db.py`: 관용구 채널 검색·`<ibl_references kind="phrase">`·

4. 트레이너·compare_models: 관용구 패턴화·분리 보고·채택 조건.

## 5. 판정이 필요한 것
- **착수 여부.** 문법 개정은 아니다 — `;`·`${}` 는 이미 표준이고, 바뀌는 것은 증류 접지 규칙·기억
  단위·회상 채널이다. 그러나 사다리에 칸을 하나 더하는 것이라 언어의 학습 방식 개정이다.
- 회상 예산: 관용구 채널 2건(문장 ~16개)을 매 턴 얹을지, `<execution_map>` 처럼 목차만 얹고
  `recall{store:"실행"}` 로 열게 할지. 권고: **매 턴 2건** — 관용구는 "이 말을 어떻게 시작하나"의
  답이라 열어 보는 것으로는 늦다(낱말 Top-5 를 자동 주입으로 둔 이유와 같다).
- 표기: 관용구 본문을 `;` 한 줄로 둘지 번호 목록으로 둘지. 권고: 저장·검색은 `;` 한 줄(코퍼스
  규약 통일), 표시(가지 문서·references)는 번호 목록(사람과 모델이 읽는 자리).

## 7. 워크플로는 왜 안 쓰였나 (2026-09-05 사용자 질문, 실측)

| 실측 | 값 |
|---|---|
| usage 궤적의 IBL 실행 | 9,117 |
| 그중 `self:workflow` | 22 (전부 프로브·상상훈련 — save→run→delete) |
| `self:script` | 254 |
| 저장된 워크플로 | 1 (`화면검수`) |
| 해마 용례 중 workflow 언급 | 73 (시드) |

사용자 정식화 — 스크립트 = 파이썬으로 굳힌 것, 워크플로 = IBL 로 굳힌 것, 그렇다면 워크플로는 관용구다. 맞다: 워크플로는
**슬롯만 있는 관용구**(`params` 주입, 2026-08-17 B8)다. 안 쓰인 뿌리는 둘이고, 사용자 가설(일부 교체 불가)이 그중 하나다.
1. **일부 교체 불가**: `params` 로 값은 바꿀 수 있지만 문장을 빼거나 더할 수 없다. 실사용 요청은 매번 조금씩 다르므로(주제·소스·
   절 구성) 얼린 문장열은 거의 맞지 않고, 모델은 얼린 것을 고치느니 새로 짓는다. 관용구 층이 이 자리를 채운다 — 읽고 고쳐 쓰는
   골격이므로.
2. **보이지 않음**: 워크플로는 이름으로만 불리고 이름은 `op:"list"` 를 돌려야 안다. 해마에 없어 유사도로 회상되지 않고 교재에도
   없다. 결정화 사다리의 그 칸으로 올라간 적도 없다(빈도가 증명해 저장한 워크플로 0). 보이지 않는 낱말은 쓰이지 않는다.
결론(제안, 판정 대기): 워크플로는 은퇴가 아니라 **관용구의 얼린 칸**으로 자리를 좁힌다 — 같은 슬롯 모양으로 N 번 쓰인 관용구를
스케줄·정기 작업용으로 얼릴 때만(`[self:workflow]{op:"save", do: <관용구 문장열>, params}`), 그리고 저장된 워크플로도 관용구와
같은 회상·교재 표면(`<ibl_idioms>` 의 "얼린 것" 줄, 관용구 채널)에 이름과 골격이 보이게 한다. 얼린 것과 고쳐 쓰는 것이 한 표면에
나란히 있어야 모델이 "그대로 돌릴까, 고쳐 쓸까"를 고른다.

## 8. 병렬 실행의 용량 문제 — 무엇이 있고 무엇이 없나 (2026-09-05 사용자 질문)

> "병렬 실행 결과가 너무 커서 긴 문장을 못 쓴다고 했는데, 그걸 피하려고 원샷 에이전트 호출이 있는 것 아닌가? 용량을 피해 가는
> 예제를 가르칠 수는 없나?"

**있는 것(엔진)**: ①봉투 다이어트 — 파이프 봉투의 `results[]` 는 step 요약, 원형은 `final_result` 만 ②자동 스필 — 이음매 통화가
임계를 넘으면 `data/spill/` 참조로 내리고 뒤 step 이 투명 해소, `[self:write]{spill:true}` 로 명시도 가능 ③파이프 안 AI 낱말
(`table:ai`·`table:brief`·`self:struct`) — 사용자가 말한 "원샷 에이전트 호출"이 이것이다: 원자료가 모델 컨텍스트에 들어오지 않고
파이프 안에서 줄어든다 ④`$변수` — 한 프로그램 안의 중간 통화는 엔진에 머문다.

**없던 것(가르침)**: 관용구 안내문이 "문장마다 따로 execute_ibl" 이라 적혀 있었다 — 그러면 중간 결과가 매번 컨텍스트로 들어온다.
교정: **여러 문장은 한 번에 여러 줄로**(`<ibl_idioms>` 노트·관용구 회상 노트·교재 한 줄). 리허설 도구도 처음부터 한 프로그램으로 돌렸다.
용량을 피하는 골격 관용구 2건 저장(#4464 큰 원문은 스필로 덜어내고 요지만 · #4465 항목마다 원문을 받되 파이프 안에서 한 줄 요지로).

**없는 것(언어)** — 개정 후보 5 ✅ 2026-09-05 집행(`[table:chunk]`, data-ops, `backend/test_table_chunk.py`; 자막 op 가 길면 파일로 내리고 안내문만 남기는 것도 실측 — chunk 는 봉투 message 보다 items 를 본문으로 본다): **긴 문자열 하나를 덩이 items 로 자르는 변환자가 없다.** 자막 84,352자 >> `[table:brief]` 는
입력 상한 60,000자에서 정직하게 죽고, 안내는 take/filter/each 인데 그것들은 items 에만 듣는다(문자열엔 자를 것이 없다). 현재의 답은
핸들러 안에서 요약하는 낱말(`[sense:video]{op:"summarize"}`)뿐 — 문장으로 map-reduce(덩이마다 brief → 합쳐 brief)를 쓰려면
`[table:structure]`/`[self:struct]` 계열에 "문자열 → 덩이 items(chars/문단 단위)" 한 낱말이 필요하다. 이것이 열리면 긴 원문 처리가
낱말 하나가 아니라 관용구(자르기→각각 요약→종합)로 조립된다.
