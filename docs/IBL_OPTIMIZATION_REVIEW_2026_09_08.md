# IBL 최적화 진단 — 검증된 절차가 실제 판단 비용을 줄이게 하기

2026-09-08. 정본 main `722ac10d5b6d6cf8ab9365ce674ebddcd8fadd85`에서 조사했다.
질문은 “언어를 계속 수리하는데 왜 시간·토큰·품질의 개선이 체감되지 않는가”다.
사용자 기준은 **상시 관용구 안에 AI 판단을 넣어 호출을 숨기지 않는 것**이다.

판정: 개선의 한계에 도달했다는 근거는 없다. 관용구의 국소 효과는 확인됐지만,
실제 업무의 반복 구간을 고르고, 에이전트가 선택하게 하며, 전체 비용으로 재검증하는
고리가 아직 닫히지 않았다. 언어 결함, 작문 오류, 관용구 부적합, 모델 판단 비용은
각기 다른 문제다. 하나의 “IBL 성공률”로 합쳐 진단하면 수리가 성능 개선으로 이어지지 않는다.

## 1. 확인한 사실과 그 한계

### 관용구가 전혀 효과 없는 것은 아니다

기존 [96건 가치 실험](IBL_IDIOM_VALUE_2026_09_08.md)의 마지막 비교에서는
지도 제공 16/16 첫 성공, 미제공 9/16 첫 성공이었다. 수리 포함 생성 출력은
1,326 대 5,757토큰이었다. 외부 AI 요약이 필요 없는 파일 읽기·복합키 누적 과제에서
검증된 절차를 재사용하는 이득이 있었다.

그러나 8개 과제 대부분이 선정한 관용구의 용도·범위 변형이었다. 이는 “관용구를 쓰면
이 계약을 더 잘 지킨다”는 증거이며, 전체 보고서에서 자연스럽게 발견·선택하고
동일한 품질을 더 싸게 만든다는 증거는 아니다. 새 3개 지도에 대해 이 성적을 그대로
인용할 수도 없다. 이번 조사에서는 모델 생성 실험을 추가로 수행하지 않았다.

### 상시 목록과 실제 반복 업무가 어긋나 있다

조사 시작 시 카탈로그와 라이브 원장의 상시 이름은 다음과 같았다.

| 이름 | 내부 AI | 원장 성공/실패 | 담당 구간 |
|---|---|---|---|
| 각각읽고요약 | 원문별 요약 | 0/0 | 크롤 후 요약 |
| 잘라각각종합 | 덩이별 요약 + 종합 | 0/0 | 긴 문서 요약 |
| 원장에누적 | 없음 | 0/0 | 기존 행 우선 JSON 누적 |
| 위치마다읽기 | 없음 | 1/0 | grep 위치의 본문 수집 |
| 최신범위읽기 | 없음 | 1/0 | 최신 파일의 지정 범위 읽기 |

두 번의 성공은 기존 실험 기록의 운영 smoke 호출과 일치한다. 원장 횟수 자체는
품질 평가도, 노출 기회 수 대비 선택률도 아니다. 실패가 본문 실행 전에 발생하는
경로까지 완전하게 계수한다고 가정하지 않는다.

실제 최근 보고서의 반복 부담은 과거 처리 목록 제외, 날짜·단위 정규화, 그룹 집계,
두 자료 결합, 선정 근거와 원본의 연결, 보고서와 원장의 일치였다. 현재의 모델 호출 없는
세 이름은 파일 읽기와 JSON 누적에 집중돼 있다. 특히 `원장에누적`은 기존 행 보존이지
upsert가 아니며, 기존 보고서가 쓰는 다른 원장 계약을 그대로 대신하지 못한다.
**이름이 짧거나 함수로 부를 수 있다는 사실만으로 지금 일이 그 함수의 일이 되지는 않는다.**

### 노출 전체가 끊긴 것은 아니지만, 제한 환경에 실제 누락이 있었다

저장된 시스템 AI 프롬프트 두 개를 본문 유출 없이 계수했다. 15:17 스냅샷은
97,672자 중 실제 관용구 블록 2,692자에 5개 이름을 실었다. 21:39 스냅샷은
95,979자 중 1,780자에 모델 호출 없는 3개 이름을 실었다. 뒤의 실행은 당시
원샷 차단 실험에 속하며 현재 설정과 같지 않다. 임시 프롬프트는 재사용 파일이므로
모든 과거 에피소드에 이 구성을 소급 적용하지 않는다.

공통 노출 코드 `_idioms_block`에서 별도 결함을 재현했다. 의존 노드를 정규식으로
찾으며 `[if:…]`의 `if`도 노드로 셌다. 허용 집합이 `None`이면 5개였지만, **똑같이 모든
6개 노드를 명시하면 `최신범위읽기`만 사라졌다.** 제한된 프로젝트 에이전트에는 영향을
주지만, 무제한 시스템 AI의 미사용을 설명하는 원인은 아니다.

프롬프트의 크기는 측정값이며 주의 분산의 인과 증거는 아니다. 무작정 줄이면
입출력 계약이 사라질 수 있다. 기존 실험에서도 짧은 지도가 더 좋은 결과를 내지 못했다.

### 호출 감소와 비용 감소는 같지 않았다

기존 [에피소드 비용 감사](IBL_EPISODE3176_COST_DIAGNOSIS.md)에서:

| 주 모델 응답 | 33 | 19 |

작은 왕복 여러 번을 어려운 작문·판단 한 번으로 합치면 호출 수는 줄어도 더 비싸질 수 있다.
이 둘은 자료와 결과가 다른 업무라 변경의 인과 효과를 보여주는 대조 실험은 아니다.

ep3176의 `table:ai`는 별도 생성·심사에 약 57초를 썼다. 원본 행을 다시 쓰지 않고
색인으로 합치는 구현은 이미 작동했다. 따라서 이를 또 새로 만들자는 처방은 틀리다.
[동일 입력 원샷 실험](IBL_EPISODE3176_ONESHOT_LATENCY.md)에서는 추론을 끄자
명백한 선별 오류가 생겼다. AI 사용을 일괄 차단하는 것도 동일 품질 절감의 해법으로
입증되지 않았다. ep3194는 그 차단 실험 중 실행이며, 현재 설정의 기준선으로 쓰면 안 된다.

### “실패”도 구분해야 한다

이번에 읽은 원문에서 ep3091은 날짜 모양·상대경로·복합 구조 생성·join 입력 연결 등에
반복해서 걸렸다. 일부는 이후 이미 수리됐다. ep3176에는 존재하지 않는 열 이름과
통화 바인딩 실패가 있었다. 이 역시 과거 오류를 현재 미수리 결함으로 세면 안 된다.

ep3194에 남은 실패 하나는 결합 결과에 다시 `union`을 붙여 생긴 입력 계약 오류였다.
그 오류를 정직하게 거절했다는 사실과 올바른 프로그램을 실행하지 못하는 결함은 다르다.
교재가 join/union/merge를 모두 “이항”으로 묶는 표현은 후속 검토 대상이다.
union은 여러 병렬 입력을 한 번에 모은다. 이 표현이 해당 작문 오류를 일으켰다는
인과관계까지 입증한 것은 아니다.

현재 코드에서 기존 관용구·접지·ep3176 관련 검사 **96개**, IR 조합 경계 **75문장**을
다시 통과했다. 이는 정해진 계약의 정상 동작을 확인하며, 오류가 전혀 없다거나 실제
업무 품질이 유지된다는 보증은 아니다.

원장 읽기 전용 계수와 프롬프트 해시: [감사 JSON](experiments/ibl_optimization_review_2026_09_08.json).
잘린 도구 입력은 관용구 호출명 검사에서 제외하고 그 수를 함께 기록했다.

## 2. 이번에 반영한 범위

1. `ibl_access`의 노드 필터가 파서의 예약어 집합을 공유하도록 고쳤다. if/repeat/def/on_error가
   있는 관용구를 허용 노드 부족으로 오인하지 않는다. 실제 허용되지 않은 노드가 each 안에
   있을 때는 계속 소개에서 빠지는 회귀를 함께 검증한다. 이 필터는 소개용이며 실행 권한을
   부여하지 않는다. 문자열 전체에서 후보를 찾는 기존 방식의 모든 한계를 없앤 AST 분석이라고
   주장하지 않는다.
2. `각각읽고요약`, `잘라각각종합`을 상시 추천에서 제외하고 카탈로그의 강등 사유를 기록했다.
   이름과 본문은 명시 호출용으로 유지한다. 전체 원샷 기능의 차단은 아니다.

라이브 원장도 표준 `register_idiom.py --demote` 경로로 반영했다. 변경 전 SQLite와
카탈로그는 `data/_backups/2026-09-08_223719_상시관용구기준/`에 보존했다. 새 프로세스의
지도 생성은 무제한/전체 6노드/코어 3노드 모두 같은 3개 이름, 1,780자를 반환했다.
상시 블록의 기존 캐시는 최대 5분이며 이미 만들어진 대화 프롬프트를 소급 교체하지 않는다.
수리 후 전체 backend 회귀 **3,067개 통과**, Android 번들 재생성 및 파생물·층 검사를 수행했다.

이는 재현 결함 수리와 사용자 기준의 반영이다. 이 변경만으로 보고서가 더 빨라졌다고
판정하지 않는다. 상시 지도의 실사용 성능 비교는 아래의 별도 검증이 필요하다.

## 3. 관용구를 고르는 기준

상시 관용구는 **모델 호출 0인, 검증된 중간 절차**로 고른다. 파일·네트워크 I/O가 들어갈 수
있으므로 “같은 입력이면 언제나 같은 결과인 순수 함수”와 혼동하지 않는다. 외부 세계의 실패를
보존하면서, 그 결과를 연결하는 절차가 모델 판단 없이 작동한다는 뜻이다.

AI 의존성은 직접 본문의 `table:brief`만 찾으면 부족하다. `[fn:]`의 하위 정의·저장 워크플로,
each/do·AI 술어·goal·criteria와 스크립트 내부 호출까지 고려해야 한다. 후속 승격 검사에서는
기존 어휘의 `ai_call` 선언을 사용하고, 따라갈 수 없는 동적 코드는 “AI 없음”으로 인증하지
않는다. 이번 작은 수리는 이러한 전이 의존성 검사를 새로 구현한 것이 아니다.

| 확인할 것 | 채택에 필요한 증거 |
|---|---|
| 실제 적용 기회 | 여러 업무에서 같은 계약이 반복되고, 작은 입력 변화에도 그대로 맞음 |
| 작문 부담 | 인자 채우기가 본문 작성보다 쉽고, 잘 틀리는 연결·수집·복구 규칙을 없앰 |
| 실행 계약 | 입력/출력 열, 단위, 순서, 빈 결과, 실패 보존, 잘림이 분명함 |
| 조합 가능성 | 앞 생산자와 뒤 소비자를 바꾼 미사용 과제에서도 첫 실행이 성공함 |
| 총비용 | 지도 입력 부담·수리·하위 호출을 포함해 같은 품질에서 시간과 토큰이 줄어듦 |

문장 두 개 이상, 이름 길이, 사용 횟수만으로는 이 기준을 대체할 수 없다.
반대로 단순한 축약도 실제 빈도와 순이득이 충분하면 유효할 수 있다. 길이만으로
무조건 탈락시키는 규칙 역시 최적화 목표와 다르다.

## 4. 먼저 시험할 세 종류의 절차

아래는 **후보의 계약**이다. 아직 등록된 함수 이름이나 실행 보장 코드가 아니다.
먼저 기존 프리미티브로 작성하고, 실제로 필요한 부족만 고친다.

| 우선 | 후보 계약 | 줄이려는 반복 판단·오류 |
|---|---|---|
| 1 | 원본 목록 + 선정 ID/근거 → 원본을 보존한 선정 행. 없는 ID·중복 선정·키 충돌은 명시 실패/신고 | 주 모델이 숫자·URL·제목을 다시 타이핑하고 근거를 떨어뜨리는 일 |
| 2 | 현재 목록 + 이미 처리한 키 → 미처리 항목. 빈 과거 목록·복합키·중복의 의미를 고정 | 매 보고서의 과거 중복 제외와 날짜/키 모양에 따른 우회 |
| 3 | 공통 키로 각각 집계한 자료 → 단위·누락·분모 0을 드러낸 비교표 | 그룹 집계→결합→비율 계산을 매번 재조립하는 일 |

첫 후보의 사용 흐름은 이렇다. 수집 결과는 엔진의 변수에 보존한다. 주 모델은 필요한
근거를 읽고 선정 ID와 짧은 판단만 만든다. 그 뒤 원본 결합·계산·정해진 표 렌더링을
엔진이 수행한다. 새로운 해석과 최종 서술은 주 모델이 맡는다. 원본을 읽지 않고 ID만
고르게 하거나, 원문을 임의로 잘라 품질을 낮추는 설계가 아니다.

`table:ai`의 색인 병합은 이미 그 도구 내부에 존재한다. 남은 기회는 **주 실행 모델과
데이터 엔진 사이에서도** 판단과 원본 운반을 같은 원칙으로 나누는 것이다. 기존 join과
턴 변수만으로 충분한 부분은 그것을 사용한다. 알려진 자료를 보고서와 DB에 각각 생성하는
부분도 하나의 검증된 자료에서 렌더링할 수 있는지 따로 시험한다.

매물 적합성, 기사 중요성, 실제로 유용한 팁인지 같은 살아 있는 판단은 이 후보에 숨기지 않는다.
정착되지 않은 판단을 단순 필터로 치환한 속도 개선은 사용자 목표의 실패다.

## 5. 효과를 증명하는 순서

**첫째, 수리와 최적화의 시험을 분리한다.** 파서/값/실행기의 회귀는 의도한 의미가
보존되는지 본다. 성능 비교는 같은 자료와 품질에서 에이전트가 스스로 더 싼 해법을
구성하는지 본다. dry-run 초록이나 `ACHIEVED` 하나를 품질 오라클로 쓰지 않는다.

**둘째, 실제 앱 경로를 고정 자료로 재생한다.** 세 보고서와 다른 종류의 작은 업무에서
외부 조회 결과·초기 파일·원장 상태를 고정한다. 생산 프롬프트·기억·도구 정책·모델·effort를
같게 하고, 산출물은 격리 경로에 쓴다. 현재 지도와 “현재 지도 + 후보 하나”를 순서 교차로
비교한다. 후보를 쓰라고 답을 알려주지 않는다. 제공해도 직접 조합한 경우 역시 결과다.
미제공 조건은 후보의 순효용을 확인할 때 추가한다. 차단 실험과 동시에 바꾸지 않는다.

**셋째, 설계에 쓰지 않은 입력을 남겨 둔다.** 신규 날짜·빈 결과·부분 실패·복합키·새 도메인,
후보가 부적합한 작업을 포함한다. 정답을 맞추기 위해 시험을 고쳤다면 그 시험은 더 이상
미사용 평가가 아니다. 저렴한 오프라인 계약 검사 뒤 작은 앱 비교를 하고, 품질이 유지된
후보만 반복 수를 늘려 비용을 쓴다.

**넷째, 측정 단위를 업무 전체로 한다.**

- 품질: 원문 근거의 정확성, 필수 항목 누락, 계산·단위 오류, 사용자 수정량.
- 비용: 주 모델과 하위 모델의 호출·입출력·캐시를 따로 기록. 추론은 출력의 부분집합이며
  다시 더하지 않는다. 고정된 가격표가 있을 때만 실제 요금으로 환산한다.
- 시간: 사용자 요청부터 검증된 결과까지의 벽시계. 중첩 IBL/모델 시간을 이중 합산하지 않는다.
- 진단: 관용구가 맞는 기회 수, 실제 노출 여부, 선택 여부, 처음 작성한 문장의 의미 정합성,
  수리 횟수, 최종 성공. 호출을 하지 않았다는 사실만으로 부적합/무시/노출 결함을 구별할 수 없다.

채택은 품질 비열화가 먼저이고 시간·토큰의 개선이 뒤다. 품질 오차 한계는 업무에 맞게
미리 정한다. 작은 반복 수에서 중앙값만 좋아진 결과를 확정 이득이라고 하지 않는다.
캐시 읽기 절감과 새 입력·출력 절감을 구분한다. 가장 긴 보고서 몇 건만으로 모든 업무를
대표하게 만들지 않는다.

**다섯째, 후보 탐색을 대장장이 고리에 연결한다.** 실행 궤적을 AST 기준으로 비교하고
값·변수명은 슬롯으로 바꾸되 데이터 흐름·순서·부작용은 보존한다. 많이 반복되는 액션의
문자열 부분열이 곧 재사용 가능한 함수는 아니다. 빈번하거나 수리가 비싼 구간과
상상한 새 조합을 후보로 만들고, 격리 실행·결과 검증·새 업무 비교를 통과한 것만 선정한다.
후보 생성·시험은 자동화할 수 있지만 상시 어휘 승격은 기존 수동 규약을 따른다.
검증되지 않은 자동 증류를 매 턴 다시 켜자는 제안이 아니다.

## 6. 하네스의 지능을 어떻게 볼 것인가

하네스가 이미 배운 절차·불변식·복구를 모델 대신 책임지면, 같은 모델로 더 많은 일을
해내거나 더 작은 모델로 같은 일을 할 수 있다. 이것은 유의미한 능력의 축적이다.
다만 임의의 새로운 의미 판단까지 언어만으로 해결한다는 뜻은 아니다. 지능의 비교는
“복잡한 문장을 얼마나 길게 쓰는가”보다 **어떤 반복 판단이 더 이상 모델을 필요로
하지 않는가, 남은 판단으로 어떤 결과를 만드는가**로 하는 편이 목표에 맞는다.

연구적으로도 가능한 방향이다. [LILO](https://arxiv.org/abs/2310.19791)는 프로그램을
합성·압축하고 사용 문맥에 맞는 이름과 문서를 붙이는 반복으로 재사용 라이브러리를
학습했다. 문서화가 합성기의 추상화 사용에도 도움을 주었다. 다만 제한된 프로그램 합성
벤치마크의 결과이며 IndieBiz OS의 비용 절감을 증명하지 않는다.
[CodeAct](https://arxiv.org/abs/2402.01030)는 실행 가능한 코드로 행동을 조합하는 방식의
효과를 시험했다. 역시 Python 기반 결과이지 IBL의 우월성을 직접 검증한 연구는 아니다.

이 연구들에서 가져올 것은 어휘 수 증가나 선언이 아니라 **새 문제 해결 → 검증 → 압축 →
문서화 → 다음 문제의 해결 개선을 측정하는 고리**다. 현재 가장 먼저 할 일은 그 고리를
실제 보고서의 모델 호출 없는 중간 절차 하나에서 완주하는 것이다.
