# 실행 없는 IBL 반복 계획 분석

2026-09-23. 목적은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)을 따른다.
긴 일회성 프로그램과 저장된 관용구에 같은 검사를 적용한다. 보고서 한 종류의
본문·프롬프트를 고치는 작업이 아니라 기존 정적 검사기의 작은 확장이다.

## 해결하는 문제

문법·열 연결이 맞아도 반복 상한 때문에 입력 일부가 빠지거나, 반복 본문이 같은
자료 전체를 AI에 계속 보낼 수 있다. 이런 구조는 도구를 실행하기 전에 조사할 수 있다.
`ibl_typecheck.typecheck`에서 공통 IR과 사전 선언을 읽는 `ibl_preflight.analyze`를 호출한다.
`execute_ibl{check:true}`, 실제 실행 전 검사, `/ibl/validate`가 같은 진단을 공유한다.
추가 LLM 호출과 사용자 프로그램 실행은 없다. 사전·외부 함수 정의는 기존 조회 경로로 읽는다.

| 진단 | 필요한 근거 | 대응 |
| --- | --- | --- |
| `each_input_limit` | 입력 행 수와 유효 each 한도를 정적으로 알고, 행 수가 더 큼 | 전건 처리 의도면 한도를 맞춤. 의도한 일부 처리면 수용 |
| `repeated_ai_batch` | 반복 상한 > 1, 입력 > 1행, 반복에 의존하지 않는 입력, 어휘가 `ai_call:true`·`flow.accepts:items` 선언 | 현재 행이 필요한지, 공통 자료의 반복 판단이 필요한지 확인 |

둘 다 **warning**이다. 사용자 의도를 대신 판단해 차단하거나 입력을 줄이지 않는다.
`statement`, `step`, `at`로 위치를, `facts`로 입력 건수·한도·제외 건수 등의 근거를 준다.
기존 확정 타입 오류의 차단 규칙은 유지한다. 정상 실행 응답의 경고 요약에도 rule과 facts를 남긴다.

예를 들어 다음 문장은 실행 없이 1행의 제외와 3행 전체의 반복 AI 입력을 알 수 있다.

```text
$목록 = [{id:"a"},{id:"b"},{id:"c"}]
$목록 >> [table:each]{limit:2} {
  [table:ai]{items:$목록,instruction:"각 항목을 분류"}
}
```

전건을 각각 처리하려는 의도라면 `limit:$목록.count`와 `items:[$it]`를 검토한다.
하지만 각 회차에서 전체 자료를 대조해야 하는 작업도 있으므로 자동 수리는 하지 않는다.

## 분석과 응답 계약

값 자체를 실행·계산하지 않고 목록 건수, 리터럴 정수, 필드 구조, 반복 변수 의존성만 전달한다.
리터럴·변수·파이프·함수 인자와 반환·공통 코드 IR의 캡처를 따라간다.
분기/반복에서 변경될 수 있는 변수는 이전 값으로 단정하지 않는다.
산술을 별도 구현하거나 열 보존 선언에서 출력 행 수를 추측하지 않는다.

지역 `def`와 조회 가능한 외부 `fn`을 호출 위치에서 분석한다. 사용하지 않은 정의는 비용에서
제외한다. 반복의 상한을 곱하고, 병렬·조건·폴백·try의 가지는 모두 합산한다.
내용어 이름 목록은 검사기에 두지 않는다. each/fn/반복 블록은 표준 언어 구조이며,
each 기본 한도는 실행기와 `workflow_contract.EACH_DEFAULT_LIMIT` 계약을 공유한다.

`preflight` 응답:

- `declared_ai_visits_upper_bound`: **선언된 AI 어휘의 방문 횟수 상한**. 미상은 `null`.
- `ai_sites`: 호출 위치·어휘·위치별 상한. `ai_sites_omitted`는 표시 한도 밖의 위치 수.
- `unknowns`: 동적 입력/본문, 해석하지 못한 본문, 미확인 함수/어휘, 분석 한도에 걸린 위치.
- `status`: `analyzed`는 지원 범위의 분석 완료, `partial`은 일부 미상, `abstained`는 분석기 예외.

입력 건수가 미상이어도 each 한도가 20이면 그 본문 방문 상한은 20일 수 있다.
반대로 동적 한도, 확인 불가능한 함수, 재귀/분석 한도로 전체 상한을 알 수 없으면 `null`이다.
0은 분석 대상인 선언된 AI 어휘의 방문이 없다는 뜻이며 전체 작업이 무료라는 뜻이 아니다.
분석 예산은 깊이 8·방문 단계 2,000, 진단/위치 표시 한도는 각각 32다.
한도를 만나면 미상으로 남기고, 기존 타입 진단이나 실행 가능 여부를 지우지 않는다.

## 한계와 품질 보호

이 상한에는 스크립트·도구 구현 내부의 모델 호출, 조건 판단, 재시도, 토큰, 실행 시간이
들어 있지 않다. 배타적인 분기의 합산이나 실제 도달하지 않는 경로 때문에 과대 추정될 수 있다.
도구 출력 건수·현재 실행 변수의 실값·동적 생성 코드도 추측하지 않는다.
일부 변환 뒤의 행 수와 문자열 형태의 한도 등 이번 분석이 다루지 않는 값은 미상이다.

내용의 충분성, 원문 근거가 필요한 위치를 포함하는지, 중복 판정의 정확성, AI의 후보별
출력 누락은 이번 규칙만으로 알 수 없다. 최근 AI 팁 보고서 사례의 모든 실패를 잡았다고
주장하지 않는다. `ok:true`는 알려진 정적 오류가 없다는 뜻이며 품질·성공·저비용의 보증이 아니다.

다음 규칙은 실제 에피소드에서 반복되는 실패를 재현하고, 정당한 프로그램의 반례도 함께
만들 수 있을 때 추가한다. 입력 절단이나 판단 단계 제거를 비용 개선으로 간주하지 않는다.

## 검증과 측정

`backend/test_ibl_preflight.py`는 한도 누락, 기본 한도, 행별 입력/전체 입력 구별,
파이프 입력 우선, 동적 입력, 변수 재할당, 중첩 반복, 함수 인자/암묵 파이프/반환,
재귀 한도, 미해석 본문, 선언에 따른 AI 판별, 분석 실패와 기존 오류 보존을 검증한다.
check:true 시험은 실행기 호출을 금지한 상태에서 계획과 경고를 확인한다.

기존 코퍼스의 긴 순서 상위 300개 중 현재 파싱·타입 검사를 통과하는 100개를 읽기 전용으로
조사했다(합계 36,842자, 최장 6,011자). 성공 이력이 확인된 실행 표본이라는 뜻은 아니다.
같은 타입 검사에서 새 계획 분석만 켜고 끄며 워밍업 뒤 순서를 교대해 5회 측정한 중앙값:

| 100개 전체 검사 | 경과 시간 |
| --- | ---: |
| 기존 타입 검사 | 106.20 ms |
| 계획 분석 포함 | 124.52 ms |
| 추가 비용 | 18.32 ms, 문장당 약 0.18 ms |

전체 회귀와 동시에 돌린 로컬 참고 측정이며 일반 성능 보증은 아니다.
분석 완료 85개·일부 미상 15개·분석 예외 0개, 기존 `ok` 변경 0개였다.
이 표본에는 새 두 규칙의 경고가 없었다. 따라서 탐지 효과의 근거는 명시적 재현 시험이고,
이 코퍼스 조사는 호환성·검사 부담의 근거다. 보고서 생성이나 사용자 프로그램은 실행하지 않았다.

실제 작업의 품질·완료 시간·전체 토큰 절감은 아직 미측정이다. 향후 같은 입력·완료 조건의
여러 업무에서 검수/수리까지 포함해 비교해야 하며, 검사 안내가 늘리는 맥락 비용도 포함한다.
상시 교재는 기존 36,000바이트 예산 안에서 문구를 교체했다.

최종 검증(2026-09-23): 새 기능 회귀 37개 통과. 전체 백엔드 회귀는
`.venv/bin/python3 -m pytest backend/ -o addopts='' -q`로 5,483개 통과·1개 건너뜀
(490.72초, 경고 116건). 검수 정합은 fixture 148개·교재 11개에서 거짓 오류 0개였다.
`check_backend_layers.py`, `check_retired_contracts.py`, `build_ibl_nodes.py --check`,
`build_body_bundle.py android --check`도 통과했다.
