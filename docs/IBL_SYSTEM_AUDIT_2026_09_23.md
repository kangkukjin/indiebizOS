# IBL 전환 후 시스템 재점검

2026-09-23 저녁, 정본 main의 `ad6d6b1d` 이후 상태를 점검했다.
실행 중인 백엔드, 작성·학습·복구 코드, 어휘 파생물, 최근 실사용 기록과 Android 설치 파일이 대상이다.

## 발견하고 수정한 문제

1. **링크된 스크립트의 변경을 재개 검사에서 놓침.**
   `script_snapshot`이 심볼릭 링크를 고정된 문자열로 취급하고 동적 범위에서도 제외했다.
   링크 대상의 본문을 바꿔도 지문이 같음을 임시 파일로 재현했다.
   이제 실제 파일 내용을 읽고, Python 진입 파일의 실제 디렉터리에서 import 의존성을 찾는다.
   동적 범위 확장 시에도 먼저 발견한 외부 의존성은 유지한다.

2. **입력 함수의 부분 저장 후 재시도에서 DB와 학습 파일이 갈라질 수 있음.**
   DB 저장 후 학습 JSON 쓰기가 실패하면, 재시도 시 기존 이름을 충돌로 판단해 다른 이름을 만들거나 저장을 거절했다.
   이제 같은 증류 후보의 영수증으로 이미 저장한 이름·본문·증거를 먼저 회수해 색인과 학습 파일을 복구한다.
   실제 임시 DB에 저장한 뒤 파일 기록을 실패시키고 재배달해, DB 1행과 학습 JSON 1행의 이름·본문·증거 일치를 검증했다.
   영수증이 가리키는 행이 삭제되었다면 새 행을 만들지 않고 충돌로 처리한다.

3. **복구 API의 잘못된 요청이 서버 오류가 되거나 모호하게 처리됨.**
   `ticket`과 `run_id`는 정확히 하나만 허용한다. 잘못된 실행 ID는 HTTP 422,
   존재하지 않는 프로젝트는 HTTP 404로 반환한다. 잘못된 입력으로 영수증 저장소에 접근하지 않는다.

## 실제 가동 상태

- 수정 후 관리 제어자의 자동 재시작이 완료되었고 `ACTIVE/ready`, 오류 없음, 실행 코드와 디스크 지문 일치를 확인했다.
- `/health`, `/ibl/capabilities`는 HTTP 200. `/portal/manifest`의 무인증 요청은 HTTP 403으로 보호된다.
- 실제 HTTP에서 명시 입력 6 → 함수 반환 7, 같은 핸들 재개 → 7, recover → completed를 확인했다.
  입력을 8로 바꾼 재개는 `RESUME_CHANGED`, 잘못된 recover 요청 3종은 HTTP 422였다.
- 로그의 Nostr 릴레이 HTTP 500 뒤에 연결 복구가 관측되었다. 외부 릴레이의 일시 오류만으로 설정을 변경하지 않았다.

## 실사용 기록과 코퍼스 해석

점검 당시 최신 완료 실사용 에피소드는 4009(14:54~15:46)이다.
IBL 시작 사건 200건 중 과거 해석 197건, 현재 해석 3건이며, 중첩 호출도 포함한 수치다.
이는 저녁의 최종 전환·배포보다 앞선 기록이므로 현재 배포본의 채택률로 해석하지 않는다.

실행 기억에는 과거 용례 3,621개와 이름 있는 관용구 48개,
현재 용례 6개와 이름 있는 함수 2개가 남아 있다. 과거 원문과 실적을 보존하는 기존 방침에 따른 상태다.
회상 안내는 저장 판본을 표시하고 과거 사례의 목적·도구를 참고하되 새 프로그램은 현재 조합 교재를 따르도록 명시한다.
전 코퍼스 번역이나 모델 비교 실험은 이번 점검에서 하지 않았다.
