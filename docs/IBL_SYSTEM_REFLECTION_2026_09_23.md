# IBL의 진화 목적에서 다시 본 IndieBiz OS

2026-09-23. 기준: [진화 목적과 개선 판단](IBL_EVOLUTION_PURPOSE.md).
조사 시점 코드 `c834bd45`와 로컬 관용구 원장을 읽었다. 수치·파일 지문·검증 범위는

이 문서는 구현 변경안의 집행이 아닌 현 상태의 진단이다.

## 판단

**IBL은 도구를 조합하는 언어의 기반과 국소적인 효용을 이미 갖췄다. 그러나 조합으로 만든 능력이
다시 다음 능력의 부품이 되어 여러 층으로 축적되는 과정은 아직 약하다.**
실행기는 언어 쪽으로 앞서갔고, 저장된 능력의 구성·훈련·성장 평가가 그 방향을 충분히 따르지 못한다.
복잡한 일을 완수한 사실과 공통 실행 능력을 키운 사실을 구분해 반성해야 한다.

이 판단은 타 하네스와의 비교 실험이 아니다. 우리 지향점에 비춘 내부 평가다.

## 1. 기반과 효용은 실제로 있다

`def/fn`, 닫힌 인자 범위, 파이프, 병렬, 조건, 반복, 오류 처리, `each`, 반환 통화,
정적 검사, 턴 변수와 부분 재개가 있다. 이름 호출·본문 전개·다음 소비자로의 반환을
공통 계약으로 맞추는 수리가 이미 이루어졌다.
관련 기존 회귀 시험 5파일을 이번에 다시 실행해 **113 passed**를 확인했다.
따라서 “조합 구조가 없다”거나 “처음부터 다시 만들어야 한다”는 진단은 맞지 않는다.

[9월 9일 v3 노출 실험](IBL_IDIOM_EXPOSURE_LEVERS_2026_09_09.md)도 긍정적인 근거다.
같은 9과제·3반복의 조건별 27회에서 관용구 노출은 첫 요구 충족 11→26,
최종 충족 15→27, 수리 16→1이었다. 전 시도 모델 벽시계는 3,002→662초,
입력 토큰 합은 2,640,493→1,823,029로 줄었다.
함수 반환 수리 위에서 호출 계약과 소개를 다듬은 묶음 효과이며, 모델 하나·제한된 과제군의
역사적 실험이다. 현재 전체 앱의 완료 시간이나 모든 업무의 일반화 성과로 확대하지 않는다.

## 2. 실행 가능한 조합과 축적된 조합 사이의 간격

로컬 원장의 이름 있는 정의 48개를 공통 스캐너로 조사했다.

- 다른 등록 관용구를 `fn`으로 부르는 정의: **0개**, 등록 정의 사이 호출 간선 **0개**.
- 내부 지역 함수를 정의해 쓰는 관용구: **1개**. 이 지역 함수 호출은 위 간선에서 제외했다.
- 전체 본문의 원시 `[fn:` 문자열도 2곳이며 모두 그 지역 함수 호출이다.
  지연 문자열 속에 등록 관용구 호출이 숨어 있는 경우는 이번 원장에 없었다.
- 상시 소개는 7개다. 개수 자체가 부족함의 증거는 아니다.

**언어는 부품을 다시 조합할 수 있지만, 현재 관용구 저장소에는 그 조합이 여러 층으로 쌓인 흔적이 없다.**
실행 중 임시 프로그램이 여러 관용구를 연결하는 경우나 스크립트 내부의 합성까지 없다는 뜻은 아니다.
정의 관계를 조사한 결과이며 실행 빈도·성공률을 추정하지 않았다.

문제는 관용구를 더 많이 만드는 것이 아니다. 필요한 부품을 찾고, 계약으로 연결하고,
검증한 큰 조합을 다음 작업에서도 부를 수 있게 남기는 과정을 실사용에서 확인해야 한다.
앞으로는 같은 완성품의 재호출뿐 아니라 기존 부품으로 새로운 큰 작업을 구성하는 능력을 본다.

## 3. 경험의 저장이 표현 단위의 성장으로 충분히 이어지지 않는다

현재 자동 증류의 `apply_experience`는 실행 원문을 선택해 저장하며 **alias를 빈 문자열로 둔다**.
이름 없는 용례에는 본문 1,000자 상한도 있다. 긴 일회성 기록과 오염된 이름의 축적을 막는
의도된 정책이다. 자동 이름 생성을 다시 켜는 것으로 해결할 문제가 아니다.

수동 `register_idiom.py`의 등록·승격·개정·후보 조회와 주간 결정화 스캔은 이미 있다.
따라서 후보 발굴 기능 자체가 없다는 진단도 틀리다. 다만 후보를 어떤 공통 부품으로 추출하고,
다른 입력에서 검증하고, 기존 부품과 연결해 상위 관용구로 보존할지는 개발·수동 선별에 의존한다.
앞 절의 정의 관계는 그 과정의 현재 결과를 보여 준다.

**용례 회상이 좋아지는 것, 생성 모델이 조합을 잘하는 것, 재사용 가능한 능력의 층이 자라는 것은 서로 다른 성과다.**
훈련에는 자연어 과제 수행과 오류 발견에 더해 “이번에 익힌 부품을 다른 과제에서 다시 조합했는가”가 필요하다.
등록과 상시 소개는 계속 구분해야 한다. 좋은 부품을 저장한다고 모든 턴에 본문·설명을 실을 이유는 없다.
성장 과정은 기존 수동·주간 경로를 보강하는 방향부터 검토하며 매 턴 별도 AI를 추가하지 않는다.

코어 어휘를 작게 유지하는 원칙도 적용 대상을 구분해야 한다. **문법·기능어 코어의 최소주의와
검증된 관용구 사전의 성장은 양립한다.** 새 액션을 막기 위해 절차를 스크립트에 보관했더라도,
그 절차의 유용한 부분을 다른 문장에서 다시 조합할 수 있는지까지 확인해야 한다.

근거: `backend/cognition/ibl_usage_rag.py`의 `apply_experience`,
`backend/cognition/ibl_idiom.py`의 `EXAMPLE_CODE_CEILING`,
`scripts/register_idiom.py`, `backend/cognition/vocab_crystallization.py`.

## 4. 복잡한 일의 이음매를 작성자가 여전히 많이 책임진다

현재 AI 팁 보고서의 `input_as`는 바깥 봉투 전달을 줄였고, `input_fields`·`preserve_rows`는
원본 보존과 모델 입력을 공통 계약으로 분리했다. 이 부분은 지향점에 맞는 일반 개선이다.
그러나 each 안의 4곳에는 오류·잘림·미처리·근거 필드를 손으로 옮기는 긴 객체가 남는다.
검증 결과 확정·다음 요청 준비·전건 분할 비교·재개는 보고서 전용 Python 보조 스크립트가 상당 부분 맡는다.

Python 구현 자체는 문제되지 않는다. 세계의 규칙과 구현 세부는 패키지·스크립트에 둘 수 있다.
문제는 **다음의 다른 복잡한 작업을 만들 때 같은 봉투 운반과 완료 경계를 또 구현해야 하는가**다.
그렇다면 한 작업을 완성한 이득은 얻어도 언어 시스템의 다음 작업 비용은 충분히 낮추지 못한 것이다.

기존 엔진에도 턴 변수·성공 변수 보존·`resume`가 있으므로 범용 재개를 처음부터 만들 필요는 없다.
다만 이것과 개별 스크립트의 확정 영수증은 같은 계약이 아니며, 보고서의 비교 단계는 일부 배치가
성공해도 단계 재개 시 배치 전체를 다시 수행한다. 현재 구현 기록도 이 한계를 명시한다.
두 번째 실제 업무에서 동일한 문제를 확인하고, 기존 구조 위에 공유할 작은 계약을 추출하는 것이 다음 단계다.

조사 중 추가된 [v3 재작성 후보](experiments/ai_tips_rewrite_2026_09_23/README.md)는
두 지역 함수로 반복 계약을 묶어 5,791→4,574자로 줄였다. 이는 기존 문법만으로도 개선할 여지가
있다는 근거다. 아직 정적 비교 후보이며 실행·품질·총비용은 미검증이고 운영 관용구를 대체하지 않았다.

## 5. 추상화의 층을 키울 때 생기는 비용과 제한을 아직 덜 검증했다

실행기에는 일반 중첩 깊이 3, 함수 깊이 5, 워크플로 깊이 5가 각각 있다.
`_execute_fn`은 `_nest`를 통해 일반 중첩 깊이도 올린다. 따라서 “함수 5층이면 모든 조합이 된다”는
가정은 성립하지 않는다. 분기·each·함수를 함께 쓰는 유한한 조합도 일반 중첩 예산을 공유한다.
이번 조사는 이 코드를 확인했으며 실제 업무가 어느 깊이에서 실패하는지 새 실행으로 재현한 것은 아니다.

상한은 자원 보호를 위한 것이지만, **순환·과다 실행과 정상적인 추상화 층을 같은 숫자로 막는 방식**은
성장 방향과 긴장한다. 무조건 상한을 올리기보다, 실제로 필요한 비순환 조합을 고정 입력으로 재현하고
시간·작업량 예산, 호출·블록 깊이의 역할을 구분해 검토할 필요가 있다.

상시 관용구 7개 중 5개의 저장 반환형은 `items⟨열 미상⟩`이다. 입력에 따라 열이 달라지는 것은 정상이다.
다만 이름과 반환형만으로 하류 연결을 판단하기 어려워 본문 확인·추측 비용이 생길 수 있다.
고정 열을 허위로 선언하기보다 입력 열 보존·열 변환 관계를 계약으로 전달하는 방향이 맞다.
이것이 모델의 현재 실패를 얼마나 설명하는지는 별도 실험이 필요하다.

근거: `backend/ibl/ibl_engine.py`, `ibl_control_blocks.py`, `ibl_executors.py`,
`workflow_contract.py`, 감사 기록의 상시 반환형.

## 6. 성장의 성과를 재는 일부 지표가 목적과 어긋난다

`scripts/ibl_composition_cost_metrics.py`는 첫 호출의 `action_count >= 2`와 실행 성공을
`first_program_success`로 정의한다. 메모리 SQLite에 **fn 한 번, 실행 성공**을 넣어 계산하면
`failed_calls=0`이면서 `first_program_success=false`가 된다.
이 지표는 원래 다액션 조합의 흔적을 보려는 자였지만, 큰 능력을 짧게 부르는 현재 목적의 대표 지표로는 맞지 않는다.
호출이 길수록 좋은 시스템처럼 평가해서는 안 된다.

전체 모델 사용량·실행 궤적·검수 기록은 이미 존재한다. 그러나 등록 관용구의 비용 메타데이터에서
`avg_tokens >= 0`은 48개 중 3개다. 이 수치는 관용구 간 공정한 비용 비교나 개선 전후 평가를 뜻하지 않는다.
9월 23일 실행 개선도 [현재 구현 기록](IBL_EXECUTION_EVOLUTION_IMPLEMENTATION_2026_09_23.md)에
같은 모델·입력의 전체 토큰·완료 시간·의미 품질 A/B는 미실시로 남아 있다.

목표 달성·최초 완주·바깥 모델 개입·내부 AI 호출·수리·전체 토큰·완료 시간을 함께 보고,
익숙한 관용구 호출 / 새 부품 조합 / 대응 관용구가 없는 새 구성으로 과제를 구분해야 한다.
정적 통과·회귀 통과·본문 단축은 각각의 성과이며 보편적 효율 향상을 대신하지 않는다.

## 우선순위

1. **한 호출의 크기 대신 완료한 일과 전체 비용을 잰다.** 이미 있는 관측 자료를 연결하고
   단일 fn 호출을 벌주는 지표를 목적에 맞게 정정한다. 새 평가 AI를 매 실행에 붙이지 않는다.
2. **서로 다른 업무에서 재사용할 부품을 검증한다.** 모든 보고서를 하나의 거대 관용구로 묶기보다,
   필요한 공통 처리·결과 보존·복구 계약을 찾는다. 이름 호출과 본문 전개가 같은 결과·진단을 내야 한다.
3. **부품으로 만든 상위 관용구를 다시 다른 작업에 쓴다.** 기존 등록·후보 조회·훈련 경로를 이용해
   실제로 층이 자라는 한 고리를 완성한다. 새 입력·실패 조건·큰 규모와 미노출 과제에서 검증한다.
4. **그 과정에서 드러난 언어 한계를 고친다.** 입력·반환 계약, 진단 전달, 중첩 제한, 국소 재개의
   공통 문제를 수리한다. 관용구 개수나 계층 깊이 자체를 달성 목표로 만들지 않는다.

지금 필요한 전환은 **사례를 해결하고 그 절차를 보관하는 데서, 해결한 절차를 다음 능력의 재료로
길러 내는 데까지 개발과 훈련의 완료 조건을 넓히는 것**이다.
이 방향에서 품질·시간·전체 토큰의 개선이 확인되어야 IBL 중심 진화가 성과를 낸 것이다.

## 검증 범위

- 관용구 SQLite 원장: 읽기 전용 연결. 원장·등록·실적·운영 워크플로 변경 없음.
- 기존 관련 회귀 시험: 113 passed, 8.09초. 외부 응답 대역을 사용하는 계약·조합 시험이며 전체 회귀는 재실행하지 않았다.
- 지표 문제: 메모리 SQLite의 합성 사건으로 재현. 모델 호출·외부 발송·보고서 실행 없음.
- 비용 효과: 기존 실험 기록 검토. 새로운 생성 모델 실험이나 보편적 절감률 측정은 수행하지 않았다.
- 이번 반영은 이 보고서와 감사 JSON뿐이다. 구현 변경은 다음 작업의 대상으로 남긴다.
