# take 음수 오작동 보고의 실제 원인: MCP 결과 절단

2026-09-09 AI 동향 보고서의 에피소드 3219, 궤적 이벤트 26–27을 확인했다.
실행 코드는 `$규칙\n$원장 >> [table:take]{n: -4}`, `verbose:true`였다.

## 관측

- 저장된 원본 봉투는 25,085자다. 최종 값은 `count:4`이며 날짜는
  2026-09-05·06·07·08이다. `take`의 음수 슬라이스는 정상 실행됐다.
- MCP는 `final_result`를 중복으로 보고 지웠다. 이후 16,000자 전달 한도에
  맞추면서 앞의 규칙 산문과 원장 10행이 예산을 차지해, 마지막 `take` 결과를
  꼬리에서 잘랐다. Claude Code의 실제 도구 결과는 16,001자이며 JSON도 불완전했다.
- 원본 결과 SHA-256(궤적 event 27):
  `73198ec21b79949d48bc7e711df5340d55617a6f35d94e9f36b20098b343d680`.
  보관 티켓 `aa2eebe61d34`와 제공자 세션의 도구 결과로 양쪽을 대조했다.

## 변경

MCP는 작은 봉투의 `final_result`를 지우지 않는다. 큰 봉투는 공용
`ibl_envelope.diet_envelope`로 중간 실행 기록부터 요약하고 최종 값을 보존한다.
표시 축약은 `_trimmed`로 알린다. JSON이 그래도 한도를 넘으면 기존 스필 저장소에
보관해 `_spilled/ref`로 반환한다. 실패 여부와 가능한 최종 값 요약도 함께 실어,
잘린 JSON이나 앞 단계의 값을 최종 결과로 오인하지 않게 한다.
스필 작업은 MCP 이벤트 루프를 막지 않도록 워커 스레드에서 수행한다.

`take`의 구현·음수 계약은 바꾸지 않았다. 실제 보관 봉투를 수정된 전달부에
그대로 넣으면 3,934자로 줄어들며 마지막 4행과 날짜가 모두 보존된다.
AI·검색·보고서 실행을 다시 호출하지 않고 보관 결과만 재검증했다.

## 회귀

`test_agent_boundary_budget.py`에 작은 verbose 봉투, 턴 변수의 큰 원장에 대한
음수 take의 실제 실행→MCP 전달, 거대한 최종 값의 성공/실패별 스필 회수 검사를
추가했다. 기존 액션별 예산·호스트 상한·봉투·괄호 변수 분기 회귀도 함께 검사한다.

관련 회귀 34건 통과. 전체 backend는 3,196건 통과·2건 건너뜀·실패 0건이다.
최종 스필 경로의 원본 보존 보완 후 경계 회귀 10건도 재검증했다.
재로딩된 실제 MCP의 `execute_ibl{code:"",recover:"aa2eebe61d34"}`로 보관 티켓을
회수했을 때도 3,976자의 유효한 JSON에 같은 마지막 4행이 보존됐다(실행 재요청 없음).
