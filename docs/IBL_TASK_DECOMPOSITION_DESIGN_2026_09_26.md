# IBL 작업 분해와 결과 전달 설계

상태: 일부 적용. 의식의 분해 스케치와 실행자의 구체화 지침을 프롬프트에 반영했다.
실제 도구 교재 확장·계측 보완·A/B 훈련은 제안 상태이며, 비용 개선은 아직 검증하지 않았다.
근거: 2026-09-26 에피소드 4077~4080 검토. 판단 기준은
[IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md), 작성 문법은
[조합 가이드](../data/guides/ibl_composition.md), 훈련 절차는
[상상행동 가이드](../data/guides/imagination_action.md)를 따른다.

## 1. 결정: 분해의 단위와 반환을 먼저 가르친다

**복잡한 작업을 완료 조건이 있는 부분으로 나누고, 각 부분이 다음 판단에 필요한 값과
근거를 반환하게 한다. 알려진 절차는 한 프로그램으로 연결하고, 새 판단이 필요한 곳에서
모델이 결과를 확인한다.** 기존의 지역 함수·명시 값·조합·실패 계약으로 시작한다.

분해는 함수 수, 병렬 호출 수, 서브에이전트 수를 늘리는 목표가 아니다. 함수로 나눠도
매번 원문 전체를 반환하고 모델이 다음 한 줄을 지시하면 왕복과 맥락 비용은 남는다.
반대로 모든 탐색을 미리 알 수 있다고 가정한 거대 프로그램도 목표가 아니다.
핵심은 책임을 나눈 뒤 **정해진 부분을 다시 조합하여 실행**하는 데 있다.

첫 변경은 교재와 작성 지침으로 한정한다. 새 문법·전용 액션·작업별 엔진 분기·상시 평가
AI·자동 관용구 추출은 추가하지 않는다. 도구 반환이나 맥락 전달의 한계가 실제로 확인되면
해당 계약을 별도 개선한다.

지침 추가 커밋 `d306852f`는 13:39, 에피소드 4077 시작은 14:02다. 다만 파일의 선행
수정만으로 각 실행이 갱신된 프롬프트를 받았다고 단정하지 않는다. 다음 실험에서는 실제
조립된 프롬프트의 지문과 해당 지침 포함 여부를 확인한다.

가설은 **순수 계산에서 배운 분해를 불확실한 도구 탐색과 결과 전달에 옮기는 교육이 부족하다**는
것이다. 네 사례로 인과관계나 절감률을 입증한 것은 아니다. 실패 원인은 도구 계약·권한·
맥락 크기에도 있었고, 단순한 4080의 비용은 분해만으로 해결되지 않는다.
앞서 수정한 명백한 오류는 [수리 기록](EPISODES_4077_4080_REPAIRS_2026_09_26.md)에 분리돼 있다.

## 3. 작성 시 적용할 규칙

### 3.1 언제 나누고 언제 멈추는가

| 상황 | 작성 행동 |
| --- | --- |
| 한 도구로 요청을 충족 | 직접 실행하고 필요한 결과를 반환한다. |
| 입력별 반복·독립 수집·정해진 변환 | `each`·`&`·값 전달로 연결한다. 각각 별도 모델 턴을 만들지 않는다. |
| 입력·완료 조건·실패 처리 중 책임이 다른 부분 | 지역 함수로 구분하고 최상위에서 조합한다. 한 액션을 이름만 바꿔 감싸지는 않는다. |
| 스키마·권한·자료 위치가 불명 | 필요한 범위만 탐색한 뒤 계약을 정한다. 알려지지 않은 인자를 지어내지 않는다. |
| 탐색으로 방법이나 목표의 전제가 달라짐 | 확인된 사실·근거·미확인점을 반환하고 모델이 다음 절차를 구성한다. |
| 실행 중 정상적인 분기나 항목별 실패 | 알려진 조건이면 프로그램에서 처리한다. 부분 실패를 보존하고 필요한 부분만 복구한다. |
| 사람의 선택이나 추가 권한이 실제로 필요 | 그 경계에서 멈춘다. 함수로 감싸 권한을 우회하지 않는다. |

지역 함수는 한 실행 안의 정의다. 다음 실행까지 변수나 정의가 남는다고 가정하지 않는다.
다음 호출에는 필요한 값을 `inputs`로 명시한다. 실행 재개는 기존 동일 코드·입력의
`resume` 계약을 따르며, 상세를 읽으려고 부작용 있는 작업을 다시 실행하지 않는다.

### 3.2 부분 작업의 계약

코드를 쓰기 전에 다음을 정한다. 긴 계획서나 별도 모델 호출은 필요 없다. 아래 항목은
설계 질문이며 모든 함수에 강제할 새 반환 스키마나 공통 통화가 아니다.

| 질문 | 예: 관련 구현을 조사하는 부분 |
| --- | --- |
| 무엇을 받는가? | 저장소 범위, 찾을 심볼·질문, 관찰 대상 버전 |
| 무엇을 해결하는가? | 해당 심볼의 위치와 요청에 관련된 동작 확인 |
| 무엇을 돌려주는가? | 확인된 위치·관련 코드 범위·관찰 사실·미확인 대상 |
| 완료라고 할 조건은? | 요구한 대상마다 확인 근거 또는 확인 불가 사유가 있음 |
| 실패·효과는? | 읽기 전용, 접근 실패·검색 절단·불완전 범위를 그대로 보고 |
| 더 확인하려면? | 실제 파일 경로와 범위 또는 실행기가 발급한 결과 참조 |

반환은 다음 단계가 사용할 만큼 작되, 완전성 조건을 훼손하지 않는다. 임의로 앞 세 개만
남기고 전체 조사라고 부르지 않는다. 전체 목록·전체 본문이 사용자 산출물이라면 그것은
보존하고 전달한다. 줄 수나 문자 수의 일률적인 상한을 새 품질 기준으로 삼지 않는다.

의미 해석이 필요한 원문은 관련 범위를 모델이 직접 보게 한다. 프로그램이 검색 일치만으로
“구현이 맞다”는 판단을 만들어서는 안 된다. 정해진 필드 선택·집계에는 순수 연산을 쓰고,
의미 요약에 내부 AI가 필요하면 그 품질과 토큰도 비용에 포함한다.

근거 참조는 실제 읽을 수 있어야 한다. 경로·범위에는 가능하면 버전/지문을 함께 두고,
저장된 결과는 실제 `result_ref.read_args`·`next_read` 계약을 사용한다. 임의 문자열을
실행 가능한 참조로 가장하지 않는다. 참조만으로 필요한 정보가 부족하면 해당 범위를 읽는다.
현재 도구가 본문 전체를 먼저 가져와야 한다면 반환 필드를 줄여도 내부 수집 비용은 남는다.

## 4. 한메일 사례에 적용한 실행 경계

다음은 책임과 경계를 보여주는 설계이며 실행 가능한 IBL 코드나 고정 업무 워크플로가 아니다.

```text
요구와 현재 능력 확인
  ├─ 관련 어휘·등록·구현 위치 확인
  └─ 설정 존재·지원 인증 방식 확인 (비밀 값은 반환하지 않음)
  → 지원 여부, 확인된 근거, 결손, 가능한 다음 행동

[새 판단: 설정만 필요한가, 구현 변경이 필요한가?]

필요한 변경 작성 → 관련 검증 → 변경과 검증 근거 반환

[기존 변경 적용·권한 경계: 허용된 경로로 반영]

실제 연결 확인 → 요청 범위 조회 → 요청 필드 전달
  → 성공/실패, 요청 범위 충족 여부, 제목 등 산출물, 미확인점
```

등록·구현 위치 확인은 서로 독립인 읽기를 묶을 수 있다. 검색 결과에서 관련 심볼별 범위를
모으고 중복 범위를 합치는 과정도 정해진 절차라면 모델 왕복 없이 처리한다. 그러나 그 코드를
어떻게 고칠지 판단하는 단계는 탐색 결과를 본 뒤 구성한다. 초기부터 최종 패치를 추측하지 않는다.

구현 완료·검사 통과·실제 인증 성공·요청 메일 전달은 서로 다른 완료 조건이다. 중간 성공이
최종 성공으로 승격되지 않도록 각 결과를 구분한다. 이미 구현과 설정이 확인된 상태의
“최근 제목 10개”에는 위 절차를 다시 적용하지 않고 바로 조회한다.

다른 분야에서도 같은 원칙을 확인한다. 예를 들어 여러 자료 파일 비교는 파일별 읽기·정규화·
검증을 조합해 불일치와 출처를 반환한다. 누락 파일은 “차이 없음”으로 만들지 않는다.
이 예제를 한메일 구현과 함께 교재에 넣어 특정 업무 절차 암기를 피한다.

## 5. 구체적으로 바꿀 위치

### 적용: 의식이 구조를 스케치하고 실행자가 구체화

`data/common_prompts/consciousness_prompt.md`의 기존 `capability_focus.hint`에 복잡한
작업의 입력·부분 작업·반환·완료 조건, 의존관계와 새 판단 경계를 짧게 담도록 반영했다.
`imagined_ibl`은 계약을 아는 핵심 구간의 선택적 코드 초안으로 유지한다. 스케치를 작성하기
위한 별도 모델 호출·새 JSON 필드·고정 단계 수·최종 평가 의무는 추가하지 않았다.

실행자의 full/compact 프롬프트는 스케치를 실제 도구 계약과 지역 함수로 구체화하도록 한다.
의식이 없는 경로에서는 직접 분해한다. 스케치는 탐색 결과에 맞춰 다듬고, 목표·달성 기준은
보존하며 전제가 깨졌을 때 기존 재규정 경로를 쓴다. 단순 작업에는 분해를 강제하지 않는다.

초기 인계의 `prompt_builder.compile_user_command`와 재규정의 `reframe.render_for_executor`는
기존 hint 문자열을 전달하므로 실행기 변경이 필요 없다. 의식 역할 파일은 mtime 변경 시
다음 의식 호출에서 재적재되며, 별도 백엔드 재시작을 요구하지 않는다.

검증: 기존 `test_consciousness_prompt_cleanup`, `test_consciousness_output_routing_2026_09_07`,
`test_consciousness_json_relax`, `test_vocabulary_prompt`, `test_ibl_composition_teaching`을
실행해 통과했다. 실제 역할 로더의 감독·호환 프롬프트에 스케치 지침이 들어가는지, 예제 JSON의
hint가 초기 인계·재규정에서 보존되는지, full/compact 실행 프롬프트에 구체화 지침이
실리는지도 확인했다. 기존 교재 실행·크기 제한을 유지한다. 모델을 호출한 행동 실험이나
시간·토큰 절감 검증은 이번 적용에 포함하지 않았다.

### A. 상시 프롬프트: 기존 분해 문단 교체

`data/common_prompts/fragments/12_ibl_only.md`와 `12_ibl_compact.md`의 분해 문단을
다음 취지로 보완했다. 아래는 적용한 지침의 요지다.

> 복잡한 일은 완료 조건이 다른 부분으로 나누고 입력·반환·실패·효과를 정한다.
> 정해진 부분은 지역 함수나 맞는 관용구로 구현해 한 프로그램에서 조합한다.
> 반환에는 다음 판단에 필요한 값·근거·미확인점을 남기고, 상세는 실제 참조로 보존한다.
> 새 정보로 방법을 정해야 하는 경계에서 결과를 확인한다. 단순 조회는 직접 실행한다.

문법·재개·실패 설명과 겹치는 문구는 통합한다. 기존 프롬프트 예산을 늘려 지침을 누적하지
않으며, 대표 예제 교체 시 순수 함수 문법 교육을 가이드에 보존한다. 한 번의 모델 호출로
모든 작업을 끝내라는 압박이나 매번 분해 계획을 출력하라는 요구는 넣지 않는다.

### B. 가이드: 실제 도구 예제와 반례

`data/guides/ibl_composition.md`에 다음 학습 요소를 넣는다. 기존 예제와 중복되는 설명을
줄여 현재 크기 제한 안에 유지한다.

1. 코드 조사: 대상별 검색 → 관련 범위 읽기 → 중복 제거 → 위치·범위·미확인 대상 반환.
2. 자료 비교: 독립 수집 → 정규화·검증 → 불일치와 근거 반환. 빈 입력·누락·실패를 구분.
3. 단순 조회 반례: 이미 알려진 계약으로 요청을 충족하면 함수·탐색·계획을 추가하지 않음.

예제는 현재 도구 스키마로 컴파일·실행되는 코드를 작성한다. 아직 없는 도구 능력을 예제로
발명하지 않는다. 필요한 조합이 표현되지 않으면 공백을 기록하고 그 계약을 별도로 검토한다.
교재 시험 `backend/test_ibl_composition_teaching.py`에는 실제 파서·실행기와 합성 자료로
대상 누락, 중복 범위, 부분 실패, 다른 입력을 검사한다. 문자열에 `def`가 있는지만 검사하지 않는다.

프롬프트 전달은 `backend/cognition/prompt_composition.py`와 관련 실제 호출 경로에서
확인한다. 소스 파일 검사뿐 아니라 실행에 사용된 full/compact 프롬프트에서 중복 주입과
지침 누락이 없는지 확인한다. 관측을 위해 프롬프트 전문이나 비밀 값을 보고서에 복제하지 않는다.

### C. 비용 관측: 먼저 기존 증거로 오프라인 측정

`scripts/ibl_composition_cost_metrics.py`의 기존 수치 의미를 유지하면서 별도 버전의
보고 항목/모듈로 아래 측정을 보완한다. 기존 `ibl_composition_metrics.py`의 역사적
정규식 분류를 새로운 지역 함수의 의미 평가로 바꾸지 않는다.

| 지표 | 산출과 한계 |
| --- | --- |
| 실제 품질 | 사전에 정한 산출물·완료 조건·누락·근거·실패 보존 검사. 최종 답의 성공 주장만으로 판정하지 않음 |
| 시간 | 요청~사용 가능한 결과의 실제 경과 시간, 후처리 시간 별도. 병렬 도구 시간을 단순 합산하지 않음 |
| 토큰 | 주 실행·내부 AI·수리·검수·후처리를 포함한 원장 사용량. 입력·출력·캐시 분리, 중복 이벤트 제외 |
| 왕복 | 코드 실행·check·describe·read_result·모델 호출을 각각 집계 |
| 결과량 | 모델에 실제 전달된 문자 수와 내부 자료량 구분. 중첩 봉투의 실제 중복 전달도 별도 확인 |
| 재열람 | 같은 자료 지문·겹치는 범위의 읽기. 수정 뒤 재검증이나 필요한 후속 읽기를 낭비로 자동 판정하지 않음 |
| 작성 구조 | corpus 원문과 현재 parser/AST로 지역 정의·호출·조합 관찰. 읽지 못한 원문과 판본은 미측정으로 표기 |

`trajectory_event`, `ibl_code_corpus`, 실제 저장된 증거를 우선한다. episode 요약 로그의
잘린 텍스트만으로 실행 구조를 복원하지 않는다. 함수 수는 관찰치일 뿐 성과 점수가 아니다.
의미 있는 책임 분해와 불필요한 중간 왕복은 소수 표본을 사람이 검토할 수 있는 근거표로 남긴다.
매 실행마다 별도 평가 모델을 부르지 않는다. 증거가 없는 항목은 0이 아닌 미측정으로 남긴다.

## 6. 적용 순서와 통과 조건

### 1단계: 교재와 계측을 준비

먼저 현행 프롬프트를 기준선 A로 고정한다. 명백한 오류 수정은 A와 변경안 B 양쪽에 동일하게
포함한다. 과거 4077~4080과 새 실행의 단순 비교를 전후 실험으로 삼지 않는다.
프롬프트 교체안·실행 예제·관련 시험·오프라인 보고를 준비하고, 코드/프롬프트 지문을 기록한다.

교재 검증은 해당 pytest와 기존 프롬프트 크기·도달성 검사를 실행한다. backend를 바꾸면
저장소의 전체 회귀·번들 재생성 규약도 따른다. 문법 검사 통과는 실제 행동 개선과 별개다.

### 2단계: 작은 비교로 가설을 검사

첫 시험은 새 자연어 과제 세 개를 A/B에 한 번씩 실행하는 **3쌍**으로 제한한다.
복합 코드 조사, 부분 누락이 있는 자료 비교, 단순 조회를 각각 포함한다.
목적은 큰 효과를 주장하는 것이 아니라 지침 전달·측정·품질의 결함을 먼저 찾는 것이다.
시작 전에 동일한 쌍별 시간/토큰 상한을 정하고 초과 실행은 중단·실패로 기록한다.

모델·추론 설정·도구 버전·자료·권한·완료 조건·초기 대화 상태를 맞춘다. A/B 순서는 교대로
배치하고, 캐시 상태를 통제할 수 없으면 실제 캐시 사용량과 순서를 함께 기록한다. B가 A의
답이나 기록을 회상하지 않도록 기억 상태를 분리한다. 통제하지 못한 항목은 제한으로 명시한다.

평가 요청에는 함수 이름·IBL 코드·풀이·분해 지시를 주입하지 않는다. 저장된 정답 관용구가
없는 문제를 포함한다. 교재 원본과 입력만 바꾼 문제만으로 구성하지 않는다. 원래 시도와
사람이 도와준 재시도는 따로 기록한다.

시험은 실제 IndieBiz 진입 경로를 사용하고 출처를 기록한다. 파일 변경은 합성 자료와 격리
사본, 외부 전송은 실제 차단된 대역을 사용한다. `origin:training`만으로 격리됐다고 간주하지
않는다. 준비되지 않은 경계는 미검증으로 남기며 실제 계정 비밀을 시험 자료로 복제하지 않는다.

### 3단계: 새 과제로 전이와 비용을 확인

첫 시험에서 품질·계측 문제가 없으면, 교재 작성에 쓰지 않은 9개 과제로 확대한다.
개발 조사·자료 처리·단순 조회 각 세 개에 입력 규모 변화와 부분 실패를 섞는다.
각 과제를 A/B 두 번씩 실행한다. 이는 제한된 후속 실험이며 대규모 통계적 확증으로 부르지 않는다.

채택 판단은 다음 순서다.

1. 필수 산출물·완료 조건을 만족하고, 누락 은폐·잘못된 외부 효과 등 중대한 품질 퇴행이 없어야 한다.
2. 단순 과제에 강제 분해·불필요한 추가 탐색이 생겼는지 작업별로 확인한다.
3. 쌍별 시간·전체 토큰 변화와 반복 간 변동을 공개한다. 복합 과제의 중앙값뿐 아니라 각 작업과
   단순 과제의 퇴행도 본다. 품질을 유지하며 시간과 토큰이 함께 줄어야 전체 목적의 개선으로 채택한다.
4. 차이가 실행 변동과 구별되지 않으면 결론을 보류한다. 한 축만 좋아지면 부분 성과로 기록한다.

다음 행동도 관측에 따라 나눈다. 작성 행동이 안 바뀌면 전달 경로·예제부터 재검토한다.
분해는 됐는데 반환이 크면 해당 도구의 선택 조회/반환 계약을 검토한다. 왕복은 줄었는데
전체 비용이 안 줄면 상시 맥락·내부 AI·후처리의 비용을 따로 개선한다.
결과를 보기 전에 대규모 프롬프트 축소나 실행기 변경을 함께 섞지 않는다.

## 7. 관용구로 남길 시점

지역 함수는 작업을 해결하기 위해 먼저 작성한다. 성공했다고 자동으로 이름 붙여 등록하지 않는다.
다른 입력에서도 계약이 성립하고 다시 조합할 가치가 확인된 것만 기존 수동 선정 경로로 남긴다.
등록할 때 입력·반환·적용 조건·완료 범위·부작용·실패·검증 사례를 함께 보존한다.

`좁혀서읽기`처럼 제한된 범위를 빠르게 읽는 관용구는 그 용도에서 유효할 수 있다.
전체 심볼 조사에 맞지 않으면 다른 부품을 조합하거나 지역 정의를 작성한다. 특정 실패 사례를
덮기 위해 업무 전용 관용구를 무조건 하나 더 늘리는 방식은 취하지 않는다.

이 설계의 첫 산출물은 **작은 프롬프트 교체, 실제 도구 조합 교재, 품질과 비용 비교표**다.
성공의 증거는 처음 보는 작업에서 완전한 결과를 더 적은 시간과 전체 토큰으로 얻는 것이다.
