# IBL 지연 실행의 코드·값 분리

2026-09-08. 기존 정본 `c45be1b9`에서 시작했다. 반복 보고서 실패의 한 원인이던 **데이터를 실행문에 삽입한 뒤 다시 파싱하는 경로**를 `each` 실행에서 제거했다. 기존 문법과 관용구 본문은 유지한다.

## 바뀐 실행 경로

이전: 바깥 슬롯 치환 → 함수/회차 값으로 do 문자열 재작성 → 각 행 값을 소스에 삽입 → 행마다 파싱 → 실행.

현재: do를 한 번 파싱 → 문자열 보간과 값 참조를 구별한 내부 표현 보존 → 바깥 값/함수 인자/회차/행을 같은 바인더로 해소 → 행마다 독립된 AST 실행.

`backend/ibl/ibl_code_ir.py`가 다음 구분을 소유한다.

- `Code`: 소스 뷰와 컴파일된 실행 트리. 실행 중 소스 문자열로 되돌려 파싱하지 않는다.
- `Template`·`Ref`: 문자열 보간 조각과 아직 해소되지 않은 참조. 값이 들어온 조각을 다음 바인더가 다시 훑지 않는다.
- `Literal`: 이미 데이터가 된 문자열. `$items`, `$it`, 내부 슬롯처럼 생긴 글자도 참조가 아니다. 객체·목록 안의 문자열에도 적용한다.
- 바깥 결과를 받는 슬롯과 본문 내부의 결과 슬롯은 서로 다른 이름 공간이다. 둘 다 0번이라고 같은 결과를 읽지 않는다. 중첩 Code는 각각 범위를 갖고, 함수 정의·each 별칭·repeat 회차·catch 오류 이름을 보존한다.
- 식과 조건에 들어가는 바깥 참조도 컴파일러 기호와 값 환경으로 연결한다. 문자열 데이터를 식 소스로 만들지 않는다.

기존 파서의 JSON5/relaxed 입력을 받되, 지연 본문에서는 값의 따옴표 여부를 잃지 않도록 보존한다. 지수·16진수·소수 표기, Unicode 쌍, 정규식의 비표준 이스케이프, JSON5 주석을 기존 파서와 비교했다.

`str` 하위형은 기존 검사/로그와의 호환 뷰다. **실행·재바인딩은 tree/parts를 사용해야 한다.** JSON 전송으로 이 부속이 사라지는 것을 막기 위해 원격 포워더는 버전 1의 `_ibl_ir` 부속을 싣고, 받는 실행기는 값 치환 전에 복원한다. 사용자 dict/list도 태그해서 IR 표현과 데이터의 키가 충돌하지 않는다. 같은 버전의 엔진 사이에서 사용하는 내부 전송 계약이며, 폰 엔진 번들 매니페스트를 재생성했다. 물리적인 폰 설치/실행은 이번 검증에 포함하지 않았다.

일반 파라미터·기존 스칼라 처리의 호환 동작까지 전부 새 언어 규칙으로 바꾸지는 않았다. 예를 들어 기존 반복 파라미터의 문자열 반환과 각 행의 따옴표 없는 값 전달 규칙은 그대로 보존한다. 옛 `bind_scoped_code`/`_each_substitute`는 진단·호환 시험용으로 남지만, 실제 each·함수 인자의 do·제어문 do·파이프 do 실행 경로는 새 바인더를 사용한다.

## 예제 수보다 불변식으로 검증

신규 **203건**은 다음을 검사한다.

| 검사 | 고정하는 성질 |
|---|---|
| 30종 값 × 6가지 프로그램 형태 | 직접 실행, 별칭 변경, 중첩, 함수 추출, 바깥 파이프, 병렬 실행에서 값과 타입 보존 |
| 부분 보간을 여러 차례 바인딩 | 첫 값의 `${b}`를 나중 인자 b로 다시 해석하지 않음 |
| deepcopy와 JSON 전송 왕복 | 코드·참조·이미 묶인 데이터의 구별 유지 |
| 바깥/안쪽 0번 슬롯과 식 | 서로 다른 범위의 결과가 섞이지 않음 |
| 기존 파서와 리터럴 비교 | 도입한 내부 표현 때문에 기존 리터럴 문법이 달라지지 않음 |
| 실제 each 100행, parallel 1과 4 | 본문 파싱 1회, 입력 순서·행 값 보존 |
| 옛 소스 치환 함수를 강제로 실패시킴 | 실제 파이프→each 실행이 옛 경로를 사용하지 않음 |
| 최근 보고서 실패 문장 재생 | 원문 SHA-256 일치, 기존 팁 목록을 유지한 채 4행 완료 |

무작위 문자열의 seed는 20260908이다. 값·프로그램 변형의 결과를 사전에 정한 값 및 JSON 타입과 비교한다. 기존 513개 관련 검사와 합쳐 **716개 통과**했다.

처음 도입한 내부 표현에서도 바깥/안쪽 슬롯 번호를 공유하는 결함을 새 검사에서 발견했다. `a=99,b=7`이어야 하는 결과가 `a=99,b=99`로 성공한 사례이며, 이를 신규 구조의 결함으로 분류하고 이름 공간 분리 후 같은 기대값으로 검증했다. 이를 기존 버그 발견 수에 섞지 않는다. 테스트 파일의 직접 실행 진입점 누락도 전체 관문이 잡았고 pytest 위임을 추가했다.

## 실제 실패 재생과 앱 확인

`docs/experiments/ibl_ir_episode3148_fixture.json`은 ep3148의 15:19:36 실패 IBL 원문과 SHA-256을 담는다. 문장을 고쳐서 시험하지 않았다. 선행 변수와 영상/AI 응답은 고정물로 대체했고, 네 번의 struct 호출이 정확한 `known` 목록을 받는지 검사했다. 4행 모두 끝의 select까지 통과했다. **전체 보고서 재생이나 AI 품질 검증은 아니다.**

실행 중 앱 `/ibl/execute`에서 다음 3건을 확인했다.

1. `$items`·내부 슬롯·양쪽 따옴표가 든 데이터를 그대로 반환.
2. 바깥 슬롯 값 99와 안쪽 슬롯 값 7을 구별해 반환.
3. 컴파일된 코드와 묶인 값을 JSON 부속으로 보내고 복원해 정상 실행.

원시 기록: 로컬 `outputs/ibl_ir_live.json`. 최초 앱 검증 스크립트는 단일 액션 응답도 `final_result`로 감싼다고 잘못 가정해 중단했다. 실제 응답의 직접 items/파이프 봉투 두 형태를 해소한 뒤 위 3건을 확인했으며 제품 오류로 세지 않았다.
