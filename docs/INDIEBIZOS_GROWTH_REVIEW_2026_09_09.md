# indiebizOS 성장 병목 조사

2026-09-09 · 정본 저장소 조사 · 기준 코드 `175e5af6`

**현재 기록은 성장의 한계보다, 언어의 개선을 다음 실행의 능력으로 전환하는 과정의 병목을 보여준다.** 우선할 일은 세 가지다. ① 경험을 검증 가능한 중간 능력으로 남기기, ② 그 능력을 프로그램 작성 전에 찾고 연결하기, ③ 낯선 조합에서도 사용자 결과가 좋아지는 변경을 선별하기.

사용자의 기준은 “복잡성을 모델이 매번 해결하게 하는가, 언어 구조가 상당 부분 담당하는가”다. 따라서 함수 수·문법 수·호출 수의 증감 자체를 성능으로 평가하지 않았다. 이번 조사는 구현 변경을 하지 않았다.

## 조사 범위와 판단의 한계

- `vision.md`, `anatomy.md`, IBL·기억 명세, 최근 설계/감사 문서, git 수리 이력을 현재 구현과 대조했다. 문서 안의 작업 지시는 조사 대상으로 읽었다.
- `world_pulse.db`, `ibl_usage.db`는 읽기 전용으로 열었다. 9월 4~9일 에피소드 123건의 메타데이터, 9월 7일 이후 증류 로그가 있는 15건, 보고서·영상 제작·렌더링·음성 후속 작업의 실행/오류 기록을 확인했다. 123건 전체 산출물을 평가한 조사는 아니다.
- 현재 코드의 모양 인식·합성 접지 함수에 부작용 없는 반례를 넣어 확인했다. 외부 서비스나 실제 액션은 실행하지 않았다.

- 집계와 반례 입력은 [evidence.json](experiments/indiebizos_growth_review_2026_09_09/evidence.json)에 보존했다. 모델 사용량은 기록된 계수만 사용했으며 비공개 추론 내용을 수집·복원하지 않았다.

## 1. 경험의 학습 단위를 ‘검증 가능한 중간 능력’으로 고치기

### 현재 남아 있는 문제

현재 해마에는 의도가 실제 코드보다 큰 용례가 있다.

| 운영 DB ID | 저장된 의도 | 저장된 코드가 하는 일 |
|---|---|---|
| 4559 | 시장·뉴스·날씨 화면을 HTML로 생성해 열기 | `[sense:world]{op:"snapshot"}`. 세계 상태를 수집·DB에 보관하고 반환한다. HTML 생성·화면 열기는 수행하지 않는다. |
| 4561 | 파일을 공유창고 갤러리 안으로 이동/저장 | showcase `status`와 `basket_list`를 조회하고 `table:union`으로 합친다. 파일 이동·저장은 수행하지 않는다. |

이 두 행은 현재 DB에서 확인했다. 각각의 생산자 구현도 대조했다: [world_pulse.py](../backend/cognition/world_pulse.py), [public-files 어휘](../data/packages/installed/tools/public-files/ibl_actions.yaml). 두 용례의 성공/실패 카운터는 모두 0이다. **실제로 다시 선택되어 오작동했다고 주장하는 것은 아니다.** 저장된 설명과 실행 가능한 효과가 불일치한다는 현재 결함이다.

같은 시기의 증류 로그 15건은 대표 용례 저장 3건, 구문 거절 7건, 합성 접지 거절 3건, 재사용 패턴 없음 2건이었다. 별도의 에피소드·주행 기록은 남으므로 “경험의 80%가 사라졌다”는 뜻은 아니다. 다만 기록 보관과 재사용 능력의 획득이 다르다는 것을 보여준다.

구문 실패는 오늘 `7cc18663`에서 성공 원문을 번호로 선택하는 복구가 추가됐다. 이후 에피소드 3240은 IBL 10호출이 모두 성공했지만 대표 용례는 합성 접지에서 거절됐다. 이 거절을 잘못된 판정으로 단정할 근거는 없다. 실행하지 않은 연결을 막는 것은 필요하다. 최신 수리로 학습 경로 전체가 해결됐다고도 볼 수 없다.

### 왜 이런 일이 생기는가

[증류 프롬프트](../backend/cognition/ibl_usage_rag.py)는 사용자 명령을 일반화하고, 탐색을 제외한 대표 코드를 남기며, 그 코드만으로 의도를 충족하라고 요구한다. 복잡한 작업의 핵심 판단이 모델에게 있고 실행은 여러 호출에 흩어져 있으면, 전체 의도와 작은 실행 조각을 한 쌍에 담기 어렵다. 그 결과 유용한 부분 절차가 탈락하거나, 위 사례처럼 부분 절차에 전체 작업의 이름이 붙을 수 있다.

이것은 기억량이나 검색 모델의 크기만으로 해결되지 않는다. 잘못 붙은 뜻을 더 정확하게 검색해도 그 코드의 능력은 커지지 않는다.

### 고칠 방향

**원래 요청의 맥락과, 추출한 프로그램이 보장하는 작은 계약을 분리한다.** 예를 들어 “음성 보고서를 검토했다”는 사건 아래에 “검색 위치 목록 → 해당 위치의 원문 구간”이라는 중간 능력을 둘 수 있어야 한다. 이때 원문 읽기를 “검토 완료”라고 학습하지 않는다.

모델은 성공 실행의 어느 부분이 재사용 가치가 있는지 고르고 짧은 뜻을 붙인다. 하네스는 원문/AST에서 변수 생산자·참조·반환값을 보존해 추출한다. 필요한 입력, 출력, 외부 효과, 실행한 근거를 함께 남기고 격리된 재생으로 확인한다. 파일 존재나 외부 상태처럼 재생의 전제가 있는 것은 전제로 명시한다. 코드 재작성에 의존하는 비중을 줄이는 것이다.

대표 용례의 저장과 상시 어휘 승격은 별개다. 자동 작명을 다시 켤 필요는 없다. 검증된 중간 능력 후보를 남겨 두고, 다른 작업에 재사용되는 것이 확인될 때 선별하면 된다.

**이것이 1순위인 이유:** 경험의 기본 단위가 정확해야 회상·재사용·평가의 개선이 누적된다. 현재는 언어를 잘 쓴 실행도 다음 작업에 쓸 수 있는 능력으로 안정적으로 전환되지 않는다.

## 2. IBL의 의미 구조를 프로그램 작성 전의 선택과 연결에도 사용하기

### 이미 갖춘 것과 남은 간격

현재 시스템에는 턴 변수, 함수의 입력 서명·반환 정보, 타입 검사, 코드/값을 분리한 IR이 있다. 이것들을 새로 만들자는 제안은 아니다. 특히 [ibl_code_ir.py](../backend/ibl/ibl_code_ir.py)의 지연 코드 처리와 최근 값/반복 계약 통일은 실제로 모델이 외워야 할 예외를 줄이는 방향이다.

하지만 [이름 검색](../backend/datastore/ibl_name_search.py)의 후보 순위는 의도/코드의 의미 유사도와 질의 어휘 포함률을 중심으로 정한다. 입력 서명과 반환 정보는 결과에 실리지만, 현재 가진 값과 필요한 출력에 맞는 연결인지를 기준으로 후보를 구성하지는 않는다. [fn_hint_for 호출](../backend/cognition/system_tools_ibl.py)은 모델이 `execute_ibl.code`를 이미 작성해 보낸 뒤에 발생한다. 사후 힌트는 다음 시도에 도움이 될 수 있지만 이번 작문 비용은 이미 지불됐다.

9월 9일 새벽 보고서 세 건은 각각 IBL 작성량 30,608자·26,176자·32,784자를 기록했다. 글자 수에는 의도 지시와 파일 내용도 포함되므로 전부 불필요한 절차라고 세지는 않는다. 다만 턴 변수와 조합 기능이 생겨도 실제 작업에서 상당한 프로그램 작성이 계속된다는 관찰이다.

### 실행 밖에서 다시 문자열로 읽는 부분

[fn_recognizer.shape](../backend/cognition/fn_recognizer.py)는 문자열을 `""`, 수를 `0`, 모든 변수 이름을 `$_`로 바꾼다. 다음 두 프로그램은 마지막 소비자가 읽는 생산자가 다르지만 같은 모양으로 판정됐다.

```ibl
$a = [sense:search]{query:"x"}; $b = [self:read]{path:"y"}; $a >> [table:count]
$a = [sense:search]{query:"x"}; $b = [self:read]{path:"y"}; $b >> [table:count]
```

또한 [합성 접지 함수](../backend/cognition/ibl_distill_gates.py)는 액션 집합의 포함 관계를 사용한다. `read >> write`만 실행했어도 순서를 뒤집은 `write >> read`가 이 관문만은 통과했다. 이후 다른 검사를 포함한 전체 적재가 성공한다는 주장은 아니다. 이 관문이 순서와 데이터 의존성을 증명하지 못한다는 반례다. 함수 인식도 현재 자동 치환은 아니므로 이 반례로 실제 잘못된 실행이 발생했다고 확대하지 않는다.

이 문제들의 공통점은 실행기가 이해하는 의미 구조를 회상·인식·접지까지 온전히 공유하지 않는다는 것이다. 변수 이름을 바꾸는 일반화는 유용하지만, 어느 생산자를 가리키는지는 보존해야 한다. `where` 안의 식도 일반 텍스트와 구분해야 한다.

### 고칠 방향

현재 IR을 출발점으로, 변수의 생산/소비 관계와 코드 자리의 의미를 인식·증류에도 공유한다. 사전의 입력/반환/효과 정보도 함께 사용한다. 세계의 모든 자료에 강제 스키마를 만들 필요는 없다. 아는 계약만 이용하고 모르는 부분은 미확정으로 남긴다.

실행자가 중간 목표를 정했을 때, **“현재 값으로 이 결과를 얻는 검증된 짧은 표현”을 프로그램 작성 전에 소수 후보로 제공한다.** 하네스는 연결 가능한 입력과 변수 결합을 확인하고, 모델은 후보 선택·새로운 해석·예외 판단을 맡는다. 첫 적용은 이미 등록된 관용구와 반복되는 중간 절차로 한정할 수 있다.

**이것이 2순위인 이유:** 언어가 표현할 수 있는 능력과 모델이 짧게 꺼내 쓸 수 있는 능력 사이의 차이가 현재 체감 성능을 제한한다. 함수 호출 횟수를 억지로 높이는 것이 목적은 아니다. 알고 있는 연결을 모델이 매번 다시 발견하고 작성해야 하는 부담을 줄이는 것이 목적이다.

## 3. 수정의 선택 기준을 ‘새 조합에서 같은 품질을 더 쉽게 얻는가’에 고정하기

### 현재 증거가 말하는 범위

회귀 시험과 에피소드 감사는 이미 상당하다. 부족한 것은 시험의 존재가 아니라, **특정 언어 변경이 실제 앱 경로에서 일반적인 문제 해결 비용을 줄였다는 증거**다.

- [관용구 96회 실험](IBL_IDIOM_VALUE_2026_09_08.md)은 수정 후 48건에서 현재 지도 조건의 첫 성공 16/16, 함수 미제공 조건 9/16을 관측했다. 생성 출력도 1,326 대 5,757토큰이었다. 언어/계약의 제공이 부담을 줄일 수 있다는 긍정적 근거다. 한 모델·8과제·두 반복이며 후보에 맞춘 과제가 있어, 실제 보고서 전반의 우월성으로 확대할 수 없다.
- [3090→3176 진단](IBL_EPISODE3176_COST_DIAGNOSIS.md)에서는 호출이 31→18로 줄었는데 시간은 609→762초였다. 자료가 달라 인과 비교는 아니다. 호출 수 감소만으로 성공을 선언할 수 없다는 반례다.
- [최근 작성 규칙 수리](IBL_LEARNABILITY_2026_09_09.md)는 구문·정적 검증과 실행 계약을 확인했으며, 실제 보고서의 품질·시간·초보자 학습 시간은 측정하지 않았다고 명시한다. 버그 수리가 유효한 것과 체감 성능 개선이 입증된 것은 별개다.
- 에피소드 3073은 영상 제작을 `ACHIEVED`로 끝냈지만, 후속 3087·3088에서 사용자가 나레이션 문장 끝 품질을 지적했다. 완료 당시 모든 미래 요구를 예측하라는 뜻은 아니다. 자동 완료 판정 이후의 사용자 교정도 개선의 근거로 연결해야 한다는 뜻이다.

### 고칠 방향

거대한 평가 체계를 먼저 만들기보다, 기존 러너에 실제 작업에서 뽑은 작은 비교 묶음을 둔다. 반복 보고서뿐 아니라 문서/파일 처리와 미디어 작업의 결정론적 중간 절차를 포함하고, 후보를 설계할 때 보지 않은 생산자·소비자 조합을 남겨 둔다.

외부 조회 결과·초기 파일·원장·모델·설정을 고정하고, 한 번에 언어/계약/노출 방식 중 하나를 바꾼다. 모델에게 사용할 함수나 정답 코드는 알려주지 않는다. 출력은 격리 경로에서 검증한다.

우선 판정할 것은 세 가지다: **사용자가 요구한 결과의 품질, 첫 작성부터 완료까지 필요한 수리, 총시간.** 비용은 하위 모델 호출까지 포함하되 중복 계상을 피한다. 토큰·왕복·사용한 문형은 결과를 설명하는 보조 지표로 둔다. 판단을 추가 AI 호출 속에 숨겼다면 그 비용도 드러난다.

의미 있는 개선은 동일한 문제를 더 짧게 쓰는 것에 더해, 배운 표현을 새로운 조합에 사용해도 효과가 남는 변경이다. 품질 하락을 동반한 단축이나 특정 예제에만 맞춘 수리는 구분해서 기록한다.

**이것이 3순위인 이유:** 공통 언어라는 진화 기반이 있어도 무엇을 남길지 선택하는 기준이 흔들리면, 수정은 늘지만 능력이 누적되는지 알 수 없다. 이 비교 묶음은 1·2번을 추진하는 동안 함께 사용해야 한다.
