# 응답 지연 수리계획

2026-11-05 · 상태: 설계 완료, 구현 전

목표는 **결과 품질과 연구의 연속성을 유지하면서 실제 완료 시간과 전체 토큰 소비를 줄이는 것**이다. 먼저 작은 연구계획 수정에 붙는 별도 작성 호출과, 이미 가진 근거를 전달하지 못해 발생하는 재평가를 줄인다. 중간 결과 표시, 짧은 판단의 대기 한도, CLI 종료 비용은 각각 별도 계약으로 수리한다.

근거는 [응답 지연 조사 보고서](../outputs/latency_research_20261105/report.md)와 정본 코드 `accdd681261f251ccbf59a64a5151c1efd28b57a`다. 이 계획은 제품 코드·모델 설정·운영 데이터를 변경하지 않는다. 목적과 범위는 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md), 검증 절차는 [회귀 검사](REGRESSION_TESTING.md)를 따른다.

새 IBL 어휘, 별도 감독 모델, 상주 감시 서비스, 추가 목표 DB는 만들지 않는다. 모델·추론 강도·어휘 노출·회상 정책을 낮추는 방식도 이번 범위에 넣지 않는다. 업무 이름·문장 길이·키워드로 연구 판단을 우회하지 않는다.

이미 존재하는 `keep` 경로, 연구계획 판본 저장, 평가 입력 예산·원문 회수, 공개 대기열, CLI 무응답 감시를 확장한다. 새 구조를 만들 때는 대체할 기존 분기를 함께 제거한다. 연구계획을 추가 모델로 검토하는 실험은 [110회차에서 운영 기본 적용이 기각](experiments/long_sentence_imagination/round_110/report.md)됐으므로 지연 수리의 기본 단계로 다시 도입하지 않는다.

## 2 실행 순서와 의존 관계

| 단계 | 작업 | 완료 조건 | 선행 조건 |
| --- | --- | --- | --- |
| R0 | 기존 사건 원장에 부족한 시간 경계와 대조 조건 연결 | 호출·화면·종료·후처리를 구분할 수 있음 | 없음. R1·R2 구현을 장기 측정 대기로 막지 않음 |
| R1 | 연구계획의 유지·부분 수정·전체 개정 구분 | 작은 수정에서 별도 계획 작성 없이 유효한 새 판본 전달 | R0의 최소 관측 |
| R2 | 첫 평가 전 기준별 필수 근거 배분 | 예산 안에 있는 필수 본문을 첫 평가에 전달 | R1과 독립적으로 구현 가능 |
| R3 | 검증된 부분 결과의 화면 전달 | 부분 결과를 보여도 최종 승인·공개 계약이 유지됨 | R2의 근거·판본 계약 재사용 |
| R4 | 분류·재개 판단의 역할별 전체 대기 한도 | 시간초과 뒤 실행·권한 확대·중복 호출이 없음 | R0. R1·R2와 독립 |
| R5 | CLI 종료 비용과 역할 문맥 중복 수리 | 완료·오류·효과 회수 보존, 역할 격리 보존 | R0의 경계 관측, R1·R2 뒤 잔여 비용 확인 |
| R6 | 통합 회귀·활성 확인·품질과 비용 대조 | 구현 상태와 관측된 효과를 구분해 기록 | 각 단계의 계약 검사 |

우선 구현 묶음은 **R0의 최소 계측 → R1 → R2**다. R4는 이 묶음과 독립된 변경으로 먼저 반영할 수 있다. R3는 화면과 공개 경계를 건드리므로 근거 계약 뒤에 둔다. R5의 성능 처방은 실제 정리 구간이 분해된 뒤 결정한다. 이는 수리 단계의 의존 관계이며 매 사용자 요청에 추가할 실행 절차가 아니다.

## 3 R0 기존 관측의 경계 보강

기존 `episode_logger`, `model.input`, `model.usage`, `evaluation.input_budget`와 실행 신원을 사용한다. 원문 프롬프트를 새 로그에 복제하거나 별도 계측 저장소를 만들지 않는다.

기록할 경계는 요청 접수, 회상·분류 종료, 최초 의식 판단, 계획 유지·부분 수정·전체 작성, 실행의 첫 본문, 평가 시작·종료, 승인 본문 전달, 서버 종료다. CLI에는 `turn.completed`, stdout EOF, 프로세스 종료, 효과·티켓 회수 종료를 같은 호출 ID로 연결한다. 재시도와 하위 호출에는 부모 ID를 붙여 중첩 시간을 합산하지 않는다.

화면은 메시지 ID·판본을 기준으로 첫 부분 결과와 최종 승인 본문이 실제 렌더된 시점을 기록한다. 브라우저 내부 경과는 단조 시계로 재고, 서버 시계와 직접 빼지 않는다. 클라이언트 접수부터 표시까지의 값과 서버 처리 시간을 각각 보고한다. 진행 문구·생각·빈 토큰은 유의미한 결과로 세지 않는다.

실행의 실제 적재 판본과 디스크 HEAD를 구분한다. 모델·강도·CLI 버전·새 세션/재개·캐시 입력·자료 판본·자료실 모드·사용자 중간 개입을 남긴다. 서비스 등급·서버 부하처럼 관측할 수 없는 조건은 미확인으로 둔다. 계측 오류가 제품 응답을 막지 않으며 원장 작성 비용도 확인한다.

## 4 R1 작은 연구계획 수정의 별도 호출 제거

### 현재 책임

`backend/cognition/research_runner.py`는 일반 연구 발언을 THINK로 보낸다. `research_planning.py`의 `topic_prompt`, `validate_topic_choice`, `prepare`는 `keep/revise`를 사용한다. `keep`은 현재 파일을 다시 읽고 새 계획 호출을 하지 않지만, `revise`는 최초 판단 뒤 별도 작성 호출을 한다. `backend/datastore/research_plans.py`는 활성 실행·프로젝트 epoch·대화 revision을 검사해 새 판본을 연결한다.

### 변경 계약

1. 기존 최초 의식 판단에서 이번 응답 범위와 지속 계획의 수정 범위를 함께 정한다. 계획 선택을 `keep`, `patch`, `revise`로 확장한다. **THINK 라우팅 자체는 이 단계에서 유지한다.** 작은 발언을 위한 새 분류 모델은 붙이지 않는다.
2. 설명·논의가 기존 목적·방법을 바꾸지 않으면 `keep`을 선택한다. 사용자 관점·질문 기록을 갱신해야 한다는 사실만으로 계획 전체 개정을 요구하지 않는다. 관점·질문은 기존 저장소에서 각각 갱신한다.
3. 좁은 정정은 최초 판단의 구조화 출력에 변경 이유, 기반 계획 지문, 변경할 정확한 원문 구간과 대체 본문을 함께 반환한다. 범위는 동일 판본의 Unicode 문자 좌표와 예상 원문으로 확인한다. 유사 문자열 추정 치환은 하지 않는다. 새 필드는 의미 판단을 위한 출력 계약이며 IBL 어휘가 아니다.
4. 하네스는 기반 파일을 다시 읽고 지문·원문 구간·중첩 여부를 검사한다. 변경하지 않은 바이트를 보존하여 새 본문을 만들고 기존 `persist`와 `ResearchPlans.bind`로 새 판본을 저장한다. 기존 파일을 제자리에서 덮어쓰지 않는다.
5. DB revision만으로 실행자의 파일 진행 갱신을 감지할 수 없으므로 **본문 지문도** 연결 직전 검증한다. 프로젝트·대화·활성 run·epoch·revision과 함께 확인하고, 같은 계획의 쓰기 소유 경계에서 검사·게시를 직렬화한다. 경쟁이 나면 기존 유효 판본을 보존하고 최신 상태로 기존 오류 복구 경로에 넘긴다. 무한 자동 재판단은 만들지 않는다.
6. 최초 계획, 연구 목적·방법의 큰 변경, 여러 질문의 연결을 다시 설계해야 하는 경우는 기존 `revise`를 사용한다. `patch`의 의미·형식·기반 판본을 검증하지 못하면 적용하지 않는다. 단순 형식 실패는 기존 한정 보완을 사용하고, 전체 재설계가 필요하면 명시적으로 `revise`로 넘긴다.

계획이 없는 첫 발언은 기존 최초 계획 계약을 유지한다. 처음부터 별도 계획 호출을 없애는 통합은 이 단계의 성과에 넣지 않는다. 명시적 심층연구, 저장 자료만 모드, 사용자 정정, 수리 재개, 기준 소유권, 계획 실패 시 조사 차단은 유지한다. 부분 수정 성공 뒤에도 최종평가는 이번 턴의 명시된 기준을 검증한다.

### 인수 검사

`backend/test_research_planning.py`, `backend/test_research_plans.py`와 실제 소비자 검사에 다음을 추가한다.

- 계획 유지: 별도 작성 호출 0회, 새 판본 0개, 최신 진행 본문 전달.
- 유효한 부분 수정: 별도 작성 호출 0회, 새 판본 1개, 이전 경로 연결, 범위 밖 바이트와 질문 ID·근거 보존.
- 목표·방법의 큰 변경과 최초 연구: 전체 계획 작성·저장·실행 전달 유지.
- 기반 지문 변경·겹치는 수정·대화 종료·삭제·취소·epoch 변경: 잘못된 판본 게시 및 조사 시작 없음.
- 동일한 수정 재전달: 중복 판본 생성이나 원문 훼손 없음. 이미 적용됐는지 판본으로 확인.
- 관점 토론·정정·추가 조사·명시적 심층연구를 서로 다른 주제로 실행하여 판단 품질 확인.

## 5 R2 첫 평가에 필요한 근거를 먼저 전달

### 현재 책임

`backend/cognition/evaluation_input.py`의 `EvaluationPrompt.prepare_request`는 회수 근거·제출물·인용 순서로 예산을 배분한다. `record`에는 이미 `criterion_ids`, 원문 참조·판본·범위가 있다. `evaluation_evidence.py`와 감독의 평가 패킷 조립을 연결하고, `conscious_supervisor.py`의 기존 회수·재평가 루프는 유지한다.

### 변경 계약

1. 명시된 기준 ID에 대해 실행 중 확보한 제출물·저장 결과의 원문 참조, 판본, 필요한 구간, 영수증을 기존 패킷에 연결한다. 모델의 근거 지정은 선택 힌트이며 충족 판정이나 저장 성공의 증명이 아니다.
2. 첫 평가 준비에서 이미 확보한 근거의 필요한 본문을 같은 턴의 불변 저장소에서 회수한다. 사용자 관점·연구 질문의 저장을 확인하는 기준에는 해당 결과의 실본문과 실제 저장 판본을 함께 전달한다. 저장 성공 문구만으로 본문을 대신하지 않는다.
3. 예산 배분은 기존 명시 회수 요청을 보존하면서 **기준별 필수 구간 → 나머지 제출물·인용 → 보조 문맥** 순서로 고친다. 기준에 연결된 구조화 결과가 전부 아니면 모두 생략되는 문제도 필요한 필드의 원문 좌표·판본을 유지하는 기존 투영 계약으로 다룬다.
4. 생략된 구간·누락된 기준 연결을 manifest에 남긴다. 지문이 같아도 역할·영수증·기준 연결이 다르면 무조건 합치지 않는다. 참조 목록이 있다는 사실을 본문 열람으로 세지 않는다.
5. 필수 근거가 입력 한도를 넘으면 총량 검사를 지킨다. 회수 가능한 근거는 기존 한정 회수 경로로 보내고, 제공할 수 없는 근거는 UNKNOWN 사유로 보존한다. 모든 원문을 강제로 넣거나 요약을 원문으로 가장하지 않는다.

별도 근거 선택 모델을 추가하지 않는다. 사용자 원문과 criteria의 권위는 유지하며 평가자가 새로운 완료 기준을 만들지 못하게 한다. 기준·응답·산출물 판본 변경 검사는 계속 적용한다.

### 인수 검사

`backend/test_evaluation_input.py`, `backend/test_evaluation_preparation.py`와 감독·연구 검수 소비자를 검사한다. 5815의 두 요청 구간을 비밀정보를 제거한 고정 자료로 재현하여, 예산 안에 있을 때 첫 패킷에 본문·판본·영수증이 들어가는지 확인한다. 중복 구간, 여러 criteria, 큰 구조화 본문, 바뀐 파일, 다른 턴의 참조, 입력 한도 초과도 검사한다.

구조 검사로 모델 승인 1회를 보장했다고 쓰지 않는다. 실제 모델 대조에서는 같은 답변 지문에 대한 **근거 누락 때문에 발생한 재평가 횟수**와 총 평가 시간·토큰을 측정한다. 새 결함 발견이나 실제 수정에 필요한 재평가는 제거 대상이 아니다.

## 6 R3 부분 결과 표시와 최종 승인 분리

대상은 `backend/cognition/agent_pipeline.py`, `backend/datastore/supervision_delivery.py`, 각 표면의 스트림 전달부와 `frontend/src/components/chat/ChatView.tsx` 및 연구 대화 소비자다. 현재 일반 `text/final` 보류 조건을 통째로 제거하지 않는다.

첫 범위는 현재 대화에서 이미 열람 가능한 원문·영수증에 결속된 **부분 관측 결과**다. 읽은 구간, 판본, 대상, 확인 범위를 함께 전달하며, 도구 성공만으로 사실의 의미나 전체 목표를 검증했다고 하지 않는다. 모델의 해석·초안·아직 공개되지 않은 파일과 알림은 기존 최종 검수 대상으로 둔다. 공개 대기열의 항목을 부분 결과 링크로 노출하지 않는다.

기존 메시지/사건 체계에 부분 결과 유형을 두고 원문 참조·판본·표시 ID를 보존한다. 화면은 이를 ‘확인된 부분 결과’로 구분하며 ‘작업 완료’로 표시하지 않는다. 후속 판본이나 반증이 나오면 같은 표시 ID를 갱신하거나 철회 상태를 보여준다. 재연결 때 중복 표시되지 않으며 취소 후 새 결과를 내보내지 않는다. 외부 채널은 지원 여부를 명시하고 지원하지 않으면 최종 응답만 보낸다.

공통 채팅뿐 아니라 실제 연구 대화에서 수신·렌더·재연결을 확인한다. 검수 탈락·파일 지문 변경·공개 실패·취소를 주입해 미승인 최종 본문이나 비공개 산출물이 나오지 않는지 검사한다. 첫 유의미한 표시가 빨라져도 최종 완료가 빨라졌다고 보고하지 않는다.

## 7 R4 짧은 판단의 대기와 복구

소유 경로는 일반 분류 호출부, `backend/cognition/framing_inheritance.py`의 `_judge_relation`, `repair_resume.py`의 `user_resume`, `consciousness_agent.py`의 원샷 호출과 실제 제공자의 요청 수명이다.

역할 `classify`에 호출 전체 마감시간을 전달한다. 초기 설계값은 **재시도 포함 15초**이며, 이는 측정 결과가 아니라 조정 가능한 시작값이다. 연결·읽기 제한과 전체 마감을 구분하고, 남은 턴 예산·사용자 취소 중 먼저 닿는 것을 적용한다. 토큰이 조금씩 도착해도 전체 마감이 늘어나지 않는다. SDK 자동 재시도도 같은 예산 안에 넣는다.

호출자만 대기를 끝내고 백그라운드 요청을 계속 실행시키지 않는다. 제공자 스트림을 닫고 늦게 돌아온 결과의 채택을 막으며 비용·오류를 기록한다. 전역 설정을 바꿔 실행·의식·연구 호출까지 15초로 제한하지 않는다.

일반 분류는 기존 분류 실패 계약을 따른다. 수리 재개 관계 판단은 strict 실패로 남겨 이전 사본·기준·인계를 보존한다. 시간초과를 `NEW`나 `CONTINUE`로 바꾸거나 새 수리 권한을 부여하지 않는다. 기존 상태에서 재시도할 수 있도록 실패 원인과 재개 대상을 전달한다.

가짜 제공자로 응답 전 정지, 부분 응답 뒤 정지, 늦은 성공, SDK 재시도, 사용자 취소를 검사한다. `backend/test_repair_resume.py`와 관계 판정·분류 실패 검사를 연결하고, 작업의 중복 시작·기준 상실·잔존 요청이 없는지 확인한다. 실측 결과는 대기 상한 준수와 정상 판단 실패율을 함께 보고한다.

## 8 R5 CLI 종료와 문맥 중복

### CLI 종료

`backend/providers/codex.py`는 `turn.completed`를 처리하고, 공통 `backend/providers/cli_provider.py`는 stdout을 읽은 뒤 `proc.wait`와 후속 처리를 수행한다. 응답 완료, 도구 효과 완료, 프로세스 종료는 서로 다른 상태다.

R0의 경계로 약 5.2초가 EOF 대기·프로세스 종료·티켓 회수 중 어디에 쓰이는지 나눈다. 제공자의 종결 사건과 진행 티켓 상태를 확인한 뒤에만 정리 전용 대기 한도를 검토한다. stdout/stderr 회수, 종료 코드·뒤늦은 오류, 세션 저장, 사용량, 진행 중인 도구·외부 효과를 빠뜨리지 않는다.

`turn.completed` 한 건만 보고 프로세스를 죽이거나 성공을 확정하지 않는다. 안전한 분리가 가능한 경우 결과 준비 상태와 정리 상태를 분리하되, 프로세스 소유자는 끝까지 회수 책임을 가진다. 지원 프로토콜에서 이를 보장할 수 없으면 조기 성공 대신 기존 실패·회수 경로의 한정 대기로 수리하고 한계를 기록한다. `_terminate_cli`, 기존 무응답 감시, 완료 티켓 계약을 재사용한다.

`backend/test_cli_provider.py`, `backend/test_cli_provider_gates.py` 등에 정상 종료, 응답 뒤 비정상 종료, EOF 없는 정지, 미완료 티켓, 취소·재개 실패를 검사한다. 프로세스 소유권을 바꾸면 관련 실제 프로세스 system 검사도 실행한다.

### 역할 문맥

역할별 입력 manifest로 동일 원문이 반복 직렬화되는 곳을 찾는다. 안정된 공통 앞부분과 턴별 가변 부분의 순서를 정리하고, 같은 판본의 본문은 한 입력 안에서 한 번 싣고 메타데이터로 참조한다. 참조를 실제 본문 공급으로 오인하지 않는다.

실행자와 평가자의 세션·권한·판정 독립성은 유지한다. 계획·최종평가를 실행자 세션에 합치지 않는다. R1 외의 추가 호출 통합은 입력·출력·실패 계약이 동일 책임에 속하는 경우로 한정한다. 캐시 적중 증가와 지연 감소는 별도로 확인하며 회상 삭제·어휘 축소로 대신하지 않는다.

## 9 품질과 비용의 대조

기존 66개 기록과 두 쌍의 실험은 원인 발견 자료다. 이를 독립적인 정상 질문 66개 또는 통계적 기준선으로 사용하지 않는다. 다음 범주의 고정 입력과 아직 사용하지 않은 다른 주제 입력을 각각 전후 비교한다.

| 범주 | 지켜야 할 결과 | 주 관측 |
| --- | --- | --- |
| 연구 설명·관점 정정 | 원 발언의 의미와 관점·질문 저장 보존 | 별도 계획 호출, 계획 수정 범위, 최종 완료 |
| 기존 계획의 좁은 수정 | 유효한 질문·근거·진행 유지 | 호출 수, 판본 충돌, 전체 토큰 |
| 새 심층연구·방법 변경 | 사전 계획과 조사·근거·멈춤 조건 유지 | 누락·잘못된 축소 여부, 전체 시간 |

| 일반 EXECUTE·REFLEX | 기존 정답·도구 효과와 평가 경로 유지 | 새 상시 비용, 종료 지연 |
| 실패·취소·부분 실행·재개 | 효과 중복 없음, 미완료 정직한 표시 | 판단 마감, 복구 가능성, 공개 경계 |

모델·강도·완료 기준·자료 판본·권한을 고정하고 세션 상태를 맞춘다. 새 세션과 재개를 별도 묶음으로 비교하고 순서를 교차한다. 각 정상 범주는 최소 5쌍을 시작 표본으로 삼되, 이는 품질 확인과 중앙값·범위 관찰용이다. 소표본의 p95나 보장 절감률을 내지 않는다. 꼬리 지연은 장애 주입의 상한 준수와 더 긴 실사용 관측을 구분한다.

품질은 사용자 목표의 정확성·완전성·근거·사용 가능성, 계획·관점 보존, 사용자 수정량으로 비교한다. 모델의 자기 승인만으로 통과시키지 않는다. 오류와 시간초과도 표본에 남기고 성공한 빠른 요청만 선택하지 않는다.

시간은 요청부터 사용 가능한 승인 결과까지, 첫 유의미한 화면 표시까지, 서버 종료까지를 따로 기록한다. 모든 역할·내부 모델·재시도·평가·해당 작업의 증류가 쓴 입력·출력·캐시 토큰을 호출 ID로 중복 없이 합산한다. 응답 뒤 비용은 대기시간에 더하지 않되 총토큰에서 숨기지 않는다.

단계별 효과를 더해 총 절감률을 만들지 않는다. 품질을 유지하며 시간과 전체 토큰이 함께 줄면 목적 달성으로, 한 축만 좋아지면 부분 성과로 기록한다. 기능 계약을 구현·검증한 상태와 실제 성능 개선을 입증한 상태는 구분한다. 통계적 확신을 기다리느라 R1·R2의 구조 수리를 미루지 않는다.

## 10 반영과 복구

각 단계는 정본 main의 독립 커밋으로 남긴다. 동시 작업 파일을 포함하지 않도록 pathspec으로 커밋하고, 변경 소유자·계약·소비자·대체 경로·검증·잔여를 커밋 본문에 기록한다.

개발 중에는 `scripts/select_tests.py --files`에 이번 변경 파일을 명시해 전이 소비자 검사를 고른다. 공통 인지·평가·제공자 변경의 통합 완료 시 `.venv/bin/python3 -m pytest backend/ -m "not system" -n auto --dist loadfile`과 관련 system 묶음을 실행한다. frontend 변경은 `npx tsc -p tsconfig.app.json`과 실제 화면 검수를 수행한다. backend 변경은 `python3 scripts/build_body_bundle.py android`, 어휘·교재 계약에 영향을 주면 `python3 scripts/build_ibl_nodes.py --check`도 확인한다. 새 파일은 층 규약과 1500줄 제한을 따른다.

활성 반영은 기존 keeper·재기동 제어를 사용하고 수동 표식을 만들지 않는다. 별도 판단·타임아웃 설정은 역할 소유 위치에 두고 기존 기본값으로 되돌릴 수 있게 한다. 계획 패치와 부분 결과의 새 형식은 읽는 소비자를 먼저 배포하며, 이전 계획 영수증과 메시지는 계속 읽을 수 있어야 한다.

잘못된 계획 연결, 미승인 공개, 기준·권한 상실, 중복 효과, 늦은 응답의 오채택은 해당 단계의 반영을 중단할 조건이다. 기존 유효 판본·영수증·사본은 보존하고 해당 변경만 되돌린다. Git 복구만으로 운영 데이터가 복구됐다고 주장하지 않는다. 부분 결과가 이미 표시됐다면 정정·철회 상태를 남긴다.

최종 인수에는 계약 회귀, 실제 활성 판본, 대표 경로의 실제 모델 호출, 연구 화면 표시, 품질·시간·토큰 비교 결과와 미확인 범위가 필요하다. 문서와 코드가 존재하는 것만으로 수리 완료를 선언하지 않는다.

## 11 이번 작업의 반영 상태

수리계획만 정본에 작성했다. 보고서의 주요 코드 경계와 기존 계획·평가·재개·CLI 소유자를 대조했다. 제품 구현, 회귀 실행, 실제 모델 성능 대조, 운영 활성화는 후속 수리 단계다.
