대역이 없어서 로컬 문서·링크 탐색으로 수행하면 **자료 발견 시험**으로 보고한다.
그 결과를 실제 검색 쿼리·검색엔진 커버리지의 성공으로 세지 않는다.

명시적인 추가 단계는 출처 간 발견→기능의 의미 확인→조건 변경에 따른 재선별이다.
폴더 위치만 바꾸거나 후보 수를 늘리는 것을 새 검증으로 세지 않는다.

## 훈련자 IBL과 독립 AI의 실행

훈련자는 공개 교재·액션 계약으로 다음 전체 흐름을 IBL 프로그램으로 작성한다.

대화 읽기 → 현재 조건과 근거 발언 추출 → 출처 조회와 실패 보존 → 상품·모델별 근거 결합 →
조건별 충족·불충족·미확인 판정 → 후보 비교와 남은 조사 결정 → 보고서 저장·재독.

최초 초안부터 보존한다. 핵심 해법을 Python 안에 숨기거나 예상 상품 ID를 코드에 넣지 않는다.
조건이 바뀌면 무관한 읽기·정규화 결과를 재사용하고 선별을 갱신한다.
새 원천이 필요하거나 원자료가 바뀌면 필요한 조회를 다시 한다.
IBL 성공은 표현·조합의 검증이며 독립 AI의 목적 이해 성공과 분리한다.

독립 AI는 같은 역할·모델·자료·완료 조건에서 다음 두 경로를 비교한다.

- EXECUTE: `#execute`를 붙인 T1~T3. 핵심 관찰 대상이다.
- THINK: `#think`를 붙인 T1~T3. 규정·평가가 어떤 차이를 만드는지 비교한다.

훈련자의 분해·코드·결과·정답은 독립 AI에 제공하지 않는다. 입력 폴더를 별도로 두고 정답은 그 밖에 둔다.
지시만으로 접근 차단이 보장됐다고 여기지 말고, 실제 호출에서 정답·다른 실행 결과 접근 여부를 점검한다.
유출되면 해당 비교를 무효로 남긴다. 내부 구현을 보고 만든 부분은 순수한 공개 교재 기반 작성과 구분한다.

## 실제 웹 탐색 시험

고정 자료와 별도의 새 대화에서 동일한 T1~T3을 EXECUTE로 실행한다.
현재 사용 가능한 쇼핑·일반 검색·블로그·판매처·제조사·브라우저 경로를 먼저 확인하되,
실행자에게 특정 정답 경로를 가르치지는 않는다. 접근 가능한 능력이 있는데 사용하지 않은 것과
접근 자체가 불가능한 것을 구분한다.

훈련자는 별도 참조 조사로 유력 후보를 확인해 실행자에게 숨겨 둔다.
출처 URL·열람 시각·정확한 모델·분리 세척 설명·조작 방식·후기 수와 집계 범위를 저장한다.
검색 요약의 인상이나 오래된 인기 글만으로 정답을 확정하지 않는다.
실행자가 참조 후보를 놓쳐도 동등하거나 더 적합한 대안을 충분히 검증했다면 실패가 아니다.

반대로 접근 가능한 적합 후보를 놓치고 부적합 후보를 추천하거나 “더 없다”고 결론 냈다면,
실제 검색어·조회 범위·누락 출처·종료 이유를 추적한다. 참조 조사도 시장 전체의 완전한 정답 집합은 아니다.
가격·재고·리뷰는 시점에 따라 바뀌므로 수리 전후 재생에는 당시 증거 사본을 사용하고,
실시간 재검색 결과는 조건이 달라진 관찰로 별도 기록한다.

## 합격 기준과 실패 원인 판정

세 축을 따로 판정하며 하나의 성공 표시로 합치지 않는다.

| 축 | 통과에 필요한 관측 | 통과의 대체물이 아닌 것 |
| --- | --- | --- |
| 요구 적용 | 현재 조건이 검색·후보 제외·우선순위를 실제로 바꿈 | 답변에서 사용자 정정을 재진술 |
| 판단 정확성 | 근거의 대상·기능 의미가 맞고 결론·표·주의사항이 일치 | 뒤에 미확인 단서만 붙임 |
| 과제 달성 | 사용자가 선택할 수 있는 적합 후보와 충분한 비교 근거 | 후보 개수 채우기, 솔직한 미완료 보고 |

미확인 보고는 정확성에서는 통과할 수 있어도 구매 목적 달성으로 세지 않는다.
조건을 모두 만족하는 후보가 없는 통제 변형에서는 그 사실을 **제공된 자료 범위에서** 정확히 판단하는 것이
변형 과제의 성공이다. 실제 시장에 적합 제품이 없다는 결론으로 확대하지 않는다.
후기 수에 임의의 합격 컷을 고정하지 않는다. 수치·모델 귀속·비교 이유가 사용자 판단을 뒷받침하는지 본다.
실제 검색도 횟수·사이트 수가 아니라 미해결 핵심 조건과 합리적으로 접근 가능한 유력 경로를 기준으로 본다.

오답이 나오면 같은 턴의 입력·도구 결과·출력을 연결해 다음 원인을 가른다.

1. 필요한 대화가 호출 입력에서 빠졌다: 전달·발췌·세션 연결 결함.
2. 대화는 도달했으나 검색·선정이 옛 조건을 따른다: 실행의 요구 적용 실패.
3. 기능 이름을 작동 방식으로 확대하거나 반증을 무시한다: 근거 해석·선택 실패.
4. 특정 도구의 실패 뒤 다른 가능한 경로를 쓰지 않는다: 능력 발견·탐색 종료 실패.
5. 미달 결과가 승인된다: 기준 누락·평가 입력·평가 판단을 각각 점검.

## 수리와 재검증

기준선의 접수 작업을 모두 종료·회수한 다음 런타임을 수정한다.
코드·프롬프트·모델 설정 변경 시각과 실제 적용 여부를 남긴다.
프롬프트 추가나 모든 EXECUTE의 THINK 전환, 상시 평가 호출 도입을 미리 해법으로 정하지 않는다.
원인에 맞는 공통 경계를 수리하고 기존 경로의 중복·비용도 함께 검토한다.

수리 뒤 원래 실패 입력을 같은 증거·모델·완료 기준으로 다시 실행한다.
새 대화에서는 다음 반전 요청도 시험한다.

> 외부 타이머 콘센트는 쓰지 않을 거야. 정해진 시간이 지나면 쿠커 자체가 꺼져야 해.
> 분리해서 물세척할 수 있고 조작이 쉬우며 후기가 충분해야 한다는 조건은 그대로야.

내장 타이머를 계속 무시하거나, 무조건 추천을 거부하는 편향이 생기지 않았는지 확인한다.
원래 오류가 발생한 EXECUTE를 재시험하지 않고 THINK의 개선만으로 수리 완료라 쓰지 않는다.
단일 성공을 성공률로 일반화하지 않는다. 같은 원인으로 두 수정 주기 연속 진전이 없으면
그 경로의 반복을 멈추고 최소 재현·남은 조건을 보존한다.

코드 변경의 회귀는 저장소 규약과 선택기를 따른다. 허브 변경이면 비-system 전수와 관련 system 묶음을 실행한다.
backend 변경 시 Android 번들을 재생성하고 필요한 빌드·층 검사를 완료한다.
수리 이후 라이브 재생의 범위·시간도 따로 적어 최초 훈련의 60분을 무제한 연장한 것으로 감추지 않는다.

## 실행 접수와 증거 회수

현재 훈련 가이드의 API 계약을 시작 때 재확인한다. 기존 검증 경로는 다음과 같다.

```text
POST /projects/{project_id}/agents/{agent_id}/command
{"command":"#execute 또는 #think와 해당 요청","origin":"training","background":true}

GET {접수 응답의 status_url}?wait=20
```

`task_id`·`status_url`을 즉시 저장하고 `succeeded`/`failed`와 result 전문을 회수한다.
API의 succeeded는 실행 종료이지 내용의 정답 판정이 아니다.
후속 대화의 세션 연속성과 직전 답변 저장을 확인한다. origin=training은 실사용 기억 혼입을 줄이지만
외부 행동을 차단하지 않으므로 조회와 지정 출력 쓰기만 수행한다. 구매·결제·문의 발송·예약은 실행하지 않는다.

다음 자료를 회차 폴더에 남긴다.

- task.md: 자연어 요청, 분기·완료 기준, 자료·권한·모델, 시작 시각과 상한.
- 원 입력과 해시, 최초 IBL과 수정 이력, 실제 요청·접수·최종 결과 봉투.
- 사용자 정정이 포함된 실제 모델 입력 또는 확인 가능한 입력 증거, 검색어·출처·도구 오류.
- 에피소드·궤적·평가·산출물과 턴별 판정. 원자료와 정답은 실행자 입력 밖에 둔다.
- 역할별 실제 모델 입력·출력·캐시 토큰, 조회·수정·검수 횟수, 종료·회복까지 벽시계 시간.

로컬 실행 자료는 `outputs/long_sentence_imagination/YYYY-MM-DD_N회차/`,
git에 남길 설계·선별 증거·보고서는 `docs/experiments/long_sentence_imagination/round_N/`에 둔다.
누적 원장에는 주요 발견·수리·잔여와 보고서 링크를 기록한다. 키·토큰·개인 대화는 커밋하지 않는다.

## 시간 배분과 종료 보고

준비·작성·기준선 실행·변형·원인 진단 합계의 기본 상한은 60분이며 시작 때 고정한다.
목표 배분은 준비와 자료 검증10분, IBL·고정 자료 비교20분, 실제 웹15분, 원인 진단10분, 회수5분이다.
이는 목표 배분이며 실행 지연을 이유로 종료 상한을 자동 연장하지 않는다.
실제 웹 시험 시간을 확보하도록 고정 자료의 부가 반복부터 줄이고, 남은 시간에 회수하기 어려운 호출은 시작하지 않는다.
필수 부분을 못 끝내면 미검증으로 남긴다. 종료 시 진행 작업은 취소하거나 실행 ID·회수 방법을 명시한다.
수리·회귀·기록 시간은 구분해서 보고한다.

최종 보고는 원래 문제의 재현 여부, IBL과 독립 AI 각각의 판정, 고정 자료와 실제 웹의 차이,
확정 원인과 가설, 수리 전후 증거, 비용 변화, 검증 범위, 잔여를 포함한다.
단순한 미확인 표시 개선을 구매 목적 달성으로 바꾸어 보고하지 않는다.
정본 반영과 실재하는 커밋 해시를 확인한 뒤 마친다.
