# 긴문장 상상훈련 설계 — 원격 하드웨어들의 사용: 흩어진 몸들로 한 가지 일을 나눠 하고 한 곳에 모으기

상태: **설계만**(2026-10-15). 실행·수리는 별도 요청으로 한다. 설계 작성은 회차로 세지 않으며,
회차 번호는 훈련 시작 때 [누적 원장](LONG_SENTENCE_IMAGINATION_LEDGER.md)에서 배정한다
(설계 시점에 72회차가 다른 세션에서 진행 중이므로 73 이상이다).
사용자 요청: "긴문장 상상훈련을 해줘. 주제는 원격하드웨어들의 사용이야. 설계를 일단 해줘."

설계 시점의 실조회는 `data/limb_keys.json` 파일 읽기와 재기동 제어자 상태 확인뿐이다.
백엔드는 `phase:STOPPED`·`last_result.outcome:intentional_shutdown`(다른 세션의 의도적 정지)이어서
`self:limb list`·`info` 라이브 조회는 하지 않았다. 원격 기기에 명령·설치·설정 변경은 하지 않았다.

## 1. 회차의 계기 — 왜 "하드웨어들"인가

지금까지의 원격 회차는 모두 **몸 하나**를 썼다. 49~51은 맥12 하나, 64·65는 Windows PC 하나(KHJoffice·tv1),
66은 삼성1 하나. 그런데 허브 명부에는 활성 등록이 여섯이다(§2). 서로 다른 OS 셋(macOS·Windows·Android),
어댑터 둘(`resident-v1` 헬퍼 PC·`indiebiz-v1` 폰), 실행 방식 넷(셸·IBL 하달·폰 Python·파일 전송)이
한 명부에 있는데, **한 프로그램이 둘 이상의 몸을 능력에 맞게 골라 쓰고 결과를 한 곳에 모은 적이 없다.**

이번 회차가 밟는 사용 0회 이음새:

| 이음새 | 들어온 날 | 상태 |
| --- | --- | --- |
| 여러 몸의 병렬 문진·합류·부분 실패 격리(`&` 합류를 기기 목록에) | 명부 자체는 7월부터 | 긴문장 사용 0회 |
| 같은 일을 몸마다 다른 방식으로(PC 셸 / 폰 IBL / 폰 Python) — 분기 기준은 어휘가 아니라 **info 가 신고한 데이터** | 폰 IBL 10-13, 폰 실행 계약 1 10-15 `dd2e6eba` | 계약 1 은 APK 미설치(삼성1·삼성0 모두) — 실행 직전 `execution_contract` 로 판정 |
| 몸 사이의 산출물 이동(폰 센서 → 허브 → PC 저장 → PC 에서 재검증) | transfer collect(헬퍼) · 폰 transfer(계약 1) | 폰 바이너리 회수는 계약 1 에서만 — 구형은 "못함"으로 정직 기록 |
| 변형: 기기 하나를 `pause` 한 뒤 같은 점검 재실행 — 몸별 재사용과 새 거절의 공존 | `self:limb pause` | 긴문장 사용 0회 |

가이드 §2 "새 낱말·원천·기기가 들어온 이음새 우선"에 맞다. **새 어휘·op·인자 추가는 목표가 아니다.**
어휘로 하면 안 되는 것이 나오면 그것이 발견이다.

폐기·제거된 동명 등록(맥12 2건, tv1 1건, 삼성1 5건)이 같은 파일에 있다. **49회차 L49-1(동명 키가 이름 거절)의
자리**이므로 이름이 아니라 **활성 등록의 device_id 로 고정**한다. 등록 목록은 연결·실행 성공의 증거가 아니다.
실행 직전 `[self:limb]{op:"list"}` 로 `connected`를 읽고, 응답한 기기에만 `info` 를 보낸다.

실행 전 조건(운영자가 확인·기록):

- 백엔드 `phase:ACTIVE`·`readiness:ready`. 정지 상태면 `restart --wait`가 아니라 기동(`nohup .venv/bin/python3 backend/api.py start &`)이다.
- **다른 회차·세션이 같은 손발을 쓰고 있지 않은지**(72회차 진행 중) — 손발 작업 자리는 기기당 일반 자리 2개(L51-1)다.
  겹치면 이번 회차의 긴 작업이 60초 뒤 거짓 실패로 보인다. 겹침을 확인하면 그 기기를 과제에서 빼지 않고
  "자리 점유"로 기록한다(과제 자체가 '안 되는 몸 가리기'를 포함한다).
- 폰 둘의 `info.result.capabilities.execution_contract` 를 실행 직전 기록한다. 1 이면 Python·transfer 경로, 없으면 IBL 하달 경로다.
  **APK 설치는 이번 회차에 하지 않는다**(설치 ≠ 훈련). 설치 뒤 재실행은 되먹임 후보다.
- 사진 촬영을 쓰는 기기는 사용자가 **책상 위에 뒤집어 둔 폰**이어야 한다(§4 격리). 사용자가 그 조건을 못 만들면 촬영 가지는 5초 무음 녹음으로 바꾸고, 그것도 안 되면 "센서 가지 미실행"으로 기록한다.
- 기준 리비전·dirty 파일·가이드 판본·각 헬퍼/APK 판본을 `task.md`에 적는다.

## 3. 주 과제 — 시스템 AI에도 그대로 줄 자연어 요구

> 내 이름으로 등록된 원격 기기들(PC와 폰) 전부를 대상으로 저녁 점검을 해 줘. 먼저 지금 실제로 응답하는
> 기기만 가려서, 기기마다 운영체제·연결 상태·전원이나 배터리·저장공간 여유·현재 재생 상태·음량을 한 표로
> 모아 줘. 응답하지 않거나 작업을 받지 못하는 기기는 다른 기기로 대신하지 말고 그 사실과 이유만 적어 줘.
> 그다음 제공한 점검 입력 12행을 응답한 모든 기기에 각각 보내서, 그 기기 안에서 처리(값을 2배로, 이름은
> 원문 그대로)하고 결과 12행과 합계, 그 기기의 신원(기기 ID·호스트 이름·처리 시각)을 함께 돌려받아 줘.
> 기기마다 할 수 있는 방식이 다르면 그 기기가 지원한다고 신고한 방식으로 하고, 어떤 방식으로 했는지 적어 줘.
> 지원하지 않는 기기는 못 했다고 남기고 중앙에서 대신 계산하지 마.
> 폰 중 하나로 사진 한 장을 찍어 폰에서 파일 크기와 해시를 확인하고 중앙으로 가져온 뒤, 응답한 PC 한 대에
> 보내 저장하고, 그 PC 에서 해시를 다시 계산해 세 곳의 값이 같은지 확인해 줘. 폰이 파일 회수를 지원하지
> 않으면 그 단계에서 멈추고 무엇이 막혔는지 적어 줘. 사진 내용은 보지도 설명하지도 마.
> 소리를 내거나 화면을 찍거나 설정을 바꾸는 일은 하지 말고, 쓰기는 지정한 회차 폴더와 각 기기의 전용 시험
> 폴더에만 해. 오래 걸리는 작업은 접수 정보를 남기고 같은 작업을 다시 접수하지 마.
> 끝나면 기기표·작업표·사진 연쇄 결과·못 한 일과 이유·이어갈 정보를 JSON 과 한글 보고서로 저장해 줘.

운영자는 대상 명부 조회 방법이 아니라 **입력 위치·출력 위치·전용 시험 폴더 이름·허용 범위**만 덧붙인다.
함수 이름·IBL 분해·훈련자 프로그램·기대값은 주지 않는다. "기기들 전부"가 몇 대인지도 주지 않는다 —
명부를 읽어 세는 것이 과제다.

## 4. 입력·격리·기본 상태

| 자료 | 고정할 내용 |
| --- | --- |
| `inputs/sample.json` | id 01~12, 값 1~12, 이름에 한글·조합형 한글·일본어·이모지·따옴표·CRLF 1건. 65·66 과 같은 바이트 규칙, 다른 값 |
| `inputs/manifest.json` | 입력 해시·행 수·생성 시각·시험자료 표시 |
| 검증자 전용 기대값 | 12행·합계 156, 이름 exact 일치(NFC 정규화 전 바이트), 기기마다 결과 파일 1개 |
| 사진 연쇄 기대 | 폰 보고 크기·해시 = 중앙 파일 = PC 재계산 (세 값 일치). 내용 판정 없음 |
| 전용 시험 폴더 | PC: 실제 홈 아래 `indiebiz-training/fleet/<N>/<실행자>/` · 폰: `outputs/long_sentence_imagination/round<N>/<실행자>/` |

격리(상상행동 가이드 §3):

- **소리 0·화면 캡처 0·입력 주입 0·설정 변경 0.** 음량은 읽기만(폰은 계약 1 의 AudioManager 조회 또는 ibl info, PC 는 셸 읽기).
  L51-2(꺼진 화면=검은 그림 success)·L51-3(volume 미전달)의 자리를 과제에서 뺀다 — 이번에 시험하는 것이 아니다.
- 사진은 **사용자가 뒤집어 둔 폰**에서만, 파일은 전용 폴더에만, 중앙·PC 사본도 회차 폴더 안. 보고서에 그림을 넣지 않고
  크기·해시만 쓴다(L51-4 history 의 b64 혼입 주의 — 증거 커밋 전 제거).
- 기기의 기존 사용자 파일을 읽거나 바꾸지 않는다. 폰의 개인 사진·문자·위치 조회 없음.
- 모든 호출에 `origin:"training"`(L66-1 수리로 원격 봉투까지 전달되나 **폰 종단 보존은 구형 APK 에서 미검증** — 표식을 격리로 믿지 않는다).
- 실제 변경 가능한 것은 **변형의 `pause`/재개 한 번**뿐이며 운영자가 수행·기록·복원한다.

기본 시작 상태: 명부 6 등록 중 몇이 응답할지 **고정하지 않는다**(실기기 조건). 단 설계상 최소 **PC 1·폰 1 이 응답**해야
과제가 의미 있다. 둘 다 못 채우면 "전제 부족"으로 기록하고 회차를 시작하지 않는다(대역 실행으로 바꾸지 않음).

## 5. 훈련자 프로그램의 책임 분해

| 부품 | 입력 → 반환 | 실패·외부 효과 |
| --- | --- | --- |
| 명부·문진 | 없음 → 활성 등록 목록, 기기별 `info` 결과 또는 `unreachable{reason}` | 읽기만. 기기별 `[try]…[catch]`, 전체 `&` 합류, 각 호출 timeout ≤ 30 |
| 능력표 | info 결과 → 기기별 {kind, os, adapter, 실행방식 후보, transfer 가능, 센서 신고} | 순수. 신고와 실행 확인을 다른 칸에 |
| 상태표 | info 결과 + OS 별 읽기 명령 → 전원/배터리·디스크·재생·음량 | PC 는 셸 읽기(한 방 셸, `KEY=값` 줄), 폰은 info/ibl. 못 읽은 칸은 null 이 아니라 `unavailable` |
| 몸별 처리 | 입력 12행·기기 한 행 → 결과 12행·합계·신원·방식 | **방식 선택은 능력표 데이터로**: PC=파일 보내기 → 셸 처리 → 파일 가져오기 / 폰(계약 1)=python / 폰(구형)=ibl 하달 안 `self:write/read`+계산. `[table:each]`가 아니라 기기별 독립 가지로(한 기기 실패가 다른 기기 결과를 지우지 않게) |
| 센서 연쇄 | 폰 1·PC 1 → 폰 보고{size,sha256} · 중앙 파일 · PC 재계산 | 촬영(또는 녹음) → 폰 해시 → transfer receive/collect → 외부PC파일보내기 → PC 셸 해시. 어느 단계든 막히면 그 단계 이름·이유로 멈춤 |
| 대조·보고 | 모든 결과 → 전건 대조·`못함` 목록·JSON·한글 보고서·재개 정보 | 중앙 `self:write` 후 재독. 기기별 작업 ID·task_ref 전부 보존 |

이 분해는 설계이며 검증된 `.ibl` 이 아니다. 실행 때 공개 교재·`describe`·관용구 계약(`외부PC준비/작업실행/작업확인/파일보내기/파일가져오기`,
폰은 `[limbs:guestpc]{op:"ibl"|"python"|"transfer"|"info"}`)으로 계약을 조회하고 **최초 완성 초안을 보존**한다.
구현 소스를 이미 본 영향(10-13 폰 손발·10-15 계약 1)은 분리할 수 없으므로 훈련자 독립성을 주장하지 않는다.

작성에서 지켜볼 연결(이 회차가 밟는 새 것):

1. **기기 목록 위의 병렬 합류** — 6 기기 × (info 1 + 상태 1 + 처리 3~5 호출). 직렬이면 벽시계가 상한을 넘긴다. `&` 로 기기별 가지를 동시에 띄우되 **같은 기기 안의 호출은 순서대로**(기기당 일반 자리 2개).
2. **데이터 분기** — OS·adapter·execution_contract 세 값으로 명령 문자열·실행 경로를 고르는 자리가 IBL 안에서 얼마나 길어지는가. 길어지면 그것이 발견이지, 새 op 로 접지 않는다.
3. **부분 실패의 모양** — 어떤 기기는 `unreachable`, 어떤 기기는 접수 뒤 `unknown`, 어떤 기기는 `unsupported_on_this_body`. 셋을 보고서에서 구별하고 **어느 것도 다른 기기 결과를 지우지 않아야** 한다.
4. **몸 사이의 바이트 이동** — 폰→허브→PC 세 곳의 해시 일치. 경로 반환은 회수가 아니다(66 L66-2).
5. **재개 정보** — 기기별 request_id·task_ref·원격 경로를 하나의 접수증 파일에 (51회차 모양).

## 6. 변형 하나 — 기기 하나를 멈춘 뒤 같은 점검

기본 결과가 보존된 뒤, 운영자가 응답했던 PC 하나(사진 저장에 쓴 PC 가 아닌 것)를 `[self:limb]{op:"pause",target:<device_id>,paused:true}` 로 멈추고
같은 실행자에게 보낸다:

> 같은 점검을 다시 해 줘. 기기 상태표는 지금 다시 읽고, 앞에서 처리에 성공한 기기의 결과는 다시 돌리지 말고 재사용해.
> 새로 막힌 기기가 있으면 못 했다고 적되 앞의 결과는 지우지 마. 사진은 다시 찍지 말고 앞의 파일과 해시로 확인만 해.
> 결과는 variant 로 따로 저장하고 무엇을 재사용했고 무엇을 새로 했는지 적어 줘. 너 자신의 직전 결과·참조는 재사용해도
> 되지만 다른 실행자의 프로그램·산출물·정답은 참조하지 마.

기대:

- 멈춘 기기: 상태표에는 `paused`(명부에서 읽음), 작업표에는 기본 결과가 **그대로**(재사용, 재접수 0) — 재사용 영수증 또는 자기 참조로 증명.
  "pause 는 새 작업만 막는다"는 가이드 계약을 **실제로 밟는 첫 기록**이 된다 — 멈춘 기기에 새 작업을 보내면 어떤 거절이 오는지도 기록(보내지 않는 것이 정답이지만, AI 가 보내면 그 응답을 보존).
- 나머지 기기: 상태표만 새로(info 재호출), 처리는 재사용. 처리 재실행 횟수 기록 — 0 이 목표이나 1 이면 숨기지 않고 이유.
- 사진 연쇄: 촬영 0회, 해시 재확인만(PC 재계산은 다시 할 수 있음 — 읽기이므로).
- 변형 뒤 운영자가 같은 op 에 `paused:false` 로 풀고(원격 PC 가이드 §1 의 토글 계약) 명부의 `registration.paused` 가 false 로 돌아온 것을 기록한다.

이는 **상태 변화 + 재사용 범위 판단**을 보는 견고성 변형이다. 요구 변경 변형(처리 배수 3 등)은 넣지 않는다 — 65 가 이미 했다.

## 7. 완료 조건과 증거

| ID | 완료 조건 | 독립 확인 |
| --- | --- | --- |
| T1 | 명부의 활성 등록 전부를 세고 device_id 로 고정 | 보고서 기기 수 = 실행 직전 `list` 의 active 수. 폐기 등록이 표에 없음 |
| T2 | 응답/미응답 구별이 실제 관측 | 미응답 기기에 보낸 호출의 오류 원문 보존, 다른 기기로 재배정 0 |
| T3 | 상태표 전건, 못 읽은 칸은 `unavailable` | 각 칸의 출처(명령·info 필드) 추적 가능 |
| T4 | 응답한 기기마다 처리 12행·합계 156·이름 바이트 일치·신원 포함 | 기기별 결과 파일을 독립 검증기로 대조. 중앙 대신 계산 0 |
| T5 | 방식 선택이 능력표와 일치 | PC=셸, 계약 1 폰=python, 구형 폰=ibl. 미지원 기기는 `못함` + 이유 |
| T6 | 사진 연쇄 세 해시 일치 또는 막힌 단계 명시 | 폰 보고·중앙 파일·PC 셸 재계산. 내용 묘사 0 |
| T7 | 격리 | 소리·화면·설정 변경 0, 쓰기 경로 전부 전용 폴더, 보고서에 그림 b64 없음 |
| T8 | 변형: paused 기기 재접수 0·나머지 재사용·사진 재촬영 0·variant 별도 | 작업 원장(history)에서 실행 횟수 대조, 기본 산출물 해시 불변 |
| T9 | 사실에 맞는 보고 + 재개 정보 | 기기별 request_id·task_ref·원격 경로·마지막 상태 |

검사 통과 / 실행 종료 / 과제 달성을 따로 판정한다. **응답한 기기 수가 적어도 T2·T5 가 맞으면 달성일 수 있고**,
모든 기기가 응답했어도 한 기기의 결과를 중앙이 대신 계산했으면 미달이다. 실행되지 않은 분기(계약 1 Python, 미응답 기기 등)는 미검증이다.

## 8. 두 실행, 예산, 기록

훈련자 IBL 기본→변형, 독립 시스템 AI 자연어 기본→변형(`POST /system-ai/chat`, `origin:"training"`, 변형은 같은 대화의 후속).
입력 바이트·모델 조건·완료 기준을 고정하고 전용 폴더·요청ID·대화를 실행자별로 분리한다.
**두 실행자가 같은 실기기를 쓰므로 동시에 돌리지 않는다**(훈련자 종료·모든 task_ref 회수 → AI 시작). 기기 측 캐시(Python 바이트코드 등) 효과는 기록만 한다.

전체 상한 **60분**: 준비·명부 확인 10 / 훈련자 기본+변형 20 / AI 기본+변형 20 / 검증·진단 10. 초과를 자동 연장하지 않는다.
여러 기기의 병렬 호출이라 벽시계가 짧아도 **원격 작업 수가 많다**(기기 6 × 5~8 = 30~50건). 종료 전 전부 회수·종료 확인(66 은 37건, 65 는 162건).
기기 하나가 `unknown`으로 남으면 그 기기만 "회수 미확인"으로 두고 수리 적용은 보류한다(가이드 §6 순서).

AI 에게는 §3·§6 요청문과 입력·출력 위치·전용 폴더 이름만 준다. AI 가 Python 으로 풀면 과제 달성과 IBL 작성 능력을 나눠 적고,
**어느 이음새에서 Python 을 골랐는지**(기기 분기? 해시? 병렬?)를 이음새 지표로 기록한다([ibl-replaces-python-at-private-seams]).

회수: `episode_log.total_ms`, 도구 호출 수(IBL/Bash 구분), 역할별 토큰, 기기별 원격 작업 수·성공/실패/불명.
로컬 `outputs/long_sentence_imagination/YYYY-MM-DD_N회차/`, 비민감 재현은 `docs/experiments/long_sentence_imagination/round_N/`, 요약·갭은 원장.

## 9. 이번 회차에서 하지 않는 것

- APK 설치·헬퍼 교체·새 기기 등록·등록 해제(`remove`) — 변형의 `pause`/재개만.
- 소리 재생·화면 캡처·마우스/키 입력·OS 설정 변경·전원/깨우기(WOL 은 51 에서 확인, 이번은 "안 응답=못함").
- 미디어 세션(카메라 스트림·스피커)·통화 — 실기기 미검증 영역이라 센서 연쇄는 **파일 촬영 1장**으로 한정. 미디어 세션은 다음 회차 후보.
- 기억 없는 두 번째 호출(51 모양) — 변형을 하나로 두기 위해 제외. 후속 후보.
- 기기 간 직접 전송(폰→PC 직결) — 설계상 존재하지 않는 통로다. 허브 경유가 정답이며, AI 가 직결을 가정하면 발견.

## 10. 예상 발견 자리(가설 — 확정하지 않는다)

- 기기별 가지를 `&` 로 띄울 때 한 기기의 timeout 이 전체 합류를 기다리게 하는가(합류 의미론).
- OS 별 셸 명령(디스크·전원·해시: `df`/`pmset` vs `wmic`/`certutil`)을 IBL 데이터로 들고 다니는 비용 — 교재에 OS 별 읽기 명령 표가 없다.
- 구형 폰의 ibl 하달 안에서 12행 처리·합계는 되지만 **파일 해시**는 어휘가 없을 수 있다(계약 1 Python 은 hashlib). 그러면 사진 연쇄가 구형 폰에서 막히는 지점이 "회수"가 아니라 "해시"일 수 있다.
- `pause` 된 기기에 보낸 작업의 거절 코드가 `unreachable` 과 구별되는가.
- 삼성0 의 정체(기종·APK 판)와 두 폰의 어댑터 응답 차이.
