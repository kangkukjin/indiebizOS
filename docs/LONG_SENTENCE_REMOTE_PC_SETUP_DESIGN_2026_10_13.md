# 긴문장 상상훈련 설계 — 원격 PC 작업 환경 설정

상태: 설계 완료, 훈련 미실행. 실제 PC 설정·등록·설치 변경 없음.
사용자 요청: “긴문장 상상훈련을 설계해줘. 주제는 원격pc설정이야.”

## 1. 목적과 선정 이유

**원격 PC의 현재 상태를 확인하고 필요한 설정만 적용한 뒤, 작업이 실제로 되는지 검증하고,
연결이나 문맥이 끊겨도 이미 적용한 일을 중복 실행하지 않고 이어가는 능력**을 시험한다.
기본 해석은 IndieBiz OS에 연결된 PC의 작업 환경 구성이다. 최초 USB 등록·OS 설치는 별도 전제다.

49·50회차의 원격 파일 처리·작업 관측 경험에, 2026-10-13의 대상 고정·단계 실행·결과 재개 기능을
연결한다. 파일 전송 성공이나 명령의 exit 0만으로 환경 설정 완료를 판정하지 않는다.
공통 개선 대상은 대상과 실행 환경 전달, 원하는 상태와 관측 상태의 차이 계산, 단계 의존성,
실패 증거 보존, 설정 변경 시 재사용 범위, 실제 완료 판정이다. 새 어휘 추가를 목표로 하지 않는다.

## 2. 주 과제 — 시스템 AI에게 줄 자연어 요청

> 지정한 원격 PC를 작은 자료 처리 작업에 바로 쓸 수 있게 준비해 줘. 먼저 PC의 신원과 운영체제,
> 연결 상태, 사용 가능한 실행 도구와 작업 폴더를 확인하고, 제공한 환경 요구사항과 비교해 줘.
> 지정한 시험 폴더 안에 독립된 실행 환경을 만들고, 제공한 프로그램과 고정된 의존성을 준비한 다음,
> 입력·출력 폴더와 프로그램 설정을 맞춰 줘. 이미 조건을 만족하는 것은 유지하고, 기존 파일의
> 사용자 설정과 관련 없는 내용은 보존해 줘. 사용할 포트가 다른 프로그램에 쓰이고 있으면 그
> 프로그램은 그대로 두고 제공한 대체 후보에서 사용 가능한 포트를 골라 줘.
> 시험 서비스를 띄워 상태를 확인하고, 샘플 자료를 실제로 처리해 결과가 맞는지 확인해 줘.
> 오래 걸리거나 응답을 못 받은 작업은 이미 실행됐는지 확인한 뒤 이어가고, 실패한 단계 뒤의
> 작업을 성공한 것처럼 진행하지 마. 필요한 권한이나 실행 도구가 없으면 막힌 조건과 내가 할 일을
> 구체적으로 남겨 줘. 마지막에는 무엇을 유지했고 무엇을 바꿨는지, 실제 동작을 어디까지 확인했는지,
> 다시 이어갈 정보와 원래 상태로 되돌리는 방법을 정리해 줘.
> 변경은 지정한 시험 폴더와 이번에 만든 시험 프로세스로 한정하고, 기존 서비스와 다른 PC의
> 설정은 건드리지 마. 설정 파일과 동작 검증 결과, 한글 요약 보고서는 지정한 결과 폴더에 저장해 줘.

운영자는 대상 식별자, 입력·출력 위치, 허용 범위와 공개 완료 조건만 붙인다.
IBL 함수 이름·훈련자 풀이·정답표·실패 주입 시점은 넘기지 않는다.

## 3. 실행 환경과 입력 준비

### 실기기와 시험 범위

기본은 **사용 가능한 상주 PC 1대**다. 실기기 조회로 device_id·OS·아키텍처·헬퍼 기능과
현재 실행 작업을 확인해 선택한다. 과거 보고서의 ‘맥12’·‘맥26’을 현재 사용 가능한 대상으로
가정하지 않는다. 다른 세션이 설치·업데이트 중인 PC는 선택하지 않는다.

원격 작업 루트는 실제 홈 경로 아래 `indiebiz-training/remote-setup/<회차>/<실행자>/`로 정한다.
중앙에도 같은 상대 이름의 미끼 폴더를 만들고 서로 다른 표식을 둔다. 실행 전 대상 PC와 루트의
식별 표식을 확인해야 하며, 중앙 파일을 읽고 원격 파일을 확인했다고 판정하면 실패다.
공백·한글이 포함된 하위 경로를 하나 넣어 경로 인용도 시험한다.

실제 헬퍼·원격 파일시스템·프로세스·통신을 사용한다. 설정 대상은 시험용 작은 프로그램이다.
실기기 확보가 안 되면 대역 실행으로 범위를 낮췄음을 먼저 기록하고 실기기 달성으로 세지 않는다.
등록되지 않은 PC의 설치, 시스템 전역 패키지·방화벽·전원·로그인 자동 실행 변경은 별도 확장 과제다.
현재 가이드상 헬퍼 교체는 사람의 조종실 작업이므로 AI가 셸 우회로 수행하는 과제로 만들지 않는다.

### 자료 묶음

| 입력 | 내용과 고정할 조건 |
| --- | --- |
| `requirements.json` | 대상 PC, 허용 루트, 실행 도구 허용 버전, 의존성 판본, 설정 값, 포트 후보, 기대 결과 |
| `app/` | 짧은 시험 프로그램: 설정 읽기, 로컬 상태 응답, 샘플 변환. 풀이·설치·복구 로직은 포함하지 않음 |
| `dependencies/` | 대상 OS·아키텍처에 맞춘 오프라인 의존성 묶음, 잠금 파일, 해시. 실제 자료를 확보해 검증한 뒤 고정 |
| `seed/` | 기존 설정, 사용자 메모, 이미 존재하는 입력 폴더, 기존 출력 파일 등 시작 상태 |
| `sample/` | 12건의 작은 입력과 독립적으로 고정한 기대 결과. 한글 파일명·공백·빈 입력 포함 |
| `manifest.json` | 입력 파일 해시·수집 시각·도구 판본·실자료/시험자료 구분 |

네트워크 다운로드 속도를 주된 평가 변수로 삼지 않도록 의존성은 미리 준비한다.
가능한 런타임과 의존성 버전은 실행 전 실측해서 확정하며 임의의 최신 버전을 요구하지 않는다.
준비 단계가 실패하면 이를 훈련 실행자의 설치 실패로 세지 않는다.

기본 시작 상태에는 ① 이미 맞는 입력 폴더 ② 유지해야 할 사용자 메모 ③ 없는 독립 실행 환경
④ 낡은 프로그램 설정 두 항목 ⑤ 이미 점유된 첫 포트 ⑥ 비어 있는 대체 포트를 넣는다.
점유 프로세스는 운영자가 소유한 시험 프로세스이며 PID·시작 시각·응답을 보존한다.
고정 조건은 정답표에, 동적인 포트·경로·PID는 실행 직전 상태 증거에 결합한다.

## 4. 훈련자가 작성할 IBL의 구조

아래는 책임 분해안이며 실행 가능한 코드나 새 관용구 등록 요청이 아니다.
실행 시 공개 교재와 `describe`로 실제 계약을 조회해 최초 완성 `.ibl` 초안을 보존한다.

| 부품 | 입력 → 반환 | 실패·외부 효과 |
| --- | --- | --- |
| 대상 확인 | 지정 PC·루트 → 고정 device_id·OS·cwd·env·연결 관측 | 불명확한 대상·다른 루트면 변경 전에 중단 |
| 차이 계산 | 요구 판본·현재 관측 → 유지/변경/보류 목록·의존 단계 | 관측 누락을 ‘없음’으로 바꾸지 않음, 읽기만 수행 |
| 준비·적용 | 계획·입력 묶음·대상 → 단계별 접수증·결과 참조 | 파일 전송·환경 구성·설정 변경, 단계마다 결과 보존 |
| 동작 검증 | 적용 결과·기대값 → 조건별 관측·미충족 이유 | 설정 재독·실행 경로/판본·서비스 응답·샘플 결과 확인 |
| 마무리 | 전체 관측·원본 지문 → 보고서·재개 정보·복원 절차 | 중앙 산출물 저장·재독, 시험 프로세스 정리 |

전체 연결은 **대상 확인 → 상태 관측 → 차이와 계획 → 준비·적용 → 동작 검증 → 보고·정리**다.
독립된 읽기는 묶고, 설치·설정·기동은 의존 순서로 실행한다. 장기 작업은 접수와 관측을 나눈다.
기존 `외부PC준비/작업실행/작업확인/파일보내기/파일가져오기`와 `scripts/remote_steps.py`를
공개 계약대로 조합할 수 있다. 전체 과제를 새 Python/셸 한 편에 숨기지는 않는다.
원격 OS 명령과 기존 단계 실행기는 부품이며, 판단·분기·결과 연결은 IBL 프로그램에 남긴다.

상주형은 매 작업에 cwd·env와 절대 실행파일을 전달한다. 앞 셸의 `cd`나 venv 활성화가 다음
셸에도 남는다고 가정하지 않는다. 설치와 검증을 별도 단계로 두어 후행 명령이 실패를 덮지 않게 한다.
접수증에는 device_id·request_id·task_ref·run_id·계획 판본·작업 루트를 연결해 보존한다.
API 응답 유실은 동일 작업 관측으로, 확정된 실패의 의도적 재실행은 새 시도 신원으로 구분한다.

## 5. 변형 하나 — 출력 설정 변경 중 접수 응답 유실

기본 실행의 산출물과 원격 상태를 보존한 뒤, 같은 실행자에게 아래 요구를 보낸다.

> 출력 위치를 제공한 새 폴더로 바꾸고 처리 설정 하나를 새 값으로 바꿔 줘. 실행 환경과 의존성,
> 입력 자료는 그대로 써도 돼. 기존 출력은 보존하고 새 설정으로 샘플을 다시 처리해 확인해 줘.
> 앞에서 진행한 작업의 결과가 늦게 오거나 연결이 끊겼다면 이미 끝난 일을 먼저 확인해서 이어가고,
> 이번에 바뀐 것과 다시 실행할 필요가 없었던 것을 구분해 줘.

이는 **요구 변경 시험**이다. 독립적인 견고성 관측으로, 운영자는 변경 작업 한 건이 접수된 뒤
훈련 운반 계층에서 첫 응답만 숨긴다. PC 네트워크·헬퍼·실서비스를 끊지 않는다.
응답 유실 시점·원래 접수증·실제 작업 기록은 검증자만 보존하며 실행자에게 가짜 성공을 주지 않는다.

기대 결과:

- 변경된 두 설정만 적용되고, 독립 실행 환경·의존성 설치는 다시 실행되지 않는다.
- 이미 접수한 동일 변경 작업이 중복 실행되지 않는다. 기존 참조로 결과를 확인한다.
- 새로운 설정이 필요한 단계와 서비스 재기동·동작 검증은 다시 수행한다.
- 옛 출력·사용자 메모는 보존되고 새 출력은 변경된 기대값과 일치한다.
- 판본이 바뀐 계획을 이전 run_id로 재사용하지 않는다. 과거 읽기 결과만으로 새 상태를 단정하지 않는다.

응답 유실 뒤 재관측은 같은 입력의 복구이며, 설정 변경에 따른 프로그램 수정과 비용을 따로 센다.
이 시험은 실제 네트워크 단절·PC 재부팅·프로세스 강제 종료의 검증을 대신하지 않는다.

## 6. 완료 판정과 독립 검증

| 조건 | 판정 증거 |
| --- | --- |
| C1 대상 정확성 | 모든 변경의 device_id·절대 경로, 원격 표식 일치, 중앙 미끼 불변 |
| C2 실행 환경 구성 | 지정 실행파일 경로·실제 버전·의존성 잠금/해시·import 결과 |
| C3 설정 보존 | 요구 항목의 실제 값, 미지정 설정·메모·기존 출력의 전후 지문 |
| C4 포트 충돌 처리 | 기존 점유 PID·응답 보존, 허용 대체 포트에서 이번 서비스의 고유 실행 표식 확인 |
| C5 업무 동작 | 샘플 12건의 결과·개수·이름·내용을 독립 기대값과 대조, 빈 입력 정상 처리 |
| C6 재개와 변경 | 접수 원장·단계 실행 횟수·실제 상태로 중복 적용 0, 무관한 설치 재실행 0 확인 |
| C7 전달 품질 | 보고서에 유지/변경/실패/미확인, 근거 참조, 재개 방법, 복원 절차가 있으며 파일 재독 가능 |
| C8 정리 | 이번 서비스의 PID·실행 표식을 확인하고 종료, 기존 점유 서비스 유지, 진행 작업 잔여 확인 |

각 실행의 **문법 검사 / 실행 종료 / 과제 달성**을 별도 기록한다.
성공 접수·exit 0·설정 파일 존재만으로 C2~C5를 통과시키지 않는다.
검증기는 실제 원격 파일·응답·작업 원장을 별도로 읽고 입력 판본에 묶인 기대값과 대조한다.
검증용 스크립트가 설정을 고치거나 실패 단계를 대신 수행해서는 안 된다.
동작 검증 전 정상 프로세스를 정리하지 않으며, 검증 증거를 보존한 다음 C8을 수행한다.

권한·런타임 부족을 정확히 보고하면 실패 보고 품질은 통과할 수 있지만 환경 구성은 미달/부분 달성이다.
검증되지 않은 조건은 미검증, 필수 조건에 실제 불일치가 있으면 미달로 남긴다.
모든 필수 조건을 충족한 경우에만 달성이다. ‘문제를 정직하게 보고했다’와 ‘설정을 완료했다’를 구분한다.

원본을 바꾸는 파일은 지정 시험 루트의 `data/_backups/YYYY-MM-DD_remote_setup/`에 보존한다.
복원 절차에는 원본 지문·변경 파일·새로 만든 환경·프로세스 식별자를 기록한다.
자동 전체 롤백은 가정하지 않는다. 변형 후 설정 파일 한 건의 복원·재독을 시험 사본에서 검증하며,
실행 환경 삭제·시스템 설정 복원의 성공으로 확대하지 않는다.

## 7. 두 실행의 비교와 예산

실행 시작 때 원장의 다음 번호 N을 배정한다. 설계 단계에서는 회차 번호를 예약하지 않는다.
작업 자료는 `outputs/long_sentence_imagination/YYYY-MM-DD_N회차/`, 요약·재현은
`docs/experiments/long_sentence_imagination/round_N/`와 누적 원장에 남긴다.

훈련자 IBL 기본→변형을 수행한 다음, 시스템 AI에게 자연어 기본→변형을 순서대로 맡긴다.
실행자별 원격 루트·포트·요청ID·프로세스·중앙 출력·대화·작업 원장을 분리하고 같은 seed를 준다.
훈련자의 설치가 시스템 전역에 영향을 줬다면 후속 AI와 동일 조건 비교를 중단하고 오염을 기록한다.
시스템 AI에는 공개 계약 조회를 허용하되 훈련자의 프로그램·진단·기대값을 주지 않는다.
풀이가 셸/Python 중심이면 실제 달성과 IBL 조합 능력을 나누어 기록한다.
모든 실행은 지원하는 진입점에서 `origin:"training"`을 명시한다.

기본 상한은 준비·작성·실행·변형·진단 합계 **60분**이다.
배분안은 준비 10분, 훈련자 작성·기본 12분, 훈련자 변형 8분, 독립 AI 기본 15분,
독립 AI 변형 8분, 검증·원인 정리 7분이다. 준비가 길어졌다고 자동 연장하지 않는다.
종료 보고·증거 보존·자원 정리 시간은 별도로 기록한다. 같은 원인으로 두 수정 주기 연속
진전이 없으면 그 경로를 멈추고 최소 재현과 미완료 조건을 보존한다.

비교표에는 달성 조건별 결과, 작성·검사·실행·변형 시간, 수정 횟수, 계약 탐색과 수작업 개입,
원격 접수/관측 횟수, 단계별 실제 실행 횟수, 전송량, 관측 가능한 역할별 입력·출력·캐시 토큰을 담는다.
훈련자 토큰 미측정은 미상으로 둔다. 성공 재사용과 불필요한 재설치·전체 재조회·출력 재전송을
구분하며, 한 번의 결과로 시간·토큰 절감률을 일반화하지 않는다.

## 8. 다음 회차로 남길 확장

기본과 변형이 끝난 뒤에만 별도 회차로 선택한다. 이번 60분에 모두 넣지 않는다.

- 실제 의존성 설치 실패 → 원인 보완 → 실패 단계만 재시도, 검증만 실패한 경우와 구별.
- 프로세스 종료 기록 유실 → 실제 파일·프로세스 확인 → 미확정 상태에서 자동 재실행하지 않기.
- 관리자 권한이 필요한 설정 → 원격 OS 인증 또는 사람 작업 경계, 거절 뒤 부분 완료 유지.
- 실제 IndieBiz 업데이트 조리법 또는 다른 OS에 적용해 공통 능력의 전이를 확인.

발견한 문제는 작성/발견·계약·구현·환경 전제·요구 해석·비용으로 분류한다.
최근 원격 실행 수리의 되먹임 증거와 신규 과제 증거를 구분한다. 훈련 실행을 모두 회수하기 전에는
공유 런타임을 수리하지 않는다. 설계만으로 지원 여부나 개선 효과를 확정하지 않는다.
