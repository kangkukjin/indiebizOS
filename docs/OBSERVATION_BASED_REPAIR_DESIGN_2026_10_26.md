# 관측을 되살리는 수리 설계

작성·보완: 2026-10-26. **상태: 순차 구현 중. 단계별 결과는 §12.**
조사 기준: 정본 main `5be795f5a3e87a4e00f5dc10056db5da7b39477a`.
목적: 오류를 일으킨 사례를 금지하는 대신, 사용자 의도와 실제 대상·실행 결과를 보고 수정할 수 있게 한다.
상위 기준: [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md), [구조 수렴 설계](IBL_SYSTEM_CONSOLIDATION_DESIGN.md).

## 1. 수리 방식에서 반성할 점

사용자의 지적은 “규칙이 있으면 안 된다”가 아니다. 앞이 보이지 않아 벽에 부딪혔을 때,
그 지점에서 핸들을 꺾는 규칙을 외우게 하는 것으로 시야의 결함을 덮지 말라는 뜻이다.
이번 조사에서는 문자열·말투·오류 로그·호출 횟수가 실제 의미나 결과를 보기도 전에
판정을 끝내는 경로를 확인했다. 일부는 오작동을 막기 위해 예외를 더하면서 생겼다.

수리할 때 다음 세 가지를 혼동했다.

- **관측과 판정:** “콘솔 오류가 있었다”를 “화면이 실패했다”로, “같은 호출이다”를 “진척이 없다”로 바꾸었다.
- **출처와 문체:** 발화자의 신원을 확인하는 일에 존댓말·접속사 같은 표현상의 특징을 대신 사용했다.
- **응답의 적절성과 작업의 달성:** 미완료를 정확하게 설명한 응답의 승인을 원래 작업의 성공으로 저장했다.

기존 시험도 이 구분을 충분히 지키지 못했다. “키워드가 있으면 초기화된다”,
“사전 점검 문자열이 있으면 모델을 부르지 않는다”를 통과 조건으로 삼으면,
잘못된 지름길이 안정적으로 작동한다는 사실만 확인하게 된다.
새 수리는 원래 사용자 목적을 보존하는지를 시험하고, 바뀐 구현 자체를 정답으로 외우게 하지 않는다.

목표 경로는 **요청·대상 확인 → 실행 → 바뀐 대상 확인 → 원래 목적과 대조 → 필요한 부분 수정**이다.
이는 매 단계에 새 AI를 붙이자는 뜻이 아니다. 이미 있는 실행자·증류기·검수기에 필요한 증거를
전달하고, 그 앞에서 의미 판단을 끝내 버리는 분기를 제거한다.

## 2. 확인한 사실과 판단의 범위

| 사례 | 확인한 사실 | 이번 설계의 판단 |
| --- | --- | --- |
| 세션 초기화 | 의식 OFF에서 부정문·인용문도 초기화 키워드로 판정된다. | 의미 판독을 문자열로 대체한 결함이다. |
| 깊은 기억 | 존댓말 때문에 사용자 진술이 증류 전에 탈락하고, 접속사 때문에 근거 있는 사실도 뒤에서 거절된다. | 발화 출처와 문맥 판단을 표현 규칙이 가로챈다. |
| 화면 검수 | 같은 화면이라도 콘솔 오류 한 줄이 있으면 이미지를 읽기 전에 0점·실패가 된다. | 관측 자료가 최종 판정으로 승격됐다. |
| 반복 조언 | 반환 결과를 받지 않는 함수가 같은 호출의 결과도 같다고 단정한다. | 재관측을 방해할 수 있는 조언이다. 실제 작업 중단의 빈도는 미측정이다. |
| 상시 프롬프트 | 특정 과제의 교훈이 실행·평가 프롬프트에 반복되어 모든 작업에 들어간다. | 중복과 적용 범위를 줄일 대상이다. 성능 악화 자체를 실측한 것은 아니다. |
| 검수 승인/달성 | 오늘 표시는 “검수 승인”으로 고쳤지만 내부에서는 승인으로 `achieved=true`를 만든다. | 표시 수리만으로 끝내면 회상·학습의 의미 혼동이 남는다. |

첫 다섯 사례가 모두 오늘 새로 생긴 것은 아니다. 오늘 수리와 직접 연결되는 마지막 사례는
`3ce94f087d510d267677bf439b46c86f3090150f`의 표시 변경과 현행 내부 경로를 함께 검토한 결과다.
오늘의 원격 갱신 수명 관리·부팅 프로세스 식별·공통 헬퍼 상태 조회는 실제 상태를 더 확인하는
수리이므로 유지한다. 정지 확인·버전 대조·권한·조건부 쓰기처럼 실제 계약을 지키는 규칙까지 없애지 않는다.

조사에서는 실제 함수 호출과 임시 HTML 렌더링으로 반례를 확인했다. 사용자 세션 초기화,
영속 기억 쓰기, 외부 PC 갱신은 실행하지 않았다. 아래 예시는 구현의 인수 시험으로 남길 대상이며,
이 문서를 작성한 것으로 수리가 끝난 것은 아니다.

## 3. 판단의 소유자를 되돌리는 원칙

| 책임 | 소유자 | 넘겨야 할 것 |
| --- | --- | --- |
| 무엇을 원하는가 | 사용자 요청과 기존 의도 해석 경로 | 원문, 현재 대화 범위, 사용자가 바꾼 조건 |
| 무엇이 일어났는가 | 도구·실행·저장 계층 | 실제 결과, 실패, 대상과 판본, 원문 참조 |
| 그 결과가 목적에 맞는가 | 기존 실행자·해당 검수기 | 대상 자체와 관련 증거, 남은 불확실성 |
| 무엇을 기억할 수 있는가 | 기존 증류기와 저장 경계 | 발화자·인용 관계·근거 범위·성과 범위 |

도구는 관측 사실을 계산하고 보존한다. 모델이 판단해야 할 의미를 도구가 대신 확정하지 않는다.
반대로 파일 부재·형식 오류·권한 부족·판본 충돌은 모델이 추측해서 통과시킬 일이 아니다.
이 구분을 별도 범용 정책 엔진이나 새 검사기 목록으로 구현하지 않는다.

## 4. 세션 초기화: 문구로 사용자의 뜻을 확정하지 않는다

**현행 경로:** `backend/cognition/cognitive_consciousness.py`의 `_is_reset_keyword`가
공백을 지운 문자열에서 문구를 찾는다. 의식 OFF의 `_decide_request_type`은 이 결과로
`SESSION_RESET`을 반환하고, `agent_pipeline.py`가 실행자 없이 초기화 핸들러로 보낸다.
길이 60자·위임 태그 예외와 “처음부터 다시”의 전체 일치 예외가 이미 붙어 있다.

확인한 반례는 다음 세 요청 모두 초기화로 판정된다는 것이다.

- “세션 초기화하지 말고 기존 작업을 이어가세요.”
- “새 세션을 만들지 마세요.”
- “\"그만하자\"라는 표현을 영어로 번역해주세요.”

**수리 결정:** OFF 경로의 키워드 초기화와 그 예외 묶음을 제거한다.
의식 ON에서는 현재의 의미 분류 경로를 사용하고, 명시적 초기화 UI/API는 유지한다.
OFF에서는 자연어를 일반 실행자에게 전달하며, 이 문구만으로 하네스가 초기화하지 않는다.
현재 일반 실행자에 안전한 세션 초기화 제어 통로가 있다고 가정하지 않는다.
따라서 첫 구현의 명시적 동작 변경은 **OFF에서 자연어 한마디로 자동 초기화되는 기능의 종료**다.
이 모드에서 실제 초기화는 기존 UI/API로 수행하며, 실행자는 수행하지 않은 초기화를 완료했다고 답하면 안 된다.

ON/OFF 기능 대칭만을 위해 분류 AI를 매 턴 추가하거나 새 IBL 낱말을 만들지 않는다.
OFF 자연어 초기화를 다시 지원하려면 기존 실행자의 구조화된 세션 제어와 실행 후 확인을
별도 변경으로 연결해야 한다. 키워드 지름길을 임시 호환 경로로 남기지 않는다.

핸들러의 성공 보고도 고친다. 현재 매핑 정리 예외를 무시하고 같은 성공 문구를 반환하는 부분은
실제 결과를 반환하도록 바꾸고, 성공 때도 대화 기록·영속 과제 삭제로 확대 해석하지 않는다.
기존 API 두 곳과 자연어 핸들러가 같은 세션 범위·정리 결과를 사용하도록 맞춘다.

**검증:** 부정·인용·번역·위임 본문은 일반 요청으로 남고 세션 매핑이 바뀌지 않아야 한다.
명시 UI 초기화는 해당 세션 범위만 바꾸고 실패하면 실패를 반환해야 한다.
ON의 의미 분류는 위 반례와 실제 초기화 요청을 함께 검증한다.
문구만 바꾼 미사용 사례도 포함하며, `_is_reset_keyword` 자체를 유지하는 시험은 대체한다.
OFF의 일반 요청 경로가 초기화 핸들러·매핑 정리 함수를 호출하지 않는지도 경계 시험으로 확인한다.
전용 초기화 도구가 없다는 사실만으로 실행자가 매핑에 접근할 수 없다고 보장하지 않는다.
셸·스크립트·HTTP 같은 일반 능력의 접근 가능성은 별개다. 이번 수리의 보장은 자연어 문구가
하네스의 초기화를 자동 발동하지 않는다는 범위이며, 수행 여부와 완료 보고의 일치도 함께 시험한다.

## 5. 기억: 출처는 보존하고 말투의 거부권은 없앤다

**현행 경로:** `backend/cognition/memory_evidence.py`의 `durable_source_units`가
존대 표현·문서 형태를 이용해 `eligible=false`를 만든다.
`cognitive_distill.py`는 적격 단위가 없으면 모델을 부르기 전에 반환한다.
`unresolved_reference`는 “그리고” 등으로 시작하는 사실을 증류 뒤에도 거절할 수 있다.
`_append_durable_unit`의 적격 조건에는 `not request`도 있어 요청 문체가 별도로 탈락한다.

확인한 반례:

- “제 선호를 말씀드리겠습니다. 저는 앞으로 모든 답변을 한국어로 받기를 원합니다.”가 전달문으로 탈락한다.
- “저는 아버님께 매주 일요일에 전화합니다.\n\n저는 채식을 합니다.”에서 존대 표현의 영향이 다른 문단까지 번진다.
- “그리고 저는 땅콩 알레르기가 있습니다.”는 원문 근거가 있어도 접속사 때문에 거절된다.
- “앞으로 모든 답변은 한국어로 해주세요.”는 `basis=request`, `eligible=false`가 된다.
  “저는 앞으로 모든 답변을 한국어로 받기를 원합니다.”만 입력하면 이 요청 정규식에는 걸리지 않는다.
  앞의 존대 반례와 원인이 다른 반례이며, 의미가 비슷한 선호도 표현에 따라 다르게 처리된다.

**수리 결정:** 신뢰할 수 있는 입력 경계의 `utterance_author`, 원문 ID·해시·위치,
인용 범위는 보존한다. 말투·길이·접속사·요청 문체는 작성자의 신원이나 사실의 부적격을 확정하지 못한다.
이 특징 때문에 모델 도달 전 탈락시키는 경로와 모델 뒤의 일괄 거절을 제거한다.

기존 증류 호출이 발화의 주체·인용·채택 여부를 원문 안에서 판단하고 선택한 근거를 반환한다.
저장 경계는 “반환한 근거가 실제 원문에 있는가, 그 원문이 누구의 발화인가”를 검증한다.
존댓말을 다른 언어 규칙으로 대체하거나 사실을 모두 자동 저장하는 방식은 쓰지 않는다.
`not request`를 제거한 뒤에는 기존 증류기의 `retention/future_use` 판단으로 일회성 작업 지시와
지속 선호를 구분한다. “오늘 이 답변만 한국어로 해주세요”를 영구 선호로 바꾸지 않으며,
요청 한 문장에 지속 선호와 당장의 작업이 함께 있으면 근거·적용 범위를 보존한다.
명령형 선호만 살리는 새 문구 목록을 두지 않는다. 주체·지속성·범위의 해석은 같은 증류 호출이 맡는다.

대명사가 앞 문맥을 필요로 하면 현재 증류 입력에 이미 있는 문맥·원문 참조를 활용한다.
범위 밖의 문맥이 필요하면 기존 원문 조회 경로로 필요한 부분만 확보한다.
이를 확보할 수 없을 때는 그 사실의 저장을 보류한다. “그리고”만으로 미해결이라고 판정하지 않는다.
인용된 타인의 선호는 사용자 선호가 아니다. 사용자가 그 선호를 채택했다면 인용과 채택 발화를
함께 근거로 남긴다. 모델의 문장만 있고 사용자 채택 근거가 없으면 사용자 사실로 저장하지 않는다.

**검증:** 같은 사실의 평서·존대·접속사 변형은 같은 판단 기회를 얻어야 한다.
반대로 타인의 자기소개·도구 결과·예약 및 에이전트 발화는 사용자 기억으로 둔갑하지 않아야 한다.
명시 채택, 부정, 철회, 지속 선호의 요청형/진술형, 일회성 요청, 실제로 지시 대상이 없는 문장,
원문 ID 위조를 함께 시험한다.
순수 근거 검증은 결정론 시험으로, 주체 해석은 기존 증류기를 통한 작은 의미 시험으로 나눈다.

## 6. 화면 검수: 보이는 대상을 먼저 읽는다

**현행 경로:** `data/packages/installed/tools/media_producer/render_artifact.py`가
콘솔 오류·요청 실패·빈 화면 추정 등을 `prescreen` 문자열로 만든다.
`vision_read.py`의 `critique_image`는 문자열이 비어 있지 않으면 이미지 로딩 전
`passed=false`, `score=0`으로 종료한다. 운영 관용구 `data/idioms/retirement_13.ibl`의
화면검수도 이 값을 전달하므로 실제 운영 경로에 연결되어 있다.

재현에서는 동일한 800×600 보고서 HTML 두 개 중 하나에 선택적 분석 기능의
`console.error` 한 줄만 추가했다. RGB 픽셀 해시는 같았지만 오류가 있는 쪽은
이미지 읽기 0회·모델 호출 0회로 실패했다. 출력 화면의 결함을 확인한 실패가 아니다.

**수리 결정:** 렌더 결과를 읽을 수 있는지와 읽은 결과가 목적에 맞는지를 구분한다.
파일 부재·디코딩 실패는 “검수 불가”라는 실행 결과로 반환한다. 품질 0점으로 바꾸지 않는다.
이미지를 읽을 수 있으면 기존 시각 검수 호출 한 번에 이미지·사용자 목적·진단 정보를 함께 준다.
콘솔 오류·잉크 비율·깨진 이미지 탐지는 증거로 유지하되 각각이 영향을 주는 대상을 밝힌다.
허용 콘솔 문구 목록이나 오류 종류별 무시 규칙을 추가하지 않는다.

`prescreen`의 생산자·소비자 계약을 같은 변경에서 고친다. 기존 문자열을 진단 자료로 받는
호환은 가능하지만, 비어 있지 않다는 이유만으로 실패하는 분기는 전부 없앤다.
`ibl_actions.yaml`의 설명, 핸들러 도움말, 운영 관용구를 함께 정렬하고 파생물은 빌드한다.
빈 화면도 요청이 빈 캔버스인지 보고 판단하며, 수식 오류 표시는 사용자가 검토하려는 오류 예제일 수 있다.

관용구의 실행 정본도 확인한다. 현행 `ibl_v2_store.installed_definitions`는 `.ibl` 파일을
실행 시 다시 읽는 대신 함수 카탈로그를 읽는다. 본문을 바꾸는 경우 파일 편집만으로 배포가 끝나지 않는다.
현재 `function_id/revision`을 읽고 `function_library.register`의 `expected_revision`으로
같은 정의를 개정한 뒤, 실제 해소된 원문·판본과 호출 결과를 확인한다.
기존 `prescreen` 인자를 그대로 유지해 관용구 본문 변경이 없다면 불필요한 개정은 하지 않는다.
`DUPLICATE_LIBRARY`는 같은 이름의 정의가 겹칠 때의 오류이며 파일 편집 자체의 결과는 아니다.

**비용 변화:** 읽을 수 있는 이미지가 사전 진단 때문에 탈락하던 경우는 비전 호출 0회에서
정상 검수 경로로 바뀐다. 파일 부재·디코딩 실패는 계속 모델 호출 없이 검수 불가로 끝난다.
이 변경은 관측 누락을 고치는 비용 증가일 수 있다. 정상 경로의 재시도·대체 모델 호출을 포함한
실제 호출 수, 입력·출력 토큰과 경과 시간을 기존 기준선과 비교한다. 화면검수의 두 뷰포트도
각각 집계한다. 불필요한 재수리가 줄어 총비용이 회수되는지는 별도로 측정한다.

**검증:** 동일 픽셀·상이한 부가 로그에서는 두 경우 모두 실제 이미지가 검수기에 도달해야 한다.
기대 판정은 화면과 목표의 관계로 정하며 모델의 점수가 항상 똑같아야 한다고 강제하지 않는다.
정상 화면, 실제 잘림·누락, 의도한 빈 화면, 의도치 않은 빈 화면, 파일 읽기 실패를 구분한다.
`test_critic_prescreen_shortcircuit_calls_no_model`은 잘못된 지름길을 보존하므로 새 계약 시험으로 대체한다.

## 7. 반복: 같은 동작이 같은 결과라는 단정을 제거한다

**현행 경로:** `backend/base/repeat_guard.py`의 `advise(key, signature)`는 결과를 받지 않는다.
`system_tools.py`와 `mcp_server.py`가 이를 사용하고, 3·5·8회에 행동 변경 또는 결론을 권한다.
턴 경계에서도 체인을 유지한다. 결과가 10→20→30→40→50으로 진행되는 상황을 호출자가 알고 있어도
그 정보는 이 함수에 전달할 수 없다. 조언일 뿐 강제 차단은 아니지만 모델의 다음 행동에 영향을 준다.

한편 `conscious_supervisor.py`에는 이미 입력·결과·오류를 보는 관측과 반복 검출이 있다.
이쪽도 완성된 답은 아니다. `_job_observation`이 작업을 `job_id/status`로 축약하므로
실제 진척이 결과에 있어도 놓칠 수 있다. 단순히 기존 감독기로 옮겼다고 수리 완료로 보지 않는다.

**수리 결정:** 기존 `advise`에 실제 결과를 전달하여 OFF에도 관측을 남긴다.
최소 계약은 `advise(execution_key, signature, result_digest)`로 정한다.
`execution_key`는 에이전트뿐 아니라 작업과 이번 실행을 식별한다. 실행 시작에 빈 상태를 만들고,
종료·취소·예외의 후처리에서 버린다. 다음 턴에 이전 횟수를 넘기는 전역 체인은 제거한다.

직접 경로는 호출 전 판정을 결과 취득 뒤로 옮기고, MCP 경로도 절단·조언 추가 전의 실제 결과에서
다이제스트를 만든다. 자신의 조언이나 새로 부여한 증거 ID를 결과로 해싱하지 않는다.
같은 호출과 결과의 연속 횟수만 세며, 결과가 다르면 그 연속 횟수를 초기화한다.
출력은 “같은 입력으로 같은 결과를 N회 관측했다”는 사실이며 행동 변경·종료 명령은 제거한다.
기존 통지 빈도 제한은 표시량 조절에만 사용하고, 횟수에 실패나 중단의 의미를 부여하지 않는다.

**결과의 차이는 진척의 증명이 아니다.** 타임스탬프나 난수만으로도 해시는 달라지고,
같은 결과도 정상적인 대기일 수 있다. 이 공용 함수가 보장하는 것은 관측의 동일성까지다.
결과 전체의 변화가 무엇을 뜻하는지 모르면 진척이라고 보고하지 않는다. 생산자가 정의한 진행량·
산출물 판본은 기존 작업 상태 관측에 남기고, `_job_observation`의 과도한 축약을 고친다.
임의 필드 삭제나 도구 이름별 예외표로 진척을 만들어 내지 않는다.

ON에서는 같은 관측을 기존 감독기에 전달하고, OFF에서는 중립적인 통지와 실제 결과를 실행자에게 돌려준다.
감독기가 있는 경로에서 같은 사건을 이중 집계·통지하지 않는다. 기존 감독기의 여러 액션에 걸친
주기 검출은 단순한 동일 호출 집계와 역할을 구분하고 원 결과·대기 조건·시간 한계를 참조해 판단한다.
OFF를 위해 상시 감독 AI를 추가하지 않는다. 현행 가드도 조언이므로 이를 결과에 근거한 조언으로 고친다.
실행 한도·시간 제한은 별도 책임으로 유지한다.

**검증:** 동일 호출의 진행량 증가, 같은 상태를 유지한 정상 대기, 같은 실패의 반복,
여러 액션으로 구성된 실제 반복, 시각만 달라지는 결과, 새 작업에서 같은 호출 재사용을 구분한다.
재관측이 필요한 시험에서는 결과를 계속 읽을 수 있어야 하며, 무진척 시험에서는
ON의 기존 감독기에 실제 결과와 대기 조건이 전달되는지 확인한다.
OFF에서는 같은 결과의 반복 통지가 추가 모델 호출 없이 도달하고, 달라진 결과를 진척이라고
단정하지 않으며, 실행 종료·취소·예외 뒤 상태가 정리되는지 직접 경로와 MCP 양쪽에서 확인한다.

## 8. 상시 프롬프트: 사례별 교훈의 적용 범위를 줄인다

**현행 경로:** `data/common_prompts/base_prompt_v6.md`는 `prompt_builder.py`에서 상시 조립된다.
특정 분석·계획 과제에서 나온 분모·인력시간·물리적 페이지·비열등·선택 상태 등의 세부 지침이
여기에 있고, `final_evaluator.py`의 `POLICY/FINAL_POLICY`에도 유사 지침이 누적되어 있다.
각 지침의 내용이 틀렸다는 뜻은 아니다. 모든 작업이 이 설명을 반복해서 읽는 배치가 문제다.

**수리 결정:** 상시 지침은 현재 사용자 목적, 권한, 실제 증거, 실행 후 확인, 불확실성 보고처럼
분야가 바뀌어도 필요한 책임을 간결하게 설명한다. 정확한 형식·보안·실행 계약은 소유 계층에 남긴다.
과제별 지식은 기존 가이드·검색·사례 회상 경로로 돌리고 해당 작업에서만 회수한다.
모든 세부 규칙을 새 파일로 옮긴 뒤 그 파일을 항상 읽히는 방식은 수리가 아니다.

실행자와 평가자에게 같은 긴 교훈을 복사하지 않는다. 실행자는 목적에 맞게 작업하고,
평가자는 그 목적과 결과·근거를 대조하도록 역할을 구분한다.
숫자·단위처럼 코드가 정확히 계산할 수 있는 사실은 기존 값 의미·계산 경로를 사용한다.
문구 검사를 늘려 특정 단어를 금지하거나 새 “좋은 프롬프트 검사기”를 만들지 않는다.

**검증:** 과거 문제를 드러낸 과제와 다른 분야의 미사용 과제를 함께 비교한다.
상시 입력 분량 감소와 필요한 가이드의 실제 회수를 확인하고, 결과 품질·완료 시간·전체 토큰을
기록한다. 글자 수 감소만으로 토큰·속도 개선을 선언하지 않는다.
먼저 앞 절들의 구조를 고쳐서 더 이상 필요 없는 보상 지침부터 제거한다.

## 9. 검수 승인과 원래 목표 달성을 내부부터 구분한다

**오늘 수리의 의미:** 에피소드 UI의 `ACHIEVED` 표시는 “달성”에서 “검수 승인”으로 바뀌었다.
정직한 중단 보고가 승인되어도 원래 작업은 끝나지 않았을 수 있다는 점을 드러낸 올바른 표시 수리다.
다만 `conscious_supervisor.py`는 여전히 승인에서 `ACHIEVED`와 `achieved=true`를 만들고,
`thread_context.py`의 평가 결과를 회상·증류 경로가 소비한다.
`framing_inheritance.py`의 이전 달성 판단과 `cognitive_distill.py`의 기억 승인 판단에도 영향이 있다.

현재 영속 과제의 `done` 쓰기는 `done_request`와 별도의 `pursuit_status` 승인·버전 확인도 요구한다.
따라서 “응답이 승인되면 모든 과제가 자동 완료된다”고 진단해서는 안 된다.
수리 대상은 이미 나뉜 일부 완료 경계를 없애는 일이 아니라, 공통 기록에 남은 의미 혼합이다.

**수리 결정:** 기존 평가 결과 안에서 다음 두 질문을 별도 필드로 기록한다.
별도 평가 서비스를 만들거나 같은 요청을 두 모델에 중복 판정시키지 않는다.

| 필드 | 값 | 뜻 |
| --- | --- | --- |
| `review_status` | `APPROVED / REWORK / UNKNOWN / NOT_RUN` | 현재 응답·산출물의 검수가 승인됐는가. |
| `goal_status` | `ACHIEVED / NOT_ACHIEVED / UNKNOWN` | 현재 유효한 사용자 목표를 실제로 충족했는가. |

부분 완료·외부 차단은 별도 상태를 계속 늘리는 대신 미충족 항목·이유·증거에 기록한다.
검수 미실행은 `NOT_RUN`, 목표 달성 증거가 없으면 `UNKNOWN`이다. 이를 자동 실패로 취급하지 않는다.
기존 `PENDING_EXECUTION/PENDING_REVIEW` 같은 진행 단계는 이 두 판정과 구분해 유지한다.

예를 들어 “외부 PC 갱신”을 요청했는데 접근 불가를 정확히 보고했다면
`review_status=APPROVED`, `goal_status=NOT_ACHIEVED`가 가능하다.
반대로 요청 자체가 “갱신할 수 없는 이유를 조사해 보고하라”라면 같은 종류의 보고가 목표 달성일 수 있다.
실패를 포함한 답변이라는 이유만으로 미달로 분류하지 않는다. 원래 요청과 관측 결과의 관계가 기준이다.

### 9.1 기준·판정·전달의 연결

`supervisor_handoff.criteria_contract`의 사용자 원문·명시 조건·기준 출처를 보존한다.
fallback은 답변 또는 복구 방식이며, 사용자의 목표를 “중단 사유 보고”로 몰래 바꾸는 근거가 아니다.
사용자가 실제로 목표를 바꾼 경우에는 기존 작업·기준 판본과 변경 근거에 연결한다.
평가자가 임의로 기준을 추가하거나 면제하지 않는 현행 제한은 유지한다.

기존 평가 호출에서 응답 검수와 목표 충족 항목·근거를 함께 반환하게 한다.
최종 하네스는 검수한 응답·산출물 판본과 실제 전달 결과를 연결한다.
사용자가 요구한 전달이 실패하면 그 목표를 달성했다고 저장할 수 없다.
검수 뒤 응답을 바꾸는 경로가 있다면 그 변경의 범위와 최종 판본을 반영하며,
수정 전 승인만으로 수정 후 전체 내용이 검수됐다고 기록하지 않는다.

### 9.2 함께 바꿔야 할 소비자

| 소비자 | 바뀌어야 할 계약 |
| --- | --- |
| `conscious_supervisor.py`, `final_evaluator.py` | 승인→달성의 자동 변환을 제거하고 같은 평가에서 두 판정을 만든다. 중간·최종 기록을 구분한다. |
| `thread_context.py`, 증류 큐, 에피소드 저장·조회 | 새 필드와 근거·판본을 비동기 작업까지 보존한다. 누락을 `true`로 채우지 않는다. |
| `framing_inheritance.py` | 다음 요청의 완료 전제는 명시적 목표 달성 근거를 사용한다. 응답 승인만으로 끝난 일로 취급하지 않는다. |
| `cognitive_distill.py`, 경험 증류·검색 | 실패 중 확인한 사용자 사실과 부분 성공을 보존할 수 있지만 전체 절차의 성공 사례로 승격하지 않는다. |
| 영속 과제 완료·수리 계속하기 | 현행 명시 완료 요청·판본 확인을 유지하고, 전체 과제 기준의 달성 근거를 요구한다. |
| 에피소드 UI·원격 런처 | 검수와 목표를 각각 표시한다. 기존 “검수 승인”을 다시 “작업 완료”로 축약하지 않는다. |

원래 요청의 사용자 사실을 기억하는 일은 작업 성공과 독립이다. 목표 미달이라는 이유만으로
출처가 분명한 사실까지 모두 버리는 새 일괄 관문을 만들지 않는다.
부분 성공 절차는 성공한 단계·입출력·한계를 함께 재사용하고 전체 목표의 성공 근거로 쓰지 않는다.

### 9.3 기존 기록과 검증

옛 `ACHIEVED`는 두 의미가 섞여 있으므로 일괄 성공·일괄 실패로 이관하지 않는다.
옛 값은 역사로 보존하고, 새 판정 필드가 없는 기록의 목표 상태는 미확정으로 읽는다.
UI는 이전 기록의 검수 결과임을 밝히고, 성공 전제가 필요한 재사용 때는 기존 증거를 다시 확인한다.
읽기 호환 때문에 새 기록을 다시 단일 `achieved`에 접어 넣지 않는다.

시험은 최소한 실제 완료, 정직한 중단 보고 승인, 조사 보고 자체의 완료, 부분 성공,
평가 미실행, 전달 실패, 완료 검수 중 과제 판본 변경, 구기록 조회를 포함한다.
각 경우의 UI뿐 아니라 큐를 거친 회상·기억·영속 과제 상태까지 확인한다.

## 10. 구현 순서와 제거 범위

| 순서 | 작업 묶음 | 같은 변경에서 없앨 것 | 완료 증거 |
| --- | --- | --- | --- |
| 1 | 화면의 실제 관측 복원(§6) | 사전 문자열의 자동 0점 분기·그 계약의 교재와 시험 | 실제 이미지 판독·운영 관용구 판본 확인과 호출 수·시간·토큰 변화 기록 |
| 2 | 검수/목표 기록 분리(§9) | 승인→전체 성공 변환·누락 값의 성공 기본값 | 저장·큐·회상·UI·과제 완료가 서로 같은 의미를 사용함 |
| 3 | 세션 의도와 실행 결과(§4) | OFF 초기화 키워드·길이/문구 예외·실패 시 성공 응답 | 반례에서 세션 유지, 명시 제어의 성공·실패가 실제 매핑과 일치함 |
| 4 | 기억 출처와 의미 해석(§5) | 말투/접속사/요청 문체의 강제 탈락·문단 간 오염 | 지속 선호·일회성 요청·타인 발화를 구분함 |
| 5 | 반복 관측 통합(§7) | 결과 없는 조언·행동 변경 명령·턴 간 전역 체인 | ON/OFF 모두 결과 기반 관측, 변화와 진척 구분, 중복 집계 없음 |
| 6 | 상시 지침 정리(§8) | 구조 수리를 대신하던 사례 지침·중복 상시 주입 | 필요한 판단을 유지하며 불필요한 상시 입력 감소 확인 |

각 묶음은 생산자·소비자·시험·교재까지 닫은 뒤 정본에 반영한다. 절 번호는 실행 의존성 자체가 아니다.
§9는 기록과 소비자를 함께 바꿔야 하므로 UI만 먼저 바꾸고 내부 정렬을 완료로 처리하지 않는다.
진행 중 범위가 커지면 새 관리 계층을 먼저 만들지 말고, 기존 경계에서 닫을 수 있는 계약으로 다시 나눈다.

여러 backend 소비자의 일관된 반영은 필요하지만 “한 스크립트로 쓰면 안전하다”를 새 규칙으로 두지 않는다.
파일 여러 개의 순차 쓰기는 한 스크립트에서도 원자적이지 않다. 현행 `restart_controller.py`는
검사 뒤 코드 지문이 바뀌면 단계에 따라 보류하거나 `FAILED`로 남긴다.
소비자 변경·정적 검사·몸 번들을 마친 일관된 파일 집합을 기준으로 기존 재기동 절차를 사용하고,
그 기동 중에 같은 집합을 다시 편집하지 않는다. 최종 세대·지문·준비 상태를 확인한다.
수동 표식을 만들거나 제어자를 우회하는 절차는 추가하지 않는다.

## 11. 검증과 수리 완료의 기준

조사 때 실행한 기존 관련 회귀는 10개 통과했다. 이는 현행 동작의 기준선이며 새 수리의 통과 증거가 아니다.
특히 화면의 사전 탈락 시험처럼 폐기할 동작을 정답으로 삼은 항목이 들어 있다.
이 설계 작성에서는 런타임 코드를 바꾸지 않으며, 구현 후 결과를 앞당겨 주장하지 않는다.

구현에서는 기존 pytest·전이 소비자 선택 절차를 사용하고 새 시험은 해당 모듈의 시험 파일에 둔다.
코드·어휘·화면 변경에 해당하는 빌드와 타입 검사를 실행한다.
의미 판단을 모의 응답만으로 검증했다고 하지 않는다. 경계 전달은 결정론 시험으로 고정하고,
의미 판단은 현재 설정의 실제 모델로 소수의 원사례·미사용 변형·반대 사례를 확인한다.
실행하지 못한 모델·외부 기기·환경은 미검증으로 기록한다.

완료를 판단할 때는 다음을 함께 확인한다.

1. 원래 실패가 없어졌고, 정상적인 재관측·부분 성공·대기·인용·부정을 해치지 않는다.
2. 판단자가 필요한 원문·이미지·실행 결과를 실제로 받으며, 원본과 판본을 확인할 수 있다.
3. 바뀐 대상의 재관측이 최종 결과에 반영되고, 관측하지 못한 것은 미확정으로 남는다.
4. 대체한 규칙·어댑터·상시 지침이 퇴장했다. 두 경로를 계속 관리하는 상태를 완료라고 하지 않는다.
5. 품질·실제 완료 시간·전체 모델 사용량의 검증 범위를 밝힌다. 구조적 개선과 비용 개선의 실증을 구분한다.
6. 구기록 계승 사례에서 자동 증거 재확인·사용자 되묻기·실제 작업 재수행의 빈도를 각각 기록한다.
   비교 대상 계승 건수를 분모로 밝히고, 추가 시간·모델 사용량도 측정한다. 과거 판정 미확정이
   자동 재수행 명령이 되어서는 안 된다. 기존 증거를 먼저 재확인하고 남은 불확실성만 다룬다.

되돌림은 변경 묶음 단위로 하며, 실패한 수리 위에 사례 예외를 덧붙이지 않는다.
판정 기록을 바꾼 뒤 되돌릴 때도 새 증거·구기록을 삭제하거나 과거 성공을 소급 확정하지 않는다.
실패 원인과 관측을 보존하고 해당 계약의 생산자·소비자를 함께 복원한다.

이 설계 자체도 새 의례로 굳히지 않는다. 각 수리의 기존 커밋·시험·변경 이력에 결과를 남기고,
매번 별도 승인표·감사 등록부·상시 프롬프트를 추가하지 않는다.


## 12. 구현·관측 기록

### 1단계 — 화면 검수

사전 진단의 자동 실패 분기를 제거했다. 이미지 바이트를 디코딩한 뒤 목적·진단과 함께 기존
비전 호출에 전달하며, 파일 부재·손상은 품질 점수 없이 검수 불가로 반환한다.
관용구의 `prescreen` 전달 계약은 그대로여서 본문 개정 없이 현재 활성 카탈로그의 원문·판본을 확인했다.
선언·생산자 주석·가이드·파생물을 같은 계약으로 갱신했다.
용례 검토에서 사전 진단만으로 실패한다고 설명한 3건은 원문을 보존하고 현행 검색에서 은퇴시켰다.
라이브 DB는 정규 백업 경로에 백업했고, 휴대용 해마 색인도 현행 검색 집합으로 재생성했다.

같은 픽셀·상이한 콘솔 로그의 결정론 시험과 관련 소비자 523개가 통과했다.
실제 실행 기어의 비전 검사에서도 정상 화면과 부가 로그 화면은 각각 7점 통과,
요구 수치 누락은 2점 실패, 의도한 빈 캔버스는 10점 통과했다.
네 호출은 각각 1회였고 7.0~7.9초가 걸렸다. 진단으로 생략되던 두 사례는 0회에서 1회로 늘었다.
입력·출력·캐시 토큰과 활성 관용구는 [실측 기록](experiments/observation_repair_2026_10_26/vision.json)에 보존했다.
전체 작업의 재수리 감소와 비용 회수는 아직 실증하지 않았다.

최초 22개 시험은 모두 통과했지만 동시에 실행한 어휘 빌드가 추적 파일을 변경하여 세션 검사가 실패했다.
빌드를 마친 후 파일 변경 없이 위 523개를 다시 실행해 세션 검사까지 통과했다.

### 2단계 — 검수와 목표 달성 분리 (구현 완료)

같은 평가 호출에 `GOAL_OUTCOME`을 추가하고 큐·증류·계승·에피소드·추적·화면까지
`review_status`와 `goal_status`를 별도로 보존했다. 옛 승인만 있는 기록은 목표 미확정이다.
수리 영수증은 실제 반영/활성/검사/커밋 관측에서 목표를 결정하며 응답 검수는 NOT_RUN이다.
검수 이후 응답 변경·취소는 전달본 지문과 미확정 판정으로 남긴다.

실제 현재 평가 모델의 합성 증거 시험은 [evaluation.json](experiments/observation_repair_2026_10_26/evaluation.json)에 있다.
PC 갱신 불가 보고는 검수 승인/목표 미달성, 제목 수정 후 재독 증거는 승인/달성으로 분리됐다.
연결 거부 증상만 있는 원인 조사도 원인을 확인한 것으로 과장하지 않고 미달성으로 남았다.
각 사례는 기존 평가 1회이며 추가 판정 호출은 없다. 실제 외부 PC 변경은 하지 않았다.

구기록 계승 시험에서는 승인만 있는 동일 요청 1건이 성공 계승 대신 재규정 1회로 바뀐다.
이는 재규정 호출 증가의 결정론 증거이며 실제 사용자 되묻기/재수행 빈도는 아직 측정하지 않았다.
일반 회귀 첫 실행 10,320 통과/31 실패/5 생략에서 잘못된 옛 계약의 시험과 예외 경로를 수정했다.
부분 성과의 증류는 실제 성공한 호출만 선택하고, 전체 작업 용례는 명시 목표 달성 증거가 있어야 한다.
사용자 사실은 작업의 성공 여부로 일괄 폐기하지 않는다.

재검사에서 실패 묶음 243건 및 평가/큐/계승/에피소드 관련 238건을 확인했다. 전체 일반 회귀는 나머지 단계 이후 같은 정본에서 다시 실행한다. UI TypeScript 검사와 Vite 빌드도 통과했다.
