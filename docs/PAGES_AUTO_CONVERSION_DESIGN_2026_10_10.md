# Pages 문서 자동 변환 설계

작성일: 2026-10-10

상태: 설계 완료, 구현 전. Pages 실파일의 변환·편집·저장 인수는 아직 수행하지 않았다.

Pages 파일을 문서 앱에서 선택하면 원본을 보존하고 DOCX 작업 사본으로 자동 변환해 연다. 이후의 읽기·직접 편집·선택 AI 수정·초안 복구·저장은 기존 DOCX 경로를 사용한다. 같은 Pages를 다시 열면 이전 작업 사본과 초안을 이어 연다. 저장 결과는 DOCX이며 `.pages`로 되돌려 저장하지 않는다.

이 설계는 [문서 앱 설계](DOCUMENT_APP_DESIGN_2026_10_02.md)의 Pages 지원 계약을 [현재 계기 기반 문서 앱](DOCUMENT_APP_ON_BINNOTE_PLAN_2026_10_05.md)에 연결한다. [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)에 따라 변환·자료 식별·편집 사이의 반복 절차를 서비스가 맡는다. 새 IBL 낱말이나 별도 문서 편집기를 만들지 않는다.

## 1 현재 동작과 확인된 공백

현재 상태를 “Pages 변환은 항상 실패한다”로 단정하지 않는다. 변환 호출과 수동 버튼은 있으며, 아래는 코드로 확인한 사실이다.

| 위치 | 현재 동작 | 보완할 내용 |
| --- | --- | --- |
| `data/instruments/document.yaml` | `self:workspace`의 `open`으로 자료를 열고 `engine` 뷰에 반환 ID를 전달 | Pages 자동 변환 결과를 같은 열기 흐름으로 받기 |
| `frontend/src/components/generic/prims-engine.tsx` | 직접 편집 불가 자료에 “.docx 사본으로 열기” 버튼 표시. 변환 뒤 컴포넌트 내부 `swap`으로 대상 교체 | 자동 변환, 재열기, 지속적인 원본 표시, 실패 복구 |
| `backend/services/document_formats.py` | `pages`가 입력 목록에 있고 ONLYOFFICE `/converter`에 전달. 결과를 별도 파일로 등록하고 출처 기록 | 실제 엔진 준비 확인, 동일 변환 중복 방지, 작업 사본 재사용 |
| `backend/services/document_office.py` | 직접 편집 형식은 DOCX·ODT·RTF·PDF | Pages는 원본으로 편집 세션을 얻지 않고 DOCX 사본에 세션 연결 |
| `backend/services/document_workspace.py` | 같은 경로가 등록됐으면 기존 자료 반환. 새로 읽은 바이트로 기존 버전을 갱신하지 않음 | Pages 재열기 시 원본 변경 확인과 새 변환의 버전 고정 |
| `backend/services/workspace_sessions.py` | 디렉터리는 코딩 프로젝트로 분류. Pages 읽기 투영은 없음 | 디렉터리형 Pages 패키지를 문서로 분류하고, DOCX 결과를 읽기 대상으로 반환 |
| `frontend/src/components/generic/prims-engine.tsx`의 이벤트 | 변환 후 자식은 DOCX를 편집하지만 부모 `emit`의 기본 `resource`는 최초 자료 ID | 선택·저장 이벤트의 자료 ID와 버전을 실제 DOCX로 일치 |
| `backend/base/document_converter.py` | 채팅·노트북의 Pages 첨부를 DOCX 등과 함께 `textutil`로 전달 | 문서 앱과 별개의 읽기 경로. 이번 문서 앱 완료를 이 경로의 지원 완료로 확대하지 않음 |

현재 Pages 관련 `test_office_not_falsely_reported_supported`는 가짜 바이트가 직접 편집으로 표시되지 않는지만 검사한다. 실제 Pages 내용의 변환·레이아웃·재저장 성공을 입증하지 않는다.

ONLYOFFICE 공식 [변환 표](https://api.onlyoffice.com/docs/docs-api/additional-api/conversion-api/conversion-tables/)에는 Pages 입력에서 DOCX·PDF 등의 출력이 명시돼 있다. 이는 구현 경로의 근거이며, 설치된 엔진 버전과 개별 문서의 호환성은 실제 파일로 검증해야 한다.

## 2 이번 구현의 범위

필수 범위는 데스크톱 문서 앱의 로컬 Pages 열기, DOCX 자동 변환, 직접 편집과 기존 DOCX 선택 AI 기능, DOCX 저장·PDF 내보내기, 재열기·초안 복구다. `self:workspace`로 Pages를 여는 AI도 같은 작업 사본 ID를 받는다. 원격의 등록 자료 접근 권한과 기존 `/documents/import` API는 유지하되 원격 편집기 배포나 새 업로드 화면을 추가하지 않는다.

단일 파일형 Pages와 macOS의 디렉터리형 Pages 패키지를 입력 대상으로 삼는다. 구판·암호·손상·지원하지 않는 문서 구조는 구별된 실패로 반환한다. 지원할 수 없는 변종까지 정상 처리된다고 표시하지 않는다.

Apple Pages 앱 제어, `.pages` 출력, Numbers·Keynote 자동 변환, 다른 문서 형식의 일괄 자동 전환은 이번 범위에 넣지 않는다. 채팅 첨부·노트북 읽기는 후속으로 같은 변환 결과를 재사용할 별도 소비자이며, 이번에는 기존 `textutil` 경로를 그대로 지원 완료로 홍보하지 않는다.

## 3 사용자가 보는 흐름

1. **열기:** 기존 파일 선택창에서 `보고서.pages`를 고른다. “Pages 문서를 편집할 수 있도록 변환 중…”을 표시하고 현재 문서의 편집 상태는 유지한다. 추가 변환 확인창 없이 시작한다.
2. **전환:** 검증된 DOCX가 준비됐을 때 기존 문서의 초안을 확보하는 정상 전환 절차를 거쳐 새 편집기를 연다. 이전 초안 확보가 실패하면 화면 전환을 멈추고 만들어진 변환 사본은 재사용 가능하게 보존한다.
3. **표시:** 파일명은 `보고서_converted.docx`, 상태는 “Pages에서 변환한 작업 사본 · 원본 유지”. 도구 패널에서 원본 경로·작업 사본 경로·변환 일시를 확인한다. “서식·쪽 배치는 원본과 다를 수 있음”은 변환 문서에 한 번 안내하고 상세에서 다시 볼 수 있게 한다.
4. **편집:** 기존 DOCX 편집기를 사용한다. AI 선택·스냅샷·제안의 대상도 DOCX 작업 사본이다. 범용 `workspace.propose`가 DOCX 전체 구조 편집을 새로 지원한다고 표시하지 않는다.
5. **저장:** 변환 사본에서는 기존 “원본 저장” 버튼을 “DOCX 저장”으로 표시한다. 앱 관리 폴더의 DOCX 파일을 확정하고 그 위치를 보여준다. `.pages` 원본은 변경하지 않는다. PDF 내보내기는 현재 편집기의 확인된 초안을 변환한다.
6. **다시 열기:** 같은 Pages를 고르면 저장된 작업 사본·미저장 초안·세션을 이어 연다. 재변환으로 편집 결과를 덮어쓰지 않는다.
7. **원본이 바뀐 경우:** 기존 사본을 이어 열면서 “Pages 원본이 변경됨”과 “변경된 원본으로 새 사본 만들기”를 제공한다. 새 변환은 새 DOCX 자료를 만들고 기존 사본·초안·버전은 보존한다.

작업 사본의 기본 위치는 기존 `data/document_workspace/files/<id>/보고서_converted.docx` 구조를 따른다. Pages 옆에 자동으로 파일을 쓰지 않는다. “위치 열기”로 실제 사본에 접근할 수 있게 하고 같은 형식의 사본 저장은 기존 계약을 유지한다. 임의 폴더로 저장하는 새로운 공통 기능은 이 변경의 선행 조건으로 만들지 않는다.

## 4 열기 계약과 책임

Pages 여부·변환 필요성·재사용 여부는 backend가 결정한다. 프론트엔드에 확장자 분기와 변환 정책을 중복 구현하지 않는다.

| 구성 요소 | 변경 책임 |
| --- | --- |
| `workspace_sessions.kind_of_path` | `.pages` 패키지는 디렉터리보다 먼저 문서로 분류. 코딩 프로젝트 등록이나 `git init`으로 보내지 않음 |
| `DocumentWorkspace.open` | Pages 원본 등록·스냅샷과 편집할 DOCX 해소를 연결. 일반 DOCX 등의 열기 의미 유지 |
| 새 `services/document_imports.py` | Pages 입력 검사·작업 사본 연결·중복 방지·상태 복구의 단일 소유자 |
| `document_formats.py` | 기존 ONLYOFFICE 변환 I/O를 재사용 가능한 내부 함수로 분리. 자동 열기와 수동 내보내기가 같은 구현 사용 |
| `OfficeResources`와 `OfficeStore` | 원본·작업 사본의 독립 ID, 불변 바이트와 버전, 변환 작업 기록 보관 |
| `Workspace.open`과 `api_documents` | 서비스 결과를 각각 기존 공통 반환값과 `Detail`로 전달. 로컬 경로·소유권 검사 유지 |
| `essentials_workspace.py`와 어휘 정의 | 기존 `open`에 필요한 선택 인자만 추가하고 소개·가이드 동기화 |
| `prims-engine.tsx`와 `OfficeDocumentEditor` | 실제 자료 ID, 변환 상태·출처, 저장 라벨, 이전 문서 보존과 실패 재시도 |

`open`에 선택 인자 `conversion: "auto" | "source" | "refresh"`를 제안한다. 기본 `auto`는 Pages에만 자동 적용하며 다른 형식에는 기존 동작을 유지한다. `source`는 원본의 등록·열람 상태만 반환하고 편집·저장을 허용하지 않는다. `refresh`는 현재 원본 버전으로 별도 사본을 만드는 명시적 동작이며 `request_id`를 함께 받아 재시도 중 중복 생성을 막는다. 내부 등록 함수와 편집 준비 함수를 분리해 변환 결과 등록이 다시 자동 변환을 호출하는 순환을 피한다.

성공한 `Workspace.open`의 `resource`, `revision`, `path`, `title`, `session`, `capabilities`는 모두 **실제 편집할 DOCX**를 가리킨다. 원본 정보는 추가 `conversion` 필드에 넣는다. HTTP `Detail.document`도 같은 DOCX를 반환한다. 원본 ID로 `/documents/{id}`를 조회하는 읽기 API는 몰래 다른 자료로 바꾸지 않고 원본과 연결 정보를 그대로 반환한다.

```json
{
  "resource": "docx_resource_id",
  "kind": "document",
  "revision": "docx_revision_id",
  "conversion": {
    "state": "ready",
    "source_resource": "pages_resource_id",
    "source_revision": "pages_revision_id",
    "source_format": "pages",
    "working_format": "docx",
    "reused": false,
    "source_changed": false,
    "original_preserved": true,
    "fidelity": "unverified"
  }
}
```

위 ID 값은 예시다. `source_changed`는 실제 원본 재검사 결과이고, 검사할 수 없으면 `false` 대신 `null`과 원인을 전달한다. 프론트엔드 타입에도 출처·상태를 추가한다. `selection`·`saved` 이벤트는 실제 `document.id`를 명시하여 부모의 최초 ID를 덮어쓰고, `$resource`와 선택·버전·책갈피가 한 자료를 가리키도록 한다. 문서 전환 시 이전 선택과 AI 제안을 초기화한다.

## 5 원본과 작업 사본의 관계

원본 Pages 자료와 편집용 DOCX 자료는 다른 ID를 가진다. Pages 바이트를 DOCX 바이트로 바꾸면서 확장자·원본 경로를 유지하는 방식은 금지한다. 출처에는 원본 자료 ID·원본 버전·입력 지문·변환 엔진 버전·출력 지문·생성 시각을 기록한다. 기존 수동 변환의 `provenance`를 확장하며 별도의 출처 체계를 만들지 않는다.

변환 작업은 기존 `OfficeStore.objects`의 새로운 kind로 저장한다. 키는 소유자·원본 자료 ID·원본 버전·출력 형식·변환 정책 버전으로 결정하고, 요청별 `request_id`는 명시적 새 사본 생성의 재시도를 식별한다. 동일 내용이라도 다른 경로의 자료를 하나로 합치지 않는다. 엔진 업그레이드만으로 편집 중인 DOCX를 자동 교체하지 않는다.

자동 열기의 활성 연결은 **원본 자료 → 마지막으로 사용자가 선택한 작업 사본**이다. 원본이 바뀌어도 기존 사본을 우선 이어 열고, 변경된 원본을 새 사본으로 가져오겠다는 선택이 성공했을 때만 연결을 바꾼다. 기존 원본 버전과 모든 작업 사본은 계속 남는다.

Pages 재열기는 디스크의 현재 지문을 확인한다. 변경됐다면 원본 자료에 새 불변 버전을 기록하되 기존 버전은 보존한다. 등록된 ID 조회처럼 원본을 재검사하지 않은 결과에는 최신 확인을 주장하지 않는다. 변환 중 원본이 바뀌어도 변환 입력은 최초 스냅샷에 고정하고, 완료 결과에는 이후 변경 여부를 표시한다.

기존 수동 변환 사본은 검증 가능한 `provenance`가 있는 후보만 연결한다. 후보가 하나면 사용하고, 여러 개면 사용자에게 선택하게 한다. 파일명이나 수정 시각만으로 편집 내용이 있는 사본을 자동 선택·폐기하지 않는다. 사본이 외부에서 변경됐거나 사라졌으면 충돌·복구 상태를 표시하고, 이를 빈 작업으로 간주해 조용히 재변환하지 않는다.

## 6 입력 검사와 변환 실행

단일 파일은 확장자와 컨테이너 구조를 함께 확인한다. 실제 Pages 샘플의 최신·구판 구조를 기준으로 검사하고, 특정 내부 파일 하나만으로 모든 판본을 판정하지 않는다. 확장자만 `.pages`인 임의 ZIP은 거절한다. 암호 파일은 변환 엔진의 암호 오류를 별도로 전달하고 이번 경로에서 암호 수집·저장을 추가하지 않는다.

디렉터리형 Pages는 원본 트리에서 일반 파일만 읽어 임시 변환용 ZIP 스냅샷으로 만든다. 루트·내부 심볼릭 링크, 상위 경로 탈출, 특수 파일은 거절한다. 파일 목록과 바이트 지문으로 안정적인 원본 지문을 만들며, ZIP 생성 시각에 따라 동일 원본이 다른 버전이 되지 않게 한다. 읽기 전후 변경을 탐지하면 재시도 가능한 `source_changed_during_read`로 멈춘다. 일반 파일용 `read_bytes` 제한을 전역적으로 풀지 않는다.

기존 파일 입력 상한 25MiB를 유지하고 디렉터리 입력은 전체 일반 파일 합계에도 같은 상한을 둔다. 압축 입력의 펼친 크기는 기존 사무 문서 검사의 200MiB 상한을 재사용하며 파일 수 상한도 별도로 둔다. 중복 엔트리·과도한 압축·잘못된 XML은 변환 전에 또는 출력 검증 단계에서 실패시킨다. 구체적인 엔트리 수 상한은 구현 상수 한 곳에 두고 경계 시험으로 검증한다.

변환 엔진은 현재 설정된 ONLYOFFICE 하나를 사용한다. 설정 파일 존재와 서버 준비 완료를 구분해 표시하며, 엔진 버전은 취득 가능한 응답이나 배포 정보에서 기록하고 알 수 없으면 `unknown`으로 둔다. 문서를 여는 부작용으로 엔진을 설치하거나 다른 외부 변환 사이트로 전송하지 않는다. 준비되지 않았으면 기존 “편집 서버 시작” 동작과 재시도를 제공한다.

기존의 만료 ticket·소유권·허용된 엔진 출처만 다운로드하는 계약을 유지한다. 변환 완료 플래그만으로 성공을 확정하지 않고 DOCX ZIP 구조·필수 파트·XML·크기와 실제 읽기를 검증한 다음 자료로 등록한다. 빈 문서는 정상 입력일 수 있으므로 텍스트가 비었다는 이유만으로 실패시키지 않는다. 입력이 빈 문서인지 판단할 근거가 없는 경우에는 내용 충실도를 `unverified`로 둔다.

## 7 중복 요청과 중단 복구

첫 구현은 기존 동기 변환 호출을 재사용한다. 별도 상주 큐·폴러를 만들지 않고, UI와 IBL 호출 경로가 기존 변환 제한 시간인 180초와 반환 처리를 수용하는지 확인한다. 프록시·호출자 제한 시간이 더 짧다면 그 환경은 인수 실패이며, 완료를 반환한 것처럼 처리하지 않는다.

작업 기록의 상태는 `converting → validating → ready`, 오류 시 `failed`, 실행자 소실 시 `interrupted`로 둔다. 기록에는 작업 키·입력 버전·실행 시도 ID·만료 시각·출력 자료 ID·오류 코드가 있다. 메타데이터 잠금은 작업 등록과 완료 확정에만 사용하고 180초 네트워크 호출 중 유지하지 않는다.

- 같은 입력을 동시에 여는 두 요청은 하나만 변환한다. 뒤 요청은 완료 결과를 재사용하거나 `conversion_in_progress`와 재시도 정보를 받는다. UI는 취소 가능한 상태에서 제한된 간격으로 같은 열기 요청을 재시도한다.
- 프로세스 중단 뒤 살아 있는 시도인지 확인할 수 없거나 기한을 넘기면 기존 시도를 `interrupted`로 남기고 새 시도를 시작한다. 늦게 온 이전 시도의 응답은 시도 ID 비교로 활성 연결을 변경할 수 없다.
- 파일 생성 뒤 메타데이터 확정 전 중단을 복구할 수 있도록 출력 위치·지문·예정 자료 ID를 먼저 기록한다. 복구는 기존 바이트를 확인해 등록을 마치며 중복 DOCX를 만들지 않는다.
- 결과 등록과 변환 작업의 `ready`·원본 연결 확정은 같은 DB 트랜잭션으로 처리한다. 파일과 DB가 하나의 트랜잭션인 것처럼 주장하지 않는다.
- 화면에서 취소하거나 다른 문서로 이동하면 늦은 완료 결과를 화면에 적용하지 않는다. 서버 변환이 이미 완료되면 보존된 사본을 다음 열기에서 재사용한다. UI 취소를 서버 작업 취소 완료로 표시하지 않는다.

편집에 들어간 뒤의 동시 창·미저장 초안·엔진 콜백·저장 복구는 기존 `OfficeSessions`를 따른다. 자동 변환을 이유로 다른 창의 작성 권한을 빼앗지 않는다.

## 8 실패 표시와 능력 구분

오류는 내부 코드와 짧은 사용자 문구로 구분한다. 일반 예외를 문자열로만 흘려 화면 전체를 막지 않으며 같은 입력으로 재시도할 수 있어야 한다.

| 상태 | 사용자에게 제공할 동작 |
| --- | --- |
| 엔진 미설정·미실행·접속 실패 | 설치 상태 안내 또는 기존 엔진 시작, 재시도 |
| 변환 중·시간 초과·프로세스 중단 | 진행 상태, 재시도, 기존 문서로 돌아가기 |
| Pages 형식 불일치·지원하지 않는 판본·암호·손상 | 구체적 원인, Apple Pages에서 DOCX로 내보낸 파일 열기 안내 |
| 원본 변경·사본 외부 수정·사본 유실 | 기존 초안 보존, 버전·복구, 별도 사본 생성 |
| 변환 출력이 잘못됨 | 편집 세션을 만들지 않고 변환 실패로 표시 |

원본 Pages의 `edit_native/save`는 계속 `false`다. 변환 경로의 존재(`conversion_available`), 엔진 준비(`engine_ready`), 검증된 결과(`state: ready`), 내용·서식 보존 정도(`fidelity`)를 구분한다. 변환 필요 여부를 단순히 `edit_native === false`로 판단하지 않는다. DOCX 엔진이 꺼졌을 때 DOCX를 다시 DOCX로 변환하라는 현재의 포괄 안내도 실제 준비 상태 안내로 교체한다.

Pages를 DOCX로 변환했다고 모든 표·그림·각주·주석·추적 변경·쪽 배치가 보존됐다고 표시하지 않는다. 엔진의 경고가 있으면 전달하고, 비교하지 못한 요소는 미검증으로 남긴다. 자동 변환에 AI 호출은 필요 없다.

## 9 구현 순서와 기존 경로의 정리

1. **입력과 변환 서비스:** Pages 파일·패키지 분류, 원본 스냅샷, 기존 ONLYOFFICE I/O 분리, DOCX 출력 검사. 새 backend 모듈을 층 검사 `LAYERS`에 등록한다.
2. **영속 연결과 복구:** 작업 사본 관계, 원본 변경, 중복 요청·중단 복구, 기존 수동 사본 이관. 기존 `convert`의 임의 내보내기 의미는 유지하되 자동 열기만 재사용 정책을 적용한다.
3. **열기와 화면 연결:** `DocumentWorkspace.open`·`Workspace.open`·HTTP·패키지 인자 연결, 계기 안내·타입·실제 자료 ID 이벤트·저장 라벨, 실패/취소 시 이전 문서 보존. Pages에는 프론트의 일시적 `swap`만으로 전환하는 경로를 사용하지 않는다.
4. **실파일 인수와 문서:** 아래 기준을 통과시키고 문서 앱 지원표·`data/guides/workspace.md`·운영 안내에 자동 변환·저장 위치·제한을 반영한다. 변경한 어휘 인자·설명은 원천에서 수정하고 빌드로 파생물을 갱신한다.

사본 관리와 출처는 문서 서비스가 소유한다. IBL 파서·실행기에 `pages` 이름이나 전용 변환 문법을 넣지 않는다. 공통 열기 결과가 실제 작업 자료를 가리키는 계약은 다른 변환 편집 형식에도 재사용 가능하지만, 이번 인수 범위는 Pages로 제한한다.

채팅·노트북의 후속 통합에서는 현재 `base/document_converter.py`가 상위 서비스·저장소를 역으로 import하지 않도록 층을 먼저 정리해야 한다. 문서 서비스의 변환 산출물과 읽기 요청을 연결하는 별도 설계 없이 `textutil` 분기만 바꾸지 않는다.

## 10 인수 기준

| 검사 | 완료 조건 |
| --- | --- |
| 단순 실문서 | 실제 Pages에서 만든 한글·영문·제목·문단 문서가 선택 한 번으로 DOCX 편집기에 열림 |
| 복합 실문서 | 표·병합 셀·이미지·머리말·꼬리말·각주·텍스트 상자가 있는 샘플의 본문 누락·표 구조·이미지·쪽 배치를 기준 PDF와 비교하고 손실 기록 |
| 파일과 패키지 | 단일 파일과 디렉터리형 Pages 모두 처리. 패키지를 코딩 프로젝트로 등록하거나 `.git`을 만들지 않음 |
| 편집과 저장 | 직접 입력→DOCX 저장→닫기→재열기에서 내용 유지. Pages 원본의 바이트/트리 지문 불변 |
| AI와 이벤트 | DOCX 선택 수정·스냅샷·저장 이벤트 및 `$resource`가 실제 사본 ID·버전을 사용. 원본 ID와 사본 버전의 혼합 없음 |
| 작업 이어쓰기 | 같은 원본 반복 열기·앱 재시작·미저장 초안·다른 창 작성 상태에서 기존 사본 재사용, 무단 세션 탈취 없음 |
| 원본 변경 | 변경 감지, 기존 편집 유지, 명시적 새 사본 생성, 이전 사본 복구 가능 |
| 중복과 장애 | 동시 열기·재시도·응답 유실·파일 생성 직후 중단·늦은 완료에서 활성 사본 하나와 일관된 작업 기록 |
| 잘못된 입력 | 가짜 확장자·손상 ZIP·암호·과대 입력·심볼릭 링크·잘못된 출력이 성공 또는 빈 문서로 위장되지 않음 |
| 화면 취소와 실패 | 기존 문서 초안 유지, 늦은 결과로 화면이 돌아가지 않음, 재시도 버튼 동작 |
| 준비 상태 | 엔진 미설정/중단/복구 안내가 다르고, 지원 여부를 설정 파일 유무로만 판단하지 않음 |
| 기존 형식 | DOCX·ODT·RTF·HWP/HWPX·PDF·TXT 열기/저장과 수동 변환 회귀 없음 |

실문서 fixture는 개인정보 없는 합성 내용으로 만들고 생성 Pages 버전·패키지 종류·기준 PDF·예상 본문과 구조를 함께 기록한다. 엔진 대역 검사만으로 실문서 인수를 대신하지 않는다. 복합 샘플에서 본문·핵심 표·이미지가 유실되면 지원 완료가 아니며, 단순한 페이지 수 차이는 원인과 허용 범위를 별도로 평가한다.

검사는 `docs/REGRESSION_TESTING.md`와 `scripts/select_tests.py`를 따른다. 새 회귀는 해당 모듈의 `backend/test_*.py`에 둔다. 문서 서비스·Workspace·변환·세션과 실제 계기 브라우저 시험을 연결하고 `npx tsc -p tsconfig.app.json`, 어휘 빌드 `--check`, 층 검사와 backend 변경 시 Android 몸 번들 갱신을 수행한다. 공통 작업 공간 변경의 영향이 허브/전수 기준에 해당하면 종합 회귀도 실행한다.

변환 전후 시간, 재열기 시 변환 호출 수, 실제 모델 호출 유무를 기록한다. 자동 변환과 재열기에서 AI 호출 0회, 동일 원본의 정상 재열기에서 변환 호출 0회를 확인한다. 검증되지 않은 속도·서식 보존·Windows 호환을 완료로 보고하지 않는다.

## 11 설계 완료와 구현 완료의 경계

설계의 결정은 **Pages 원본 보존, DOCX 자동 작업 사본, 영속 연결과 재사용, 실제 편집 자료의 ID 일치, 기존 세션 저장 계약 재사용**이다. 현재 수동 변환의 존재를 인정하면서 자동 열기·복구·실파일 검증의 공백을 닫는다.

구현 완료는 위 인수 기준의 결과와 지원하지 못한 문서 변종을 정본에 기록한 시점이다. 이 문서를 추가한 것만으로 Pages 지원 상태가 바뀌지는 않는다.
