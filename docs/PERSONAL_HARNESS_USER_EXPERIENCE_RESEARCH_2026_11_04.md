# IndieBiz OS의 개인 하네스 사용자 경험과 차별화 연구

2026-11-04 · 제품 방향과 개발 우선순위 제안

IndieBiz OS가 입증해야 할 차이는 **개인의 도구와 일이 늘어나도, 사용자가 도구 연결자와 시스템 관리자로 보내는 시간은 적게 유지하면서 스스로 할 수 있는 일은 넓어진다**는 것이다. IBL은 이를 위한 중요한 기반이다. 차별화의 완성은 그 기반이 처음 시작하기, 새 일 맡기기, 진행 중 변경하기, 재사용하기, 고장과 업데이트를 넘기기에 걸쳐 일관된 경험으로 전달될 때 이루어진다.

가장 먼저 할 일은 기존 능력을 하나의 실제 사용자 여정으로 연결하는 것이다. 새 언어나 대규모 관리 체계를 더 만드는 것보다, **사용자 자료로 첫 업무 완료 → 조건 변경 → 부분 재실행 → 재사용 → 도구 변경 뒤 복구**를 같은 작업의 연속으로 만드는 데 우선순위를 둔다. 설치·업데이트의 정직한 상태 표시와 복구는 이 여정의 바닥 조건이다.

조사는 정본 저장소의 설계·가이드·프런트엔드 및 관련 실행 코드와 외부 공식 문서·연구 논문을 대조했다. 로컬 조사 기준은 `8f34f7bc`를 바탕으로 한 작업 트리다. 실제 제품 간 비교 실험이나 새 사용자 관찰은 수행하지 않았으므로, 기능의 존재·소스에서 확인한 제약·제품 제안·검증할 가설을 구분한다. 이 문서는 구현 완료 보고가 아니다.

## 1 자동차 비유를 사용자 경험의 조건으로 바꾸기

사용자의 기차와 자동차 비유에서 중요한 것은 소스 공개 여부보다 **일의 방향을 누가 정하고, 경로를 바꾸는 비용과 고장을 처리하는 부담을 누가 지는가**다. 상용 제품도 개방적인 확장 구조를 가질 수 있고, 공개 소스도 사용자가 실질적으로 바꾸기 어려울 수 있다. 비유는 제품군 전체의 사실 분류보다 IndieBiz OS의 목표를 정하는 기준으로 유용하다.

자동차에 해당하는 경험에는 다음 조건이 함께 필요하다.

| 사용자 경험 | 관측할 행동 | 사용자에게 넘기지 않을 기술적 부담 |
| --- | --- | --- |
| 원하는 곳으로 간다 | 사전 등록하지 않은 새 요구를 기존 도구와 새 부품으로 수행한다 | 도구 이름 암기, 매번 연결 코드 작성 |
| 가는 중에 방향을 바꾼다 | 조건·자료·대상을 바꾸고 유효한 작업은 유지한다 | 어느 결과를 버리고 다시 계산해야 하는지 추적 |
| 익숙해지면 편해진다 | 지난 방법을 새 입력과 다른 일에 다시 쓴다 | 프롬프트 복사, 절차 재설명, 중복 도구 정리 |
| 고장 나도 돌아온다 | 실패 구간을 진단·복구하고 남은 업무를 끝낸다 | 로그 순회, 재시작 순서 기억, 중복 외부 실행 판별 |
| 오래 소유할 수 있다 | 업데이트·기기 이동·모델 교체 뒤에도 개인 자산을 쓴다 | 개인 수정과 배포본 병합, 기억·도구의 재구축 |

여기서 줄여야 하는 부담은 설치·검색·변환·진단·복구의 부담이다. 무엇을 원하는지 정하고 결과를 판단하는 사용자의 참여는 가치 있는 활동이다. 질문 횟수나 개입 횟수를 모두 줄이는 목표는 인지 외골격의 목적과 맞지 않는다. **기술적인 구조를 대신 설명해야 하는 개입과, 취향·판단을 반영하는 개입을 분리해서 측정해야 한다.**

IBL의 공통 계약은 도구 사이의 일부 연결 비용을 공통 기반으로 옮긴다. 그러나 JSON 필드의 모양이 같다고 단위·시점·대상 식별·자료의 뜻까지 같아지지는 않는다. 도구 수만으로 관리 비용을 계산하거나, 공통 언어가 모든 의미 변환을 자동 해결한다고 주장해서는 안 된다. [현재 비전](../data/system_docs/vision.md), [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)

## 2 다른 접근에서도 조합 기반은 발전하고 있다

현재 공개 문서에는 IBL과 비교해야 할 강한 대안이 있다. 다른 개인 하네스를 모두 개별 스위치로 보는 전제로는 차별화 방향을 정확히 정할 수 없다.

| 비교 대상 | 공식 문서에서 확인한 기능 | IndieBiz OS에 주는 시사점 |
| --- | --- | --- |
| OpenClaw와 Lobster | 선택 설치하는 작은 DSL로 여러 단계를 실행하며, 승인·입력 체크포인트와 재개 토큰을 제공한다 | 언어·파이프라인·재개 자체는 독점적 차별점이 아니다. 기본 사용 흐름과 얼마나 연결되는지가 중요하다 |
| goose | 도구·목표·지침을 recipe로 보관하고 UI에서 저장·실행한다. 실험적 subrecipe는 별도 세션으로 부품을 호출하고 결과를 돌려준다 | 재사용 버튼과 조합 부품도 이미 경쟁 영역이다. 새로운 입력과 다른 업무로의 전이가 비교 대상이다 |
| OpenCode | TypeScript/JavaScript 도구 정의에서 Python 등 다른 언어의 프로그램을 호출할 수 있다 | 도구를 추가할 수 있다는 사실보다 연결·검사·운영에 필요한 사용자 작업을 비교해야 한다 |
| Deep Agents와 LangGraph | 계획·파일 문맥·기억·스킬의 점진적 로딩, 체크포인트에 의한 지속성을 제공한다 | 스킬 중심 구조도 관리와 지속 실행을 개선할 수 있다. 독립 스킬은 반드시 고립된 스위치라는 주장은 성립하지 않는다 |
| Cloudflare Code Mode | 타입이 있는 도구 호출, 선택적 발견, 재사용 코드, 승인 후 실행 기록을 이용한 재개를 제공한다 | 범용 언어 기반도 조합을 미리 준비할 수 있다. 실행 언어의 이름만으로 사용자 부담을 예측할 수 없다 |

근거: [Lobster](https://docs.openclaw.ai/tools/lobster), [goose recipes](https://goose-docs.ai/docs/guides/recipes/session-recipes/), [goose subrecipes](https://goose-docs.ai/docs/guides/recipes/subrecipes/), [OpenCode custom tools](https://opencode.ai/docs/custom-tools/), [Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview), [Skills](https://docs.langchain.com/oss/python/deepagents/skills), [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [Cloudflare tools](https://developers.cloudflare.com/agents/concepts/tools/).

이 표는 완성 제품·선택 플러그인·개발 프레임워크의 구성 요소를 비교한 것이다. 설치 상태와 사용 난이도가 같다는 뜻도, 실제 업무 성공률 순위도 아니다. 비교 시험에서는 기본 설치와 필요한 확장까지 구성한 상태를 구분하고 그 구성 비용을 기록해야 한다.

따라서 방어 가능한 차별화 주장은 **IBL의 조합 계약, 개인의 기억과 재사용, 사용 중 조향, 실행 증거, 유지보수를 하나의 개인용 제품으로 연결한다**는 것이다. 다른 제품이 원리적으로 못 한다는 주장 대신, 같은 사용자가 더 적은 기술적 지원으로 더 다양한 일을 끝내는 결과로 입증한다.

## 3 현재 IndieBiz OS에 이미 있는 기반과 사용자 경계

| 영역 | 현재 확인한 기반 | 다음에 연결하거나 확인할 경험 |
| --- | --- | --- |
| 처음 시작 | 사용 가능한 AI 후보 탐지, 실제 응답 후 설정 저장, 첫 응답 상태 기록 | 자신의 자료로 의미 있는 업무를 끝내고 다시 실행할 수 있는가 |
| 도구 추가 | 어휘 패키지 가져오기·활성화, Python Script 등록, 호출 계약, 능력 변경 관용구 | 사용자가 내부 분류를 결정하지 않아도 적절한 부품 형태로 받아들일 수 있는가 |
| 조합 | 명시 값·함수·파이프·병렬·실패 처리, 검사와 실행의 공통 컴파일러 | 처음 보는 업무에서도 적합한 부품을 발견하고 올바르게 연결하는가 |
| 방향 변경 | 실행 중 텍스트 조향, 턴·요청 ID를 통한 접수 확인, 다음 실행 경계 전달 | 새 자료 첨부와 조건 변경의 영향이 보이고 필요한 부분만 다시 실행되는가 |
| 재사용 | 관용구·Script·해마 회상, 판본과 소비자 검사, 선언형 앱 실행 | 한 번 성공한 일이 사용자에게 재사용 가능한 능력으로 쉽게 나타나는가 |
| 결과 확인 | 실행 통합 조회, 근거 참조, 검수 승인과 목표 달성의 분리 | 사용자가 결과·누락·확인할 항목을 한 자리에서 이해하는가 |
| 복구 | 한정 자기수리, 외부 재시작 제어자, 세대 교체와 일부 부모 업무 복귀 | 지원되는 범위에서 고장 후 원래 업무 완료까지 연결되는가 |
| 장기 유지 | 코어와 사용자 파일의 구분, 활성 상태 보존, 업데이트와 복구 경로 | 새 설치·업데이트·이동 뒤 대표 개인 업무가 실제로 작동하는가 |

이 기반은 상당하다. 부족한 것이 모두 새로운 엔진인 것은 아니다. 동시에 기반의 존재를 일상 경험의 완성으로 간주할 수도 없다. 다음은 소스에서 확인한 구체적인 경계다.

1. **온보딩 종료는 첫 업무가 아니라 첫 응답이다.** `OnboardingDialog.tsx`는 후보→probe→설정 저장→첫 대화로 이어지고, `onboarding_state.py`는 `first_reply_at`을 완료 기준으로 쓴다. 이는 인증·모델 설정 문제를 줄이는 기반이며, 개인 업무 성공을 추가로 연결할 위치다. [화면](../frontend/src/components/OnboardingDialog.tsx), [상태](../backend/datastore/onboarding_state.py)
2. **조향의 일부 표면은 실행 중 텍스트만 받는다.** `useConversationSession.ts`는 실행 중 첨부와 도구 선택을 거절하고, 추가 지시를 1~2000자로 제한한다. 따라서 이 경로에서 ‘새 파일을 주면서 같은 일을 계속하기’는 그대로 되지 않는다. 앱 전체에 조향이 없다는 의미가 아니다. [세션 연결 코드](../frontend/src/components/chat/useConversationSession.ts)
3. **소스 업데이터의 완료와 의존성 준비가 어긋날 수 있다.** `scripts/update.py`는 pip 설치가 실패하면 경고를 출력하지만, 마지막에 완료 메시지와 종료 코드 0을 반환한다. 이 명령만으로 전체 사용 가능성을 판단하면 문제가 다음 업무까지 미뤄질 수 있다. 패키징 설치나 외부 호출자가 추가 검사를 하는지와 별도로, 해당 명령의 상태 계약을 수리할 근거가 된다. [소스 업데이터](../scripts/update.py)
4. **사용 가이드가 첫 업무 이전의 부담을 크게 보이게 할 수 있다.** `GUIDE.md`는 AI만으로 동작한다고 설명하면서 공개 주소를 필수 기둥으로, 폰을 준필수로 설명한다. 원격·발행이 필요 없는 신규 사용자가 이를 전체 준비 과제로 받아들일 가능성이 있다. 실제 이탈 효과는 사용자 관찰로 확인해야 한다. [사용자 가이드](../GUIDE.md)
5. **복구·상황 전달은 실행 경로마다 범위가 다르다.** 현재 설계는 Codex 네이티브 도구 사이의 상황 전달과 임의 상태 부품의 무재기동 교체 등을 보장하지 않는다. 실제 모델이 일반 구현 수리와 재기동을 모두 넘겨 완주하는 검증도 별도로 남아 있다. 이 범위는 제품이 표시하는 ‘이어가기’의 의미와 맞아야 한다. [상황 인식](EXECUTION_SITUATION_AWARENESS_DESIGN_2026_10_31.md), [수리 검증 경계](TASK_CONTINUOUS_REPAIR_DESIGN_2026_10_31.md)

## 4 첫 번째 과제는 내 일로 시작해 끝내게 하는 것

첫 진입의 질문은 필요한 업무와 자료를 고르는 수준이면 충분해야 한다. 모델 연결에 성공한 다음에는 사용자가 고른 로컬 파일·폴더 또는 이미 연결한 자료로 실제 산출물을 만들게 한다. 외부 계정·공개 주소·폰 연결은 그 업무가 요구할 때 연결한다.

예를 들어 사용자가 ‘이 폴더의 회의록에서 결정사항과 아직 끝나지 않은 일을 모아줘’라고 하면, 결과에는 원문으로 돌아갈 수 있는 결정사항과 누락·모호한 항목이 나타난다. 사용자가 ‘일정이 없는 일도 남겨줘’라고 바꾸면 새 조건을 반영한다. 유용하다고 판단한 뒤에만 다음 주에도 같은 방법을 쓰도록 보관한다.

필요한 개선은 기존 온보딩을 없애는 것이 아니라 그 다음 성공을 연결하는 것이다. 사용자는 자료 접근과 업무 기준을 결정하고, AI는 프로젝트·부품·입출력 연결의 기술적 선택을 담당한다. 적절한 기본값은 제공하되 사용자에게 프로젝트·에이전트·어휘·관용구의 내부 분류를 먼저 배우도록 요구하지 않는다.

‘빈 몸’은 개인의 목적과 기억을 임의로 채우지 않는다는 원칙으로 유지한다. 파일을 읽고, 결과를 확인하고, 잘못된 부분을 고치고, 다시 쓸 방법을 보관하는 기본 조작까지 빈 상태여야 할 이유는 없다. 예시 업무는 입구이며 지원 가능한 업무의 고정 노선이 되어서는 안 된다.

완료 기준은 설치 성공률 외에 **첫 유효 산출물까지의 사용자 실제 조작 시간, 개발자 도움의 필요 여부, 다음 실행의 독립 성공 여부**다. 첫 응답과 첫 업무 성공을 같은 지표로 합치지 않는다.

## 5 두 번째 과제는 작업 중의 조향을 일관된 경험으로 만드는 것

자동차에 가까운 경험은 출발 전에 긴 명세를 완성하는 능력보다, 진행하며 발견한 것을 반영하는 능력에서 드러난다. 사용자가 알아야 할 것은 현재 작업의 목적, 사용한 자료, 완료한 부분, 남은 부분, 자기 판단이 필요한 부분이다. 모든 도구 호출을 기본 화면에 펼칠 필요는 없다.

작업 화면은 기존 대화·주행기록·결과 화면에 다음 동작을 연결하는 방향이 적절하다.

- 결과나 자료를 선택하고 ‘이것만 제외’, ‘이 기준으로 다시’, ‘이 파일로 바꿔’를 전달한다.
- 접수한 변경이 무엇인지, 언제부터 반영되는지, 이미 끝난 외부 행동에는 무엇이 달라지지 않는지 보여준다.
- 조건 변경에 의존하는 결과만 다시 계산하고, 재사용 가능한 읽기 결과와 완료한 행동은 보존한다.
- 실패한 단계에서 다른 방법 선택·자료 추가·범위 축소·중단을 같은 업무 문맥으로 처리한다.
- 미리보기와 실제 외부 효과, 요청 접수와 실제 반영을 구분한다.

이 기능은 단순한 채팅 입력 추가만으로 완성되지 않는다. 변경된 자료의 판본, 의존 관계, 실행 신원, 효과 영수증이 소비자까지 이어져야 한다. 기존 상황 인식·조향·continuation·실행 원장을 재사용한다. 새 작업 상태 DB나 범용 감독자를 먼저 만들지 않는다. 임의 프로그램의 자동 의존 분석을 약속하지 않고, 현재 계약으로 확인 가능한 범위를 표시한다.

UIST 2024 연구는 데이터 분석 작업에서 가정과 실행 계획을 수정할 수 있는 단계·단계군 기반 인터페이스가 대화형 기준선보다 사용자가 느끼는 통제와 수정·검증 편의에 도움이 된다고 보고했다. 이는 작업을 이해 가능한 단위로 보이게 할 근거이며, 모든 도메인에서 같은 화면이 우월하다는 증거는 아니다. [원 논문](https://arxiv.org/abs/2407.02651)

독해·선택·기준 변경으로 일하는 사용자와 IBL 원문을 편집하는 사용자가 같은 실행 기반을 써야 한다. 기본 화면은 업무와 결과를 중심으로 하고, 원하는 사용자는 계약·원문·기록을 펼칠 수 있게 한다. IBL 문해력은 더 큰 통제력을 얻는 선택이어야 하고 일상 사용의 입장료가 되어서는 안 된다.

## 6 세 번째 과제는 도구를 추가하면 실제 능력이 늘어나게 하는 것

개인 Python 프로그램·MCP·기존 API·스킬을 받아들이는 입구는 최대한 기존 형태를 보존한다. 사용자는 ‘이 도구를 내 일에 쓰고 싶다’고 요청하고 입력 예와 기대 결과를 제공하면 된다. AI는 임시 Script, 등록 Script, 저장 함수, 패키지 가운데 필요한 수명과 책임에 맞는 경로를 고른다.

‘설치됨’과 ‘조합해서 쓸 수 있음’을 구분해야 한다. 추가한 도구는 기존 계약 안에서 다음을 설명할 수 있어야 한다.

| 연결에 필요한 정보 | 사용자에게 전달할 의미 |
| --- | --- |
| 목적과 적용 조건 | 어떤 일에 쓸 수 있고 어떤 경우에는 맞지 않는가 |
| 입력·반환 계약 | 어떤 자료를 받아 무엇을 돌려주는가 |
| 단위·시점·출처·대상 식별 | 숫자와 기록을 다른 자료와 합쳐도 뜻이 유지되는가 |
| 효과와 실행 위치 | 무엇을 변경하며 어느 기기·계정에서 실행하는가 |
| 의존성·판본·확인 상태 | 지금 쓸 수 있는가, 무엇이 준비되지 않았는가 |
| 실패와 복구 조건 | 다시 실행해도 되는가, 효과 확인이 먼저 필요한가 |

모든 도구에 거대한 온톨로지나 새 메타데이터 체계를 강요하지 않는다. 기존 `callable_contract`, 패키지 메타데이터, 판본과 실행 근거에 필요한 정보를 보충하고, 실제 소비자가 쓰는지 확인한다. 알 수 없는 의미·효과는 미확정으로 둔다. 최소 예제의 성공을 모든 입력의 검증으로 확대하지 않는다.

가장 중요한 인수 시험은 추가한 도구의 단독 실행이 아니다. **기존의 서로 다른 부품과 연결해 새로운 사용자 과제를 끝낼 수 있는지**다. 예컨대 개인 자료 정리 프로그램이 파일을 읽어 목록을 만들었다면, 기존 필터·검색·보고서 부품과 결합하여 새 조건의 산출물을 만들어본다. 권한이 필요한 외부 쓰기는 승인된 시험 대상에서 확인한다.

IBL 전용 도구로 다시 작성해야만 편입할 수 있게 만들면 조합의 이점이 이식 비용에 잠식된다. 외부 표준과 기존 프로그램을 어댑터로 수용하고, IBL 내부에서는 공통 계약을 유지하는 편이 사용자의 선택권에 맞다. [현재 Script 계약](../data/guides/script.md), [능력 변경 절차](../data/guides/capability_change.md)

## 7 네 번째 과제는 축적된 방법이 다시 발견되고 바뀌게 하는 것

관용구 저장 기능과 성공 기록은 이미 있다. 다음 단계는 사용자가 ‘지난번 방식으로, 이번에는 조건만 바꿔’라고 할 때 적합한 정의와 입력을 찾아 실제로 실행하는 경험이다. 새 입력에 맞지 않는 절차를 억지로 재사용하지 않고, 일부만 가져와 조합하거나 새로 작성할 수 있어야 한다.

저장된 능력의 사용자 표시는 기술 이름보다 업무 목적에 가까워야 한다. ‘무엇을 해주는지, 바꿀 수 있는 조건, 최근 확인한 결과, 필요한 자료·접근, 현재 쓸 수 있는지’를 보여주고 내부 구현은 펼쳐본다. 이 화면의 사실은 기존 등록부와 실행 기록에서 파생하여 별도의 수동 목록을 만들지 않는다.

‘다음에도 쓰기’는 이번 요청의 임시 조건과 지속할 선호를 나누는 작은 결정이다. 특정 날짜·대상·일회성 예외를 자동으로 영구 정책으로 굳히지 않는다. 사용 빈도만으로 저장을 늘리지 않고 재사용 가치가 있을 때만 축적한다. 저장한 뒤에는 새 입력의 성공, 실패 귀속, 대체된 판본, 실제 소비자를 바탕으로 수정·은퇴한다.

여기서 앱의 버튼은 문제의 스위치와 다르다. **같은 호출 가능한 정의를 다른 조합에서도 사용할 수 있고 필요한 부분을 바꿀 수 있다면**, 버튼은 부품의 편리한 표면이다. GUI에만 갇힌 매크로라면 조합은 다시 끊긴다. 선언형 앱과 저장 함수의 연결을 유지하고, 정의 변경 시 앱·다른 함수의 소비 계약까지 확인해야 한다. [선언형 앱 기반](../data/system_docs/architecture.md), [능력 변경의 호출자 보호](../data/guides/capability_change.md)

발견 개선은 목록 전체를 프롬프트에 싣거나 추천 알림을 계속 늘리는 방향이 아니다. 사용자 요구의 하위 과제와 자료·권한·실행 위치에 맞는 후보를 제공하고, 선택된 부품의 계약만 상세히 읽는다. 후보를 못 찾았을 때 전체 탐색으로 빠져나갈 경로도 필요하다. 이름을 기억하지 못해도 찾을 수 있어야 한다.

## 8 다섯 번째 과제는 관리와 고장을 사용자 업무에서 분리하는 것

개인 하네스의 자유는 장기간 쌓인 자산이 유지될 때 의미가 있다. 자기수리의 기술적 성공뿐 아니라 **원래 업무가 어디까지 복구되었는지**가 완료 기준이어야 한다. 수리된 코드·활성 세대·검증 결과·원래 요청을 기존 영수증으로 연결하고, 사용자는 기술 절차 대신 복구 상태와 필요한 결정을 받는다.

실패는 원인과 효과에 따라 다르게 다룬다. 입력 문제는 해당 입력을 보완하고, 인증 만료는 인증을 인계하며, 일시적 읽기 실패는 한정 재시도나 다른 자료원으로 전환한다. 계약 변화는 영향을 받는 부품을 검사·수리한다. 외부 쓰기의 응답이 사라졌다면 중복 실행보다 실제 효과 확인이 먼저다. 현재 범위 밖 수리는 그 한계를 알려주고 작업 결과와 진단 근거를 보존한다.

AI가 자기 실행 기반까지 항상 복구할 수 있다고 가정하면, 가장 필요한 순간에 정비 기능도 함께 사라질 수 있다. 기존 외부 재시작 제어자와 이전 정상 세대를 유지하고, 모델 없이도 상태 확인·안전한 복귀·진단 자료 내보내기를 할 수 있어야 한다. 이것은 새 감독 AI를 상주시킬 이유가 아니라 기존 생명주기 제어를 사용자 경험까지 닫을 이유다.

업데이트는 파일 교체, 의존성 준비, 프로세스 기동, 대표 개인 업무의 사용 가능성을 구분해서 보고해야 한다. 모든 외부 서비스의 성공을 설치 과정에서 요구할 수는 없으므로, 핵심 런타임 실패와 선택 도구의 미준비도 구분한다. `scripts/update.py`에서 확인한 경고 후 완료 반환은 이 구분을 시작할 구체적인 수리 지점이다.

OpenClaw도 업데이트·백업·복구를 별도 제품 기능으로 다룬다. 특히 실행 파일의 이전 버전 복귀와 데이터·설정의 이전 상태 복원은 다르다고 설명한다. IndieBiz OS에서도 코드 세대 복귀만으로 모든 사용자 데이터의 호환성이 복구되었다고 판단하면 안 된다. [OpenClaw 복구 문서](https://docs.openclaw.ai/install/updating/rollback-and-recovery)

개인 자산의 이동도 사용 가능성을 기준으로 검사한다. 도구·관용구·앱·필요한 기억을 새 설치에 가져온 뒤 자격 증명은 별도로 다시 연결하고 대표 업무를 수행한다. 원본 파일이 존재하는 것과 같은 기능이 작동하는 것은 다른 상태다. 비밀값을 포함한 무차별 환경 복사로 이 문제를 해결하지 않는다.

## 9 차별화를 보여줄 대표 사용자 여정

첫 시연은 익숙한 고정 절차의 성공만 보여주면 부족하다. 다음은 기능 목록보다 경험의 차이를 보여주는 **제안 시나리오**이며, 현재 전 과정의 성공을 주장하는 예시는 아니다.

1. 사용자가 자기 자료와 외부 공개 자료를 함께 사용해 비교·정리·산출물을 만드는 일을 맡긴다. 도구 이름이나 실행 순서는 지정하지 않는다.
2. 중간 결과를 보고 기준 하나를 바꾸고 새 파일을 제공한다. 시스템은 무엇이 바뀌는지 알리고 필요한 부분을 다시 수행한다.
3. 수집 도구 하나에 오류를 주입한다. 유효한 결과를 남기고 허용된 대안·복구로 업무를 계속한다.
4. 완료된 방법을 다음에도 쓰도록 보관한다. 다음 대화에서는 다른 입력과 다른 주제로 일부 부품을 재조합한다.
5. 관련 없는 도구들을 추가하고, 사용하던 개인 도구 한 개의 계약을 변경한다. 영향을 받는 호출자를 찾아 보완한 뒤 같은 업무를 다시 끝낸다.

연구·집필, 개인 자료 관리, 소규모 운영처럼 서로 다른 분야에서 수행한다. 필수 단계가 없는 간단한 요청까지 이 흐름으로 늘리지 않는다. 사용자가 목표를 수정하는 열린 과제도 포함하여 ‘미리 정한 결과를 자동 실행’하는 능력만 평가하지 않는다.

첫 개선 묶음은 이 여정의 구현된 연결을 최대한 사용하고 실제 공백만 메운다. 예시 업무 이름은 파서·엔진에 넣지 않으며, 필요한 특화는 기존 Script·함수·개인 사전에 둔다.

## 10 비교와 사용자 연구 설계

### 도구 수와 과제 복잡성을 나누어 비교하기

많은 도구를 가진 상황과 한 업무에서 많은 도구를 사용하는 상황은 다르다. 다음 축을 따로 변화시킨다. 수치는 시험 설계의 출발 제안이며 실측된 성능 경계가 아니다.

| 시험 축 | 구성 제안 | 확인할 질문 |
| --- | --- | --- |
| 검색해야 하는 도구 수 | 같은 과제에서 카탈로그 20·100·300개 | 무관한 도구가 늘어도 적합한 도구를 찾는가 |
| 조합 길이와 형태 | 같은 카탈로그에서 2·5·10단계, 병렬·조건 분기 포함 | 의존성과 실패가 늘어도 완주하는가 |
| 도구 이질성 | 로컬 파일·Python·HTTP·MCP·기기 도구를 분리 또는 혼합 | 실행 위치와 데이터 의미의 경계를 다루는가 |
| 익숙함 | 새 과제, 같은 방법의 새 입력, 다른 분야의 재조합 | 축적이 실제 새 일의 부담을 줄이는가 |
| 변화와 고장 | 입력 교체·스키마 변경·연결 실패·응답 유실·재시작 | 부분 결과와 효과를 보존하며 이어가는가 |

카탈로그를 늘릴 때 이름만 복제한 도구로 난이도를 부풀리지 않는다. 실사용 가능성이 있는 별도 기능·유사 후보를 포함하고, 동등 기능 매핑과 기본 도구 구성을 기록한다. 비용이 큰 실제 외부 쓰기는 격리된 시험 서비스에서 재현한다.

### 두 종류의 비교를 함께 하기

**IBL의 기여를 분리하는 시험**에서는 같은 모델·같은 도구 구현·같은 입력·권한·완료 조건을 두고, 현재 IBL과 구조화된 Python/TypeScript 조합 실행을 비교한다. 대안에도 적절한 도구 검색·계약·실패 처리 기반을 제공하고 구성 비용을 기록한다. 모델 호출마다 도구 하나만 허용하는 약한 대안만 이기고 일반 우위를 선언하지 않는다.

**제품의 사용자 부담을 비교하는 시험**에서는 IndieBiz OS, 실제 구성된 OpenClaw와 Lobster, goose 같은 완성 사용자 표면을 비교한다. SDK인 LangGraph를 일반 사용자가 처음부터 제품으로 만들어야 하는 조건으로 놓으면 불공정하다. SDK 계열은 개발·통합 부담을 연구하는 별도 비교로 둔다. 모델 통제가 가능한 조건과 각 제품의 권장 기본 조건을 나누고, 버전·확장·설치 도움을 명시한다.

### 측정할 결과

| 지표 | 정의와 해석 |
| --- | --- |
| 검증된 업무 완료율 | 산출물·외부 상태·사용자 요구를 확인한다. 응답의 완료 주장과 다르다 |
| 기술적 개입 시간 | 사용자가 설정·코드·도구 선택·복구 절차를 대신 처리한 실제 시간 |
| 유용한 개입 | 취향·판단·새 근거를 반영한 개입을 별도로 기록한다. 적다고 항상 좋은 것이 아니다 |
| 첫 가치까지 시간 | 설치 시작부터 자신의 첫 유효 결과까지의 경과 시간과 실제 조작 시간을 분리한다 |
| 수정 비용 | 기준·입력 변경 뒤 추가 설명, 버려진 유효 작업, 재실행 시간과 토큰 |
| 복구 품질 | 원래 목표 복귀, 누락·중복 효과, 사용자 구조 요청, 정상 상태 확인 |
| 재사용 전이 | 적합한 재사용 기회 중 새 입력·다른 조합에서 실제 성공한 비율 |
| 유지 부담 | 정해진 관찰 기간 동안 점검·업데이트·수리의 사용자 시간과 지원 요청 |
| 전체 실행 비용 | 주 모델·보조·검수·수리·후처리의 토큰과 청구액, 대기 시간을 별도 기록 |
| 소유와 이동 | 새 환경에서 개인 능력을 복구하고 실제 대표 업무를 수행하는 데 든 작업 |

정답이 있는 시험은 산출물·상태 검사로, 열린 업무는 사용자의 활용 가능성 판단과 별도 평가 기준으로 확인한다. 성공 사례만 평균내지 않고 실패·중도 포기·긴 지연을 포함하며 중앙값과 상위 지연 구간, 과제별 결과를 공개한다. 토큰 감소를 시간·청구액 감소로 대체하지 않는다.

ToolSandbox는 상태 의존성과 대화 중의 정보 부족을 포함한 평가를, τ-bench는 최종 상태와 반복 실행의 일관성을 평가하는 접근을 제시한다. 이 연구들의 과거 모델 점수를 현재 제품의 성능으로 인용하지 않고 평가 설계의 원칙만 사용한다. [ToolSandbox](https://arxiv.org/abs/2408.04682), [τ-bench](https://arxiv.org/abs/2406.12045)

### 일반 사용자 관찰과 장기 사용

처음에는 개발에 참여하지 않은 사용자 6~8명으로 실제 자료를 사용한 관찰을 제안한다. 개발자·비개발자를 구분하고, 사용자가 막혔을 때 제작자가 구해준 시간과 숨은 설명을 모두 기록한다. 이 규모는 주요 마찰을 발견하는 탐색 연구이며 시장 전체의 성공률을 추정하는 근거가 아니다.

이어 4주 정도의 반복 사용에서 도구 추가, 새 업무, 최소 한 번의 업데이트와 복구 상황을 관찰한다. 제품 비교를 하는 경우 순서를 균형 있게 배정하고 유사하지만 다른 과제를 사용해 학습 효과를 줄인다. 정량 우위를 주장할 단계에서는 예비 관측의 변동성과 목표 효과 크기를 바탕으로 표본 수를 정한다.

출시 판단은 자의적인 점수 하나보다 다음 조건을 함께 본다. 핵심 여정을 제작자 개입 없이 완료하고, 중복 외부 효과와 데이터 손실 없이 복구하며, 새 입력과 새로운 조합으로 능력이 전이되고, 품질을 유지하면서 사용자 기술적 개입과 전체 비용이 줄어야 한다. 테스트에서 사고 0건은 보편적 안전 보증이 아니다.

Microsoft의 Human-AI Interaction 연구는 처음 사용, 평상시, 오류 발생, 장기 사용을 함께 설계 대상으로 다룬다. 이 관점에 따라 첫 성공만큼 실패 후 복귀와 개인화의 수정 가능성을 제품 평가에 포함한다. [연구](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/), [HAX Toolkit](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/)

## 11 개발 순서와 기존 책임 연결

일정은 현재 인력과 운영 상태에 따라 산정하되, 의존 관계에 따른 순서는 다음과 같다. 사용자 연구를 기다려야만 공통 능력을 개발할 수 있다는 뜻은 아니다. 구조적으로 확인한 공백은 먼저 수리하고 실제 경험으로 효용과 퇴행을 확인한다.

| 순서 | 구현 묶음 | 재사용할 책임 | 완료를 판단할 근거 |
| --- | --- | --- | --- |
| 1 | 사용 가능 상태의 정직한 표시와 첫 업무 연결 | 온보딩·업데이터·재시작 제어·기존 대화 | 의존성 실패를 완료와 구분, 사용자 자료로 첫 결과, 외부 개발자 없이 다음 실행 |
| 2 | 한 작업에서 결과·자료·조향·복구 연결 | 대화 세션·steer·상황 인식·실행 통합 조회·continuation | 변경 접수와 반영 구별, 입력 판본 반영, 유효 결과 보존, 중복 효과 방지 |
| 3 | 개인 도구의 등록부터 기존 부품과 조합까지 | Script·callable_contract·능력변경완료·패키지 수명 | Python 등 기존 도구 편입 후 서로 다른 기존 부품과 새 과제 완료 |
| 4 | 다시 찾기와 수정 가능한 재사용 표면 | 함수 원장·해마·앱 선언·호출자 검사 | 이름을 몰라도 발견, 새 입력·다른 조합 성공, 정의 변경의 영향 안내 |
| 5 | 장기 유지와 개인 자산 이동 검증 | 코어 매니페스트·업데이트·백업·기존 복구 | 업데이트 후 대표 업무, 고장 후 원래 업무, 새 환경의 자산 재사용 |

1과 2를 첫 제품 개선 묶음으로 연결하고, 그 여정에 필요한 만큼 3과 4를 함께 적용하는 편이 적절하다. 기능을 다 완성한 뒤 한꺼번에 통합하지 않는다. 각 단계는 다른 분야의 미사용 과제에도 적용되는 공통 계약을 구현한다.

이 과정에서 별도 종합 플랫폼·세계 온톨로지·새 목표 DB·상시 감독 모델·독립 스킬 장터를 기본 해법으로 만들지 않는다. 새 표면이 필요하면 기존 원장의 조회와 명령을 연결하고, 대체되는 옛 입력·중복 설정·진단 경로를 함께 정리한다. 코어 어휘를 늘리기 전에 현재 Script와 함수로 표현 가능한지 확인한다.

## 12 무엇을 약속할 것인가

사용자에게 약속할 내용은 언어의 존재보다 자신의 일에서 확인할 수 있는 변화여야 한다.

> 내 자료와 도구로 새로운 일을 맡기고, 하던 중에 바꾸고, 잘된 방법을 다음 일에 다시 쓰며, 고장 나도 이미 한 일을 잃지 않고 이어갈 수 있다. 이를 위해 내가 매번 도구 연결과 시스템 정비를 맡을 필요는 없다.

지원 범위 밖의 외부 효과를 되돌릴 수 있다거나 모든 고장을 자동 수리한다는 약속은 포함하지 않는다. 책임 있는 통제는 가능한 행동과 불가능한 행동을 이해할 수 있게 하는 것이다.

장기 차별화의 자산은 IBL 문법만이 아니라 **검증된 부품의 계약, 사용자의 실제 기준, 새로운 조합에 쓰이는 경험, 변화와 고장을 넘긴 신뢰**다. 이 자산이 많아질수록 사용자의 선택 폭은 커지고 기술적 관리 부담은 낮게 유지되는지 확인해야 한다. 그것이 자동차 비유를 제품의 실제 차이로 바꾸는 기준이다.
