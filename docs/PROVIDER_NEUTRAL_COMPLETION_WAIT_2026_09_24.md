# 프로바이더 공통 완료 대기

## 문제와 완료 조건

에피소드 4018은 관용구 한 번으로 보고서와 공유판을 저장했지만, 바깥 Codex는
30초 반환 뒤 wait 9회·sleep 3회로 기다렸다. 16라운드 중 12라운드,
571,663토큰(캐시 포함)이 대기 관리에 쓰였다. 결과 회수도 약 43초 늦었다.

첫 수정 b96eb031은 공통 완료 경계와 Codex 직접 MCP 호출을 도입했으나,
840초 완료 대기·CLI 무출력 600초·IBL 실행 예산 900초가 남았다.
따라서 14분 이내를 일괄 보장한다는 설명도 정확하지 않았다. 이번 개정은
관용구와 임의의 긴 IBL 프로그램 모두에서 이 세 경계를 분리한다.

원칙: 정상 실행의 길이만 늘었다고 모델 호출 수가 늘면 안 된다.
완료·실패·사용자 취소·연결/소유자 소실만 결과 경계를 연다.
대기자의 생존과 업무 진행을 같은 사실로 기록하지 않는다.

## 공통 실행 계약

- `tool_completion.await_completion`의 기본 총시간 마감은 없다.
  신뢰된 `DeferredToolResult(task_id, poll)` 또는 Future를 기다린다.
  업무 JSON의 status=running을 실행 명령으로 해석하지 않는다.
  명시적 `timeout`을 준 호출만 시간 예산을 적용한다.
- API 8경로(OpenAI·OpenRouter·DeepSeek·Anthropic·Gemini·Ollama·Gemini REST·
  DeepSeek REST)는 같은 `BaseProvider._execute_tool_to_completion`을 거친다.
  동기 값·이미지·승인 요청과 각 제공자의 tool-result 계약을 보존한다.
- CLI 두 경로는 같은 MCP 서버를 쓴다. 최초 HTTP 제출은 1회다.
  30초 전송 대기나 연결 오류 후 같은 티켓을 코드에서 회수한다.
  회수 중 running은 모델로 반환하지 않는다. 완료 업무 값의 status=running은
  `_recovered_from_ticket`으로 구별한다. 짧게 실패하는 연결에는 backoff가 있다.
- IBL 판본 2의 `Budget.seconds` 기본값은 None이다. 단계·행·깊이 한도는 유지한다.
  개별 도구의 자체 시간 제한과 명시적 `Budget(seconds=...)`는 그대로다.
  따라서 긴 대기를 허용하면서 무한 반복 방지와 개별 작업 정책을 보존한다.

## 생존·통신·취소

`completion_lease.py`가 턴마다 무작위 채널을 만든다. CLI→MCP의 env/HTTP 헤더로
전달하고 모델 인자에는 넣지 않는다. MCP 대기자는 티켓별 lease를 원자적으로 갱신한다.
CLI는 출력이 없어도 유효한 lease와 대기자 프로세스가 있으면 기다린다. lease는
45초 후 만료하며 죽은 대기자·다른 턴·끝난 티켓은 무출력 감시를 해제하지 못한다.
동시 도구는 티켓별로 기록하여 하나의 완료가 다른 도구의 대기를 지우지 않는다.

MCP의 연속 연결/읽기 실패는 120초 후 `transport_unavailable`과 원래 티켓을
반환한다. 정상 응답이 오면 장애 구간을 초기화한다. 이 시간은 업무 실행 한도가 아니다.
CLI 취소 감시는 stdout과 독립적으로 동작하고 채널에 취소를 기록한다. IBL은 이를
기존 협력적 취소 검사로 받는다. 이미 블로킹 중인 외부 도구까지 강제 종료됐다고
주장하지 않는다. 정상 종료·취소된 채널의 파일은 뒤에 24h GC로 정리한다.

티켓은 실행 소유 프로세스의 PID·생성 시각을 보관한다. 프로세스 소실이나 PID 재사용은
`interrupted`와 `execution_status=unconfirmed`로 보고한다. 원격 부작용의 완료 여부는
추정하지 않으며, 자동 재제출하지 않는다. 살아 있는 실행 티켓은 24h 스필 GC에서
제외한다. 완료 영수증의 기존 보관 기간은 유지한다. 옛 owner 없는 티켓의 생존 여부는
단정할 수 없다. Future는 프로세스 안의 핸들이며 영속 재개 수단이 아니다.

기존 명시적 recover(한 번의 조회 최대 840초)와 백그라운드 상태 조회는 유지한다.
작업을 의도적으로 배경으로 보낸 호출에 강제 완료 대기를 덧붙이지 않는다.
진행 좌표·마지막 갱신 시각은 업무 관측이며, 오랫동안 바뀌지 않았다는 사실만으로
작업이 죽었다고 판단하지 않는다.

## 외부 CLI 연결 계약과 한계

Codex는 IBL MCP 네임스페이스를 `direct_only_tool_namespaces`로 직접 호출한다.
전역 사용자 설정을 변경하지 않고 자식 실행에만 적용한다.
[공식 구성 참조](https://learn.chatgpt.com/docs/config-file/config-reference).

Claude Code는 `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0`으로 자동 배경 전환을 끈다.
두 CLI의 stdio/HTTP 도구 timeout은 `common.completion_contract.MCP_CLIENT_TIMEOUT_S`로 통일한다.
Codex의 stdio 환경 필터를 통과하도록 신원을 명시적 env에 넣고, Claude Code도
턴별 임시 stdio 설정에 넣는다. 공유 설정의 신원을 덮어쓰지 않는다.
[Claude Code MCP 문서](https://code.claude.com/docs/en/mcp)는 배경 전환과
도구별 hard timeout, 진행 알림이 그 한도를 연장하지 않음을 명시한다.

외부 CLI는 무기한 timeout 해제를 공통으로 지원하지 않는다. 따라서 숫자형 연결 한도는
JS의 signed 32-bit 밀리초 타이머 범위 안의 2,147,483초(약 24.8일)로 설정했다.
이것을 무제한 연결이라고 주장하지 않는다. 한 시간 임계나 모델 폴링 주기가 아니며,
그 한도·클라이언트 종료·호스트 재시작까지 자동으로 넘어서는 세션 복구는 제공하지 않는다.
그 경우 원래 작업의 영수증과 실행 저널을 이용해 복구해야 한다.
기존 자동 생성 timeout 900000ms는 이행하고 그 외 사용자 명시값은 보존한다.

## 호출 설명

함수 describe는 서명·상태·검사 수·증거 참조를 기본 반환한다. 내부 검사 진단은
read_result로 조회한다. 실행 검사는 유지한다. 4018의 62개 진단(약 5.6만 자)은
이미 참조로 접혔으므로 이를 주된 토큰 낭비로 계산하지 않는다.

## 검증

`test_long_completion.py`는 시간 경과 1시간·2시간·48시간의 완료 경계, 2시간 지난
예산으로 실행하는 실제 병렬/함수 IBL, 명시적 예산, 실제 subprocess의 무출력 장기
도구·취소·lease 만료, 티켓 GC·PID 재사용, API 취소 전달을 검사한다.
실시간으로 한 시간 기다린 시험은 아니며 시간 경과를 주입한다.
기존 `test_tool_completion.py`의 API 8경로는 고정 모델 응답을 이용한 실제 어댑터
회귀다. 모든 원격 모델을 유료 실호출했다는 뜻이 아니다.

최초 Codex 실호출(40초): 도구 1회·모델 응답 2회·wait/sleep 0회,
입력 30,695·출력 73·캐시 20,608토큰. 작은 시험이므로 4018과 절감률을 직접 비교하지 않는다.
Claude Code는 CLI 미로그인으로 실제 모델을 통한 완료 시험을 못 했다.
실행·검증 최종 결과는 아래에 기록한다. 운영 보고서는 새로 발행하지 않았다.

후속 Codex 실호출: 실제 provider → MCP → 격리 HTTP 서버 연결로 40초 작업을 실행했다.
작업 시작 시 CLI 무출력 한도를 3초로 낮췄다. 최초 시험에서 stdio env 필터가
채널을 지우는 문제를 재현했고, 명시적 전달 수정 후 제출 1회·코드 회수 48회·
모델 응답 2회로 완주했다. 입력 35,102·출력 58·캐시 5,504토큰, 총 약 49초.
모델의 wait/sleep 호출은 없었다. 기록: `outputs/long_completion_probe/`.

회귀 통과. 전체 재실행과 이 집중 검증을 구분한다. 층·몸 번들·어휘/문서 파생·
은퇴 계약 검사 통과. 실행 런타임은 ACTIVE이며 최종 소스의 코드 해시와 일치한다.
