# 프로바이더 공통 완료 대기

## 문제와 완료 조건

4018의 IBL 관용구는 한 번 실행되어 보고서와 공유판을 저장했다. 바깥 Codex는
코드 실행 셀의 30초 반환 뒤 wait 9회·sleep 3회로 기다렸다. 전체 16라운드 중
12라운드, 571,663토큰(캐시 포함)이 대기 관리에 쓰였다. 186초 실행의 결과를
약 43초 늦게 회수했다. 관용구 내부 작성과 별개인 실행 연결의 문제다.

공통 원칙: 대기 중인 작업은 모델의 판단 재료가 아니다. 실행기는 같은 작업의
완료·실제 실패·취소 요청·대기 마감까지 기다린다. 정상 작업의 길이만 늘어난다고
모델 호출 수가 늘면 안 된다. 진행 관측은 모델 입력과 분리한다.

## 소유 구조

- `backend/base/tool_completion.py`가 완료 대기의 공통 계약을 소유한다.
  `DeferredToolResult(task_id, poll)`와 `CompletionState(done, value, progress)`는
  실행 코드가 만든 Python 핸들이다. Future도 수용한다. 임의 도구 JSON의
  status=running을 비동기 실행 명령으로 해석하지 않는다.
- `BaseProvider._execute_tool_to_completion`을 API 어댑터의 도구 결과 경계로 쓴다.
  OpenAI·OpenRouter·DeepSeek·Anthropic·Gemini·Ollama·Gemini REST·DeepSeek REST가
  같은 완료 함수를 거친 뒤 벤더별 tool-result 메시지를 만든다. 동기 결과·이미지·
  승인 요청은 그대로 보존한다. 기존 동기 API 경로에 새 모델 호출을 추가하지 않는다.
- CLI 두 경로(Codex·Claude Code)는 공통 MCP 서버에서 같은 대기 함수를 사용한다.
  최초 HTTP 실행은 한 번만 제출한다. 30초 전송 대기나 연결 오류가 생기면 서버가
  기존 티켓을 회수한다. 회수 중 running·일시 읽기 실패는 모델로 반환하지 않는다.
  완료한 업무 값 자체의 status=running은 `_recovered_from_ticket`으로 구별한다.
- Codex 어댑터는 IBL MCP 네임스페이스를 직접 호출하도록 연결한다.
  `features.code_mode.direct_only_tool_namespaces=["mcp__indiebizos"]`로 호스트의
  exec/wait 반복을 우회한다. 전역 설정은 변경하지 않고 해당 자식 프로세스에만 적용한다.
  MCP timeout은 공통 SURFACE_CLIENT_WALL_S를 사용한다. Claude Code는 기존 직접
  MCP 호출과 공통 timeout 설정을 유지한다. 프로바이더별 프롬프트 대기 요령은 추가하지 않는다.

설정 근거: [공식 구성 참조](https://learn.chatgpt.com/docs/config-file/config-reference).
현재 설치된 Codex의 실제 도구 호출로 지원을 확인했다. 외부 CLI의 미래 버전이
이 계약을 계속 지키는지는 연결 회귀로 확인해야 한다.

## 실패·수명·취소

대기 마감은 공통 840초, MCP 클라이언트 벽은 900초다. 내부 HTTP 왕복과 모델의
왕복은 다르다. 빠르게 실패하는 연결에는 코드에서 backoff를 적용한다.
진행 변경·대기 종료는 `tool.completion_wait` 관측 콜백으로 기록할 수 있다.
이벤트 기록이 곧 새 UI 화면이나 모델 호출을 뜻하지 않는다.

마감·취소는 대기자의 종료다. `execution_status=unconfirmed`와 작업 ID를 남기며
원격 작업이 죽었다고 표현하지 않는다. 알려지지 않거나 만료된 티켓은 불확실한
결말로 반환하고 실행을 자동 재제출하지 않는다. MCP 클라이언트 취소는 대기 워커를
해제하며 실행 중인 원래 작업과 영수증은 기존 런타임이 소유한다.

영속 회수는 기존 IBL 티켓 저장소가 담당한다. Future는 프로세스 안의 대기에만 쓰며
프로세스 재시작 후 복구 가능한 핸들이라고 주장하지 않는다. 새 영속 작업 엔진이나
범용 취소 RPC를 만들지 않는다. 명시적 `recover`·백그라운드 상태 조회는 기존의
짧은 조회 계약을 유지하며 의도적으로 분리한 작업을 강제로 기다리지 않는다.

## 호출 설명 비용

함수 계약 조회의 62개 내부 검사 진단(약 5.6만 자)을 호출 계약과 분리했다.
기본 describe는 서명·상태·검사 수·증거 참조를 반환한다. 전체 진단은 동일한
read_result 경로에서 읽는다. 실행 시 검사나 오류의 의미를 약화하지 않는다.
4018에서는 큰 조회가 이미 참조로 접혔으므로 그것을 주된 토큰 낭비로 계산하지 않는다.

## 검증

- 실제 API 어댑터 결과 경로에 지연 완료 핸들을 넣어 제출 1회, 완료 후 후속 모델
  호출 1회만 발생함을 확인한다. OpenAI 상속 제공자와 REST 두 경로도 포함한다.
- 가상 시계의 1·30·300·800초 작업에서 완료 경계 불변. 취소·마감·업무 실패·이미지
  보존·업무 status=running과 대기 상태 구별·실제 HTTP 연결 타임아웃 후 회수를 검사한다.
- Codex 실호출: 무해한 40초 MCP 도구를 한 번 호출해 완료. wait/sleep 없음,
  도구 요청과 최종 답변의 2 모델 응답. 입력 30,695·출력 73·캐시 20,608토큰.
  작은 시험 프롬프트이므로 4018과 토큰 절감률을 직접 비교하지 않는다.
- Claude Code는 MCP 연결과 직접 도구 노출까지 확인했다. 최초 시험은 환경의 API
  잔액 부족, 실제 프로바이더 환경으로 재시험은 CLI 미로그인으로 모델 호출을 못 했다.
  이를 실제 완료 검증으로 세지 않는다. API 제공자들도 유료 원격 모델 전체를 호출한
  것이 아니라 실제 어댑터 루프의 모델 응답을 고정한 회귀다.

회귀: `backend/test_tool_completion.py`, `backend/test_surface_ticket_recovery.py`.
로컬 CLI 시험 기록: `outputs/provider_wait_probe/`(인증 정보는 기록하지 않는다).
새 보고서 발행이나 운영 작업 재실행은 하지 않았다.

전체 백엔드 1차: 5,797 통과·1 skip·2 실패. 새 시험의 직접 실행 진입점 누락을
고쳤다. 다른 실패는 기존 `_bg_runner.py`가 `time.time()` 차이를 -148ms로 기록한
시간 측정 건으로, 이번 완료 대기의 monotonic 시계와 별개다. 최종 변경 뒤 관련
집중 회귀 51개가 모두 통과했다(두 실패 검사 포함). 기존 러너의 코드는 변경하지
않았으며 전체 재실행은 하지 않았다. 어휘·문서 파생, 몸 번들, 층·은퇴 계약 검사도
통과했다. 실행 중인 백엔드와 최종 코드의 manifest digest 일치를 확인했다.
