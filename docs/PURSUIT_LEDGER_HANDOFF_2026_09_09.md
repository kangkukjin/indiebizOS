# 과제 객체 영속화 — 구현 계약 (2026-09-09)

상태: **구현됨.** 초기 설계와 두 차례 검토를 반영한 현재 계약이다.
사용자 요청: 의식이 만드는 규정·전제·진행이 여러 턴과 재기동을 넘어 이어지도록 한다.
실패 회상 검색과 조건 자동 재개는 별도 후속 범위다.

## 0. 무엇을 보존하는가

`pursuit`는 여러 턴에 걸친 과제다. 기존 `task_id`는 계속 한 턴을 뜻한다.
과제에는 현재 규정·깨진 전제·전체 완료 기준·확보한 결과·다음 행동·미해결 질문이 산다.
과제 원장은 실패 회상과 전망 기억의 기반이며, 요약 자체가 손실 없음을 보증하지는 않는다.
원문 사건과 산출물 참조를 함께 남겨 요약을 다시 검토할 수 있게 한다.

IBL 어휘는 추가하지 않았다. `pursuit`는 `reframe`과 같은 인지 이음매 도구다.
몸 사이의 과제 동기화는 없다. 자아별 DB/소유자 키로 격리하며 대화 삭제와 독립이다.

## 1. 구현 위치

- `backend/datastore/pursuit_ledger.py`: SQLite 저장, 소유권, 버전, 순서, 멱등성, 삭제 트랜잭션.
- `backend/cognition/pursuit_bind.py`: 턴 연결, AI 선택·재검토·요약, 재규정 훅, 주입, 관문.
- `backend/cognition/pursuit_tools.py`: 실행자 도구의 단일 구현.
- `backend/cognition/pursuit_maintenance.py`: 기존 일일 생명주기 순찰에 붙는 검사.
- `backend/surface/api_pursuits.py`: MCP 브리지와 조종실 HTTP 표면. `api_ibl` 라우터가 포함한다.
- `frontend/src/components/launcher-components/PursuitLedger.tsx`: 조종실 목록·상세·상태·삭제.
- `backend/test_pursuit_ledger.py`: SQLite, 실제 파이프라인, 브리지, S1~S3 회귀.

시스템 AI는 `system_ai_memory.db`, 프로젝트 에이전트는 해당 프로젝트 `conversations.db`에 저장한다.
같은 DB에서도 `agent_key`가 다른 과제는 실행자가 읽거나 고칠 수 없다.
조종실은 사용자의 관리 표면이므로 자아별 과제를 함께 보여준다.

## 2. 저장 계약 — 세 표와 세 종류의 상한

| 표 | 역할 | 수명 |
|---|---|---|
| `pursuit` | 현재 상태 JSON, version, 상태, 생성·갱신·마지막 참여 시각 | 명시 삭제 전까지 |
| `pursuit_event` | 생성·재규정·진행 갱신·목표 변경·상태 변경·도구 관측의 원문 사건 | 명시 삭제 전까지, 페이지 단위 읽기 |
| `pursuit_turn` | 턴 입력·도구 결과·응답·요약 처리 상태·출처 순서 | 명시 삭제 전까지 |

`pursuit_turn`을 별도로 둔 이유는 **실행 완료와 요약 완료가 다른 시각**이기 때문이다.
턴은 running → pending/interrupted → applied로 관리한다. 이는 사용자 일의 단계가 아니라 저장 처리 상태다.

현재 상태의 주요 상한:

| 필드 | 상한 | 의미 |
|---|---|---|
| title | 60자 | 과제 이름 |
| framing / progress | 각 3000자 | 현재 규정 / 확인된 결과 |
| approach / goal_criteria | 각 1500자 | 접근 / 과제 전체의 완료 기준 |
| next | 600자 | 다음 행동 |
| assumptions | 12항목 | holding/broken, 근거, 턴 |
| open_questions / artifacts | 8 / 30항목 | 미해결 질문 / 산출물 참조 |
| waiting_for | text 300자, probe 2000자 | 조건 저장만. 자동 실행하지 않음 |

원장 쓰기는 필드 상한 초과를 거절한다. 이전 상태를 손상하지 않는다.
사건과 턴 개수에는 누적 상한을 두지 않는다. 현재 전제 목록에서 접힌 과거 전제도 사건에 남는다.
주입은 별도 예산이다: 목차 최대 10줄, 본문 3000자. 목표 공간을 먼저 확보하고 다른 필드는
생략 표식과 `pursuit read` 경로를 남긴다. XML escaping으로 목표 자체가 예산을 넘는 예외에도
목표 전문을 읽으라는 명시 표식을 남기며 말없이 숨기지 않는다.

## 3. 선택과 규정 재검토

1. 회상 뒤, 실행 전에 이 메시지가 어느 과제의 이어짐인지 선택한다.
   선택은 THINK/EXECUTE/Reflex와 독립이다. 목차가 없으면 선택 호출도 없다.
   고유 title 또는 ID 명시는 선택 호출만 생략한다. 완료·보관 과제도 ID로 다시 열 수 있다.
   추론 선택에는 최근 대화와 과제 목차를 제공한다. 모호하거나 새 일이면 연결하지 않는다.
2. 연결된 과제의 이전 완료 턴 중 아직 요약되지 않은 것을 먼저 반영한다.
   실패하면 원문을 보존하고 실행 전에 오류로 돌려보낸다. 다음 시도에서 재개한다.
3. 별도 AI 판단으로 규정을 keep/amend/rewrite 중 선택한다.
   사용자 반박·대상 변경·전제 정정은 과제 연결을 끊지 않고 재검토한다.
   빠른 실행으로 분류됐어도 amend/rewrite라면 THINK로 올려 의식을 거친다.
4. THINK의 keep/amend는 기존 규정을 재사용하되 이번 턴 `achievement_criteria`를 새로 만든다.
   amend 전문이 너무 짧거나 연속 고쳐쓰기 2회 상한에 닿으면 의식을 다시 깨운다.
   수리 권한이 걸렸던 규정은 매번 새 의식으로 검토한다. 과거 권한은 상속하지 않는다.
5. 새 규정을 원장과 이번 실행자 본문 양쪽에 반영한다. 저장한 구조화 전제는 기존 실행자가
   받는 문자열 목록으로 변환한다. 깨진 전제는 과제 본문과 사건 기록에서 읽힌다.

동일 과제의 두 실행 턴이 겹치면 뒤의 실행은 기다렸다 다시 시작하도록 오류를 반환한다.
다른 과제의 동시 실행과 조종실에서의 상태 변경은 허용한다. MCP는 agent_id+task_id로
활성 턴을 식별하며 모호한 신원으로 다른 턴에 붙지 않는다.

선택·재검토·진행 요약은 유효한 JSON 예시를 제시하고 응답의 객체 모양·필드·값 타입을
검증한다. 형식 또는 필드 검증 실패 시 원래 요청과 직전 실패 응답을 주어 **한 번만 재요청**한다.
두 번 모두 실패하면 기존 과제와 실행 기록을 보존한 채 오류를 반환한다. 실패한 응답을
`keep` 또는 새 과제로 간주하지 않는다. 로그에는 단계·시도 횟수·검증 오류와 비밀 마스킹을
거친 응답 미리보기(1200자, 초과분 표시), 궤적에는 `pursuit.judgment_failed` 메타데이터를 남긴다.
에피소드 #3315의 재검토 JSON 오류를 계기로 추가했다(2026-09-10).

## 4. 생성과 완료 기준

- 의식 출력 `scope:"pursuit"`이면 title/goal_criteria와 함께 생성한다.
- 재규정, 사용자 질문으로 마침, 최종 NOT_ACHIEVED는 아직 과제가 없는 턴을 승격한다.
- 사용자는 실행자에게 open을 요청해 명시적으로 생성할 수 있다.
- 전체 `goal_criteria`와 이번 턴 `achievement_criteria`는 별개다. 턴 평가 성공만으로 과제를 닫지 않는다.
- 전체 완료는 실행자의 `pursuit{op:"done", why}` 또는 사용자의 조종실 조작으로 기록한다.
  시작 시점의 의식 출력만으로 아직 실행하지 않은 일을 완료 처리하지 않는다.
- 전체 목표 변경은 `pursuit{op:"goal", goal_criteria, why}`이며 사건을 별도로 남긴다.

## 5. 갱신·순서·재시도

모든 상태 쓰기는 읽었던 version을 원자적으로 검사한다. 사건 적재와 상태 변경은 같은
트랜잭션이다. event_key가 같은 재시도는 다시 적용하지 않는다.

턴의 source_order는 실행 시작 사건에서 고정된다. 각 상태 필드에 마지막 작성 턴의 순서를
기록한다. **늦은 이전 턴 요약은 후속 턴이 이미 고친 필드를 다시 쓰지 못한다.**
예: A가 “파일 생성 완료”, B가 “잘못된 파일 폐기”를 남겼으면 현재 상태는 B다.
A의 주장도 사건에는 남고 `superseded_fields`로 왜 현재 상태에 적용하지 않았는지 보인다.
호환되는 나머지 필드는 반영한다. 의미 충돌을 AI가 임의로 해결해 최신 정정을 되살리지 않는다.

요약은 최신 상태와 원문 턴을 AI에게 주어 다시 쓴다. 호출 중 버전이 변하면 최신 상태로
다시 요약하고 쓰기 직전에 다시 검사한다(3회 한도). 요약이 쓸 수 있는 필드는
progress/next/open_questions/artifacts뿐이다. 상태·전체 목표·규정은 요약이 고치지 못한다.

요약 실패는 error와 사건으로 남기고 원문을 만료하지 않는다. 24시간은 삭제 시각이 아니라
자기점검 RED의 기준이다. 영속 증류 큐가 패킷(DB·자아·과제 ID)을 운반하고 재시도한다.
앞선 요약이 밀린 경우 다음 연결 시에도 같은 함수를 호출하므로 큐 처리만 기다릴 필요가 없다.

## 6. 중단과 재기동

도구 시작/결과는 스트림에서 관측할 때 즉시 원장에 남긴다. 턴 종료 시 응답과 도구 이력을
pending으로 먼저 저장한 뒤 비동기 요약을 요청한다. 프로세스가 죽어도 이미 관측한 결과는 남는다.
실행과 사건 저장 사이의 강제 종료까지 원자적일 수는 없으므로 중단된 턴은 완료로 추정하지 않는다.

다음 연결 또는 기존 일일 순찰에서 이전 프로세스의 running 턴을 interrupted로 표시한다.
응답 없는 중단 턴은 AI가 억지로 완료 요약하지 않는다. 본문에 중단 표식을 넣고 실행자가
`pursuit read section=turns`로 원문·산출물을 확인한 뒤 이어가도록 한다.

프로젝트 WebSocket 작업은 워커의 종료 신호까지 도구 메타를 수신한 뒤 `tasks`를 닫는다.
예외·오류 이벤트·최종 응답 부재는 `failed`, 사용자 중단은 `cancelled`, 정상 응답은
`completed`로 기록하며 실패 사유를 result에 남긴다. 클라이언트가 시간 초과로 먼저 떠나면
같은 종료 처리를 워커가 맡는다. `pursuit_turn.episode_id`는 현재 에피소드의 실제 번호를 저장한다.

대화 삭제/SESSION_RESET은 과제를 지우지 않는다. 삭제는 조종실에서 version 확인 후
과제·사건·턴을 외래키 CASCADE 한 트랜잭션으로 지운다.

## 7. 도구와 조종실

실행자와 MCP의 의미는 한 구현으로 닫힌다.

```text
pursuit {op:"read", id?, section?, offset?, limit?}
pursuit {op:"open", title, goal_criteria}
pursuit {op:"note", progress?, next?, open_questions?, artifacts?}
pursuit {op:"wait", waiting_for, probe?}
pursuit {op:"park"|"done"|"abandon"|"resume", why}
pursuit {op:"goal", goal_criteria, why}
```

read section=list는 자아의 전체 목차, events/revisions는 사건 페이지, turns는 턴 원문,
그 외 section은 해당 상태 필드 전문이다. 쓰기는 이 턴에 연결된 과제만 허용한다.
MCP 도구 이름은 `mcp__indiebizos__pursuit`, HTTP 브리지는 `/ibl/pursuit`다.

조종실의 “이어가는 과제”에서 목록·전체 완료 기준·규정·진행·깨진 전제·사건을 읽고,
보류/완료/보관/재개/삭제할 수 있다. “이어갈 요청 복사”로 ID가 포함된 요청을 대화에 전달한다.
과제 전체 목록과 상세·상태 변경·삭제 API는 `/ibl/pursuits` 아래에 있다.

## 8. 생명주기와 관문

- 30일 무접촉은 parked, 120일 무접촉은 abandoned. 행을 지우지 않는다.
- 기존 `component_lifecycle` 일일 번들에 편입했다. 새 순찰/자동 재개는 없다.
- G1: 의식의 과제 생성 선언과 원장 행의 존재를 턴 종료 때 대조한다.
- G2: 재규정 시도 수와 해당 턴의 원장 재규정 사건 수를 대조한다.
- G3: 상태 쓰기 한도는 거절, 주입 생략은 표식. 원문과 주입의 상한은 다르다.
- G5: 삭제의 외래키 정합과 rollback을 회귀로 검증한다.
- G6: 버전 없는 상태 쓰기는 거절, 미반영 턴 24시간 초과는 일일 자기점검에 남긴다.

## 9. 검증 고정물

`backend/test_pursuit_ledger.py`는 실제 SQLite로 다음을 검증한다.

- S1: 동일 과제 반박 → rewrite → 깨진 전제 기록, 전체 기준 보존.
- S1 확장: 실제 파이프라인의 Reflex 정정 → THINK → 새 본문 → 영속 종료 패킷.
- S2: 다른 일을 거친 뒤 옛 과제 선택. 모호한 경우는 연결하지 않는다.
- S3: A 요약 전 B 정정, 버전 충돌 재합류, 늦은 A가 B를 되돌리지 못함.
- S3 읽기: 요약 대기 중 다음 턴 시작 → 원장 따라잡기. 요약 실패 시 원문 보존·실행 보류.
- 자아 격리, 생성/쓰기 멱등성, 사건 200건 초과, 예산 표식, 중단 복구,
  삭제 rollback, 생명주기·부활, 전체 완료 분리, 동일 과제 동시 실행 차단, HTTP 도구 대칭.

기존 재규정 시험은 유지한다. 캐시 기반 재사용 시험은 영속 과제의 같은 동작을 검사하도록
옮겼다. 의식 출력 라우팅 관문은 scope/title/goal_criteria가 실제 원장에 닿는지 확인한다.

## 10. 후속 범위

과거 과제의 깨진 전제를 검색해 새 과제에 주입하는 실패 회상, waiting_for.probe의 자동 검사·재개,
몸 사이 과제 공유는 구현하지 않았다. 저장·이어 하기·도구·조종실·망각은 이번 구현 범위다.
