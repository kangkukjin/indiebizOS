# 과제 연결의 실행 전 AI 호출 제거 — 2026-09-20

최초 숙고 OFF에서도 과제 원장에 후보가 있으면 별도 경량 AI가 선택하고, 선택됐으면 다시
연결을 검토했다. 미정리 턴의 요약도 실행 전에 기다렸다. 과제 준비가 EXECUTE를 THINK로
바꾸는 분기까지 있어 토글의 기대와 실행 시작 비용이 어긋났다.

윈도우 사용자의 약 30초 지연 보고가 계기다. 해당 윈도우의 원인·개선 시간을 측정한 것은 아니다.
이 맥의 최근 100개 에피소드에서는 선택 68건 중 61건이 미연결, 7건이 연결 후보였고 그중 1건은
재검토에서 분리됐다. 로컬 관측은 불필요한 사전 호출의 반복을 보여주며 윈도우 지연의 진단을 대신하지 않는다.

## 실행 계약

- `prepare()`는 후보 목차만 반환한다. 모델 호출, begin_turn, 진행 요약, THINK 승격을 하지 않는다.
- 목차는 최대 9개 과제의 ID·제목·상태·목표 발췌와 누락 개수/조회 경로를 싣는다. 목표 발췌는
  180자, XML escaping 뒤 목록 본문은 5000자 이내다. 명시 ID는 후보 앞에 배치하지만 자동 연결하지 않는다.
  전체 목록과 상세는 기존 read로 접근한다. 타 자아/없는 ID는 현재 질문을 막지 않는다.
- THINK/REPAIR에서는 원래 호출하는 의식이 `pursuit_id`와 `pursuit_reason`을 출력한다.
  기존 출력 검증·정정 통로로 검증한 뒤 해당 과제를 연결하고 새 현재 프레임을 기록한다.
  새 과제(scope=pursuit이고 기존 연결/선택 ID 없음)일 때만 제목·전체 목표가 필수다.
- EXECUTE/반사에서는 실행자가 `pursuit{op:"bind", id, why}`로 필요한 과제만 연결한다.
  반환값은 전체 목표·현재 상태·미정리 턴 요약이며 AI 요약을 기다리지 않는다.
  `bind`는 기존 인지 도구의 연산이며 IBL 어휘 추가가 아니다.
- 미연결/모호한 요청은 현재 모델이 그대로 답한다. 최신 과제·같은 분야만으로 연결하지 않는다.
  대명사의 대상은 현재 요청·최근 대화로 해소하며, 후보 설명을 선행 발화로 삼지 않는다.
- 의식의 연결 후에는 `refresh_memory`가 전체 목표·상태·pending 표식을 실행자에게 전달한다.
  실행자의 연결은 같은 정보를 도구 결과로 전달한다. 미정리·중단 턴의 실제 결과를 확인하고 이어간다.
  MCP `detail=true, task_id`는 과거 턴 조회에 전달되며 활성 호출 신원 task_id와 구별한다.
- 사실 통보(CONTEXT_UPDATE)도 기존 과제 읽기·연결·진행/목표 정정·분리는 허용한다.
  open/done/resume 등 새 과제 생성·상태 변경으로 작업을 확대하지 않는다.
- 진행 요약은 응답/도구 원문 영속화 후 기존 증류 큐에서 수행한다. 기존 요약 필드 검증·재시도·
  출처 순서·늦은 정정 보호는 유지한다. 요약 오류가 다음 요청의 준비 단계를 막지 않는다.

## 보존하는 경계

소유자와 활성 턴 신원, 같은 과제의 동시 실행 차단, 전체 목표의 명시 변경, 분리된 턴의 원문 보존과
늦은 요약 차단을 유지한다. bind에는 1~800자의 연결 근거가 필요하고 같은 연결의 재호출은 멱등이다.
연결 실패 후 인메모리 row가 연결된 것처럼 남지 않는다. 현재 턴에서 분리한 과제는 다시 연결하지 않는다.

현재 모델의 실제 연결은 `pursuit.bound`에 source(consciousness/execution)와 근거를 기록한다.
실행 중 연결돼도 감독의 원래 전체 목표 스냅샷을 세워 후속 목표 변경과 완료 평가를 구분한다.
HTTP/MCP의 다른 워커 스레드에서 연결해도 시작 시 보관한 궤적으로 에피소드·연결 사건을 보존하고,
명시적 agent/task 키로 감독을 찾는다. 사건 기록 뒤 워커의 이전 궤적 문맥을 복원한다.
과제 준비는 실행 차선을 변경하지 않는다. 기존 #think/#repair·수리 판정 등 최초 숙고의 별도 예외는 유지한다.

## 검증과 성능 범위

모델을 실패 대역으로 바꾸고도 후보 준비·연결·미정리 기록 조회가 성공하는지 검사한다.
실제 SQLite 및 공통 인지 파이프라인에서 다음을 검증한다.

- 최초 숙고 OFF의 EXECUTE·반사에 별도 과제 모델/의식 호출이 없고 실행 중 연결·종료 기록이 남는다.
- THINK는 기존 의식 한 번의 응답으로 연결하고 전체 목표·새 프레임을 실행자에게 전달한다.
- 무관한 과제는 원장을 건드리지 않으며 오연결 분리·늦은 요약 차단이 유지된다.
- 소유자/태스크 격리, 진행 중 과제 연결 실패, 멱등 연결, 잘못된 의식 출력의 쓰기 전 거절.
- 목차의 크기·발췌 표식·첫 페이지 밖 명시 ID·한국어 조사 접미사·MCP 과거 턴 조회.
- 요약은 응답 후 수행하며 필드 오류 전체 정정과 원문 보존이 유지된다.

보장하는 절감은 **과제 준비의 독립 AI 호출 0회**다. 실제 실행 모델의 호출·추론 시간은 남으며,
과제 연결/상세 조회가 필요한 실행 턴은 도구 왕복을 사용할 수 있다. 자연어 연결 판단의 정확도나
윈도우의 실제 지연 개선량을 시험 대역으로 입증했다고 보지 않는다.

검증 결과: macOS 전체 backend **5,100 passed, 1 skipped**(489.45초).
마지막 MCP 스레드의 에피소드·감독 신원 보완 후 과제·의식·궤적 관련 **236 passed**(12.76초).
IBL 파생물, 의식 출력 스키마/소비처, backend 층, 은퇴 계약 검사와 Android 엔진 번들 재생성·일치를 확인했다.
