## 1. 결론과 범위

과제 목록에서 보류·완료·재개하는 기능은 사라진다. 대화 삭제 뒤에도 별도 과제 요약이

## 4. 구현 순서

### 1단계 — 공통 실행 기능 분리

1. `pursuit_bind`의 실행 등록에 섞인 runner, agent/task, provider alias, 문맥, 대화 세션을
   현재 실행 수명으로 분리한다. 기존 `thread_context`/`conversation_sessions`/`supervision_bus`를
   재사용하며, 스레드 간 조회에 필요한 최소 등록만 둔다. 감독 비활성 실행에서도 동작해야 하므로
   `supervision_bus.current()` 하나로 대체하지 않는다. 새 모듈이 필요하면 층을 배정한다.
2. `todo_bridge`와 일반 실행 파이프라인을 새 소유자로 옮겨 과제 없는 실행에서도 할 일 갱신,
   토큰 계측·권한 문맥·세션 복원·종료 정리가 유지되게 한다.
3. 실행 기록의 소유권을 과제 FK에서 분리한다. 기존 tasks/episode/대화 실행 메타데이터를 대조하고,
   부족한 project/owner/session/episode 연결은 기존 실행 기록 생성 시 명시적으로 보존한다.
   동명 task·다른 프로젝트·세션에서 혼합되지 않아야 한다. 추측으로 과거 행을 채우지 않는다.
4. 과거 과제 기록의 조회가 필요한 부분만 읽기 전용 기록 어댑터로 분리한다. 과제 생성/복구를
   수행하는 `PursuitLedger` 생성자를 역사 조회에 쓰지 않는다. 옛 기록은 권한 검증된 범위에서만 읽는다.

### 2단계 — 수리 인계와 평가 분리

1. 수리의 기준 정본은 기존 `criteria_contract`로 모은다. 저장된 현재 기준, done_request의
   목표, 과제 목표를 비교하여 누락 여부를 확인한다. 서로 다른 기준을 무조건 합치거나 옛 목표로
   되돌리지 않는다. 과제에만 있는 유효 기준은 근거와 함께 수리 인계에 이전한다.
2. 최상위 계약이 없는 기존 기록은 연결된 수리 세션의 readiness.criteria, 저장 검수 packet,
   프레임의 criteria/achievement_criteria 등 정본 증거로 복원한다. 근거가 모자라거나 서로
   모순되면 blocked와 사유를 유지한다. AI로 기준을 새로 만들거나 과제 제거를 재개 승인으로 삼지 않는다.
3. `bind_pursuit/restore_completion`과 감독의 과제 완료 요청·버전 충돌·완료 쓰기를 제거한다.
   수리 자체의 변경/검수 판본 확인, 승인 신원, 취소, 중복 적용 방지는 기존 수리 계약으로 유지한다.
4. old `repair_review.json`의 packet/snapshot도 읽기 경계를 확인한다. 과거 평가에 포함된 유효한
   전체 기준은 그대로 보존하고, 더는 존재하지 않는 과제 행의 완료 쓰기만 하지 않는다.

### 3단계 — 과제 실행 기능 전체 제거

- `pursuit_bind.py`, `pursuit_tools.py`, `pursuit_maintenance.py`, `api_pursuits.py`와
  쓰기용 `pursuit_ledger.py`를 제거한다. 1단계에서 분리한 실행 신원/역사 조회만 각 소유자에 남긴다.
- `agent_pipeline`의 후보 주입·과제 도구 관측·종료 패킷, `reframe`의 원장 훅,
  `framing_inheritance`의 과제 필드, `cognitive_distill/distill_queue`의 과제 요약을 제거한다.
- `cognitive_consciousness`와 `research_runner`는 정상 의식 호출을 유지한다. 과제 전용
  scope/id/reason/title/goal/detach 출력 요구와 과제 오류 정정 프롬프트를 걷어낸다.
  일반 JSON/계획 계약, 연구계획 정정 경로까지 삭제하지 않는다. 필드가 다른 기능에서 쓰이면
  과제 전용 소비만 없앤다.
- `agent_cognitive/system_ai_tools/system_tools`, `mcp_server.py`, CLI 허용 도구 목록에서
  `pursuit`를 제거한다. `/ibl/pursuit`와 `/ibl/pursuits` 라우팅·조종실 컴포넌트/마운트를 제거한다.
- 구 클라이언트의 오래된 도구 호출은 미지원으로 실패해야 한다. 조용한 성공이나 자동 생성으로
  호환하지 않는다. 제공자/MCP 세션의 도구 목록 갱신과 실행 중인 구 세션의 종료 시점을 확인한다.
- 일일 순찰, schema 검사 소비자 목록, 층 목록, 프롬프트와 현재 가이드를 함께 정리한다.
  일반 실행 기록 UI는 유지하고 과제 관리 UI만 없앤다. 과거 연결 표시는 역사 조회와 구분한다.

### 4단계 — 운영 데이터 전환과 배포

1. 진행 중인 사용자 실행과 재기동 인계를 확인한다. 실행 도중 코드를 갈아 기존 신원 등록을
   끊지 않는다. 기존 런타임 작업/재기동 조정 경로로 안전한 전환 시점을 잡는다.
2. 수정할 DB는 SQLite backup/VACUUM INTO로, 수리 인계·검수 JSON은 원문 그대로
   `data/_backups/YYYY-MM-DD_pursuit_removal/`에 백업한다. 개별 비밀값을 문서/로그/Git에 복사하지 않는다.
3. 일회성 변환은 먼저 dry-run으로 건수·누락·충돌만 보고하고 실제 변경은 원문 지문/버전
   확인 후 적용한다. 재실행해도 중복 기준/중복 쓰기가 없어야 한다. 실행 직전 상태를 재조회한다.
4. 남은 증류 패킷에 pursuit가 있어도 과제 요약을 재시도하지 않는다. 기존 job_key/일반 단계
   영수증을 유지하고 과제 단계만 은퇴로 건너뛴다. 패킷 전체 삭제·나머지 증류 재실행은 금지한다.
5. 기존 `pursuit/pursuit_event/pursuit_turn` 표는 자동 읽기·쓰기·순찰에서 제외해 보존한다.
   이번 기능 제거에 물리 DROP/기록 삭제를 포함하지 않는다. 보존된 표는 휴면 데이터이며,
   조회가 필요할 때만 역사 어댑터가 읽는다. 이를 영구 기능 토글/구 실행 엔진 존치로 바꾸지 않는다.
6. 롤백은 코드만 되돌리는 것으로 충분하지 않다. 변환 전 수리/검수 스냅샷과 증류 단계 처리
   기록으로 해당 변경만 복구하고, 배포 후 발생한 새 대화·수리 결과를 DB 통째 복원으로 덮지 않는다.

이는 제거 전 기준선이다. 임시 DB/시험 대역을 쓰는 기존 회귀이며, 제거 후 동작·실제 모델
품질·비용 절감·모든 제공자/실기기 정상까지 입증하지 않는다. 이 계획 작성으로 runtime 코드를 바꾸지 않았다.

개발 중 `scripts/select_tests.py --files ... --explain`으로 소비자 범위를 확인하고 해당 검사를 실행한다.
과제 전용 동작을 요구하는 검사는 제거하되, 섞여 있는 권한·완료 기준·수리·동시성 검사를 함께
버리지 말고 새 소유자의 모듈명 시험으로 옮긴다. 일반 실행을 검증하는 고정물에서 과제 생성 의존도 제거한다.

`scripts/consciousness_schema_check.py`, backend 층 검사, IBL 빌드 신선도 검사를 확인한다.
Android 엔진 매니페스트와 UI 카탈로그/번역은 정본 생성기로 갱신하고 파생물을 손으로 수정하지 않는다.
현재 문서 anatomy/memory/architecture와 가이드·코드맵을 실제 상태에 맞추고 과거 설계/수리 이력은 보존한다.
