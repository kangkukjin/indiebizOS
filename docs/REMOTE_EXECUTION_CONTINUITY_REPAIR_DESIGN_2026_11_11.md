## 1. 목표와 사용자 제약

자연어 최초 요청에서 실행한 작업을 다음 요청에서도 정확히 찾아 조회·수정·중지할 수 있게 한다.
대화, 기기, 실행 작업, 실제 자원, 관측 결과를 연결하여 이미 확보한 정보를 재탐색하는 비용을 줄인다.
음악은 출발 사례이며 앱·파일·지속 프로세스·상태 조회에도 같은 연결을 적용한다.
기능의 정확성과 품질을 보존하는 것이 구현 조건이고, 시간·전체 토큰 절감은 별도로 실측한다.

**사용자 추가 조건: 대상 PC에 IndieBizOS가 없어도 헬퍼가 작동해야 한다.**
처음 등록하는 일반 PC는 헬퍼만 설치된 상태를 기준으로 삼는다. 대상의 IndieBizOS 저장소,
백엔드·IBL 엔진·Python 가상환경·Node·개발 도구 설치를 기본 원격 기능의 전제로 만들지 않는다.
중앙 허브에는 기존 IndieBizOS가 있으며 의미 판단·IBL 조합·대화 문맥은 중앙이 소유한다.
독립 헬퍼란 대상 PC의 본체 설치로부터 독립이라는 뜻이지 중앙 연결 없이 자연어를 해석한다는 뜻은 아니다.

이번 설계는 기존 작업·관측·대화 경계를 수리한다. 새 전역 ‘최근 기기’ 관리자, 새 감독 모델,
별도 작업 DB, PC용 전체 폰 엔진, 명령별 인지 코어 분기는 추가하지 않는다.
REFLEX는 다시 만들지 않으며 기존 EXECUTE의 모델·기어·세션 연속성을 유지한다.

기존 계약의 근거이며 이 설계의 구현·개선 효과를 입증한 검사로 재사용하지 않는다.
연구 산출물은 로컬 `data/outputs/`에 있고 Git 배포 문서는 아니다. 핵심 판단은 이 문서에도 남긴다.

## 4. 반드시 유지할 계약

1. **출처와 권한은 다르다.** 대화/턴 ID는 참조의 출처이며 권한 증명이 아니다.
   기존 principal·기기 등록·설치 세대·IBL 결과 접근 권한을 매 소비 경계에서 유지한다.
2. **접수·프로그램 종료·효과·사용자 목표는 다르다.** `accepted`, exit 0, 재생 진행,
   사용자가 실제 소리를 들었다는 사실을 하나의 success로 합치지 않는다.
3. **완료된 대화 턴에도 살아 있는 자원이 있을 수 있다.** “재생 시작했습니다”라는 응답의 완료가
   재생 종료를 뜻하지 않는다. turn_state, job_state, resource_state를 따로 보존한다.
4. **늦게 온 결과가 현재 대상을 결정하지 않는다.** 결과는 자기 job에만 귀속된다.
   사용자의 명시 대상·정정과 같은 대화의 근거를 기존 실행 모델이 판단한다.
5. **모호하거나 오래된 핸들로 다른 자원을 조작하지 않는다.** 기기 세대, 재생 ID,
   창/탭 판본, 파일 판본, 프로세스 세션을 해당 드라이버가 확인한다. PID 단독을 영구 신원으로 삼지 않는다.
6. **결과 유실은 자동 재실행의 근거가 아니다.** 같은 원 작업을 조회하고,
   새 반복 실행은 사용자의 의도에 따라 새 요청 ID로 구분한다. 조회만으로 새 변경을 접수하지 않는다.
7. **기록 전달은 새 지시가 아니다.** 도구 출력·원 요청 발췌는 관측 자료로 표시하며,
   현재 사용자 지시와 권한을 바꾸거나 취소 작업을 자동으로 재개하지 않는다.

## 5. R0 — 헬퍼 단독 설치를 기준 환경으로 고정

아래는 구현·인수의 필수 조건이다. 대상에 IndieBizOS가 깔린 개발 PC만으로 합격시키지 않는다.

| 환경/능력 | 기본 계약 | 추가 구성의 경계 |
| --- | --- | --- |
| 헬퍼만 있는 PC | 등록·연결·info·파일 list/read/write/transfer·OS 셸 실행·작업 조회/취소 유지 | OS 제공 셸과 현재 사용자 권한 사용. Python/Node 코드를 기본 점검에 사용하지 않음 |
| OS 앱·설정 제어 | 기존 OS별 드라이버와 실제 지원 계약 사용 | OS 권한·로그인 상태·필요한 OS 도구를 신고. 미지원이 기본 파일/셸을 막지 않음 |
| 재생·화면 공유 등 | 실제 발견한 구성요소와 지원 기능으로 선택 | mpv/ffmpeg 등은 헬퍼의 기존 선택 설치·탐색 경로. IndieBizOS 전체 설치로 대체하지 않음 |
| 사용자가 요청한 임의 프로그램 | 해당 프로그램의 의존성을 별도로 확인 | “Python 프로그램 실행”의 Python 요구는 헬퍼 기본 실행의 의존성이 아님 |
| IndieBizOS도 설치된 PC | 동일 헬퍼 계약으로 동작 | 본체를 꺼도 헬퍼 기본 기능 유지. 본체의 `.venv`를 암묵적으로 빌려 쓰지 않음 |

`helper/README.md`의 최소 등록·미디어 선택 설치 정책을 유지한다. 플레이어가 없는 PC에서
모든 미디어 기능이 즉시 된다고 약속하지 않는다. 누락된 기능과 이유를 기존 capabilities·결과로
알리고 기존 설치 경로로 필요한 구성요소만 보완할 수 있어야 한다. 추가 설치가 실패하거나
거절되어도 등록·기본 원격 실행은 계속 작동한다. 이번 문서 작성은 설치·배포 요청이 아니다.

중앙이 이미 해소한 콘텐츠는 기존 파일 전송 또는 media content 전달을 사용한다.
검색·YouTube 스트림 해소를 위해 대상 PC에 Python·yt-dlp·IndieBizOS를 필수 설치하지 않는다.
중앙의 기존 검색/다운로드 부품에서 소스를 해소하고, 필요하면 전달 가능한 파일로 보낸다.
직접 URL은 수신지 접근·만료·헤더 제약을 확인하고, 중앙에서 얻은 URL이 다른 IP에서도
재생된다고 가정하지 않는다. 실패 시 원 결과를 남기고 대체 전달을 선택한다.

검증 환경은 개발 PATH·HOME의 플레이어·저장소·가상환경을 우연히 발견할 수 없게 격리한다.
macOS·Windows·Linux의 기본 명령으로 파일 왕복·관측·취소를 실행한다. 현대 상주 헬퍼,
구형 macOS legacy, 휴대형은 지원 계약을 구분한다. legacy의 미디어 세션 미지원 때문에
기존 media/shell·파일 기능을 없애거나 전체 본체 설치를 요구하지 않는다.

## 6. R1 — 실행 출처를 원 접수와 원자적으로 보존

`resident_pcs.submit`에서 활성 `execution_turn`과 그 conversation binding을 확인하고,
principal/agent/중앙 task/session/turn/revision의 출처를 캡처한다. MCP 재진입은
`execution_turn.adopt_session`이 이미 검증한 binding을 사용한다. 원격 명령의 사용자 입력에서
받은 ID나 모델이 적은 `owner`를 신뢰하여 출처를 만들지 않는다.

`resident_store.submit`은 선택적인 구조화 출처를 받아 기존 `resident_events`에
`attribution` 사건으로 기록한다. 새 job 생성·queued 사건·최초 attribution은 같은
`phone_jobs` 트랜잭션에서 확정한다. 장치에 전달하는 명령과 fingerprint는 바꾸지 않는다.
식별 필드는 기존 이름을 재사용하고 비밀 stdin/env·등록 키·grant는 복사하지 않는다.

- 기존 `(device,generation,request_id)` 멱등 키를 유지한다. 같은 내용의 재접수는 원 job을 반환한다.
- 같은 job을 다른 대화가 명시적으로 회수할 수 있으므로 최초 생성 출처와 후속 참조 출처를
  `submitted`/`reused` 관계로 구분한다. 다른 대화의 회수를 최초 소유권 변경으로 기록하지 않는다.
- attribution 사건은 job+출처+관계로 멱등 처리한다. 같은 요청 ID의 다른 명령은 기존 충돌을 유지한다.
- 중앙의 대화 사건에는 같은 job/task_ref를 연결한다. 두 DB 간 단일 트랜잭션을 가장하지 않는다.
  접수 뒤 대화 저장이 실패해도 원 job과 출처가 남고, 같은 request_id 재조회로 연결을 복원한다.
  저장 오류를 이유로 새 ID를 만들어 같은 효과를 재접수하지 않는다.
- 스케줄러·관리 화면 등 대화 없는 적법한 호출은 실제 principal/task 출처만 기록하고 conversation은 비운다.
  이 경우와 R3의 대화 입구가 binding 확보에 실패한 경우를 구별한다.
- 과거 작업은 출처 미상으로 남긴다. 기기나 시간의 근접성으로 대화 소유권을 소급 추정하지 않는다.

task_ref의 `kind/task_id`와 기존 task wait/cancel 소비자는 그대로 유지한다. generation·출처는
호환 가능한 추가 근거로 반환하며, 작업 상태의 정본은 기존 resident 원장 한 곳이다.
후속 전달은 현재 대화가 가진 사건과 검증된 attribution으로만 후보를 회수한다.

## 7. R2 — 최종 효과에 원 작업과 실제 자원 연결

PC/Android verifier는 현재처럼 준비 영수증·접수 영수증·요청 지문·반환 판본·readback을
검사한다. 검사 뒤 새로 만드는 `operation-effect/1`에도 원 job의 device/generation/request_id,
결과 수신 시점과 원문 참조를 보존한다. generation은 조회 순간의 등록값이 아니라 원 job 값이다.

`operation_effects.bind`의 기존 의미는 “인증된 장치 보고를 어느 job이 반환했는가”다.
허브에서 만든 readback을 장치의 원 보고로 위장하지 않는다. 공용 구조 조립을 재사용하되
허브 검증 결과의 `source`와 검증 방법을 유지하고, 운반 근거의 basis도 구별한다.
스크립트가 받은 임의 dict를 그대로 신뢰하지 않고 기존 receipt 소유 API가 회수한 접수·관측을 사용한다.
충돌은 unknown·원 근거로 반환하며 기존 실패/partial 값을 성공으로 올리지 않는다.

자원 참조는 각 생산자가 제공한다. 재생 ID, media session ID, process session ID,
window/tab revision, 파일 경로+판본/해시처럼 현재 기능에 있는 값을 사용한다.
행동 이름은 자원 종류일 수 있지만 자원 인스턴스의 신원은 아니다. 신원이 없는 드라이버는
`resource`의 제한과 원 job 참조를 제공하며 generic 코드가 stdout/PID/파일명에서 신원을 추정하지 않는다.
파일 해시는 무조건 새로 계산하지 않고 이미 확인한 판본이나 필요한 변경 전제를 재사용한다.

관측 내용·관측 시각·운반 수신 시각을 보존한다. 전달됐다는 사실로 관측 시각을 현재로 갱신하지 않는다.
정지·변경 전 현재 확인이 필요한지는 기존 실행자와 드라이버의 조건부 제어 계약이 판단한다.

## 8. R3 — 대화 연결 실패 후 무소유 실행 제거

`conversation_sessions.owned_turn`이 busy 또는 저장 오류를 만나면 `None`으로 계속하는
호환 경로를 제거한다. 대화 HTTP 입구는 모델 호출·원격 제출 전에 이를 처리한다.
busy는 기존 오류 봉투와 HTTP 409로, 저장소 장애는 재시도 가능한 서버 오류로 구분한다.
새 자동 세션이나 별도 큐를 만들지 않는다. 정상 대화의 동시성 정책과 맞춘다.

기존 호출부 전부를 조사하여 대화·rehearsal·프로젝트의 owner 구분과 최종 응답 저장→턴 해제→
공개 순서를 유지한다. 내부 IBL HTTP 재진입은 부모의 활성 binding을 채택할 뿐 새 대화 턴을
열지 않으므로, 이 수리가 자기 도구 재진입을 busy로 막으면 실패다.
busy/DB 오류 경로에서 미리 만든 태스크가 있으면 기존 종료 절차로 정리하고 실행 중 표시를 남기지 않는다.

## 9. R4 — 완료 작업 참조를 기존 상황 전달에 연결

보고서 A안의 의미를 다음처럼 구체화한다. `Handoff.recovery()`가 완료 턴을 중단 작업으로
되살리게 만들지 않는다. 같은 저장소에서 **완료 작업 참조 관측**을 별도로 읽어
`situation_evidence.attach`가 현재 `Situation`에 복원하고 기존 `situation_delivery`로 전달한다.
새 provider별 실행 경로·요약 모델·이력 DB를 추가하지 않는다.

### 후보와 최소 표현

현재 대화/행위자·판본에서 보이는 이전 사건을 대상으로, 원 요청 참조·원 tool call ID·
기기/설치 세대·중앙 task·원격 task_ref·자원 참조·마지막 상태·관측 시각·검증 범위·원문 참조를 묶는다.
원문·도구 인자 전체를 기본 입력으로 복사하지 않는다. ID 없는 서로 다른 호출을 임의로 결합하지 않는다.
권한상 볼 수 없는 기록, 다른 대화, 체크포인트로 제외된 기록, 다른 연구 thread를 섞지 않는다.
연구/회원 문맥은 해당 저장소·epoch·권한을 유지하며 지원되지 않는 표면은 그 한계를 명시한다.
옛 사건에 행위자 정보가 없으면 해당 대화의 소유 경로로 확인 가능한 범위만 사용한다.
새 출처 ID를 과거 사건에 추정 부착하거나 다른 행위자의 참조를 같은 대화라는 이유로 합치지 않는다.

기본 후보는 보이는 최근 작업과 이미 연결된 지속 자원의 관측이다. 구조화 결과·상황 snapshot을
우선 사용하고 없으면 기존 tool 사건의 참조를 남긴다. 장치 상태의 온라인 전수 조회나
로그 산문을 읽는 별도 모델 호출을 초기 문맥 조립에 붙이지 않는다. 현재 메시지의 음악·파일
키워드로 전역 대상을 정하는 규칙도 두지 않는다.

같은 의미의 snapshot과 결과 영수증은 기존 evidence identity·판본으로 합치고 충돌은 보존한다.
과거 snapshot에서 사용자 지시·수리 복구 행동·오래된 전달 cursor를 현재 턴의 것으로 복원하지 않는다.
이전 TurnStore의 evidence ID는 현재 TurnStore의 ID로 해석하지 않는다. 원 저장 위치·소유 범위·
지문·내부 경로를 포함한 기존 원문 참조를 유지하고, 읽을 때 기존 접근·무결성 검사를 거친다.
원문이 정리됐거나 접근할 수 없으면 unavailable로 남기고 요약만으로 효과를 확정하지 않는다.
완료 관측은 `last_observed`로 표시하며 완료 대화 턴과 지속 중인 자원의 상태를 분리한다.
큰 이력은 기존 상황/모델 입력 예산 안에서 참조로 제한하고 생략 범위·원문 회수 경로를 함께 전달한다.
기록 조회도 최근 사건부터 페이지 단위로 읽어 제한한다. 기존 `_previous()`의 전 이력 스캔을
완료 작업 수만큼 반복하지 않으며 필요한 인덱스는 기존 DB의 조회 계획을 보고 정한다.

### 실제 모델 소비와 연속성

현재 CLI는 자체 압축이 불투명하여 `situation_delivery.prepare`로 매 입력에 작은 baseline을
전달한다. 이 설계도 그 경계를 재사용한다. **resume라고 무조건 아무것도 보내지 않는 새 최적화는
하지 않는다.** 기존 도구 이력 전문을 중복 첨부하지 않고 압축된 참조 관측만 보존한다.
API는 보유한 delivery ID와 기존 baseline/delta 규칙을 사용한다. resume 실패 후 fresh 재시도,
모델/프롬프트 변경, history 교체 후에도 같은 출처의 참조가 실제 모델 입력에 있어야 한다.

전달 확인은 기존 provider의 실제 소비 경계에서 한다. DB에서 읽었거나 SDK 스트림을 만들었다는
이유로 확인하지 않는다. 전달 확인은 원 사건을 삭제하거나 새 세션의 참조 복원을 금지하는 ack가 아니다.
분류·회상의 검색문은 계속 사용자의 원문을 사용하고 과거 관측을 새 사용자 지시로 검색하지 않는다.

상황 전달 설정이 꺼져 있으면 이를 몰래 다시 켜지 않는다. 그 설정에서의 기존 history 동작과
기능 제한을 명시하고 전달 활성 상태를 진단에 남긴다. 정상 활성 경로에서는 CLI와 API 모두
최종 입력으로 검증하며, 인위적으로 tool history를 넣어 준 단위시험만으로 완료 판정하지 않는다.

`execution_history.py`의 과거 REFLEX 결과 인계는 신규 작업 참조 저장소로 확장하지 않는다.
같은 원 사건이 양쪽에 잡히면 출처로 중복을 제거하되 기존 성공/실패 전달 확인 의미는 보존한다.

## 10. R5 — 헬퍼 독립성을 유지한 지속 자원 제어

### PC 미디어

새 재생 관리자를 만들기 전에 기존 `media_sessions.create/status/update/end`와
헬퍼 `media_session_playback.go`를 재사용한다. 이 경로는 대상의 IndieBizOS 백엔드 없이
헬퍼와 플레이어로 동작하며, mpv IPC의 위치·일시정지·음량 관측과 세션 수명을 이미 가진다.
중앙의 기존 등록 스크립트 `미디어세션`에서 접근하고, 음악의 검색/해소는 R0의 중앙 부품이 맡는다.

콘텐츠 전달이 가능한 대상은 session ID·관계 세대·원 장치 job·실제 재생 관측을 한 결과로
반환하도록 기존 wrapper/영수증을 보완한다. 정지는 같은 session/job을 대상으로 하며
임의 프로세스 목록 재탐색을 정상 경로에 넣지 않는다. 전체 파일 재생 종료를 기다려야만
“재생 시작”을 응답할 수 있는 구조로 만들지 않는다. 준비·재생 진행·종료를 별도로 관측한다.
프로세스만 관측 가능한 afplay 경로는 해당 범위를 표시하고 실제 진행/가청음까지 verified로 만들지 않는다.

세션 미지원 legacy·휴대형과 기존 raw `media`/`shell`은 해당 기능을 계속 제공한다.
일반 media의 job cancel로 정지 가능하다는 기존 계약을 유지하고, 충분한 제어 정보가 없는
경로는 제한을 반환한다. 모든 미디어 요청을 지원되지 않는 media_session으로 강제 전환하지 않는다.
세션 교체·허브 재기동·임대 만료 후에는 기존 종료/unknown 규칙을 따르며 새 재생을 자동 생성하지 않는다.

### 폰·앱·파일·프로세스

폰의 전역 음악 stop은 현재 재생을 끄는 기능으로 유지하되, 앞선 특정 재생을 가리키는 후속
제어에는 기존 Playback ID가 반환·소비되도록 연결한다. 필요하면 기존 stop 연산에 선택적인
기대 playback ID를 사전 데이터/드라이버 경계에서 추가하고 `stopStreamIf`를 사용한다.
교체된 재생에는 stale을 반환하며 “현재 재생을 꺼”라는 명시 의도와 구분한다.
재생 ID 없이 큐 전체 소유권이 보호된다고 주장하지 않고, 큐 교체·다음 곡 이동의 의미도 시험한다.
동작 변경이 APK 쪽에 필요하면 구형 APK는 지원 여부를 명시하고 기존 명시 제어는 유지한다.

지속 셸은 지원 대상에서 기존 `remote_process_sessions`를 사용하되 PTY·설치 신원·입력 ACK의
제약을 유지한다. 모든 짧은 셸을 이 경로로 옮기지 않는다. 앱은 기존 창/탭 판본,
파일은 원 경로·판본/해시를 기존 결과와 연결한다. 없는 자원 제어 기능을 이번에 모두 새로 구현하는
범위로 확대하지 않으며, 일반화의 인수는 이미 있는 서로 다른 자원 계약이 같은 전달 경계를 쓰는지로 한다.

## 11. 구현 순서·삭제할 중복·호환성

순서는 **R0 기준 고정 → R1/R2/R3 → R4 → R5**다. R1~R4는 허브 공통 수리이며
PC·폰에 새 전체 엔진을 설치하지 않는다. R5는 기존 헬퍼/폰 능력에 따라 가능한 연결부터 적용한다.
계약 공백 수리를 자연어 속도 비교가 끝날 때까지 미루지 않되, 측정하지 않은 개선율을 보고하지 않는다.

| 단계 | 완료 조건 | 제거·대체할 것 |
| --- | --- | --- |
| R0 | 헬퍼 단독 기준과 기능별 선택 의존성의 재현 환경 확보 | 개발 PC의 설치 경로·Python 환경을 기본 전제로 쓰는 예제/인수 조건 |
| R1/R2 | 접수→출처→원 결과→최종 효과를 검증된 관계로 조회 가능 | 소비자마다 action 이름·현재 등록값으로 job/resource를 추정하는 중복 |
| R3 | 대화 입구는 binding 또는 명시 오류, 모델 무소유 실행 0 | `owned_turn`의 대화 busy/DB 오류 후 실행 지속 fallback |
| R4 | 완료 작업의 참조가 fresh/resume/API의 실제 입력까지 전달 | 별도 완료 결과 요약문·provider별 사설 재전달 경로를 새로 만드는 방식 |
| R5 | 지원 기기의 기존 핸들로 실행·관측·정지, 단독 헬퍼 인수 | 정상 제어에서 PID/IPC 경로를 매번 다시 찾는 wrapper·교재의 우회 절차 |

과거 사건·REFLEX 표시·원문은 삭제하지 않는다. 기존 receipt 필드와 멱등 키는 유지하고
추가 출처 필드가 없는 구형 결과는 제한된 근거로 읽는다. 버전이 맞지 않는 기기에 새 제어
능력이 있다고 가정하지 않는다. 문서·관용구·용례·실제 dispatcher를 같은 계약으로 갱신한다.

허브 변경은 기존 활성 세대 교체 절차로 반영하고, 진행 중 사용자 작업을 끊지 않는다.
헬퍼 변경이 필요하면 기존 서명·해시·설치 세대·업데이트/되돌리기 계약을 사용한다.
APK 교체는 Android의 기존 ABI·서명·OS 설치 절차를 따르며 PC와 같은 자동 롤백을 가정하지 않는다.
이 문서는 배포를 실행하지 않는다. 구현 완료 보고에서는 허브, 각 헬퍼, 각 폰의 실제 반영 범위를 나눈다.

되돌릴 때는 새 소비 경로를 이전 코드로 복원하되 추가 사건은 보존한다. 데이터 삭제·기존 job
재접수·전체 DB 덮어쓰기를 되돌리기 절차로 삼지 않는다. 이미 진행 중인 작업은 기존 소유자가 마무리한다.

## 12. 계약 검증과 실제 효과 측정

| 검증 묶음 | 자극 | 필수 결과 |
| --- | --- | --- |
| 헬퍼 단독 | 본체/개발 런타임 없는 깨끗한 사용자·최소 PATH | OS별 파일 왕복·셸·조회·취소 성공. 대상 8765/API 호출이나 `.venv` 탐색 없음 |
| 선택 의존성 | 플레이어 없음/추가/실패, 본체 설치/중지 | 기본 원격 기능 유지, 능력 신고와 실제 실행 일치, 필요한 미디어 구성만 보완 |

| 접수/저장 교차 | job 커밋 직후 대화 기록 실패·응답 유실·동일 ID 회수 | 원 job 재사용, 출처 복구, 새로운 효과 0. 다른 명령 같은 ID는 충돌 |
| 동시 HTTP | 같은 legacy 대화 두 요청, DB 오류, MCP 재진입 | binding 또는 명시 오류. 중첩 도구는 부모 문맥 유지. 실패 태스크 잔류 없음 |

회귀는 변경별로 `scripts/select_tests.py`를 사용하고 기존 모듈 시험을 보강한다.
주요 소유 시험은 `test_conversation_handoff`, `test_conversation_sessions`, `test_api_system_ai`,
`test_system_ai_memory`, `test_agent_pipeline`, `test_situation_evidence`, `test_situation_delivery`,
`test_cli_provider`, `test_resident_pcs`, `test_operation_effects`, `test_pc_control`,
`test_android_control`, `test_media_sessions`, `test_remote_process_sessions`, `test_youtube_phone`이다.
입력 조립은 실제 이력 조회→대화 인계→provider 요청까지 연결하고, 과거 도구 이력을 시험이
직접 넣는 경우와 구분한다. 헬퍼는 기존 Go 단위·가짜 허브·플랫폼별 인수 검사를 보강한다.

공통 문맥·저장소 변경 후에는 [회귀 규약](REGRESSION_TESTING.md)의 비system 전수와 관련
system 묶음을 실행한다. 층·IBL 정합·Android 번들 파생을 확인하고, 어휘/관용구를 바꾸면
가이드·등록·용례 재검토·번역까지 연결한다. 헬퍼 변경에는 Go 회귀·대상별 빌드·설치 호환을,
프런트엔드를 바꾸면 실제 TypeScript 검사를 추가한다. 문서만 작성하는 현재 단계에는 해당 구현 검사를 했다고 쓰지 않는다.

실제 효과는 음악·앱·파일·조회 각각에서 첫 요청과 생략 후속 요청을 짝지어 비교한다.
같은 모델/기어·자원 초기 상태·기기 판본·fresh/resume 조건을 기록하고, 먼저 제어 가능한
로컬 콘텐츠로 실행 연속성을 본 뒤 외부 검색/스트림 변수를 별도로 추가한다. 세션 두 개가
같은 기기를 다루는 경우와 기기 두 개를 번갈아 다루는 경우를 포함한다.
기존 사용자 자원 대신 전용 시험 자원을 사용하며 결과를 원래 상태로 정리한다.

요청→접수→작업 시작→효과 관측→사용자 응답 시간을 나누고, 모델 도구 호출·IBL 잎 호출·
원격 제출·로컬 원장 조회·실제 통신 재시도를 구분한다. 전체 토큰은 분류·실행·내부 AI·후처리를
같은 범위로 집계하고 캐시를 중복 합산하지 않는다. 관측 전달이 무관한 일반 작업에 더하는
입력 크기·지연도 포함한다. 개발 의존성 없는 헬퍼 환경의 성공을 별도로 기록한다.

잘못된 대상, 중복 효과, 거짓 완료, 기능 퇴행이 있으면 속도만 줄어도 합격이 아니다.
소수 표본으로 p95나 일반 절감률을 주장하지 않는다. 구조 계약의 구현 완료와 관측한 성능
개선은 별도 결과로 남긴다. 자연어 원인 판별이 필요하면 같은 저장 사건의 참조 전달 유무를
격리 환경에서 비교하되 운영의 권한/결과 검증을 제거하지 않는다.

## 13. 이번 산출물과 다음 구현의 경계

이번에는 보고서·원자료·현재 코드·헬퍼 설치 계약을 대조하여 설계만 작성했다.
운영 코드·설정·관용구·등록부·기기 설치는 변경하지 않았다.
사용자 조건인 **IndieBizOS 미설치 PC의 헬퍼 단독 동작**을 필수 계약과 인수 항목으로 포함했다.
R0~R5의 구현·회귀·실기 배포와 시간/토큰 개선은 아직 완료하지 않았다.

설계와 다르게 정한 점과 그 이유:
- 완료 참조의 상한은 관측 6건(그중 끝난 작업의 영수증 3건)·최근 완료 턴 4개다. 한 턴이 상주 작업을 10~20건 남기는
  실제 기록에서 전부 싣면 baseline 예산의 절반을 넘기 때문이다. 넘친 것은 `reference_index.omitted` 와 원 사건 참조로 남는다.
- 이전 턴 증거 ID 는 기존 lineage 읽기(같은 행위자·대화의 최근 8턴, 무결성 확인)가 닿을 때만 넘기고, 닿지 않으면
  `availability:"unavailable"` 과 원 작업의 `task_ref` 만 남긴다. 다른 저장소를 여는 새 읽기 경로는 만들지 않았다.
- 상주 작업 참조는 스냅숏 값만 싣지 않고 허브 원장의 그 행을 다시 따라간다(로컬 읽기, 장치 접촉·재접수 없음).
- 연구 thread 는 이번 참조를 지원하지 않는다(`scope:"unsupported_surface"` 로 진단에 남김).
- PC·Android 검증기의 관측은 접수 영수증의 task_ref 로 허브가 읽은 원장 투영을 근거로 한다. 관용구가 넘기는
  `observation` 인자는 같은 작업인지 대조하는 용도로만 남겼다(관용구·등록부 계약 불변).

실제 반영 범위:
- **허브**: 위 코드는 정본에 저장됐고 봉인 세대 교체로 현역에 들어간다. 커밋 `a5704558`.
- **PC 헬퍼**: Go 실행 코드를 바꾸지 않았다(시험 파일만 추가). 재빌드·서명·교체가 필요 없다.
- **폰**: youtube 패키지와 어휘(`stop` 의 `playback_id`)는 APK 번들에 들어가야 폰에 닿는다. APK 를 다시 빌드·설치하지
  않았으므로 등록된 폰은 아직 옛 계약이며 새 인자를 `UNKNOWN_ARGUMENT` 로 거절한다. Android 엔진 번들 파생(`--check`)은 일치한다.
- **해마 용례·재학습(같은 날 사용자 지시로 수행)**: 라이브 해마(`ibl_usage.db`)의 옛 용례 2행(외부PC작업실행 +
  `python --version`, 실행 이력 0)을 시드와 같은 `echo HELPER_OK` 로 고쳤다. 이어 임베딩을 재학습했다 — 현재 판본
  1,518행·학습 1,256쌍·평가 289쌍, 최적 epoch 3(검증 0.875). 직전 모델 대비 패턴 공간 code Top-1/3/5 +5.0/+5.7/+3.5p,
  설명문 공간 desc Top-5 −3.5p 로 비교 도구는 보류를 냈고, 런타임 공간(`runtime_ab.py`)은 프로브 Top-1 37→38·Top-5 동률,
  새 어휘 Top-5 6→7, 보류 분할 Top-1/5 85.6/94.0→83.1/93.0 이었다. 라이브 회상 43질의 대조는 1위 적중 15→14,
  회상 묶음 내 적중 20→21(4건 얻고 4건 잃음)로 동률이라 새 모델을 채택했다. 개선이라기보다 현재 코퍼스에 맞춘 교체다.
  재색인 1,518행(벡터 없던 3행 해소), 제어자 재기동 완료. 되돌리기 = `data/models/ibl_embedding.bak.20261111_021709`.
  `playback_id` 용례는 폰 APK 반영 뒤에 심는다.

하지 않은 것:
- §12 의 실제 효과 측정(같은 모델·기어·자원 초기 상태에서 첫 요청과 생략 후속 요청의 시간·도구 호출·토큰 비교).
- 실기 확인: 실제 PC·폰에서의 재생→다음 요청 정지, 플레이어가 없는 PC, Windows·Linux 헬퍼 단독 인수.
- 지속 셸(`remote_process_sessions`)·창/탭·파일 판본을 참조로 싣는 생산자 쪽 연결 — 이들이 `operation-effect/1`
  이나 소유 접수증을 내면 같은 전달 경계를 그대로 쓰지만, 이번에 새로 연결한 생산자는 상주 작업·미디어 세션·PC/Android 제어다.
