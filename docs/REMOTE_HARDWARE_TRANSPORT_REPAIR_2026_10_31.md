## 1. 수리 목표와 범위

원격 PC에서 큰 파일을 받거나 화면을 조작할 때, 회선의 용량을 낭비하는 전송 대기와 화면 처리 비용을 줄이고 짧은 통신 장애에서 자동 복구한다. tv1은 Windows 상주 헬퍼 PC의 별칭이며 실제 TV 제어 장치와 다르다. 이름에 따른 예외 없이 등록 PC의 공통 전송 계층을 고친다.

파일 전송과 화면 공유는 같은 회선·허브 자원을 사용할 수 있지만 병목과 완료 계약은 다르다. 파일은 모든 바이트와 무결성·이어받기가 중요하고, 화면은 최신 영상과 입력 반응·세션 복구가 중요하다. 하나의 범용 스트림으로 무리하게 합치지 않는다. 인증, 경로 선택, 수명 정책, 제한된 성능 관측처럼 의미가 같은 기반만 공유한다.

사용자의 플랫폼 확장 요청에 따라 Windows·Mac·Linux 헬퍼 및 Android 파일 소비자에 공통 바이너리 전송과 복구를 적용한다. 화면 세션 복구는 공통 서버·뷰어와 PC 헬퍼·Android 앱이 함께 협상하며, 캡처 품질 조절은 운영체제별 워커가 맡는다. tv1은 실장치 인수 대상이지 코드 분기의 기준이 아니다. 구현·빌드와 각 기기의 설치·성능 검증은 별도로 기록한다.

새 IBL 어휘·노드·상시 프롬프트는 추가하지 않는다. 기존 `limbs:guestpc`, 파일 전송 관용구, 화면 공유 버튼을 유지한다. 판단 기준은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)이다.

## 3. 보존할 계약

1. 등록 기기·설치 세대·사용자·방향·자원 범위 인증을 모든 경로에 적용한다. LAN이라는 이유로 인증을 생략하거나 공개 파일 서버를 열지 않는다.
2. request_id·task_ref·transfer_id의 기존 의미와 중복 실행 방지를 유지한다. 전송 복구가 원격 셸이나 사용자 입력의 재실행을 유발하면 안 된다.
3. 파일의 전체 크기·SHA-256 검증 뒤에만 완료를 확정한다. 동일 바이트 재요청은 멱등 처리하고 다른 원본 판본·다른 목적지 내용은 충돌로 남긴다.
4. ACK한 영속 offset은 프로세스/장치 재시작 후에도 유효해야 한다. RAM에만 받은 바이트를 이어받기 확정 지점으로 보고하지 않는다.
5. 취소·등록 해제·명시 창 닫기는 복구보다 우선한다. 취소된 작업이나 만료된 화면 세션을 자동 부활시키지 않는다.
6. 화면·키 입력·텍스트·인증값은 진단 로그에 저장하지 않는다. 입력 단절 시 누른 키와 버튼을 해제하고, 재연결 전에 보냈던 클릭·문자 입력을 재전송하지 않는다.
7. 파일 전송이 화면 조작·취소·heartbeat를 굶기지 않아야 한다. 별도 연결만으로 대역폭 경쟁이 해결됐다고 보지 않는다.

## 4. 공통 관측과 경로 선택

기존 작업·세션에 제한된 계측을 붙인다. 새 감독 AI, 상시 폴링 서비스, 별도 작업 DB를 만들지 않는다. 경과 시간은 단조 시계로 재고, 다른 기기의 시계를 빼서 편도 지연을 계산하지 않는다.

- 공통: 실행 코드/헬퍼 판본, 선택 경로(`lan`/`public`), 연결 시도·fallback 이유, 연결/인증 시간, 종료 코드·단계, 재연결 횟수.
- 파일: 원본 해시, 읽기, 인코딩, 네트워크 요청, 서버 쓰기·영속화·DB 갱신, 최종 검증, collect의 각 경과 시간과 바이트. 사용자에게는 진행량·속도·마지막 진전 시각을 제공한다.
- 화면: 캡처·인코딩·송신 대기·전송 시간, 프레임 크기·생성/표시 fps·폐기 수, 입력 큐 길이, heartbeat 지연, 복구 시간. 화면 내용 없이 집계한다.
- UI: 연결 중·복구 중·종료를 구별하고 경로와 구체적인 종료 이유를 보여준다. 순간 속도 하나를 안정적인 예상 완료 시간으로 오인시키지 않는다.

화면의 기존 LAN TLS 검증을 보존한다. 파일에도 경로 선택을 확장할 때는 기존 listener가 현재 WebSocket 채널만 허용한다는 점을 반영해, 기기 인증된 파일 경로만 명시적으로 연다. owner API 전체를 LAN listener에 노출하지 않는다. 같은 인증된 허브/transfer_id로만 fallback하고 실패한 요청의 영속 offset을 재조회한다. Tailscale·TURN·외부 저장소를 필수 설치 조건으로 추가하지 않는다.

## 5. 파일 전송 수리

### 첫 단계와 최종 구조

먼저 기존 계약 안에서 PC 청크 크기를 협상 가능한 한도로 높이고 전후를 비교한다. 이는 ACK 횟수를 줄이는 중간 단계다. 최종 구조는 **유한한 크기의 바이너리 스트림 배치를 지속 연결로 보내고, 배치의 영속 확정을 ACK하는 방식**으로 한다. 한 HTTP 요청에 파일 전체를 싣거나 무제한 메모리 버퍼를 쓰지 않는다.

서버와 헬퍼가 지원 버전·최대 배치·진행 중 허용 바이트를 협상한다. 배치 크기는 실제 프록시 요청 제한·메모리·취소 반응을 고려해 한정한다. 서버는 스트리밍 수신하고 순차 파일 쓰기를 소유한다. 큰 배치를 통해 작은 청크별 왕복을 줄이며, 추가 파이프라이닝이 필요하면 바이트 예산 안에서만 허용한다. 같은 파일에 임의 순서의 병렬 쓰기를 도입하지 않는다.

### 영속화와 재개

한 전송에는 쓰기 소유자 하나만 둔다. 재연결·중복 요청·동시 세션이 같은 파일 offset을 경합하지 않도록 전송별 잠금과 세대를 검증한다. 네트워크 수신이나 전체 해시 계산 동안 공유 작업 DB의 긴 트랜잭션을 유지하지 않는다.

배치 수신 → 데이터 영속화 → 확정 offset 원장 커밋 → ACK 순서를 보존한다. 디렉터리 항목 생성·원자적 게시까지 포함한 충돌/재시작 계약을 OS별로 검증한다. 수신 중 위치와 영속 확정 위치는 구별하고, 재접속은 확정 위치에서 시작한다. 디스크 파일이 원장보다 길면 미확정 꼬리를 재검증하거나 잘라 다시 받으며, 원장보다 짧으면 손상으로 처리한다. `fsync`를 단순 삭제해서 속도를 높이지 않는다.

최초 원본 해시·수신 최종 해시와 목적지 no-clobber 게시를 우선 유지한다. 읽는 도중 원본이 바뀌면 판본 충돌/해시 실패로 남긴다. 재개 이후에도 전체 최종 해시를 검사한다. 해시 비용 절감은 별도 증거 없이 검사 생략으로 해결하지 않는다.

진행·취소는 전송 스트림과 독립적으로 처리하고 배치 내부에서도 취소를 확인한다. 파일 송신 속도를 한정해 화면·제어에 여유를 주며 동시 작업에서 검증한다. collect는 기존 최종 경로·충돌 보호를 유지하고 복사 시간이 전체 완료 시간에 포함되도록 표시한다.

구형 헬퍼·폰은 기존 JSON 경로를 계속 쓴다. 새로운 capability가 양쪽에서 확인될 때만 바이너리 경로를 선택한다. 새 경로 실패 후 fallback은 확정 위치 재조회와 동일 원본 확인 뒤 수행한다. 프로토콜 전환 때문에 새 전송을 중복 생성하지 않는다.

## 6. 화면 공유 수리

### 품질과 입력 반응

첫 배포는 JPEG 경로를 유지하며 해상도·JPEG 품질·캡처 빈도를 전송 압력에 맞춰 조절한다. 하한·상한·회복 속도와 히스테리시스를 정의해 품질이 매 프레임 흔들리지 않게 한다. 전송이 밀리면 새 캡처/인코딩 빈도도 낮춘다. 최신 프레임 한 장을 유지하는 기존 처리는 보존한다.

정지 화면은 변화 확인 후 재전송을 줄인다. 커서는 가능하면 영상과 분리하되 좌표·DPI·다중 모니터 계약을 유지한다. 워커가 OS 스레드 제약을 가지므로 단순 병렬 호출로 캡처·입력을 경합시키지 않는다. 입력을 우선 처리하고 캡처의 실행 예산을 제한한다. 연속 이동은 합칠 수 있지만 클릭·버튼 해제·키 순서는 유지한다. 큐 포화 시 원인을 기록하고 제어를 안전하게 중지한다.

### 일시 단절 복구

기존 screen 세션 소유자 안에 `starting → running → reconnecting → running/closed`를 도입한다. 복구 유예와 heartbeat 정책은 세션 정책 파일이 소유하고 헬퍼에 협상해 전달한다. 네트워크/일시 timeout과 인증 철회·사용자 종료·캡처 권한 실패를 구분한다. 후자는 무조건 재연결하지 않는다.

일시 단절 시 입력을 멈추고 워커의 눌린 키/버튼을 해제한다. 뷰어는 마지막 화면 위에 복구 중 표시를 하고 입력을 받지 않는다. 같은 사용자·장치·설치 세대·세션에 한정된 재접속을 허용하며, 연결 세대로 늦은 이전 소켓의 프레임·종료 처리를 차단한다. 한쪽 이전 소켓의 finally가 새 연결까지 닫지 않도록 attach/detach와 최종 close를 분리한다.

복구 후 새 프레임을 받은 다음 입력을 다시 허용한다. 이전 입력은 재생하지 않는다. 사용자 종료·등록 해제·유예 만료는 세션을 확정 종료하고 작업/워커를 회수한다. 허브 재시작은 첫 배포에서 세션 종료로 명시하며 자동 복원 지원을 주장하지 않는다. 기존 메모리 세션을 억지로 영속화하지 않는다.

### 후속 영상 엔진

적응형 JPEG와 복구 후에도 캡처 CPU·대역폭·반응 목표가 충족되지 않으면 Windows Desktop Duplication 또는 Windows Graphics Capture와 하드웨어 영상 인코딩을 검토한다. 변경 영역 처리나 H.264/VP8 등 코덱은 성능·화질·배포 의존성·구형 장치 호환성으로 선택한다.

기존 `helper/media_session_*`의 WebRTC·경로·코덱 협상 기반은 재사용 후보지만 화면 공유의 제어 권한과 등록 기기 계약을 일반 통화의 수락 정책으로 바꾸지 않는다. JPEG fallback을 유지하고 새 capability로 선택한다. 동영상 엔진 도입은 별도 단계이며 첫 배포의 완료 주장에 포함하지 않는다.

## 8. 검증과 인수 기준

다음 수치는 **목표와 시험 조건**이며 측정 결과가 아니다. 원자료에는 경로·판본·파일 크기/해시·망 조건·표본 수·실패를 함께 남긴다. 정상 완료만 골라 평균을 내지 않는다.

### 자동 계약 검증

- 파일: 빈 파일, 배치 경계 전후, 큰 파일, 양방향, ACK 유실·중복·잘못된 offset·초과 크기·원본 변경·해시 불일치·목적지 충돌·취소를 검사한다.
- 파일 영속성: 데이터 쓰기/영속화/DB 커밋/ACK/최종 게시 사이에 프로세스 종료를 주입한다. 기존 확정 offset과 최종 해시를 복구하고, 동시 작성자와 구형 경로 혼용을 거절하거나 직렬화한다.
- 화면: 1·3·8초 단절, 프레임 송신 정체, 입력 폭주, 늦은 이전 소켓 종료, 중복 attach, 유예 만료, 창 닫기·등록 해제와 재연결의 경합을 검사한다.
- 입력: 드래그·조합키 도중 단절과 재개, 키/버튼 해제, DPI·해상도 변경을 검사한다. 재연결로 클릭·문자가 두 번 전달되면 실패다.
- 호환: 새 서버+구형 헬퍼/Android, 새 헬퍼+구형 서버, Mac/Linux JPEG 경로, LAN 인증 실패→외부 fallback을 확인한다.

기존 시험의 위치는 `backend/test_resident_pcs.py`, `backend/test_resident_screen.py`, `backend/test_resident_terminal_lan.py`, `backend/test_phone_limb_transfer.py`, `helper/resident_transfer_retry_test.go`, `helper/resident_screen_test.go`다. 새 시험도 모듈명 파일에 둔다. UI는 기존 `frontend/scripts/test_screen_share.py`와 실제 연결 수명 시험을 보강한다.

검사 선택·종합 회귀는 [회귀 규약](REGRESSION_TESTING.md)을 따른다. Go는 `helper/`에서 `go test -race ./...`와 Windows 빌드/실기 검사를 구분한다. frontend 변경은 `npx tsc -p tsconfig.app.json`, backend 변경은 몸 번들 재생성 및 관련 필수 관문을 포함한다. 실행한 회귀와 미실행 인수 기준은 §11에 기록한다.

### 성능과 실장치 인수

| 영역 | 시험과 합격 기준 |
| --- | --- |

고정 시험 파일·화면은 전용 임시 위치에 만들고 사용자 영화·진행 중 전송·실제 업무 화면에 장애를 주입하지 않는다. 물리 상한 비교는 같은 방향·경로·인증 조건에서 시행한다. 인터넷 speed test 하나로 tv1→허브 경로의 상한을 판정하지 않는다.

## 9. 배포와 완료 보고

1. 허브에 구형 소비자 호환 구현을 먼저 반영하고 capability 협상을 확인한다. 전송 DB 변경은 읽기 호환·rollback 계획을 포함한다. 라이브 DB 백업이 필요하면 백업 규약의 SQLite backup/VACUUM INTO를 사용한다.
2. 기존 헬퍼 교체 경로로 tv1 Windows 헬퍼를 배포한다. tv1의 IndieBiz 앱 업데이트와 상주 헬퍼 업데이트를 별개로 확인한다. 설치 파일 생성만으로 적용 완료라 하지 않는다.
3. 실제 실행 중인 헬퍼 판본/해시·capability, 허브 활성 코드, 뷰어 판본을 확인한다. Electron 연결 코드가 바뀌었다면 필요한 앱 재시작도 완료한다.
4. tv1 양방향 파일, 화면 30분, 짧은 단절 복구, 파일+화면 동시 사용을 인수한다. 기존 전송은 자동 취소/재시작하지 않고 호환 경로로 마무리한다.
5. 실패하면 새 capability 선택을 닫고 기존 경로로 복귀한다. 진행 중 바이너리 전송은 영속 offset을 대조한 뒤 재개하고 부분 파일을 임의 삭제하지 않는다. 구형 헬퍼 복귀와 원장 판본 호환을 먼저 확인한다.

구현 커밋은 정본 main에 변경 pathspec만 포함한다. 문서·가이드의 실제 지원 범위와 changelog를 갱신하며 `git log`로 존재하는 커밋만 보고한다. 완료 보고에는 구현 범위, 회귀 결과, tv1 활성 판본, 전후 측정, 미지원/미검증 장치를 각각 적는다. 코드 반영·배포 성공·성능 인수는 서로 다른 확인 단계다.

## 10. 기존 설계와 근거

- [2026-10-25 연결 지연 개선](HARDWARE_CONNECTION_LATENCY_DESIGN_2026_10_25.md)은 명령 결과 즉시 보고와 실제 TV의 연결 재사용이 중심이다. 이번 설계는 그 구현을 보존하고 파일 처리량·화면 품질·일시 단절 복구를 추가한다.
- [원격 PC 자원 설계](REMOTE_PC_RESOURCE_DESIGN_2026_10_10.md)의 인증·작업 원장·파일 무결성 계약, [원격 접근 안내](../data/system_docs/remote_access.md), [헬퍼 가이드](../data/guides/guest_helper.md)를 따른다.
- [RFC 4648 Base64](https://www.rfc-editor.org/rfc/rfc4648.html#section-4): 3바이트를 4문자로 표현하는 전송량 근거.
- [Microsoft Desktop Duplication](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api): 변경/이동 영역을 제공하는 후속 캡처 구현 후보. 현재 사용 중이라는 뜻은 아니다.
- [Cloudflare WebSockets](https://developers.cloudflare.com/network/websockets/): 중계 서버 재시작으로 연결이 끝날 수 있어 복구가 필요하다. tv1의 실제 끊김 원인이 Cloudflare였다는 증거는 아니다.


## 11. 구현과 적용 기록 (2026-10-31)

### 공통 구현

- `resident_transfer_io.py`: 전송별 OS 파일 잠금, 최대 1MiB 배치, 파일 영속화 후 짧은 DB offset 갱신, 동일 바이트 재요청의 멱등 처리, ACK 이전 꼬리 정리, rename 이후 완료 기록 복구. 전체 크기·SHA-256 확인을 유지한다.
- `api_resident_transfer.py`: 설치 인증을 거친 WebSocket 바이너리 채널. 바이트 앞 8바이트는 big-endian offset이다. 기존 HTTPS JSON 경로를 유지하고 `binary_version=1` 협상 시에만 새 경로를 제공한다. 매 메시지마다 등록·소유·취소를 확인한다.
- Go 헬퍼와 `phone_transfer_wire.py`가 같은 프로토콜을 사용한다. PC는 1MiB, Android는 512KiB 배치를 쓰며 인증된 LAN 후보의 인증서 지문 검증 및 외부 허브 fallback을 적용한다. 연결 설정이 실패하면 기존 HTTPS 전송으로 돌아간다. 인증·계약 거절은 성공으로 감추지 않는다.
- 화면 공유 중인 기기의 바이너리 파일 전송은 서버에서 약 512KiB/s로 제한한다. 기존 JSON 소비자에는 이 제한이 적용되지 않는다. 제한은 입력 지연을 보장하는 QoS가 아니라 경합 완화 조치다.
- 화면의 새 연결 세대와 15초 복구 유예를 협상한다. 옛 소켓·옛 비동기 프레임 콜백은 새 세션을 덮지 못한다. 단절 시 입력 큐를 비우고 reset을 보내며 새 프레임을 받기 전에는 뷰어 입력을 막는다. 명시 종료는 복구하지 않는다. 서버 프로세스 재시작은 메모리 화면 세션을 보존하지 않는다.
- PC는 송신 대기에 따라 1600/1280/960/640 너비, JPEG 65/55/45/35, 목표 15/10/6/3fps를 조절한다. Windows·Mac 워커는 너비와 품질을 적용한다. Linux 워커는 품질과 캡처 간격을 적용하고 너비는 기존 값을 유지한다. 정지 화면은 최대 2초 간격으로 보낸다.
- Android는 송신 큐 상태에 따라 1280/65/400ms 또는 800/40/800ms로 조절하고 큐가 쌓이면 프레임을 버린다. Accessibility/MediaProjection 모두 적용한다. 이미 진행 중인 캡처를 짧은 재접속 때문에 다시 승인받지 않으며, OS의 캡처·접근성 권한은 그대로 필요하다.

### 관측과 남은 범위

파일 결과에 transport·route·전체 경과 시간을 남기고 서버 ACK에 처리 시간을 제공한다. 화면 상태에는 경로·재연결 횟수·종료 코드를 제공한다. §4의 세부 단계별 시간·입력 p50/p95·fps 대시보드 전체가 구현된 것은 아니다. 현재 적응형 품질은 송신 대기/큐 기반이며, 최종 뷰어 표시까지의 혼잡 피드백이나 하드웨어 영상 코덱은 후속 범위다.

§8의 100MiB/1GiB 각 3회, 제한 망 조작 100회, 화면 30분 및 모든 플랫폼의 실제 권한·장기 안정성 인수는 별도 기준이다. 아래의 소규모 실측·자동 검사를 이 전체 인수의 통과로 대체하지 않는다.


### tv1 실측과 배포

전용 임시 파일을 쓰며 사용자의 기존 대용량 전송·부분 파일은 건드리지 않았다. 새 Windows 헬퍼 SHA-256은 `1cd2194ff0950de954eef8a2144c1c151dca864e3b5ff45fe4419a229c1413d7`이다. 운영 등록에서 이 해시 및 `binary_transfer:1`, `screen_reconnect:1`, 연결 상태를 확인했다.

| 측정 | 결과 |
| --- | --- |
| 8MiB 구형 3회, 명령 접수→완료 조회 | 36.445 / 36.496 / 35.461초, 중앙값 36.445초 |
| 8MiB 신형 3회, 같은 관측 | 5.114 / 4.087 / 3.072초, 중앙값 4.087초 |

| 신형 100MiB 수신 1회 | 전체 17.431초, 헬퍼 내부 15.433초, 크기·SHA-256 일치 |

### 다른 플랫폼 적용 상태

- Windows: tv1에 새 실행 파일 적용과 양방향 전송·뷰어 단절 복구 확인.
- Mac: arm64/amd64/legacy 헬퍼 및 네이티브 워커 빌드 완료. 등록 Mac에 설치하지 않았다. `helper/build.sh`의 ad-hoc 빌드는 정식 업데이트 후보가 아니며, 실제 배포는 기존 인증서 서명 릴리스 절차를 거쳐야 한다.
- Android: arm64·arm32 앱 0.25(versionCode 25)와 공통 Python 소비자 빌드 완료. 중앙의 ABI별 업데이트 아티팩트로 발행했으며 실제 폰 설치·권한·성능은 미검증이다. 앱 관리의 기존 업데이트 절차로 설치해야 화면 복구 capability가 활성화된다.
- Linux: 헬퍼 빌드 완료. X11/Wayland 실장치 인수는 미실행.
- 뷰어: TypeScript 검사·Vite 빌드·실제 Chromium 렌더/입력/재연결 시험 완료. 실행 중인 기존 화면 창은 닫고 새로 열어 갱신된 뷰어를 사용한다. 패키지에 묶인 이전 앱은 해당 앱 업데이트가 필요하다.


### 회귀 검증

- 백엔드 최종 전수(`pytest backend/ -n auto --dist loadfile`): 11,685 통과, 24 건너뜀, Electron 캡처 시험 1 실패. 첫 프레임이 준비되기 전 `capturePage()`가 실행되어 `UnknownVizError`가 났고 단독 실행에서도 재현됐다. `ready-to-show`를 기다리도록 시험을 수정한 뒤 해당 모듈 및 파일/폰 업데이트/화면/시험 실행 규약 **77건 재검사 통과**. 수정 뒤 전체를 한 번 더 실행한 것은 아니다.
- 첫 전수의 구형 HTTP 전용 폰 설치 fixture 2건과 새 시험의 직접 실행 진입점 1건도 수정했다. 구형 HTTPS 전송 검사는 유지하고 바이너리 서버/폰 소비자 왕복을 별도 시험한다.
- Go `go test -race ./...` 통과. 실제 WebSocket ACK 유실·동일 offset 재전송·바이너리 읽기, 품질 조절 경계 검사를 포함한다. Windows/Mac/Linux 빌드 완료.
- Android `testArm64DebugUnitTest`, `testArm32DebugUnitTest`, 두 ABI `assemble…Debug` 통과. Kotlin의 실기기 캡처/권한 수명 전체를 단위 시험이 보증하지는 않는다.
- TypeScript 프로젝트 검사, Vite 빌드, Chromium 뷰어 검사 통과. 소켓 재연결, 이전 소켓의 늦은 close/error 무시, 텍스트 입력 재전송 방지, 명시 종료를 검사한다.
- 층 배정·파일 크기/가이드 예산·몸 번들·IBL 파생 검사 통과. 운영 허브 ACTIVE와 변경된 서버 모듈 6개의 활성 세대/정본 바이트 일치를 확인했다. 이 작업의 시험용 tv1 임시 파일 3개는 제거했다.
