## 2. 이번 수정의 우선순위

### P1-A. 정본 텍스트 인코딩과 실행 진입점의 일관성 — 확정 결함

**증거:** seq 237의 원문 예외는 `UnicodeDecodeError: 'cp949' codec can't decode byte 0x80`.
현재 main의 `backend/datastore/vocabulary_state.py`에도 인코딩 없는 읽기가 남아 있다:
manifest.json(81), tool.json(83), ibl_actions.yaml(93), activation.json(147).
활성 원장 쓰기는 이미 UTF-8이므로 읽기와 쓰기의 계약도 다르다.

**최소 재현:** 임시 폴더에 한글·이모지가 있는 UTF-8 tool.json을 만들고 실제 `inventory()`를 호출했다.
Path.open의 기본 텍스트 인코딩만 cp949로 모사하면 같은 UnicodeDecodeError가 발생했다.
명시 `encoding="utf-8"` 읽기는 동일 자료를 손실 없이 복원했다. Mac에서의 경계 모사이며
Windows 실기기 수리 검증은 아니다. 원격 변경 0건이다.

**수정 범위:** 정본 JSON/YAML/활성 원장의 읽기를 명시 UTF-8로 맞추고, 실제 부팅 경로에서
같은 계약을 가진 누락을 점검한다. 임의 사용자 파일까지 일괄 UTF-8로 강제하거나
`errors="ignore"`로 손상을 숨기지 않는다. README/CLI/bootstrap 기동 안내와 자식 프로세스의
환경 전달도 정렬한다. `PYTHONIOENCODING`은 표준 입출력 설정이므로 파일 읽기 수정의 대체물이 아니다.

**검증:** UTF-8 모드를 끈 Windows 기본 코드페이지에서 실제 inventory·활성 원장 재독,
CLI 기동 → 같은 설치 루트의 health를 확인한다. Electron 경로도 유지한다.
`scripts/ci_boot_smoke.py`는 현재 PYTHONUTF8=1을 강제하므로 이 한 조건만으로 회귀를 닫지 않는다.
최종 응답의 ‘약 500곳’은 당시 grep 결과이며 500개 확정 결함 목록이 아니다.

### P1-B. 기동 관측을 현재 실행 세대에 묶고 확정 실패에서 끝내기 — 절차 결함

**증거:** 첫 기동 셸은 health만 반복 대기하다 400초 제한에 걸렸다(seq 205~220).
실패 영수증의 finished_at는 접수 시각 이후 약 34초를 가리킨다. 이를 검토했을 때 알 수 있는
실패와 실제로 실행자가 알아챈 시각은 구분하되, 실패 뒤에도 기다린 비용은 분명하다.
재기동 셸은 12초 뒤 `PHASE FAILED`를 찍은 다음 `phase=STARTING`을 보고했다(seq 261).
이후 91초 관측으로 ACTIVE를 확인했다(seq 270). 조회에 generation·PID 대조가 없어 12초 시점의
FAILED가 이전 시도인지 새 시도인지 확정할 수 없다. 누적 로그·last_result와 현재 phase를
같은 시도의 결과로 묶어도 되는지 확인하지 않은 것이 관측된 절차 문제다.

**수정 범위:** 기존 재기동 제어자의 generation·controller PID·현재 시도와 상태를 대조하는
설치 검증 경로를 사용한다. 살아 있는 STARTING은 기다리고, 같은 시도의 확정 FAILED는
즉시 이유와 증거를 반환한다. 옛 실패·다른 프로세스의 health는 현재 결과로 사용하지 않는다.
`scripts/ci_boot_smoke.py`의 PID 대조와 실패 진단을 참고하되 새 상태 저장소를 만들지 않는다.

**검증:** 이전 실패 → 새 기동 지연 → 성공, 현재 세대 실패, 다른 서비스의 health 200 세 조건.
검증기에서 관측 간격 2초인 대역은 현재 실패 확정 후 다음 두 관측 이내 종료하도록 고정한다.
실기기 관측은 전송 지연을 별도 기록한다. 제어자 자체의 세대 계약 결함은 아직 확인하지 않았다.

### P1-C. 설치·검증 실패가 셸의 최종 성공에 가려지지 않게 하기 — 확정 작성 문제

**증거:** bootstrap 호출은 `$LASTEXITCODE`를 출력한 뒤 Get-Content로 끝난다(seq 141).
이번 bootstrap 자체는 0으로 성공했으므로 설치 실패 은폐가 발생했다고 단정하지 않는다.
반면 기동 관측은 FAILED와 접속 실패를 출력하면서 실제 셸 exit는 0이었다(seq 261).
OS 명령 성공과 설치 목표 성공이 다른데, 그 차이를 매번 모델이 로그에서 해석해야 했다.

**수정 범위:** 설치 argv·검증 argv의 종료를 나눠 보존하고, 기동 검증 실패는 검증 단계의 비정상
종료로 반환한다. `remote_steps.py`의 기존 계약을 사용한다. 일반 셸의 로그 문자열을 보고
런타임이 임의로 성공/실패를 뒤집는 방식은 쓰지 않는다.
bootstrap의 선택 의존성 경고도 요구 기능별 준비/누락으로 확인한다. 선택 실패를 무조건
전체 실패로 바꾸거나, 전체 종료 0을 모든 기능 성공으로 바꾸지 않는다.

**검증:** 시험 설치 명령 exit 7 뒤 로그 읽기 성공, 명령 성공·검증 실패, 필수/선택 의존성 누락.
후행 의존 단계는 실행되지 않고, 성공한 설치를 재실행하지 않은 채 검증만 재시도할 수 있어야 한다.

### P2-D. Windows 원격 출력의 문자 보존 — 현상 확정, 손상 지점 추가 진단

**증거:** Git/Node 사전 점검부터 최종 로그까지 한글·일본어가 깨졌다(seq 55·104·237·270).
출력 파일을 `Get-Content -Encoding UTF8`로 읽은 경우에도 원격 결과에 대체문자가 남았다.
헬퍼가 UTF-8을 해독하는 경계와 PowerShell/자식 프로세스의 출력 인코딩을 따로 확인해야 한다.

**수정 후보:** `helper/resident_execute.go`의 셸 구성·residentLog.Write·process와 Windows 셸 경계.
UTF-8 출력 계약을 정하고 원시 바이트→디코딩→전송의 손상 위치를 먼저 찾는다.
이미 깨진 문자열을 추정 복구하거나 모든 외부 명령이 UTF-8이라고 가정하지 않는다.
한글·일본어·이모지, stdout/stderr, 분할된 다중 바이트, 대용량 꼬리 읽기를 검증한다.
헬퍼 배포가 필요한 수리와 중앙 코드 수리를 별도로 기록한다.

### P2-E. 새 설치·기존 설치 갱신의 발견 경로와 기능별 완료 증거

**증거:** 회상 후보는 로컬 라이브러리 설치 2건과 폴더변화 스크립트였다(seq 27).
감독은 guest_helper.md를 제시했지만 실행자는 원격 단계 실행 관용구를 사용하지 않았다.
최종 검증에는 없는 `self:task.seconds` 접근 거절(seq 118), 큰 상태 JSON 출력 후 재조회(seq 229→237),
패키지 존재에서 실제 기억 검색 가능으로의 과장(seq 279·최종 응답)이 있었다.

**수정 범위:** 새 설치는 bootstrap, 기존 저장소 갱신은 remote_install이라는 적용 조건을
교재·발견 경로에 드러낸다. 현재 remote_install은 기존 저장소와 런타임을 전제로 하므로
‘안 골랐으니 실패’로 채점하지 않는다. 새 설치도 원격 접수증·단계 검증을 재사용하도록 잇는다.
필수 반환 필드는 실제 계약에서 확인하고 상태 보고는 필요한 필드와 로그 참조를 반환한다.
설치/기동/인증/GUI/ML 준비를 구분하며 API 키 자리표시자나 find_spec를 기능 시험으로 세지 않는다.
403은 보호된 상태 조회의 미확인이지 서비스 다운이나 인증 우회 요청이 아니다.

**검증:** 도구 이름을 알려주지 않은 자연어 과제로 방법 선택을 관측한다. 패키지 존재·import 성공·
실제 작은 질의 성공을 구분하고, 하지 않은 검증을 ‘사용 가능’으로 보고하지 않아야 한다.
새 설치와 갱신에 서로 맞는 조리법을 골랐는지 본다. 토큰 절감은 동일 조건 실행 뒤에만 주장한다.

## 3. 후속 후보와 이번 범위 밖

부팅 뒤 `data/guides/codebase_map.md` 하나가 추적 변경으로 남았다(seq 279).
현재 prompt_builder는 mtime 기반으로 이를 다시 쓰며, remote_install은 추적 변경을 모두 거절한다.
따라서 ‘첫 설치 성공 → 다음 갱신 거절’의 연결 가능성이 있다. 원격 diff 원문을 이번에 확보하지
않았으므로 CRLF·내용 차이·파생판 불일치 중 원인을 확정하지 않는다. 별도 재현 후보로 둔다.
수리 때도 임의 reset이나 모든 파생물 변경 무시로 실제 사용자 수정을 지우면 안 된다.

이번 사용자 요청에 따라 한 일은 **설계 보강과 수정 대상 식별**이다.
우선 P1-A를 제품 결함으로, P1-B·C를 설치 실행/검증의 공통 절차로 수리하는 것이 타당하다.
P2-D는 문자 손상 경계를 확인한 뒤, P2-E는 독립 AI의 발견·완료 보고 재시험과 함께 진행한다.
현재 다른 세션의 자기수리·모바일·번역 작업이 있어 그 미커밋 변경에는 손대지 않았다.
