# 변경 대상의 소유권과 자기수리 경계

## 원칙

수리 턴이라는 이유로 모든 변경을 코어 변경으로 취급하지 않는다. 코어는 실행·해석·
권한 검사·작업 지속·프로세스 생존을 구현하는 기질이다. 그 기질이 관리 연산으로
조회·검증·개정하는 정의와 데이터는 입력이다. 입력의 개정과 입력을 처리하는 구현의
교체를 구분한다. 파일 확장자나 '수리'라는 표현으로 구분하지 않는다.

| 변경 대상 | 반영 계약 | 완료 근거 |
|---|---|---|
| 관리되는 정의·데이터 | 소유 관리 연산의 검증·충돌 검사·저장 | 저장된 판본과 새 호출 결과, 사용자 목표 |
| 실행 구현 | 같은 후보의 검사·정본 반영·기존 활성화 절차 | 적용·활성화·커밋 영수증과 원 증상 재검사 |
| 지침·권한·목표 기준 | 업무 중 편의상 변경하지 않는 통제 경계 | 별도 명시 요청의 범위와 기존 통제 |

구현 변경도 전체 재기동과 동의어가 아니다. 등록 순수 부품은 부품 게시, 워커 구현은
세대 교체, 제어 기반은 기반 인계를 사용한다. 기존 활성화 계약을 유지한다.
관용구 본문은 관리되는 정의이고, 관용구 해석기·실행기는 구현이다. 관용구를 Python
파일에 복제하거나 코어 회귀시험을 만들 수 있다는 이유만으로 정의 개정을 코드 수리로
확대하지 않는다. 배포 시드도 갱신해야 하는 개발 요청은 정의 개정과 소스 변경을 각각
검증하며, 운영 원장 반영을 소스 파일 수정으로 대신하지 않는다.

## 실행 경계

### 기본값: 보호 코어 밖은 교체 가능한 프로그램

독립 부품의 허용 목록을 늘리는 것은 목표 구조가 아니다. 사용자 목적·기본 지침·권한·
완료 기준과 그 경계를 집행하는 최소 구현을 보호 코어로 명시하고, 나머지 구현은
기본적으로 에이전트가 업무 범위 안에서 검사·수정할 수 있는 프로그램으로 취급한다.
`backend/`라는 위치, 실행 중 적재 여부, Python 확장자만으로 보호 코어가 되지 않는다.
언어 처리·검색·문서·동영상 같은 기능의 일반 알고리즘과 그 안의 권한 집행이 섞였으면
권한 집행을 보호 경계로 분리한다. 기능 전체를 코어로 승격해서 해결하지 않는다.

수정 권한과 교체 방식은 별개의 축이다. 일반 프로그램의 상태·공유 자원 때문에
재시작이 필요할 수 있지만, 그것은 그 프로그램의 수명 계약이며 자기 지침을 고칠
권한이나 시스템 전체 재검사를 뜻하지 않는다. 호출 계약·의존성·소유 상태·검사·활성
판본을 공통 실행 기반에서 다룬다. 기존 패키지·모듈·표면의 소유 정보를 재사용하고
새 일반 프로그램도 같은 경로에 들어온다. 기능마다 코어에 새 예외 분기를 추가하거나
순수 함수 등록을 해야만 수정할 수 있는 구조를 최종 해법으로 삼지 않는다.

검사 범위는 변경 프로그램과 영향을 받는 의존·소비 계약에서 정한다. 다른 프로그램의
편집이나 사용하지 않는 설치 라이브러리 변화가 그 수리를 무효화해서는 안 된다.
실제 공유 계약이 바뀌면 영향 범위를 넓히고, 경계가 불명확하면 그 불명확한 연결을
표시한다. 동적 의존을 무관하다고 추정해 검사를 생략하거나 전체 몸을 코어로 분류하지 않는다.
후보의 검사 판본, 정본 반영, 활성 판본, 복구 판본과 원 업무의 재개는 연결해서 보존한다.

순수 변환은 호출 경계에서 판본을 바꿀 수 있고, 상태 있는 프로그램은 진행 호출을
마무리하거나 중단 상태를 보존한 뒤 해당 실행 단위를 교체한다. 공유 프로세스에
얽힌 기존 구현은 실제 수명 경계를 분리해야 한다. 수정 허용 경로만 넓히거나
`sys.modules`를 지우는 일을 독립 교체 구현으로 보고하지 않는다.

**구현 경계(2026-11-02):** `program_boundary`가 보호 코어를 명시하고 일반 패키지·
모듈·표면·스크립트·사전 정의의 소유 단위를 경로에서 판정한다. `program_dependencies`는
의존·소비 검사와 외부 설치 의존을 수집한다. 변경 프로그램의 입력만 봉인하고, 동적
의존이 해소되지 않으면 넓은 환경 검사와 그 이유를 유지한다. 관리 정의의 기존 원장과
충돌 검사는 그대로 쓴다. 어휘 빌더가 선언한 파생물만 소유 검사 후 후보에 포함하고,
문서 마커 밖 산문 변경이나 빌더·보호 코어 수정은 이를 통해 우회할 수 없다.

`program_versions`와 `program_runtime`은 일반 도구 패키지의 전체 소스·하위 모듈을
불변 판본으로 게시한다. 첫 배포 호출부터 수명을 추적하며 생성기·비동기 호출이 끝나기
전에 그 프로그램의 판본을 바꾸지 않는다. 다른 패키지 호출은 교체를 막지 않는다.
상태는 기존 데이터 원장에 남고, 프로그램이 소유하는 임시 상태는
`__program_export__`/`__program_restore__`, 자원 종료는 `__program_close__` 계약으로
옮긴다. 직접 소유한 실행 중 Thread/Popen은 종료 계약이 없으면 활성화를 대기한다.
임의 외부 자원·중첩 객체의 백그라운드 작업을 자동 발견하는 범용 격리는 아니다.
게시 실패와 부분 파일 쓰기 실패는 정확히 해당 후보의 이전 바이트·게시 기록으로 복구한다.

`program_modules`는 워커가 일반 backend 모듈을 처음 가져오기 전에 호출 경계를 설치한다.
이미 가져온 함수·등록된 API 핸들러·기존 클래스 인스턴스도 같은 경계를 사용한다.
새 API 라우트도 동일 게시에서 해당 라우터만 다시 연결한다.
진행 중인 동기/비동기/생성기 호출은 이전 함수 전역과 호출 표를 유지하고 새 호출부터
새 판본을 사용한다. 모듈 전역의 기존 상태·잠금은 보존하며, `from`으로 가져온 상수를
쓰는 일반 소비 모듈도 전이적으로 다시 결합한다. 혼합 패키지의 일반 형제 모듈은 같은
경계로 들어오고 그 패키지의 보호 게이트는 교체하지 않는다.

`program_publication`은 선택한 모듈·사전·검증된 파생물을 불변 객체로 준비하고 하나의
게시 기록으로 활성화한다. 사전 로더는 게시 경로를 캐시 키에 포함하며 패키지·노드·실행기
캐시의 소유 무효화 절차까지 확인한다. 검사 통과, 정본 쓰기, 활성 판본, 정확한 커밋이
각각 확인되어야 완료다. 진행 중인 패키지 호출을 기다리는 적용은 런타임이 자동 재개한다.
정확히 게시한 파일만 워커 재시작 감시에서 제외하며 다른 파일 변경은 숨기지 않는다.

이 계약은 공유 프로세스 안의 모든 Python 변경이 무조건 호환된다는 뜻은 아니다.
기존 호출 삭제·인자 변경, 클래스의 슬롯/필드 구조 변경, 등록 데코레이터 변경은 해당
부품의 소비 계약 이전이 필요하다고 적용 전에 거절한다. 호환 어댑터를 유지하거나
그 부품의 소유 상태·소비자를 함께 이전해야 한다. 변경된 상태 초기화는
`__program_export__`/`__program_restore__`로 옮기며 선택적 `__program_retire__`는
이전 호출 표의 마지막 참조가 사라진 뒤 자원을 정리한다. 새 import 부작용을 임의로 재실행하지
않으며, 범용 외부 자원 격리를 주장하지 않는다. 프런트엔드는 해당 표면의 빌드·재적재,
스크립트·관용구는 기존 정의 소유자의 판본 계약을 사용한다. 이 제약은 일반 기능을
보호 코어로 승격하거나 전체 워커 재시작으로 우회하는 사유가 아니다.

구조 인수는 사전 등록하지 않은 새 일반 프로그램의 수정·재호출, 무관한 프로그램의
편집에도 유효한 검사 유지, 공유 계약 변경의 영향 검출, 보호 코어 및 우회 변경 거절,
진행 작업의 중복 실행 없는 교체·복구로 확인한다. 동영상 한 사례의 성공이나 권한
목록 확장만으로 이 구조의 완료를 주장하지 않는다.

- `repair_workspace`는 파일·코드 작업 대상이다. 관리 원장의 소유권을 덮어쓰지 않는다.
- 함수 원장은 다른 운영 데이터와 같이 프로세스의 `INDIEBIZ_BASE_PATH`에 속한다.
  RED 권한이 있어도 원장이 사본으로 바뀌지 않는다. 정의 이름별 예외 목록은 없다.
- 격리 시험은 `repair_process`가 별도 BASE_PATH와 OS 쓰기 경계를 제공한다. 시험 자식의
  원장 개정은 운영 원장을 수정하지 않는다. 파일·셸의 사본 경계도 그대로 유지한다.
- 개정은 기존 불변 판본·컴파일·저장 호출자 검사·expected_revision 충돌 검사를 따른다.
  이미 컴파일한 계획은 판본을 고정하므로 개정 확인은 새 호출로 한다.
- 완료 경로는 RED 권한의 존재가 아니라 실제 적용 대상의 존재를 본다. 미수집 셸 변경도
  후보 델타에서 확인한다. 빈 사본이나 조사만 한 턴은 원래 목표를 일반 평가한다.
  코드 변경·적용 인계·파손된 사본 기록은 적용 영수증 검사를 생략하지 않는다.
- 정의 개정 성공만으로 사용자 업무 전체를 성공으로 처리하지 않는다. 코드와 관리
  대상이 섞인 작업도 전체 기준을 유지한다. 기준을 낮추거나 새 승인 요청을 만들어
  진행을 넘기는 방식으로 해결하지 않는다.

요구했다. 코드 수리 기반의 보호를 정의 개정에 잘못 적용한 공통 경계 문제다.

## repair 안의 일반 능력 보존 — 후속 수정

분류 교정과 별개로 repair 실행 안에서 원래 업무를 끝낼 수 있어야 한다. 실패 후 방법을

턴당 한 번의 공유 한도를 유지하며, 실패가 이미 해소됐으면 추가 모델을 호출하지 않는다.

후속 실행 여부는 현재 단계의 실행 소유권으로 결정한다. 적용 예약·자식 수리 인계·평가·
활성 검사 단계는 새 실행자를 열지 않는다. 실패 후 후속과 능력 부정 교정 후속이 이
판단을 공유한다. 능력 조회 도중 새 인계가 생긴 경우에도 실행 직전에 다시 확인한다.
수리 권한 아래의 후속은 최초 실행과 같은 사본 소유 잠금을 사용하고 종료·예외 때 해제한다.

관용구 정의만 운영 원장에 남고 호출 관측은 사본으로 가던 불일치도 제거했다. 기본 수명
조회·호출 통계는 프로세스 데이터 원장을 사용한다. 명시 root를 지정한 후보 검사와 별도
BASE_PATH로 실행되는 격리 자식의 관측은 계속 분리한다. 운영 함수의 성공/실패 경험이
수리 문맥 종료 뒤 사라지지 않으며, 시험 성공을 운영 성공으로 기록하지 않는다.
