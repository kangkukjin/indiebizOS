# 변경 대상의 소유권과 자기수리 경계

## 원칙

수리 턴이라는 이유로 모든 변경을 코어 변경으로 취급하지 않는다. 코어는 기본 지침·권한·격리·언어·목표와 완료 판정을 집행하는 보호 구현이다.
일반 기능 구현은 코어가 아니며, 그 구현이 관리 연산으로
조회·검증·개정하는 정의와 데이터는 입력이다. 입력의 개정과 입력을 처리하는 구현의
교체를 구분한다. 파일 확장자나 '수리'라는 표현으로 구분하지 않는다.

| 변경 대상 | 반영 계약 | 완료 근거 |
|---|---|---|
| 관리되는 정의·데이터 | 소유 관리 연산의 검증·충돌 검사·저장 | 저장된 판본과 새 호출 결과, 사용자 목표 |
| 실행 구현 | 같은 후보의 검사·정본 반영·기존 활성화 절차 | 적용·활성화·커밋 영수증과 원 증상 재검사 |
| 지침·권한·목표 기준 | 업무 중 편의상 변경하지 않는 통제 경계 | 별도 명시 요청의 범위와 기존 통제 |

구현 변경도 전체 재기동과 동의어가 아니다. 등록 순수 부품은 부품 게시, 워커 구현은
세대 교체, 제어 기반은 기반 인계를 사용한다. 기존 활성화 계약을 유지한다.
관용구 본문은 관리되는 정의이고, 관용구 해석기·실행기는 구현이다. 관용구를 Python
파일에 복제하거나 코어 회귀시험을 만들 수 있다는 이유만으로 정의 개정을 코드 수리로
확대하지 않는다. 배포 시드도 갱신해야 하는 개발 요청은 정의 개정과 소스 변경을 각각
검증하며, 운영 원장 반영을 소스 파일 수정으로 대신하지 않는다.

## 실행 경계

### 기본값: 보호 코어 밖은 교체 가능한 프로그램

독립 부품의 허용 목록을 늘리는 것은 목표 구조가 아니다. 사용자 목적·기본 지침·권한·
완료 기준과 그 경계를 집행하는 최소 구현을 보호 코어로 명시하고, 나머지 구현은
기본적으로 에이전트가 업무 범위 안에서 검사·수정할 수 있는 프로그램으로 취급한다.
`backend/`라는 위치, 실행 중 적재 여부, Python 확장자만으로 보호 코어가 되지 않는다.
언어 처리·검색·문서·동영상 같은 기능의 일반 알고리즘과 그 안의 권한 집행이 섞였으면
권한 집행을 보호 경계로 분리한다. 기능 전체를 코어로 승격해서 해결하지 않는다.

수정 권한과 교체 방식은 별개의 축이다. 일반 프로그램의 상태·공유 자원 때문에
재시작이 필요할 수 있지만, 그것은 그 프로그램의 수명 계약이며 자기 지침을 고칠
권한이나 시스템 전체 재검사를 뜻하지 않는다. 호출 계약·의존성·소유 상태·검사·활성
판본을 공통 실행 기반에서 다룬다. 기존 패키지·모듈·표면의 소유 정보를 재사용하고
새 일반 프로그램도 같은 경로에 들어온다. 기능마다 코어에 새 예외 분기를 추가하거나
순수 함수 등록을 해야만 수정할 수 있는 구조를 최종 해법으로 삼지 않는다.

검사 범위는 변경 프로그램과 영향을 받는 의존·소비 계약에서 정한다. 다른 프로그램의
편집이나 사용하지 않는 설치 라이브러리 변화가 그 수리를 무효화해서는 안 된다.
실제 공유 계약이 바뀌면 영향 범위를 넓히고, 경계가 불명확하면 그 불명확한 연결을
표시한다. 동적 의존을 무관하다고 추정해 검사를 생략하거나 전체 몸을 코어로 분류하지 않는다.
후보의 검사 판본, 정본 반영, 활성 판본, 복구 판본과 원 업무의 재개는 연결해서 보존한다.

순수 변환은 호출 경계에서 판본을 바꿀 수 있고, 상태 있는 프로그램은 진행 호출을
마무리하거나 중단 상태를 보존한 뒤 해당 실행 단위를 교체한다. 공유 프로세스에
얽힌 기존 구현은 실제 수명 경계를 분리해야 한다. 수정 허용 경로만 넓히거나
`sys.modules`를 지우는 일을 독립 교체 구현으로 보고하지 않는다.

**구현 경계(2026-11-02):** `program_boundary`가 보호 코어를 명시하고 일반 패키지·
모듈·표면·스크립트·사전 정의의 소유 단위를 경로에서 판정한다. `program_dependencies`는
의존·소비 검사와 외부 설치 의존을 수집한다. 변경 프로그램의 입력만 봉인하고, 동적
의존이 해소되지 않으면 넓은 환경 검사와 그 이유를 유지한다. 관리 정의의 기존 원장과
충돌 검사는 그대로 쓴다. 어휘 빌더가 선언한 파생물만 소유 검사 후 후보에 포함하고,
문서 마커 밖 산문 변경이나 빌더·보호 코어 수정은 이를 통해 우회할 수 없다.

`program_versions`와 `program_runtime`은 일반 도구 패키지의 전체 소스·하위 모듈을
불변 판본으로 게시한다. 첫 배포 호출부터 수명을 추적하며 생성기·비동기 호출이 끝나기
전에 그 프로그램의 판본을 바꾸지 않는다. 다른 패키지 호출은 교체를 막지 않는다.
상태는 기존 데이터 원장에 남고, 프로그램이 소유하는 임시 상태는
`__program_export__`/`__program_restore__`, 자원 종료는 `__program_close__` 계약으로
옮긴다. 직접 소유한 실행 중 Thread/Popen은 종료 계약이 없으면 활성화를 대기한다.
임의 외부 자원·중첩 객체의 백그라운드 작업을 자동 발견하는 범용 격리는 아니다.
게시 실패와 부분 파일 쓰기 실패는 정확히 해당 후보의 이전 바이트·게시 기록으로 복구한다.

`program_modules`는 워커가 일반 backend 모듈을 처음 가져오기 전에 호출 경계를 설치한다.
이미 가져온 함수·등록된 API 핸들러·기존 클래스 인스턴스도 같은 경계를 사용한다.
새 API 라우트도 동일 게시에서 해당 라우터만 다시 연결한다.
진행 중인 동기/비동기/생성기 호출은 이전 함수 전역과 호출 표를 유지하고 새 호출부터
새 판본을 사용한다. 모듈 전역의 기존 상태·잠금은 보존하며, `from`으로 가져온 상수를
쓰는 일반 소비 모듈도 전이적으로 다시 결합한다. 혼합 패키지의 일반 형제 모듈은 같은
경계로 들어오고 그 패키지의 보호 게이트는 교체하지 않는다.

`program_publication`은 선택한 모듈·사전·검증된 파생물을 불변 객체로 준비하고 하나의
게시 기록으로 활성화한다. 사전 로더는 게시 경로를 캐시 키에 포함하며 패키지·노드·실행기
캐시의 소유 무효화 절차까지 확인한다. 검사 통과, 정본 쓰기, 활성 판본, 정확한 커밋이
각각 확인되어야 완료다. 진행 중인 패키지 호출을 기다리는 적용은 런타임이 자동 재개한다.
정확히 게시한 파일만 워커 재시작 감시에서 제외하며 다른 파일 변경은 숨기지 않는다.

이 계약은 공유 프로세스 안의 모든 Python 변경이 무조건 호환된다는 뜻은 아니다.
기존 호출 삭제·인자 변경, 클래스의 슬롯/필드 구조 변경, 등록 데코레이터 변경은 해당
부품의 소비 계약 이전이 필요하다고 적용 전에 거절한다. 호환 어댑터를 유지하거나
그 부품의 소유 상태·소비자를 함께 이전해야 한다. 변경된 상태 초기화는
`__program_export__`/`__program_restore__`로 옮기며 선택적 `__program_retire__`는
이전 호출 표의 마지막 참조가 사라진 뒤 자원을 정리한다. 새 import 부작용을 임의로 재실행하지
않으며, 범용 외부 자원 격리를 주장하지 않는다. 프런트엔드는 해당 표면의 빌드·재적재,
스크립트·관용구는 기존 정의 소유자의 판본 계약을 사용한다. 이 제약은 일반 기능을
보호 코어로 승격하거나 전체 워커 재시작으로 우회하는 사유가 아니다.

구조 인수는 사전 등록하지 않은 새 일반 프로그램의 수정·재호출, 무관한 프로그램의
편집에도 유효한 검사 유지, 공유 계약 변경의 영향 검출, 보호 코어 및 우회 변경 거절,
진행 작업의 중복 실행 없는 교체·복구로 확인한다. 동영상 한 사례의 성공이나 권한
목록 확장만으로 이 구조의 완료를 주장하지 않는다.

- `repair_workspace`는 파일·코드 작업 대상이다. 관리 원장의 소유권을 덮어쓰지 않는다.
- 함수 원장은 다른 운영 데이터와 같이 프로세스의 `INDIEBIZ_BASE_PATH`에 속한다.
  RED 권한이 있어도 원장이 사본으로 바뀌지 않는다. 정의 이름별 예외 목록은 없다.
- 격리 시험은 `repair_process`가 별도 BASE_PATH와 OS 쓰기 경계를 제공한다. 시험 자식의
  원장 개정은 운영 원장을 수정하지 않는다. 파일·셸의 사본 경계도 그대로 유지한다.
- 개정은 기존 불변 판본·컴파일·저장 호출자 검사·expected_revision 충돌 검사를 따른다.
  이미 컴파일한 계획은 판본을 고정하므로 개정 확인은 새 호출로 한다.
- 완료 경로는 RED 권한의 존재가 아니라 실제 적용 대상의 존재를 본다. 미수집 셸 변경도
  후보 델타에서 확인한다. 빈 사본이나 조사만 한 턴은 원래 목표를 일반 평가한다.
  코드 변경·적용 인계·파손된 사본 기록은 적용 영수증 검사를 생략하지 않는다.
- 정의 개정 성공만으로 사용자 업무 전체를 성공으로 처리하지 않는다. 코드와 관리
  대상이 섞인 작업도 전체 기준을 유지한다. 기준을 낮추거나 새 승인 요청을 만들어
  진행을 넘기는 방식으로 해결하지 않는다.

| 보호 코어 | `program_boundary.CORE_MODULES`, `ESSENTIALS_CORE`, `CORE_PREFIXES`와 보호 계약이 정본. 요청 신원·권한·격리·적용 권한·완료 계약과 영수증의 최소 경계만 내부 자기 변경을 거절한다. 외부 개발이 담당한다. |
| 재기동이 필요한 실행 기반 | 같은 파일의 `RESTART_MODULES`·`RESTART_ESSENTIALS`로 판정한다. 수정·검사 후 기존 외부 제어자가 세대 교체·복구·활성 확인을 맡는다. 수리 금지가 아니다. |
| 일반 프로그램 | `describe`가 기존 소스 배치에서 소유자·활성화 계약을 찾는다. 새 기능마다 허용 목록을 추가하지 않는다. 사본→관련 검사→apply→활성·각인으로 완료한다. |
| 관리 정의·원장 | 소유 관리 API를 사용한다. 관용구만 개정하면 코드 적용은 불필요하다. 스크립트 구현과 등록 원장을 함께 바꾸면 공식 등록 영수증을 포함한 같은 후보로 적용한다. |
| 검사·파생물 | 기존 검사는 보호 계약이다. 새 검사와 소유자가 만든 정확한 출력만 `change`가 기준 판본·영수증으로 허용한다. |

업무 중 `self:patch propose`의 대상 판정도 `program_boundary.eligible`을 직접 사용한다.
별도 코어 목록과 script/vocabulary 제외 규칙을 제거했다. 파일 쓰기 관문도 현재 작업이
소유한 사본의 baseline으로 같은 `change`를 호출한다. 새 검사를 기존 검사처럼 거절하던
정적 판정 중복을 제거했고, 운영과 같은 backend/frontend 구조 및 실제 실행 바인딩으로
새 검사 작성부터 적용까지 재현한다. 정본 직접 쓰기와 다른 사본에는 이 예외가 적용되지 않는다.
업무의 명시 경로 범위,
의존성 검사 범위, 활성화 방식은 서로 다른 책임이므로 유지한다. 경로 범위 안에서도
보호 계약을 넘지 못하고, 관리 원장의 정확한 영수증은 수집과 최종 적용에서 다시 확인한다.

`[self:patch]{op:"status",path:"data/scripts/example.py"}`는 사본을 만들거나 재개하지 않고
현재 정적 소유권·보호 사유·활성화 소유자를 반환한다. 절대 경로는 정본 내부만 허용한다.
실제 수정 허용 여부는 이후 `change`가 판정한다. `kind:managed, mutable:false`는 원장
직접 편집 불가를 뜻하며, 관리 API 개정 불가라는 뜻이 아니다. 새 검사도 정적 조회에서는
acceptance이며, 기준 판본에 없는 새 파일인지 실제 후보에서 확인해야 한다.

의식과 실행자에게 주입하는 경계 안내는 `program_boundary.guidance()` 한 곳에서 만든다.
프롬프트·도구 교재에는 이 계약의 사용법을 설명한다. 경계 변경은 이 모듈을 수정하고
권한·수집·적용·조회 회귀를 검증한다. 목록을 서로 다른 실행 코드에 복사하지 않는다.

검증: `test_repair_tool_scope`는 의식의 false 응답에서 실제 파이프라인을 거쳐
스크립트 작성·등록·시험·apply·새 호출·Git 각인까지 수행하며 보호 코어·직접 원장 쓰기와
비소유자 적용을 거절한다. `test_task_repair`는 일반 업무에서 스크립트 수리를 요청할 때
원래 목표와 한정 범위를 보존함을 검사한다. `test_program_boundary`는 경계 변경이 업무
진입·상태 조회에 함께 반영되고, 두 프롬프트 소비자가 같은 안내를 받는지 검사한다.
실제 모델의 자연어 판단 품질이나 과거 개발 후보의 기능 완료를 이 시험으로 주장하지 않는다.


## 최소 자기 변경 금지와 수리 경로 (2026-11-03, #5779–5782 후속)

코어라는 이름은 수리 거절 사유가 아니다. 권한과 교체 수명을 분리한다. 정본은
`backend/base/program_boundary.py` 하나이며, 다른 파일과 프롬프트에서 별도 목록을
만들지 않는다. `describe/change`가 수정 가능 여부, `requires_restart/host_bound`가
재기동·부분 교체 여부를 결정한다. 수리 진입, 파일 편집, 후보 수집, 적용, Python
적재기, 의존 분석, 경계 안내가 같은 정책을 소비한다. 사본에서 제외할 운영 상태
경로도 `WORKSPACE_PRIVATE` 한 벌을 후보 경로 검사와 공유한다.

이전의 보호 backend 모듈 중 실행 기반 62개는 수정 금지가 아니라 세대 교체 대상이
되었다. 파서·컴파일러·실행기, 목표 규정·프롬프트 조립, 평가 구현, 수리 재개·검사
처리와 재시작 제어 구현을 포함한다. 기본 지침 원문, 요청 신원·그랜트, 격리와 적용
권한, 원래 완료 계약·영수증의 보호는 유지한다. 목록의 최신 내용은 코드가 정본이며
이 문서의 변경 시점 수치를 운영 판정에 사용하지 않는다.

일반 코드도 실행 중인 함수 인자·클래스·상태를 호환되게 교체할 수 없으면
`RestartRequired`로 기존 외부 제어자 경로를 선택한다. 임의 예외·검사 실패를
재기동으로 덮지 않는다. 같은 검사·봉인 후보를 인계하고, 적용·활성 확인·커밋을
계속 구별한다. 호스트 교체를 부분 게시로 잘못 보내지 않도록 실제 변경 파일에서
경로를 다시 판정하므로 이전 정책으로 만들어진 세션에도 적용된다.

수리 자료 읽기는 쓰기 대상 해소와 구분한다. 절대·상대 경로 모두 현재 사본에
파일이 있으면 사본을 우선하여 자기 편집을 되읽는 기존 계약을 유지한다. 사본에 없는 보고서 같은 비코드 자료는 정본에서
읽는다. 명시한 이전 소유 사본은 읽기·복사 원본으로 사용할 수 있으며 다른 사본에
직접 쓰지는 않는다. 없어진 사본 소스 대신 정본 소스를 조용히 읽는 폴백도 없다.
기존 파일 처리기의 두 번째 사본 재매핑을 제거해 실제 handler 경로로 검사한다.

미완료 수리를 계속하라는 일반 사용자 요청은 특별한 `#repair` 없이 원래 완료 기준과
사본을 잇는다. 같은 대화의 명시 작업 키도 선택할 수 있다. 단순 상태 질문은 실행
재개로 분류하지 않으며, 관계 판정에 기존 대화를 전달한다. 과거 수동 등록부 초안은
공식 등록 시 원본 바이트로 보존한 뒤 검증 가능한 기준 등록부 위에서 해당 연산만
실행한다. 초안 전체에 가짜 영수증을 붙이지 않고, 실패하면 초안 바이트를 복원한다.

회귀 계약은 `test_program_boundary`, `test_program_modules`, `test_program_publication`,
`test_repair_tool_scope`, `test_repair_resume`, `test_task_repair`에 둔다. 특히 보고서 읽기,
이전 사본 읽기, 일반 후속 재개, 실제 후보 검사 후 재기동 인계, 부분 교체 불가 시
정본 무변경 인계, 수동 등록부 초안 복구를 확인한다. 실제 업무 완료의 증거는 별도
에피소드·적용 영수증과 커밋으로 기록한다.


### 영수증 기반 수리도 남은 실행을 자동으로 잇는다

#5783은 보고서 읽기·기존 구현 복사·등록·회귀시험 작성까지 진행했지만, 외부 개발의
세대 교체 중 검사 접수가 거절된 뒤 v2 영수증 판정이 `UNKNOWN`으로 끝났다. 이 경로는
기존 의미 검수의 `waiting_execution`에 연결되지 않아 사용자의 재요청을 기다렸다.
`repair_policy.finalize`는 이제 미적용 사본을 동일한 `repair_continuation` 계속 실행에
연결한다. 전체 기준·사본·원래 root를 보존하고 ACTIVE에서 재개하며, 같은 파일과
미달 기준·기계 검사 상태가 세 번 반복되면 원인을 남기고 멈춘다. 타임스탬프·로그
양은 진전으로 세지 않고 실제 후보 검사 상태만 추가한다. 취소와 적용 후 미확인은
무조건 재실행하지 않는다. 상태는 `PENDING_EXECUTION`, 목표 달성은 계속 미확인이다.

사용자 후속은 같은 대화의 원래 작업에서 `continued → child_task_id`를 따라 현재
미완료 사본을 찾는다. 단계별 실행 ID가 바뀌어도 빈 사본으로 바꾸지 않는다.
재기동·수리 영수증 저장소는 소유자 수리의 읽기 진단에 제공하지만 쓰기는 기존
호스트 경계에서 계속 거절한다. 읽기/쓰기 차이도 공통 경계 함수가 결정한다.

완료 판정과 후속 요청은 `repair_continuation.staging_session`으로 사본 소유권의
`reused_by` 인계를 끝까지 따른다. 자식 기록의 이전 키·소유자·root·작업 폴더를 모두
대조한다. #5783처럼 이어받은 실행이 이전 키를 보존한 기록도 최신 사본의 변경과
영수증으로 판단하며, 다른 소유권이나 순환 연결은 거절한다.

### 새 파일의 빌드 입력 연결

#5784의 실제 재개는 신규 시험을 통과했으나, 새 스크립트가 사본 Git 인덱스에 없어
배포 빌더가 이를 개인 파일로 분류했다. 실행자의 `git add -N`은 공유 Git 메타데이터
쓰기 격리 때문에 거절됐다. 이제 후보 수집 서비스가 공통 변경 범위 판정을 모두 통과한
새 파일만 해당 사본에 intent-to-add로 등록한다. 실행자에게 Git 쓰기 권한을 주거나
정본 인덱스·커밋을 바꾸지 않는다. 빌더는 기존 `git ls-files` 계약을 그대로 사용한다.

### 검사 자식과 실행 수명의 복구

같은 에피소드의 확대 검사에서 별도 임시 몸의 등록이 부모 수리의 apply를 호출했다.
`capability_changes`는 격리 자식이라는 표식만으로 수리라고 판단하지 않고 실제
계획 대상 root와 사본 root가 일치할 때만 수리 완료 경로를 선택한다. 임시 몸의
정상 등록·새 호출·해제는 실제 격리 프로세스에서도 그대로 검사한다.

도구 종료 관측 중 macOS `proc_cmdline`의 일시적 SystemError가 실행 레지스트리에
영구 오류로 남아, 이후 실행 소유자가 없어도 제어자가 모든 재개·교체를 대기하는
문제도 확인했다. 입양 판정의 명령행 관측 실패는 입양하지 않은 소유 프로세스로
보수적으로 유지한다. 일반 관측 실패는 실행 lease를 해제하지 않고 재관측하며,
정상 종료를 확인했을 때 해당 오류만 회수한다. 다른 미확인 오류를 지우지 않는다.


### 적용 뒤 커밋 관문 실패의 복구

#5785는 같은 사본의 605개 회귀와 정본 활성 확인을 통과했지만 신규 검사 파일의
직접 실행 진입점 누락으로 커밋 관문에서 거절됐다. 각인 실행기가 성공 로그 앞부분만
반환해 실제 거절 이유도 사라졌다. 긴 출력은 비밀 값을 마스킹한 원문 진단 파일과
머리·꼬리 발췌를 함께 반환한다.

프로그램 적용 서비스는 각인 실패 후 HEAD 불변이 확인된 경우에만 기존 바이트 복구와
게시 소유자를 통해 이번 적용을 되돌린다. 다른 수정과 충돌하거나 커밋 결과가 불명확하면
복구하지 않는다. 같은 후보 사본과 원래 기준은 보존하고 봉인·준비·활성 검사 영수증은
무효화하여 수정·재검사·재적용으로 돌아간다. 기존 계속 실행자가 staging 상태를 받아
자동 재개한다. package와 host 프로그램 모두 실제 Git 훅 거절→복구→수정→각인으로
시험한다. 관문을 건너뛰거나 검사 파일을 서비스가 몰래 고치지 않는다.


### 도구 재진입의 재개 문맥

#5786의 대화는 기존 적용 영수증을 찾았으나 HTTP 도구 재진입은 실행 ID만 가지고
들어와 재개 문맥을 잃었다. 새로운 스레드별 인계나 원장을 추가하지 않는다. 기존
Supervisor가 승인된 재개 문맥을 소유하고, repair_continuation.current가 같은
agent/task 바인딩에서 찾는다. 직접 호출과 HTTP 도구가 동일한 활성 작업을 참조한다.
다른 작업 ID와 종료된 작업은 이 문맥을 상속하지 않는다.


### 점검과 수정의 소유권 분리

부팅/일일 derived_freshness는 읽기 전용이다. 별도의 자동 빌드를 제거했다. #5788에서
부팅 점검이 각인 전 신규 파일을 모르는 Git 인덱스로 core_manifest를 재생성해,
검사·적용된 스크립트를 은퇴 목록으로 옮기고 수리 커밋을 막는 충돌을 확인했다.
불일치는 기존 수리/빌드 흐름으로 보고한다. 검사·파생·반영의 소유자는 그 흐름 하나이며,
건강 점검이 병렬 수정자가 되지 않는다. 별도 몸의 경로도 runtime_utils의 공통 판정으로
선택하여 다른 저장소의 활성 프로그램 목록을 가져오지 않는다.


### 코어 경로도 같은 종료 흐름을 사용한다

코어 여부는 수리 가능 여부와 동일하지 않다. program_boundary 한 곳의 변경 가능성과
활성화 방식에 따라 같은 사본·검사·적용·활성 확인·각인 흐름을 사용한다. 실행 중인
기반의 교체만 기존 외부 제어자가 맡는다. FAILED에서도 기존 소스 감시를 재사용하여
수정된 입력은 다시 시작하고, 동일 실패 지문은 반복하지 않는다. 새 재개 원장이나
별도 복구 프로토콜을 추가하지 않는다.

새 봉인 세대에 게시된 실행 바이트가 이미 포함되어 있으면 그 세대를 직접 사용한다.
세대에서 제외되는 검사 파일의 기준도 generation_store의 기존 판정을 재사용한다.
이미 흡수된 게시물이 삭제된 옛 세대의 심볼릭 링크를 계속 요구하지 않으며 게시
영수증은 유지한다. 사전 자동 경로는 공통 경로 해소점에서 매번 정하고, 명시적 경로
재정의는 존중한다. 없는 사전의 캐시도 해당 경로의 판본을 기록하여 다른 몸의 빈
사전이 원래 사전으로 되돌아온 뒤 남는 문제를 방지한다.


### 공통 수리 종료 처리

`program_apply.complete`가 등록 순수 부품·패키지·모듈·재시작 경로의 활성 검사·각인·각인 거절 복구를
소유한다. `program_host_apply.finish`, 패키지 `finish`, 일반 즉시 적용, 외부 제어자의
`commit_applied`는 이를 호출한다. 재시작 경로만 새 실행본을 만들기 전에 각인하고
활성 검사는 기동 뒤 수행한다. 검사 실행은 공통 `repair_candidate.activation`과
`red_apply._run_post_verify`, 전체 완료 판정은 `repair_policy.completion`을 사용한다.
판본 2 수리는 일반 프로그램·부품의 게시가 끝나도 이 완료 경로를 유지한다. 게시 성공을
이유로 일반 모델 검수로 전환해 이미 승인된 사본 기준을 다시 심사하지 않는다.
첫 종료와 재개 모두 `repair_policy.receipt_completion`으로 이 경로를 선택한다.
영수증만 남은 재개는 모델 전환·프롬프트 조립·과거 모델 검토 체크포인트를 거치지
않는다. 추가 내용 검토나 대기 중인 전달이 있으면 기존 검토 경로를 유지한다.
각인 거절 때 재시작 경로도 같은 정확한 이전 바이트 복구를 거쳐 staging으로 돌아가며,
적용이 취소된 결과를 제어자에 돌려주므로 실패한 후보로 워커를 바꾸지 않는다.

활성 검사 계획도 공통 사본 코드가 보존한다. apply 재시도에서 명령을 생략해도
기존 검사가 사라지지 않는다. 적용 후 빠진 읽기 전용 검사는 같은 apply에 추가할 수
있으며, 기존 검사를 제거하거나 바꾸거나 코드를 다시 적용하지 않는다. 추가 검사의
실패·결과 불명은 그대로 미완료다. 실행 세대에서 의도적으로 제외한 검사 파일은
게시물과 정본의 바이트로 대조하고, 실행 파일은 실제 선택된 판본과 계속 대조한다.
세대 제외 범위는 generation_store 한 곳의 기존 정의를 따른다.

재개 문맥의 적용 여부는 현재 수리 세션의 상태를 따른다. 복구된 staging 세션을
과거 applied 스냅샷이 계속 잠그지 않는다. 같은 실행에서도 기존 사본 소유권을
이어받아 고칠 수 있으므로 이 상태를 맞추기 위한 새 사용자 요청은 필요 없다.
재기동으로 대화 캐시가 비어도 사용자가 지정한 기존 작업은 저장된 대화 규정에서
찾는다. 같은 사용자·에이전트·프로젝트와 요청 관계를 확인하고 원래 기준을 보존한다.


검사 준비도 직접 apply와 셸이 같은 `repair_candidate.refresh`를 사용한다.
검사 시작 전에만 미수정 의존 파일을 정본에 맞추고 새 후보·환경으로 검사하며,
양쪽에서 다르게 고친 파일과 검사 도중 변경은 계속 충돌로 보존한다.
별도 동기화 명령을 알아야만 수리를 계속할 수 있는 조건을 제거했다.

MCP 재진입의 부모 실행 정보는 `_post_backend`가 요청 문맥에서 한 번 해소한다.
IBL 호출에만 부모를 실어 수리 셸이 drain 중 새 작업으로 거절되던 차이를 없앴다.
진행 중인 부모의 호출만 기존 접수 관문을 통과하며, 끝난 부모나 추측한 부모는 거절한다.


의미·사본·최종 검토가 원문 부족으로 보완을 요청하면 `final_evaluator.invoke`가
기존 보충 증거 시작점을 기록한다. 후속 실행의 원문 읽기는 같은 `prepare`의
recovered_evidence로 전달되어 일반 발췌 예산에서 다시 빠지지 않는다.
감독자의 최종 보완 분기를 거쳐야만 근거가 보존되던 차이를 제거하며,
승인 기준과 현재 사본 검사 id 연결은 유지한다.
