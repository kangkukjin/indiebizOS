## 목적과 범위

개발 실행자와 개발 대상의 수명을 불필요하게 결합하지 않는다. 사본에서 필요한 만큼 수정·검사하며 원래 요청을 이어가고, 완성된 수리 묶음의 활성화 때만 기존 적용 제어자를 사용한다. 정상 경로의 목표는 수리 요청 하나에 최종 적용 한 번이며, 실제 적용 실패의 복구와 사용자가 명시한 단계별 배포는 별도 사건이다.

이번 범위는 기존 REPAIR 경로의 격리·완료 판정·적용 연결이다. 새 검증 어휘, 별도 수리 엔진, 상시 검증 에이전트, 범용 개발 서버 UI, 코딩 앱의 자기 저장소 지원 전체는 만들지 않는다. 기존 스크립트·관용구와 직접 도구 호출은 허용하되 같은 쓰기 경계를 지킨다. 필요시 기존 모듈에서 공통 함수를 추출하고 1500줄 규칙과 backend 층 배정을 따른다. 기존 사용자 명령·소유자·모델·의식의 수리 권한 조건은 유지하고, 단계마다 사람 승인을 다시 받는 관문은 추가하지 않는다.

성공은 품질을 유지하면서 조기 적용·재기동·불필요한 새 실행 세션을 없애는 것이다. 비용 절감량은 아직 미측정이며 에피소드 수 감소 자체를 품질 향상으로 간주하지 않는다. 상위 기준은 [IBL 진화 목적](IBL_EVOLUTION_PURPOSE.md)이다.

## 반드시 지킬 불변조건

1. 실행자가 수리를 위해 바꾸는 소스·설정·문서·검사·파생 산출물은 모두 사본에 남는다. `backend/`라는 경로 이름만으로 범위를 한정하지 않는다.
2. 정본의 수리 대상 바이트는 사본 검증 완료와 적용 준비 판정 전에는 바뀌지 않는다. 운영 로그·수리 원장 등 기존 서비스가 기록하는 실행 상태는 이 금지의 대상과 구분한다. 에이전트에 운영 데이터 디렉토리 전체 쓰기 권한을 주는 예외로 쓰지 않는다.
3. 격리를 확보하지 못하면 쓰기를 거절한다. 정본 직접 쓰기·즉시 적용으로의 폴백은 없다.
4. 원래 수리 요청의 **사본에서 확인 가능한 필수 기준**을 모두 충족하기 전에는 적용을 예약하지 않는다. 실행자가 하위 기능 완료를 전체 완료로 바꾸거나 실패한 기준을 삭제할 수 없다.
5. 예약·즉시 적용·제어자 적용·재시도·제안 적용 모두 동일한 준비 판정을 통과한다. `verified:true`, 종료 코드 0, 모델의 “완료”라는 말 하나로 대신하지 않는다.
6. 검증한 대상·기준·검사·의존성이 달라지면 관련 근거와 적용 준비 판정은 낡는다. 미확정 영향 범위는 보수적으로 재검증한다.
7. 적용 직전에도 취소·소유권·정본 충돌·검증한 묶음의 일치를 확인한다. 적용은 실행자가 아닌 기존 신뢰된 적용 제어 경로가 소유한다.
8. 코드 반영, 활성 검증, 커밋, 전체 요청 완료는 다른 사실이다. 사본 검증 완료만으로 사용자에게 전체 완료라고 보고하지 않는다.

## 수리 작업의 시작과 유지

기존 `repair_sessions`에 요청의 `root_task_id`와 안정적인 작업 공간 식별을 연결한다. 에피소드·실행 task ID는 이 작업의 시도 식별자이며 사본 교체 사유가 아니다. 같은 root의 변경 소유자는 동시에 하나만 허용하고, 상태 확인 요청은 소유권을 가져오거나 별도 수정 실행을 만들지 않는다. 분류 태그나 RED 그랜트만으로 이 충돌 검사를 우회하지 못하게 한다.

사본은 기존 승인된 REPAIR 생성 경로로 만들고 라이브 미커밋 변경을 기준으로 가져오는 현 정책을 유지한다. 시작 기준과 수리가 만든 델타를 구분하여 남의 변경을 커밋에 포함하지 않는다. `git diff HEAD`만으로 수리의 변경 범위를 계산하지 않는다. 일반 코딩 앱의 clean HEAD 정책을 그대로 복사하지 않는다.

조사·편집·검사·실패 수정은 같은 작업 공간과 가능한 한 같은 실행자 세션에서 계속한다. 도구 완료·테스트 통과·기능 하나 완성은 세션 종료 조건이 아니다. 취소·외부 장애·문맥 한도·실행자 종료로 끊기면 같은 작업의 사본·근거·세션을 복원한다. 세션 복원이 불가능할 때만 새 실행자에 인계한다. 에피소드 기록의 분할은 허용하되 적용이나 새 개발 과제 생성과 결합하지 않는다.

기존 실행 예산·취소 기능은 유지한다. 예산 소진이나 외부 조건 미충족은 사본을 보존한 미완료 종료 사유이며, 부분 적용을 자동 허용하는 조건이 아니다. 숫자 상한을 없애 무한 실행으로 바꾸지 않는다.

## 쓰기 경계와 실행 환경

구현 시작 시 IBL write/edit/delete/move, patch/propose/apply, 셸·등록 스크립트, Python 등 직접 실행, 네이티브 실행자 파일 도구, 빌더, 패키지·사전 갱신 경로의 소유자를 표로 확인한다. 진입점마다 별도 정책을 복사하지 말고 공통 수리 컨텍스트로 사본과 허용 경로를 해소한다.

IBL 쓰기는 같은 사본을 대상으로 하고, 읽기·검색·셸 cwd도 사본의 변경된 내용과 의존성을 일관되게 보게 한다. 정본 비교는 명시적인 읽기 전용 조회로 한다. 현재처럼 일부 읽기는 사본, 다른 검사는 라이브를 보아 성공하는 혼합 상태를 허용하지 않는다. 실제 경로·심볼릭 링크·경로 탈출·삭제·이동·자식 프로세스에도 제한이 적용돼야 한다.

네이티브 실행자는 작업 사본과 과제별 실행 디렉토리만 쓸 수 있도록 실제 프로세스 경계를 사용한다. cwd 변경이나 셸 문자열 검사만으로 격리를 보장했다고 하지 않는다. 기존 `coding_process`는 참고·재사용 대상이나, 현재 네트워크 차단 및 네이티브 자체 샌드박스 정책을 그대로 복사하면 브라우저·문서 엔진 검사가 막힐 수 있다. 모델 통신과 테스트 통신의 소유자를 구분하고 필요한 테스트 서버·콜백 접근을 명시적으로 허용하는 실행 구성을 검증한다. 샌드박스를 이중으로 감싸지 않는다. 지원하지 않는 실행자는 읽기 전용 진단 또는 격리 가능한 도구 경로로 제한한다.

수리 실행자에 정본 Git 공용 메타데이터 수정 권한을 주지 않는다. 사본 생성·기준 기록·최종 pathspec 커밋은 기존 신뢰된 서비스가 맡는다. 사본의 중간 저장은 적용과 독립적이다. 외부 사용자 세션의 정본 작업까지 OS 수준으로 통제할 수 있다고 주장하지 않고, 그런 동시 변경은 적용 전 충돌 검사로 다룬다.

테스트는 임시 데이터·별도 포트·별도 출력 경로를 사용한다. 작업 사본 생성이 DB·토큰·프로세스·네트워크 격리를 자동 제공하지 않는다는 점을 유지한다. 운영 DB를 쓰기 가능한 심볼릭 링크로 연결하지 않는다. 의존성 공유는 읽기 전용으로 하거나 작업별 설치를 사용하며 빌드 캐시는 사본 영역에 둔다. 개발 서버 종료는 해당 수리가 소유한 프로세스로 한정한다.

정본의 파생물 신선도 수리는 사전 검사 부작용으로 수행하지 않는다. 기존 `sync_live_derived` 소비처를 조사해 사본 생성·검사와 적용 후 읽기 검사를 구분한다. 수리와 관련된 파생물은 사본에서 생성·검사하여 묶음에 넣는다. 정본의 무관한 선행 파손을 발견하면 근거를 남기고 원래 수리의 의존 관계를 판단하며, 몰래 고치거나 검증 통과로 덮지 않는다.

## 검증 완료와 적용 준비 판정

기준 정본은 기존 `criteria_contract`다. 새로운 요구사항 원장을 만들지 않는다. 기존 기준에 다음 구분을 보충한다.

| 구분 | 의미 | 적용 전 요구 |
| --- | --- | --- |
| 사본 확인 | 기능·회귀·타입·빌드·요청된 브라우저 행동 등 사본에서 실행 가능한 조건 | 필수 항목의 유효한 통과 근거 모두 필요 |
| 활성 확인 | 정본 코드가 실제 적재됐는지 등 반영 후에만 관찰 가능한 조건 | 실행 방법과 예상 결과가 준비돼 있어야 하며 통과로 미리 표시하지 않음 |

구분은 실행 편의를 위해 임의 변경할 수 없다. 사본에서 가능한 기능 검사를 “활성 확인”으로 옮겨 조기 적용하는 것을 막는다. 기존 의식·평가자가 원래 요청과 대조하고, 기준 변경은 기존 reframe 경로에서 근거와 이전 판본을 보존한다. 사용자가 목표를 바꾼 경우와 단순히 검사에 실패한 경우를 구분한다.

각 검사 근거에는 기존 증거 참조를 재사용해 다음 정보를 연결한다: 기준 ID, 검사 식별/판본, 대상 내용 지문, 입력·의존성·환경 식별, 실행 결과, 원문 참조. 상태는 통과·실패·미검증을 구분하고 오류 원인(제품/검사/환경/미확정)은 별도 진단 정보로 둔다. 검사 0건·skip·timeout·출력 소실은 필수 조건의 통과가 아니다. 기존 `시험.py`의 pytest 종료 코드 5 성공 처리와 `repair_gates._tsc_check`의 `passed=True, skipped=True`도 소비자가 올바르게 해석하도록 수리한다.

검사 범위는 [회귀 규약](REGRESSION_TESTING.md)에 따른다. 관련 검사를 먼저 수행하고, 필요한 종합 회귀·시스템 검사를 마친다. 매 수정마다 전수를 반복하지 않는다. 확정 가능한 독립 검사 실패는 한 번에 모으되, 준비 실패로 결과가 무의미해지는 후속 검사는 중단한다. 기존 시험·빌드 스크립트와 훅의 관문을 재사용하며, 새 스크립트에 훅 목록을 복제하지 않는다. 범용 레시피 UI와 전체 훅 재설계는 이번 완료의 전제조건이 아니다.

`apply` 요청은 바로 예약하지 않고 기존 감독·최종 평가의 경로에 사본 준비 판정을 요청한다. 기능마다 새 평가 에이전트를 돌리지 않는다. 기존 최종 평가의 관측 대상을 사본으로 연결하고, “사본 준비 완료”와 “정본 작업 완료”를 구분한다. 현재 평가가 도구 없는 방식인 점을 유지하여 부족한 실행 근거는 실행자에게 돌려준다. 사본 준비 승인이 정본 전체 완료 승인으로 소비되지 않도록 명시한다. 준비 평가를 받으려고 먼저 현재 턴을 종료하는 순환을 만들지 않는다. 기존 감독의 일시 정지·평가·보완 경로에 연결해, 거절되면 같은 실행이 계속되고 승인된 경우에만 적용 인계를 시작한다.

선행 실패가 있는 저장소에서 무조건 전부 깨끗해질 때까지 수리를 확대하지 않는다. 기존 회귀 규약과 근거 있는 기준선 비교로 이번 변경의 새 실패를 식별하고 미해결 선행 실패를 보고한다. 기준선 예외가 이번 수리의 필수 기능 조건이나 새 실패를 면제하지는 않는다.

판정은 두 책임으로 나눈다. 기계는 필수 검사 누락·낡은 지문·실패를 확인하고, 기존 평가자는 요구사항과 검사 근거의 의미적 부합을 판단한다. 이 방식도 임의 코드의 완전한 정당성을 증명하지는 않는다. 현재처럼 일부 기계 검사 성공을 전체 수리 준비 완료로 취급하는 공백을 닫는 것이 목표다.

## 검증한 변경 묶음의 고정

기존 수리 원장과 적용 잡에 준비 판정 참조를 추가한다. 개념 필드는 아래와 같으며 실제 직렬화 이름은 기존 스키마와 맞춘다. 에이전트가 전달한 Boolean이나 임의 JSON을 신뢰된 영수증으로 받아들이지 않는다. 증거·준비 판정·적용 원장의 쓰기는 기존 신뢰된 서비스가 소유하며 실행자에게 그 디렉토리의 직접 쓰기를 허용하지 않는다. 사본에서 수정한 검사기·게이트 코드로 현재 적용 정책을 바꾸지 못하게 한다. 게이트 자체의 수리도 현재 신뢰된 적용자가 검증한 변경으로만 활성화한다.

- 수리 root·소유자·사본 식별과 기준 판본의 해시.
- 추가·수정·삭제·이름 변경·파일 모드·필요한 바이너리를 포함한 변경 목록 및 내용 지문.
- 정본의 변경 전 기대 상태와 수리 델타의 기준. 시작 HEAD 하나만으로 대신하지 않는다.
- 사본 검증 근거의 참조와 환경·검사 지문, 기존 평가자의 준비 판정 참조.
- 반영 후 활성 확인 계획, 적용 시도 ID, 취소/무효화 상태.

기존 세션 파일 목록만 믿지 않고 사본의 실제 변경을 대조한다. 네이티브 셸·빌더가 만든 신규 파일과 파생물도 검토 묶음에 포함되어야 한다. 런타임 로그·비밀·빌드 캐시를 자동 포함하지 않는다. 보호 대상에 필요한 미추적 파일 누락은 준비 실패다.

검증이 산출물을 생성하면 먼저 산출물을 포함한 최종 후보를 고정하고 영향을 받는 검사를 확인한다. 검증 전 지문과 검증 후 바뀐 사본을 같은 근거로 승인하지 않는다. 시험 중 코드가 바뀌면 그 실행의 통과를 새 코드의 증거로 쓰지 않는다.

준비 판정 뒤 편집은 가능하지만 판정을 무효화하고 사본 개발로 돌아간다. 예약된 묶음은 변경 불가능한 스냅샷 또는 동일한 보장을 주는 잠금·지문 대조로 고정한다. 적용자가 지문을 확인한 뒤 가변 파일을 다시 읽는 사이에 다른 바이트가 들어가는 경쟁도 막아야 한다. 단순한 사전 해시 확인만으로 원자성이 확보됐다고 하지 않는다.

## 적용 경로의 변경

기존 `self:patch`와 제어자를 유지한다. 아래 단계는 책임 순서이며 별도 상태 머신을 하나 더 만들라는 뜻이 아니다. 기존 `repair_sessions`, `repair_continuations`의 phase/status와 준비 판정 참조로 표현하고 구현 문서에 실제 매핑을 남긴다.

| 단계 | 허용 동작 | 다음 조건 |
| --- | --- | --- |
| 사본 개발 | 편집·검사·재검사·근거 수집 | 필수 사본 조건이 충족돼 준비 평가 가능 |
| 준비 평가 | 후보 고정·검사 근거 대조·기존 의미 평가 | 유효한 준비 판정 생성 |
| 적용 대기 | 변경 묶음 보존·기존 제어자에 인계 | 소유권·취소·정본 충돌·묶음 지문 재확인 |
| 적용과 활성 확인 | 기존 백업·반영·필요한 재기동·활성 검증 | 실제 결과에 따라 완료 또는 복구 |
| 사본 보완 또는 종료 | 실패 근거로 같은 사본 수정, 취소/외부 막힘 보고 | 새 준비 판정 없이는 재적용 불가 |

`op_apply`의 즉시/지연 분기보다 앞에 동일한 관문을 둔다. 준비가 안 됐으면 누락 기준과 근거 참조를 반환하고 같은 턴의 개발을 계속한다. 아직 준비되지 않은 적용 요청 때문에 `defer`나 턴 종료를 시작하지 않는다. 제안 적용도 동일하게 처리한다.

`perform_scheduled_apply`와 `restart_red.apply_job`에서도 같은 판정과 고정된 묶음을 확인한다. 기존 잡 파일을 직접 넘기거나 이전 영수증을 재사용해 우회하지 못해야 한다. 적용 실패의 멱등 재시도는 같은 시도 ID로 기존 결과를 먼저 회수하며 결과 불명 작업을 무조건 재실행하지 않는다.

현재 `verify`는 라이브 동기화·파생물 생성으로 후보를 바꿀 수 있다. 준비 전에는 이를 수행할 수 있지만, 준비 이후 내용이 바뀌면 기존 준비 판정을 버리고 사본 검증으로 되돌린다. 예약 직전/실제 쓰기 직전에는 검증한 후보를 조용히 재구성하지 않는다. 최종 검증은 원문을 변경하지 않는 검사로 만들고 준비 함수와 분리한다.

정본의 동일 파일에 다른 변경이 생기면 덮어쓰지 않는다. 기존 기준·정본 현재본·수리 사본을 대조해 충돌을 반환한다. 영향을 주는 의존 파일이 바뀌면 사본 동기화와 필요한 검증부터 다시 한다. 관련 없는 외부 변경 때문에 무조건 전체 개발을 처음부터 반복하지 않는다.

적용은 기존 백업·복구 제어자를 사용하고 경로 한정 커밋으로 닫는다. `verify_cmd`/`active_verify_cmd`는 적용 후에만 가능한 검사와 정리로 좁히며, 사본에서 가능한 기능 구현·수정을 뒤로 미루는 수단으로 쓰지 않는다. 기존 스프레드시트 `--activate`처럼 검사와 커밋을 함께 수행하는 소비처도 새 판정의 소유권·실패 복구와 일치시키되 중복 커밋 실행기를 만들지 않는다.

정상 적용 뒤에는 활성 확인과 결과 보고만 남아야 한다. 기존 재개 경로를 사용할 수 있지만 새 개발 세션을 열어 이미 끝낸 조사를 반복하지 않는다. 활성 확인에서 실제 결함이 발견되면 같은 root의 복구 작업으로 되돌리고 새 준비 판정 후 재적용한다. 취소가 적용 도중 들어오면 현재의 안전한 원자적 작업/복구 경계까지 처리하고 후속 개발·재시작을 중단한다. 강제 종료로 부분 반영을 만들지 않는다.

재기동 필요 여부는 개발 완료와 별개다. 이번 구현은 조기 적용을 막는 것이 우선이며 동적 Python hot reload를 새로 만들지 않는다. 테스트 파일도 재기동 대상으로 잡는 거친 분류의 개선은 독립적으로 확인할 수 있으나 필수 순서 변경을 지연시키지 않는다.

## 구현 순서

1. **우회 경로와 부작용을 먼저 닫는다.** 임시 저장소에서 IBL 격리 실패 폴백, 사전 라이브 파생물 생성, 셸/직접 도구의 정본 쓰기를 재현한다. 지원 가능한 실행 경계를 연결하고 준비 단계 정본 무변경 검사를 통과시킨다.
2. **사본과 근거를 요청 전체에 연결한다.** 기존 root·소유권·criteria·검증 기록을 사용해 동일 사본의 개발을 유지한다. 필요한 데이터 필드는 기존 원장에 추가하고 실제 반환 계약을 소비자까지 연결한다.
3. **사본 준비 판정과 모든 적용 관문을 연결한다.** 즉시 적용·예약·제어자·제안·재시도를 함께 바꾸고, 아직 준비 안 된 apply를 같은 개발 세션의 보완으로 돌린다. 일부 진입점만 강화한 상태를 완료로 보고하지 않는다.
4. **재개·최종 확인을 정리한다.** 정상 경로에서는 적용 뒤 새 기능 개발이 없도록 하고, 결과 불명·롤백·취소·커밋 실패를 기존 경로로 복구한다. 기존 프롬프트와 문서의 상충 내용을 갱신한다.
