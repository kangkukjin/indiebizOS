## 4. R0 — 개명 충돌의 작은 수리

`update_agent`에서 설정 dict를 바꾸거나 role/note를 이동하기 **전에** 두 목적지와 대상 에이전트 신원을 함께 확인한다. 다른 에이전트와 표시 이름이 겹치거나, 이동해야 할 원본과 목적지 파일이 모두 존재하면 충돌로 거절한다. 내용이 같아 보여도 자동 삭제·병합하지 않는다. `role=`을 함께 보낸 개명도 같은 사전 확인을 거친다. 같은 이름으로 역할만 편집하는 기존 동작은 유지한다.

실패는 기존 함수의 예외 경로를 사용하되 충돌을 구분 가능한 예외로 표현한다. HTTP update는 409, IBL update는 `success:false`와 충돌 사유를 반환하도록 각 입구에서 매핑한다. 이는 기존의 조용한 삭제를 명시적 실패로 바꾸는 의도된 계약 수정이다. 경로·내용 등 민감한 데이터 전체를 오류에 포함하지 않는다.

사전 검사 후 목적지가 새로 생기는 경합에서도 덮어쓰지 않도록 대상 생성은 배타적으로 수행한다. YAML은 같은 디렉터리의 임시 파일을 완성한 뒤 원자 교체하며, 저장 실패 전에 원본 텍스트를 삭제하지 않는다. 자신이 만든 목적지만 식별하여 복구한다. 두 파일 중 하나라도 충돌하면 아무것도 바꾸지 않는 사례를 먼저 고정한다. 프로세스 강제 종료를 포함한 일반 다중 파일 트랜잭션의 완성은 이 작은 수리의 주장에 포함하지 않는다. 변경 중단 때 양쪽 사본이 남으면 보존하고 자동 재시도·정리로 원본을 지우지 않는다.

검증: role 충돌, note 충돌, role 이동 가능+note 충돌, 동일 내용 충돌, 개명과 role 동시 변경, 목적지의 경합 생성, 정상 개명, 같은 이름 편집, 저장 실패. 합성 디렉터리에서 YAML과 양쪽 role/note의 전후 지문으로 검증한다. 관련 새 시험은 `backend/test_agent_lifecycle.py`에 둔다. 코드 되돌리기는 가능하지만 원본 삭제 동작을 복원하지 않도록 R0은 이후 단계의 롤백과 분리한다.

## 5. R1 — 텍스트 파일 처리의 소유자를 한 곳으로

현재 `read_text/write_text`를 그대로 HTTP에서 호출하는 것만으로는 호환성이 성립하지 않는다. HTTP role 응답에는 이름도 필요하고, 설정 누락과 ID 누락을 구분한다. lifecycle 안에서 ‘프로젝트 설정 읽기 → 저장 ID 해소 → role/note 위치 → 읽기/쓰기’를 재사용한다. 파일 접근 결과에 해소된 이름을 함께 전달하여 HTTP가 YAML을 다시 읽지 않게 한다. 문자열을 기대하는 기존 IBL 호출은 기존 반환 계약을 유지한다. 범용 repository 클래스나 별도 저장 서비스는 만들지 않는다.

| 입력 상태 | 현행 HTTP note GET | 현행 role GET / 두 PUT | 수리 결정 |
| --- | --- | --- | --- |
| 설정 파일 없음 | 빈 note | 404 | 그대로 보존 |
| ID 없음 | 빈 note | 404 | 그대로 보존 |
| 대상 있음, 텍스트 파일 없음 | 빈 note | role GET은 빈 role, PUT은 생성 | 그대로 보존 |
| 빈 문자열 저장 | 저장 | 저장 | 그대로 보존 |
| 파싱 오류·실제 I/O 오류 | 500 | 500 | ‘대상 없음’으로 숨기지 않음 |
| 빈 YAML | 현재 HTTP는 `None.get`으로 500, lifecycle은 빈 agents로 해소 | 같음 | 빈 agents로 통일하여 GET note는 빈 값, 나머지는 404. 명시적인 오류 동작 수정으로 시험 |
| name 키 없음 | HTTP는 ID로 대체, lifecycle은 문자열 None 경로 가능 | 같음 | 새 정상 경로는 ID 대체. 예전 `agent_None_*`에 데이터가 있으면 조용히 무시·이전하지 않고 충돌/수동 확인 대상으로 표시 |

`kind`는 role/note 두 값으로 제한한다. HTTP와 IBL의 인증·소유자·삭제 승인 경계는 입구에 남긴다. 전체 에이전트 설정을 응답에 반환하지 않고 기존 공개 필드만 유지한다. 실제 네 함수의 응답 키(`note`, `role`, `agent_name`, `status`)와 오류 상세를 계약 검사로 고정한다. 중복 ID/불명확한 이름은 첫 항목을 임의 선택하는 대신 명시 실패로 처리하는 변경을 별도 시험한다.

R0의 update/delete/create와 텍스트 쓰기가 서로 다른 이름 해소 규칙을 갖지 않도록 같은 내부 해소를 사용한다. 그러나 이 단계에서 agent_cognitive·확장 전체를 동시에 옮기거나 저장 파일명을 바꾸지는 않는다.

검증은 `backend/test_api_agents.py`와 모듈명 lifecycle 시험에서 같은 합성 프로젝트를 HTTP와 IBL 양쪽으로 읽고 쓰며 바이트와 응답을 대조한다. 기존 `test_lifecycle_vocab_2026_10_05.py`의 입구 권한·생애주기 검사를 함께 실행한다. 데이터 형식은 유지되므로 코드 롤백 가능하다.

## 6. R2 — 단건 조회를 정본의 범위로 제한

목표 경로는 `routing_system._agent_info → agent_lifecycle의 단건 조회 → 지정 프로젝트 agents.yaml 한 번 → 공개 descriptor 투영 + runner_registry 상태`다. `_agent_info`는 공개 인자 해소·기존 오류 모양을 맡고 실제 프로젝트 읽기는 lifecycle에 둔다. 다른 프로젝트를 스캔하거나 flat/typed descriptor를 만들지 않는다. 전역 agent cache 무효화 이벤트도 새로 추가하지 않는다.

신원 계약은 저장 ID 우선, 해당 프로젝트 안에서만 이름 대체, 중복 매치 거절, project_id와 접두사의 불일치 거절이다. project_id 없는 bare ID는 임의 탐색하지 않는다. 현재 `ProjectManager.get_project_path`는 단순 경로 결합이다. 기존 glob 조회를 직접 경로 읽기로 바꾸면서 절대경로·부모 경로·프로젝트 경계 밖 심볼릭 링크가 새 읽기 경로가 되지 않도록 제한한다. 읽기 위해 프로젝트를 생성하지 않는다.

descriptor의 `id/type/protocol/description/actions/action_count/tags/project_id/agent_id/agent_name/active/running/capabilities`는 유지한다. `active`는 설정값, `running`은 현재 runner_registry라는 차이를 유지한다. 태그 순서를 새 의미 계약으로 삼지 않는다.

기존 `_build_agent_descriptor`의 순수 투영 부분을 공개 함수로 바꾸고, 계산한 capabilities를 인자로 받게 한다. lifecycle은 IBL 해소기를 호출할 수 있는 cognition 층이고 node_registry는 datastore 층이다. node_registry에서 cognition이나 ibl_access를 역방향 import하지 않는다. 기존 전체 목록 소비자는 자신의 현재 능력 매핑을 명시 인자로 넘기도록 바꾸되 이 단계에서 레지스트리 전체를 삭제하지 않는다. 반환 구조를 lifecycle에 또 복사하여 두 벌의 descriptor를 만들지 않는다.

능력 표시 규칙:

- `allowed_nodes`가 선언된 경우 기존 `resolve_allowed_nodes`를 사용한다. `None`/`[]`의 무제한 의미, 그룹 확장과 always_on은 재구현하지 않는다.
- 표시 capabilities는 현재 몸의 활성 사전과 해소된 집합의 교집합이다. 무제한이면 활성 노드 전체를 표시한다. 이는 현재 기어·계정·개별 도구 승인의 실행 성공을 보증하지 않는다.
- allowed_nodes가 없고 구 allowed_tools만 있으면 기존 도구→노드 매핑을 재사용한다. 이를 실제 IBL 허용 범위와 동일하다고 주장하지 않는다. 양쪽 설정의 부재는 IBL 해소기의 무제한 의미로 처리한다.
- 사전 읽기 실패를 빈 능력으로 숨기지 않는다. 현재 방식의 명시 오류로 남긴다. 능력 표시 때문에 활성 사전 원문은 필요할 수 있지만 전체 노드 descriptor·다른 프로젝트 목록을 생성할 이유는 없다.

확인 대상: create→info, 캐시를 데운 뒤 update→info, delete→info, 이름/role_description/allowed_nodes 변경, 같은 이름·중복 ID, 깨진 무관 프로젝트, 조회 대상의 깨진 YAML, 사전 읽기 실패, 실행 상태 변화, []/None/always_on/구 도구 설정. 현재 `test_routing_system.py`의 list_nodes mock은 새 경계의 합성 프로젝트 fixture로 교체하되 공개 식별 계약 assertion은 유지한다. 실제 접근 권한 검사는 별도로 기존 경로에 남긴다.

성공 기준은 다른 프로젝트 파일 읽기 0, flat/typed 집계 0, 변경 직후 최신 설정 반환, 공개 필드·식별·권한 보존이다. 조회 지연은 같은 합성 프로젝트 수·같은 캐시 조건에서 측정하며 파일 읽기 증가를 숨기지 않는다. 코드 롤백 가능, 저장 형식 변경 없음.

## 7. R3 — 실제 경로를 층 소속의 정본으로

검사기 한 번의 실행에서 경로표와 층표를 한 번 만들고 모든 판정 함수에 명시 전달한다. 모듈 이름별 수동 `LAYERS`와 surface 접두사 추론을 제거한다. `ORDER`, 디렉터리 대응(`datastore → data`), 조립 루트, 면제 부류, 동결 간선, 순수 코어 뿌리와 이음매 정책은 유지한다. 정책 목록과 위치에서 자동 파생되는 모듈 목록을 구분한다.

수집 시 동일 stem이 둘 이상이면 두 경로를 오류로 보고하고 그래프를 만들지 않는다. 정상 모듈은 정확한 층 폴더 바로 아래에 있어야 한다. 임의 새 폴더·루트의 일반 모듈·면제/조립 루트의 잘못된 위치는 실패한다. `_SKIP_DIRS`와 common/drivers/providers/channels의 별도 순수 코어 검사 경계는 보존한다. 검사 과정의 파일 읽기·구문 분석 실패도 정상 그래프 누락으로 삼지 않고 해당 경로의 검사 실패로 보고한다.

`find_violations`, `cross_layer_cycles`, `pure_core_leaks`, `private_symbol_leaks`가 모두 같은 경로 기반 소속을 사용한다. IBL 사적 심볼 보호 집합은 실제 ibl 폴더의 모듈과 기존 `SEAM_MODULES`에서 파생한다. 기본 함수 인자의 전역 정본 경로 때문에 임시 트리 검사가 정본 소속을 참조하지 않게 한다.

현재 self-test에는 합성 `ibl_registry.py`를 ibl 폴더에 놓고 수동 LAYERS의 data 배정에 기대는 사례와, 선언만 있고 파일이 없는 ibl_access 사적 심볼 사례가 있다. 새 검사에서는 합성 파일을 실제 의도한 층에 배치하고 가져오는 대상 파일도 만든다. assertion을 약하게 바꾸는 방식으로 맞추지 않는다.

의도된 정책 차이: 폴더 이동은 곧 층 소속 변경이다. 별도 배정표와 대조하는 독립 통제는 사라진다. 동일한 모든 보장을 주장하지 않는다. 이동 diff 검토와 의존 방향·순환·코어 검사가 남는다. 새 중앙 표나 파일별 선언문을 다시 만들어 이중 기록을 복원하지 않는다.

변경 소비자에는 `AGENTS.md`, `data/system_docs/{architecture,technical}.md`, `backend/boot_paths.py` 설명, `scripts/git-hooks/pre-commit`의 안내 문자열이 포함된다. 이번 설계에서는 현재 규칙을 미리 바꾸지 않는다. 파생 마커는 손으로 수정하지 않는다. 폰 번들 평면 import 방식도 변경하지 않는다.

검증: 변경 전후 실제 590개 소속·위반 간선·순환·코어 폐포·사적 심볼 위반 결과를 비교한다. 현재 기준은 층 가드 통과, 동결 간선 4, 순수 코어 폐포 18이다. 임시 트리로 새 정상 모듈 자동 편입, `api_`라는 이름의 ibl 모듈, 잘못된 루트/중첩, 동명, 직접/전이 역방향, 조립 루트 참조, 순환, common 허용, 새 ibl 모듈의 사적 심볼 월경, 구문 오류를 검증한다. 경로표는 검사 중 파생물일 뿐 저장·동기화하지 않는다.

기존 검사기의 main/self-test 및 선택된 소비자 검사를 실행한다. bootstrap 동작까지 바꾸거나 영향 범위가 넓어지면 회귀 규약의 전수를 적용한다. 초기 단계의 개발 시간 절감률은 미측정이다. 코드·개발 규칙을 같은 커밋으로 되돌릴 수 있으며 운영 데이터 이전은 없다.

## 8. R4 — 안정 ID 저장으로 개명과 데이터 이동 분리

R0~R2와 별도 단계다. 목표 형식은 일반 프로젝트의 `agent_roles/<stable-id>/role.txt`, `note.txt`, 프로젝트 agents.yaml의 `agent_text_storage: id-v1` 선언이다. 기존 이름 파일은 선언 없는 구 형식으로 해석한다. 파일 존재 여부에 따라 매번 두 저장소 중 임의로 고르는 방식이나 영구 이중 쓰기를 사용하지 않는다. ID는 경로 성분으로 검증하고 저장된 신원을 재발급하지 않는다.

계층 책임은 구분한다. 프로젝트 파일·템플릿/복원도 사용하는 **경로 및 형식 해소**는 기존 datastore `project_manager`에 두고, ID 선택·공개 동작은 cognition `agent_lifecycle`가 맡는다. datastore가 lifecycle을 import하지 않는다. 하위 파일 helper에 모델·런너·HTTP 책임을 넣지 않는다. R1의 파일 규칙을 또 복사하지 않고 해당 부분을 아래로 이동한다.

소비자 전환 범위:

- lifecycle의 create/update/delete/read/write, HTTP의 공통화된 경로, agent_cognitive의 역할·메모 두 실행 경로, prompt_composition의 실제/설명 표시.
- research_runner의 `_selected_agent`와 기본 역할 보존: 대화 제목·실행 ID와 저장된 템플릿 ID를 구분한다. 제목으로 역할 파일을 재탐색하지 않는다.
- api_config의 역할 생성·변경·내보내기·가져오기, project_manager의 템플릿 복사. 현재 agent_roles를 프로젝트 루트에도 복사하는 동작은 새 형식에서 반복하지 않는다. 구 템플릿 읽기는 유지한다.
- `extensions/conversation/my_conversations.py`의 이름 기반 role/note 읽기·쓰기·개명: 현재 정적 존재를 확인했으나 실제 활성 여부는 미측정이다. 이름을 유일한 저장 ID로 해소하는 어댑터로 연결하거나, 해당 구 실행 경로가 존재하는 배포에서는 프로젝트 이전을 보류한다. 새 쓰기를 구 파일로 우회시키는 호환은 금지한다.
- member_session의 ID 없는 임시 실행자는 이 이전 대상이 아니다. 임시 역할의 명시 출처를 전달하고 기존 동작을 보존한다. 시스템 AI 역할 파일도 그대로 유지한다. 모든 역할을 일반 프로젝트 파일로 강제 통합하지 않는다.

이전은 프로젝트 단위의 일회성 유지보수로 실시한다. 새 상주 이주 서비스는 만들지 않는다.

1. 파일·ID·이름 매핑과 구 형식 소비자를 읽기 전용으로 확인한다. 중복 ID/이름, 잘못된 경로, 소유가 불명확한 파일, 서로 다른 기존 목적지는 이전 불가로 분류한다. 모호한 프로젝트는 선언을 바꾸지 않는다.
2. 해당 프로젝트 쓰기를 멈춘 유지보수 구간에 `data/_backups/YYYY-MM-DD_이름/`으로 원문·설정·매핑·지문을 보존한다. 실행 중 역할 편집과 외부 확장 쓰기를 제어할 수 없으면 이전하지 않는다.
3. ID별 파일을 먼저 배타적으로 생성하고 바이트를 대조한다. 원본은 남긴다. 생성 실패/중단에는 구 형식 선언이 계속 유효하다. 재시도는 지문이 일치하는 자신이 만든 사본만 재사용한다.
4. 모든 파일과 입력 판본이 일치할 때 같은 디렉터리의 임시 YAML을 원자 교체하여 형식 선언을 마지막에 바꾼다. 중단 후에는 이 선언이 읽기 대상을 결정한다. 프로세스 내 잠금만으로 외부 쓰기까지 막았다고 주장하지 않는다.
5. 새 형식의 조회·쓰기·개명·복원·연구 역할을 확인하고, 일반 개명이 YAML 표시 속성만 바꾸는지 검증한다. 구 파일의 제거는 이 작업에서 자동 수행하지 않는다.

새 형식 선언 후 파일 누락은 데이터 손실/미완료로 보고하며 낡은 이름 파일로 자동 회귀하지 않는다. 새 쓰기는 새 형식 한 곳에만 한다. 되돌릴 때는 이전 뒤의 최신 텍스트까지 현재 이름에 역매핑해야 한다. 중복 이름 등으로 무손실 역매핑이 불가능하면 구 코드로 롤백하지 않고 데이터 보존 상태에서 수정한다. 코드 revert만으로 완료됐다고 보고하지 않는다.

인수: ID/역할/메모 바이트 보존, 개명 시 텍스트 이동 0, 충돌 시 무변경, 각 단계 중단·재개, 이전 후 편집→롤백, 템플릿 생성·백업 복원, 연구 제목 변경·선택 역할, 회원 임시 역할, 구 확장 쓰기 거절/연결. 개인 프로젝트 충돌 규모와 외부 배포 소비자가 아직 미확인이므로 실제 이전은 이 인수 조건 확인 후에만 실행한다.

## 9. R5 — 화면 조립의 계산 시점을 드러내기

기존 launcher_web_shell/app/render 및 하위 조각 모듈에 명시적 로드 함수를 둔다. 원격 조립자에서 한 번의 asset_snapshot 안에 호출하고, 폰은 필요한 shell 조각만, 회원은 기존 패널 조합만 가져간다. 단순 원문 자산은 기존 read_asset를 직접 사용하고 조합·변환이 있는 곳만 함수로 남긴다. 새 함수가 내부에서 옛 동적 상수를 다시 import하는 것으로 전환을 완료했다고 하지 않는다.

호환용 `__getattr__`가 필요한 동안에는 같은 함수 결과를 반환하게 하여 구현을 한 벌로 유지한다. 정적 검색·시험·빌드 소비자의 전환이 확인된 내부 이름만 제거한다. 외부 Python import 계약까지 확인하지 못한 이름은 호환으로 남기고 제거 완료를 주장하지 않는다. `program_modules.LiveModule`의 동적 export 지원은 별개 호환 계약으로 유지한다.

`surface_assets.asset_sources`는 composition Python 파일도 빌드 입력으로 봉인한다. 따라서 산출 HTML이 같더라도 구현 변경의 자산 판본·매니페스트는 재빌드해야 한다. 전후 동일성은 판본 ID가 아니라 동일 자산 입력의 HTML/JS 바이트·읽은 자산 집합·조립 순서로 비교한다. 활성화는 기존 화면 판본 게시 경로를 사용한다.

인수는 원격 원문/번역, display true/false, 폰/회원/lite, JS 순서, 진행 요청의 구 판본 고정과 새 요청의 새 판본, 번역 지문 불일치 시 원문, 손상 활성 판본의 기존 복구를 포함한다. `test_surface_assets.py`, `test_program_modules.py`, `test_surface_display.py`, `test_launcher_app_manual.py`, `test_launcher_lite.py`와 선택기가 고른 직접 소비자를 확인한다. 조립 전환 후 기존 브라우저 회귀도 실행한다. 바이트 비교만으로 브라우저 동작 전체를 검증했다고 보고하지 않는다.

복구는 코드와 활성 화면 판본을 맞춰 되돌린다. HTML 원문 파일을 손으로 고쳐 게시 상태를 우회하지 않는다. 같은 바이트를 만드는 단순화가 초기 성과이며 속도 향상은 별도 측정이다.

## 10. 검증·반영과 남은 범위

각 구현 단계는 [회귀 규약](REGRESSION_TESTING.md)의 선택기와 전이 소비자 검사를 따른다. 새 회귀는 `backend/test_<모듈>.py`에 둔다. 기존 assertion을 삭제해 통과시키지 않는다. backend 변경에는 Android 번들 재생성과 관련 어휘/몸 관문을 적용하고, 어휘 선언·반환 계약 설명을 바꾸면 원본·교재·빌더 결과를 같이 갱신한다. 공통 기능·범위 미확정·격리/부트스트랩 변경에는 규약의 종합/전체 검사를 적용한다.

운영 반영은 등록 순수 부품으로 확인된 경우에만 기존 무재기동 적용을 쓰고, 그 밖은 기존 외부 재기동 제어자가 검증된 후보를 반영·복구한다. 이번 설계는 임의 모듈 reload나 수동 keeper 표식 조작을 요구하지 않는다. 각 단계는 정본 main의 경로 한정 커밋, 필요한 활성 확인과 동작 검사를 마친 뒤 구현 완료로 기록한다.

성과 측정은 같은 요구의 수동 수정 위치·별도 동기화 규칙·파일 읽기 범위·실패 위치 추적을 먼저 본다. 시간·토큰을 비교할 때에는 모델/입력/캐시/검수 조건을 맞추고 전체 사용량·캐시·후처리를 분리한다. 이번 연구 에피소드의 토큰 수를 이 수리의 절감 기준으로 그대로 쓰지 않는다. 실제 모델 재실행은 표현·탐색 비용 비교에 필요할 때만 수행한다.

이번에 수행한 확인:

- [재현 스크립트](experiments/simplification_2026_11_03/verify_facts.py)를 `.venv/bin/python3 -B`로 실행했다. Git/코드만 읽고 `/tmp` 합성 프로젝트에서 캐시·개명·동명 수집을 재현했다. [결과 JSON](experiments/simplification_2026_11_03/facts.json)에 기준 HEAD와 결과를 보존한다. 미래 구현 후 재실행 결과가 바뀌는 것은 의도된 수리 효과일 수 있다.
- `python3 -B scripts/check_backend_layers.py` 통과: 수집 그래프 1,474모듈, 동결 간선 4, 순수 코어 폐포 18, 사적 심볼 월경 0. 1,474는 테스트/면제 부류도 들어간 그래프 수이며 층 폴더의 590과 다른 집계다.
- `python3 -B scripts/check_backend_layers.py --self-test` 통과. 이는 **현행 검사기**의 결과이며 제안된 경로 기반 검사기의 검증이 아니다.
- 제품 구현·pytest 전수·UI/폰/외부망·실제 데이터 이전·새 구조의 성능 측정은 수행하지 않았다. 운영 프로젝트 데이터와 비밀 설정은 재현 입력으로 사용하지 않았다.

미확인은 외부 import/확장 계약, 사용자 파일 충돌 규모, 새 구조의 실제 성능이다. 이들은 R0~R3의 국소 수리를 막는 이유가 아니며 R4의 실제 이전과 R5의 호환 제거 조건에 연결한다. 설계 문서의 존재를 구현·활성화·비용 개선의 완료로 읽지 않는다.
