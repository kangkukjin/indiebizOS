# 시스템 단순화 검토와 수리 계획

상태: 순차 집행 중. 아래 집행 기록에 완료 범위와 검증을 갱신한다.
작성: 2026-09-11. 검토 기준: 정본 main `05468cbd`.
대상: [Fable의 전체 반성](SYSTEM_REFLECTION_2026_09_11.md), 조사 기준 커밋 `9c1dfc8c`.

## 1. 판단

**복잡성이 IBL 주변 처리와 신구 구현의 공존에 쌓였다는 진단에는 동의한다. 다만 삭제 가능성과 위험도 판정은 상당 부분 고쳐야 한다.**

파일·객체·검사 횟수가 많다는 것은 조사할 신호다. 그것만으로 같은 책임의 중복이라고 결론낼 수는 없다. 특히 현재 선택하지 않은 프로바이더, 감독을 끈 호환 경로, 실행 결과의 보관과 모델용 표시, 사건 기록과 현재 상태 저장은 구별해야 한다.

단순화의 목표는 코드 줄 수보다 **판정의 소유자, 실제 전달 비용, 동시 작업의 격리, 유지보수 때 함께 고쳐야 하는 자리**를 줄이는 것이다. 문법·통화·정직성 표지·승인한 바이트만 공개하는 계약은 유지한다. IBL 전체가 건강하다는 판단도 이번 표본 검토로 언어 전체의 정확성을 증명했다는 뜻은 아니다.

## 2. 원문에서 수정할 핵심 주장

### C-2: 모든 THINK 턴의 카탈로그 비용이라는 진단은 잘못됐다

[consciousness_agent.py](../backend/cognition/consciousness_agent.py)의 `_load_prompt`는 130행에서 카탈로그를 붙이기 **전에** `_supervisor_prompt`를 저장한다. 238행에서 감독이 있으면 이 별도 프롬프트를 `supervisor.plan`에 넘기고, 감독이 없는 호환 경로에서만 전체 `_prompt`를 쓴다. 이 분리는 원문 기준 `9c1dfc8c`에도 있었다.

[supervisor_runtime.py](../backend/cognition/supervisor_runtime.py)의 `tool_context`는 액션 이름, 선택된 액션의 상세 계약, 필요할 때의 관용구 지도를 제공한다. 따라서 `build_environment(compact=True)` 한 줄을 바꿔 **모든 THINK 턴에서 약 9천 토큰을 절감한다는 주장은 철회**해야 한다.

호환 경로를 가볍게 할 여지는 있다. 그러나 이 경로는 도구 없는 원샷이며 `compact=True`는 액션 설명뿐 아니라 문법서도 바꾼다. 상세 조회가 가능한 실행자와 동일하게 취급하면 안 된다. 계획 출력의 `imagined_ibl`·달성 기준·액션 선택 품질까지 비교해야 한다.

현재 정본에서 같은 기본 인자의 `build_environment()`는 85,676자, `compact=True`는 27,579자였다. 이는 **문법·관용구를 포함한 전체 환경 문자열**이고, 원문의 카탈로그 단독 길이와 측정 범위가 다르다. 실제 모델 입력·캐시 읽기·비용은 따로 측정해야 한다. 문자 수를 고정 비율로 토큰 비용으로 환산하지 않는다.

### C-1: GoalEval은 조건부 호환 경로다

[conscious_supervisor.py](../backend/cognition/conscious_supervisor.py)의 `open_supervisor`는 설정이 꺼져 있거나 task/agent가 없으면 `None`을 반환한다(24~33행). 이 경우 [agent_pipeline.py](../backend/cognition/agent_pipeline.py) 723행의 GoalEval 분기에 들어갈 수 있다. 이 동작은 [anatomy.md](../data/system_docs/anatomy.md)에도 명시돼 있다.

정확한 표현은 **“정상 감독 턴에서는 대체됐지만 일부 진입점의 대체 평가로 남아 있다”**이다. 신원 보완으로 실제 빈도가 낮아졌는지는 별도 관측 대상이다. 사흘 동안 호출이 없다는 것만으로 삭제하지 않는다. 감독 비활성화의 의미와 신원 없는 내부 호출의 처리부터 정한다. 전부 fail-closed로 바꾸는 것은 단순 삭제가 아니라 동작 변경이다.

`agent_goals`도 이름이 비슷하다는 이유로 같은 루프로 취급하지 않는다. 장기 goal의 승인·중단·라운드·비용 상한과 턴 최종 검수의 책임을 대응시킨 뒤 이관 여부를 정한다.

### C-5: 조건 지문과 실행 카운터는 같은 질문이 아니다

[conscious_supervisor.py](../backend/cognition/conscious_supervisor.py) 185~207행은 목표·해결되지 않은 문제·관련 작업의 상태를 검사한다. `_take_pending`은 조건이 있으면 이를 사용하고, 없는 옛 형식에만 revision을 대체 기준으로 쓴다(409행).

다른 주소를 성공적으로 읽었다고 실패한 주소에 대한 수리 지시가 무효가 되지는 않는다. 반대로 그 주소가 실제 회복됐다면 지시는 무효여야 한다. 기존 행동 시험이 이 두 경우를 구분한다. 따라서 **조건 지문을 `exec_revision` 하나로 대체하는 제안에는 반대**한다. 신선도 판정의 소유자를 한 곳에 모으고, 모든 생산자가 이 계약으로 옮긴 뒤 옛 형식을 제거하는 것이 맞다.

예산도 누적 총량·호출 중 사용량·단계 배정·최종 재검수 예비분이 각각 다른 질문에 답한다. 원천 사용량의 중복 합산은 없애되, 현재 지원하는 hard 상한과 재검수 예비분을 `soft + max_repairs`로 삭제하지 않는다.

### C-8: `_PriorityLock`은 불필요한 증류 잠금이 아니다

[consciousness_agent.py](../backend/cognition/consciousness_agent.py) 549~600행은 제공자별 호출 슬롯과 전경 우선권을 관리한다. 일반 `BaseProvider`에는 4개, 그 밖에는 1개 슬롯을 준다. 배경 워커가 하나여도 전경 분류·계획과 경합할 수 있다. 삭제 후보에서 제외한다. 위치·이름을 정리할 수는 있지만 동시 실행 상한과 우선권은 보존한다.

REPAIR grant 중복은 발급·갱신·회수 시점을 맞춘 공통 함수로 추출할 수 있다. `_collect`의 평행 리스트도 소비자가 요구하는 정보·순서·원문 보존을 확인한 뒤 같은 사건에서 파생하도록 한다. 둘 다 “위험 없음, 각각 10줄”을 약속할 근거는 없다.

### S-3·S-7·S-8: 현재 미사용과 삭제 가능한 죽은 코드를 구분해야 한다

- [providers/__init__.py](../backend/providers/__init__.py)의 팩토리는 Anthropic·Ollama·OpenRouter를 실제 등록하고 있다. 프론트의 온보딩·설정·Ollama 제어에도 소비처가 있다. 현재 모델 설정이 가리키지 않는다는 이유로 지원 기능을 삭제하지 않는다. 필요하면 지연 import와 선택 기능의 의존성 분리로 부팅 비용을 줄인다.
- 프론트 호출자가 없다는 것만으로 공개 API의 소비자가 없다고 증명할 수 없다. 폰·MCP·외부 도구·저장된 스크립트도 확인해야 한다. 실제 폰 코드에는 `/business/sync/merge`, `/health/sync/merge` 호출이 있다. 공통 내부 구현은 가능하지만 기존 URL·도메인별 인증·스키마는 보존한다.
- [write_ledger.py](../backend/base/write_ledger.py)는 `[self:body]{op:"writes"}`라는 명백한 소비처가 있고, 이미 8MB 기준 1세대 회전을 한다. 이를 쓰기 전용 원장 삭제 묶음에 넣는 것은 잘못이다. `boot_profile`·`body_ask_log`의 보존 정책은 별도로 다룬다.
- `api_engine`의 IBL router 참조 0은 확인했다. 그러나 [system_tools.py](../backend/cognition/system_tools.py) 1003행의 직접 실행 경로와 `data/api_registry.yaml`의 pipeline 선언은 살아 있다. IBL 사전에서의 비노출과 전체 시스템에서의 도달 불가는 다르다.

### T-3·2.4: 0이라는 감사 결과만으로 고장이나 불필요함을 판정할 수 없다

가이드 은퇴는 이미 [component_lifecycle.py](../backend/cognition/component_lifecycle.py)의 `_retire_guide` 및 실행 분기에 구현돼 있다. [lifecycle_policy.yaml](../data/lifecycle_policy.yaml)의 정책은 신생 유예 30일·최근 신호 60일·candidate 이후 은퇴 대기 90일이다. 원문의 25일 미주입 관측은 이 정책의 미집행을 입증하지 않는다. 참조가 생존 신호를 만드는 방식에 문제가 있는지는 별도 확인해야 한다.

감사 카덴스의 공통화에는 동의한다. 그러나 `flags=[]`는 깨끗한 성공 외에도 실행 생략·관측 부족·실패 뒤 남은 옛 결과일 수 있다. **“0건 3회면 무조건 감쇠”는 채택하지 않는다.** 성공·검사 범위·입력 변경 여부를 함께 확인하고, 비용이 큰 조언성 감사에만 상한 있는 감쇠를 적용한다. 커밋 정합성·부작용 승인 관문은 별도다.

### I-1·I-3: 중복 판정은 줄이되 서로 다른 경계는 남겨야 한다

[model_result_view.py](../backend/cognition/model_result_view.py)의 `project_result`는 이미 모델용 진입점이며 그 안에 여러 축소가 겹친다. 표시 정책을 이곳으로 모으는 방향에 동의한다. 다만 원문 보관·실행 중 메모리 스필·단계 상태 요약·모델 표시·전송 상한을 기능 하나로 없앨 수는 없다. `display_delivery_budget`은 선언된 표시를 공급자의 옛 16K 상한이 다시 자르지 않도록 하는 조정 함수다. 언제나 추가 절단하는 여섯 단계라는 묘사는 부정확하다.

T1은 정적 검사·실행 초크포인트·pipeline 입구에서 겹치는 경로가 있다. T2와 분기별 횟수는 다르며, 직접 pipeline 호출·resume·블록·each는 입력 문맥도 다르다. 검사 결과를 재사용하려면 정규화된 AST, 들어오는 통화, 변수 타입, 사전 버전, 검사 종류를 묶어야 한다. `typecheck`의 `abstained`는 통과 증명이 아니므로 단순한 `checked=True`로 하위 검사를 생략하지 않는다.

### S-1·S-2: 대체 구조의 비용이 빠져 있다

blue/green을 “9겹에서 2겹”으로 계산하는 데는 반대한다. [api.py](../backend/api.py)의 lifespan은 World Pulse·채널 폴러·창고 폴러 등을 시작한다. 프로세스를 둘 띄우면 작업의 중복 실행, 공유 SQLite의 마이그레이션, 외부 세션·장치·포트 소유권, 모델 메모리, 진행 중 스트림 인계 문제가 생긴다. `/health` 응답만으로 이 준비 상태를 보장할 수 없다.

단일 이벤트 저장소로 옮겨도 신원은 스레드·프로세스·HTTP 경계를 건너야 한다. 그리고 대화 이력·과제의 현재 상태·검수 증거·쓰기 이력의 수명과 실패 허용도가 다르다. **공통 사건 식별자와 조회 통로부터 정리하고, 저장소 물리 통합은 나중에 판단**한다. 내부 저장 모델 변경이 자동으로 IBL 언어 개정인 것도 아니다. 외부 계약이 변하는지를 따져야 한다.

### 수치·위험도·나머지 항목의 정정

- 164액션, op를 가진 74액션, op 값 381개는 현재 정본에서도 확인했다. 평균은 `381 / 74 = 5.15`로, 원문의 4.3은 계산 오류다. keeper 규약의 “09-17 개정”은 제공된 작업 규약의 “08-17 개정”과 맞지 않는다.
- `execute_pipeline` 915줄은 AST로 확인했다. 상태 추출에는 동의하지만 순서·예외·취소·변수 수명이 얽혀 있어 I-5의 위험도는 **중간**으로 올린다.
- I-6: executor 생성·컨텍스트 승계 규약은 공통화할 수 있다. 중첩 작업을 하나의 전역 풀로 몰면 자식 작업을 기다리는 교착이나 작업군 간 기아를 만들 수 있다. 공통 팩토리와 단일 풀은 다르다.
- I-7·I-8: 공통 스캐너 후보에는 동의하되 후순위다. 현재 파라미터 경로는 JSON5→JSON→relaxed이며, 비표준 escape와 CAPTURE 때 우회한다. 단순한 두 파서 경쟁이라는 설명부터 수정한다. 소스 위치·이스케이프·오류 위치까지 비교해야 한다.
- I-9·S-10·T-7: 스크래치·스텁·일회 스크립트 정리는 후보별로 타당하다. 동적 import·설정 등록·수동 복구·외부 진입점을 확인한 작은 집합만 삭제/격리한다. 원문의 “참조 0 함수 12개” 전체를 이번 검토에서 독립적으로 입증하지는 않았다.
- I-10: 문서 마커 전체 재생성에 동의한다. appview 검사를 별도 모듈/명령으로 분리해도 상위 빌드와 CI가 필요한 검사를 계속 호출해야 한다. 결합 제거가 검사 누락이 되면 안 된다.
- C-6·C-7: 증류의 카덴스·재시도·사용량 계측과 제공자 생성은 공통화 후보다. 저장소별 병합 의미·원문 근거·모델 기능·상태 격리는 어댑터 책임으로 남긴다. 겉모양만 같다고 LLM 프롬프트까지 강제 통합하지 않는다.
- T-1·T-2·T-4: 의미 계약과 예제를 한 곳에서 관리하고 역할별 교재를 파생하는 데 동의한다. 세 문서의 문장 교집합이 작다는 것은 모순의 증거가 아니다. 짧은 교재·전체 명세·도메인 가이드의 독자와 목표는 다르다. 권한·가용성 필터와 도메인 고유 검수 기준을 보존한다.
- T-5·T-6: 무참조 설계 문서는 완료 상태와 미래 복구 가치를 보고 정리한다. 사건 이름 시험은 원인의 재현 기록일 수도 있다. 같은 불변조건의 사례를 주제별로 모으되 케이스를 지우지 않는다. `__main__` 287개 삭제를 별도 수리 프로젝트로 만들 이유는 약하다.
- S-4·S-5·S-6·S-9: 공통 UI·설정 해석·서비스 계층 추출은 타당한 후속이다. 설정창·로그창은 용도와 권한부터 비교한다. 원격 React 전환에는 인증·폰·정적 번들 부재 경로가 포함된다. 모델 파일 통합은 현재 `model_resolver`를 소유자로 두고 명시적 이전 절차를 설계한다. 폴백은 기능·정책별로 검토하며 일괄 제거하지 않는다.
- 성장 규율에는 동의한다. 기존 계약 시험·정본 문서·감사 정형에 합류하는 것을 기본값으로 삼는 것은 현재 규약과 양립한다. 이 작업 습관을 시작하기 위해 별도의 승인 절차를 만들 필요는 없다.

## 3. 집행 계획

아래 각 묶음은 별도 커밋으로 검토 가능하게 한다. 정상 계약을 먼저 적고, 현재 처리와 변경 처리를 같은 입력으로 비교한다. 회귀가 나오면 그 묶음의 변경을 되돌릴 수 있게 한다. 대규모 파일 이동과 동작 변경을 한 커밋에 섞지 않는다.

### 0단계 — 실행 경로와 비용 기준선

대상: `agent_pipeline`, `consciousness_agent`, `conscious_supervisor`, 기존 episode/model 계측.

1. 감독 계획·호환 계획·반사/EXECUTE·재규정·최종 검수·보완 경로를 구분한다. supervisor 미생성 사유도 `disabled / no_task / no_agent`처럼 기록한다.
2. 기존 사건 원장에 입력 크기·실제 input/cache/output 사용량·결과 조회 횟수·각 경로 선택을 붙인다. 새 상주 감사나 상태 파일은 만들지 않는다.
3. 비교 표본은 짧은 조회, 긴 조사/보고서, 부분 실패 후 재개, 동일 에이전트의 동시 두 작업, 스케줄·위임·MCP 재진입, 감독 비활성화로 구성한다. 외부 쓰기는 시험용 어댑터로 대체한다.

완료 기준: 각 공개 진입점의 평가·표시 경로가 설명되고, 동일 입력의 비용과 동작을 재현할 수 있다. 고정된 사흘 관측 대신 **경로별 시험과 실제 대표 실행의 확보 여부**로 다음 단계를 결정한다. 이번 검토의 11개 시험은 이 기준선의 일부이지 전체가 아니다.

### 1단계 — 확인된 작은 정리

대상: `tool_loader`, `system_tools_ibl`, 관련 도움말·은퇴 계약, 확정된 스크래치.

1. 모델 스키마의 무효 `verbose`를 제거한다. 앱 원형 결과는 이미 `call_channel == "app"` 분기로 결정되므로 그 계약을 유지한다. 저장된 옛 호출의 추가 인자는 이행 기간 동안 오류 없이 무시할 수 있게 한다.
2. 미사용 `diet_envelope` import 세 곳과 `verbose:true`가 옛 전체 모양이라는 낡은 주석을 정리한다. 은퇴 계약과 오류·도움말까지 한 번에 맞춘다.
3. event 스텁·스크래치·`.bak`·고아 스크립트는 각 소비처를 확인한 것만 정리한다. 제공자·공개 라우트·원장은 이 묶음에 넣지 않는다.
4. 항상 제공되는 가이드 색인의 정보·권한 범위가 같음을 확인하면 중복 주입을 제거한다. 기존 `execution_map`을 남길 기준으로 삼는다.

완료 기준: 모델 스키마에 무효 옵션이 없고, 결과의 원문 회수·앱 렌더·옛 호출 입력 수용이 보존된다. 삭제한 항목별로 등록·import·수동 실행 경로의 확인 근거를 남긴다.

### 2단계 — 결과 표시의 소유권 정리

대상: `model_result_view`, `ibl_envelope`, `system_tools_ibl`, provider 결과 어댑터, 기존 표시 정책.

1. 실행 원문을 먼저 보관하고, 모델 경계에서 만든 사본에만 표시 정책을 적용한다. 앱·변수·후속 IBL 연산은 전체 통화를 받는다.
2. `project_result`가 단계 요약·최종 미리보기·진단 보존·`result_ref`를 조립한다. 기존 `envelope_preview`를 확장해 **표시** 임계값을 모은다. 보관 TTL·실행 메모리 스필·전송 상한은 별도 목적임을 선언한다.
3. provider 3벌의 전달 처리를 공통 어댑터로 옮긴다. 이미 투영된 결과를 다시 임의 절단하지 않고, 전송 상한 초과 시에도 오류·출처·원문 참조를 보존한다.
4. `tool_evidence`와 감독 작업대의 보관 소유권을 확인한다. 활성 턴·재개 가능 작업·미승인 공개 대기물·유효한 증거 참조를 보호하는 청소 정책을 기존 수명 체계에 추가한다. 용량만 보고 지우지 않는다.

완료 기준: 큰 성공·큰 오류·부분 실패·중첩 final_result·병렬 결과에서 상태와 정직성 표지가 유지되고, 원문을 재실행 없이 회수할 수 있다. 전체 원문을 해시/바이트로 비교한다. 같은 대표 작업에서 **추가 조회 왕복을 포함한** 모델 입력 비용이 줄어야 한다.

### 3단계 — 턴 신원과 지시 전달 정리

대상: `thread_context`, `model_call_context`, `supervision_bus`, `steer_inbox`, `reframe`, MCP/HTTP·워커 진입점.

1. 실행 신원의 공통 계약을 정의한다. agent/task/run/turn의 의미와 수명을 분리하고, owner와 감독 역할의 별칭을 명시한다. process 내부 저장 방식만 contextvar로 바꾸면 경계 전파가 끝나는 것은 아니다.
2. 먼저 agent 하나만 키로 쓰는 조향·재규정 통로를 작업 단위로 격리한다. 현재 감독 bus는 `(agent, task)`를 쓰지만 조향·재규정은 agent 키여서 같은 에이전트의 동시 턴에서 충돌할 수 있다.
3. 공통 전달 봉투에 발신 유형, 대상 작업, 순번, 만료, 적용 조건을 둔다. 사용자 조향·의식 재규정·감독 지시의 우선순위와 의미는 유지한다. 사용자 지시가 자동 감독 조건의 변화만으로 폐기되지 않게 한다.
4. 감독 없는 턴도 사용자 조향을 받아야 한다. 큐를 Supervisor의 수명에 종속시키지 않고 감독은 소비자로 참여한다. 취소는 즉시 중단 신호로 유지한다.
5. 모델 사용량은 호출 식별자에 따라 한 번 계상하고 단계별 수치를 파생한다. 조건 지문은 유지하며 옛 revision 전용 지시는 생산자 이전 후 제거한다.

완료 기준: 같은 agent의 두 작업을 동시에 돌려 조향·재규정·비용·원문 참조·종료 정리가 섞이지 않는다. MCP 재진입과 풀 스레드 재사용에서도 신원이 승계·복구된다. 무관한 진척은 유효한 지시를 지우지 않고 실제 회복은 오래된 지시를 지운다. hard 상한·최종 재검수 예비분도 보존된다.

### 4단계 — 평가 경로의 명시적 이관

선행조건: 0단계의 경로 표와 3단계의 신원 계약.

1. 정상 감독, 명시적 감독 비활성화, 내부 원샷, 신원 없는 호출 각각의 검수 동작을 표로 확정한다.
2. GoalEval 부품의 실제 소비처를 분리한다. 달성 기준·시각 산출물 수집·평가 입력은 필요하면 공통 모듈로 옮기되 기존 이름의 일괄 재수출을 새 결합으로 남기지 않는다.
3. 호환 호출을 새 경로로 옮기고 동일한 완료/미완료/불명/검수 미실행 상태를 확인한 뒤 구 루프·설정·재규정 배선을 함께 제거한다. 아직 대체되지 않은 경로가 있으면 해당 루프는 남긴다.
4. 장기 `agent_goals`는 활성 목표·승인/중단 API·스케줄 상태를 조사하고 pursuit와의 책임 대응안을 별도로 결정한다.

완료 기준: 이관한 모든 진입점에서 검수 누락·중복 검수·의도하지 않은 거절이 없고, 자동 기억·공개 대기물 처리까지 같은 결과를 낸다. 사용자가 선택할 수 있는 감독 비활성화를 조용히 무효화하지 않는다.

### 5단계 — 감사·문서·시험의 누적 방식 정리

대상: 기존 `weekly_audits`, `component_lifecycle`, `world_pulse_health`, `iblbuild_docs`, 문법 교재·가이드.

1. 감사 실행 시각·카덴스·실패 격리를 기존 레지스트리로 모은다. `성공-깨끗함 / 발견 / 생략 / 실패 / 관측 부족`을 구분한다. 상태 저장 파일 수 감소는 동시 쓰기·독립 복구 계약을 확인한 뒤 진행한다.
2. 비용이 큰 감사만 입력 지문이 같고 충분한 범위를 연속 검사한 경우 최대 주기 이내에서 감쇠한다. 소스 변경·실패·새 발견 때 원래 주기로 복귀한다. 빌드 정합성·부작용 관문은 감쇠 대상에서 제외한다.
3. 가이드가 은퇴 후보가 안 되는 이유를 현재 참조·최근 사용·유예로 설명한다. 부풀린 참조가 있다면 그것부터 수정한다. 기존 수명 정책의 기간을 미사용 25일이라는 이유만으로 줄이지 않는다.
4. 문법의 의미 계약·예제는 정본에서 파생하되 compact/full의 교육 목적은 유지한다. 문서 빌드는 마커 구간을 통째 생성하도록 바꾸고, 수동 산문 표현에 대한 정규식 의존을 줄인다.
5. 손대는 주제부터 사건 시험을 기존 주제 시험에 합류시킨다. 사례·과거 실패 식별자는 유지한다. 완료된 docs의 결정은 설계 정본에 반영하고, 참조 갱신과 함께 필요한 문서만 archive로 옮긴다.

완료 기준: 감사 실패/생략이 정상 0건으로 집계되지 않고, 입력 변경 시 검사가 재개된다. 문법/가이드 합류 후 핵심 예제와 동작 계약이 빠지지 않는다. 시험 파일 수 감소를 성공 지표로 사용하지 않는다.

### 6단계 — 엔진 구조와 표면의 후속 정리

앞 단계와 독립적으로 검토할 수 있지만, 의미를 바꾸는 대규모 일괄 작업으로 묶지 않는다.

| 순서 | 작업 | 완료 조건 |
|---|---|---|
| 6a | `PipelineState` 추출 → 실패·스필 함수 추출 → 실제 소비처의 직접 import로 정리 | 순차/병렬/폴백·resume·부분 실패·취소·턴 변수·진행 티켓이 동일 |
| 6b | 비용 측정 후 불필요한 T1 호출 제거; 일반 캐시는 근거가 생길 때 도입 | 직접/중첩 진입점의 검사가 남고, abstained/문맥 변경은 재검사. 부작용 전에 같은 오류를 거절 |
| 6c | executor 생성·문맥 승계 공통화, 역할별 풀 격리 | 중첩 each/parallel·타임아웃·취소·실행 중 자식 작업에서 교착/비용 누락 없음 |
| 6d | 제공자 생성 공통화, API registry의 생존 경로 이관 또는 위치 정리 | 선택 가능한 모델과 등록된 호출의 동작 보존. 이관이 끝난 옛 구현만 삭제 |
| 6e | 설정/로그/메시지의 공통 컴포넌트와 원격 React 표면 | 데스크톱·폰·원격 인증·lite/번들 부재 경로의 기능 비교 통과 |
| 6f | 모델 설정을 `model_resolver` 중심으로 정리, sync/WS 서비스 추출 | 기존 설정 읽기·이전·복구, 외부 URL·도메인별 권한·스트림 취소 보존 |
| 6g | 스캐너·파라미터 파서 공통화 | 골든 코퍼스에서 AST·값·원문 위치·오류 위치가 같음. 차이는 언어 변경 여부로 별도 판정 |

6a/6b/6c/6g는 각각 중간 이상 위험이다. 함수 추출이라는 형식만으로 기계적 저위험이라고 부르지 않는다.

### 보류 — blue/green·원장 물리 통합·대용량 정리

- **재기동**: 먼저 기존 상태 전이·중단 이유·타임아웃의 소유자를 정리한다. blue/green은 후보 프로세스가 폴러·스케줄·외부 쓰기를 수행하지 않는 준비 모드, 단일 실행 소유권과 이전 차단, DB 호환성, 메모리 상한, WS/턴 종료 대기, 실패 시 복귀를 검증한 별도 실험 뒤 결정한다. 살아 있는 프로세스가 죽은 뒤 스스로 마무리해야 하는 단계를 만들지 않는다.
- **원장**: 동일한 event/call/run/task 참조와 한 번의 조회로 연결되는 뷰를 먼저 만든다. 장기 상태·불변 사건·증거 blob·대화 이력의 소유권과 수명을 유지한다. 물리적 단일 스트림은 실제 다중 쓰기 실패와 복구 비용이 이를 정당화할 때 검토한다.
- **디스크**: `showcase_stage`·`_backups`·spill은 소유자·활성 참조·재생성 가능성별로 보존 목록을 만든다. 특히 백업 실삭제는 기존 규약대로 사용자가 결정한다. 27GB와 528KB 로그를 같은 긴급도로 다루지 않는다.

## 4. 최초 검토의 검증과 집행 규칙

### 0단계 — 경로·입력·조회 계측

### 3단계 — 작업별 조향·재규정 격리

- 실행 키는 `thread_context.execution_key` 한 곳에서 만든다. None(문맥 승계)과 빈 값(명시적 무신원)을 구별한다. 감독·모델 호출·원문 보관·재규정·조향이 같은 agent/task 계약을 사용한다.
- 조향의 별칭 등록·종료 정리는 `cognitive_stream`의 task_scope가 소유하며 감독 비활성화·강제 역할에서도 동작한다. WebSocket은 연결별 작업 ID를 전달하고, HTTP 조향은 대상이 모호하거나 종료됐으면 409로 알린다. 서로 다른 작업을 대신 골라 주지 않는다.
- 재규정은 task별 채널과 객체 일치 종료를 사용한다. MCP 워커는 해당 작업의 신원·궤적·비용 원장을 채택하고 호출자 상태를 복원한다. 같은 작업의 중복 채널은 기존 채널을 덮지 못한다.
- 사용자 지시에는 source/target/sequence/expires_at/conditions를 명시한다. 사용자 지시는 감독의 조건 변화로 버리지 않는다. 감독 지시의 생산자는 모두 조건 지문을 사용함을 확인해 revision 전용 유효성 폴백만 제거했다. revision은 관측 메타로 남는다. hard 상한·최종 검수 예비분·원천 사용량 계상은 유지한다.
- 원문 보관 신원은 구분자 결합 대신 구조화한 쌍을 해시한다. 구분이 명백한 옛 경로는 호환한다. 콜론 포함 옛 신원이 충돌할 수 있는 경로는 자동 채택하지 않으며 파일은 삭제하지 않는다.

| 진입 조건 | 평가 동작 |
|---|---|
| 감독 존재·활성·최종 응답 있음 | 감독의 최종 검수·보완·공개 대기물 처리 |
