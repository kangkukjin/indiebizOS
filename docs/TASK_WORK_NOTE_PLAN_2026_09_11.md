## 3. B — 요약 오류를 함께 보고하고 실패 비용도 누적

`pursuit_bind._validate_answer`가 각 요약 필드를 기존 `pursuit_ledger.validate`로 검증하고
잘못된 필드의 오류를 모아 보고한다. 제한의 정본은 그대로 한 벌이다. JSON 전체를 한 번
재요청하는 기존 경로를 사용하며 부분 필드 재작성·정상 필드 고정 프로토콜은 추가하지 않았다.
절단으로 통과시키지 않고, 전체 검증 뒤에만 원장에 적용한다. 재시도 상한도 그대로다.

`prepare()`는 다음 턴 실행 전에 미완료 요약을 동기로 처리한다. 따라서 배경 실패가
계속되면 다음 전경을 막을 수 있다. 이 경로에서 두 길이 위반을 함께 알리고, 재요청 성공 시
진행하거나 실패 시 원문과 기존 과제를 보존하며 정지하는 것을 검사했다.

`distill_queue._execute`의 `finally`에서 성공·실패 시도 모두 비용을 기록한다.

- 기존 `postprocess.json`: 큐 행 ID·시도 번호로 실행시간·토큰을 누적하며 재개 시 이어 읽는다.
  같은 시도는 중복 가산하지 않는다. 누락 시도나 미확인 토큰은 `incomplete`와 `tokens:null`로 표시한다.
- 기존 `distillation.cost`: 시도별 증분과 성공 여부를 기록한다. 누계 파일과 다시 합산하지 않는다.
- 범위는 후처리 큐의 시도 실행 합이다. 전경의 동기 요약·큐 대기·backoff는 제외한다.
  토큰은 기존 턴 계측의 차이이며 캐시 포함이다. 새 사용량 집계 체계는 만들지 않는다.
- 계측 파일 쓰기 실패가 성공한 기억 쓰기를 재실행하게 하지 않는다. 기존 큐 영속성과 재시도는 유지한다.

실제 첫 요약 성공률과 재요청 감소는 후속 실사용에서 측정한다. 오류를 함께 알려도 모델이
다시 틀릴 수 있으므로 항상 한 번의 수정으로 끝난다고 보장하지 않는다.

원장의 장기 `goal_criteria`·framing·접근법·메타는 보존하며 amend의 명시적 규정 수정과

개발 파일 변경이 만든 재기동 요청을 공식 취소 경로로 보류해 기존 백엔드의 요청 접수를
복구했다. 확인 당시 실행 digest는 수정 전 코드였다. 따라서 정본 코드 반영과 실행 중인
백엔드 반영은 구분하며, 이번 수리의 실사용 효과를 관측하려면 정상 재기동이 먼저 필요하다.

고정 재현과 실사용 절감은 구분한다. 후속 에피소드에서 재조회·요약 실패·전경/후처리
모델 라운드와 출력량·지연·품질을 함께 본다. 추가 본문 비용이 이득을 상쇄하면
기존 정책값을 되돌린다. 새 작업노트, 부분 요약 프로토콜, 세션 강제 초기화는 보류한다.

selected·reason이 81행, dedup_note가 14행 들어 있다. 각각의 필요성과 비용은 별도 문제다.

**보편적인 개선 방향은 명확하다: 원자료는 코드가 보존하고 모델은 식별자·변경분·새 정보만
생성한다.** 분류·검토·선별·문서 수정 등에 같은 원리가 적용되며 업무 절차를 고정할 필요가 없다.
다만 table:ai에는 이미 그 구현과 명세·시험이 있으므로 같은 기능을 추가 제안하지 않는다.
추가 개선 여부는 다른 경로에서 이 원칙이 빠져 큰 복사 비용을 만드는지를 확인해 결정한다.

seq 245의 2차 추출도 영상별 선정 팁을 이미 구분할 수 있는데, 전체 선정 제목을 각 영상에
모두 보내고 “다른 영상의 제목은 무시”하라고 했다. 영상 키로 먼저 나눠 넘기는 것은 기존
데이터 연산으로 할 수 있다. 제목 선별 후 선택한 팁을 원문에서 정독하는 두 단계 자체는 유지할
가치가 있으며, 내부 추출·평가 17회를 전부 불필요하다고 판정할 근거는 없다.

### 8-4. 최초 수리 순서 철회 — 관측과 수리 우선순위는 다름

최초에는 check 중복 제거 → 부분 성공 기억 연결 → 큰 결과 재출력 축소 → 중간 결과 전달
순서를 제안했다. **작게 고칠 수 있다는 이유와 큰 효과가 있다는 이유를 혼동한 순서이므로
철회한다.** 사용자 지시는 자잘한 낭비를 무시하고, 보편적으로 큰 비용을 만드는 구조를 찾는 것이다.
별도 검사 5회를 줄일 수 있다는 사실만으로 17분 주행의 핵심 병목이라고 말할 수 없다.
81행 원자료 재출력이라는 최초 판정은 §8-3의 추가 코드·증거 대조에서 정정됐다.

3544·3545에서 관측한 중간 결과 전달 문제는 3546에도 이어진다. 직전 보고서를 함수로
읽은 뒤 중간 결과가 접혀 파일 꼬리를 다시 읽었다(seq 23→34). 서로 다른 업무에서 같은
경계 문제가 보인다는 근거는 있지만, 누적 비용의 크기는 아직 확정하지 않았다.

추가 관측은 당장 별도 수리 체계를 만들지 않고 남긴다. 두 번째 감독 검토는 02:51:40에
시작했고 HTML 생성은 02:51:43에 성공했다. 02:52:12에 나온 REWORK는 아직 HTML을 만들라고
지시했다. 실제 지시 전달·HTML 재실행 기록은 없어서 추가 실행 낭비로 세지 않는다.
기존 판정 신선도 검사에서 생성 완료와 공개 대기를 구분하는지 확인할 사례다.
작업기록 #529도 공개 승인 약 42초 전에 “발행했다”고 썼다. 이번에는 뒤의 공개가 성공했지만,
기억을 쓸 당시의 상태는 저장·검수 대기였다. 기존 네 상태 구분을 기억 문구에도 적용할 근거다.

3545에서 확인한 A의 전달 개선은 유지한다. 3546 후처리 비용도 합계가 맞는다.
이번에는 과제 요약 실패 재시도가 없어 B의 오류 집계 효과를 추가 입증하지 않았다.
전체 반성의 “배관과 누적 방식” 지적을 유지한다. 위 결함을 모두 수리 대상으로 올리지 않고,
다음 기준으로 큰 문제를 먼저 가린다.

## 9. 반성의 기준 — 큰 효과와 보편성 (2026-09-12 사용자 확정)

사용자는 특정 에피소드에 최적화한 과정을 얼려 실행 시간을 줄이려는 것이 아니다.
목표·방법을 바꾸고 새 도구를 조합하는 능력을 유지하면서, 함께 일할수록 잘하게 되는
하네스를 만드는 것이 목적이다. 다음 반성에서도 이 기준을 적용한다.

1. **전체 비용에서 큰 것을 찾는다.** 오류·재조회·호출 수를 세는 것만으로 수리 우선순위를
   정하지 않는다. 전체 지연·출력 비용·결과 품질에서 비중이 큰지 먼저 입증한다. 필요한 조사·
   판단·집필도 오래 걸릴 수 있으므로 소요 시간이 곧 낭비는 아니다. 작은 결함은 관측에만 남긴다.
2. **업무가 아니라 공통 작동 원리를 고친다.** 특정 보고서의 편수·선정 순서·출력 형태에 맞춰
   최적화하지 않는다. 기존 자료를 다시 생성하게 하는 전달 계약, 진행 상태를 다시 알아내게
   만드는 문맥, 복구한 실행을 잃는 학습 경계처럼 다른 업무에서도 같은 비용을 만드는지 본다.
   원래 에피소드 외의 업무에서 이득이 없거나 새로운 판단을 제한하면 보편적 개선으로 채택하지 않는다.
3. **줄일 것은 불필요한 재구성이고, 남길 것은 판단의 자유다.** 새 자료·목표 변경·예외에 대한
   판단은 모델에게 남긴다. 이미 확보한 자료와 실행 상태를 보존·참조하는 일반 기능으로
   비용을 줄인다. 관용구도 수정 가능한 표현 수단이며, 성공한 한 주행을 의무 절차로 승격하지 않는다.

현재 후속 조사의 중심 가설은 **모델이 실제 과제보다 하네스 안에서 자료·코드·진행 상태를
다시 구성하는 데 큰 비용을 지불하는가**다. 3546의 47,410 출력 토큰 전부를 낭비로 세지 말고,
여러 업무에서 새 판단·집필과 반복 전달·재구성을 구분해 비중을 확인해야 한다.
부분 성공의 기억 유실은 성장 능력에 대한 공통 구조 결함 후보지만, 이를 고치면 다음 업무의
성과가 크게 좋아진다는 효과까지 입증된 것은 아니다. 단일 주행에서 확인한 결함과 보편적
효과의 가설을 분리한다. 추가 모델·관문·저장소를 먼저 짓지 않는다.
