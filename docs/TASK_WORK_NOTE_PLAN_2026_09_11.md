## 2. 먼저 계측 누락을 고친다

대상은 backend/cognition/distill_queue.py의 기존 시도 경계와 비용 기록이다.
성공·예외 모두에서 시도 비용을 남기고 postprocess.json은 기존 사건을 합산한 값으로 만든다.
기존 큐 행 ID·attempt·run/call ID를 사용하며 새 비용 저장소나 신원 객체는 추가하지 않는다.

- 실패한 시도도 기존 원장에 기록한다. 같은 시도를 재집계해도 중복 가산하지 않는다.
- 호출 경계·실제 모델 라운드·도구 호출 수를 구분한다. billable usage를 집계하고
  response snapshot과 중복 합산하지 않는다. 신규·캐시 입력을 구분한다.
- 시도 실행시간 합과 대기·backoff를 포함한 전체 경과를 구분한다. 재기동 뒤 이전
  시도도 기존 기록에서 회수한다. 누락된 계측은 0이 아니라 미확인으로 표시한다.
- 비용 기록 실패가 성공한 기억 쓰기를 다시 실행시키지 않게 한다.
  큐의 기존 재시도 상한·영속성·과제 갱신의 멱등성은 유지한다.

완료 조건: 실패 뒤 성공·재집계·큐 재개에서도 호출과 토큰이 빠지거나 중복되지 않는다.
3536의 model.usage를 대조 기준으로 사용하고 운영 작업을 다시 실행하지 않는다.

## 3. 수리 A — 작은 최종 결과의 재조회 줄이기

새 표시 판단기 없이 data/lifecycle_policy.yaml의 기존 envelope_preview.min_chars를
조정한다. **첫 비교 후보는 3,000→6,000자**다. 6,000은 시험할 초기값이다.
순수 코어 기본값·계약 설명과 실제 정책 경로도 대조한다.

- 4,430자 결과는 전량 전달한다. filter/take를 썼다는 이유로 무조건 전량을 보내지 않고
  실제 결과 크기로 결정한다. 큰 표·긴 문자열, 원문 참조·턴 변수, 앱 전체 전달은 유지한다.
- 기존 preview_envelope와 전송 경계만 사용한다. 모델 수신 결과까지 확인해 뒤 단계가
  다시 자르면 그 기존 경계를 고친다. 별도 축소 단계나 작업별 예외를 추가하지 않는다.
- 조회만 할 때 MCP의 필수 code를 채우지 않아도 되게 기본값을 빈 문자열로 맞추고
  공통 스키마·API 기본값·예시를 대조한다. read_result만으로 조회할 수 있어야 한다.
  실제 코드와 조회를 함께 보낸 입력은 계속 거절하며 임의 코드를 무시하지 않는다.
- 크롤링·union의 기존 도움말에 부모 봉투의 URL과 문단 행 필드를 구분해 설명한다.
  없는 열은 계속 오류다. URL 자동 복제나 새로운 출처 통화 계약은 추가하지 않는다.

검증: 50행·약 4.4K 결과, 6K 경계, 큰 표, 한 행의 긴 본문, 중간 결과가 큰 파이프,
원문 회수, API/MCP 조회의 code 생략과 혼합 입력 거절을 확인한다.
전량 전달과 실제 모델의 재조회 감소는 별도로 확인한다. 추가 본문 비용이 이득을
상쇄하면 기존 정책값으로 복귀한다.

## 4. 수리 B — 과제 요약에서 오류 필드만 다시 작성

대상은 pursuit_bind.py의 ask_json/summarize_pending과 pursuit_ledger.py의 기존 검증기다.

- 첫 요청은 이번 턴으로 바뀐 진행 필드만 출력하게 한다. 제한은 TEXT_LIMITS·LIST_LIMITS에서
  가져와 프롬프트와 검증의 숫자가 어긋나지 않게 한다.
- 기존 검증기가 오류 필드·실측 길이·허용 길이를 한꺼번에 보고할 수 있게 한다.
  첫 위반만 알려 다음 위반을 다시 발견하게 하지 않는다. 검증 규칙은 한 벌을 유지한다.
- JSON은 유효하나 일부 필드가 틀렸으면 정상 필드는 호출 중 변수에 보존하고 오류 필드만
  모델에게 다시 요청한다. 사실 판단에 필요한 원문·과제 맥락은 유지한다. 실패 객체 전체의
  재출력을 요구하지 않는다. 수정 응답이 정상 필드나 허용 밖 필드를 바꾸면 거절한다.
- 합친 후보 전체가 검증을 통과한 뒤 기존 version/source_order 검사와 같은 트랜잭션으로
  적용한다. JSON 자체가 깨졌으면 기존의 제한된 전체 재요청을 사용한다.
- 문자열을 잘라 통과시키거나 부분 성공을 완료로 표시하지 않는다. 재시도 상한을 늘리지
  않으며 일시 오류를 복구하는 기존 큐도 없애지 않는다.

검증: progress와 next 동시 초과를 한 번에 진단하고 한 번의 필드 수정으로 완료하는 대역,
정상 필드 불변, 잘못된 JSON, 저장 전 검증, 동시 정정·버전 충돌·재개를 확인한다.
실제 모델의 첫 요약 성공률·출력량도 측정한다. 항상 한 호출에 끝난다고 보장하지 않는다.

## 5. 수리 C — 옛 과제 계획을 이번 턴의 지시로 복사하지 않기

대상은 pursuit_bind.prepare/run_consciousness/accept_output의 기존 경계다.
이미 수행하는 과제 검토 호출의 criteria를 이번 턴 실행 기준으로 사용한다.
그 기준이 빈약한 경우도 기존 검토 계약에서 다루며 별도 판정 호출은 추가하지 않는다.

- 장기 goal_criteria·과제 framing과 이번 턴 실행 문맥을 구분한다. keep는 과제 틀이
  유지된다는 뜻이며 이전 턴의 검색·계산 프로그램을 그대로 실행하라는 뜻이 아니다.
- keep/amend에서 옛 imagined_ibl·expert_choice·행동 힌트를 현재 지시로 자동 복사하지
  않는다. 이번 문제 정의에는 현재 요청·검토 기준을 쓴다. 과거 계획은 원장의 배경으로 남는다.
- 원장에 쓸 과제 갱신과 실행자에게 보낼 일시 문맥을 구분한다. 현재 턴의 짧은 기준으로
  장기 framing을 덮어쓰지 않는다. amend의 명시적 과제 수정과 rewrite 경로는 보존한다.
- 모델의 새 계획·사용자 정정은 기존 경로로 저장한다. 필요한 의미 판단을 코드로 대체하지 않는다.

검증: 경유시간→객실 선택처럼 하위 질문이 바뀌면 과제 ID·전체 목표는 유지하면서
옛 경로 계산 지시가 현재 프롬프트에서 빠져야 한다. 같은 일의 계속 수행, 사용자 반박·
대상 변경, amend/rewrite, 재개, 최종 평가 기준 전달을 확인한다.
API·CLI의 새 실행과 세션 재개에서 동일한 현재 기준이 전달되는지 본다.

## 6. 적용 순서와 종료 조건

계측 → A → B → C를 각각 검토 가능한 변경으로 나눈다. 기존 주제별 시험에 회귀를 추가한다.
새 사건별 시험 파일·관문·DB 테이블·프로바이더별 로직 복제는 만들지 않는다.

- 표시: test_envelope_preview_2026_09_06.py, test_public_result_contract.py, 경계 행렬 시험.
- 요약·과제: test_pursuit_ledger.py. 큐·비용: test_distill_queue.py.
- 최종 평가·보완: test_final_evaluator.py 등으로 도구 없음·보완 1회 정책 보존.
- 구현 완료 시 전체 backend pytest, 층·IBL 파생물 검사, Android 번들 재생성 및 커밋 관문.
  계획만 수정하는 현재 단계에는 런타임 검사·모델 호출·백엔드 재기동을 하지 않는다.

비교는 저장된 결과를 사용하는 고정 재현과 새로운 실사용을 구분한다. 실제 모델 비교는
같은 질문·자료·모델·세션/캐시 조건에서 한 요소씩 바꾸고 외부 쓰기·운영 기억 갱신은 격리한다.
전경/후처리 라운드, 오류·재조회, 출력·신규/캐시 입력, 경과와 품질을 비교한다.
합성 대역의 호출 감소와 실사용 절감률을 혼동하지 않는다.

합격은 **기존 정보·사용자 정정을 잃지 않고 불필요한 왕복이 줄어드는 것**이다.
개선이 없거나 비용이 늘면 되돌리거나 보류한다. 한 사례로 전체 통합을 시작하지 않는다.
변수 목록 확장, 새 작업노트, 자동 출처 전파, 세션 강제 초기화·전체 역사 재요약은 보류한다.
큰 CLI 세션 입력량은 캐시를 구분해 관측할 문제이며 이 계획에서 일괄 초기화하지 않는다.
