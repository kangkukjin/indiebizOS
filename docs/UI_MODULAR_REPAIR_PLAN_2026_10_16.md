# 화면의 중앙 반영과 모듈별 독립 수리 계획

상태: 설계 초안. 선행 사용자 업데이트 수리의 정본 커밋 `36532011`을 대조했다. 이번 수리는 시스템 전반의 화면·수리 경계를 하나의 완결된 작업으로 전환한다. 단계는 내부 구현 순서이며 부분 출시·후속 유예의 단위가 아니다. 이 문서의 개정은 구현 착수가 아니다.

버튼의 위치나 문구를 바꾸는 일은 해당 화면의 수정과 확인으로 끝나야 한다. 화면 변경 때문에 실행 중인 AI 작업·로컬 실행부·무관한 앱까지 함께 멈추거나 갱신하는 비용을 줄인다. 중앙에서 공통 화면을 한 번 고치면 연결된 표면에 전달하되, 각 기기의 작업·입력·권한을 보존한다.

핵심 목표는 **수정 단위, 검사 단위, 배포 단위, 활성화 단위, 복구 단위를 가능한 한 일치시키는 것**이다. 파일 분할이나 중앙 배포만으로 이 목표를 달성했다고 보지 않는다.

현재 시스템은 운영 중이다. 새 경로를 부분적으로 운영에 올리고 옛 경로와 함께 유지하는 상태를 결과물로 남기지 않는다. 공통 화면의 수정·배포·열린 화면 반영, 기능별 수리 범위, 기존 중복 경로 제거와 전체 인수를 같은 작업 범위로 묶는다. 회원 화면에서 먼저 구현하더라도 주인·원격·폰의 연결이 남아 있으면 전체 수리는 진행 중이다.

목적 기준은 [IBL 진화 목적과 개선 판단](IBL_EVOLUTION_PURPOSE.md), 전체 지도는 [해부도](../data/system_docs/anatomy.md)를 따른다. 새 IBL 어휘·범용 플러그인 프레임워크·일괄 마이크로서비스 전환은 이 계획의 전제가 아니다.

### 이번에 끝낼 구조와 만들지 않을 확장

전체 전환은 필요한 변경의 모든 소비자와 제거 작업을 끝낸다는 뜻이다. 시스템에 가능한 개선을 전부 넣거나, 이미 독립적으로 동작하는 기능까지 다시 구현한다는 뜻은 아니다. 판단 기준은 다음과 같다.

1. **목표에 필요한가:** 이것이 없으면 공통 화면을 한 번 수정하고 독립적으로 반영·복구하는 결과를 얻을 수 없는가.
2. **늦추면 무엇이 굳어지는가:** 새 기능이 낡은 결합을 계속 복제하거나, 나중에 API·저장 상태·배포 형식·소비자를 함께 다시 바꿔야 하는가.
3. **기존 구조로 충분한가:** 같은 결과를 기존 모듈·상수·빌더·업데이트 경로의 작은 변경으로 얻을 수 있는가.
4. **추가 책임을 정당화하는가:** 새 관리자·설정·프로토콜이 없애는 복잡성보다 유지해야 할 복잡성을 더 만들지는 않는가.

필요성은 실제 결합과 목표 구조에서 판단한다. 이미 설명된 불편을 다시 겪거나 시간 절감을 먼저 실측해야 필수 변경을 시작하는 조건은 두지 않는다. 반대로 미래에 쓸 수도 있다는 가능성만으로 기반 시설을 만들지 않는다.

| 구분 | 이번 판단 | 이유 |
| --- | --- | --- |
| 공통 화면·동작의 단일 소유, 문자열 치환 제거, 기기 어댑터 경계 | 이번에 완료 | 늦출수록 새 기능이 표면별 사본과 내부 의존을 복제한다. |
| 화면 자산과 실행부 분리, 호환 판본·원자적 활성화·화면 복구 | 이번에 완료 | 배포와 복구 계약이 굳은 뒤 분리하면 모든 소비자의 재이행이 필요하다. |
| 화면 상태와 작업 수명 분리, 공통 화면의 열린 상태 갱신 | 이번에 완료 | 화면 수정이 실행 중 작업과 편집 상태를 침범하는 원인을 없애야 한다. |

| 범용 화면 DSL·플러그인 관리자·모든 앱의 독립 업데이트 관리자 | 범위에서 제외 | 기존 구성·모듈·업데이트 경로로 목표를 달성할 수 있는 한 추가 체계의 효과가 불확실하다. |
| 모든 렌더러의 React 이식, 모든 서비스의 프로세스 분리 | 일괄 전환 제외 | 같은 기술을 쓰는 것 자체가 수리 독립성을 보장하지 않는다. 필요한 경계만 실제로 분리한다. |
| 외부 편집 엔진·네이티브 브리지·임의 실행 스택까지 무중단 코드 교체 | 범위에서 제외 | 일반 화면 갱신과 다른 수명·호환 문제다. 해당 실행부의 기존 검증된 업데이트 절차를 유지한다. |
| 별도 메뉴 레지스트리·자동 의존 분석의 전면 재작성 | 필요할 때만 최소 구현 | 공통 상수·함수와 기존 선택기 확장으로 충분하면 그것으로 끝낸다. |

0단계에서 이 기준으로 대상과 제외 항목을 확정한다. 착수 뒤 범위 변경은 필수 의존과 대안 검토를 명시한 이행 표 개정으로 관리한다. 구현이 어렵다는 이유로 필수를 제외하거나, 유사한 기능을 발견했다는 이유만으로 범위를 자동 확대하지 않는다.

## 1 선행 작업과 연결

원격 데스크톱 사용자 업데이트 수리는 2026년 10월 16일 정본 커밋 `36532011`에 반영됐다. 코드와 [회원 데스크톱 설계](MEMBER_DESKTOP_DESIGN_2026_10_15.md) §15에서 앱 0.1.2 / shell 2의 계약을 확인했다. 새 판본 정보는 조용히 확인하고, 사용자가 업데이트 버튼을 눌러 설치를 확인한 뒤 내려받아 적용한다. 자동 적용은 제거됐으며 예전 자동 적용 설정도 새 설치의 허가로 쓰지 않는다. 커밋 반영과 실제 OS·배포 환경의 인수 완료는 구분한다.

선행 수리에서 확정된 다음 항목을 그대로 계승한다.

- 새 업데이트 표시와 사용자의 명시적 설치 선택. 자동 다운로드·설치나 반복 알림을 다시 추가하지 않는다.
- 배포자 신뢰, 서명·지문 확인, 호환 판본 판단, 실패 복구.
- 실행 중 작업을 보호하는 수명 관리와 설치형 앱의 권한 경계.
- 실제 지원 OS·기기에서 확인한 설치 및 업데이트 범위.

착수 첫 단계에서 이 커밋 이후의 변경과 실제 인수 결과를 다시 확인한다. 업데이트 관리자를 새로 만들지 않고, 기존 업데이트 경로에 화면만 교체할 수 있는 단위를 추가한다. 현행 설치물에는 화면 전용 매니페스트를 읽는 코드가 없으므로 이를 지원하는 최초 main/preload 변경은 전체 설치물 갱신이 필요하다. 그 뒤 호환되는 화면 릴리스부터 가벼운 경로를 사용한다. 지원하지 않는 구형 클라이언트에는 기존 형식 또는 전체 설치물을 안내한다.

| 공통 브리지·권한·DB 구조 | 해당 실행부와 실제 의존 소비자 | 선행 수리의 업데이트·백업·복구 보장 |
| 공통 인지·언어·인증 계약 | 관련 모듈 전체와 필요한 종합 회귀 | 기존 시스템의 의미와 격리 경계 |

새 동작을 구현하는 버튼과 기존 동작의 위치만 바꾸는 버튼을 구분한다. 지원되지 않는 능력은 UI 등록만으로 생성되지 않는다. 기능의 권한 판정은 서버·실행부가 계속 소유한다.

## 4 목표 구조

### 공통 화면과 기기 어댑터

공통 화면 부품은 화면 표시와 사용자 의도를 담당한다. 브라우저·Electron·Android 차이는 파일 선택, 창 열기, 저장, 장치 접근 등 명시적인 어댑터가 담당한다. 공통 화면이 다른 표면의 HTML 문자열이나 내부 전역 상태를 직접 수정하지 않는다.

공통화 범위는 실제로 같은 기능과 표시 규칙이다. 주인 화면과 회원 화면의 권한·작업 의미, 원격 리모컨과 폰 자체 화면의 정체는 유지한다. 모든 표면을 하나의 거대한 조건문으로 합치거나, React 전면 이식을 선행 조건으로 만들지 않는다.

공통화하는 동작과 소비자는 0단계의 닫힌 이행 표로 확정한다. 표에 포함한 동작은 한 소유 위치에서 정의하고 React·HTML 렌더러는 이를 표시·연결한다. 구성 데이터만 공유해서 동일 동작을 반복 수정하게 되는 항목은 그 표에 동작 로직의 이전까지 명시한다. 동일 HTML·동일 프레임워크 자체가 목표는 아니다. 기준선의 대화 헤더·이전 기록·사전은 조사 시작점이며 전체 중복 목록의 증명으로 쓰지 않는다.

메뉴·화면 등록은 실제 중복 항목을 조사한 뒤 필요한 정보만 한 곳으로 모은다. 안정된 ID, 제목, 아이콘, 그룹·순서, 대상 화면, 필요한 능력 가운데 반복되는 사실이 대상이다. 소수 항목은 공통 상수·함수로 끝내고 별도 레지스트리를 만들지 않는다. 화면 부품 내부의 복잡한 편집기 동작까지 범용 설정 언어로 바꾸지 않는다. 번역 카탈로그·선언형 앱 정의가 이미 소유하는 정보는 참조하고 중복 저장하지 않는다.

### 자산의 위치와 읽기 수명

새로 분리하는 화면 원본의 계획상 위치는 `frontend/surfaces/`다. `shared/`에 공통 부품·구성, `member/`·`remote/`·`phone/`에 필요한 표면별 조립과 어댑터를 둔다. 기존 `frontend/src/`의 React 화면과 이미 공유하는 `backend/static/app_render_core.js`는 이 결정만으로 옮기지 않는다.

빌드 산출물은 `frontend/dist-surfaces/<판본>/`에 만들고, 현재 생성되는 helper 번들은 같은 빌더 결과를 사용한다. 이 경로는 신규 제안이며 아직 생성하지 않았다. 0단계에서 배포 패키징·폰 번들·무시 규칙과 연결하고, 실행 중 제공되는 판본은 다음 빌드가 덮어쓰지 않도록 별도로 보존한다.

RED 보호 여부, 제어자 재기동 여부, 화면의 실제 신선도는 각각 확인한다. `_reload_triggering`은 현재 `backend/` 아래 `.py`와 패키지·사전 경로를 판정하며, `backend/static/*.js` 자체는 그 재기동 조건이 아니다. `restart_protocol.code_manifest`도 backend의 Python 소스를 추적한다. 따라서 정적 자산이 backend 폴더에 있다는 이유만으로 재기동이 필수라고 판단하지 않는다. 새 원본은 기존 `frontend/` 보호 범위에서 검사·적용하고 보호를 우회하는 폴더 이동을 하지 않는다.

현재 원격 조립은 import한 Python 문자열을 사용하면서 번역 JSON은 요청 때 읽는다. 회원 브라우저는 공통 Python 셸과 요청 때 읽는 정적 JS를 섞는다. 이행 후에는 요청마다 활성 판본을 확인하고 해당 판본의 완성된 자산을 읽는다. 캐시가 필요하면 불변 판본·지문을 키로 삼고 import 시점의 화면 본문을 영구 재사용하지 않는다. 열린 창은 자신이 시작한 판본의 자산 주소를 유지한다.

### 중앙 배포와 로컬 실행의 경계

중앙은 사용자의 IndieBiz 허브 또는 기존에 신뢰하도록 설정한 배포 경로다. 하나의 화면 원본에서 대상별 자산을 만들고 해당 경로로 전달한다. 소스 파일 저장, 빌드·검사, 배포, 기기 활성화를 구분한다. 개발 중인 중간 저장이 모든 기기에 즉시 노출되는 방식은 사용하지 않는다.

브라우저는 허브의 화면 자산을 읽는다. 설치형 앱은 기존 신뢰 체계로 검증한 화면 번들을 로컬에 보관하고 활성화한다. 허브에서 받은 임의 HTML에 파일·셸 브리지를 붙이지 않는다. 승인·권한 확대·네이티브 브리지 변경은 일반 화면 수정과 구분하며 기존 신뢰된 업데이트 경로를 따른다.

화면 릴리스는 필요한 범위의 식별자·자산 지문·화면 상태 판본·API/브리지 호환 범위를 가진다. 기존 매니페스트에 같은 정보가 있다면 확장해서 쓰고 별도의 병렬 원장을 만들지 않는다. 개발용 HMR은 개발 편의로 유지하며 운영 배포 계약을 대신하지 않는다.

### 모듈의 책임과 수명

기능 모듈은 자기 화면, 상태, 서비스 진입점, 검사와 복구 범위를 소유한다. 층별 폴더 규약을 유지하면서 기능의 소유 범위를 연결한다. 단지 폴더를 기능별로 다시 배치하는 일을 목표로 삼지 않는다.

화면 수명과 작업 수명을 분리한다. 작업은 기존 서버·로컬 실행부 원장에서 계속되고, 갱신되는 화면은 동일한 작업 ID로 다시 구독한다. 기존 창·스트림·임대와 실행 수명의 연결을 확인하고, 화면 모듈의 교체가 작업 제출·취소·재실행을 유발하지 않도록 이번 작업에서 분리한다. 웹의 실제 탭 종료 계약은 별도로 유지하되, 탭 내부의 화면 교체를 탭 종료로 처리하지 않는다.

열린 화면 반영은 이번 완료 범위다. 문구·배치는 구성 갱신으로, 자체 화면 코드 변경은 모듈의 상태 보존·구독 인계·재마운트로 처리한다. 임의 실행 스택을 교체하는 개발 서버식 HMR을 전제로 하지 않는다. 초안·선택·스크롤·미저장 편집·작업 구독의 소유자를 정하고 표시 모듈 바깥에 필요한 상태를 보존한다. 적용 대상 모듈의 인계·실패 복구 계약은 완성해야 한다.

외부 문서·시트 편집 엔진과 장치 세션은 안정된 연결 경계 뒤에서 수명을 유지한다. 주변 버튼·메뉴를 고치기 위해 그 엔진의 내부 상태를 새 형식으로 추출하거나 엔진 코드까지 교체하지 않는다. 해당 엔진 자체의 버전 변경은 기존 저장·재개·업데이트 계약을 따른다. 이 경계 덕분에 일반 화면 변경을 열린 상태에서 반영할 수 있어야 하며, 화면과 엔진이 아직 분리되지 않아 함께 재시작하는 경우는 이번 수리에서 해결한다.

모든 Python 모듈의 무중단 교체는 범위에 넣지 않는다. 서비스 변경은 기존 재기동 제어자가 담당할 수 있다. 독립 프로세스가 필요한지는 장기 작업·장치 자원·실패 격리 요구가 실제로 있는 모듈별로 판단한다.

## 5 전체 전환의 내부 작업 순서

아래 단계는 같은 수리의 의존 순서다. 먼저 각 표면의 기존 진입점이 새 단일 원본에서 생성한 **동작 동일 산출물**을 소비하게 연결한다. 기존·신규 산출물의 바이트와 이벤트·API 계약을 확인한 뒤 원본의 소유 위치를 전환한다. 상태·활성화 동작을 바꾸는 후보는 전체 인수 전까지 운영에서 선택하지 않는다. 소스 단일화와 새 동작의 활성화를 구분하며 정본 main의 경로 한정 커밋 규약을 따른다.

생성 경로를 연결한 뒤 수정은 새 원본에서만 하고, 옛 입력은 제거하거나 생성 어댑터로 만든다. 빌더의 정합 검사로 생성물·옛 사본의 수작업 수정을 검출한다. 각 연결 시점의 기준 커밋·입력 지문을 기록하고, 동시 세션이 관련 원본을 바꾸면 그 변경을 포함해 재생성·재검증한 뒤 적용한다. 오래된 후보가 최신 main을 덮어쓰지 않도록 적용 직전에 다시 대조한다. 바이트 동일 확인만으로 이후의 표류까지 해결됐다고 보지 않는다.

초기 설치물 갱신이 필요한 기기는 먼저 새 계약을 지원하도록 준비하되 기존 화면을 유지한다. 준비되지 않은 기기가 있으면 해당 배포 인수는 미완료로 남긴다. 서로 다른 기기의 네트워크를 전역 원자적 전환으로 가장하지 않고, 기기별 판본 전환·호환을 확인한 뒤 전체 완료를 판정한다.

### 0단계 선행 수리 인수와 의존 범위 확정

선행 업데이트 수리의 완료 상태를 확인하고, 주인 데스크톱·원격 런처·회원 데스크톱·회원 웹·폰의 실제 진입점, 화면 원본, 생성물, 제공자, 활성화 방법을 연결한다. 설치형 회원 앱과 주인용 원격 PC 화면 공유 기능을 같은 제품으로 취급하지 않는다.

2장의 커밋 기준선에 빌드·검사·활성화 경로를 연결한다. 현재 알 수 없는 과거 실행 시간이나 재시작 횟수는 추정하지 않는다. 1단계 전에 다음 결정을 마친다.

1. `frontend/surfaces/` 원본과 판본별 산출물의 배포·폰 번들 경로, RED 보호·재기동 분류를 확정한다.
2. 각 제공자가 요청 시 디스크를 읽는지, import 값이나 프로세스 캐시를 유지하는지와 활성 판본 전환 방법을 기록한다.
3. 메뉴·라우트·창 열기에서 같은 사실을 반복 정의한 항목 수를 센다. 파일이 네 개라는 이유만으로 중복 네 건으로 세지 않는다. 결과에 따라 3단계를 공통 상수·함수 추출 또는 등록 정보 통합으로 확정한다.
4. 화면 전용 릴리스의 파일 허용 목록·호환 판본과 적용·복구 상태 전이를 발행기와 소비자 양쪽에서 확정한다. 최초 지원을 위한 전체 설치물과 구형 앱의 배포 경로도 포함한다.
5. 모든 지원 표면을 조사하여 아래 형식의 **닫힌 이행 표**를 완성한다. 동작 ID·소비자·유지/변경/제외 판정을 유한한 행으로 적고 `등`·`관련 화면 전체` 같은 열린 항목을 두지 않는다. 1단계 착수 전에 문서 커밋으로 기준을 고정하며 이 표가 7장의 완료 집합이다.
6. 변경 모듈마다 **상태 소유자 표**를 작성해 보존·인계·실패 복구와 필요한 재작성 범위를 확정한다. 현재 DOM·전역 변수 의존을 단순 자산 추출로 계산하지 않는다. 소유자가 미정인 행이 있으면 0단계 설계가 끝나지 않은 것이다.

이행 표의 필수 열은 다음과 같다. 현재 계획서는 형식을 정한 것이며 대상 조사가 완료됐다고 주장하지 않는다.

| 행의 단위 | 반드시 기록할 내용 |
| --- | --- |
| 공통 동작 또는 독립 화면 모듈 ID | 정확한 동작·표면·원본 파일·진입점·서비스 소비자 목록 |
| 판정과 비용 | 변경/유지/제외, 목표와 의존 근거, 추출/어댑터 수정/상태 구조 재작성 구분 |
| 최종 연결 | 단일 소유 위치·생성물·로더·활성화·복구 경로와 상태 표 참조 |
| 정리와 인수 | 제거할 파일/분기, 남길 기기별 차이, 검증 항목·지원 OS, 완료 증거 |

상태 소유자 표는 모듈마다 아래 항목을 채운다. 없는 상태는 해당 없음과 이유를 적는다.

| 상태 종류 | 현재 위치와 새 소유자 | 인계 때 정할 것 |
| --- | --- | --- |
| 입력 초안·선택·스크롤·미저장 편집 | DOM/전역 변수/React 상태 등 실제 위치 → 화면 밖 소유 모듈 | 추출·복원·최신 입력 병합, 상태 판본과 실패 복구 |
| 작업·요청·구독·타이머·이벤트 | 작업 원장과 표시 측 핸들 각각의 소유자 | 해제·재연결 순서, 중복 실행 방지, 종료 콜백의 세대 판정 |
| 승인·IME·저장 중 동작 | 원래 권한·편집 소유자 유지 여부 | 일시 보류 조건·재개 사건·오래된 승인 차단 |
| 외부 편집 엔진·장치 세션 | 수명을 유지할 호스트/어댑터 | 화면 교체에서 유지할 인스턴스와 연결 핸들 |

통과 조건: 여섯 결정, 닫힌 이행 표, 상태 소유자 표, 표면별 활성화 계약과 기존 출력 연결 순서가 확정된다. 표의 변경은 범위·필수 의존·비용·검증의 차이를 먼저 문서에 기록한다. 새로 발견한 무관한 개선을 끼워 넣거나 미완료 행을 삭제해 완료 집합을 바꾸지 않는다.

### 1단계 화면 소스와 조립 방식 분리

첫 내부 구현 대상은 회원 작업 화면의 공통 헤더·메뉴·대화 탐색이다. 문자열 치환이 집중되어 있고 선행 업데이트 경로와 직접 연결되므로 여기서 계약을 확인한 뒤 전체 이행 표의 공통 부품으로 확장한다. 회원 화면만 운영 전환하고 나머지를 남기는 출시 단계로 삼지 않는다.

1. HTML·CSS·JS 화면 자산을 Python 처리 로직과 분리한다. Python은 권한·데이터 API와 얇은 자산 제공을 담당한다.
2. `member_shell`과 `member_browser`의 표시 문구·태그 검색 치환을 명시적인 구성·슬롯·어댑터로 교체한다.
3. 표면별 기존 진입점과 빌더가 새 원본의 동작 동일 산출물을 소비하도록 먼저 연결한다. 바이트 비교는 같은 입력의 결정적 출력에 적용하고, 달라져야 하는 자산 주소·판본 표식은 항목별로 명시해 나머지를 비교한다. 이벤트·API·권한 계약도 검사한다. 같은 원본의 현재 동작 출력과 새 동작 후보를 만들며 장기간 별도 화면 사본을 유지하지 않는다.
4. 예전 조립 경로·사본·특수 치환을 대체하고 운영 전환 때 제거한다. 검증 중 필요한 임시 경로는 대상과 제거 조건을 기록하고 이번 수리의 종료 전에 정리한다.

통과 조건: 전체 이행 표의 공통 부품을 한 원본에서 수정해 모든 해당 표면에 생성할 수 있고, UI 변경만으로 backend Python 수정이나 백엔드 재기동을 요구하지 않는다. 기능·권한·작업 동작은 기존과 동일하다.

### 2단계 화면 전용 배포와 활성화

선행 업데이트 수리의 매니페스트·다운로드·검증·상태 표시를 확장한다. 화면만 바뀌고 API/브리지가 호환되는 릴리스는 Go 실행부 교체·DB 백업·실행부 재시작을 하지 않는다. 승인 영역이나 실행부 계약이 달라지면 해당 변경 등급으로 올린다.

이는 파일 목록만 바꾸는 일이 아니다. 기존 업데이트 소유자 안에서 화면 릴리스와 실행부 릴리스를 명시적으로 구분한다. 발행기·검증기는 종류별 허용 파일과 호환 범위를 같이 판정하고, sequence의 비교 범위와 함께 사용할 실행부 판본을 정의해 한 종류의 설치가 다른 종류의 유효한 업데이트를 가리지 않게 한다. 설치 승인도 표시된 종류·판본·지문에 묶는다.

화면 전용 상태 전이는 **발견 → 사용자 설치 선택 → 다운로드·검증 → 후보 준비 → 대상 모듈의 상태 인계와 활성 확인 → 정상 판본 확정**이다. 후보 준비 중 기존 화면과 실행부는 계속 동작한다. 후보의 준비 검사는 부작용을 발생시키지 않으며 같은 입력·구독을 구·신 화면이 동시에 처리하지 않도록 인계한다. pending에는 화면 종류·이전/후보 판본·대상 모듈·확인 단계를 남기며 DB 스냅샷 복원을 호출하지 않는다. 기존 실행부 업데이트의 pending·복구는 유지한다. 두 적용을 동시에 시작하지 않고, 실행부 업데이트 때 화면 판본과의 호환을 재검사한다.

활성 확인 전 실패는 보존한 화면 상태와 이전 모듈로 복구한다. 후보 적용 이후 생긴 사용자 입력·작업 결과를 과거 스냅샷으로 덮어쓰지 않는다. 판본 간 복구에서도 최신 상태를 읽을 수 있는지 확인하고, 앱 종료 뒤에는 영속 적용 기록과 기존 작업 원장으로 마지막 확인 판본·최신 상태를 회수한다. 화면 교체 시험 때문에 기존 실행부를 전역 시험 모드로 바꾸지 않는다.

`workspace.cjs`는 preload 브리지의 소비자다. 화면 전용 허용 목록은 실제 DOM·이벤트 코드와 사용하는 브리지 계약으로 정하고, 브리지 정의의 이전 작업은 가정하지 않는다. main/preload의 검증기 변경은 기존 런타임 피드로 배포할 수 없으므로 첫 지원은 전체 설치물로 전달한다. Android는 4장의 두 로더에 같은 화면 릴리스 계약을 연결한다.

화면 자산은 판본별로 완성한 다음 활성 포인터를 원자적으로 바꾼다. 사용 중인 이전 판본의 자산은 유지해 새 HTML과 옛 JS가 섞이거나 열린 창의 추가 자산 요청이 실패하지 않게 한다. 여러 창의 사용 여부를 보고 정리하며 현재·복구용 판본을 먼저 삭제하지 않는다.

새 창은 설치·활성화가 확인된 호환 판본을 사용한다. 열린 화면도 같은 배포의 소비자이며 다음 규칙으로 반영한다.

- 문구·순서 등 기존 스키마로 표현되고 상태를 건드리지 않는 구성은 해당 영역만 갱신할 수 있다. 설치형 앱에서는 검증과 사용자의 설치 선택을 통과한 구성만 적용한다.
- 자체 화면의 HTML·JS·CSS 코드 변경은 해당 모듈만 상태를 보존하여 교체한다. 새 창 적용만으로 이번 수리를 완료하지 않는다. 브라우저에서도 일반 화면 변경에 사용자의 전체 새로고침을 요구하는 경로를 기본으로 남기지 않는다. 외부 엔진·네이티브 실행부의 코드 변경은 4장의 별도 수명 경계를 따른다.
- 승인 처리·IME 조합·파일 저장처럼 인계 중 끊을 수 없는 동작은 종료 사건까지 적용을 보류한 뒤 같은 업데이트 절차가 자동으로 이어간다. 미저장 편집은 인계 가능한 초안으로 보존한다. 단지 입력이 있다는 이유로 사용자가 창을 다시 열 때까지 무기한 미루지 않는다.
- 인계 검증이 실패한 모듈은 기존 화면을 유지하고 이행 표의 해당 행에 실패 증거를 남긴다.
- 선행 수리의 사용자 확인 후 설치 정책을 계승한다. 중앙 배포·새 창 열기 자체가 설치 동의는 아니다.

시작 실패·자산 손상·호환 실패는 이전 화면 판본으로 복구한다. 화면 복구가 사용자 파일·DB·작업 결과를 되돌리지 않는다. 오프라인 설치 앱은 마지막으로 검증된 화면으로 열린다. 구형 앱은 새 형식을 오해하지 않고 기존 화면 또는 기존 전체 업데이트 경로를 유지한다.

통과 조건: 전체 대상 표면에서 구성·코드 변경을 열린 화면에 반영하고, 작업 진행·입력·편집·일시 보류 후 재개·실패 복구에서도 작업 ID와 최신 상태가 유지된다. 기존 업데이트 버튼과 실패 안내는 계속 동작한다. 지원 준비가 필요한 설치물·폰은 갱신 경로까지 확인한다.

### 3단계 확인된 메뉴 중복의 최소 통합

주인 런처의 메뉴 정의·라우트·창 열기를 같은 화면 ID로 연결한다. 메뉴 순서와 제목을 바꾸려고 `Launcher.tsx`, `App.tsx`, navigation, Electron 창 목록에 같은 사실을 반복 입력하지 않게 한다. 창 크기 등 기기별 정보는 해당 어댑터가 소유한다.

0단계에서 확인한 중복이 소수이면 공통 상수·함수 추출로 종료한다. 반복 항목과 소비자가 충분하여 등록 정보 통합이 필요한 경우에만 공통 정의에서 표면별 능력에 맞는 항목을 선택한다. 주인·회원 메뉴를 같은 목록으로 강제하지 않는다. 선언형 앱의 기존 매니페스트는 계속 정본이며 새 레지스트리에 복제하지 않는다.

통과 조건: 확인된 메뉴의 동일 정보 중복을 없애고, 위치 변경은 해당 정의 수정으로 끝난다. 등록 정보 통합을 선택한 경우 새 화면은 한 번의 등록으로 연결된다. 작은 상수·함수 추출로 해결되면 레지스트리는 필요 없다. 권한과 네이티브 기능 추가는 해당 책임의 구현으로 구분한다.

### 4단계 기능별 수리와 검사 경계 연결

확정한 이행 표의 동작을 주인·원격·회원·폰 소비자에 연결하고 중복 수정 경로를 제거한다. 주인용 폰의 로컬 제공자와 회원용 폰의 APK 자산 로더는 4장의 독립 화면 활성화 경로로 연결한다. 최초 지원 APK 설치 뒤에는 표에 지정한 일반 화면 변경을 APK 재설치 없이 적용하며, 네이티브 코드·권한 변경은 기존 설치 경계를 따른다.

기존 자기수리에 변경 종류와 소비자에서 도출한 적용 범위를 연결한다. 화면 자산, 기능 서비스, 실행부·권한, 공통 코어를 구분하되 작성자의 자기신고만으로 검사를 생략하지 않는다. 변경 파일·의존 관계·계약 변경이 근거다. 범위를 확인할 수 없으면 기존의 넓은 검사·적용 경로를 사용한다.

검사 선택기는 화면 import, 자산 생성 입력, 공통 브리지 소비자까지 필요한 관계를 반영한다. 기존 빌드 입력 목록을 재사용하고 별도의 수작업 목록을 중복 관리하지 않는다. 자기수리 완료 기록에는 소스 적용과 실제 활성 화면 판본을 구분하여 남긴다.

통과 조건: 화면 수리는 해당 화면과 경계 검증으로 끝나고, 공통 API·브리지 변경은 실제 소비자까지 검사한다. 손과 발이 공유하는 계약을 바꿀 때만 양쪽 검사가 함께 선택된다. 전체 이행 표에 미연결 소비자가 남지 않는다.

### 5단계 운영 전환과 기존 경로 제거

1. 표면별 기존 진입점이 단일 원본의 현재 동작 산출물을 소비하고 있는지, 최종 main의 변경이 반영됐는지 먼저 확인한다. 그 원본에서 만든 새 동작 후보의 전체 통합 인수·복구 검증을 마치고 설치물·자산·호환 API를 준비한다.
2. 운영 진입점을 검증된 새 경로로 전환하고 실제 활성 판본·기능·진행 중 작업을 확인한다. 전환 전후 사용자 데이터는 기존 원장이 계속 소유한다.
3. 대체된 화면 사본·문자열 치환·중복 동작·임시 전환 플래그·구형 생성 경로·중복 검사 목록을 제거한다. 문서·빌드·자기수리 안내도 최종 경로로 맞춘다.
4. 정리 후 최종 코드에 대해 관련 종합 회귀와 실제 표면 인수를 수행하고 이행 표에 결과를 연결한다.

개발이나 전환이 중단되면 운영 진입점은 이전에 검증된 경로를 유지하거나 그 경로로 되돌린다. 사용자 데이터·다른 세션의 변경은 덮어쓰지 않는다. 새 경로를 일부 기능에 활성화한 혼합 운영을 방치하지 않고, 남은 작업·후보·전환 상태를 기록해 같은 수리로 이어간다. 복구용 과거 불변 산출물은 보관할 수 있지만 병렬로 수정해야 하는 두 번째 소스 체계를 남기지 않는다.

구형 기기 지원이 필요한 경우 동결된 구버전 배포물·판본이 명시된 호환 경계로 제공한다. 과거 지원 범위를 조용히 없애거나 새 기능을 구·신 소스 양쪽에 계속 수작업 반영하는 방식으로 완료하지 않는다. 호환 소비자의 적용·검사·유지 책임을 이행 표에 포함한다.

## 6 검증과 인수

기본 회귀 규약은 [REGRESSION_TESTING.md](REGRESSION_TESTING.md)를 따른다. 화면 변경에 무조건 backend 전수를 붙이지 않으며, 언어·격리·부트스트랩·공통 계약의 영향이 넓으면 기존 종합 검사를 수행한다. 프론트엔드는 `npx tsc -p tsconfig.app.json`, 생성물은 해당 빌더의 `--check`, 실행부는 변경된 계약의 기존 검사를 사용한다.

| 인수 장면 | 확인할 결과 |
| --- | --- |
| 기존 버튼의 위치·문구 변경 | 한 원본 수정, 대상 화면 반영, backend·Go·Electron main 재시작 없음 |
| 회원 웹과 설치 앱의 같은 부품 변경 | 문자열 치환 없이 공통 결과를 소비하고 표면별 기능은 유지 |
| 작업 실행 중 새 화면 판본 설치 | 열린 화면의 해당 모듈 반영, 같은 작업·구독 유지, 중복 명령·작업 취소 없음 |
| 입력·편집·승인 중 새 판본 도착 | 최신 초안·선택·스크롤 보존, 인계 불가 동작 종료 뒤 같은 적용 절차 재개, 오래된 승인 재사용 없음 |
| 다운로드 중단·자산 손상·시작 실패 | 완성된 이전 판본 유지 또는 화면만 복구, 실행부·사용자 데이터 유지 |
| 새 창과 기존 창의 판본 차이 | 각 창의 자산 일관성 유지, 지원 API 범위 안에서 동작 |
| 구형 앱·오프라인·허브 연결 실패 | 검증된 기존 화면 유지, 미지원 기능을 성공으로 표시하지 않음 |
| 공통 API·브리지·권한 변경 | 영향 소비자를 검사하고 필요한 실행부 업데이트 경로 선택 |
| 화면 후보 준비 중 앱 종료 | 다음 시작에서 이전 화면 선택, DB 복원·실행부 롤백 호출 없음 |
| 화면과 실행부 릴리스 혼용 | 종류별 파일 검증, sequence·호환 판정, 적용 직렬화, 구형 앱의 정직한 거절 |
| 선행 업데이트 기능 회귀 | 조용한 새 판본 표시·사용자 확인 후 다운로드와 설치·실패 복구 보존, 자동 적용 재도입 없음 |
| 주인·회원·원격·폰의 공통 동작 수정 | 같은 동작 정의 한 번 수정, 각 렌더러의 사설 동작 재작성 없음 |
| 편집 엔진·장치 사용 중 주변 화면 변경 | 해당 엔진·장치 세션과 미저장 내용 유지, 일반 화면 갱신이 엔진 교체로 확대되지 않음 |
| 전환 도중 중단·후보 결함 | 검증된 운영 경로 유지 또는 복귀, 사용자 데이터 보존, 미완성 혼합 운영 방치 없음 |
| 최종 경로 정리 | 이행 표의 대체 경로·임시 분기 제거, 실제 소비자가 최종 원본·빌더·검사를 사용 |
| 동시 세션이 관련 화면 원본 수정 | 최종 입력 지문 재대조, 현재 동작·후보 산출물 재생성, 옛 후보로 최신 변경을 덮어쓰지 않음 |
| Android 두 앱의 일반 화면 갱신 | 최초 로더 지원 후 APK 재설치 없이 적용, 오프라인·실패 복구·APK 재추출 후 판본 호환 확인 |

문구·순서만 검증하는 구현 복제형 시험은 늘리지 않는다. 테스트는 작업 수명, 상태 보존, 자산 일관성, 호환성, 복구처럼 실패 비용이 있는 계약에 집중한다. 배치·좁은 화면·키보드 조작은 실제 UI에서 확인한다.

릴리스 인수는 선행 수리가 지원하는 OS·표면에서 수행하고, 실행하지 못한 기기 검증은 따로 남긴다. 한 OS의 모의 검사 통과를 다른 OS의 실제 업데이트 성공으로 보고하지 않는다.

## 7 완료 기준과 범위

완료 집합은 0단계에서 확정한 이행 표와 명시적으로 기록한 개정이다. 모든 변경 행의 소비자 연결·상태 인계·활성화·복구·옛 경로 제거·인수 증거가 채워지고, 유지/제외 행의 경계도 보존됐을 때 전체 완료다. 아래 기준은 그 표의 각 해당 행에 적용한다. 회원만 구현하거나 새 창 적용만 제공한 상태는 부분 진척으로 기록한다.

반드시 충족할 기준은 다음과 같다.

1. 기존 버튼 배치 수정에 무관한 기능 코드 수정이나 실행부 재시작이 필요하지 않다.
2. 공통 화면의 변경이 한 원본에서 생성·배포되며 수동 사본 수정을 요구하지 않는다.
3. 화면 배포와 활성화가 진행 중 작업·미저장 입력의 수명을 침범하지 않는다.
4. 화면만 실패하면 화면만 복구할 수 있다.
5. 기능별 소유자와 실제 소비자를 근거로 검사·적용 범위를 정한다.
6. 기존 업데이트·인증·권한·백업 계약을 유지하고 중복 관리 경로를 남기지 않는다.
7. 열린 화면에 구성과 코드 변경을 상태 보존과 함께 반영하며, 일시적인 인계 보류는 같은 적용 절차가 재개한다.
8. 전체 이행 표에 미연결 소비자·미완성 상태 인계·제거하지 않은 임시 경로가 없다. 실제 기기 인수 미실행은 완료 조건의 누락으로 남기며 모의 검사로 대체 보고하지 않는다.

성과는 같은 종류의 변경에 필요한 수작업 수정 위치, 빌드·배포 단계, 재시작한 프로세스, 검사 범위와 실제 완료 시간을 비교한다. 자동 생성 파일 수는 수작업 수정 위치와 구분하고, 측정하지 않은 시간·토큰 절감을 주장하지 않는다.

전체 백엔드의 임의 코드 무중단 교체, 모든 화면의 동일 프레임워크 이식, 모든 앱의 별도 다운로드 관리자는 그 자체를 목표로 삼지 않는다. 서두의 판단 기준에 따라 필요한 구조는 이번에 완성하고 효과가 불확실한 확장은 만들지 않는다. 선택한 필수 범위의 모든 소비자 연결·옛 경로 제거·운영 인수를 끝내며, 그 안의 미완성은 난도나 작업량을 이유로 후속으로 빼지 않는다.
