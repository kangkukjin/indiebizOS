## 3. 결정적 실측 — 복잡도가 줄었나, 자리만 옮겼나

액션 수만 세면 속을 수 있다. 액션을 없애고 그 개념을 op 로 옮기면 수치는 줄지만 언어는
그대로다. 그래서 **어휘 표면 총량(액션 수 + op 값 총합)** 을 두 시점에서 쟀다.

| 시점 | 액션 | op 값 총합 | **어휘 표면 총량** |
|---|---:|---:|---:|
| `8e5874b` (149 기준선) | 149 | 349 | **498** |
| 현재 `HEAD` | 142 | 339 | **481** |
| 변화 | −7 | **−10** | **−17** |

**op 값이 액션보다 더 많이 줄었다(−10 vs −7).** 복잡도가 op 축으로 도피하지 않았다는 뜻이다.

감소분의 출처를 분해하면 거의 전부가 한 수술에서 나온다:

| 수술 | 액션 | op | 표면 |
|---|---:|---:|---:|
| 사업 4형제 → `ledger` | −3 | −10 | **−13** |
| 지역정보 3형제 은퇴 | −3 | 0 | −3 |
| `contact` → `neighbor` op | −1 | ±0 | −1 |
| **합** | **−7** | **−10** | **−17** ✓ |

산술이 정확히 맞는다. **오늘 감소의 76%가 `ledger` 통합 하나에서 나왔다.**

## 4. 반증 — 오늘 악화된 곳도 있다

감사는 개선만 세면 안 된다. R2 가 세운 원칙(**한 op 축은 한 개념만 나른다** — 사용자가
`radio_favorite` 를 재생 축에서 잘라내며 명시한 것)으로 오늘 변경분을 다시 재면:

### 4-1. `others:neighbor` 는 축이 더 섞였다

```
이전: neighbor(list·detail·save·delete·favorite·merge) + contact(add·update·delete)  = 2 액션
현재: neighbor(list·detail·save·delete·favorite·merge·contact_add·contact_update·contact_delete)
```
9 op 가 **4개념**(이웃 CRUD / 즐겨찾기 / 신원 병합 / 연락처 하위 CRUD)을 나른다.
액션 수는 1 줄었지만 축 혼재는 늘었다.

> **다만 은퇴 논거 자체는 타당하다** — `contact` 에는 `list` op 이 없었고 전 op 가 부모 id 를
> 요구했으므로 대등한 원장이 아니라 **자식 컬렉션**이었다. 자식을 부모의 op 로 두는 것은
> 옳은 판단이다. 문제는 다음 항목이다.

### 4-2. 같은 부모-자식 관계가 두 곳에서 다르게 처리된다

| 관계 | 처리 | 표현 |
|---|---|---|
| business → item | **store 축의 값** | `[self:ledger]{store:"item", op:"save"}` |
| neighbor → contact | **부모의 op** | `[others:neighbor]{op:"contact_add"}` |

둘 다 "부모 원장에 딸린 자식 컬렉션"인데 문법 자리가 다르다. AI 는 이 둘에서 배운 것을
서로 전이할 수 없다 — **관용구가 두 개 생겼다.** 어느 쪽이 옳은지는 설계 판정 사안이나,
**같은 관계를 같은 자리에 두는 것**이 조합 가능한 언어의 조건이다.

### 4-3. `ledger` 자신이 축 혼재를 물려받았다

`ops = list·detail·save·delete·regenerate·publish·add_image·remove_image` — CRUD 4 +
AI 재생성 1 + Nostr 발행 1 + 파일 첨부 2 = **4개념/1축**. 명사 축(store)은 깨끗해졌지만
연산 축(op)은 그대로다. **절반의 승리다.**

### 4-4. 손대지 않은 축 혼재 (R2 목록 잔존)

| 액션 | op | 섞인 개념 |
|---|---:|---|
| `self:music` | 14 | 조회 / 플레이리스트 원장 / 소스 원장 / 작업 — **4개념, 최악, 그대로** |
| `others:portal` | 12 | 포털 원장 / 회원 CRM / 진열 / 감사 / 설정 |
| `others:showcase` | 10 | 폴더 원장 / 바스켓 원장 — 원장 2개가 한 축에 |
| `others:family_news` | 10 | 발행 / 초안 편집 / 수신함 |
| `self:trigger` | 9 | CRUD / 상태 토글 / 이력 |
| `self:notebook` | 8 | 노트북 원장 / 소스 원장 / 질의 |
| `sense:video` | 7 | 데이터 능력 4 + **yttv 앱 전용 3**(`feed·watch·history`) |

## 5. 조합성 지표 — 자(尺)가 바뀐 것을 먼저 밝힌다

`44c59ce` 가 지표를 **[행동](실사용 증류 205문장) / [교재](전 코퍼스 3,213문장)** 로 갈랐다.
스크립트 자신이 적어 둔 규율이 정확하다 — *"시드는 교재만 올리고 행동은 못 건드린다
(그래서 시딩으로 못 속이는 지표다)."*

**★비교 주의**: `8e5874b` 기준선은 **분리 전 단일 측정**이라 현재의 [교재]와만 같은 자다.
[행동]은 오늘 신설된 계기라 "before"가 존재하지 않는다. 따라서 **"파이프 길이가 2에서
3으로 늘었다"고 말할 수 없다** — 그건 다른 자로 잰 다른 모집단이다.

### 5-1. 같은 자로 잰 것 ([교재] vs 149 기준선)

| 지표 | 8e5874b (149) | 현재 (142) | 판정 |
|---|---:|---:|---|
| 파이프 길이 중앙값 | 2 | **2** | **불변** |

### 5-2. 새 자가 드러낸 것 ([행동] — 비교 대상 없음, 절대값)

파이프 길이도 실사용 3.0 이 코퍼스 2 보다 길다. **AI 가 배운 것보다 더 조합하고 있다.**
이는 언어가 조합을 *허용*하고 있다는 구조적 신호다(코퍼스가 병목이지 문법이 병목이 아니다).

`적용`(each) 문형이 [행동] 1건 · [교재] 12건으로 등장한다. **오늘 이전에는 표현 자체가

## 6. 판정 — "이제 좋은 언어가 되었는가"

### **아니다. 아직은.**

그러나 **오늘 이전과 이후는 종류가 다르다.** 정확히 말하면:

> **좋은 언어의 필요조건 하나를 오늘 획득했고, 충분조건은 아직 아니다.**

**획득한 것 — 언어가 곱셈을 시작했다**
- `[table:each]` + 씨앗 대칭으로 **문형이 늘어나는 경로**가 처음 열렸다. 어제까지의 작업은
  전부 뺄셈(복합어 정리)이었고, 뺄셈은 아무리 해도 언어를 좋게 만들지 못한다 —
  나쁜 단어가 줄어들 뿐이다. 오늘 처음으로 **표현 가능한 문장의 종류**가 늘었다.
- 어휘 표면 498 → 481, 그중 −13 이 `ledger` 하나에서. 명사 복합어를 데이터로 내리는
  헌법("명사의 자리")이 처음 집행됐다.
- 자기상 가드로 **시스템이 자기 크기를 틀리게 알 수 없게** 됐다.

**아직인 것 — 세 가지 구조적 근거**
1. **파이프 길이 중앙값 2 불변**([교재], 같은 자). 문형은 늘었는데 문장은 안 길어졌다.
   여전히 "가져와서 정리해 사람에게" 2단이 지배한다.
2. **미조합 51/142 (35.9%)** — 특히 `others` 11개가 조합 밖이다. 발신 어휘가 파이프에
   거의 안 들어온다. `each` 가 그 문을 열었으나 아직 통과한 것이 1건이다.
3. **축 혼재 7건이 그대로이고 1건은 악화**(§4). 명사 축은 정리를 시작했으나 **연산 축은
   손대지 않았다.** `self:music` 14 op/4개념이 상징적이다 — 이름 하나에 네 개념이
   숨어 있으면 그것은 이미 복합어이고, AI 는 그 op 들을 서로 전이할 수 없다.

### 판정을 뒤집을 조건 (반증 가능하게)

다음 셋이 동시에 관찰되면 "좋은 언어"로 판정을 바꿀 근거가 된다 —
① [교재] 파이프 길이 중앙값 3 이상 ② `others` 미조합 11 → 5 이하
③ 축 혼재 액션(§4-4) 중 최소 절반이 개념당 한 축으로 분리.

## 8. 미이행 제안 재확인

- **`table:of`** (리터럴 생성자에 이름 주기) — P1 로 `each` 는 해결됐으나 `filter`·`sort`·
  `groupby` 앞에 데이터를 놓는 일반형은 여전히 `take{n, items}` 라는 거짓 이름 아래 있다.
- **`table:derive`** (행 단위 필드 계산) — `select`=투영 / `groupby`=집계 / `each`=IBL 실행
  사이의 빈칸. 순수 산술에 고차 실행기(limit 20·외부 호출)를 쓰는 낭비가 남아 있다.
  ★착수 전 `expr` 안전 평가 설계 필요(없이 하면 침묵 실패 계열 재생산).

   조합 시도는 안 보인다. 조합률 22.9% 는 상한 쪽으로 치우쳤을 수 있다.
3. **축 혼재 7건 중 이번에 핸들러를 연 것은 `ledger`·`neighbor` 2건.** 나머지는 op 목록·
   desc 판정이다.
4. **사용빈도·사용계수는 어떤 판정의 근거로도 쓰지 않았다.** 근거는 어휘 표면 총량,
   op 축의 개념 수, 라이브 실행 결과, 지표 4종(전부 구조 지표)이다.
