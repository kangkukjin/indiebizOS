# 웹사이트 유지보수와 배포 검증

`data/guides/web_builder.md`의 상세 절차다. 가이드 크기 제한에 맞춰 유지보수 근거와
시각 검증 절차를 원문 그대로 분리했다. 사이트 갱신·배포 전에 해당 절을 읽는다.

## 사이트는 만드는 일보다 유지하는 일이 크다 (2026-10-30 반성)

2026년 1~10월 홈페이지 관련 요청 82건의 기존 키워드 분류에서는 정본 동기화·재구축 표현이 자주 나타났다.
중복 분류와 앞부분 발췌를 이용한 근사이므로 실패 원인의 빈도나 인과를 입증하지 않는다.
일부 재구축 사례에서 사용자가 내용 손실과 로컬·운영 불일치를 지적했다.
4월 6일 이후 운영 배포 10여 회는 커밋 없이 나갔고, 렌더되지 않는 섹션 파일 30개가 쌓였다.
측정해 보니 첫 화면은 외부 웹폰트 스타일시트에 막혀 모바일 LCP가 13초였다. 근거와 분류는
`projects/홍보/outputs/research_plans/1435ef3792584e17a682a772a6b07eeb/research_plan.md`에 있다.
그래서 화면을 손보기 전에 다음 경계를 지킨다.

- **갱신의 계기부터 가른다.** 정본이 바뀌었는가(내용 신선도), 보기에 불만인가(미감), 동작이 깨졌는가(기능).
  사이트에 정본 판본 기록이 있으면 그 기록 이후 바뀐 정본 문서와 커밋만 대조한다. 기억·레지스트리 수정일·
  "많이 바뀌었다"는 인상으로 기준 시각을 정하지 않는다. 바뀐 정본이 페이지 표현에 닿지 않으면 내용 수정은 없다고 답한다.
  indiebiz-homepage는 `src/content/canon.json`이 기록이고 `npm run canon:check`가 대조한다.
- **고치기 전에 커밋, 배포한 커밋에 태그.** Vercel Hobby 플랜의 즉시 롤백은 바로 직전 운영 배포 하나뿐이다.
  그보다 앞선 상태로 돌아갈 수단은 git뿐이다. 작업 트리의 변경을 소유·범위별로 구분하고 허용된 파일만 커밋한다. 다른 세션의 작업을 일괄 커밋하지 않는다. 커밋 제한이 있으면 diff·지문·복원 사본과 배포 영수증으로 보존하고 미커밋 배포임을 알린다.
  git이 없는 사이트(예: ai-era)는 수정 전에 저장소화하거나 사본을 남긴다.
- **증분 수정이 기본.** 프레임워크 교체나 전면 재작성은 기존 섹션·링크·이미지·문구 목록을 먼저 만들고, 새 결과가 그 목록을
  전부 담는지 대조할 수 있을 때만 한다. 목록 없는 재작성은 내용 손실로 끝났다.
- **렌더되는 경로만 고친다.** 진입 파일(page 등)에서 실제로 불러오는 컴포넌트를 먼저 확인한다. 불러오지 않는 파일은 고쳐도
  화면에 나오지 않는다. 기준점 커밋으로 보존한 뒤 정리한다.
- **자주 바뀌는 사실은 본문에 박지 않는다.** 액션 수 같은 수치는 정본에서 파생하거나 쓰지 않는다. 6월에 옛 수치가 그대로
  게시된 적이 있다.
- **사용자가 준 실제 자료를 먼저 쓴다.** 제공된 화면 캡처가 있으면 그 목록과 배치(몇 장이 어디에)를 확인한 뒤 생성 이미지를 고려한다.
  사용자가 준 파일은 지금 쓰이지 않아도 지우지 않는다.
- **공개 문구는 정본 원문에서.** 새 제목·소개는 사용자 작성 출처가 확인된 원문을 쓴다. README·vision이라는 위치만으로 작성자를 단정하지 않는다. 출처가 불명확하면 기존 문구로 가능한 구조·동작 개선을 진행하고 콘텐츠 공백을 알린다.
- **미리보기 → 측정 → 운영 승격 → 운영 재측정.** 미리보기 배포는 `noindex`가 붙어 SEO 점수가 낮게 나오는 것이 정상이다.
  Lighthouse 한 번은 편차가 크다(배포 직후 73, 이어서 97·98). 판단에 쓰는 값은 두 번 이상 재서 범위로 말한다.
- **성능은 원인부터 읽는다.** 점수가 낮으면 보고서의 렌더 차단 요청과 LCP 요소를 먼저 본다. 외부 CDN 스타일시트(웹폰트)는
  첫 화면을 막는다. 폰트는 프로젝트에 번들하고 한글은 서브셋을 쓴다. LCP 이미지는 지연 로딩하지 않고 우선순위를 높인다.
  기준: LCP 2.5초·INP 200ms·CLS 0.1 이하(web.dev), 본문 대비 4.5:1(WCAG 1.4.3).
- **사람용 면과 AI용 면을 나눈다.** 사람에게는 페이지를, 검색엔진에는 robots·sitemap을, 에이전트에게는 `/llms.txt`(정본 요약과 링크)를 준다.
- **빌드 검사의 환경을 확인한다.** 호스트가 `NODE_ENV=development`를 물려주면 Next.js 운영 빌드가 오류 페이지 사전 렌더에서 실패한다.
  코드 결함으로 판단하기 전에 `NODE_ENV=production`으로 다시 빌드해 가른다.

## 배포 후 시각 검증 (필수)

⚠️ **HTTP 200 ≠ 내용 정확.** `check`의 `screenshot`은 스크린샷을 **찍기만 하고 읽지 않는다.** 캡처 파일이 생겼다고 "통과"로 처리하면, 옛 수치·깨진 이미지·잘못된 카피가 그대로 게시된다 (실제로 stale 숫자가 그대로 배포된 사고의 직접 원인). 아래 단계 **없이 "완료" 선언 금지.**

### 절차

1. 배포 전 변경 대상의 옛 수치·문구·중복 위치와 기존 콘텐츠 보존을 확인한다.
2. 같은 후보의 데스크톱·모바일 화면과 변경된 흐름을 검사한다. 좁은 세로 콘텐츠는 320 CSS px에서 가로 넘침을 확인하고, 메뉴는 짧은 화면과 너비 전환도 검사한다.
3. 탐색 변경은 키보드 진입·활성화·닫기·포커스 복귀·목적지 이동을 확인한다. 일반 탐색 펼침은 비모달 disclosure로 구현할 수 있다. Escape로 닫고 제어 버튼으로 돌아가며, 포커스가 밖으로 나갈 때와 화면 전환 뒤 숨은 요소에 남지 않는지 확인한다.
4. 캡처를 실제로 열어 판독한다. 호스트에서 읽은 동일 화면을 image_read로 중복 판독할 필요는 없다. critic을 쓰면 criteria=web을 명시한다. 자동 접근성 점수는 상태 전이 검사를 대체하지 않는다.
5. 운영 배포 후 같은 주소에서 해당 내용·자산·흐름을 다시 확인한다. 미리보기 승격이 재빌드를 거치는지 공급자 계약을 확인한다. 소스가 같아도 환경·산출물이 같다고 단정하지 않는다.
6. 배포 ID·검사한 소스 지문·검사 결과를 보존한다. 콘텐츠 정본 판본은 실제 대조한 경우에만 **빌드·배포 전에** 기록한다. 탐색·스타일만 수정했다면 콘텐츠 반영일을 임의로 최신화하지 않는다.

- 판독은 보통 전체 화면 1~2장과 변경 영역 1장으로 시작하고, 새 결함에 필요한 곳만 확대한다.
- 지연 로딩 이미지가 빈 캡처에 잡히면 해당 영역을 실제로 스크롤해 로딩·디코딩을 확인한 뒤 다시 판독한다. 이미지 URL의 HTTP 성공만으로 배치·가시성을 인증하지 않는다.
- 캡처 경로는 해당 실행 영수증과 연결한다. 파일명 최신순만으로 다른 실행의 화면을 고르지 않는다.
- 성능은 같은 조건에서 반복 측정하고 편차·LCP 요소·차단 요청을 본다. 실험실 지표와 실제 사용자 지표를 구분한다.
- 자동화된 브라우저 검수는 실물 폰·보조기술·사용자 시험을 대신하지 않는다.

## 2026-11-04 연구에서 확인한 경계

이전 연구의 접근성 100점 보고와 양립하는 상태에서 운영 홈페이지의 Escape 미처리와
모바일 메뉴를 연 채 데스크톱 너비로 바꿀 때 body 스크롤 잠금을 재현했다.
이는 당시 검증을 전부 하지 않았다는 증거가 아니라, 단일 점수·정적 화면으로 상태 전이의
품질을 보장할 수 없다는 직접 사례다. 화면 폭 전환·포커스·닫기를 같은 흐름으로 검사한다.

구축에서는 방문자 과업 → 정보 구조 → 기존 자료 보존을 먼저 연결한다.
content-shop의 재고/진열 분리는 유지할 강점이지만, 좋은 시각 취향과 방문자 중심 정보 구조는
별개다. CMS·프레임워크 이전은 편집·운영 요구가 정당화할 때 선택하며, 한 사례의
실패를 특정 기술의 필연적 결함으로 일반화하지 않는다.
