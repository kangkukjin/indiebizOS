## 1. 목표와 이번 작업의 경계

IBL은 몸 중심의 실행 어휘를 조직한다. 세계의 지도는 세계의 개념·방법·자료원·판정 기준을 조직하여, 사용자가 몰랐던 가능성까지 생각과 행동에 연결한다. 검색된 낱말뿐 아니라 **그 낱말의 구조적 위치와 관계**가 전달 단위다. 이는 비전의 ‘판단을 더 멀리 닿게 한다’와 ‘어휘는 연결을 흡수한다’를 잇는다.

이번 산출물은 비전 요약 반영과 이 구현계획이다. 전 분야 어휘 구축, 코어 변경, 색인 재생성, 모델 실험, 배포는 이번 완료 조건이 아니다. 아래 데이터·함수·예산·테스트 이름 중 ‘제안’으로 적힌 것은 향후 구현 대상이다. 이 문서의 설계 선택은 사용자 확정 판정과 구분한다.

유지할 원칙:
- 전체 카탈로그를 검색·열람할 수 있다. 턴의 문맥 예산은 전달량을 조절하며 어휘의 접근 권한이나 활성 상태를 줄이지 않는다.
- IBL 전체 어휘 소개를 작업별로 축소하거나, 사용 빈도로 어휘를 끄지 않는다.
- 새로운 세계 개념을 IBL 액션으로 하나씩 만들지 않는다. 기존 액션·가이드·검증된 스크립트와 연결한다.
- 구조가 존재하고 전달되는 것은 검증 가능한 구현 사실이다. 구조가 답변 품질을 높이는지는 별도 실험 가설이다.
- 지도는 세계의 수정 가능한 설명이며 명령·권한·실시간 사실의 대체물이 아니다.

## 3. 구조의 원칙 — 패싯, 계층, 관계를 구분한다

### 3.1 서로 다른 관점으로 같은 대상을 찾는다

초기 탐색 관점은 분야·문제 유형·방법·자료원·판정 기준이다. 이 다섯 가지를 하나의 고정된 부모→자식 사슬로 만들지 않는다. 예컨대 ‘간호 인력 배치’는 분야로는 의료·운영, 문제로는 일정·자원배분에 걸치며, 방법·자료·판정 기준은 각각 연결된 다른 노드다.

노드에는 kinds와 통제된 facets를 둔다. kind는 concept/problem/method/tool/resource/criterion/condition 중 주된 종류 하나, facets는 domain/problem_type/representation/region/time_scale 같은 독립 관점의 ID 배열이다. ‘방법·자료원·판정 기준’ 탐색 화면은 해당 kind와 관계에서 파생한다. 동일 사실을 별도 태그·관계 두 곳에 손으로 중복 기입하지 않는다. 패싯 값의 정의·포함 경계·별칭도 사전에 둔다.

분야 이름을 바꿔도 대상 ID는 유지한다. 여러 분야에 속하면 여러 facet 값을 붙이며 노드를 복제하지 않는다. 다른 뜻의 동음이의어는 ID·scope_note로 구별한다.

### 3.2 계층은 직접 상하위, 연관은 횡단 연결

| 관계 | 의미·방향 | 제약 |
|---|---|---|
| broader | 하위 개념 → 직접 상위 개념 | 같은 개념 체계의 일반화/특수화로 한정. 여러 부모 허용. 자기 간선·순환은 이 프로젝트에서 금지한다. |
| narrower | 상위 → 직접 하위 | broader의 역관계로 계산; 양쪽 수기 편집 금지. |
| related | 의미 있는 일반 연관 | 대칭, 비추이. 이유를 적고 동일 계층의 조상·자손에는 쓰지 않는다. |
| implements | 도구 → 방법 | ‘OR-Tools는 제약 프로그래밍의 하위 개념’ 같은 잘못된 계층을 막는다. 도구가 방법을 구현한다는 별도 관계다. |
| addresses | 방법 → 문제 | 해결을 시도할 수 있다는 뜻; 성공 보장이나 사용 가능성 선언이 아니다. |
| requires / applicable_when / unsuitable_when | 방법 → 입력·조건 | 필수 입력/전제, 적합 조건, 부적합 조건을 구별. 조건은 검토해야 할 주장이다. |
| alternative_to | 방법 ↔ 방법, 문제·조건으로 한정 | 같은 목표에서 검토할 대안. 무조건 동등하거나 상호 교체 가능하다는 뜻이 아니다. |
| complements | 방법 ↔ 방법, 목표·조건으로 한정 | 함께 쓸 때의 역할을 설명. 실행 순서는 별도 절차에 둔다. |
| uses_source / evaluated_by | 방법·문제 → 자료원 / 판정 기준 | 데이터 공급과 결과 평가를 계층 관계로 오인하지 않는다. |

broader 자체를 추이 간선으로 복제하지 않는다. 조상 조회는 별도 파생 closure로 계산하고 직접/간접·깊이·경유 경로를 표시한다. related를 이어 related의 related까지 자동 확장하지 않는다. SKOS가 모든 순환을 일률 금지한다고 주장하지 않는다. 순환 금지는 이 지도의 탐색·설명 품질을 위한 더 엄격한 로컬 규약이다.

위 사용자 정의 관계는 SKOS 표준 어휘가 아니다. 필요한 경우 별도 namespace로 내보낸다. ‘조건부 대안’ 같은 관계를 무조건 skos:related의 하위 속성으로 선언해 계층과 충돌시키지 않는다. SKOS는 계층·연관 구분의 참고이며 완전한 OWL/RDF 추론기나 그래프 DB 도입은 초기 요구가 아니다.

## 4. 데이터 모델과 출처 관리

정본은 data/knowledge_catalog/world.yaml의 version 2로 확장한다. 최초에는 한 파일로 검토하되 1500줄 한도 전에 같은 디렉터리의 분야별 YAML로 분할하고 world.yaml을 매니페스트로 둔다. 모든 조각을 하나의 불변 snapshot으로 읽고, SQLite는 재생성 가능한 검색·인접 조회 색인만 맡긴다.

제안 스키마의 레코드:
- Node: id, kind, labels{언어:대표명}, aliases{언어:[별칭]}, summary, scope_note, facets, evidence_ids, execution_refs, legacy_path.
- FacetValue: id, facet, label, definition, parent_id(동일 facet 내에만), evidence_ids.
- Edge: id, subject, predicate, object, scope{problem_ids, condition_ids}, rationale, evidence_ids, status, reviewed_at.
- Evidence: id, source_kind(user_decision/local_doc/external_doc), path 또는 url, locator(절/anchor), quote 또는 claim_summary, checked_at, content_hash(로컬), author_or_owner, status.
- ExecutionRef: kind(ibl_action/idiom/script/guide), target, purpose, required_inputs, expected_output, evidence_ids. 키·토큰·로그인 상태는 저장하지 않는다.
- Snapshot: schema_version, revision, nodes, edges, facets, evidence, generated_indexes. revision은 모든 정본 조각과 검색/관계 정책 버전을 반영한다.

status는 proposed/verified/disputed/retired로 구분한다. verified는 해당 출처와 대조했다는 뜻이며 영구적 진실이나 도구 실행 가능성을 뜻하지 않는다. 사용자 설계 결정은 owner와 원문 근거를 기록한다. 모델이 제안한 관계는 proposed로 시작하고, 권위 있는 출처·사용자 선언과 대조된 뒤 승격한다. 추정 관계는 사실처럼 주입하지 않는다.

기존 source.path는 ‘이 항목을 소개하는 문서’라는 provenance다. 그 문서가 모든 적용 조건을 입증한 것으로 승격하지 않는다. 새 관계는 관계별 locator·근거를 갖는다. 충돌하는 출처는 덮어쓰지 않고 disputed로 표시하며 결정적인 추천의 근거에서 제외하거나 충돌을 함께 전달한다. 출처가 바뀌면 해시 변경을 검출해 재검토 대상으로 돌린다. 외부 URL은 checked_at과 인용 대목을 남기며 갱신 전 최신 사실로 부르지 않는다.

예시 데이터 조각(미구현 설계 예시; 표시한 ID·근거는 향후 함께 작성할 대상):
~~~yaml
version: 2
nodes:
  - id: method.cp_sat
    kind: method
    labels: {ko: "CP-SAT 제약 최적화"}
    aliases: {ko: ["근무표 제약 최적화"]}
    summary: "이산 변수의 제약과 목적을 표현해 배치를 탐색하는 방법"
    facets: {domain: [domain.operations], problem_type: [problem_type.scheduling]}
    evidence_ids: [ev.cp_sat_docs]
  - id: ortools
    kind: tool
    labels: {en: "OR-Tools"}
    summary: "최적화 모델을 구성하고 푸는 도구 모음"
    legacy_path: ["계산", "최적화"]
    evidence_ids: [ev.legacy_ortools]
edges:
  - id: edge.ortools.cp_sat
    subject: ortools
    predicate: implements
    object: method.cp_sat
    rationale: "도구와 방법의 연결; 하위 개념 관계가 아님"
    evidence_ids: [ev.cp_sat_docs]
    status: proposed
~~~
이 조각만으로 빌드하지 않는다. ev.*·facet 대상까지 채운 완전한 fixture에서 참조 무결성을 검사한다. 도구/방법/문제/조건/기준을 한 계층에 섞지 않는 형태를 보여주기 위한 예시다.

## 5. 자연어에서 검색·관계 확장·주입까지

제안 파이프라인:

사용자 질문 → QueryContext → 전체 지도에서 후보 검색 → 의미별 관계 확장 → 예산에 맞춘 구조 묶음 → 의식·실행에 같은 묶음 전달 → 근거 열람·IBL 계약 확인 → 실행.

### 5.1 질문의 진입

QueryContext는 원문, 현재 명시 제약, 목적 표현, 자료 형태, 시간·지역, 보조 대화와 각각의 출처를 보존한다. 최초에는 규칙·별칭·기존 대화 메타데이터로 구성하고 매 턴 분류 모델을 하나 더 부르지 않는다. 과거 발화를 더할 때 현재 정정을 우선하며, 현재 질문과 보조 질문의 점수를 따로 보존한다. 도구 이름이 없는 ‘주말 근무가 편중되지 않게 해줘’도 problem·criterion 별칭으로 들어갈 수 있게 한다.

facet은 후보 정렬과 다양성 선택의 단서다. 추정한 분야가 틀려도 전체 검색을 막지 않는다. 사용자가 명시한 자료 범위와 권한은 지킨다. 명시 범위 밖 대안은 ‘범위 밖 참고’로 구분하고 실행하지 않는다.

### 5.2 검색: 어휘 매칭과 의미 검색의 책임 분리

우선 현재 이름·별칭·설명 검색과 FTS 폴백을 유지하고, 모든 종류의 노드에 확장한다. problem·condition·criterion도 검색되므로 도구명 미언급 질문이 진입점을 갖는다. entry.path의 문자열 점수와 별도로 facet·정의·scope_note를 검색 필드에 넣는다.

의미 검색은 후속 단계에서 선택적으로 추가한다. 현재 코드에 미구현인 semantic_enabled를 성공처럼 표시하지 않고, 오프라인 임베딩 색인과 질의 임베딩 제공자·버전·차원을 명시한다. 어휘/의미 후보를 각각 보존하고 RRF 같은 결정적 순위 결합을 적용하되 점수는 확률로 부르지 않는다. 고유 이름은 어휘 경로로 보호한다. 모델 적재·대규모 색인 생성은 질문 경로에서 하지 않는다. 사용할 수 없으면 lexical_fallback과 원인을 신고한다.

질의 임베딩의 콜드스타트·호출·비용도 측정한다. 동일 묶음에 주입될 결과가 같으면 의식·실행에서 검색을 다시 하지 않는다. 초기 구조 구현의 검증을 의미 검색 도입에 종속시키지 않는다.

### 5.3 관계 확장: 왜 이 노드를 더하는가

후보에는 seed_id·retrieval_reason·score_components를 남긴다. 각 seed에 대해:
1. 직접 상위와 이해에 필요한 조상 경로를 붙인다. 다중 부모가 있으면 질문의 facet에 맞는 경로를 우선하고 다른 경로 수·열람 손잡이를 남긴다.
2. 필수 입력·부적합 조건·판정 기준을 먼저 붙인다. 관계 조건이 질문에서 확인되면 matched, 반하면 contradicted, 정보가 없으면 unknown으로 표시한다. unknown을 참으로 만들지 않는다.
3. 같은 문제의 대안·보완·자료원을 제한된 수로 추가한다. 단순 형제 노드는 ‘같은 부모 아래’라는 구조 사실만 전달하고 대안이라고 추정하지 않는다.
4. 일반 related는 마지막 우선순위로 1홉만 추가한다. 모든 노드는 ID로 중복 제거하고 경유 간선은 보존한다.

초기 예산 제안: seed 최대 4개, typed relation 1홉, 조상 최대 3단, 총 노드 최대 16개, 간선 최대 20개. 이는 실험 시작값이며 품질이 증명된 최적값이 아니다. 조건 없는 무한 그래프 순회는 하지 않는다. 단순 인기·사용 빈도로 확장 대상을 결정하지 않는다.

### 5.4 구조 묶음과 전달

제안 WorldContext DTO는 revision, query_provenance, seeds, nodes, edges, paths, evidence_refs, open_refs, omitted{ids/count/reason}, conflicts, retrieval_mode를 가진다. 의식과 실행은 이 DTO의 같은 revision·digest에서 렌더한 조각을 공유한다. 기존 method_map XML 태그는 호환을 위해 유지하고 내부 표현에 버전을 둔다.

한 노드의 최소 전달 단위는 ID·이름·종류·짧은 뜻·직접 관계·그 관계의 이유/조건이다. 노드와 간선을 서로 떨어뜨려 잘라 의미를 바꾸지 않는다. 출처는 짧은 evidence ID와 조회 주소로 연결하고, 자세한 원문은 요청 시 읽는다.

현재 600자 상한으로는 이 계약을 보장하기 어렵다. 구조 모드는 별도 max_tokens(초기 실험안 1200)와 렌더 문자 안전상한을 설정 가능하게 하며 현재 4/600 clamp를 그대로 통과시키지 않는다. 토크나이저를 쓸 수 없으면 문자 기반 추정임을 기록한다. 예산을 넘으면 일반 연관→부차적 대안→낮은 순위 seed 묶음 순으로 뺀다. 추천의 필수 조건·한계를 보존할 수 없는 seed는 묶음째 빼고 이유를 신고한다.

자동 전달에서 생략된 노드도 열 수 있어야 한다. 새 IBL 낱말 대신 등록 스크립트 하나에 search/open/ancestors/neighbors 동작을 두는 방안을 사용한다. 반환은 items와 revision·truncated·omitted, 다음 조회 인자다. self:script로 호출하고 self:read로 정본·근거 문서를 열 수 있다. 실제 op·인자는 구현 단계에서 기존 script 계약과 대조해 고정한다. 잘못된 ID, 숨겨진 권한 범위, 0건을 구별하며 전체 검색 통로를 계속 제공한다.

자동 구조 주입이 실패하면 원인을 기록하고 기존 이름 전달로 폴백한다. 권한 오류에는 범위를 넓히는 폴백을 하지 않는다. 모든 렌더 문자열은 escape하고, 외부 설명·근거가 프롬프트의 명령으로 승격되지 않게 데이터 영역에 넣는다.

## 6. 대표 질문에서 전달되는 구조

**설계 예시이며 실제 생성·비교 결과가 아니다.**

질문: “직원 12명의 다음 달 근무표를 짜고 싶다. 하루 3명이 필요하고, 연속 근무는 3일까지, 주말 근무도 공평하게 나눠줘.”

이름 위주 대조군 예시:
> 최적화 / OR-Tools — 인원·시간·순서 제약을 만족하는 배치·경로·일정 최적화

구조 전달군의 의미 예시:
~~~text
질문에서 찾은 문제: 인력 일정 배치
관점: 운영관리 / 일정·자원배분 / 날짜별 이산 배정
개념 경로: 제약 최적화 → 제약 기반 일정 배치
후보 방법: CP-SAT
  addresses → 인력 일정 배치
  requires → 직원별 근무 가능일·기간·필수 인원 정의 [미확인 입력]
  applicable_when → 배정을 이산 변수·제약으로 표현할 수 있음 [검토 필요]
  evaluated_by → 매일 인원 충족, 연속 근무 위반 0
  evaluated_by → 주말 배정 편차 [‘공평’의 의미는 사용자와 정할 사항]
도구: OR-Tools — implements → CP-SAT [설치/현재 계약 미확인]
대안: 혼합정수계획 — 같은 배치 문제를 선형 제약으로 표현할 때 비교
보완: 제약 충족 여부 독립 검사 — 생성 결과가 모든 강제 조건을 지키는지 확인
자료: 직원별 가용일 표, 대상 월의 실제 날짜·주말 구분
다음 확인: 다음 달의 연월, 휴무 조건, 공평의 기준
근거/다른 상위 경로/생략 대안: 각 ID로 열람 가능
~~~

이 예시의 이점은 도구 이름을 떠올리는 데서 끝나지 않고 **실행 전 필요한 입력과 결과를 판단할 기준**을 드러낸다는 데 있다. 이것이 실제 오류 감소로 이어지는지는 아직 측정하지 않았다. 예시 관계와 방법 설명은 실제 카탈로그에 올릴 때 공식 문서로 검토한다. ‘공평’의 기준은 지도에서 일방적으로 확정하지 않는다.

실행 접점은 다음과 같다. 먼저 가용일 표를 self:read로 읽고 table 변환자로 입력을 정리한다. 기존 IBL만으로 닫히는 부분은 그 조합을 사용한다. 최적화 솔버가 필요한 부분은 설치 상태·API 문서를 확인하고, 허용된 실행 통로로 검증한 뒤 반복 절차를 self:script에 등록한다. 그 결과를 items로 돌려 table 처리와 독립 제약 검사로 잇는다. 검증 전의 가상 IBL 코드나 존재하지 않는 idiom을 지도에 넣지 않는다.

두 번째 최소 검증 사례는 “동네 카페 매출이 떨어졌는데 원인을 알고 싶다”처럼 분야·문제·자료·판정이 여러 갈래인 질문으로 둔다. 이때 상권 통계·자체 매출·계절성 분석은 서로 다른 출처와 역할을 갖고, 상관관계를 원인으로 단정하지 않는 기준도 전달되는지 본다. 이 사례 역시 실제 자료 수집은 이번 범위 밖이다.

## 7. 단계별 변경 대상·담당·검증·멈춤선

## 8. 기존 데이터 이행과 실패 복구

1. v1의 id는 그대로 유지한다. name/hint/aliases/source.path는 대응 v2 필드로 손실 없이 옮기고 원래 path는 legacy_path에 보존한다.
2. path의 인접 문자열을 무조건 broader 간선으로 바꾸지 않는다. 현재 path에는 분야·행동·대상이 섞일 수 있다. 우선 legacy 분류 멤버십으로 보존하고 검토된 가지에만 facet/계층 ID를 배정한다.
3. source.path에서 소개 문서 Evidence를 만든다. 관계 근거는 별도로 작성한다. 자동 생성된 관계는 proposed이며 검색할 수 있어도 검증된 추천 관계로 쓰지 않는다.
4. ID alias/migration 표, 누락 필드·중복·해소 실패 보고서를 만든다. dry-run 검토 후에만 정본을 바꾸고 파생 색인을 임시 파일→원자 교체로 만든다.
5. 양식이 바뀌는 동안 v1·v2 로더를 함께 지원하되 정본 쓰기는 한 곳만 둔다. revision이 다른 노드와 간선을 섞지 않는다. 외부 출처 장애가 있어도 기존 검증 자료의 기준 시각을 보존한다.
6. 문제 발생 시 기능 모드를 names로 되돌리고, v2 데이터는 삭제하지 않는다. 데이터 자체 오류면 해당 작업 커밋과 그에 대응하는 정본 스냅샷으로 복구한다. 다른 세션 변경을 포함한 저장소 전체 reset은 하지 않는다. 재생성 가능한 색인은 정본에서 다시 만든다.

빈 그래프는 관계가 없다는 뜻이지 해당 세계에 관계가 없다는 뜻이 아니다. 누락·검토 중·기각·출처 충돌을 구별해 표시한다.

## 9. 검증 — 네 가지 성공을 따로 판정한다

### 9.1 검색 성공

노드 retrieval Recall@k·Precision@k, 문제 이름→방법/도구의 도달 여부, 고유명 오탐, 미등록 질문의 정직한 0건, 분야 횡단 누락을 검사한다. 정답은 하나의 도구명이 아니라 허용 가능한 seed 집합으로 작성한다. 라벨을 보완한 개발 질문과 최종 평가 질문을 분리한다. 이 지표가 높아도 구조 전달이나 답변 품질 성공으로 부르지 않는다.

### 9.2 구조 전달 성공

gold 구조에서 필요한 상위 경로·적용 조건·대안·기준이 전달됐는지, 방향/종류가 맞는지, 모든 참조가 해소되는지, 조건이 불명인데 참으로 바뀌지 않았는지 검사한다. 생략·다중 부모·출처 충돌·stale revision·과도하게 연결된 노드·긴 한국어·escape를 포함한다. 자동 품질 관문은 참조 무결성 100%, 잘못된 계층/방향 0, 추천의 필수 조건 침묵 절단 0으로 둔다.

### 9.3 실제 답변·행동 품질

비교를 두 겹으로 수행한다.
- 표현 효과 대조: **같은 seed·확장 노드 집합**을 고정하고 A는 이름만, B는 이름·위치·관계·조건을 전달한다. 선택된 노드 수 차이가 효과인 것처럼 오인하지 않는다.
- 현행 대비: 현재 names+hint renderer와 새 전체 파이프라인을 비교한다. 추가 후보를 발견한 효과와 구조를 표현한 효과를 별도 표로 낸다.
- 보조 대조: 같은 토큰 예산에서 목록+설명을 준 C를 넣어 ‘텍스트가 더 많아서’와 ‘관계가 있어서’를 구별한다. 필요하면 전달량을 동일하게 맞춘 반복도 한다.

질문·모델/제공자 버전·기어·도구 권한·자료 스냅샷·온도·가능한 seed·후속 질문 응답을 고정하고 실행 순서를 무작위화한다. 비결정적 모델은 쌍별 반복을 한다. 이름을 알고 묻는 질문만 쓰지 말고 목적만 있는 질문·조건 충돌·다분야·새 주제 전환도 포함한다.

가려진 출력으로 적합한 방법 선택, 조건 누락, 근거 충실성, 실행 가능성, 사용자 판단 여지, 허위 능력 주장, 최종 결과의 제약 충족을 평가한다. LLM 판정만 정답으로 삼지 않고 골드 기준·결정적 검사와 사람의 표본 검토를 함께 쓴다. 동일 질문의 차이·분산·승/무/패·실패 예시를 보고한다. 표본이 작으면 탐색적 결과로 표시한다.

초기 채택 제안 기준: 사전에 정한 핵심 과제군에서 정확성·조건 보존이 악화되지 않고 적어도 한 목표 지표가 개선되어야 한다. 통계적으로 불확실하면 ‘효과 미확인’으로 남기고 전면 채택의 근거로 삼지 않는다. 사용자의 실용 판단 기준은 모델 평가지표로 대체하지 않는다.

### 9.4 비용

검색/확장/렌더 지연 p50·p95, 입력·출력 토큰, 캐시 토큰, 임베딩 비용, 추가 모델/도구 왕복, 최종 완료까지 시간·재시도·사용자 정정량을 기록한다. names 모드 대비 구조 추가 비용과 전체 작업 비용을 모두 본다. 콜드/웜 캐시를 분리하고, 문자 수를 토큰 실측으로 부르지 않는다.

예산 값은 실험 전에 잠근다. 초기 1200토큰은 상한 제안이며 비용 개선 주장이 아니다. 품질이 같은 결과에서 시간·토큰이 줄거나, 추가 비용 대비 사용자 기준의 품질이 나아질 때만 실용 이익을 주장한다.

### 9.5 구현 검증과 마무리

단계별 단위 테스트 뒤 통합 테스트를 수행한다. backend 전체 회귀 명령은 .venv/bin/python3 -m pytest backend/ -q이다. 카탈로그 --check, 층·모듈 충돌·1500줄·은퇴 계약 관문을 통과하고 backend 변경 시 폰 번들도 재생성한다. frontend를 실제 바꿀 경우에만 npx tsc -p tsconfig.app.json을 추가한다. 실행 못 한 검사와 원인은 최종 보고에 남긴다.

마지막에는 변경 대상·이행 결과·네 검증 축·잔여 한계를 통합해 사용자에게 보고하고, 본인 변경 경로만 정본 main에 커밋한다. 좋은 검색 점수만으로 사용자 목표 완료를 선언하지 않는다.
