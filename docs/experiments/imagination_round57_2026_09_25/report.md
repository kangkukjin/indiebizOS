## 갭 원장과 근본 원인

### B57-1 — 평가의 성공·실패·조기 반환이 서로 다른 증거 전달 경로를 썼다 (수리)

최소 재현:

```ibl
$rows=[table:take]{items:[],n:1}
$total=reduce($rows,0,($a,$r)=>$a+$r.amount)
return evidence($total)
```

실측: 전체 trace에는 table:take invoke가 있지만 반환 proof에는 없다.
반복 첫 회차의 조회 후 다음 회차 return, 실패한 조건·산술·필드·컨테이너 평가,
finally 실행 후 원래 오류 재전파에서도 같은 누락을 회귀로 격리했다.
콜백이 누적값을 무시하는 비어 있지 않은 reduce도 목록의 조회 근거를 잃었다.

원인은 값 계산이 아니라 **문형마다 성공 값의 부모만 수동 연결하는 실행기 구조**다.
eval 공통 경계가 실제 평가한 자식과 직접 발생한 사건을 수집하고, 정상 값·Returned·Fault
모두에 연결한다. 일반 Python 예외를 VALUE로 바꾸는 경로도 동일하게 기록한다.
전역 trace 전체를 결과에 붙이지 않으므로 무관한 선행 문장·미선택 분기까지 섞지 않는다.

### B57-2 — 병렬 실패 집계가 성공 가지의 증거만 부모로 연결했다 (수리)

T05의 두 원천 모두 실제 조회했지만, coverage의 부모는 성공 결과 한 개뿐이었다.
실패한 가지의 설명은 details에 존재해도 evidence DAG에서 원래 호출로 이어지지 않았다.
fanout의 합류점에서 성공 결과와 **모든 실패의 증거 루트**를 함께 연결한다.
작업자별 평가 범위는 thread-local로 격리하고 이미 시작한 가지의 종료 대기·원래 인덱스·
미처리 표시·권한/취소/예산의 비포획 규칙은 유지한다.

### B57-3 — 분기·반복·catch 내부에서 대입한 값은 실행 조건을 잃었다 (수리)

부류 점검의 최소 재현:

```ibl
$rows=[table:take]{items:[1],n:1}
[if:len($rows)>0]{$x=1}[else]{$x=2}
return evidence($x)
```

수리 전에는 x의 근거에서 조회가 사라졌다. if/case/repeat/catch의 제어 근거를 실행 범위로
전달하여 내부 변수 대입과 병렬 작업자에서도 보존한다. 반복의 마지막 while/until 판정도
반복에서 갱신된 값에 연결한다. 반복 몸통의 루트가 이전 회차를 가리키게 하여 모든 옛
부모를 매 단계 복제하는 제곱 증가를 피한다.

세 항목 모두 같은 도메인의 특례가 아닌 공통 실행 의미 수리다. 새 문법·낱말·기존 판본
계약을 추가하거나 바꾸지 않았다. 근거 지문과 사건 연결은 의도적으로 바뀐다.
