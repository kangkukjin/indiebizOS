## 갭 원장과 근본 수리

### B61-1 — 조건부 타입을 값의 대안으로 처리하지 않는 검사

최소 재현: `[if:true]{$x=10}[else]{$x="대기"}; return f"${x}"`.
양쪽 값은 각각 허용되지만 검사기는 합쳐진 Union이라는 바깥 종류만 보고 보간을 거절했다.
목록/문자열 인덱스도 같은 구조였고, + 및 숫자 피연산자 검사에도 직접 종류 분기가 있었다.

공통 타입 모듈에 대안 순회를 두고 Union을 평탄화·중복 제거한다. 보간은 기존 공통 호환 검사를
사용하고 필드/인덱스는 각 가능한 수신값의 계약을 검사한다. +는 허용되는 대안의 실제 연산을
실행 시 확인하며, 다른 숫자 연산은 불가능한 대안을 검수에서 거절한다.
같은 접근 경로 조사에서 발견한 레코드의 동적 문자열 키도 필드 존재를 실행 시 확인하도록 했다.
잘못된 구조의 보간·인덱스·숫자 연산은 통과시키지 않는다. 새 값 종류·연산자·어휘는 없다.

### B61-2 — 이미 반환한 경로 뒤의 코드가 반환형을 오염

최소 재현: `[def:f](){return {id:"a"}; return "종료"}; $r=[fn:f]{}; return $r.id`.
실행기는 첫 return에서 끝나지만 검사기는 모든 문장의 반환형을 실제 도달 결과처럼 합쳤다.
따라서 유효한 Record 반환이 Text와 섞여 후속 필드 접근을 거절했다.

공통 sequence 분석에서 무조건 반환한 뒤의 문장은 별도 정적 검사 범위로 옮기고, 실제 반환형과
진행 환경에서는 제외한다. 죽은 코드의 미정의 변수·예약 변수 쓰기·finally return 검사도 유지한다.
if/case/try뿐 아니라 반드시 한 번 실행되는 양수 반복·until의 조기 반환도 인식한다.
함수·each·병렬 가지·프로그램의 반환 프레임을 각각 검사했다. 실행기의 반환 의미는 바꾸지 않았다.

### B61-3 — catch가 진입 시 타입을 읽는다고 오판

최소 재현: `$x=0; [try]{$x={score:70}; 1/0}[catch]{return $x.score}`.
실행기는 같은 프레임의 x를 바꾸지만 검사기는 catch를 try 진입 시 환경으로만 검사했다.
정상적인 복구는 거절했고, 반대로 예전 Record가 숫자로 바뀐 뒤의 잘못된 접근은 검수에서 놓쳤다.

try 본문에서 바뀔 수 있는 기존 변수는 catch에서 Unknown으로 넓혀 실제 값을 검사한다.
finally도 본문·catch가 중간에 실패한 상태를 볼 수 있으므로 같은 원칙을 적용한다.
대입 이전/이후 실패·중첩 if/case/repeat/try·복구 도중 실패를 대조했다.
실패 전에 정의됐다고 보장할 수 없는 새 변수는 여전히 UNBOUND이며, 잘못된 실제 값은
실행 시 FIELD_TYPE 등으로 실패한다. 변수 롤백이나 숨은 기본값을 도입하지 않았다.
