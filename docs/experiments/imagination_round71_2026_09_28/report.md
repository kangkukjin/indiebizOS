## 갭의 원장

### B71-1 ★최우선 — 함수 이름의 유일성을 **읽을 때 전역 예외로만** 집행한다 (저장 한 번이 판본 2 실행 전체를 멈춤)

- **요약**: `ibl_v2_store.definitions()`는 관용구 별칭(`ibl_examples.alias`)과 저장본(`data/workflows/*.yaml`)을 합치며 이름이 겹치면 `Fault("DUPLICATE_LIBRARY")`를 **던진다**. 그런데 `save`는 겹침을 보지 않는다(`known[name] = source`로 덮어쓴 사전으로만 검사). 그래서 겹치는 이름의 저장은 성공하고, 그 뒤 `handle_request`가 매 실행마다 부르는 `definitions()`가 던져 **그 함수와 무관한 모든 판본 2 프로그램**이 실패한다.
- **최소 재현(격리)**: `save [def:IT71_배수]($x){return $x*2}` → `save [def:IT71_배수]($x){return $x*3}` with `workflow_id:"it71-v2"` → `return 1+1` 실패 "같은 판본 2 함수 이름이 두 개입니다: IT71_배수". 관용구 이름(`[def:정렬해추리기]`)으로 한 번 저장해도 같다.
- **영향**: workflow.md가 "의미가 바뀌는 이행은 **새 ID로 저장**하고 호출자를 옮긴다"고 가르친다 — 이름을 바꾸라는 말이 없으므로 그대로 따르면 T18이 된다. 한 번의 저장이 예약·앱·모델 턴의 판본 2 실행을 동시에 멈추고, 오류 문구는 실행한 프로그램과 무관한 이름을 말한다.
- **뿌리**: 불변식(이름 하나에 정의 하나)의 집행 자리가 **쓰기가 아니라 읽기**이고, 읽기에서의 위반이 **국소화되지 않는다**. `list_workflows`는 이미 "깨진 원장 항목을 조용히 감추지 않되 목록 전체를 죽이지 않는다"를 지키는데 해소기(`definitions`)만 그 규율 밖이다.
- **제안(수리성)**: ①쓰기에서 막는다 — 다른 저장 ID나 관용구가 가진 이름이면 `save` 거절(같은 ID 덮어쓰기는 개정), 문구에 새 이름 예시. ②읽기에서 국소화 — 겹친 이름은 해소 사전에서 빼고 출처를 기록, 그 이름을 **부르는 호출 자리만** `DUPLICATE_LIBRARY` 진단(전용 안내 포함). 무관한 프로그램은 돈다. describe·목록도 같은 기록을 본다. 가드: 다른 ID 같은 이름·관용구 이름·디스크 손 복사 겹침·같은 ID 재저장(허용)·무관 프로그램 생존·겹친 이름 호출 진단.

### B71-2 저장 정의의 개정·삭제가 **호출자를 보지 않는다** (workflow.md "호출자의 계약을 확인한다"가 거짓)

- **요약**: `save`는 새 정의 하나만 검사하고, `delete`는 파일만 지운다. 다른 저장 정의가 그 함수를 부르고 있어도 둘 다 조용히 성공하고, 호출자는 다음 실행에서 `MISSING_ARGUMENT`·`등록된 함수가 없습니다`로 죽는다(목록에는 `runnable:false`로 뒤늦게 보인다).
- **최소 재현**: T05의 성적표(`[fn:IT71_등급]{s:$it}`)가 있는 상태에서 `save [def:IT71_등급]($점수){…}` → 성공 → `[fn:IT71_성적표]{목록:[95]}` → `MISSING_ARGUMENT: 필수 인자 누락: 점수` + `UNKNOWN_ARGUMENT`. T09: 성적표가 부르는 `IT71_등급2`를 `op:"delete"` → "삭제 완료".
- **영향**: 교재(12_ibl_only "기존 저장 정의를 고칠 때도 새 정의를 따로 검사한 후 호출자를 전환한다")와 workflow.md("`op:"save",workflow_id:"기존 ID"`: 현재 판본의 정의 변경. 호출자의 계약을 확인한다")는 이 확인이 있다고 말한다. 모델은 그 말을 믿고 제자리 개정을 하고, 고장은 개정한 턴이 아니라 **다음에 호출자를 쓰는 누군가**(예약 발화·앱)에게 나타난다.
- **뿌리**: 저장소가 정의들 사이의 **호출 관계를 모른다** — 쓰기 연산이 자기 항목만 검사하는 구조. 컴파일러는 이미 저장 함수의 본문을 해소하므로 판정 도구는 있다.
- **제안(수리성)**: 쓰기 연산(save·delete) 앞에서 영향받는 호출자(원문이 `[fn:이름]`을 전이적으로 부르는 저장 정의)를 **개정 전/후 사전으로 각각 컴파일**해, 전에는 되고 후에는 안 되는 호출자가 있으면 거절한다(이미 깨져 있던 호출자는 막지 않음). 거절 문구는 호출자 이름·첫 진단·교재의 이행 순서(새 이름 저장 → 호출자 전환 → 옛 정의 삭제)를 말한다. 새 인자·새 op 없이(강제 플래그 없음) 교착도 없다 — 이행 순서가 항상 열려 있다(T08이 실증). 가드: 인자 개명·반환형 변경·전이 호출자·삭제·호출자 없는 개정(허용)·이미 깨진 호출자(허용)·이행 순서 성공.

### B71-3 중첩 판본 2 실행·저장의 실패가 **바깥 경계에서 진단을 잃는다**

- **요약**: `[self:workflow]{op:"run"|"save"}`는 안쪽에서 판본 2 컴파일·실행을 하고 실패 봉투(`issues` 또는 `diagnostic`)를 돌려준다. 그러나 ①런타임의 사전 검사 거절 문구가 `"실행 전 검사에서 거절했습니다."`, 저장의 거절 문구가 `"저장 전 검사 거절"`로 **자기 설명이 없고**, ②어댑터의 `decode_envelope`는 실패 세부를 고정 허용 목록(`hint`·`path`·`error_code`…)으로만 옮겨 **`issues`·`diagnostic`을 버린다**. 바깥은 `TOOL`·`details:{}`만 본다.
- **최소 재현**: `[self:workflow]{op:"run", name:"IT71_세금", params:{세율:0.2}}` → `error:"실행 전 검사에서 거절했습니다."` (안쪽은 `MISSING_ARGUMENT: 필수 인자 누락: 금액`). 저장 구문 오류(T13)는 안쪽 `SYNTAX`와 저장 원문 줄·칸이 사라진다.
- **영향**: 앱·예약·모델이 저장 함수를 run으로 부를 때 실패 이유를 알 길이 없다(같은 원인을 `[fn:…]` 직접 호출로 다시 짜 봐야 보인다 — 턴 하나를 더 쓴다). 69회차 B69의 "값 통로와 표시 통로" 부류와 달리 이번엔 **진단 통로**가 경계에서 끊겼다.
- **뿌리**: 거절 봉투의 `error`가 요약을 싣지 않는 것(문자열만 읽는 소비자 — 알림·이력·스케줄 결과 — 가 많다) + 경계 어댑터가 판본 2 자신의 진단 형식을 모르는 것. 둘 다 "봉투를 만든 쪽이 판본 2인데 받는 쪽은 옛 도구 봉투로 읽는다"는 같은 이음매다.
- **제안(수리성)**: 거절 문구가 첫 진단(코드·메시지, 외 N건)을 싣게 하고, `decode_envelope`가 판본 2 봉투의 `issues`/`diagnostic`을 크기 제한된 `inner_diagnostics`(코드·메시지·안내·줄·칸)로 옮긴다. 가드: run 누락·미지 인자·저장 미등록 함수·저장 구문 오류(SYNTAX와 줄 보존)·크기 상한.

### F71-1 설명 없이 재저장하면 기존 설명이 지워진다

- T15: `description:"부동산 메모 정리"`로 저장 → 본문만 고쳐 재저장 → `detail`의 `description:''`. `params.get("description","")`가 "안 줌"과 "비움"을 구별하지 않는다. 수리성: 키가 없으면 이전 설명 유지.

### F71-2 분해한 프로그램을 그대로 저장하면 고치는 법을 말하지 않는다

- T14: 정의 둘 → "저장본은 하나의 [def:이름](명시 인자){몸통}이어야 합니다." 교재가 지역 함수 분해를 기본 작성법으로 가르치므로 **예측 가능한 다음 행동**이다. 저장 함수끼리는 `[fn:이름]`으로 부를 수 있으니, 받은 정의 이름과 "다른 정의가 부르는 보조 함수부터 하나씩 저장"을 문구에 싣는다(수용 집합 불변 — 문구만).

### F71-3 교재 표면이 선언에 없는 `op:"get"`을 가르치고, 경고는 거짓 예언을 한다
