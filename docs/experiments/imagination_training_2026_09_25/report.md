## 갭의 원장

### B56-1 — join의 명시 입력은 받는다고 선언했지만 컨테이너 타입을 빠뜨렸다

**영향:** 두 데이터 원천을 연결하려는 정상 문장이 실행 전에 도구 라우팅에서 거절된다.
현재 문법의 파이프 입력 자리도 없어 직접 목록 입력을 피해 갈 수 없다.

```ibl
#!ibl edition=2
[table:join]{left:[{id:"a",price:300}],right:[{id:"a",memo:"역세권"}],on:"id"}
```

- J1: 검사 `incomplete`, 실행 `success:false`, `TOOL`.
- 오류: `data_join: left 에는 타입 선언이 없는 자리인데 1개짜리 목록이 왔습니다`.
- J2: `{items:[...]}` Record로 감싸도 동일하게 사전 타입을 거절한다.
- J3: `A & B >> [table:join]`은 `PIPE_COLLISION`으로 거절한다.
- **J5 대조:** 같은 두 Record를 `json(...)` 문자열로 바꾸면 결합 1행을 정상 반환한다.
- **L2 대조:** 기존 판본의 병렬 공급은 정상 결합한다. 실제 결합 구현은 살아 있다.

원인: `data/packages/installed/tools/data-ops/tool.json`의 `data_join.left/right`에
description만 있고 type이 없다. 정본 `ibl_actions.yaml` 선언을 따라 생성된 상태다.
`backend/ibl/ibl_routing.py:398` 이후의 컨테이너 관문이 array/object 선언 부재를 거절한다.
반면 `dataops_join.py`의 `join/inner_join`은 명시 left/right 입력을 실제 처리한다.

**수리 제안:** 정본 어휘의 입력 타입을 실제 소비 계약에 맞추고 빌드로 파생물을 갱신한다.
컨테이너 관문을 약화하지 않는다. 목록·items 봉투·빈 입력·left 결합 defaults를
HTTP 입구부터 확인하는 회귀를 붙인다. 문자열로 변환해야만 되는 우회는 교재의 정답으로 굳히지 않는다.

### B56-2 — merge에 현재 문법에서 병렬 목록을 전달할 입력 경로가 없다

**영향:** 두 기사 목록의 결합·중복 제거가 기존 구현에 도달하지 못한다.
T04의 left/right는 액션 설명의 flow.input_params에 있으나 실제 호출 계약에는 없다.
단순 작성 오류인지 확인하기 위해 계약에 있는 items와 설명의 병렬 파이프도 각각 시험했다.

```ibl
#!ibl edition=2
([{id:"a"}] & [{id:"b"}]) >> [table:merge]{by:"id"}
```

- M2: `PIPE_COLLISION: 파이프 입력 자리가 없거나 명시 인자와 충돌합니다`.
- M1: left/right 봉투를 명시하면 `UNKNOWN_ARGUMENT`.
- M3: 계약에 있는 `items:[{id:"a"},{id:"b"}]`는 실행에 도달하지만
  `merge: & 병렬로 두 개 이상의 items 입력이 필요합니다`로 실패한다.
- **L3 대조:** 기존 판본의 `take & take >> merge`는 a·b 2행을 반환한다.
- **M4 우회:** 현재 문법에서 `& → each(mode:"flat_map") → dedup(items:...)`는 a·b를 반환한다.

원인: `backend/ibl/ibl_v2_contracts.py:4`의 호환 계약에는 `pipe_input`이 없고,
`data-ops/handler.py:1055`의 `_op_merge`는 앞 단계의 분기 목록을 소비한다.
표준 items 직접 주입으로 만들어진 단일 봉투는 그 분기 목록을 대신하지 못한다.
선언의 flow와 실제 입력 스키마, 호환 어댑터가 서로 다른 입력 경로를 말한다.

**수리 제안:** 기존 병렬 결합을 현재 명시 값 계약으로 잇는 어댑터를 선언한다.
함수 이름을 언어 파서에 넣지 않는다. 인접한 pair/병렬 입력 액션은 다음 수리 턴에서
계약·실행 경로를 전수 점검하고, 두 목록/세 목록/빈 목록/부분 실패의 보존을 검사한다.
이번 회차에서 union 등 다른 액션까지 같은 결함이라고 확정한 것은 아니다.

### B56-3 — time의 정상 평문 반환을 JSON 실행 봉투로 해석해 실패한다

**영향:** 보고서 날짜·파일 이름·시간 조건처럼 기본적인 조회를 현재 프로그램에 연결할 수 없다.

```ibl
#!ibl edition=2
[self:time]{format:"%Y-%m-%d"}
```

- T08: `ADAPTER_SHAPE: 선언된 JSON 실행 봉투가 아닙니다: 2026-09-25`.
- D1/D2: 기본 포맷·시간 포맷 `%H`도 각각 같은 반환 계약 오류다.
- D3: catch는 오류를 담아 돌려줄 뿐 날짜 조회를 복구하지 못한다.
- **L1 대조:** 기존 판본은 `{"result":"2026-09-25"}`를 반환한다.
- **D4 대조:** `format:'{"date":"%Y-%m-%d"}'`로 평문을 JSON 객체 모양으로 강제하면
  현재 문법에서도 `date:"2026-09-25"`가 반환된다.

원인: `system_essentials/handler.py:861`은 `strftime` 문자열을 반환한다.
호환 계약은 `Record + legacy-envelope`를 지정하고,
`backend/ibl/ibl_v2_adapters.py:94`의 `decode_envelope`는 JSON 객체를 요구한다.
조회 자체는 성공하고 반환 해석에서 실패한다.

**수리 제안:** 평문·스칼라 도구의 실제 반환에 맞는 명시 계약/어댑터를 두고 기존 판본을 보존한다.
모든 평문을 무조건 성공으로 간주하는 공통 예외를 추가하지 않는다.
다른 평문 반환 도구도 같은 계약 생성기를 쓰는지 다음 수리 턴에서 전수 점검한다.
