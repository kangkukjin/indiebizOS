## 1. 결론 요약

- **지금 가능한 것.** 원문 보존, 판본 고정 인용, 질문·잠정 답변 기록이 대화(주제) 단위로 문서화된 기능으로 존재한다. 한 사람의 여러 주제를 분리해 이어 가는 용도는 문서상 지원된다(M1, M3, M5, M7).
- **두 사람의 분리.** 문서가 보장하는 분리 단위는 '대화'다. '사람'을 나누는 장치는 아니다. 사람별 계정·접근 권한은 세 문서 어디에도 없다(M2).
- **권장.** 문서 근거만으로 보면 **사람마다 별도 연구 프로젝트**를 두는 편이 이름 변경·복제·휴지통·백업 같은 생애주기 결합을 피한다(M2). 그러려면 단일 백엔드에서 쓰는지와 공통 기억 범위를 먼저 확인해야 한다(점검 목록 S1~S4).
- **흔한 오독 주의.** 검색 결과(snippet)를 확보한 것과 원문을 확보한 것은 다르다. 자동 회수됐다는 사실이 모델이 그 자료를 활용했다는 뜻도 아니다(M3, M4).
- **질문 보존은 자동이 아니다.** 질문·관점 문서는 실행 모델이 도구로 저장해야 남는다. 지속 연구 질문 기능에는 R1에 구현 검증 기록이 없다(M7, M8).

## 2. 축 ① 대화별 자료의 범위

**M1. 자료실의 경계는 대화(thread)다. 현재 대화의 자료만 검색·참조한다.** [구현][실사용]
- 초기 설계는 '프로젝트가 자료를 소유하고 여러 대화가 공유'하는 방식이었다. 회수도 '프로젝트 전체를 검색'했다(R1 L20, L189).
- §19는 사용자 정정에 따라 이를 대화별 자료실로 바꿨다고 적는다. 바뀐 내용은 획득 원장의 `thread_id`가 가시성의 정본이라는 것, 그리고 목록·판본·직접 읽기·검색이 같은 경계를 쓴다는 것이다. 검색은 순위 계산 전에 그 대화의 source ID로 제한하고, 검색 제외도 대화별 설정이다(R1 L418-422).
- 사용 가이드도 같다. 각 대화에 독립 자료실이 붙고 AI는 현재 대화에 연결된 자료만 검색·참조한다(R2 L3-5, L27). 질문 기록도 다른 대화와 자동 공유하지 않는다(R3 L4).
- 다른 대화의 결론과 자료는 현재 AI 맥락에 자동으로 넣지 않는다(R1 L71).
- 화면 검증: 교육·경제 주제의 메시지 분리(R1 L410-411)와 대화별 자료 목록 분리(R1 L434-435)를 확인했다. 다만 AI 답변은 모의 생성기를 썼다. [실사용·모의 모델]
- 같은 원문 바이트를 중복 저장하지 않더라도 검색·조회·제외 설정은 대화마다 구분된다. 옛 공용 자료는 '이전 공용 자료' 대화로 옮겨졌고, 다른 대화에 자동으로 섞지 않는다(R2 L110; R1 L423).
- **문서 간 차이(D1).** R1 §15의 통과 시나리오 'PDF를 일자리 대화에서 재사용 → 새 대화에서도 관련 원문 회수'(R1 L327)는 §19 이전의 공용 자료실 전제를 따른다. 현재 대화별 경계와 맞지 않는다. 대화 사이에 자료를 옮기는 수단도 세 문서에 없다. 한 대화에서 다른 대화로 넘기는 기능은 [미확인]이다.
- 기억은 자료실과 범위가 다르다. 해마·심층·포식기억 같은 공통 기억은 일반 프로젝트와 같은 범위·정책을 따르고, 자료실만 대화별이다(R2 L45-47; R1 L467-468). '일반 정책'이 실제로 어떤 범위인지는 세 문서에 정의되어 있지 않다. [미확인]

**M2. 두 사람의 운영: 한 프로젝트를 함께 쓸지, 프로젝트를 따로 쓸지.** [설계·구현 서술 + 미확인]

| 관점 | 한 프로젝트 · 사람별 대화 | 사람별 별도 프로젝트 |
| --- | --- | --- |
| 자료 분리 | 대화별 자료실로 분리(M1). 단, 같은 `conversations.db`·`research/objects`를 공유(R2 L97-98) | 프로젝트마다 별도 정본·원문 저장소(R2 L97-98). 프로젝트 사이 blob 공유 없음(R1 L302) |
| 동시 실행 | 단일 백엔드 안에서 다른 대화는 병렬 실행 가능(R1 L184, L390) | 같음 |
| 생애주기 결합 | 이름 변경·복제·휴지통·삭제 전에 진행 중인 대화를 먼저 중단해야 함(R2 L105-106; R1 L386-387). 한 사람의 실행이 다른 사람의 프로젝트 조작을 막음 | 각자 독립 |
| 백업·복제 | 프로젝트 전체 단위(R2 L98-99; R1 L304). 한 사람 몫만 떼어 내는 절차는 문서에 없음 | 사람별로 백업·복제 단위가 맞음 |
| 영구 정리 | 대화·자료의 영구 정리는 현재 프로젝트 삭제로 처리(R1 L394) → 한 사람의 정리가 공용 프로젝트 전체에 걸림 | 각자 프로젝트 삭제로 정리 가능 |
| 나중에 자료 공유 | 대화 간 이동 수단 [미확인] | 프로젝트 간 가져오기는 후속 범위(R1 L392) → 현재 불가로 읽힘 |

- **확인할 조건(접근 권한).** 세 문서에는 사용자 계정, 사람별 접근 권한, 한 사람이 다른 사람의 대화나 자료실을 열 수 없게 하는 장치가 없다. '공개 참조는 조회 권한을 대신하지 않는다'(R1 L260)와 '기존 소유자·승인 관문'(R1 L241)이 있을 뿐, 그 관문이 사람을 구별하는지는 [미확인]이다. 대화 분리는 AI 맥락과 자료 가시성을 나누는 장치이지 사람 간 보안 경계가 아니다.
- **확인할 조건(접속 형태).** 서로 다른 프로세스가 같은 프로젝트를 동시에 서비스하는 다중 백엔드 운영은 지원 범위가 아니다(R1 L389-390). 두 사람이 각자 다른 기기의 백엔드로 같은 프로젝트를 열면 지원 밖이다. 같은 백엔드에 접속하는 경로(웹·Electron이 같은 IBL 서비스 사용, R1 L267)가 실제 두 사람 환경에 맞는지는 [미확인]이다.
- **판단.** 위 두 조건을 확인하기 전에는 사람별 별도 프로젝트를 권한다. 이 권고는 생애주기·백업이 독립된다는 문서 근거에서 나온 추론이다. 권한 보장을 근거로 한 것은 아니다.

## 3. 축 ② 확보한 원문과 검색 결과의 차이

**M3. 검색 결과는 '발견 기록'이고 원문 확보가 아니다. 확보 범위 표시(coverage)로 구분한다.** [설계][구현][자동검증]
- 설계의 확보 등급(R1 L111-121). 검색 결과는 검색어·목록·제목·URL·받은 발췌만 남기고 '발견 기록, 원문 미확보'로 표시한다(L115). 웹 본문은 당시 반환된 본문을 '본문 확보 또는 일부 확보'로(L116), PDF·첨부는 실제 바이트를(L117) 남긴다. AI 답변은 외부 원문과 구분한다(L121).
- 'coverage: full | partial | snippet | unknown'(R1 L138). 구현은 웹 검색을 snippet, crawl을 실제 반환 플래그에 따라 full/partial, 나머지를 unknown으로 표시한다(R1 L373-374). 가이드도 full은 도구가 반환한 본문 기준이고, snippet은 페이지 원문과 다르며, unknown은 전체 확보를 확인하지 못했다는 뜻이라고 적는다(R2 L34-35).
- 반환되지 않은 원문은 확보로 치지 않는다. 대상은 로그인 벽 뒤 원문, CLI 도구 이벤트에 오지 않은 자료, URL만 기록한 브라우저 이동이다(R1 L168, L172, L374-375, L448; R2 L38-39).
- 링크만으로는 '저장됨'이 아니다. 일시 결과 보관소·spill을 가리키는 링크만 있으면 보존이 아니다. 정본 objects에 복사하거나 보존된 해시를 참조해야 저장된 것이다(R1 L127).
- 부분 읽기는 전체 검토가 아니다. 작은 페이지로 읽은 것은 전체 문서 검토가 아니고, 인용 근거에는 실제 반환된 부분만 기록된다(R2 L93; R1 L123, L336).
- 보존 실패는 조사 실패로 처리하고 추가 획득을 막는다(R2 L102-103; R1 L159). 추출·색인 실패는 원문을 유지한 채 재시도한다(R2 L103-104; R1 L381-382).
- 자동검증: '검색만 한 링크·실제 읽은 링크의 분리', '검색 발췌·부분 페이지 오표시 없음'이 통과 기준이다(R1 L335, L339). §18의 연구 전용 검사 23개가 통과했다(L398). 다만 시나리오별 통과 대응표는 없다. [자동검증·시나리오별 대응 미확인]

**M4. 자동 회수 ≠ 모델 전달·활용 ≠ 인용.** [실사용]
- 실사용 4545~4548 점검(R1 L535-539). 네 턴 모두 웹 검색만 했고 원문 열람·자료실 read·최종 인용은 0회였다. 검색 결과는 snippet으로 보존됐다. 자동 회수가 매번 12개 문단이었지만 이것을 모델 활용으로 간주하면 안 된다고 적었다. 답변에는 '원문 미확인·기억 의존 수치'가 남았다.
- 원인은 실행 직전 프롬프트 재조립이 연구 자료·관점을 덮어쓴 것이었다. 수정 후 최종 입력 검증을 추가했다(R1 L541-549). 그러나 실제 모델의 조사 깊이·인용 행동은 검증하지 않았다(R1 L550-551). [구현·자동검증 / 실사용 재확인 미확인]
- 4543·4544 점검(R1 L487-498). 저장 파일 226개의 해시를 검사했고 누락·손상은 없었다. 4544는 자동 회수만 있고 직접 자료실 호출이나 최종 인용이 없어 활용을 추적할 수 없었다. 획득 횟수·판본 수는 독립 문헌 수가 아니다(L498).
- **판단.** 장기 조사에서 '자료가 쌓였다'는 숫자는 보존의 증거일 뿐이다. 답변이 원문에 근거했는지는 인용 기록(`research_citations`, R1 L100)과 질문의 supporting 목록(R3 L29-31)으로 확인해야 한다.

## 4. 축 ③ 자료 판본

**M5. 원문 판본은 불변이다. 내용이 바뀌면 새 판본, 같으면 기존 판본을 쓴다.** [설계][구현]
- 원문은 해시 주소의 불변 바이트(`research/objects/<sha256 앞 2자>/<sha256>`)로 저장한다(R1 L81-82, L367). 판본(`research_versions`)은 생성 후 내용이 바뀌지 않는다(R1 L96).
- 같은 URL이라도 내용이 바뀌면 새 판본이 되고, 바뀌지 않았으면 기존 판본에 수집 경위만 연결한다. URL은 내용 동일성의 증명이 아니다(R1 L125). 표시 설정·캐시 시각만 바뀌고 본문이 같으면 같은 판본이다(R1 L368-369).
- 판본이 원문 저장소이고 색인은 파생물이다. `research/index.db`는 다시 만들 수 있다(R2 L98, L104; R1 L83, L382).
- 자동검증 기준: '같은 URL의 내용 변경 → 두 버전 유지, 옛 답변의 인용은 옛 내용'(R1 L330), '임시 다운로드·spill 삭제 후에도 영구 원문 열림'(R1 L332). [설계 기준 · 개별 통과 대응 미확인]

**M6. 인용은 (판본, 추출 revision, 위치)에 고정된다. 재추출은 새 revision을 더한다.** [설계][구현][실사용]
- 인용 좌표는 `(project_uid, version_id, extraction_revision, locator)`다. 재추출·OCR 정정은 새 revision을 만들 뿐 옛 인용 위치를 바꾸지 않는다(R1 L220).
- 읽기 이어가기에는 같은 `version_ref`, 반환된 `extraction_revision`, `next_cursor`를 쓴다(R2 L91-92). 질문의 근거는 `{version_ref,extraction_revision,locator,quote}` 형식이고, 다른 대화 자료나 잘못된 추출 판본은 거부된다(R3 L29-32).
- 실사용 사례: 옛 스냅샷 24개에 추출 revision을 추가하면서 원문·이전 revision·인용을 보존했다(R1 L491-493; R2 L112-113).
- 이름을 바꿔도 uid·원문 판본·인용은 유지된다(R2 L100; R1 L296, L386).
- 최신 판본을 우선하되 시점 비교에서는 당시 판본을 지정한다. 최신 판본의 색인이 실패했을 때 과거 판본으로 조용히 대체하지 않는다(R1 L224). 현재 구현은 최신 판본도 '그 대화가 실제 확보한 판본 중'에서 고른다(R1 L421-422).
- 인용 검증은 출처와 문구가 실재하는지만 확인한다. 주장의 타당성은 증명하지 않는다(R1 L222, L383-384; R3 L5).
- **판본 삭제·보존 기간.** 원문은 자동 TTL로 삭제하지 않는다. 원문 단위 영구 삭제와 보존 용량 정책은 후속 범위다(R1 L392-394). 장기 조사에서 용량이 계속 늘어날 수 있다는 뜻이다. 용량 상한과 정리 방법은 [미확인]이다.
- **문서 간 차이(D2).** 설계는 '자료 영구 삭제'를 기존 확인 절차로 처리한다고 적는다(R1 L295). 구현 상태는 원문 단위 영구 삭제를 후속으로 미뤘다(R1 L392-394). 현재 영구 삭제는 프로젝트 삭제 단위다.

## 5. 축 ④ 질문과 잠정 결론의 보존

**M7. 지속 연구 질문: 질문·잠정 답변·지지/반박·남은 확인·다음 조사를 판본으로 보존한다.** [구현 서술(가이드) · 검증 기록 미확인]
- 대화 헤더의 '연구 질문' 화면은 다섯 가지를 보존하고 판본별로 비교한다. 다음 턴에는 요약 목록이 전달된다(R2 L116-119; R3 L1-4).
- 기록 필드는 text·scope·provisional_answer·gaps·next_probes다. `question_id`와 `revision`을 유지하고, 수정 전에 전체 기록을 읽는다(R3 L9-15). 갱신은 `expected_revision`으로 하고, 묶음은 전부 성공하거나 전부 취소된다(R3 L22-24).
- 근거는 실제로 읽은 판본에서만 연결한다. 'AI가 읽지 않은 새 인용'은 거부되고 AI의 이전 답변을 외부 근거처럼 연결하지 않는다(R3 L29-34).
- 종결은 판단 기록이지 진위 인증이 아니다. answered로 닫으려면 지지 근거, 빈 gaps, 모든 반박에 대한 검토 판단이 필요하다. 새 발견이 있으면 다시 열린다(R2 L120; R3 L38-42).
- 이력은 `question_history:true`로 과거 판본을 읽는다. 충돌 시 작성 내용을 버리지 말고 최신 판본과 비교해 다시 저장한다(R3 L44-46).
- 다음 턴 요약에는 gaps·next_probes 앞 3건과 총수만 실린다(R3 L48). 나머지는 조회해서 읽어야 한다.
- **문서 간 차이(D3).** R1에는 이 '지속 연구 질문' 기능(question_id, supporting/contradicting, resolution)의 설계·구현·검증 절이 없다. R1이 정한 것은 진행 상태 네 항목(R1 L207-212)과 `research_notes` 테이블(R1 L101)뿐이다. R2는 구현·범위 정본을 R1 §17로 지목하지만(R2 L108), R1 §17~24 어디에도 질문 기능이 나오지 않는다. 따라서 이 기능은 **가이드 서술로만 근거가 있고, 자동검증·실사용 기록은 제공 문서에서 확인하지 못했다.** [미확인]

**M8. 사용자의 관점 문서(notes)는 질문 기록과 별개다. 보존은 모델의 도구 사용에 달려 있다.** [구현][자동검증][실사용 일부]
- 관점 문서는 대화별 장기 문서로, 핵심 주장·판단 기준·입장 변화·열린 질문을 담는다. `[발언:메시지ID]`로 사용자 원문을 연결하고 AI·외부 주장을 사용자 입장으로 바꾸지 않는다(R2 L57-64; R1 L513-516).
- 수정 이력은 DB에 남고 화면에서 최근 20개를 볼 수 있다. revision으로 충돌을 감지하며 문서는 12000자 이내다(R2 L65-66).
- 질문 기록과 관점은 별개다(R3 L5).
- **자동 보존이 아니다.** 정리는 실행 모델의 도구 사용으로만 이뤄진다. 중단·실패하거나 저장하지 않은 턴에서는 직전 문서가 유지된다(R2 L71-72; R1 L520-521). 질문 기록도 '주 실행 모델이 직접 저장'한다(R3 L49).
- 검증: 관련 연구 검사 33개와 저장 자료만 모드 왕복 검사가 통과했고, 실제 교육 대화의 화면도 확인했다. 실제 모델의 자동 정리 도구 선택은 별도 호출하지 않았다(R1 L527-530). §24 수정 전에는 관점 문서도 덮어쓰기 경로에 있었다(R1 L544). [자동검증 / 실사용 자동 정리 미확인]
- **판단.** 장기 조사의 잠정 결론이 남는지는 매 턴 저장 기록으로 확인해야 한다. 조사자가 중요한 전환점마다 관점·질문 저장을 명시적으로 요청하거나 직접 수정하는 운영 습관이 필요하다(R2 L72).

**M9. 대화 원문과 이어가기.** [구현][실사용·모의]
- 메시지 원문은 요약으로 대체하지 않는다(R1 L94). 대화 기록과 첨부는 재시작 뒤에도 유지된다(R2 L32). 백엔드 재시작 때 남은 실행은 중단 상태로 보존된다(R2 L104-105; R1 L388).
- 맥락에는 최근 원문 + 체크포인트 + 정정을 넣고, 전체 대화를 상시 주입하지 않는다(R1 L188). 관점 근거는 최근 사용자 발언 20개·16000자이고, 그보다 오래된 발언은 기록 조회로 읽는다(R2 L68-69).
- 대화 하나가 독립 에이전트 신원이다. 제목을 바꿔도 이력·기억 신원은 유지된다(R2 L41; R1 L458, L483-485).
- 화면 검증: 재접속 후 대화·첨부 복원(R1 L435)과 기록 재개(R1 L477)를 확인했다. 모의 모델이었다. [실사용·모의]

**M10. 실행 모델 설정과 API 평가 역할의 적용 조건.** [구현 서술][미확인]

- 연구 대화는 현재 기어의 실행 에이전트를 쓰며 API·CLI 모두 같은 경로를 사용하고, 별도 API 보조 모델 설정을 요구하지 않는다고 적혀 있다(R2 L36-L37). 연구 전용 CLI→API 보조 모델 치환과 API 필수 검사를 제거했다는 구현 기록도 있다(R1 L441-L442).
- 그러나 같은 가이드에는 API 평가 모델도 미설정이면 모델 설정 오류부터 해결하라는 문장이 남아 있다(R2 L40). **보조 모델과 평가 역할의 관계, 이 오류 조건의 적용 범위는 세 사본만으로 확정할 수 없다.** 문장을 단순히 폐기된 지침이라고 단정하지도 않는다(D8).
- 운영 판단: 선택한 실행 기어·제공자의 설정은 확인하되, API 평가 모델 미설정을 모든 연구 대화의 일괄 시작 차단 조건으로 삼지 않는다. 반대로 공통 인지 파이프라인의 평가 역할까지 언제나 설정 불요라고 주장하지 않는다. 해당 역할을 요구하는 조건·실제 오류가 확인된 경우 그 범위의 설정을 확인한다. 이번에는 설정 조회·모델 호출을 하지 않았으므로 미확인 10으로 남긴다.
