# 105회차 — 업무 중 관용구·스크립트·어휘 등록 절차

## 판정

실제 실행 모델은 자연어 업무에서 `능력변경완료`를 발견해 관용구를 등록하고,
저장본을 새 호출로 사용해 원래 업무를 완수했다. 조건 변경에서는 같은 정의를 개정했고,
대화 이력이 없는 새 세션은 보존된 정의를 찾아 다른 분야의 업무와 새 집계에 조합했다.
스크립트 형태로 제공하라는 추가 요구에서도 본문·계약·등록·정상/오류 검증·실제 소비까지 수행했다.
어휘 보조 과제는 선언·구현·직접 검사·빌드까지 성공했으나 정식 반영 사전검사에서 멈췄다.
활성화·새 어휘 호출은 성공하지 않았으며, 어휘 등록 완료로 판정하지 않는다.
시험 몸에는 Git이 없으므로 스크립트 소스 각인은 미완료이며, 모델도 이를 `complete:false`로 보고했다.

이는 **격리된 실제 실행 모델과 IBL 관리 경로의 성공**이다. 운영 HTTP의 분류·의식·검수 전체,
실제 운영 사전에 대한 코드 반영·재기동·Git 각인, Android는 검증 범위가 아니다.
관용구·스크립트·어휘가 같은 종류의 변경이라는 뜻도 아니다.

## 과제·실험 조건

- 사용자 요청: 최근 수리한 관용구·어휘·스크립트 등록 절차를 에이전트가 일하면서 쓸 수 있는지 훈련.
- 시작: 2026-11-01 14:18 KST. 준비·작성·실행·변형·진단의 상한은 15:18 KST.
- 주 업무: 6지점, 장비 600대, 점검 540행, 청구 636행. 총 1,776행의 합성 원천.
- 변형: KRW 접두 금액, 점검 6행 추가, 차액 500원까지 허용. 원래 입력·보고서는 보존.
- 전이: 차량 80대, 점검 64행, 청구 84행. 기존 대사에 지점별 합계라는 새 연결을 추가.
- 입력과 독립 기대값은 첫 실행 전에 고정. 기대값은 executor가 읽지 못하는 `oracle/`에 보관.
- 원자료·정답·모델 원문·IBL 원시 영수증: `outputs/long_sentence_imagination/2026-11-01_105회차/`.
- 정본 코드의 실제 `handle_request`, 컴파일러, 함수 원장, script 관리·자식 프로세스, 능력 변경 구현을 사용.
  등록·삭제·판본·소비자 검사·결과를 모의 성공으로 바꾸지 않았다.
- 별도 Git 저장소나 정본 clone을 만들지 않았다. 시험 몸은 쓰기 데이터와 필요한 빌드 입력만 분리했다.
  실행 코드의 정본은 이 저장소다. 함수 원장·스크립트 등록부·실행 원장은 몸별로 분리했다.
- macOS sandbox-exec: 자기 몸 안 쓰기 허용, 몸 밖 쓰기·네트워크 차단.
  사전 탐침에서 자기 출력 쓰기는 허용, 정본의 시험 파일 쓰기와 localhost 연결은 거절됨을 확인.
- 모델은 현재 설치된 Claude Code의 `opus`를 사용했다. 응답의 실제 모델 식별자는
  `claude-opus-5-5`다. 네이티브 도구를 끄고 IBL MCP·가이드 읽기를 연결했다.
- 운영 IBL 문법 프롬프트와 공개 가이드/계약을 제공했다. `read_guide`는 같은 공개 가이드의
  파일명 읽기/목차 문자열 검색 어댑터이며, 운영 RAG·프롬프트 조합 전체를 복제한 것은 아니다.
- 시작 등록 목록에는 절차용 `능력변경`/`능력변경완료`만 설치했다. 운영의 많은 후보 사이에서의
  검색 성공률은 이 작은 카탈로그의 단일 성공으로 추정하지 않는다.
- 독립 모델에는 훈련자의 함수명·분해·프로그램·정답을 제공하지 않았다. 하네스 배선 때문에
  내부 구현과 기존 실제 모델 시험을 읽었지만 훈련자의 업무 알고리즘은 공개 계약으로 작성했다.

과제 원문: [기본](request_main.txt), [변경](request_variant.txt), [새 세션 차량](request_transfer.txt),
[스크립트 형태 요구](request_script.txt), [어휘 등록 보조 과제](request_action.txt).

## 등록·개정·복구에서 실제로 본 행동

1. **독립 발견과 등록:** 모델은 공개 가이드와 등록 목록에서 `능력변경완료`를 찾아
   `장비점검청구대사`를 저장했다. 표본 probe와 새 전체 호출을 따로 수행했다.
   `complete:true`, 판본 일치, 새 호출에 기록된 판본을 관측했다.
2. **조건 변경:** 같은 CLI 세션이 기존 정의를 개정해 KRW·허용차 인자를 지원하고
   기존 형식도 별도 호출로 확인했다. 후반 검산에서 행 예산을 넘겼으나 이미 저장된 결과를
   읽고 남은 확인을 분리했다. 예산 실패를 원래 계산 전체의 미수행으로 오인하지 않았다.
3. **새 세션 재발견:** 업데이트된 함수 원장과 등록부, 차량 입력만 새 몸으로 복사했다.
   이전 대화·보고서·실행 결과는 복사하지 않았고 원래 몸 읽기도 차단했다.
   CLI session_id는 기본/변형 세션과 다르다. 새 모델은 목록으로 `장비점검청구대사`를 찾아
   실제 호출하고 반환 rows에 지점 합계를 연결했다. 함수 이름은 요청에 넣지 않았다.
4. **스크립트:** 다른 소비자가 JSON 스크립트 계약을 요구한다는 후속 요청에
   `청구정규화`를 작성·등록했다. `ibl-script/2`, `rows: List<Record>`, 결과
   `{items: List<Record>}`, `pure` 계약을 선언했다. 정상·금액 부재·소수 거절 probe 3건과
   직접 오류 호출을 수행했다. 이 결과를 지역 대사 함수에 연결한 전체 보고서도 일치했다.
   지역 대사 함수를 저장하지 않은 사실을 모델이 명시했다.
5. **완료 의미:** 스크립트의 `behavior_verified:true`와 `source_change.completed:false`를
   구분했다. Git이 없는 시험 몸에서 각인을 못 했으며 이를 성공으로 대체하지 않았다.
6. **훈련자의 보호·재개:** 사용 중인 `LS105Normalize`와 `LS105Reconcile`의 삭제는
   호출자 `LS105Report`를 명시하며 거절됐다. 정의 개정 뒤 의도적으로 틀린 기대값을 주어
   후속 검사만 실패시킨 다음 `status → verify`로 완료했다. verify 전후 판본은 같고 재등록은 없다.
7. **퇴역 순서:** 훈련자 과제 완료 뒤 역순으로 넘긴 삭제 묶음이 호출자 우선으로 정렬됐다.
   보고 관용구·대사 관용구가 은퇴하고 스크립트 등록은 해제됐다. 소스 파일은 보존됐다.
   함수 은퇴는 완료, 스크립트 해제의 각인은 Git 부재로 미완료다.

## 마찰과 해석

- **H105-1, 시험 환경 오류:** 초기 등록부를 만들 때 `file` 대신 `path`를 썼다.
  첫 모델은 관리 스크립트 부재를 관측하고 직접 `workflow save`로 우회해 업무를 완수했다.
  결과는 맞았지만 새 통합 절차의 발견 평가로 사용하지 않았다. 오류 시도는
  `ai_fixture_fault/`, `ai_fault.*`에 보존했다. 실제 생산 등록 항목을 복사하고 계획 호출까지
  사전 확인한 새 몸·새 세션에서 기본 과제를 다시 실행했다. 제품 결함으로 세지 않는다.
- **L105-1, 작성 경계:** 이미 등록된 스크립트의 본문 쓰기와 관리 호출을 하나의 컴파일된
  IBL에 넣으면 `DEFINITION_CHANGED`로 거절됐다. 최초 초안·영수증은 보존했다.
  이미 완료한 파일 쓰기를 반복하지 않고 나머지를 새 프로그램으로 컴파일해 성공했다.
  가이드의 “파일 준비 뒤 계획”을 실행 경계로도 지켜야 한다. 보호 검사를 풀 필요가 있다는
  근거는 없으며, 같은 긴 프로그램에서 가능한 변경 경계를 더 명확히 안내할 여지가 있다.
- **L105-2, 검산 예산:** 모델의 변형 프로그램에서 후반 검산 중 rows 10,001/10,000이 됐다.
  보고서 쓰기는 이미 완료돼 있었으며, 재독·분리 검증으로 업무를 마쳤다.
  시험 MCP는 budget 인자를 노출하지 않았으므로 예산 확장 선택의 평가에는 하네스 제약이 있다.
- 기본 모델은 초기 작성에서 `each`의 List<Record> 조건에 걸렸고 고쳐서 진행했다.
  첫 초안 무오류 성과로 기록하지 않는다. 자세한 시도별 진단은 events/programs JSONL에 있다.

## 새 어휘 등록 보조 과제 — 부분 달성

남은 시간에 별도 시험 몸에서 `sense:ls105_inspection` 등록을 명시적으로 요구했다.
이는 모델이 업무에서 새 어휘의 필요성을 자율 판단했는지 평가하는 과제가 아니라,
이미 선택한 어휘 추가 경로를 끝까지 사용할 수 있는지 보는 보조 진단이다.

- 선언·핸들러·교재·검사 예제를 준비했다. [후보 원문](action_candidate/)은 실험 자료로만 보존한다.
- 실제 핸들러 직접 검사는 전체/M1 한 건/X 0건/원천 부재/파싱 실패 **5/5 통과**했다.
  실제 실행 영수증 `action` index 12와 23에서 확인했다. IBL을 통한 새 액션 호출과는 다르다.
- 실제 `build_ibl_nodes.py`는 **exit 0**, 시험 카탈로그 171→172, 삼각 대조 통과.
  모델이 처음 빠뜨린 pc_only·query 읽기·용례 재검토를 보완하고 빌더로 파생물을 생성했다.
- `--check`는 **exit 1**이다. 시험 몸에 복사하지 않은 가이드 링크 대상과
  읽기 전용 frontend의 설치 필터 문제가 남고, Git·코퍼스 관련 검사는 일부 건너뛰었다.
  따라서 전체 빌드 검증 완료로 세지 않는다.
- 정식 `능력변경` check는 시험 선택 0/0으로 실패해 `self:patch apply`까지 도달하지 않았다.
  **운영자 진단:** 시험 몸이 `outputs/` 아래에 있고 선택기가 그 경로 성분을 제외한다.
  동일 변경 경로를 정본의 선택기에 읽기 전용으로 넣으면 **76/837**이 선택된다.
  선택만 확인했으며, 정본에 없는 후보에 대해 이 76개 검사를 실행한 것은 아니다.
- 모델은 backend 검사 파일을 추가하려 했으나 정본으로 이어진 읽기 전용 링크에서 거절됐다.
  정본 파일은 생기지 않았다. 모델 원문이 제안한 “backend 쓰기 권한/선택 규칙 변경 필요”는
  확정 제품 수정안이 아니다. 먼저 outputs 제외 규칙을 충족하는 독립 시험 환경을 마련해야 한다.
- 새 프로세스에서도 계약 조회가 비었고 호출은 `UNSUPPORTED_ADAPTER`였다.
  사전검사 이후 반영·활성·Git 각인은 미검증이다. 적용 권한이 실제로 거절됐다고도 주장하지 않는다.

모델은 보고서에서 미완료를 명시했다. 모델 34회 IBL 호출 뒤 운영자 계약 조회·새 호출 2회가
추가됐으며, events의 index 34/35는 모델 행동으로 세지 않는다. 모델의 자체 보고 원문은
[ai_action_response.md](ai_action_response.md), 교차 확인은 [evidence.json](evidence.json)에 남긴다.
환경 장애를 제품 등록 결함으로 승격하지 않았고, 운영 코드 수리를 하지 않았다.

토큰은 제공자가 반환한 **입력 / 캐시 생성 / 캐시 읽기 / 출력**을 별도 열로 그대로 남긴다.

훈련자 모델/운영자 전체 토큰은 미측정이다. 수리 전 동일 조건의 기준선이 없으므로
시간·토큰 절감률을 주장하지 않는다. 등록·복구·새 업무 재조합의 관측은 비용 비교와 별도로 유효하다.

## 재현과 보존

`harness.py`는 시험 몸 생성, 실제 IBL 자식, 제한된 MCP, 실제 모델 실행을 제공한다.
`run_trainer.py`, `trainer_changes.py`, `trainer_variant.py`, `trainer_transfer.ibl`은 각 단계의
입력·최초 초안·변경 이유를 남긴다. 기존 등록 상태에서 추가 프로그램을 재실행하면
당연히 충돌할 수 있으므로 새 시험 몸을 만들어 순서대로 실행한다.

[요약 증거](evidence.json), 각 `*_events.jsonl`과 `*_programs.jsonl`은 원시 영수증의 실행 ID·지문·
진단·요청을 연결한다. 모델 응답은 `ai_*_response.md`에 원문 그대로 보존하며,
그 응답의 자체 성공 주장보다 위 독립 검증을 우선한다.

운영 제품 코드를 수리하지 않았다. 회귀 전수·Android·frontend 빌드는 실행하지 않았다.
훈련 기록과 재현 자료만 정본에 반영한다. 재현 Python 구문, JSON/JSONL 파싱, 파일당
1500줄 제한, 민감 키 패턴, 공백 오류를 확인했다. 검수 시 운영 `/health`는 healthy였다.
