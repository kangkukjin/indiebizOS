# 연구계획서: 10월 5일 백업(v2.1)의 보존 범위와 복원 가능 조건

상태: 계획 초안. 조사·복제·시험은 아직 시작하지 않았다. 아래의 사실은 모두 사용자 진술이며, 나머지는 확인할 질문이다.

## 1. 목적과 현재 질문

- **판단하려는 것:** 이 백업 프로그램(과 그 운영)을 믿을 수 있는가.
- **판단 기준:** 현재 2.3 코드가 좋아 보이는지가 아니다. 다음 두 가지다.
  - (A) 10월 5일 v2.1 백업에 당시 파일이 무엇까지 보존됐는가: 내용, 메타데이터, 포함 범위.
  - (B) 어떤 조건에서 복원이 되고, 어떤 조건에서 실패하는가.
- **계기:** 운영자는 '백업 성공' 로그를 보여 줬지만, 지난주 중요한 파일 하나가 복원되지 않았다.
- **이 문서의 범위:** 연구의 문제·방법·진행을 정한다. 실제 자료 조사와 실행은 사용자가 진행을 요청한 뒤에 한다.

## 2. 출발점

**사용자 진술(미검증):**
- 10월 5일 백업은 v2.1로 생성됐다. 현재 판본은 2.3이다.
- 운영 로그에는 '성공'이 표시됐다.
- 지난주 중요한 파일 하나의 복원에 실패했다.

**사용자 조건(강도 그대로 보존):**
- 원본과 운영 백업은 절대 수정하지 않는다.
- 복원 시험은 복제한 시험 자료에서만 한다.

**잠정 가정(첫 확인 대상):**
- 지난주 복원 시도는 10월 5일 스냅샷을 대상으로 했다.
- 그 시도에는 2.3을 썼다.
- 둘 다 확인되지 않았으며, 틀리면 질문 구성이 바뀐다.

**미확인:**
- 백업 제품과 저장 방식: 스냅샷형인지 동기화형인지, 중복제거·암호화 여부.
- 실패한 파일의 경로·크기·종류, 그리고 실패 증상(오류 메시지, 파일 없음, 손상된 내용 등).
- 로그 원문: 경고와 건너뛴 파일이 포함된 원문이 있는지, 요약만 있는지.
- 그 파일이 10월 5일에 존재했는지, 원본이 그 뒤 바뀌었는지.
- 2.1 바이너리를 구할 수 있는지.
- 저장소를 복제할 권한과 수단이 있는지.

## 3. 접근과 선택 이유

이 연구는 '시스템이 약속한 대로 작동했는가'를 묻는다. 그래서 문서·로그가 약속하는 것, 당시 판본, 당시 입력(원본), 저장된 기록, 실제 복원 출력을 대조하는 방식을 택한다.

'백업 성공'에서 '복원 가능'까지는 여러 층위를 거친다. 실패한 층위에 따라 결론과 대응이 달라지므로 층위를 나눠 검증한다.

1. **대상 선정:** 포함·제외 규칙, 열린 파일 처리, 권한 부족으로 건너뛴 파일.
2. **카탈로그 기록:** 스냅샷 목록에 해당 파일 항목과 메타데이터가 있는가.
3. **저장 데이터 무결성:** 항목이 가리키는 데이터 블록이나 청크가 존재하고, 체크섬이 맞는가.
4. **판독 호환성:** 2.1이 쓴 형식을 2.3이 올바르게 읽는가.
5. **복원 절차와 환경:** 단일 파일 복원 방식, 경로 길이·문자 인코딩·권한, 암호화 키, 대상 파일시스템.

현재 코드와 변경 이력은 판정 근거가 아니다. 2.1과 2.3 사이의 형식·복원 관련 변경을 찾아 시험 변수를 고르는 보조 자료로만 쓴다. 제품의 공식 검증·복원 절차는 예비 조사에서 해당 제품 문서로 확인한다. 이 계획은 특정 제품의 명령을 전제하지 않는다.

## 4. 안전 규칙 (모든 단계에 우선)

1. **운영 저장소와 원본에 백업 도구를 직접 실행하지 않는다.** 백업, 검증, 수리(repair), 정리(prune/forget), 인덱스 재구축, 잠금 해제, 마운트, 형식 업그레이드 모두 해당한다. 많은 도구가 읽기 명령에서도 잠금 파일이나 캐시를 쓰고, 상위 판본이 하위 판본 저장소를 자동 변환할 수 있기 때문이다.
2. **복제는 권한자(운영자)가 저장 계층에서 수행한다.** 파일시스템·스토리지 스냅샷, 읽기 전용 이미지 등을 쓴다. 복제 직후 전체 파일 해시 매니페스트를 만들어 '마스터 사본'으로 고정하고 읽기 전용으로 보관한다.
3. **시험마다 마스터에서 새 작업 사본을 만든다.** 시험이 끝나면 마스터의 해시를 다시 대조해 변경이 없음을 확인한다.
4. **원본 해시 대조가 필요하면 읽기만 한다.** 가능하면 원본의 스냅샷이나 사본에서 한다.
5. **복원 대상은 격리한다.** 빈 디렉터리나 별도 시험 기기에만 복원한다. 원본 경로로는 복원하지 않는다. 알림·후크가 운영 시스템에 영향을 주지 않도록 시험 환경을 분리한다.
6. **키와 자격증명은 기록하지 않는다.** 로그와 보고서에 남기지 않는다.
7. **이 계획은 복제·접근 권한을 만들어 주지 않는다.** 복제는 사용자와 운영자의 승인을 거친다.

## 5. 핵심 질문과 조사 방법

### Q0. 예비 확인: 사실 확보 (저장소 접근 없음)

- **확보할 정보:**
  - 제품명과 2.1·2.3 판본 정보, 저장 형식 문서.
  - 10월 5일 작업의 원문 로그: 처리 파일 수, 건너뜀, 경고를 포함한 것.
  - 지난주 복원 시도의 기록: 대상 스냅샷, 사용 판본, 명령·절차, 오류 원문.
  - 실패 파일의 정보: 경로, 크기, 생성·수정 시점, 저장 위치의 특성(네트워크 드라이브, 열려 있던 파일 등).
  - 백업 설정의 당시 판본: 포함·제외 규칙.
  - 2.1 바이너리를 구할 수 있는지.
  - 복제 수단과 권한.
  - 원본 상태의 대체 기준이 될 출처(9절).
- **판단:** 잠정 가정이 맞는지, 저장 방식에 맞춰 Q2·Q3의 구체 명령을 정한다.
- **부족할 때:**
  - 복원 시도가 10월 5일 스냅샷 대상이 아니었다면 질문 대상을 실제 시도된 스냅샷으로 넓힌다. 이는 재규정 대상이다.
  - 로그 원문이 없으면 '로그가 증명하는 것'은 요약 범위로 한정해 말한다.

### Q1. 그 파일은 백업 대상이었는가

- **증거:** 당시 설정의 포함·제외 규칙, 10월 5일 로그의 해당 경로 언급(건너뜀·오류), 그 시점에 파일이 존재했다는 증거.
- **판단:**
  - 파일이 대상 밖이거나 그 시점에 존재하지 않았다면 → 저장·복원의 문제가 아니라 선정·운영의 문제(H1, H5).
- **부족할 때:** 설정 이력이 없으면 Q2의 카탈로그 결과로 간접 판단하고, 원인이 설정인지 동작인지는 미확인으로 남긴다.

### Q2. 10월 5일 스냅샷에는 무엇이 기록됐는가

- **증거:** 작업 사본에서 생성한 스냅샷 파일 목록(2.1과 2.3 각각), 해당 파일 항목의 크기·시각·권한·확장속성.
- **판단:**
  - 항목이 없으면 → H1.
  - 항목은 있으나 크기 0이나 비정상 메타데이터면 → 기록 단계 문제.
  - 2.1과 2.3의 목록이 서로 다르면 → H3.
- **부족할 때:** 목록 기능이 판본마다 다르면 형식 문서와 대조한다.

### Q3. 저장된 데이터는 온전한가

- **증거:** 작업 사본에서 데이터까지 읽는 전체 검증 결과(2.1과 2.3 각각), 해당 파일이 참조하는 청크의 존재와 체크섬.
- **판단:**
  - 청크가 없거나 체크섬이 틀리면 → H2.
  - 2.1에서만 통과하면 → H3.
- **부족할 때:** 손상 시점을 가를 수 없으면 '생성 시인지 이후인지'를 미확인으로 둔다. 저장소의 이후 정리 이력과 저장 매체 기록을 추가 확인 대상으로 둔다.

### Q4. 어떤 조건에서 복원되는가 (복원 시험)

- **방법:** 8절의 시험 매트릭스.
- **판단:** 성공·실패를 판본·방식·환경 조건에 연결한다.
  - 데이터는 온전한데 특정 조건에서만 실패하면 → H4 또는 H3.
- **부족할 때:** 재현되지 않으면 지난주 시도의 정확한 절차·환경을 다시 확보한다. 재현하지 못한 상태는 원인 미확인으로 보고한다.

### Q5. 복원된 내용이 당시 파일과 같은가

- **증거:** 복원본의 해시·메타데이터와 9절의 기준 출처.
- **판단:**
  - 기준과 일치하면 '보존됨'.
  - 기준이 없으면 '백업 내부 기록과 일치'까지만 말한다.

### Q6. 이 실패는 한 파일의 문제인가, 조건의 문제인가

- **증거:** 같은 스냅샷에서 고른 표본 두 가지.
  - 실패 파일과 특성을 공유하는 파일들: 같은 폴더, 비슷한 크기, 긴 경로·특수 문자, 백업 중 열려 있던 파일 등.
  - 무작위 표본.
- **판단:** 원인 조건이 다른 파일에도 재현되는지 본다. 표본 결과는 표본의 범위로만 일반화하고, 전체 보존율로 확대하지 않는다.

## 6. 실패 원인 가설과 판별 증거

| 가설 | 내용 | 지지 관측 | 반박 관측 |
|---|---|---|---|
| H1 포함 실패 | 처음부터 백업 대상이 아니었거나 건너뜀 | 카탈로그에 항목 없음, 로그·설정의 제외·건너뜀 | 카탈로그에 정상 항목 있음 |
| H2 저장 손상 | 기록됐으나 데이터가 없거나 깨짐 | 항목 있음 + 청크 누락·체크섬 불일치(두 판본 공통) | 2.1 검증·복원 정상 |
| H3 판본 호환 | 2.1 형식을 2.3이 잘못 읽음 | 2.1 복원 성공, 2.3 실패 또는 결과 상이 | 두 판본이 같은 결과 |
| H4 절차·환경 | 복원 방식, 경로, 인코딩, 권한, 키 문제 | 특정 방식·대상 환경에서만 실패 | 모든 조건에서 동일하게 실패 |
| H5 대상 혼동 | 다른 스냅샷을 찾았거나, 파일이 10월 5일 이후에 생겼거나 다른 경로였음 | 시도 기록의 스냅샷이나 경로 불일치, 파일 생성 시점이 10월 5일 이후 | 시도 기록이 10월 5일 스냅샷과 실제 경로를 가리킴 |

가설은 서로 배타적이지 않다. 예: H1의 원인이 설정이 아니라 열린 파일 처리라면 H1과 H4가 함께 해당한다. 결론은 관측된 증거가 가리키는 범위까지만 낸다.

## 7. '성공' 로그의 의미 검증

- 문서와 원문 로그에서 '성공'의 정의를 확인한다. 예: 작업이 끝까지 진행됨, 오류 없이 종료, 일부 건너뜀 허용 여부.
- 건너뛴 파일과 경고가 '성공'과 함께 기록되는지 확인한다.
- 보고서에는 '로그가 증명하는 것'과 '증명하지 못하는 것'을 나눠 적는다.

## 8. 복원 시험 설계 (복제본에서만)

- **기준 시험:** 지난주 실패를 같은 판본·절차로 작업 사본에서 재현한다.
- **변수:** 한 번에 하나씩 바꾼다.
  - 도구 판본: 2.1, 2.3.
  - 복원 방식: 단일 파일 복원, 스냅샷 전체 복원, (지원 시) 마운트 후 복사.
  - 대상 환경: 원래와 같은 종류의 OS·파일시스템, 다른 종류. 차이가 의심되는 경우에만 둘 다 시험한다.
- **우선순위:** 판본 × 단일/전체 4칸이 핵심이다. 나머지는 앞 결과가 가리키는 방향만 시험한다.
- **매 시험의 기록:**
  - 작업 사본의 해시.
  - 도구 판본과 명령(키는 가림).
  - 종료 코드와 전체 로그.
  - 복원된 파일 목록·해시·메타데이터.
  - 시험 후 마스터의 해시 재확인 결과.
- **2.1 바이너리를 구할 수 없을 때:**
  - 형식 문서와 2.1→2.3 변경 이력으로 호환성 위험을 추정한다.
  - 2.3 결과만으로 H3을 배제하지 않는다.
  - 이 근거가 대조군 시험보다 약하다는 점을 결론에 명시한다.

## 9. '당시 상태' 기준(ground truth) 세우기

기준 출처는 아래 순서로 찾는다.

1. 10월 5일 무렵의 독립 스냅샷이나 다른 백업.
2. 원본이 그 뒤 바뀌지 않았다는 증거와 원본 해시. 수정 시각만으로는 약하므로 변경 기록을 함께 본다.
3. 다른 사본: 메일 첨부, 협업 도구 판 이력 등.
4. 백업 자체의 카탈로그. 이것은 내부 일관성만 보여 준다.

결론의 강도는 어느 출처까지 확보했는지에 맞춘다. 4만 있으면 '보존됐다'고 말하지 않는다. '백업이 기록한 대로 복원된다'까지만 말한다.

## 10. 결과의 종합

1. 실패 파일을 6절의 가설 중 증거가 직접 지지하는 것으로 분류한다. 남은 가설은 무엇이 부족해 가르지 못했는지와 함께 둔다.
2. 다음 셋을 합쳐 최종 답을 만든다.
   - Q2·Q3·Q5: 무엇이 보존됐는가. 내용·메타데이터·포함 범위별로, 근거 수준을 함께 적는다.
   - Q4: 어떤 조건에서 복원되는가. 성공·실패 조건을 표로 정리한다.
   - Q6: 조건이 다른 파일에도 해당하는가.
3. 근거가 충돌하면 다수결로 정하지 않는다. 판본·방식·작업 사본 차이로 설명되는지 확인한다. 예: 카탈로그에는 있고 2.1 검증은 통과하는데 2.3 복원만 실패하면 H3·H4 쪽으로 판단한다.
4. '믿을 만한가'의 답은 조건부로 낸다. 형식: 어떤 범위·조건에서 보존과 복원이 확인됐고, 무엇이 실패하거나 미확인이며, 운영자의 '성공'이 무엇을 보장하지 않는가.

## 11. 진행 순서, 분기, 멈춤

**진행 순서:**
1. Q0
2. 복제와 해시 고정(권한자 승인 후)
3. 지난주 실패 재현
4. Q1·Q2·Q3
5. 복원 매트릭스(Q4)
6. 기준 대조(Q5)
7. 표본(Q6)
8. 종합

**분기:**
- 복제가 불가능하면 → 문서·로그·설정 분석에서 멈춘다. 복원 조건에 대한 주장은 하지 않고 미해결로 보고한다.
- 제품이 스냅샷형이 아니거나(예: 동기화형), 복원 시도가 10월 5일 스냅샷 대상이 아니었다면 → 실행자가 근거와 계획 경로를 붙여 재규정(reframe)을 요청한다.
- 시험 중 운영 쪽 변경 위험이 발견되면 → 즉시 중단하고 보고한다.

**멈춤 조건:** 아래 셋을 모두 충족하면 멈춘다.
- 실패 원인이 직접 증거로 가설에 귀속되거나, 남은 가설을 가를 관측이 접근 불가로 확인됨.
- 핵심 매트릭스 4칸의 결과가 있음.
- 표본 결과가 있음.

모든 파일 전수 검사는 비용이 낮을 때만 한다. 시간·접근 한계로 확인하지 못한 항목은 미확인으로 남기며 충족으로 표시하지 않는다.
