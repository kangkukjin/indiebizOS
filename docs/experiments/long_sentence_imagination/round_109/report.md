## 무엇을 바꿔 비교했나

사용자의 요청은 문제규정·목적·연구계획을 더 잘 만들도록 변경하고, 실제 개선이 없으면 변경을 기각하는 것이었다. 연구 실행이나 최종 연구보고서 품질은 이번 대상이 아니다.

- **S:** 요청별로 현재 의식이 처음 만든 규정을 한 번 생성했다. A/B가 같은 S를 받는다.
- **A 현행:** 현재 `research_planning.prepare`의 계획 작성·검사·저장 경로.
- **B 작성 보완:** 같은 호출 안에 원문/가정/미확인 구별, 이전 AI 초안 재검토, 대안 반례와 전 필드 일치를 요구하는 지시를 추가했다. 상시 의식 프롬프트와 가이드는 그대로다.
- **C 별도 검토:** 정확히 B가 만든 결과를 별도 문맥의 같은 모델이 검토하고 최대 한 번 정정한다. 사용자 원문과 이전 사용자 요청도 제공하며, 의식이 정한 기준 자체도 검토 대상이다.

의식과 검토는 모두 실제 설정의 `claude_code/opus`, 고급 등급을 사용했다. Codex가 답을 대신 작성한 모의 결과가 아니다. 실행 도구는 연결하지 않았고 30회 호출 모두 training 출처다. 원자료 조사·분석·외부 연락·연구 실행은 하지 않았다.

기존 실패 2개(D1 민원 감소, D2 봉사 경험 후속 요청)와 새 요청 4개(H1 처리시간과 인력, H2 취업 사이트 성과, H3 메모 의미 보존, H4 기사 검색의 허용 범위)를 고정했다. 문제별 네 가지 checks와 채택 조건을 호출 전에 [task.md](task.md)·[cases.json](cases.json)에 저장했다. A/B 순서는 교대했고, 입력의 차이는 후보 지시와 작업공간 경로뿐임을 검증했다. D2의 이전 계획도 같은 바이트를 별도 작업공간에 복제했다.

중요한 결함을 없애고 새 결함·check 퇴행이 없는 경우만 해당 사례의 개선으로 셌다. 문장이 더 길거나 세밀해진 것은 개선으로 세지 않았다.

**B 기각:** 개선 사례는 H4 한 개여서 사전 최소 두 개에 못 미친다. D2 등에서는 기존 결함을 없애면서 새로운 결함을 만들었다. 비용 한도는 통과했지만 품질 조건을 충족하지 못했다.

**C 기각:** B 대비 D1·H1·H3 세 사례에서 중요한 결함을 줄였다. 그러나 H2 정정에서 새 오류가 생겨 퇴행 금지 조건을 어겼다. B가 기각된 상태에서 결합안 C를 A와도 비교했다. H1·H4 개선은 있으나 D2·H3의 새로운 문제를 그대로 가져와 결합안 역시 채택하지 않았다. 검토의 유용성을 부정하는 결론은 아니다.

판정은 [review.json](review.json), 사전 조건별 비교는 [comparison.json](comparison.json)에 있다. 중요한 결함·원문 인용·반례를 함께 기록했다.

## 판정을 지탱하는 반례

- **경험 부재:** 기록에 일화가 없을 때는 경험 자체가 없었을 수도 있고 경험이 있었으나 기록되지 않았을 수도 있다. B/C의 “기존 면담이 이 경험을 어떻게 놓쳤는가”라는 방향 전환은 후자만 전제한다. 사용자 목적은 경험의 공존 여부를 이해하는 것이다.
- **낮은 적용률:** 100건 중 99건이 4분, 1건이 804분이면 평균 12분이다. 그 1건만 404분으로 줄어도 평균은 8분이다. 적용률 1%가 감소 전체를 설명하는 가상 반례다. 실제 센터가 이렇다는 주장이 아니다.
- **분모:** 방문자 100→200, 지원 100→200, 채용 20→30이면 지원은 두 배, 채용은 1.5배지만 방문자당 채용은 20%→15%다. C가 쓴 확정문에는 분모 값이 일정하다는 가정이 빠졌다. 같은 분모 정의와 같은 분모 값은 다르다.
- **재산출:** 두 해 모두 원래 지표가 대기+상담이고 새 지표를 상담만으로 바꾸면 감소폭은 달라질 수 있다. 그것만으로 두 해 사이에 측정 정의가 바뀌었다고 결론 내릴 수 없다.

[check_counterexamples.py](check_counterexamples.py)로 산술을 확인했다. 실제 자료나 가능성 우열의 증거로 쓰지 않는다.

## 검토자를 어떻게 평가했나

검토자의 지적 10개를 모두 원문과 대조했다. 타당한 지적뿐 아니라 방법 선택 논쟁, 미확인 조건의 명료화, 검토 신호와 최종 결정의 혼동도 있었다. 지적 수와 수정 호출 수를 품질로 세지 않았다. 여섯 사례 모두 검토가 지적을 냈으므로 각각 정정 호출까지 갔다. 무지적 시 B를 그대로 반환하는 분기는 이번 실제 모델 묶음에서는 실행되지 않았다.

D1·H1·H3의 B에서 훈련자의 최초 검토도 놓친 결함이 있었다. 검토자가 제시한 반례를 확인한 뒤 수동 판정을 정정했으며 변경 이력을 보존했다. 따라서 **독립·맹검 평가가 아니다.** C의 자체 승인을 정답으로 사용한 것도 아니다.

H4의 메타데이터 판정이나 일부 조건 표현은 해석 여지가 있다. 이를 중요한 결함에서 제외해도 B의 최소 개선은 늘지 않는다. H2의 분모 문장을 ‘분모 고정의 생략된 예시’로 관대하게 읽더라도 C 결합안에는 A에 없던 D2의 경험 존재 전제가 남는다. 이번 기각을 한 개의 논쟁적 표현에만 의존시키지 않았다.

시간은 실제 단계 실행 구간의 합이다. A/B 사이 대기와 훈련자 판독 시간을 제외하며, 배포 환경에서 사용자 지연을 직접 측정한 값은 아니다. 병렬 실행·캐시·순서 효과가 완전히 통제되지는 않았다.

## 실험 코드 오류와 보존

첫 D1/D2 검토 응답은 정상 JSON이었지만, 실험 코드가 `task_framing`을 요구하는 의식 응답 파서에 검토 JSON을 넣어 실패했다. 모델 결함으로 세지 않았다. 원 응답·사용량·실패 영수증·v0 코드를 그대로 보존했다.

검토 JSON만 일반 JSON 파서로 읽도록 고치고, 두 저장 응답을 그대로 재사용해 정정만 호출했다. 후보 지시·문제·checks는 바꾸지 않았다. 원 검토 비용과 회복 정정 비용을 모두 C에 포함했다. 총 26시도 기록 가운데 2개는 이 실험 코드 실패다. 회복 때 세 프로세스가 일시적으로 병행되어 최초 두 프로세스 계획에서 벗어났으며 시간 비교의 한계로 남긴다. 상세: [harness_recovery.json](harness_recovery.json).
