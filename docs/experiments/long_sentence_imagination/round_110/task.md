# 110회차 — 다섯 원칙 점검 루틴

사용자: “그럼 그렇게 만들어서 실험해봐. 시간과 토큰이 얼마나 드는가도 확인하고.”

범위는 문제규정·목적·연구계획 작성과 점검이다. 실제 연구 실행은 하지 않는다. 연구계획의 과업별 질문·증거·방법 연결을 시험하므로 합성 사용자 요청과 이전 실제 모델 계획을 사용한다. 전체 IBL 연구 실행 대신 실제 의식의 최초 규정·계획 작성과 코드로 강제하는 점검 루틴을 시험한다.

## 호출 전에 고정한 비교

- 네 요청 K1/K2(이전 오류 유형의 회귀), N1/N2(새 요청). 모델은 현재 의식 설정 claude_code/opus 고급을 그대로 쓴다.
- S: 현재 의식의 최초 문제규정. A: 현재 prepare로 계획 작성·검사·저장. R: **정확히 같은 A 산출물**을 입력으로 다섯 원칙의 근거를 점검한다. 작성 우연 차이가 없어 추가 루틴의 효과를 직접 비교한다.
- 점검은 한 호출에서 purpose/progress/method/execution/bounds 다섯 기록을 각각 반환한다. 각 기록에는 사용자 원문 인용, 계획의 정확한 인용·필드, 짧은 판정 근거, pass/fail/uncertain, 필요한 수정이 있다.
- 코드는 다섯 항목 누락·중복·없는 인용·부정확한 상태를 거절한다. 모든 pass만 다음 단계에 넘길 수 있다. 사실 의미의 타당성을 기계 검사가 보증하지는 않는다.
- fail/uncertain이면 최대1회 계획을 수정하고 다섯 항목 **전부 다시** 점검한다. 수정된 문서에는 이전 판본의 통과 기록을 재사용하지 않는다. 형식 오류·호출 실패·두 번째 미통과는 미통과/실패로 보존하고 실행용 전달을 차단한다. 사용자의 자료 미확인을 적절한 첫 확인·축소 계획으로 다룬 것은 그 자체로 실패가 아니다.
- 실제 수정을 위한 호출에는 사용자 원문·초안·점검 결과·현재 의식 지침과 연구 가이드를 주며, 지적도 오류일 수 있어 사용자 요청과 대조하게 한다. 과제별 정답/checks·다른 실행 결과는 주지 않는다.
- 두 프로세스에서 K1/N1, K2/N2를 실행한다. 같은 사례의 S→A→R은 순차다. 캐시·시간 효과가 완전 통제된 것은 아니다.

## 사전 판정

질문·목적, 조사 결과가 바꿀 판단, 증거/방법의 적합성, 첫 조사/수정/종료의 실행 가능성, 결론의 한계를 모두 읽고 평가한다. case checks 네 항목은 요청별 핵심 범위의 확인표이며 다섯 원칙 판정과 함께 쓴다. 문장 길이·항목 존재·모델의 pass만으로 성공을 세지 않는다. 정확한 인용과 중요 결함의 반례를 수동 보존한다. 전문 분야 연구방법 전체를 인증하지 않는다.

채택 후보가 되려면 코드 계약 시험을 통과하고 실제 네 결과를 회수해야 한다. A 대비 중요한 결함 또는 실제 실행 가능성의 부족을 새 퇴행 없이 두 사례 이상에서 고치고 새 사례 하나 이상이 포함되어야 한다. 어느 요청에도 새로운 중요한 목적·권한·의미 손실이 없어야 한다. 정당한 미통과 차단은 능력 성과로 따로 기록하되 사용 가능한 계획 개선으로 대신 세지 않는다. 중요한 결함을 놓친 상태로 pass가 된 경우도 별도로 기록한다.

R의 S+A+전체 점검·수정·재점검 입력+출력 토큰과 단계 시간 합 중앙값은 A의 각각2.5배 이하를 이번 허용 상한으로 둔다. 비용 절감과 구별한다. 품질/기계 조건/비용 상한 미달 또는 불명확이면 운영 기본 적용을 기각하고 구현·증거를 보존한다. 통과하면 남은 시간에 새 요청으로 확인한 뒤 정본에 연결한다. 후보 지시와 기준은 출력 관측 후 이번 비교 안에서 고치지 않는다.
