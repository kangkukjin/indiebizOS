# 14회차 — 미완성 설정 초안의 원문 점검

정본 main 80b726e8에서 시작. 자연어·사전 조건은 request.txt/task.md, 합성 원문은 fixtures,
재생기는 generate.py, 첫 완성 초안과 실행본은 first_draft.ibl/main.ibl이다.

## 최초 관측과 발견

manifest 수집→각 초안을 원문으로 읽기→파일·줄·표식 보존→실패 모으기→평탄화와 표식 집계→
두 산출물 저장·재독을 하나의 IBL로 수행했다. 함수는 점검·취합, each는 최대 3개 병렬이다.
직접 원문을 비교하는 한 번의 작은 과제라 시스템 AI 두 번째 실행은 §4-5의 규모 기준에
해당하지 않아 생략했다. 작성자 토큰 미측정·프로그램 내부 모델 호출 0회다.
앞 회차에서 읽기 내부를 보았으므로 도움받은 작성이며 공개 교재만의 독립 발견률로 보지 않는다.

첫 초안 검사 ok/incomplete. 정상 0.776초, 종료 success=true이나 read=2/failed=4,
표식은 기대 7건 중 3건뿐이어서 **부분 달성**이다. 파일 부재 변형 0.785초,
read=1/failed=5·표식 2건으로 역시 부분 달성. 실패와 불완전 표시는 보존했다.

L14-1 구현 결함: `format:"text"`가 명시되어도 JSON 확장자이면 파싱 분기를 타며,
미완성 초안을 읽을 수 없다. 유효 JSON도 text 요청인데 data에 구조를 넣어 계약을 어긴다.
최소 재현은 `.json` 파일의 `{"draft":` 본문을 `[self:read]{path,format:"text"}`로 읽기.
신규 회귀 9개는 수정 전 4실패·5통과였다(소문자/대문자 JSON, txt 대조, 자동/명시 JSON).

## 수리 방향과 품질

read_file 안에서 유효 형식(명시 format 우선, 생략하면 확장자)을 한 번 정하고 JSON/CSV/TSV가
함께 사용하게 한다. 원문 점검을 하려고 확장자를 바꾸거나 셸로 재독하는 우회를 없앤다.
자동 JSON/명시 JSON은 계속 파싱·검증해야 하며, 없는 파일은 실패로 유지한다.
판정 위치만 고치며 공통 출력 검증이나 JSON 유효성 규칙을 완화하지 않는다.

필요한 비용: 여섯 원문과 두 산출물의 재독·줄별 근거 대조. 줄 수가 작아 전체 프로그램도
빠르지만 실패한 파일 때문에 필요한 원문 검사를 끝내지 못했다. 성공/실패 정보는 보존한다.
품질 개선은 검증할 수 있으나 시스템 AI 자발적 선택·전체 토큰 절감률은 미측정이다.

## 수리 적용과 최종 판정

주 과제·변형 HTTP 응답을 회수하고 23:27:25 health live_turns=[]를 확인한 뒤 수정했다.
`data_format`을 JSON 분기 앞으로 이동하고 그 분기도 CSV/TSV와 같은 값을 사용한다.
명시 text가 확장자를 이기며, 자동/명시 JSON의 파싱·거절은 그대로다. 새 문법·어휘 없음.
handler.py만 변경해 `/packages/reload` 성공 후 라이브 검증했다.

세 산출물 쌍의 전건 파일ID·1기반 줄번호·원문·표식·집계와 재독을 verify.py로 확인했다.
실행 ID·지문은 evidence.json에 보존. 최초 초안 무수정으로 수리 후 전체가 달성되었으며
작성 수정 주기 0회다. 원래 실패 상태를 성공으로 소급하지 않는다.

최종 관련 회귀: 신규 세 회차·기존 긴문장 파일/CSV·문서 포맷·회원 파일·공개 결과 계약·
값 의미 소비자·단일 러너를 묶어 **226 passed, 실패 0, 21.30초**. 어휘/파생물·폰 번들 재생성,
공백 검사 및 커밋 관문으로 정합 확인. 읽기 핸들러에 한정된 수정으로 backend 전수와
system 전체 묶음·실제 시스템 AI 후속 사용은 미실시. 성능 비교를 위한 동일 부하 반복은 하지 않았다.
수리 후 더 많은 원문을 처리했으므로 0.776→1.289초를 순수 속도 퇴행/개선으로 해석하지 않는다.
