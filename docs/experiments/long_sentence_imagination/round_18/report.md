# 긴문장 상상훈련 18회차 — 프로젝트 일정표의 선후관계 전파

훈련만 했고 코어 수리는 하지 않았다. 훈련자·시스템 AI 의 기본/변형 네 결과가 모두 사전 완료 조건과 전건 일치했다.
오류(틀린 결과)는 0건이고, 발견은 **낭비 3건(L18-1·3·7)·계약 공백 1건(L18-2)·관측 기록 문제 2건(L18-5·6)·판정이 필요한 관측 1건(L18-4)**이다. 가장 큰 것은 L18-1 이다(같은 날 후속 수리는 맨 아래 절):
순수 표 변환 한 번마다 인자 전체를 네 번 직렬화·해시해서, 훈련자 프로그램 실행 시간의 절반 이상이 쓰이지 않는 지문 계산이었다.

### 시스템 AI 는 어떻게 풀었나

기본(ep4337): 읽기 → IBL 로 정규화·중복 제거·기간 판정 → **그래프 전파는 99줄 Python(`cpm.py`)을 써서 셸로 실행** →
IBL 로 집계·저장 → IBL assert 로 저장본 재읽기 대조 → 58줄 Python 검증기(`verify.py`)를 다시 셸로 실행.
즉 이번 회차의 새 연결(전파 반복)을 IBL 로 쓰지 않았다. `[self:script]` 도 쓰지 않고 실행자 CLI 의 셸 도구로 돌렸다.
최종평가는 **첫 판에 APPROVED**(8.9초, 보완 왕복 0) — 17회차에서 수리한 평가 증거 발췌가 새 분야에서 통했다.

변형(ep4338): 원자료 세 파일을 다시 읽지 않고 **자기 기본 결과 파일**(`agent/base/result.json`·`prepared.json`·`graph.json`·`cpm.py`·`verify.py`)과
지연 파일만 읽었다. 17회차에서 고친 "자기 결과는 다시 써도 된다" 지시가 통했다(L17-2 후속 확인, 표본 1회).
다만 재사용은 결과 참조가 아니라 파일 경로로 이뤄졌고(핵심이 셸에 있었으므로), `cpm.py`·`verify.py` 를 고쳐 쓰지 않고 전체를 새로 썼다.
그 결과 **변형이 기본보다 80초 더 걸렸다**(463.8 → 544.1초). 최종평가는 이번에도 첫 판 APPROVED(7.8초).

## 3. 발견

### L18-1 — 순수 표 변환 호출마다 인자 전체를 네 번 직렬화·해시한다 (확인된 낭비, 구현)

훈련자 P2 는 2,040행·3,243관계짜리 그래프에 62~66초가 걸렸다. 시스템 AI 가 같은 전파를 맡긴 99줄 Python 은 셸에서 곧바로 끝났다(11:04:02 호출, 다음 모델 라운드 전 완료).
단계 예산(54만 / 100만)은 여유였으므로 프로그램은 성공했지만, 시간은 단계 수와 다른 곳에서 나왔다.

- 최소 탐침(라이브, origin training, 입력 2,040행): `table:select` 8회 2.7초(회당 0.33초), `table:join` 8회 6.3초,
  `table:groupby` 8회 3.7초, 람다 `compute` 8회 3.4초. select·join 은 단계 수가 회당 1~2 로 거의 0 인데 시간은 가장 비싸다.
  → `repro/t_*.ibl`.
- 격리 프로파일(임시 상태 폴더, 라이브 저장소 미사용): P2 의 일정 계산만 돌리면 프로파일 포함 70.1초 중
  `expression_ir.digest` 가 **38.6초(55%)**, 타입 추론 4.9초, deepcopy 3.7초였고 **실제 표 처리(data-ops 핸들러)는 1.47초(2%)** 였다.
  프로파일 없이는 34.2초(시스템 AI 와 겹치지 않은 단독 실행). → `repro/profile_p2.py`.
- 원인 위치: `backend/ibl/ibl_v2_runtime.py` `_invoke`. 모든 도구 호출에서 `pack(args)` → `digest(request)` →
  `digest(reuse_identity)` → 필드별 `digest(...)` 로 인자 전체(행 목록)를 네 번 훑는다. 그런데 이 값을 쓰는 저널 영수증·재사용 조회는
  `external`(효과가 pure 가 아닌 호출)·`reusable_read` 일 때만 탄다. `effects:["pure"]` 인 select·join·groupby·compute 에서는
  `reuse_key`·`reuse_parts` 가 어디에도 쓰이지 않고, `request_hash` 는 증거 사건에 한 번 실릴 뿐이다.

시스템 AI 실행도 같은 자리를 밟았다: ep4337 의 집계·저장 프로그램(1,920행 groupby·join 몇 번) 한 번이 16.6초였다.

개선 방향(수리는 별도 작업): 순수 호출에서는 재사용 지문을 만들지 않고, 요청 해시는 필요할 때만 계산한다.
보존할 품질: 읽기·모델 호출의 재사용 판정과 `reuse.skipped` 진단, resume 의 호출 대조는 그대로여야 한다.
확인 방법: `repro/profile_p2.py` 의 digest 누적 시간과 P2 원래 프로그램의 `usage.elapsed_ms`, reuse/resume 회귀 시험.
함께 볼 것: 단계 예산은 표 도구 호출을 1 로 세므로 "어디가 비싼가"를 가리키지 못한다. `steps_by_line` 상위 3줄은 전부 람다였고
실제로 비싼 join 줄은 목록에 없었다. 작성자가 예산 표시만 보고 줄일 곳을 고르면 틀린 줄을 고친다.

### L18-2 — 순수 변환자의 효과 계약 수리가 groupby 한 낱말에 그쳤다 (계약 공백, L17-1 과 같은 부류)

17회차는 `table:groupby` 의 `effects:[unknown]` 을 `pure` 로 고쳤다. 같은 부류를 `describe` 로 전부 조회하니
`table:dedup`·`rename`·`flatten`·`since`·`reduce`·`chunk` 여섯 개가 여전히 `unknown` 이다.
`repro/dedup_in_lambda.ibl` 은 dedup 을 쓰는 지역 함수를 람다에서 불러 17회차와 같은 `PURE_EXPRESSION` 거절을 재현한다.
주 과제는 람다 밖에서 dedup 했으므로 막히지 않았지만, P1 전체 효과가 `unknown` 으로 표시됐다.
개선 방향: 낱말을 하나씩 고르지 말고 "입력만 보고 값을 내는 table 변환자" 전체에 관문을 먼저 건다
(`since` 는 현재 시각에 의존할 수 있으니 순수 여부를 따로 판정). 구현 원인은 조사하지 않았다.

### L18-3 — 자작 관문이 핵심 구현이 끝난 뒤에 울리고, 확인 한 번으로 걷힌 뒤 아무것도 바뀌지 않았다 (낭비, 발견·학습)

ep4337 에서 99줄 `cpm.py` 는 관문 없이 쓰이고 실행됐다. **ep4338 에서도 똑같은 순서가 그대로 반복됐다**(검증기 쓰기에서 201줄로 울림 → 같은 networkx 확인 → 같은 내용 재쓰기). 관문은 두 번째 파일(`verify.py`)을 쓸 때 누적 159줄에서 울렸고,
에이전트는 `[self:install_lib]{package:"networkx",check:true}` 한 번으로 관문을 걷은 뒤 **거절됐던 같은 내용을 그대로 다시 썼다**.
networkx 가 이미 설치돼 있다는 답을 받고도 직접 짠 전파 코드를 유지했다. 관문 문구가 "확인을 요구할 뿐"이라고 밝히므로 설계대로지만,
이 실행에서 관문이 만든 것은 실패 호출 1·확인 호출 1·재쓰기 1(11:07:15~11:07:31)과 그 세 라운드의 모델 왕복이고 결과물은 같다.
한편 턴 시작 회상의 방법 지도에는 `critical_path` 항목이 이미 제시돼 있었다(§아래 L18-5). 지식은 앞에서 제시됐고 관문은 뒤에서 울렸는데
둘이 이어지지 않았다. 결과가 정확했으므로 직접 구현 자체를 오류로 세지 않는다 — 낭비는 관문의 시점과 효과다.
개선 후보(가설): 관문을 첫 구현 파일을 쓰기 전에, 제시된 방법 지도 항목과 함께 건다. 표본 1회라 일반화하지 않는다.

### L18-4 — 핵심 계산이 IBL 밖 셸로 나갔다 (관측, 판정은 주인 몫)

시스템 AI 는 `cpm.py`·`verify.py` 를 `[self:script]` 가 아니라 실행자 CLI 의 `shell` 도구(`/bin/zsh -lc python3 …`)로 돌렸다.
감독 원장에는 호출과 출력이 남았지만(`elapsed_s 0.002` 로 기록 — 실제 실행 시간이 아니다), IBL 의 실행 저널·결과 참조·효과 계약·
`side_effect.write` 기록 밖이다. 스크립트가 쓴 `graph.json` 은 쓰기 사건으로 잡히지 않았다. 변형 요청에서 이 중간 결과를 다시 쓰려면
파일 경로로만 이을 수 있다. 15회차에서 "Script 통로를 만들었는데 사용 0"이던 것이 이번에는 "Script 대신 셸"로 나타났다.
그래프 전파를 IBL 로 쓰는 것이 가능하다는 것은 훈련자 실행이 보였으므로 언어 공백이 아니라 선택의 문제다.
다만 L18-1 때문에 IBL 경로는 같은 계산에 60초가 걸리고 Python 은 즉시 끝난다 — 이 선택에는 근거가 있다.

### L18-5 — 회상 사용 집계가 쓰지 않은 것을 "사용"으로 적었다 (관측·축적)

ep4337 의 `recall.used` 는 방법 지도 제시 6개 중 `duckdb` 를 used(evidence `mentioned`)로 적었다. 14개 도구 호출 어디에도
duckdb 는 없다(작성 프로그램·두 스크립트의 import 확인). 반대로 실제 과제와 맞닿은 `critical_path` 는 제시됐으나 쓰이지 않았다.
`mentioned` 근거는 글에 낱말이 나왔다는 뜻일 뿐이라, 이 집계를 증류 게이트나 지식 지도 평가에 쓰면 거꾸로 된 신호가 된다.
해마 실행기억은 empty 였다(새 분야이므로 기대대로).

### L18-7 — 긴 프로그램의 한 낱말을 고치려면 전체를 다시 써 보내야 한다 (낭비, 작성 마찰)

ep4338 의 저장·보고 프로그램(7,201자)이 `[table:rename]{mapping:…}` 때문에 검사에서 `UNKNOWN_ARGUMENT`("비슷한 인자: map")로 거절됐다.
