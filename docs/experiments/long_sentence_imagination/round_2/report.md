## 4. 발견 (갭 8건, 수리 안 함)

### L2-1 쓰기로 끝나는 프로그램은 reuse 로 앞 읽기를 하나도 재사용하지 못한다 — ★최우선
- **분류**: 계약 공백 + 과도한 비용
- **최소 재현** (`repro/reuse_after_write_{a,b}.ibl` vs `reuse_no_write_{a,b}.ibl`): `읽기(venues.json) → 쓰기(out/scratch.txt)` 프로그램을 반환만 바꿔 reuse →
  `candidates 0, reused 0`. 쓰기 줄만 뺀 같은 쌍 → `candidates 1, reused 1`. 원 실행의 continuation 도 `read_calls 0, state_change_possible true`.
- **전체 과제에서**: 원래 v3 → 변형 B reuse 에서 읽기 6건(CSV·JSON·후기 4) 중 **0건 복원**, 후보 1건(쓰기 뒤 재읽기).
  교재 381행 "원 실행의 쓰기 전·동시 읽기는 제외한다"와 일치하는 **문서화된 동작**이지만, `self:write` 는 `write_resources:{file:path}` 를 선언하고
  쓰기 경로(out/)와 읽기 경로(input/)가 겹치지 않는데도 전부 제외된다. 긴 작업의 대부분이 "계산 → 저장"으로 끝나므로
  교재 6항의 "함수 하나 고쳐 reuse" 흐름이 실전에서 거의 통하지 않는다(1회차 변형 reuse 가 3건 복원된 것은 그 실행이 쓰기 전에 실패했기 때문).
- **함께 관측**: 모델 호출은 재사용하지 않으므로(계약) 입력이 같은 `table:ai` 가 다시 불렸다 — 변형 B 17.9s 중 ~17s, 토큰 미상.
  열린 항목 "model 효과 재사용 판정"(메모리 ibl-incremental-execution-2026-09-26)과 같은 계열.
- **우회(미검증)**: 계산 프로그램과 저장 프로그램을 나누고 `$ref` 로 잇기.

### L2-2 `table:ai` 의 schema 가 정적 검사에 쓰이지 않는다 — 오타가 모델 비용을 치른 뒤에야 잡힌다
- **분류**: 문법·값 계약 공백
- **재현** `repro/ai_schema_typo.ibl`: schema `"pros(문자열 목록), cons(문자열 목록)"` 뒤 `$it.conz` 를 읽음 → check **통과**(incomplete, result_type `{c: Unknown}`)
  → 실행 6.2s(모델 호출) 뒤 `MISSING_FIELD conz`(available pros·cons). 전체 과제에서도 `$요약` 의 형은 `Unknown` 이라 `pros/cons` 접근이 검사되지 않았다.
- **계약과의 불일치**: describe `target_description` 은 schema 를 "정적 검사·출력 지시·필드 존재 검사 공용"이라 적는다. `callable_contract` 의 params 는 전부 `Unknown`, result 는 `Record`.
- **영향**: 긴 프로그램에서 모델 호출 뒤의 오타는 앞 단계·모델 비용을 모두 치른 뒤에 실패하고, L2-1 때문에 재실행 때 복원도 거의 없다.

### L2-3 실패한 check 응답은 여전히 정보 가드를 통째로 싣는다 (51KB)
- **분류**: 과도한 비용 (L1-5 의 남은 가지)
- **관측** `runs/v1_check.json`: status invalid, 전체 51,008자 = guards 26,090(information 24건 표시, `guards_total 82`·`guards_omitted 58`, **`guards_ref` 없음** → 생략분을 읽을 길도 없음)
  + issues 11,784 + functions 6,281 + preflight 5,307. 같은 프로그램의 성공 check(v2)는 13,422자·`guards_ref` 있음.
  가드 한 건의 `message` 는 `"Record"`(형 이름뿐), `actual:"Unknown"`.
- **영향**: 작성 중엔 실패 check 가 성공 check 보다 잦다. 오류를 고치는 동안 매번 정보 가드 ~26KB 가 모델 문맥에 들어간다. 오류·경고는 보존해야 한다.

### L2-4 실행 결과 저장본이 행 수에 비례해 커진다 (행당 ~1.4KB의 식 단위 증거)
- **분류**: 과도한 비용(저장·조회)
- **관측**: 원래 v3 의 업무 값은 ~5KB 인데 `result_ref.chars` = **1,255,621**. 내역: `evidence` 1,090,567(식 노드 사건 10,488건 — ref 3,762·field 2,525·binary 1,440·literal 924…),
  `source_map` 104,639, `recordings` 55,645(읽기 원문 사본). 재현 `repro/evidence_scale.ibl`(each+filter 두 단계, 결과는 정수 하나):
  100행 146,993자 / 1,000행 1,452,346자 — **선형, 행당 ~1.45KB**. 10,000행이면 ~15MB 로 추정(미측정).
- **영향**: 실행 시간은 작다(1,000행 0.58s). 비용은 저장 용량과 `result_ref.chars` 가 업무 값 크기를 가리는 것. 보존 기간·정리 정책은 확인하지 않았다(미검증).
  증거가 L2-1 의 reuse·실패 진단에 필요한지, 요약(호출·실패 사건만)으로 충분한지는 수리 턴의 판단.

### L2-5 같은 수가 출처(리터럴/inputs)에 따라 "6"과 "6.0"으로 표시되고, `//` 는 정수를 보장하지 않는다
- **분류**: 문법·값 계약 공백 (산출물 품질)
- **재현** `repro/floordiv_display.ibl`(inputs `비율:0.5`): `(0 - 12*0.5)//1` → `f"${…}"` = **"-6"**, `(0 - 12*$비율)//1` → **"-6.0"**, 두 값 `==` true.
  `repro/input_float.ibl`: `f"${12*0.5}"` = "6.0". 전체 과제 변형 B 제안서: "필요 좌석 67.0/70", "수용 부족(67.0명 > 60석)".
- **계약과의 불일치**: 문법 전문 113~114행 "계산한 위치는 `round(x)`나 `//`로 정수로 만든다" — `//` 결과는 인덱스로는 받아지지만(`$L[6.0]` 성공) 표시는 정수가 아니다.
  교재 "소수 리터럴은 십진수로 유지"는 리터럴 경로만 말하고 inputs 의 JSON 소수 경로는 말하지 않는다.
- **영향**: 사람에게 보이는 산출물에 "67.0명" 이 새어 나간다. 우회 `round()`(v4).

### L2-6 삼항 가지 안의 파이프가 "`:`가 필요합니다" 라는 엉뚱한 SYNTAX 로 온다
- **분류**: 작성·발견 마찰 (경미)
- **재현** `repro/ternary_pipe.ibl`: `len($s) > 0 ? $s >> [table:each]{…} : []` → `SYNTAX` "조건 값은 `조건 ? 참 : 거짓` 형태입니다. ':'가 필요합니다."
  같은 부류(순수 식 자리의 호출)를 내장 함수 인자에 쓰면 `PURE_EXPRESSION` + "호출 결과를 먼저 `$이름=`으로 받으라"는 정확한 처방이 온다. 삼항 가지만 원인과 처방이 빠진다.

### L2-7 목록 키 `sorted` 가 정적으로 알 수 있는데도 check 를 통과한다
- **분류**: 작성·발견 마찰 (경미)
- **재현** `repro/sorted_list_key.ibl`: `sorted($r, ($x)=>[$x.a, $x.b])` → check 통과(결과형까지 계산) → 실행 `UNORDERED`.
  키 람다의 반환형이 `List<Number>` 로 정적으로 확정되는 경우다. 실행 오류 문구는 훌륭하다 — 검사 단계로 앞당길 여지.
  전체 과제에서는 앞의 읽기 전부를 치르고 94행에서 실패했다(모델 호출 전이라 비용은 작았음).

### L2-8 프로그램 안 모델 호출의 비용이 실행 봉투 어디에도 없다
- **분류**: 과도한 비용(관측 불가)
- **관측**: 원래 v3 의 `usage` = `{steps:13793, rows:590, elapsed_ms:18707}` 뿐. 저장본 전체(1.25MB)에 모델 토큰·모델 이름·기어가 없고, `table:ai` 녹화의 evidence 는
  `{markers:{}, attachments:{}}`. describe 는 "일반 실행은 모델 비용(기어 실행 축)"이라고만 한다. 비교로 `table:judge` 설명은 "usage 신고"를 명시한다.
- **영향**: 가이드 §5 비용 축(모델 입력·출력·캐시 토큰)을 IBL 표면에서 잴 수 없다 — 이번 회차 모델 토큰은 **미상**. 시스템 내부 로그에 있는지는 확인하지 않았다(소스 미열람).

### 발견이 아님(확인만)
- `table:groupby` 의 describe `effects:["unknown"]` 이지만 실행기는 순수로 취급해 뒤 읽기의 reuse 를 막지 않는다(`repro/reuse_after_groupby_*`: 2/2 복원). 표시만 어긋남.
- `sorted`·flat_map 을 거쳐도 레코드 필드 형은 보존된다(`repro/sorted_type_loss.ibl`). 본 과제의 `venue: Unknown` 은 JSON `.data` 가 정적으로 `Unknown` 이기 때문(1회차 수리 설계대로).
- 변형 A 제안서에 후기 파일의 절대 경로가 실린 것은 훈련자 프로그램이 `$error.message` 를 그대로 쓴 선택이다.

## 5. 개선 방향 (다음 수리 턴의 입력 — 이번에는 집행 안 함)

1. **L2-1** reuse 제외 판정을 "쓰기 전 전부"에서 **선언된 쓰기 자원과 겹치는 읽기**로 좁힌다(`write_resources` 가 있는 쓰기만; 효과 미상 호출은 지금처럼 보수적으로).
   소유 = reuse 후보 판정 한 곳. 관문 = `repro/reuse_after_write_*`(다른 경로 1/1, 같은 경로 0/1) + 원래 v3→변형 B 에서 읽기 6건 복원. 교재 381행 동시 개정.
   모델 호출 재사용은 별도 판정(열린 항목과 합류) — 입력 해시가 같으면 명시적 선택으로 복원할지.
2. **L2-2** `table:ai`(및 schema 를 받는 모델 변환자)의 schema 문자열을 정적 결과형 `Record{items: List<{입력 필드…, 스키마 필드…}>}` 로 투영.
   1회차 원칙 "선언 계약도 같은 투영 함수로"와 같은 자리. 관문 = `repro/ai_schema_typo.ibl` 이 check 에서 `MISSING_FIELD`.
3. **L2-3** 성공 check 의 가드 접기(L1-5)를 invalid check 에도 같은 함수로 적용하고, 생략이 있으면 반드시 `guards_ref` 를 싣는다. 형 이름뿐인 `message` 정리.
4. **L2-4** 저장본의 식 단위 증거를 요약 가능한지 판단(호출·실패·값 출처 사건만 유지, 순수 식 노드는 source_map 참조로). `result_ref` 에 업무 값 크기를 따로 표기.
   관문 = `repro/evidence_scale.ibl` 1,000행의 저장 크기, 실패 진단·reuse·evidence() 조회가 유지되는지.
5. **L2-5** 수의 표시 규칙을 출처와 무관하게 하나로(정수값 소수는 정수로 표시하거나, `//` 결과를 정수로). 문법 전문 114행 문장과 대조하는 관문.
6. **L2-6·L2-7** 삼항 가지의 호출을 `PURE_EXPRESSION` 으로 같은 처방과 함께 보고. 정적으로 List/Record 로 확정된 `sorted` 키는 check 에서 `UNORDERED`.
7. **L2-8** 모델 변환자 호출의 토큰·모델·기어를 실행 봉투 `usage` 에 합산(1회차 L1-5 와 함께 비용 축의 관측 기반).
