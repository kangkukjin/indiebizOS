## 최초 실행과 작성 수정

prepare_v0는 첫 초안 통과. 기본3600행·누락2400행이며 실패 경로·불완전성도 보존했다.
훈련자 참조 연결에서 input_args의 이름 봉투를 값 자리에 한 겹 더 넣어 검사 거절1회.
이는 하네스 작성 실수이며 제품 결함으로 세지 않는다. 이름을 prepared로 바꾸어 수정했다.
settle_v0는 빈 입력 check 통과했지만 실제 참조 입력에서는 nullable 단가 산술로 거절됐다.
별도 status가 ok인 분기의 단가 non-null 관계까지 검사기가 추론하지 않는다.
settle_v1은 같은 필드의 null을 직접 분기해 통과했다. 원자료 재수집은 없었다.
진단 최소 요청의 edition 생략도 HTTP 계약대로 거절됐고 수정했다.

## 발견과 수리

- L25-1 작성 마찰/진단: null을 포함한 산술의 안내가 숫자문자열 변환을 제시해 직접 null 분기라는
  현재 지원 해법을 설명하지 못했다. `ibl_v2_analysis.numeric_operand`의 Null 오류에 직접 분기 안내를 넣었다. 상태 변수로 관계를 숨긴 식은 거절이 유지되는 보수적 검사 범위이며,
  무조건 허용하거나 null을0으로 바꾸는 해결은 하지 않는다. 실제 거절과 실행되는 수정 표현을 함께 가르친다.
- L25-2 구현 낭비: guard가 Unknown·필드 제약 없는 Record·원소 제약 없는 List까지 infer로 내부 전건의
  구조 타입을 만들었다. 기존 계약은 바깥 종류만 확인하면 된다. 3600행의 독립 프로세스 측정에서
  해당 검사마다 약0.4초. `ibl_v2_types.guard`에서 계약이 요구하지 않는 내부 추론을 생략했다. 선언된 필드/원소 타입은
  원래 깊은 검사를 유지한다. 시간비보다 불필요한 내부 방문0회를 회귀 조건으로 삼는다.
- 독립 AI는 검증의 이질 원천 자료에서 필드 타입 정보를 잃어 check 거절 뒤 get을 사용했다.
  이어 전건 검증·저장·재독을 한 실행에 넣어 최대100만 걸음 예산에서 중단했다.
  완료된 저장·읽기 영수증을 재사용해 후속 검증을 끝냈다. 검수 자체는 필요 비용이며,
  예산을 넘겨 이미 끝낸 부분을 되짚은 비용은 작성·분할 개선 대상이다.

## 검증·비용·잔여

훈련 전체 종료 전 라이브 구현/계약 변경 없음. 프로파일과 수리 후보는 별도 프로세스에서만 실행했다.
훈련자 작성·진단·수리·회고 토큰 미측정, 프로그램 내부 모델0. 훈련자 실행기 시간은 AI의 작성·검수 포함
시간과 직접 성능비로 비교하지 않는다. 국소 guard 개선을 전체 AI 시간/토큰 절감률로 환산하지 않는다.
[훈련 종료 영수증](evidence/training_end.json)으로 모든 훈련 종료를 확인한 뒤 코드를 고쳤고,
[수리 적용 기록](evidence/repair_activation.json)과 라이브 진단으로 새 코드 적용을 확인했다.

### 동일 계산 비교

[반복 측정](evidence/runtime_after.json)은 수리 전 guard를 기준 커밋에서 추출하고 실제 수정 guard와
같은 컴파일 결과·준비 자료를 번갈아3회 실행했다. 이미 컴파일된 순수 정산 구간이며
파일 I/O·모델·네트워크·최종 응답 투영을 제외했다. 중앙값 **2.461590→1.983648초, 약19.4% 감소**.
값·근거·기록·걸음 수·행수 모두 동일했다. 선언된 원소/필드 타입은 기존 깊은 검사를 유지한다.
라이브 전체 HTTP도 성공했지만 부하가 달라 전체 시간 개선의 증거로 사용하지 않는다.

### 남은 범위

계산 값 오류는 발견하지 않았다. 이번 수리는 불필요한 깊은 검사·부정확한 처방·시험 격리다.
상태 문자열을 통한 nullable 관계 추론은 지원하지 않으며 원래 거절식을 허용하도록 바꾸지 않았다.
예산 분할과 참조 연결은 교재를 보완했지만 수정 교재를 읽은 독립 AI의 새 과제를 재훈련하지는 않았다.
따라서 AI 전체 시간·토큰 비용 감소나 일반 업무 전체의 안정성을 입증했다고 말할 수 없다.
