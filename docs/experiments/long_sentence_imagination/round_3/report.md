## 4. 발견 (갭 11건, 수리 안 함)

### L3-1 효과 미상 호출 하나가 프로그램 전체의 reuse 를 0 으로 만든다 — ★최우선
- **분류**: 계약 공백 + 과도한 비용.
- **관측**: 크롤 설명이 "대목 찾기는 fn:본문에서찾기"라고 권하는 관용구는 `effects:["unknown"]`(describe). 이것이 끼면 `continuation.read_calls 0`·`state_change_possible true`.
  최소 대조: `repro/reuse_lambda_{a,b}.ibl` → 크롤 1건 **reused 1/1**, `repro/reuse_find_{a,b}.ibl` → **0/0**. 실과제 변형 B: candidates 1·reused 0, 크롤 6건 재수집 + 모델 7회 재호출.
- **원인 가설**: L2-1 수리의 "쓰기 자원 미상이면 전체 제외"가 효과 미선언 legacy 관용구에도 적용. 이 관용구는 실제로 텍스트 검색이며, 관측된 외부 효과는 큰 입력의 스필 파일(`data/spill/…`) 기록뿐.
- **긴장**: 작성자는 "람다 필터 = 예산 초과(L3-3)" 와 "관용구 = reuse 소실" 중 하나를 잃는다. 웹 규모 조사에서 두 권장 경로가 충돌.

### L3-2 모델 호출 뒤 순수 계산 실패마다 모든 모델 호출을 다시 낸다
- **분류**: 과도한 비용(계약상 동작 + L3-1 결합). 2회차 L2-1 의 "모델 출력 재사용 미지원" 잔여, 열린 "model 효과 재사용 판정"과 연결.
- **관측**: v5b→v6→v7 의 실패 원인은 모두 모델 **뒤** 순수 계산(`number()`)이었는데 매번 모델 6~8회·입력 10.2만~13.9만 토큰을 재지불.
  회차 전체 모델 입력 814,155·출력 38,168(47요청) 중 최종 성공 1회분은 123,249. `partial`/`partial_reads` 는 실패 지점 가지만 담아 앞 단계 변수(`$추출`)를 새 프로그램에 넘길 수 없다 —
  구제하려면 처음부터 중간값을 반환하도록 프로그램을 나눠 설계해야 하며, 교재에는 이 설계 지침이 없다.

### L3-3 웹 본문 규모의 거르기가 기본 실행 예산을 넘고, BUDGET 진단은 무엇이 다했는지 말하지 않는다
- **분류**: 작성·발견 마찰 + 계약 공백.
- **관측**: 위키 6쪽(약 6,300문단) 키워드 람다 필터 → steps 100,002 로 중단(v3). 모델·웹 없는 재현 `repro/budget_filter.ibl`(6,000줄) → rows 10,001·steps 99,025.
  진단은 "공유 실행 예산을 초과했습니다" + `details:{row_index, operation}` 뿐 — 어느 예산(단계/행)·소비량·한도·처방(도구 쪽 필터 등)이 없다.
  한도 수치는 문법 전문 234행에만 있고 교재·오류 hint 에 없다. `split` 결과의 each 행도 1만 행 예산을 먹는다는 사실은 재현으로 처음 알았다.

### L3-4 `table:ai` schema 가 2필드 이상이고 입력이 `목록 | []` 합집합이면 입력 필드가 결과형에서 사라진다(거짓 MISSING_FIELD)
- **분류**: 구현 결함(정적 투영). L2-2 수리(선언 이름 투영)의 인접 경로 — 회귀 가능성.
- **최소 재현**: `repro/ai_schema_input_fields_9.ibl`(함수가 `{문단:[{a,t}]}` 또는 `{문단:[]}` 반환 → `$d.문단 >> [table:ai]{schema:"x(…), y(…)"}` → `$it.a`) → check `MISSING_FIELD a, t`.
  schema 1필드(8·11)는 통과, 2필드(9·10·12)는 모두 실패. 입력이 단일 타입이면(1~7) 통과. 실과제 v8 에서 필드 `논쟁` 하나 추가로 발생 → `get()` 우회.

### L3-5 `has()` 술어로 거른 뒤에도 필드 좁힘 없음 — 오류 문구는 "has/get을 쓰세요"
- **분류**: 문법·값 계약 공백. L1-2(Bool 판별 필드 좁힘, 수리됨)의 인접 형태.
- **재현**: `repro/has_narrow.ibl` — `filter{where:($r)=>has($r,"실패")}` 뒤 `$it.실패` → MISSING_FIELD. 처방 문구가 이미 쓴 has 를 권해 순환한다. 우회 `get(…,…,"")`.

### L3-6 `preserve_rows` 위반 진단에 어느 행이 누락/중복인지와 모델 원출력이 없다
- **분류**: 작성·발견 마찰(실행 진단).

## 5. 개선 방향 (다른 분야에도 통하는 공통 원인)

1. **L3-1·L3-11 한 벌**: legacy 관용구의 효과·반환을 선언하는 공통 경로(효과 추론 또는 등록 계약)가 없어, 순수 검색이 "미상 쓰기"로 취급된다.
   처방 후보 = 관용구 효과를 본문 도구 효과의 합으로 계산해 계약에 싣고, 스필 같은 내부 임시 파일은 업무 쓰기 자원에서 제외. 검증 = `reuse_find_b` 1/1, 변형 B 크롤 6건 복원.
2. **L3-2**: 모델 출력 재사용은 별도 판정(열린 과제). 그 전이라도 교재에 "모델 뒤 계산이 길면 추출 단계 결과를 반환하는 프로그램으로 나누고 `$ref` 로 잇는다"는 설계 지침과 예제가 필요.
   검증 = 뒤 단계 버그 수정 때 모델 호출 0.
3. **L3-3**: BUDGET 진단에 소진 차원·소비·한도·처방(도구 쪽 필터, 사전 take 금지 시 분할 실행)을 싣고, 교재 "전건 처리" 절에 예산 수치와 웹 규모 권장 경로를 둔다. 검증 = `budget_filter` 진단 문구.
4. **L3-4·L3-5**: 정적 타입의 합집합 처리 — schema 투영이 입력 행 합집합을 보존하도록, filter 좁힘에 `has()` 를 판별 술어로 추가. 검증 = 재현 12개 + v8·v5 원문이 우회 없이 통과.
5. **L3-6·L3-7·L3-10**: 실패 진단에 "무엇이 들어왔고 무엇을 기대했나"(누락/중복 `_i`, 원문 값, HTTP 상태) — 1회차 L1-6 계열의 공통 처방.
6. **L3-8·L3-9**: 문구·경고 정밀화(경미).

재검증 조건: 원래 `v8b.ibl`·`varB_v1.ibl` 을 우회(`get`) 없이 되돌린 판으로 실행 → 달성 조건 유지 + 변형 B reuse 로 크롤 6건 복원, round_3/repro 전부, round_1·2 repro 회귀.
