## 2. 상반된 결과가 함께 나오는 조건 [해석]

- **과제 성격**: 단축은 표준화된 신규 구현(S1)과 짧은 자기완결 글쓰기(K1)에서 나왔다. 감속은 숙련자가 익숙한 대형 저장소에서 문서·테스트·린트 같은 암묵적 요건까지 충족해야 하는 이슈(S3)에서 나왔다. K2는 같은 도구라도 과제가 AI 능력 경계 밖이면 정답률이 떨어진다는 것을 보여준다.
- **숙련도·익숙함**: 저숙련·저근속자의 이득이 큰 경향은 K3(근속 1개월 미만 +46%), K2(하위 절반 43% 대 상위 절반 17%), S2 Microsoft(주니어 +21~40%, 시니어 +7~16%)에서 보인다. 다만 S2의 집단 간 차이는 비유의(p=0.13~0.77)이고, S1에서도 탐색적 수준이다.
- **측정 지표가 다름**: S2의 PR +26%는 산출량이지 시간 단축이 아니다. 빌드가 +38% 늘고 성공률이 하락한 점은 시행착오형 작업일 가능성이 있다고 저자도 언급한다. S1의 55.8%는 시간 감소율이며 같은 크기의 생산성 증가율이 아니다.
- **자기보고와 측정의 괴리**: S3에서는 실제로 19% 느려졌는데도 개발자들이 20% 빨라졌다고 믿었다. S1에서는 자기보고(35%)가 측정치보다 낮았다. 어느 쪽이든 체감으로는 계획 수치를 정할 수 없다.
- **인과 추정 대상(estimand)이 다름**: S1은 완료자 조건부, S2는 채택자 기준 TOT, S3·K1은 배정 효과, K3는 준실험 접근 효과다. 같은 '효과'라는 말로 묶어 비교할 수 없으므로, 서로 다른 효과값을 평균해 20%를 도출하는 것은 부당하다.
- **도구 세대**: S1·S2는 자동완성형이고, S3는 채팅·에이전트형(2025년 초)이다. 최신 도구가 S1·S2보다 낫다는 근거도, S3보다 낫다는 근거도 위 자료에는 없다.

## 3. "최소 20% 단축"을 계획해도 되는가

**[결론] 계획 수치로 약속할 수 없다.**
- **관측**: 개발 시간을 직접 잰 RCT 두 건의 결과가 −55.8%(S1)와 +19%(S3)로 방향부터 반대다. 실무 현장 RCT(S2)는 시간을 재지 않았다.
- **해석**: 20% 이상 단축의 직접 근거는 S1 하나다. S1은 단일 신규 과제, 프리랜서, 완료자 분석이라는 조건이어서 유지보수 절반과 리뷰 절차를 포함하는 팀 단위 계획에 그대로 옮길 수 없다. S1의 신뢰구간 하한 21%도 그 과제 조건에서만 성립한다.
- **품질**: 직접 측정한 개발 연구가 없다. S2의 빌드 성공률 하락 신호와 K2의 프런티어 밖 오류 증가가 경고 근거다.

## 4. 회사 구성별 적용과 한계 [해석]

회사 구성은 주변분포(주니어/시니어 절반, 신규/유지보수 절반)만 주어졌다. 따라서 주니어×신규 같은 교차칸의 비중은 추정하지 않으며, 효과를 칸별로 가중합산하지도 않는다.

- **신규 기능 개발(절반)**: S1과 가장 가깝다. 다만 S1은 테스트가 미리 주어진 소규모 단일 과제였다. 실제 요구 해석과 기존 시스템 연동이 붙으면 효과가 얼마나 남는지는 미확인이다.
- **기존 코드 유지보수(절반)**: 담당자가 해당 코드베이스에 익숙하고 품질 기준이 높다면 S3 조건과 겹친다. 이 경우 감속 가능성을 배제할 수 없다. 반대로 낯선 코드베이스에 대해서는 S3 저자가 일반화하지 말라고 명시했으므로 근거가 비어 있다.
- **주니어(절반)**: S2, K2, K3에서 이득이 더 크다는 방향성이 보이지만 개발 분야에서는 비유의하거나 탐색적이다. K2의 프런티어 밖 결과는 출력을 맹목적으로 수용하는 데 따르는 오류 위험을 시사한다.
- **시니어(절반)**: S2에서 +7~16%(산출량), S3에서 감속이 나왔다. 20%를 기대할 근거가 가장 약한 집단이다.
- **K1~K3의 적용 범위**: 설계 문서·이메일·티켓 설명 같은 작성 업무에는 유비할 수 있다. 코드 정확성, 리뷰 통과, 유지보수성에 대해서는 근거가 되지 못한다.

## 5. 권고: 조건부 도입 [제안]

- 도구는 6주 실험 범위 안에서만 도입한다.
- 사업계획에는 시간 단축을 **0%**로 둔다. 20%는 7절의 채택 규칙을 통과했을 때에만 반영한다.
- 보류를 권하지 않는 이유: 산출량 증가 근거(S2)와 신규 과제 단축 근거(S1)가 있고, 자체 측정 없이는 판단 자체가 불가능하다.
- 전면 도입을 권하지 않는 이유: 유지보수·시니어 영역의 감속 근거(S3)와 품질 근거의 공백이 있다.

## 6. 6주 사내 실험안 [제안값]

| 항목 | 제안 |
|---|---|
| 무작위화 단위 | **티켓** 단위로 'AI 허용/불허'를 배정한다(S3 방식). 같은 개발자가 두 조건을 모두 수행하므로 개인차가 상쇄된다 |

| 티켓 규모·난이도 | 착수 전에 담당자와 리뷰어가 예상 인력시간과 난이도(상·중·하)를 독립적으로 기록한다. 대상은 예상 2~16시간 티켓으로 하고, 이보다 큰 작업은 분할하거나 제외 목록에 기록한다 |

| 시간 지표 | ① **인력시간**: 작성자 작업시간 + 리뷰어 시간 + 재작업 시간(주지표). ② **달력시간**: 착수부터 머지까지(보조지표). 두 지표를 혼용하지 않는다 |
| 리뷰어 시간 | 리뷰 코멘트·승인에 쓴 시간을 리뷰어가 기록한다. 작성 시간이 줄어도 리뷰 시간이 늘면 그 증가분을 상쇄해 계산한다 |
| 반복측정 불확실성 | 개발자 무작위효과와 층 고정효과를 넣은 로그시간 모형을 쓴다. 신뢰구간은 개발자 단위 클러스터 부트스트랩으로 구한다. 20명·6주라는 규모로는 검정력을 보장할 수 없으므로, 구간이 넓으면 '판단 불가'로 보고한다 |
| 미완료·이월 | 6주 시점의 미완료 티켓은 제외하지 않는다. 배정 그룹별 완료율을 보고하고, 이월 티켓은 2주 추적 후 반영한다. 미완료분에 최악값과 최선값을 대입한 민감도 분석을 함께 낸다 |
| 품질 지표 | 리뷰 반려 횟수, CI 실패율, 머지 후 결함, 리버트·핫픽스, 보안 스캔 경고를 본다 |
| 품질 관찰 지연 | 머지 후 결함은 마지막 머지로부터 **6주 추가 관찰**한 뒤에 확정한다. 그 전에는 채택 판정을 하지 않는다 |
| 비열등 한계(제안) | AI 허용군이 불허군보다 다음 수준 이상 나쁘지 않아야 한다. 머지 후 결함 티켓 비율 +3%p 이하, 리뷰 반려율 +10%p 이하, CI 실패율 상대 +20% 이하. 고위험 보안 결함은 0건 허용 |
| 중단 규칙 | 다음 중 하나라도 해당하면 실험을 즉시 중단하거나 해당 층에서 AI를 정지한다. AI 관련 고위험 보안 결함 또는 장애 1건 발생, 3주 중간점검에서 품질 지표가 비열등 한계를 2배 초과, 특정 층(예: 유지보수)에서 인력시간이 명확히 증가하고 구간 전체가 0보다 위 |
| 최종 20% 채택 규칙 | 다음을 모두 충족할 때만 계획에 20%를 반영한다. 첫째, 인력시간 감소 ITT 추정치의 90% 구간 **하한이 20% 이상**. 둘째, 신규와 유지보수 각 층의 점추정이 모두 단축 방향. 셋째, 모든 품질 비열등 기준 통과. 점추정은 20% 이상이지만 하한이 0~20%라면 도구는 유지하되 계획에는 하한값만 반영한다. 구간이 0을 포함하면 계획 수치 없이 재실험한다 |
| 체감 지표 | 개발자의 체감 단축률을 따로 수집하되 판단 근거로 쓰지 않는다(S3의 괴리 사례) |

## 7. 남은 불확실성

- **개발 품질**: 직접 측정한 연구가 없다(S1 미측정, S3 수치 없음, S2 빌드 지표만).
