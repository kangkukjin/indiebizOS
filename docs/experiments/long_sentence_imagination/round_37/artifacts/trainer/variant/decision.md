# 의사결정 메모: 시니어 중심·유지보수 중심 조건에서 AI 코딩 도구 도입

## 1. 결론

**이 조건에서는 개발시간 20% 절감을 약속할 수 없다.** 사업계획의 시간 절감 가정은 **0%**로 둔다(제안값). 도구는 6주 사내 실험 범위에서만 쓴다.

조건이 바뀌면서 근거는 20% 약속에 더 불리해졌다. 우리 회사(개발자 20명 중 시니어 18명, 업무 90%가 익숙한 대형 기존 저장소의 유지보수)와 가장 비슷한 연구는 METR(S3)이다. 이 연구에서는 AI 허용 이슈의 완료시간이 **19% 늘었다**([METR 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). 이번 판단에는 기존 근거표만 다시 썼고, 웹 원문을 새로 수집하거나 추출하지 않았다. 결정을 뒤집을 만한 공백은 외부 연구로는 채울 수 없고 사내 측정으로만 채울 수 있다고 봤기 때문이다.

## 2. 연구별 적용 비중 변화

| 연구 | 변화 | 근거 |
|---|---|---|
| S3 METR | **↑ 핵심 근거** | 숙련 개발자 16명이 여러 해 기여해 온 대형 저장소(100만 줄 이상)에서 실제 이슈를 처리했다. 결과는 완료시간 +19%이며, 이 수치는 'AI 사용 허용' 배정의 효과다. 저자가 밝힌 적용 범위(익숙한 대형 저장소, 높은 품질 기준)와 우리 조건이 겹친다. 다만 표본이 16명이고, 신뢰구간 수치는 블로그 본문에 없으며, 시간은 자기보고값이다. 사용 도구는 2025년 초 기준이다 |
| S2 현장 RCT 3건 | 유지(부분 근거) | Microsoft의 장기근속자는 +8~13%, 시니어는 +7~16%였다. 단, 측정 대상은 시간이 아니라 PR 산출량이고, 집단 간 차이는 비유의(p=0.13~0.77)이며, 추정치는 채택 기준 W-IV(TOT)다([Cui 외 2025](https://economics.mit.edu/sites/default/files/inline-files/draft_copilot_experiments.pdf)). 시니어 수치도 20%에 못 미친다 |
| S1 Peng | **↓** | 프리랜서가 JavaScript HTTP 서버를 처음부터 구현한 단일 과제에서 완료시간이 55.8% 줄었다([Peng 외 2023](https://arxiv.org/pdf/2302.06590)). 신규 구현 과제라서 우리 업무의 90%인 유지보수와 맞지 않는다. 해당 연구에서도 경력이 많을수록 효과가 작아지는 방향의 계수가 나왔지만(p=0.0629) 탐색적 수준이다 |
| K2 Dell'Acqua | ↓(이득 크기) / 유지(위험) | 상위 절반 기량자의 향상폭은 17%로, 하위 절반의 43%보다 작았다. 이는 시간이 아니라 품질 점수 기준이다. 과제가 AI 능력 범위 밖이면 정답률이 평균 19%p 떨어졌다는 경고는 그대로 적용된다([HBS WP 24-013](https://mitsloan.mit.edu/sites/default/files/2023-10/SSRN-id4573321.pdf)) |
| K3 Brynjolfsson | ↓(이득 크기) / ↑(시니어 위험) | 근속 1년 초과 상담원은 효과가 없었다. 최상위 숙련층은 생산성 증가가 없었고, 해결률·NPS가 소폭 유의하게 떨어졌다([NBER 31161](https://www.nber.org/system/files/working_papers/w31161/w31161.pdf)). 고객지원 업무이므로 간접 참고로만 쓴다 |
| K1 Noy·Zhang | ↓ | 짧은 글쓰기 과제 결과이며, 문서 작성 업무에 대한 유비 근거로만 쓴다([Noy·Zhang 2023](https://economics.mit.edu/sites/default/files/inline-files/Noy_Zhang_1.pdf)) |

**바뀌지 않은 점**
- 개발 품질을 직접 측정한 연구는 여전히 없다.
- 연구마다 추정 대상이 다르다(완료자 조건부, TOT, 배정효과, 준실험). 그래서 수치를 평균해 하나의 기대값으로 만들 수 없다.
- 체감과 실측이 어긋난다. S3 참가자들은 실제로 느려졌는데도 20% 빨라졌다고 믿었다.
- 최신 도구에 일반화할 근거가 없다.

주니어 2명과 신규 업무 10%에는 S1·S2의 방향성 근거를 일부 적용할 수 있다. 하지만 비중이 작아 회사 전체 수치를 바꾸지 못한다.

## 3. 권고 [제안]

- 도구는 실험용 라이선스로만 도입하고, 계획 수치는 0%로 둔다.
- 감속 가능성이 있으므로, 유지보수 일정은 AI 도입을 전제로 당기지 않는다.
- 20%(또는 그 이하 수치)는 아래 채택 규칙을 통과한 경우에만 계획에 반영한다.

## 4. 수정된 6주 실험안 [모든 수치는 제안값]

| 항목 | 기존안 대비 수정 |
|---|---|
| 배정 | 티켓 단위로 AI 허용/불허를 1:1 배정한다. 블록은 개발자 × 규모 구간으로 나눈다. **주분석은 시니어 18명의 유지보수 티켓으로 한정**한다. 주니어 2명과 신규 기능 티켓은 기술 통계로만 보고한다 |
| 대상 티켓 | 예상 2~16 인력시간 규모로 한다. 착수 전에 담당자와 리뷰어가 예상시간과 난이도를 각자 기록한다 |
| 주지표 | 인력시간 = 작성 + 리뷰 + 재작업. 달력시간은 보조지표로만 쓴다. 분석은 배정 기준 ITT로 하고, 실제 사용 여부는 로그로 따로 남긴다 |
| 감속 감시 | **신설.** 3주 중간점검에서 유지보수 층의 인력시간 증가 추정의 구간 전체가 0보다 위에 있으면 해당 개발자군의 AI 허용을 중단한다 |
| 품질 | 리뷰 반려, CI 실패, 머지 후 결함, 리버트·핫픽스, 보안 경고를 본다. 마지막 머지 후 6주를 더 관찰한다. 비열등 한계는 기존안 그대로다(결함 +3%p, 반려 +10%p, CI 상대 +20%, 고위험 보안 결함 0건) |
| 불확실성 | 개발자 무작위효과를 넣은 로그시간 모형을 쓰고, 신뢰구간은 개발자 클러스터 부트스트랩으로 구한다. 18명·6주로는 검정력을 보장할 수 없으므로, 구간이 넓으면 '판단 불가'로 보고한다 |
| 채택 규칙 | 유지보수 층 인력시간 감소의 90% 구간 **하한이 20% 이상**이고 품질 기준을 모두 통과한 경우에만 20%를 반영한다. 하한이 0~20%이면 하한값만 반영한다. 구간이 0을 포함하면 계획 수치를 0%로 두고 도구 지속 여부를 따로 판단한다. 구간 전체가 증가 쪽이면 유지보수 업무에서 도구를 철회한다 |
| 체감 | 체감 단축률은 수집하되 판단 근거로 쓰지 않는다 |

**한계**: 결과는 6주 동안 처리한 이 팀의 티켓 구성에만 해당한다. S3 저자도 배제하지 못한 장기 학습효과는 이 실험으로 측정할 수 없다.
