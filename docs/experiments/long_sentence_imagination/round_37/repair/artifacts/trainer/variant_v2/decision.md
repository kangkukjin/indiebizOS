# 의사결정 메모: 시니어 중심·유지보수 중심 조건에서 "개발시간 20% 절감" 약속 가능 여부

## 1. 결론 (제안)

**20% 절감은 약속할 수 없다.** 직전 판단보다 근거가 더 불리해졌다. 도구는 조건부로 도입하되 일정·인력 계획의 단축치는 0%로 둔다. 단축치는 아래 실험의 최종 규칙을 통과한 대상에만 반영한다.

이번 판단에는 새 원문 조회나 재추출을 하지 않았다. 기존 근거표만으로도 약속 불가 판단의 방향이 정해지기 때문이다. 결정에 필요한 공백이 없다고 보았다. METR의 신뢰구간 수치가 없다는 한계는 그대로 남지만, 보고된 점추정이 감속 방향이므로 결론을 뒤집지 않는다.

## 2. 바뀐 조건과 연구별 적용 비중

조건은 두 가지다. 개발자 20명 중 18명이 시니어이고(인원 기준), 업무의 90%가 익숙한 대규모 기존 저장소의 유지보수다. 이 90%가 건수 기준인지 시간 기준인지는 주어지지 않았으므로 작업시간 비중으로 바꿔 읽지 않는다.

**비중이 커진 연구**
- **METR**: 이제 가장 가까운 근거다. 숙련 개발자 16명이 여러 해 기여한 100만 줄 이상 저장소에서 이슈 246건을 수행했고, AI를 허용한 이슈의 **완료시간이 19% 늘었다**([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)).
  - 개발자들은 사전에 24% 향상을 기대했고, 사후에도 20% 빨라졌다고 믿었다. 자기보고나 체감은 계획 근거가 될 수 없다.
  - 한계는 그대로다. 신뢰구간 수치가 없고, 시간은 자기보고값이며, 학습효과를 배제하지 못했다. 업무에 기능 추가가 포함되어 순수 유지보수와 일치하지도 않는다.

**비중이 줄어든 연구**
- **Peng**: **시간 55.8% 감소**는 신규 단일 과제에서 나왔다([Peng](https://arxiv.org/pdf/2302.06590)). 표본은 Upwork 프리랜서이고, 완료자는 35명(집단별 수 불명)이다. 경험이 적을수록 이득이 크다는 결과도 탐색적이다. 이번 조건에서는 업무의 나머지 10%인 신규 업무에만 제한적으로 유비할 수 있다.
- **Cui**: 효과는 시간이 아니라 **주당 완료 PR +26.08%**로 측정됐다([Cui](https://economics.mit.edu/sites/default/files/inline-files/draft_copilot_experiments.pdf)). Microsoft 자료에서 시니어 효과는 +7~16%로 주니어(+21~40%)보다 작았지만, 집단 간 차이는 비유의였다(p=0.13~0.77). PR 증가율을 시간 절감률로 바꿀 수 없다.
- **Brynjolfsson**: 고객지원 업무다. 최상위 숙련층은 생산성 증가가 없었고 해결률·NPS가 소폭 하락했다([NBER w31161](https://www.nber.org/system/files/working_papers/w31161/w31161.pdf)). 개발 업무에는 방향 참고로만 쓴다.

**그대로인 것**
- Noy와 Dell'Acqua는 여전히 문서·기획 작성 업무에만 유비할 수 있다([Noy](https://economics.mit.edu/sites/default/files/inline-files/Noy_Zhang_1.pdf), [Dell'Acqua](https://mitsloan.mit.edu/sites/default/files/2023-10/SSRN-id4573321.pdf)).
- 프런티어 밖 과제에서 **정답률이 평균 19%p 떨어진** 결과는 맹목적 수용 위험의 근거로 유지한다.
- 코드 품질을 직접 측정한 개발 연구는 여전히 없다.
- 단위·대상·추정량이 다른 값(55.8%, +26.08%, +19%)은 평균하지 않는다.

## 3. 수정된 6주 실험안 (모두 제안값)

**일정**
- 1주차(준비): 보안 설정, 사용 교육, 작업시간 기록 리허설, 적격 기준 확정
- 2~5주차: 실행
- 6주차: 분석·보고
- 지연 관찰: 6주 종료 후 30일간 결함을 추적한다. 최종 품질 판정과 채택 결정은 지연 관찰이 끝난 뒤 내린다.

**설계**
- 무작위화: 각 개발자 안에서 티켓 단위로 AI 허용/불허를 1:1 블록 배정한다. 층은 업무유형 × 사전 규모 구간이다.
- 적격 티켓: 배정 전 작성자가 기록한 예상 작업시간이 3인일 이하인 티켓만 포함한다.
- **1차 추정 대상**: 개발자 20명의 적격 **유지보수** 티켓.
- 신규 업무 티켓과 주니어 2명의 하위집단은 표본이 작으므로 기술 통계로만 보고하고 채택 판정에 쓰지 않는다.
- 분석: 배정대로 분석한다(ITT). 사용불이행은 기록한다.

**측정**
- 1차 지표: 티켓당 작업 인력시간. 작성자와 리뷰어의 실제 작업 구간 합계이며, 휴식·대기는 제외한다.
- 기록 방식: 체감 편향(METR 사례)을 고려해 작업 시작·종료를 그때그때 타이머로 기록한다.
- 보조 지표: 달력시간(착수~머지 타임스탬프 차이), 리뷰 왕복 수.
- 체감 확인: 사전 기대치와 사후 체감치를 함께 수집해 실측과 비교한다.

**분석**
- 모형: log(인력시간) ~ 배정 + log(사전 추정) + 층 고정효과
- 불확실성: 개발자 20명 군집에 대해 wild cluster bootstrap으로 95% CI를 구한다.
- 검정력은 보장되지 않으며, 결과가 판정 불가로 끝날 수 있다.

**품질 비열등 한계**
- 결함·revert 발생 티켓 비율 차이의 95% 상한 ≤ +5%p
- 리뷰 재작업 왕복 비의 상한 ≤ 1.2
- 빌드 성공률 차이의 하한 ≥ −5%p

**중단 경보** (최종 품질 판정과 별개)
다음 중 하나가 발생하면 일시 정지하고 원인을 검토한다.
- AI 배정 티켓이 원인인 고심각도 장애 1건
- 보안 취약점 머지
- AI 쪽 빌드 성공률이 2주 연속 10%p 이상 낮음

**최종 채택 규칙**
1차 추정 대상(적격 유지보수 티켓)에만 적용한다.
- ITT 인력시간 감소의 95% CI 하한이 20% 이상이고, 지연 관찰을 포함한 품질 기준을 충족하면 → 20%를 계획치로 채택한다.
- 하한이 0%와 20% 사이이면 → 하한값을 계획치로 쓴다.
- 하한이 0% 이하이면 → 단축 계획을 세우지 않는다.

신규 업무, 대형 티켓, 장애 대응까지 포함한 팀 전체 20% 목표는 이 실험으로 채택할 수 없다. 전체 목표를 채택하려면 나머지 집단의 효과를 측정하고, 업무량으로 가중한 전체 효과의 CI 하한을 따로 판정해야 한다.

## 4. 남은 불확실성

- 4주 실행 기간으로는 METR이 미확인으로 남긴 장기 학습효과를 관찰할 수 없다.
- 최신 에이전트형 도구로의 일반화 여부와 장기 품질 영향은 확인되지 않았다.
