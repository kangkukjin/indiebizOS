## 4. 발견한 갭

### L37-1 — 입력 검사 결과가 오류 경계에서 사라짐 (구현·진단 결함, 중간)

`table:ai inspect:"batch"`로 큰 논문의 요청 크기를 먼저 확인했지만,
응답에는 '계획된 요청이 입력 상한을 초과합니다'와 `error_type:input_size`만 있었다.
어느 요청이 몇 자 초과했는지·상한·inspection을 받지 못해 범위를 다시 설계해야 했다.

[최소 재현](repro/inspect_oversize.ibl): 60,010자의 합성 입력. 모델 호출0, 검사 실패가 아닌 실행 시 TOOL 오류.
[응답](evidence/repro_results.json)의 diagnostic에 inspection과 limit_chars가 없음을 확인했다.
성공한 작은 입력에서는 inspection.limit_chars=60000 등이 정상 반환됐다.

최초 실패와 재현을 보존한 뒤에만 소스를 열었다. ai-ops/handler.py:531~536은 inspection과 items를 만든 뒤
실패 봉투에 넣지만, backend/ibl/ibl_v2_adapters.py:236 이후 오류 세부값 허용 목록이 inspection을 전달하지 않는다.
일반 입력 상한 경로의 input_chars/input_bytes/limit_chars도 같은 목록에 없다(후자는 소스 진단이며 별도 라이브 재현은 안 함).

개선 방향: 실패의 업무 입력 전체를 되돌리지 않으면서 작은 진단 구조를 보존한다. 소유 위치는 공통 어댑터 오류 계약이다.
확인 조건: 같은 oversize/정상/행별 inspect와 원래 전체 연구 프로그램에서 크기·위치가 보이고 모델 호출0 유지.
L2-8/L3-6과 같은 **계측·진단을 도구에서 실행자까지 보존하는 경계** 문제다. 새 연구 전용 어휘는 필요 없다.

주어진 90%는 업무 비중이지 시간 비중이라는 보장도 없다. 측정 대상과 약속 대상의 불일치를 먼저 해소해야 한다.

AI 변형의 인원 비중×업무 비중=81% 계산은 독립성을 가정했다고 밝혔으므로 숨긴 가정으로 세지 않았지만,
인원 비중을 인력시간 비중으로 옮기는 추가 가정은 설명하지 않았다.

**B. 훈련자 기본 보고의 확인 범위 오기.** 실제 PDF 페이지/추출 단위는 Peng19/20, Cui28/29,

**C. 실험안 완결성.** AI 기본/변형은 최종 판정에 '품질 비열등'을 쓰지만 허용 악화 폭과 통계적 판정 규칙을

집단별/총수 해석이 불명확하여 이번 조사에서 확정 오답으로 세지 않고 재확인 대상으로 남긴다.

개선 방향: 이미 수행하는 완료 검수에서 **주장의 대상·분모·단위·불확실성 ↔ 근거 ↔ 최종 의사결정 규칙**을
대조한다. 제안된 평가 단계마다 새 모델을 붙이거나 보고서 분량을 늘리는 방식은 피한다.
페이지/단위 같은 확정 사실은 구조화 값을 그대로 렌더링하고 의미 판단이 필요한 결론만 모델에 맡긴다.
재검증은 같은 주제의 원래 과제와 새 집단비중 변형에서, 부분 집단 결론을 전체에 무조건 적용하지 않는지 본다(R3).

### L37-3 — 이미 작성한 근거가 평가 입력에서 잘려 재검수 왕복 발생 (관측 전달·비용 공백, 중간)

기본의 첫 평가가 research.md §3.4의 지식노동 전이 설명과 evidence.json 미확인 표시를
'발췌라서 확인할 수 없다'고 판단했다. 두 내용은 최초 저장본에 이미 있었다.
[evaluations.json](evidence/evaluations.json)은 필요한 작성/재독 호출까지 지정해 UNKNOWN을 반환한 것을 보여준다.
이후4도구 호출이 추가됐다: grep2개 연결 프로그램 → 긴 JSON 줄 절단 실패 → IBL 구문 거절 → Bash2회.
파일 내용 변경 없이 최종 설명만 늘고 두 번째 평가가 승인했다.

execution:repair 입력554,695·출력2,268(캐시 읽기524,751 포함), 재평가1회가 들어갔다.
첫 평가 종료부터 두 번째 평가 종료까지 약31.2초. 이 전체가 제거 가능하다고 단정하지는 않는다.
실제 미확인 값을 확인하는 검수는 필요했지만, 저장돼 있는 특정 절/JSON 필드를 처음부터 제공했다면
발췌 부족으로 시작된 재검수 왕복과 잘못된 grep/문법 시도는 피할 수 있었다.

개선 방향: 평가 기준별로 기존 산출물의 경로/구조화 필드/해당 절을 전달하고, 필요할 때 그 참조를 회수한다.
증거가 생략된 것과 미수행을 구별하는 정책은 유지한다. 자료를 더 많이 상시 주입하는 처방은 비용을 키운다.
L36-2(능력 검토의 관련 실행 근거 누락)와 인접하지만, 이번 소유 경로는 **최종 산출물 평가 근거 선택**이다.
기존 근거 패킷만 개선한 재생에서 판정 품질·입력량·재검수 발생을 확인하고 원래 독립 과제로 확인해야 한다.

캐시는 입력의 부분집합이며 더하지 않는다. 금액은 계산하지 않았다. 훈련자 Codex 자신의 작성·검색·검수·회고 토큰은
미측정이므로 위 표를 전체 토큰 절감률로 비교할 수 없다. 훈련자는 연구6건, AI는9건이고 방법·모델 입력 범위도 다르다.
원천 공유 캐시, 훈련자 개입, 독립 AI의 추가3연구 때문에 동일 조건 성능 대조가 아니다.

훈련자 성공 HTTP 시간: 검색5.634, 수집4.044, 추출123.330, 보고83.152, 변형65.971초.
합282.131초는 개별 호출 시간 합이며, 전체 준비/작성/검수/AI 관측과 병렬인 벽시계19분6초와 같지 않다.
초기 준비·탐색부터 첫 추출 검사까지8분54초, 이후 추출 수정·범위 선택·실행3분56초,
보고 조합·수정·실행3분15초, 변형 작성·실행 약2분3초였다. 이 구간에는 독립 실행 관측/검수가 섞여 있다.
순수 작성 시간과 읽기 전용 원인 진단의 모델 시간은 별도 분리 측정하지 못했다.

- **필요했던 비용:** 서로 다른 원문/판본 확인, 방법·단위·품질 비교, 실패/미확인 표시, 저장·재독,
  조건 변경의 적용성 재판단. 원문 수집량만 줄여 깊이를 낮추는 것은 개선으로 세지 않는다.
- **피한 비용:** 양쪽 변형은 재수집·재추출0. 훈련자 report_v0 실패 후 추출6회 재지불0.
  AI의 같은 URL crawl5회는 실제 cache.hit=true였다. 이를 네트워크5회 낭비로 부풀리지 않는다.
- **줄일 일:** 작성자 문법/반환 계약 오용, 결과 일부를 더 읽기 위한 반복 crawl 호출(캐시로 네트워크는 피함),
  L37-1의 불충분한 진단, L37-3의 평가 근거 전달과 재검수 오류. AI가 최소6건 대신9건을 조사한 것은
  품질·대안 조건을 보강했으므로 자동으로 낭비라고 세지 않는다.
- **측정 한계:** crawl_reuse.json은 영수증에 보존된 직접 sense:crawl 호출21건의 관측이다.
  다른 관용구 내부 호출 전체/실제 네트워크 요청 수와 동일하지 않다. 원천 실패5는 API 계측값이며 검사 거절과 다르다.
- **남은 검수:** 모든 도표 픽셀·통계 재분석, AI만 추가한 Google/Cursor/DORA 3건의 전수 독립 사실 대조,
  메모 실제 인쇄 페이지 수, 6주 실험의 실제 검정력은 검증하지 않았다.

## 6. 종료와 다음 수리 범위

모든 접수 task가 succeeded이고 훈련자의 최종 프로그램은 completed다. 실패 실행의 원본도 보존했다.
라이브 코드·설정·패키지 변경, reload, 적용 예약, 새 관용구 등록은 하지 않았다.
산출물 오류를 고쳐 이번 최초 성과를 바꾸지 않았다. 수리 시에는 L37-1 진단 경계,
L37-2 완료 검수의 의미 대조, L37-3 평가 근거 선택을 별도 작업으로 다루면 된다.

개발환경 테스트 전수를 이 훈련의 품질 증명으로 쓰지 않았다. 이번 변경은 훈련 문서·재현·계측 하네스뿐이며,
JSON/하네스 구문·파일 보존·실행 영수증·git 차이를 검사했다. 확인된 개선량은 아직 없다.
