## 1. 범위와 근거 상태

- **시나리오(합성)**: 한 Linux 호스트, 로컬 SSD, 데이터 20GB. 수집 프로세스 1개가 1분마다 작은 배치를 추가하고, 분석가 4명이 별도 Python 프로세스로 동시에 SQL을 실행한다. 원천 데이터는 다시 모을 수 있지만 사람 주석은 잃으면 안 된다.
- **확인한 공식 원문 8건**(수집 텍스트 전문을 전달받음):
  - SQLite: WAL, Backup API, Network
  - DuckDB: Concurrency, EXPORT
  - PostgreSQL 18: MVCC 13.1, SQL Dump 25.1, PITR 25.3
- **읽지 않은 것(미확인)**: 이미지, 실DB, 성능 실험, 검색 요약, 옛 판본 문서, PG 13.2(격리 수준), PG 49장(아카이브 모듈), SQLite 백업 API 상세 문서.
- 아래에서 **[원문]**은 문서 사실이고, **[추론]**과 **[제안]**은 이 팀에 대한 판단이다.

## 2. 비교표 [원문 요약]

| 축 | SQLite (WAL) | DuckDB (native embedded) | PostgreSQL 18 서버 |
|---|---|---|---|
| 동시 읽기/쓰기 프로세스 경계 | 같은 호스트의 여러 프로세스가 읽기·쓰기를 서로 막지 않음. 쓰기는 한 번에 하나 ([wal](https://www.sqlite.org/wal.html)) | 읽기쓰기 모드는 **한 프로세스만** 가능. READ_ONLY 다중 프로세스는 쓰기 프로세스와 혼용 불가 ([concurrency](https://duckdb.org/docs/stable/connect/concurrency)) | MVCC로 읽기·쓰기가 서로 막지 않음. SSI에서도 유지 ([mvcc](https://www.postgresql.org/docs/current/mvcc-intro.html)) |
| 분석 적합성 | 읽기 위주 앱은 약 1~2% 느릴 수 있다는 서술뿐. 수치 근거 없음 | RAM 캐시로 분석 쿼리를 빠르게 하려는 설계라고 설명. 수치 없음 | 다중 사용자에서 "합리적 성능" 목표. 수치 없음 |
| 일관된 백업 | Backup API: 완료 시 일관된 스냅샷이라 서술하나 기준 시점 서술이 모호함. 쓰기가 잦으면 재시작이 반복돼 끝나지 않을 수 있음 ([backup](https://www.sqlite.org/backup.html)) | EXPORT DATABASE: 스냅샷 시점·일관성 **미기재**. 가져오기는 빈 DB에만 가능 ([export](https://duckdb.org/docs/stable/sql/statements/export)) | pg_dump: 실행 시작 시점의 내부 일관 스냅샷이며 다른 작업을 막지 않음 ([dump](https://www.postgresql.org/docs/current/backup-dump.html)). WAL 아카이브로 PITR 가능 ([pitr](https://www.postgresql.org/docs/current/continuous-archiving.html)) |
| 운영 복잡성 | 서버 없음. 다만 -wal 파일을 함께 다뤄야 하고, 네트워크 FS는 불가 | 서버 없음. 다중 프로세스 쓰기에는 별도 경로 필요 | 별도 서버, 역할·권한, 아카이브 명령, 설정 파일 백업이 필요 |

**DuckDB의 별도 경로 [원문]**: native와는 구분해야 한다.
- Quack 원격 프로토콜은 v1.5.2 기준 **베타**다. v2.0(2026년 가을)에서 성숙할 "예정"이라고만 적혀 있어, 기준일 현재 출시 여부는 **미확인**이다.
- DuckLake는 PostgreSQL을 카탈로그로 쓰는 **다른 저장 형식**이다. v1.0 사양과 구현이 2026년 4월 프로덕션용으로 공개되었다.

## 3. 판본·불일치 설명 [원문+추론]

- **DuckDB**: 상단은 "1.5 current", 본문은 v1.5.2를 언급한다. 요청 URL은 stable이지만 resolved_url은 current다. 사이트 판본 표기와 본문 패치 버전이 다른 것으로 보이며[추론], 정확한 판본은 단정하지 않는다.
- **PostgreSQL**: 18이 현재 판이다. 19는 Beta 4 개발판이므로 근거에서 제외했다. 2026-09-24는 19 Beta 공지 날짜이며 18 판본 날짜가 아니다.
- **SQLite**: 갱신 표기가 WAL 2026-08-25, Backup 2025-11-13, Network 2022-06-22로 서로 다르고, 버전 표기는 없다.
  - WAL-reset 버그 발생률은 텔레메트리 추정치다.
  - 2026-08-24 재현자 보고는 링크만 있어 세부는 미확인이다.
- **검색 요약·옛 문서**: 읽지 않았으므로 현 문서와 대조할 수 없다(미확인).

## 4. 권고 구조 [제안]

**기본안: 같은 호스트에 PostgreSQL 18 서버를 두고 주석과 수집 데이터를 저장한다.**
- [추론] 수집 1 + 분석 4 = 5개 프로세스가 동시에 읽고 쓰는 구조다.
  - DuckDB native는 단일 쓰기 프로세스 제약에 바로 걸린다.
  - SQLite WAL은 가능하지만 주석 보호에 필요한 조건(버전, 동기화 수준, 장기 읽기 관리)이 많다.
- 백업은 두 겹으로 둔다.
  - pg_dump(custom 형식 -Fc)를 정기 실행하고, 별도로 `--globals-only`로 역할 정의를 받는다.
  - 주석 손실 범위를 줄이려면 WAL 연속 아카이빙과 `archive_timeout`을 추가한다.
  - 원문에는 RPO 수치 보장이 없으므로, 손실 시간은 측정한 뒤 정한다.
- postgresql.conf, pg_hba.conf, pg_ident.conf는 WAL로 복원되지 않으므로 파일로 따로 백업한다.

**대안 A: SQLite WAL 단일 파일.** 도입 조건 [제안]:
- 버전이 3.51.3 이상이거나 백포트판(3.44.6, 3.50.7)일 것. 2개 이상의 연결이 동시에 쓰기·체크포인트할 때 발생하는 WAL-reset 손상 버그 때문이다.
- `synchronous=FULL`. NORMAL이면 정전 후 커밋이 롤백될 수 있다.
- 분석 쿼리의 읽기 트랜잭션을 짧게 유지할 것.
- 로컬 SSD에만 두고, 백업은 Backup API로 하며 -wal 파일과 분리하지 않을 것.
- Backup API의 WAL 모드 동작은 문서에 미기재이므로 실측이 필요하다.

**대안 B: DuckDB.** 도입 조건 [제안]:
- 쓰기를 한 프로세스(수집기)로 모으고, 분석가는 그 프로세스를 거치게 한다.
- 또는 분석 시간대에 수집을 멈추고 READ_ONLY로만 연다.
- Quack은 베타이고 성숙 여부가 미확인이므로 주석 저장소로는 보류한다.
- DuckLake는 결국 PostgreSQL이 필요하므로 기본안과 비교해 다시 평가한다.

## 5. 실패 시나리오 [원문 근거 → 추론]

1. **SQLite: 분석가의 장기 읽기 트랜잭션.** 체크포인트가 막혀 WAL이 무한히 커질 수 있다. RESTART/TRUNCATE로 강제하면 리더가 막힐 수 있다.
2. **SQLite: DB 파일만 복사하거나 이동.** -wal 파일이 분리되면 커밋이 유실되거나 손상될 수 있다.
3. **SQLite: 수집 쓰기 중 증분 백업.** 다른 연결의 쓰기 때문에 백업이 재시작되고, 쓰기가 잦으면 끝나지 않을 수 있다. `step(-1)`은 복사하는 동안 쓰기를 막는다. 1분 주기 쓰기에서 어느 쪽이 될지는 미측정이다.
4. **DuckDB: 두 번째 쓰기 프로세스.** 파일 잠금으로 실패한다. 같은 프로세스 안에서도 같은 행을 동시에 갱신하면 "Transaction conflict"가 나고, 재실행은 애플리케이션 책임이다.
5. **DuckDB: 기존 DB 위로 IMPORT.** "already exists" 오류가 나므로 병합 복구는 불가능하다.
6. **PostgreSQL: archive_command 연속 실패.** pg_wal이 차고 PANIC으로 오프라인이 된다(커밋은 보존). `cp -i`는 대상 파일이 있어도 0을 반환하므로 덮어쓰기 거부 용도로 부적합하다.
7. **PostgreSQL: psql 기본 복원.** 오류가 나도 계속 진행해 부분 복원 DB가 된다. `-1`을 쓰면 사소한 오류 하나로 전체가 롤백된다.
8. **PostgreSQL: pg_dump만 사용.** 역할과 테이블스페이스가 빠진다. 소유자가 없으면 권한이 복원되지 않는다.

## 6. 백업·복구 검증 절차 [제안]

1. **복원 대상 분리**: 운영 DB가 아닌 빈 DB에 복원한다.
   - PG는 template0에서 생성한 뒤 `pg_restore`를 쓴다.
   - DuckDB는 빈 DB에 IMPORT한다.
   - SQLite는 Backup API로 만든 사본을 연다.
2. **주석 데이터 대조**: 주석 테이블의 행 수와 키 집합 해시를 운영본의 같은 시점 값과 비교한다.
   - pg_dump의 비교 기준은 "실행 시작 시점"이다.
   - SQLite와 DuckDB는 스냅샷 시점이 원문에 모호하거나 미기재이므로, 백업 직전·직후 값을 모두 기록해 범위로 판정한다.
3. **PITR 리허설**: 베이스 백업 종료 이후의 시점을 목표로 복구한다. 새 타임라인 생성을 확인하고 설정 파일을 수동으로 복원한다.
4. **복원 후 처리**: ANALYZE를 실행한 뒤 분석가 대표 쿼리 결과를 운영본과 비교한다.
5. **경보와 판정 구분**:
   - archive 실패와 pg_wal 증가는 즉시 대응하는 **중단 경보**다.
   - 복원본의 주석 일치 여부는 리허설마다 내리는 **최종 품질 판정**이다.

## 7. 아직 측정해야 할 항목 [제안값, 원문 수치 아님]

| 측정량 | 관찰 기간 | 허용 한계(제안값) | 판정 규칙 |
|---|---|---|---|
| 주석 행 복원 일치율 | 주 1회 리허설 × 4주 | 불일치 0건 | 1건이라도 불일치하면 그 백업 방식을 채택하지 않음 |
| 복원 소요 시간(달력시간, 착수~완료) | 같은 리허설 | 팀이 정한 업무 허용 시간 이내 | 4회 모두 이내일 때만 채택 |
| 실제 손실 구간(마지막 아카이브~장애 주입 시점) | 같은 리허설 | `archive_timeout` 설정값 이내 | 초과가 한 번이라도 나오면 설정을 재조정하고 재측정 |
| SQLite WAL 파일 크기 / 백업 재시작 횟수 | 분석 피크 포함 2주 | 증가가 멈추고 백업이 매회 완료 | 미완료가 한 번이라도 나오면 대안 A 탈락 |
| 대표 분석 쿼리 지연(20GB, 4명 동시) | 2주 | 팀이 기준선을 정한 뒤 설정 | 제품 간 같은 쿼리 집합으로만 비교 |

판정 대상은 **주석 데이터**에 한정한다. 재수집 가능한 원천 데이터까지 포함한 전체 목표는 이 측정만으로 채택하지 않는다.

## 8. 남은 불확실성

- SQLite Backup API의 스냅샷 기준 시점과 WAL 모드에서의 동작
- DuckDB EXPORT의 일관성, 그리고 Quack이 기준일 현재 성숙했는지 여부
- PG 격리 수준별 스냅샷 시점과 쓰기-쓰기 충돌(13.2를 읽지 않음)
- 세 제품 모두 RPO/RTO와 성능 수치가 원문에 없다(미확인).
