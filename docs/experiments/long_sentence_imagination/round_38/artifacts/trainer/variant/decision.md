# 결정 메모: 다중 호스트에서 NAS/NFS 공유 DB 파일을 직접 여는 제안 검토

## 1. 결론 (제안)

- **제안안(각 컴퓨터가 NAS/NFS의 DB 파일 하나를 직접 열기)은 채택하지 않을 것을 제안한다.** 수집 프로세스의 지속 쓰기와 여러 호스트 분석가의 동시 읽기가 함께 필요한데, 입력 근거 안에서는 파일시스템 공유 방식으로 이 요구를 충족하는 경로가 확인되지 않는다.
- **우선 대안은 DB 서버 접속(PostgreSQL 클라이언트/서버)으로 제안한다.** 차선은 DB 파일이 있는 한 호스트에서만 읽고 쓰고, 원격 요청을 프록시로 중계하는 구성이다.
- **"서버 운영을 없앤다"는 목표는 달성할 수 없다.** 근거에 있는 모든 대안이 별도 서버나 직접 구현하는 상주 프로세스를 요구한다.

## 2. 구분 기준: 접근 경로 × 호스트 수

| 구분 | 단일 호스트 | 다중 호스트 |
|---|---|---|
| **파일시스템 공유**(DB 파일 I/O가 로컬 또는 네트워크 FS를 거침) | SQLite WAL: 읽기와 쓰기가 서로 막지 않음. 쓰기는 한 번에 하나만 가능 | 네트워크 FS에서는 SQLite WAL이 동작하지 않음. 쓰기 순서 뒤바뀜·유실, 잠금 오동작으로 손상 사례가 있음 |
| **DB 서버 접속**(네트워크가 API 호출 채널에 있음) | 해당 없음(서버를 둘 필요가 적음) | 네트워크 장애 시 트랜잭션이 실패·롤백될 뿐 무결성은 유지됨(트랜잭션을 올바르게 쓴 클라이언트 전제) |

핵심은 네트워크가 **파일 I/O 채널**에 있는지, **API 채널**에 있는지다. 파일 I/O 채널에 네트워크가 끼면 DB가 손상될 수 있다(sqlite_network).

## 3. 제안안 검토: 제품별 판정

**SQLite + WAL 모드**
- WAL은 모든 프로세스가 한 호스트에서 공유 메모리(wal-index)를 써야 하며, 네트워크 파일시스템에서는 동작하지 않는다. → **불가**

**SQLite + 롤백 모드(네트워크 FS)**
- 다중 동시 리더 또는 단일 라이터는 가능하지만, 리더와 라이터의 동시 접근은 불가능하다. 수집 프로세스의 지속 쓰기와 분석가의 동시 읽기라는 요구와 정면으로 충돌한다.
- 문서는 네트워크 불안정 완화 효과를 "완전히 또는 허용 가능한 수준"이라고만 적었다. 네트워크 환경은 테스트되지 않았고 사용자 책임이라고 명시한다. 초기 테스트 성공을 신뢰 근거로 삼으면 안 된다는 경고도 있다. → **불가**

**DuckDB native 파일**
- 읽기쓰기 모드는 한 프로세스만 가능하다. READ_ONLY 모드는 여러 프로세스가 읽을 수 있지만 쓰기 프로세스와 함께 쓰는 것은 지원되지 않는다.
- 동시 접근은 파일 잠금으로 처리되며, NAS·공유 디렉터리에서는 특별한 주의가 필요하다고만 적혀 있다. 잠금 신뢰성 보장은 미기재다. → **불가**

## 4. 대안 비교 (제안)

| 대안 | 접근 경로 | 동시 읽기·쓰기 | 서버 운영 | 제약·불확실성 |
|---|---|---|---|---|
| A. PostgreSQL | DB 서버 접속 | MVCC로 읽기와 쓰기가 서로 막지 않음(SSI에서도 유지) | 필요(별도 서버 프로세스) | 성능·사용자 수 수치 보장 없음. 쓰기-쓰기 충돌, SSI 재시도 조건은 미확인 |
| B. SQLite WAL + 단일 호스트 프록시 | 원격은 프록시 API, DB I/O는 로컬 | 같은 호스트 안에서 WAL 성립 | 프록시를 직접 구현·운영해야 함(SQLite 기능 아님) | 쓰기 1개씩만 가능. 오래 열린 읽기가 체크포인트를 막아 WAL이 커질 수 있음. 동시 쓰기·체크포인트 시 WAL-reset 버그(3.51.3 수정, 백포트 3.44.6·3.50.7) |
| C. DuckDB Quack | 클라이언트-서버 | 다중 프로세스 native 쓰기 | 필요 | v1.5.2 기준 베타. v2.0 성숙은 예정일 뿐 출시 여부 미확인 |
| D. DuckLake + PostgreSQL 카탈로그 | 별도 형식 + 외부 PG | 다중 프로세스용 안정 대안으로 권장됨 | PG 필요 | native 파일 형식 아님. v1.0은 2026년 4월 공개 |

A를 우선하는 이유는 세 가지다. 다중 호스트 동시 읽기·쓰기를 문서 차원에서 직접 다루고, 서버를 어차피 피할 수 없으며(B·C·D도 상주 프로세스 필요), SQLite 문서도 원격 시나리오에서는 보통 클라이언트/서버 방식이 낫다고 권한다. 근거에는 사용자 수·데이터 규모별 성능 수치가 없으므로 용량 적합성은 판단하지 않았다.

## 5. 이전 단일 호스트 전제에서 바뀐 부분

이전 결정문 원문은 이 입력에 없다. 따라서 아래 비교의 기준은 "근거상 단일 호스트에서 성립하던 판단"이다.

| 항목 | 단일 호스트 전제 | 다중 호스트(현재) |
|---|---|---|
| SQLite WAL | 읽기·쓰기 동시 진행 성립 | 네트워크 FS에서 동작 안 함 → 직접 공유 불가. DB 호스트 한 곳에 고정하는 B로만 유지 |
| DuckDB 단일 프로세스 + MVCC 스레드 | 한 프로세스 안의 여러 쓰기 스레드 가능 | 호스트 간 공유 불가. 서버형(C)이나 PG 의존(D) 필요 |
| 서버 불필요성 | 임베디드로 충분할 수 있었음 | 근거상 서버(또는 자작 프록시)가 필수 |
| 백업 실행 위치 | 같은 호스트에서 복사·백업 API | PostgreSQL은 pg_dump를 원격 호스트에서 일반 클라이언트로 실행 가능 |

## 6. 백업 측면의 함의

- **PostgreSQL**
  - pg_dump는 실행 시작 시점의 스냅샷이며, 대부분의 작업을 막지 않는다. 다만 배타 잠금이 필요한 ALTER TABLE 등은 막힐 수 있다.
  - 역할·테이블스페이스는 덤프되지 않는다. pg_dumpall은 DB 간 스냅샷이 동기화되지 않는다.
  - 연속 아카이빙(PITR)은 클러스터 전체 단위로만 복원된다. 설정 파일은 별도로 백업해야 한다.
- **SQLite(B안)**
  - WAL 파일은 DB 영속 상태의 일부이므로 함께 다뤄야 한다.
  - 백업 API의 스냅샷 시점은 "복사 시작"과 "완료 시 최신" 서술이 공존해 단정할 수 없다. 쓰기가 잦으면 백업이 끝나지 않을 수 있다.
- **RPO/RTO 수치는 모든 문서에서 미기재다.**

## 7. 미확인 사항과 추가 조사 판단

- **추가 조사는 하지 않았다.** 결정의 핵심인 "네트워크 FS에서 WAL 불가"와 "롤백 모드에서 리더·라이터 동시 접근 불가"가 근거에 직접 있다. 결론이 미확인 항목에 의존하지 않으므로 빈 근거를 메울 필요가 없다고 판단했다.
- 미확인 항목:
  - 네트워크 FS별 안전 여부 목록(문서에 없음)
  - DuckDB 파일 잠금의 NAS 신뢰성
  - PostgreSQL 쓰기-쓰기 충돌과 SSI 재시도 조건
  - 팀 규모·데이터량에 따른 성능
- 이 항목들은 대안 A의 **운영 설계 단계**에서 필요해질 수 있다. 그 경우 PostgreSQL 13.2(격리 수준) 문서부터 조사할 것을 제안한다.
