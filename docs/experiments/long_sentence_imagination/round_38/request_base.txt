가상의 5명 콘텐츠 연구팀을 위한 데이터 저장·분석 구조를 심층 조사하고 한국어 분석 보고서를 작성해줘. 기준일은 2026-10-08이고 공개 공식 문서만 핵심 근거로 사용해. 현재 한 Linux 컴퓨터의 로컬 SSD에 20GB 데이터가 있고 Python 수집 프로세스 하나가 1분마다 작은 배치로 추가하며, 분석가 4명은 각자 별도 Python 프로세스로 SQL 분석을 동시에 실행해. 원천은 다시 모을 수 있지만 사람의 주석 데이터는 잃으면 안 돼. 실제 DB나 성능 측정 자료는 없는 합성 시나리오야.
SQLite(WAL), DuckDB(native 파일 기반 embedded 사용), PostgreSQL 서버를 동시 읽기/쓰기의 프로세스 경계, 분석 적합성, 일관된 백업·복구, 운영 복잡성으로 비교해. 공식 원문 최소6개를 직접 확인하고 세 제품의 동시성 및 백업 근거를 모두 포함해. 최신 문서에서 별도 서버 프로토콜/확장/다른 저장 형식을 제안하면 native embedded와 구분하고 성숙도·판본을 확인해. 검색 요약·옛 문서·현 문서가 다르면 이유를 설명하고 읽지 못한 근거는 미확인으로 남겨. 원문에 없는 성능 수치나 손실시간 보장은 만들지 마.
권고 구조와 대안·도입 조건, 실패 시나리오, 백업과 복구 검증 절차, 아직 측정해야 할 항목을 구체적으로 써줘. 원문 사실과 이 팀에 대한 추론·제안을 분리하고 핵심 주장에 가까운 URL을 붙여. research.md, evidence.json(제품/원문 URL/확인한 범위/주장/제약/불확실성), source_notes.md(확인·실패·판본)를 자기 출력 폴더에 저장하고 재독해. 실제 시스템 설정 변경·DB 생성·외부 발송·공개는 하지 마. 다른 실행자의 trainer/harness/drafts·정답은 보지 말고 자신의 결과와 참조만 재사용해.
