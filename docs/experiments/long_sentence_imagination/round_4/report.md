## 4. 발견 (갭 4건, 수리 안 함)

### L4-1 실제 입력 값에서 추론한 `Null` 타입이 null 가드 뒤 가지를 거절 — 같은 프로그램이 입력에 따라 검사·실행 거절 ★
- **분류**: 구현 결함(정적 타입) — 견고성.
- **재현**: `repro/null_instance_type.ibl` `return $x >> each { return $it.이유 == null ? "사유 없음" : text($it.이유) }` —
  inputs `x=[{이유:null},{이유:"404"}]` 는 valid, `x=[{이유:null},{이유:null}]` 는 **check·실행 모두 `TYPE` "Bool|Number|Text가 필요하지만 Null"**.
  `[if:…==null]{return}` 조기 반환 형태(`null_instance_type2.ibl`)도 같다.
- **영향**: 실패가 없을 때 전부 null 인 "이유" 칸처럼, 정상 입력일수록 선택 필드가 한 가지 값으로 굳는다. `$ref` 로 앞 단계 결과를 넘기는 파이프라인에서
  "실패 원천이 있는 입력(변형 A)에는 통과, 없는 입력(원래)에는 거절" — 견고성 시험을 거꾸로 만든다. 1회차 L1-1(null 좁힘) 수리의 인접 경로: 좁힘은 있으나
  **확정 Null 의 죽은 가지**를 검사한다. 우회 `json()`(의미가 바뀜 — 따옴표가 붙은 문자열).

### L4-2 식 자리 파이프 하나가 PURE_EXPRESSION 3건으로 보고되고, 처방이 순수 대안을 알려 주지 않는다
- **분류**: 작성·발견 마찰 + 과도한 비용.
- **재현**: `repro/pure_expr_triple.ibl` `unique($행 >> [table:each]{…})` → 같은 줄 3건(열 17·23·38 — 파이프·원천·each 노드). p3_v0 는 실수 7곳 → 22건·응답 36.5KB.
- **반복 근거**: 같은 실수가 2회차 v1(10건)·3회차 v2(10건)·v8·4회차 p3_v0 에서 반복. 교재는 "먼저 변수에 받는다"와 `reduce` 목록 변환을 따로 설명하지만,
  오류 hint 는 "호출 결과를 먼저 $이름=[...]으로"만 말한다. 한 번에 하나로 접고 순수 대안(`reduce`)이나 옮겨 적을 변수 문장을 제시하면 된다.

### L4-3 순수 지역 함수 호출도 람다 안에서 "도구 호출"로 거절
- **분류**: 작성·발견 마찰(문구) — 규칙 자체는 교재대로.
- **재현**: `repro/pure_fn_in_lambda.ibl` — `[def:큰가]` 의 컴파일러 계약은 `effects:["pure"]`, 그러나 `where:($r)=>[fn:큰가]{…}` 는
  `PURE_EXPRESSION` "도구 호출은 앞 문장에 두세요". 도구가 아닌데 도구라고 하고, 실제로 통하는 형태(술어 람다를 돌려주는 함수, 람다 변수)를 알려 주지 않는다.

### L4-4 `sense:search` 배치의 `query` 태그가 관측 반환에 없어 거짓 `UNOBSERVED_FIELD` 경고(경미)
- **재현**: `repro/search_query_tag.ibl`. describe 설명은 "queries — 행마다 query 태그"라 하고 실제 행에도 있으나(`probe_search`),
  `observed_returns` 가 `title·meta·summary·url` 뿐이라 매 check 마다 경고.

**갭 아닌 관측**
- 검색 결과가 실행마다 크게 달랐다(1회: docs.python.org 0건, 2회: 3.13·3.14 직접, 변형 A: 3.14 는 릴리스 페이지 경유) — 외부 원천. 프로그램의 두 단계 탐색으로 흡수.
- HTTP 응답 `value` 가 `_preview` 로 표시 절단(문단 31/46)되지만 `read_args` 가 있고 `$ref` 는 전체 — 교재대로.
- 변형 A P1 은 링크 목록을 버전마다 람다로 거르며 **61,830 계산 단계**(한도 10만의 62%) — 버전을 2개 더 넣으면 BUDGET 가능. 링크를 한 번만 거르도록 짤 수 있었다(훈련자). 다음 회차 관찰 후보.
- P3 는 모델 0인데 실행마다 저장본 33~36만 자(증거 DAG) — 결과 값 ~2.6KB 대비 큼. 3회차에 이어 추가 확인 후보.
- `preserve_rows` 실패가 이번엔 없어 3회차 수리의 `model_output_ref` 는 **미검증**.

## 5. 개선 방향

1. **L4-1**: 정적 검사에서 "값 인스턴스에서 추론한 타입"과 "선언·계약 타입"을 구분 — 입력 값 추론은 null 을 `Nullable<Unknown>` 으로 넓히거나, 좁힘으로
   죽은 가지는 경고로 내린다. 검증 = 두 재현 + `p3_v1.ibl` 이 원래(전부 null)·변형 A(문자열 섞임) 입력 모두 통과.
2. **L4-2·L4-3**: PURE_EXPRESSION 을 원천 식 하나로 접고, 호출 종류(도구/순수 함수/파이프)에 맞는 처방 — 파이프면 변수 문장 또는 `reduce`, 순수 함수면
   "술어 람다 반환". 검증 = 재현 2개의 오류 건수·문구, p3_v0 응답 크기.
3. **L4-4**: `queries` 변형의 반환 계약에 `query` 를 선언(관측 픽스처 갱신). 검증 = `search_query_tag.ibl` 경고 0.

## 8. 후속 수리 (2026-09-30)

요청: “최신 긴문장 상상훈련 보고서를 보고 근원적 문제를 생각하면서 수리를 해줘”.

공통 원인은 **분석에서 얻은 사실의 적용 범위를 잃는 것**이었다. 입력에서 추론한 Null을
가드의 반대 가지에 되살렸고, 한 순수 식 위반을 자식 노드별 독립 오류로 세었으며,
단일 검색에서 관측한 반환 모양을 배치 검색에 빌려주었다. 업무별 조건이나 새 어휘를
추가하지 않고, 타입 좁힘·진단 원인·관측 좌표를 각 소유 지점에서 보존한다.

- **L4-1 수리**: 불가능한 좁힘을 내부 bottom 타입 `Never`로 보존한다. Unknown으로 넓히거나
  원래 Null로 되돌리지 않는다. 필드 접근·타입 호환·산술 관측·합류가 이 사실을 유지한다.
  런타임 값이나 새 선언 문법이 아니다. 소스 검사는 계속하므로 가드 없는 `text(null)`,
  도달 가능한 잘못된 변환, 다른 미정의 이름·잘못된 내장 함수는 여전히 오류다.
- **L4-2·L4-3 수리**: 순수 식 안에서 처음 발견한 불가능한 호출·조합을 한 진단으로 내고
  그 아래 중복 순수 식 진단을 접는다. 별개 식의 오류는 보존한다. 파이프에는 앞 문장으로
  옮기는 법과 `reduce` 대안을, `[fn:이름]`에는 each 본문 호출 또는 람다 반환 술어를 안내한다.
  순수 효과와 순수 식 문법은 다른 계약이므로 문법 허용 범위는 바꾸지 않았다.
- **L4-4 수리**: 검색 사전에 `queries`를 반환 모양의 좌표로 명시한다. 실행 시 결정되는
  인자도 ‘없음’으로 버리지 않고 공통 관측 해석기에 전달한다. 따라서 기본 원천·단일 검색
  관측을 다른 모양에 적용하지 않는다. 같은 좌표의 오타 경고는 유지한다. 배치 관측이 없으면
  미상으로 두며, 단일 관측에 query가 언제나 있다고 꾸미지 않는다.
