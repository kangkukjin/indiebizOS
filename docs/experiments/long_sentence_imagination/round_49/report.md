## 2. 발견

### ★★ L49-1 — 이름으로 부르면 관용구가 맥12 를 못 찾는다
`[fn:외부PC준비]{PC:"맥12"}` → `target_not_unique`. 원장에 폐기된 옛 휴대형 키(별칭 `맥12`, revoked)가 남아 있어 별칭 일치가 2건이다. 같은 이름을 직접 어휘 `[limbs:guestpc]{limb:"맥12"}` 에 주면 통과한다 — **관용구와 핸들러의 이름 해석이 다르다.** 이름을 받는 관용구(준비·파일보내기·파일가져오기·깨워준비·재생)가 전부 해당하고, 지금 연결된 유일한 원격 PC 가 그 대상이다.
- 우회: `self:limb list` 에서 `revoked==false and expired==false` 로 걸러 `device_id` 를 넘긴다(훈련자 프로그램).
- 처방 후보: 관용구의 대상 고르기에 "살아 있는 등록" 조건(관용구 정의 수정, 새 낱말 0).

### ★★ L49-2 — 큰 파일 보내기가 조각 하나의 45초 제한으로 통째 실패하고, 다시 이어지지 않는다
6.8MB 묶음: 21:46 11초 성공 → **21:50~22:05 8회 연속 실패**(훈련자 4 + 탐침 4, 각 47~137초, `context deadline exceeded … while reading body`) → 22:08 15.7초 성공.
- 헬퍼는 512KB 조각을 하나씩 받고(`resident_transfer.go`), HTTP 제한이 45초(`residentHTTP`), 조각 실패 시 재시도 없이 전송 전체가 `failed`.
- 원격에 남은 `.part` 는 0 / 524,288 / 2,621,440 바이트에서 멈춰 있었다. 같은 `transfer_id` 로 이어 보내기 4회 → **0바이트 진전**.
- 같은 시각 측정: 맥12 → 외부 1MB 는 1.0초, 맥12 → 허브의 6.9MB GET 은 첫 회 50초에 5.3MB 에서 끊기고 다음 두 회는 7초. 맥12 무선은 RSSI −70dBm·전송률 7Mbps·게이트웨이 핑 손실 0~10%. **간헐적으로 멎는 구간이 있다는 것까지가 관측이고 멎는 원인은 확정하지 못했다.**
- 부수 관측: 실패한 전송의 `.part` 가 원격 폴더에 남는다(이름이 transfer_id 별이라 새 시도는 0부터). 중앙 `resident_transfers` 는 실패한 보내기도 `committed` 로 적혀 있다(중앙 쪽 적재 상태라는 뜻이지만 읽는 사람에겐 완료로 보인다).
- 처방 후보: 조각 단위 재시도(같은 offset), 조각 크기 축소 또는 진행이 있으면 제한 연장.

### ★★ L49-3 — "다시 시키지 마"와 "실패하면 다시 해"가 같은 요청ID 에서 부딪힌다
과제 조건(같은 부탁을 두 번 받아도 원격에서 두 번 돌지 않게)을 지키려고 요청ID 를 일감에서 계산했다. 그러면 **한 번 실패한 전송은 그 ID 로 영원히 실패를 돌려준다** — 재부탁이 곧 같은 실패다. 훈련자는 ID 에 시도 번호를 붙여(`…-send-zip-try2`) 풀었는데, 세 번 다 실패한 뒤의 재실행은 그 세 실패를 그대로 밟고 멈췄고(v2), 상한을 8로 올려야 네 번째에서 지나갔다(v3). 가이드의 "실패는 자동 재실행하지 않는다, 새 의도엔 새 ID" 는 사람이 끼는 흐름에는 맞지만, 프로그램이 혼자 재시도하면서 중복도 막아야 할 때의 길(끝난 실패에 대한 재시도 표기)이 계약에 없다.

### ★ L49-4 — 동기 호출을 같은 요청ID 로 다시 부르면 거짓 시간 초과
2.1초에 성공한 동기 `shell` 을 같은 인자·같은 ID 로 한 번 더 부르면 **14ms 만에** "응답을 100초 안에 못 받았습니다 … `op:"result"` 로 확인하세요"(상태 running)로 실패한다. 실제 작업은 `succeeded` 였다. 안내하는 `op:"result"` 는 휴대형 전용이다. 같은 호출에 `background:true` 만 붙이면 `request_id_conflict`. `background:true` 끼리의 중복은 같은 접수증을 정상 반환한다. → 가이드의 "응답 유실 시 같은 인자·같은 ID 재사용" 은 배경 접수에서만 성립한다.

### ★ L49-5 — 맥에서 `zip` 으로 묶은 결과는 중앙에서 한글 이름이 깨진다
맥12 의 `zip` 은 한글 이름에 UTF-8 표시를 하지 않는다. 중앙 `[self:script]{id:"압축"}` 의 list 는 그 이름을 `δ░öδï╖Ω░Ç ∞òä∞╣¿ (6).jpg` 처럼 돌려준다(unpack 도 같은 이름으로 풀 것). v0 은 장수·지문만 봐서 "완료" 로 판정했다. 우회 = 원격에서 `python3 -m zipfile -c`(v1, 이름 47/47·131/131 일치). 처방 후보: 표시가 없어도 UTF-8 로 읽히는 이름은 UTF-8 로 해석.

### ★ L49-6 — 작업 기록은 출력 한 줄이 사건 하나, 한 쪽 100건
`history(job)` 은 한 번에 사건 100건이고 종료 사건(`result`)은 맨 끝이다. 출력이 100줄을 넘는 작업은 첫 쪽에 종료 시각이 없다 — 변형 B 의 변환(131줄)·검사에서 소요가 "시각 없음" 으로 나갔고 판정은 "완료" 였다. `tasks` 행에는 `created` 만 있고 시작·종료 칸이 없어 쪽을 끝까지 넘겨야 한다. 같은 이유로 `self:task wait`·`외부PC작업확인` 의 `progress` 가 줄 수만큼 커진다(변형 B 25.6만 단계의 주된 몫, AI 가 볼 때는 토큰).
- 처방 후보: tasks 행(또는 접수증 관측)에 started·ended·seconds, progress 는 꼬리만.

### L49-7 — 큰 원격 파일 `read` 의 안내가 길을 가리키지 않는다
400KB 파일 `read` → "원천 결과가 불완전합니다 … 범위 인자(offset·limit)로 나눠 읽으세요". 원격 read 에는 그 인자가 없고, 실제 길은 `transfer` 다.

### L49-8 — 환경 조회의 도구 목록
`info.package_managers` = `["apt"]`(맥의 옛 Java 도구, 오탐). `info.tools` 는 git·python3·python·curl 뿐이라 이 과제의 도구(sips·unzip·shasum)는 셸로 따로 확인해야 했다(가이드도 `ready` 가 도구를 보장하지 않는다고 적고 있다).

### 관측(번호 없음)
- `self:limb list` 는 폐기·만료 키까지 전부, `limbs` 와 `items` 로 두 번 싣는다(대상 1건을 찾으려고 13건×2).
- 원장에 `expired` 상태가 있다(가이드 상태 목록에 없음).
- 요청ID 없는 직접 `write`·`read`·`list` 는 재부탁 때 다시 실행된다 — 훈련자는 스크립트를 파일 보내기로, 목록·검사 결과를 작업 출력으로 받아 전부 요청ID 아래에 뒀다.
