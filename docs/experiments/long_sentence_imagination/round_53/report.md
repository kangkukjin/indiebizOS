## 2. 발견

### ★★ L53-1 — 법령 검색 결과로는 전문을 조회할 수 없다: `items` 에 번호가 없고, 보이는 번호는 틀린 번호다
가이드의 길은 "검색 → 법령 ID 확보 → `id` 로 전문" 이다. 실제:
- 검색 `items` 의 칸은 `title·meta·summary·url·date` 뿐. 번호 칸이 없다.
- `url` 에 보이는 번호(`MST=276291`, 법령일련번호)를 `id` 로 넣으면 **`success:true` 에 `{Law:"일치하는 법령이 없습니다. 법령명을 확인하여 주십시오."}`**.
- 통하는 번호는 `법령ID`(예 `001248`)인데 `message`(원천 JSON 을 글로 통째 넣은 칸) 안에만 있다. JSON 글을 값으로 바꾸는 내장이 없어 훈련자는 `split` 으로 잘랐다(`split(split($hit[0],"\"법령ID\": \"")[1],"\"")[0]`).
- 판례는 반대로 `url` 의 `ID=` 번호가 통한다. 같은 낱말 안에서 두 대상의 길이 다르다.
- 독립 AI 도 같은 자리에서 멈췄다: 세 번째 호출 뒤 패키지 폴더를 열어 `MST|ID=|JO|section|search=` 를 grep 했고, 번호 추출은 Python 스크립트(`ids.py`)로 했다.
- 증거: `evidence/probe_legal_search.json`·`probe_law_id_mst.json`·`probe_law_shape_id.json`·`probe_civil_id.json`.
처방 후보: 검색 `items` 에 상세 조회에 바로 넣을 `id` 칸(법령=법령ID, 판례=판례일련번호)을 싣는다. 새 인자 불필요.

### ★★ L53-2 — 못 찾은 것이 성공 모양으로 오고, 반환 모양이 선언(`returns: items`)과 다르다
- 없는 번호 상세: `{success:true, Law:"일치하는 법령이 없습니다…"}`. 판례 대상이어도 키는 `Law`(`"일치하는 판례가 없습니다"`).
- 0건 검색: `success:true` 에 `items`·`count` 칸 자체가 없다(`message` 속 `totalCnt:"0"` 뿐). `$s.items` 를 그대로 읽으면 실패하므로 `?? []` 를 붙여야 한다.
- 상세의 값은 원천 키 그대로다: 법령 `{법령:{기본정보,조문:{조문단위:[…]},부칙,…}}`, 판례 `{PrecService:{판시사항,판결요지,참조조문,…}}`. 선언은 `items` 인데 `items` 가 없다. 관측 반환 필드도 검색 모양 하나뿐이다.
- 증거: `evidence/probe_bad_id.json`·`probe_guide_example.json`·`probe_prec_detail.json`.
처방 후보: 못 찾음은 실패(`NOT_FOUND`)로, 0건은 `items:[]`·`count:0` 으로. 상세 모양을 계약에 적는다.

### ★★ L53-3 — 판례는 사건명으로만 찾아진다. 가이드의 예시 질의가 0건이다
- 응답의 `section:"evtNm"` — 사건명 검색이다. 가이드에 실린 `[sense:legal]{query:"전세 사기 임차인 보호", target:"prec"}` 를 그대로 보내면 0건(성공). "임금채권 소멸시효" 0건, "임금" 1,382건, "계약갱신" 9건.
- 그래서 "이 쟁점의 판례" 를 찾는 길이 없다. 훈련자 프로그램은 사건명 낱말(모델 제안) → 대법원 상위 4건을 열어 참조조문에 그 법 이름이 있는 첫 건을 골랐다: **11건 중 4건**(변형 B 의 두 번째 표본은 5건). 붙은 4건을 읽어 보니 C10(대항력·보증금 반환)·C09(유류분)는 쟁점 언저리, C01(임금피크제 취업규칙)·C02(근로자성·영업양도)는 그 법의 다른 쟁점이다. 메모는 "참조조문에 이 법이 있는 판례" 라는 기준을 적었지만 쟁점 일치는 보증하지 못한다.
- 독립 AI 는 검색어를 건당 2~4개씩 바꿔 가며 11건 모두 붙였고, 4건(C02·C06·C08·C11)에는 "쟁점을 직접 다룬 판례는 못 찾음, 가장 가까운 것" 이라고 적었다.
처방 후보: 본문 검색(원천 API 의 검색 범위 선택)을 기존 `query` 길에서 고를 수 있게 하거나, 최소한 가이드의 "자연어 가능"·예시를 실제에 맞춘다.

### ★ L53-4 — 조문 하나를 꺼낼 길이 없다: 전문이 통째로 오고, 고르는 비용이 기본 예산을 넘는다
- 상세 조회는 법령 전문이다(민법: 조문 단위 1,337개·42만 자, 2.8초). 조 번호를 주는 인자가 없다(`jo` 는 `UNKNOWN_ARGUMENT`).
- 프로그램은 조문 단위 목록에서 번호·가지번호로 걸러 항·호를 펴야 한다. 11건·조문 32개를 고르는 데 **233,960 단계** — 기본 예산(10만)으로는 `BUDGET` 실패(메시지는 정확했고 부분 결과도 실렸다). 요청에 `budget` 을 올려 보냈다.
- 가장 비싼 줄은 조문 찾기의 `filter`(조문 단위마다 번호·가지번호 비교) 하나다.
- 독립 AI 는 이 자리를 Python(`art.py`)으로 넘었다.
처방 후보: 상세 결과를 조 단위 `items`(번호·제목·본문 글)로 싣거나, 기존 `id` 길에서 조 번호를 고를 수 있게.

### ★ L53-5 — 응답의 모든 링크와 원문에 법령정보 API 사용자 식별값이 들어 있다
`items[].url` 과 `message` 속 상세 링크가 전부 `…lawService.do?OC=<사용자 식별값>&…` 이다. 출처 링크를 메모에 붙이거나 받은 원문을 파일로 남기면 그 값이 따라간다.
- 훈련자 메모·요약·index: 0건(링크를 싣지 않았다). 독립 AI 의 메모·요약·index: 0건, 그러나 보관한 원문 `_sources/` 75개 중 38개 파일에 들어갔다.
- 이 회차의 증거도 git 에 넣기 전에 가렸다(`harness/pack.py`).
처방 후보: 응답의 링크에서 식별값을 빼거나 사람이 여는 주소(law.go.kr 의 공개 주소)로 바꾼다.

### L53-6 — `table:ai` 결과 행에서 입력 칸을 읽으면 정적 검사가 "선언된 필드가 없습니다"
설명은 "fields 생략 = 입력 필드 보존" 이고 실행도 그렇다. 정적 타입은 `schema` 에 적은 새 칸만 안다 — `$a1.items` 의 `id`·`text` 를 읽는 세 곳이 `MISSING_FIELD` 였다. `preserve_rows` 순서에 기대어 `$filled[$i].id` 로 다시 묶어 넘었다(8줄).

### 관측(번호 없음)
- **재사용**: 기본 실행의 응답은 "읽기 1·모델 2 재사용 가능, 읽기 72건 제외 — `self:mkdir` 의 쓰기 자원 미상" 이라고 알려 줬다(L41-3 과 같은 규칙, 이제 사유·위치가 응답에 있다). `mkdir` 을 빼도(v2) 메모 쓰기와 "겹치는 쓰기" 라며 법령 조회 60건이 빠졌다 — 바깥 조회에 읽기 자원 선언이 없어 파일 쓰기와 겹친다고 본다. 상담일만 바꾼 재실행은 모델 0·12초였으니 실손해는 법령을 다시 받는 약 8초다. 현행 법령은 다시 받는 편이 옳을 수도 있다.

- **말일이 휴일인 경우**: 훈련자 프로그램은 C06 을 2026-10-25(일요일)로 냈다. 독립 AI 는 민법 제157·160·161조를 원문으로 가져와 2026-10-26 으로 냈고, 양력 고정 공휴일까지 대조했다(음력·임시공휴일은 미대조라고 적음). 정답표도 이 규칙을 몰랐고 ±1일 허용에 가려졌다 — 훈련자 누락.
- 모델이 제안한 조문 32개(건당 2~3개)는 전부 그 법에 실재했다. 없는 법 이름(「임차인보호특별법」·「소상공인 임대료 동결법」)은 두 번 다 "현행 법령에 없음 + 검색에 나온 비슷한 이름" 으로 드러났다. 변형 A 의 없는 법만 주장한 건에는 모델이 실제 법(상가건물 임대차보호법)을 제안했고 그 조문이 원문으로 실렸다.
- "민법" 검색의 첫 결과는 난민법이다(이름 부분 일치). 이름이 정확히 같은 것을 골라야 한다.

## 3. 작성
