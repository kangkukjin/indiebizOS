## 3. 고정 과제와 완료 조건 (후보 A)

synthetic/ 의 runs.json·requirements.json·artifacts·checks·events_0~3.json으로 실행마다 검사 통과(validation)·실행 상태(execution)·달성(outcome)을 독립 칸으로 판정한다.

판정 규칙(계약 그대로 + 해석 고정):
1. runs: 정확한 run_id 문자열(정규화 없음). 내용 동일 중복=1회. 내용 다른 중복=충돌 → execution="충돌", 모든 판본 보존. validation도 판본 간 다르면 "충돌", 같으면 그 값.
2. 수정/재실행(parent_run 있음)은 별도 행. phase·parent_run 보존.
3. 조건(C1~C3, requirements 기준): artifact·check 파일 부재 / 조건 키 부재·비불리언 / 파일 run_id 불일치 → 미검증(모순). artifact.revision ≠ check.revision → 미검증. 같은 판본에서 값 false 또는 검수 false → 미충족. 둘 다 true → 충족. (판본 불일치는 artifact 값이 false여도 미검증 — 이 해석은 보고서에 영향 건수를 따로 적는다.)
4. outcome: 충족3=달성, 충족≥1&<3=부분 달성, 충족0&미충족≥1=미달, 그 외=미검증. execution 충돌은 outcome을 덮지 않는다.
5. events: 2400행 전부 계수. 같은 event_id 동일 내용=1회, 다른 내용=충돌(모든 판본 제외, ID 기록, 관련 run_id 전부에 귀속). kind=billable만 비용, summary 및 기타 kind는 제외(건수만).
6. observed_input/output=충돌 없는 고유 billable의 비null 성분 합, missing_*=그 성분 null인 이벤트 수. conflict_event_ids 있으면 total_input/output 모두 null. 아니면 성분별로 missing>0이면 그 total null, 아니면 observed와 같음. 토큰 null을 0으로 확정하지 않는다.
7. history 수치와 synthetic 수치는 같은 표·합계에 넣지 않는다.

**사전 예상**(실행 전 기록, 사후 수정 금지): 고유 실행 24개, 충돌 run 1~3개, artifacts/checks 부재 R03·R11·R19 → 이 셋은 outcome 미검증, 판본 불일치 조건 몇 개 존재, 이벤트 2400행 = 고유+중복+충돌+summary, 일부 run total null.
