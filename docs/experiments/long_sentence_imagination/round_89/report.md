# 89회차 — 복잡한 일의 분해·병렬 처리·부분 합류·선택 재실행

훈련 완료. 훈련자 최종 전체 IBL은 기본·조건변경·누락·복구와 파일부재 보조 시험을 달성했다.
독립 AI는 산출물·분할 실행·결과 보존을 달성했으나, 필요한 결과만의 합류와
“변경 한 건만 계산”이라는 설명은 부분 달성이다. 최초 훈련에서는 시스템 코어·도구·프롬프트를 수정하지 않았다.
사용자 후속 수리의 변경·재실행 결과는 아래 §8에 별도로 기록한다.

## 1. 과제·조건

13:22 준비 시작, 마지막 AI13:41:05 종료, 13:41:49 정지·health 확인(상한14:22).
훈련 후 증거 감사·보고·커밋 시간은 별도다. 시작/끝 제품 HEAD는 `e8dd6305`로 동일했다.
실제 이전·배포·외부 연락은 없다. 회차 프로젝트는 `L89_training`, 에이전트는
`agent_e2a414b1`, 모든 실행 요청에 `origin:training`을 명시했다.

원문·기준은 [task.md](task.md), 입력은 `seed.json`에서 복원 가능하다.

원시 요청·응답·판본·산출물은 `outputs/long_sentence_imagination/2026-10-22_89회차/`에 있다.
로컬 출력이 없어져도 최초·최종 전체 IBL, 합성 seed, 실제 AI가 작성한 프로그램,
전량 대조의 항목과 압축 증거를 이 폴더에서 검토할 수 있다.

## 2. 작성과 분해

A 자료검증, B 비용검토, C 일정검토, D 운영조건을 지역 함수로 분해했다.
`(A & D) → E 보완대상`을 한 가지로 만들고 B·C와 병렬 실행한 뒤 F 최종검토로 합류한다.
가지별 파일 소유를 분리하고 최종 state·검토서는 한 함수가 저장·재독한다.
단계별 입력·산출물·시작/종료 시각·정책을 보존하며 정책 불일치는 assert로 막는다.
사용한 작성 자료는 공개 조합 교재·명세·describe 및 기존88회차 예제다. 제품 구현 소스 열람은 없었다.

| 판본 | 최초 결과와 변경 | 분류 |
|---|---|---|
| v0 | 검사 통과 뒤 일정 함수의 `from_entries` 중복 키로 실행 실패. B/A/D/E 일부 성공 흔적 보존 | 작성 오류 |
| v1 | 분야 중복 제거를 reduce로 표현. 이전 읽기 영수증을 사용해 재실행 성공. 원래4단계와 순차/병렬 비교 | 오류 수정1주기 |
| v2 | 기대ID마다 전체 ID목록을 찾던 식을 한 번 만든 색인의 has 조회로 변경 | 비용 보완, 동작 동일 |
| v3 | 파일부재 보조 시험에서 A 읽기 실패를 명시 catch, 전량 미확인·원인 코드를 반환 | 실패경계 보완1주기 |

최초 완성 초안은 `complete_v0.ibl`, 최종은 `complete_v3.ibl`이다.
v1 비교와 v2 비용 보완 비교를 섞지 않는다. v3은 원래 전체4단계까지 다시 실행했다.
검증기의 `False`/`false` 표시 기대 실수10건은 대조기 수정으로 정정했으며 제품 실패로 세지 않았다.

훈련자 상세행·작업72개·조건별 ID·합계·정책·반환·저장·보고서·의존 시각·재사용을
독립 Python oracle로 확인해 **862항목 통과, 실패0**이다. 항목 하나가 전량 목록 대조일 수 있으며
862가 자료 행수나 pytest 개수라는 뜻은 아니다. 증거는 `trainer_verification.json`이다.
업무 조합은 IBL로 실행했고 Python은 준비·전송·대조만 맡았다.

병렬 함수 구간의 겹침을 확인했다. T2에서 E 시작13:29:13.043555는 C 종료13:29:13.045570보다
약2ms 빠르고 A/D 뒤였다. F는 E/B/C 모두 끝난 다음이었다. 함수 구간 겹침은 CPU 물리 동시 수행을
입증하지 않는다. 기본에서는 A가 가장 오래 걸려 E가 다른 가지보다 먼저 끝날 이유가 없었다.

보조 파일부재 시험의 v2는 읽기 NOT_FOUND를 정직하게 실패로 반환했으나 B/C만 보존하고
D/E/F까지 진행하지 못했다. v3에서는 `source_complete:false`를 유지한 채 1800건 전부를 미확인으로
표시하고 B/C/D와 최종 부분 보고를 보존했다. 파일 복구 후 A를 다시 실행하고 B/C/D를 이어 썼다.
catch 뒤 `success:true`는 프로그램 종료이지 원천 완전성이나 개통 성공이 아니다.
이 시험은 의도한 읽기 실패이며 실제 서비스를 고장 내지 않았다.

전체 훈련자 API 실제 실행26회(정밀시계 탐침1 포함): 정상24, 최초 작성 오류와 파일부재 최초시도 실패2.
`interrupted` IBL은 동기 호출이 끝난 재개 가능 실패 기록이며 실행 중 AI 티켓과 구분한다.

## 4. 순차·병렬 비용 비교

같은 함수·입력·검수·산출물 조건으로 각3회 교대 실행했다. 순차는 검토 함수 단위의 순차이며
B/C 내부의 독립 파일 읽기는 두 조건 모두 같다. 비교 묶음 동안 이 회차 AI는 종료 상태였다.
운영 OS의 다른 부하는 격리하지 않았다. 시간은 HTTP 요청부터 응답 회수까지이며 검사·작성은 제외한다.

| 작성 판본 | 순차 중앙값 | 병렬 중앙값 | 해석 |
|---|---:|---:|---|
| v1 반복 목록 검색 | 6.525초 | 6.711초 | 이 표본에서 병렬이 약2.8% 느림 |
| v2 ID색인 조회 | 2.514초 | 2.660초 | 병렬이 약5.8% 느림 |

병렬 v1→v2는 약60% 짧아졌지만 **병렬화 효과가 아니라 훈련자 프로그램의 중복 검색 제거 효과**다.
행별 결과·근거·보고 조건은 동일했다. 이 자료는 작은 로컬 파일과 계산 중심이라 병렬 이득이 없었다.
네트워크·큰 렌더·모델 호출 작업에서의 속도 개선, 전체 작성시간·총토큰 절감률로 일반화하지 않는다.
프로그램 내부 모델 호출은0이지만 작성자 모델 비용은0이 아니며 이 세션의 작성 토큰은 미측정이다.

## 5. 시스템 AI 독립 실행

분해안·IBL·정답 없이 자연어 요구와 입력·자기 출력 경로만 전달했다. 실제 실행은 ClaudeCode `opus`,
분류/배경은 `deepseek-flash`로 기록됐다(완전 모델 버전으로 추정하지 않음). AI는 네 턴 모두 자체
Python/ThreadPoolExecutor 경로를 선택했고 IBL 작성 성공으로 세지 않는다.

| 턴·에피소드 | 경과시간 | 총 입력 | 총 출력 | 결과 |
|---|---:|---:|---:|---|
| T1·5169 | 230.562초 | 771,024 | 24,154 | 독립5검토 병렬, 전체 검토서 |
| T2·5170 | 180.552초 | 698,624 | 20,732 | A/영수증 재사용, 예산초과·필수 유지 |
| T3·5171 | 151.767초 | 1,087,261 | 17,741 | D1800 현재 미확인, 비용/일정 등4결과 보존 |
| T4·5172 | 156.846초 | 909,894 | 19,011 | 복구·정책 유지, 검토완료/개통불가 구분 |

합계719.727초, 입력3,466,803·출력81,638, 캐시읽기3,033,715·캐시생성374,583.
입력/출력/캐시는 원장 칸을 따로 보고하며 캐시를 입력에 다시 더하지 않는다.
역할별 billable_usage를 합산했고 분류·의식·실행·평가·배경을 숨기지 않았다.
실행도구18·계획도구2, 평가4회 APPROVED, 압축0회, T2~T4 실행 세션 resume 관측.
훈련자와 AI는 보고서 범위·작성량이 다르므로 두 경과시간의 배율을 IBL 성능 우열로 쓰지 않는다.

독립 대조 **259항목 통과, 실패0**(`ai_verification.json`). AI는 동의 missing을 세분화해
기본을 “명시적 실패136·동의만 미확인48”, 누락을 “실패135·미확인49”로 표현했다.
이는184개 조건미충족 집합과 동일하며, 조건별 모든 ID와 현재 입력부재를 따로 대조했다.
W4-02도 JSON ready에는 포함하고 최종 답에서는 신규착수4건과 재검증1건으로 구분했다.

하지만 산출물 통과가 모든 병렬 행동의 합격은 아니다. `ai_behavior.json`의 행동2항목은 미달이다.

- **부분 합류:** T1은 C1/R이 끝나도 `ex.map`으로 독립5개 전체를 기다린 뒤 C2를 시작한다.
  실제 추가 대기는 약0.37ms였으며 큰 시간 손실은 입증하지 않았다. 큰 이질 작업에서는 불필요한 대기 경계가 된다.
- **증분 처리 설명:** T4는 상태 교체는1건이지만 `states_of`를1800행 전체에 적용하고 최종 verdict도
  전량 계산한다. “1799판정 재사용·1건만 다시 판정”을 계산량 절감의 증거로 인정하지 않는다.
  실행된 소스와 입력에 근거한 판단이며 별도 함수 호출 추적기를 달지는 않았다.

실제 AI 코드4개를 `ai_T*_observed.py`로 보존했다. T1~T3의33파일은 끝까지 해시가 동일하고,
T4까지 총44파일이 남았다. 실행·계획도구 전문과 보존 스크립트에서는 금지된 정답/훈련자 접근이나
지정 출력 밖 쓰기가 관측되지 않았다. OS격리 보증은 아니다. AI의 이전 원천 원본 사본은 없고
해시·판정으로 연결했으므로 이전 입력의 바이트 보존 성공으로 세지 않는다(훈련 운영자는 별도 사본 보유).

필요했던 비용은 최신 파일 해시 대조, 전량 기준 확인, 실패·미확인의 구분, 조건별 근거,
저장 재독과 독립 oracle다. 이 검수나 출처를 제거해 절감하지 않는다.
AI의 본 계산 구간은 턴별 약3~10ms이고 전체 턴은152~231초였다. 기록 구간에 포함되지 않은
프로그램 작성·자료 탐색·검수·보고·모델 왕복이 있으므로 스레드 수만 늘려 전체 지연이 해결된다고 보지 않는다.
T4 전량 교차검수 자체를 무조건 낭비로 보지는 않지만, 그 비용을 숨긴 “한 행만 계산” 설명은 고쳐야 한다.
T2 재실행도 수ms라 해당 중복의 큰 시간 손실은 미입증이다. 큰 비용 후보는 매 턴 재작성·전달의 반복이다.

이번 회차는 능력·행동 훈련이며 라이브 제품 수리나 관용구 등록·해마 시딩은 하지 않았다.
다음 개선은 기존 R2(부분 재개)·R4(경로/비용) 범위의 공통 계약과 작성 행동으로 검토한다.
무작정 에이전트를 늘리는 것보다 의존관계·캐시 경계·반환 계약과 실제 비용의 일치가 우선이다.

## 7. 검증 범위와 종료

훈련자862·AI산출259항목 통과와 AI행동2항목 미달을 분리한다. backend/frontend 소스 변경이 없어

## 8. 사용자 요청에 따른 공통 지침 수리

소유 위치는 병렬 실행기가 아니라 계획·작성·검수의 계약이다. 기존 `&` 실행기는 필요한 가지를
먼저 합류시킬 수 있었으며, AI가 작성한 단계 장벽과 재계산 설명이 문제였다. 새 스케줄러·어휘·
회차 전용 런타임은 만들지 않았다.

- 의식의 분해 스케치: 실제 선행 결과, 변경 영향, 재사용할 계산을 구분하고 사용자가 병렬·부분 갱신을
  요구했으면 실행 관계와 설명의 일치도 완료 기준에 넣는다.
- 실행 지침: 무관한 가지를 기다리는 장벽을 없애고, 프로그램·산출물을 재사용한다. 입력/행 지문과
  판정 규칙 버전으로 변경을 탐지한다. 스캔·판정·집계·독립 검증을 구별하며 상태 교체 수를 계산 수로 보고하지 않는다.
- 기존 최종 평가: 요청된 병렬·부분 갱신 기준의 의미를 실행 증거와 대조한다. 정당한 전체 스캔·검증은
  금지하지 않고 요청 밖 최적화도 의무로 만들지 않는다. 추가 상시 평가 호출 없음.
- 조합 가이드: `((A & D) >> E) & B & C`와 불필요한 전체 합류를 구분하는 예를 기존 작성 순서에 추가했다.

기본 실행 지침 +416자, 의식 +223자, 최종 평가 +285자. 글자 수는 토큰이 아니다.

동일 입력 바이트·동일 네 요청(경로만 치환)·동일 모델 기어를 사용한다. 원래 실행 증거는 보존했다.
