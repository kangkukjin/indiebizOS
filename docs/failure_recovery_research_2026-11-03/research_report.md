## ① 핵심 발견과 근거

### 결론

**실패 이후의 문제 해결을 ‘더 끈기 있게 실행하라’는 지침으로만 개선하기 어렵다. 기존 실행 원장에 미해결 사건과 원래 목표의 관계를 유지하고, 관측·행동 선택·재개·종결이 같은 사건을 소비하도록 연결하는 것이 우선이다.** 새 감독자나 별도 실패 DB를 도입할 근거는 확보하지 못했다.

현재 구조에는 실패 후 추가 실행, 능력 부정 검사, 반복 감지, 실행 상황 전달, 부분 수리, 영수증 재개가 이미 있다. 다만 서로 다른 신호를 본다. 마지막 호출의 실패, 동일 입력·출력의 반복, 응답의 능력 부정, 수리 단계의 영수증이 각각 진입 조건이다. 따라서 **관측을 더 했다는 사실과 장애가 해소됐다는 사실이 혼동되거나, 원래 업무가 아니라 설명·검수·수리 단계만 끝나는 틈**이 생긴다. 다음 발견은 이 일반 구조와 실제 사례를 함께 지지한다.

|---|---|---|

### 연구 기준과 범위

지정된 [anatomy](../../data/system_docs/anatomy.md), [vision의 진화 목적](../../data/system_docs/vision.md), [IBL_EVOLUTION_PURPOSE](../../docs/IBL_EVOLUTION_PURPOSE.md)를 먼저 확인했다. 기준은 같은 사용자 목표의 품질, 실제 완료 시간, 전체 모델 토큰, 새 과제로의 전이다. 언어·호출·감독의 개수가 아니라 **판단에 필요한 관측과 제어의 연결**을 본다. 기존 사용자 판정에 따라 어휘 축소·빈도별 비활성화·무조건적인 새 어휘 추가를 권고하지 않는다.

기록은 `data/world_pulse.db`를 읽기 전용 연결로 조회했다. 예비 조회 시 `episode_log` 3,159행(2026-07-29~11-03), `episode_summary` 3,988행, `trajectory_event` 719,523행이 있었다. 이 숫자는 실행 기록의 보존량이지 전체 사용자 업무 수가 아니다. 로그 보존 상한·빈 로그·훈련·재개·후처리·동시 실행이 존재한다. 현재 연구 #5803은 제외했다. 기준 표본 21건은 모두 비어 있지 않은 episode_log와 단일 run_id의 추적 사건이 있었다. 다만 로그 존재가 전체 모델 입력·모든 외부 효과의 보존을 뜻하지는 않는다.

빈도용 틀은 **직전 완결일 11월 2일의 `source=usage` 21개 실행(#5747~5767) 전체**다. 실패 단어로 뽑지 않았다. 날짜 선택은 결과를 상세 분석하기 전에 계획에 기록했다. THINK 13, EXECUTE 4, REFLEX 1, REPAIR 3이다. 주간 자동 재조사 #5752도 포함한다. `usage`는 출처 표식일 뿐 모든 요청을 사람이 직접 입력했다는 증거가 아니다.

원인 분석에는 11월 1일 승인 인계 #5663~5664와 11월 3일 수리 연속 실행을 추가했다. 이들은 **목적 표본**이고 21개 실행의 빈도에 합산하지 않았다. 원래 업무와 수리 자식·재개는 `task_id`, `source_task`, `staging_task`, 실제 대화로 연결되는 경우만 묶었다. 일자 전체를 조사했어도 전 기간의 무작위 표본은 아니며, 수리·연구 업무가 많이 포함돼 있다.

## ② 실제 사례별 원인 분석

여기서 `#번호:s숫자`는 `trajectory_event`의 episode_id와 event_seq다. 감독 파일의 `seq`는 다른 좌표이므로 혼용하지 않는다. 원문 주소는 [사건 원장](episode_audit.json)의 `store`·`input_ref`·`result_ref`로 찾는다. 원문 로그를 Git에 복제하지 않았다. 사용자 목표는 관련 요청에서 요약했고, 모델의 해석을 새 사용자 조건으로 취급하지 않았다.

### A. #5748 → #5749: 시간 초과 재시도와 입력 교정은 다른 실패다

**목표:** 지정 폰에서 요청한 곡을 재생한다. 완료 확인은 명령 접수에 그치지 않고 해당 곡의 재생 상태 확인이다.

#5748은 폰 info와 곡 검색을 한 뒤 재생했다. s65에서 “스트림 준비 시간 초과(25초)”와 원격 task_ref가 반환됐다. s68~80에서 큐를 조회해 `now_playing:null`을 확인했다. s83에서 같은 URL·audio 방식으로 다시 재생했으나 s92에서 동일 오류였다. 이후 에피소드 로그에는 `youtube_relay.md` 가이드 조회가 있고 다음 재생·진단은 없다. 대화 DB의 assistant id 5390은 “시간 초과 두 번으로 재생하지 못했다”는 최종 응답이다.

- **당시 정보·수단:** 폰 연결·지원 op, 곡 검색 결과, 실패와 큐 상태, task_ref, 가이드가 있었다. 진단에 쓸 원격 info·IBL·shell/python 능력은 명함에 있었지만, 그것이 특정 스트림 원인의 진단 성공을 보장하지 않는다.
- **달라진 것 / 그대로인 것:** 중간 큐 관측이 추가됐고 재생 인자·경로는 같았다. 첫 재시도는 일시 장애 확인이라는 합리적 해석이 가능하다. 스트림 공급·네트워크·디코더 등 원인은 구별되지 않았다.
- **종료 계기:** 정상 모델 턴 종료 기록이 있고 명시적 예산·취소 이벤트는 발견하지 못했다. 최종 호출 단위의 자료 조회와 원래 미해결 재생이 분리되지 않는 코드 구조가 후속 누락과 양립한다. 정확한 `needs_followup` 입력 배열은 별도 저장되지 않아 원인 확정은 유보한다.
- **판정:** 재생 미달성은 확인. 무익한 반복·성급한 포기는 후보이며 원인 미확인. 실패 정보는 생성·전달됐다. 모델이 전혀 정보를 못 받은 사례는 아니다.

#5749는 다른 곡 요청이므로 동일 장애의 해결 사례로 합치지 않는다. s90에서 최상위 `timeout`이 지원되지 않는다는 컴파일 오류를 받자 s98에서 그 필드를 제거했다. s105에서 재생 성공, s125에서 요청 곡의 `now_playing`과 elapsed 5초를 확인했다. **오류 위치에 맞춰 입력을 바꾸고 원래 작업으로 돌아온 성공적 교정**이다. 실제 스피커 청취까지 관측한 것은 아니다. REFLEX 경로에서도 이 교정이 가능했다.

### B. #5753·#5758: 호출 실패를 업무 실패로 승격하면 생기는 오판

#5753의 목표는 AI 동향 보고서 작성·발행이었다. 검수용 필드 오류, 결과 직렬화 오류, 원장 경로 오류가 함께 발생했다. s787·819의 원장 오류는 동일 메시지였지만 입력 경로를 바꿔 확인한 뒤 구현을 조사하는 흐름이었다. 두 번의 같은 오류만으로 무익한 반복이라고 할 수 없다. 당시 모듈 위치와 데이터 소유 루트를 혼동한 원인은 후속 [완료 수리 계획 R1](../../docs/EXECUTION_COMPLETION_REPAIR_PLAN_2026_11_03.md)에 연결되어 있으며 현재는 `get_base_path()`·workspace 기준으로 변경됐다. 이 과거 오류를 현재의 미수리 항목으로 다시 제안하지 않는다.

#5758의 목표는 동영상 내용 소개와 시스템에 참고할 점 정리였다. 영상 자막과 문서를 얻은 뒤 Bash s78은 141, s86은 grep의 1로 끝났다. 반환 내용에는 문서 근거가 이미 있었다. s104에서 `cognition.task_continuation(reason=observed_failure)`가 발생했고 이후 별도 도구 실행 없이 응답·평가로 이어졌다.

### 조사 방법과 원문 범위

웹 검색은 `sense:search`, 원문 획득은 `sense:crawl`로 수행했다. 검색어는 실패 복구·외부 피드백·self-correction/Reflexion, OpenHands stuck loop, 도움 요청/KnowNo의 세 묶음이었다. 원 논문, 저자 페이지, 공식 문서, 공개 구현을 우선하고 내부 사례와 직접 연결되는 자료를 확장했다. 완전한 체계적 문헌고찰이나 2026년 연구 전수조사는 아니다.

### 종합 적용 판단

외부 근거는 세 종류로 나뉜다. **도구·환경·검사에 기대는 교정**, **외부 정보 없는 답변 수정**, **실행 제어와 상태 보존**이다. 앞의 두 가지를 같은 ‘자기반성’으로 묶으면 추가 모델 호출이 원인 해결을 대신하게 된다. 세 번째는 모델 지능과 별개로 올바르게 연결해야 하는 프로그램 책임이다.

실패 경험을 기억한다고 다음 행동이 저절로 좋아지지 않는다. 오류 원인 가설과 검증된 해결은 다른 등급으로 남겨야 하고, 적용 조건·도구 판본이 바뀌면 다시 확인해야 한다. 공개 구현도 문서의 존재·코드 구현·실행 연결·효과 검증을 구분해야 한다는 점에서 내부 연구와 같은 기준을 적용했다.

주요 소스는 [sources.json](sources.json)의 파일 SHA-256으로 고정했다. `model.input`은 크기·shape만 남기는 경로가 있으므로 당시 전체 프롬프트를 복원했다고 주장하지 않는다. 해당 tool_result 원문과 에피소드 로그를 통해 전달 사실을 보강했지만, 모델의 내부 이해를 관측할 수는 없다.

### 남아 있는 공통 공백

1. **호출 성공과 장애 해소의 관계가 약하다.** 추가 관측·도움말 조회의 성공은 실패한 작업의 해결이 아니다. 감독 issues는 있으나 최종 후속 판단은 별도의 마지막 호출 규칙을 쓴다. 이 틈이 우선 개선 대상이다.
2. **실패 신호의 뜻이 소비자마다 달라진다.** 오류 봉투·내부 source_failures·셸 종료·검사 거절·미확인 효과를 한 Bool로 요약하면 오탐·누락이 생긴다. 생산자 신호를 지우지 않고 업무에 미치는 영향을 별도로 붙여야 한다.
3. **관측의 변화와 진전이 다르다.** 새 해시나 다른 문구, 새 조회의 성공이 원래 완료 조건에 기여했는지 현재 cycle 비교만으로 알 수 없다. 반대로 동일 status는 정상 대기일 수 있다.
4. **부분 제어의 신원 연결이 핵심이다.** 원래 task, 사본, 후보 지문, 수리 단계, 활성 세대와 효과 영수증이 한 경로에서 일치해야 한다. 이미 수정된 재개 경로를 별도 구현으로 다시 만들지 않는다.
5. **비용·종료 원인의 관측을 목표 단위로 묶어야 한다.** `run.ended.total_ms`만으로 종료 주체를 판정할 수 없다. 취소 이후 늦게 도착한 결과와 postprocess 비용도 같은 작업의 기록이다.

## ⑤ 권고 설계와 단계별 구현 순서·인수 조건

### 설계의 중심: 미해결 사건을 유지하되 계속 실행을 강요하지 않는다

원래 요청·명시적 완료 조건은 기존 요청/criteria 참조로 고정한다. 작업 중 바꿀 수 있는 것은 **그 조건에 도달하는 방법과 관측 범위**다. 실제 차단·사용자 결정·취소·예산 종료는 정상적인 제어 결과이며 완료 성공과 별도로 남긴다.

현재 `Situation`과 TurnStore의 사건·근거 참조를 이용해 다음 네 관계를 보존한다.

- 무엇이 막혔는가: 실패한 호출·대상·의존 단계와 남은 사용자 조건.
- 무엇을 알고 있는가: 원천 오류·부분 결과·효과 영수증·확인 시각·판본. 해석은 관측과 구별한다.
- 다음 시도는 무엇을 바꾸거나 구별하는가: 수정 입력, 원인 가설을 가를 관측, 다른 의존 경로, 필요한 사용자 답.
- 무엇으로 해소·보류·중단을 확인하는가: 대응하는 결과·상태 영수증 또는 실제 제약과 종료 주체.

이는 새 과제 관리 DB가 아니다. 일반 대화의 자동 과제 원장 제거 결정을 되돌리지 않는다. 기본 수명은 기존 실행 턴이며, 이미 지원되는 수리·연구 인계에서만 현재 스냅샷의 참조를 계승한다. 일반 세션의 자동 무한 재개는 추가하지 않는다.

같은 호출이더라도 전제 조건·시간·상태가 바뀌면 새로운 시도다. 서로 다른 도구라도 “실행되지 않은 요청을 이미 실행됐다고 가정”하거나 “다른 경로도 같은 자격이 필요”하면 같은 실패를 되풀이할 수 있다. 이 의미 관계는 결과 문자열 해시만으로 확정할 수 없다.

**무진전 판정은 이중 경계로 둔다.** 기존 결정론 검사는 동일/교대 패턴·동일 오류군·같은 차단 단계를 후보로 찾는다. 기존 실행자나 이미 활성인 감독만 다음 선택을 판단한다. 후보 신호만으로 중단하거나 새 모델을 호출하지 않는다. 대기 중 task_ref가 살아 있으면 기한·진척 관측에 따른 polling으로, 끝난 실패이면 진단·방법 변경으로 보낸다. 무익성의 근거가 없는 경우 ‘반복 관측’만 전달한다.

### 짧은 선택 기록의 계약

장문의 반성문·내부 사고 전문은 저장하지 않는다. 기존 진행/관측 이벤트에 필요한 때만 다음 정도를 연결한다. 아래는 **새 어휘가 아니라 내부 사건 필드의 설계 예시**다.

```json

  "request_ref": "기존 요청 주소",
  "remaining": ["기존 완료 조건의 미충족 항목"],
  "incident_ref": "실패 호출/현재 단계 주소",
  "observation_refs": ["원문·상태·효과 영수증"],
  "next_action": "inspect",
  "purpose": "전송 실패와 작업 계속 실행을 구별",
  "branches": {
    "running": "같은 접수증을 대기",
    "failed_before_effect": "실패한 입력만 수정",
    "effect_unknown": "대상 상태를 확인하고 재전송 보류"
  },

}
```

모든 필드를 매 호출에 요구하지 않는다. 기존 상태·참조를 재사용하고 장애 후 행동을 바꾸거나 종료할 때만 delta를 남긴다. 자유로운 purpose 문장은 **모델의 선택 주장**이며 시스템이 관측한 사실로 승격하지 않는다. branches도 실행 권한을 부여하지 않는다. 후속 관측이 실제 분기를 지지했는지 비교할 수 있어야 한다.

기존 `tool.finished`를 생산 사실의 정본, Situation을 관측 투영, 감독의 issues를 판단 대기 상태로 둔다. 같은 사건에 대해 독립 원장 세 개를 생성하지 않는다. 현재 의미 관계가 없으면 `unknown`으로 남기고 실행자가 기존 출력 경계에서 짧게 판단한다. 추가 구조 필드를 도입할 경우 기존 이벤트의 선택 메타데이터로 설계하고 이전 소비자는 무시할 수 있게 한다. 별도 필수 프로토콜·매번 모델 호출을 만들지 않는다.

기존 프롬프트의 보강이 필요하다면 위 계약을 설명하는 짧은 문장으로 중복 내용을 교체하는 정도가 적절하다. 데이터 전달과 실행 제어를 고치기 전에 “끝까지 하라”를 추가하면 동일 실패의 비용만 늘 수 있다. 그렇다고 일반 능력 설계를 과거 성능 실험 완료 때까지 미룰 필요는 없다. 계약·구현의 인수와 관측된 성능 개선 주장을 분리한다.

## ⑥ 검증 계획과 아직 확인하지 못한 가설

### 비교 설계

과거 사례는 회귀용 설계 자료로만 사용한다. **새 목표·새 자료·다른 실패 원인 조합**의 보류 세트를 만든다. 폰 재생의 곡명 변경, 같은 수리 로그의 문구 변경은 새 과제로 세지 않는다. 예를 들어 문서 변환, 통계 집계, 읽기 전용 원격 검색, 모의 재고 동기화, 제한된 패키지 테스트 등 서로 다른 업무를 배치한다. 실제 발송·결제·운영 설정은 모의 endpoint로 대체하고 부작용을 확인할 외부 oracle을 둔다.

비교군은 A 현행 고정 판본, B 같은 판본에 프롬프트만 보강한 후보, C P1~P3의 최소 연결 변경이다. 모델·reasoning 설정·tool schema·권한·초기 파일·환경·오류 발생 순서·총토큰/시간 상한을 맞춘다. 필요할 때 C에서 P1 또는 P3를 제거해 기여를 구별하되 처음부터 모든 조합을 전수 실행하지 않는다. 실패 스크립트의 실제 상태 전이와 oracle이 정상 작동하는지 모델 투입 전 확인한다.

설계 예비안은 아래 7조건마다 2개의 독립 새 과제, A/C 2군, 각각 2회 반복으로 **56실행**이다. 이는 변동성과 측정 비용을 알아보기 위한 pilot이며 우월성을 확정할 표본수가 아니다. B 및 구성요소 제거는 질문을 가를 대표 조건에서 진행한다. 본 비교의 과제·반복 수는 pilot의 변동성과 사전 결정한 최소 효과로 산정하고, 비교 전 고정한다. 과제 간 반복은 독립 표본처럼 세지 않으며 과제 단위 cluster bootstrap 또는 짝지은 결과 차이의 불확실성을 보고한다. 추가 표본 결정과 중단 규칙을 사전 등록해 유리한 결과에서만 멈추지 않는다.

### 실패 조건과 관측할 결과

| 조건 | 모델에게 정답을 알려주지 않는 시험 구성 | 반드시 구별할 결과 |
|---|---|---|
| 정상 작업 | 정상 데이터·성공 도구와 충분한 정보. 합리적인 빈 검색 결과 포함 | 목표 완료, 불필요한 추가 진단·반성·도움 요청 0을 지향. 정상 0건을 장애로 세지 않음 |
| 복구 가능한 실패 | 잘못된 인자 위치·새 반환 형태·명확한 오류 정보. 허용된 다른 경로 존재 | 오류가 지목한 경계 수정 또는 대안 실행, 결과 확인. 도움말 조회 성공으로 장애 해소를 표시하지 않음 |

| 잘못된 성공 신호 | 도구는 success지만 잘못된 파일·빈 산출물·틀린 버전 반환. 검사는 일부만 통과 | 접수·실행·효과·목표를 구별. 실제 산출물·목표 oracle로 실패 탐지. 불필요한 전수 재실행 금지 |
| 정보·권한 부족 | 사용자만 아는 대상/선호, 명시 승인 필요, 실제 권한 거절. 이미 승인된 사례도 쌍으로 제공 | 정확한 질문·권한 요청과 답 후 복귀. 답과 무관한 작업 수행. 재승인 요구·허위 권한 부재·우회 시도 분리 |

각 조건을 THINK/EXECUTE/REFLEX와 제공자별 지원 경계 중 관련 경로에 배치한다. 모든 조합이 의미 있는 것은 아니므로 경로별 coverage와 미실험 경로를 보고한다. 실패 뒤 정상 조회, 병렬 부분 실패, 보충 증거의 형식 오류, 부모 수리 복귀, 취소·다른 사용자 요청 도착, 같은 상태 polling을 교차 조건으로 포함한다. 단순 text tool만으로 성공하면 이미지·오디오·기기 상태의 일반 복구까지 검증했다고 하지 않는다.

| 정상 작업 부담 | 정상군의 품질·모델 호출·시간·토큰 차이 | 실패군 평균 이득이 정상군 퇴행이나 한 경로의 큰 악화를 가리지 않게 분리 |
| 효과 보존·복귀 | 완료 쓰기 중복, stale 결과 재사용, 잘못된 후보 적용, 수리 뒤 원목표 복귀 | 설명의 타당성 승인과 목표 완료를 분리. 효과 불명에서 재전송한 사례 별도 |

후속의 짧은 선택 기록과 실제 행동이 다르면 기록보다 행동을 채점한다. 무익한 반복·조기 종료·도움 요청의 의미 분류는 두 명의 독립 검토 후 불일치를 조정하는 방식을 제안한다. 내부 사고 기록 없이 도구 인자·결과·상태·짧은 선택 이유만 쓴다.

### 채택·인수 기준 제안

다음 수치는 **향후 실험의 협의 가능한 제안값**이며 현재 운영 완료 기준이나 이번 연구의 합격 조건을 변경하지 않는다.

1. 계약 인수: 잘린 원문·부분 실패·취소·효과 불명·판본 변경·수리 단계 충돌 시험에서 정보·권한·완료 효과 보존. 모의 비멱등 외부 쓰기의 중복은 0건이어야 한다. 발견한 중복은 평균 성공률과 상쇄하지 않는다.
2. 성능 인수: 복구 가능한 과제의 목표 달성이 기준선보다 개선되고, 정상군 품질은 사전 설정한 비열등 한계를 만족해야 한다. 초기 후보 한계는 성공률 2%p, 정규화 품질 0.02 이하의 악화다. 표본이 그 한계를 판정할 만큼 충분하지 않으면 ‘동등’이 아니라 미확정이다.
3. 비용 인수: 같은 예산 비교에서 개선을 확인하고, 실제 종료 정책 비교에서도 정상군 시간·전체 토큰의 중앙값 및 p90 증가를 각각 5% 이내로 관리하는 것을 초기 목표로 둔다. 측정 변동·과제 중요도로 조정하되 결과를 본 뒤 한계를 바꾸지 않는다.
4. 실패군의 완료 이익·정당한 중단·비용을 함께 제시한다. 목표 달성이 늘어도 시간·토큰이 늘면 **능력 개선과 비용 상충**이라고 보고한다. 품질을 유지하면서 시간과 토큰이 함께 감소해야 상위 진화 목적의 비용 개선까지 입증했다고 한다.
5. 충분한 정상 대조군 없이 실패 사례만 잘 처리하거나, 더 많은 예산으로 겨우 끝낸 것을 일반 개선으로 채택하지 않는다. 새 과제 전이·과제별 회귀와 예산 도달률을 함께 본다.
