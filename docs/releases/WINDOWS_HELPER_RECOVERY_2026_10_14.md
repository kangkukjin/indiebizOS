# Windows 헬퍼 연결 복구 보강 — 2026-10-14

중앙 기록만으로 사용자가 말한 끊김의 직접 원인을 확정하지는 못했다. 조사 시 tv1과
KHJoffice는 서로 다른 구형 헬퍼를 사용 중이었고 오프라인이었다. 네트워크 실패는
기존 헬퍼가 재접속하지만, Windows의 로그인 자동 실행은 헬퍼가 비정상 종료된 뒤
다시 띄우지 않는다. macOS의 launchd·Linux의 systemd와 달리 복구 주체가 빠진 부분을 고쳤다.

## 변경

- 설치된 Windows 실행파일은 별도 부모 프로세스가 실제 작업 프로세스를 시작하고 종료를 기다린다.
  부모는 실제 프로세스 종료에만 반응한다. 통신 지연만으로 작업 프로세스를 강제 종료하지 않는다.
- 비정상 종료는 5·10·15·20초 대기 후 재시작한다. 1분 미만의 연속 실패 5회에서는 멈추고
  기록을 남긴다. 1분 이상 살아 있었으면 연속 실패 횟수를 초기화한다.
- 설치별 Windows 커널 잠금으로 부모 중복 실행을 막는다. 정상 종료·제거·재등록은 되살리지 않는다.
- 교체 중인 옛 부모는 업데이트 감시자에게 넘기고, 새 판의 부모는 새 작업자를 실행해 교체 확인을
  보낼 수 있게 한다. 업데이트 프로세스가 물려받은 환경변수만으로 감시를 건너뛰지 않는다.
- 작업자가 죽은 뒤 미확인 작업은 기존 원장의 `unknown` 처리를 따른다. 부작용 작업을 자동 재실행하지 않는다.
- 설치 폴더의 `recovery.json`·`recovery-last-exit.json`에 상태·종료 코드와 최근 오류를 남긴다.
  출력은 8 KiB까지이고 잘림을 표시한다. 등록 키는 출력에서 가린다.
- 새 작업자의 접속 능력에 `process_recovery:true`를 포함한다. OS 서비스나 관리자 권한을 새로 요구하지 않는다.

## 사용

중앙 `helper/dist`에 새 Windows 실행파일 2개를 준비했다. 연결된 Windows PC는 조종실 →
손발(USB) → 해당 PC → **헬퍼 교체**로 바꾼다. 새 헬퍼로 연결되면 **헬퍼 최신**이 된다.
오프라인이면 그 PC에서 설치된 헬퍼를 한 번 실행해 연결한 뒤 교체한다.
그 방법이 불가능하면 기존 등록 USB 폴더의 Windows 실행파일을 새 GUI 판으로 바꾸고
기존 `indiebiz-helper.json`을 유지한 채 실행해 기존 설치를 교체한다.

보관 ZIP: `outputs/windows-helper-recovery-2026-10-14.zip`.
`indiebiz-helper-win-resident.exe`는 창 없는 상주/USB 교체용, `indiebiz-helper-win.exe`는
콘솔형이다. 등록 설정은 ZIP에 넣지 않았다. Windows 등록 정보·전원 설정·현재 실행 중
헬퍼는 이번 준비 작업에서 변경하지 않았다. 직전 중앙 배포본은
`data/_backups/2026-10-14_windows_helper_before_recovery/`에 보존한다.

## 확인 범위

공통 복구 상태 기계의 비정상 종료·정상 종료·연속 실패·업데이트 인계·제거·재등록·
환경 상속·느린 연결 중 생존 및 실제 자식 프로세스 진단을 회귀시험으로 확인한다.
Windows 실행파일과 Windows 전용 커널 잠금/레지스트리 시험은 교차 컴파일한다.
**Windows 실기기에서의 새 프로세스 감시·업데이트·재연결은 아직 검증하지 않았다.**
절전·로그아웃·인터넷 단절, 살아 있지만 멈춘 프로세스, 감시 부모 자체의 종료는 이 수정의
자동 복구 대상이 아니다. 새 판을 설치한 뒤에도 끊기면 로컬 복구 기록과 전원·네트워크 상태를 함께 확인해야 한다.

검증 결과: macOS에서 Go 전체 시험 `go test -race -count=1 ./...` 통과(22.911초).
관련 Python 검사 55개 통과. Windows 전용 시험 실행파일의 교차 컴파일 통과,
배포 실행파일 2개의 PE amd64 및 GUI/콘솔 subsystem 확인. Windows 실기기 실행과
이번 개선의 장시간 연결 유지율은 미검증이다. 실제 PC에 교체 명령은 보내지 않았다.
