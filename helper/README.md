# indiebiz-helper — USB·상주 PC 헬퍼

USB 로 낯선 PC 에 꽂아 실행하는 **얇은 손발**(Go 실행파일; Linux 화면 공유 구성요소는 설치 과정에서 준비).
두뇌가 아니다 — 옆의 `indiebiz-helper.json` 에서 내 몸(허브) 주소와 limb key 를 읽어 허브에
아웃바운드로 붙고, 허브가 내려보내는 셸/파일 명령을 그 PC 에서 실행해 결과를 돌려준다.

## 빌드 (macOS에서 Go·Xcode Command Line Tools 필요)

```bash
cd helper && ./build.sh
```

산출물: `dist/indiebiz-helper-win.exe`, `-mac-arm64`, `-mac-amd64`, `-linux`.
발급기(`[self:limb]{op:issue, os:...}`)가 대상 OS 실행파일을 USB 페이로드에 동봉한다.

## 실행 (그 PC 에서)

`indiebiz-helper.json` 과 실행파일을 같은 폴더에 두고 실행파일을 더블클릭.

```json
{ "base": "https://mac.example.ts.net", "key": "limb_…", "alias": "사무실PC" }
```

- `base` 내 몸(허브)의 공개 주소 — `/limb/*` 가 백엔드에 직접 닿는 direct host.
- `key` limb key (허브 비밀번호 아님. 이 손발 하나만 인가).
- 휴대 모드는 유효한 키로 자동 연결한다. 상주 등록은 아래의 별도 설치 화면을 사용한다.
- 창을 닫으면 손발이 떨어진다.

## 프로토콜

| 방향 | 엔드포인트 | 내용 |
|------|-----------|------|
| 접속 | `POST {base}/limb/connect` | `{key, host}` → 등록·승인상태 |
| 하행 | `POST {base}/limb/poll` | `{key, wait}` 롱폴 → 셸 봉투 jobs |
| 상행 | `POST {base}/limb/result` | `{key, job_id, result}` |

셸 봉투 op: `shell`(cmd/cwd/timeout) · `read`(path) · `write`(path/content) · `list`(path) · `info`.
휴대 모드는 화면 캡처·입력도 지원한다. 상주 모드의 화면 작업은 `mode:interactive`가 필요하다.


## 회원 모드 (2026-09-14)

설정에 `"mode":"member"`를 넣는다. 기존 `limb` 모드는 변하지 않는다. neighbor_id로 발급한 키의 설정에는
회원 모드가 자동으로 들어가며, 서버도 회원 키의 구형 모드 접속을 거절한다. 접속 승인과 별도로 파일 쓰기·
명령·프로그램·장기기억 저장은 **회원의 로컬 화면에서 승인**한다. 위의 옛 승인 대기 설명과 달리 현재 유효한
일반 손발 키는 접속 시 자동 승인된다(명령 목적지 이름과 키 폐기로 관리).

회원 화면은 127.0.0.1 임의 포트에서 열린다. 설정 키는 브라우저에 보내지 않고 loopback 한시 토큰을 쓴다.
`data_dir`를 지정하지 않으면 사용자 설정 폴더/IndieBizMember/허브·키 해시 아래 member.db를 만든다.
동일 별칭의 다른 회원이 SQLite를 공유하지 않는다. 파일·기억·작업 원장은 회원 기기에만 쓴다.
`auto_allow`는 로컬 설정의 작업 op 목록이며 기본값은 비어 있다. 테스트의 자동 허용을 실사용 설정으로 복사하지 않는다.

재시도는 원래 request_key로 결과를 조회한다. 같은 키에 다른 내용은 거절한다. 실행 중 재시작은 unknown이다.
UI 결과 목록에서 미확인 작업을 확인하고, 효과를 내는 작업은 자동 반복하지 않는다.
프로그램은 list/register/run, 역할 인터프리터는 python3/bash/node다. .ibl 등록은 로컬 문장 원장에 보관한다.
resources는 프로그램 폴더 안의 자원 상대경로, dependencies는 필요한 패키지 기록이다. 실행 시 자동 설치는 없다.
화면의 기억 내보내기는 7종 내용 테이블+등록 파일+자원+의존성의 ZIP을 만든다. 작업 키/인증 키는 졸업 데이터가 아니다.
독립 설치본에서 `.venv/bin/python3 scripts/import_member_archive.py member-export.zip`로 가져온다.

검사: `go test -race ./...`, 배포 파일: `bash build.sh` (Windows amd64, macOS arm64/amd64, Linux amd64).
회원 공개 후보는 파일/문서/등록 프로그램과 라디오다. 문서의 임시 변환은 허브에서, 원본·결과는 회원 기기에 둔다.
라디오 media 봉투는 로컬 번들의 브라우저 오디오로 실행하고 실제 재생/중지/상태/볼륨 응답을 받는다.
별도 플레이어 설치는 필요 없다. 화면을 켜 두어야 하며 브라우저가 지원하는 스트림 형식에 한한다.
전달받은 media 명령은 한 번만 획득한다. 새로고침·연결 종료로 결과를 잃어도 자동 재생하지 않는다.

회원 승인 화면은 접속한 허브에서 받아 실행하지 않는다. scripts/build_member_shell.py가 공통 member_shell/launcher_app_common을
PC 바이너리와 APK의 정적 자산으로 파생한다. /m/app은 별도 웹 폴백이다. `build_member_shell.py --check`로 번들 드리프트를 검사한다.


## 상주 PC 등록 (resident-v1)

중앙 조종실 **손발 (USB) → 폴더 준비**에서 `outputs/pc-helper`를 준비한다.
폴더에는 전 OS 실행파일과 `indiebiz-helper.json`이 함께 들어 있다. 폴더 전체를 USB에
복사하고 대상 PC에서 맞는 실행파일을 실행한다. 열린 설치 화면에서 PC 이름을 정해 등록한다.
같은 USB로 여러 PC를 등록하며 이름별 파일이나 ZIP 다운로드는 필요 없다.
중앙 조종실에서 등록 목록·해제를 관리하고, **화면 공유**를 누르면 사람이 원격 데스크톱을 직접 조작한다. 중앙 AI에게 PC 이름으로 작업을 요청하는 경로도 함께 쓴다.
USB 등록 키는 등록 전용이며 각 설치에 별도 실행 자격을 발급한다. USB 분실 시 조종실의
등록 키 폐기로 새 등록만 차단할 수 있다. 이미 등록된 PC는 독립적으로 유지된다.

- macOS: 사용자 LaunchAgent. macOS 12는 `mac-arm64`(Apple Silicon) 또는 `mac-amd64`(Intel).
  `mac-amd64-legacy`는 10.15~11용 별도 빌드다. 실제 OS 지원 판정은 실기기 시험을 거친다.
- Windows: 콘솔 창이 없는 `win.exe`(공용 폴더에 GUI-subsystem 빌드를 복사)와 현재 사용자의 로그인 자동 실행(HKCU Run, 기존 예약 작업 설치는 유지). Linux: systemd 사용자 서비스.

Windows의 내부 점검·셸·화면 캡처/입력·작업 취소는 콘솔 창 없이 실행한다.
미디어 장치/인코더의 주기적 조회도 같은 `backgroundCommandContext` 경로를 사용한다.
명시적으로 여는 앱·영상 창과 OS 권한/관리자 승인 창은 별도 경로이며 이 처리로 숨기지 않는다.
이 변경은 대상 PC의 헬퍼 교체 뒤 적용된다. 오프라인 PC에 접수한 교체 작업은 재접속 뒤
실행되며, 중앙의 접수 성공과 실제 새 실행파일의 연결 확인을 구분한다.
  모두 사용자 로그인 범위다. 로그인 전 실행·관리자 권한 서비스는 설치하지 않는다.
- 프로그램·설정은 사용자 설정 폴더의 `IndieBiz/resident-…`에 복사한다. USB를 빼도 실행한다.
  설치한 실행파일을 다시 열면 로컬 관리 화면이 열린다. Linux는 systemd 사용자 세션이 필요하다.
- 손으로 갱신: 등록된 PC에서 USB 폴더의 헬퍼를 다시 실행하고 설치 화면의 버튼을 누르면, 설치된 헬퍼가
  USB와 다른 판일 때 그 프로세스를 끝내고 실행파일을 바꿔 다시 시작한다(이전 판은 `.previous`로 남긴다).
  등록·이름·작업 폴더는 그대로이고 같은 판이면 아무것도 바꾸지 않는다. 실행 중이던 작업은 `unknown`으로
  끝난다. 원격 교체를 아직 지원하지 않는 옛 헬퍼는 이 경로로 한 번 바꿔야 한다. 같은 USB 등록 키의 폴더여야 한다.
- 원격 교체: 중앙 PC의 `helper/dist`에 새 판이 있으면 조종실 손발(USB)에서 각 PC의 **헬퍼 교체**를 누른다.
  Windows·macOS·Linux 모두 같은 버튼으로 전송·검증·교체·재연결을 진행하고, 실제 새 판이 연결되면
  **헬퍼 최신**으로 표시한다. 등록·이름·설정은 유지된다. 업데이트 기능이 없는 옛 설치의 첫 갱신은 위 손 갱신을 사용한다.
  맥·리눅스는 헬퍼가 새 판을 놓고 종료하면 서비스 관리자가 다시 띄운다.
  Windows 로그인 자동 실행은 종료된 헬퍼를 다시 띄우지 않으므로, 감시자(이전 판 사본)가 옛 헬퍼가 제어
  포트를 놓은 것을 확인한 뒤 설치된 실행파일을 직접 시작한다(기존 예약 작업 설치는 `schtasks /Run`). 아직 실행되지 않았으면 재시도한다. 실행 중인 실행파일은 `.replaced`로 비켜 둔다.
  기존 Windows 로그인 작업의 사용자·활성 트리거·실행파일·인자가 현재 설치와 일치하면
  재등록하지 않는다. 매번 `/Create`하다가 권한 오류를 내는 일을 피하며, 다른 설정은 여전히
  갱신 결과를 확인한다. 권한 때문에 실제 갱신이 실패한 경고는 숨기지 않는다.
  5분 안에 확정이 없으면 감시자가 새 판 프로세스를 끝내고 이전 판을 되돌려 다시 띄운다.
- 서명·공증된 설치 패키지는 아니다. OS가 확인되지 않은 개발자로 표시하면 사용자가 해당
  실행파일의 실행을 허용해야 한다. 설치 확인이나 OS 권한을 원격에서 우회하지 않는다.
- 연결은 HTTPS/WSS 아웃바운드다. 지속 WebSocket이 막히면 HTTPS 롱폴로 돌아간다.
  중앙 주소는 `/limb/*`와 `/remote-pcs/*`를 직접 전달하는 터널 호스트여야 한다.
  기존 Cloudflare Tunnel을 사용할 수 있으며 별도 공유기 포트 개방을 요구하지 않는다.
- 기본 작업은 별도 workspace·프로세스·환경으로 실행한다. 일반 동시 작업 상한은 2개이며 info/list/read와 명시한 짧은 확인 셸(mode:observe, timeout 1~10초)은 별도 자리 1개를 쓴다. 자리별 접수 순서를 보존하며 observe는 셸의 읽기 전용 보안 보장이 아니다. 로그는 작업당
  16 MiB 이후 `log_gap`으로 알린다. CPU/메모리 하드 제한이나 OS 보안 샌드박스를 제공하는 것은
  아니다. 현재 사용자의 파일·프로그램 권한을 그대로 사용한다.
- 중앙의 작업·이벤트는 기존 작업 DB에 보존한다. 기기는 미확인 이벤트를 디스크에 저장하고
  중앙의 ACK 뒤 지운다. 실행 중 재시작은 `unknown`이며 자동으로 같은 부작용을 재실행하지 않는다.
  별도 감독 프로세스가 헬퍼의 생존 파이프를 감시하여 헬퍼가 죽어도 자식 작업을 종료한다.
- 파일 전송은 바이너리 청크·offset 재개·SHA-256 검사·대상 덮어쓰기 거절을 사용한다.
  폴더는 ZIP 등으로 묶어 전송한다. 전송은 중앙 AI의 IBL 경로로 요청한다.
- 기본 등록은 최소 헬퍼 연결을 우선한다. 미디어 설치는 기본 선택하지 않으며 등록 뒤 로컬 관리 화면에서 실행할 수 있다. 미디어 설치 실패는 등록을 취소하지 않고 누락된 ffmpeg·ffplay·mpv와 보완 방법을 표시한다. 선택 설치를 함께 요청해도 등록 완료 안내를 먼저 표시한다.
- 로그인 자동 시작 설정이 실패해도 현재 헬퍼 실행을 시도한다. 다음 로그인 때 수동 실행이 필요할 수 있다는 경고는 설치/관리 화면과 중앙의 `capabilities.installation_warnings`에 남는다. 화면 권한 안내는 헬퍼 실행 뒤 시작한다. 자격 저장·중앙 등록·실행파일 복사·프로세스 실행 실패는 여전히 설치 오류다.
- 설치 상태와 실제 재생은 같은 탐색 경로(헬퍼 데이터 `bin/`, PATH, OS별 설치 위치)를 사용한다. `capabilities.media_components`는 현재 경로·누락·보완 방법을 전달하며, ffmpeg/ffplay의 발견 경로가 바뀌면 장치 검사 캐시도 갱신한다. 관리 화면에서 재설치를 요청할 수 있고, 진행 중인 설치는 중복 실행하지 않는다.
- `media`는 mpv를 사용한다. Mac 로컬 오디오는 afplay로도 재생한다. 영상·사진은 mpv와
  `interactive` 모드가 필요하다. 로그인·오디오 장치·macOS 화면/손쉬운 사용 권한은 OS가 관리한다.
- 깨우기는 **대상 LAN에 켜진 중계 PC**의 UDP magic packet이다. 같은 집·동일 LAN을 가정하지 않는다.
  중계기는 원격지에 있어도 된다. 신호 전송 성공은 부팅·로그인·재생 준비 완료가 아니다.

등록 해제는 중앙에서 즉시 새 작업을 차단하고 `removal_pending`으로 기록한다. 기기가 연결되면
작업을 취소하고 로그를 보내며 실행파일·자동 시작·자격을 제거한다. 작업 폴더는 보존한다.
제거기는 본 프로세스와 별개이며 확인 수신 뒤 자신을 지운다(Windows는 별도 삭제 프로세스).
중앙과 통신할 수 없으면 제거 확인은 대기 상태다. 로컬 제거도 가능하며 중앙 응답 전에는
제거용 자격·미전송 로그·제거기가 남을 수 있다. USB 원본은 자동 삭제하지 않는다.

개발 검증: `go test -race ./...`, `bash build.sh`,
`python -m pytest backend/test_resident_pcs.py`(마지막 system 검사는 OS 설치 없이 임시 중앙 서버와
빌드한 네이티브 실행파일을 연결한다). 실기기 설치·제거·WOL 시험은 별도로 필요하다.

셸이 정상 종료해도 백그라운드 자식이 출력 파이프를 잡고 있으면 2초 뒤 수집을 끝내고 exit:0과 output_incomplete·warning을 돌려준다. 다시 실행하지 말고 자식 상태를 확인한다. 장기 자식은 `nohup command >server.log 2>&1 </dev/null &`로 입출력을 분리한다.


## 미디어 세션 (카메라·마이크·스피커·재생)

허브가 `op: media_session` 봉투(docs/MEDIA_SESSION_CONTRACT.md §6)를 내려보내면 헬퍼는 그 세션에만 유효한
grant 로 WS `/limb/resident/media/{sid}` 에 붙고(첫 프레임 `{key, installation_id, grant}` — grant 토큰은 이 소켓에만
실린다), 허브의 `offer` 에 pion/webrtc(v4) 로 `answer` 한다. 작업은 `desktop` 처럼 세션이 사는 동안 실행 중이며
취소 = 종료다. `keepalive` 는 `lease.keepalive_s` 마다 같은 세대·증가 순번으로, `state` 는 5초(재생은 2초)마다
`{state, path, quality}` 로 보고한다. WS 가 끊기면 `lease.reconnect_s` 안에 다시 붙고(WebRTC 는 유지), 넘기면
`signaling_unavailable` 로 끝난다. ICE 실패는 `connectivity_failed`.

캡처·출력은 **ffmpeg/ffplay 하위 프로세스**(cgo 없음)로 한다 — 카메라 → H.264(맥 `h264_videotoolbox`, 없으면
`libx264 -tune zerolatency`) · 마이크 → Opus 를 RTP 로 로컬 UDP 에 쏘고 헬퍼가 WebRTC 트랙에 싣는다. 스피커는
수신 RTP 를 로컬 UDP 로 넘기고 ffplay 가 생성된 .sdp 로 재생한다(영상 표시는 `display` 능력일 때 창). 재생(콘텐츠
전달)은 기존 `media` 와 같은 플레이어(mpv, 맥 오디오는 afplay)를 세션 범위로 띄우고 mpv IPC 로 위치·일시정지·볼륨을
실제로 읽고 `update` 프레임을 적용한다(afplay 는 상태만 대략 보고).

| OS | 카메라 입력 | 마이크 입력 | 필요한 실행파일 |
|----|------------|------------|----------------|
| macOS | `-f avfoundation` | `-f avfoundation` | ffmpeg·ffplay (`brew install ffmpeg`) |
| Windows | `-f dshow` | `-f dshow` | ffmpeg.exe·ffplay.exe (`C:\ffmpeg\bin`, winget/scoop 도 탐색) |
| Linux | `-f v4l2` | `-f pulse` | ffmpeg·ffplay (배포판 패키지), 영상 표시는 DISPLAY 필요 |

탐색 순서: 봉투 `ffmpeg_path` → 헬퍼 데이터 폴더 `bin/ffmpeg` (허브가 transfer 로 밀어 넣을 수 있다) → PATH →
OS 별 설치 위치. 없으면 능력 `media_session.ffmpeg=false` 로 신고하고 시작은 `needs_local_action{code:
ffmpeg_missing}` 으로 거절한다(카메라/마이크 장치가 없으면 `camera_missing`/`microphone_missing`). 능력
`media_session = {camera, microphone, speaker, playback, display, ffmpeg, engine:"pion/<ver>"}` 은 실행파일과
`ffmpeg -list_devices` 결과로 계산해 10분 캐시한다.

구형 인텔 맥용 legacy 빌드(Go 1.22, `-tags legacy`)는 pion/webrtc v4 가 Go 1.24 를 요구해 미디어 엔진이 없다 —
`engine:""` 으로 신고하고 봉투는 `needs_local_action{code: engine_unsupported}` 로 거절한다.
검사: `go test -race ./...` (pion 루프백·가짜 허브 WS 협상 포함; ffmpeg 가 있으면 lavfi 가짜 카메라 시험도 돈다).

## 사람용 화면 공유

조종실 → 손발 (USB) → 등록된 PC의 **화면 공유**를 누르면 별도 제어 창이 열린다.
Mac·Windows·Linux 모두 같은 버튼이다. 작업창·경로 선택·PC별 VNC 설정은 없다.
화면 공유 중에도 중앙 AI의 셸·파일 작업과 헬퍼 교체 경로는 그대로 유지된다.

- 새 헬퍼의 `desktop_stream` 능력이 필요하다. 기존 설치는 **헬퍼 교체** 후 사용한다.
- 화면은 최대 너비 1600, JPEG, 최대 15 fps다. 입력과 영상 전송을 분리하고 느린 연결에서는
  최신 프레임만 남긴다. 고해상도 동영상·게임용 스트리밍이나 오디오 전달은 제공하지 않는다.
- 현재 로그인한 그래픽 세션을 공유한다. 로그인 전 화면·Windows UAC 보안 데스크톱은
  이 사용자 헬퍼의 제어 대상이 아니다. Windows 관리자 창은 로컬 승인·조작이 필요하다.
- Mac은 번들 안의 Quartz 네이티브 워커를 쓴다. 설치 때 **IndieBiz Screen**의 화면 기록·
  손쉬운 사용을 허용한다. 보호된 폴더·외장 드라이브는 설치된 헬퍼에 전체 디스크 접근도
  허용한다. 관리자 비밀번호만으로 macOS 개인 정보 접근 권한을 대신할 수는 없다.
  일반 빌드는 ad-hoc 서명이므로 OS가 갱신 후 권한 재승인을 요구할 수 있다. 배포 서명 절차는 아래를 따른다.
- Windows는 GDI 캡처·User32 입력을 사용한다. Linux X11은 GStreamer·xdotool,
  Wayland는 RemoteDesktop 포털·PipeWire를 사용한다. Linux 구성요소가 없으면 설치 시
  pkexec 관리자 인증으로 apt/dnf/pacman 설치를 진행한다. Wayland 포털이 허용하면
  공유 승인을 복원하고, 지원하지 않으면 OS가 공유할 화면을 다시 묻는다.
- 헬퍼가 중앙의 내부망 후보에 최대 1초 동안 병렬 연결한다. 인증된 작업으로 받은
  TLS 인증서 지문을 확인한 뒤 설치 자격을 전송한다. 실패하면 기존 중앙 외부 WSS로
  연결한다. 외부 접속은 기존 중앙 터널 하나로 가능하며 PC마다 터널을 만들지 않는다.
- 생성·종료와 사람용 WebSocket은 런처 인증을 따르고, 헬퍼 WebSocket은 설치 키와
  세션의 PC를 대조한다. 양쪽 연결 종료·등록 해제·중앙 재기동 시 세션을 끝낸다.
  입력은 재전송하지 않으며 워커는 EOF에서 누른 키와 버튼을 해제한다.
- 영상·입력은 메모리에만 두며 작업 DB에는 저장하지 않는다. 별도 대화형 실행 자리를
  사용하므로 AI 작업 두 자리가 차 있어도 화면 공유를 시작할 수 있다.

## 전체 파일 접근과 관리자 명령

작업 폴더는 기본 작업 위치일 뿐 접근 제한이 아니다. `cwd`와 `path`에 절대 경로를 주면
사용자 권한으로 모든 마운트된 폴더·외장 드라이브를 사용할 수 있다. 쓰기 금지 볼륨,
잠긴 암호화 볼륨, OS 보호·개인 정보 권한은 OS의 허용·해제 과정이 필요하다.

상주 `shell`의 `elevate:true`는 macOS 관리자 인증창, Windows UAC 또는 Linux pkexec를
통해 **이번 명령만** 관리자 권한으로 실행한다. 비밀번호를 중앙 채팅·명령·환경변수에
넣지 않는다. 원격 PC의 OS 인증창에서 입력한다. 권한이 필요한 파일 작업도 해당 경로를
대상으로 하는 관리자 셸 명령으로 실행한다. 인증 전에는 명령을 전달하지 않으며, 작업 취소·
시간 초과·헬퍼 종료로 연결이 끊기면 관리자 자식 프로세스와 명령 그룹도 종료한다.

예: `[limbs:guestpc]{op:"shell",limb:"사무실PC",cmd:"id",elevate:true,background:true}`.
관리자 인증을 지원하지 않는 이전 헬퍼·휴대형·mode:observe에서는 거절한다.

### Windows 등록 화면의 autostart 오류

중앙에 이름이 생겼지만 연결 기록이 없고 등록 화면에 `autostart`가 나오면 로그인 자동 실행
설정에서 실패한 것이다. 새 설치는 관리자 승격 없이 현재 사용자의 HKCU Run에 등록한다.
기존 예약 작업 설치는 유지하며, 예약 작업 오류의 OEM 출력을 UTF-8로 변환해 표시한다.
Windows 레지스트리·실제 로그인 동작은 Windows 실기기 검증이 필요하다.
이미 중앙에서 제거를 요청한 설치는 새 USB 헬퍼로 설치를 마치면 기존 제거 요청을 처리한다.
중앙에서 제거 완료를 확인한 다음 같은 USB를 다시 실행해 이름을 등록한다. 제거 대기를
임의로 활성 상태로 되돌리지 않으며 작업 폴더는 보존한다.

## Mac 빌드와 키체인 승인

`bash helper/build.sh`는 개발용 ad-hoc 빌드다. 로그인 키체인의 개인키를 사용하지 않는다.
기존 환경변수에 인증서 이름이 있어도 실제 인증서 서명으로 자동 전환하지 않는다.

소유자가 Mac 업데이트를 요청하면 배포 실행자는
`.venv/bin/python3 scripts/release_mac_helper.py --build mac-amd64`를 실행한다.
이 명시적 배포 경로는 일반 셸에서 실행되므로 사용자가 매번 터미널을 열 필요가 없다.
`--build`는 `mac-arm64`·`mac-amd64-legacy`도 지원한다. 일반 시험과 자동 수리에서는
개인키 접근 전에 중단한다. `build.sh --sign`과 인증서 생성은 기존 대화형 경로로 남는다.

`helper/mac_signing.json`의 인증서 지문과 식별자로 화면 워커를 먼저 서명하고,
그 워커를 포함한 헬퍼를 서명한다. 두 서명 요구사항·무결성·내장 워커 바이트를 확인한 뒤
`helper/releases/<build>/<sha256>/`에 보관하고 `current.json`을 원자적으로 게시한다.
Mac의 **헬퍼 교체**는 이 검증된 배포본만 사용한다. `helper/dist/`의 개발 빌드는
업데이트 후보가 되지 않는다. 배포물이 없거나 해시·인증서가 다르면 업데이트를 제안하지 않는다.
배포 바이너리는 Git에 넣지 않으며, 다른 허브에서는 기존 인증서를 사용할 수 있는 빌드 환경에서 생성한다.

같은 소스·도구 체인의 검증된 배포본은 개인키에 다시 접근하지 않고 재사용한다.
인증서 신뢰와 개인키 접근 승인은 별개이므로 macOS가 처음 또는 정책 변경 후 승인 창을
띄울 수 있다. 거절·시간 초과 때는 게시를 중단하고 이전 배포본을 유지한다.
키체인 잠금 해제·접근 제어 완화·다른 인증서 대체·자동 재시도는 하지 않는다.
회귀시험에서는 가짜 서명 도구만 사용한다.

서명 방식이나 인증서가 달라진 첫 설치는 대상 Mac에서 기존 IndieBiz Screen 권한 항목을
− 로 지우고 + 로 다시 넣어야 할 수 있다. 화면 기록·손쉬운 사용을 대상 Mac에서 실제 확인해야 한다.
서명 시험 통과만으로 배포 완료나 권한 복구를 선언하지 않는다.

검증한 인증서 서명 교체본과 맥12의 교체 절차:
[2026-10-14 Mac 헬퍼 배포 기록](../docs/releases/MAC_HELPER_2026_10_14.md).
별도 보관본은 `outputs/mac-helper-signed-2026-10-14/`에 있다.

### Windows 비정상 종료 자동 복구

Windows 설치본은 로그인 자동 실행에 더해 별도 부모 프로세스가 실제 헬퍼를 감시한다.
예상하지 못한 종료는 5·10·15·20초 간격으로 다시 시작하며, 1분 미만의 연속 실패는
총 5회에서 멈춘다. 1분 이상 실행하면 연속 실패 횟수를 초기화한다. 정상 종료·등록 해제는
되살리지 않고, 교체 중에는 기존 업데이트 감시자에게 넘긴다. 새 교체본은 확인 응답을
보낼 수 있도록 시작한다. 설치별 Windows 커널 잠금으로 감시자가 중복 실행되지 않는다.
관리자 서비스 설치나 전원 설정 변경은 없다. macOS·Linux는 기존 OS 서비스 관리를 쓴다.

설치 폴더의 `recovery.json`에 상태·재시작 횟수, `recovery-last-exit.json`에 마지막
종료 코드·최근 오류 출력(최대 8 KiB, 잘림 표시)을 남긴다. 등록 키는 출력에서 가린다.
연결 능력의 `process_recovery:true`로 새 감시 아래 실행되는지 확인할 수 있다.
네트워크가 느리다는 이유만으로 살아 있는 헬퍼나 진행 중 작업을 죽이지 않는다.
절전·로그아웃·인터넷 단절은 별도이며, 이 변경만으로 항상 연결된다고 보증하지 않는다.
